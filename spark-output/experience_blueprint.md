# 完整体验方案：员工自助申请权限

## §0 本次关键设计判断

**判断 1：超管配置阶段采用"选择引导+分步设置"模式，在第一步就帮超管选对方向**

两种申请方式（申请角色/申请功能权限）一旦选错，后续员工侧体验全偏。配置页第一步不应只是两个选项加一段描述，而应该做成"场景匹配"——用超管看得懂的业务语言描述两种方式的适用企业画像。

- **主要影响**：配置页第一步的文案和引导结构
- **建议方案**：第一步以对比卡片形式展示两种方式，每张卡片包含适用场景、典型企业特征、推荐标注
- **不建议方案**：两个 radio 加一段说明文字，超管需要自己判断
- **关键待确认**：OA 审批预设流程的复核人节点是否去除（影响预设流程的配置复杂度）

**判断 2：员工申请入口放在"我的权限"页面右上角，而不是个人中心直接放一个"申请权限"按钮**

员工需要先了解自己有什么权限，才知道需要申请什么。查看当前权限→发现不够→发起申请，这是自然的认知链条。

- **主要影响**："我的权限"页面结构和按钮位置
- **建议方案**："我的权限"页面右上角放置"申请权限"按钮，从查看到申请的路径一步可达
- **不建议方案**：个人中心直接放两个并列入口（我的权限、申请权限），增加认知负担
- **关键待确认**：无

**判断 3：审批人收到的不是简单待办，而是一份带决策上下文的"权限申请审查卡片"**

审批决策的关键信息（申请原因、申请内容、申请人背景）必须在待办卡片中直接可见，审批人不需要点开详情才能做初步判断。

- **主要影响**：OA 审批待办的卡片设计
- **建议方案**：审批待办卡片包含申请人姓名/组织、申请类型（角色/功能权限）、申请内容摘要、申请原因
- **不建议方案**：待办只有"XXX 提交了权限申请"，点进去才看详情
- **关键待确认**：无

**判断 4：从"审批通过"到"权限已生效"之间需要明确过渡状态**

审批通过后系统自动分配权限，但这个分配过程不是瞬时的。员工需要知道"已经批了，正在生效"和"已经生效"的差别。

- **主要影响**：申请记录的状态机设计
- **建议方案**：在"已通过"和"已生效"之间增加"生效中"状态，分配完成后变为"已生效"
- **不建议方案**：审批通过直接跳到"已生效"
- **关键待确认**：权限分配的耗时范围（秒级还是分钟级），影响"生效中"状态的展示方式

## §1 旅程消费摘要

*当前未经过 Journey Analysis 深度分析，以下旅程基于 UXB 上游结论推导。*

### 角色：员工（普通用户）

| 阶段 | 目标 | 信心 | 在本蓝图中的落点 |
|------|------|------|-----------------|
| 发现入口 | 找到"我的权限"在哪里 | 低 | §6.2 我的权限页面——入口在"我的企业"下方，可发现性偏弱 |
| 查看权限 | 了解自己当前有什么权限 | 中 | §6.2 权限展示 tab |
| 发起申请 | 提交权限申请 | 低 | §6.3 申请权限抽屉——需要引导填写 |
| 等待结果 | 知道申请到了哪一步 | 中 | §7 状态反馈——申请记录状态可见 |
| 收到结果 | 知道申请是否通过、权限是否生效 | 中 | §5 异常——拒绝后有归因和下一步 |

- **信心最低点**：发现入口和发起申请，驱动 §6 加强入口引导和申请流程引导
- **关键转折**：从"查看权限"到"发起申请"，需要清晰的操作入口
- **流失风险**：审批等待期长时员工可能反复询问超管，失去自助意义

### 角色：超级管理员

| 阶段 | 目标 | 信心 | 在本蓝图中的落点 |
|------|------|------|-----------------|
| 了解模式 | 理解自助申请是什么 | 中 | §6.1 模式宣传页 |
| 选择方式 | 决定用角色还是功能权限 | 低 | §3 主流程——场景比对引导 |
| 设置范围 | 指定员工可申请的范围 | 高 | §3 主流程——选择角色/应用 |
| 配置审批 | 设置审批流程 | 中 | §3 主流程——预设审批人 |
| 启用模式 | 正式开启 | 高 | §3 主流程——确认启用 |
| 日常管理 | 编辑、关闭模式 | 高 | §4 次流程——编辑/关闭 |

- **信心最低点**：选择申请方式，驱动 §3 配置第一步的场景匹配设计
- **关键转折**：从宣传到了解配置细节，需要平滑过渡
- **流失风险**：配置流程过长或术语难懂可能导致超管放弃配置

### 角色：审批人（组织负责人）

| 阶段 | 目标 | 信心 | 在本蓝图中的落点 |
|------|------|------|-----------------|
| 收到待办 | 知道有人申请了权限 | 中 | §3 主流程——待办通知 |
| 审查决策 | 判断是否应该批准 | 中 | §3 主流程——决策上下文展示 |
| 执行审批 | 同意或拒绝 | 高 | §3 主流程——审批动作 |

- **信心最低点**：审查决策——信息不足时审批人倾向于拒绝或搁置
- **关键转折**：从待办通知到审查详情，信息连续性
- **流失风险**：决策信息不足导致审批人拖延

## §2 交互流程总览

### 路径清单

| 序号 | 路径名称 | 涉及角色 | 类型 |
|------|---------|---------|------|
| P1 | 超管配置自助申请模式 | 超管 | 主路径 |
| P2 | 员工查看我的权限并发起申请 | 员工 | 主路径 |
| P3 | 审批人处理权限申请 | 审批人 | 主路径 |
| S1 | 超管编辑已开启的模式 | 超管 | 次路径 |
| S2 | 超管关闭自助申请模式 | 超管 | 次路径 |
| S3 | 员工撤销正在审批中的申请 | 员工 | 次路径 |
| S4 | 员工查看申请记录 | 员工 | 次路径 |

### P1：超管配置自助申请模式

权限管理模式 Page（宣传页）
→ 点击 [立即启用]
→ 校验互斥模式
→ 通过 → 进入自助申请模式配置页（3 步设置）
→ 第一步：选择申请方式（角色/功能权限）
→ 第二步：设置范围（角色范围或应用范围）
→ 第三步：设置审批流程（预设/修改）
→ 点击 [启用]
→ 再次校验互斥模式
→ 通过 → Toast：开启成功
→ 个人中心增加"我的权限"入口
→ 页面刷新为已开启状态

分支：
- 互斥模式已开启 → 弹窗提示，阻止进入，引导去关闭互斥模式
- 第二步选择"部分角色/部分应用" → 打开选择弹窗

### P2：员工查看我的权限并发起申请

个人中心 → 点击"我的权限"
→ 我的权限 Page（默认功能权限 tab）
→ 浏览当前权限
→ 点击 [申请权限]
→ 打开申请权限 Drawer
→ 查看可申请的角色（或功能权限树）
→ 选择目标角色/功能
→ 输入申请原因
→ 点击 [提交申请]
→ 校验通过
→ Drawer 关闭
→ Toast：提交成功
→ 申请记录新增一条"审批中"记录

分支：
- 未选择角色/功能 → [提交申请] 置灰
- 申请原因为空 → 原因输入框提示必填
- 校验不通过（资金用户/子管理员/实名）→ Drawer 不关闭，显示对应错误提示

### P3：审批人处理权限申请

审批人收到 OA 待办
→ 点击待办
→ 打开审批详情页
→ 查看申请人、申请内容、申请原因
→ 点击 [同意] 或 [拒绝]
→ 如拒绝 → 填写拒绝理由
→ 确认提交
→ 系统自动分配权限（同意时）
→ 申请人收到结果通知

分支：
- 审批人缺失 → 系统自动按降级规则查找上级组织负责人
- 同意但分配权限失败 → 系统通知超管人工处理

## §3 主交互流程

### P1-1：超管了解自助申请模式

**用户动作**：进入权限管理模式页，看到"自助申请权限模式"卡片

**需要前置解释的信息**：该模式与其他三种模式（子管理员、双管理员互审、权限变更审批）的定位差异——自助模式是让员工发起，其他模式是管理员之间制衡

**建议文案**：
- 卡片标题：自助申请权限模式
- 卡片说明："员工可自助申请权限，工作流审批通过后，系统将自动分配权限。适合需要将权限分配压力分散到员工自服务的企业。"
- 了解更多：跳转帮助文档
- 按钮：立即启用

**下一步**：超管点击"立即启用"

---

### P1-2：互斥模式校验

**用户动作**：点击"立即启用"

**系统反馈**：校验双管理员互审模式、权限变更审批模式是否已开启

**正常流转**：未开启 → 进入自助申请模式配置页

**异常流转**：已开启 → 弹窗提示

**建议文案**（异常弹窗）：
- 标题：无法启用
- 内容："企业已开启「双管理员互审模式」（或「权限变更审批模式」），与自助申请权限模式互斥，不能同时开启。如需启用自助申请模式，请先关闭互斥模式。"
- 按钮：知道了

**下一步**：超管前往关闭互斥模式，或返回

---

### P1-3：第一步——选择申请方式

**用户动作**：在两种申请方式中选择一种

**需要前置解释的信息**：两种方式的区别不在于给员工什么，而在于超管怎么管理权限。如果企业已经建好了角色体系，选"申请角色"；如果企业习惯按应用直接给人授权，选"申请功能权限"。

**建议页面结构**：两种方式以对比卡片展示，而不是 radio 列表

卡片 A：申请角色
- 标题：员工申请角色
- 适用场景："适用于已建立角色体系的企业。员工申请某个角色后，自动获得该角色关联的所有权限。建议已启用常用角色进行授权的企业采用。"
- 流程说明：员工申请 → 审批通过 → 自动关联角色
- 推荐标签（默认）

卡片 B：申请功能权限
- 标题：员工申请功能权限
- 适用场景："适用于按应用直接授权企业的企业。员工申请某个应用的功能权限后，系统直接授权对应功能。建议常用用户直接授权的企业采用。"
- 流程说明：员工申请 → 审批通过 → 自动授权功能权限

**默认值**：申请角色（默认选中）

**按钮**：下一步

**下一步**：进入第二步（根据选择展示不同内容）

---

### P1-4a：第二步——设置角色范围（申请角色模式）

**用户动作**：选择全部角色或部分角色

**需要前置解释的信息**：这里设置的是"员工能看到哪些角色并申请"，不是给员工直接关联角色

**建议文案**：
- 提示语：请选择允许员工自助申请的角色
- 选项：全部角色、部分角色
- 默认：全部角色

**选择"部分角色"时的弹窗**：
- 标题：选择角色
- 搜索框：搜索角色名称
- 列表字段：复选框、角色名称、角色说明、角色状态（已启用/已停用）
- 分页展示
- 已选角色展示在配置页（限制展示个数，超出用"+N"折叠）
- 按钮：确认、取消

**设置项**：后续新增角色自动加入员工可申请的范围（默认开启）

**按钮**：上一步、下一步

**下一步**：进入第三步——设置审批流程

---

### P1-4b：第二步——设置应用范围（申请功能权限模式）

**用户动作**：选择全部应用或部分应用

**建议文案**：
- 提示语：请选择允许员工自助申请权限的应用
- 选项：全部应用、部分应用
- 默认：全部应用

**选择"部分应用"时的弹窗**：
- 标题：选择应用
- 搜索框：搜索应用名称
- 列表字段：复选框、应用名称、应用终端、应用启用状态
- 分页展示
- 已选应用展示在配置页（限制展示个数，超出用"+N"折叠）
- 按钮：确认、取消

**设置项**：后续新添加的应用自动加入员工可申请的范围（默认开启）

**按钮**：上一步、下一步

**下一步**：进入第三步——设置审批流程

---

### P1-5：第三步——设置审批流程

**用户动作**：查看预设审批流程，决定是否修改

**需要前置解释的信息**：预设审批人为员工所在组织的组织负责人。如果组织没有负责人，系统会自动向上查找上级组织的负责人。

**建议文案**：
- 提示："系统已预设了员工申请权限时的审批流程，预设审批人为员工所在组织的组织负责人。如需调整，可点击修改审批流程。"
- 当前审批流程摘要：显示预设流程的简要描述（审批人来源、审批层级数）

**修改审批流程**：
- 点击"修改审批流程"→ 打开表单编辑页面（子页面）
- 编辑完成后点击返回，回到配置页，页面不刷新

**按钮**：上一步、取消、启用

---

### P1-6：启用模式

**用户动作**：点击"启用"

**系统反馈**：
1. 再次校验互斥模式（防止在配置过程中互斥模式被开启）
2. 校验通过 → Toast：开启成功
3. 个人中心增加"我的权限"入口
4. 页面刷新为已开启状态

**需要前置解释的信息**：启用后员工将立即看到"我的权限"入口，可以开始查看和申请权限

**按钮**：启用、取消（返回上一页）

---

### P2-1：员工进入我的权限

**用户动作**：个人中心 → 点击"我的权限"入口

**进入条件**：企业已开启自助申请权限模式；当前用户不是服务人员

**页面默认展示**：我的权限 Page，默认选中"功能权限"tab

**系统反馈**：加载用户权限数据，按 tab 展示

**下一步**：浏览权限或点击右上角"申请权限"

---

### P2-2：员工发起权限申请

**用户动作**：点击"申请权限"按钮

**系统反馈**：打开"申请权限"Drawer

**需要前置解释的信息**：Drawer 展示的内容由超管配置决定——如果超管选了"申请角色"，Drawer 显示角色列表；如果选了"申请功能权限"，Drawer 显示功能权限树。

**建议文案**（Drawer 标题）：申请权限

**Drawer 结构**：
- 申请人：当前用户姓名（不可编辑，灰色背景）
- 申请原因：输入框，必填，placeholder"请填写申请原因"，最多 500 字
- 申请内容区域（根据超管配置动态变化）：
  - 角色方式：可勾选的角色表格（角色名称、角色说明）
  - 功能权限方式：功能权限树（与权限组件一致）
- 提示文案（功能权限方式）："提交申请后，默认申请功能的所有数据权限。如需申请部分数据权限，请联系企业管理员授权。"
- 按钮：提交、取消

**下一步**：员工选择申请内容、填写原因、点击提交

---

### P2-3：提交申请

**用户动作**：点击"提交申请"

**系统反馈**：
1. 前端校验：申请原因是否填写、是否选择了角色/功能
2. 后端校验：资金用户校验、子管理员模式校验、实名校验
3. 校验通过 → 提交 OA 审批
4. Drawer 关闭
5. Toast：提交成功
6. 申请记录新增一条"审批中"记录

**校验失败时的反馈**：
- 原因未填写 → 原因输入框下方显示 InlineError："请填写申请原因"
- 未选择角色/功能 → [提交申请] 置灰，hover 显示"请选择要申请的角色或功能"
- 资金用户校验失败 → Toast 或 Drawer 内提示："当前账号非资金用户，无法申请代发付款相关权限"
- 子管理员模式冲突 → Toast 或 Drawer 内提示："子管理员不能授予子管理员模式权限"
- 实名未通过 → Toast 或 Drawer 内提示："请先完成实名认证后再申请权限"

**下一步**：等待审批结果

---

### P3-1：审批人收到待办

**用户动作**：审批人登录系统，在 OA 待办列表中看到新的权限申请

**需要前置解释的信息**：审批待办卡片需要展示足够的决策上下文

**建议待办卡片信息**：
- 标题：权限申请 - {申请人姓名}
- 摘要：申请 {角色名称} / 申请 {应用名称} 的功能权限
- 详情：申请人组织、申请原因
- 状态：待处理

**下一步**：点击待办进入审批详情

---

### P3-2：审批人处理申请

**用户动作**：查看申请详情，决定同意或拒绝

**审批详情页展示信息**：
- 申请人信息：姓名、组织、岗位
- 申请内容：如果是角色，显示角色名称和角色说明；如果是功能权限，显示应用名称和具体功能点
- 申请原因
- 申请时间

**审批动作**：
- 点击 [同意] → 直接提交，不需要填写额外信息
- 点击 [拒绝] → 必须填写拒绝理由（必填），建议 placeholder："请说明拒绝原因，以便员工了解并调整"

**系统反馈（同意）**：
- Toast：审批已通过
- 系统开始自动分配权限
- 权限分配完成后，申请人收到通知
- 申请单状态更新为"已生效"

**系统反馈（拒绝）**：
- Toast：已拒绝
- 申请人收到通知，包含拒绝理由
- 申请单状态更新为"已拒绝"

## §4 次交互流程

### S1：超管编辑已开启的模式

**触发条件**：超管在已开启状态页点击"编辑"

**用户动作**：
1. 点击"编辑"→ 关闭模式和编辑按钮隐藏
2. 页面变为可编辑状态
3. 底部出现"取消编辑"、"确认编辑"按钮
4. 超管修改各步骤内容
5. 点击"确认编辑"

**系统反馈**：Toast：编辑成功

**需要前置解释的信息**：编辑已开启的模式不会影响已发起的在途申请，只会影响后续的新申请。

**下一步**：页面回到不可编辑状态

**异常**：配置过程中互斥模式被外部开启 → 点击"确认编辑"时校验失败，弹窗提示

---

### S2：超管关闭自助申请模式

**触发条件**：超管在已开启状态页点击"关闭模式"

**用户动作**：
1. 点击"关闭模式"
2. 弹出二次确认弹窗

**二次确认弹窗**：
- 标题：关闭模式
- 文案："关闭模式后，员工将无法自助查询和申请权限，已有权限不受影响，当前未完成的申请将继续流转。请确认是否关闭自助申请模式？"
- 按钮：不关闭、确认关闭

**用户动作**：点击"确认关闭"

**系统反馈**：
1. 校验是否有在途流程
2. 无在途流程 → 关闭成功 → Toast："关闭「自助申请权限模式」成功"
3. 有在途流程 → 关闭失败 → 弹窗提示

**关闭失败弹窗**：
- 标题：关闭失败
- 文案："当前有申请流程未完成审批，请联系审批人审批完成，再关闭模式。"
- 按钮：知道了

**需要前置解释的信息**：关闭模式后员工不能再发起新申请，但已有的权限不受影响，已发起的申请继续流转。

---

### S3：员工撤销正在审批中的申请

**触发条件**：员工在申请记录列表中，看到某条记录状态为"审批中"

**用户动作**：点击该条记录的"撤销"操作

**二次确认**：
- 标题：撤销申请
- 文案："确定要撤销该申请吗？撤销后不可恢复。"
- 按钮：取消、确认撤销

**系统反馈**：
- 申请单状态更新为"已撤销"
- Toast：已撤销
- 审批人收到通知：该申请已被申请人撤销

**不可撤销的场景**：申请状态为已通过、已拒绝、已生效、已撤销时，撤销按钮不可点击

---

### S4：员工查看申请记录

**触发条件**：员工在我的权限页面或通过其他入口进入申请记录列表

**页面结构**：
- 筛选区：申请日期（日期选择）、审批状态（下拉：全部/已通过/已拒绝/审批中/已撤销）
- 列表区：
  - 申请时间（年月日 时分秒）
  - 申请原因
  - 申请内容：角色名称，或"查看详情"链接（功能权限）
  - 审批状态：标签展示（已通过/已拒绝/审批中/已撤销）
  - 操作：撤销（仅审批中状态可点击）

**分页**：底部分页

**空状态**：暂无申请记录

## §5 异常与阻断流程

### E1：互斥模式已开启

**发生时机**：超管点击"立即启用"或"启用"时

**触发条件**：双管理员互审模式或权限变更审批模式已开启

**判断依据**：系统实时校验互斥模式的开关状态

**反馈形式**：居中弹窗

**系统反馈**：弹窗提示，阻止进入配置页或阻止启用

**用户下一步**：关闭互斥模式后重新操作

**恢复路径**：记住当前弹窗提示，关闭弹窗，前往权限管理模式关闭互斥模式，再回到自助申请。原路返回，无信息丢失。

---

### E2：审批人缺失

**发生时机**：员工提交申请后，系统查找审批人时

**触发条件**：员工所在组织的组织负责人不存在，且递归上级组织也没有负责人

**判断依据**：遍历组织链后仍找不到任何一级组织的负责人

**反馈形式**：提交申请时的 Toast

**系统反馈**（推荐降级方案——按 UXB §9 推理）：
1. 递归查找上级组织的组织负责人
2. 如果到企业顶层都没有负责人，系统将申请单标记为"待管理员处理"，通知超管手动指派审批人
3. 员工侧状态显示"审批人待指定"

**用户下一步**：员工看到"审批人待指定"后，可联系超管确认审批人

**恢复路径**：超管收到通知 → 手动指定审批人 → 申请继续流转。员工不需要重新提交。

---

### E3：审批人等于申请人

**发生时机**：系统查找审批人时

**触发条件**：员工所在组织的组织负责人就是员工本人（如部门经理给自己申请权限）

**判断依据**：审批人 ID 与申请人 ID 相同

**反馈形式**：系统自动跳过

**系统反馈**：自动递归到上级组织的负责人作为审批人。如果上级组织负责人也不存在，走 E2 流程。

**用户下一步**：无感知，系统自动处理

**恢复路径**：自动降级，无需用户干预。

---

### E4：申请校验失败

**发生时机**：员工点击"提交申请"后

**触发条件**：资金用户校验、子管理员模式校验、实名校验不通过

**判断依据**：后端依次执行校验规则

**反馈形式**：Drawer 内 InlineError 或 Toast

| 校验类型 | 触发条件 | 反馈形式 | 建议文案 |
|---------|---------|---------|---------|
| 资金用户 | 非资金用户申请代发付款 | Drawer 内提示 | "当前账号非资金用户，无法申请代发付款相关权限" |
| 子管理员模式 | 子管理员尝试授予子管理员模式权限 | Drawer 内提示 | "子管理员不能授予子管理员模式权限" |
| 实名 | 申请人未实名 | Drawer 内提示 | "请先完成实名认证后再申请权限" |

**用户下一步**：根据提示调整申请内容或完成前置条件后重新提交

**恢复路径**：Drawer 不关闭，用户修正后重新提交。已填写的信息不丢失。

---

### E5：权限分配失败

**发生时机**：审批通过后，系统自动分配权限时

**触发条件**：系统内部权限分配异常（如角色已被删除、应用已停用、系统错误）

**判断依据**：权限分配接口返回失败

**反馈形式**：系统通知超管

**系统反馈**：
1. 申请单状态更新为"已通过（权限分配失败）"
2. 通知超管："{员工姓名} 的权限申请已通过审批，但系统自动分配权限失败，请人工处理。"
3. 员工侧显示"已通过"（系统处理中），或"已通过（生效异常）"

**用户下一步**：
- 员工：联系超管确认权限分配情况
- 超管：收到通知后人工处理权限分配

**恢复路径**：超管在用户授权页手动给员工分配对应权限。

---

### E6：员工提交申请后角色/应用状态变更

**发生时机**：申请提交后、审批人处理前

**触发条件**：员工申请的角色在审批期间被超管停用，或应用被停用

**判断依据**：审批人打开审批单时系统重新校验角色/应用状态

**反馈形式**：审批时提示

**系统反馈**：
- 审批人打开审批单时看到提示："申请的角色/应用当前已停用，无法继续分配。建议拒绝此申请。"
- 审批人可选择"拒绝"并填写拒绝理由

**用户下一步**：收到拒绝通知，了解原因后重新申请可用角色

**恢复路径**：员工重新提交新的申请。

---

### E7：已停用角色申请

**发生时机**：员工查看可申请的角色列表时

**触发条件**：超管在配置角色范围时包含了"全部角色"（包括已停用的），但员工申请时只展示已启用角色

**反馈形式**：无需反馈（展示层已经过滤）

**系统反馈**：员工在申请角色 tab 中只能看到已启用的角色，已停用角色不展示。如果某个角色在员工打开申请列表后刚被停用，提交时会校验并提示。

**用户下一步**：超管重新启用该角色，或员工选择其他已启用角色

---

## §7 状态与反馈文案

### 申请单状态口径

| 状态 | 含义 | 适用对象 | 用户可操作 | 统一反馈口径 |
|------|------|---------|-----------|------------|
| 审批中 | 申请已提交，等待审批人处理 | 员工、审批人 | 员工可撤销 | "申请已提交，等待审批人处理" |
| 已通过 | 审批人已同意，等待系统分配权限 | 员工 | 无 | "审批已通过，权限正在生效中" |
| 生效中 | 系统正在分配权限 | 员工 | 无 | "权限正在生效中，请稍候" |
| 已生效 | 权限分配已完成 | 员工 | 无 | "权限已生效，可前往我的权限查看" |
| 已拒绝 | 审批人拒绝申请 | 员工 | 可重新申请 | "申请未通过：{审批人拒绝理由}" |
| 已撤销 | 员工主动撤销 | 员工 | 无 | "申请已撤销" |
| 审批人待指定 | 系统找不到审批人，待超管处理 | 员工 | 联系超管 | "审批人待指定，请联系企业管理员" |

### 关键通知文案

| 通知场景 | 通知对象 | 建议文案 |
|---------|---------|---------|
| 新申请待审批 | 审批人 | "{员工姓名} 申请了 {角色名称/功能权限}，请及时处理" |
| 申请已通过 | 员工 | "您申请的 {角色名称/功能权限} 审批已通过，权限正在生效中" |
| 权限已生效 | 员工 | "您申请的 {角色名称/功能权限} 已生效，可前往我的权限查看" |
| 申请被拒绝 | 员工 | "您申请的 {角色名称/功能权限} 未通过审批，原因：{拒绝理由}" |
| 申请被撤销 | 审批人 | "{员工姓名} 已撤销了 {角色名称/功能权限} 的申请" |
| 权限分配失败 | 超管 | "{员工姓名} 的权限申请已通过但因系统异常分配失败，请人工处理" |

| 准则 | 命中判断 | 设计落点 |

| U-02 贴近现实世界 | 员工不理解"角色"和"功能权限"术语 | §3 P1-3 申请方式选择用场景化语言 |
| U-05 错误预防与前置约束 | 互斥模式校验、资金用户校验等 | §5 E1、E4 异常流程的校验反馈 |

| U-03 用户控制与自由 | 员工可以撤销申请 | §4 S3 撤销流程 |

### 交互模式消费

| 模式 | 选择原因 | 排除原因 | 设计落点 |
|------|---------|---------|---------|
| 独立页面（配置页） | 三步配置需要完整页面空间，用户完成后不需要回到原宣传页 | 弹窗信息量不足，抽屉左右空间受限 | §6.1 配置页设计 |
| 抽屉（申请权限） | 申请操作与"我的权限"页面强相关，完成后需要回到我的权限 | 弹窗不适合展示角色列表表格，独立页面会脱离上下文 | §6.3 申请权限抽屉 |
| Tab 页签（我的权限） | 功能权限/数据权限/角色三个子视图平级，用户需要切换查看 | 各视图性质相近不应拆成独立页面 | §6.2 我的权限页面 |
| 弹窗（二次确认） | 关闭模式、撤销申请等高风险操作需要强制用户确认 | 抽屉会让确认和操作混在一起 | §4 S2、S3 |
| 同步结果分层表达 | 审批通过≠权限已生效，需要区分"已通过""生效中""已生效" | 不能把三个阶段压成一个"已通过" | §7 状态口径 |
