# 体验蓝图：员工自助权限申请

## §0 本次关键设计判断

**判断**：在现有权限管理体系中嵌入员工自助申请能力，核心设计策略是「先翻译再交互」——用统一的权限业务语言翻译层同时支撑员工查看、员工申请、管理员配置三个端面，让权限从技术对象变成员工和管理员都能理解的事。

**主要影响**：员工端需要全新的信息架构来表达「我有什么权限」和「我可以申请什么」两个概念；管理端需要在现有权限管理页面中嵌入自助申请配置，又不能和旧的权限变更审批配置混在一起；审批端需要同时兼容管理员发起的审批和员工发起的申请两条路线。

**建议方案**：先定义翻译层的表达规则（能力描述 + 范围描述 + 来源说明 + 生效状态），以此为底座分别设计员工查看页、员工申请页、管理员配置页和审批处理页。员工申请不另建审批引擎，而是复用现有审批管理的表单-流程-处理链路，仅扩展发起方为员工角色。

**不建议方案**：跳过翻译层直接做申请入口（导致选项无法理解、配置难以精准）；或把自助申请做成一个完全独立的权限子系统（导致与现有权限管理割裂，治理复杂度翻倍）。

**关键待确认**：权限业务语言翻译层的语义建模范围和命名规范需要与产品侧确认（按角色归类、按业务场景归类、还是按功能模块归类）；三个层级一的 GAP（双管理员叠加、子管理员隔离、授权写入方式）基于推荐方案推进。

## §1 旅程图

### 旅程图 1：普通员工 — 自主获取权限

**阶段 1：了解自己有什么权限**

- 用户目标：搞清楚自己当前能做什么、不能做什么
- 关键触点：工作台 → 我的权限入口 → 权限清单页
- 用户信心：低。员工通常不知道自己有什么权限、也不知道看到的权限是什么意思
- 痛点：当前没有统一的权限查看入口；即使有列表，权限以技术语言呈现，员工看不懂能力边界

**阶段 2：发现权限缺口**

- 用户目标：确认自己缺少某个操作能力，并找到对应的申请项
- 关键触点：权限清单页 → 申请权限入口 → 可申请范围列表
- 用户信心：中低。员工能感知到自己「做不了某事」，但不确定该申请什么、申请后能覆盖哪些场景
- 痛点：权限名称与实际工作任务之间的映射不直观；员工需要猜测「申请了这个能解决我的问题吗」

**阶段间过渡**：从「我缺什么」到「我去申请」，关键转折是员工在可申请列表中找到了匹配需求的选项——如果找不到，链路就断了。

**阶段 3：提交权限申请**

- 用户目标：填写申请原因并提交，期望尽快获得权限
- 关键触点：申请表单 → 申请确认 → 提交成功页
- 用户信心：中。提交动作本身简单，但员工不确定审批人会怎么判断、需要等多久
- 痛点：申请原因怎么写审批人才能理解；不知道审批通过后权限多久生效

**阶段 4：等待与追踪**

- 用户目标：知道申请走到哪了、大概什么时候有结果
- 关键触点：我的申请列表 → 申请详情页 → 审批进度
- 用户信心：中低。如果没有主动通知，员工需要反复查看
- 痛点：审批中无进度可见；长时间无响应时不知道该催谁

**阶段间过渡**：审批完成后，触发通知。如果通过，员工进入「确认权限生效」阶段；如果拒绝，员工需要知道为什么以及下一步怎么办。

**阶段 5：确认权限生效**

- 用户目标：确认申请的权限已经可以使用
- 关键触点：审批结果通知 → 我的权限页（更新后的清单）
- 用户信心：高。权限已生效，员工可以正常使用
- 痛点：如果通知只说「审批通过」但不说「什么时候生效」或「生效范围是什么」，员工可能误以为已经可以使用但其实还需要等待

### 旅程图 2：审批人 — 处理员工权限申请

**阶段 1：收到申请待办**

- 用户目标：知道有新的权限申请需要处理
- 关键触点：待办通知（站内/移动端/邮件）→ 待办列表
- 用户信心：中。能收到通知，但不一定清楚这个申请的背景
- 痛点：待办标题信息不足，审批人需要点进去才知道申请人是谁、申请了什么

**阶段 2：理解申请内容**

- 用户目标：快速判断该申请是否合理——申请了什么、为什么申请、有什么风险
- 关键触点：审批详情页（申请人信息 + 申请权限内容 + 申请原因 + 权限影响范围说明）
- 用户信心：取决于信息完整度。如果能看到申请人当前权限概览和申请权限的风险提示，信心较高
- 痛点：如果申请内容以技术语言表达，审批人可能看不懂具体影响；缺少申请人已有权限的上下文

**阶段间过渡**：审批人理解申请内容后做出判断——同意或拒绝。如果信息不足以判断，审批人可能需要联系申请人补充说明。

**阶段 3：做出审批决定**

- 用户目标：同意或拒绝，并给出清晰的理由
- 关键触点：审批操作区（同意/拒绝按钮 + 审批意见输入）
- 用户信心：高（如果前一步信息充分）；低（如果信息不足以支撑判断）
- 痛点：同意时不知道系统接下来会自动做什么；拒绝时不填意见申请人不知道原因

**阶段 4：完成审批**

- 用户目标：确认审批结果已生效，申请进入后续流程
- 关键触点：审批完成提示 → 待办列表（该条已移除）
- 用户信心：高
- 痛点：如果审批通过但后续自动授权失败，审批人不会收到通知，无法知道自己的审批决定没有落地

---

### 旅程图 3：权限管理员 — 配置自助申请

**阶段 1：评估是否开启**

- 用户目标：理解自助申请能力对企业的影响，决定是否开启
- 关键触点：权限管理 → 自助申请配置入口
- 用户信心：中。管理员需要理解开启后的影响范围和与现有模式的兼容性
- 痛点：如果开启前没有兼容性检查或影响说明，管理员可能在不完全理解的情况下做出配置

**阶段 2：配置可申请范围**

- 用户目标：定义员工可以申请哪些权限，确保范围安全且覆盖真实需求
- 关键触点：可申请范围配置页（从现有角色/功能权限中选择）
- 用户信心：中。管理员需要在「安全收敛」和「覆盖员工需求」之间找平衡
- 痛点：从技术权限结构翻译成员工能理解的申请选项——如果管理员自己也只能看到技术字段，他无法判断员工会怎么理解这些选项

**阶段间过渡**：配置完可申请范围后，必须为每个范围绑定审批流程，否则申请无法流转。

**阶段 3：配置审批流程**

- 用户目标：为每个可申请范围指定审批人和审批方式
- 关键触点：审批流程绑定页（复用现有审批引擎）
- 用户信心：中高（如果审批配置流程与现有审批管理体验一致）
- 痛点：如果同一个管理员需要分别在「权限变更审批」和「自助申请审批」两个地方维护审批配置，重复工作量大

**阶段 4：监控与调整**

- 用户目标：观察申请数据，根据需要调整配置或关闭能力
- 关键触点：申请记录查看 → 配置调整 → 关闭操作
- 用户信心：高。能看到数据就能做出判断
- 痛点：关闭时不确定在途申请会怎样；调整范围后不确定已提交的申请是否受影响

---

### 旅程图 4：超级管理员 — 控制全局开关

**阶段 1：了解能力**

- 用户目标：理解自助申请是什么、与现有权限管理的关系
- 关键触点：权限管理总览 → 自助申请模块
- 用户信心：中
- 痛点：如果没有与现有治理模式的兼容矩阵，超管无法判断开启后会不会造成冲突

**阶段 2：开启/关闭决策**

- 用户目标：做出开启或关闭的决策
- 关键触点：开关控件 + 影响说明 + 兼容性检查
- 用户信心：依赖信息呈现的完整度
- 痛点：开启前如果没有兼容性检查，可能出现治理模式冲突；关闭时如果影响说明不清晰，可能误关闭

## §2 交互流程总览

### 分角色交互流程

**普通员工 — 主路径**

```
M1-1 进入我的权限 → M1-2 查看权限清单 → M1-3 发现缺口 → M1-4 进入申请 → M1-5 选择申请项 → M1-6 填写原因 → M1-7 确认提交 → M1-8 查看申请进度 → M1-9 收到审批结果
```

**审批人 — 主路径**

```
M2-1 收到待办通知 → M2-2 进入待办列表 → M2-3 打开申请详情 → M2-4 判断申请合理性 → M2-5 同意/拒绝 → M2-6 确认审批结果
```

**权限管理员 — 主路径**

```
M3-1 进入自助申请配置 → M3-2 开启能力 → M3-3 配置可申请范围 → M3-4 为范围绑定审批流程 → M3-5 发布配置 → M3-6 查看申请数据 → M3-7 调整或关闭
```

**超级管理员 — 主路径**

```
M4-1 进入权限管理总览 → M4-2 查看自助申请状态 → M4-3 开启/关闭 → M4-4 确认兼容性
```

### 异常流程重点

- E1 审批人不存在：申请无法路由，通知申请人+管理员
- E2 自动授权失败：审批已通过但写入失败，通知双方+管理员手动补授
- E3 可申请范围为空：员工无可用申请项
- E4 管理员关闭能力时存在在途申请：保护在途，停止新申请
- E5 治理模式冲突：开启时检查到未解决兼容规则
- E6 重复提交拦截：员工已有同权限的在途或通过申请
- E7 申请已被他人处理：审批人打开时发现已处理
- E8 申请被拒后的重新申请

## §3 主交互流程

### 节点 M1-1：员工进入「我的权限」

- **用户动作**：员工从工作台或导航进入「我的权限」页面
- **系统反馈**：
  - 若自助申请能力已开启：展示权限清单页，包含「我的权限」和「申请权限」两个标签
  - 若自助申请能力已关闭：展示权限清单页，仅展示「我的权限」标签，不展示申请入口
- **需要前置解释的信息**：页面标题「我的权限」说明此处展示的是员工当前拥有的所有权限结果，以业务语言呈现
- **建议文案**：
  - 页面标题：「我的权限」
  - 标签栏：「我拥有的权限」「申请权限」（能力开启时）
- **下一步**：M1-2 查看权限清单

### 节点 M1-2：员工查看权限清单

- **用户动作**：浏览以业务语言呈现的权限清单
- **系统反馈**：
  - 展示权限卡片列表，每张卡片包含：能力描述、适用范围、权限来源、生效状态
  - 权限按业务场景分组（如「人事管理」「数据报表」「审批处理」）
  - 已生效的显示绿色标记；审批中或待生效的显示黄色标记；已失效或已拒绝的显示灰色标记
- **需要前置解释的信息**：
  - 「能力描述」是员工能做什么的业务语言表达，如「可以查看本部门所有员工的考勤记录」
  - 「权限来源」说明这个权限是怎么来的：管理员授予、某个角色自动获得、自己申请获得
  - 「生效状态」说明权限当前是否可用
- **建议文案**：
  - 空状态（员工无任何权限）：「暂未拥有任何权限。如需获取权限，请联系管理员或通过右上角申请入口提交申请。」
  - 权限来源示例：「由角色'部门考勤员'授予」「通过自助申请获得」「管理员直接授予」
- **下一步**：M1-3 发现缺口 或 M1-4 进入申请

### 节点 M1-4：员工进入申请权限

- **用户动作**：点击「申请权限」标签或入口按钮
- **系统反馈**：展示可申请范围列表，分组展示管理员已配置的权限选项
- **需要前置解释的信息**：列表中仅展示员工当前尚未拥有的权限；每个选项显示能力描述和范围，帮助员工判断是否匹配需求
- **建议文案**：
  - 页面副标题：「以下权限当前可申请，请选择你需要的权限」
  - 权限选项分组示例：「人事管理」「数据与报表」「审批相关」
- **下一步**：M1-5 选择申请项

### 节点 M1-5：员工选择申请项

- **用户动作**：从可申请列表中点击一个权限选项
- **系统反馈**：跳转至申请表单页，顶部展示所选权限的详细说明（能力描述+范围+审批通过后的影响），下方为申请表单
- **需要前置解释的信息**：「审批通过后你将获得」区域展示具体的权限变化预览——这不是申请通过后的通知，而是提交前的确认信息
- **建议文案**：
  - 权限详情区标题：「审批通过后你将获得以下能力」
  - 提示：「请确认以上权限符合你的实际工作需求」
- **下一步**：M1-6 填写原因

### 节点 M1-6：员工填写申请原因

- **用户动作**：在申请表单中填写申请原因，可选填补充说明
- **系统反馈**：
  - 申请原因输入框（必填），提示建议包含业务场景说明
  - 显示当前已选择的权限摘要，防止员工遗忘
- **需要前置解释的信息**：申请原因将直接展示给审批人，建议说明业务场景和必要性；不需要填写技术细节
- **建议文案**：
  - 输入框占位符：「请说明你需要这项权限的业务场景和原因，例如：因负责本部门月度考勤汇总，需要查看部门成员的考勤记录」
  - 提示文字：「审批人将根据你填写的原�因判断是否批准」
- **下一步**：M1-7 确认提交

### 节点 M1-7：员工确认提交

- **用户动作**：点击提交按钮
- **系统反馈**：
  - 提交前弹出确认弹窗，展示：申请权限摘要 + 审批流程预览（审批人、预计处理时间）+ 提交确认
  - 提交后跳转至提交成功页，展示申请单状态和预计后续流程
  - 若命中重复提交规则（已有同权限的在途或通过申请），阻断并提示
- **建议文案**：
  - 确认弹窗标题：「确认提交权限申请」
  - 提交成功标题：「申请已提交」
  - 提交成功正文：「你的权限申请已提交，审批人将很快处理。你可以在「我的申请」中查看进度。」
- **下一步**：M1-8 查看申请进度

### 节点 M1-8：员工查看申请进度

- **用户动作**：在「我的申请」列表查看申请状态，或在收到通知后查看结果
- **系统反馈**：
  - 申请列表展示：申请权限名称、提交时间、当前状态、审批人
  - 点击进入申请详情：完整申请信息 + 审批进度（已处理节点 + 当前节点 + 待处理节点）
  - 审批中状态：显示当前审批人和已等待时长
- **建议文案**：
  - 状态「待审批」：「审批中，当前审批人：张经理」
  - 列表空状态：「暂无申请记录」
- **下一步**：M1-9 收到审批结果

### 节点 M1-9：员工收到审批结果

- **用户动作**：查看审批结果通知，进入申请详情或我的权限页确认
- **系统反馈**：
  - 通过：通知告知已获得什么权限、何时生效、可前往哪里查看；「我的权限」页自动更新
  - 拒绝：通知告知拒绝原因和审批意见，引导员工根据原因决定是否重新申请
- **建议文案**：
  - 通过通知：「你的权限申请已通过。你已获得「查看本部门考勤记录」权限，立即生效。」
  - 拒绝通知：「你的权限申请未通过。审批意见：当前岗位暂不需要此权限，如有疑问可联系审批人。」
- **下一步**：进入「我的权限」确认 或 重新申请

---

### 节点 M3-2：管理员开启自助申请能力

- **用户动作**：管理员在自助申请配置页点击开启开关
- **系统反馈**：
  - 开启前执行兼容性检查：检查当前是否存在未解决的治理模式冲突
  - 无冲突：开关打开，能力状态变为「已开启」，展开配置区域
  - 有冲突：弹窗提示冲突内容和建议处理方式，阻止开启
- **需要前置解释的信息**：开启后员工即可看到申请入口，但此时管理员尚未配置可申请范围，员工将看到空状态——建议在配置完成前不展示给员工或展示「即将开放」状态
- **建议文案**：
  - 开关标签：「员工自助申请权限」
  - 开启成功提示：「自助申请能力已开启。请配置可申请范围和审批流程，配置完成后员工即可提交申请。」
  - 兼容性冲突弹窗：「无法开启。当前存在以下治理模式兼容问题：[具体冲突描述]。请先处理以上问题后再开启。」
- **下一步**：M3-3 配置可申请范围

### 节点 M3-3：配置可申请范围

- **用户动作**：从现有角色和功能权限中选择可作为申请项的权限
- **系统反馈**：
  - 展示可选权限池（来自现有角色管理和功能权限），支持搜索和按角色筛选
  - 已添加的权限项展示在「已配置可申请范围」列表中，每个项可编辑业务语言描述
  - 支持为每个权限项自定义「员工看到的名称和描述」
- **需要前置解释的信息**：管理员在此处配置的不是技术权限结构，而是员工将看到的申请选项——需要填写员工能理解的名称和描述
- **建议文案**：
  - 配置区标题：「可申请范围」
  - 权限项名称输入框占位符：「员工将看到的权限名称，如：查看本部门考勤记录」
  - 权限项描述输入框占位符：「说明该权限能做什么，如：可查看本部门所有员工的打卡记录、请假记录和加班记录」
- **下一步**：M3-4 绑定审批流程

### 节点 M3-4：为范围绑定审批流程

- **用户动作**：为每个可申请范围指定审批人或审批流程
- **系统反馈**：
  - 复用现有审批管理引擎：管理员可选择已有审批模板或新建审批流程
  - 每个可申请范围至少绑定一个审批流程方可保存
  - 提供预览：管理员可查看员工提交后审批将如何流转
- **建议文案**：
  - 绑定区标题：「审批流程」
  - 未绑定时提示：「请为此权限配置审批流程。审批人将负责审核员工的申请。」
- **下一步**：M3-5 发布配置

### 节点 M3-5：发布配置

- **用户动作**：管理员确认配置并发布
- **系统反馈**：
  - 发布前展示配置摘要：已配置的权限项数量 + 各自绑定的审批流程
  - 发布后员工端申请入口展示最新的可申请范围
  - 若此前能力已开启但未配置范围，员工端从空状态切换为可申请状态
- **建议文案**：
  - 发布确认：「确认发布后，员工即可看到并申请已配置的权限范围。是否确认发布？」
  - 发布成功：「配置已发布。员工现在可以在「申请权限」中看到 {N} 个可申请项。」
- **下一步**：M3-6 查看申请数据

---

### 节点 M2-3：审批人打开申请详情

- **用户动作**：从待办列表点击一条申请，进入详情页
- **系统反馈**：
  - 展示申请详情：申请人姓名/部门、申请的权限（业务语言描述+技术映射摘要）、申请原因、提交时间
  - 展示辅助判断信息：申请人当前已有权限概览、申请权限的风险提示（如涉及敏感数据）
  - 若申请已被其他审批人处理，展示当前结果并禁用操作
- **需要前置解释的信息**：审批人在此处看到的权限信息需要兼顾业务语言（理解申请内容）和技术映射（确认授权范围准确）
- **建议文案**：
  - 详情页标题：「权限申请详情」
  - 风险提示示例：「该权限包含敏感数据查看能力，请确认申请人的岗位职责需要此权限」
- **下一步**：M2-5 同意/拒绝

### 节点 M2-5：审批人做出审批决定

- **用户动作**：点击同意或拒绝，填写审批意见（拒绝时必填）
- **系统反馈**：
  - 同意：弹出确认，展示「审批通过后将自动授予以下权限：[权限摘要]」，确认后系统执行授权写入
  - 拒绝：弹出确认，要求填写拒绝原因（必填），确认后申请状态变更为已拒绝
  - 处理完成后待办列表自动更新
- **建议文案**：
  - 同意确认：「确认通过后，系统将自动为 [员工姓名] 授予 [权限名称] 权限。是否确认？」
  - 拒绝确认：「请填写拒绝原因，员工将看到你的审批意见。」
  - 拒绝原因输入框占位符：「请说明拒绝的原因，帮助员工理解为什么这次申请未被批准」
- **下一步**：M2-6 确认审批结果

## §4 次交互流程

### 次流程 S1：员工撤回待审批申请

- **触发条件**：员工在「我的申请」中对「待审批」状态的申请执行撤回操作
- **用户动作**：点击撤回按钮 → 确认撤回
- **系统反馈**：申请状态变更为「已撤回」，审批人待办中移除该条
- **建议文案**：撤回确认：「撤回后该申请将不再进入审批流程。是否确认撤回？」
- **下一步**：员工可重新编辑草稿后再次提交

### 次流程 S2：员工在被拒后重新申请

- **触发条件**：员工查看被拒申请详情，点击「重新申请」
- **用户动作**：基于原申请内容修改申请原因或权限选项后重新提交
- **系统反馈**：生成新的申请单（非原单修改），重新进入审批流程
- **需要前置解释的信息**：重新申请是一张新单，不是对原单的申诉或修改——原申请记录保留，新申请独立流转
- **建议文案**：重新申请入口：「基于此申请重新提交」
- **下一步**：新申请提交成功，进入待审批

### 次流程 S3：管理员调整已发布的配置

- **触发条件**：管理员修改已发布的可申请范围（新增/移除权限项）或修改审批流程绑定
- **用户动作**：修改配置 → 保存
- **系统反馈**：
  - 新增权限项：立即对员工可见
  - 移除权限项：员工端该选项消失，但已提交的在途申请按旧配置继续流转至结束
  - 修改审批流程：[GAP] 基于推荐方案——已提交未审批的申请按旧审批流程继续，新提交的申请按新流程路由
- **建议文案**：
  - 移除权限项确认：「移除此项后，员工将无法再申请该权限。当前已有 N 个在途申请不受影响。是否确认移除？」
- **下一步**：配置更新生效

### 次流程 S4：管理员关闭自助申请能力

- **触发条件**：管理员或超管在配置页点击关闭开关
- **用户动作**：点击关闭 → 确认关闭
- **系统反馈**：
  - 展示关闭影响说明：员工将无法看到申请入口、当前有 N 条在途申请将继续流转
  - 关闭后：员工端申请入口消失，已提交的在途申请不受影响
  - 「我的权限」页保留，仅移除申请入口
- **建议文案**：
  - 关闭确认弹窗：「关闭后，员工将无法提交新的权限申请。当前有 {N} 条在途申请将继续正常流转，不受关闭影响。确认关闭？」
  - 关闭后配置页状态：「自助申请能力已关闭。员工无法提交新申请，历史申请记录可继续查看。」
- **下一步**：能力关闭，管理员可随时重新开启

### 次流程 S5：审批人委托审批

- **触发条件**：审批人因故无法处理待办，使用委托审批功能
- **用户动作**：在审批管理设置委托（复用现有 OA 审批委托能力）
- **系统反馈**：委托生效后，被委托人可代为处理权限申请
- **下一步**：被委托人按正常审批流程处理

### 次流程 S6：员工查看权限来源详情

- **触发条件**：员工在「我的权限」中点击某条权限的来源信息
- **用户动作**：点击来源标签
- **系统反馈**：弹窗或展开区域展示该权限的详细来源信息：授予人/授予角色、授予时间、生效时间、到期时间（如有）
- **建议文案**：
  - 来源详情标题：「权限来源详情」
  - 自助申请来源示例：「通过自助申请获得，申请于 2026-06-15 提交，经张经理审批于 2026-06-16 通过，立即生效」
- **下一步**：关闭详情，返回权限清单

## §5 异常与阻断流程

### 异常 E1：审批人不存在或无效

- **发生时机**：员工提交申请后，系统路由审批时发现审批人为空或已离职
- **触发条件**：管理员配置的审批人（成员组/角色/组织架构负责人等）在申请提交时已失效
- **判断依据**：审批流程路由时校验审批人有效性，失败则阻断路由
- **反馈形式**：系统消息通知（站内 + 移动端）+ 申请状态变更为「审批异常」
- **系统反馈**：
  - 申请人看到：「你的权限申请已提交，但审批流程配置存在异常，暂时无法进入审批。管理员正在处理中。」
  - 管理员收到通知：「员工 [姓名] 的权限申请因审批人配置异常无法流转，请尽快更新审批人配置。」
  - 申请状态展示：「审批异常 — 审批流程配置问题」
- **用户下一步**：申请人等待管理员修复配置后自动恢复流转；管理员进入自助申请配置页更新审批人

### 异常 E2：自动授权写入失败

- **发生时机**：审批人同意申请后，系统执行授权写入时失败
- **触发条件**：权限写入接口异常、权限冲突、数据校验不通过等
- **判断依据**：授权写入返回失败，审批已通过但权限未写入
- **反馈形式**：弹窗（审批人侧）+ 系统消息通知（申请人+管理员）+ 申请状态变更为「授权失败」
- **系统反馈**：
  - 审批人侧（操作时）：「审批已通过，但系统自动授权时遇到问题。管理员已收到通知，将尽快处理。」
  - 申请人通知：「你的权限申请已审批通过，但授权过程中遇到技术问题。管理员正在处理，权限将在修复后自动生效。」
  - 管理员通知：「员工 [姓名] 的权限申请（审批已通过）授权写入失败，失败原因：[原因]。请前往处理。」
  - 申请状态展示：「授权失败 — 审批已通过，授权待管理员手动处理」
- **用户下一步**：管理员在后台手动完成授权操作；授权成功后申请状态自动更新为「已生效」

### 异常 E3：可申请范围为空

- **发生时机**：员工点击「申请权限」入口时
- **触发条件**：管理员尚未配置可申请范围、或管理员已移除所有配置项、或员工已拥有所有可申请权限
- **判断依据**：系统查询可申请范围列表，过滤掉员工已拥有的权限后结果为空的
- **反馈形式**：页面空状态（非弹窗）
- **系统反馈**：空状态页面展示说明和去向引导
- **建议文案**：
  - 未配置时：「暂无可申请的权限。管理员正在配置可申请范围，请稍后再试。」
  - 已全部拥有时：「你已拥有当前所有可申请的权限。如有额外需求，请联系管理员。」
- **用户下一步**：联系管理员或等待管理员新增配置

### 异常 E4：重复提交

- **发生时机**：员工尝试提交与已有在途申请相同权限的申请
- **触发条件**：员工存在一条状态为「待审批」或「已通过（已生效）」的同权限申请
- **判断依据**：提交前校验，比对申请权限项与已有申请记录
- **反馈形式**：提交阻断弹窗
- **系统反馈**：
  - 已有在途：「你已有一条相同权限的申请正在审批中，请勿重复提交。可前往「我的申请」查看进度。」
  - 已拥有：「你已拥有此权限，无需再次申请。可前往「我的权限」确认。」
- **用户下一步**：关闭弹窗，前往查看已有申请或权限

### 异常 E5：申请已被其他审批人处理

- **发生时机**：审批人打开申请单时
- **触发条件**：在多人审批（会签/或签）场景中，另一审批人已先行处理
- **判断依据**：打开时查询申请单最新状态，检测到已被处理
- **反馈形式**：页面状态更新（非弹窗阻断）
- **系统反馈**：
  - 页面顶部 Banner：「此申请已被 [审批人姓名] 处理，结果为：[通过/拒绝]。你无需再次处理。」
  - 审批操作区禁用
- **用户下一步**：返回待办列表

### 异常 E6：管理员关闭能力时存在大量在途申请

- **发生时机**：管理员关闭自助申请能力
- **触发条件**：当前存在超过阈值的在途申请
- **判断依据**：关闭前统计在途申请数量
- **反馈形式**：关闭确认弹窗中追加提示
- **系统反馈**：
  - 弹窗中追加：「当前有 {N} 条在途申请，关闭后这些申请将继续流转至结束，但员工无法提交新申请。」
  - 不阻止关闭，仅提示影响范围
- **用户下一步**：管理员确认关闭或取消

### 异常 E7：治理模式兼容性冲突

- **发生时机**：管理员尝试开启自助申请能力时
- **触发条件**：当前启用的治理模式与自助申请存在未解决兼容规则
- **判断依据**：开启前执行兼容性检查矩阵，命中未解决冲突
- **反馈形式**：阻断弹窗
- **系统反馈**：
  - 弹窗展示冲突详情：当前启用的模式、冲突原因、建议处理方式
  - 阻止开启，引导管理员先处理兼容性配置
- **建议文案**：
  - 冲突弹窗标题：「无法开启 — 治理模式兼容性问题」
  - 示例冲突说明：「当前已启用双管理员模式。自助申请与双管理员的叠加规则尚未配置，请先在权限管理设置中完成兼容性配置后再开启。」
- **用户下一步**：管理员前往处理兼容性配置或联系超管

### 异常 E8：审批超时

- **发生时机**：申请在审批节点停留超过设定的超时时间
- **触发条件**：管理员在审批流程中配置了超时处理策略
- **判断依据**：审批节点停留时长 ≥ 超时配置值
- **反馈形式**：系统自动执行超时策略 + 通知相关方
- **系统反馈**：
  - 按配置的超时策略执行：提醒审批人 / 转派他人 / 自动通过 / 自动拒绝
  - 通知申请人超时处理结果
- **用户下一步**：申请人根据超时处理结果（自动通过则确认权限、自动拒绝则联系管理员或重新申请）

## §7 状态与反馈文案

### 统一状态口径表

| 状态 | 含义 | 适用对象 | 用户可操作 | 统一反馈口径 |
|------|------|---------|-----------|-------------|
| 已开启 | 自助申请能力启用中，员工可提交申请 | 管理员 | 配置范围、关闭 | 「自助申请能力已开启，员工可以提交权限申请。」 |
| 已关闭 | 自助申请能力已停用，员工无法提交新申请 | 管理员、员工 | 管理员可开启；员工无可操作 | 「自助申请能力暂未开放，如需申请权限请联系管理员。」 |
| 草稿 | 员工正在填写的申请，尚未提交 | 申请人 | 编辑、提交、删除 | 「申请尚未提交，请完善信息后提交。」 |
| 待审批 | 申请已提交，等待审批人处理 | 申请人、审批人、管理员 | 审批人可处理；申请人可撤回 | 「审批中，当前审批人：[姓名]」 |
| 已通过 | 审批已通过，系统正在或已完成授权 | 申请人、审批人、管理员 | 无 | 「审批已通过，权限已生效。」 或 「审批已通过，权限生效中...」 |
| 已生效 | 权限已授予且可正常使用 | 申请人、管理员 | 管理员可收回 | 「权限已生效，你现在可以使用该权限了。」 |
| 授权失败 | 审批已通过但授权写入失败 | 申请人、审批人、管理员 | 管理员手动补授 | 「审批已通过，授权暂时遇到问题，管理员正在处理。」 |
| 已拒绝 | 审批人拒绝了申请 | 申请人、审批人、管理员 | 申请人可重新申请 | 「申请未通过。审批意见：[原因]。你可以根据意见修改后重新申请。」 |
| 已撤回 | 申请人主动撤回了申请 | 申请人、管理员 | 申请人可重新编辑提交 | 「申请已撤回。你可以修改后重新提交。」 |
| 已撤销 | 管理员收回了已生效的权限 | 申请人、管理员 | 申请人可重新申请 | 「你的 [权限名称] 权限已被管理员收回。如有疑问请联系管理员。」 |
| 审批异常 | 申请因审批流程配置问题无法流转 | 申请人、管理员 | 管理员修复配置 | 「审批流程配置异常，管理员正在处理，请耐心等待。」 |

### 关键反馈场景文案

**通知类 — 审批结果**

| 场景 | 渠道 | 文案 |
|------|------|------|
| 申请通过 — 站内 | 站内消息 / 待办通知 | 「你的权限申请已通过：你已获得「查看本部门考勤记录」权限，立即生效。前往查看 →」 |
| 申请通过 — 移动端 | App Push | 「权限申请已通过！「查看本部门考勤记录」权限已生效。」 |
| 申请被拒 — 站内 | 站内消息 | 「你的权限申请未通过：审批意见：当前岗位暂不需要此权限。如有疑问可联系张经理。重新申请 →」 |
| 申请被拒 — 移动端 | App Push | 「权限申请未通过。查看原因 →」 |
| 新的待审批申请 | 审批人通知 | 「[员工姓名] 申请了「查看本部门考勤记录」权限，请审批。」 |

**提示类 — 操作反馈**

| 场景 | 反馈形式 | 文案 |

## §8 待确认问题

### 基于推荐方案推进（UXB §9 层级一未闭合）

以下问题在 UXB 阶段标记为层级一但未闭合，本次体验设计基于推荐方案推进：

1. **自助申请与双管理员模式的叠加行为**：基于推荐方案——双管理员模式下自助申请的审批流程由管理员在配置时指定，不强制要求两位管理员都审批。如需双重审批，管理员可在审批流程配置中选择会签模式实现。

2. **自助申请与子管理员隔离模式的叠加行为**：基于推荐方案——子管理员隔离模式下，员工的自助申请范围受子管理员管辖范围约束，只能申请子管理员管辖范围内的权限。超出范围的权限不在可申请列表中展示。

3. **审批通过后授权写入的具体方式**：基于推荐方案——审批通过后以「角色分配」方式写入为主（角色标记为「自助申请」来源），以直授方式为辅（适用于无对应角色映射的权限）。写入成功后权限来源标记为「自助申请」。

### 待确认（体验设计阶段新增）

4. **权限业务语言翻译层的命名规范**：可申请项的员工可见名称和描述由管理员自行填写，还是需要平台预置一套命名模板？前者灵活但管理员工作量较大，后者一致但可能不覆盖所有场景。
   - 影响：管理端配置页设计、翻译层语义建模范围
   - 建议确认方：产品

5. **审批结果通知的完整渠道覆盖**：当前设计假设了站内消息和移动端 Push 两种渠道。是否需要支持邮件通知？短信通知是否已有审批管理侧的基础能力可复用？
   - 影响：通知文案结构、触发条件设计
   - 建议确认方：产品 + 审批管理

6. **移动端员工申请和查看的适配范围**：当前设计以 PC 端为主，移动端需要覆盖哪些页面？申请表单在移动端的适配策略是什么？
   - 影响：跨端一致性设计、页面结构调整
   - 建议确认方：产品

7. **可申请范围的权限项数量上限**：是否需要限制管理员可配置的最大申请项数量？如果权限项过多（如超过 50 个），员工端的分组和搜索策略是否需要加强？
   - 影响：员工端列表页信息架构
   - 建议确认方：产品 + 技术

### UXB 承接追踪

| UXB 判断 | 对体验意味着什么 | 体验设计决策 | 落点章节 |
|----------|----------------|-------------|---------|
