# 体验蓝图：员工自助申请权限

> 生成时间：2026-07-06
> 上游来源：`spark-output/uxb_output.md` + `spark-output/context/uxb.json` + `spark-output/journey_analysis.md`
> 运行模式：链式模式

---

## §0 关键设计判断

### 判断 1：申请入口必须与权限查看页面形成闭环

员工必须先知道"自己有什么"才能判断"缺什么"，而"缺什么"的结论必须能一键进入申请。如果把"我的权限"和"申请权限"拆成两个独立入口，员工会在查看→申请之间反复跳转，增加认知摩擦。

**主要影响：** "我的权限"页面结构和权限申请 Drawer 的入口位置。

**建议方案：** 在"我的权限"页面列表中，每条权限项旁保留"申请"按钮（对未拥有的权限灰态提示可申请）。同时在页面右上角保留"申请权限"全局按钮，支持直接跳选。

**不建议方案：** 仅在全局导航放一个"权限申请"入口，员工需要自己先想清楚缺什么再进去选。

**关键待确认：** 员工端权限查看的粒度（应用级还是功能权限点级）。

---

### 判断 2：审批处理应复用现有审批中心，但需要增强信息面板

审批人已有的审批中心里会看到大量待办，权限申请只是其中一类。如果权限申请的信息展示和其他待办没有区别，审批人无法快速判断"这个人申请这个权限是否合理"。

**主要影响：** 审批中心中权限申请类待办的详情展示。

**建议方案：** 在审批中心的标准待办卡片/列表中，权限申请类的待办额外展示：申请人现有权限简览、"申请的权限"说明、申请原因。审批人不用点进详情就能做初步判断。

**不建议方案：** 为权限申请另建独立的审批页面——审批人需要维护多个审批入口，增加切换成本。

**关键待确认：** 审批中台是否支持自定义待办卡片的内容展示。

---

### 判断 3：授权失败不应只通知申请人，审批人也需要介入链路

审批人同意后系统自动授权，但授权可能失败（系统写权限记录失败、权限数据异常）。如果只通知申请人"授权异常"，申请人不知道该找谁、审批人不知道出了什么问题。

**主要影响：** 授权失败的通知链路和异常处理流程。

**建议方案：** 授权失败时同时通知审批人和超管，并附带"查看异常详情"入口，说明失败原因和推荐的人工处理步骤。

**不建议方案：** 仅提示"提交成功"后无后续反馈，或仅告知申请人"出错了请稍后再试"。

**关键待确认：** 授权失败的具体场景和失败原因分类还需要技术侧确认。

## §1 旅程消费摘要

### 信心最低点

| 角色 | 阶段 | 信心度 | 对体验蓝图的驱动 | 落点 |
|------|------|--------|----------------|------|
| 员工 | 发起权限申请 | 低到中 | 申请表单的设计质量直接影响员工的提交意愿，需要在选择器易用性、原因填报引导、提交后预期管理三处做保护 | §6 权限申请 Drawer |
| 员工 | 等待审批处理 | 低 | 审批状态透明度和催办机制是全流程信任度的关键支撑 | §3 等待环节设计 |
| 审批人 | 审查申请内容 | 低到中 | 申请详情的完备性是审批质量的前提，缺乏申请人现有权限参考会导致误判或倾向同意 | §6 审批详情展示 |
| 管理员 | 评估与决策 | 低 | 首次开启前的引导说明决定了管理员是否愿意启用该功能 | §4 配置流程 |

> 四个信心最低点中，两个在员工端（申请表单和等待审批）、一个在审批人端（审查信息不足）、一个在管理员端（开启决策）。体验设计的重点应优先放在这三个角色各自的卡点阶段。

### 关键转折

| 来源角色 | 转折 | 对体验蓝图的驱动 | 落点 |
|---------|------|----------------|------|
| 员工 | 确认权限现状 → 发起申请 | 确认缺少权限后需要明确的"申请"入口，转折点是让流程自然延续的设计时机 | §3 主流程 |
| 员工 | 获知审批结果 → 验证生效 | 通过后需要明确告知"正在生效"还是"已生效"，引导用户去验证 | §3 主流程 |
| 审批人 | 审查内容 → 做出决定 | 信息完备性决定审批质量，转折点的信息展示是体验设计的核心 | §6 审批详情 |
| 审批人 | 做出决定 → 确认授权 | 同意后需要等待系统执行，转折点的即时反馈决定信任 | §3 主流程 |

### 流失风险

| 角色 | 阶段 | 流失场景 | 对体验蓝图的驱动 | 落点 |
|------|------|---------|----------------|------|
| 员工 | 确认权限现状 | 找不到查看权限入口或页面看不懂 | "我的权限"页面必须有清晰的引导和空状态设计 | §6 |
| 员工 | 发起权限申请 | 表单太复杂或不知道选什么 | 权限选择器需要有分组搜索和说明；原因输入提供模板 | §6 |
| 员工 | 等待审批处理 | 审批太久或不知道状态 | 审批状态进度可见+催办入口 | §3 |
| 员工 | 获知审批结果 | 拒绝后不知道怎么办 | 拒绝原因必须清晰，提供重新申请入口 | §3、§4 |
| 审批人 | 审查申请内容 | 信息不足先同意（安全风险） | 审批详情必须展示申请人现有权限 | §6 |

## §2 交互流程总览

本次设计包含以下交互路径：

**1 条主路径：员工申请并获取权限**

- 员工查看自有权限 → 发起申请 → 填写申请内容 → 提交 → 等待审批 → 获知结果 → 验证生效
- 页面串联：我的权限 Page → 权限申请 Drawer → 申请记录列表 → 通知/详情 → 验证

**3 条次路径：**

- **管理员配置自助申请能力：** 开启开关 → 设置可申请范围 → 配置审批流程 → 确认生效
- **员工管理申请：** 查看申请记录 → 查看详情 → 撤销申请 / 重新申请
- **管理员运维与关闭：** 查看统计 → 处理异常 → 配置调整 → 关闭能力

**2 条异常路径：**

- 审批异常：审批人不存在 / 审批超时 → 通知管理员补配 / 催办升级
- 授权异常：自动授权失败 / 部分成功 → 通知审批人和管理员 → 人工介入

## §3 主交互流程

### 3.1 员工查看自有权限

| 字段 | 内容 |
|------|------|
| **用户动作** | 进入"我的权限"页面，浏览按应用分组的权限列表 |
| **系统反馈** | 展示当前生效的权限：应用名称、功能权限概览、数据范围（如有） |
| **需要前置解释的信息** | 权限按来源解释——标明"管理员授予"或"自助申请获得"（后者需来源归属方案确认后实施）。部分权限可能有延迟生效，需标注生效时间 |
| **建议文案** | 页面标题："我的权限"。空状态文案："暂无权限数据，你可以向管理员申请所需权限" |
| **下一步** | 点击列表中的"申请权限"按钮或页面右上角的"申请权限"按钮，进入权限申请流程 |

> 此节点是旅程转折点"确认权限现状→发起申请"的触发位置。

### 3.2 员工提交权限申请

| 字段 | 内容 |
|------|------|
| **用户动作** | 进入权限申请 Drawer → 浏览可申请权限列表（按应用/功能分组） → 选择所需权限项 → 填写申请原因 → 提交 |
| **系统反馈** | 提交后系统执行可申请范围校验（R2）→ 校验通过则生成申请记录 → 推送给审批人。提交成功后 Drawer 关闭，页面显示提交成功 Toast |
| **需要前置解释的信息** | ① 可选范围是管理员已配置的，不在列表中的权限无法申请 ② 审批流程由管理员预先配置，提交后会通知对应审批人 ③ 申请原因帮助审批人判断，请写清楚业务场景 |
| **建议文案** | 提交成功 Toast："申请已提交，等待审批人处理"。提交按钮文案："提交申请"。取消按钮文案："取消" |
| **下一步** | 员工可前往"申请记录"查看审批进度。系统通知审批人处理 |

> 此节点是旅程信心最低点之一，表单设计和提交反馈的体验质量直接影响员工的提交意愿。

### 3.3 审批人审查与处理

| 字段 | 内容 |
|------|------|
| **用户动作** | 审批人收到通知 → 进入待办列表 → 查看申请详情 → 做出同意/拒绝决定 |
| **系统反馈** | 同意→系统自动执行授权；拒绝→要求填写拒绝原因→流程结束 |
| **需要前置解释的信息** | ① 申请人现有权限概览（帮助审批人判断是否会冲突） ② 该权限的风险等级标注（如有） ③ 该权限的历史申请记录（如有：之前是否申请过、拒绝原因） |
| **建议文案** | 同意按钮："同意并授权"。拒绝按钮："拒绝"。拒绝原因提示："请说明拒绝原因，这将帮助申请人了解如何调整" |
| **下一步** | 同意→等待授权结果。拒绝→通知申请人，申请结束 |

### 3.4 授权执行与结果通知

| 字段 | 内容 |
|------|------|
| **用户动作** | 系统自动执行授权（审批人同意后） |
| **系统反馈** | 授权成功→更新权限记录→标记申请为"已生效"→通知申请人和审批人。授权失败→标记为"授权异常"→同时通知申请人和审批人 |
| **需要前置解释的信息** | 授权执行是系统自动完成，不需要人工干预。如果授权失败，需要人工处理 |
| **建议文案** | 授权成功通知："你申请的 {权限名称} 已生效，现在可以使用了"。授权失败通知："授权过程中遇到问题，审批人正在处理，请稍候" |
| **下一步** | 成功→员工验证生效。失败→审批人/管理员进入异常处理流程 |

## §4 次交互流程

### 4.1 管理员配置自助申请能力

| 字段 | 内容 |
|------|------|
| **触发条件** | 管理员首次进入自助申请配置，或需要调整现有配置 |
| **用户动作** | 进入配置入口（通用权限管理→自助权限申请）→ 开启能力开关 → 设置可申请范围 → 配置审批流程 → 确认生效 |
| **系统反馈** | 配置保存后即时生效。员工端在下次刷新后可见申请入口和可申请范围 |
| **需要前置解释的信息** | ① 开启前说明：开启后员工可看到"申请权限"入口，可申请范围仅限于你配置的内容 ② 与现有治理模式的关系：已开启权限变更审批模式时，两者审批链路如何叠加 ③ 配置建议：建议先按角色配置，后续可按需细化到功能权限 |
| **建议文案** | 能力开关提示："开启后，员工可在'我的权限'中发起权限申请"。配置说明："设置员工可申请的权限范围，超出范围的申请将被系统拦截" |
| **下一步** | 配置完成→通知管理员可通过统计看板监控使用情况 |

### 4.2 员工撤销申请

| 字段 | 内容 |
|------|------|
| **触发条件** | 员工提交申请后、审批人处理前，员工改变主意或发现申请有误 |
| **用户动作** | 进入申请记录 → 找到目标申请 → 点击"撤销申请" → 确认撤销 |
| **系统反馈** | 撤销成功后申请状态变更为"已撤销"。通知审批人该申请已撤销 |
| **需要前置解释的信息** | 撤销后不可恢复，如仍需申请需重新提交 |
| **建议文案** | 撤销确认弹窗："确定撤销此申请吗？撤销后不可恢复，如需该权限请重新提交申请" |
| **下一步** | 撤销完成，流程结束。员工可重新提交新的申请 |

### 4.3 被拒绝后重新申请

| 字段 | 内容 |
|------|------|
| **触发条件** | 员工的权限申请被拒绝后，员工希望修改原因或补充信息后再次申请 |
| **用户动作** | 查看拒绝原因 → 点击"重新申请" → 修改申请原因或调整申请的权限范围 → 重新提交 |
| **系统反馈** | 生成新的申请记录，进入审批流程。原有被拒绝的申请保留在历史记录中 |
| **需要前置解释的信息** | 重新申请是新建审批流程，不是对原有申请的修改。建议根据拒绝原因调整后再提交 |
| **建议文案** | 重新申请入口文案："修改后重新申请"。拒绝原因展示标题："拒绝原因" |
| **下一步** | 新申请进入审批流程 |

### 4.4 管理员处理授权异常

| 字段 | 内容 |
|------|------|
| **触发条件** | 审批人同意后系统自动授权失败 |
| **用户动作** | 管理员收到异常通知 → 查看异常详情（失败原因、申请信息）→ 手动完成授权或标记为"无法授权" |
| **系统反馈** | 管理员手动授权成功后，更新申请状态为"已生效"；标记为无法授权的，更新为"授权异常（已关闭）" |
| **需要前置解释的信息** | 授权异常通常由于系统写权限记录失败导致，需要人工确认后手动补授权。手动授权后需要标记来源以便后续追溯 |
| **建议文案** | 异常通知："XX 的权限申请审批已通过，但系统自动授权失败，需要你手动处理"。异常详情标题："授权异常详情" |
| **下一步** | 手动授权完成→通知申请人权限已生效。无法授权→通知申请人并说明原因 |

### 4.5 管理员关闭自助申请能力

| 字段 | 内容 |
|------|------|
| **触发条件** | 管理员决定不再开放员工自助申请 |
| **用户动作** | 进入配置入口 → 查看进行中申请数量 → 选择关闭策略 → 确认关闭 |
| **系统反馈** | 根据选择的策略处理进行中申请 → 关闭员工端申请入口 → 配置保留但能力停用 |
| **需要前置解释的信息** | ① 关闭后已生效的权限不受影响 ② 进行中申请的处理策略（继续流转 / 通知员工后作废）待确认 ③ 历史申请记录保留可查 |
| **建议文案** | 关闭确认弹窗："关闭后员工将无法提交新申请。当前有 {N} 个进行中的申请，请选择处理方式。已生效的权限不受影响" |
| **下一步** | 关闭完成。如需重新开启，管理员可再次进入配置页开启 |

## §5 异常与阻断流程

### 5.1 提交时审批人不存在

| 字段 | 内容 |
|------|------|
| **发生时机** | 员工提交申请时 |
| **触发条件** | 管理员配置的审批人已离职、调岗或无审批权限 |
| **判断依据** | 系统校验审批人状态（R3 不满足） |
| **反馈形式** | 系统阻止提交，Toast 提示员工，同时通知管理员 |
| **系统反馈** | 员工侧 Toast："审批人配置异常，暂时无法提交申请，请联系管理员处理"。管理员侧通知："自助权限申请审批人配置异常，请重新设置" |
| **用户下一步** | 员工：联系管理员。管理员：重新配置审批人 |
| **恢复路径** | 管理员重新配置审批人后，员工重新提交。原申请内容保留，不走审批，不产生记录 |

### 5.2 审批超时未处理

| 字段 | 内容 |
|------|------|
| **发生时机** | 申请提交后、审批人在规定时间内未处理 |
| **触发条件** | 审批人忽略通知、请假、或不确定如何处理 |
| **判断依据** | 系统计时器：超过管理员配置的处理时限 |
| **反馈形式** | 系统发送催办通知给审批人，同时开放员工催办入口 |
| **系统反馈** | 第1次催办：系统自动提醒审批人。第2次催办（可选）：升级通知给管理员或审批人的上级 |
| **用户下一步** | 员工：点击"催办"按钮。审批人：处理申请。逾期严重时管理员重新指派审批人 |
| **恢复路径** | 审批人处理申请后恢复正常流程（同意→授权 或 拒绝→结束）。如果审批人一直不处理，管理员可手动重新指派后继续流转 |

### 5.3 自动授权失败

| 字段 | 内容 |
|------|------|
| **发生时机** | 审批人同意后 |
| **触发条件** | 系统写权限记录失败（数据库异常、权限数据冲突等） |
| **判断依据** | 系统执行 R4 时返回失败结果 |
| **反馈形式** | 系统标记"授权异常"，同时通知审批人和管理员 |
| **系统反馈** | 员工侧："审批已通过，但授权遇到问题，管理员正在处理"。审批人侧："授权异常，请手动处理或通知管理员"。管理员侧：收到异常通知，附带异常详情 |
| **用户下一步** | 员工：等待管理员处理。审批人/管理员：进入异常处理流程 |
| **恢复路径** | 管理员手动完成授权→申请状态更新为"已生效"→通知员工。原路恢复但有信息丢失：员工需重新验证权限是否生效 |

### 5.4 授权部分成功

| 字段 | 内容 |
|------|------|
| **发生时机** | 员工一次申请了多个权限项，审批人全部同意后 |
| **触发条件** | 部分权限授权成功，部分失败 |
| **判断依据** | 系统逐项授权，部分项返回成功、部分返回失败 |
| **反馈形式** | 成功部分→标记"已生效"。失败部分→标记"授权异常"。通知时区分列出 |
| **系统反馈** | "已为您授予以下 {N} 项权限：{权限列表}。以下 {M} 项授权遇到问题，管理员正在处理：{失败列表}" |
| **用户下一步** | 员工：确认已生效部分可用。管理员：处理失败项 |
| **恢复路径** | 管理员逐项处理失败的权限。已生效部分不受影响。恢复后通知员工 |

### 5.5 重复申请

| 字段 | 内容 |
|------|------|
| **发生时机** | 员工选择权限时，选择的权限已经拥有 |
| **触发条件** | 员工尝试申请已生效的权限（R6 来源叠加规则） |
| **判断依据** | 系统比对申请权限与员工已有权限 |
| **反馈形式** | 提交时系统提示员工已拥有该权限，建议取消申请 |
| **系统反馈** | Toast 或内联提示："你已拥有 {权限名称}，无需重复申请" |
| **用户下一步** | 员工确认后移除重复项或取消申请 |
| **恢复路径** | 员工移除重复项后继续提交，恢复到正常申请流程，无信息丢失 |

### 5.6 关闭能力时存在进行中申请

| 字段 | 内容 |
|------|------|
| **发生时机** | 管理员关闭自助申请能力时 |
| **触发条件** | 有申请处于"草稿"或"审批中"状态 |
| **判断依据** | 系统查询当前进行中申请数量 |
| **反馈形式** | 关闭确认弹窗中提示进行中申请数量，要求管理员选择处理策略 |
| **系统反馈** | 策略A（继续流转）：已有申请继续完成，新申请入口关闭。策略B（全部作废）：进行中申请批量作废，通知申请人。策略C（转人工）：将审批中申请转发给超管 |
| **用户下一步** | 管理员选择策略后确认关闭。员工根据策略收到对应通知 |
| **恢复路径** | 策略A：进行中申请正常完成。策略B：员工需联系管理员重新走线下流程 |

### 知识缺口

- 当前知识库中没有员工端"我的权限"页面的参考结构——该页面是本次新增，不在现有管理后台的页面语义覆盖范围内。本次按照"应用级聚合+功能权限点展示+来源标记"的结构设计，待实现后验证。
- 当前知识库中没有"自助权限申请"配置页面的参考结构——同样为新增页面，本次参考权限管理页面的数据列表+配置表单结构设计。

### UXB 承接追踪

| UXB 判断 | 对体验意味着什么 | 体验设计决策 | 落点章节 |
|---------|---------------|------------|---------|
| 自助申请权限需要新增来源类型 | 权限列表需展示来源，申请记录需与权限关联 | "我的权限"列表中增加"来源"列，标明"管理员授予"或"自助申请" | §6.1 |
| 员工端需要权限查看能力 | 独立的权限查看页面 | "我的权限"页面（Page），按应用分组展示 | §6.1 |
| 可申请范围由管理员配置 | 申请表单动态展示可选权限 | 权限申请 Drawer 的可选项由管理员配置决定，超范围权限不可见 | §6.2、§6.5 |
| 审批通过后自动授权 | 授权结果需明确反馈 | 授权成功/失败的 Toast 通知，附带后续指引；授权异常走分支流程 | §3.4、§5.3 |
| 关闭能力时处理策略待定 | 关闭交互取决于策略 | 关闭确认弹窗提示进行中申请数量，提供策略选择 | §4.5 |
| 自助申请与现有治理模式的共存关系 | 多模式叠加影响审批配置 | 管理员配置页中标注与权限变更审批模式的兼容关系；审批流程复用现有中台 | §6.5、§4.1 |
