# Solution Swimlane 语义制图 Agent 重构计划

## 1. 文档目的

将当前 `solution-swimlane` 从“全量来源编译器 + 严格覆盖校验器”重构为“语义制图 Agent + 确定性 HTML/SVG 渲染器”。

本计划只定义重构范围、目标架构、实施步骤和验收标准，不直接修改现有 Skill。

---

## 2. 不可违反的红线

### 2.1 必须做到

1. 完整扫描正式蓝图 Markdown。
2. Markdown 中所有会改变泳道图语义的有效信息必须被抽取。
3. 抽取结果必须覆盖：
   - 参与角色与系统方；
   - 角色责任；
   - 流程开始与结束；
   - 业务动作；
   - 系统处理；
   - 条件判断；
   - 跨角色交接；
   - 主流程；
   - 次流程；
   - 异常流程；
   - 恢复、回流或终止；
   - 局部待确认事项。
4. Agent 只生成精简语义模型。
5. HTML、SVG、布局、连线和交互必须由脚本确定性生成。
6. 相同输入重复运行时，泳道、节点、关系、流程的 ID、类型、归属、成员和排序必须一致。
7. 局部信息不完整且不属于第 7.2 节阻断条件时，必须生成 `pending` 或 `open_question` 并继续；不得自行扩大阻断条件。

### 2.2 禁止事项

1. 不逐段、逐句、逐字段建立全量覆盖清单。
2. 不要求每个 Markdown 段落都映射到图元素。
3. 不枚举 JSON 的所有数组、对象和叶子字段。
4. 不让 Agent 手写 `coverage_rules`。
5. 不使用宽泛 `source_ref_prefix` 做全量对账。
6. 不抽取与泳道图无关的：
   - 背景介绍；
   - 旅程分析；
   - 设计判断过程；
   - 页面布局；
   - 字段清单；
   - 按钮清单；
   - 提示文案；
   - Toast 文案；
   - 视觉草图；
   - 知识消费记录；
   - 上游追踪说明；
   - 统计和分析结论。
7. 不因一条文案、一个状态字段或一个局部关系缺失而反复重跑整个流程。
8. 不允许无限修复循环。

### 2.3 语义完整性红线

1. “有效信息”仅指会改变以下任一结果的信息：
   - 泳道或责任主体；
   - 业务动作或系统处理；
   - 开始、结束或业务结果；
   - 先后顺序；
   - 条件、分支或例外；
   - 跨角色交接；
   - 次流程、异常流程、恢复、回流或终止。
2. 抽取必须执行两遍：
   - 第一遍建立语义模型；
   - 第二遍只复核上述八类有效信息是否已被表达。
3. 第二遍发现的每条有效信息必须满足以下三种结果之一：
   - 已映射为泳道、节点、关系或流程；
   - 已与语义等价的现有元素合并；
   - 因原文信息不足而写入 `pending` 或 `open_questions`。
4. 已确认的有效信息既未进入模型、也未被等价合并或标记待确认，判定为“语义漏抽”，真实测试必须失败。
5. 第二遍复核是内部检查，不得重新建立逐段、逐句或逐字段来源清单。
6. 不得为了满足节点数量、文件大小或耗时建议值而删除已确认的有效信息。

### 2.4 修改范围隔离红线

本次重构的唯一对象是 `.claude/skills/solution-swimlane/`。实施和测试必须遵守以下文件级边界。

允许写入：

1. `.claude/skills/solution-swimlane/**`：Skill 定义、引用、模板、脚本与测试。
2. `spark-output/solution-swimlane/**`：真实测试生成物。
3. `spark-output/solution-swimlane-refactor-plan.md`：仅用于维护本计划。
4. 系统临时目录中的 `solution-swimlane-*`：仅存放可删除的临时产物。

允许只读：

1. `spark-output/experience_blueprint.md`：正式 Markdown 输入。
2. `spark-output/context/experience-blueprint.json`：可选 Context JSON 输入。
3. 用户明确指定的其他测试输入：只读，不得原地改写或生成相邻产物。
4. 为核验现有调用关系而读取的仓库文件；只读不构成修改授权。

绝对禁止：

1. 修改、删除、移动、重命名或格式化其他 `.claude/skills/**`。
2. 修改 `.Codex/skills/**`、`shared-workflow/**`、`input/**`、`packages/**`、`knowledge/**`、项目配置、依赖文件、`AGENTS.md` 或 Git 配置。
3. 修改正式输入文件、上游体验蓝图或其他 Skill 的输出。
4. 修改或覆盖 `spark-output/progress-preview.html` 及任何非 `spark-output/solution-swimlane/**` 的运行产物。
5. 安装依赖、升级依赖或通过公共脚本改变其他模块。
6. 暂存、提交或推送任何文件；除非用户另行明确授权。

范围核验：

1. 实施前记录 `git status --short`，区分用户已有改动与本次改动。
2. 每个阶段结束后检查 `git diff --name-only` 和未跟踪文件。
3. 本次新增或修改的路径只要超出允许写入范围，立即停止；只撤销本次造成的越界改动，不得回退用户原有改动。
4. 新主链路不得调用 `shared-workflow/generate-progress-preview.js` 或其他范围外写入脚本。

## 3. 问题定义

### 3.1 当前机制

```text
MD + JSON
→ 全量来源清单
→ Agent 手写巨大 diagram-draft.json
→ source selector 物化
→ 全量覆盖校验
→ 图模型校验
→ HTML 渲染
```

### 3.2 当前机制的根本问题

1. 来源清单粒度远小于泳道图语义粒度。
2. Agent 必须手工处理数百到上千个来源项。
3. 一个来源可能同时支撑泳道、节点、关系或流程，但现有契约要求唯一类型。
4. 前缀选择器容易产生交叉命中。
5. 校验发生在巨大草稿生成之后，错误发现过晚。
6. 每次运行使用新的临时目录，无法复用已经完成的语义模型。
7. 当前测试只覆盖脚本组件，没有覆盖“真实蓝图 → 语义模型 → HTML”的完整生成链路。

## 4. 目标架构

```text
正式蓝图 MD
        │
        ├── 可选 Context JSON
        │
        ▼
Agent 语义抽取
        │
        ▼
semantic-model.json
        │
        ├── 轻量结构校验
        │
        ▼
确定性 HTML/SVG 渲染
        │
        ▼
solution_swimlane.html
```

### 4.1 职责边界

#### Agent 负责

- 理解自然语言；
- 识别角色、任务、系统处理和责任边界；
- 合并同义角色与重复步骤；
- 判断流程先后；
- 识别条件、分支、交接和回流；
- 区分主流程、次流程和异常流程；
- 将无法确认的局部内容标记为待确认；
- 输出符合固定 Schema 的精简语义模型。

#### 校验脚本负责

- JSON Schema 合法性；
- ID 唯一性；
- 节点所属泳道存在；
- 关系两端节点存在；
- 流程成员存在；
- 至少有一条主流程；
- 主流程存在开始和结束；
- 判断分支具有条件标签；
- 异常流程具有恢复、终止或待确认出口；
- 防止无限循环和不可渲染结构。

#### 渲染脚本负责

- 横向泳道布局；
- 节点尺寸；
- 时间列；
- 正交连线；
- 回流通道；
- 流程颜色；
- 流程切换；
- 缩放、适应画布、打印和 SVG 导出；
- 自包含 HTML；
- HTML/SVG DOM 完整性检查。

## 5. 输入策略

### 5.1 输入优先级

1. Markdown 存在时是唯一权威业务语义来源。
2. Context JSON 是可选结构化辅助来源。
3. 只有 Markdown 时必须能够生成。
4. 只有 JSON 且包含角色、流程、异常、状态等结构化语义时可以生成。
5. 两者同时存在时：
   - JSON 只能补充 Markdown 未表达且不冲突的结构化信息；
   - JSON 不得覆盖、改写或否定 Markdown 中已确认的信息；
   - 同一事实冲突时采用 Markdown，冲突内容写入 `open_questions`；
   - JSON 含有可识别的项目名或业务范围，且与 Markdown 明示的项目名或业务范围不一致时，整份 JSON 不参与抽取，并输出明确警告；
   - JSON 无法判断项目归属时不得自行判定为其他项目；按补充来源处理，任何冲突仍由 Markdown 裁决；
   - 不进行逐字段双向覆盖对账；
   - 局部冲突不直接阻断整图。

### 5.2 Markdown 扫描规则

Agent 必须完整扫描 Markdown，但只抽取能回答以下问题的内容：

1. 谁在执行？
2. 谁承担责任？
3. 做了什么完整业务任务？
4. 系统自动处理了什么？
5. 下一步是什么？
6. 在什么条件下分支？
7. 任务交给了谁？
8. 产生了什么业务结果？
9. 出错后如何恢复、回流或终止？
10. 哪些关系无法确认？

只有能回答以上至少一个问题的内容才允许进入语义模型；不能回答时不得抽取。

### 5.3 章节路由

章节标题只用于定位，不得缩小完整扫描范围。

以下章节通常包含有效信息：

- 主交互流程；
- 次交互流程；
- 异常与阻断流程；
- 状态流转；
- 角色与职责；
- 流程总览中未在正文重复表达的关系。

以下内容本身不得抽取：

- 背景；
- 旅程消费；
- 设计判断；
- 页面设计；
- 控件和字段；
- 反馈文案；
- 设计指南消费；
- 上游承接追踪；
- 纯分析和纯说明。

章节名称不能覆盖内容语义。如果上述章节中出现第 2.3 节定义的有效信息，必须只抽取该有效信息，不抽取其背景、分析或文案。

## 6. 精简语义模型

正式模型名固定为：

```text
semantic-model.json
```

### 6.1 顶层结构

```json
{
  "schema_version": "2.0",
  "title": "项目名称",
  "scope": "本图覆盖的业务范围",
  "start_condition": "流程开始条件",
  "end_conditions": ["完成条件", "终止条件"],
  "lanes": [],
  "nodes": [],
  "edges": [],
  "flows": [],
  "open_questions": []
}
```

### 6.2 泳道

```json
{
  "id": "employee",
  "name": "员工",
  "type": "human",
  "responsibility": "发起并跟踪权限申请",
  "source_refs": ["§3 P2"]
}
```

字段：

- `id`：稳定、唯一；
- `name`：正式角色或系统名称；
- `type`：`human`、`team`、`system`；
- `responsibility`：该泳道对流程承担的责任；
- `source_refs`：可选，节点级或章节级来源，不做全文覆盖。

### 6.3 节点

允许类型：

- `start`
- `action`
- `system_process`
- `decision`
- `result`
- `end`
- `pending`

```json
{
  "id": "submit-request",
  "lane_id": "employee",
  "label": "提交权限申请",
  "type": "action",
  "summary": "选择权限并填写申请原因",
  "certainty": "confirmed",
  "source_refs": ["§3 P2-2"]
}
```

### 6.4 关系

允许类型：

- `normal`
- `conditional`
- `handoff`
- `exception`
- `return`
- `terminate`

```json
{
  "id": "submit-to-validate",
  "from": "submit-request",
  "to": "validate-request",
  "label": "提交后",
  "type": "handoff",
  "certainty": "confirmed",
  "source_refs": ["§3 P2-2 下一步"]
}
```

### 6.5 流程

允许类型：

- `main`
- `secondary`
- `exception`

```json
{
  "id": "main-flow",
  "name": "权限申请主流程",
  "type": "main",
  "node_ids": ["start", "submit-request", "validate-request", "end"],
  "edge_ids": ["start-to-submit", "submit-to-validate", "validate-to-end"]
}
```

### 6.6 待确认项

```json
{
  "id": "question-approval-timeout",
  "question": "审批超时后是否自动终止？",
  "impact": "影响异常流程出口",
  "related_element_ids": ["approval-timeout"],
  "fallback": "使用 pending 结果节点表达"
}
```

## 7. 容错与失败策略

### 7.1 不应阻断

- 节点摘要不够完整；
- 页面或按钮信息缺失；
- 提示文案缺失；
- 次要条件未确认；
- 局部恢复路径不明确；
- Markdown 与 JSON 局部描述不一致；
- 无法确认一个次流程的最终处理人；
- 缺少非核心状态说明。

处置方式：

- 使用 `certainty: "uncertain"`；
- 生成 `pending` 节点；
- 生成虚线关系；
- 写入 `open_questions`；
- 继续生成其余已确认内容。

### 7.2 必须阻断

仅以下情况停止生成：

1. 输入文件不存在或不可读取；
2. 无法识别任何泳道；
3. 无法识别任何业务节点；
4. 无法形成至少一条主流程；
5. 语义模型 JSON 在一次自动修复后仍不符合 Schema；
6. 渲染器自身报错或输出 HTML 不完整；
7. 端到端执行达到 180 秒硬超时；
8. 检测到本次执行将写入第 2.4 节允许范围之外。

### 7.3 重试上限

- 语义模型生成：1 次；
- Schema 自动修复：最多 1 次；
- 渲染修复：最多 1 次；
- 禁止对同一模型进行无上限循环修补。

结构修复只能修正 JSON 语法或 Schema 结构，不得借修复之名重新抽取全文。渲染修复只能处理同一语义模型的渲染错误，不得重新调用 Agent。达到任一上限后输出具体缺口并停止。

## 8. 时间与复杂度预算

以下数值是重构验收门禁，不代表当前 Skill 已达到。

### 8.1 执行预算

- 输入读取与预处理：必须不超过 5 秒；
- Agent 语义抽取：只允许一轮完整生成；
- 结构修复：最多一轮；
- 脚本校验与渲染：必须不超过 10 秒；
- 常规蓝图端到端执行达到 180 秒时必须终止并判定失败；
- 不把浏览器人工视觉确认计入自动生成耗时。

以上时间门禁使用当前工作站和阶段六选定的三套正式蓝图核验，并记录每一阶段的起止时间。不得通过跳过有效信息、关闭校验或减少测试输入来满足门禁。

### 8.2 模型规模控制

以下仅为压缩建议，不是删除语义的依据：

- 泳道：2–8 条；
- 主流程节点：5–20 个；
- 单条次流程节点：2–8 个；
- 单条异常流程节点：2–6 个；
- 节点总数超过 60 时，优先合并同义步骤，而不是继续平铺；
- 单个节点摘要保持一至两句话；
- `source_refs` 每个元素建议不超过 3 条。

超过建议值时允许生成并给出复杂度提示。任何压缩都必须保持第 2.3 节定义的有效信息完整。

## 10. 新的 Skill 执行流程

```text
1. 记录工作树状态并校验写入白名单
2. 检查 MD 或 JSON 是否存在
3. 按第 5.1 节确定权威输入与补充输入
4. 完整扫描输入并抽取泳道图语义
5. 第二遍复核有效信息，消除语义漏抽
6. 写入 semantic-model.json
7. 运行轻量 Schema 校验
8. 如失败，只允许一次结构修复
9. 运行确定性渲染器
10. 校验 HTML/SVG
11. 输出 solution_swimlane.html
12. 复核实际改动路径未越过白名单
13. 可选人工视觉检查
```

Agent 不再执行：

- 来源清单构建；
- 覆盖规则编写；
- 来源项逐个排除；
- 多轮物化；
- 宽泛选择器修复；
- 阻断项逐个清零。

## 11. 分阶段实施计划

### 阶段一：冻结语义模型 2.0

任务：

## 12. 测试矩阵

| 测试层级 | 输入 | 验证重点 |
|---|---|---|
| Schema 单元测试 | 手工小模型 | ID、引用、流程闭合 |
| 渲染单元测试 | 合法小模型 | HTML/SVG DOM 一致 |
| 容错测试 | 缺少局部恢复路径 | 输出 pending，不阻断 |
| 过滤测试 | 含大量背景、分析、页面文案的 MD | 非必要信息不进入模型 |
| 真实端到端测试 | 三套正式蓝图 | 抽取完整性、耗时、输出稳定性 |
| 重复运行测试 | 相同蓝图运行两次 | 结构一致、无随机增删 |
| 大输入测试 | 50KB 以上 Markdown | 不创建上千项覆盖清单 |
| 输入冲突测试 | 同一事实在 MD 与 JSON 中冲突 | MD 生效，冲突进入 open_questions |
| 范围隔离测试 | 执行完整生成链路 | 允许写入范围外零新增、零修改、零删除 |
| 超时测试 | 人为构造或注入超时 | 180 秒时停止，不追加重试 |

## 13. 完成定义

1. 正式主链路不再包含来源清单和覆盖物化。

11. 人工视觉检查通过。

13. 第二遍语义复核不存在语义漏抽。

## 14. 实施顺序结论

必须按以下顺序实施：

```text
先冻结语义模型
```
