§0 本次关键判断

子管理员「复制」功能是在现有子管理员配置能力上新增的批量效率路径，不改变底层业务骨架。

  • 判断：这项需求的本质是解决大客户实施阶段的批量配置效率问题，不是新增治理模式或改造权限模型。
  • 主要影响：200+ 级别子管理员客户的配置时间将从逐条勾选压缩为批量复制，显著降低实施周期。
  • 建议方案：在子管理员列表操作列新增「复制」入口，通过弹窗选择复制内容和目标对象。非互审模式下直接写入权限；双管理员互审模式下提交审批，审批通过后写入。
  • 不建议方案：不要为复制单独新建页面（弹窗足够承载）；不要在本次引入「覆盖」选项（与当前叠加逻辑冲突，且无明确需求支撑）。
  • 关键待确认：无影响主方案成立的层级一待确认项。

§1 需求输入摘要

需求背景

集团型企业使用「子管理员模式」下放权限管理能力。部分客户子管理员数量较多（如广西交投 200+），这些子管理员的「可授权功能」通常一致，但「可授权组织」不同。当前需逐个配置，效率较低。

业务目标

降低大客户批量配置子管理员的时间成本和实施周期。

产品目标

新增「复制」能力，使权限管理员可以复用已配置子管理员的权限信息。

功能范围

  • 子管理员列表操作列新增「复制」入口
  • 复制弹窗，支持选择复制内容（可授权组织 / 可授权功能）
  • 支持选择一个或多个用户作为复制目标
  • 员工选择弹窗复用现有样式
  • 点击确认时按顺序校验（复制信息 → 复制对象 → 加入状态 → 认证状态）
  • 复制成功后 toast 提示
  • 复制成功后生成操作记录
  • 双管理员互审模式下生成审批

明确约束

#约束
1复制来源必须是已有子管理员
2复制信息至少选择一项
3复制对象至少选择一名用户
4复制对象最多选择 200 名
5复制对象必须已加入且已认证
6已有子管理员接收复制采用叠加逻辑，不覆盖原有权限
7普通用户接收复制后成为子管理员
8复制成功必须生成操作记录
9开启双管理员互审模式时，复制需生成审批

原始输入未覆盖区域

  • 审批中的复制申请是否支持撤销
  • 操作记录是否支持按复制操作聚合查看
  • 「加入状态」校验的目标状态口径（已启用 / 已加入）未统一

§2 业务场景判断

业务定位

这次是在「子管理员模式」治理框架内新增的批量效率能力，不是引入新的治理模式或改变权限模型。复制操作后端的规则（叠加 / 成为）和生效机制（直接生效 / 审批后生效）都是已有逻辑的复用。

与现有能力的关系

  • 复用子管理员配置页中的「可授权组织」和「可授权功能」数据结构
  • 复用现有员工选择弹窗
  • 复用双管理员互审模式的审批链路
  • 与操作记录、审计体系衔接

最大不确定性

审批机制细节已确认（审批通过后才写入权限），不存在影响主方案的方向性不确定性。

如果判断错了

如果本次复制操作实际上改变了子管理员的状态模型或引入了新的状态流转（如「复制中」状态），则 §5 和 §6 需要重新评估。基于当前材料，没有证据指向这种可能性。

§3 需求成立性判断

收益

  • 批量配置效率提升：对 200+ 子管理员客户，从逐条勾选变为一次批量复制
  • 减少重复劳动和误配置风险
  • 降低大客户实施周期，提升客户满意度
  • 与现有双管理员互审模式兼容

系统代价

  • 新增一个操作入口和弹窗
  • 操作记录系统新增两条记录模板
  • 审批链路已存在，复用成本低

更低成本替代路径

  • 模板导入（如 Excel 批量导入子管理员配置）：适合初始大规模配置场景，但交互路径长，不适合日常逐个小调整。复制功能更适合日常运维场景。
  • 角色化授权（通过角色模板分发权限）：已在能力范围内，但与子管理员模式是不同治理路径。复制补的是子管理员体系内的效率缺口。

判断

建议进入正式体验设计。

§4 推荐业务边界

推荐能力形态

  • 在子管理员列表操作列新增「复制」入口
  • 以弹窗承载复制内容选择和复制对象选择
  • 复制内容默认为全选（可授权组织 + 可授权功能），至少选一项
  • 复制对象选择器复用现有员工选择弹窗
  • 点击确认后执行顺序校验，通过后写入或提交审批
  • 操作结果区分场景反馈

不推荐能力形态

  • 不要为复制单独新建页面：弹窗足够承载，且不打断管理员对列表的上下文感知
  • 不要引入「覆盖」选项：当前需求明确为叠加逻辑，且无需求支撑覆盖场景
  • 不要新增「从零创建子管理员后复制」的混合路径：复制入口只从已有子管理员发起
  • 不要为复制单独设计审批流程：复用双管理员互审模式既有审批链路

与现有能力的边界

  • 复制入口仅在「子管理员模式」列表中出现
  • 复制来源必须是已有子管理员
  • 复制不改变来源子管理员的配置
  • 复制不创建新的子管理员配置入口（复用现有添加子管理员路径）

复用对象

  • 员工选择弹窗（与添加子管理员一致）
  • 双管理员互审模式的审批链路
  • 操作记录系统的存储和展示能力

不应新增的内容

  • 不应新增子管理员状态类型
  • 不应新增审批流程类型
  • 不应新增权限维度或业务对象

§7 体验蓝图承接要求

要求 1：复制入口的位置语义

  • 业务判断：复制入口放在子管理员列表操作列最左侧，说明这是一条与编辑、移除并列的操作路径
  • 体验影响：用户需要区分「编辑已有子管理员」和「复制已有子管理员给他人」两种操作的目的差异
  • 必须承接的问题：操作列按钮的排布既要突出新增的复制入口，又不能降低原有操作的可发现性
  • 禁止下游重判：复制入口必须出现在操作列，不得移到列表顶部的批量操作区

要求 2：批量复制的结果反馈

  • 业务判断：一次复制可能涉及最多 200 个目标用户，每个用户的处理规则可能不同（成为 / 叠加），校验结果也可能不同（全部通过 / 部分通过）
  • 体验影响：如果只用单一 toast 反馈，用户无法知道具体每个目标用户的处理结果
  • 必须承接的问题：批量复制后必须提供按用户维度的结果反馈，明确谁成功、谁失败、失败原因；部分成功的边界策略需要产品确认后纳入方案
  • 禁止下游重判：不得只用「复制成功」一句话覆盖所有批量场景

要求 3：双管理员互审模式下的语义区分

  • 业务判断：互审模式下审批通过后才写入权限，「复制成功」的实际含义是「已提交审批」而非「已生效」
  • 体验影响：统一 toast「复制成功」会让用户误以为权限已生效，实际还在等审批
  • 必须承接的问题：互审模式下，操作完成后的反馈必须明确表达「已提交审批，等待确认后生效」；审批通过后应有可感知的结果通知，而非静默写入
  • 禁止下游重判：不得在互审模式下使用与非互审模式相同的成功表述

要求 4：混合目标用户的规则差异前置提示

  • 业务判断：复制目标中可能混着普通用户（将「成为」子管理员）和已有子管理员（将「叠加」权限），两种规则在确认前就可以区分
  • 体验影响：用户点击确认后才知道谁走了什么规则，缺乏事前掌控感
  • 必须承接的问题：在选择复制对象后、点击确认前，系统应提示目标用户中哪些是已有子管理员（将叠加）、哪些是普通用户（将成为），让用户确认预期
  • 禁止下游重判：不得将规则差异的提示延后到复制完成后

要求 5：操作记录的消费场景

  • 业务判断：复制操作按复制内容分条存储（可授权组织一条、可授权功能一条），但用户实际追溯时关注的是「某次复制操作」的整体
  • 体验影响：两条独立记录的用户信息（来源、目标、时间）重复，用户需要自行关联同一批次的两条记录
  • 必须承接的问题：操作记录的展示层面需要考虑如何将同一复制操作的两条记录聚合展示，避免用户手动关联
  • 禁止下游重判：不得要求用户自行关联两条操作记录来理解一次完整的复制操作

要求 6：审批中的复制申请状态可见性

  • 业务判断：互审模式下复制申请提交后到审批通过前，目标用户看不到权限变化，权限管理员也需要跟踪哪些申请还在审批中
  • 体验影响：审批中的复制申请对操作者是不可见的，操作者只能去审批系统查看，脱离了子管理员列表的上下文
  • 必须承接的问题：在子管理员列表或相关位置，需要让权限管理员感知到「有复制申请在审批中」的状态；审批通过后，目标用户的子管理员身份和权限应在列表中可见
  • 禁止下游重判：不得要求管理员离开当前页面前往审批系统自行查询复制申请的审批状态

§8 约束与不做什么

硬约束

  • 复制入口仅在「子管理员模式」列表中出现，不出现在其他模块
  • 复制来源必须是已有子管理员
  • 复制信息至少选择一项
  • 复制对象至少选择一名用户，最多选择 200 名
  • 复制对象必须已加入且已认证
  • 已有子管理员接收复制采用叠加逻辑，不得覆盖
  • 普通用户接收复制后自动成为子管理员
  • 双管理员互审模式下，审批通过后才写入权限
  • 复制成功必须生成操作记录
  • 子管理员模式与双管理员互审模式不可同时开启（R-009），但复制逻辑需预判互审场景，非互审模式下直接生效

不做什么

  • 不新增「覆盖」选项
  • 不为复制单独创建新的审批类型
  • 不改变子管理员的状态模型
  • 不新增权限维度或业务对象
  • 不为复制设计独立页面
  • 不做批量导入（与复制是不同的效率路径）
  • 不做复制后自动通知目标用户
