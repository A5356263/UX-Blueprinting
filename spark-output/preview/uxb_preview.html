§0 本次关键判断

这是一项"把权限授权从管理员集中处理转向员工自助+上级审批+自动生效"的治理结构调整，不是页面级功能优化。

业务判断：推荐在现有权限模块中新增"员工自助申请"能力线。关键前提是审批流基建（审批引擎、上级负责人路由、自动授权执行接口）的成熟度，它们决定方案可行性和实施路径。不建议保留人工执行环节或改为管理员审批——那没有解决时效不稳定的核心矛盾。最高优先级待确认：审批流引擎的接口能力是否支持"审批通过后自动触发授权执行"。

---

§1 需求输入摘要

需求背景

中大型企业员工权限分配目前依赖管理员或超级管理员集中处理。员工数量多、人员流动频繁，权限新增、变更、核对工作量大。部分企业的超级管理员就是老板本人。

目标用户

  • 员工（核心）：业务人员/经办人员，需要被授予功能权限或加入角色
  • 上级组织负责人：审批人，审批下属的权限申请
  • 权限管理员/超级管理员：负责权限策略配置和治理

业务目标

支持员工自助查看和申请权限，把部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对申请范围和审批流程的控制。

功能范围

  • 覆盖：功能权限申请 + 角色授权申请
  • 不覆盖：数据权限的自助申请、协作可见性的自助申请

明确约束

  • 申请范围由管理员预制，排除敏感权限 [FACT]
  • 审批人为上级组织负责人，不是管理员 [FACT]
  • 审批通过后自动生效，不留人工执行环节 [FACT]
  • 作为已有平台新增能力，需兼容现有权限模块架构 [CONFIRMED]

输入缺口

  • 审批流引擎基建就绪度未明确 [GAP]
  • 自动授权执行接口可用性未明确 [GAP]

§2 业务场景判断

业务定位

这是权限管理域中新增的自助服务子能力，不是对现有授权方式的替代或重构。现有管理员侧授权保持不变，新增一条员工侧发起→上级审批→系统自动执行的并行路径。

与现有能力的关系

现有能力关系说明
管理员用户直授并行存在管理员仍可主动为员工授权，自助申请是新增入口
角色授权被复用员工申请加入角色后，复用已有角色-权限绑定关系
审批中台依赖关系审批流需要接入平台审批能力路由到上级负责人
组织域成员关系依赖关系审批人匹配依赖组织域中"上级负责人"关系的完整性

最大业务不确定性

审批流转链路能否闭环——从"员工提交"到"上级审批"到"系统自动授权"的三段链路，每一段都依赖平台既有基建。审批流引擎和自动授权执行接口的就绪度是当前最大的业务风险。

判断错误的影响

如果判断错"审批基建已就绪"但实际上未就绪，后续体验方案中"自动生效"环节需要改为半自动（通知管理员手动执行），这会破坏核心价值主张（时效可预期）。如果判断错"上级负责人关系已定义完整"但实际上不完整，审批人匹配会大面积失败，需要补充兜底机制。

§3 需求成立性判断

价值判断

成立。 从三个角度看：

  1. 问题真实 — 中大型企业人员流动性高，非正式沟通模式无法规模化管理，这是管理常识级痛点，不依赖特定场景验证
  2. 收益明确 — 员工获得可预期的授权时效，管理员从执行者变为策略定义者，审批人在上下文中做判断而非空白审批，三层角色各有所获
  3. 用户体验收益 — 从"找到人→说清楚→等待"的模糊链路变为"提交→等审批→自动获得"的清晰链路

系统代价

  • 建设成本中等：新增员工端入口、申请目录、申请 Drawer、审批详情 Drawer、我的申请页等前端实体
  • 依赖成本偏高：审批流引擎、上级负责人路由、自动授权接口三项基建缺一不可
  • 维护成本中等：管理员需持续维护可申请目录和敏感权限标记

更低成本替代方案

  • 不做自助申请，只优化管理员授权体验：在后台增加批量授权、模板授权能力。这能解决管理员的效率问题，但不解决员工侧的"不知道找谁、不知道有什么权限"问题
  • 不做自动生效，只做申请+审批通知：审批通过后通知管理员手动执行。这降低了对授权接口的依赖，但重新引入了时效不稳定的核心矛盾

建议：进入正式体验设计，但前提是审批流基建和自动授权接口必须在设计阶段确认就绪度。如果基建不满足，需要在上游提前暴露风险，而不是等方案完成后再回头补。

§4 推荐业务边界

推荐能力形态

  • 员工侧：可申请目录浏览 → 权限/角色详情查看 → 选择并发起申请 → 追踪进度 → 接收结果
  • 审批人侧：待办列表 → 申请详情查看（含权限说明和风险提示）→ 审批操作
  • 管理员侧：角色和功能权限的"可自助申请"标记开关 → 批量标记 → 配置生效

不推荐能力形态

  • 不推荐让员工自由申请全部权限（必须预制范围）— 安全失控
  • 不推荐由管理员审批（必须限定为上级负责人）— 未解决管理者负担
  • 不推荐审批通过后留人工执行环节 — 未解决时效不稳定
  • 不推荐在员工侧暴露可申请的数据权限或协作可见性 — 超出本次范围

与现有能力的边界

  • 复用现有角色-权限绑定关系（员工加入角色即获得关联的功能权限）
  • 复用现有组织架构成员关系（审批人路由依赖上级负责人定义）
  • 不改变管理员侧授权路径
  • 不改变敏感权限的管控方式

不新增

  • 不新增独立的审批流引擎（复用平台审批能力）
  • 不新增权限对象模型（复用现有主体、资源、动作、范围定义）

§6 状态、异常与边界

核心状态

状态说明用户下一步
待审批申请已提交，等待上级审批等待或催办
审批人已查看审批人已打开查看等待审批结果
已通过审批人已批准等待权限生效
已拒绝审批人未批准查看拒绝原因，重新申请或放弃
授权中系统正在执行授权等待
授权成功权限已生效去使用权限
授权失败系统自动授权不成功联系管理员

关键异常

异常触发条件系统处理结果用户下一步
审批人不存在/已离职提交后匹配审批人失败申请状态→"审批人匹配失败"；通知员工+通知管理员员工联系管理员确认组织关系，管理员修复后系统自动重新路由
审批超时超过预设时限（如24h/48h）未处理员工端可催办，审批端超时标记置顶员工催办或联系审批人
自动授权失败授权执行接口返回失败申请状态→"授权失败"；通知双方+失败原因员工联系管理员；审批人可协助排查
批量授权部分失败逐项执行时部分失败成功项即时生效，失败项展示原因；状态→"部分成功"失败项单独重新申请或联系管理员
权限已拥有重复申请员工选择的项含已拥有权限提醒可移除，不阻断提交选择一键移除重复项或保留（系统自动过滤）

边界

  • 敏感权限不在员工可申请目录中展示，管理员也无法标记为可自助申请 [GAP：敏感权限标记机制是否已定义]

§7 体验蓝图承接要求

业务判断对体验设计的影响必须承接的问题禁止下游重判
申请范围由管理员预制，排除敏感权限目录不是全量权限，员工只看到可申请的项权限目录的筛选逻辑、可申请标记的展示方式、敏感权限的保护机制不得让员工自由申请全部权限
审批人为上级组织负责人审批人自动匹配，申请人不需要选择审批人匹配失败时的降级处理、审批上下文中展示权限说明和风险提示不得改为管理员审批或让申请人自选审批人
审批通过后自动生效生效环节无人工干预，状态需实时可感知自动授权执行链路、授权成功/失败的反馈机制、部分成功的处理策略不得保留人工执行环节
覆盖功能权限和角色授权目录有两类授权对象，角色是权限集合角色与功能权限的分栏展示、角色详情中包含关联权限清单不得扩展至数据权限或协作可见性
员工可看到全部角色角色列表全量，但仅部分可申请可申请角色与不可申请角色的视觉区分、全部角色的可浏览性不得隐藏不可申请的角色
申请需填写理由理由帮助审批人判断理由输入引导、理由校验、拒绝时原因的填写不得取消理由必填
申请进度需透明可追踪等待区间需中间态状态时间线、催办机制、超时标记不得仅展示终态

§8 约束与不做什么

硬约束

  • 作为已有平台新增能力，需兼容现有权限模块的架构和数据模型 [FACT]
  • 所有申请必须可审计、可追溯 [CONFIRMED]
  • 管理员仍为权限策略的定义者和控制者，不被绕过 [CONFIRMED]
  • 从申请到生效的全链路必须有明确的失败感知和处理机制 [CONFIRMED]

不做什么

  • 不覆盖数据权限的自助申请 [FACT]
  • 不覆盖协作可见性的自助申请 [FACT]
  • 不做员工自由申请全部权限（必须预制范围） [FACT]
  • 不做管理员侧的权限申请代办（审批人限定为上级负责人） [CONFIRMED]
  • 不做审批通过后仍需人工执行的半自动模式 [FACT]
