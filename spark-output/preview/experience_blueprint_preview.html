§0 本次关键判断

判断：在现有权限变更审批模式上新增一条员工侧自助发起通道，同时支持按角色申请和按功能权限申请，不改变底层权限体系和审批引擎。

主要影响：权限发起人从管理员扩展到员工，引入了"申请→审批→自动授权"的新任务链路，需要在管理员配置端、员工申请端、审批处理端三个方向同时承接体验设计。

建议方案：复用现有审批中台和权限授权体系。按角色申请通过后走 RBAC_ROLE 来源，按功能权限申请通过后走 ACL_DIRECT 来源，均在权限详情中标注"自助申请"来源以保可追溯。管理员可分别配置两类可申请范围，并可独立开关。

不建议方案：自建审批引擎、新增权限来源枚举值、改变现有治理模式核心逻辑。

关键待确认：审批人来源规则、自助申请与三种已有治理模式的互斥/叠加关系声明。

§1 需求输入摘要

需求背景

[FACT] 目前企业员工权限分配由管理员集中处理。中大型企业员工多、流动快，权限申请需私下找管理员，沟通成本高，授权时效不稳。

目标用户

[FACT] 员工（申请人）、权限管理员（配置者）、审批人（处理申请）、超管（开关控制者）。

业务目标

[FACT] 把部分权限申请工作从管理员侧分散到员工侧，降低沟通成本，缩短授权等待时间，同时保留管理员对申请范围和审批流程的控制。

产品目标

[FACT] 员工可查看自己当前权限、主动申请权限、查看申请记录和审批状态。管理员可控制开关、可申请范围、审批流程。初步价值指标：至少 3 家客户使用。

功能范围

[FACT] 管理员配置自助申请能力（设置可申请范围、审批方式）、员工查看自己权限、员工提交权限申请、审批人处理申请（同意/拒绝，通过后自动授权）、管理员关闭自助申请能力。

明确约束

[FACT] 只有最高权限管理员可开关此能力。开启前需设置可申请范围和审批方式。关闭时不能影响审批中的申请。PC 端。同时支持按角色和按功能权限申请。

原始输入缺口

[FACT] 原始文档在员工端规则、审批端规则、能力关闭时的具体行为、模式互斥处理等方面标注了"帮我补充"或留空。

§2 业务场景判断

在现有体系中的位置

[CONFIRMED] 这是一项既有能力扩展——现有体系已有权限变更审批模式（发起→审批→生效），也有按人授权和按角色授权两条成熟的授权路径。自助申请不替代其中任何一条，而是在它们旁边新增一条员工侧发起通道。

与现有能力的关系

[CONFIRMED] 复用的能力：审批中台的流程引擎、审批人配置和审批操作能力；现有 ACL_DIRECT 和 RBAC_ROLE 的权限落点机制；现有治理状态模型中的 draft→pending→approved→effective 链路。

[CONFIRMED] 新增的能力：员工侧权限查看入口；员工侧权限申请入口（按角色 + 按功能权限两条路径）；管理员配置"可申请范围"的能力（角色维度 + 功能权限维度）；"自助申请"作为权限来源标注；自助申请能力的全局开关。

是否改变治理模式

[CONFIRMED] 不改变现有三种治理模式的内部逻辑。但自助申请与这三种模式存在关系需要显式声明：自助申请依赖权限变更审批模式；与子管理员模式的关系 [GAP]；与双管理员模式的关系 [GAP]。

最大业务不确定性

员工申请权限的审批人从哪来——如果默认取直属上级但员工没有明确的上级，整个申请链路会在第一步就断掉。

如果判断错了会怎样

如果把自助申请误判为独立新模式，会导致自建审批闭环、引入新权限来源枚举、或重复建设授权落点——增加不必要的系统复杂度。

§3 需求成立性判断

收益

[CONFIRMED] 对中大型企业，员工自助申请可以减少权限分配的管理员瓶颈。申请全流程可追踪，比线下口头沟通更规范。

代价

[CONFIRMED] 系统侧需新增员工端两个页面、管理端可申请范围配置能力、审批端适配。管理员存在学习成本；配置不当可能带来安全风险。

更低成本替代路径

[CONFIRMED] 可先只做员工权限查看（只读），不做申请流程——但只能解决"知情"问题，解决不了"申请效率"问题。

建议

[CONFIRMED] 建议进入正式体验设计。需求方向成立。

§4 推荐业务边界

推荐能力形态

[CONFIRMED] 员工侧：查看自己所有权限（含来源标注）；按角色申请；按功能权限申请；查看申请记录和审批状态。

[CONFIRMED] 管理端：全局开关；可申请角色范围配置；可申请功能权限范围配置；审批流程配置。

[CONFIRMED] 审批端：查看申请内容；同意/拒绝操作；通过后系统自动完成授权。

不推荐能力形态

[CONFIRMED] 不推荐：员工自定义自由文本权限申请；员工端直接看到所有系统角色/权限；申请通过后绕过审批立即生效。

与现有能力的边界

[CONFIRMED] 复用：审批中台流程引擎、ACL_DIRECT/RBAC_ROLE 授权落点、权限详情查询。新增：自助申请全局开关、可申请范围配置、申请记录查询、权限来源标注"自助申请"。

体验蓝图

§0 本次关键设计判断

判断：体验设计的核心是把"管理员集中授权"的单通道扩展为"管理员授权 + 员工自助申请"的双通道，同时保证员工侧低认知门槛、审批人侧判断信息充分、管理员侧配置可控。

主要影响：员工端需要在现有权限体系中新增两条申请路径（角色/功能），且两条路径的信息结构、申请粒度、审批判断依据不同。管理端需新增双维度范围配置能力。

建议方案：员工端以"我的权限"为前置页。申请入口按角色和功能分两个 Tab。管理端用单页 Tab 切换承载双维度配置。审批端扩展"当前权限"和"通过后变化"两个信息区。关闭能力时弹窗展示在途申请清单并强制选择处理策略。

不建议方案：角色和功能合并为统一表单；关闭能力时不做在途确认；员工端展示系统全部权限。

关键待确认：GAP-01~03 基于推荐方案推进，详见 §8。

§2 交互流程总览

分角色流程

员工路径：我的权限（查看）→ 申请权限（选择角色或功能）→ 填写原因并提交 → 申请记录（追踪状态）→ 收到结果通知

审批人路径：审批中心待办 → 审批详情 → 同意/拒绝 → 结果确认

管理员路径：权限管理后台 → 自助申请配置（角色范围/功能范围/审批规则）→ 开启能力 → 申请记录监控

超管路径：权限管理模式页 → 自助申请开关 → 关闭时处理在途申请

异常流程重点

  • 审批人不存在：提交时阻断，引导员工联系管理员
  • 自动授权失败：通知管理员人工处理
  • 能力关闭时有在途申请：强制超管选择处理策略后才允许关闭
  • 可申请范围为空：员工端展示空状态引导
  • 重复申请：已拥有权限在列表中置灰不可选

§5 异常与阻断流程
异常一：审批人不存在
发生时机
员工点击"提交申请"时
触发条件
审批人来源规则未匹配到有效审批人

阻止提交

异常二：自动授权失败
发生时机
审批人点击"同意"后
触发条件
系统尝试自动授予权限时发生异常

审批人端弹窗提示；管理员端通知

申请状态标记为"授权异常"。管理员收到通知。

审批人继续处理其他待办；管理员人工补授权

发生时机
超管点击关闭开关
触发条件
系统中存在待审批或审批中的申请
反馈形式
弹窗
系统反馈
弹窗展示在途申请数量和状态分布，提供三种处理策略：全部自动拒绝/等待处理完毕/逐单处理
用户下一步
超管选择处理策略并确认关闭
异常四：可申请范围为空
发生时机
员工进入申请页
触发条件
管理员开启了能力但未配置任何可申请范围
反馈形式
空状态（页面占位）
系统反馈
展示空状态插图 + "当前暂无可申请的权限，如需帮助请联系管理员"
异常五：重复申请已拥有的权限
发生时机
员工在可申请列表中看到自己已拥有的权限
触发条件
员工通过其他途径已拥有该权限
反馈形式
列表项置灰 + "已拥有"标签
系统反馈
该项不可点击、不可勾选
