§0 本次关键判断

判断：在现有权限管理体系上叠加员工自助申请能力，核心挑战不是加一个申请入口，而是要在多来源权限模型里新增一条员工发起的获取路径，同时保证它与现有治理模式可共存、可解释、可关闭。

主要影响：权限来源模型、治理状态机、审批闭环和管理端配置结构都会受影响。员工端的权限「可看懂」和「可申请」依赖同一套业务语言翻译层，如果这层没建好，两端同时失败。

建议方案：复用现有审批引擎和权限写入能力，新增自助申请配置层（管理员侧）和申请-查看层（员工侧）。先建权限的业务语言翻译层作为两端共享基础，再往上搭申请和审批能力。

不建议方案：另建一套独立的审批和授权引擎；或在未解决权限业务语言翻译前直接做申请入口。

关键待确认：自助申请与双管理员模式、子管理员隔离模式的叠加行为尚未明确。

§1 需求输入摘要

需求背景

当前企业员工权限分配由管理员或超管集中处理。中大型企业员工数量多、人员流动频繁，权限新增和变更的线下沟通成本高，授权时效不稳定。希望通过员工自助申请分散管理压力，同时保留管理员对申请范围和审批流程的控制。

目标用户

  • 普通员工：需要查看已有权限并发起权限申请
  • 权限管理员：配置可申请范围和审批流程
  • 审批人：处理员工提交的权限申请
  • 超级管理员：控制自助申请能力的开启与关闭

业务目标

  • 降低管理员处理权限申请的线下沟通成本
  • 规范权限申请流程，使申请、审批、授权可追踪
  • 保持管理员对权限分配的最终控制权

产品目标

  • 新增员工自助申请权限能力
  • 员工可查看当前权限、提交申请、追踪审批状态
  • 管理员可配置申请范围、审批方式、开关能力
  • 审批通过后系统自动授权
  • 至少 3 家客户使用

输入文档已知缺口

  • 员工端业务规则未填写
  • 审批端业务规则未填写
  • 管理员关闭能力的在途申请处理方式未定义
  • 与现有治理模式的具体兼容规则未展开

§2 业务场景判断

需求在现有体系中的位置

本需求是对现有权限管理体系的能力叠加，不替代任何已有能力。

  • 与「权限变更审批模式」的关系：叠加共存。现有审批模式是管理员发起权限变更 → 审批 → 生效；本需求新增员工发起申请 → 审批 → 系统自动授权。两条路径共用审批引擎和权限写入层，但发起方、申请表单结构、授权执行方式不同。
  • 与权限来源模型的关系：在现有来源基础上，新增一条由员工发起、经审批后系统自动写入的来源路径。需要独立标识，不应混入现有的直授或角色来源。
  • 与治理模式的关系：自助申请能力本身是一种新的治理触发方式，须与双管理员、子管理员隔离等模式各自定义叠加行为。

最大业务不确定性

自助申请与双管理员模式、子管理员隔离模式的叠加行为尚未定义。这两个问题会直接影响审批流程设计和管理端配置结构。

如果这个判断错了：如果自助申请实际需要替代而非叠加，则管理端需要合并两个配置入口、统一审批流程定义、迁移旧的审批数据——整套方案结构需要重做。

§3 需求成立性判断

用户问题真实性

员工不知道自己的权限、缺权限时只能私下找管理员——这是一个真实存在的体验问题，在中大型企业和权限频繁变更的组织中尤为突出。

业务价值

  • 将权限申请的沟通从线下无序转移到线上标准化
  • 申请记录可追踪、可审计，补上了权限治理链路中缺失的「谁申请了什么、谁批的、为什么」
  • 员工获得自主查看和申请权限的能力

系统代价

  • 需要新建权限的业务语言翻译层——这是最大的隐性成本
  • 来源模型需要扩展以容纳新的获取路径
  • 管理端新增自助申请配置模块
  • 需要额外设计治理模式兼容矩阵

更低成本替代路径

  1. 只做「查看我的权限」不做申请：先解决信息不透明问题，改动范围更小
  2. 在现有审批模式中增加「员工发起」选项：不另建一套，但灵活性降低

结论：建议进入正式体验设计。

§4 推荐业务边界

推荐能力形态

  1. 权限业务语言翻译层（本次新增）：技术权限表达 → 业务能力描述
  2. 员工权限查看能力（本次新增）：以业务语言呈现自身权限清单
  3. 员工权限申请能力（本次新增）：在可申请范围内发起申请
  4. 管理员自助申请配置能力（本次新增）：开启/关闭、配置范围、配置审批
  5. 审批处理能力（复用现有审批管理）：审批后自动授权

不推荐能力形态

  • 员工端不做完整权限体系浏览
  • 管理员端不另建独立于现有权限管理的配置体系
  • 不在本次范围内改造审批流程引擎本身

§8 约束与不做什么

硬约束

  • 自助申请能力必须可被管理员关闭，关闭时在途申请继续流转
  • 员工只能申请管理员已配置范围内的权限
  • 审批通过后系统自动授权，不得要求管理员手动执行
  • 必须复用现有审批管理引擎
  • 权限业务语言翻译层必须同时支撑查看和申请两端

不做什么

  • 不做员工端完整权限管理后台
  • 不改造审批流程引擎本身
  • 不改变现有权限来源模型的优先级和计算规则
  • 不支持员工申请超出范围的权限

§0 本次关键设计判断

判断：在现有权限管理体系中嵌入员工自助申请能力，核心设计策略是「先翻译再交互」——用统一的权限业务语言翻译层同时支撑员工查看、员工申请、管理员配置三个端面。

主要影响：员工端需要全新的信息架构来表达「我有什么权限」和「我可以申请什么」两个概念；管理端需要在现有权限管理页面中嵌入自助申请配置；审批端需要同时兼容两条路线。

建议方案：先定义翻译层表达规则，以此为底座分别设计员工查看页、员工申请页、管理员配置页和审批处理页。复用现有审批管理的表单-流程-处理链路，仅扩展发起方为员工角色。

不建议方案：跳过翻译层直接做申请入口；或把自助申请做成完全独立的权限子系统。

关键待确认：权限业务语言翻译层的语义建模范围；三个层级一 GAP 基于推荐方案推进。

§1 旅程图

旅程图 1：普通员工 — 自主获取权限

阶段 1：了解自己有什么权限
用户目标搞清楚自己当前能做什么、不能做什么
关键触点工作台 → 我的权限入口 → 权限清单页
用户信心低。员工通常不知道自己有什么权限
痛点权限以技术语言呈现，员工看不懂能力边界
↓关键转折：从「我有什么」到「我缺什么」——员工能感知到自己做不了某事
阶段 2：发现权限缺口
用户目标确认自己缺少某个操作能力，并找到对应申请项
关键触点权限清单页 → 申请权限入口 → 可申请范围列表
用户信心中低。不确定该申请什么
痛点权限名称与实际任务之间的映射不直观
↓关键转折：在可申请列表中找到了匹配需求的选项——如果找不到，链路就断了
阶段 3：提交权限申请
用户目标填写原因并提交，期望尽快获得权限
关键触点申请表单 → 确认弹窗 → 提交成功页
用户信心中。不确定审批人会怎么判断
痛点不知道审批通过后多久生效
↓关键转折：提交后进入等待——如果没有主动通知，员工需要反复查看
阶段 4：等待与追踪
用户目标知道申请走到哪了、什么时候有结果
关键触点我的申请列表 → 申请详情页
用户信心中低。无通知时需反复查看
痛点审批中无进度可见；长时间无响应不知道催谁
↓关键转折：审批完成后触发通知——通过则确认生效，拒绝则知道下一步
阶段 5：确认权限生效
用户目标确认申请的权限已经可以使用
关键触点审批结果通知 → 我的权限页
用户信心高。权限已生效
痛点通知只说「通过」不说「何时生效」导致误判

旅程图 3：权限管理员 — 配置自助申请

阶段 1：评估是否开启
用户目标理解自助申请对企业的影响，决定是否开启
痛点没有兼容性检查或影响说明，管理员可能不完全理解
阶段 2：配置可申请范围
用户目标定义员工可申请的权限，确保安全且覆盖需求
痛点需在安全收敛和覆盖需求间找平衡；只能看到技术字段
阶段 3：配置审批流程
用户目标为每个可申请范围指定审批人和方式
痛点如果需要在两处维护审批配置，重复工作量大

M3-3 配置可申请范围
M2-5审批人做出审批决定
用户动作
点击同意或拒绝，填写审批意见（拒绝时必填）
系统反馈
同意：确认弹窗（授权预览）→系统执行授权写入；拒绝：确认弹窗（必填原因）→状态变更
建议文案
同意确认：「确认通过后，系统将自动为 [员工姓名] 授予 [权限名称] 权限。」
下一步
M2-6 确认审批结果

§4 次交互流程

S4管理员关闭自助申请能力
触发条件
管理员或超管在配置页点击关闭开关
用户动作
点击关闭 → 确认关闭
系统反馈
展示关闭影响说明（在途数量、影响范围），关闭后员工申请入口消失，在途继续流转
建议文案
「关闭后，员工将无法提交新的权限申请。当前有 {N} 条在途申请将继续正常流转。确认关闭？」
S3管理员调整已发布的配置
触发条件
修改可申请范围或审批流程绑定
系统反馈
新增立即生效；移除时保护在途申请（旧配置继续）；修改审批流程时在途按旧流程、新申请按新流程
建议文案
移除确认：「移除此项后，员工将无法再申请该权限。当前已有 N 个在途申请不受影响。」

§5 异常与阻断流程

E1 审批人不存在或无效

发生时机员工提交申请后，系统路由审批时
触发条件管理员配置的审批人在申请提交时已失效
反馈形式系统消息通知（站内 + 移动端）+ 申请状态变更
系统反馈申请人：「你的申请已提交，但审批流程配置存在异常，暂时无法进入审批。管理员正在处理中。」；管理员通知：「员工 [姓名] 的权限申请因审批人配置异常无法流转。」
用户下一步申请人等待管理员修复配置后自动恢复流转；管理员更新审批人配置

E2 自动授权写入失败

发生时机审批人同意申请后，系统执行授权写入时
触发条件权限写入接口异常、冲突或校验不通过
反馈形式弹窗（审批人侧）+ 通知（申请人+管理员）+ 状态变更
系统反馈审批人侧：「审批已通过，但系统自动授权时遇到问题。管理员已收到通知。」；申请人：「权限已审批通过但授权遇到技术问题，管理员正在处理。」
用户下一步管理员在后台手动完成授权

E7 治理模式兼容性冲突

发生时机管理员尝试开启自助申请能力时
触发条件当前启用的治理模式与自助申请存在未解决兼容规则
反馈形式阻断弹窗
系统反馈弹窗展示冲突详情、当前启用的模式、冲突原因、建议处理方式。阻止开启。
用户下一步管理员前往处理兼容性配置或联系超管
