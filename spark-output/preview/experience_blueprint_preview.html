§0 本次关键判断

判断：这不是给现有权限页加一个申请入口，而是在当前四种权限来源之外新增一种"员工发起→审批→系统自动授权"的权限获取方式。

主要影响：权限来源模型、生效机制、治理模式互斥约束都会变化，不能按"既有能力扩展"处理。

建议方案：复用现有"权限变更审批模式"的治理框架和审批中台能力，将自助申请定义为该模式下的一种新发起方式，而非独立治理模式。可申请范围优先按角色配置（粒度清晰、员工理解成本低），后续按需扩展功能权限粒度。

不建议方案：新建独立治理模式（会与子管理员模式/双管理员模式产生额外互斥约束）；将自助申请做成纯粹的审批中台表单（会丢失权限来源解释能力）。

关键待确认：自助申请是否复用现有权限变更审批模式；可申请范围按角色还是功能权限配置。

§1 需求输入摘要

需求背景

[FACT] 当前企业员工权限分配由管理员集中处理，中大型企业员工数量多、流动频繁，权限新增和变更工作量较大。

[FACT] 部分企业超级管理员为老板本人，员工需权限时私下找老板处理，沟通成本高、时效不稳。

[FACT] 希望将部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对范围和流程的控制。

目标用户

[FACT] 中大型企业员工（申请者）、权限管理员（配置者）、审批人（处理者）、超级管理员（开关控制者）。初步目标为至少3家客户使用。

业务目标

[FACT] 员工可查看自己当前权限、主动申请所需权限、经审批后自动获得权限、查看申请记录和审批状态。管理员可控制是否开启、可申请范围、审批流程，以及关闭或调整该能力。

功能范围

[FACT] 覆盖五个核心场景：管理员配置自助申请权限、员工查看自己权限、员工申请权限、审批人处理申请、管理员关闭自助申请能力。

明确约束

[FACT] 关闭能力时不能影响正在审批中的申请。配置、审批、校验环节需设置安全保护。需与现有权限治理模式兼容。

需求文档缺口

[GAP] 员工端业务规则、审批端业务规则未定义。可申请范围配置维度未定。管理员关闭能力时的具体处理规则不完整。审批流程自定义还是预设未明确。

§2 业务场景判断

业务定位

这是一项新增能力。现有权限体系不支持员工端主动发起权限获取，所有权限授予均从管理员侧单向操作。

与现有能力的关系

现有权限来源共四种：个人直授、角色授予、应用可见性、协作可见性。自助申请的核心变化不是新建审批流程，而是：权限变更的发起方从管理员变为员工、可申请范围由管理员预先限定、整个能力做成可开关。它应当在现有治理框架内运行。

最大业务不确定性

[GAP] 可申请范围的定义方式（角色 vs 功能权限）尚未确定，会影响员工侧信息架构、管理员配置复杂度、审批语义清晰度。

判断错误影响

如果自助申请需要独立模式运行，状态机设计、互斥规则、审批中台对接方式和权限来源解释模型都需要重新设计。

§3 需求成立性判断

收益

  • [CONFIRMED] 将权限申请从线下沟通转为系统闭环
  • [CONFIRMED] 管理员从逐人操作变为设定范围+审批确认
  • [CONFIRMED] 申请记录可追踪可审计

代价

  • [CONFIRMED] 新增申请单业务对象及配套数据结构、状态流转和界面
  • [CONFIRMED] 管理员配置责任扩展，初始配置和调整成本不容忽视
  • [CONFIRMED] 培训和支持成本可能上升
  • [CONFIRMED] 需处理与现有治理模式兼容互斥逻辑

替代路径

  • 优化现有按角色批量授权+权限到期自动提醒，不引入员工侧发起链路
  • 在权限不足时给出申请指引（告诉员工联系谁），不建设完整申请审批系统

成立性结论

[CONFIRMED] 需求成立。建议进入正式体验设计，但须优先确认层级一问题。

§4 推荐业务边界

推荐能力形态

  • 自助申请作为权限变更审批模式的发起方式运行
  • 管理员在权限管理模块统一完成开启、设范围、指定审批
  • 员工在"我的权限"页面查看已有权限并触达申请入口
  • 审批人在审批中台统一待办中处理申请
  • 申请全生命周期可追踪

不推荐能力形态

  • 将自助申请做成独立治理模式
  • 在审批中台直接建业务表单取代权限侧申请入口
  • 首次版本支持数据权限申请

与现有能力的边界

复用：审批中台表单承载、流程引擎、待办列表；权限系统角色/功能权限配置、治理状态模型。

新增：申请单对象、可申请范围配置模型、自助申请开关、申请→授权自动执行链路。

§8 约束与不做什么

硬约束

  • 不能破坏现有四种权限来源的定义和优先级
  • 审批流程必须对接审批中台，不得自建审批引擎
  • 首次版本不做数据权限的自助申请
  • 能力关闭时不得自动回收已授权权限
  • 配置、审批、校验环节必须设置安全保护

依赖项

  • 审批中台需支持将自助申请作为审批表单类型接入
  • 权限系统需支持新的权限来源标识（自助申请）

不做什么

  • 不新建独立的权限治理模式
  • 不在权限管理模块内自建审批流程引擎
  • 不改变现有角色边界定义
  • 首次版本不覆盖非标准员工身份的权限申请

§0 本次关键设计判断

判断：体验设计的核心是把"员工→管理员→系统"的三角授权关系，收敛为"员工→可申请范围→审批→自动授权"的线性闭环，并且让三个角色的控制感都不丢失。

主要影响：员工侧需从"查看已有权限"自然过渡到"申请缺失权限"；管理员侧需在同一配置页内完成开启+设范围+指定审批；审批人侧需在待办中不混淆自助申请和其他权限变更。

建议方案：员工侧"我的权限"→"申请权限"形成连续页面关系。管理员侧单页配置+锚点导航。审批人侧复用审批中台待办容器，通过来源标签区分自助申请。

不建议方案：将配置拆分到两个入口；员工侧只给空白搜索框；将拒绝设为终态无引导。

关键待确认：可申请范围按角色还是功能权限；审批流程是否在权限管理侧直接指定审批人。

§3 主交互流程

主流程一：员工发起权限申请

节点 1.1：进入"我的权限"
用户动作
员工进入"我的权限"页面，查看当前拥有的权限列表
系统反馈
页面展示已有权限清单，按角色和功能权限分组，每项标注来源标签（直接授予/来自角色/自助申请）
建议文案
页面标题："我的权限"。来源标签：直接授予 / 来自角色：{角色名} / 自助申请
下一步
点击"申请更多权限"进入节点 1.2
节点 1.2：进入"申请权限"
用户动作
员工点击"申请更多权限"，浏览可申请的角色/权限列表
系统反馈
顶部"已拥有"摘要条可折叠；主体区域按角色分组展示可申请权限卡片，已拥有标记"已拥有"置灰
建议文案
页面标题："申请权限"。空状态："当前暂无可申请的权限，如有需要请联系管理员"
下一步
点击某个角色/权限的"申请"按钮进入节点 1.3
节点 1.3：填写申请信息并提交
用户动作
确认目标权限和包含的功能，填写申请原因，查看预估审批人信息后提交
系统反馈
展示目标权限详情（角色名+包含的功能列表）；申请原因必填；展示预估审批人和审批方式。提交后 toast "申请已提交"，自动跳转申请详情页
建议文案
申请原因 placeholder："请说明申请该权限的原因，以便审批人了解"。提交按钮："提交申请"
下一步
自动跳转到申请详情页
节点 1.4-1.5：查看详情 + 收到结果
系统反馈
详情页展示：申请内容、原因、提交时间、审批进度、审批人。审批通过：状态更新"已通过→已生效"，通知"权限已生效"。审批拒绝：展示拒绝原因，底部"修改并重新申请"按钮
建议文案
状态标签：审批中 / 已通过 / 已拒绝。拒绝后按钮："修改并重新申请"
下一步
通过→返回"我的权限"；拒绝→修改重提

主流程二：管理员配置并开启自助申请

节点 2.1-2.4：进入配置 → 设定范围 → 指定审批 → 预览并开启
用户动作
管理员在权限管理模块进入"自助申请设置"，按顺序完成：选择可申请范围（角色或功能权限）→ 指定审批人来源和多人审批方式 → 查看配置摘要 → 确认后开启
系统反馈
单页表单+锚点导航承载三项配置。每项配置区展示实时预览。开启前自动校验：范围不为空、审批人有效、无治理模式冲突。开启后状态切换为"已开启"，toast 提示
建议文案
页面标题："自助申请设置"。开启按钮："开启自助申请"。成功 toast："自助申请能力已开启"。配置摘要区展示已选范围和审批人

主流程三：审批人处理申请

节点 3.1-3.3：识别待办 → 查看详情 → 审批决策
用户动作
审批人在待办列表识别"权限申请"来源标签的待办，点击进入详情页查看申请内容和申请人已有权限，做出同意或拒绝决策
系统反馈
详情页三区展示：申请信息（申请人+目标权限+原因）→ 参考信息（申请人已有权限）→ 操作区（同意/拒绝+审批意见）。同意后自动授权+toast；拒绝后通知员工
建议文案
同意按钮："同意"。拒绝按钮："拒绝"。同意后 toast："已同意，权限已自动授予"。拒绝意见 placeholder："请说明拒绝原因"

§4 次交互流程

员工查看申请记录

从"我的权限"或工作台进入"申请记录"列表页。按状态筛选（全部/审批中/已通过/已拒绝）。每条记录展示目标权限、提交时间、当前状态和审批人。点击进入申请详情页。

员工撤回申请

在审批中的申请详情页点击"撤回申请"，弹窗确认后状态更新为"已撤回"。审批人待办自动消失。Toast 提示"申请已撤回"。

员工重新申请（拒绝后）

在已拒绝申请详情页点击"修改并重新申请"，进入预填上次内容的申请表单页。员工可修改目标权限和原因后重新提交，生成新申请单。

管理员调整可申请范围

在已开启状态下点击"调整配置"，修改可申请范围。变更不影响已提交申请，仅对新申请生效。保存后 toast "可申请范围已更新"。

管理员关闭能力

点击"关闭自助申请"，弹窗展示影响说明：当前审批中申请数、关闭后新申请不可发起、存量申请继续审批、已授权不回收。确认后入口隐藏，toast "自助申请能力已关闭"。

§5 异常与阻断流程

异常一：申请范围内无可申请项

发生时机员工进入"申请权限"页面
触发条件范围为空或员工已拥有全部可申请权限
反馈形式页面空状态（操作前说明）
系统反馈空状态插图 + "当前暂无可申请的权限，如有需要请联系管理员"
用户下一步联系管理员确认或等待管理员调整范围

异常二：审批人不存在

发生时机员工提交申请时或提交后
触发条件审批人被删除或离职
反馈形式管理端 banner + 员工端详情说明
系统反馈管理端配置页顶部 banner："审批人配置异常"。员工端详情页："审批人暂时无法处理，系统已通知管理员"
用户下一步管理员点击 banner 重新设置审批人；员工等待

异常三：审批超时

发生时机申请提交后超过预设时长未审批
触发条件审批人在超时阈值内未处理
反馈形式系统自动催办 + 员工手动催办
系统反馈员工详情页显示"已等待 {N} 小时" + "提醒审批人"按钮。系统自动向审批人发送催办提醒
用户下一步员工点击催办或联系管理员

异常四：授权时权限已被修改

发生时机审批通过后系统自动授权时
触发条件目标权限配置在审批期间变更
反馈形式管理端弹窗告警 + 员工端状态说明
系统反馈员工申请状态更新为"授权异常"。管理端弹窗告警，通知手动处理
用户下一步管理员手动授权；员工等待管理员处理

异常五：能力关闭时有审批中的申请

发生时机管理员关闭自助申请能力
触发条件关闭时存在 pending 状态的申请
反馈形式关闭确认弹窗展示存量申请数
系统反馈弹窗展示审批中申请数和影响说明。关闭后新申请入口隐藏，存量申请继续审批
用户下一步管理员可查看存量申请；员工继续等待审批

异常六：员工被停用或离职

触发条件员工账号状态变更为停用或离职
系统反馈该员工所有 pending 申请自动撤回。已生效权限按现有回收机制处理
用户下一步不适用（员工已不可操作）

异常七：与现有治理模式冲突

发生时机管理员尝试开启自助申请
触发条件已开启子管理员模式或双管理员模式且存在互斥
反馈形式弹窗阻断
系统反馈弹窗："当前已开启「{冲突模式名}」，与该模式存在互斥。如需开启自助申请，请先关闭该模式。"
用户下一步管理员先关闭冲突模式或等待确认兼容规则
