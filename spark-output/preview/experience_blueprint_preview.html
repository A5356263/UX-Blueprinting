§0 关键设计判断

判断：在现有权限治理体系中新增一条"员工自助申请"的权限来源通道，本质是扩展来源模型和生效路径，不是做一个独立的申请表单。

主要影响：涉及管理员、员工、审批人三类角色；底层触及申请单状态机、审批后自动授权生效机制、权限来源可追溯性；依赖审批中台回写链路是否已闭环。

建议方案：首期收敛为"按角色申请"——管理员配置可申请的角色范围并绑定审批流程，员工从角色列表中选择申请，审批通过后自动授权。角色天然有"模板化"语义，能同时降低管理员配置负担和员工理解门槛。

不建议方案：首期同时开放角色、功能权限、数据权限三层申请。三层叠加会让管理员配置变得复杂，员工也难以理解"我该申请什么"。

关键待确认：自助申请模式与现有三种治理模式的关系是替代、叠加还是子场景？审批中台回写链路是否已具备？

§1 结论与定位

结论：可以做，建议首期收敛为按角色自助申请。

当前产品已有权限变更审批模式、角色授权体系和审批中台基础。这次的改动不是在空地上盖房子，而是在已有的权限治理框架上开一条"员工侧发起"的通道——把原来"管理员主动授权→员工被动接收"的单向模式，扩展为"员工主动申请→审批→自动授权"的双向模式。

产品定位上，这不是一个所有企业都需要的默认能力，而是面向中大型企业、权限变更频繁场景的可选治理工具。管理员的控制感是这条通道能否被接受的前提。

§2 价值论证

现在的问题

中大型企业里，员工需要新权限时只能私下找管理员或老板，沟通成本高、授权时效不稳定。超管或权限管理员被频繁的权限申请和核对工作淹没，当超管是老板本人时矛盾更突出。员工没有自助查看"我有什么权限"的入口，只能反复向管理员确认。

为什么不能继续靠线下兜底

随着企业规模增长，线下沟通的成本是非线性的——每多一个员工就多一条潜在的消息通道。权限变更越频繁，管理员越容易成为瓶颈。同时，线下沟通没有记录、不可追溯，出了权限问题没法定位是谁在什么时候因为什么原因给了权限。

收益

  • 权限申请从"找人"变成"走流程"，减少线下沟通成本
  • 申请记录可追踪，权限来源可解释
  • 管理员从"被动响应"变为"主动治理"，只处理审批而非每条都手动配置
  • 员工能自助查看已有权限，减少反复确认

系统代价

  • 需要新增申请单对象和完整的状态机
  • 需要和审批中台对接回写链路
  • 需要在管理端新增一套配置界面
  • 权限来源模型需要扩展新的来源类型
  • 后续权限查询和排障需要能区分自助申请来源

§3 角色与功能范围

超级管理员/权限管理员

  • 现有能力边界：可在后台按人授权、按角色授权、配置治理模式、查看权限结果 [FACT]
  • 本次新增能力：开启/关闭自助申请能力、配置可申请的角色范围、绑定审批流程、查看自助申请产生的权限记录 [CONFIRMED]

员工

  • 现有能力边界：被动接收管理员授予的权限，无自助查看和申请入口 [FACT]
  • 本次新增能力：查看自己当前拥有的权限及来源、浏览可申请的角色列表、提交权限申请并说明原因、查看申请记录和审批状态 [CONFIRMED]

审批人

  • 现有能力边界：在审批中台中处理各类审批任务 [FACT]
  • 本次新增能力：查看员工提交的权限申请详情（申请人、申请角色、申请原因）、同意或拒绝申请并填写审批意见 [CONFIRMED]

功能单元

F1：自助申请开关与配置 [P0] — 角色：超管。开启/关闭自助申请能力。

F2：可申请角色范围配置 [P0] — 角色：超管。从系统已有角色中选择可申请范围。

F3：审批流程绑定 [P0] — 角色：超管。为自助申请绑定审批流程模板。

F4：我的权限查看 [P1] — 角色：员工。按应用聚合展示当前权限，标注来源。

F5：权限申请提交 [P0] — 角色：员工。选择角色、填写原因、提交申请。

F6：申请记录与状态追踪 [P1] — 角色：员工。按时间倒序展示申请记录和状态。

F7：申请审批处理 [P0] — 角色：审批人。查看详情、同意/拒绝、填写意见。

§6 体验风险与设计策略

风险一：管理员不敢开

配置信息密度过高、概念边界模糊导致管理员保守不开启。策略：首期只开放按角色申请，配置页采用渐进披露，高级选项折叠收起。

风险二：员工看不懂角色名

角色名称与实际权限内容脱节。策略：角色列表提供详情展开入口，用通俗语言描述角色包含的关键功能和应用。

风险三：审批通过但权限没到账

审批中台回写链路不通或失败。策略：加入"授权处理中"中间状态，授权失败立即通知管理员。

风险四：关闭能力时在途申请处理不清

管理员不知道关闭后会发生什么。策略：关闭前展示确认弹窗，明确告知在途申请数量和关闭后处理方式。

风险五：权限来源混乱

自助申请与管理员直授的权限无法区分。策略：权限页标注来源，后台支持按来源筛选，审计日志记录完整链路。

§7 体验承接要求

按角色承接

  • 超管/权限管理员：自助申请配置页（开关、角色选择、审批流程绑定、高级设置）、配置变更后的状态提示、关闭确认弹窗
  • 员工：我的权限页（权限清单+来源标注）、申请角色页（角色列表+详情展开+已拥有标注）、申请提交页（原因填写）、申请记录页（状态追踪+审批意见）
  • 审批人：审批详情页（申请人信息、申请角色及权限详情、申请原因、同意/拒绝操作+审批意见）

按流程承接

  • 管理员首次开启自助申请的完整配置流程
  • 管理员调整配置/关闭能力的流程（含在途申请提示）
  • 员工查看权限 → 发现缺失 → 浏览角色 → 查看详情 → 提交申请 → 等待审批 → 查看结果的完整链路
  • 审批人收到审批 → 查看详情 → 同意/拒绝的处理链路
  • 自动授权成功/失败的后续处理分支

按异常承接

§5 中列出的 E1-E8 全部异常场景的反馈设计。

按状态承接

申请单全部状态（待审批、已通过、已生效、已拒绝、已撤回）的页面呈现和文案；自助申请能力全局状态（已开启、已关闭）对员工端入口和页面的影响。

§8 约束与不做什么

硬约束

  • [FACT] 只有最高权限管理员可以开启或关闭自助申请能力
  • [CONFIRMED] 首期只支持按角色申请
  • [CONFIRMED] 不改变现有权限的授予来源和治理模型
  • [GAP] 与子管理员模式、双管理员互审模式、权限变更审批模式的关系待确认

依赖项

  • [FACT] 依赖审批中台提供流程模板和审批处理能力
  • [GAP] 依赖审批中台与权限系统之间的回写链路
  • [CONFIRMED] 依赖现有角色管理体系

排除项

  • [CONFIRMED] 本期不做功能权限和数据权限级别的自助申请
  • [CONFIRMED] 本期不做批量申请
  • [CONFIRMED] 本期不做移动端
  • [CONFIRMED] 不改变现有角色管理流程

  2. 审批中台回写链路是否已具备？如果不存在，自动授权链路断裂。

§0 关键设计判断

判断：自助申请的核心体验不是"做一个申请表单"，而是让三类角色各自在关键决策点上有清晰的信息支撑。

主要影响：管理端配置页是使用率的第一道门槛；员工端角色列表必须有"角色→实际权限"的解释层；审批详情须让审批人充分了解申请全貌。

建议方案：管理端单页表单+锚点导航；员工端路径收敛为看权限→选角色→看详情→写原因→提交→追踪；审批人侧所见即所得。

不建议方案：管理端用步骤条；员工端角色列表纯名称不加解释层。

关键待确认：自助申请与现有治理模式的关系（基于推荐方案推进）。审批中台回写链路假设已具备。

§1 旅程图

超管/权限管理员

了解能力 → 首次配置 → 持续治理 → 关闭或调整

信心变化：中低→中→高→中。转折点：看到配置说明后尝试；配置完成状态确认；遇到需要关闭的情况。

员工

了解权限现状 → 选择要申请的权限 → 等待审批 → 获得权限或重新申请

信心变化：低→中→中→（通过时高/被拒时低）。转折点：发现缺失权限看到申请入口；收到审批结果。

审批人

收到审批任务 → 判断是否批准 → 完成审批

信心变化：中→高→高。转折点：进入审批详情获取充分信息。

§3 主交互流程

管理员线

节点 A1：进入自助申请配置页

超管在管理后台导航中找到"自助申请权限"入口并点击。系统展示当前能力状态及配置项。仅超管可见。

节点 A2：配置可申请角色范围

从已有角色列表中选择一个或多个角色。实时展示已选数量，每个角色可展开查看权限详情。至少选择一个角色后才能开启。

节点 A3：绑定审批流程

从审批流程模板列表中选择。展示流程简要预览。无可选流程时引导去审批管理创建。

节点 A4：开启能力

校验配置完整性后切换开关。校验通过toast"自助申请权限已开启，员工端已出现申请入口"。校验不通过标红对应缺失项。

节点 A5：查看运行状态

展示状态摘要："当前可申请角色：N个 | 审批流程：XXX | 今日申请：M条 | 在途：K条"。

节点 A6：关闭能力

弹出确认弹窗展示在途申请数量和处理说明，确认后关闭。在途申请继续走完（推荐方案），已通过权限不受影响。

员工线

节点 B1：查看我的权限

按应用分组展示权限列表，每项标注来源（"管理员授予"/"自助申请"）。若能力已开启引导"申请更多权限"。

节点 B2-B3：浏览可申请角色

卡片式展示角色列表，每张含角色名、描述、权限概要。已拥有标注"已拥有"。展开可查看详细权限说明。

节点 B4-B5：提交申请

确认角色后进入提交页，展示角色权限摘要+申请原因输入框。校验原因非空、无重复申请。提交成功toast并跳转记录页。

节点 B6-B7：追踪与结果

申请记录列表按时间倒序展示，状态标签区分颜色。已生效可跳转"我的权限"验证；已拒绝展示审批意见+重新申请按钮。

审批人线

节点 C1-C2：查看申请详情

审批中心待处理列表展示概要→进入详情页查看完整信息（申请人、角色权限、原因、已有权限）。

节点 C3-C4：做出决定

同意/拒绝+填写意见。同意后触发自动授权；拒绝后通知员工。审批完成自动返回列表。

§4 次交互流程

管理端

S-A1 调整可申请角色范围：在已开启状态下增删角色→系统检查在途→有在途时弹窗提示→确认保存生效。

S-A2 切换审批流程：重新选择模板→提示新流程对在途无影响→确认保存。

S-A3 查看申请明细：进入申请记录列表→按状态/角色/时间筛选→查看详情或手动介入。

员工端

S-B1 撤回申请：对待审批的申请点击撤回→弹窗确认→状态变为已撤回（终态）。

S-B2 重新申请：对已拒绝的申请点击重新申请→跳转到提交页预填信息→修改后重新提交。

S-B3 权限变更通知：自助申请的权限被回收时→系统通知员工→可重新申请。

§5 异常与阻断流程

异常反馈形式系统反馈用户下一步
E1：无可申请角色页面空状态"暂无可以申请的角色，如有需要请联系管理员"联系管理员
E2：自助申请已关闭入口隐藏+页面提示"自助申请权限功能暂未开放"联系管理员
E3：角色已被删除Toast阻断"该角色已被移除，请选择其他角色"返回重新选择
E4：审批人不存在站内通知+状态标记通知管理员手动转派；员工侧"审批异常"管理员转派
E5：自动授权失败Toast+通知+状态标记通知管理员手动授权管理员手动授权
E6：重复申请提交前阻断提示"该角色已有申请正在审批中"等待或撤回
E7：关闭时在途申请确认弹窗"当前有 N 条申请在审批中"确认关闭或取消
E8：治理模式冲突阻断弹窗说明冲突情况确认后继续或取消
