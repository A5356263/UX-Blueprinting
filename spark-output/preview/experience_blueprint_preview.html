§0 本次关键设计判断

判断 1：无权限拦截页采用"信息告知 + 行动引导"双层结构

  • 主要影响：无权限拦截页（S1 核心触点）
  • 建议方案：拦截页上方告知缺少的具体权限名称和可申请状态（信息层），下方提供"去申请"按钮引导进入权限中心申请流程（行动层）。员工不需要离开拦截页理解全部信息。
  • 不建议方案：只显示"无权限"并让员工自己去找申请入口。根据旅程分析 Stage 1，员工在没有引导的情况下大概率放弃操作。
  • 关键待确认：拦截页能否准确识别缺少的权限并判断可申请状态；如果网络异常或权限信息不可达，需要降级文案。

判断 2：权限申请采用单页 Drawer 而非步骤条

  • 主要影响：权限申请流程（S1、S4）
  • 建议方案：使用 Drawer 承载申请流程——上方展示可申请的权限列表（含搜索/分类），下方为申请理由输入区和提交按钮。选择权限 + 填写理由 + 提交，三步在一页内完成。参考 BFM-01（默认非步骤化），权限申请的任务依赖简单，不需要分步。
  • 不建议方案：使用步骤条（Step 1 选权限 → Step 2 填理由 → Step 3 确认）。这增加了跨步骤往返成本，且每个步骤信息量不足以独立成步。
  • 关键待确认：一次申请可包含多个权限/角色还是每次只能一个（影响列表是否支持多选）。

判断 3：审批侧以"权限申请上下文"为核心展示审批信息

  • 主要影响：审批人处理申请（S2）
  • 建议方案：在 OA 底座审批详情页中，除了展示申请人、申请时间和权限名称外，额外展示申请理由、该权限的简要说明（"有了它可以做什么"）和当前同类权限的持有情况（可选）。审批人不需要切出审批页面查背景信息就能做决策。
  • 不建议方案：只展示"XX 申请了 YY 权限"的极简信息。根据旅程分析 Stage 5，审批人缺乏上下文会导致决策延迟或频繁驳回。
  • 关键待确认：OA 底座审批页面的自定义信息承载能力范围。

判断 4：状态追踪以"当前节点 + 预计时间"为核心信息

  • 主要影响：申请进度追踪（S5）
  • 建议方案：在"我的申请"列表中，每条申请展示：申请时间、权限名称、当前状态（带标签颜色）、处理人（如已进入审批）、预计剩余时间（如可计算）。点击进入详情展示完整审批流转历史。
  • 不建议方案：只显示"审批中"一个状态没有时间参考。根据旅程分析 Stage 4，员工最大的焦虑是"不知道要等多久"。
  • 关键待确认：通知渠道和审批超时策略。

§3 主交互流程

节点 1：无权限拦截

用户动作 员工在操作某功能时，页面顶部出现无权限提示条，或功能入口置灰不可点击。

系统反馈 系统识别当前用户缺少的具体权限，并判断该权限是否可自助申请（非敏感且管理员已开放可申请范围）。

  • 如可申请 → 拦截页显示："你需要 {权限名} 才能使用此功能。此权限可以申请。"
  • 如不可申请（系统排除）→ 拦截页显示："此权限当前不可申请，请联系管理员。"
  • 如无法判断 → 降级显示："无法确认此权限的申请状态，请联系管理员。"

需要前置解释的信息

  • 告知员工缺少的具体权限名称（而非泛化"无权限"）
  • 告知该权限是否可自助申请
  • 如可申请，告知审批人由谁处理（你上级负责人）

建议文案

场景文案
可申请你需要「{权限名}」才能使用此功能，此权限可以自助申请。点击下方按钮前往申请。
不可申请此权限涉及敏感操作，当前不可自助申请。如需使用，请联系你的管理员。
无法判断暂无法确认此权限的申请状态，请联系管理员处理。

下一步

  • 可申请 → 员工点击"去申请"进入申请 Drawer（§3 节点 2）
  • 不可申请/无法判断 → 员工联系管理员

---

节点 2：权限申请 Drawer

用户动作 员工从无权限拦截页点击"去申请"，或从权限中心主动发起申请，打开权限申请 Drawer。

系统反馈

  • 如从拦截页进入：Drawer 中该权限已预勾选/预填充，且为只读不可取消
  • 如从权限中心主动进入：Drawer 展示可申请权限/角色列表，支持搜索和按应用分类筛选
  • 列表中的每个权限项显示：权限名 + 业务说明（"有了它可以做什么"）+ 是否已拥有标签
  • 底部：申请理由输入区（多行文本框）+ 提交按钮

需要前置解释的信息

  • 每个权限项附带业务语义说明，不展示"功能权限""数据权限"等管理术语
  • 如果权限已拥有，标记"已拥有"并置灰不可选择

建议文案

区域文案
Drawer 标题申请权限
预填场景提示缺少「{权限名}」，请确认并补充申请理由
理由占位请说明你需要此权限做什么（如：每月需处理部门报销单）
提交按钮提交申请
已拥有标记已拥有

下一步

  • 选择权限 + 填写理由 → 点击提交 → 系统校验 → 提交成功反馈（§3 节点 3）
  • 权限未选择 → 提交按钮置灰
  • 理由为空 → 提交按钮置灰（或提交时 InlineError 提示"请填写申请理由"）

---

节点 3：提交成功反馈

用户动作 员工点击提交后，系统进行校验。

系统反馈

  • 校验通过 → Drawer 关闭 → 页面底部 Toast："申请已提交，等待上级审批"
  • "我的申请"列表新增一条记录，状态为"审批中"
  • 同步推送审批待办至申请人的上级组织负责人

需要前置解释的信息

  • 告知员工审批人是谁（你的上级 {审批人姓名}）
  • 告知预计处理时间（如有，如"通常在 2 个工作日内处理"）

建议文案

区域文案
Toast申请已提交，已通知你的上级 {审批人姓名} 处理
记录状态审批中

下一步

  • 员工可在"我的申请"列表追踪进度（§4 路径 D）

---

节点 4：审批人处理申请

用户动作 审批人在 OA 底座待办列表中看到待审批申请，点击进入审批详情页。

系统反馈 审批详情页展示：

  • 申请人姓名 + 部门
  • 申请的权限/角色名称 + 业务说明（"有了它可以做什么"）
  • 申请理由（员工填写的原文）
  • 该权限当前在企业内的持有情况（可选，如"当前有 5 人拥有此权限"）

需要前置解释的信息

  • 审批人需要理解"这个员工为什么需要这个权限"——申请理由是最关键信息
  • 如该权限已拥有敏感标记或高风险标签，建议在审批页标注"请注意：此权限涉及 {说明}"

建议文案

区域文案
审批页面标题权限申请审批
申请人信息{员工姓名} · {部门名称}
申请详情权限：{权限名}；理由：{员工填写}
批准按钮批准
拒绝按钮拒绝
拒绝原因输入请说明拒绝原因（将通知申请人）

下一步

  • 批准 → 状态更新为"已批准" → 系统执行权限生效 → 员工收到通知
  • 拒绝（附原因）→ 状态更新为"已拒绝" → 员工收到通知及拒绝原因

---

节点 5：接收审批结果

用户动作 员工收到审批结果通知，或在"我的申请"列表中看到状态变更。

系统反馈

  • 批准 → 状态变为"已生效" → 员工可立即使用权限（如即时生效）或看到预计生效时间
  • 拒绝（附原因）→ 状态变为"已拒绝" → 展示拒绝原因
  • 通知方式：站内通知（默认）+ 可选消息/邮件（取决于企业配置）

需要前置解释的信息

  • 批准后：告知员工"权限已生效，你可以访问 {功能名} 了"
  • 拒绝时：展示拒绝原因，并提供后续引导（"如需更多帮助，请联系你的上级或管理员"）

建议文案

场景文案
通过生效你的「{权限名}」申请已通过，权限已生效。
申请被拒你的「{权限名}」申请未通过。原因：{审批人填写}。如需进一步了解，可联系你的上级或管理员。

下一步

  • 通过 → 员工回到功能页面使用权限
  • 被拒 → 员工可选择联系审批人/管理员，或查看其他可申请权限

§4 次交互流程

路径 C：查看已有权限

触发条件 员工希望了解自己当前拥有哪些权限，或核对某项权限是否已到位。

用户动作 进入权限中心 → 切换到"我的权限"标签页。

系统反馈

  • 按应用或功能分类展示已生效的权限清单
  • 每项权限显示：权限名 + 业务说明 + 生效状态标签（已生效/审批中/已失效）
  • 如果某个权限还在审批中，标注"审批中"而非"已生效"
  • 分类展示，每类可折叠展开

需要前置解释的信息

  • 权限展示使用业务语言（如"查看和编辑报销单"而非"费用管理_编辑"）
  • 如果需要展示来源（来自哪个角色/哪次申请），以次要信息形式展示（小字或 tooltip）

下一步

  • 员工检查完权限后，可返回权限中心首页或发起新申请

---

路径 D：查看申请进度

触发条件 员工提交申请后想了解审批处理状态。

用户动作 进入权限中心 → 切换到"我的申请"标签页。

系统反馈

  • 按时间倒序展示所有申请记录（进行中在前，已完成在后）
  • 每条记录展示：
  • 申请时间
  • 申请的权限/角色名称
  • 当前状态（审批中/已批准/已拒绝/已生效）
  • 处理人（如已进入审批）
  • 操作时间（审批人在何时处理）
  • 点击单条记录进入详情页，展示完整审批流转历史

需要前置解释的信息

  • 审批中 → 告知审批人和预计时间
  • 已批准 → 告知权限将在何时生效（即时/定时）
  • 已拒绝 → 展示拒绝原因和后续建议

下一步

  • 如仍在审批中 → 员工可继续等待
  • 如已拒绝 → 可联系审批人或管理员

---

路径 E：管理员配置可申请范围

触发条件 权限管理员需要设定哪些功能权限和角色允许员工自助申请。

用户动作 进入权限管理后台 → 找到"可申请范围"配置入口。

系统反馈

  • 按"功能权限"和"角色"两个标签页分类展示
  • 每个权限/角色项显示：
  • 名称 + 业务说明
  • 当前状态（可申请/不可申请/系统锁定）
  • 切换开关（系统锁定的不可操作且明确标识）
  • 提供批量搜索和筛选能力
  • 支持批量勾选设置

需要前置解释的信息

  • 系统锁定的权限（敏感权限）明确标注，管理员不可误操作
  • 修改后提示"修改将立即生效，员工侧只能看到你开放的内容"

下一步

  • 保存配置 → 配置即时生效
  • 如有高风险操作，增加二次确认

---

路径 F：撤销申请（待确认）

触发条件 员工提交申请后，在审批人尚未处理前希望撤销。

用户动作 在"我的申请"列表中找到待处理的申请 → 点击"撤销申请"。

系统反馈

  • 如申请状态为"审批中"且审批人尚未处理 → 允许撤销
  • 撤销后状态变为"已撤销" → 审批人待办自动取消
  • 如审批人已处理 → 撤销按钮置灰不可操作

建议文案

场景文案
撤销确认确定要撤销此申请吗？撤销后审批人的待办将自动取消。
撤销成功申请已撤销。

下一步

  • 员工可重新发起申请或放弃

§5 异常与阻断流程

E1：从缺口到申请的链路失败

发生时机：员工在无权限拦截页点击"去申请"时 触发条件：无法确定员工缺少的权限，或该权限信息不可达 判断依据：系统无法获取当前用户的权限缺失详情（网络异常/权限服务不可达） 反馈形式：拦截页降级文案 系统反馈：显示"暂无法确认此权限的申请状态" 用户下一步：联系管理员处理 恢复路径：原路恢复，无信息丢失。网络恢复后员工可从权限中心正常发起申请。

E2：搜索无结果

发生时机：员工在权限申请 Drawer 中搜索权限时 触发条件：搜索关键词无匹配结果 判断依据：权限名称和业务说明均不匹配 反馈形式：Drawer 内空状态展示 系统反馈：显示"没有找到匹配的权限"，并提供替代方案 用户下一步：

  • 更换搜索关键词
  • 浏览全部分类列表
  • 联系管理员（提供"联系管理员"入口）

恢复路径：原路恢复，无信息丢失。

E3：权限不可申请

发生时机：员工在权限申请 Drawer 中选择权限时 触发条件：该权限被系统设为不可申请（敏感权限/管理员未开放） 判断依据：系统级权限标记或管理员配置 反馈形式：该权限项在列表中置灰，并标注不可申请原因 系统反馈：显示"此权限不可自助申请" + 原因 用户下一步：联系管理员申请 恢复路径：原路恢复，无信息丢失。

E4：提交校验失败

发生时机：员工点击提交申请时 触发条件：申请理由为空或不符合要求 判断依据：前端校验 反馈形式：Drawer 不关闭，申请理由输入区下方显示 InlineError 系统反馈：显示"请填写申请理由" 用户下一步：填写申请理由后重新提交 恢复路径：原路恢复，已填写内容不丢失。

E5：审批长时间未处理

发生时机：申请提交后，审批人在规定时间内未处理 触发条件：超过预设处理时限（如 48 小时）审批人仍未操作 判断依据：OA 底座超时规则 反馈形式（推荐方案，待确认）：

  • 首次超时 → 系统自动发送催办通知给审批人
  • 二次超时 → 升级至审批人的上级或后备审批人
  • 员工侧：在申请详情中显示"审批人暂未处理，已发送催办提醒"

系统反馈：根据超时等级执行催办或升级 用户下一步：继续等待或联系审批人 恢复路径：审批人处理或升级后自动流转，申请信息不丢失。

E6：审批拒绝

发生时机：审批人拒绝申请 触发条件：审批人点击拒绝并填写（或未填写）原因 判断依据：审批人操作 反馈形式：通知 + 状态更新 系统反馈：

  • 员工收到通知：申请被拒 + 原因（如有）
  • "我的申请"列表中该记录状态变为"已拒绝"，展示拒绝原因

用户下一步：

  • 如有拒绝原因 → 根据原因调整后重新申请，或联系审批人沟通
  • 如无拒绝原因 → 可联系审批人了解情况

恢复路径：重新发起新的申请流程。

E7：审批通过但权限未生效

发生时机：审批人批准后 触发条件：权限系统生效失败（权限服务异常/配置异常） 判断依据：后端生效结果回调 反馈形式：状态更新 + 说明 系统反馈：

  • 申请状态变为"已批准"（而非"已生效"）
  • 显示"权限生效中，请稍后查看"
  • 系统后台自动重试生效

用户下一步：等待生效结果或联系管理员 恢复路径：后台自动重试，生效后状态更新为"已生效"并通知员工。如果重试仍失败，需要管理员介入。
