# 需求定案：员工自助权限申请

## §0 本次关键判断

**判断**：在现有权限管理体系上叠加员工自助申请能力，核心挑战不是加一个申请入口，而是要在多来源权限模型里新增一条员工发起的获取路径，同时保证它与现有治理模式可共存、可解释、可关闭。

**主要影响**：权限来源模型、治理状态机、审批闭环和管理端配置结构都会受影响。员工端的权限「可看懂」和「可申请」依赖同一套业务语言翻译层，如果这层没建好，两端同时失败。

**建议方案**：复用现有审批引擎和权限写入能力，新增自助申请配置层（管理员侧）和申请-查看层（员工侧）。先建权限的业务语言翻译层作为两端共享基础，再往上搭申请和审批能力。

**不建议方案**：另建一套独立的审批和授权引擎；或在未解决权限业务语言翻译前直接做申请入口。

**关键待确认**：自助申请与双管理员模式、子管理员隔离模式的叠加行为尚未明确。

---

## §1 需求输入摘要

### 需求背景
当前企业员工权限分配由管理员或超管集中处理。中大型企业员工数量多、人员流动频繁，权限新增和变更的线下沟通成本高，授权时效不稳定。希望通过员工自助申请分散管理压力，同时保留管理员对申请范围和审批流程的控制。[FACT]

### 目标用户
- 普通员工：需要查看已有权限并发起权限申请 [FACT]
- 权限管理员：配置可申请范围和审批流程 [FACT]
- 审批人：处理员工提交的权限申请 [FACT]
- 超级管理员：控制自助申请能力的开启与关闭 [FACT]

### 业务目标
- 降低管理员处理权限申请的线下沟通成本 [FACT]
- 规范权限申请流程，使申请、审批、授权可追踪 [FACT]
- 保持管理员对权限分配的最终控制权 [FACT]

### 产品目标
- 新增员工自助申请权限能力 [FACT]
- 员工可查看当前权限、提交申请、追踪审批状态 [FACT]
- 管理员可配置申请范围、审批方式、开关能力 [FACT]
- 审批通过后系统自动授权 [FACT]
- 至少 3 家客户使用 [FACT]

### 明确约束
- 管理员必须保留对申请范围和审批流程的控制 [FACT]
- 关闭自助申请时不能影响在途审批 [FACT]
- 不能与已有权限治理模式冲突 [FACT]
- 可申请范围按角色或功能权限配置 [FACT]

### 输入文档已知缺口
- 员工端业务规则未填写 [FACT]
- 审批端业务规则未填写 [FACT]
- 管理员关闭能力的在途申请处理方式未定义 [FACT]
- 与现有治理模式的具体兼容规则未展开 [FACT]

## §2 业务场景判断

### 需求在现有体系中的位置

本需求是对现有权限管理体系的**能力叠加**，不替代任何已有能力。具体关系如下：

- **与「权限变更审批模式」的关系**：叠加共存。现有审批模式是管理员发起权限变更 → 审批 → 生效；本需求新增员工发起申请 → 审批 → 系统自动授权。两条路径共用审批引擎和权限写入层，但发起方、申请表单结构、授权执行方式不同。[CONFIRMED]

- **与权限来源模型的关系**：在现有来源（直授、角色、应用可见性、协作可见性）基础上，新增一条由员工发起、经审批后系统自动写入的来源路径。它需要独立标识，不应混入现有的直授或角色来源，以确保权限溯源可解释。[CONFIRMED]

- **与治理模式的关系**：自助申请能力本身是一种新的治理触发方式。现有治理模式包括双管理员模式、权限变更审批模式、子管理员隔离模式。自助申请须与这些模式各自定义叠加行为，不应默认兼容。[CONFIRMED]

### 是否改变治理模式

不改变现有治理模式定义，但需要在治理状态模型中扩展自助申请触发的状态流转路径。现有六类治理状态（发起、待处理、通过、拒绝、生效、撤销）可复用，但「发起」的触发角色从管理员扩展为管理员+员工。

### 最大业务不确定性

自助申请与双管理员模式、子管理员隔离模式的叠加行为尚未定义。这两个问题会直接影响审批流程设计和管理端配置结构。

### 如果这个判断错了

如果自助申请实际需要替代而非叠加权限变更审批模式，则管理端需要合并两个配置入口、统一审批流程定义、迁移旧的审批数据——整套方案结构需要重做。

## §3 需求成立性判断

### 用户问题真实性

员工不知道自己的权限、缺权限时只能私下找管理员——这是一个真实存在的体验问题，在中大型企业和权限频繁变更的组织中尤为突出。当前权限信息以技术语言存储，员工看不懂、管理员解释成本高，线下沟通效率低且无记录可追踪。[CONFIRMED]

### 业务价值

- 将权限申请的沟通从线下无序转移到线上标准化，减少管理员的重复人工处理 [CONFIRMED]
- 申请记录可追踪、可审计，补上了当前权限治理链路中缺失的「谁申请了什么、谁批的、为什么」这一段 [CONFIRMED]
- 员工获得自主查看和申请权限的能力，减少对单个管理员的依赖 [CONFIRMED]

### 系统代价

- 需要新建权限的业务语言翻译层——这是本次最大的隐性成本，不建则两端体验都会失败，建则需要投入语义建模和与现有权限结构的映射工作 [CONFIRMED]
- 来源模型需要扩展以容纳新的获取路径 [CONFIRMED]
- 管理端新增自助申请配置模块，需要与现有权限管理页面整合 [CONFIRMED]
- 需要额外设计治理模式兼容矩阵，逐一对过叠加行为 [CONFIRMED]

### 更低成本替代路径

1. **只做「查看我的权限」不做申请**：先把权限翻译成业务语言展示给员工，权限申请仍走现有审批模式。这能解决「不知道自己有什么权限」的问题，且改动范围更小。代价是无法解决「申请路径不标准化」的问题。
2. **在现有权限变更审批模式中增加「员工发起」选项**：不另建一套申请能力，而是在现有审批流程中增加一个员工可触达的发起入口。代价是管理员配置面和员工申请面耦合在一套流程里，灵活性降低。

### 成立性结论

**建议进入正式体验设计。** 员工自助申请解决的是真实问题，方向成立。但建议先完成权限业务语言翻译层的设计，再往上搭申请和审批体验——这是确保两端体验不失败的前提。

## §4 推荐业务边界

### 推荐能力形态

1. **权限业务语言翻译层**（本次新增）：将技术层面的权限表达（功能点 + 数据范围 + 来源 + 治理状态）转译为员工可理解的业务能力描述。这是「查看权限」和「申请权限」的共享基础。[CONFIRMED]

2. **员工权限查看能力**（本次新增）：员工可在统一入口查看自己当前拥有的权限，以业务语言呈现。展示内容需包含：能做什么、在什么范围内、权限来源、是否已生效。[CONFIRMED]

3. **员工权限申请能力**（本次新增）：员工可在可申请范围内选择需要的能力，填写申请原因并提交。申请选项来源于管理员已配置的「可申请范围」，以业务语言呈现。[CONFIRMED]

4. **管理员自助申请配置能力**（本次新增）：管理员可开启/关闭自助申请、定义可申请范围（以业务语言表达的权限选项）、为每个范围配置审批流程。配置项复用现有审批引擎的流程设计能力。[CONFIRMED]

5. **审批处理能力**（复用现有审批管理）：审批人收到员工申请后，查看申请内容和原因，决定同意或拒绝。审批通过后系统自动完成授权写入。[CONFIRMED]

### 不推荐能力形态

- 员工端不做「完整权限体系浏览」：不把权限管理的全部技术结构暴露给员工，只展示与员工自身相关的权限结果和可申请的选项
- 管理员端不把自助申请配置做成独立于现有权限管理的另一套体系：可申请范围的定义应复用角色和功能权限的现有配置，不另建一套权限定义
- 不在本次范围内改造审批流程引擎本身

### 与现有能力的边界

- 可申请范围的底层数据源复用现有角色管理和功能权限配置，[GAP] 具体映射方式待确认
- 审批流程复用现有审批管理引擎，自助申请不另建审批能力
- 授权写入复用现有权限写入能力（直授或角色分配），[GAP] 具体写入方式待确认
- 权限查看的数据来源复用现有权限计算链路，新增业务语言翻译层

## §5 角色、功能、规则范围

### 角色清单

| 角色 | 职责 |
|------|------|
| 普通员工 | 查看自身权限、发起权限申请、查看申请记录和审批进度 |
| 审批人 | 接收并处理员工提交的权限申请、查看申请详情、同意或拒绝 |
| 权限管理员 | 配置可申请范围、配置审批流程、调整和关闭自助申请能力 |
| 超级管理员 | 开启或关闭自助申请能力、拥有权限管理员的全部能力 |

### 功能单元

| 功能 | 输入 | 输出 | 结果 |
|------|------|------|------|
| F1 员工查看自身权限 | 员工身份 | 以业务语言呈现的权限清单（含来源、范围、生效状态） | 员工知晓自己能做什么、不能做什么、权限从哪来 |
| F2 员工发起权限申请 | 所选权限选项 + 申请原因 | 生成权限申请单，进入审批流程 | 申请状态变更为「待审批」，审批人收到待办 |
| F3 审批人处理申请 | 申请单详情（申请人、申请权限、原因） | 同意或拒绝 + 可选审批意见 | 同意：系统自动授权；拒绝：流程结束，申请状态变更为「已拒绝」 |
| F4 员工查看申请记录 | 员工身份 | 申请记录列表（含申请内容、时间、状态、审批结果） | 员工可追踪自己的申请进度和历史 |
| F5 管理员开启/关闭自助申请 | 开启或关闭操作 | 能力状态变更 | 开启：员工可发起申请；关闭：员工不再看到申请入口，在途申请继续流转 |
| F6 管理员配置可申请范围 | 选择角色或功能权限作为可申请项 | 生成员工可见的申请选项列表 | 员工发起申请时的可选范围受此约束 |
| F7 管理员配置自助申请审批流程 | 选择审批人、审批方式 | 审批流程绑定到可申请范围 | 对应范围的申请按配置流转审批 |
| F8 管理员调整配置 | 修改可申请范围或审批流程 | 配置更新 | [GAP] 已提交的在途申请是否受新配置影响待确认 |
| F9 系统自动授权 | 审批通过结果 + 申请单中的授权信息 | 执行权限写入 | 员工获得申请权限，权限来源标记为「自助申请」 |

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时 |
|------|---------|---------|---------|
| R1 能力开关前置 | 员工尝试进入申请入口 | 能力已开启：显示申请入口；已关闭：不显示入口 | 显示能力关闭提示，说明联系管理员的方式 |
| R2 可申请范围约束 | 员工发起申请 | 仅展示管理员已配置的、当前员工尚未拥有的权限选项 | 无可申请项时显示空状态，说明暂无可用申请项 |
| R3 审批流程绑定 | 员工提交申请 | 按管理员配置的审批流程自动路由到对应审批人 | [GAP] 审批人不存在或无效时的降级策略待确认 |
| R4 审批通过自动授权 | 审批人同意申请 | 系统按申请单中的权限映射执行授权写入 | [GAP] 写入失败时的回滚和通知策略待确认 |
| R5 关闭能力时在途申请保护 | 管理员关闭自助申请能力 | 停止接受新申请，已提交的在途申请继续流转至结束 | 不取消在途申请，不中断已授权的权限 |
| R6 重复申请识别 | 员工发起申请 | 如果员工已有一条「待审批」或「已通过」的同权限申请，不允许重复提交 | 提示已有申请在处理中或已获得该权限 |
| R7 申请原因必填 | 员工提交申请 | 申请原因作为审批人判断依据，必须填写 | 提示申请原因为必填 |
| R8 审批结果通知 | 审批完成 | 系统通知申请人审批结果；通过时告知已获得什么权限和生效时间；拒绝时告知原因和后续建议 | [GAP] 通知渠道和通知内容结构待确认 |

## §6 状态、异常与边界

### 核心状态流转

| 状态 | 谁可见 | 可执行动作 | 下一状态 |
|------|--------|-----------|---------|
| 已开启 | 管理员 | 配置范围/流程、关闭 | 已关闭 |
| 已关闭 | 管理员 | 开启 | 已开启 |
| 草稿 | 申请人 | 编辑、提交 | 待审批 |
| 待审批 | 申请人、审批人、管理员 | 审批人处理（同意/拒绝）、申请人撤回 [GAP] | 已通过、已拒绝 |
| 已通过（待生效） | 申请人、审批人、管理员 | 无（等待系统自动授权） | 已生效、授权失败 [GAP] |
| 已生效 | 申请人、管理员 | 无（可被管理员收回） | 已撤销 |
| 已拒绝 | 申请人、审批人、管理员 | 无（申请人可重新申请）[GAP] | 草稿（重新发起） |
| 已撤销 | 申请人、管理员 | 无 | 终态 |

### 关键异常

| 异常 | 触发条件 | 系统处理结果 | 用户下一步 |
|------|---------|-------------|-----------|
| 审批人不存在 | 申请单路由时发现审批人为空或已离职 | 申请无法进入审批，状态停留在待处理 | 通知申请人「审批流程配置异常，请联系管理员」，通知管理员补充审批人配置 |
| 自动授权失败 | 审批通过后系统执行授权写入时失败 | 申请状态变更为「授权失败」，保留审批通过结果和失败原因 | 通知申请人「权限已审批通过但授权遇到问题，管理员正在处理」，通知管理员手动完成授权并修复写入链路 |
| 可申请范围为空 | 员工进入申请页但管理员未配置可申请项，或所有可申请项员工已拥有 | 显示空状态 | 提示「当前暂无可申请的权限，如有需要请联系管理员」 |
| 能力被管理员关闭时有在途申请 | 员工有「待审批」的申请，管理员关闭了自助申请能力 | 在途申请继续流转不受影响，但员工无法提交新申请 | 员工仍可查看在途申请进度，但申请入口消失；审批人仍可正常处理 |
| 治理模式冲突 | 自助申请开启时，管理员尝试开启与自助申请存在未解决兼容规则的模式 | [GAP] 是阻止开启还是仅警告待确认 | 管理员需先确认兼容性配置 |
| 申请已被他人处理 | 审批人打开申请单时发现已被其他审批人处理 | 显示申请单当前状态和审批结果，不允许重复处理 | 审批人返回待办列表 |

## §7 体验蓝图承接要求

| 业务判断 | 对体验设计的影响 | 下游必须承接的问题 | 禁止下游重判 |
|----------|----------------|-------------------|-------------|
| 自助申请是现有权限体系的叠加能力，不替代已有模式 | 需要设计两个模式共存的入口和信息结构 | 员工侧：如何区分「我已有的权限」和「我可以申请的权限」；管理侧：如何在现有权限管理结构中嵌入自助申请配置 | 不得把自助申请当成独立的权限体系来设计 |
| 权限信息需要从技术语言转译为业务语言 | 员工端的信息展示和申请选项都需要重新设计语义层 | 权限清单的业务语言表达方式（能力描述+范围描述）；申请选项的命名和分组方式；管理端配置可申请范围时的语义编辑体验 | 不得直接展示技术字段和来源枚举 |
| 审批通过后系统自动授权 | 申请表单必须包含足够信息让系统执行写入，审批人确认前需看到将授予什么 | 申请确认页需要展示「审批通过后将授予的具体权限」的预览；授权结果的反馈和生效时间说明 | 不得将授权动作留给管理员手动执行 |
| 管理员全程可控 | 管理端的配置体验直接影响员工端的安全和可用性 | 可申请范围的配置方式（按角色/按功能/混合）；审批流程的绑定方式；关闭能力的在途保护说明 | 不得因简化管理端而削弱安全控制 |
| 涉及员工、审批人、管理员、超管四个角色 | 每个角色对权限的理解深度不同，需要差异化的信息表达 | 员工侧以业务场景为锚点；审批侧以申请内容+风险提示为核心；管理侧以权限结构为操作对象 | 不得用同一套信息结构覆盖所有角色 |
| 不能与已有治理模式冲突 | 模式叠加时可能出现审批链重复、授权冲突等问题 | 自助申请开启时的前置兼容性检查交互；模式冲突时的提示和引导 | 不得默认所有模式天然兼容 |

## §8 约束与不做什么

### 硬约束

- 自助申请能力必须可被管理员关闭，关闭时在途申请继续流转，不得中断 [FACT]
- 员工只能申请管理员已配置范围内的权限 [FACT]
- 审批通过后系统自动完成授权写入，不得要求管理员手动执行 [FACT]
- 不得另建独立的审批引擎，必须复用现有审批管理能力 [CONFIRMED]
- 权限的业务语言翻译层必须同时支撑「查看权限」和「申请权限」两端，不得各自另起一套说法 [CONFIRMED]

### 依赖项

- 依赖现有审批管理引擎的能力完整性（审批人配置、流程路由、结果通知）
- 依赖现有权限写入能力的稳定性（直授或角色分配的写入接口）
- 依赖现有角色管理和功能权限配置作为可申请范围的数据源

### 不做什么

- 不做员工端的完整权限管理后台——员工只查看和申请，不配置
- 不在本次范围内改造审批流程引擎本身（如新增审批人类型、动态审批规则等）
- 不在本次范围内改变现有权限来源模型的优先级和计算规则
- 不做移动端的独立审批应用，但员工申请端需在移动端可达 [GAP]
- 不支持员工申请超出管理员配置范围之外的权限
- 不支持员工为他人代申请权限 [GAP]

## §9 待确认问题

### 层级一：影响主策略

1. **自助申请与双管理员模式的叠加行为**：双管理员模式下，员工的自助申请需要两位管理员都审批吗？还是仅走自助申请配置的审批流程即可？这会影响审批流程配置结构和授权生效条件。
   - 影响：审批流程设计、状态流转、管理端配置界面结构
   - 建议确认方：产品 + 业务

2. **自助申请与子管理员隔离模式的叠加行为**：子管理员隔离模式下，员工能否申请超出子管理员管辖范围的权限？如果不能，如何判断申请范围是否越界？
   - 影响：申请范围校验逻辑、审批人路由规则
   - 建议确认方：产品 + 技术

3. **审批通过后授权写入的具体方式**：是以直授方式写入还是以角色分配方式写入？这会决定授权后的权限结果如何被来源模型解释和追踪。
   - 影响：来源模型扩展方式、权限溯源和审计体验
   - 建议确认方：技术 + 产品

### 层级二：影响局部设计

4. **管理员关闭能力时在途申请的具体处理**：是否允许管理员选择「仅停止新申请」和「同时取消所有在途申请」两种关闭方式？
   - 影响：管理端关闭操作的交互设计
   - 建议确认方：产品

5. **管理员调整配置后对已提交在途申请的影响**：修改可申请范围或审批人后，已提交但尚未审批完成的申请是按旧配置继续还是按新配置重新路由？
   - 影响：在途申请的状态处理和异常分支
   - 建议确认方：产品 + 技术

6. **员工申请权限的审批通知渠道**：审批结果通过什么渠道通知员工？是否需要支持站内消息、邮件、移动端推送等多种方式？
   - 影响：通知触达设计和文案策略
   - 建议确认方：产品

7. **移动端适配范围**：员工申请和查看功能是否需要在移动端完整覆盖？审批人的审批处理是否已有移动端能力？
   - 影响：跨端一致性设计和移动端交互方案
   - 建议确认方：产品
