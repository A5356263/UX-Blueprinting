# 需求定案文档：员工自助权限申请

---

## §0 本次关键判断

**判断**：本次需求"员工自助申请权限"方向合理，属于既有权限治理能力的自然扩展，不是颠覆性改造。核心价值是将权限变更的发起侧从管理员延伸到员工，同时保持管理员对范围、审批、开关的绝对控制。建议按中等复杂度推进，不建议做成本独立的平行模块。

**主要影响**：在现有权限体系上新增"员工发起→审批→生效"的申请链路，引入申请单这个临时对象及对应的申请治理规则，但不改变已有权限对象关系和生效机制。

**建议方案**：先收敛管理员配置体验与员工申请触发链路的低保真方案，审批人判断依据和状态可见性作为配套同步设计。第一期优先做集中申请入口 + 审批处理，上下文触发申请可在二期扩展。

**不建议方案**：不要把自助申请做成独立于现有权限体系的平行模块；不应与已有"权限变更审批模式"走两套审批逻辑导致治理分裂。

**关键待确认**：当前系统是否已启用"权限变更审批模式"——如有，审批流程应尽量复用，避免另配一套。

## §1 需求输入摘要

### 需求背景

当前企业员工的权限分配主要由权限管理员或超级管理员集中处理。在中大型企业中，人员流动频繁，权限变更工作量大。部分企业的超管是老板本人，员工需要权限时需私下沟通，沟通成本高、时效不稳定。

### 目标

新增"员工自助申请权限"能力，使员工可以查看当前拥有的权限、主动申请所需权限、通过审批后自动获得权限、查看申请记录和审批状态。管理员可以控制是否允许自助申请、员工可申请范围、审批流程、关闭能力。

### 核心场景

1. 管理员配置自助申请权限
2. 员工查看自己的权限
3. 员工申请权限
4. 审批人处理申请
5. 管理员关闭自助申请能力

### 输入来源

- 本次分析基于用户提供的需求文档 `input/自助权限申请/需求文档_员工自助申请权限.md`
- 文档标注完整度：低（多处标注"帮我补充"）

## §2 业务场景判断

### 业务定位

这是一项**扩展型需求**，不是全新能力。当前权限域已有"用户直授""角色授权""权限变更审批模式"等能力（知识库 `10_能力地图`、`24_治理状态模型`）。自助申请的定位是：**把权限变更的发起端从管理员延伸到员工，审批和授权执行仍走现有能力。**

### 与现有能力的关系

- **用户直授/角色授权**：不改变。自助申请审批通过后，系统应调用现有授权机制完成自动授权
- **权限变更审批模式**：**需要对齐**。如果当前系统已开启该模式，自助申请的审批流应复用同一套审批配置，而不是另起一套
- **子管理员模式/双管理员模式**：自助申请的授权结果需受这些治理模式的约束（如子管理员只能授权其管辖范围内的权限）

### 最大业务不确定性

审批人确定机制尚未定义。审批人是谁，直接影响申请流程能否流转闭环。如果审批人配置不当（如默认审批人不合适），申请可能积压或形成绕过。这是主方案成立的前提条件。

### 判断错误的影响

如果"自助申请是权限变更审批模式的员工侧延伸"这个判断是错的（即当前系统没有可复用的审批模式），则自助申请的审批模块需要从零构建，工作量和复杂度将升级为高复杂度，业务边界也需要重新收敛。

## §3 需求成立性判断

### 收益

- 减少管理员/超管的分散性授权工作，释放管理精力
- 员工权限申请流程规范化、可追踪、可审计
- 缩短权限获取时间，提高业务效率（从"找老板"变成"提交申请"）
- 与线下沟通相比，系统留痕，便于后期核查和排障

### 系统代价

- 管理员前期配置成本：第一次开启时需要配置可申请范围和审批流程
- 现有权限治理模式的适配成本：需要确认复用还是扩展
- 培训成本：部分企业需要教会员工使用自助申请功能（文档 8.1 已识别）
- 安全运营成本：需要监控是否有越权申请、审批人设置是否合理

### 更低成本替代路径

可考虑两期分步：

- **第一期（推荐先做）**：仅做"员工查看自己的权限"。这是只读、零风险的，能让员工先减少向管理员询问的频率。同时验证员工侧权限展示的信息完整性。
- **第二期**：在查看权限的基础上，增加申请功能。此时员工已经知道权限体系是什么，申请的前提条件（知道自己缺什么）更成熟。

如果管理员普遍接受度不高，也可以先做轻量方案：员工填写申请表单 → 管理员在管理后台看到申请 → 管理员手动授权。审批链路全部走线下，系统只做记录。但这样做损失了闭环效率，只适合初期灰度。

### 建议

**建议进入正式体验设计**。第一期以"员工查看权限 + 集中申请入口"为核心，审批流程尽量复用现有治理模式。上下文触发申请（在功能无权限处直接申请）作为第二期方向明确，但不纳入本期范围。

## §4 推荐业务边界

### 推荐能力形态

- **管理端**：在权限管理域内新增"自助申请配置"入口，集中管理开启/关闭、可申请范围、审批方式。配置与开启动作绑定，管理员在开启时完成最小必要配置
- **员工端**：在一级入口增加"我的权限"或"权限申请"，聚合展示已有权限、可申请权限和申请记录
- **审批端**：申请进入现有审批流程，审批人在审批处理界面可见申请详情、权限影响范围和风险提示

### 不推荐能力形态

- 不推荐在多个管理入口分散配置可申请范围（如用户授权页配一点、角色管理页配一点）
- 不推荐在员工端展示完整的后台权限模型（如来源枚举、覆盖规则、冲突原因码），员工侧只需看功能名称和说明
- 不推荐让员工手动输入权限名称来搜索申请

### 与现有能力的边界

- **复用什么**：审批流程应复用现有审批中台或权限变更审批模式；授权执行应复用已有授权接口
- **不该新增什么**：不应新增一套独立于现有权限模型的审批流程引擎；不应在权限域外定义可申请范围

## §5 角色、功能、规则范围

### 角色与职责

| 角色 | 职责 |
|---|---|
| 超级管理员 | 开启/关闭自助申请能力、配置全局可申请范围与审批方式、监控申请动态 |
| 子管理员 | 如果超管授予了管理权限，可在管辖范围内查看申请记录（不涉及本需求的默认角色） |
| 审批人 | 收到审批通知、查看申请详情与原因、同意/拒绝、了解授权结果 |
| 普通员工 | 查看已有权限、申请权限、查看申请记录与状态 |

### 功能范围

| 功能 | 输入 | 处理 | 输出/结果 |
|---|---|---|---|
| 开启自助申请 | 管理员确认开启 | 系统校验是否已存在冲突的治理模式（如双管理员模式与子管理员模式互斥）；如无冲突，进入范围配置 | 自助申请能力可用 |
| 配置可申请范围 | 管理员选择范围类型（按功能权限/按角色/按应用） | 系统加载对应权限列表供勾选 | 可申请范围生效 |
| 配置审批方式 | 管理员选择审批流程 | 对接审批中台完成流程关联 | 申请的审批按此流程流转 |
| 查看我的权限 | 员工进入"我的权限"页 | 系统按来源汇总并展示当前员工的权限 | 员工看到自己已有的功能权限和数据权限 |
| 申请权限 | 员工选择需申请的权限、填写申请原因 | 系统校验是否在可申请范围内 → 校验是否已有该权限 → 如通过则创建申请单进入审批 | 申请单进入对应审批流程 |
| 审批处理 | 审批人查看申请详情 | 展示权限影响范围、风险等级、申请原因 | 同意：走自动授权 / 拒绝：申请结束 |
| 关闭自助申请 | 管理员确认关闭 | 系统校验是否存在进行中的申请 → 允许关闭但保留进行中申请继续流转 | 新申请不可提交，已有申请正常流转 |
| 查看申请记录 | 员工/管理员进入申请记录页 | 按条件筛选和展示申请列表 | 展示状态、时间、结果 |

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时处理 |
|---|---|---|---|
| 可申请范围约束 | 员工提交申请时 | 系统校验申请的权限是否在管理员配置的可申请范围内 | 超出范围：提示员工该权限不可自助申请，建议联系管理员 |
| 权限去重 | 员工提交申请时 | 系统校验员工当前是否已有该权限 | 已有权限：提示"您已有该权限，无需重复申请" |
| 进行中申请约束 | 员工提交申请时 | 系统校验该权限是否存在进行中的申请 | 存在进行中的申请：提示"该权限申请正在审批中" |
| 审批通过自动授权 | 审批人点击同意 | 系统调用现有授权接口完成授权 | 授权失败：通知审批人和员工授权失败及原因 |
| 关闭期间申请保护 | 管理员关闭功能 | 系统标记进行中的申请不受影响 | 无（关闭操作不可逆，进行中申请继续流转） |
| 模式互斥校验 | 管理员开启自助申请时 | 系统校验是否与现有治理模式冲突 | 存在冲突：提示管理员当前治理模式不支持同时开启自助申请（具体冲突规则需与治理模式对齐） |

## §6 状态、异常与边界

### 核心状态流转

```
申请单状态：
  草稿（draft）→ 审批中（pending）→ 已通过（approved）→ 已生效（effective）
                                       → 已拒绝（rejected）
                                       → 已撤销（revoked）
```

| 状态 | 说明 | 对员工可见 | 对审批人可见 |
|---|---|---|---|
| 草稿 | 员工已填写但未提交 | 可编辑、可提交 | 不可见 |
| 审批中 | 已提交，等待审批人处理 | 可撤回，不可编辑 | 可处理（同意/拒绝） |
| 已通过 | 审批人已同意，等待生效 | 可见结果，等待系统授权 | 可见结果 |
| 已生效 | 权限已成功授予 | 权限到位，流程结束 | 确认授权完成 |
| 已拒绝 | 审批人不同意 | 流程结束，可查看拒绝原因 | 流程结束 |
| 已撤销 | 员工在审批中自行撤回 | 流程结束 | 流程结束 |

### 关键异常清单

| 异常 | 触发条件 | 系统处理结果 | 用户下一步 |
|---|---|---|---|
| 申请超出可申请范围 | 员工申请了管理员未配置的权限 | 提示"该权限不可自助申请" | 建议联系管理员 |
| 员工已有该权限 | 员工申请已拥有的权限 | 提示"您已有该权限" | 无需继续申请 |
| 存在进行中的相同申请 | 员工重复提交 | 提示"该权限申请正在审批中" | 查看已有申请记录 |
| 审批人缺失 | 审批流程中无有效审批人 | 申请无法提交，提示管理员 | 管理员需先配置审批流程 |
| 审批通过但授权失败 | 系统调用授权接口失败 | 通知审批人和员工授权异常 | 联系管理员手动处理 |
| 关闭期间有新申请 | 管理员已关闭自助申请 | 禁止提交，提示"当前未开放自助申请" | 联系管理员 |
| 申请超时未处理 | 审批人长时间未处理 | 触发超时提醒（可选） | 员工可催办或联系其他审批人 |

### 边界说明

- 自助申请的范围配置不能超过管理员自身的权限边界（子管理员不能开放超出其管辖范围的权限申请）
- 关闭自助申请不回溯已生效的授权结果（已授予的权限不因关闭能力而收回）

## §7 体验蓝图承接要求

| 业务判断 | 对体验设计的影响 | 必须承接的问题 | 禁止下游重判 |
|---|---|---|---|
| 可申请范围由管理员在开启能力时一次配置 | 范围配置需要一个集中的配置界面，关联开启动作 | 如何让管理员在"不先学好权限模型"的情况下完成最小必要配置 | 不允许把范围配置散落在多个现有入口，也不允许不做范围配置就开启能力 |
| 当前员工的权限来自多个来源（直授/角色/应用可见性） | 员工侧展示权限列表时，来源信息对员工没有意义，只需要展示功能名称和说明 | 怎样用员工能懂的语言展示已有权限和可申请权限，且不需要展示来源模型 | 不允许直接把后台权限来源模型展示给员工 |
| 审批人需要决策依据 | 审批界面不能只有"同意/拒绝"两个按钮 | 审批人需要看到什么信息来判断该不该批（权限影响范围、风险等级、申请原因） | 不允许把审批界面简化到只有申请内容和两个操作按钮 |
| 审批通过后自动授权 | 员工和审批人都需要知道"审批通过了≠已生效" | 如何展示从审批通过到授权生效的过程状态（尤其是在治理模式叠加时） | 不允许把审批通过直接等同于授权完成 |
| 关闭能力不影响进行中的申请 | 关闭操作需要有校验和提示，进行中的申请状态需要保持可见 | 关闭时如何提示管理员进行中的申请数量，关闭后这些申请在员工端如何展示 | 不允许关闭时强制终止进行中的申请 |
| 可申请范围采用预定义选项（按功能权限/按角色/按应用） | 范围选择器的交互需要适配不同的权限组织形式 | 如何在范围配置中清晰区分不同权限组织形式，且让管理员理解每种形式的含义和后果 | 不允许把权限模型的技术分层直接作为配置选项的标签 |

## §8 约束与不做什么

### 硬约束

- 自助申请的可申请范围不能超出管理员的权限边界（子管理员不能开放其管辖范围外的权限）
- 关闭自助申请不影响已生效的授权结果
- 进行中的申请不受关闭操作影响，需继续走完流程
- 审批流程应在现有审批中台或权限变更审批模式的基础上复用，不新造流程引擎

### 依赖项

- 需要确认当前"权限变更审批模式"的可用性和覆盖范围
- 员工端入口需要平台级导航/工作台的支持
- 审批通知需要消息/通知系统的支持

### 不做什么

- 不替代现有用户直授和角色授权的管理方式
- 不改变已有权限的生效机制和治理模式
- 不在第一期支持上下文触发的权限申请（在功能无权限处直接申请）
- 不提供员工侧权限冲突检测和解释（超出自助申请范围的权限问题引导找管理员）
- 不做批量申请功能
