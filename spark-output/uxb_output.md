# 需求定案文档：财富小助 Skill 管理功能

---

## §0 本次关键判断

本次需求是在企业财富+平台上新增一套完整的 AI Skill 管理能力，包含模板创建、共享发布、分行订阅、智能联想调用和沙盒同步机制。这不是对现有功能的体验优化，而是全新功能模块上架，涉及内容生产、消费和管理三类角色的协同闭环。

**主要影响**：核心设计压力不在"能不能做"，而在于（1）分行级订阅的操作者与受影响者分离，需要兜底设计；（2）消费者（客户经理）缺少发现和评价工具，调用目标的达成依赖消费侧体验；（3）审核流程在创建者和审核者之间缺乏透明度。

**建议方向**：按"内容管理平台"而非"配置工具"定位设计，重点做消费端发现、订阅安全感和生产者效果反馈。

**不建议方向**：仅作为管理后台配置项实现，忽略消费侧体验闭环。

**关键待确认**：分行级订阅的取消保护机制深度（二次确认还是分行管理员管控）。

---

## §1 需求输入摘要

### 背景与目标

企业财富+平台的财富小助 AI 功能不断丰富，各分行在提示词模板方面缺乏统一管理和共享机制，导致重复建设和优秀实践无法复用。本次需求旨在建立 Skill 管理功能，提供创建、共享、订阅和智能联调的完整链路。

### 目标用户

| 角色 | 职责定位 | 优先级 |
|------|----------|--------|
| 总行产品经理 | 创建全行通用 Skill 模板 | 高 |
| 分行产品经理 | 创建分行特色 Skill 模板 | 高 |
| 开发人员 | 创建技术类 Skill 模板 | 中 |
| 客户经理 | 一线营销人员，调用 Skill 完成业务 | 高 |

### 功能范围

- **Skill 广场**：展示所有可用的 Skill，支持搜索、筛选、排序、订阅
- **Skill 创建编辑**：支持手动创建和上传 md 文件两种方式
- **我发布的 Skill**：管理所属分行已创建的 Skill
- **智能联想**：财富小助输入框输入"/"触发匹配
- **沙盒同步**：每周全量 + 实时增量同步

### 明确约束

- 订阅主体为**分行级**（非个人级），一个人订阅全分行可用
- 内容必须通过审核（敏感词检测、注入攻击检测、格式检测）后才能发布
- 沙盒同步采用异步 MQ 机制，不阻塞用户操作
- Skill 创建者仅限总行/分行产品经理和开发人员

### 输入缺口

- 消费端（客户经理）的发现、选择和评价机制描述较简略
- 审核流程只定义了规则，未设计创建者和审核者的交互流程
- 未明确 Skill 数量增长后的内容组织策略（分类/标签）
- "我发布的 Skill"与"所属分行所有 Skill"的语义差异在文档中未加说明

## §2 业务场景判断

### 业务定位

这是一个**全新的内容管理+分发能力**，是企业财富+平台从"工具型"向"生态型"演进的标志性功能。Skill 本质上是一种可复用的 AI 能力包，Skill 广场则是这个能力包的分发市场。

### 与现有能力的关系

**独立新增**，不依赖或修改现有业务对象。但需要集成两个既有体系：
- 企业财富+的**权限体系**（控制谁能创建、谁可查看）
- 财富小助的**调用链路**（智能联想和提示词执行）

### 治理模式变化

引入了"分行级共享"和"分行级订阅"的横向协作机制。这与传统的"上级下发→下级执行"的纵向模式不同——分行之间可以横向共享优质内容，这在当前体系里是新的治理维度。

### 最大业务不确定性

- 分行级订阅在实际运营中是否会产生分行内冲突（一个人取消、全分行不可用）
- 消费侧行为假设是否成立——客户经理是否愿意主动在 Skill 广场中发现新 Skill，还是更依赖被动推送

### 判断错误影响

如果分行级订阅与分行实际协作方式不匹配（例如实际需求是个人订阅+团队启用双层模型），则后续订阅流程、权限模型和页面结构都需要重做。如果消费侧发现假设不成立，则智能联想的调用量会远低于预期。

---

## §3 需求成立性判断

### 收益

- **消除重复建设**：各分行不再各自维护相似提示词，优秀模板可跨分行复用
- **放大 AI 能力覆盖**：更多业务场景可通过 Skill 快速接入 AI 能力
- **降低使用门槛**：一线客户经理不需要自己编写提示词，"/"即可调用
- **形成正向生态**：优质 Skill 被更多分行订阅，激励创建者持续优化

### 代价

- 新增 Skill 对象模型、订阅关系、使用记录、同步日志等数据结构
- 审核流程带来发布延迟，需要有运营人力配合
- 沙盒同步机制增加系统架构复杂度
- 需要持续运营推动 Skill 的活跃度（前期的冷启动问题）

### 更低成本替代路径

- **审核流程**可考虑"先发后审"模式（先上架再抽检），但需评估内容安全风险是否可接受——考虑到 Prompt 注入等安全风险，先审后发在当前阶段更稳妥
- **MVP 阶段**可以不建完整的评分/优化体系，先做核心的创建、订阅和调用链路

### 结论

**建议进入正式体验设计**。需求逻辑通顺，业务价值明确，但消费端体验和审核流程的体验设计空间较大，需要在体验蓝图阶段重点处理。

---

## §4 推荐业务边界

### 推荐能力形态

- 定位为**内容管理平台**（含生产、分发、消费、治理四个环节），而非管理后台的一个配置项
- 生产侧提供模板引导降低创建门槛（文档已含编写模板）
- 消费侧以"好发现、快调用"为核心目标

### 不推荐能力形态

- 不做个人级订阅——如果后续发现分行级模式不够灵活，可以考虑"分行订阅+个人启用"的双层模型，但不建议在初期同时做两层
- 不在 MVP 阶段加入消费者评分/点赞机制（可后续迭代）

### 与现有能力的边界

- **复用**：企业财富+用户认证、权限管理、分行信息
- **不冲突**：不与现有任何功能重叠

### 不该新增什么

- 短期内不新增个人维度的推荐算法（先用订阅量排序即可）
- 不新增独立的审核工作台——初期可复用现有审核能力或简化审核流程

## §5 角色、功能、规则范围

### 角色职责

| 角色 | 职责 | 核心任务 |
|------|------|----------|
| 总行产品经理 | 创建全行通用 Skill 模板，推动优质 Skill 跨分行复用 | 创建/编辑 Skill、查看全行数据概览 |
| 分行产品经理 | 创建分行特色 Skill，可选择共享给全行 | 创建/编辑 Skill、设置共享开关、查看分行订阅数据 |
| 开发人员 | 创建技术类 Skill 模板 | 创建/编辑 Skill |
| 客户经理（一线营销） | 发现并调用合适的 Skill 完成业务场景 | 浏览 Skill 广场、"/"联想调用 |
| 审核人员（系统/人工） | 内容合规审核 | 执行审核、通过/驳回、记录原因 |

### 功能闭环

| 功能单元 | 输入 | 处理 | 输出/结果 |
|----------|------|------|-----------|
| Skill 创建 | 用户填写的名称/描述/提示词，或上传的 md 文件 | 保存 Skill 信息，触发审核流程 | Skill 进入"待审核"状态 |
| Skill 审核 | 待审核的 Skill 内容 | 自动检测（敏感词/注入/格式）+ 人工兜底 | 通过→"已发布"；不通过→退回并告知原因 |
| Skill 订阅 | 用户在 Skill 广场点击"订阅" | 记录分行ID与Skill的订阅关系 | 该分行所有用户可使用此 Skill |
| 智能联想 | 用户在财富小助输入"/" | 查询用户所在分行可用 Skill，按订阅量排序 | 显示匹配列表（最多10条） |
| Skill 调用 | 用户从联想列表选择 Skill | 加载提示词内容执行 AI 交互 | 返回 AI 响应结果 |
| 沙盒同步 | Skill 数据变更事件 | MQ 消息异步同步到沙盒 | 沙盒缓存更新 |

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时处理 |
|------|----------|----------|-------------|
| 分行级订阅 | 用户在 Skill 广场点击"订阅" | 记录分行与 Skill 的订阅关系，全分行可用 | 分行已订阅时提示"已在本分行订阅" |
| 内容审核 | 创建/编辑 Skill 点击保存 | 自动检测 + 人工兜底 | 不通过则拒绝发布，提示具体不通过原因 |
| 共享权限 | 创建者设置是否共享 | 共享→全行可见；不共享→仅本分行可见 | 总行用户默认共享，分行用户默认不共享 |
| 创建权限 | 用户点击"发布技能" | 校验用户角色 | 非产品经理/开发人员不可创建 |
| 编辑权限 | 用户点击"编辑" | 校验用户是否为 Skill 所属分行 | 非所属分行不可编辑 |
| 删除权限 | 用户点击"删除" | 校验用户是否为创建者或管理员 | 非创建者/管理员不可删除 |
| 沙盒增量同步 | 创建/编辑/删除/订阅操作 | MQ 发送同步消息 | 失败后重试3次（间隔 1min/5min/30min） |
| 智能联想匹配 | 用户在财富小助输入"/" | 查询分行可用 Skill，名称模糊匹配 | 无匹配时联想列表为空 |

## §6 状态、异常与边界

### 核心状态

| 状态 | 说明 | 用户下一步 |
|------|------|-----------|
| 草稿 | Skill 创建中尚未提交 | 继续编辑或提交审核 |
| 待审核 | 已提交等待审核结果 | 等待审核通过 |
| 已发布 | 审核通过，在 Skill 广场正常展示 | 可被订阅和调用 |
| 已下架 | 创建者删除或手动下架 | 不再展示，订阅关系自动解除 |

### 关键异常

| 异常场景 | 触发条件 | 系统处理结果 | 用户下一步 |
|----------|----------|-------------|-----------|
| 审核不通过 | 内容含敏感词/注入攻击/格式不符 | 拒绝发布，返回具体不通过原因 | 修改后重新提交，或放弃创建 |
| 订阅已存在 | 分行已订阅目标 Skill | 提示"该 Skill 已在本分行订阅"，开关保持已订阅状态 | 无需处理 |
| 取消订阅影响全分行 | 用户点击取消订阅 | 解除分行订阅关系，全分行不可用 | 系统需二次确认后执行 |
| 取消未订阅的 Skill | 用户对未订阅 Skill 执行取消操作 | 提示"该 Skill 未在本分行订阅"，开关保持未订阅 | 无需处理 |
| 沙盒增量同步失败 | MQ 消费失败或沙盒异常 | 重试3次仍失败 → 告警运维 | Skill 可能暂不可用（不影响数据库） |
| 文件上传格式错误 | 上传非 .md 文件 | 提示"仅支持 .md 格式" | 更换文件 |
| 文件上传超限 | 文件超过 1MB | 提示"文件大小不能超过 1MB" | 压缩或精简文件后重试 |
| Skill 名称重复 | 创建的 Skill 名称已存在 | 提示"Skill 名称已存在" | 修改名称 |
| 删除已订阅的 Skill | 有分行订阅时执行删除 | 提示被多少分行订阅，确认后执行删除 | 确认后删除并解除所有订阅关系 |
| 智能联想无匹配 | 用户输入"/"后无可用的匹配 Skill | 联想列表为空 | 无 Skill 可用 |

## §7 体验蓝图承接要求

| 业务判断 | 对体验设计的影响 | 必须承接的问题 | 禁止下游重判 |
|----------|-----------------|---------------|-------------|
| 分行级订阅——个人操作影响全分行 | 取消订阅的安全感设计比普通订阅场景要求更高 | 取消订阅需要什么层级的二次确认？分行内用户如何感知订阅状态的变更？ | 禁止改为个人级订阅 |
| 消费者（客户经理）被动获得 Skill | "发现"不能完全依赖用户主动搜索，需要系统推送/引导 | 分行新订阅 Skill 后如何通知全员？Skill 广场如何帮助用户找到"适合自己业务场景"的 Skill？ | 禁止忽略消费端发现设计 |
| 审核流程使创建到发布存在等待期 | 提交到发布之间存在不确定的等待时间，创建者需要感知进度 | 如何向创建者传达审核进度？审核不通过时如何精确引导修改？ | 禁止跳过审核或改为自动发布 |
| 生产者看不到使用效果数据 | 缺少数据反馈会降低持续优化意愿 | 初期需要给生产者提供哪些效果指标（调用量、订阅趋势）？ | 禁止在 MVP 阶段完全不做效果数据 |
| 智能联想仅依赖名称匹配 | 随着 Skill 增长，仅靠名称匹配精度会下降 | 初期是否引入分类/标签维度？联想排序策略是否可以引入调用频次因素？ | 禁止将匹配策略限定为仅按名称 |
| "我发布的 Skill"实际展示所属分行所有 Skill | 用户预期和实际内容不一致 | 是否需要通过文案/引导说明"分行内所有成员创建的 Skill"？ | 禁止改为仅展示个人创建 |
| 沙盒同步非实时——最短秒级延迟 | 用户发布后需要等待同步才能在财富小助中使用 | 如何向用户传达同步状态（发布成功但稍后才可调用）？ | 禁止让用户误以为发布后立即可用 |

## §8 约束与不做什么

### 硬约束

- **必须包含内容审核流程**：安全合规要求，含敏感词检测、注入攻击检测、格式检测
- **沙盒同步必须异步**：与现有系统架构一致，创建/编辑操作不阻塞
- **订阅主体为分行级**：文档已明确，体验设计不得改为个人订阅
- **仅支持 .md 格式上传**：文件上传方式限定为 Markdown 格式

### 依赖项

- 企业财富+的权限管理系统（角色校验）
- 财富小助的输入框组件（联想触发）
- 消息队列服务（异步同步）
- 沙盒环境（Skill 缓存和执行）

### 不做什么

- 不实现个人维度的个性化推荐算法（初期使用订阅量排序）
- 不做客户经理之间的个人级 Skill 分享（共享最小颗粒度为分行）
- 不在 MVP 阶段实现消费者评分/点赞机制
- 不创建独立的审核工作台（复用现有审核能力或简化流程）

## §9 待确认问题

### 层级一：影响主方案是否成立的问题

1. **分行级订阅的取消保护机制**
   - 问题：取消订阅影响全分行，是否设置"二次确认"以外的保护机制（如需要分行管理员审批取消）？
   - 影响：取消订阅的交互流程和权限设计
   - 建议确认方：业务方

### 层级二：影响局部体验设计的问题

1. **"我发布的 Skill"的认知边界**
   - 问题：Tab 展示的是所属分行所有 Skill 而非个人创建，是否需要在页面增加引导说明？Tab 名称是否需要调整？
   - 影响：导航文案和页面引导
   - 建议确认方：交互设计

2. **Skill 分类/标签体系**
   - 问题：MVP 阶段是否需要引入按业务场景的分类维度？还是仅靠名称搜索即可支撑初期使用？
   - 影响：筛选区和搜索功能的设计
   - 建议确认方：业务方 + 交互设计

3. **审核流程的预期时间**
   - 问题：审核的预期时效是多久？超过多长时间需要主动通知创建者？
   - 影响：审核进度提示的策略设计
   - 建议确认方：运营

4. **智能联想触发规则**
   - 问题：文档描述"光标在输入框开头或空格后"才触发——这条规则的体验细节（例如输了一半退格到开头是否触发）是否需要细化？
   - 影响：联想触发交互设计
   - 建议确认方：交互设计
