# UXB 需求定案：员工自助申请权限

## §0 本次关键判断

**总判断：新增"员工自助申请权限"能力是成立的，但前提是先解决与现有治理模式的共存策略。**

- **判断**：本次需求是在已有管理员侧授权体系上新增一个员工侧入口能力，不改变底层权限对象关系和生效机制。核心挑战不在"能不能做"，而在"怎么做才能既让员工用起来顺，又不打乱已有的治理体系"。
- **主要影响**：三个角色（员工、审批人、管理员）的任务路径和信息结构有明显变化，但底层业务骨架不变。
- **建议方案**：采用"自助申请为补充能力，不是替代能力"的定位——管理员保持全局控制，员工获得自助入口，审批流由 OA 底座承接。
- **不建议方案**：把自助申请做成完全开放的系统（削弱管控），或把它做成仅一个入口没有审批（失去治理）。
- **关键待确认**：与子管理员模式、双管理员模式、权限变更审批模式的共存策略——这决定了产品层面的功能开关逻辑。

## §1 需求输入摘要

### 需求背景（原文提取）

- 中大型企业员工数量多、流动频繁，权限管理工作量大
- 超管可能是老板本人，员工需要私下找管理员处理，沟通成本高、时效不稳定
- 目标：把部分权限申请工作从管理员侧分散到员工侧，保留管理侧控制

### 目标用户（原文提取）

- **员工**：查看已有权限、申请权限、查看申请记录和审批状态
- **审批人**：收到申请后查看内容和原因，决定同意或拒绝
- **管理员**：开启/关闭自助申请能力，配置可申请范围和审批流程

### 功能范围（原文提取）

- 管理员配置：开启/关闭、设置范围、设置审批流程、后续调整配置
- 员工端：查看权限、申请权限、查看申请记录
- 审批端：查看申请、同意/拒绝、系统自动授权

### 未覆盖内容（原文缺口标注）

| 缺口 | 原文标注 |
|---|---|
| 可申请范围配置方式 | "需要进一步设计" |
| 员工端业务规则 | "帮我补充" |
| 审批端业务规则 | "帮我补充" |
| 与现有治理模式的关系 | 提出风险但未做判断 |
| 关闭能力时的影响范围 | 提出但未展开 |

## §2 业务场景判断

### 业务定位

本次需求是**既有能力扩展**，不是全新能力，也不是替代方案。

- 当前产品已有完整的**管理员侧授权链路**（用户授权→功能授权→数据授权、角色管理、应用管理），这些不受影响
- 自助申请是**在员工侧新增一个入口**，本质上把"申请→审批→生效"流程中"发起"这一步从线下沟通转为线上操作
- 审批和生效环节仍然复用已有能力（OA 底座审批、权限生效机制）

### 与现有能力的关系

| 现有能力 | 关系 |
|---|---|
| 管理员侧用户授权 | 互补，员工自助申请通过审批后自动触发的授权，等同于管理员授权的一种来源 |
| 子管理员模式 | 潜在互斥或叠加，需进一步判断 |
| 双管理员模式 | 潜在互斥或叠加，需进一步判断 |
| 权限变更审批模式 | 潜在互斥或叠加，需进一步判断 |
| 角色管理 | 自助申请的目标之一是角色权限包，但角色定义和管理仍在管理员侧 |

### 最大业务不确定性

**与现有治理模式的共存策略**是最不确定的问题。当前产品有三种治理模式（子管理员、双管理员、权限变更审批），自助申请加入后是"可同时开启"还是"互斥选择"，会直接影响：
- 产品功能开关的设计方式
- 权限来源的解释逻辑（同一份权限从"自助申请"来 vs 从"管理员授权"来）
- 审批链路的冲突处理（同时开启自助申请审批和双管理员互审时如何处理）

### 判断错误的影响

如果共存策略判断错误，后续体验蓝图中的功能开关设计、权限来源展示、审批链路设计都需要重做。

## §3 需求成立性判断

### 收益

- 降低管理侧重复性工作：管理员从逐个处理申请变为一次性配置规则
- 缩短授权时效：员工在线提交，审批人在线处理，不再依赖线下沟通
- 审计可追溯：每笔申请有完整的发起→审批→生效记录
- 员工体验提升：从"找谁问"变为"自己办"

### 代价

- 开发成本：新增员工侧入口、申请流程、状态管理、与 OA 底座对接
- 培训成本：需要让员工理解"什么是自助申请权限"——但这个成本可以通过语义降维（用业务语言代替管理术语）来降低
- 治理复杂度：新增一种权限来源，权限解释链路（"为什么有这个权限"）需要增加"自助申请"这一来源类型

### 更低成本的替代路径

- **替代路径 A**：不做自助申请，只做"权限查看"功能——员工只能看自己有什么权限，申请仍走线下。成本最低，但未解决"申请效率"这个核心问题。
- **替代路径 B**：不做产品功能，只在管理侧做一个"代客下单"工具——管理员替员工提交申请。成本中等，但核心矛盾（管理员仍要逐个处理）没有解决。
- **替代路径 C（推荐）**：本次需求方案——员工自助申请+管理员配置规则。成本最高，但从根本上解耦了"发起"和"处理"两个环节。

### 结论

**建议进入正式体验设计。** 需求真实（中大型企业权限管理确实是痛点），方案合理（在线化+审批流+管理员配置），且已有 OA 底座能力支撑。但需要先确认 §0 所述的共存策略。

## §4 推荐业务边界

### 业务能力边界

| 维度 | 本次范围 | 不在本次范围 |
|---|---|---|
| 申请发起 | 员工在线提交申请，含申请理由 | 批量申请、代他人申请 |
| 申请内容 | 功能权限、角色（权限包） | 数据权限（本次不覆盖） |
| 敏感权限 | 系统级排除，不可申请 | 不改变敏感权限定义规则 |
| 审批流程 | 由 OA 底座承接，上级负责人审批 | 不重新设计审批引擎 |
| 权限生效 | 审批通过后系统自动授权 | 定时生效、权限回收（后续考虑） |
| 管理员控制 | 可申请范围配置、开启/关闭 | 不改变管理员侧已有授权功能 |
| 权限来源 | 新增"自助申请"作为权限来源类型 | 不改变已有来源类型的管理逻辑 |

### [CONFIRMED] 与现有治理模式的建议关系

基于领域知识和当前系统架构判断：

- **自助申请 ≠ 治理模式**
- 自助申请是一种权限来源方式，而不是一种治理模式
- 它与子管理员模式、双管理员模式、权限变更审批模式**不互斥**
- 关系建议：自助申请作为"权限的获取方式"独立存在，已获取的权限在流转过程中仍受已有治理模式约束

### [GAP] 需进一步验证

上述关系判断需要产品侧和架构侧确认。如果判断错误，需要返回 §2 和 §4 重做。

## §5 角色、功能、规则范围

### 角色职责

| 角色 | 职责 |
|---|---|
| 员工 | 查看已有权限 → 发现可申请权限 → 发起申请 → 追踪进度 → 使用已获得的权限 |
| 审批人（上级组织负责人） | 查看申请上下文 → 批准/拒绝（附理由）→ 申请生效/退回 |
| 权限管理员/超管 | 开启/关闭自助申请能力 → 配置可申请范围 → 配置审批规则 → 查看审计记录 |

### 功能范围

1. **权限查看**：员工查看自己当前拥有的权限清单（功能权限+角色），含生效状态
2. **权限申请**：员工从缺口触发或主动搜索，选择所需权限/角色，填写理由，提交申请
3. **进度追踪**：员工查看申请记录列表，含当前状态、处理人、处理时间
4. **审批处理**：审批人在 OA 底座中查看申请上下文，批准或拒绝
5. **管理员配置**：管理员配置可申请范围（按功能权限/角色维度），开启/关闭能力
6. **权限自动生效**：审批通过后系统自动完成授权

### [FACT] 业务规则

| 规则 | 说明 |
|---|---|
| 申请资格 | 所有正式员工均可提交申请，已离职/停用成员不可 |
| 申请范围 | 仅管理员开放且非系统排除的权限可申请 |
| 申请理由 | 员工需说明申请原因（选填，但建议填写以利审批） |
| 审批人 | 默认为员工的上级组织负责人 |
| 审批决策 | 批准即进入生效流程，拒绝需附原因 |
| 生效机制 | 审批通过后由权限系统自动执行授权 |
| 关闭能力 | 管理员关闭后，员工侧申请入口隐藏；进行中的申请按预设策略处理 |

### [GAP] 待确认的规则

| 规则 | 当前状态 |
|---|---|
| 一次申请可包含的权限数量 | 未定，建议支持多选 |
| 申请理由是否必填 | 未定，建议选填 |
| 审批超时处理方式 | 未定 |
| 关闭能力时进行中申请的处理策略 | 未定 |
| 与现有治理模式的具体技术互斥关系 | 未定 |

## §6 状态、异常与边界

### [CONFIRMED] 核心状态

| 状态 | 含义 | 用户下一步 |
|---|---|---|
| 审批中 | 申请已提交，等待审批人处理 | 查看进度，或联系审批人提醒 |
| 已批准 | 审批人已批准，权限进入生效流程 | 等待系统完成授权 |
| 已生效 | 权限已完成授权，员工可使用 | 回到功能页面使用权限 |
| 已拒绝 | 审批人拒绝申请（附原因） | 查看拒绝原因，重新申请或联系审批人 |
| 已撤销 | 员工在审批前主动撤销 | 重新发起申请 |

### [GAP] 异常场景

| 异常 | 触发条件 | 系统处理 | 用户下一步 |
|---|---|---|---|
| 审批超时 | 审批人超过预设时限未处理 | 系统自动催办/升级 | 等待或联系审批人 |
| 生效失败 | 审批通过后权限系统授权失败 | 系统自动重试，状态保持"已批准" | 等待或联系管理员 |
| 审批人缺失 | 申请人没有上级组织负责人 | 申请无法提交，提示联系管理员 | 联系管理员设置审批人 |
| 能力关闭冲击 | 管理员关闭时存在进行中申请 | 需预设策略（允许完成/强制终止） | 视策略而定 |

## §7 体验蓝图承接要求

### 判断 1：缺口触发是主要入口

- **业务判断**：员工在操作无权限功能时被拦截，是最自然、转化率最高的申请触发场景
- **体验影响**：拦截页除了告知"无权限"，还需告知"能不能申请"、"怎么申请"
- **必须承接的问题**：拦截页如何识别缺失的权限、判断可申请状态、降级策略
- **禁止下游重判**：不需要重新判断"缺口触发是否为主要入口"

### 判断 2：语义降维

- **业务判断**：功能权限、数据权限、角色是管理术语，员工不熟悉
- **体验影响**：权限列表和权限展示需要业务语言描述（"可以做什么"），而不是管理分类名
- **必须承接的问题**：如何把管理术语转译为业务语言，角色和功能权限如何统一呈现
- **禁止下游重判**：不需要重新判断"是否需要语义降维"

### 判断 3：审批上下文决定决策效率

- **业务判断**：审批人需要知道"谁、申请了什么、为什么"才能做判断
- **体验影响**：审批详情页不能只展示权限名称，还需展示申请理由、业务说明、持有情况
- **必须承接的问题**：OA 底座审批页面的自定义信息承载能力范围
- **禁止下游重判**：不需要重新判断"审批人是否需要上下文"

### 判断 4：状态透明度影响信任

- **业务判断**：申请→审批→生效的全链路对员工不透明，是"私下问"的根本原因
- **体验影响**：员工需要随时知道"当前在哪个环节、谁在处理、预计还要多久"
- **必须承接的问题**：进度展示方式、通知策略、生效确认
- **禁止下游重判**：不需要重新判断"状态是否需要可视化"

### 判断 5：关闭行为需要治理设计

- **业务判断**：关闭自助申请能力不是简单功能开关，会影响进行中的申请和已生效的权限
- **体验影响**：关闭时需要告知影响范围，并提供预设策略（允许完成/强制终止）
- **必须承接的问题**：关闭策略的选项设计、关闭后的展示和引导
- **禁止下游重判**：不需要重新判断"关闭是否需要治理设计"

## §8 约束与不做什么

### [FACT] 约束

| 约束 | 说明 |
|---|---|
| 敏感权限系统级排除 | 不可由员工申请，不可通过配置开放 |
| 审批流程引擎由 OA 底座提供 | 不重新设计审批引擎 |
| 上级负责人由组织域定义 | 权限中心引用不定义 |
| 角色定义在管理员侧 | 自助申请可申请角色权限包，但不创建/修改角色 |

### [CONFIRMED] 不做什么

- 不做管理员侧的角色管理与权限配置功能（已有成熟链路）
- 不做审批流程引擎设计（OA 底座承担）
- 不做敏感权限的定义与标记（系统级预置）
- 不做批量权限申请（本次聚焦单次申请）
- 不做权限到期自动回收（属于治理范畴，后续考虑）
