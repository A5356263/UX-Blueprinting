# 需求定案：员工自助申请权限

---

## §0 本次关键判断

**判断：** 这不是给员工加一个申请按钮，而是在现有权限体系里新增一条"员工申请→审批→自动授权"的来源链路。这会触动权限来源模型、生效机制和治理模式兼容性三层底层结构。

**主要影响：** 权限的授予从"纯管理员下发"变成双通道并行（管理员主动授权 + 员工申请审批后自动授权），权限来源解释、查询排障、治理互斥判断都需要随之扩展。

**建议方案：** 复用现有 OA 审批中台承载申请审批链路，可申请范围与现有权限体系（角色/功能权限）对齐而非另建目录，自助申请作为独立治理模式开关与现有模式显式声明共存关系。

**不建议方案：** 另建一套独立的可申请权限目录（会制造第二套权限语言，增加解释和排障成本）；在权限域内自建审批引擎（与已有 OA 审批中台重复建设）。

**关键待确认：** 自助申请与权限变更审批模式是互斥还是依赖关系，直接决定管理端配置结构和体验设计起点。

## §1 需求输入摘要

### 需求背景

企业员工的权限分配目前由权限管理员或超级管理员集中处理。中大型企业中，员工数量多、人员流动频繁，权限新增与变更的工作量较大。部分企业超管为老板本人，业务人员需要权限时须私下找老板处理，沟通成本高，授权时效不稳定。

### 目标用户

- **普通员工：** 需要查看自己已有权限、申请新权限、追踪申请状态
- **权限管理员/超管：** 需要控制自助申请能力的开关、范围与审批流程
- **审批人：** 需要审核员工提交的权限申请并做出决策

### 业务目标

将部分权限申请工作从管理员侧分散到员工侧，降低管理员处理压力，同时保留管理员对申请范围和审批流程的完整控制。

### 功能范围（原始输入明确列出）

- 员工查看自己当前拥有的权限
- 员工主动申请所需权限
- 审批通过后系统自动授权
- 员工查看自己的申请记录和审批状态
- 管理员控制自助申请开关
- 管理员配置员工可申请的权限范围
- 管理员配置审批流程
- 管理员关闭能力时不影响审批中的申请

### 原始输入明确约束

- 只有具备最高权限的管理员可以开启或关闭该能力
- 开启前需设置可申请范围和审批方式
- 可申请范围可按角色或功能权限配置，具体方式待定
- 管理员应可后续调整配置

### 原始输入已知缺口

- 员工端完整业务规则未定义（文档标注"帮我补充"）
- 审批端完整业务规则未定义（文档标注"帮我补充"）
- 管理员关闭能力时的具体处理逻辑未说明
- 自助申请与现有权限治理模式的关系未提及
- 审批表单需要展示哪些信息未定义
- 申请被拒后的员工操作路径未定义

## §2 业务场景判断

### 在现有业务体系中的位置

此项需求属于**对现有权限体系的既有能力扩展**——不是替代现有授权方式，而是在管理员主动授权（ACL_DIRECT / RBAC_ROLE）之外，新增一条员工侧发起的权限获取路径。

现有体系的权限来源包括：用户直授、角色授予、应用可见性、协作可见性。本次需求在此基础上新增第五类来源：**员工自助申请审批后自动授予**。

### 与现有能力的关系

| 现有能力 | 关系 | 说明 |
|---|---|---|
| 用户直授（按人授权） | 并存 | 管理员仍可直接给人授权，不受自助申请开关影响 |
| 角色授权与自动授权规则 | 并存 | 角色的模板化分发与自助申请是两条独立的权限获取路径 |
| 权限变更审批模式 | 待确认 | 自助申请是否需要/能否复用权限变更审批模式作为其审批通道 |
| 子管理员模式 | 边界相交 | 子管理员的管辖范围是否影响自助申请的可申请范围定义 |
| 双管理员互审模式 | 边界相交 | 按 R-009，子管理员与双管理员已互斥；自助申请作为第四种能力需明确与其他模式的共存矩阵 |

### 是否改变治理模式

**会。** 自助申请本质上是一种新的治理模式选择——它改变了"谁能发起权限授予"这个基本前提。现有三种治理模式（子管理员分权、双管理员互审、权限变更审批）均围绕管理员侧行为设计，自助申请首次将发起权赋予员工侧。

### 最大业务不确定性

自助申请与权限变更审批模式的关系。如果二者是互斥的，则管理端需要设计模式选择逻辑；如果是依赖关系（自助申请必须依赖权限变更审批模式作为审批通道），则管理端需要先引导管理员完成审批模式配置再开启自助申请。

### 如果这个判断错了

- 如果把自助申请判为独立模式而实际应复用权限变更审批模式，会导致管理端重复配置、两套审批链路并存，增加管理员理解成本和系统维护复杂度
- 如果把范围定义方式判为按角色而实际需要按功能权限，会导致员工侧信息架构推倒重来
- 如果低估模式兼容性复杂度而按中等复杂度处理，会导致体验蓝图遗漏关键的治理互斥判断和状态流转分支

## §3 需求成立性判断

### 收益

- **减少管理员瓶颈：** 将高频、低风险的权限申请从管理员手动操作中解放出来，管理员只需处理审批而非逐一手动配置 [CONFIRMED]
- **提升授权时效：** 员工不需要线下找人，申请提交后按审批流程推进，时效可预期 [CONFIRMED]
- **规范化权限申请：** 申请有记录、审批有痕迹、授权可追溯，比口头沟通更合规 [CONFIRMED]
- **减轻超管负担：** 对小企业"老板即超管"的场景，减少非必要的权限沟通成本 [CONFIRMED]

### 系统代价

- **权限来源模型需扩展：** 新增一类权限来源类型，影响权限查询、排障、审计的完整链路 [CONFIRMED]
- **状态机需新建：** 申请单的生命周期状态机需要从零定义，并与审批系统、权限系统双向同步 [CONFIRMED]
- **治理互斥矩阵需重新梳理：** 现有 R-009 只覆盖子管理员与双管理员的互斥关系，需扩展为包含自助申请的四模式兼容矩阵 [CONFIRMED]
- **审批表单需新建：** 需要在 OA 审批中台创建对应的审批表单类型、流程模板和字段配置 [GAP] 具体实施成本待评估
- **员工侧入口需设计：** 需要在工作台或全局导航中新增权限查看与申请的入口 [GAP] 具体承载位置待体验蓝图阶段确定

### 更低成本替代路径

- **仅开放"查看自己的权限"，不做申请能力：** 可以解决员工"不知道自己有什么权限"的认知问题，但不能解决"需要新权限时找不到人"的核心痛点。可作为分阶段交付的首期范围
- **优化现有角色自动授权规则：** 如果权限需求有规律可循（如按部门、职务自动匹配角色），加大角色自动授权的覆盖范围可能比开放自助申请更轻量。但无法覆盖个性化、临时性的权限需求
- **管理员侧的权限申请代办/转派：** 不向员工开放申请入口，但在管理端优化权限请求的提交和分发效率。治标不治本

### 成立性结论

建议进入正式体验设计。核心用户痛点真实存在（尤其是中大型企业和"老板即超管"的小企业），现有替代路径只能部分覆盖需求。但进入体验设计前，必须先确认模式兼容关系这一前提条件。

## §4 推荐业务边界

### 推荐能力形态

- 作为权限域内的一项可选治理能力，以开关形态存在，默认关闭 [CONFIRMED]
- 管理员开启前必须完成两项前置配置：可申请范围定义、审批流程设置 [FACT]
- 员工在统一入口查看自己的权限和提交申请，不分散到多个页面 [CONFIRMED]
- 审批通过后由系统自动完成授权，不由管理员手动操作 [FACT]
- 申请记录与审批状态对员工全程可见 [FACT]
- 授权结果纳入现有权限查询与排障链路，标记来源为"自助申请" [CONFIRMED]

### 不推荐能力形态

- 不推荐在自助申请中引入数据范围的员工自行选择——员工不应自行决定数据范围的边界，数据范围应由管理员在配置可申请范围时预设 [CONFIRMED]
- 不推荐员工可以申请超出管理员预设范围的权限——不存在"越级申请"通道 [CONFIRMED]
- 不推荐审批通过后支持审批人手动调整授权内容——审批人的职责是同意/拒绝申请，不是修改申请内容（如需修改应退回让员工重新提交）[CONFIRMED]

### 与现有能力的边界

- **不与用户直授合并：** 管理员在用户授权页直接给人授权时，不走申请审批链路
- **不与角色自动授权混淆：** 角色的自动授权规则（按部门/职务等条件）由系统自动匹配，不需要员工主动申请
- **不替代权限变更审批模式：** 除非确认二者为依赖关系，否则自助申请的审批链路应独立存在

### 应复用的现有能力

- OA 审批中台的审批流程引擎（审批人来源、多人审批方式、超时处理、消息通知）[CONFIRMED]
- 现有权限决策链模型（L0 可见性 → L1 功能权限 → L2 数据权限 → L3 治理生效）[CONFIRMED]
- 现有权限查询与排障链路（按人查询、按用户查看结果、权限详情）[CONFIRMED]

### 不应新增的能力

- 不应在权限域内自建审批引擎
- 不应另建一套独立的可申请权限目录（应与角色/功能权限体系对齐）
- 不应为自助申请单独建立一套授权结果存储

## §5 角色、功能、规则范围

### 角色清单

| 角色 | 职责 | 标记 |
|---|---|---|
| 超级管理员 | 开启/关闭自助申请能力，配置可申请范围和审批流程，可查看所有申请记录 | [FACT] |
| 权限管理员 | 同超管职责范围，取决于是否被授予对应管理权限 | [GAP] 权限管理员的具体权限边界需要与现有子管理员体系对齐 |
| 员工（申请人） | 查看自己的权限，提交权限申请，查看申请记录和审批状态 | [FACT] |
| 审批人 | 审核员工提交的权限申请，决定同意或拒绝 | [FACT] |

### 功能清单

#### F-01 开启/关闭自助申请能力

- **操作角色：** 超级管理员
- **输入：** 开启指令
- **前置校验：** 是否已完成可申请范围配置、是否已完成审批流程设置
- **输出：** 能力状态变更（开启/关闭）
- **关闭时结果：** 已完成的申请不受影响，审批中的申请按预设策略处理（具体策略见 §6 异常部分）[GAP] 关闭策略待确认

#### F-02 配置可申请范围

- **操作角色：** 超级管理员
- **输入：** 选择哪些角色或功能权限纳入可申请范围
- **处理：** 将选中的角色/功能权限标记为"员工可申请"
- **输出：** 可申请范围生效，员工端可见对应申请项
- **约束：** 范围定义方式（按角色/按功能权限/组合）为关键待确认项 [GAP]

#### F-03 配置审批流程

- **操作角色：** 超级管理员
- **输入：** 审批流程定义（审批人、审批节点、多人审批方式等），通过 OA 审批中台完成
- **输出：** 审批流程与自助申请能力绑定，员工提交申请后按此流程流转
- **约束：** 不重复建设审批引擎，复用 OA 审批中台现有能力 [CONFIRMED]

#### F-04 查看自己的权限

- **操作角色：** 员工
- **输入：** 进入权限查看页
- **输出：** 按应用/功能分组展示当前拥有的权限列表，标注每项权限的来源（直授/角色/自助申请等）
- **约束：** 只读，不承载配置能力 [CONFIRMED]

#### F-05 提交权限申请

- **操作角色：** 员工
- **输入：** 选择要申请的权限项、填写申请原因
- **前置条件：** 自助申请能力已开启、所选权限项在可申请范围内
- **输出：** 申请单生成，进入审批流程，员工可见申请状态
- **约束：** 同一权限项在审批中时不允许重复申请 [CONFIRMED]

#### F-06 审批处理

- **操作角色：** 审批人
- **输入：** 审批决策（同意/拒绝），可选填写审批意见
- **处理：** 同意 → 触发自动授权；拒绝 → 申请单状态更新，通知员工
- **输出：** 审批结果同步至权限系统，员工收到结果通知
- **异常：** 自动授权失败时，审批通过但授权未完成，需告警并支持管理员手动处理 [GAP]

#### F-07 查看申请记录

- **操作角色：** 员工 / 管理员
- **输入：** 员工查看自己的申请记录；管理员可按人或按申请单查看
- **输出：** 申请单列表及详情（申请时间、申请内容、审批状态、结果）
- **约束：** 员工的查看范围仅限于自己的申请 [CONFIRMED]

### 关键业务规则

| 编号 | 规则 | 触发条件 | 处理结果 | 不满足时处理 | 标记 |
|---|---|---|---|---|---|
| R-01 | 仅超管可开关 | 非超管尝试开启/关闭 | 拒绝操作 | 提示"仅超级管理员可操作" | [FACT] |
| R-02 | 开启前置检查 | 超管发起开启 | 校验可申请范围和审批流程是否已配置 | 未完成配置时阻止开启，提示缺失项 | [CONFIRMED] |
| R-03 | 申请范围限制 | 员工提交申请 | 校验所申请权限是否在可申请范围内 | 超出范围时阻止提交，提示"该权限不在可申请范围内" | [CONFIRMED] |
| R-04 | 重复申请控制 | 员工提交申请 | 校验同一权限是否已有审批中的申请 | 存在审批中申请时阻止重复提交，提示"该权限已有审批中的申请" | [CONFIRMED] |
| R-05 | 审批通过自动授权 | 审批人同意申请 | 系统自动按申请内容授予权限 | 自动授权失败时：审批通过但授权未完成，触发告警，管理员手动处理 | [GAP] |
| R-06 | 关闭能力时保护审批中申请 | 管理员关闭自助申请 | 已完成的申请不受影响，审批中的申请按预设策略处理 | [GAP] 具体策略待确认（走完/批量取消） | [GAP] |
| R-07 | 权限来源标记 | 审批通过自动授权完成 | 权限来源标记为"自助申请" | 无 | [CONFIRMED] |
| R-08 | 治理模式共存判断 | 开启自助申请时 | 校验与当前已开启的治理模式是否兼容 | 不兼容时阻止开启，提示冲突模式名称及原因 | [GAP] |

## §6 状态、异常与边界

### 核心状态

#### 申请单状态

| 状态 | 说明 | 可见角色 | 可操作角色 | 允许操作 |
|---|---|---|---|---|
| 草稿 | 员工已创建但未提交 | 员工本人 | 员工本人 | 编辑、提交、删除 |
| 审批中 | 已提交，在审批流转中 | 员工本人、当前审批节点审批人、管理员 | 当前审批节点审批人 | 同意、拒绝、转派 |
| 已通过 | 审批通过，授权已完成 | 员工本人、审批人、管理员 | 无（终态） | 仅查看 |
| 已拒绝 | 审批被拒绝 | 员工本人、审批人、管理员 | 员工本人 | 查看拒绝原因，可重新申请 |
| 已撤销 | 员工在审批通过前主动撤销 | 员工本人、已处理审批人、管理员 | 无（终态） | 仅查看 |

#### 自助申请能力状态

| 状态 | 说明 |
|---|---|
| 未配置 | 超管从未开启过，或关闭后未重新配置 |
| 已开启 | 能力生效中，员工可查看和申请 |
| 已关闭 | 能力已关闭，员工不可提交新申请 |

### 关键异常

| 编号 | 异常 | 触发条件 | 系统处理 | 用户下一步 |
|---|---|---|---|---|
| E-01 | 未配置前置条件即尝试开启 | 超管未完成范围/审批配置就开启 | 阻止开启，提示"请先完成可申请范围配置和审批流程设置" | 管理员按引导完成配置 |
| E-02 | 申请权限不在可申请范围 | 员工选择或提交了超出范围的权限 | 阻止提交，明确指出不在范围内的权限项 | 员工确认是否正确选择了权限项 |
| E-03 | 审批人不存在或无效 | 审批流程中的审批人已离职/被移除 | [GAP] 待确认——建议纳入 OA 审批中台的超时转派或数据管理中的流程转派机制 | [GAP] |
| E-04 | 自动授权失败 | 审批通过后系统自动授权执行失败 | 记录失败日志，触发管理员告警，授权状态标记为"待处理" | 管理员在权限管理后台手动完成授权 |
| E-05 | 关闭能力时存在审批中申请 | 管理员在仍有申请审批中时关闭能力 | [GAP] 两种策略待定：A) 允许关闭但审批中的申请继续走完，B) 关闭前提示存在审批中申请并阻止关闭 | [GAP] |
| E-06 | 员工已离职或被禁用 | 审批流转中员工账号状态变更 | 申请单自动作废，通知审批人 | 审批人无需处理 |
| E-07 | 员工已有相同权限 | 员工申请时，该权限已通过其他来源获得 | 提示"你已拥有此权限，无需申请"，阻止提交 [CONFIRMED] | 员工确认权限状态 |
| E-08 | 治理模式冲突 | 管理员尝试开启自助申请时，与当前已开启的治理模式不兼容 | 阻止开启，提示冲突模式名称及原因 [GAP] | 管理员先关闭冲突模式或放弃开启 |

### 状态流转

```
申请单生命周期：
草稿 → (提交) → 审批中 → (同意) → 已通过 → (自动授权) → 完成
                         → (拒绝) → 已拒绝 → (重新申请) → 草稿
              → (撤销) → 已撤销
草稿 → (删除) → 已删除（不展示）

能力生命周期：
未配置 → (完成前置配置 + 开启) → 已开启 → (关闭) → 已关闭 → (重新配置 + 开启) → 已开启
```

## §8 约束与不做什么

### 硬约束

- 不绕过现有权限决策链模型（L0→L1→L2→L3），审批通过后的授权必须走完完整链路 [CONFIRMED]
- 不在权限域内自建审批引擎，审批链路统一由 OA 审批中台承载 [CONFIRMED]
- 不改变现有权限来源的优先级和覆盖规则，自助申请的授权结果与直授、角色授权享有同等的权限效果，但来源标记独立 [CONFIRMED]
- 不向员工开放数据范围自行选择的能力 [CONFIRMED]
- 不突破"只有超管可以开关和配置"的安全边界 [FACT]
- 不替代子管理员模式中的范围隔离逻辑 [CONFIRMED]

### 依赖项

- OA 审批中台的审批表单创建、流程设计与发布能力 [CONFIRMED]
- 现有权限查询与排障链路的来源解释扩展 [CONFIRMED]
- 权限治理模式互斥矩阵的更新（从三种模式扩展为包含自助申请）[GAP]

### 不做什么

- 不做员工之间的权限比较或权限排行榜
- 不做基于 AI 的权限推荐或智能申请建议（首期不做）
- 不做批量申请（单次只能申请一项权限，降低审批复杂度）
- 不做移动端专属流程（复用 OA 审批移动端现有能力即可）
- 不改变管理员在用户授权页的直接授权能力
