# 需求定案：企业数字化产品权限自助申请

---

## §0 本次关键判断

这是一项"把权限授权从管理员集中处理转向员工自助+上级审批+自动生效"的治理结构调整，不是页面级功能优化。

**业务判断**：推荐在现有权限模块中新增"员工自助申请"能力线。**关键前提**是审批流基建（审批引擎、上级负责人路由、自动授权执行接口）的成熟度，它们决定方案可行性和实施路径。**不建议**保留人工执行环节或改为管理员审批——那没有解决时效不稳定的核心矛盾。**最高优先级待确认**：审批流引擎的接口能力是否支持"审批通过后自动触发授权执行"。

---

## §1 需求输入摘要

### 需求背景

中大型企业员工权限分配目前依赖管理员或超级管理员集中处理。员工数量多、人员流动频繁，权限新增、变更、核对工作量大。部分企业的超级管理员就是老板本人。

### 目标用户

- **员工**（核心）：业务人员/经办人员，需要被授予功能权限或加入角色
- **上级组织负责人**：审批人，审批下属的权限申请
- **权限管理员/超级管理员**：负责权限策略配置和治理

### 业务目标

支持员工自助查看和申请权限，把部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对申请范围和审批流程的控制。

### 功能范围

- **覆盖**：功能权限申请 + 角色授权申请
- **不覆盖**：数据权限的自助申请、协作可见性的自助申请

### 明确约束

- 申请范围由管理员预制，排除敏感权限 [FACT]
- 审批人为上级组织负责人，不是管理员 [FACT]
- 审批通过后自动生效，不留人工执行环节 [FACT]
- 作为已有平台新增能力，需兼容现有权限模块架构 [CONFIRMED]

### 输入缺口

- 审批流引擎基建就绪度未明确 [GAP]
- 自动授权执行接口可用性未明确 [GAP]

## §2 业务场景判断

### 业务定位

这是权限管理域中**新增的自助服务子能力**，不是对现有授权方式的替代或重构。现有管理员侧授权保持不变，新增一条员工侧发起→上级审批→系统自动执行的并行路径。

### 与现有能力的关系

| 现有能力 | 关系 | 说明 |
|----------|------|------|
| 管理员用户直授 | 并行存在 | 管理员仍可主动为员工授权，自助申请是新增入口 |
| 角色授权 | 被复用 | 员工申请加入角色后，复用已有角色-权限绑定关系 |
| 审批中台 | 依赖关系 | 审批流需要接入平台审批能力路由到上级负责人 |
| 组织域成员关系 | 依赖关系 | 审批人匹配依赖组织域中"上级负责人"关系的完整性 |

### 最大业务不确定性

**审批流转链路能否闭环**——从"员工提交"到"上级审批"到"系统自动授权"的三段链路，每一段都依赖平台既有基建。审批流引擎和自动授权执行接口的就绪度是当前最大的业务风险。

### 判断错误的影响

如果判断错"审批基建已就绪"但实际上未就绪，后续体验方案中"自动生效"环节需要改为半自动（通知管理员手动执行），这会破坏核心价值主张（时效可预期）。如果判断错"上级负责人关系已定义完整"但实际上不完整，审批人匹配会大面积失败，需要补充兜底机制。

## §3 需求成立性判断

### 价值判断

**成立。** 从三个角度看：

1. **问题真实** — 中大型企业人员流动性高，非正式沟通模式无法规模化管理，这是管理常识级痛点，不依赖特定场景验证
2. **收益明确** — 员工获得可预期的授权时效，管理员从执行者变为策略定义者，审批人在上下文中做判断而非空白审批，三层角色各有所获
3. **用户体验收益** — 从"找到人→说清楚→等待"的模糊链路变为"提交→等审批→自动获得"的清晰链路

### 系统代价

- **建设成本中等**：新增员工端入口、申请目录、申请 Drawer、审批详情 Drawer、我的申请页等前端实体
- **依赖成本偏高**：审批流引擎、上级负责人路由、自动授权接口三项基建缺一不可
- **维护成本中等**：管理员需持续维护可申请目录和敏感权限标记

### 更低成本替代方案

- **不做自助申请，只优化管理员授权体验**：在后台增加批量授权、模板授权能力。这能解决管理员的效率问题，但不解决员工侧的"不知道找谁、不知道有什么权限"问题
- **不做自动生效，只做申请+审批通知**：审批通过后通知管理员手动执行。这降低了对授权接口的依赖，但重新引入了时效不稳定的核心矛盾

**建议**：进入正式体验设计，但前提是审批流基建和自动授权接口必须在设计阶段确认就绪度。如果基建不满足，需要在上游提前暴露风险，而不是等方案完成后再回头补。

## §4 推荐业务边界

### 推荐能力形态

- 员工侧：可申请目录浏览 → 权限/角色详情查看 → 选择并发起申请 → 追踪进度 → 接收结果
- 审批人侧：待办列表 → 申请详情查看（含权限说明和风险提示）→ 审批操作
- 管理员侧：角色和功能权限的"可自助申请"标记开关 → 批量标记 → 配置生效

### 不推荐能力形态

- **不推荐**让员工自由申请全部权限（必须预制范围）— 安全失控
- **不推荐**由管理员审批（必须限定为上级负责人）— 未解决管理者负担
- **不推荐**审批通过后留人工执行环节 — 未解决时效不稳定
- **不推荐**在员工侧暴露可申请的数据权限或协作可见性 — 超出本次范围

### 与现有能力的边界

- 复用现有角色-权限绑定关系（员工加入角色即获得关联的功能权限）
- 复用现有组织架构成员关系（审批人路由依赖上级负责人定义）
- 不改变管理员侧授权路径
- 不改变敏感权限的管控方式

### 不新增

- 不新增独立的审批流引擎（复用平台审批能力）
- 不新增权限对象模型（复用现有主体、资源、动作、范围定义）

## §5 角色、功能、规则范围

### 角色职责

| 角色 | 职责 |
|------|------|
| 员工 | 浏览可申请目录 → 选择需要项 → 提交申请（含理由）→ 追踪进度 → 申请通过后使用权限 / 被拒后查看原因并决定是否重试 |
| 上级组织负责人 | 接收审批待办 → 查看申请详情（含申请人、内容、理由、权限说明）→ 通过或拒绝 → 拒绝时填写原因 |
| 权限管理员 | 在角色/功能权限管理中标记"可自助申请" → 批量标记/取消标记 → 配置即时生效；持续维护可申请目录和敏感权限边界 |

### 功能单元

| 功能 | 输入 | 处理 | 结果 |
|------|------|------|------|
| 浏览可申请目录 | 员工进入权限申请页面 | 系统按管理员预制的可申请标记过滤，排除敏感权限，聚合展示 | 角色列表（全量，区分可申请标记）+ 功能权限列表（仅可申请项） |
| 提交权限申请 | 员工选择项 + 申请理由 | 校验重复项和必填项，匹配审批人，写入申请记录 | 申请进入待审批状态，记录持久化 |
| 审批申请 | 审批人通过/拒绝操作 + 拒绝原因（拒绝时必填） | 审批人操作确认后，写入审批结果 | 通过→触发自动授权；拒绝→通知申请人 |
| 自动授权 | 审批通过事件 | 系统执行为用户添加功能权限/加入角色 | 授权成功→通知双方；授权失败→通知双方+失败原因 |
| 配置可申请目录 | 管理员设置角色/权限的可自助申请标记 | 系统保存配置，排除敏感权限的保护性禁用 | 员工端目录即时更新 |

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时处理 |
|------|----------|----------|------------|
| 申请范围预制 | 员工浏览可申请目录 | 仅展示管理员标记为可申请的项，排除敏感权限 | 员工不可见的项视为无权申请 |
| 审批人确定 | 员工提交申请 | 自动匹配申请人上级组织负责人 | 匹配失败→通知员工联系管理员 |
| 申请理由必填 | 提交申请时 | 理由为空则校验不通过 | InlineError + 阻断提交 |
| 拒绝原因必填 | 审批人拒绝时 | 原因为空则校验不通过 | InlineError + 阻断提交 |
| 审批通过自动生效 | 审批人点击通过 | 触发授权执行接口 | 执行失败→通知双方+失败原因 |
| 已有权限重复申请 | 提交时检测 | 提示重复项，支持一键移除 | 不阻断，可保留重复项（系统自动过滤） |

## §6 状态、异常与边界

### 核心状态

| 状态 | 说明 | 用户下一步 |
|------|------|------------|
| 待审批 | 申请已提交，等待上级审批 | 等待或催办 |
| 审批人已查看 | 审批人已打开查看 | 等待审批结果 |
| 已通过 | 审批人已批准 | 等待权限生效 |
| 已拒绝 | 审批人未批准 | 查看拒绝原因，重新申请或放弃 |
| 授权中 | 系统正在执行授权 | 等待 |
| 授权成功 | 权限已生效 | 去使用权限 |
| 授权失败 | 系统自动授权不成功 | 联系管理员 |

### 关键异常

| 异常 | 触发条件 | 系统处理结果 | 用户下一步 |
|------|----------|------------|------------|
| 审批人不存在/已离职 | 提交后匹配审批人失败 | 申请状态→"审批人匹配失败"；通知员工+通知管理员 | 员工联系管理员确认组织关系，管理员修复后系统自动重新路由 |
| 审批超时 | 超过预设时限（如24h/48h）未处理 | 员工端可催办，审批端超时标记置顶 | 员工催办或联系审批人 |
| 自动授权失败 | 授权执行接口返回失败 | 申请状态→"授权失败"；通知双方+失败原因 | 员工联系管理员；审批人可协助排查 |
| 批量授权部分失败 | 逐项执行时部分失败 | 成功项即时生效，失败项展示原因；状态→"部分成功" | 失败项单独重新申请或联系管理员 |
| 权限已拥有重复申请 | 员工选择的项含已拥有权限 | 提醒可移除，不阻断提交 | 选择一键移除重复项或保留（系统自动过滤） |

### 边界

- 敏感权限不在员工可申请目录中展示，管理员也无法标记为可自助申请 [GAP：敏感权限标记机制是否已定义]

## §7 体验蓝图承接要求

| 业务判断 | 对体验设计的影响 | 必须承接的问题 | 禁止下游重判 |
|----------|----------------|---------------|-------------|
| 申请范围由管理员预制，排除敏感权限 | 目录不是全量权限，员工只看到可申请的项 | 权限目录的筛选逻辑、可申请标记的展示方式、敏感权限的保护机制 | 不得让员工自由申请全部权限 |
| 审批人为上级组织负责人 | 审批人自动匹配，申请人不需要选择 | 审批人匹配失败时的降级处理、审批上下文中展示权限说明和风险提示 | 不得改为管理员审批或让申请人自选审批人 |
| 审批通过后自动生效 | 生效环节无人工干预，状态需实时可感知 | 自动授权执行链路、授权成功/失败的反馈机制、部分成功的处理策略 | 不得保留人工执行环节 |
| 覆盖功能权限和角色授权 | 目录有两类授权对象，角色是权限集合 | 角色与功能权限的分栏展示、角色详情中包含关联权限清单 | 不得扩展至数据权限或协作可见性 |
| 员工可看到全部角色 | 角色列表全量，但仅部分可申请 | 可申请角色与不可申请角色的视觉区分、全部角色的可浏览性 | 不得隐藏不可申请的角色 |
| 申请需填写理由 | 理由帮助审批人判断 | 理由输入引导、理由校验、拒绝时原因的填写 | 不得取消理由必填 |
| 申请进度需透明可追踪 | 等待区间需中间态 | 状态时间线、催办机制、超时标记 | 不得仅展示终态 |

## §8 约束与不做什么

### 硬约束

- 作为已有平台新增能力，需兼容现有权限模块的架构和数据模型 [FACT]
- 所有申请必须可审计、可追溯 [CONFIRMED]
- 管理员仍为权限策略的定义者和控制者，不被绕过 [CONFIRMED]
- 从申请到生效的全链路必须有明确的失败感知和处理机制 [CONFIRMED]

### 不做什么

- 不覆盖数据权限的自助申请 [FACT]
- 不覆盖协作可见性的自助申请 [FACT]
- 不做员工自由申请全部权限（必须预制范围） [FACT]
- 不做管理员侧的权限申请代办（审批人限定为上级负责人） [CONFIRMED]
- 不做审批通过后仍需人工执行的半自动模式 [FACT]

## §9 待确认问题

### 层级一：影响主方案是否成立

| 问题 | 影响 | 建议确认方 |
|------|------|------------|
| 审批流引擎的接口能力是否支持"审批通过后自动触发授权执行" | 若不可支持，自动生效需改为半自动，核心价值受损 | 后端架构师 |
| 自动授权执行接口就绪度 | 是否存在可被外部事件触发的授权执行接口 | 后端架构师 |

### 层级二：影响局部体验设计

| 问题 | 影响 | 建议确认方 |
|------|------|------------|
| 审批流引擎是否提供"审批人已查看"事件回调 | 影响申请进度时间线中"审批人已查看"节点的可行性 | 后端架构师 |
| 审批流引擎是否支持超时自动提醒 | 影响审批超时机制的实现方式 | 后端架构师 |
| 组织域中"上级负责人"关系是否已定义完整 | 影响审批人匹配的准确性和异常处理策略 | 产品/架构师 |
| 权限管理域是否有"敏感等级"标记 | 影响可申请目录的筛选逻辑和敏感权限保护机制 | 产品/知识维护方 |
| 员工端入口位置（工作台/导航/全局） | 影响入口设计和引导策略 | 产品/体验决策方 |
