# 需求定案：员工自助权限申请

---

## §0 本次关键判断

**判断：** 这不是加一个申请入口的局部功能，而是在现有权限体系中引入第五种权限获取路径——员工发起、审批通过后系统自动授权。

**主要影响：** 来源模型扩展、状态机变三方闭环、审批中台成链路强依赖、与三种现有治理模式的关系需明确。

**建议方案：** 定义为新的权限变更触发方式，复用现有审批链路骨架，独立配置范围与流程，与现有治理模式按互斥规则管理。

**不建议方案：** 不做独立的孤立申请系统；不做无审批直接生效；不在治理模式关系未明确前进入详细设计。

**关键待确认：** 自助申请与"权限变更审批模式"是复用还是并列关系，会直接改变流程架构。

---

## §1 需求输入摘要

### 需求背景

当前企业员工的权限分配由管理员或超管集中处理。中大型企业中人员流动频繁，权限新增、变更的工作量大。员工需要权限时通过私下沟通找管理员处理，沟通成本高、时效不稳定。

### 目标用户

- **员工：** 需要获取业务权限的普通成员，希望减少等待和沟通成本
- **审批人：** 收到申请后需要做出审批决策的角色
- **权限管理员/超管：** 控制自助申请能力的开启范围、审批流程和配置调整

### 业务目标

把部分权限申请工作从管理员侧分散到员工侧，降低管理员处理压力，同时让权限变更可追踪、可审计。文档提出"推动至少 3 家客户使用"作为初步指标。

### 功能范围（文档明确列出）

- 员工查看自己当前拥有的权限
- 员工主动申请所需权限
- 审批通过后系统自动授权
- 员工查看自己的申请记录和审批状态
- 管理员控制是否允许自助申请
- 管理员控制可申请权限范围
- 管理员控制审批流程
- 管理员关闭或调整该能力

### 明确约束

- 保留管理员对申请范围和审批流程的控制
- 必须结合当前产品已有权限体系
- 审批人不存在或审批链路配置错误时需要保护机制
- 与现有治理模式可能存在互斥，需明确能否同时开启

### 文档缺口

- 员工端业务规则（文档标注"帮我补充"）
- 审批端业务规则（文档标注"帮我补充"）
- 管理员关闭能力时在途申请的处理方式
- 可申请范围的配置粒度（按角色还是按功能点）
- 审批方式的具体类型

## §2 业务场景判断

### 在现有体系中的定位

这项需求是对现有权限管理体系的**能力扩展**，而非替代或互斥。当前权限域中权限获取的来源只有四种：管理员直授、角色分配、应用可见性配置、协作可见性配置。员工自助申请引入了一种新的权限获取触发方式——从"管理员单向分配"扩展为"员工主动发起、审批后自动分配"。

它不是对现有授权能力的替代，而是在管理员直授和角色分配之外增加一条补充路径。

### 与现有能力的关系

- **与"用户授权"（按人直授）的关系：** 互补。管理员直授仍保留，自助申请作为并行通道。
- **与"权限变更审批模式"的关系：** 待确认。如果该模式已开启，自助申请是复用其审批链路还是另起一条独立链路，决定了流程架构的复杂度和状态模型的规模。
- **与"子管理员模式"的关系：** 存在潜在冲突。子管理员只能在其管辖范围内授权，自助申请的可申请范围可能与子管理员的组织管辖范围重叠或冲突。
- **与"双管理员互审模式"的关系：** 可能存在互斥。两个模式都改变了权限的生效机制，同时开启时需要明确优先级和互斥规则。

### 最大业务不确定性

自助申请与三种现有治理模式（权限变更审批、子管理员分权、双管理员互审）的共存或互斥关系，文档未给出任何方向。这个不确定性会直接影响整个流程架构和状态设计。

### 判断错误会带来的影响

如果把自助申请错误地判断为"权限变更审批模式的子集"，后续的流程设计会过度依赖现有审批链路，当审批配置缺位时整个自助申请链路断裂。如果错误地判断为"完全独立的新模式"，可能重复建设审批能力，且与现有治理模式产生未预期的状态冲突。

## §3 需求成立性判断

### 业务价值

- 对中大型企业，员工数量多且权限变更频繁的场景，能显著降低管理员处理压力和员工等待时间 [CONFIRMED]
- 权限变更从线下沟通转为线上审批，每次变更都有记录可追踪，补上了现有权限治理中缺少的"申请发起"这一审计起点 [CONFIRMED]
- 为后续权限自助化治理（如权限续期、权限回收确认）提供基础的申请链路 [CONFIRMED]

### 系统代价

- 权限来源模型需要扩展，影响从授权、查询、排障到审计的全链路 [CONFIRMED]
- 审批中台成为链路的强依赖，审批配置缺失时自助申请无法闭环 [CONFIRMED]
- 需要在管理端新增一套配置界面（可申请范围、审批方式、开关控制），增加管理员的认知和操作负担 [CONFIRMED]
- 与现有治理模式的互斥规则需要在权限管理引擎层面实现，不是纯前端逻辑 [CONFIRMED]

### 更低成本替代路径

- **仅开放"我的权限"查看能力，不做申请。** 可以解决员工不知道自己有什么权限的痛点，但不解决获取权限的时效问题。
- **保留管理员集中授权，优化授权效率。** 通过批量授权、权限模板等方式降低管理员操作成本，管理边界不变但效率提升。
- **先做"权限申请表单 + 通知管理员"，不做自动审批和自动授权。** 申请提交后以通知形式到达管理员，由管理员在现有授权页完成授权。降低了审批引擎对接成本和状态机改造风险。

### 成立判断

该需求对目标客户群（中大型、人员流动频繁、权限变更高频）有真实价值，但系统代价和上游不确定性较高。建议在补充关键确认项（特别是与权限变更审批模式的关系）后进入正式体验设计。[CONFIRMED]

## §4 推荐业务边界

### 推荐能力形态 [CONFIRMED]

- 管理员可开启/关闭"员工自助申请权限"能力开关 [FACT]
- 管理员可配置可申请权限范围（推荐初期按角色粒度，保留后续扩展到功能点的余地）[CONFIRMED]
- 管理员可为自助申请绑定审批流程 [FACT]
- 员工可查看自己当前拥有的权限列表 [FACT]
- 员工可从可申请范围中选择权限并提交申请 [FACT]
- 审批人可查看申请内容并做出通过/拒绝决策 [FACT]
- 审批通过后系统自动完成授权，拒绝后申请结束并通知员工 [CONFIRMED]
- 员工可查看申请记录和当前状态 [FACT]
- 管理员关闭能力时，在途申请需有明确处理策略 [CONFIRMED]

### 不推荐能力形态 [CONFIRMED]

- 不推荐员工可自由申请任意权限（无范围限制）
- 不推荐申请直接生效跳过审批环节
- 不推荐员工自行撤销已生效的权限（撤销应走管理端）
- 不推荐自助申请与所有治理模式同时开启不加互斥规则
- 不推荐在审批引擎未就绪时开放员工申请入口

### 复用现有能力 [CONFIRMED]

- 复用现有"权限查询"的权限结果解释能力
- 复用现有"用户授权"页的权限详情查看能力
- 复用审批管理域的流程引擎和审批操作能力
- 复用现有治理状态模型的状态定义（draft / pending / approved / effective / rejected / revoked）

### 不应新增 [CONFIRMED]

- 不应新建独立的审批引擎
- 不应新建独立的权限存储或来源真源
- 不应修改现有四种权限来源的定义和优先级规则

## §5 角色、功能、规则范围

### 角色职责

| 角色 | 职责 | 关键约束 |
|---|---|---|
| 超管/权限管理员 | 开启/关闭自助申请能力；配置可申请范围；绑定审批流程；监控申请记录；调整或关闭配置 | 只有最高权限管理员可操作开关 [FACT]；配置变更需考虑在途申请的处理 |
| 员工（申请人） | 查看已有权限；发现权限缺口；从可申请范围中选择并提交申请；追踪申请状态 | 只能申请管理端配置的可申请范围内的权限 [FACT] |
| 审批人 | 查看申请内容与申请人已有权限；做出通过或拒绝决策 | 审批人由管理端配置的审批流程决定；需有足够的决策依据 |
| 系统 | 校验申请范围合法性；驱动审批流转；审批通过后自动执行授权；记录申请与审批日志 | 自动授权失败时需有补偿机制 |

### 关键功能

**管理端配置**

- 输入：管理员开启自助申请开关 → 处理：系统检查是否已完成必要配置（可申请范围、审批方式） → 输出：能力生效，员工端入口可见 [CONFIRMED]
- 输入：管理员配置可申请范围（角色粒度） → 处理：系统校验所选范围在管理员管辖范围内 → 输出：可申请范围保存，作为员工端可申请列表的数据源 [CONFIRMED]
- 输入：管理员关闭自助申请开关 → 处理：系统检查在途申请数量，按预设策略处理在途单 → 输出：能力关闭，员工端入口隐藏 [CONFIRMED]

**员工端操作**

- 输入：员工打开"我的权限" → 处理：系统按已有来源模型聚合展示当前权限结果 → 输出：权限列表，按应用或功能点分组展示，标注来源 [CONFIRMED]
- 输入：员工从可申请范围中选择权限并填写申请原因 → 处理：系统校验所选权限在可申请范围内、不与已有权限重复 → 输出：生成申请单，进入审批流程 [CONFIRMED]
- 输入：员工查看申请记录 → 处理：系统按时间倒序展示历史申请及当前状态 → 输出：申请记录列表，含状态、提交时间、处理人 [CONFIRMED]

**审批端操作**

- 输入：审批人查看申请详情 → 处理：系统展示申请权限内容、申请原因、申请人已有权限全貌 → 输出：审批决策页 [CONFIRMED]
- 输入：审批人通过申请 → 处理：系统触发自动授权流程，按申请人所选权限完成授予 → 输出：权限生效，通知员工 [CONFIRMED]
- 输入：审批人拒绝申请 → 处理：系统结束申请流程 → 输出：申请状态变更为已拒绝，通知员工 [CONFIRMED]

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时处理 |
|---|---|---|---|
| 能力开关前置校验 | 管理员开启自助申请 | 检查可申请范围和审批方式是否已配置 | 未配置时阻止开启，提示需先完成配置 [CONFIRMED] |
| 申请范围校验 | 员工提交申请 | 校验所选权限在管理端配置的可申请范围内 | 不在范围内时拒绝提交，提示"该权限不在可申请范围内" [CONFIRMED] |
| 已有权限去重 | 员工提交申请 | 校验申请权限是否已经拥有且有效 | 已拥有时提示"你已拥有该权限"，阻止重复申请 [CONFIRMED] |
| 关闭能力时的在途申请 | 管理员关闭自助申请能力 | [GAP] 需确认：作废并通知 / 允许走完 / 转为管理员处理 | [GAP] |
| 审批人不存在 | 申请进入审批流程但审批人为空 | [GAP] 需确认：通知管理员、挂起申请或自动拒绝 | [GAP] |
| 自动授权失败 | 审批通过后系统执行授权 | 记录失败日志，通知管理员人工介入 | 触发补偿授权流程 [CONFIRMED] |
| 治理模式冲突检测 | 管理员尝试同时开启自助申请与互斥的治理模式 | 阻止同时开启，提示互斥关系 | 管理员需先关闭互斥模式再开启 [CONFIRMED] |
| 配置变更时在途申请范围 | 管理员修改可申请范围时存在在途申请 | [GAP] 需确认：在途申请按旧范围还是新范围执行 | [GAP] |

## §6 状态、异常与边界

### 核心状态

| 状态 | 说明 | 用户下一步 |
|---|---|---|
| 待提交 | 员工已选择权限但未提交 | 编辑或提交申请 |
| 审批中 | 申请已提交，等待审批人处理 | 等待审批结果，可查看进度 |
| 已通过 | 审批人已通过，权限尚未生效或已生效 | 权限生效后可开始使用对应功能 |
| 已拒绝 | 审批人已拒绝 | 查看拒绝原因，可重新提交 |
| 已生效 | 权限已自动授予并生效 | 正常使用对应功能 |
| 已撤销 | 申请被管理员撤销或能力关闭导致作废 | 查看撤销原因，能力恢复后可重新申请 |
| 已过期 | [GAP] 申请是否有时效限制待确认 | [GAP] |

### 关键状态流转

```
待提交 → 审批中 → 已通过 → 已生效
                → 已拒绝
审批中 → 已撤销（管理员关闭能力 / 手动撤销）
已拒绝 → 待提交（员工重新申请）
```

### 关键异常

| 异常 | 触发条件 | 系统处理结果 | 用户下一步 |
|---|---|---|---|
| 申请范围为空 | 管理员未配置可申请范围时，员工进入申请页 | 展示空状态，提示"暂无可申请的权限，请联系管理员" | 联系管理员完成范围配置 |
| 能力已关闭 | 员工在申请过程中管理员关闭了能力 | [GAP] 取决于关闭策略：作废在途单或允许走完 | [GAP] |
| 审批链路未配置 | 开启自助申请但未绑定有效审批流程 | 阻止管理员开启，提示需先配置审批流程 | 进入审批管理完成流程配置 |
| 审批人账号异常 | 审批人离职、停用或被移除 | 申请无法流转，系统检测到审批人不可达时触发告警或自动转交 | [GAP] 需确认转交策略：上级/管理员/挂起 |
| 重复提交 | 员工对同一权限重复发起申请 | 已有审批中或已生效的同权限时阻止提交 | 查看已有申请的状态 |
| 自动授权失败 | 审批通过后权限引擎授予失败 | 记录失败日志，标记该申请为"待补偿"，通知管理员 | 管理员人工介入完成授权 |
| 权限被管理员收回 | 自助申请获得的权限被管理员手动移除 | 权限正常移除，按现有来源模型记录来源变更 | 如有需要可重新提交自助申请 |
| 可申请范围变更导致在途申请越界 | 管理员缩小了可申请范围，在途申请中的权限不再可申请 | [GAP] 需确认：按发起时范围还是当前范围判断 | [GAP] |

## §7 体验蓝图承接要求

### 承接清单

**① 权限来源透明度**

- 业务判断：新增第五种权限获取路径后，员工和管理员都需要能区分权限是"管理员给的"还是"自己申请的"。
- 体验影响：权限列表、权限详情的来源展示需要扩展；员工需要理解"我能申请什么"与"我已经有什么"之间的关系。
- 必须承接的问题：如何让员工在申请前就知道自己能申请什么、申请后能得到什么能力；如何在权限结果页清晰区分不同来源；如何在权限被收回时追溯来源历史。
- 禁止下游重判：来源分类和优先级由权限域规则定义，体验蓝图不可新增或修改来源类型。

**② 多角色任务链路闭环**

- 业务判断：管理员、员工、审批人三条角色链路各自独立，但不能断裂——任何一条链路的断点都会导致整个自助申请能力不可用。
- 体验影响：管理员的配置链路需要清晰的完成引导（配置范围→绑定审批→开启）；员工的申请链路需要从"发现缺口"到"获得权限"全程无障碍；审批人的决策链路需要足够的判断依据和便捷的操作入口。
- 必须承接的问题：管理员首次配置时如何引导完成三步前置配置；员工如何发现"我缺什么权限"而不仅是"我有什么权限"；审批人如何在审批页快速理解申请人已有权限全貌和本次申请的影响范围。
- 禁止下游重判：审批节点的配置、多人审批方式（会签/或签/依次）由审批管理域承载，体验蓝图只做审批体验的承接，不设计审批引擎逻辑。

**③ 治理可控性**

- 业务判断：管理员需要对自助申请能力有明确、可逆的控制感。开关不是简单的"开/关"，而是一个有生命周期管理的治理动作。
- 体验影响：开启前的前置校验、开启后的状态监控、关闭时的风险告知和在途处理，都需要在体验上清晰呈现。
- 必须承接的问题：管理员开启时的前置配置检查如何呈现；能力运行中如何让管理员感知当前的申请量、审批效率和异常情况；关闭时如何告知在途申请数量和预设处理方式，避免管理员在不确定后果时做决策。
- 禁止下游重判：能力开关的互斥规则和关闭策略由权限域定义，体验蓝图不可自行决定互斥关系或关闭策略。

**④ 状态可见性与在途处理**

- 业务判断：员工提交申请后到权限生效前，中间有一个"审批窗口期"。这个窗口期内的状态不透明会导致员工反复询问审批人，失掉自助的意义。
- 体验影响：状态需要持续可见且有明确的时间预期；审批中如果发生能力关闭、范围变更等事件，员工需要及时感知且理解发生了什么。
- 必须承接的问题：申请提交后的状态追踪如何让员工随时可见；审批超时或审批人异常时如何告知员工并给出下一步；能力关闭或范围变更时如何通知受影响员工，不让在途申请静默消失。
- 禁止下游重判：状态定义和流转规则由权限治理状态模型定义，体验蓝图不可新增或改写状态语义。

**⑤ 审批决策依据**

- 业务判断：审批人的决策质量取决于看到的信息完整度。如果审批人在审批页只能看到"某人申请了某权限"，而看不到这个人已有权限的全貌和这个权限对应的实际能力，审批会变成盲签。
- 体验影响：审批页的信息组织直接影响审批效率和授权安全性。
- 必须承接的问题：如何在审批页中呈现申请人已有权限全貌而不造成信息过载；如何让审批人理解"批准后会有什么变化"；拒绝时如何收集拒绝原因以帮助员工理解下一步。
- 禁止下游重判：权限结果的聚合方式和来源解释口径由权限域定义，体验蓝图不可自行设计权限计算或聚合逻辑。

## §8 约束与不做什么

### 硬约束 [FACT]

- 必须保留管理员对申请范围和审批流程的控制权 [FACT]
- 必须结合当前产品已有权限体系，不能另起独立的权限存储 [FACT]
- 审批通过后系统自动授权，不能依赖人工操作完成授权 [FACT]
- 仅最高权限管理员可开启或关闭自助申请能力 [FACT]

### 依赖项 [CONFIRMED]

- 审批管理域的流程引擎和审批操作能力 [CONFIRMED]
- 权限域的来源模型、治理状态模型、权限查询能力 [CONFIRMED]
- 成员管理域的员工身份和状态信息 [CONFIRMED]

### 不做什么 [CONFIRMED]

- 不做审批流程引擎本身（节点配置、多人审批方式等由审批管理域承载）
- 不做权限冲突自动解决（如申请了与已有权限互斥的权限，只检测不自动处理）
- 不做跨端底层适配（各终端自行承接，定案只定义业务规则和状态）
- 不修改现有四种权限来源的定义和优先级规则
- 不做权限的自动续期或到期提醒（本次范围外）
- 不做移动端审批的原生适配（本次范围外）

## §9 待确认问题

### 层级一：影响主方案是否成立

1. **自助申请与"权限变更审批模式"的关系**
   - 影响：决定自助申请的流程架构是复用现有审批链路还是独立建设
   - 建议确认方：产品 + 权限域技术负责人

2. **管理员关闭能力时在途申请的处理策略**
   - 影响：决定关闭行为的完整语义和员工侧体验
   - 建议确认方：产品

3. **自助申请与子管理员模式、双管理员互审模式的互斥规则**
   - 影响：决定能否同时开启，以及开启顺序的校验逻辑
   - 建议确认方：权限域技术负责人 + 产品

### 层级二：影响局部体验设计

4. **可申请范围的配置粒度**
   - 影响：员工端申请列表的信息组织和搜索方式
   - 建议确认方：产品 + 设计

5. **审批人不存在或不可达时的降级策略**
   - 影响：审批页的异常展示和员工的等待体验
   - 建议确认方：产品 + 审批域技术负责人

6. **申请是否有有效期/超时机制**
   - 影响：状态模型是否需要"已过期"状态
   - 建议确认方：产品

7. **管理员修改可申请范围时，在途申请按新范围还是旧范围执行**
   - 影响：员工在途申请可能因范围缩小而失效的体验处理
   - 建议确认方：产品 + 权限域技术负责人
