# 需求定案：子管理员复制

---

## §0 本次关键判断

子管理员「复制」功能是在现有子管理员配置能力上新增的批量效率路径，不改变底层业务骨架。

- **判断**：这项需求的本质是解决大客户实施阶段的批量配置效率问题，不是新增治理模式或改造权限模型。
- **主要影响**：200+ 级别子管理员客户的配置时间将从逐条勾选压缩为批量复制，显著降低实施周期。
- **建议方案**：在子管理员列表操作列新增「复制」入口，通过弹窗选择复制内容和目标对象。非互审模式下直接写入权限；双管理员互审模式下提交审批，审批通过后写入。
- **不建议方案**：不要为复制单独新建页面（弹窗足够承载）；不要在本次引入「覆盖」选项（与当前叠加逻辑冲突，且无明确需求支撑）。
- **关键待确认**：无影响主方案成立的层级一待确认项。

---

## §1 需求输入摘要

### 需求背景

集团型企业使用「子管理员模式」下放权限管理能力。部分客户子管理员数量较多（如广西交投 200+），这些子管理员的「可授权功能」通常一致，但「可授权组织」不同。当前需逐个配置，效率较低。

### 业务目标

降低大客户批量配置子管理员的时间成本和实施周期。

### 产品目标

新增「复制」能力，使权限管理员可以复用已配置子管理员的权限信息。

### 功能范围

- 子管理员列表操作列新增「复制」入口
- 复制弹窗，支持选择复制内容（可授权组织 / 可授权功能）
- 支持选择一个或多个用户作为复制目标
- 员工选择弹窗复用现有样式
- 点击确认时按顺序校验（复制信息 → 复制对象 → 加入状态 → 认证状态）
- 复制成功后 toast 提示
- 复制成功后生成操作记录
- 双管理员互审模式下生成审批

### 明确约束

| # | 约束 |
|---|------|
| 1 | 复制来源必须是已有子管理员 |
| 2 | 复制信息至少选择一项 |
| 3 | 复制对象至少选择一名用户 |
| 4 | 复制对象最多选择 200 名 |
| 5 | 复制对象必须已加入且已认证 |
| 6 | 已有子管理员接收复制采用叠加逻辑，不覆盖原有权限 |
| 7 | 普通用户接收复制后成为子管理员 |
| 8 | 复制成功必须生成操作记录 |
| 9 | 开启双管理员互审模式时，复制需生成审批 |

### 原始输入未覆盖区域

- 审批中的复制申请是否支持撤销
- 操作记录是否支持按复制操作聚合查看
- 「加入状态」校验的目标状态口径（已启用 / 已加入）未统一

## §2 业务场景判断

### 业务定位

这次是在「子管理员模式」治理框架内新增的批量效率能力，不是引入新的治理模式或改变权限模型。复制操作后端的规则（叠加 / 成为）和生效机制（直接生效 / 审批后生效）都是已有逻辑的复用。

### 与现有能力的关系

- 复用子管理员配置页中的「可授权组织」和「可授权功能」数据结构
- 复用现有员工选择弹窗
- 复用双管理员互审模式的审批链路
- 与操作记录、审计体系衔接

### 最大不确定性

审批机制细节已确认（审批通过后才写入权限），不存在影响主方案的方向性不确定性。

### 如果判断错了

如果本次复制操作实际上改变了子管理员的状态模型或引入了新的状态流转（如「复制中」状态），则 §5 和 §6 需要重新评估。基于当前材料，没有证据指向这种可能性。

---

## §3 需求成立性判断

### 收益

- 批量配置效率提升：对 200+ 子管理员客户，从逐条勾选变为一次批量复制
- 减少重复劳动和误配置风险
- 降低大客户实施周期，提升客户满意度
- 与现有双管理员互审模式兼容

### 系统代价

- 新增一个操作入口和弹窗
- 操作记录系统新增两条记录模板
- 审批链路已存在，复用成本低

### 更低成本替代路径

- 模板导入（如 Excel 批量导入子管理员配置）：适合初始大规模配置场景，但交互路径长，不适合日常逐个小调整。复制功能更适合日常运维场景。
- 角色化授权（通过角色模板分发权限）：已在能力范围内，但与子管理员模式是不同治理路径。复制补的是子管理员体系内的效率缺口。

### 判断

建议进入正式体验设计。

## §4 推荐业务边界

### 推荐能力形态

- 在子管理员列表操作列新增「复制」入口
- 以弹窗承载复制内容选择和复制对象选择
- 复制内容默认为全选（可授权组织 + 可授权功能），至少选一项
- 复制对象选择器复用现有员工选择弹窗
- 点击确认后执行顺序校验，通过后写入或提交审批
- 操作结果区分场景反馈

### 不推荐能力形态

- 不要为复制单独新建页面：弹窗足够承载，且不打断管理员对列表的上下文感知
- 不要引入「覆盖」选项：当前需求明确为叠加逻辑，且无需求支撑覆盖场景
- 不要新增「从零创建子管理员后复制」的混合路径：复制入口只从已有子管理员发起
- 不要为复制单独设计审批流程：复用双管理员互审模式既有审批链路

### 与现有能力的边界

- 复制入口仅在「子管理员模式」列表中出现
- 复制来源必须是已有子管理员
- 复制不改变来源子管理员的配置
- 复制不创建新的子管理员配置入口（复用现有添加子管理员路径）

### 复用对象

- 员工选择弹窗（与添加子管理员一致）
- 双管理员互审模式的审批链路
- 操作记录系统的存储和展示能力

### 不应新增的内容

- 不应新增子管理员状态类型
- 不应新增审批流程类型
- 不应新增权限维度或业务对象

## §5 角色、功能、规则范围

### 角色与职责

| 角色 | 职责 |
|------|------|
| 权限管理员（操作者） | 选择来源子管理员，发起复制操作，确认复制内容与目标，查看复制结果 |
| 来源子管理员 | 作为被复制对象，提供其可授权组织和可授权功能配置（被动） |
| 复制目标用户（普通用户） | 接收复制内容，复制后成为子管理员（被动） |
| 复制目标用户（已有子管理员） | 接收复制内容，叠加到现有配置上（被动） |
| 互审管理员 | 在双管理员互审模式下审批复制申请 |

### 功能与闭环

| 功能 | 输入 | 处理 | 输出 | 结果 |
|------|------|------|------|------|
| 复制入口 | 用户点击子管理员列表操作列「复制」 | 打开复制弹窗，加载来源子管理员的配置信息 | 复制弹窗 | 弹窗打开成功 |
| 复制信息选择 | 用户勾选可授权组织和/或可授权功能 | 记录选中项 | 选中状态更新 | 至少一项时确认按钮可点击 |
| 复制对象选择 | 用户打开员工选择弹窗，选择目标用户 | 记录选中用户列表 | 选中用户显示在弹窗中 | 至少一名时确认按钮可点击 |
| 复制校验 | 用户点击确认 | 按顺序校验：复制信息→复制对象→加入状态→认证状态 | 校验结果 | 通过后执行复制 |
| 复制执行（非互审） | 校验通过 | 对每个目标用户按规则处理：普通用户→成为子管理员并写入权限；已有子管理员→叠加权限 | 写入权限数据 + 操作记录 | toast「复制成功」 |
| 复制执行（互审中） | 校验通过 | 生成审批申请 | 审批实例 + 操作记录 | toast「已提交审批」 |
| 审批处理 | 另一位管理员审批 | 通过→写入权限；驳回→流程结束 | 权限数据或驳回通知 | 写入成功或驳回 |
| 操作记录生成 | 复制执行完成 | 按复制内容分条写入操作记录 | 操作记录 | 可追溯 |

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时处理 |
|------|----------|----------|-------------|
| 复制内容必选 | 用户点击确认 | 继续后续校验 | toast 提示「请选择复制信息」 |
| 复制对象必选 | 复制信息已选 | 继续后续校验 | toast 提示「请选择至少一名复制对象」 |
| 加入状态校验 | 复制对象已选 | 目标用户已加入→继续 | 提示「XXX 加入状态不是已加入，不能成为子管理员」 |
| 认证状态校验 | 加入状态通过 | 目标用户已认证→继续 | 提示「XXX 未完成实名认证，不能成为子管理员」 |
| 普通用户成为子管理员 | 目标用户非子管理员 | 写入可授权组织和/或可授权功能，用户成为子管理员 | — |
| 已有子管理员叠加 | 目标用户已是子管理员 | 在原有配置上叠加新的可授权组织和/或可授权功能 | — |
| 互审模式审批 | 系统中已开启双管理员互审 | 不直接写入，提交审批 | 审批驳回时不写入 |
| 操作记录 | 复制成功或提交审批成功 | 按复制内容分条写入操作记录 | — |

## §6 状态、异常与边界

### 核心状态

| 状态 | 说明 | 系统处理结果 | 用户下一步 |
|------|------|-------------|-----------|
| 复制弹窗打开 | 用户已进入复制流程 | 加载来源子管理员配置，显示默认全选的复制信息和空的选择对象 | 选择复制内容和目标 |
| 复制校验中 | 用户已点击确认 | 顺序执行四项校验 | 等待校验结果 |
| 复制校验不通过 | 某项校验失败 | 中断校验，显示对应错误提示 | 根据提示修正后重新提交 |
| 复制执行中（非互审） | 校验通过，写入权限 | 对每个目标用户执行写入 | 等待处理结果 |
| 复制成功（非互审） | 权限写入完成 | 生成操作记录，显示 toast | 查看结果或继续其他操作 |
| 审批提交成功（互审中） | 校验通过，审批已提交 | 生成审批实例和操作记录，显示 toast | 等待审批结果 |
| 审批通过 | 另一位管理员通过审批 | 写入权限数据 | 确认权限已生效 |
| 审批驳回 | 另一位管理员驳回申请 | 不写入权限 | 查看驳回原因，重新操作 |

### 异常与边界

| 异常场景 | 触发条件 | 系统处理结果 | 用户下一步 |
|----------|----------|-------------|-----------|
| 复制内容未选 | 用户未勾选任何选项即点击确认 | 阻断确认，提示「请选择复制信息」 | 勾选至少一项后重新确认 |
| 复制对象未选 | 用户未选择任何目标即点击确认 | 阻断确认，提示「请选择至少一名复制对象」 | 选择至少一名用户后重新确认 |
| 目标用户未加入 | 部分目标用户加入状态为未加入 | 阻断确认，列出未加入用户，提示「XXX 加入状态不是已加入，不能成为子管理员」 | 移除未加入用户或确认该用户已加入后重新操作 |
| 目标用户未认证 | 部分目标用户未完成实名认证 | 阻断确认，列出未认证用户，提示「XXX 未完成实名认证，不能成为子管理员」 | 移除未认证用户或确认该用户已完成认证后重新操作 |
| 部分目标用户异常 | 200 名目标中部分校验不通过 | 完整校验结果需明确是否部分提交还是全部退回 | 需要产品明确策略 |
| 审批超时 | 互审模式下的审批长期未处理 | 依赖于审批系统的超时机制 | 联系另一位管理员处理 |
| 来源子管理员配置变更中 | 复制时来源子管理员正在被编辑 | 应锁定或提示配置变更中，避免复制到不一致数据 | 等待配置稳定后重新操作 |
| 操作记录写入失败 | 复制成功但操作记录写入异常 | 需要明确是否阻断复制流程 | 查看操作记录是否缺失 |

**注**：「部分目标用户异常」（200 名中部分校验不通过）的处理策略当前未明确：是全部退回还是通过部分提交？这个决策会影响体验设计方向，已列入 §9。

## §7 体验蓝图承接要求

### 要求 1：复制入口的位置语义

- **业务判断**：复制入口放在子管理员列表操作列最左侧，说明这是一条与编辑、移除并列的操作路径
- **体验影响**：用户需要区分「编辑已有子管理员」和「复制已有子管理员给他人」两种操作的目的差异
- **必须承接的问题**：操作列按钮的排布既要突出新增的复制入口，又不能降低原有操作的可发现性
- **禁止下游重判**：复制入口必须出现在操作列，不得移到列表顶部的批量操作区

### 要求 2：批量复制的结果反馈

- **业务判断**：一次复制可能涉及最多 200 个目标用户，每个用户的处理规则可能不同（成为 / 叠加），校验结果也可能不同（全部通过 / 部分通过）
- **体验影响**：如果只用单一 toast 反馈，用户无法知道具体每个目标用户的处理结果
- **必须承接的问题**：批量复制后必须提供按用户维度的结果反馈，明确谁成功、谁失败、失败原因；部分成功的边界策略需要产品确认后纳入方案
- **禁止下游重判**：不得只用「复制成功」一句话覆盖所有批量场景

### 要求 3：双管理员互审模式下的语义区分

- **业务判断**：互审模式下审批通过后才写入权限，「复制成功」的实际含义是「已提交审批」而非「已生效」
- **体验影响**：统一 toast「复制成功」会让用户误以为权限已生效，实际还在等审批
- **必须承接的问题**：互审模式下，操作完成后的反馈必须明确表达「已提交审批，等待确认后生效」；审批通过后应有可感知的结果通知，而非静默写入
- **禁止下游重判**：不得在互审模式下使用与非互审模式相同的成功表述

### 要求 4：混合目标用户的规则差异前置提示

- **业务判断**：复制目标中可能混着普通用户（将「成为」子管理员）和已有子管理员（将「叠加」权限），两种规则在确认前就可以区分
- **体验影响**：用户点击确认后才知道谁走了什么规则，缺乏事前掌控感
- **必须承接的问题**：在选择复制对象后、点击确认前，系统应提示目标用户中哪些是已有子管理员（将叠加）、哪些是普通用户（将成为），让用户确认预期
- **禁止下游重判**：不得将规则差异的提示延后到复制完成后

### 要求 5：操作记录的消费场景

- **业务判断**：复制操作按复制内容分条存储（可授权组织一条、可授权功能一条），但用户实际追溯时关注的是「某次复制操作」的整体
- **体验影响**：两条独立记录的用户信息（来源、目标、时间）重复，用户需要自行关联同一批次的两条记录
- **必须承接的问题**：操作记录的展示层面需要考虑如何将同一复制操作的两条记录聚合展示，避免用户手动关联
- **禁止下游重判**：不得要求用户自行关联两条操作记录来理解一次完整的复制操作

### 要求 6：审批中的复制申请状态可见性

- **业务判断**：互审模式下复制申请提交后到审批通过前，目标用户看不到权限变化，权限管理员也需要跟踪哪些申请还在审批中
- **体验影响**：审批中的复制申请对操作者是不可见的，操作者只能去审批系统查看，脱离了子管理员列表的上下文
- **必须承接的问题**：在子管理员列表或相关位置，需要让权限管理员感知到「有复制申请在审批中」的状态；审批通过后，目标用户的子管理员身份和权限应在列表中可见
- **禁止下游重判**：不得要求管理员离开当前页面前往审批系统自行查询复制申请的审批状态

## §8 约束与不做什么

### 硬约束

- 复制入口仅在「子管理员模式」列表中出现，不出现在其他模块
- 复制来源必须是已有子管理员
- 复制信息至少选择一项
- 复制对象至少选择一名用户，最多选择 200 名
- 复制对象必须已加入且已认证
- 已有子管理员接收复制采用叠加逻辑，不得覆盖
- 普通用户接收复制后自动成为子管理员
- 双管理员互审模式下，审批通过后才写入权限
- 复制成功必须生成操作记录
- 子管理员模式与双管理员互审模式不可同时开启（R-009），但复制逻辑需预判互审场景，非互审模式下直接生效

### 不做什么

- 不新增「覆盖」选项
- 不为复制单独创建新的审批类型
- 不改变子管理员的状态模型
- 不新增权限维度或业务对象
- 不为复制设计独立页面
- 不做批量导入（与复制是不同的效率路径）
- 不做复制后自动通知目标用户

## §9 待确认问题

### AI 设计判断

| 判断 | 依据 |
|------|------|
| 不需要为复制单独建页面，弹窗足够 | 复制操作的复杂度不高于添加子管理员，弹窗不打断列表上下文 |
| 不需要引入「覆盖」选项 | 当前需求明确是叠加，且无覆盖场景的需求支撑 |
| 不需要为复制设计独立审批流程 | 复用双管理员互审既有审批链路 |
| 复制成功表述需区分互审/非互审场景 | 互审模式下审批通过后才写入，语义完全不同 |
