# 需求定案：子管理员权限复制

## §0 本次关键判断

**判断**：在子管理员配置中新增批量复制能力，是用户直授能力体系中「复制」往子管理员场景的一次自然延伸，不改底层权限对象关系和生效机制。

**主要影响**：批量配置效率从逐人手动勾选变为一键复用。但体验质量取决于三个关键点——校验失败的反馈方式、操作后果在确认前的透明度、以及复制后权限是否实际可用。

**建议方案**：选人阶段前置过滤不符合条件的用户（加入状态、认证状态），确认前展示操作后果摘要（新增子管理员数、叠加权限数、复制内容），部分校验失败时支持过滤后继续而非全部回退。

**不建议方案**：不在选人阶段做任何过滤（仅提交时校验拦截），不展示操作后果预览，部分失败时一刀切全部回退。

**关键待确认**：复制时是否需要校验目标用户的组织管辖范围与来源可授权组织的匹配性；权限叠加时的去重策略。

---

## §1 需求输入摘要

### 需求背景

集团型企业在使用子管理员模式时，大量子管理员的「可授权功能」配置相同，仅「可授权组织」不同。当前需要逐人手动勾选，实施工作量大。典型场景如广西交投存在 200+ 子管理员，重复配置成本显著。

### 目标用户

权限管理员 / 超级管理员：负责维护子管理员及其可授权范围的核心操作者。

### 业务目标

- 支持将已有子管理员的权限信息（可授权组织、可授权功能）复制给其他用户
- 降低批量配置的重复劳动
- 支持批量复制（最多 200 人）
- 操作可追溯，满足审计要求

### 功能范围（原始输入摘要）

- 在子管理员列表操作列增加「复制」入口
- 复制弹窗包含两部分：复制信息（可授权组织 / 可授权功能，默认全选，至少选一项）、复制对象（支持多选，最多 200 人）
- 确认时按顺序校验：复制信息 → 复制对象 → 加入状态 → 认证状态
- 普通用户接收复制后成为子管理员；已有子管理员接收复制后叠加权限
- 复制成功生成操作记录；开启双管理员互审时生成审批

### 明确约束

- 复制入口仅在子管理员模式中出现
- 复制来源必须是已有子管理员
- 复制对象上限 200 名
- 复制对象必须已加入且已认证
- 复制成功必须生成操作记录

### 输入缺口

- 加入状态和认证状态的统一表述口径（文档中同时出现「已启用/已加入」）
- 部分用户校验失败时的处理策略
- 复制后目标用户的组织管辖范围与被复制组织的匹配性处理
- 权限叠加时的去重逻辑

## §2 业务场景判断

### 业务定位

这项需求在现有权限体系中属于**既有能力的场景延伸**，不是新增能力域。

当前权限域已包含「用户直授」中的复制能力（按人授权场景下的权限复制），但尚未覆盖「子管理员配置」场景。本次需求是把复制能力的适用面从「给用户授权」扩展到「给子管理员配置可授权范围」——操作对象从普通用户变为子管理员候选者，复制的不是业务权限而是「授权的权限」。

### 与现有能力的关系

- 与「用户直授-复制」：同属复制模式，但操作入口不同（子管理员列表 vs 用户授权列表），复制内容语义不同（可授权范围 vs 业务权限）
- 与「角色批量授权」：互补关系。角色适合模板化长期管理，复制适合一次性快速复用。两者不应互相替代
- 与「子管理员手动配置」：增量补充，不替代手动配置路径

### 是否改变治理模式

不改变。复制操作遵循现有治理框架——结果即时生效（除非开启双管理员互审），子管理员范围隔离规则不变，审计契约沿用现有字段模型。

### 最大业务不确定性

目标用户的组织管辖范围与复制来源的可授权组织是否匹配——如果复制了来源的「华东区」可授权组织给一个只能管辖「华南区」的用户，复制操作成功但权限实际不可用。这个场景的处理策略会直接影响选人器的过滤逻辑和复制后的状态反馈。

### 如果这个判断错了

如果复制能力实际上需要改变权限来源模型（比如复制产生新的权限来源类型），或者需要单独的状态机和审批链路，那后续的体验设计、审计字段、操作记录格式都需要重新评估。

## §3 需求成立性判断

### 用户问题是否真实

真实。集团型企业（如广西交投 200+ 子管理员）逐人手动勾选相同功能权限，是经过验证的痛点。这不是假设场景。

### 业务价值

- 直接降低大客户实施周期和实施人力成本 [FACT]
- 减少重复配置中的人为漏选、错选 [CONFIRMED]
- 为后续批量权限治理提供交互模式基础 [CONFIRMED]

### 系统代价

- 新增复制弹窗及校验链路，中等前端工作量 [CONFIRMED]
- 操作记录需支持新的操作类型（复制-可授权组织、复制-可授权功能）[FACT]
- 双管理员互审模式下需对接审批中台 [FACT]
- 不需改动底层权限判定引擎、组织底座或状态机 [CONFIRMED]

### 更低成本替代路径

- **角色模板**：如果子管理员的权限组合是有限几种模式，可以预置角色模板批量分发，比复制更结构化。但不适用于「以人为参照物」的灵活复用场景
- **导入 Excel**：允许管理员通过表格批量导入子管理员配置。表达能力更强但操作门槛更高，且失去「以现有配置为参照」的直观性

### 结论

建议进入正式体验设计。需求方向成立，中等复杂度，不改底层业务骨架。体验设计的重点应放在批量操作的校验反馈、操作后果透明度和治理一致性上。

## §4 推荐业务边界

### 推荐能力形态

- 以已有子管理员为复制来源，支持将其可授权组织、可授权功能（可多选）复制给一个或多个目标用户
- 复制为一次性动作，不建立来源与目标之间的持续关联
- 复制完成后，目标用户的权限独立于来源——后续修改来源不影响已复制的目标

### 不推荐能力形态

- 不建立「权限模板」概念（那是角色体系的事）
- 不支持「仅复制部分组织」的细粒度选择（保持与现有可授权组织配置粒度一致）
- 复制不触发来源用户的任何变更

### 与现有能力的边界

- 区别于角色：复制是一次性动作，角色是持续关联。复制后的权限是真源，角色则是来源之一
- 区别于手动配置：复制是快捷方式，结果等价于手动逐项配置
- 区别于用户直授中的复制：操作入口不同，复制的权限语义不同

### 要复用的能力

- 员工选择器（与「添加子管理员」弹窗一致）
- 操作记录基础设施
- 双管理员互审的审批中台对接

### 不该新增的能力

- 不新建独立的权限来源类型
- 不改变子管理员范围隔离模型
- 不新增权限状态或生效机制

## §5 角色、功能、规则范围

### 角色

**权限管理员 / 超级管理员**

- 职责：维护子管理员配置，对已有子管理员执行复制操作，选择复制内容和目标用户，确认执行
- 可见范围：子管理员列表、复制入口、复制弹窗、操作记录
- 不可做：超出自身管理范围的操作（受子管理员范围隔离约束）

**被复制子管理员**

- 职责：作为复制来源，提供可授权组织和可授权功能配置
- 不参与复制流程中的任何确认或审批（仅作为数据来源）

**复制对象用户**

- 职责：无主动操作。接收复制后或成为子管理员，或在现有权限上叠加
- 前置条件：必须已加入企业、必须已完成实名认证 [FACT]

### 功能

**复制入口**

- 输入：管理员在子管理员列表中定位目标子管理员
- 处理：点击操作列「复制」按钮
- 输出：打开复制弹窗，复制信息来源默认为当前子管理员

**复制信息选择**

- 输入：弹窗中的可授权组织、可授权功能勾选项
- 处理：默认全选，管理员可取消勾选，但至少保留一项 [FACT]
- 输出：确定本次复制的内容范围

**复制对象选择**

- 输入：管理员通过员工选择器搜索和勾选目标用户
- 处理：支持多选，最多 200 人 [FACT]
- 输出：确定本次复制的目标用户列表

**复制执行与校验**

- 输入：复制信息 + 复制对象
- 处理：按顺序校验——复制信息是否勾选 → 复制对象是否选择 → 加入状态是否已加入 → 认证状态是否已认证 [FACT]
- 输出：校验通过则执行复制；校验失败则展示对应错误提示

**复制结果处理**

- 输入：校验通过的复制信息 + 目标用户列表
- 处理：目标原本不是子管理员→设为子管理员并写入权限；原本已是子管理员→在现有配置上叠加 [FACT]
- 输出：toast 提示结果；生成操作记录；若开启双管理员互审则生成审批 [FACT]

### 关键业务规则

**复制信息必选规则**

- 触发条件：管理员取消所有复制信息勾选后点击确认
- 处理结果：校验拦截
- 不满足时处理：提示「请选择复制信息」，阻止提交 [FACT]

**复制对象必选规则**

- 触发条件：管理员未选择任何目标用户时点击确认
- 处理结果：校验拦截
- 不满足时处理：提示「请选择至少一名复制对象」，阻止提交 [FACT]

**加入状态校验规则**

- 触发条件：目标用户中存在加入状态非「已加入」的用户 [FACT]
- 处理结果：校验拦截，提示「XXX、XXX 加入状态不是已加入，不能成为子管理员」 [FACT]
- 不满足时处理：需产品确认——全部回退还是过滤后继续 [GAP]

**认证状态校验规则**

- 触发条件：目标用户中存在未完成实名认证的用户 [FACT]
- 处理结果：校验拦截，提示「XXX、XXX 未完成实名认证，不能成为子管理员」 [FACT]
- 不满足时处理：同上 [GAP]

**叠加规则**

- 触发条件：复制对象原本已经是子管理员 [FACT]
- 处理结果：在原有可授权组织/可授权功能基础上叠加，不覆盖 [FACT]
- 去重策略：需求文档未提及，需确认相同权限项的去重行为 [GAP]

**审计记录规则**

- 触发条件：复制成功 [FACT]
- 处理结果：生成两条操作记录——「复制-可授权组织」和「复制-可授权功能」，分别记录来源子管理员、目标用户列表、操作时间 [FACT]
- 不满足时处理：复制失败不生成记录 [CONFIRMED]

**双管理员互审规则**

- 触发条件：系统开启双管理员互审模式且复制成功 [FACT]
- 处理结果：生成一条审批，进入审批链路 [FACT]
- 生效时机：审批通过后权限生效（遵循现有治理状态模型） [CONFIRMED，依据知识库 24_治理状态模型]

## §6 状态、异常与边界

### 核心状态

**复制操作的生命周期**

- 操作中：管理员打开弹窗，正在选择复制信息和目标用户
  - 用户下一步：完成选择后点击确认
- 校验拦截：提交时未通过校验（信息未选 / 对象未选 / 状态不符 / 未认证）
  - 用户下一步：根据错误提示修正后重新提交
- 复制成功（直接生效）：校验通过且未开启双管理员互审，权限即时生效
  - 用户下一步：关闭弹窗，在列表中查看结果或继续其他操作
- 复制成功（待审批）：校验通过且开启双管理员互审，已生成审批
  - 用户下一步：等待另一位管理员审批 [CONFIRMED，依据知识库 24_治理状态模型]
- 复制失败：系统异常导致操作未完成
  - 用户下一步：根据失败原因决定重试或联系支持

### 关键异常

**部分目标用户校验失败**

- 触发条件：多个目标用户中部分不符合加入状态或认证状态要求
- 系统处理结果：需求文档未明确。可能的处理方式——①全部回退，提示所有不满足的用户；②自动过滤不满足的用户，仅对满足的执行复制并告知过滤结果
- 用户下一步：需产品确认处理策略后确定 [GAP]

**复制来源的子管理员状态在操作期间变更**

- 触发条件：管理员打开复制弹窗期间，来源子管理员被删除、停用或权限范围被修改
- 系统处理结果：需求文档未提及。建议提交时做最终一致性校验
- 用户下一步：提示「复制来源已变更，请重新操作」[CONFIRMED，设计判断]

**目标用户数量超限**

- 触发条件：管理员在员工选择器中选择了超过 200 名用户
- 系统处理结果：选择器应限制最多 200 人 [FACT]
- 用户下一步：减少选择至 200 人以内

**目标用户组织管辖范围与复制内容不匹配**

- 触发条件：复制来源的可授权组织超出目标用户的组织管辖范围
- 系统处理结果：需求文档未提及。可能——①复制时校验并提示；②复制成功但不生效部分；③不做校验
- 用户下一步：需产品确认策略后确定 [GAP]

**双管理员互审审批被拒绝**

- 触发条件：复制生成的审批被另一位管理员拒绝
- 系统处理结果：遵循治理状态模型——状态变为 `rejected`，权限不生效 [CONFIRMED，依据知识库 24_治理状态模型]
- 用户下一步：可在操作记录中查看审批结果，必要时重新发起复制

### 边界条件

- 复制来源与目标为同一人时：需求文档未明确。建议允许（叠加自身权限），或提示「不能复制给自己」[GAP]
- 目标用户已被删除或退出企业时：应在选人器中不可见，或提交时校验拦截 [CONFIRMED]
- 操作的幂等性：重复复制同一来源给同一目标，依据叠加规则会重复叠加相同权限。是否允许取决于去重策略 [GAP]

## §7 体验蓝图承接要求

以下按「业务判断 → 体验影响 → 必须承接的问题 → 禁止下游重判」逐条展开：

---

**1. 批量校验的双层策略**

业务判断：校验涉及四个步骤（复制信息 → 复制对象 → 加入状态 → 认证状态），其中后两项在选择阶段即可判断。

体验影响：如果只在提交时校验，管理员选完 200 人后被拦下，体验断裂严重。

必须承接的问题：
- 选人器中如何前置标识不符合条件的用户（不可选 / 可选但提示风险）
- 提交时的校验作为兜底，如何与前置过滤的信息保持一致
- 部分用户在前置过滤后仍因并发变更而校验失败时，如何反馈和恢复

禁止下游重判：校验项的顺序和内容已由产品规则确定，体验蓝图不应调整校验项或顺序。

---

**2. 操作后果的确认前预览**

业务判断：复制涉及三种后果——新增子管理员、叠加已有子管理员权限、仅更新特定维度（组织或功能）。

体验影响：管理员在确认前不知道自己即将做什么，尤其是批量 200 人时，属于高风险盲操作。

必须承接的问题：
- 确认按钮前如何呈现后果摘要（新增 N 人、更新 M 人、复制内容为哪些）
- 摘要信息如何分层展示（先总览后明细），避免信息过载
- 摘要中如何区分「将变为子管理员」和「将叠加权限」两类目标

禁止下游重判：复制内容是「可授权组织+可授权功能」两个维度，体验蓝图不应新增维度或拆分粒度。

---

**3. 复制操作的可追溯性**

业务判断：复制生成两条操作记录（组织+功能），但管理员的心理模型是「一次复制操作」。

体验影响：操作记录列表中两条分散的记录难以还原「这次复制做了什么」。

必须承接的问题：
- 两条操作记录是否需要统一的聚合标识（如批次 ID），便于关联查看
- 操作记录详情中如何清晰展示来源、目标列表、复制内容和结果
- 双管理员互审模式下，操作记录的生效状态如何与审批状态联动

禁止下游重判：审计字段的最小集合（who / to_whom / what / where / when / why / approval / outcome / snapshot）已由审计契约确定。体验蓝图不应删减字段。

---

**4. 治理模式下的状态一致性**

业务判断：双管理员互审模式下，复制不即时生效，需走审批链路。当前需求文档用「复制成功」覆盖了所有情况。

体验影响：如果 toast 说「复制成功」但权限实际未生效（待审批），用户产生错误认知。后续审批被拒绝时，用户更困惑。

必须承接的问题：
- 直接生效和待审批两种结果的 toast、弹窗关闭后状态、列表反馈需要分别设计
- 审批中的复制操作在操作记录中如何表达（状态标记、与直接生效的区分）
- 审批被拒绝后，是否需要通知发起人

禁止下游重判：治理状态模型（draft → pending → approved → effective → rejected → revoked）已由知识库确定。体验蓝图不应新增或修改状态节点。

---

**5. 组织范围匹配的用户提示**

业务判断：复制不校验目标用户的组织管辖范围与来源可授权组织的匹配性（当前需求未定义此项校验）。

体验影响：可能出现「复制成功但目标用户实际无法授权对应组织」的情况，管理员不知情。

必须承接的问题：
- 确认前是否需要提示「请确认目标用户的管辖范围覆盖复制的组织」（取决于产品确认结果）
- 如果产品决定不做系统校验，体验侧是否需要在复制完成后提供「建议检查管辖范围匹配」的提示
- 如果产品决定做系统校验，校验结果如何呈现

禁止下游重判：是否做系统校验由产品决定。体验蓝图不自行决定校验策略。

---

**6. 权限叠加的去重语义**

业务判断：叠加不覆盖，但若目标已有相同的权限项，是去重静默处理还是提示。

体验影响：影响操作后果摘要的准确性——如果去重，摘要中「实际新增内容」与「复制内容」不一致。

必须承接的问题：
- 如果去重：摘要中是否需要区分「已存在」和「本次新增」
- 如果不做提示：操作记录是否需要体现去重情况
- 如果提示：何时提示、如何表达

禁止下游重判：叠加不覆盖的规则已确定。去重策略由产品决定，体验蓝图不自行确定。

## §8 约束与不做什么

### 硬约束

- 复制入口仅在「子管理员模式」中出现 [FACT]
- 复制来源必须是已有子管理员 [FACT]
- 复制信息至少选择一项 [FACT]
- 复制对象至少选择一人，最多 200 人 [FACT]
- 复制对象必须已加入企业且已完成实名认证 [FACT]
- 复制成功必须生成操作记录 [FACT]
- 不改变子管理员范围隔离模型 [CONFIRMED]
- 不改变权限来源模型和生效机制 [CONFIRMED]

### 不做什么

- 不建立来源与目标的持续关联（复制是一次性动作，非绑定）
- 不支持对复制内容的细粒度编辑（如仅复制部分可授权组织中的特定节点）
- 不覆盖已有子管理员的现有权限（叠加模式）
- 不在本需求中引入「权限模板」或「角色预设」概念
- 不改变「添加子管理员」的现有流程

### 依赖项

- 员工选择器组件（复用「添加子管理员」弹窗的现有实现）
- 操作记录基础设施（需支持新的操作类型）
- 双管理员互审的审批中台对接（如开启）

## §9 待确认问题

### 层级一：影响主方案是否成立

1. **复制时是否需要校验目标用户的组织管辖范围与来源可授权组织的匹配性？**
   - 影响：决定选人器的过滤逻辑、提交校验的步骤、复制后的状态反馈
   - 建议确认方：产品经理

2. **部分目标用户校验失败时的处理策略是什么？**
   - 影响：决定批量操作的体验模式——全部回退 / 过滤后继续 / 让用户选择
   - 建议确认方：产品经理

3. **权限叠加时，相同权限项的去重策略是什么？**
   - 影响：决定操作后果摘要的呈现方式和操作记录的详细程度
   - 建议确认方：产品经理 + 后端开发

### 层级二：影响局部体验设计

4. **加入状态和认证状态的目标状态统一表述口径是什么？**
   - 影响：校验提示语、选人器中的状态标签
   - 建议确认方：产品经理（文档中「已启用/已加入」两处不一致）

5. **双管理员互审模式下复制完成后，toast 提示语和列表反馈是什么？**
   - 影响：操作结果的即时反馈设计
   - 建议确认方：产品经理

6. **复制来源与目标为同一人时，是否允许？**
   - 影响：选人器的过滤规则
   - 建议确认方：产品经理

7. **复制弹窗关闭后，是否需要刷新列表并定位到目标用户？**
   - 影响：操作后的列表交互逻辑
   - 建议确认方：产品经理（可与体验蓝图协同确定）
