# 需求定案：员工自助申请权限

## §0 本次关键判断

**判断**：这不是给现有权限页加一个申请入口，而是在当前四种权限来源之外新增一种"员工发起→审批→系统自动授权"的权限获取方式。

**主要影响**：权限来源模型、生效机制、治理模式互斥约束都会变化，不能按"既有能力扩展"处理。

**建议方案**：复用现有"权限变更审批模式"的治理框架和审批中台能力，将自助申请定义为该模式下的一种新发起方式，而非独立治理模式。可申请范围优先按角色配置（粒度清晰、员工理解成本低），后续按需扩展功能权限粒度。

**不建议方案**：新建独立治理模式（会与子管理员模式/双管理员模式产生额外互斥约束）；将自助申请做成纯粹的审批中台表单（会丢失权限来源解释能力）。

**关键待确认**：自助申请是否复用现有权限变更审批模式；可申请范围按角色还是功能权限配置。

---

## §1 需求输入摘要

### 需求背景
[FACT] 当前企业员工权限分配由管理员集中处理，中大型企业员工数量多、流动频繁，权限新增和变更工作量较大。
[FACT] 部分企业超级管理员为老板本人，员工需权限时私下找老板处理，沟通成本高、时效不稳。
[FACT] 希望将部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对范围和流程的控制。

### 目标用户
[FACT] 中大型企业员工（申请者）、权限管理员（配置者）、审批人（处理者）、超级管理员（开关控制者）。
[FACT] 初步目标为至少 3 家客户使用。

### 业务目标
[FACT] 员工可查看自己当前权限、主动申请所需权限、经审批后自动获得权限、查看申请记录和审批状态。
[FACT] 管理员可控制是否开启、可申请范围、审批流程，以及关闭或调整该能力。

### 功能范围
[FACT] 覆盖五个核心场景：管理员配置自助申请权限、员工查看自己权限、员工申请权限、审批人处理申请、管理员关闭自助申请能力。

### 明确约束
[FACT] 关闭能力时不能影响正在审批中的申请。
[FACT] 配置、审批、校验环节需设置安全保护，防止可申请范围过宽导致越权。
[FACT] 需要与现有权限治理模式兼容，避免模式互斥。

### 需求文档缺口
[GAP] 员工端业务规则未定义（文档标注"帮我补充"）。
[GAP] 审批端业务规则未定义（文档标注"帮我补充"）。
[GAP] 可申请范围的配置维度未定（文档说"可以按角色或功能权限配置，但具体采用哪种需要进一步设计"）。
[GAP] 管理员关闭能力时的具体处理规则未完整（文档标注"会发生什么"）。
[GAP] 审批流程是由管理员自定义还是系统预设未明确。

## §2 业务场景判断

### 业务定位
这是一项**新增能力**。现有权限体系不支持员工端主动发起权限获取，所有权限授予均从管理员侧单向操作。自助申请在现有"权限变更审批模式"的框架下，新增一种由员工端发起、经审批后自动授权的获取方式。

### 与现有能力的关系

现有权限来源共四种：个人直授（ACL_DIRECT）、角色授予（RBAC_ROLE）、应用可见性（APP_VISIBILITY）、协作可见性（COLLAB_VISIBILITY）。审批类权限变更已由"权限变更审批模式"治理框架覆盖，该模式定义了发起→审批→生效的状态流转和责任归属。

自助申请的核心变化不是新建审批流程，而是：
1. 权限变更的**发起方**从管理员变为员工
2. 权限的**可申请范围**需要由管理员预先限定
3. 整个能力本身需要做成**可开关**

这意味着它应当在现有治理框架内运行，而不是作为独立的第五种权限来源或独立的治理模式。

### 是否改变治理模式
[CONFIRMED] 建议复用现有"权限变更审批模式"。若被确认为独立新模式，则会与子管理员模式、双管理员模式产生互斥约束，增加系统复杂度。

### 最大业务不确定性
[GAP] 可申请范围的定义方式（角色 vs 功能权限 vs 两者可切换）尚未确定。这个决策会影响员工侧信息架构、管理员配置复杂度、审批语义清晰度，以及后续是否需要在可申请范围中引入数据权限维度。

### 判断错误影响
如果"自助申请复用现有治理框架"的判断错误、实际上需要独立模式运行，那么后续的状态机设计、互斥规则、审批中台对接方式和权限来源解释模型都需要重新设计，影响所有角色的全部链路。

## §3 需求成立性判断

### 收益
- [CONFIRMED] 将权限申请从线下沟通转为系统闭环，减少员工与管理员之间的来回确认成本。
- [CONFIRMED] 管理员从逐人操作变为设定范围 + 审批确认，日常授权工作量可显著降低。
- [CONFIRMED] 申请记录可追踪、可审计，权限变更的来源解释更完整。

### 代价
- [CONFIRMED] 新增一个业务对象（申请单），需要在权限系统、审批中台、消息通知链路中增加对应的数据结构、状态流转和界面。
- [CONFIRMED] 管理员的配置责任从"直接给人授权"扩展到"设定可申请范围 + 指定审批流程"，初始配置和后续调整成本不容忽视。
- [CONFIRMED] 培训和支持成本可能上升，尤其对小企业和流动性大的企业。
- [CONFIRMED] 需要处理与现有治理模式的兼容和互斥逻辑。

### 替代路径
- 如果核心问题是"管理员授权太慢"，更轻的方案是优化现有的按角色批量授权能力 + 增加权限到期自动提醒，不引入员工侧发起链路。
- 如果核心问题是"员工不知道找谁要权限"，更轻的方案是在现有权限不足时给出明确的权限申请指引（告诉员工联系谁），不建设完整的申请审批系统。

### 成立性结论
[CONFIRMED] 需求成立。员工无法自助获取权限是中大型企业的真实痛点，竞品已有相近方向验证。建议进入正式体验设计，但必须在方案中优先确认 §9 层级一的问题，并在体验设计阶段控制审批中台对接和模式兼容的复杂度。

## §4 推荐业务边界

### 推荐能力形态
- [CONFIRMED] 自助申请作为"权限变更审批模式"的一种发起方式运行，由员工端发起，进入现有审批治理框架。
- [CONFIRMED] 管理员在权限管理模块中统一完成：开启/关闭能力、设定可申请范围、指定审批方式。三项操作为同一配置流程。
- [CONFIRMED] 员工在"我的权限"页面中查看已有权限，并从此页直接触达可申请权限的入口。
- [CONFIRMED] 审批人在审批中台的统一待办中处理申请，审批通过后系统自动完成授权。
- [CONFIRMED] 申请全生命周期可追踪：提交→审批中→已通过/已拒绝，员工可随时查看进度。

### 不推荐能力形态
- [CONFIRMED] 不推荐将自助申请做成独立的第五种治理模式。
- [CONFIRMED] 不推荐在审批中台直接建业务表单取代权限侧的申请入口（会丢失权限来源解释和范围校验）。
- [CONFIRMED] 不推荐首次版本支持数据权限申请（数据权限的条件组计算和范围解释对员工过于复杂，应先从功能权限/角色入手）。

### 与现有能力的边界
- 复用：审批中台的表单承载、审批流程引擎、待办列表；权限系统的角色/功能权限配置、治理状态模型。
- 不重复建设：不新建审批流程引擎、不新建消息通知体系、不改变现有四种权限来源的定义和优先级。
- 新增：申请单对象、可申请范围配置模型、自助申请开关、申请→授权的自动执行链路。

## §5 角色、功能、规则范围

### 角色清单

| 角色 | 职责 |
|------|------|
| 超级管理员 | 开启/关闭自助申请能力；设定可申请范围和审批方式；调整配置 |
| 权限管理员 | 同超管权限管理职责，受子管理员范围隔离约束时仅管辖范围内的员工和权限 |
| 员工（申请者） | 查看自己已有权限；发起权限申请；查看申请记录和审批进度 |
| 审批人 | 接收申请待办；查看申请内容；同意或拒绝申请 |

### 功能清单

| 功能 | 角色 | 输入 | 输出 | 结果 |
|------|------|------|------|------|
| 开启自助申请能力 | 超管/权限管理员 | 可申请范围（角色或功能权限）、审批方式设定 | 能力开启，员工端可见申请入口 | 员工可开始发起申请 |
| 调整可申请范围 | 超管/权限管理员 | 新增或移除的范围项 | 更新后的可申请范围 | 新申请按新范围校验；已提交申请不受影响 |
| 关闭自助申请能力 | 超管/权限管理员 | 关闭确认 | 能力关闭，员工端入口隐藏 | 新申请不可发起；存量审批中的申请继续走完或按策略处理 |
| 查看我的权限 | 员工 | — | 当前拥有的功能权限和角色列表 | 员工了解已有权限 |
| 发起权限申请 | 员工 | 选择目标权限、填写申请原因 | 生成申请单，进入审批 | 审批人收到待办 |
| 查看申请记录 | 员工 | — | 申请单列表（申请内容、提交时间、当前状态） | 员工了解申请进度 |
| 处理申请 | 审批人 | 申请单 ID、审批决策（同意/拒绝）、可选审批意见 | 审批结果，系统自动授权或通知拒绝 | 申请单状态更新，权限生效或终止 |

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时处理 |
|------|----------|----------|-------------|
| 仅超管/权限管理员可开启能力 | 非管理员尝试配置 | 入口不可见 | 不适用 |
| 可申请范围必须在开启前设置 | 管理员尝试开启但未设范围 | 提示先设置范围再开启 | 阻止开启，引导完成范围设置 |
| 员工仅能申请可申请范围内的权限 | 员工提交范围外的申请 | 前端不可选 | 不适用（前端过滤） |
| 已拥有权限不可重复申请 | 员工申请已有权限 | 申请列表中标记"已拥有"，不可选中 | 前端置灰并说明原因 |
| 审批通过后自动授权 | 审批人点击同意 | 系统自动授予对应权限，权限立即生效 | 若授权失败（如权限已被收回），记录异常并通知管理员 |
| 审批拒绝后申请终止 | 审批人点击拒绝 | 申请单状态为"已拒绝"，通知员工 | 员工可查看拒绝原因，可重新发起 |
| 能力关闭时存量申请处理 | 管理员关闭能力 | 存量审批中的申请继续走完；新申请不可发起 | 若需批量撤回，由管理员手动操作 |
| 已授权权限不因能力关闭而回收 | 能力关闭 | 已通过申请授予的权限保留 | 如需回收，通过现有权限管理链路单独操作 |
| 审批人不存在或不合适 | 申请路由到无效审批人 | 申请停留在待审批状态 | 系统提示管理员配置审批人；一定时长后自动提醒 |

## §6 状态、异常与边界

### 核心状态

| 状态 | 说明 |
|------|------|
| draft | 员工已创建但未提交的申请，可编辑 |
| pending | 已提交，等待审批人处理 |
| approved | 审批通过，但权限可能尚未完成系统授权 |
| rejected | 审批拒绝，申请终止 |
| effective | 审批通过且权限已成功授权，申请完成 |
| revoked | 申请被撤回或权限被回收 |

### 关键状态流转

| 从 | 到 | 触发条件 |
|----|-----|----------|
| — | draft | 员工进入申请页选择目标权限 |
| draft | pending | 员工点击提交 |
| pending | approved | 审批人点击同意 |
| pending | rejected | 审批人点击拒绝 |
| pending | revoked | 员工主动撤回 |
| approved | effective | 系统自动授权成功 |
| approved | revoked | 管理员回收权限或权限被其他流程覆盖 |
| effective | revoked | 管理员回收权限 |

### 异常清单

| 异常 | 触发条件 | 系统处理 | 用户下一步 |
|------|----------|----------|-----------|
| 申请范围内无可申请项 | 管理员配置范围为空，或员工已拥有全部可申请权限 | 员工申请入口显示空状态："当前暂无可申请的权限，如有需要请联系管理员" | 联系管理员确认或等待管理员调整范围 |
| 审批人不存在 | 管理员配置的审批人已被移除或离职 | 申请停留在 pending 状态，系统在管理端提示"审批人无效，请重新配置" | 管理员收到告警后重新指定审批人；员工等待或主动联系管理员 |
| 审批超时 | 申请提交后超过预设时长无审批结果 | 申请保持 pending，系统向审批人发送催办提醒；是否自动转交需根据审批中台能力确定 | 员工可选择催办或联系管理员 |
| 授权时权限已被修改 | 审批通过后系统授权时，目标权限的配置已被管理员变更 | 记录授权失败，通知管理员手动处理 | 管理员收到异常通知后手动授权或调整 |
| 能力关闭时有审批中的申请 | 管理员关闭能力 | 新申请入口关闭，存量 pending 申请继续走审批流程 | 管理员可查看存量申请列表，决定是等待走完还是批量撤回 |
| 员工在申请过程中被停用或离职 | 员工账号状态变更 | 该员工所有 pending 申请自动撤回，已生效权限按现有回收机制处理 | 不适用（员工已不可操作） |
| 与现有治理模式冲突 | 管理员尝试开启自助申请时，与已开启的子管理员模式或双管理员模式冲突 | 阻止开启，提示具体冲突原因和解决方式 | 管理员需先关闭冲突模式，或确认兼容规则 |

## §7 体验蓝图承接要求

| 业务判断 | 对体验设计的影响 | 必须承接的问题 | 禁止下游重判 |
|----------|-----------------|---------------|-------------|
| 自助申请是权限变更审批模式下的新发起方式，非独立模式 | 申请单的状态流转可复用现有治理状态模型，不需要设计全新状态机 | 审批中台待办中如何区分"管理员发起的权限变更"和"员工自助申请" | 不得将自助申请设计为独立治理模式 |
| 员工"查看已有权限"和"发起申请"必须形成连续体验 | 两个页面的信息架构需要能够自然衔接，而非独立入口 | 员工在"我的权限"中如何感知自己缺了什么、能申请什么 | 不得将这两个页面设计为无关联的独立入口 |
| 可申请范围优先按角色配置 | 员工侧展示的角色数量和选择方式需要控制认知负担 | 可申请角色较多时，如何帮助员工快速定位目标角色 | 不得将范围配置方式在体验方案中切换为功能权限而不说明理由 |
| 管理员配置必须在一个流程内完成 | 开启能力 + 设范围 + 指定审批是同一个任务，不应拆分到多个模块 | 配置完成后如何确认配置已生效，以及如何回看和调整 | 不得将配置拆分到审批中台和权限管理两个入口 |
| 能力关闭时存量申请的过渡策略 | 员工侧和管理员侧需要一致的状态反馈 | 关闭能力后，仍在审批中的员工如何知道申请还在进行 | 不得在关闭能力时静默取消所有存量申请 |
| 审批拒绝时员工需要知道原因和下一步 | 拒绝反馈不只是"已拒绝"三个字，需要说明原因和可选的后续动作 | 拒绝原因是否必填、员工是否可以在原申请上修改重提 | 不得将拒绝设计为无解释、无引导的终态 |
| 现有四种权限来源的解释模型不能破坏 | 在"我的权限"中新增"来源：自助申请"标识时，不能干扰现有来源解释 | 权限来源为"自助申请"的权限，在权限列表和排障查询中如何区别于直授和角色授予 | 不得改变现有来源的语义和优先级关系 |

## §8 约束与不做什么

### 硬约束
- [CONFIRMED] 不能破坏现有四种权限来源（个人直授、角色授予、应用可见性、协作可见性）的定义和优先级。
- [CONFIRMED] 审批流程必须对接审批中台，不得自建审批引擎。
- [CONFIRMED] 首次版本不做数据权限的自助申请。
- [CONFIRMED] 能力关闭时不得自动回收已通过申请授予的权限。
- [FACT] 配置、审批、校验环节必须设置安全保护。

### 依赖项
- [CONFIRMED] 审批中台需支持将自助申请作为一种审批表单类型接入，且支持管理员在权限管理侧完成审批人指定。
- [CONFIRMED] 权限系统需支持新的权限来源标识（自助申请），用于权限查询和排障时的来源解释。

### 不做什么
- [CONFIRMED] 不新建独立的权限治理模式。
- [CONFIRMED] 不在权限管理模块内自建审批流程引擎。

### A.3 AI 设计判断

| 判断 | 类型 | 依据 |
|------|------|------|
| 复杂度为"高" | 复杂度判断 | 改变权限来源模型、生效机制、状态机；涉及多角色、高异常分支、概念边界模糊 |
| 建议复用现有治理框架而非独立模式 | 设计判断 | 避免额外互斥约束；复用已有状态机和审批对接；降低系统复杂度 |
| 建议首次版本按角色配置可申请范围 | 设计判断 | 角色粒度清晰，员工理解成本低，审批语义明确；功能权限粒度可在后续扩展 |
| 建议统一配置入口 | 设计判断 | 管理员开启+设范围+指定审批为同一任务，拆分到多模块会增加配置失败风险 |
| 建议员工查看权限与发起申请形成连接页面 | 设计判断 | 基于认知原则 C-02（工作记忆有限），不应让员工在两个独立页面间记住权限信息 |
| 建议能力关闭时存量申请继续走完 | 设计判断 | 基于损失厌恶（C-06），突然撤回员工等待中的申请会造成负面体验 |
