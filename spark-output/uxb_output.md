# 需求定案：员工自助申请权限

## §0 本次关键判断

本次需求是将权限分配权从超管下沉到员工，通过"自助申请→审批→自动分配"链路降低超管瓶颈。方向成立，金蝶已有相似方案验证，但核心风险在于审批人仅凭申请原因判断是否批准，缺少申请人权限画像和岗位上下文，容易导致审批形式化或反复驳回。建议按中等复杂度进入体验设计，不改变底层权限模型，重点解决三个角色的任务衔接、概念引导和流程可见性。不建议方向：全员开放无限制申请、绕过审批直接生效。最高优先级待确认问题：审批人决策辅助信息的范围界定。

## §1 需求输入摘要

### 背景与现状

- 当前超管统一分配权限，中大型企业员工多、流动大，分配与核对工作量大
- 部分客户自行搭建了体外审批流程（员工上级审批→通知超管→超管授权），但未自动化

### 目标用户

| 角色 | 说明 |
|------|------|
| 超级管理员 | 配置自助申请模式、设置范围与审批流程 |
| 员工 | 查看已有权限、发起权限申请 |
| 审批人 | 审批权限申请（预设为组织负责人） |

### 业务目标

新增 3 家客户使用率，种子客户已明确（诺思格）。

### 功能范围

- 超级管理员：自助申请权限模式配置（开启/关闭/编辑），含申请方式选择、范围设置、审批流程配置
- 员工：我的权限查看（功能权限/数据权限/角色）、申请权限（角色/功能权限）、申请记录查询与撤销
- 审批人：审批权限申请（同意/否决），默认仅看到申请内容与申请原因

### 明确约束

- 与"双管理员互审模式""权限变更审批模式"互斥，不能同时开启
- 服务人员不展示"我的权限"入口
- 员工只能申请管理员设定的角色范围或应用范围内的权限
- 后端校验规则沿用：资金用户校验、子管理员模式权限校验、实名要求、特殊身份默认权限

### 输入缺口

- 审批人离职或不可达时的处理方式未说明
- 自动分配权限失败的处理方式未说明
- 申请撤销的时间限制未说明
- OA 审批流程的对接细节未展开

## §2 业务场景判断

### 在现有体系中的位置

本次属于**既有能力扩展**，而非新增业务域。底层权限模型（角色、功能权限、数据权限、治理状态）不变，新增的是"自助申请"这个权限获取入口路径。

### 与现有能力的关系

- 复用已有角色、功能权限、数据权限模型
- 复用已有审批流程引擎（对接 OA 审批）
- 与双管理员互审模式、权限变更审批模式互斥——开启了这些治理模式的企业不能启用自助申请，意味着自助申请的目标客群与高治理需求客群不重叠
- 不改变治理状态模型（仍为 draft→pending→approved→rejected→effective→revoked），但新增了"已撤销"作为申请人侧主动终止的状态

### 最大业务不确定性

审批人的决策质量。审批人仅看到申请内容和申请原因，缺少申请人当前权限画像、岗位职责匹配等判断上下文。如果审批人频繁驳回或随意批准，自助申请反而会降低效率而非提效。

### 如果这个判断错了

如果审批链路在实际运营中不可靠（审批人随意批准导致权限滥用，或反复驳回导致员工放弃），那么自助申请的核心价值（提效）不成立，需要回到"超管统一分配"或"角色预设+自动关联"等替代路径。

## §3 需求成立性判断

### 收益

- 减少超管瓶颈：分配权限的工作从超管分散到审批链和系统自动处理
- 降低沟通成本：员工不需要"找老板教老板授权"，社恐场景被覆盖
- 竞品验证：金蝶已有"权限申请单→工作流审批→自动分配"方案，方向经市场验证
- 调研支持：10 名实施同事中 6 名认为有价值，有真实客户场景

### 代价

- 培训成本：员工需要学习自助申请流程（1 名实施同事认为会带来高培训成本）
- 审批人负担：组织负责人需要承担审批判断责任，可能增加其工作负担
- 治理冲突：开启自助申请后不能同时使用双管理员互审等治理模式

### 更低成本替代路径

角色预设方案（管理员维护好角色模板，加人时直接关联角色）与自助申请不冲突，可以并存。角色预设解决的是"批量分发"场景，自助申请解决的是"员工按需申请"场景。但角色预设无法覆盖员工临时需要某个权限的灵活场景，两者应互为补充而非替代。

### 结论

**建议进入正式体验设计。** 需求方向成立，业务价值清晰，但需要重点关注审批决策支持的体验设计。

## §4 推荐业务边界

### 推荐能力形态

- 管理员可控范围的员工自助申请：包括可申请的内容范围（角色/应用）和可申请的额度/权限级别
- 审批驱动的自动分配：审批通过后系统自动分配权限，审批拒绝则流程终止
- 管理员的持续管控能力：开启后可编辑、可关闭，关闭时保护在途流程

### 不推荐能力形态

- 全员开放无限制申请：必须保留管理员的控制边界
- 绕过审批直接生效：审批是风险控制的核心环节，不应跳过
- 改变底层权限模型：不应为自助申请引入新的权限类型或状态模型

### 与现有能力的边界

- 复用：角色定义、功能权限、数据权限的基础模型；审批流程引擎；治理状态模型
- 不新增：不做新的权限对象类型、不做新的状态模型、不改变生效机制
- 新增：自助申请权限模式的配置面、员工端权限查看与申请的入口、权限申请单的管理

### 要复用、不该新增什么

- 复用权限域已有的后端子校验规则（资金用户校验、子管理员模式校验、实名要求等），不再重新实现
- 复用审批管理已有的审批流程引擎和表单模板，不再重复造审批流
- 不复用的：不可复用双管理员互审和权限变更审批的治理逻辑（互斥关系）

## §5 角色、功能、规则范围

### 角色职责

| 角色 | 职责 | 边界 |
|------|------|------|
| 超级管理员 | 开启/关闭自助申请模式；配置申请方式、范围、审批流程；编辑已启用配置 | 专属功能，不可授予其他角色 |
| 员工（申请人） | 查看我的权限；发起权限申请；查看申请记录；撤销审批中的申请 | 仅能申请管理员设定的范围内的权限 |
| 审批人（组织负责人/可配置） | 查看申请详情；同意或否决申请 | 默认按预设审批流程确定 |

### 功能单元

**F-1 自助申请权限模式配置**

| 项目 | 内容 |
|------|------|
| 输入 | 选择申请方式（角色/功能权限）、设置范围（全部/部分）、配置审批流程 |
| 处理 | 校验互斥模式（双管理员互审、权限变更审批）、保存配置、启用/关闭模式 |
| 输出 | 模式已启用/已关闭状态；模式启用后员工端出现"我的权限"入口 |

**F-2 我的权限**

| 项目 | 内容 |
|------|------|
| 输入 | 用户进入"我的权限"页面 |
| 处理 | 查询用户的功能权限、数据权限、角色三种维度的权限数据 |
| 输出 | 按 tab 展示权限清单（功能权限/数据权限/角色）；无数据时显示空状态提示 |

**F-3 申请权限**

| 项目 | 内容 |
|------|------|
| 输入 | 选择申请内容（角色或功能权限）、填写申请原因、提交 |
| 处理 | 校验申请内容是否在管理员设定范围内、执行后端校验（资金用户、子管理员模式、实名等）、提交审批 |
| 输出 | 创建权限申请单、进入审批流程、记录到申请记录列表 |

**F-4 审批权限申请**

| 项目 | 内容 |
|------|------|
| 输入 | 审批人查看申请详情（申请内容、申请原因） |
| 处理 | 同意或否决申请 |
| 输出 | 同意→系统自动分配权限；否决→流程终止，通知申请人 |

**F-5 申请记录管理**

| 项目 | 内容 |
|------|------|
| 输入 | 申请人查看自己的申请记录列表 |
| 处理 | 按申请日期、审批状态筛选；审批中的申请可撤销 |
| 输出 | 带状态标识的申请记录列表 |

### 关键业务规则

| 规则 | 触发条件 | 处理结果 | 不满足时的处理 |
|------|---------|---------|--------------|
| 互斥模式校验 | 启用自助申请模式时 | 检测双管理员互审或权限变更审批是否已开启 | 已开启则不能启用，提示具体原因 |
| 范围限制 | 员工提交申请时 | 仅允许申请管理员设定的角色/应用范围内的内容 | 不在范围内的内容不可选或提交失败 |
| 后端安全校验 | 员工提交权限申请时 | 执行资金用户校验、子管理员模式校验、实名要求校验 | 校验不通过则阻止提交并提示原因 |
| 审批通过自动分配 | 审批人同意后 | 系统自动将所申请的角色或功能权限授予申请人 | 分配失败需通知相关人员（[GAP] 具体处理方式未明确） |
| 申请撤销限制 | 申请人点击撤销时 | 仅审批中的申请可撤销 | 已通过/已拒绝/已撤销的申请不可操作 |

## §6 状态、异常与边界

### 核心状态

权限申请单状态流转：

```
审批中 → 已通过 → 已生效
审批中 → 已拒绝（流程终止）
审批中 → 已撤销（申请人主动终止）
```

| 状态 | 说明 | 用户下一步 |
|------|------|-----------|
| 审批中 | 申请已提交，等待审批人处理 | 等待审批结果；可撤销 |
| 已通过 | 审批人同意，等待系统分配权限 | 等待权限生效通知 |
| 已生效 | 系统已完成权限自动分配 | 可使用已获得的权限 |
| 已拒绝 | 审批人否决 | 查看拒绝原因，可重新申请 |
| 已撤销 | 申请人主动取消申请 | 可重新发起申请 |

### 关键异常

| 异常 | 触发条件 | 系统处理结果 | 用户下一步 |
|------|---------|-------------|-----------|
| 模式互斥 | 启用时检测到互斥模式已开启 | 阻止启用，提示具体冲突模式 | 关闭冲突模式后再尝试启用 |
| 申请超范围 | 员工申请不在设定范围内的权限 | 阻止提交或在选择时即限制 | 仅在范围内选择 |
| 后端校验不通过 | 提交时触发安全校验失败 | 阻止提交，提示具体校验失败原因 | 根据提示调整或联系管理员 |
| 关闭模式时存在在途流程 | 管理员关闭模式 | 关闭失败，提示需完成在途审批 | 联系审批人尽快处理或等待审批完成 |
| 审批人长时间未处理 | 申请单超过一定时间未审批 | [GAP] 文档未覆盖 | [GAP] 文档未覆盖 |
| 审批人离职或不可达 | 审批人账户异常 | [GAP] 文档未覆盖 | [GAP] 文档未覆盖 |
| 自动分配权限失败 | 审批通过后系统分配异常 | [GAP] 文档未覆盖 | [GAP] 文档未覆盖 |
| 申请撤销后重新申请相同内容 | 撤销后再提交相同申请 | [GAP] 文档未覆盖，系统行为未定义 | [GAP] 文档未覆盖 |

## §7 体验蓝图承接要求

### 1. 角色概念引导

| 项目 | 内容 |
|------|------|
| 业务判断 | 管理员需要在"申请角色"和"申请功能权限"两种方式中选择，员工在申请时也面对同样的概念区分 |
| 对体验设计的影响 | 概念理解成本可能成为使用门槛——两端角色都需要理解差异才能正确操作 |
| 下游必须承接的问题 | 设计申请入口和申请表单时，需要引导员工理解当前企业采用的是哪种申请方式，以及"我应该怎么选" |
| 禁止下游重判 | 不改变"两种申请方式二选一"的业务决策；不把概念引导变成推翻模式的入口 |

### 2. 审批决策辅助

| 项目 | 内容 |
|------|------|
| 业务判断 | 审批人仅看到申请内容（角色名/功能权限名）和申请原因，缺少判断依据 |
| 对体验设计的影响 | 审批页面的信息密度和交互方式取决于审批人能看到什么上下文 |
| 下游必须承接的问题 | 在有限的输入信息下，设计审批页面的信息展示方式，帮助审批人做出有依据的决策；具体需要展示哪些信息见 §9.1 |
| 禁止下游重判 | 不改变"审批人判断是否批准"的业务机制；不跳过审批环节直接分配 |

### 3. 申请流程透明度

| 项目 | 内容 |
|------|------|
| 业务判断 | 员工提交申请后进入等待状态，不可见审批人、审批进度 |
| 对体验设计的影响 | 员工在等待期间的焦虑感和不确定性会影响体验满意度 |
| 下游必须承接的问题 | 设计申请全生命周期的状态可见性，包括当前环节、审批人信息、通知触达 |
| 禁止下游重判 | 不改变"需审批后生效"的业务机制；不绕过审批直接告知结果 |

### 4. 管理员持续管控

| 项目 | 内容 |
|------|------|
| 业务判断 | 管理员开启自助申请模式后仍然需要编辑和关闭的能力，关闭时存在在途流程保护 |
| 对体验设计的影响 | 配置态和已启用态的页面状态切换较多，需要清晰的模式反馈 |
| 下游必须承接的问题 | 设计模式开启后的编辑态/查看态切换、关闭时的二次确认与在途流程拦截 |
| 禁止下游重判 | 不改变"管理员可随时关闭"的控制权归属；不绕过在途流程保护 |

### 5. 后端校验反馈

| 项目 | 内容 |
|------|------|
| 业务判断 | 提交权限申请时需执行资金用户、子管理员模式、实名要求等多道后端校验 |
| 对体验设计的影响 | 校验失败原因多样，反馈需要具体、可理解，否则员工不知如何调整 |
| 下游必须承接的问题 | 设计提交时刻的校验结果展示方式，让员工清楚知道"哪里不通过"以及"该怎么解决" |
| 禁止下游重判 | 不改变校验逻辑的触发条件；不把校验失败反馈简化为"提交失败" |

## §8 约束与不做什么

### 硬约束

- 自助申请模式不能与双管理员互审模式、权限变更审批模式同时开启
- 服务人员不展示"我的权限"入口
- 员工可申请的范围不能超出管理员设定的角色范围或应用范围
- 后端安全校验不可跳过

### 依赖项

- 依赖 OA/审批流程引擎的正常运行
- 依赖权限域已有的后端子校验逻辑
- 依赖审批流程已配置完成（预设审批人为组织负责人或可配置）

### 不做什么

- 不改变底层权限模型（角色、功能权限、数据权限、治理状态）
- 不新增权限类型或状态模型
- 不支持无审批的直接生效
- 不支持全员无限制申请
- 不提供员工自行设置数据权限范围的能力（申请功能权限时默认授予全部数据权限）

## §9 待确认问题

### 层级一：影响主策略的问题

| 问题 | 影响 | 建议确认方 |
|------|------|-----------|
| 审批人是否需要看到申请人当前已有权限作为判断参考？还是仅凭申请内容即可决策？ | 决定了审批页面的信息密度和权限查询的交互范围，直接影响审批体验的核心方案 | 产品/业务方 |

### 层级二：影响局部体验设计的问题

| 问题 | 影响 | 建议确认方 |
|------|------|-----------|
| 员工端如何区分"申请角色"和"申请功能权限"两种模式？是否需要统一入口还是分开展示？ | 影响申请页面的入口设计和表单结构 | 体验设计/产品 |
| 关闭模式时存在在途流程，管理员除了等待还有无替代处理方式（如强制转派、超时关闭）？ | 影响管理模式关闭流程的异常处理设计 | 产品/业务方 |
| 自动分配权限失败时的处理机制是什么（重试/人工介入/通知谁）？ | 影响异常场景的系统行为和用户通知设计 | 后端/产品 |
| 申请撤销是否有时间限制（审批人已处理时是否可撤销）？ | 影响撤销按钮的可用性逻辑 | 产品/后端 |
| 审批人离职或不可达时，在途申请如何处理？ | 影响审批流程的稳定性和在途申请的安全性 | 业务方/审批管理 |

### 设计判断

| 判断 | 说明 |
|------|------|
| 复杂度为中等 | 不改底层业务骨架，新增入口路径和角色任务流 |
| 核心风险在审批决策支持 | 审批人缺少判断上下文可能导致形式化审批 |
| 角色预设与自助申请应并存 | 两者解决不同场景，非替代关系 |
| 关闭模式的在途流程保护是合理机制 | 但缺少兜底路径是缺口 |
