## §0 关键设计判断

员工自助申请权限的本质是在现有权限供给体系中新增一种来源类型——从"只有管理员发起"变为"员工发起、审批后生效"。这不只是加一个申请表单。

**主要影响：** 权限来源模型需扩展、员工端需权限查看能力、与现有治理模式需定义共存关系。

**建议方案：** 先扩展来源模型（新增"审批授予"来源类型），再设计员工端权限查看与申请流程，最后定义与双管理员/子管理员/审批治理模式的兼容策略。

**不建议方案：** 仅前端加申请页面，不处理来源追溯、冲突解释和治理共存——这将导致权限结果不可解释、审计断裂。

**关键待确认：** 自助申请权限在来源模型中的归属策略（新增来源类型 vs 归入现有来源附加审批追踪字段）。

## §1 需求输入摘要

### 背景

目前企业员工权限分配由权限管理员或超级管理员集中处理。中大型企业员工多、流动频繁，权限变更工作量大。部分企业的超管是老板本人，业务人员需要权限时通过非正式渠道找管理员，沟通成本高、授权时效不稳定。

### 业务目标

将部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对申请范围和审批流程的控制。

### 功能范围（按需求文档）

员工侧：
- 查看自己当前拥有的权限 [FACT]
- 主动申请所需权限 [FACT]
- 通过审批后自动获得权限 [FACT]
- 查看申请记录和审批状态 [FACT]

管理员侧：
- 控制是否允许员工自助申请权限 [FACT]
- 控制员工可申请的权限范围 [FACT]
- 控制申请提交后的审批流程 [FACT]
- 控制是否关闭该能力 [FACT]

### 缺口

- 员工端如何查看权限、查看什么粒度的权限，未明确 [GAP]
- 可申请范围按什么粒度配置（角色/功能权限/应用），未明确 [GAP]
- 管理员关闭能力时对进行中申请的处理方式，未明确 [GAP]
- 审批流程是复用现有审批中台还是独立新增，未明确 [GAP]

### 已知风险（需求文档原文）

- 培训成本：需要教会更多人使用，小企业或人员流动性大的企业支持成本可能上升 [FACT]
- 权限安全风险：可申请范围设置过宽可能导致员工申请到不合适的权限 [FACT]
- 审批流程风险：默认审批人不存在或不合适导致申请无法流转 [FACT]
- 模式互斥风险：与已有权限治理模式可能产生冲突 [FACT]

## §2 业务场景判断

### 业务定位

这是一项**新增能力**，不是对现有功能的扩展或替代。当前权限体系支持管理员按人直授、按角色授权、子管理员分权、双管理员互审、审批治理五种供给模式——但所有模式的发起方都是管理员，员工侧没有任何主动发起权限变更的入口。

### 与现有能力的关系

- **权限变更审批模式**：这是最接近的现有模式，但它面向的是管理员发起的变更需要审批，而非员工主动申请。自助申请开启后，如果企业同时启用了权限变更审批模式，两者的审批链路需要明确是叠加还是二选一。
- **子管理员模式**：子管理员已有部分授权能力。自助申请开启后，子管理员管辖范围内的员工申请是否由子管理员审批，还是由超管统一配置审批人，需要定义。
- **角色授权**：员工通过角色获得的权限，与通过自助申请获得的权限之间如何叠加/互斥，目前未定义。

### 最大业务不确定性

自助申请权限在现有来源模型（ACL_DIRECT、RBAC_ROLE、APP_VISIBILITY、COLLAB_VISIBILITY）中没有自洽的位置。这是整个方案最大的不确定性——如果来源归属不解决，权限查询、冲突解释、审计追溯全链路都会受影响。

### 判断错误的影响

如果这项需求的业务定位判断错误（实际更适合的路径不是扩展来源模型，而是仅作为工单流程不进入权限来源体系），那么后续的体验设计需要全部回退重做——因为所有状态设计、来源解释、治理共存的前提都不成立。

## §3 需求成立性判断

### 收益

- 减少管理员侧零散授权请求的处理压力 [CONFIRMED]
- 建立标准化的权限申请通道，减少非正式沟通 [CONFIRMED]
- 审批留痕，权限变更可追溯 [CONFIRMED]
- 员工端权限自助查看可以减少向管理员反复确认"我有什么权限"的成本 [CONFIRMED]

### 系统代价

- 权限来源模型需要扩展——当前四种来源类型不够，需要新增至少一种来源类型（或等同的处理机制）[CONFIRMED]
- 员工端需要建设权限查看能力——权限查询入口原先只在管理后台，员工端需要独立建设 [CONFIRMED]
- 审批流程与权限体系的集成需要打通——审批通过后自动授权涉及审批中台与权限系统的回写 [CONFIRMED]
- 治理模式共存逻辑需要全量定义——自助申请与现有子管理员、双管理员、审批治理模式的关系不能留到开发阶段临时判断 [CONFIRMED]

### 更低成本的替代路径

**方案A——由子管理员承接授权请求而非开放员工自助申请：**
如果企业的核心痛点是"超管处理不过来"，而不是"员工想自助"，那么多设子管理员、下放授权权限可能是更轻的方案。它在不改变权限来源模型的前提下缓解了管理员压力。

**方案B——员工提工单、管理员手动处理：**
如果只是想让员工有一个标准化提交入口，不走审批后自动授权，那可以简化为"工单→通知管理员→管理员手动配置"。代价是授权时效仍然取决于管理员响应速度，而且权限来源仍然无法自动追踪。

**方案C——仅开放角色申请：**
如果员工申请的权限可以收敛到角色层面（"申请加入某个角色"），而不是直接申请功能权限点，那么复杂度会显著降低——角色已经是现有权限来源的一部分，不需要新增来源类型。

### 建议

**建议进入正式体验设计，但前提是必须先确认来源归属策略（§9 层级一）。** 如果来源归属问题无法在本次范围确认，建议退回方案C（仅角色申请）作为保底路径。

## §4 推荐业务边界

### 推荐的能力形态

- 员工端具备查看"我已有的权限"的能力，至少到应用级可见，推荐到功能权限点级
- 员工端可发起权限申请，选择可申请范围内的权限项并填写申请原因
- 申请提交后进入审批流程，审批通过后系统自动完成授权
- 审批拒绝时告知员工拒绝原因
- 管理员端配置：开启/关闭该能力、配置可申请范围、配置审批人/审批流程
- 授权记录中可追溯"本权限通过自助申请获得"的来源信息

### 不推荐的能力形态

- 不推荐将自助申请直接归入管理员直授（ACL_DIRECT）来源而不加区分——这会破坏来源解释能力
- 不推荐在来源模型未定案的情况下先开发申请页面——后续改造成本高
- 不推荐默认所有权限都可申请——管理员必须有控制可申请范围的配置能力

### 与现有能力的边界

- **复用**：审批流程建议复用现有审批中台，不另建审批引擎
- **复用**：权限解释和冲突定位复用现有来源优先级规则，仅在来源枚举中扩展
- **新增**：员工端"我的权限"查看页面（如果当前不存在）
- **新增**：管理员端"自助申请配置"能力单元
- **不新增**：不新增独立的审批流程引擎

### 需复用的现有组件/能力

- 审批中台或通用审批流程 [FACT]
- 现有功能权限/数据权限的选择控件
- 现有权限查询的解释模型（扩展来源后复用）
- 现有冲突原因码体系（扩展来源后复用）

## §5 角色、功能、规则范围

### 角色清单

| 角色 | 职责 |
|------|------|
| 员工（权限申请人） | 查看自有权限、发起权限申请、查看申请状态与结果 |
| 审批人 | 查看待审批申请、同意/拒绝申请、查看审批记录 |
| 系统管理员/超管 | 开启/关闭自助申请能力、配置可申请范围、配置审批流程、查看全量申请记录 |

### 功能单元

**F1：管理员开启/配置自助申请权限**

- 输入：系统管理员进入配置入口
- 处理：开启能力 → 设置可申请范围 → 设置审批流程 → 确认生效
- 输出：自助申请能力开启，配置生效
- 关联规则：R1、R3、R5

**F2：员工查看自有权限**

- 输入：员工进入权限查看入口
- 处理：按应用聚合展示当前生效的权限列表（含功能权限和数据范围）
- 输出：权限查看结果展示
- 关联规则：R2
- [GAP] 查看粒度未明确——应用级 vs 功能权限点级

**F3：员工提交权限申请**

- 输入：员工选择所需权限项、填写申请原因
- 处理：校验申请权限是否在可申请范围内 → 生成申请记录 → 推送给审批人
- 输出：申请成功提交，等待审批
- 关联规则：R2、R3、R4

**F4：审批人处理申请**

- 输入：审批人查看待审批申请及申请原因
- 处理：同意 → 系统自动完成授权；拒绝 → 申请结束并告知申请人原因
- 输出：审批结果通知申请人和系统
- 关联规则：R4、R5、R6

**F5：员工查看申请记录**

- 输入：员工进入申请记录列表
- 处理：按时间倒序展示历史申请及当前状态
- 输出：申请记录列表及详情
- 关联规则：无

**F6：管理员关闭自助申请能力**

- 输入：管理员进入配置入口选择关闭
- 处理：处理进行中申请（策略待定）→ 禁用申请入口 → 配置保留
- 输出：能力关闭，员工端不再可见申请入口
- 关联规则：R5
- [GAP] 进行中申请的处理方式未明确

### 关键业务规则

| 编号 | 规则 | 触发条件 | 处理结果 | 不满足时处理 |
|------|------|---------|---------|-------------|
| R1 | 自助申请能力开关 | 管理员开启/关闭配置 | 开启则员工端可见申请入口；关闭则隐藏入口 | — |
| R2 | 可申请范围校验 | 员工提交申请 | 系统校验申请权限是否在管理员配置的可申请范围内 | 超出范围则阻止提交并提示 |
| R3 | 审批流程指派 | 申请提交时 | 按管理员配置的审批流程生成审批任务 | 审批人不存在或无效时，申请无法提交，提示管理员配置不完整 |
| R4 | 自动授权 | 审批人同意申请 | 系统按申请内容为员工添加权限记录，来源标记为"审批授予" | 授权失败时通知审批人和申请人，标记为"授权异常"待人工处理 |
| R5 | 关闭能力时处理 | 管理员关闭自助申请 | 进行中申请的处理方式取决于策略选择（方案待定） | — |
| R6 | 来源叠加 | 员工已通过其他来源拥有同权限 | 按来源优先级规则判断最终生效结果 | — |

[GAP] R6 的叠加/互斥规则在来源归属策略确认后才能完整定义。

## §6 状态、异常与边界

### 核心状态：权限申请

| 状态 | 含义 | 操作方 | 可操作动作 | 下一状态 |
|------|------|--------|-----------|---------|
| 草稿 | 填写中，未提交 | 员工 | 编辑、提交、放弃 | 审批中 |
| 审批中 | 已提交，等待审批 | 审批人 | 通过、拒绝 | 已通过 / 已拒绝 |
| 已通过 | 审批通过，等待授权 | 系统 | 执行授权 | 已生效 |
| 已拒绝 | 审批拒绝 | 员工 | 查看拒绝原因 | —（终态） |
| 已生效 | 授权已完成 | 员工、管理员 | 查看、追溯 | —（终态） |
| 已撤销 | 员工自行撤销 | 员工 | — | —（终态） |
| 已作废 | 管理员关闭能力时处理 | 系统 | — | —（终态） |

[GAP] "已通过"到"已生效"之间的授权处理如果有延迟或失败，中间态如何反馈未明确。

### 关键状态流转

```
草稿 → 审批中 → 已通过 → 已生效
                → 已拒绝（终态）
      → 已撤销（终态）
已通过 → 已生效 / 授权异常（GAP）
审批中 → 已作废（管理员关闭能力时）
草稿 → 已作废（管理员关闭能力时）
```

### 异常清单

| 异常 | 触发条件 | 系统处理结果 | 用户下一步 |
|------|---------|-------------|-----------|
| 审批人不存在 | 申请提交时，配置的审批人已离职/无审批权限 | 阻止提交，提示管理员 | 管理员重新配置审批人 |
| 审批超时 | 审批人在规定时间内未处理 | 可配置自动提醒或自动升级 | 员工可催办；管理员可重新指派 |
| 自动授权失败 | 审批通过后系统写权限记录失败 | 标记"授权异常"，通知审批人和员工 | 管理员人工处理 |
| 授权部分成功 | 多权限项申请，部分授权失败 | 成功部分标记为已生效，失败部分标记为授权异常 | 管理员处理失败项 |
| 关闭能力时进行中 | 管理员关闭能力，存在审批中的申请 | 依策略而定（§9 未定项） | 视策略而定 |
| 重复申请 | 员工申请已拥有的权限 | 提示员工已拥有该权限，可选择取消申请 | 员工确认后放弃提交 |

## §8 约束与不做什么

### 硬约束

- 员工自助申请不能绕过管理员对可申请范围的控制 [FACT]
- 权限变更必须有审批记录和审计追踪 [FACT]
- 关闭自助申请能力时不能忽略进行中申请的处理 [FACT]
- 自助申请权限必须能在来源解释体系中自洽定位（是新增来源还是归入现有来源+追踪，二选一）

### 依赖项

- 审批中台或通用审批流程的存在（如尚未建设则不在本次范围内解决）
- 权限来源追踪能力的现有实现程度（是已有容器只差枚举值，还是需要从零建设）

### 不做什么

- 不设计审批流程引擎（复用现有审批中台）
- 不改变现有权限来源优先级规则（仅扩展来源枚举）
- 不涉及组织架构或成员管理的变更
- 不涉及应用入口可见性治理的变更

### 不可突破的安全或业务边界

- 可申请范围不能自动扩大到管理员配置之外 [CONFIRMED]
- 审批通过后的自动授权不能跳过审计记录 [CONFIRMED]
- 关闭能力不应对已经生效的权限造成自动回收（除非另有治理规则） [CONFIRMED]
