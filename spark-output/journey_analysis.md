# 旅程分析：员工自助申请权限

- **运行模式**：`stories-chain`
- **是否使用补问**：否
- **数据来源**：`spark-output/context/stories.json`（3.0）、`spark-output/stories.md`、`spark-output/context/uxb.json`（5.0）
- **结果等级**：完整旅程

---

## 主线角色旅程：员工（申请人）

### 角色摘要

员工在日常工作中发现缺少某项功能或数据权限，通过企业已开启的自助申请模式，查看自己的权限全景，选择需要申请的角色或功能权限并提交申请，等待审批人审批后获得或被拒绝权限。根据企业配置的申请方式不同，员工看到的是角色列表或功能权限列表。

---

### 阶段一：感知权限缺失

| 字段 | 内容 |
|------|------|
| **目标** | 意识到自己缺少某个工作所需的权限 |
| **行动** | ① 尝试访问应用或功能时发现无权限 ② 向同事或上级确认该权限是否必要 ③ 了解到企业已开通自助申请权限模式，可以去申请 |
| **触点** | 应用/功能访问入口、团队成员或上级的口头告知、个人中心入口提示 |
| **用户心声** | "这个功能我进不去，是不是没开权限？" |
| **信心度** | 高 |
| **信心依据** | 故事 ST-03 场景明确说明"员工发现缺少某项工作所需的权限，通过自助申请途径发起申请" |
| **痛点** | ① 员工可能不知道权限不足时应该去申请还是找超管 ② 如果企业未开启自助申请模式，员工绕了一圈还是回到找超管的老路 |
| **流失风险** | 低——有实际工作需求驱动，但可能走错路径直接找超管 |
| **机会** | 在权限被拦截的页面提供"申请权限"的直接入口，减少员工摸索成本 |

### 阶段二：了解自己的权限全景

| 字段 | 内容 |
|------|------|
| **目标** | 查看自己当前已有什么权限，判断需要申请什么 |
| **行动** | ① 进入个人中心，找到"我的权限"入口（位于"我的企业"下方） ② 浏览功能权限 tab，看自己已有的应用和功能权限 ③ 切换到数据权限和角色 tab 了解全貌 ④ 确定需要申请的内容 |
| **触点** | 个人中心、"我的权限"页面（功能权限/数据权限/角色三个 tab）、空状态占位图 |
| **用户心声** | "我到底有哪些权限？缺的那个能不能自己申请？" |
| **信心度** | 高 |
| **信心依据** | 故事 ST-02 明确了查看权限的完整场景和三个 tab 结构 |
| **痛点** | ① 功能权限列表同时包含全员应用和管理类应用，信息密度高，员工难以快速找到关心的条目 ② 空状态只提示"您没有功能权限"，没有引导去申请 ③ 员工可能不清楚"申请角色"和"申请功能权限"的区别 |
| **流失风险** | 中——看不懂或找不到入口时可能转向找超管 |
| **机会** | 空状态和权限列表底部提供"申请权限"入口；区分"我已拥有的"和"我可以申请的"两种视图 |

### 阶段三：发起权限申请

| 字段 | 内容 |
|------|------|
| **目标** | 正确选择申请内容，填写申请原因并成功提交 |
| **行动** | ① 点击"申请权限"打开申请抽屉 ② 根据企业配置的模式，从可选角色列表或功能权限列表中勾选目标项 ③ 填写申请原因（必填，最多500字） ④ 提交申请，通过后端校验 |
| **触点** | "申请权限"按钮、申请抽屉、角色/权限选择列表、申请原因输入框、提交按钮 |
| **用户心声** | "我要这个权限，希望能批下来。" |
| **信心度** | 高 |
| **信心依据** | 故事 ST-03 详细描述了申请流程的字段、校验和提交逻辑 |
| **痛点** | ① 员工看到的申请内容取决于管理员配置的模式，如果与预期不符（想申请角色但只能申请功能权限）会增加困惑 ② 申请原因自由文本无填写指引，员工可能写不到点子上 ③ 后端校验（资金用户、子管理员模式、实名要求）失败后提示是否足够清晰，员工能否自行解决不确定 |
| **流失风险** | 中——反复校验失败或看不懂错误提示时可能放弃 |
| **机会** | 申请原因提供结构化填写引导（如"请说明你需要该权限处理什么工作"）；校验失败时给出可操作的解决方案而非错误码 |

### 阶段四：等待审批结果

| 字段 | 内容 |
|------|------|
| **目标** | 了解申请进展，等待审批人做出决定 |
| **行动** | ① 提交后查看申请记录，确认已进入"审批中"状态 ② 等待审批结果通知 ③ 如果等待时间过长，进入申请记录列表查看状态 ④ 如改变主意，可撤销审批中的申请 |
| **触点** | 申请记录列表（筛选条件、状态标签、撤销按钮）、分页组件、消息/通知 |
| **用户心声** | "批了没有？卡在谁那里了？还要等多久？" |
| **信心度** | 中 |
| **信心依据** | 故事 ST-05 明确了申请记录查看和撤销的场景，但没有催办机制 |
| **痛点** | ① 员工不知道审批人是谁，无法预估等待时间 ② 没有催办机制，只能被动等待 ③ "已通过"和"已生效"前后分离，员工以为"已通过"就能用，实际上权限还未生效 ④ 撤销的时间限制不明确 |
| **流失风险** | 高——长时间无响应时员工可能转向找超管走线下途径，自助流程被架空 |
| **机会** | 展示审批人信息和当前审批环节进度；对长时间未审批的申请提供提醒或升级机制；通过状态说明清晰区分"已通过"和"已生效" |

### 阶段五：处理审批结果

| 字段 | 内容 |
|------|------|
| **目标** | 审批通过后正常使用新权限，或被拒绝后了解原因并决定下一步 |
| **行动** | ① 审批通过：收到通知 → 等待权限生效 → 尝试使用新权限 ② 审批拒绝：收到通知 → 查看原因 → 决定是否重新申请或联系管理员 ③ 进入"我的权限"确认权限已生效 |
| **触点** | 消息/通知、申请记录列表、我的权限页面、应用/功能入口 |
| **用户心声** |（通过）"终于可以用了。"（拒绝）"为什么没批？接下来怎么办？" |
| **信心度** | 中 |
| **信心依据** | 故事 ST-04 明确了审批通过/拒绝后的通知和系统行为；自动分配失败的处理未定义 |
| **痛点** | ① 拒绝原因不明确时，员工不知道"哪里不符合条件"或"怎么调整" ② 自动分配权限失败时，员工以为审批通过就完事了但实际还没权限 ③ 被拒绝后重新申请需重复填写全部内容，不能复用历史信息 |
| **流失风险** | 中——被拒绝后原因不清晰时可能放弃自助转向找超管 |
| **机会** | 拒绝原因结构化展示（具体哪个条件不满足）；自动分配失败时主动通知并告知处理进展；被拒后提供"修改后重新申请"的一键复用能力 |

## 支持角色旅程一：超级管理员

### 角色摘要

超级管理员负责决定是否启用自助申请模式，在管理后台完成申请方式、范围和审批流程的三步配置，并在启用后进行持续的编辑和关闭等运维操作。他是权限下沉的控制者。

---

### 阶段一：评估与决策

| 字段 | 内容 |
|------|------|
| **目标** | 了解自助申请模式的价值和互斥条件，决定是否启用 |
| **行动** | ① 进入权限管理模式，看到"自助申请权限模式"入口和说明 ② 了解与双管理员互审、权限变更审批模式的互斥关系 ③ 评估模式是否适合企业管理方式 ④ 决定进入配置流程 |
| **触点** | 权限管理模式宣传页、"了解更多"帮助文档 |
| **用户心声** | "这个模式适不适合我们公司现在的管理方式？互斥条件会不会影响现有配置？" |
| **信心度** | 中 |
| **信心依据** | 故事 ST-01 描述了开启入口和互斥校验，但管理员的决策过程信息来自 UXB |
| **痛点** | ① 互斥关系只在启用时校验，决策阶段管理员看不到提前预警 ② 帮助文档链接"待补充" |
| **流失风险** | 低——管理员有明确的业务目标驱动 |
| **机会** | 在宣传页提前告知互斥条件和适用企业场景，辅助管理员决策 |

### 阶段二：模式配置

| 字段 | 内容 |
|------|------|
| **目标** | 完成申请方式、范围和审批流程的参数配置 |
| **行动** | ① 进入三步设置页 ② 选择申请方式：申请角色（默认）或申请功能权限（单选必选） ③ 设置范围：全部（默认）或部分，选择部分时从弹窗中筛选 ④ 设置后续新增角色/应用自动加入可申请范围（默认选中） ⑤ 设置审批流程（预设为组织负责人，可修改） |
| **触点** | 自助申请模式设置页（三步表单）、选择角色弹窗（搜索/分页/选项框）、选择应用弹窗（搜索/分页/选项框）、表单编辑子页面 |
| **用户心声** | "选角色还是功能权限？哪些角色要开放给员工申请？审批流程怎么设？" |
| **信心度** | 高 |
| **信心依据** | 故事 ST-01 详细的完成标准覆盖了全部配置步骤和弹窗交互 |
| **痛点** | ① "申请角色"和"申请功能权限"的差异需要管理员自行理解，选错后员工端体验全偏 ② 角色/应用弹窗中列表字段有限，管理员可能不清楚该选哪些 ③ 审批流程预设为组织负责人，如需按申请内容设置不同审批人不支持 |
| **流失风险** | 中——配置步骤较多且选项有理解成本，管理员可能选错或中途退出 |
| **机会** | 在设置页提供两种申请方式的适用画像提示（如"用角色管权限选申请角色，直接授权选申请功能权限"） |

### 阶段三：启用的上线

| 字段 | 内容 |
|------|------|
| **目标** | 完成前置校验，正式启用模式 |
| **行动** | ① 点击"启用" ② 系统校验双管理员互审和权限变更审批模式是否已开启 ③ 如互斥模式已开启，阻止启用并提示具体冲突 ④ 如通过校验，启用成功，员工端出现"我的权限"入口 |
| **触点** | 启用按钮、互斥校验提示、成功 Toast |
| **用户心声** | "开了，员工那边应该能看到入口了。" |
| **信心度** | 高 |
| **信心依据** | 故事 ST-01 明确了启用时的校验逻辑和成功后的页面反馈 |
| **痛点** | ① 互斥模式冲突只在此刻拦截，管理员需要折回去关闭冲突模式再回来 ② 启用后页面刷新为只读态，管理员如果想继续调整需切换到编辑模式 |
| **流失风险** | 低——校验有明确结果 |
| **机会** | 互斥冲突时提供"去关闭冲突模式"的快捷跳转 |

### 阶段四：运维与调整

| 字段 | 内容 |
|------|------|
| **目标** | 日常维护模式配置，必要时编辑或关闭模式 |
| **行动** | ① 日常查看模式运行状态 ② 如需调整配置，点击"编辑"切换到编辑态修改 ③ 如需关闭，走二次确认和关闭流程 ④ 若有在途流程，关闭被拦截，需等待审批完成 |
| **触点** | 模式已开启状态页（查看态/编辑态）、关闭确认弹窗、关闭失败弹窗 |
| **用户心声** | "开了之后基本不用管，但偶尔需要调一下或者关掉。" |
| **信心度** | 中 |
| **信心依据** | 故事 ST-06 明确了编辑和关闭流程，但关闭失败时无替代方案 |
| **痛点** | ① 关闭模式时存在在途流程会关闭失败，管理员只能等待，无替代处理方式 ② 编辑时修改范围或申请方式可能影响已在途的申请单，影响范围不透明 |
| **流失风险** | 低——管理员有操作需求时才会进入 |
| **机会** | 关闭失败时展示在途流程列表和联系人信息；编辑时提示本次修改对在途申请的潜在影响 |

## 支持角色旅程二：审批人

### 角色摘要

审批人（默认为申请人的组织负责人，可由管理员配置）通过 OA 审批流程收到权限申请待办，查看申请内容（角色/功能权限）和申请原因后，做出同意或否决的决策。同意后系统自动分配权限。

---

### 阶段一：接收待办

| 字段 | 内容 |
|------|------|
| **目标** | 收到权限申请通知，了解有申请待处理 |
| **行动** | ① 在 OA 审批待办列表中看到权限申请条目 ② 查看简要信息（申请人、申请内容） ③ 决定是否立即处理 |
| **触点** | OA 审批待办列表、待办卡片 |
| **用户心声** | "有人申请权限了，先看看是什么。" |
| **信心度** | 中 |
| **信心依据** | 故事 ST-04 确认了审批人通过 OA 审批流程收到待办，但待办列表显示的信息粒度未详细说明 |
| **痛点** | ① 待办列表中是否显示足够的摘要信息（申请人、申请内容、紧急程度）影响审批人的处理优先级判断 |
| **流失风险** | 中——待办信息不充分时可能拖延处理 |
| **机会** | 待办卡片上展示申请人、申请内容和提交时间，帮助审批人快速判断紧急程度和重要性 |

### 阶段二：审查申请内容

| 字段 | 内容 |
|------|------|
| **目标** | 查看申请详情，了解申请了什么以及为什么 |
| **行动** | ① 打开申请详情页 ② 查看申请人信息 ③ 查看申请的角色名称或功能权限详情 ④ 阅读申请原因（自由文本） ⑤ 判断批准是否合理 |
| **触点** | 审批详情页、申请内容展示区（角色名或权限详情"查看详情"）、申请原因文本区 |
| **用户心声** | "他申请的权限是做什么的？这个理由充分吗？" |
| **信心度** | 中 |
| **信心依据** | 故事 ST-04 明确了审批人能看到申请人信息、申请内容（角色名/权限名）和申请原因，但缺少决策上下文 |
| **痛点** | ① 审批人只看到角色名，不知道这个角色具体包含哪些功能和数据权限 ② 审批人不知道申请人当前已有权限，无法判断是否重复或合理 ③ 申请原因质量参差不齐，自由文本缺乏结构 |
| **流失风险** | 高——判断依据不足时不敢批导致反复驳回，或盲目批失去审批意义 |
| **机会** | 在审批详情中提供申请角色/权限的简要说明（包含哪些功能范围）；考虑是否需要展示申请人当前权限概览 |

### 阶段三：做出审批决策

| 字段 | 内容 |
|------|------|
| **目标** | 同意或否决申请 |
| **行动** | ① 选择"同意"或"否决" ② 如选择否决，填写否决原因（是否必填未明确） ③ 确认提交决策 |
| **触点** | 审批操作区（同意/否决按钮） |
| **用户心声** |（同意）"理由合理，批了。"（否决）"这个不太合适，跟他说一下原因。" |
| **信心度** | 高 |
| **信心依据** | 故事 ST-04 明确了二选一决策的操作 |
| **痛点** | ① 如果否决原因不做要求，审批人可能不写或只写"不同意"，申请人无法了解原因 ② 审批人可能需要在多个系统间切换才能判断 |
| **流失风险** | 低——到达此阶段通常会做出决定 |
| **机会** | 否决时引导审批人填写具体原因（选项或自由文本），为申请人提供有意义反馈 |

### 阶段四：确认处理结果

| 字段 | 内容 |
|------|------|
| **目标** | 确认审批结果已生效 |
| **行动** | ① 审批同意后系统自动分配权限，审批人不需要额外操作 ② 如果系统分配失败，是否需要审批人介入未明确 |
| **触点** | 申请单详情（查看最终状态） |
| **用户心声** | "批了之后系统会自动处理，应该没问题。" |
| **信心度** | 低 |
| **信心依据** | 故事 ST-04 风险中标注"自动分配权限失败的兜底机制未明确" |
| **痛点** | ① 审批人不知道权限是否已成功分配 ② 自动分配失败时无人通知审批人 |
| **流失风险** | 低——审批人已完成自身职责 |
| **机会** | 自动分配失败时通知审批人以便人工介入，形成审批闭环 |
