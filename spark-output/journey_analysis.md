# 用户旅程分析：企业数字化产品员工权限自助申请

- **运行模式**：`prd-standalone`
- **是否使用补问**：否
- **数据来源**：`problem-framing`（问题框定）+ `stories`（用户故事）
- **结果等级**：完整旅程

## 角色摘要

### 主角色：员工

员工是企业数字化产品的日常使用者。当需要新增或变更权限时，当前只能通过私下联系管理员或老板解决。本次旅程分析聚焦员工视角，覆盖从"意识到需要权限"到"权限生效并使用"的全过程。

辅助角色（本旅程中作为触点出现，不做独立旅程展开）：

- **上级组织负责人**：审批人，在审批阶段作为关键触点出现
- **权限管理员/超管**：控制面配置方，在后台配置可申请范围

### 旅程范围

| 项目 | 内容 |
|---|---|
| 旅程类型 | end-to-end |
| 起点 | 员工意识到自己缺少某项权限 |
| 终点 | 权限生效，员工能正常使用所需功能 |
| 上游约束 | 敏感权限系统预置排除；审批由 OA 底座提供；上级负责人由组织域定义 |

## 阶段正文

---

### Stage 1：感知权限缺口

- **阶段目标**：员工意识到自己当前缺少操作某项功能所需的权限
- **来源**：`原文提取`（problem-framing 核心场景 D+A）+ `规则推导`

| 字段 | 内容 |
|---|---|
| **用户行动** | ① 正常操作功能时遇到无权限拦截页面；② 收到业务任务后主动检查自己是否有权限；③ 尝试操作发现按钮置灰/不可用 |
| **触点** | 功能操作页面、无权限拦截页/提示条、权限中心入口 |
| **用户心声** | "为什么我不能点这个？" |
| **信心** | 高 |
| **信心理由** | problem-framing 明确两个核心触发场景（缺口感 D + 目标驱动 A），故事 S1/S4 已展开 |
| **痛点** | ① 拦截页只提示"无权限"但不告诉缺少的具体权限名称；② 员工不知道去哪里了解"自己有什么权限"；③ 没有引导下一步的行动入口，员工只能放弃或找人问 |
| **流失风险** | 高。当前没有引导的情况下，员工大概率放弃操作，转而私下联系管理员或干脆不处理 |
| **机会** | 在拦截页直接告知缺少的具体权限并引导申请；在权限中心提供"我的权限"概览让员工主动检查 |

---

### Stage 2：定位与选择权限

- **阶段目标**：员工明确需要申请哪些权限/角色
- **来源**：`原文提取`（problem-framing 场景 A）+ `规则推导` + `故事 S1/S4 设计触点`

| 字段 | 内容 |
|---|---|
| **用户行动** | ① 从无权限拦截页跳转到申请流程，查看预填充的权限信息；② 在权限中心按"我要做的事"搜索相关权限；③ 浏览可申请权限列表，勾选所需项 |
| **触点** | 权限中心、任务搜索框/分类导航、可申请权限列表、权限说明卡片 |
| **用户心声** | "是这个权限吗？选对了会不会出问题？" |
| **信心** | 中 |
| **信心理由** | 缺口触发场景（S1）的路径较清晰；目标驱动场景（S4）的任务→权限映射关系为 `critical_assumption`，尚不确定可行性和覆盖率 |
| **痛点** | ① 权限名称偏管理术语，员工看不懂"功能权限""数据权限"的区别；② 不知道选了多个会不会有冲突；③ 搜索不到想申请的权限时没有替代方案；④ 不确定自己选择的权限"对不对" |
| **流失风险** | 中高。如果员工找不到对应的权限，或列表过于复杂看不懂，可能在此阶段放弃 |
| **机会** | 用业务语言描述权限（"你可以查看和编辑报销单"而非"费用管理_编辑权限"）；在搜索无结果时提供人工帮助入口或引导联系管理员 |

---

### Stage 3：发起申请

- **阶段目标**：填写申请信息并提交，进入审批流程
- **来源**：`原文提取`（problem-framing 审批流程描述）+ `规则推导` + `故事 S1 设计触点`

| 字段 | 内容 |
|---|---|
| **用户行动** | ① 确认申请的权限/角色信息；② 填写申请理由（为什么要这个权限）；③ 提交申请；④ 看到提交成功反馈 |
| **触点** | 申请表单页（权限预填项、理由输入框）、提交按钮、提交成功确认页 |
| **用户心声** | "希望快点批下来" |
| **信心** | 高 |
| **信心理由** | problem-framing 明确了审批流程（上级负责人审核，OA底座支撑），故事 S1 有明确验收标准 |
| **痛点** | ① 不知道申请理由写多详细才够；② 不确定审批人是谁（系统自动匹配上级）；③ 提交后只有一个"成功"提示，不知道下一步发生什么、多久有结果；④ 不知道申请能否被中途撤销 |
| **流失风险** | 低。到了提交阶段说明员工有明确需求，流失主要发生在理由填写卡顿上 |
| **机会** | 提供申请理由模板/引导；提交后明确告知审批人、预计时限和下一步流程 |

---

### Stage 4：等待审批与追踪进度

- **阶段目标**：等待审批结果，期间了解申请处理状态
- **来源**：`原文提取`（problem-framing 场景 3 状态追踪）+ `规则推导` + `故事 S5`

| 字段 | 内容 |
|---|---|
| **用户行动** | ① 查看申请进度页面，了解当前状态；② 等待审批结果通知；③ 必要时联系审批人提醒 |
| **触点** | 我的申请列表、申请详情页、状态标签、审批通知 |
| **用户心声** | "怎么还没批？要不要去问一下？" |
| **信心** | 中 |
| **信心理由** | 故事 S5 确认了状态追踪场景，但审批超时策略、通知渠道均为 `open_gap`，尚未确认 |
| **痛点** | ① 不知道审批进行到哪一步了（卡在审批人待办中还是已被忽略）；② 不知道大概要等多久；③ 审批人不在线时没有升级机制；④ 只能被动等待，无法主动推动 |
| **流失风险** | 中。长时间无反馈时，员工可能重复私下联系审批人，或认为流程不可靠而放弃 |
| **机会** | 提供清晰的进度可视化（当前步骤 + 预计剩余时间）；审批超时自动升级或提醒；关键状态变更主动通知 |

---

### Stage 5：接收审批结果

- **阶段目标**：收到审批通过/拒绝的通知，了解并处理结果
- **来源**：`规则推导` + `故事 S2 完成标准`

| 字段 | 内容 |
|---|---|
| **用户行动** | ① 收到审批结果通知；② 查看结果详情（通过或拒绝及原因）；③ 如通过，确认权限已生效；④ 如被拒，了解原因并决定是否再次申请或沟通 |
| **触点** | 通知（站内/消息/邮件）、我的申请详情页、权限中心（最新权限状态） |
| **用户心声** | "终于批了！" / "为什么拒了？" |
| **信心** | 中 |
| **信心理由** | 审批流程由 OA 底座支撑，但通知渠道（`open_gap`）和拒绝原因表达方式未确认 |
| **痛点** | ① 拒绝时只显示"审批不通过"但没有原因，员工不知道是不需要还是不该申请；② 通过后权限没有即时生效，存在"已批准但还不能用"的空窗期；③ 生效后没有主动提醒，员工需要自己再去试 |
| **流失风险** | 中。被拒无理由时，员工可能丧失再次尝试的意愿或对系统失去信任 |
| **机会** | 审批拒绝必须附可理解的原因；通过后主动告知生效时间和可用范围；提供"被拒后怎么办"的引导 |

---

### Stage 6：使用已获得权限

- **阶段目标**：使用已生效的权限完成业务操作，并管理已有权限
- **来源**：`规则推导` + `故事 S6`

| 字段 | 内容 |
|---|---|
| **用户行动** | ① 回到目标功能页面确认权限已生效；② 正常使用功能完成业务操作；③ 日后在权限中心查看已有权限清单 |
| **触点** | 目标功能页面、权限中心（我的权限页） |
| **用户心声** | "有了，可以用了。" |
| **信心** | 高 |
| **信心理由** | 故事 S6 的验收标准已明确"按应用或功能分类展示已有权限"和生效状态 |
| **痛点** | ① 不知道权限来自哪个角色或哪次申请（多个来源叠加时不好核对）；② 权限调整或回收后没有通知，员工可能以为自己还有权限；③ 不知道权限的有效期限 |
| **流失风险** | 低。主要问题在信息透明度而非核心功能 |
| **机会** | 展示权限来源说明；权限变更（回收/调整）时主动通知并提供原因；标注权限有效期或下次复核时间 |

## 缺口说明

| 缺口 | 影响阶段 | 说明 |

| 审批超时/升级策略未确认 | Stage 4 | 影响等待阶段的流失风险和体验设计 |

| 权限来源展示方式未确认 | Stage 6 | 影响权限概览页的信息深度 |
