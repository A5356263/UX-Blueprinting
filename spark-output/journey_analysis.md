# 用户旅程分析：员工自助申请权限

- **运行模式**：uxb-chain
- **是否使用补问**：否
- **数据来源**：spark-output/context/uxb.json、spark-output/uxb_output.md
- **结果等级**：完整旅程

---

## 角色摘要

本次旅程分析聚焦**普通员工**这一主行动角色——自助申请权限的核心用户。超级管理员和审批人作为关键触点和支撑角色出现在员工旅程的对应阶段中，但不单独展开独立旅程。

---

## 阶段一：发现受限

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工在工作中遇到功能限制，意识到自己缺少某项权限 |
| **用户行动** | 尝试使用某项业务功能 → 遇到功能不可用的提示 → 排查原因 → 意识到是权限不足 |
| **关键触点** | 业务功能页面、功能限制提示/报错、同事（线下咨询） |
| **用户心声** | "怎么这个功能我用不了？是坏了还是我没权限？" |
| **信心等级** | 高 |
| **信心依据** | UXB 明确描述"员工通常先遇到功能限制才发现缺权限"，需求文档核心场景确认了该触发路径 |
| **痛点** | ① 限制提示不明确，分不清是系统异常还是权限问题；② 员工需要自己排查原因，缺乏引导；③ 不确定找谁确认，可能辗转多人 |
| **流失风险** | **中高** — 如果提示模糊或排查成本高，员工直接放弃该功能或转找管理员，回到线下老路 |
| **设计机会** | 在功能受限时直接给出明确提示（"你需要 XX 权限才能使用此功能"），并提供"立即申请"入口 |

---

## 阶段二：定位申请

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工找到权限申请入口，明确自己要申请什么权限 |
| **用户行动** | 寻找申请入口 → 进入权限相关页面 → 浏览可申请权限列表 → 确认自己要申请的权限项 |
| **关键触点** | 权限申请入口、权限中心/"我的权限"页面、可申请权限列表、权限说明 |
| **用户心声** | "入口在哪？这些权限名都是什么意思？我该选哪个？" |
| **信心等级** | 中 |
| **信心依据** | UXB 已识别"入口不明确"和"权限术语门槛"两个关键断点，但具体入口位置（功能触发现场 vs 独立模块）和权限命名标准化程度尚未确认 |
| **痛点** | ① 入口位置不自然，员工不知道从哪发起申请；② 权限名称是管理后台术语，员工看不懂；③ 权限列表信息密度高，不知道哪个是自己需要的；④ 如果入口只放在独立模块，员工需要先找到该模块（额外认知成本） |
| **流失风险** | **高** — 这是整个自助申请路径中最脆弱的环节。找不到入口或看不懂权限名，员工必然退回线下找管理员 |
| **设计机会** | ① 在功能受限处直接提供"申请权限"按钮，缩短路径；② 权限名附带通俗解释和用途说明；③ 提供搜索或分类筛选，降低选择负担 |

---

## 阶段三：提交申请

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工正确填写申请信息并成功提交 |
| **用户行动** | 选择要申请的权限（如阶段二未完成）→ 填写申请原因 → 确认申请内容 → 提交 → 看到提交结果反馈 |
| **关键触点** | 申请表单、提交按钮、提交成功/失败反馈页、申请记录页 |
| **用户心声** | "申请原因要怎么写才合适？提交成功了没？接下来会怎样？" |
| **信心等级** | 高 |
| **信心依据** | UXB §5 功能单元完整定义了"提交权限申请"的输入、处理和输出；§6 定义了"待审批"状态的后续流转 |
| **痛点** | ① 不知道申请原因写多详细、什么角度，担心写太短被拒；② 提交后反馈不充分，不确定是否真的提交成功；③ 提交后不知道下一步会发生什么、等多久 |
| **流失风险** | **中** — 如果填写门槛高（如原因必须写满多少字），部分员工可能放弃；如果提交后无明确反馈，员工会以为失败并重复提交或找管理员 |
| **设计机会** | ① 提供申请原因示例或模板（如"我需要此权限来完成 XX 工作"）；② 提交成功后明确展示"申请已提交，预计审批人 XX，预计处理时间 XX"；③ 自动跳转到申请记录页，让状态可见 |

---

## 阶段四：等待审批

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工了解审批进度，知道何时能获得权限 |
| **用户行动** | 查看申请记录 → 关注审批状态变化 → 状态长时间不变时可能催办或再次询问管理员 |
| **关键触点** | 申请记录页、审批状态标签、消息/待办通知、审批人（线下催促） |
| **用户心声** | "怎么还没批？卡在谁那了？还要等多久？" |
| **信心等级** | 中 |
| **信心依据** | UXB §6 定义了申请状态流转（待审批→审批中→已通过/已拒绝），但审批时长、催办机制、超时处理等尚未定义 |
| **痛点** | ① 审批状态不更新或更新滞后，员工不知道卡在哪；② 不知道审批人是谁，不敢催；③ 等待时间长且不确定，不如直接找管理员快（破坏自助流程动力）；④ 如果审批流程多人，不知道当前卡在谁那 |
| **流失风险** | **高** — 等待时间过长或状态不透明，员工可能绕过自助流程，再次线下联系管理员，自助申请能力沦为摆设 |
| **设计机会** | ① 展示审批流转路径（当前节点、审批人、等待时长）；② 状态变更时主动推送通知，不依赖员工主动刷新；③ 支持在合理超时后提醒审批人或允许员工催办 |

---

## 阶段五：获得结果

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工收到审批结果，并根据结果采取下一步行动 |
| **用户行动** | （通过）收到审批通过通知 → 查看权限是否已生效 → 回到原功能使用； （被拒）收到拒绝通知 → 查看拒绝原因 → 决定重新申请或联系管理员 |
| **关键触点** | 审批结果通知（消息/待办）、我的权限页面、申请记录页 |
| **用户心声** | "批了！现在就能用了吗？/ 为什么被拒了？我做错了什么？" |
| **信心等级** | 高 |
| **信心依据** | UXB §6 明确定义了"已通过"和"已拒绝"两个终态及其系统处理结果和用户下一步 |
| **痛点** | ① 审批通过了，但权限未即时生效，员工尝试使用功能时仍不可用（授权延迟）；② 被拒绝时原因模糊（如"审批不通过"），员工不知道具体问题；③ 被拒后没有明确的重申请或申诉路径 |
| **流失风险** | **中** — 被拒后如果原因不明确且无申诉渠道，员工不再信任自助流程，退回线下；审批通过但延迟生效也会让员工困惑 |
| **设计机会** | ① 通过后明确告知"权限已生效，可立即使用"，并提供"回到功能"的快捷入口；② 拒绝原因结构化展示（如"原因：该权限需要部门负责人另行审批"），并建议下一步；③ 被拒后可一键重新申请或联系审批人 |

---

## 阶段六：回归工作

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工回到原工作任务，使用获得的权限完成工作 |
| **用户行动** | 回到之前受限的功能页面 → 确认功能已可用 → 正常开展工作；或被拒后与管理员沟通 → 寻找替代方案 |
| **关键触点** | 原功能页面、新权限对应的业务模块、管理员（线下） |
| **用户心声** | "终于可以正常用了 / 还是得找管理员才行" |
| **信心等级** | 中 |
| **信心依据** | UXB 确认了"自动授权"作为审批通过的终态处理，但未定义审批通过后如何引导员工回到使用场景 |
| **痛点** | ① 审批通过但员工不知道从哪继续之前的工作，需要重新定位功能入口；② 被拒后没有标准替代路径，员工只能回归线下沟通 |
| **流失风险** | **低** — 通过审批后员工基本获得所需能力；但被拒后的升级路径缺失可能导致员工对系统的信任下降 |
| **设计机会** | ① 审批通过通知中附带"回到之前的功能"直接链接；② 被拒后提供建议路径（如"建议联系部门管理员为你授权"） |

## 阶段转折

| 从 | 到 | 触发条件 | 风险 |
|----|----|---------|------|
| 发现受限 | 定位申请 | 员工意识到是权限问题，决定主动申请 | 如果限制提示不明，员工可能在"排查原因"阶段流失 |
| 定位申请 | 提交申请 | 员工找到入口并确认要申请的权限项 | 找不到入口或看不懂权限名 → 高流失风险 |
| 提交申请 | 等待审批 | 员工成功提交申请，系统创建申请单 | 反馈不充分时员工可能重复提交或以为失败 |
| 等待审批 | 获得结果 | 审批人做出通过/拒绝决定 | 等待过长 → 回到线下，自助流程被架空 |
| 获得结果 | 回归工作 | 员工收到审批结果并采取行动 | 被拒后无标准路径 → 回归线下 |

## 缺口说明

| 缺口 | 影响 | 需要的输入 |
|------|------|-----------|
| 员工端入口位置未确定 | 影响"定位申请"阶段的体验方案设计，入口融合程度不同则信息架构不同 | 产品决策：入口设在功能受限处还是独立权限中心 |
| 权限命名标准化程度未确认 | 影响"定位申请"阶段中权限列表的可读性，如果权限名本身就是内部编码则无法展示 | 权限域确认：当前权限是否有统一名称和分类 |
| 审批时长和催办机制未定义 | 影响"等待审批"阶段的状态反馈和催办设计，如果审批超长但没有催办，等待体验差 | 产品决策：是否支持催办、超时提醒等 |
| 被拒后申诉路径未定义 | 影响"获得结果→回归工作"阶段的流转，被拒后员工不知道该怎么做 | 产品决策：是否支持申诉或建议替代路径 |
