## 一、员工（权限申请人）

### 阶段 1：感知权限缺口

**用户目标**
意识到自己缺少某项权限，有了申请需求。

**用户行动**
在工作中遇到"无权访问"提示、需要使用某个功能却找不到入口、或者同事/上级告知需要某种权限才能继续下一步。

**关键触点**
- 系统返回的无权限提示或功能灰态
- 同事或上级的口头告知
- 业务场景中自然产生的需求

**用户心声**
"这个功能我怎么打不开？好像我没权限。"

**用户信心度**
高。自己有切身需求，动机明确。

**痛点**
- 如果系统没有明确的"无权限"反馈（比如直接隐藏入口），用户可能根本不知道自己缺权限
- 当前只能通过非正式渠道找管理员，没有标准化通道

**流失风险**
如果不知道找谁处理，或者找管理员的过程太麻烦，可能放弃使用该功能，转向线下处理方式。

**设计机会**
- 无权限时提供清晰的"申请权限"入口（下游：蓝图）
- 在功能不可用时告知用户"申请此权限需要多长时间、谁审批"（下游：故事）

### 阶段 2：确认权限现状

**用户目标**
查看自己当前有什么权限，确认确实缺少某项权限，避免重复申请。

**用户行动**
进入"我的权限"或类似页面，浏览自己已有的应用、功能和数据范围，对比自己需要的权限，确认确实没有。

**关键触点**
- "我的权限"查看页面
- 权限列表按应用或功能分组的展示结构

**用户心声**
"让我先看看我到底有没有……嗯，确实没有这个权限。"

**用户信心度**
中。取决于权限查看页面的信息结构是否清晰。如果只显示应用级不显示功能级，用户可能无法确认。

**痛点**
- 如果权限查看粒度只到应用级，用户无法判断自己是否缺少某个功能级权限 [GAP]
- 权限列表如果缺乏分组和搜索，在权限较多时查找成本高
- 如果"我的权限"页面不存在，用户直接跳过此环节，在申请页面凭感觉选

**流失风险**
找不到查看权限的入口，或者页面信息看不懂，用户可能放弃自助，回到找管理员的老路。

**设计机会**
- 提供结构化的权限展示——按应用分组、区分功能权限和数据范围（下游：蓝图）
- 权限列表与申请入口形成闭环——看到缺少的权限可以直接申请（下游：蓝图）
- 搜索和筛选能力——权限数量多时快速定位（下游：故事）

### 阶段 3：发起权限申请

**用户目标**
选择所需权限、说明申请原因、提交申请。

**用户行动**
进入申请页面 → 浏览可申请范围（管理员已配置的权限项）→ 选择需要的权限 → 填写申请原因 → 确认提交。

**关键触点**
- 权限申请入口（可能在"我的权限"页、具体功能页、全局导航等位置）
- 申请表单（权限选择器 + 申请原因输入框）
- 可申请范围的配置决定了表单里能看到什么

**用户心声**
"申请个权限还要填原因啊……希望别太复杂，也别让我选那些看不懂的选项。"

**用户信心度**
低到中。原因：
- 申请表单的复杂度取决于可申请范围的配置粒度和权限选择器的易用性 [基于规则推导]
- 如果可选权限项太多且缺乏分类，用户容易选错或不敢选
- 用户对"申请后会发生什么"没有预期

**痛点**
- 可申请范围如果按功能权限点配置，列表可能很长，选择困难 [GAP]
- 申请原因要写到什么程度才算合理，用户没有参照
- 如果可选权限项缺乏说明（"这个功能是干什么的"），用户可能选错
- 提交后系统反馈如果只给一个"提交成功"，用户不知道下一步谁来处理、等多久

**流失风险**
- 表单太复杂 → 用户放弃填写
- 不知道选什么 → 用户退出，先去问同事
- 提交后没有明确预期 → 用户仍然去找管理员确认"收到了吗"

**设计机会**
- 权限选择器提供分类分组和搜索（下游：蓝图）
- 每个可选权限项附带简短说明，帮助用户理解（下游：故事）
- 提交后给出明确的"下一步"指引——谁来审批、预计时长、如何催办（下游：蓝图）
- 申请原因提供常用模板或选项，降低输入门槛（下游：故事）

### 阶段 4：等待审批处理

**用户目标**
了解申请进度，在必要时催办。

**用户行动**
查看申请记录列表或详情页面，了解当前审批状态（审批中 / 已通过 / 已拒绝）。如果长时间没有处理，可能通过系统催办或线下联系审批人。

**关键触点**
- 申请记录列表页
- 申请详情页（当前状态、审批人信息、处理时间线）
- 催办按钮或通知机制

**用户心声**
"怎么还没批？要不要催一下……希望别卡在审批人那里。"

**用户信心度**
低。原因：
- 审批时长不确定，用户无法预期什么时候有结果 [基于规则推导]
- 如果审批人失联或超时，用户没有有效的升级手段 [基于规则推导]
- 查看状态的入口如果隐藏较深，用户会感到焦虑

**痛点**
- 审批状态停留在"审批中"，但不知道审批人是谁、有没有在看
- 超时后没有自动提醒或升级机制
- 如果需要催办，系统没有催办入口，又回到线下沟通

**流失风险**
- 审批太久 → 用户线下找管理员，自助申请的信任度下降
- 完全不知道审批状态 → 用户以为系统坏了或申请丢了

**设计机会**
- 申请详情展示完整状态时间线——提交时间 → 审批人查看时间 → 处理结果（下游：蓝图）
- 提供催办功能——超过一定时间未处理可一键催办（下游：故事）
- 状态变更推送通知——审批结果第一时间触达用户（下游：故事）

### 阶段 5：获知审批结果

**用户目标**
知道申请通过了还是被拒绝了，以及下一步该怎么做。

**用户行动**
收到系统通知（站内信/消息/邮件）→ 查看审批结果。如果通过，等待系统自动授权；如果拒绝，查看拒绝原因。

**关键触点**
- 通知消息（站内通知、邮件、工作台消息）
- 申请详情页（审批结果、审批意见、拒绝原因）

**用户心声**
（通过时）"通过了！这下我可以用了吧？"
（拒绝时）"为什么拒绝？是因为理由不充分还是这个权限不适合我？"

**用户信心度**
中。关键在于审批结果是否附带足够的信息让用户理解"为什么"。

**痛点**
- 如果拒绝原因过于模糊（如"审批人不同意"），用户不知道应该调整什么再申请
- 如果审批人只给了拒绝没有建议，用户下次申请仍然可能被拒
- 通过后如果权限没有立即生效，用户会困惑"到底能不能用"

**流失风险**
- 拒绝后不知道怎么办 → 用户直接找管理员，绕过自助申请
- 通过后权限未及时生效 → 用户以为系统有问题，投诉或放弃

**设计机会**
- 拒绝结果必须附带明确原因，必要时给出建议（下游：蓝图）
- 通过后给出"权限已生效 / 正在生效中"的明确状态（下游：蓝图）
- 被拒绝后提供"重新申请"入口，允许修改原因后再次提交（下游：故事）

### 阶段 6：验证权限生效

**用户目标**
确认申请的权限已经生效，可以正常使用。

**用户行动**
回到之前遇到权限问题的地方，尝试使用功能或查看数据，验证权限确实已生效。

**关键触点**
- 目标功能的操作页面
- "我的权限"页面（确认新权限已在列表中）

**用户心声**
"好，试试看能不能用了……嗯，可以了。"

**用户信心度**
高。如果生效反馈明确，用户很快就能验证。

**痛点**
- 如果权限生效有延迟或部分生效，用户反复尝试失败，不知道是还没生效还是授权有问题
- 如果系统中没有地方确认"我的权限"列表已更新，用户只能靠试错验证

**流失风险**
- 权限未及时生效且无反馈 → 用户以为自助申请没用，回到管理员渠道
- 部分生效但无提示 → 用户使用时遇到异常，体验断裂

**设计机会**
- 授权完成后推送通知并附带"查看我的权限"链接（下游：蓝图）
- 授权异常时明确告知哪些权限生效、哪些失败、失败原因（下游：蓝图）

### 阶段转折

**感知缺口 → 确认现状**：用户决定查一下自己到底有什么权限，主动进入查看入口。

**确认现状 → 发起申请**：用户确认确实缺少某项权限，决定申请。

**发起申请 → 等待审批**：用户提交申请，系统进入审批流程。

**等待审批 → 获知结果**：审批人做出审批决策（通过/拒绝），系统通知用户。

**获知结果 → 验证生效**（通过时）：用户收到通过通知，去验证权限是否生效。

**获知结果 → （回到发起申请）**（拒绝时）：用户查看拒绝原因后，可能调整申请再次提交。

## 二、审批人

### 阶段 1：接收审批通知

**用户目标**
知道有新的权限申请需要处理。

**用户行动**
收到系统通知（站内消息、邮件、审批中心待办）→ 查看待审批列表 → 了解有多少申请待处理。

**关键触点**
- 审批中心 / 待办列表
- 通知消息

**用户心声**
"又有人申请权限了，让我看看是什么。"

**用户信心度**
高。通知送达和待办列表是标准能力。

**痛点**
- 如果通知不具备足够的信息量（只有"XX提交了权限申请"没有具体内容），审批人需要点进去才知道是什么
- 申请数量多时，待办列表缺乏优先级区分

**流失风险**
- 通知太多 → 审批人忽略或延迟处理
- 待办列表没有分类筛选 → 审批人优先处理自己熟悉的申请，陌生申请积压

**设计机会**
- 通知中包含关键信息——申请人和申请权限名称，帮助审批人提前判断紧急性（下游：故事）
- 待办列表支持按申请时间、紧急程度排序和筛选（下游：故事）

### 阶段 2：审查申请内容

**用户目标**
理解谁申请了什么权限、申请原因是什么，判断是否合理。

**用户行动**
打开申请详情 → 查看申请人信息（部门、职位、现有权限）→ 查看申请的权限内容 → 查看申请原因 → 必要时核对申请人的实际业务需要。

**关键触点**
- 审批申请详情页
- 申请人信息展示
- 申请权限的内容说明
- 申请人的现有权限参考

**用户心声**
"这个人为啥需要这个权限？理由是写清楚了，不过我得看看他现有的权限有没有冲突。"

**用户信心度**
低到中。原因：
- 审批人判断的充分性取决于申请信息的完整程度 [基于规则推导]
- 如果审批人不了解申请人的业务场景，很难判断"这个权限是否真的需要"
- 如果拒绝权限申请的流程过于复杂，审批人可能倾向于一律同意

**痛点**
- 申请原因太简单（如"工作需要"），审批人无法判断合理性
- 缺乏申请人现有权限的参考信息，审批人不知道新权限是否会与已有权限冲突
- 没有"该权限的历史申请记录"参考——该申请人之前是否申请过、是否被拒绝过、拒绝原因是什么
- 审批人可能不是该业务领域的负责人，缺乏判断依据

**流失风险**
- 信息不足且无法快速补充 → 审批人先同意再说，安全风险上升
- 审批流程太复杂 → 审批人拖延处理
- 审批人觉得自己不够了解情况 → 把决策推给其他人或超管，自助申请链路断裂

**设计机会**
- 申请详情展示完备信息——申请人背景、申请原因、申请的权限说明、申请人现有权限概览（下游：蓝图）
- 显示该权限的风险等级和审批建议——系统基于规则自动标注（下游：待确认）
- 审批人可一键查看申请人现有权限，辅助判断是否会冲突（下游：蓝图）
- 提供"转交审批"能力——如果审批人不适合处理，可转给更合适的人（下游：故事）

### 阶段 3：做出审批决定

**用户目标**
决定同意或拒绝申请，并给出相应的处理结果。

**用户行动**
选择"同意"或"拒绝"→ 如果同意，确认授权范围；如果拒绝，填写拒绝原因 → 提交决定。

**关键触点**
- 审批操作区（同意 / 拒绝按钮）
- 拒绝原因输入框
- 授权范围确认（如果允许审批人在授权前调整范围）

**用户心声**
"这个申请合理，同意吧。……这个说不太清楚，我先拒绝，把理由写清楚。"

**用户信心度**
中。取决于审批人对业务和自己判断的把握程度。

**痛点**
- 拒绝时必须填写原因——如果审批人赶时间，可能写得很模糊，导致员工不理解
- 如果允许审批人在同意前调整授权范围，复杂的权限树操作可能出错
- 操作不可逆——同意或拒绝后无法撤回，决策压力较大

**流失风险**
- 审批操作复杂 → 审批人暂时搁置，申请积压
- 过度担心决策风险 → 审批人倾向拒绝而不解释，员工体验差

**设计机会**
- 拒绝原因提供常用模板选项，降低输入门槛（下游：故事）
- 同意时默认使用申请范围，特殊情况下才支持调整（下游：蓝图）
- 操作前给出明确的"决策结果影响"预览，降低决策焦虑（下游：故事）

### 阶段 4：确认授权完成

**用户目标**
确认系统已按审批结果完成授权操作。

**用户行动**
（同意后）等待系统自动授权 → 查看授权结果通知 → 确认授权成功。如果授权失败，需要介入处理。

**关键触点**
- 审批完成确认页
- 授权结果通知
- （授权失败时）异常处理入口

**用户心声**
"同意完了，系统应该会自动处理吧……好，授权成功了。"

**用户信心度**
中。审批人期望系统能自动完成授权，但不清楚如果授权失败自己是否需要负责。

**痛点**
- 授权结果反馈如果延迟，审批人不知道是否出了异常
- 授权失败时，审批人可能需要手动处理但还是缺少工具
- 无授权失败的进一步指引——审批人被丢在一个"出错了"的状态

**流失风险**
- 授权失败且无明确处理指引 → 审批人觉得还是以前手动授权更可靠，不信任自助流程
- 多次授权异常 → 审批人建议员工直接线下找他，自助申请失去价值

**设计机会**
- 授权完成后即时反馈——成功或失败都通知审批人（下游：蓝图）
- 授权失败时提供问题原因和推荐的解决步骤（下游：故事）
- 长期无法自动处理的异常，系统可升级给超管介入（下游：待确认）

### 阶段转折

**接收通知 → 审查内容**：审批人点击待办或通知，进入申请详情。

**审查内容 → 做出决定**：审批人收集了足够信息，做出判断。

**做出决定 → 确认授权**（同意时）：系统自动执行授权，等待结果。

**做出决定 → （结束）**（拒绝时）：流程结束，通知申请人。

**确认授权 → （结束）**：授权完成，流程关闭。异常时转异常处理。

## 三、系统管理员 / 超管

### 阶段 1：评估与决策

**用户目标**
判断员工自助申请权限这项能力是否适合自己管理的企业。

**用户行动**
了解自助申请权限的功能范围、对现有权限体系的影响、需要投入的配置成本。对比当前授权模式和自助申请模式的优劣。

**关键触点**
- 功能说明或引导页
- 与现有治理模式的关系说明

**用户心声**
"开启这个功能方便员工，但我得先搞清楚会不会影响现有的权限管理……"

**用户信心度**
低。原因：
- 现有治理模式已经有多套（子管理员、双管理员、审批治理），新增能力的管理成本不确定 [基于规则推导]
- 不清楚开启后是否能关闭、关闭的代价是什么 [基于规则推导]
- 如果可申请范围和审批流程配置不当，可能导致权限失控，风险不确定 [基于规则推导]

**痛点**
- 缺乏"开启这个能力会改变什么"的清晰说明——尤其是与现有治理模式的互动关系
- 不确定开启后需要多少日常维护工作
- 担心员工滥用或误申请

**流失风险**
- 觉得风险不确定 → 管理员选择不开启，保持现状
- 现有治理模式已经很复杂了 → 管理员不想再增加一层配置负担

**设计机会**
- 首次开启前提供清晰的引导——说明开启后的变化、推荐的配置顺序、注意事项（下游：故事）
- 明确标注与现有治理模式的兼容关系——什么模式下可开启、什么模式下建议关闭（下游：待确认）
- 提供"先小范围试用"的能力——指定部分部门或角色先开通（下游：待确认）

### 阶段 2：首次配置

**用户目标**
完成自助申请权限的初始配置——开启能力、设置可申请范围、配置审批流程。

**用户行动**
进入管理后台的配置入口 → 开启自助申请能力开关 → 设置可申请范围（选择哪些权限员工可以申请）→ 配置审批流程（指定审批人或审批链）→ 确认生效。

**关键触点**
- 配置入口（可能在权限管理或治理模式相关页面）
- 能力开关
- 可申请范围配置器
- 审批流程配置

**用户心声**
"可申请范围怎么设比较好？设太宽怕风险，设太窄员工还是得找我，那开这个功能意义就不大了。"

**用户信心度**
中。管理员熟悉权限配置，但不确定如何平衡"安全"和"有用"。

**痛点**
- 可申请范围的配置粒度选择困难——按角色、按功能权限点、按应用各有优劣，但缺乏指导 [GAP]
- 审批流程配置如果复用现有审批中台，配置路径可能较长，涉及跨模块跳转
- 配置完成后缺乏预览机制——管理员无法快速验证"员工端看这个配置是什么样子"

**流失风险**
- 配置过程太复杂 → 管理员搁置配置，以后再说
- 不知道什么配置是"合理的" → 管理员设了过于严格的范围，员工使用后发现没什么用，自助申请形同虚设

**设计机会**
- 配置流程提供"推荐配置模板"——按企业规模和行业给出建议值（下游：故事）
- 配置完成后提供"员工视角预览"——让管理员看到员工端的申请页面长什么样（下游：蓝图）
- 可申请范围配置建议——如"建议先按角色配置，后续可按需细化到功能权限"（下游：故事）

### 阶段 3：日常运营维护

**用户目标**
监控自助申请的使用情况，及时处理异常，根据实际需要调整配置。

**用户行动**
定期查看申请统计（申请量、通过率、拒绝率、处理时长）→ 查看异常记录（授权失败的申请）→ 根据运行情况调整可申请范围和审批流程 → 处理审批人缺失等配置问题。

**关键触点**
- 使用统计看板
- 异常记录列表
- 配置调整入口

**用户心声**
"最近申请量上来了，大部分都批了，没什么问题。……嗯？有几个审批人离职了，申请卡在那里，我得重新指派。"

**用户信心度**
中高。管理员熟悉运营维护模式，但异常处理可能超出预期。

**痛点**
- 如果统计看板不够细致（如无法区分按部门、按权限类型的申请量），管理员无法精细化调整
- 审批人离职或调岗时，系统可能没有及时提醒管理员更新配置
- 异常记录如果分散在不同模块，管理员需要多处查看

**流失风险**
- 异常处理不及时 → 员工申请长期卡住 → 员工对自助申请失去信心
- 统计看板缺乏关键指标 → 管理员无法判断"这个功能到底帮了多少忙"

**设计机会**
- 提供使用统计看板——申请量、通过/拒绝率、平均处理时长、各部门分布（下游：故事）
- 异常自动预警——审批人缺失、授权失败等异常主动通知管理员（下游：故事）
- 提供"配置检查"建议——基于历史申请数据建议调整可申请范围（下游：待确认）

### 阶段 4：关闭能力（可选）

**用户目标**
在不影响现有授权和进行中申请的前提下，关闭自助申请能力。

**用户行动**
进入配置入口 → 查看当前进行中的申请数量 → 选择关闭策略（进行中申请的处理方式）→ 确认关闭。

**关键触点**
- 配置入口的关闭操作区
- 关闭前的确认信息（进行中申请数量、关闭影响说明）
- 关闭策略选择

**用户心声**
"公司调整策略，这个功能暂时不需要了。不过有几个还在审批中的申请，怎么处理好呢……"

**用户信心度**
中。关键在于关闭流程是否清晰、是否留下后遗症。

**痛点**
- 关闭策略不确定——文档和系统都未明确进行中申请该怎么处理 [GAP]
- 关闭后员工端入口消失，但已生效的权限不受影响，这点如果不明确，管理员会担心误回收
- 历史申请记录是否保留、如何查看不明确

**流失风险**
- 关闭流程不清晰 → 管理员不敢关，或者关了但留下未处理的申请
- 关闭后发现已生效权限也被自动回收了 → 运营事故

**设计机会**
- 关闭前展示清晰的影响说明——进行中申请数量、处理建议、已生效权限不受影响（下游：蓝图）
- 提供可选的关闭策略——继续流转 / 通知员工后作废（下游：待确认）
- 关闭后保留历史申请记录查询入口，便于审计追溯（下游：故事）

### 阶段转折

**评估决策 → 首次配置**：管理员决定开启自助申请能力。

**首次配置 → 日常运营**：配置生效后，进入日常使用阶段。

**日常运营 → 关闭能力**（可选）：管理员决定关闭功能，进入关闭流程。

**关闭能力 → （结束）**：关闭完成，功能下线。

## 附录：旅程信息汇总

### 员工旅程断点优先级

| 优先级 | 断点 | 影响 |
|--------|------|------|
| P0 | 员工无法查看自有权限的粒度不足以判断"缺什么" | 阻断申请前提 |
| P0 | 申请提交后无明确的状态预期 | 降低信任度 |
| P1 | 可申请范围配置太粗或太细导致选择困难 | 增加放弃率 |
| P1 | 拒绝原因太模糊导致重复申请或线下回流 | 增加管理成本 |
| P2 | 审批超时无催办机制 | 堵塞流程 |
| P2 | 授权结果反馈延迟或不明确 | 体验断裂 |

### 三个角色的关系依赖

- **员工 → 管理员**：管理员的配置质量（可申请范围、审批流程）直接影响员工的申请体验
- **员工 → 审批人**：审批人的响应速度和决策质量直接影响员工对自助申请的信任
- **管理员 → 审批人**：管理员配置的审批人是否有效，决定审批流程能否闭环
- **核心制约**：三个角色中任何一个断链，自助申请能力就会失效或回流到线下渠道
