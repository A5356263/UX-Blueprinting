# 旅程分析：员工自助申请权限

- **运行模式**：`uxb-chain`
- **是否使用补问**：否
- **数据来源**：UXB 5.0 定案（spark-output/context/uxb.json、spark-output/uxb_output.md）
- **结果等级**：完整旅程

---

## 角色摘要

**主角色**：企业员工（普通用户）
- 希望不需要通过管理员就能自行查看和申请所需权限
- 当前痛点：私下找老板/管理员 → 沟通成本高、授权时效不稳定、社恐不好意思

**辅助角色**：
- 超级管理员 — 配置自助申请模式（选择方式、设置范围、审批流程、启用/关闭）
- 审批人（组织负责人） — 审核权限申请，做出同意或拒绝决策

---

## 阶段一：感知配置与入口

| 字段 | 内容 |
|------|------|
| **目标** | 超管完成模式配置，员工知道可以从哪里申请权限 |
| **行动** | 超管：进入权限管理模式 → 了解自助申请 → 选择方式 → 设置范围 → 配置审批 → 启用。员工：在个人中心看到"我的权限"入口 |
| **触点** | 权限管理模式页、自助申请配置页（三步设置）、个人中心 |
| **用户心声** | 超管："别选错了方式，不然后面全偏。" 员工："咦，这里多了个我的权限？" |
| **信心度** | 高 |
| **信心依据** | UXB §5 功能范围明确了配置流程和启用后的入口规则 |
| **痛点** | ① 超管可能不理解两种申请方式的差异，选错后员工侧体验全偏 ② 配置步骤多，启用时互斥校验可能阻断 ③ 员工可能没注意到新出现的入口，不知道可以自助申请 |
| **流失风险** | 超管配置时因互斥冲突或不理解选项而放弃启用；入口不显眼导致员工不知道可用 |
| **设计机会** | ① 配置第一步用场景比对卡片替代 radio 选项 ② 互斥冲突时提供快捷跳转关闭 ③ 启用后给员工侧轻提示或引导 |

---

## 阶段二：发现权限缺口

| 字段 | 内容 |
|------|------|
| **目标** | 员工意识到自己缺少某项工作所需的权限 |
| **行动** | 在工作中遇到功能不可用或数据不可见 → 进入个人中心 → 点击"我的权限" → 浏览功能权限/数据权限/角色 tab → 确认缺少的目标权限 |
| **触点** | 功能拦截提示、个人中心、"我的权限"页面（三 tab）、空状态占位图 |
| **用户心声** | "这个功能我点不了，是我没权限吗？缺的那个能不能自己申请？" |
| **信心度** | 高 |
| **信心依据** | UXB §5 功能范围定义了"我的权限查询"的输入、处理和输出 |
| **痛点** | ① 权限列表展示后台名称，员工看不懂对应什么功能 ② 功能权限 tab 同时展示全员应用和管理类应用，信息密度高 ③ 空状态只有"您没有功能权限"，没有引导去申请 ④ 入口位置在"我的企业"下方，可发现性偏弱 |
| **流失风险** | 中 — 看不懂权限列表或没找到入口时可能放弃自助，转回找超管 |
| **设计机会** | ① 用业务语言描述权限而非后台权限名 ② 空状态和权限列表底部提供"申请权限"入口 ③ 在功能拦截处直接给出去申请的快捷链接 |

---

## 阶段三：发起并提交申请

| 字段 | 内容 |
|------|------|
| **目标** | 正确选择申请内容，填写申请原因并成功提交 |
| **行动** | 点击"申请权限" → 根据超管配置的模式看到可申请角色列表或功能权限树 → 勾选目标项 → 填写申请原因（必填，最多500字） → 提交 → 通过校验 → 申请记录新增"审批中" |
| **触点** | "申请权限"按钮、申请抽屉（角色列表/功能权限树、原因输入框）、提交按钮、校验错误提示 |
| **用户心声** | "我要这个权限，希望能批下来。申请原因怎么写才能让审批人痛快批准？" |
| **信心度** | 高 |
| **信心依据** | UXB §5 功能范围定义了"权限申请"的输入、校验、处理和输出 |
| **痛点** | ① 员工看到的申请内容取决于超管配置的模式，如果与预期不符增加困惑 ② 申请原因自由文本无填写指引 ③ 专项校验（资金用户、子管理员模式、实名）可能在提交时才暴露 ④ 提交后无法撤回编辑 |
| **流失风险** | 中 — 反复校验失败或看不懂错误提示时可能放弃；申请原因写不满不敢提交 |
| **设计机会** | ① 申请原因提供结构化填写引导 ② 校验失败时给出可操作的解决方案而非错误码 ③ 专项校验前置到选择时即时提示 |

---

## 阶段四：等待审批结果

| 字段 | 内容 |
|------|------|
| **目标** | 了解申请进展，等待审批人做出决定 |
| **行动** | 提交后查看申请记录 → 确认进入"审批中"状态 → 等待审批结果通知 → 如等待时间过长，再次查看状态 → 如改变主意可撤销申请 |
| **触点** | 申请记录列表（筛选、状态标签、撤销按钮）、消息/通知 |
| **用户心声** | "批了没有？卡在谁那里了？还要等多久？" |
| **信心度** | 中 |
| **信心依据** | UXB §6 状态流转定义了从"审批中"到"已通过/已拒绝/已撤销"的状态闭环；审批人预设和通知渠道为 open_question |
| **痛点** | ① 员工不知道审批人是谁，无法预估等待时间 ② 没有催办机制，只能被动等待 ③ "已通过"和"已生效"前后分离，员工以为通过就能用了，实际上权限还未生效 ④ 撤销的时间限制不明确 |
| **流失风险** | 高 — 长时间无响应时员工可能转向超管线下处理，自助流程被架空 |
| **设计机会** | ① 展示审批人信息和审批进度 ② 长时间未审批提供催办或升级机制 ③ 清晰区分"已通过"和"已生效"两个状态 |

---

## 阶段五：处理审批结果

| 字段 | 内容 |
|------|------|
| **目标** | 审批通过后正常使用新权限，或被拒绝后了解原因并决定下一步 |
| **行动** | 通过：收到通知 → 权限生效 → 回到功能入口使用。拒绝：收到通知 → 查看拒绝原因 → 决定是否重新申请或联系管理员 |
| **触点** | 消息/通知、申请记录列表、我的权限页面、功能入口 |
| **用户心声** | 通过："终于可以用了。" 拒绝："为什么没批？接下来怎么办？" |
| **信心度** | 中 |
| **信心依据** | UXB §5 功能范围定义了申请结果输出；§7 承接要求明确了拒绝归因和生效状态覆盖 |
| **痛点** | ① 拒绝原因不明确时不知道如何改进 ② 自动分配权限失败时员工以为审批通过就完事了，实际还没权限 ③ 被拒绝后重新申请需重复填写全部内容 ④ 通过后权限未即时生效，存在空窗期 |
| **流失风险** | 中 — 拒绝后原因不清晰时可能放弃自助转向找超管 |
| **设计机会** | ① 拒绝原因结构化展示（具体哪个条件不满足） ② 自动分配失败时主动通知并告知处理进展 ③ 被拒后提供"修改后重新申请"的一键复用能力 ④ 通过后引导到对应功能入口 |

---

## 阶段转折

| 从 | 到 | 触发条件 | 风险 |
|----|----|---------|------|
| 阶段一 → 阶段二 | 员工发现入口并浏览权限 | 入口不显眼，员工不知道可用 |
| 阶段二 → 阶段三 | 员工点击"申请权限" | 看不懂权限列表→放弃自助 |
| 阶段三 → 阶段四 | 申请提交成功 | 校验失败反复卡住→放弃 |
| 阶段四 → 阶段五 | 收到审批结果通知 | 等待过久→转线下找超管 |

## 缺口说明

| 缺口 | 影响 | 所需输入 |
|------|------|----------|
| 审批人缺失时的降级方案未确认 | 影响阶段四审批流转可靠性 | 产品确认 |
| 通知渠道未明确 | 影响所有阶段的通知触点设计 | 产品确认 |
| "默认复核人员"风险未展开 | 影响审批人环节的流程设计 | 产品确认 |
