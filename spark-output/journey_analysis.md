# 旅程分析：员工自助申请权限

- 运行模式：prd-standalone
- 是否使用补问：否
- 数据来源：需求文档_员工自助申请权限.md
- 结果等级：完整旅程

---

## 角色摘要

### 主角色：员工

员工是权限申请旅程的主要执行者，核心目标是以自助方式获得工作中所需的系统权限，减少对管理员或超级管理员的线下依赖。

**角色边界说明**：管理员配置（开启/关闭能力、设置可申请范围）和审批人审核是本旅程的外部依赖条件，不属于员工可控制的环节。本旅程假设管理员已完成基础配置。

---

## 阶段正文

---

### 阶段一：发现权限缺口

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工在执行工作任务时意识到自己缺少某项权限，并确认需要通过申请获取 |
| **用户行动** | ① 在工作中遇到需要特定权限才能操作的功能或数据 → ② 尝试操作失败或被拦截 → ③ 确认当前账号缺少该权限 → ④ 决定走申请流程 |
| **关键触点** | 业务功能页面（权限不足提示）、同事/主管（口头指引）、权限状态说明 |
| **用户心声** | "这个功能我点不了，是不是没给我开权限？" |
| **信心度** | 中 |
| **信心度理由** | 通用场景推导，文档未展开具体触发场景和权限不足时的交互表现 |
| **痛点** | ① 权限不足提示可能不明确，员工不清楚具体缺什么权限 ② 不确定该权限是否能通过自助方式申请 ③ 习惯性走线下找管理员的路径依赖 |
| **流失风险** | 员工可能直接放弃、转向线下找管理员，绕过自助申请通道 |
| **机会** | 在权限不足时直接提供"申请权限"的快捷入口；在员工常访问的功能入口处提示当前权限状态 |

---

### 阶段二：探索可申请范围

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工找到自助申请入口，了解自己能申请哪些权限及申请规则 |
| **用户行动** | ① 进入自助申请权限页面/模块 → ② 浏览可申请的权限目录（按角色或功能分类） → ③ 对照自己需要的权限进行匹配 → ④ 了解申请条件和审批规则 |
| **关键触点** | 自助权限申请页面、权限目录/列表、申请规则说明 |
| **用户心声** | "原来可以自己申请，看看哪些我能申请" |
| **信心度** | 中 |
| **信心度理由** | 文档描述"员工查看权限"场景但未展开页面结构和信息展示方式，目录呈现方式需进一步设计 |
| **痛点** | ① 权限目录可能过于复杂，员工难以定位自己需要的权限 ② 权限名称和描述偏技术化，非技术人员看不懂 ③ 可申请范围与员工实际需要的范围可能存在偏差 |
| **流失风险** | 目录太复杂或难以理解 → 员工放弃自助、转线下 |
| **机会** | 提供搜索和分类筛选；用业务场景语言描述权限，而非纯技术名称；根据员工岗位推荐常用权限 |

---

### 阶段三：发起权限申请

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工选定需要的权限，填写申请信息并成功提交申请 |
| **用户行动** | ① 选择目标权限 → ② 填写申请原因/说明 → ③ 确认申请信息 → ④ 提交申请 → ⑤ 收到提交成功反馈 |
| **关键触点** | 申请表单、权限选择器、原因输入框、提交确认/反馈 |
| **用户心声** | "希望申请能快点批下来" |
| **信心度** | 中 |
| **信心度理由** | 文档给出场景描述但缺少表单字段细节、校验规则、提交后反馈形式等具体说明 |
| **痛点** | ① 不确定申请原因要写多详细 ② 选错权限范围导致被拒或授权不当 ③ 不清楚提交后多久会有结果 ④ 缺少草稿或暂存功能 |
| **流失风险** | 表单填写成本高 → 放弃提交；担心选错带来后续麻烦 → 犹豫不提交 |
| **机会** | 提供申请原因模板/示例；提交后给出明确的时效预期；支持暂存草稿 |

---

### 阶段四：等待审批处理

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工了解申请进度，等待审批人做出决定 |
| **用户行动** | ① 收到申请已提交的确认 → ② 等待审批结果（查看申请记录/状态） → ③ 如长时间未处理，可能线下跟进审批人 |
| **关键触点** | 申请记录/进度页、审批状态标签、系统通知（待审批、已审批）、审批人（线下沟通） |
| **用户心声** | "怎么还没批？审批人是不是没看到？" |
| **信心度** | 中 |
| **信心度理由** | 文档描述了"查看审批状态"的需求但未展开进度展示方式和通知策略 |
| **痛点** | ① 不知道审批进展到哪一步 ② 审批人长时间不处理，员工没有催办方式 ③ 申请被拒时原因可能不充分 |
| **流失风险** | 审批等待过长 → 员工转线下绕过系统 → 自助申请的可信度和使用意愿下降 |
| **机会** | 提供审批进度可视化；支持审批超时自动提醒审批人；被拒时要求填写具体原因 |

---

### 阶段五：获取授权结果

| 字段 | 内容 |
|------|------|
| **阶段目标** | 员工收到审批结果，授权通过后能正常使用权限，或被拒后了解原因及后续行动 |
| **用户行动** | ① 收到审批结果通知 → ②（通过）查看已获得的权限 → ③（通过）回到业务功能验证权限已生效 → ④（被拒）查看拒绝原因 → ⑤（被拒）决定是否重新申请或寻求其他途径 |
| **关键触点** | 结果通知（系统）、权限状态展示、业务功能页面（权限验证） |
| **用户心声** | "批下来了，现在可以用了" / "为什么被拒了？还能再申请吗？" |
| **信心度** | 中 |
| **信心度理由** | 文档描述了自动授权但未展开被拒后的引导和重试机制 |
| **痛点** | ① 被拒后不清楚还能不能再申请 ② 被拒原因笼统，无法针对性改进 ③ 授权生效时间不确定 |
| **流失风险** | 被拒后无明确指引 → 员工放弃自助渠道、不再信任该能力 |
| **机会** | 被拒后提供重新申请的快捷入口；给出被拒原因和改进建议；明确授权生效时效 |

---

## 阶段转折说明

| 阶段 | 转折条件 |
|------|----------|
| 发现权限缺口 → 探索可申请范围 | 员工确认自己缺少权限，决定通过自助渠道解决 |
| 探索可申请范围 → 发起权限申请 | 员工在可申请目录中找到匹配的权限选项 |
| 发起权限申请 → 等待审批处理 | 员工成功提交申请，系统确认受理 |
| 等待审批处理 → 获取授权结果 | 审批人做出同意或拒绝的审批决定 |
| 获取授权结果 → （可选）重新发起申请 | 被拒后员工选择重新发起申请补充说明 |
