# 用户旅程分析：子管理员复制

- **运行模式**：uxb-chain
- **是否使用补问**：否
- **数据来源**：UXB 定案（spark-output/context/uxb.json、spark-output/uxb_output.md）
- **结果等级**：完整旅程

---

## 角色摘要

**主角色：权限管理员**

负责维护子管理员及其可授权范围。本次旅程聚焦权限管理员执行「复制」操作的完整过程——从定位复制来源到最终确认复制生效。

---

## 阶段一：定位配置蓝本

**目标**：在子管理员列表中，找到配置最完整或最接近所需场景的子管理员作为复制蓝本。

| 维度 | 内容 |
|------|------|
| **动作** | 进入子管理员列表页 → 通过姓名、手机号、部门筛选检索目标 → 浏览列表中可授权组织和可授权功能概览，判断哪个来源最合适 |
| **触点** | 子管理员列表页（筛选区、数据表格区、可授权范围概览列） |
| **用户心声** | 「得找个权限配得最全的当模板，省得到时候还得逐个补。」 |
| **置信度** | 高 |
| **置信理由** | UXB 明确复制入口只在子管理员列表中；来源子管理员是复制的前置条件 |
| **痛点** | 如果多个子管理员配置不同，需要人工判断哪个最适合做蓝本——但这是已有操作，非复制新增 |
| **流失风险** | **低**。定位来源是管理员在列表中的日常操作 |

**机会**：如果列表中的可授权组织/功能概览信息不够直观，改进后也能间接提升复制效率。

---

## 阶段二：选定复制内容

**目标**：确定要复制的信息范围。

| 维度 | 内容 |
|------|------|
| **动作** | 点击操作列「复制」按钮 → 在弹窗中查看默认全选的复制选项 → 根据需要勾选或取消：可授权组织、可授权功能 → 确认至少选择了一项 |
| **触点** | 操作列「复制」按钮、复制弹窗（复制信息区复选框） |
| **用户心声** | 「组织和功能都勾上，省得漏。要是只想复制组织就把功能取消。」 |
| **置信度** | 高 |
| **置信理由** | UXB 已明确默认全选、至少选一项的规则 |
| **痛点** | 几乎没有——这是一个清晰的复选操作，默认值安全合理 |
| **流失风险** | **低**。勾选工作简单直接 |

**机会**：无显著改进点。

---

## 阶段三：确定复制目标

**目标**：挑选需要接收权限的用户。

| 维度 | 内容 |
|------|------|
| **动作** | 点击复制对象选择器 → 在员工选择弹窗中按姓名、手机号、部门查找用户 → 选中目标用户 → 确认已选用户在弹窗中显示 → 检查选中用户数量（最多 200 名） |
| **触点** | 复制弹窗（复制对象选择器）、员工选择弹窗 |
| **用户心声** | 「把新来的几个子管理员都选上，一次性搞定。」 |
| **置信度** | 高 |
| **置信理由** | UXB 明确员工选择弹窗与添加子管理员弹窗一致，支持多选，最多 200 名 |
| **痛点** | **已识别**：列表中混合了普通用户和已有子管理员，但弹窗中未标注其当前身份。用户可能未预期到有些人会成为子管理员、有些人会叠加权限——差异要到确认后才知道。 |
| **流失风险** | **中**。如果要选择的目标用户较多（如几十上百人），连续搜索添加容易产生疲劳。 |

**机会**：
- 目标列表中在用户名称旁标注「当前身份」（普通用户/子管理员），用户确认前就能了解规则差异
- 对于高频场景，可支持从组织树批量选择

---

## 阶段四：确认并提交复制

**目标**：完成最后确认，通过校验后执行复制。

| 维度 | 内容 |
|------|------|
| **动作** | 点击弹窗「确认」按钮 → 系统执行四项顺序校验（复制信息→复制对象→加入状态→认证状态） → 校验通过后执行复制 → 查看系统反馈 |
| **触点** | 复制弹窗（确认按钮）、校验错误提示、Toast 提示 |
| **用户心声** | 「确认没问题，提交。」 |
| **置信度** | 高 |
| **置信理由** | UXB 明确了校验顺序、失败处理和各场景下的反馈文案 |
| **痛点** | **已识别**：批量 200 人中部分校验不通过时，「全部退回还是通过部分」尚未明确；用户确认前没有被告知哪些目标会「成为」子管理员、哪些会「叠加」权限——差异在确认后才知道，可能超出预期 |
| **流失风险** | **中**。如果校验反复不通过（如选到未认证用户），来回修正的过程拉长后可能中断操作 |

**机会**：
- 确认前增加一条轻提示，汇总目标用户身份分布：「N 名用户将成为子管理员，M 名已有子管理员将叠加权限」
- 部分校验不通过的策略明确后，体验设计方案才能闭合

---

## 阶段五：跟进生效结果

**目标**：确认复制结果，确保权限按预期生效。

| 维度 | 内容 |
|------|------|
| **动作** | **非互审**：收到 Toast「复制成功」→ 查看操作记录确认详情 → 回到子管理员列表确认生效。**互审**：收到 Toast「已提交审批」→ 等待另一位管理员审批 → 审批通过后权限自动写入 → 到列表确认 |
| **触点** | Toast、操作记录、子管理员列表、审批系统 |
| **用户心声** | 非互审：「好了，一次搞定。」互审：「提交了，等另一位确认。」久久没动静时：「那边批了没有？是不是得去提醒一下？」 |
| **置信度** | 中 |
| **置信理由** | UXB 确认了两种模式的机制差异，但「审批中不可见」的具体体验影响需要实际设计才能验证 |
| **痛点** | **已识别**：非互审下 Toast 消失后缺少可回顾的复制结果详情；互审下审批状态在子管理员列表中不可见，需离开页面去审批系统查询；操作记录按组织和功能分条存储，追溯一次完整复制需要手动关联两条记录 |
| **流失风险** | **中高**。互审模式下审批流程不透明会带来两个后果：(1) 管理员不确定审批进度，可能重复操作；(2) 审批通过后没有主动通知，管理员可能以为还没生效 |

**机会**：
- 复制完成后给结果汇总（非互审：谁成功/谁失败；互审：已提交、待谁审批），而非只有一句话
- 审批状态在子管理员相关页面的可见性——在来源子管理员或目标用户上标注「复制审批中」
- 操作记录聚合展示：同一复制操作的两条记录默认合并为一条

## 阶段转折

| 从 | 到 | 触发条件 | 风险 |
|----|----|---------|------|
| 定位配置蓝本 | 选定复制内容 | 点击操作列「复制」按钮 | — |
| 选定复制内容 | 确定复制目标 | 完成复制内容勾选 | — |
| 确定复制目标 | 确认并提交复制 | 确认目标选择完毕 | 用户未意识到混合身份（普通/已有子管理员）的处理差异 |
| 确认并提交复制 | 跟进生效结果 | 复制执行成功 | 非互审→低；互审→审批状态不透明，用户可能重复操作或误以为已生效 |
