# 用户故事：员工自助申请权限

## 1. 来源与方向

- **来源**：UXB 需求定案（`spark-output/uxb_output.md`）
- **深化输入**：体验蓝图（`spark-output/experience_blueprint.md`）和页面规格（`spark-output/page_spec.md`）
- **方向**：员工自助发现缺权限 → 提交申请 → 审批通过后自动获得权限
- **主角色**：普通员工、超级管理员、审批人
- **核心约束**：只有超管可开启/关闭；开启前必须配置范围和审批流程；关闭时不能影响进行中申请；复用现有审批引擎和授权接口

## 3. Story 详情

### S1. 查看自有权限

- **Persona**：普通员工
- **场景**：员工想知道自己当前拥有哪些功能和数据权限，或确认某个功能是否已有权限
- **目标**：快速了解自己的权限全貌，知道每项权限的用途和来源
- **优先级**：P0
- **来源依据**：UXB §5 功能单元"查看自有权限"

**用户要完成什么**

作为普通员工，我想在一个地方集中查看我当前拥有的所有权限，看到每项权限的名称、用途和来源，从而不用向管理员反复确认"我有没有 XX 权限"。

**完成标准**

- 员工可以进入"我的权限"页面
- 页面展示员工当前有效权限列表，按业务域分组
- 每条权限项显示权限名称、用途说明、来源标签（自助申请/角色继承/系统授予）
- 员工可以通过搜索框按名称筛选权限
- 员工可以通过业务域筛选器切换查看不同域的权限
- 加载失败时展示错误提示和重试入口
- 员工无权限时展示空状态引导

**设计触点**

- 涉及页面/场景：我的权限 Page
- 涉及组件类型：Page、Input、Select、ListGroup、Tag、EmptyState、LoadingState
- 涉及状态：加载态、空状态、失败态、正常展示态
- 涉及交互模式：列表浏览、关键词搜索、下拉筛选

**风险或待验证点**

- 权限来源信息的标准化程度影响来源标签的展示准确性
- 如果权限缺乏用途说明，列表的可读性会大幅下降

### S2. 提交权限申请

- **Persona**：普通员工
- **场景**：员工在使用某个功能时发现缺少权限，或提前知道自己需要某项权限，发起自助申请
- **目标**：选择需要的权限，填写原因，成功提交申请
- **优先级**：P0
- **来源依据**：UXB §5 功能单元"提交权限申请"、蓝图 §3 主流程节点 1-4

**用户要完成什么**

作为普通员工，当我在功能受限页面或权限中心发现缺少某项权限时，我想直接从当前页面发起权限申请、选择我要的权限、说明原因并提交，从而不用线下联系管理员。

**完成标准**

- 员工可以从"我的权限"页面点击[申请权限]打开申请 Drawer
- 员工可以从功能受限页面的提示入口点击进入申请流程
- Drawer 中按业务域分类展示可申请的权限列表
- 员工可以通过关键词搜索定位目标权限
- 员工选择权限后，该权限附带用途说明
- 员工必须填写申请原因，提供示例引导
- 提交前校验：权限在可申请范围内、审批流程有效
- 提交成功：Drawer 关闭、Toast 提示、申请记录新增"待审批"记录
- 校验失败时就地提示（InlineError 或 Toast），不关闭 Drawer

**设计触点**

- 涉及页面/场景：功能受限页面、我的权限 Page、权限申请 Drawer
- 涉及组件类型：Drawer、Tabs、Input、Select、CheckboxGroup、Textarea、InlineError、Toast、Button
- 涉及状态：初始态、搜索态、选中态、校验失败态、提交成功态
- 涉及交互模式：分类浏览、关键词搜索、多选、表单填写、就地校验、提交反馈

**风险或待验证点**

- 功能受限页面是否支持嵌入"申请权限"入口，影响现场触发的可行性
- 权限的业务域分类是否标准化，影响分类 Tab 的设计

### S3. 审批权限申请

- **Persona**：审批人
- **场景**：审批人收到权限申请通知，需要判断是否批准该员工获得指定权限
- **目标**：获取充分的判断依据，做出批准或拒绝的决定
- **优先级**：P0
- **来源依据**：UXB §5 功能单元"审批处理"、蓝图 §3 节点 6

**用户要完成什么**

作为审批人，当我收到权限申请时，我想看到申请人申请的权限信息、申请原因以及申请人当前的权限现状，从而做出合理的批准或拒绝决定。

**完成标准**

- 审批人收到权限申请的审批通知（应用内/消息）
- 审批卡片/页面展示申请权限的名称、用途说明
- 审批卡片展示申请人的申请原因
- 审批卡片展示申请人当前已有的相关权限摘要
- 审批人可以选择"通过"或"拒绝"
- 拒绝时需要填写拒绝原因
- 审批通过后系统自动执行授权
- 授权失败时通知审批人和申请人，提供手动处理入口

**设计触点**

- 涉及页面/场景：审批卡片/审批详情（复用现有审批流程）
- 涉及组件类型：Card、Tag、Button、Textarea、Toast
- 涉及状态：待审批态、已通过态、已拒绝态、授权异常态
- 涉及交互模式：查看上下文、做出决策（通过/拒绝）、填写拒绝原因

**风险或待验证点**

- 审批端是否支持定制化审批卡片内容，影响申请人权限现状的展示方式
- 自动授权接口的可用性和可靠性会影响审批通过后的生效体验

### S4. 跟踪申请进度

- **Persona**：普通员工
- **场景**：员工提交权限申请后，想了解审批进展到了哪一步、审批人是谁、预计还要多久
- **目标**：随时掌握申请的审批状态，了解卡在哪个节点
- **优先级**：P0
- **来源依据**：UXB §6 状态定义、蓝图 §3 节点 5、蓝图 §6.3

**用户要完成什么**

作为普通员工，在我提交权限申请后，我想查看我的申请清单和每条申请的当前状态、审批人和处理时间，从而不用重复询问管理员"批了没有"。

**完成标准**

- 员工可以进入"申请记录"页面查看所有历史申请
- 列表按时间倒序展示，卡片形式呈现
- 每条申请显示：权限名称、提交时间、当前状态（带标签）、审批人姓名
- 进行中的申请显示已等待时长
- 员工可以按"全部/进行中/已完成"筛选申请
- 员工点击"查看详情"可以查看申请的完整信息和审批流转路径
- 状态变更时主动推送通知
- 无申请记录时展示空状态引导
- 加载失败时展示错误提示和重试入口

**设计触点**

- 涉及页面/场景：申请记录 Page、申请详情 Modal
- 涉及组件类型：Page、Tabs、List、Card、Tag、Modal、TextLink、Button、EmptyState、LoadingState
- 涉及状态：待审批、审批中、已通过、已拒绝、已撤回、已失效、授权异常
- 涉及交互模式：列表浏览、Tab 切换、点击查看详情、状态变更推送

**风险或待验证点**

- 审批流转信息的获取依赖于审批引擎的开放数据

### S5. 开启并配置自助申请

- **Persona**：超级管理员
- **场景**：超管决定开放员工自助申请权限能力，需要先完成初始配置
- **目标**：开启能力、设定可申请范围、绑定审批流程
- **优先级**：P1
- **来源依据**：UXB §4 推荐业务边界、蓝图 §4.1 次流程、蓝图 §6.5

**用户要完成什么**

作为超级管理员，我想开启"员工自助申请权限"能力，设定员工可以申请哪些权限，并关联审批流程，从而让员工能通过自助渠道申请权限，同时保证安全可控。

**完成标准**

- 超管可以从管理后台进入"自助申请配置"页面
- 页面提供开关用于开启/关闭该能力
- 开启前必须配置可申请范围和审批流程
- 可申请范围支持按业务域批量勾选，也可选择"全部权限"
- 审批流程从已有审批流程中选择
- 范围为空或流程未选时，保存操作被阻止并提示
- 保存成功后 Toast 提示，配置立即生效
- 开关关闭时范围和流程配置区置灰不可编辑
- 配置页提供引导说明，帮助超管理解各配置项的含义

**设计触点**

- 涉及页面/场景：自助申请配置 Page（管理端）
- 涉及组件类型：Page、Switch、Radio、CheckboxGroup、Select、Button、Toast、TextLink
- 涉及状态：开启态（可编辑）、关闭态（置灰）、校验失败态、保存成功态
- 涉及交互模式：开关切换、多选配置、下拉选择、保存校验

**风险或待验证点**

- 权限的业务域分类是否已在管理后台存在，影响范围配置的交互方式
- 如果权限分类不清晰，超管可能无法准确限定范围

### S6. 调整或关闭自助申请

- **Persona**：超级管理员
- **场景**：超管需要修改自助申请的配置，或不再需要该能力时将其关闭
- **目标**：调整配置或安全关闭能力，不影响已有申请
- **优先级**：P1
- **来源依据**：UXB §4.5、蓝图 §4.3 次流程

**用户要完成什么**

作为超级管理员，我想随时调整自助申请的配置或关闭该能力，同时确保已经提交的审批申请不受影响。

**完成标准**

- 超管可以随时修改可申请范围和审批流程并保存
- 超管可以关闭"允许员工自助申请权限"开关
- 关闭时如果存在进行中的申请，弹出确认提示窗口
- 确认提示中显示进行中的申请数量
- 超管确认关闭后，员工端新申请入口隐藏
- 已提交的申请继续正常流转至结束
- 超管取消关闭时，开关保持开启状态
- 关闭后超管可以随时重新开启

**设计触点**

- 涉及页面/场景：自助申请配置 Page（管理端）、关闭确认 Modal
- 涉及组件类型：Page、Switch、Modal、Button、Toast
- 涉及状态：开启态、关闭态、确认弹窗态、关闭成功态
- 涉及交互模式：开关关闭 → 检测进行中申请 → 确认弹窗 → 确认/取消

**风险或待验证点**

- 无（关闭保护逻辑在 UXB 中已明确确认）

### S7. 重新申请被拒权限

- **Persona**：普通员工
- **场景**：员工的权限申请被审批人拒绝，想查看原因后重新提交申请
- **目标**：了解拒绝原因，修改后重新申请或放弃
- **优先级**：P2
- **来源依据**：蓝图 §3 节点 6 结果态

**用户要完成什么**

作为普通员工，当我的权限申请被拒绝时，我想知道拒绝的原因，并在合适的时候重新提交申请，从而最终获得我需要的权限。

**完成标准**

- 被拒绝的申请在申请记录中标记为"已拒绝"状态
- 员工可以查看拒绝原因
- 被拒绝的申请卡片上提供"重新申请"按钮
- 点击"重新申请"打开权限申请 Drawer，可修改申请内容后重新提交
- 重新提交的申请作为新申请单进入审批流程

**设计触点**

- 涉及页面/场景：申请记录 Page、权限申请 Drawer
- 涉及组件类型：Card、Tag、Button、Drawer
- 涉及状态：已拒绝态、重新申请态
- 涉及交互模式：查看拒绝原因 → 重新申请 → 提交

**风险或待验证点**

- 拒绝原因是否需要审批人填写，影响 "查看原因" 的信息来源
- 重新申请时是否支持修改权限选择，需要产品确认

## 4. 不进入 Story 的内容

| 内容 | 原因 |
|------|------|
| 自动授权执行 | 系统行为，不是用户任务。作为 S3 "审批权限申请"的完成标准之一 |
| 权限来源模型改造 | 超出本次范围，UXB 明确"不改造现有权限判断链路" |
| 审批流程引擎改造 | 超出本次范围，复用现有审批引擎 |
| 催办功能 | 当前按暂不支持处理，待产品决策 |
| 操作审计日志接入 | 超出当前用户故事范围，待确认需求后补充 |
