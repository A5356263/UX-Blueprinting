# 问题框定：薪福通子管理员批量配置效率优化

## §0 关键判断

| 关键判断 | 结论 | 来源 | 状态 |
|---------|------|------|------|
| 主角色 | 超级管理员（超管） | 用户明确 | `confirmed_facts` |

## §1 输入摘要

### 用户初始描述

集团型企业使用子管理员模式下放权限管理能力。部分客户（如广西交投）存在 200+ 子管理员。所有子管理员「可授权功能」一致，但「可授权组织」不同。当前需要逐个子管理员单独勾选相同功能权限，实施工作量大。希望支持将已配置子管理员的权限信息复制给其他用户。

### 校准补充

- 操作发生在子管理配置页，是超管配置"权限的权限"
- 复制范围是完整配置（功能上限 + 组织范围），粘贴后可微调
- 场景覆盖：首次批量创建 + 后续零散新增复用
- 产品为薪福通平台权限管理模块

### 三层信息

**confirmed_facts:**
- 主角色为超级管理员
- 正式业务对象为子管理员
- 产品平台为薪福通
- 场景涉及子管理配置页，属于全局治理能力
- 所有子管理员可授权功能相同、可授权组织不同
- 当前通过逐个勾选完成配置，200+ 时工作量极大
- 复制目标为完整配置（功能 + 组织），粘贴后可微调
- 使用场景覆盖首次批量创建和后续新人加入

**working_assumptions:**
- 子管理员配置为一次配置长期使用，不涉及高频变更
- 复制后的微调主要是修改组织范围，功能权限基本不需调整
- 当前子管理配置页为列表页 + 详情/编辑页结构

**open_gaps:**
- 复制后是否涉及冲突检测（如目标用户已是子管理员）→ 影响复制交互设计但不影响方向成立
- 复制后的生效机制（即时/审批）→ 不影响主方向判断
- 超管对哪些子管理员可被复制是否有权限限制 → 不影响主方向判断

## §2 问题定义

### 核心问题

在薪福通子管理员模式下，超管为多个子管理员配置权限时，**功能权限部分高度重复（所有子管理员一致），但当前配置链路要求逐个子管理员独立完成全部选择，缺乏信息复用机制**，导致批量配置场景（200+ 级别）效率极低，实施成本高。

### 为什么重要

随着薪福通向中大型集团企业深入，子管理员数量快速增长。200+ 子管理员不是个例，而是集团型客户的典型规模。配置效率直接影响：
- 超管日常工作效率（单人重复劳动）
- 大客户实施体验（上线速度）
- 后续管理维护便利性（新人加入时的操作成本）

### 这不是什么

- 不是普通用户的功能授权问题（对象是子管理员，是"权限的权限"）
- 不是角色模板缺失问题（子管理员与普通角色的授权语义不同）
- 不是组织范围配置的批量问题（组织范围天然是差异化的）
- 不是审批流程或治理模式的问题
- 不是子管理员自身的产品能力缺失问题

## §3 目标用户与场景

### 主角色：超级管理员

| 属性 | 内容 |
|------|------|
| 角色 | 薪福通企业超级管理员 |
| 典型场景 | 配置子管理员、管理企业权限治理 |
| 当前痛点 | 重复勾选相同功能权限，操作量大、易疲劳、易出错 |
| 目标 | 快速完成大批量子管理员的权限配置 |

### 次生场景：新入职超管接手

超管人员变更时，需要理解和维护已配置的子管理员体系。如果配置过程缺乏可读性和可复用性，接手成本也会增加。

### 三层信息

**confirmed_facts:**
- 超管是唯一执行配置的人
- 场景分首次批量创建和后续零散新增

**working_assumptions:**
- 超管对产品较熟悉，不是新手
- 日常新增子管理员的频率中等（大客户月均若干人）

**open_gaps:**
- 无

## §4 当前替代做法

### 做法：逐个子管理员单独配置

1. 进入子管理配置页
2. 选择一个待配置的子管理员
3. 勾选功能权限（200+ 人一致的集合）
4. 配置组织范围
5. 保存
6. 对下一个子管理员重复 2-5

### 局限性

| 局限性 | 影响 |
|--------|------|
| 功能权限重复勾选 | 200 次 × 重复选择 ≈ 极高操作疲劳度 |
| 缺乏参照 | 每个子管理员配置都是孤立的，无法确认是否遗漏某项功能 |
| 无批量入口 | 无法一次配置后批量关联 |
| 错误风险 | 反复操作易导致功能权限不一致（有的多勾、有的少勾） |
| 新人加入成本 | 每次新增都要重新走完整流程 |

### 三层信息

**confirmed_facts:**
- 当前链路为"子管理配置页"逐个子管理员配置
- 功能权限需逐个重复勾选
- 200+ 场景下工作量极大

**working_assumptions:**
- 子管理配置页目前没有批量操作或复制入口

**open_gaps:**
- 无（替代做法已确认）

## §5 机会点

### OP1：子管理员配置复用

**用户价值：** 超管配置一次后可直接复用完整配置，消除功能权限的重复勾选。首次批量创建时，配好一个模板子管理员即可快速扩散；后续新增时也可从已配置的子管理员直接复制。  
**业务价值：** 大幅降低大客户实施配置周期，提升平台在集团型客户中的竞争力。  
**风险：** 复制后如果忘记微调组织范围，可能导致新子管理员管辖范围错误。

### OP2：功能权限与组织范围解耦

**用户价值：** 功能权限部分从子管理员配置中抽离为独立模板，变更功能权限时联动所有关联子管理员，不需要逐个修改。  
**业务价值：** 当企业使用的应用或功能点发生变化时，批量更新子管理员的可用功能更灵活。  
**风险：** 引入模板概念增加学习成本和数据结构复杂度的提升，对中小企业可能过度设计。

### OP3：批量创建向导

**用户价值：** 一次输入公共信息（功能权限），然后批量关联人员和组织范围，类似"先填表头、再填行"的体验。  
**业务价值：** 适合超大批量首次创建的极速配置场景。  
**风险：** 向导流程对经验丰富的超管可能反而降速（非批量场景也要走流程）；不能覆盖后续零星新增场景。

### OP4：配置差异可视化

**用户价值：** 在列表层直接展示各子管理员的权限概览，快速识别谁配了什么、谁和谁一样、谁的配置有差异。  
**业务价值：** 提升配置可管理性，降低排查和维护成本。  
**风险：** 单独使用不能解决重复勾选问题，只能作为辅助。

## §6 候选方向

### 方向 A：子管理员配置复制（推荐）

**解决的问题：** 超管配好一个子管理员后，可将完整配置（功能上限 + 组织范围）复制给目标用户，目标用户获得的配置与来源完全一致，超管再根据实际需要微调组织范围。

**用户价值：**
- 消除功能权限重复勾选
- 操作路径从"逐个完整配置"变为"一次配置 → N 次复制 → 逐人微调"
- 同时覆盖首次批量创建和后续新增两种场景

**风险：**
- 微调组织范围是必须的人工步骤，不能省略
- 复制后来源变更不会同步到副本（单向复制，非模板绑定）

**成立前提：**
- 子管理员配置页现有数据模型支持复制一份完整配置
- 目标用户的同名同结构配置可以覆盖写入

### 方向 B：功能权限模板化

**解决的问题：** 将可授权功能提取为独立模板，超管先定义模板，配置子管理员时引用模板。模板更新时联动所有引用的子管理员。

**用户价值：**
- 一次维护模板，多处自动生效
- 功能权限变更时不需要逐个修改子管理员

**风险：**
- 引入"模板"作为新业务对象，数据结构复杂度增加
- 子管理员的功能权限来源多了一层（模板 + 个人补充），解释成本高
- 模板变更的自动联动如果不受控可能造成非预期影响

**成立前提：**
- 产品愿意引入模板化抽象
- 子管理员功能权限变更场景确实高频到值得模板化

### 方向 C：批量创建向导

**解决的问题：** 针对首次批量创建 200+ 子管理员的极速配置场景，提供向导式批量创建流程。

**用户价值：**
- 首次创建的效率最高（一步配置多人）
- 流程引导清晰，减少遗漏

**风险：**
- 对日常零星新增场景不友好（每次都要走向导）
- 与现有配置页结构差异大，学习成本高
- 适用场景单一（仅首次批量）

**成立前提：**
- 批量创建是压倒性的主要使用场景（超过日常零星新增）

## §7 推荐方向与承接要求

### 推荐方向：方向 A — 子管理员配置复制

以"复制已有子管理员配置"为核心操作模式，在子管理配置页增加复制能力。超管首次手工配置好一个"基准"子管理员后，后续子管理员通过复制来源获得完整配置，再微调组织范围即可完成。

#### 推荐理由

- 与用户原始诉求一致（用户明确说了"复制"）
- 操作模型简单直观（复制 → 粘贴 → 微调），几乎不需要学习成本
- 同时覆盖首次批量创建和日常新增两个场景
- 不改变现有数据结构和业务语义（不引入新对象如模板）
- 低风险、对现有系统侵入小

#### 体验侧关注点

1. **复制源的选定**：超管怎么选择一个已配置的子管理员作为来源
2. **目标用户的选择**：支持一次复制到单个还是多个目标
3. **复制后的确认**：目标子管理员的原有配置被覆盖时的提示与确认
4. **微调路径**：复制后如何快速进入微调（尤其是组织范围修改）
5. **差异可视化**：能否在列表层面展示哪些子管理员从哪个来源复制

#### 承接契约（下游不可重判的边界）

| 承接项 | 要求 | 原因 |
|--------|------|------|
| 业务边界 | 复制操作发生在子管理配置页，属于全局治理能力，不改变子管理员业务对象定义 | 防止把复制能力泛化到其他权限配置场景 |
| 状态边界 | 子管理员模式与双管理员模式互斥的约束保持不变 | 避免复制操作绕过治理约束 |
| 角色责任 | 只有超管可执行子管理员配置操作和复制操作，子管理员不可 | 不改变角色权力边界 |
| 复制语义 | 复制为一次性快照；来源后续变更不影响已复制的子管理员 | 防止复制退化为隐式模板绑定 |
| 范围隔离 | 复制完成后目标子管理员仍受其组织范围和应用管辖范围约束 | 不因复制操作突破范围隔离约束 |

#### 下游必须继续展开的判断面

| 判断面 | 说明 |
|--------|------|
| 复制交互流程 | 选择来源 → 选择目标 → 确认覆盖 → 进入微调的具体交互路径 |
| 批量粒度 | 一次复制到单个目标还是支持选择多个目标 |
| 覆盖检测 | 目标已存在配置时的数据覆盖策略（全量覆盖 / 合并 / 提示保留） |
| 组织范围微调 | 复制后组织范围的快速修改路径 |

## §8 约束与不做什么

### 约束

- 子管理员模式与双管理员模式互斥，不可同时启用
- 子管理员只能在其组织管辖范围内操作，不因复制突破
- 子管理员配置的是"权限的权限"，不是业务权限本身
- 薪福通平台采用一年一个大版本迭代节奏

### 不做什么

- 不做角色模板化改造（未来可按需进化）
- 不做子管理员配置审批流程的调整（方向 A 不涉及审批改造）
- 不做组织范围批量配置（方向 A 保留逐人微调，组织范围不是复用对象）
- 不做权限查询或审计功能的变更
- 不做子管理员自身产品能力的增强
