## §1 输入摘要

用户描述的场景为企业数字化平台中权限模块的员工自助能力缺口。当前权限分配依赖管理员或超级管理员集中处理，中大型企业员工数量多、流动频繁，导致以下问题：

- 新增、变更、核对权限的工作量大
- 员工需要权限时需私下找老板或管理员，沟通成本高
- 授权时效不稳定，影响业务开展效率

希望通过支持员工自助查看和申请权限，将部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对申请范围和审批流程的控制。

通过知识库锚定，明确了该产品为成熟的企业数字化平台，权限管理域已有完善的业务对象定义（主体、资源、动作、范围、来源、治理因子）、能力地图（用户直授、角色授权、全局治理、查询排障等）和相邻域边界（组织域、应用域、审批域、协作域）。

## §2 问题定义

**核心矛盾：** 企业权限配置权集中在管理员侧，员工获取权限需经过"发现需求→找到管理员→沟通申请→等待处理"的长链路。随着企业规模扩大，链路的沟通成本和时效不稳定非线性增长，最终同时损害员工体验（不可预期、等待时间长）和管理侧效率（被打断、重复性工作多）。

**关键变量：**
- 企业规模越大，人员流动性越高，该问题越严重
- 当前"私下找人"的模式无法规模化管理
- 解决方案需要在"自助化"和"控制权"之间取得平衡

## §3 目标用户与场景

### 主要角色

| 角色 | 描述 | 核心诉求 |
|------|------|----------|
| 员工（业务人员/经办人员） | 需要被授予功能权限或加入角色的业务执行者 | 可预期地获取权限、减少沟通等待、知道能申请什么 |
| 上级组织负责人（审批人） | 员工的直属或组织上级，审批权限申请 | 快速判断申请的合理性、不被重复性审批淹没 |
| 权限管理员/超级管理员 | 负责权限策略配置和治理的管理者 | 控制可申请范围、排除敏感权限、可审计可追溯 |

### 典型场景

**场景A：新员工入职权限获取**
新员工加入团队后，需要获取一组业务功能权限。当前流程是上级或管理员逐项配置；目标流程是上级可指引员工自助申请标准权限集（角色），审批→自动生效。

**场景B：业务变更需新增权限**
员工因职责调整需要某项功能权限，当前需打听找谁申请；目标流程是员工在权限目录中查看并提交申请，自动流转到上级审批。

**场景C：角色清理与回收**
员工离职或转岗后，管理员需清理权限。自助申请模式下，角色关联关系天然提供了"申请记录→生效记录→回收依据"的审计链路。

## §4 当前替代做法

| 方式 | 描述 | 成本 |
|------|------|------|
| 私下找老板/管理员 | 员工通过即时通讯或当面沟通申请，管理员手动配置 | 沟通中断、等待不确定、无记录 |
| 集中处理定期批量变更 | 管理员定期集中处理一批权限变更请求 | 时效差、容易遗漏 |
| 超级管理员直接承担 | 老板自己当管理员，亲自处理权限配置 | 占用核心管理者时间、风险高 |

所有替代做法的共同特征：
- 依赖人与人之间的非正式沟通
- 缺乏结构化的申请→审批→生效链路
- 规模扩大后成本非线性增长
- 无标准化的审计和追溯能力

## §5 机会点

### 机会1：减少咨询类沟通成本
员工可自行查看"可申请哪些权限"，无需询问管理员或查阅散落文档。在自助目录中清晰展示权限名称、所属应用、作用描述，从源头消除"我有这个权限吗""我能申请什么"类咨询。

### 机会2：预制+审批的权责分离
管理员预先定义"什么人可以申请什么"，上级审批人判断"这个人现在是否需要"，系统自动执行授权。三层角色各司其职，既不放任失控、也不集中于一人。

### 机会3：角色作为批量授权载体
员工申请加入角色以获取一组功能权限，比逐项申请功能权限更高效。管理员维护角色模板和可申请标记，一次配置覆盖批量场景。

### 机会4：自动生效缩短等待
审批通过即自动执行授权，消除"审批通过→等待管理员手动配置"的空窗期，将授权时效从"天级"缩短到"分钟级"。

### 机会5：审计链路闭环
自助申请天然产生完整的申请记录、审批记录和授权记录，为后续的权限审计、合规检查和权限回收提供完整证据链。

## §6 候选方向

### 方向A：基于申请目录的自助授权（推荐）

**解决的问题：** 员工获取权限需要经过非正式沟通链条，周期不可控。

**基本逻辑：**
- 管理员在后台预制可申请的功能权限清单和角色清单（排除敏感权限）
- 员工在前端可浏览全部角色，对标记为"可自助申请"的角色和功能权限发起申请
- 申请自动流转至员工的上级组织负责人审批
- 审批通过后系统自动执行授权，员工即时获得权限

**目标用户价值：**
- 员工：从"找人"变为"自助提交→等审批→自动获得"，链路清晰可预期
- 管理员：从"执行者"变为"策略定义者"，减少被打断
- 审批人：在上下文（员工申请了什么、为什么需要）中做判断，而非空白审批

**主要风险：**
- 审批人准确率风险：上级可能不了解某项权限的具体含义或风险等级
- 自动生效执行可靠性：需与现有授权执行链路对接，失败必须可感知可回滚
- 申请目录维护成本：管理员需持续维护可申请清单与敏感权限标记

**成立前提：**
- 组织架构中"上级负责人"关系链路已就绪（组织域支持）
- 平台已有授权执行链路可被审批通过事件触发（或可扩展）
- 审批流引擎已存在或可接入

### 方向B：申请工单式审批台

**解决的问题：** 员工端需要统一的权限申请入口来替代非正式沟通。

**基本逻辑：**
- 员工提交权限申请工单，可混合选择功能权限和角色
- 工单进入统一审批池，管理员或上级均可处理
- 审批通过后通知管理员手动执行或触发自动执行

**与方向A的区别：**
- 审批人可能是管理员或上级，不限定为上级负责人
- 保留人工执行环节或半自动
- 更接近"把线下沟通搬到线上"的思路

**风险：**
- 未解决"时效不稳定"问题（若保留人工执行环节）
- 审批人身份模糊可能导致推诿或延迟
- 工单模式体验较重

### 方向C：角色驱动自助授权（方向的轻量变体）

**解决的问题：** 功能权限粒度过细，逐项申请管理成本高。

**基本逻辑：**
- 员工仅能申请加入角色，通过角色获得关联的功能权限
- 不再支持单独申请功能权限
- 管理员维护角色模板和可申请标记

**风险：**
- 功能权限单独申请场景被排除，可能覆盖不足
- 需要角色体系已足够成熟和覆盖全面

## §7 推荐方向与承接要求

### 推荐方向：基于申请目录的自助授权（方向A）

理由：
- 直接命中核心矛盾（沟通成本高、时效不稳定）
- 预制目录+审批+自动生效的链路完整覆盖了"控制权交给管理员、效率还给员工"的目标
- 与现有权限能力体系的衔接成本相对可控
- 角色授权的批量效应能进一步降低管理负担

### 体验侧关注点

| 关注面 | 说明 |
|--------|------|
| 权限目录的可理解性 | 员工看到的不是技术权限码，而是业务语义的描述：谁可以用、用来做什么、申请后有何影响 |
| 透明可追踪的申请进度 | 提交后员工能清晰看到当前处于审批中/已通过/已拒绝，以及预计等待时间 |
| 审批上下文充足性 | 审批人看到的不只是"XX申请了XX权限"，还包括该权限的用途、风险提示、申请人说明 |
| 自动生效的可感知性 | 审批通过后，员工即时感知权限已生效（通知/页面刷新/引导下一步） |
| 管理员配置负担 | 可申请目录的初始搭建和持续维护成本不能过高，需支持批量设置和模板化 |

### 承接契约

**下游不得重判的业务边界：**
1. 申请范围由管理员预制，排除敏感权限——下游不得开放员工自由申请全部权限
2. 审批人为上级组织负责人——下游不得改为管理员审批或任意审批
3. 审批通过后自动生效——下游不得保留人工执行环节
4. 功能权限和角色授权为本次覆盖范围——下游默认不扩展至数据权限和协作可见性

**下游必须继续展开的判断面：**
1. 权限目录的员工端呈现方式——如何让非技术员工理解"功能权限"和"角色"的业务含义
2. 审批人在移动端的审批体验——上级负责人可能在移动场景处理审批
3. 申请进度追踪和结果通知的触达方式——站内信、消息中心、外发通知等
4. 自动授权失败时的降级处理和可感知回滚
5. 可申请角色标记的管理员配置界面——如何让管理员高效标记哪些角色可自助申请
6. 功能权限单独申请的展示粒度——是以操作点展示还是按功能分组展示

### 明确不做什么

- 不覆盖数据权限的自助申请
- 不覆盖协作可见性的自助申请
- 不做员工自由申请全部权限（必须预制范围）
- 不做管理员侧的权限申请代办（审批人限定为上级负责人）
- 不做审批通过后仍需人工执行的半自动模式

### 关键待确认前提

1. **组织负责人链路：** 平台组织域是否已定义清晰的"上级组织负责人"关系，供审批流按人路由
2. **审批流引擎：** 平台是否已有审批流引擎，或需要基于审批域的基建新增
3. **自动授权执行链路：** 审批通过事件是否能触发现有授权服务的执行接口
4. **敏感权限标记：** 权限管理域目前是否有"敏感等级"标记，或需要新增

## §8 约束与不做什么

### 约束
1. 作为已有平台新增能力，需兼容现有权限模块的架构和数据模型
2. 管理员仍为权限策略的定义者和控制者，不被绕过
3. 所有申请必须可审计、可追溯
4. 从申请到生效的全链路必须有明确的失败感知和处理机制

### 已排除范围
- 数据权限的自助申请
- 协作可见性的自助申请
- 员工自由申请全部权限（无预制范围）
- 管理员作为审批人
- 审批通过后仍需人工执行

## §9 待确认问题

| 问题 | 影响 | 优先级 |
|------|------|--------|
| 平台是否有现成的审批流引擎？ | 若没有则需同步建设审批链路，影响方案可行性和工期 | 高 |
| 组织域中"上级负责人"关系是否已定义完整？ | 审批路由的准确性依赖此数据 | 高 |
| 现有授权服务是否有可被外部触发的执行接口？ | 自动生效的技术可行性前提 | 高 |
| 权限管理域是否有"敏感等级"或类似标记？ | 影响可申请目录的筛选逻辑 | 中 |
| 员工端入口是在工作台、权限管理模块还是全局导航？ | 影响信息架构和交互设计 | 低（蓝图层展开） |
| 审批人拒绝时是否允许员工重新申请或补充说明？ | 影响异常流程设计 | 低（蓝图层展开） |
