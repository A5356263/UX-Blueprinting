# 问题框定：企业数字化产品员工权限自助申请

## §0 关键判断

| 判断类型 | 内容 |
|---|---|
| confirmed_facts | 用户已明确产品类型、主角色、目标结果、当前替代做法、核心场景入口模式 |
| working_assumptions | 审批流程为单级上级审批（由 OA 底座承接）；可申请范围由管理员后台预配置 |
| open_gaps | 审批超时/升级处理策略；申请批量组合的交互边界；申请结果的通知渠道 |

## §1 输入摘要

企业数字化产品，面向中大型企业场景：

- **主角色**：员工（申请人）、上级组织负责人（审批人）、权限管理员/超级管理员（控制面配置方）
- **当前问题**：权限新增/变更/核对完全依赖管理员或超级管理员集中处理。员工多、流动频繁时工作量巨大。部分企业超管即老板本人，员工需私下联系，沟通成本高、授权时效不稳定。
- **目标**：支持员工自助查看和申请权限（功能权限 + 角色权限包），把部分申请工作从管理侧分散到员工侧，同时保留管理侧对申请范围和审批的控制。
- **底层能力**：有 OA 底座支撑组织架构和审批流程引擎；敏感权限由系统级预置排除，不在本次设计范围内。
- **核心触发场景**：① 缺口感（访问无权限功能时引导申请）② 目标驱动型（知道要做什么事，系统引导发现所需权限）。

## §2 问题定义

**问题表述：**

在中大型企业数字化产品的使用场景中，员工权限的新增、变更和了解完全依赖管理员侧集中处理，导致：

1. **管理侧瓶颈**：人员流动频繁时，管理员被反复的权限申请沟通打断，影响核心管理效率。
2. **员工体验断层**：员工不知道"自己有什么权限"、"能申请什么权限"、"申请到哪里了"，只能私下询问。
3. **授权时效不可控**：依赖人与人之间的异步沟通，权限到位时间无保障。

**核心矛盾：权限配置的集中管控需求 vs 员工侧自主获取权限的效率需求。**

**解决思路：** 新增"员工自助申请"这一任务场景，作为现有管理员侧授权体系的伴生能力，而非替代。员工在缺口感或目标驱动场景下发起申请，由上级组织负责人审批，最终由 OA 底座完成流程闭环。

## §3 目标用户与场景

### 目标用户

| 角色 | 核心诉求 |
|---|---|
| **员工** | 知道自己有什么权限；知道能申请什么权限；申请后能追踪进度；无需私下找人 |
| **上级组织负责人** | 在业务上下文中快速理解申请事项并做出审批决策；不被无关申请打扰 |
| **权限管理员 / 超管** | 保持对可申请范围的全局控制；无需处理单个替换请求；审计可追溯 |

### 核心场景

**场景 1（缺口感-主要入口）：** 员工在访问某个功能或操作时被提示"无权限"，系统告知此权限是否可以申请，引导进入申请流程。

**场景 2（目标驱动型-辅助入口）：** 员工知道需要完成某项业务任务（如"处理报销单"），但不确定需要什么权限。系统按任务推荐所需权限/角色，引导申请。

**场景 3（状态追踪）：** 员工查看已发起的申请进度，知道当前卡在哪个环节、由谁处理。

## §4 当前替代做法

| 做法 | 问题 |
|---|---|
| 私下联系老板/管理员，口头或消息申请 | 沟通成本高、信息易遗漏、无记录可追溯 |
| 管理员在所有申请中按优先级插队处理 | 工作量大、时效不稳定、影响管理员核心工作 |
| 员工自行摸索"有没有权限" | 到操作入口才发现无权限，路径浪费，体验断层 |
| 离职/转岗时由管理员被动发现并调整权限 | 权限治理滞后，存在安全风险 |

## §5 机会点

| # | 机会点 | 关联场景 |
|---|---|---|
| 1 | **即时触发式申请**：在无权限拦截页面直接提供"申请"入口，把挫折感转化为可执行的下一步，路径最短、转化率最高 | 缺口感（D） |
| 2 | **任务语义解耦**：员工不需要理解"功能权限"和"角色"的管理概念，通过"我要做 XX"的自然语言找到所需权限，降低认知门槛 | 目标驱动型（A） |
| 3 | **申请进度可视化**：公开申请状态（提交→审批中→已通过→生效中），减少"问到哪了"的沟通需求 | 状态追踪 |
| 4 | **管理侧控制面前置**：管理员只需预设"哪些权限可申请""审批规则"，无需处理单个请求，实现控制权与操作权的分离 | 管理员控制 |
| 5 | **申请即治理**：每次申请自动产生审计记录，与离职/转岗联动形成权限生命周期闭环 | 权限治理 |

## §6 候选方向

### 方向 A：以缺口触发为核心的轻量申请方案

- **解决的问题**：员工在操作入口被拦截时的即时申请需求
- **目标用户价值**：最短路径解决"我没有权限"的问题，无需事先了解权限体系
- **主要风险**：被动触发，员工仍然无法主动了解和规划权限
- **成立前提**：系统能够明确告知"缺少哪些权限"以及"是否能申请"

### 方向 B：以任务感知为核心的权限发现方案

- **解决的问题**：员工不知道需要什么权限的认知缺口
- **目标用户价值**：用业务语言（"我要报销"）而非管理语言（"我需要费用管理的功能权限"）匹配权限，降低理解门槛
- **主要风险**：任务与权限的映射关系维护成本高；覆盖不全时员工依然需要退路
- **成立前提**：产品侧能建立稳定的"业务任务→所需权限"映射关系

### 方向 C：统一自助权限中心（推荐）

- **解决的问题**：同时覆盖"即时缺口感"和"主动发现"两个场景，在一处完成查看、申请、追踪全链路
- **目标用户价值**：一个入口解决所有与权限相关的问题；有明确的归属感（"去看我的权限"）
- **主要风险**：入口曝光度不足时，员工遇到无权限时仍然不知道去哪里申请；需要与已有权限管理页面做入口协调
- **成立前提**：独立入口嵌入工作台或全局导航；缺口拦截页能正确引导到自助中心

## §7 推荐方向与承接要求

### 推荐方向：统一自助权限中心

以独立"权限中心"聚合员工侧所有权限操作 — 查看已有权限、发现可申请权限、发起申请、追踪申请进度。核心入口来自两个场景的汇聚：

- **缺口感（主要入口）**：无权限拦截 → "去申请"按钮 → 跳转权限中心申请页，预填充缺少的权限
- **目标驱动型（辅助入口）**：工作台/全局入口 → "我要申请权限" → 按业务任务引导 → 勾选所需权限 → 提交申请

### 体验侧关注点

1. **语义降维**：终端用户不感知"功能权限 vs 角色"的管理区分，统一呈现为"你能申请的能力"
2. **审批上下文**：审批人看到的不只是"XX申请了YY权限"，而是"XX因为需要做 ZZ 事申请了 YY 权限"
3. **状态闭环**：申请提交仅是起点，生效通知和失败可解释才是体验闭环
4. **权限拒绝可解释**：当员工被拒绝或发现权限不可申请时，能知道原因（系统排除 / 管理员限定 / 审批拒绝）

### 承接契约

| 契约类型 | 内容 |
|---|---|
| 不可重判的边界 | 敏感权限由系统级预置排除，不在员工可申请范围内 |
| 不可重判的边界 | OA 底座提供审批流程引擎，不重新设计审批流引擎 |
| 不可重判的边界 | 组织架构和上级负责人关系由组织域定义，权限中心仅引用 |
| 必须展开的判断面 | 员工可通过哪些维度感知"自己需要什么权限"（任务映射关系） |
| 必须展开的判断面 | 管理员如何配置"可申请范围"（哪些角色/功能权限允许员工自助申请） |
| 必须展开的判断面 | 审批人与被审批人的上下级关系确认规则（组织树 vs 指定审批人） |
| 必须展开的判断面 | 申请生效后的通知策略与生效时机（即时/定时/审批完成后） |

## §8 约束与不做什么

### 约束

- 敏感权限由系统级预置排除，不可由员工申请
- 审批流程由 OA 底座提供，不重新设计审批引擎
- 上级负责人判定基于组织域管辖关系
- 角色本身的定义、创建和管理在管理员侧，不属于员工自助范畴

### 不做什么

- 不做管理员侧的角色管理与权限配置功能（已有成熟链路）
- 不做审批流程引擎设计（OA 底座承担）
- 不做敏感权限的定义与标记（系统级预置）
- 不做批量权限申请的处理策略（本次聚焦单次申请场景）
- 不做权限到期自动回收机制（属于权限治理范畴，不在此次范围）
