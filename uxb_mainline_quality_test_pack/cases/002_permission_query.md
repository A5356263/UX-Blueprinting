# 测试用例 002：权限查询

## 1. 用例定位

- 用例 ID：`uxb-qc-002-permission-query`
- 输入文档：`inputs/低完善读权限查询.md`
- 需求类型：策略类需求 / 低完整度需求
- 推荐领域：权限管理、审计 / 安全、信息架构、查询与排障
- 推荐输出深度：通常可先产出 `business_blueprint_lite.md` 或完整 `business_blueprint.md`，由 UXB 判断单决定

## 2. 为什么选这个样本

该需求信息较少，但目标清楚：补齐统一权限查询视角，帮助管理员从不同维度查看权限归属关系。

它适合测试 AI 是否会只根据竞品和常规后台页面经验输出“列表 + 筛选 + 详情”，而忽略权限对象关系和查询能力的业务定位。

## 3. 重点测试问题

### 3.1 需求理解

检查 AI 是否识别：

1. 这是查询 / 审计 / 排障能力，不是授权配置能力。
2. 查询对象至少包括人、角色、权限项、权限结果。
3. 查询不是直接修改权限，查询与授权操作要分离。
4. 该能力可能服务于权限核对、审计、安全排查、离职交接。
5. 低完整度文档没有给出完整字段、页面结构和规则，应保留 GAP。

### 3.2 知识选择

| 知识类型 | 应关注内容 |
|---|---|
| 权限对象模型 | 主体、资源、动作、范围、来源、状态 |
| 对象关系 | 人拥有哪些权限、角色包含哪些权限、权限被哪些人拥有 |
| 查询与配置路径 | 查询不等于配置，查询视角与配置视角的关系 |
| 能力地图 | 权限查询、排障、审计应放在什么能力域 |
| 设计准则 | 信息架构、列表信息密度、结果解释、空状态和无权限状态 |

### 3.3 固定习惯风险

重点检查是否出现：

- 直接输出页面布局，没有说明查询能力边界。
- 把查询能力写成权限配置入口。
- 所有维度都用同一种列表结构，没有解释不同查询角度。
- 没有区分“查某人有什么权限”“查某权限谁拥有”“查某角色有哪些权限”。
- 没有解释权限来源、权限状态、数据范围如何展示。
- 只引用竞品，不结合现有权限体系。

## 4. 预期评估重点

### 4.1 route_decision

应识别这是低完整度策略类需求，需要先判断业务形态和查询视角，不应直接按复杂新业务全量展开，除非 AI 证明其影响对象关系、状态和能力地图。

### 4.2 business

应至少覆盖：权限查询能力是否成立；它和授权配置、权限治理、审计排障的关系；推荐查询视角；每种视角解决什么问题；必要展示字段；查询结果是否允许跳转到配置页；不明确事项和边界。

### 4.3 experience

应至少覆盖：查询入口和视角切换、查询条件组织方式、查询结果信息层级、无结果 / 无权限 / 权限过多 / 结果不完整状态、查询结果到详情或配置页的跳转边界、风险权限或异常权限提示。

## 5. 主要失败信号

| 失败信号 | 严重度 |
|---|---|
| AI 只输出“筛选区 + 表格 + 详情抽屉” | 高 |
| 没有解释查询维度背后的权限对象关系 | 高 |
| 把查询和配置混在一起 | 高 |
| 没有处理权限来源、范围、状态解释 | 中 |
| 没有 GAP，只给完整确定方案 | 中 |
| 竞品内容被直接照搬 | 中 |

## 6. 耗时关注

该用例应比复杂业务能力短。重点看 AI 是否因为“权限”而过度读取知识导致耗时过长。
