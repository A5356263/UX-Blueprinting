# 测试用例 001：员工自助申请权限

## 1. 用例定位

- 用例 ID：`uxb-qc-001-employee-self-service-permission`
- 输入文档：`inputs/低完整度需求文档_员工自助申请权限.md`
- 需求类型：复杂业务能力 / 低完整度需求
- 推荐领域：权限管理、审批管理、工作台与全局入口、设计准则
- 推荐输出深度：通常应达到 `business_blueprint.md` + `experience_blueprint.md`

## 2. 为什么选这个样本

该需求不是简单页面优化，而是新增一条“员工自助申请权限”的业务通道。

它涉及员工查看权限、员工发起申请、审批人审批、审批通过后自动授权、管理员配置申请范围和审批流程、管理员关闭能力、现有权限治理模式互斥、服务人员是否支持、培训成本与权限安全风险。

该样本用于测试 AI 是否能在低完整度输入下，真实调用知识进行业务推理，而不是按常规“申请表单 + 审批流程 + 记录列表”输出。

## 3. 重点测试问题

### 3.1 需求理解

检查 AI 是否识别：

1. 这是新增业务能力，不是局部体验优化。
2. 这是权限体系的一条新来源路径，不只是新增员工入口。
3. 它影响权限来源、审批状态、授权生效、关闭行为、申请记录。
4. 低完整度文档中存在大量不确定项，不应全部脑补成确定规则。

### 3.2 知识选择

应重点关注 AI 是否选择并说明以下知识：

| 知识类型 | 应关注内容 |
|---|---|
| 权限对象模型 | 员工、权限、角色、数据权限、来源、状态 |
| 权限来源模型 | 自助申请是否应作为新的权限来源或授权渠道 |
| 治理状态模型 | 申请、审批、通过、拒绝、生效、撤销、关闭后的状态 |
| 角色边界 | 超管、权限管理员、员工、审批人、服务人员边界 |
| 能力地图 | 管理端、员工端、审批端分别承载什么 |
| 审批管理 | 审批人、审批流程、审批异常、审批结果回写 |
| 设计准则 | 多步骤流程、反馈与报错、异常说明 |

### 3.3 固定习惯风险

重点检查是否出现：

- 只写“员工提交申请、审批人审批、管理员配置”，没有解释为什么和现有权限体系有关。
- 没有定义审批通过后的权限生效方式。
- 没有处理关闭能力时审批中申请如何处理。
- 没有区分“权限申请通道关闭”和“已授予权限是否回收”。
- 把服务人员是否支持直接脑补为支持或不支持。
- 对模式互斥只写“需要注意”，没有提出明确判断或待确认项。

## 4. 预期评估重点

### 4.1 route_decision

应判断为复杂业务能力，业务改动深，需要完整 business blueprint 和 experience blueprint。

如果 AI 判断为普通体验优化，应记为严重问题。

### 4.2 business

应至少覆盖：需求是否成立、是否值得做、自助申请权限在现有权限体系中的能力形态、角色职责、可申请范围控制、审批流程与授权回写、权限来源或授权渠道如何记录、模式互斥、关闭能力时的处理、培训 / 安全 / 审批人缺失等风险、明确 GAP。

### 4.3 experience

应至少覆盖：管理员开启能力流程、管理员配置可申请范围流程、员工查看我的权限、员工发起申请、审批人审批、审批通过后员工看到权限生效、审批拒绝 / 撤销 / 审批人缺失 / 能力关闭 / 模式互斥等异常、可展示给用户的提示文案。

## 5. 主要失败信号

| 失败信号 | 严重度 |
|---|---|
| route_decision 只选择通用权限知识，没有选择审批管理 | 高 |
| business 基本复述需求，没有把自助申请放入权限来源 / 生效链路 | 高 |
| experience 只写申请表单，不写审批状态和异常反馈 | 高 |
| 对 15 个不明确事项全部脑补成确定方案 | 高 |
| 模式互斥只出现一次口号式提醒 | 中 |
| 培训成本、审批人缺失、安全风险没有转成体验保护动作 | 中 |

## 6. 耗时关注

该用例复杂度最高，应重点记录 route_decision、business、experience 是否明显耗时较长，以及是否出现返工。
