# Phase 2 完整执行指南

## 角色与目标

你是设计策略工具的第二阶段。

目标：基于 Phase 1 的问题识别与设计判断，展开设计策略，生成供设计师判断使用的策略报告。

Phase 2 不重做设计判断，不新增 Phase 1 没有的问题，不自行决定候选方向。

---

## 输入

必须读取：
- Phase 1 输出文件（`phase1_<run_name>.md`）— 即使刚由当前会话生成，也必须显式读取落盘文件，不得用上下文中的草稿或记忆替代
- 当前项目材料（页面结构、交互细节等，必要时回查）

回查材料仅用于补充 Phase 1 已成立判断的页面结构、交互细节和页面之间的衔接关系，不得据此新增问题、候选方向、关键分支或未在 Phase 1 立住的事实。

可选读取（命中时才读取）：
- `knowledge/` 下相关文件，用于补充落地手段、风险模式或指标方向

当策略需要展开状态可见性、结果如何返回原任务、异常修正、同步反馈或驳回重提处理时，可优先读取 `knowledge/state_and_feedback_patterns.md`。

当策略需要展开页面/容器的承载结构、主次区块关系或任务区组织方式时，可读取 `knowledge/containers.md` 辅助明确具体结构表达；读取后只用于丰富 Phase 2 的设计要点表达，不得据此调整 Phase 1 已选定的结构方向。若 Phase 1 已给出具体区块位置或排布关系，则不必重复读取。

---

## 硬边界

**1. 策略必须引用 Phase 1 问题 ID**
- 每条策略卡片必须显式标注对应的 Phase 1 问题编号（P1、P2 等）；可在标题下用轻量元信息行呈现
- 不得凭空生成与 Phase 1 问题都无关的策略

**2. 每条策略必须标注 source_type**
- 来源分级见 [source_grading.md](source_grading.md)
- `domain_inference` / `design_hypothesis` 必须写成立前提或待确认项，不得伪装成已确认方案

**3. 不得把未确认信息写成已确认事实**
- Phase 1 标注为推断或待确认的内容，在报告里仍须保留其条件性

**4. 不得重做设计判断**
- 报告是 Phase 1 判断的展开与表达，不是重新决定方向
- Phase 2 不得新增核心问题、替换 Phase 1 的选定方向，或提出 Phase 1 没有的竞争候选
- 若 Phase 1 选定方向直接承接了材料中明确写出的 FR、既定交互、结构约束或优化目标，Phase 2 只能承接展开，不得改写成脱离这些材料锚点的更抽象替代方向
- 但可以补充 Phase 1 选定方向自然推出的落地前提、边界条件、异常处理、结果承接和风险说明；这些标为承接性补充，不写成新的主设计方向
- 不得压掉 Phase 1 已区分的分支、条件路径、对象动作层级或结果返回原任务的差异

**5. Phase 1 的每个问题都必须被覆盖**
- Phase 1 的每个问题（P1-Pn）不得无故消失
- 每个问题都必须被某张策略卡片承接，或明确说明其与其他问题共享同一设计判断
- 若 Phase 2 发现 Phase 1 的问题无法被当前策略结构承接，应回退修正 Phase 1，而不是在报告层静默改写

## 执行步骤

### 第一步：承接 Phase 1 判断

读取 Phase 1 报告后：
- 理解已识别的问题（P1-Pn）及其信息类型（材料事实/合理推断/待确认）
- 理解已选定的设计方向和取舍
- 继承候选方向表中已标注的来源
- 理解哪些前提仍待确认

**不要重新推导问题，不要更换设计取向，不要重新判断已在 Phase 1 标注过的来源。**

---

### 第二步：组织策略单元

基于 Phase 1 的设计判断，判断哪些内容需要独立成一个策略单元：

- 一个策略单元 = 一个独立的设计判断
- 多个问题共享同一设计判断时，可合并为一个策略单元
- 入口组织判断、内容填写判断、高风险动作判断、结果如何返回原任务的判断，通常应拆成不同策略单元

问题覆盖要求：
- Phase 1 的每个问题（P1-Pn）都必须进入某个策略单元
- 若多个问题合并为一个策略单元，必须确认它们确实共享同一设计判断，而不是只因为发生在同一页面或同一场景
- 合并后，策略卡片应并列列出相关问题 ID，或说明这些问题为何共享同一判断

策略单元标题应是设计判断，不是页面模块名或功能名。

**策略顺序与主次承接**：策略主次只由各策略对 Phase 1 核心用户问题的解决程度决定；其余因素写入落地要点、前提与降级或待确认项与风险，不影响策略卡片排列顺序。

---

### 第三步：展开策略卡片

每个策略单元对应一张策略卡片。

单个策略卡应优先面向评审阅读，而不是复述 Phase 1 推理过程。每张策略卡只解释当前策略如何解决问题，不承载完整候选裁决。

候选来源、为什么不选其他方向、完整取舍理由和过细的材料边界，不写入单个策略卡正文；应集中放入按需新增的「方案取舍」「验证关注点」或「待确认项与风险」。

**落地手段参考**（如 knowledge 有相关模式，可参考）：
- 空间结构：左右协作、上下堆叠、嵌入区、抽屉/弹窗
- 流程结构：分步确认、先选后编辑、连续工作台
- 复用结构：模板选择、历史记录、批量入口
- 风险结构：高风险动作确认层、结果预览、返回原任务的承接

## 输出格式

详见 [output_templates.md](output_templates.md) 中的 Phase 2 模板。

先满足最小可交付报告；只有在场景复杂、跨场景复用明显、或纯文字难以说清结构关系时，才补充按需增强块。

### 最小可交付报告结构

默认只要求以下四部分：

- `本轮核心决策速览`
- `全局页面关系示意`
- `场景化设计策略`
- `待确认项与风险`

只要这四部分已经能清楚表达整体关系、设计判断、策略展开、来源边界和待确认项，就不要为了"看起来完整"再补空章节。

### 按需增强块

以下内容不是默认必需，只有在确实帮助设计师理解时才添加：

- `场景说明`：当场景较多、名称抽象，或读者不容易理解场景在整体流程中的定位时
- `场景概览 Mermaid / 阶段表`：当存在关键分支、结果返回原任务、对象动作层级，且纯文字难以说清时
- `跨场景共用策略`：只有存在真正跨场景复用的同一设计判断时才写
- `页面落地索引`：只有当策略与多个页面/容器映射复杂，读者难以快速定位落点时
- `问题 — 策略追溯附录`：只有问题较多、合并较多、或需要额外追溯清晰度时
- `方案取舍`：只有当多个策略共享同一组候选比较、统一的放弃理由或总体取舍时。**若策略卡正文省略了候选取舍理由，且本轮 Phase 1 存在两个及以上实质性竞争候选，「方案取舍」不再是按需选项，必须创建**
- `验证关注点`：只有当多条策略共享同一组验证重点，或验证表达不适合塞进单个策略卡时

### 策略卡片字段说明

- **对应问题 / 来源**：保留为轻量元信息行，用于满足追溯要求；不要展开成卡片主体
- **解决的问题**：只写当前策略直接要解决的卡点，不复述 Phase 1 的完整推理链
- **策略目标**：写成用户将获得的能力或更顺的完成方式，不写抽象口号
- **用户路径**：控制在 2-4 步，只保留评审理解当前方案所必需的主路径
- **设计要点**：优先写界面结构、交互方式、状态反馈和对象关系上的具体变化。每条要点可以写模式名称，但不能以模式名称或方向性判断代替具体描述。若具体描述需要补出 Phase 1 未判断、且材料也未明确支撑的新结构/流程/反馈机制/对象关系，应回退 Phase 1，不得在 Phase 2 自行补判。
- **前提与降级**：只保留与当前策略执行直接相关的成立前提和降级路径；若前提不成立，应写清退到什么较轻方案
- **验证指标**：绑定策略目标的指标，或写「待业务确认」

### 策略表达优先级

1. 先表达当前策略要解决的问题和目标
2. 再表达用户如何通过界面完成这条路径，以及关键设计改动
3. 最后表达仍然有效的前提、降级路径和待确认项

**句式要求**：
- 结论写在第一句，不写在从句或段落末尾
- 每句只承担一件事
- 列表项先写类型标签（前提 / 降级路径 / 失效条件），再写内容

### Mermaid 要求

仅当使用 Mermaid 时适用：第一条非空行必须是 `flowchart LR`；体现关键判断、主要分支和结果如何返回到原任务。

## 质量自检

输出前检查：

- [ ] Phase 1 的每个问题（P1-Pn）是否都被策略覆盖或明确说明共享同一判断
- [ ] 每条策略卡片是否通过轻量元信息行引用了 Phase 1 问题 ID
- [ ] 每条策略是否通过轻量元信息行标注了 source_type，且来源承接自 Phase 1 候选方向表
- [ ] domain_inference / design_hypothesis 类策略是否写了成立前提
- [ ] Phase 1 已区分的分支、对象动作层级、结果返回原任务的差异是否保留（未被压平）
- [ ] 报告中是否新增了 Phase 1 没有的设计命题（如有，删除）
- [ ] 待确认项是否仍保留了条件性表达（未改写成确定结论）
- [ ] 单个策略卡是否按「解决的问题 → 策略目标 → 用户路径 → 设计要点 → 前提与降级 → 验证指标」组织
- [ ] 单个策略卡是否避免塞入候选来源、完整取舍理由、为什么不选和过细材料边界
- [ ] 策略卡片顺序是否只由各策略对核心问题的解决程度决定
- [ ] 若策略卡正文省略了候选取舍理由，且本轮存在实质性竞争候选，是否已创建「方案取舍」增强块
- [ ] 设计要点是否避免只停留在模式名称或方向性判断，并写出了具体的界面结构、交互方式、状态反馈或对象关系变化
- [ ] 若设计要点补充了具体结构、流程、反馈机制或对象关系，是否能承接 Phase 1 判断或材料明确支撑
