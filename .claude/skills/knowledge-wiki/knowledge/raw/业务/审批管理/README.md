# 审批管理

## 这是什么

这是审批管理领域的二级路由入口，用来说明本领域承载什么知识、遇到什么问题该优先看哪些语义文件。

本 README 承载领域契约与任务路由；具体业务规则仍保留在对应语义文件中。


## 领域契约

### 领域定义

审批管理领域回答的是：
平台如何提供通用审批能力（审批角色、表单模板、数据管理、系统审批承接），支撑各业务域的审批流程。

它覆盖的不是单一审批流程，而是一整套与平台审批基础设施相关的业务语义，包括：

- 通用审批：跨业务复用的审批能力
- 审批角色：审批流程中的角色定义与分配
- 表单模板：审批表单的设计与管理
- 数据管理：审批数据的存储与查询
- 系统审批承接：各业务域如何接入审批能力

### 解决的问题

审批管理领域主要用于解释以下问题：

- 平台审批能力如何组织和管理
- 审批角色如何定义和分配
- 审批表单模板如何设计
- 各业务域（人事、费用等）如何接入审批能力
- 审批数据如何管理和审计

### 为什么独立成域

审批管理需要独立沉淀，是因为它同时具备以下特征：

- 是平台级审批基础设施，被多个业务域（人事、费用、权限等）共用
- 审批角色和表单模板具有跨业务通用性
- 与各业务域有明确的上下游关系：审批域提供能力，业务域定义具体审批规则

### 与下游领域的关系

- 人事服务域消费审批能力：入职、调动、离职等异动审批
- 费用管理域消费审批能力：报销单审批、账单审批、垫款审批
- 权限域消费审批能力：权限变更审批
- 企业支付域消费审批能力：供应商准入审批、付款审批

这里描述的是下游依赖事实，审批域作为平台级能力被各业务域调用。

### 稳定结论

- 审批管理是平台级审批基础设施的承载域
- 其核心价值是为审批角色、表单模板、数据管理和系统承接提供稳定输入
- 它可以服务业务分析、产品设计、体验解释和排障分析，但本文件本身不承载下游消费说明

### 显式缺口

- [GAP] 各业务域接入审批能力的具体对接规范和边界条件待进一步明确
- [QUESTION] 审批管理与 OA 审批的关系和边界是否已完全清晰，需持续校验
## 任务触发索引

- 需要理解审批管理域的边界与覆盖范围：读本 README 的“领域契约”
- 需要理解审批管理能力结构与承接方式：读 `审批管理.md`
- 需要理解审批角色和权限范围：读 `角色与权限.md`
- 需要理解审批表单类型、基本信息、表单设计和打印模板：读 `表单配置.md`
- 需要理解流程节点、审批人来源、流程版本、动态流程和高级设置：读 `流程设计.md`
- 需要理解流程转派、流程交接和审批角色管理：读 `数据管理.md`
- 其他业务域涉及审批时，只按实际问题补读：角色与权限读 `角色与权限.md`，表单读 `表单配置.md`，节点、审批人来源、版本与高级设置读 `流程设计.md`，转派与交接读 `数据管理.md`
- 本域只提供通用审批机制，不决定权限新增、修改、删除中的审批触发条件、授予事实和生效结果；这类事实必须回到权限管理的 `任务场景.md`、`规则契约.md`、`治理状态模型.md` 和 `审计契约.md`

## 条件依赖与回主域

- 审批角色、表单、节点、审批人来源、流程版本、转派和交接由本域回答；某项业务为何触发审批、审批前后业务状态如何变化由对应业务域回答
- 从权限、人事、费用或企业支付进入本域时，只读取命中的机制文件；读完必须返回原业务域，不得用通用审批机制补造业务规则
- 审批人离职需要确认成员退出状态时补读成员管理；本域只承接审批任务转派与流程交接，成员生命周期仍归成员域

## 维护原则

- README 只承载领域契约与领域内路由，不展开具体业务规则正文
- 正式业务事实写入对应语义文件
- 不在本目录中写其他业务域的具体审批规则细节
- 不在本目录中沉淀主链路消费地图、蓝图移交说明或下游执行指令
- 做结构替换时不保留兼容层，确认替换后直接移除旧知识位
