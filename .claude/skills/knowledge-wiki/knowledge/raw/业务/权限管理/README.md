# 权限管理

## 这是什么

这是权限管理领域的二级路由入口，用来说明这个目录里各编号段分别承载什么知识、遇到什么问题该优先看哪些文件。

本 README 承载领域契约与任务路由；具体业务规则仍保留在对应编号文件中。


## 领域契约

### 领域定义

权限管理领域回答的是：
谁在什么条件下，对什么资源，可以做什么，以及结果何时生效。

它覆盖的不是单一授权动作，而是一整套与权限结果相关的业务语义，包括：

- 可见性
- 功能权限
- 数据范围
- 治理与生效状态
- 查询、追踪与审计

### 解决的问题

权限管理领域主要用于解释以下问题：

- 某个主体为什么有权限
- 某个主体为什么没有权限
- 某项权限来自哪里
- 某项权限是否已经生效
- 权限变更由谁发起、由谁审批、何时生效
- 当结果异常时，如何定位到失败层级与冲突原因

### 为什么独立成域

权限管理需要独立沉淀，是因为它同时具备以下特征：

- 有稳定的业务判断链路，不应散落在页面说明或零散文档中
- 涉及多种主体、角色、应用、协作可见性和治理模式
- 具备强规则性，存在前置、覆盖、互斥、审批、生效等约束
- 经常与组织、成员、应用、审批、审计等领域发生上游依赖

### 与上游领域的关系

在当前平台组织重构背景下，权限管理与以下上游事实关系密切：

- 成员作为权限主体，由成员域承载
- 组织视图、部门、岗位等结构会影响权限授予和数据范围
- 应用可见范围与功能权限会共同影响最终访问结果

这里描述的是上游依赖事实，不等于具体授权规则已经由其他领域定义完成。

### 稳定结论

- 权限管理是一个规则密集、状态敏感、可审计的业务领域
- 它的核心价值是为权限判断、来源解释、冲突定位和治理追踪提供稳定输入
- 它可以服务业务分析、产品设计、体验解释和排障分析，但本文件本身不承载下游消费说明

### 显式缺口

- [GAP] 某些帮助文档和历史外部口径仍需继续与当前权限真源核对
- [QUESTION] 当前组织重构后，上游领域边界是否已完全稳定，仍需结合邻近领域持续校验

## 任务触发索引

- 需要先理解权限管理领域是什么、覆盖什么、不覆盖什么：读本 README 的“领域契约”和 `01_范围与边界.md`
- 需要理解角色、对象、入口、路径、页面载体：读 `03`、`04`、`10-15`
- 需要把权限需求翻译为页面蓝图：读 `15_页面载体语义.md`，但默认只读取命中的完整章节：用户直授读 `2`，角色授权读 `3`，管理模式、子管理员或权限变更审批读 `4`，成员协作可见性读 `5`，权限查询与排障读 `6`，应用入口治理读 `7`
- 首次使用 `15` 的页面语义卡格式时补读 `0-1`；命中具体页面后，从对应 `###` 标题读到下一个同级标题即停止，不得因“页面设计”整篇读取
- 需要做规则判断、来源判断、冲突判断、治理与审计判断：读 `20-25`
- 需要做用户解释、风险分析、体验翻译、文案说明：读 `30-32`
- 需要核对帮助文档、FAQ、历史外部口径或异常排障：读 `50_帮助文档权限差异.md`
- 普通权限查询、来源解释或可见性排障：以 `11`、`20-22` 为主，不自动读取审批管理
- 权限新增、修改、删除涉及审批：先读 `11_任务场景.md`、`23_规则契约.md`、`24_治理状态模型.md`；再按需进入审批管理 README 的“领域契约” 与 `13_流程设计.md`
- 权限审批涉及审批角色或权限边界：补读审批管理 `11_角色与权限.md`；涉及审计追溯：补读本域 `25_审计契约.md`
- 读取审批机制后，必须回到本域确认权限对象、授予事实、治理状态、生效结果、异常与审计；审批管理不得替代权限规则

## 条件依赖与回主域

- 主体身份命中成员问题时补读成员管理；组织视图或数据范围命中组织问题时补读组织架构；应用启用、治理或可见范围命中应用问题时补读应用管理
- 上述依赖只补充权限判断的输入；最终能否访问、能做什么、能看什么数据以及何时生效必须回到本域确认

## 维护原则

- README 只承载领域契约与领域内路由，不展开具体业务规则正文
- 正式业务事实写入对应编号文件
- 不在本目录中沉淀主链路消费地图、蓝图移交说明或下游执行指令
- 做结构替换时不保留兼容层，确认替换后直接移除旧知识位
