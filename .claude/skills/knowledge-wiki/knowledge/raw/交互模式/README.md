# 交互模式

## 这是什么

这是交互模式知识库的二级路由入口，用于存放跨业务、跨产品复用的任务组织方式与信息承载模式。

它服务的是页面结构推导、任务组织和形式选择，不服务业务规则定义，也不替代设计准则。

## 与设计准则的关系

- `设计准则` 回答为什么这样判断
- `交互模式` 回答这类任务通常怎么组织

读取顺序通常是：

1. 先读相关设计准则，判断当前问题类型
2. 再读交互模式，选择常见组织方式和承载形式

交互模式不是组件模板。使用前必须先结合当前业务事实、角色、对象、状态、风险和上下游约束建立完整问题结构，再选择模式；不得根据“弹窗、抽屉、审批、报错”等单一关键词直接套用。

## 全局交互地图

进入具体模式前，必须先整体判断以下五个相互关联的维度：

1. **入口**：用户从哪里发起，如何发现；角色、对象状态和任务频次是否改变入口位置与主次。
2. **承载**：任务使用页面、弹窗、抽屉还是工作区；是否必须保留原页面信息与处理位置。
3. **行为**：用户要完成哪些核心动作；操作顺序、依赖、批量、中断与恢复如何组织。
4. **状态与反馈**：操作前、中、后分别有哪些状态、结果、异常、阻断和可执行恢复路径。
5. **回流**：完成、取消或失败后返回哪里；结果如何作用回原对象，原任务如何继续。

五个维度共同形成完整交互行为链：

```text
进入 → 理解 → 操作 → 反馈 → 恢复或完成 → 返回原任务
```

必须先形成整体判断，再深读实际命中的模式。不得只设计入口或容器而遗漏状态、异常与回流，也不得为了覆盖形式读取无关模式。

## 读取与装配规则

1. 先读本文件的全局交互地图，结合当前材料判断五个维度分别是相关、不相关还是信息不足。
2. 相关维度继续读取对应 raw 中命中的完整模式块；不相关维度不强制展开，但必须有业务依据；信息不足进入待确认，不得静默补造。
3. 完整模式块以命中的 `###` 标题为起点，读取到下一个同级标题之前；不得只摘适用条件或组件名称。
4. 采用模式时必须说明当前业务证据、选择原因和至少一个相近模式的排除原因；模式只提供候选与边界，不直接成为项目结论。
5. 将命中模式装配为入口、承载、核心行为、状态反馈、异常恢复和回流关系；完成后回看全局地图，确认交互链闭合。
6. 不设固定读取数量。简单任务可只命中少量模式；跨角色、多状态、高风险或复杂异常任务按真实影响扩展。

## 当前主题

- `行为模式.md`：识别输入、提交、列表、审批、配置、导航和数据任务中的行为意图与常见摩擦，只负责还原问题，不直接推出方案
- `容器与工作区.md`：页面、弹窗、抽屉、全屏容器以及复杂工作区的适用边界
- `入口与导航.md`：场景入口、状态入口、角色差异入口和导航层级的组织方式
- `状态、反馈与恢复.md`：状态链、结果承接、反馈承载、异常修正、引导和返回原任务的模式

## 场景路由

- 需要识别用户行为、任务意图和常见摩擦：读 `行为模式.md`
- 需要选择页面、弹窗、抽屉或复杂工作区：读 `容器与工作区.md`
- 需要判断入口位置、入口主次和导航关系：读 `入口与导航.md`
- 需要表达审批、处理中、同步、失败、驳回、反馈承载、引导和返回原任务：读 `状态、反馈与恢复.md`
- 需要判断“反馈还是引导”、什么时候前置说明、什么时候强阻断：先读 `设计准则/设计准则.md` 中的“反馈与引导原则”章节
- 需要组织新手指引、任务引导、结果反馈、异常恢复：读 `状态、反馈与恢复.md`
- 需要为某类任务选择更合适的承载形式：优先读 `容器与工作区.md`，涉及反馈承载时再读 `状态、反馈与恢复.md`

## 边界

- 放模式和形式边界，不放业务规则
- 放任务组织方法，不放组件实现 API
- 放常见承载方式，不放视觉样式规范
- 模式必须结合当前业务证据选择，不得把知识库中的候选直接写成项目事实
