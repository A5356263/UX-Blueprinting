## 数据反馈相关组件指南


本文档用于帮助 AI 在设计知识检索、组件推荐、交互方案生成、PRD 转设计方案等场景中，判断数据反馈类组件的使用边界、层级关系、结构规范和选型规则。

数据反馈相关组件主要用于在用户操作前、操作中、操作后提供信息承载、任务中断、确认提醒、状态反馈或异步通知。不同组件的关键差异在于：是否阻断当前流程、是否要求用户立即决策、是否承载复杂内容、是否属于操作结果反馈、是否需要在不打断用户任务的情况下提示信息。

---

### 1. 组件总览

| 组件 | 中文名称 | 核心用途 | 是否阻断流程 | 典型内容复杂度 | 典型触发时机 |
|---|---|---|---|---|---|
| Drawer | 抽屉 | 在当前页面侧边展开补充内容、详情、编辑或子任务 | 中等，可阻断但弱于弹窗 | 中到高 | 用户点击查看、编辑、配置、详情入口 |
| Functional Modal | 功能类对话框 | 承载独立任务、表单填写、功能操作或局部流程 | 高 | 中 | 需要用户聚焦完成一个明确任务 |
| Confirmation Modal | 确认类对话框 | 在高风险、不可逆或需要二次确认的操作前拦截 | 高 | 低 | 删除、提交、关闭、放弃、发布等操作前 |
| Result | 结果 | 展示操作完成后的结果状态、结果说明和后续动作 | 低到中 | 低到高 | 操作提交后、流程完成后、任务结束后 |
| Notification | 通知提醒框 | 展示系统主动推送、异步状态、轻量通知 | 低，不阻断 | 低 | 后台任务、系统通知、消息提醒、流程外提醒 |

### 2. 全局层级与遮罩规则

#### 2.1 容器层级

推荐的层级关系为：

页面 > 抽屉 > 弹窗

当页面中已经打开抽屉，如果需要在抽屉内触发更强的操作确认、表单填写或局部任务，可以在抽屉之上再打开弹窗。弹窗层级高于抽屉。页面可加遮罩，抽屉可加遮罩，弹窗通常需要遮罩以强调阻断和聚焦。

#### 2.2 叠加规则

- 页面可以触发抽屉。
- 页面可以触发弹窗。
- 抽屉中可以触发弹窗。
- 不建议出现多层抽屉连续叠加。
- 不建议出现多个弹窗连续叠加，除非业务强依赖，且必须保持来源和返回路径清晰。
- 弹窗与抽屉同时存在时，弹窗应位于最上层。
- 当页面、抽屉、弹窗均存在时，用户当前焦点应落在最上层组件。
- 遮罩应表达当前可交互范围：遮罩后的内容通常不可交互。

#### 2.3 打断强度从弱到强

Notification < Result < Drawer < Functional Modal < Confirmation Modal

其中 Notification 通常不阻断用户流程；Result 用于结束后反馈；Drawer 用于在当前上下文中承载额外内容；Functional Modal 用于聚焦完成任务；Confirmation Modal 用于阻止用户误操作或确认高风险行为。

### 3.1 定义

Drawer 是从页面边缘滑出的承载容器，通常从右侧出现，用于在不完全离开当前页面的情况下展示补充内容、详情信息、编辑表单或任务分支。

Drawer 适合在当前页面上下文仍然重要时使用。它让用户在保持对原页面感知的同时，处理一个相关但相对独立的内容区域。

### 3.2 何时使用

适合使用 Drawer 的场景：

- 查看详情，例如查看列表项详情、订单详情、用户详情、任务详情。
- 编辑当前对象，例如编辑表单、修改配置、补充信息。
- 展示与当前页面强相关的扩展信息。
- 承载不会完全脱离主流程的子任务。
- 用户需要在当前页面和详情内容之间保持上下文关联。
- 内容量中等或较多，需要比弹窗更大的阅读或操作空间。
- 需要在页面右侧形成固定操作区，同时保留页面背景上下文。

不适合使用 Drawer 的场景：

- 只需要展示一句简短提示，应使用 Notification 或轻量提示。
- 需要用户对高风险操作进行二次确认，应使用 Confirmation Modal。
- 任务需要强制聚焦且不依赖页面上下文，应优先使用 Functional Modal。
- 需要展示完整页面级流程，应跳转页面或使用页面级容器。
- 内容过于复杂，已经接近完整页面的信息架构，不宜塞入抽屉。

### 3.3 组件结构

Drawer 通常由以下区域组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|
| 标题区 | 必需 | 展示抽屉标题，必要时包含关闭按钮、帮助入口或补充操作 |
| 内容区 | 必需 | 展示详情、表单、说明、配置项、列表等主要内容 |
| 底部操作区 | 可选 | 在编辑、配置、确认等场景中展示主按钮和次按钮 |
| 遮罩层 | 视场景而定 | 用于弱化页面背景并表达当前焦点 |
| 关闭入口 | 必需 | 通常包含右上角关闭按钮，也可支持点击遮罩关闭 |

### 3.4 尺寸与布局

Drawer 从右侧滑出，固定宽度，贴合页面右侧。

##### 尺寸适配

提供 4 种固定宽度：

| 宽度 | 适用场景 |
|------|---------|
| 480px | 简单详情、轻量表单、短内容 |
| 740px | 中等复杂详情、常规编辑表单 |
| 1060px | 复杂信息、较多字段、结构化配置 |
| 1200px | 高复杂内容、大型详情、需要更大横向空间的任务 |

##### 红线标识间距

| 属性 | 规格 |
|------|------|
| 顶部内边距 | 20px |
| 头部标题距顶部/左侧/右侧 | 20px |
| 容器圆角 | 12px |
| 头部标题区到内容区 | 12px |
| 底部操作区到容器底部 | 12px |

##### 布局特征

- 标题区固定在顶部。
- 内容区根据内容高度滚动。
- 底部操作区在需要操作时固定在底部。
- 抽屉应从右侧进入，关闭时回到右侧。

### 3.5 样式状态

Drawer 可分为查看类、编辑类、设置类等状态。

#### 查看类 Drawer

用于阅读详情，不一定需要底部按钮。用户可通过关闭按钮或点击遮罩关闭。内容以信息展示为主，不应强制用户操作。

#### 编辑类 Drawer

用于修改内容，需要底部操作区。通常包含“取消”和“确定”按钮。关闭前如果存在未保存内容，应提示用户确认是否放弃修改。

#### 设置类 Drawer

用于局部配置，通常包含表单项、开关、选项列表和底部操作。配置项较多时应分组展示。

### 3.6 交互规则

- 打开 Drawer 后，焦点进入 Drawer。
- 点击关闭按钮可以关闭 Drawer。
- 查看类 Drawer 可允许点击遮罩关闭。
- 编辑类 Drawer 如存在未保存内容，不应直接关闭，应触发确认。
- 底部主按钮通常位于右侧，次按钮在主按钮左侧。
- 抽屉内可以触发弹窗，但应避免触发新的抽屉。
- 抽屉关闭后应回到触发入口所在的上下文。

### 4.1 定义

Functional Modal 是居中出现的功能型对话框，用于承载一个明确、独立、需要用户聚焦完成的任务。它通常比 Drawer 更强地打断当前流程，适合表单输入、配置操作、选择任务或局部功能处理。

### 4.2 何时使用

适合使用 Functional Modal 的场景：

- 用户需要完成一个明确任务，例如填写信息、选择对象、配置参数。
- 当前操作需要聚焦，不希望用户被页面其他内容干扰。
- 任务内容相对独立，完成后回到原页面。
- 内容复杂度中等，不需要完整页面承载。
- 需要用户在弹窗内完成输入、确认、提交或取消。
- 页面中操作入口较多，但任务本身可以被封装成一个短流程。

不适合使用 Functional Modal 的场景：

- 只是展示一个操作风险确认，应使用 Confirmation Modal。
- 只是展示操作结果，应使用 Result。
- 只是通知用户某个异步消息，应使用 Notification。
- 内容过多、流程过长，应使用页面或 Drawer。
- 用户需要频繁参考页面背景内容时，不宜使用 Modal 强阻断。

### 4.3 组件结构

Functional Modal 通常由以下区域组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|
| 标题区 | 必需 | 展示任务名称，包含关闭按钮 |
| 内容区 | 必需 | 承载表单、说明、选择器、列表、配置项等 |
| 底部操作区 | 必需或可选 | 展示取消、确定、提交等操作 |
| 遮罩层 | 必需 | 阻断背景交互，聚焦当前任务 |
| 关闭入口 | 必需 | 通常为右上角关闭按钮 |

### 4.4 尺寸与布局

Functional Modal 居中显示，宽度可根据场景选择。

##### 尺寸适配

| 宽度 | 适用场景 |
|------|---------|
| 480px | 轻量任务 |
| 740px | 常规表单/配置 |
| 1060px | 复杂内容 |
| 1200px | 特殊宽场景（谨慎使用） |

##### 高度约束

| 属性 | 规格 |
|------|------|
| 弹窗最小高度 | 222px |
| 弹窗最大高度 | 页面可视高度的 80% |
| 分步骤弹窗 | 必须固定高度 |

##### 红线标识间距

| 属性 | 规格 |
|------|------|
| 头部内边距（顶部） | 20px |
| 头部内边距（左右） | 20px |
| 标题区到内容区间距 | 16px |
| 内容区到按钮操作区（紧凑） | 16px |
| 内容区到按钮操作区（宽松） | 40px ~ 48px |
| 底部按钮区到容器底部 | 16px |
| 顶部标题栏高度（红线） | 56px |

##### 溢出处理

当内容超过最大高度时，内容区滚动，标题区和底部操作区保持可见。

### 4.5 样式状态

Functional Modal 可以根据任务类型呈现不同内容形态：

- 表单填写型：包含输入框、选择器、校验提示。
- 信息查看型：展示较短的结构化详情。
- 配置操作型：包含开关、选项、规则设置。
- 选择操作型：包含列表、树、表格或候选项。
- 多步骤型：只有在步骤较少时使用；复杂多步骤应考虑页面化。

### 4.6 交互规则

- 打开 Modal 后，焦点进入 Modal。
- 背景页面不可操作。
- 点击右上角关闭按钮关闭。
- 点击取消按钮关闭。
- 点击主按钮提交或确认当前任务。
- 存在未保存内容时，关闭前应触发确认。
- 弹窗内如需展示风险确认，可嵌套 Confirmation Modal，但应控制层级。
- 不建议弹窗中再打开功能弹窗，除非是极短的确认行为。

### 5.1 定义

Confirmation Modal 是用于二次确认的对话框，核心目的是防止用户误操作，让用户再次确认意图，避免不可逆风险或高成本错误。

它不是普通信息展示组件，也不是结果反馈组件。它只在用户即将执行某个需要确认的操作前出现。

### 5.2 何时使用

适合使用 Confirmation Modal 的场景：

- 删除、移除、清空、作废等不可逆操作。
- 提交、发布、审批、关闭流程等会产生明确后果的操作。
- 取消、放弃编辑、离开页面时存在未保存内容。
- 操作会影响他人、影响数据、影响流程状态。
- 操作失败成本较高，需要用户再次确认。
- 系统需要解释风险、影响范围或后果。

不适合使用 Confirmation Modal 的场景：

- 展示成功、失败或完成结果，应使用 Result。
- 展示系统公告、异步通知，应使用 Notification。
- 承载复杂表单任务，应使用 Functional Modal。
- 承载大量详情内容，应使用 Drawer 或页面。
- 低风险、可轻易撤销的操作不应频繁打断用户。

### 5.3 组件结构

Confirmation Modal 通常由以下区域组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|
| 图标 | 必需 | 表达确认类型，如成功、提示、警示、错误 |
| 标题 | 必需 | 简洁说明用户即将确认的事项 |
| 内容 | 可选 | 补充说明操作影响、原因、后果或注意事项 |
| 错误码 / 详情 | 可选 | 用于系统错误、校验失败或异常说明 |
| 操作区 | 必需 | 提供主按钮、次按钮或更多操作 |

### 5.4 尺寸与布局

Confirmation Modal（对话框）的内容应短小清晰。

##### 组件结构

| 元素 | 是否必选 | 说明 |
|------|---------|------|
| 图标 | 必选 | 表达状态语义 |
| 标题 | 必选 | 直接表达确认动作 |
| 内容 | 非必选 | 尽量短，避免长段落 |
| 错误码 | 非必选 | 需要展示详细原因时使用 |
| 操作区 | 必选 | 1~3 个按钮 |

##### 红线标识间距

| 属性 | 规格 |
|------|------|
| 顶部内边距 | 12px |
| 标题区左右内边距 | 12px |
| 标题区到内容区 | 12px |
| 内容区到操作区 | 32px |
| 操作区到底部内边距 | 12px |

##### 布局规则

- 底部按钮通常右对齐。
- 危险操作的主按钮应使用危险样式。

### 5.5 样式状态

#### 成功确认对话框

用于确认正向操作或说明操作即将成功执行的场景。一般不应用于最终成功结果展示，最终结果应使用 Result。

#### 信息说明对话框

用于普通确认、说明性确认或需要用户理解规则后继续的场景。

#### 警示对话框

用于有风险但不一定错误的操作，例如是否确认删除、是否确认覆盖、是否确认关闭。

#### 出错对话框

用于操作前校验异常、系统错误说明或需要用户知晓失败原因的场景。若是完整结果页，应使用 Result。

### 5.6 按钮规则

| 按钮数量 | 适用场景 | 示例 |
|---|---|---|
| 一个按钮 | 仅需用户知道并关闭 | 我知道了 |
| 两个按钮 | 取消 + 确认 | 取消 / 确定 |
| 三个按钮 | 需要额外操作分支 | 取消 / 导出 / 直接保存 |

按钮原则：

- 主按钮应表达最关键动作。
- 危险动作按钮应使用危险样式。
- “取消”通常放在主按钮左侧。
- 按钮文案应具体，避免只有“是/否”。
- 不要用确认弹窗承载复杂决策树。

### 6.1 定义

Result 用于展示用户操作完成后的结果状态，帮助用户理解操作是否成功、是否失败、是否处理中，以及下一步可以做什么。

Result 是操作后的反馈，不是操作前确认，也不是异步轻提示。它适合在任务结束、流程完成、提交完成或状态变化后出现。

### 6.2 何时使用

适合使用 Result 的场景：

- 表单提交后展示成功、失败、处理中等状态。
- 任务完成后展示下一步操作。
- 流程结束后展示结果摘要。
- 批量操作后展示成功和失败明细。
- 审批、导入、导出、检测、发布等任务完成后反馈状态。
- 需要承载结果说明、结果表格或后续动作。

不适合使用 Result 的场景：

- 操作前需要用户确认风险，应使用 Confirmation Modal。
- 只是后台异步消息提醒，应使用 Notification。
- 需要承载编辑表单，应使用 Drawer 或 Functional Modal。
- 只需要一句轻提示，不需要结果区域。

### 6.3 状态类型

Result 常见状态包括：

| 状态 | 语义 | 使用场景 |
|---|---|---|
| 成功 | 操作已完成且结果符合预期 | 提交成功、保存成功、发布成功 |
| 处理中 / 等待 | 操作正在进行或等待系统处理 | 导入中、审批中、任务执行中 |
| 警示 | 操作完成但存在部分异常或注意事项 | 部分成功、存在风险、需补充处理 |
| 错误 | 操作失败或无法继续 | 提交失败、校验失败、系统异常 |
| 信息 | 中性结果或说明性反馈 | 查询无结果、状态说明、提示信息 |

### 6.4 组件结构

Result 通常由以下内容组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|
| 状态图标 | 必需 | 表达成功、失败、警示、等待、信息等状态 |
| 标题 | 必需 | 简明说明结果 |
| 描述 | 可选 | 补充结果原因、处理建议或影响范围 |
| 操作按钮 | 可选 | 提供返回、查看详情、继续操作等下一步 |
| 明细区域 | 可选 | 展示结果列表、表格、错误明细、分组状态 |

### 6.5 布局形式

Result 可根据场景使用不同布局：

#### 居中卡片型

适用于单个操作结果。状态图标、标题、描述和按钮居中排列。

#### 横向列表型

### 7.1 定义

Notification 是系统主动推送的通知提醒，用于展示与用户相关的异步信息、后台任务状态、消息提醒或轻量反馈。它通常不阻断用户当前操作。

### 7.2 何时使用

适合使用 Notification 的场景：

- 后台任务完成、失败或需要查看详情。

### 11.1 定义

Message 是全局层面的轻量反馈提示，用于向用户反馈操作结果、状态变化、警告信息或错误信息。它通常出现在页面顶部居中位置，自动消失，是一种不打断用户当前操作的反馈方式。

Message 的核心作用是“即时告知”。它适合反馈用户刚刚完成的操作是否成功、失败或需要注意，但不适合承载复杂内容、长文本、后续处理任务或强制确认。

### 11.2 何时使用

适合使用 Message 的场景：

- 用户完成保存、提交、复制、删除等操作后，需要即时反馈结果。
- 操作成功后只需要一句短提示，例如“保存成功”“复制成功”。
- 操作失败后只需要短错误提示，例如“提交失败，请重试”。
- 用户输入或操作触发轻量校验反馈。
- 系统需要给出短暂、非阻断、自动消失的信息反馈。
- 页面内不需要留下长期可见的反馈内容。

不适合使用 Message 的场景：

- 需要用户点击按钮处理，应使用 Notification、Result 或 Modal。
- 需要展示较长说明、明细、表格或错误列表，应使用 Result、Drawer 或页面。
- 需要用户二次确认，应使用 Popconfirm 或 Confirmation Modal。
- 需要展示异步任务消息或系统推送，应使用 Notification。
- 需要展示加载占位或进度，应使用 Spin、Skeleton 或 Progress。

### 12.1 定义

Popconfirm 是一种轻量级的气泡确认框，用于在用户执行某个操作前进行就近确认。它通常依附于触发元素出现，适合低到中等风险、影响范围较小、确认文案较短的操作。

Popconfirm 的核心价值是“就地确认”。它比 Confirmation Modal 更轻量，不会强烈打断当前流程；但它仍然要求用户在继续操作前做出确认或取消。

### 12.2 何时使用

适合使用 Popconfirm 的场景：

- 对某个列表项、按钮、表格行操作进行二次确认。
- 删除、移除、取消、停用等低到中等风险操作。
- 操作影响范围明确，用户不需要阅读大量说明。
- 确认内容很短，一两句话即可说明。
- 希望保持用户当前位置，不打开居中弹窗。
- 操作入口与确认内容存在强空间关联。

不适合使用 Popconfirm 的场景：

- 高风险、不可逆或影响范围大的操作，应使用 Confirmation Modal。
- 需要展示详细影响、错误明细或复杂说明，应使用 Confirmation Modal 或 Drawer。
- 需要填写表单或配置参数，应使用 Functional Modal。
- 只是操作完成后的反馈，应使用 Message 或 Result。
- 气泡位置空间不足、容易遮挡关键内容时，不宜使用。

### 12.3 组件结构

Popconfirm 通常由以下元素组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|

| 操作按钮 | 必需 | 通常包含取消和确认，最多两个按钮 |

### 13.1 定义

Progress 用于展示任务执行进度，帮助用户了解当前任务已经完成多少、是否仍在进行、是否成功或失败。Progress 适合用于可量化进度的任务，例如上传、下载、导入、导出、批量处理、步骤执行等。

Progress 的核心前提是：系统能够提供相对明确的进度值、阶段或百分比。如果无法提供明确进度，应考虑使用 Spin 或 Skeleton。

### 13.2 何时使用

适合使用 Progress 的场景：

- 当前任务需要等待，且等待时间较长。
- 操作预计耗时超过短暂反馈时间，例如超过 2 秒。

- 上传、下载、导入、导出、批量处理等任务。
- 用户需要知道任务是否还在进行、完成多少、是否成功或失败。
- 页面内、弹窗内或模块内需要展示明确处理进度。

不适合使用 Progress 的场景：

- 无法计算进度或进度不准确，应使用 Spin。
- 页面首次加载内容时，需要占位，应使用 Skeleton。
- 只是操作完成后的反馈，应使用 Message 或 Result。
- 任务非常短，不需要展示进度。
- 需要展示系统主动推送的完成提醒，应使用 Notification。

### 14.1 定义

Skeleton 是在真实内容加载完成前展示的占位结构，用于预告页面或模块的内容布局，降低用户等待焦虑。它通常以灰色块、灰色线条、卡片占位等形式模拟真实内容结构。

Skeleton 的核心价值是“结构预期”。它不是单纯告诉用户正在加载，而是让用户提前感知页面即将出现的内容结构。

### 14.2 何时使用

适合使用 Skeleton 的场景：

- 页面首次加载，内容尚未返回。
- 网络较慢，需要等待接口响应。
- 图文信息、内容较多的列表、详情页、卡片区域加载中。
- 页面局部模块需要等待数据加载。
- 用户需要提前理解页面结构。
- 希望比 Spin 提供更好的视觉稳定性和用户体验。

不适合使用 Skeleton 的场景：

- 加载时间极短，展示 Skeleton 反而造成闪烁。
- 不知道最终内容结构，无法提供合理占位。
- 操作正在提交、保存或处理，应使用 Spin 或 Progress。
- 任务具有明确百分比，应使用 Progress。
- 只是操作成功或失败反馈，应使用 Message、Result 或 Notification。

### 14.3 组件结构

Skeleton 通常由以下元素组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|
| 占位块 | 必需 | 模拟图片、头像、卡片或大内容区域 |
| 占位线 | 必需 | 模拟标题、正文、字段、列表内容 |
| 容器 | 可选 | 与真实内容容器保持一致 |
| 动效 | 可选 | 可使用轻微闪烁或流光动效表示加载中 |

### 14.4 尺寸与布局

Skeleton 应尽量贴近真实内容的布局，而不是随意放置灰色块。

布局规则：

- 占位结构应与最终页面结构一致。
- 标题、正文、图片、卡片、列表应使用不同尺寸的占位。
- 占位线条可使用不同长度模拟真实文本节奏。
- 骨架屏高度应接近最终内容高度，减少加载完成后的布局跳动。
- 局部加载时，只替换加载中的区域，不应覆盖整个页面。
- 页面级加载时，可展示完整页面结构的骨架。

### 14.5 场景规则

#### 局部加载

当页面已有部分内容可见，只有某个模块、卡片、详情或列表仍在加载时，使用局部 Skeleton。这样可以避免全局遮挡，并保持页面可读性。

#### 页面首次加载

当主要内容尚未返回，但页面结构明确时，可以使用页面级 Skeleton。用户可以在等待过程中理解内容即将出现的位置和形态。

#### 卡片或列表加载

对于多条同构数据，例如列表、消息流、商品卡片、数据卡片，应使用重复的骨架单元模拟最终内容。

### 14.6 与 Spin 的区别

| 对比项 | Skeleton | Spin |
|---|---|---|
| 用户看到什么 | 内容结构占位 | 加载动画 |
| 适合内容 | 列表、详情、卡片、图文内容 | 操作处理、局部加载、未知结构加载 |
| 用户感知 | 页面即将出现什么 | 系统正在处理 |
| 视觉稳定性 | 更强，可减少跳动 | 较弱，只表达等待 |
| 示例 | 详情页加载、列表加载 | 保存中、查询中、按钮加载 |

### 15.1 定义

Spin 用于表示系统正在加载、查询、提交、保存或处理中。它适用于无法明确展示进度百分比，但需要让用户知道当前任务仍在进行的场景。

Spin 的核心作用是“表达等待”。它不展示完成比例，只告诉用户系统正在处理。若任务可以量化，应优先使用 Progress；若内容结构明确且属于页面加载，应优先使用 Skeleton。

### 15.2 何时使用

适合使用 Spin 的场景：

- 查询、保存、提交、加载等过程需要等待。
- 系统无法提供准确进度百分比。
- 局部区域正在加载或刷新。
- 按钮点击后需要防止重复提交。
- 弹窗、抽屉或页面局部区域正在处理。
- 数据表格、卡片区域、详情区域短时间加载。

不适合使用 Spin 的场景：

- 可以展示明确百分比，应使用 Progress。
- 页面内容首次加载且结构明确，应使用 Skeleton。
- 只是操作完成后的反馈，应使用 Message 或 Result。
- 后台异步任务完成提醒，应使用 Notification。
- 加载时间很长且无说明文案，会导致用户焦虑，应补充文案或改用 Progress / Result。

### 15.3 组件结构

Spin 通常由以下元素组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|
| 加载图标 | 必需 | 表示系统正在处理中 |
| 加载文案 | 可选 | 说明当前加载任务，例如“加载中”“保存中” |
| 遮罩层 | 可选 | 局部或全局遮罩，用于阻止重复操作 |
| 容器 | 可选 | 根据页面、模块、按钮或弹窗场景决定 |

### 15.4 类型

#### 局部 Spin

用于页面某个区域、卡片、表格、详情模块加载中。只覆盖相关区域，不影响其他区域操作。

#### 全局 Spin

用于整个页面或关键流程加载中。使用时应谨慎，避免长时间阻断用户。

#### 按钮 Spin

用于按钮提交、保存、加载过程中，表示该操作正在执行，并防止重复点击。

#### 弹窗内 Spin

用于弹窗内容加载、提交或查询中。可与遮罩结合，避免用户重复操作。

### 15.5 尺寸与布局

布局规则：

- 小尺寸 Spin 适合按钮、局部文本、轻量模块。
- 中尺寸 Spin 适合卡片、表格局部区域。
- 大尺寸 Spin 适合页面级或弹窗级加载。
- 局部 Spin 应居中于被加载区域。
- 全局 Spin 应居中于页面主内容区。
- 按钮 Spin 应与按钮文案保持对齐。
- 有文案时，文案应靠近加载图标，避免用户误解。

### 15.6 场景规则

#### 页面或模块加载

当页面局部模块正在请求数据且无法明确展示内容结构时，可以使用 Spin。若结构明确且加载时间相对可感知，优先使用 Skeleton。

#### 表格加载

表格刷新、筛选、查询时可使用局部 Spin，通常覆盖表格内容区域，保留表头或容器结构。

#### 弹窗、抽屉、下拉选择加载

当弹窗、抽屉或下拉内容需要异步获取数据时，可以在内容区展示 Spin。加载完成后替换为真实内容。

#### 按钮加载

用户点击提交、保存、确认后，按钮可进入加载态，避免重复点击，并表达操作正在执行。

### 17.1 定义

Alert 是页面内的信息提示组件，用于展示用户需要关注的重要信息、状态说明、风险提醒、规则提示或操作前后的补充说明。它通常嵌入在页面、表单、列表、卡片或模块内部，不会像 Message 一样自动消失，也不会像 Modal 一样强制打断用户。

Alert 的核心作用是“在页面中持续展示重要信息”。它适合承载比 Message 更长、更稳定的信息，也适合在用户浏览或操作过程中持续提醒用户注意某些规则、风险或状态。

### 17.2 何时使用

适合使用 Alert 的场景：

- 页面顶部需要展示业务规则、风险提醒、系统说明或状态提示。
- 表单、列表、详情页中需要展示持续可见的提示信息。
- 用户需要在操作过程中反复查看提示内容。
- 信息重要，但不需要强制用户立即确认。
- 提示内容比 Message 更长，且不适合自动消失。
- 需要在页面上下文中展示成功、提示、警告或错误信息。
- 某个模块、表格或流程存在特殊状态，需要在区域内明确说明。

不适合使用 Alert 的场景：

- 只需要一句短暂反馈，应使用 Message。
- 系统主动推送或后台异步提醒，应使用 Notification。
- 高风险操作前需要用户确认，应使用 Confirmation Modal 或 Popconfirm。
- 操作完成后需要展示完整结果，应使用 Result。
- 需要承载复杂表单、详情或配置内容，应使用 Drawer、Modal 或页面。
- 信息非常轻微，不应长期占用页面空间。

### 17.3 组件结构

Alert 通常由以下元素组成：

| 区域 | 是否必需 | 说明 |
|---|---|---|
| 状态图标 | 可选但推荐 | 表达成功、提示、警告、错误等信息类型 |
| 标题 | 可选 | 用于概括提示主题，适合较重要或较长的提示 |
| 描述内容 | 必需 | 展示具体说明、规则、风险或状态信息 |
| 操作链接 | 可选 | 提供“查看详情”“了解更多”等轻量操作 |
| 关闭按钮 | 可选 | 允许用户手动关闭提示 |
| 容器背景 | 必需 | 用颜色和边框表达提示状态 |

### 17.4 样式状态

Alert 常见状态包括：

| 状态 | 语义 | 使用场景 |
|---|---|---|
| 成功 | 操作或状态符合预期 | 配置已生效、信息已验证、任务已完成说明 |
| 提示 | 中性信息说明 | 页面规则、操作说明、系统提示 |
| 警告 | 存在风险或需要注意 | 数据异常、条件限制、操作风险提醒 |
| 错误 | 当前存在错误或阻塞问题 | 表单错误、系统异常、无法继续操作说明 |

### 17.5 是否展示图标和关闭按钮

Alert 可以根据场景决定是否展示图标和关闭按钮。

| 形态 | 适用场景 |
|---|---|
| 无图标、无按钮 | 普通说明类提示，信息较轻 |
| 有图标、无按钮 | 需要强调状态，但提示应持续存在 |
| 无图标、有关闭按钮 | 信息不强调状态，但用户可主动收起 |
| 有图标、有关闭按钮 | 状态明确，同时允许用户关闭 |

使用建议：

- 重要状态建议展示图标，提升识别效率。
- 临时提示可提供关闭按钮。
- 关键规则、风险或错误提示不建议默认可关闭，除非业务允许用户忽略。
- 如果 Alert 被关闭后会影响用户理解流程，应谨慎提供关闭入口。

| 图标与文字标题间距 | 8px |
| 文字与右侧关闭/操作按钮间距 | 16px |
| 右侧关闭按钮到容器边缘间距 | 12px |

##### 样式组合

支持四种组合形式：
1. 无图标 - 无按钮
2. 有图标 - 无按钮
3. 无图标 - 有按钮
4. 有图标 - 有按钮

##### 位置规则

Alert 通常出现在页面或模块内容区域中：
- 页面顶部：全局业务规则、风险提示、系统状态。
- 表单顶部：填写说明、校验提示、提交前注意事项。
- 表格顶部：筛选规则、数据范围、批量操作提醒。
- 卡片或模块内部：局部状态、异常说明、辅助提示。

布局规则：
- Alert 应靠近它所解释或影响的内容。
- 高度自适应，无固定强制值。
- 多个 Alert 同时出现时，按重要程度或业务流程顺序排列。
- Alert 不应遮挡页面内容，而是作为页面内容的一部分占位展示。

### 17.7 交互规则

- Alert 默认不阻断用户操作。
- 用户可以继续浏览或操作页面。
- 可提供关闭按钮，但关闭后是否再次出现需要根据业务决定。
- 可提供轻量操作链接，例如“查看详情”“了解规则”“重新配置”。
- 不应在 Alert 中放置复杂操作按钮组。
- 如果用户必须立即决策，应改用 Confirmation Modal 或 Functional Modal。
- 如果提示是短暂操作反馈，应改用 Message。
- 如果提示来自系统主动推送，应改用 Notification。

### 17.8 与 Message、Notification 的区别

| 对比项 | Alert | Message | Notification |
|---|---|---|---|
| 展示位置 | 页面或模块内部 | 页面顶部浮层 | 页面右侧或通知区域 |
| 展示时长 | 持续展示，通常不自动消失 | 短暂展示，自动消失 | 可停留较久，可关闭 |
| 信息复杂度 | 低到中 | 极低 | 低到中 |
| 触发来源 | 页面状态、业务规则、模块状态 | 用户刚刚完成操作后的即时反馈 | 系统推送或异步任务 |
| 是否占据布局 | 占据页面空间 | 不占据页面布局 | 通常浮层展示 |
| 典型场景 | 页面规则、风险提醒、表单说明 | 保存成功、复制成功 | 导出完成、审批提醒 |

### 17.9 与 Result、Modal 的区别

| 对比项 | Alert | Result | Confirmation Modal |
|---|---|---|---|
| 使用阶段 | 操作前、中、后都可使用 | 操作完成后 | 高风险操作前 |
| 是否阻断 | 不阻断 | 低到中 | 强阻断 |
| 信息作用 | 持续提醒或说明 | 展示最终结果 | 要求用户确认 |
| 内容位置 | 页面内嵌 | 页面、弹窗或容器中 | 居中弹窗 |
| 典型场景 | 页面顶部提示、表格提示、表单说明 | 提交成功、导入失败明细 | 删除确认、放弃修改 |

### 18. 弹窗/抽屉选型决策流程

本文档提供弹窗（Modal）、抽屉（Drawer）、气泡弹窗（Popover）和页面（Page）之间的选型决策逻辑。核心判断维度为：是否需要用户确认或选择、内容是仅查看还是需填写、内容量大小、以及是否有后续叠加操作。

#### 18.1 决策流程

**流程起点：操作入口点击**

##### 第一步：确认/选择判断

用户点击操作后，是否需要用户确认或选择后才能继续？

- **否，且内容仅查看** → 使用 **气泡弹窗（Popover）**
- **否，且内容非仅查看** → 使用 **非模态抽屉**
- **是** → 进入第二步

##### 第二步：内容类型判断（需要确认/选择时）

内容是否仅查看？

- **是，且内容 < 10 条** → 使用 **模态弹窗（Modal）**
- **是，且内容 ≥ 10 条** → 使用 **模态抽屉**
- **否** → 进入第三步

##### 第三步：表单内容量判断（内容非仅查看时）

表单内容是否 ≥ 10 条？

- **是** → 使用 **抽屉或页面**
- **否** → 进入第四步

##### 第四步：后续操作叠加判断

流程是否有后续操作需要叠加容器？

- **否** → 使用 **模态弹窗（Modal）**
- **是** → 进入第五步

##### 第五步：叠加场景选择

当前场景是否需要叠加？

- **是** → 使用叠加，最终导向 **页面**

#### 18.2 决策结果速查表

| 条件组合 | 推荐容器 |
|---------|---------|
| 仅查看内容（< 10 条） | 模态弹窗 |
| 仅查看内容（≥ 10 条） | 模态抽屉 |
| 需要确认/选择 + 表单内容 < 10 条 + 无后续叠加 | 模态弹窗 |
| 需要确认/选择 + 表单内容 ≥ 10 条 | 抽屉/页面 |
| 需要确认/选择 + 表单内容 < 10 条 + 有后续叠加 | 叠加 → 页面 |
| 无需确认/选择 + 仅查看内容 | 气泡弹窗 |
| 无需确认/选择 + 非仅查看内容 | 非模态抽屉 |

#### 18.3 核心原则

- 信息量大时优先用抽屉，信息量小时用弹窗。
- 轻量查看用气泡弹窗。
- 非模态抽屉用于无需打断用户流程的场景。
- 有后续叠加操作时，最终导向页面。
- 先判断是否需要用户确认/选择，再判断内容是仅查看还是需填写，然后看内容量大小，最后考虑是否有后续操作需要叠加。
