# 反馈与引导原则

## 这是什么

这是用于处理任务过程中的说明、提示、报错、阻断、恢复和引导的上位设计原则。

它服务体验判断与方案推导，不直接定义组件选型、视觉样式或实现细节。

## 适用范围

- 操作前说明限制、准备条件和风险
- 操作中反馈当前状态、进度和等待关系
- 操作后反馈结果、原因和下一步
- 新手认识型引导
- 当前任务型引导
- 异常阻断与恢复路径设计

## 不覆盖范围

- 不定义组件 API 和前端实现方案
- 不定义视觉规范和样式 token
- 不沉淀行业案例正文
- 不把具体组件形式写成硬规则

## F-01 先判断信息目的，再决定是否展示

- 来源：任务导向设计
- 定义：先判断当前信息是在解释结果、暴露限制、帮助理解，还是推动下一步，再决定是否展示和如何展示。
- 触发：页面出现说明、提示、报错、引导、阻断时。
- 推导输出：先回答“这条信息要帮助用户完成什么”，再决定它属于反馈还是引导。
- 文档落点：任务说明｜状态反馈｜异常与恢复
- 自检问句：如果删掉这条信息，用户到底会失去什么？
- 反模式：一看到失败就写报错；一看到复杂就加引导。
- 取舍提示：不是所有信息都值得展示，优先保留能改变用户决策的信息。

## F-02 能前置说明，就不要后置报错

- 来源：可预期性原则
- 定义：如果权限、状态、配置或前置条件在操作前已经已知，应尽量在用户动作前说明，而不是等失败后再解释。
- 触发：权限不足、状态不允许、配置缺失、需准备材料等场景。
- 推导输出：入口说明、置灰说明、前置提示优先于提交后报错。
- 文档落点：操作前说明｜限制提示
- 自检问句：用户是否必须点击一次失败后，才知道这件事做不了？
- 反模式：把可预见的限制全部做成提交后弹窗。
- 取舍提示：只有限制依赖实时状态、无法前置判断时，才保留后置阻断。

## F-03 反馈用于解释“刚刚发生了什么”

- 来源：系统状态可见性
- 定义：反馈用于解释刚刚发生的结果、状态变化或异常，不负责教学式介绍功能。
- 触发：提交成功、提交失败、处理中、状态改变、加载失败等。
- 推导输出：反馈至少回答结果、原因和下一步，不把用户留在不确定状态中。
- 文档落点：结果反馈｜异常反馈｜状态变化
- 自检问句：用户看完这条反馈后，是否知道现在发生了什么？
- 反模式：只说“操作失败”“请检查”，不说原因和去向。
- 取舍提示：轻反馈写重点；复杂失败再分层承载细节。

## F-04 引导用于支持“接下来怎么做”

- 来源：任务支持设计
- 定义：引导用于帮助用户理解路径、准备条件或后续动作，核心是支持决策和完成任务，而不是解释刚刚失败的结果。
- 触发：首次接触复杂功能、任务前准备、结果后下一步承接、关键路径中断时。
- 推导输出：引导要围绕任务路径组织，而不是围绕组件说明组织。
- 文档落点：新手引导｜任务引导｜恢复引导
- 自检问句：这条信息是在解释结果，还是在帮助用户继续行动？
- 反模式：把报错文案写成教学说明，把引导写成结果提示。
- 取舍提示：用户已经在执行任务时，引导要尽量短，避免重新开始教学。

## F-05 新手指引与任务引导不是一回事

- 来源：学习成本与执行成本区分
- 定义：新手指引用于帮助用户认识功能和建立整体理解；任务引导用于帮助用户完成当前任务或承接下一步。
- 触发：首次使用、新功能曝光、复杂任务开始前、任务完成后承接等。
- 推导输出：先判断用户缺的是“功能认知”还是“当前步骤支持”。
- 文档落点：首次使用｜任务前后引导
- 自检问句：用户是不知道这是什么，还是不知道下一步怎么做？
- 反模式：把所有引导都做成 Tour；把所有说明都归到“新手指引”。
- 取舍提示：同一功能可以同时存在新手指引和任务引导，但两者目的不能混写。

## F-06 强阻断只用于高风险、高影响、不可逆场景

- 来源：打断成本控制
- 定义：只有当错误会造成高风险、不可逆损失、重大状态变化或必须显式确认时，才升级为强阻断。
- 触发：删除、结账、提交不可撤销动作、跨字段复杂异常、关键外部失败等。
- 推导输出：字段问题、轻量失败、终态提醒和持续状态，不默认使用强阻断。
- 文档落点：阻断策略｜确认策略
- 自检问句：如果不阻断，会不会造成实际损失或错误决策？
- 反模式：所有异常都弹窗；所有提醒都要求确认。
- 取舍提示：阻断越强，越要给出充分理由和明确去向。

## F-07 轻问题优先就地解释，避免全局打断

- 来源：最小打扰原则
- 定义：局部问题优先在局部解释，让用户在原位置完成修正，不把本地问题升级成全局打断。
- 触发：字段校验、上传校验、单区域失败、局部状态提示。
- 推导输出：字段附近、上传区域、模块内部提示优先于全局提示和弹窗。
- 文档落点：局部反馈｜表单校验
- 自检问句：用户是否必须离开当前视线位置，才能知道哪里错了？
- 反模式：字段错误弹窗化；局部失败全局化。
- 取舍提示：局部反馈要保证可见，避免提示虽然就地但仍难以发现。

## F-08 持续状态要可见，不要让用户反复触发后才知道

- 来源：状态可见性
- 定义：锁定、流程中、处理中、冻结、已结账等持续状态，应在页面中持续可见，而不是每次点击才出现一次性提示。
- 触发：状态限制会持续影响一段时间时。
- 推导输出：持续状态优先做成页面状态区、Banner、入口说明、禁用说明等可见结构。
- 文档落点：状态表达｜持续限制
- 自检问句：用户如果不点击，能否提前知道当前状态会影响哪些操作？
- 反模式：用户每点一次，都弹一次同样的“当前不可操作”。
- 取舍提示：持续可见不等于持续打扰，表达要稳定但不过度占位。

## F-09 技术原因必须转译成用户语言

- 来源：可理解性原则
- 定义：内部错误原因、技术术语和实现细节，必须转译成用户能理解的业务对象、状态、影响和行动建议。
- 触发：接口异常、登录失效、字段校验、外部系统失败、状态机异常等。
- 推导输出：不直接暴露接口名、token、HTTP 状态码、数据库字段名、英文裸错误。
- 文档落点：文案转译｜异常说明
- 自检问句：这句话用户是否能据此做出正确行动？
- 反模式：把技术日志直接展示给用户。
- 取舍提示：如必须保留专业词，只保留用户需要识别的最小集合。

## F-10 反馈和引导都必须指向明确下一步

- 来源：行动闭环
- 定义：无论是反馈还是引导，都应帮助用户继续推进任务、回退到安全路径，或明确等待条件。
- 触发：成功、失败、阻断、引导结束、任务结果承接时。
- 推导输出：给出重试、返回列表、去设置、联系角色、等待结果、继续下一任务等明确路径。
- 文档落点：恢复路径｜下一步设计
- 自检问句：用户看完之后，是否知道下一步该做什么？
- 反模式：只告诉用户“不能做”“已失败”，不提供后续动作。
- 取舍提示：下一步不一定总是按钮，也可以是等待条件、责任角色或返回去向。
