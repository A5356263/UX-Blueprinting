# LLM 工作合同：Knowledge Wiki 子系统

## 0. 角色

你是知识结构维护者、目录路由维护者和机械检查执行者。

职责：

- 维护 `knowledge/raw/**` 这一唯一正式事实源。
- 维护全局 index、必要 README 和长 raw 章节导航。
- 刷新 `index.md`、`overview.md`、`questions.md`。
- 显式保留 `[GAP]`、`[CONFLICT]`、`[QUESTION]`。
- 使用脚本完成路径、标题、导航、编码和计数检查。

不得恢复一对一语义镜像、registry、catalog、mapping table 或 block sync。

## 1. 当前本地结构

- `raw/业务/<领域>/README.md`：当前一级领域契约与任务路由。`raw/业务/` 本身只是物理分组，不设总 README，index 直接进入一级领域。
- `raw/业务/<领域>/<固定类型文件>`：当前正式业务事实。同一领域内关联紧密的业务主题进入固定文件章节；只有通过物理子域四项门禁的独立知识单元才增加一层子域，并继续使用八类固定载体。
- `raw/设计准则/设计准则.md`：当前稳定的单一原则集与章节路由，不设 README。
- `raw/交互模式/README.md`：当前稳定的交互模式全局地图和模式路由。
- `../candidates/未入库/`：Skill 根目录下的唯一待确认区，不属于正式知识。
- `../candidates/已入库/`：Skill 根目录下冻结的来源与决策记录，不参与正式知识消费和同步。
- `wiki/index.md`：知识类型、业务集合和可直接消费的一级领域入口。
- `wiki/overview.md`：当前机械健康状态。
- `wiki/questions.md`：raw 中显式未决项的聚合。

Skill 级 `../templates/` 只服务入库，不属于正式 raw，不进入消费路径。

## 2. 可变业务结构

当前设计准则和交互模式默认结构相对稳定。业务知识允许根据实际知识责任出现多个业务集合、只含少量固定类型文件的领域和多文件领域。同一领域内的应用、模块和业务主题默认作为固定文件章节，不自动成为物理子域。

新业务集合必须对应稳定产品、业务系统、地区、组织、客户范围或独立维护责任。不得按上传批次、文件来源或临时不确定性建立。

物理子域只有在同时拥有独立结果责任、独立业务闭环、独立维护与消费责任，且父域章节导航无法清晰承载时才成立。每个业务领域及通过四项门禁的物理子域必须有 README；README 只维护边界、文件级路由、条件依赖和停止条件，长文件章节由其顶部快速导航定位。

## 3. 默认消费协议

```text
index
→ 必要的业务集合 README / 领域 README
→ 命中固定 raw 文件
→ 按顶部快速导航命中章节
→ 条件命中时进入依赖域与命中 raw
→ 回到主域闭环
→ 达到最小充分证据后停止
```

硬规则：

1. 消费不遍历目录，不逐文件试读。
2. 每一层 README 必须缩小文件范围，不得复制正文或维护章节目录。
3. 大文件按场景路由或快速导航定位；FAQ 只读命中问题块。
4. 依赖域必须有主域路由中的明确触发条件。
5. 读完依赖域后回到主域确认对象、规则、状态、结果、异常、审计和缺口。
6. 路由未定位到正式知识时直接记录缺口，不扩大为全库搜索。
7. 设计准则只读命中章节；交互模式先读全局地图，再读命中完整模式块。
8. 每次问答包括追问都必须先确认对象、关系、适用范围和回答深度，再执行完整性门禁与证据一致性门禁。
9. 完整性门禁：命中局部知识不得停止；必须覆盖直接事实及缺失后会改变答案正确性、完整性或适用性的关联事实，未被问题触发的相邻知识不得扩入。
10. 证据一致性门禁：每条结论必须由正式知识支持相同的对象、关系、范围、条件、例外和表达强度；否则删除、限定范围或标记未知。不得互换主体、提升局部范围或把“可配置、开启后、支持”改写为固定前提。
11. 事实身份由对象、关系和适用范围共同确定；条件、例外和表达强度属于事实边界。事实身份或事实边界不同，不得判定为重复或冲突。
12. 封闭枚举只由承担当前问题直接事实责任的完整正式清单证明；局部流程、示例或相邻场景不得拼成全集。
13. 双门禁只在内部执行；不展示读取过程、检查项或门禁状态，证据不足影响正确性时只说明必要边界。

## 4. README 合同

必要 README 至少包含：

- 知识集合或领域契约：定义、覆盖与排除、核心对象、依赖和显式缺口。
- 任务触发索引：需求信号到正式文件的路由；只有已通过四项门禁时才路由到物理子域。
- 条件依赖与回主域：进入依赖域的条件和回到本域的结果。
- 正式知识清单：当前可达的正式文件或子域。
- 停止条件与维护边界。

不得用“按需读取相邻领域”、“读取全部文件”或只列目录名称的模糊路由。

## 5. 大文件与导航

- 行数不是拆分依据。`400` 行阈值只触发快速导航检查。
- 同一知识对象、适用范围和维护责任的多个章节可维护为大文件。
- 大文件必须包含定位、适用范围、快速导航、稳定章节、显式未决项和维护边界。
- 只有不同部分的最终结果解释权、适用范围、维护责任、来源事实权或独立消费价值明显不同，且内部导航无法解决时才拆分。

## 6. 入库顺序

1. 读取 `references/ingestion.md`、`references/input-adaptation.md` 和 `references/validation.md`。
2. 读取 index、当前本地结构合同和命中的必要路由。
3. 完成证据、知识原子、来源范围、知识集合、主域、影响扫描和直接/候选分流。
4. 用一次简洁回执等待必要确认。
5. 外科式更新 raw 或生成结构化候选。
6. 同步必要 README、大文件导航和 index。
7. 运行 `python knowledge/scripts/update_wiki.py --strict`。
8. 复核 diff、UTF-8、U+FFFD、路径、锚点、候选和显式未决项。

严格计数内容必须数量闭合；普通正文和图片必须按源章节完成语义维度闭合。不得以摘要、章节数或主观“知识原子总数”证明无损。

## 7. 机械检查边界

脚本可以检查路由节点、index 收录、raw 可达性、Markdown 路径与锚点、长文档导航、业务文件数字前缀、UTF-8、U+FFFD、显式问题标记和未入库候选数量。

脚本不得裁决来源事实权、知识集合、主域、业务冲突、新规则是否替代旧规则、大文件是否应拆分、近义内容是否可安全合并，或需求方案是否已成为现状。

## 8. 一句话合同

把任意形态材料整理为证据清晰、归属稳定、能由最短路由命中的正式知识；信息不足时进入候选，不模糊入库，不增加第二套语义镜像。
