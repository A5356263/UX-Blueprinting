# Knowledge Ingestion Skill

## 1. Skill 目标

将任意新知识安全并入目标项目已有知识库。

本 skill 不规定目标知识库必须长什么样。

它的职责是：

1. 识别目标知识库契约
2. 判断新知识是否值得入库
3. 过滤过程信息和噪声
4. 决定新建、合并、更新或暂存
5. 按目标知识库现有结构写入
6. 维护入口、索引、问题、日志
7. 调用维护脚本，或由 AI 直接维护相关文件
8. 输出清晰的变更说明

核心原则：

> 先读懂目标知识库，再安全入库。  
> 不把所有项目强行整理成同一种结构。

---

## 2. 适用输入

本 skill 支持任意形态的新知识输入，包括但不限于：

- Markdown 文档
- 普通文本
- 帮助中心文档
- 产品说明
- 业务规则
- 设计规范
- 体验原则
- 会议纪要
- 表格
- 问答记录
- 页面截图解析结果
- 视频解析结果
- 外部对标资料
- 采集产物
- 零散补充信息

输入不需要是标准格式。

AI 必须先做输入识别和归一化，再决定是否入库。

---

## 3. 禁止行为

严禁：

- 未识别目标知识库契约就直接写入
- 把所有输入都塞进正式知识层
- 把过程日志、采集记录、失败记录写入正式知识
- 把 AI 推测写成事实
- 擅自裁决业务冲突
- 覆盖原始真源
- 强行新建领域
- 为了整齐而补不存在的编号文件
- 强制创建 summary、wiki、raw、scripts 等结构
- 把入口层内容写成第二套真源
- 建立复杂强依赖知识图谱

---

## 4. 第一步：识别目标知识库契约

处理任何新知识前，必须先识别目标知识库的现有约定。

优先读取：

```text
README.md
LLM.md
AGENT.md
CONTRIBUTING.md
docs/
knowledge/
wiki/
kb/
scripts/
已有知识文件样例
```

必须判断：

```text
1. 真源层在哪里
2. 入口层在哪里
3. 是否有 summary / index / README / wiki
4. 是否有问题池
5. 是否有维护日志
6. 是否有来源台账
7. 是否有过程产物目录
8. 是否有维护脚本
9. 是否有命名规则
10. 是否有编号规则
11. 是否有示例文件可参考
```

如果目标项目没有明确契约，AI 应基于现有目录和样例推断最小契约，并在输出中说明推断依据。

---

## 5. 目标知识库契约识别结果

入库前，AI 必须先形成简短判断：

```md
## 目标知识库契约判断

- 真源层：
- 入口层：
- 问题池：
- 日志：
- 过程产物：
- 来源台账：
- 维护脚本：
- 命名规则：
- 编号规则：
- 本次应遵守的入库方式：
```

如果缺少某项，写：

```text
未发现
```

不要为了补齐结构而强行创建。

---

## 6. 输入归一化

AI 需要先将输入拆成 4 类信息。

### 6.1 可入库事实

符合以下条件的信息可以作为入库候选：

- 稳定
- 可复用
- 能支撑后续判断
- 属于业务、产品、体验、设计、规则、流程、对象、页面、状态、字段、权限、依赖、异常等知识
- 有明确来源或上下文

### 6.2 过程信息

以下内容不进入正式知识层：

- 采集过程
- 工具调用记录
- 覆盖率
- 访问路径
- 失败日志
- 截图失败
- 视频解析失败
- 页面加载失败
- 临时分析
- 执行记录
- AI 的工作过程

应放入目标知识库的过程产物、日志或报告目录。

### 6.3 不确定信息

以下内容必须显式标记：

```text
[GAP] 信息缺口
[CONFLICT] 信息冲突
[QUESTION] 待确认问题
```

不得自动补全。

### 6.4 无入库价值信息

以下内容默认不入库：

- 页脚
- 联系方式
- 二维码
- 备案信息
- 法律声明
- 营销口号
- 无产品知识价值的宣传信息
- 重复噪声
- 与目标知识库无关的信息

---

## 7. Raw Eligibility Gate：正式知识入库门槛

只有通过以下检查，信息才能进入正式真源层。

```text
[ ] 是否稳定
[ ] 是否可复用
[ ] 是否能支撑后续判断
[ ] 是否有明确来源
[ ] 是否不是过程信息
[ ] 是否不是临时日志
[ ] 是否不是 AI 推测
[ ] 是否与目标知识库范围相关
[ ] 是否可归入已有领域或有必要新建领域
```

未通过时：

```text
归属不明 → 放入 inbox / 待处理区
过程信息 → 放入 log / outputs / reports
冲突信息 → 标记 [CONFLICT]
缺口信息 → 标记 [GAP]
待确认信息 → 标记 [QUESTION]
无价值噪声 → 不入库
```

---

## 8. 新建、合并、更新、暂存判断

AI 入库前必须判断本次新知识属于哪种情况。

### 8.1 合并到已有知识

符合以下情况时，优先合并：

- 与已有领域一致
- 补充已有对象、规则、页面、流程、场景
- 修正已有内容
- 增加明确案例或限制
- 是已有文件的自然延展

### 8.2 新建知识文件

符合以下情况时，可以新建：

- 已有知识库没有对应承载文件
- 信息稳定且可复用
- 内容量足够独立
- 不适合塞入已有文件
- 可以形成清晰主题

### 8.3 新建领域

只有满足以下条件，才新建领域：

- 输入包含一组独立业务对象、能力、流程或规则
- 与已有领域边界明显不同
- 后续很可能继续补充
- 不是一次性材料
- 不是临时项目记录

### 8.4 暂存

以下情况进入 inbox / 待处理区：

- 归属不明
- 来源不完整
- 内容不稳定
- 信息需要人工确认
- 与多个领域有关但关系不清
- 需要进一步拆分

### 8.5 不入库

以下情况不入库：

- 纯过程日志
- 工具失败记录
- 重复材料
- 无知识价值内容
- 与项目无关内容

## 9. 编号和命名规则

如果目标知识库已有编号规则，必须遵守。

如果没有编号规则，不要强行引入。

如果有编号段，可按“知识槽位”理解，而不是强制模板。

常见编号槽位：

```text
00      领域总览
01-04   边界 / 术语 / 对象 / 关系
10-19   能力 / 场景 / 路径 / 页面承载
20-29   规则 / 决策 / 治理 / 审计
30-39   体验风险 / 文案解释 / 体验转译
40-49   下游消费 / 交接 / 蓝图映射
50+     外部资料 / delta / 差异 / 补充来源
```

规则：

- 编号是可选槽位
- 不符合槽位时不要硬套
- 不要求每个领域补齐所有编号
- 不为了整齐制造空文件
- 优先匹配目标项目已有命名风格

---

## 10. 写入真源层

如果目标知识库存在真源层，AI 应将稳定事实写入真源层。

真源层写入要求：

- 保留事实
- 保留来源
- 保留上下文
- 结构清晰
- 不写 AI 推测
- 不混入过程信息
- 不裁决冲突
- 不抹平缺口
- 不为了好看牺牲准确性

推荐结构，仅在目标项目没有模板时使用：

```md
# 标题

## 文件定位

说明本文件解决什么判断问题。

## 来源与范围

- 来源：
- 适用范围：
- 不适用范围：

## 核心事实

按对象、能力、流程、页面、规则、状态、字段组织。

## 明确规则

只写输入材料中明确出现的规则。

## 前置条件 / 依赖关系

记录明确出现的前置、依赖、影响关系。

## 边界与例外

说明容易混淆的边界和例外。

## 缺口 / 冲突 / 待确认

- [GAP] ...
- [CONFLICT] ...
- [QUESTION] ...
```

如果目标项目已有 raw 模板，优先使用目标模板。

---

## 11. 入口层维护

不要预设目标知识库一定有 summary。

AI 必须先判断目标项目的入口层是什么：

```text
summary
index
README
wiki
catalog
manifest
navigation doc
其他入口页
```

### 11.1 如果目标知识库有 summary

按目标项目已有 summary 契约生成或更新。

要求：

- 不机械摘录
- 不写成第二套真源
- 不冒充证据
- 只承担导航、定位、路由或入口职责
- 需要细节时指向真源层

如果目标项目将 summary 定义为 AI 路由卡，则 summary 应回答：

```text
1. 这份真源解决什么判断问题
2. 哪些任务会触发它
3. 它覆盖哪些对象、能力、页面、规则、状态、风险
4. 哪些稳定结论可用于导航判断
5. 什么时候必须回查真源
6. 有哪些 GAP / CONFLICT / QUESTION
```

但不要把这些字段强制用于所有项目。

### 11.2 如果目标知识库没有 summary

不要强行创建 summary。

应维护现有入口，例如：

- index
- README
- catalog
- docs 目录导航
- 知识清单

入口层只负责帮助 AI 或人找到真源，不应替代真源。

---

## 12. 问题、冲突和缺口处理

任何不确定信息必须显式保留。

### 12.1 GAP

用于信息缺口。

```md
- [GAP] 当前材料未说明 xxx。
```

### 12.2 CONFLICT

用于来源冲突。

```md
- [CONFLICT] A 来源与 B 来源对 xxx 的描述不一致。
```

### 12.3 QUESTION

用于待人工确认。

```md
- [QUESTION] 是否需要将 xxx 独立成领域？
```

规则：

- 不自动抹平
- 不擅自补全
- 不写成确定结论
- 如果目标知识库有问题池，必须同步
- 如果没有问题池，应写入对应文件的待确认区或维护日志

---

## 13. 过程信息处理

过程信息不得进入正式知识正文。

过程信息包括：

- 采集覆盖率
- 失败项
- 工具错误
- 浏览器操作记录
- 截图失败
- 视频解析失败
- 访问路径
- 执行日志
- 临时判断
- AI 操作记录

处理规则：

```text
目标知识库有 outputs / reports / logs → 放入对应目录
目标知识库有 log.md → 写入维护记录
没有明确位置 → 新建最小 process log，或在最终报告中说明未写入
```

不要污染真源层。

---

## 14. 来源台账

如果目标知识库有来源台账，必须更新。

来源台账可记录：

```text
source_id
source_title
source_path
target_path
source_type
source_origin
source_confidence
status
last_verified_at
notes
```

如果没有来源台账，不要强行创建，除非目标项目已有类似机制或用户要求。

---

## 15. 脚本协作规则

本 skill 不绑定任何脚本名。

AI 必须先发现目标知识库是否有维护脚本。

查找位置：

```text
scripts/
knowledge/scripts/
tools/
package scripts
README / LLM / docs 中的维护命令
```

### 15.1 如果存在主入口脚本

优先调用主入口脚本完成刷新和检查。

例如目标项目可能提供：

```text
update_wiki
build_index
refresh_docs
lint_knowledge
generate_summary
```

AI 应按目标项目说明执行。

### 15.2 如果没有维护脚本

由 AI 直接维护目标知识库中的相关文件。

这表示：

```text
AI 写文件
AI 更新入口页
AI 更新问题池
AI 更新日志
AI 更新索引
AI 输出检查结果
```

不是让用户手动维护。

### 15.3 脚本不能做的事

即使有脚本，也不能让脚本做语义裁决。

脚本适合：

- 扫描
- 建索引
- 更新统计
- 检查链接
- 刷新报告
- 生成骨架
- 校验结构

脚本不应：

- 判断业务规则真伪
- 裁决冲突
- 编造结论
- 用关键词替代语义理解

## 16. 帮助中心 / 采集产物入库规则

当输入是帮助中心采集结果时，必须分层处理。

### 16.1 可作为候选知识

通常来自：

```text
help/modules/**
docs/articles/**
manuals/**
```

可入库内容：

- 产品功能
- 操作流程
- 配置步骤
- 字段说明
- 明确规则
- 前置条件
- 依赖关系
- 异常说明
- 注意事项
- FAQ 正文
- 图片 / 视频中明确识别的产品信息

### 16.2 不进入正式知识

通常来自：

```text
_collection/
coverage
process-log
failed-items
crawler-log
screenshots-log
```

这些只作为入库参考，不作为正式知识。

### 16.3 未完成采集

如果采集覆盖率不完整，不要假装完整。

处理方式：

- 已采集正文可以入库
- 未采集模块标记为 `[GAP]`
- 采集失败留在过程记录
- 不把失败原因写成产品知识

### 16.4 关联关系

帮助文档中明确出现的关系可入库：

- 前置条件
- 数据依赖
- 权限依赖
- 审批依赖
- 状态影响
- 配置影响
- 流程后置影响

未明确出现的关系不得推断。

---

## 17. 更新已有知识时的原则

更新已有知识时，优先做最小变更。

步骤：

1. 找到最接近的已有知识文件
2. 判断是否合并、补充、修正或冲突
3. 保留旧内容
4. 新内容注明来源或上下文
5. 有冲突时标 `[CONFLICT]`
6. 不直接覆盖原判断
7. 同步入口层和问题池
8. 写入维护日志

如果不确定，应放入 inbox / 待处理区。

---

## 18. AI 入库执行流程

标准流程：

```text
1. 读取目标知识库契约
2. 识别输入类型
3. 过滤过程信息和噪声
4. 判断可入库事实
5. 判断新建 / 合并 / 更新 / 暂存 / 不入库
6. 写入真源层或待处理区
7. 按目标契约维护入口层
8. 标记 GAP / CONFLICT / QUESTION
9. 更新来源台账、问题池、日志
10. 调用维护脚本，或由 AI 直接刷新入口文件
11. 执行检查
12. 输出变更报告
```

---

## 19. 验收清单

每次入库后必须检查：

```text
[ ] 是否已读取目标知识库契约
[ ] 是否未强行套用固定结构
[ ] 是否过滤过程信息
[ ] 是否只把稳定事实写入真源层
[ ] 是否判断了新建 / 合并 / 更新 / 暂存
[ ] 是否处理了 GAP / CONFLICT / QUESTION
[ ] 是否维护入口层
[ ] 是否更新问题池或待确认区
[ ] 是否更新日志或变更记录
[ ] 是否更新来源台账（如存在）
[ ] 是否调用维护脚本（如存在）
[ ] 是否由 AI 直接维护系统文件（如无脚本）
[ ] 是否没有把入口层写成第二套真源
[ ] 是否输出了清晰变更说明
```

## 21. 最终判断原则

始终遵守：

> 目标知识库优先。  
> 真源层优先。  
> 稳定事实优先。  
> 过程信息隔离。  
> 不确定项显式保留。  
> 入口层只做导航，不替代真源。  
> 有脚本用脚本，无脚本由 AI 维护文件。  
> 不把所有项目整理成同一种结构。
