# 问题与业务方案

本 Skill 把已形成的问题和证据收敛为正式问题与主推荐业务方案。它是问题驱动路线的方案定义环节，与 PRD Review 主链平行；它不生成需求基线、体验定案或交互方案。

## Step 0 · 运行入口

### Step 0.1 · 本 Skill 产物状态

执行前只检查以下正式产物是否存在：

- `spark-output/problem_framing.md`
- `spark-output/context/problem-framing.json`

存在时仅提示“检测到本 Skill 已有正式产物（已产出）”，继续按当前用户输入执行。已有产物不改变当前任务类型，也不自动触发下游。

### Step 0.2 · 上游读取

按以下顺序读取：

1. 用户当前提供的问题描述、目标、约束和背景。
2. 用户明确指定的文件、链接或正式上游产物。
3. 用户明确要求基于已有产物继续时，读取其 Markdown 正文；JSON 只定位产物类型和正文路径。

原始数据集、批量工单、未整理聊天记录和待诊断界面证据，先由对应上游分析能力形成问题描述、证据结论或正式诊断结论。本 Skill 接收这些结论，不执行统计、聚类、原始材料清洗或界面证据诊断。

Markdown 与 JSON 同时存在时，以 Markdown 为正式语义源。只有 JSON 而缺少对应 Markdown 时，先请用户补充正式语义源。

### Step 0.3 · 输入校准与模式判断

正式 PRD 的审核任务交给 `prd-review`；界面证据诊断任务交给 `interface-audit`；明确要求体验定案时使用 `uxb`；明确要求交互方案时使用 `experience-blueprint`。用户明确要求本 Skill 时，按本 Skill 执行。

选择一个内部模式：

- `problem-definition`：已有问题现象或证据，正式问题、目标或解决方向尚未明确。
- `direction-correction`：已有方向被用户质疑，或正式证据说明它不能解决问题、遗漏关键前提或违反业务约束。

已有方案本身不构成方向纠偏证据。模式只改变分析重点，正式产物和 Handoff 保持一致。

## 职责与边界

本 Skill 负责：

- 明确谁遇到什么问题、当前如何处理、目标结果和影响方案选择的约束。
- 校准正式业务对象、既有能力边界、角色责任和关键规则。
- 形成、比较业务方案并确定一个主推荐方案。
- 输出可供用户故事、用户旅程和可选 UXB 消费的正式问题与业务方案。

本 Skill 不负责：

- PRD 审核、需求基线和完整 PRD。
- 原始数据分析、工单聚类和现有界面诊断。
- 用户故事、用户旅程、体验策略定案。
- 页面、组件、布局、具体交互和文案。
- 完整权限、状态、异常、字段、验收用例、埋点、排期和技术方案。

## Step 1 · 问题与证据校准

进入方案比较前，确认以下信息：

1. 问题来源或证据。
2. 主要受影响角色或业务对象。
3. 当前发生了什么或当前如何处理。
4. 期望达到什么结果。
5. 会改变方案选择的已知约束。

缺失项会改变正式问题或主推荐方案时，向用户追问最少必要信息。缺失项只影响局部展开时，记录为待确认事项。

区分三层信息：

- 已确认事实：用户明确提供或业务知识可证实的当前事实和约束。
- 工作假设：为继续比较方案暂时采用的判断。
- 待确认事项：答案会改写主推荐方案的问题。

### Step 1.5 · 业务知识锚定

当业务对象、已有能力边界、角色责任或关键规则影响方案成立时，读取与该判断直接相关的业务知识。

读取方式：

1. 先明确当前需要校准的判断问题。
2. 读取 `knowledge-wiki` 的 `knowledge/wiki/index.md` 定位主域。
3. 按主域 README 的实际路由读取对应 raw 文件和章节。
4. 补读已触发的相邻依赖，直到当前业务对象、能力边界、角色责任、规则或依赖可被说明。

知识用于校准当前事实与方案成立条件。正式产物只记录命中领域、已读章节、用于校准的判断和仍无法确认的内容，不复述知识原文。

## Step 2 · 形成业务方案

进入本步骤时，完整读取 `references/business_solution_guide.md`。

优先形成 2—3 个在业务机制、角色责任、业务过程或能力组合上有实质差异的方案。每个方案说明：

- 解决目标和面向角色。
- 需要新增、修改、复用或停止的业务能力。
- 角色责任或协作关系的变化。
- 核心业务过程。
- 成立条件、依赖、风险和适用边界。

已确认事实、约束或目标排除的方向，可保留排除理由。只有一个方向具备成立条件时，输出该方案并说明其他方向的排除依据。没有方向具备成立条件时，在聊天中说明缺少条件；得到补充后从 Step 1 继续。

## Step 3 · 比较与主推荐

先排除与已确认事实冲突、无法解决正式问题、缺少关键成立条件、无法形成业务闭环或明确超出范围的方案。

对其余方案比较：问题匹配度、证据支持度、用户与业务价值、业务闭环、现有能力复用、组织运营系统依赖、风险与副作用。

确定一个主推荐方案。推荐理由必须能指向输入证据、正式问题或已确认约束。

方向纠偏模式额外说明：当前方向为何不成立、跳过了什么关键前提、主推荐方案如何处理该问题。

主推荐方案写清业务机制、角色责任、核心过程、成立条件和可观察的成效信号后停止。成效信号使用可观察结果，例如任务是否完成、人工环节是否减少、责任是否清楚；没有证据时不填数值目标。

## 输出结构

输出到：

- `spark-output/problem_framing.md`
- `spark-output/context/problem-framing.json`

Markdown 固定结构：

```markdown
# 问题与业务方案：{主题}

## §0 关键结论
## §1 问题来源与证据
## §2 正式问题
## §3 目标角色、现状、目标结果与成效判断
## §4 方案成立条件
## §5 候选业务方案
## §6 方案比较
## §7 主推荐业务方案
## §8 业务能力、角色责任、核心过程与关键规则
## §9 范围与不做什么
## §10 风险、依赖与待确认事项
## §11 下游承接要求
## §12 知识锚定
```

先写结论，再写依据。使用短段落、小标题和短列表。方案比较可以使用表格。相同结论只在最相关章节完整表达。

`confirmed_facts` 只记录当前事实和约束。主推荐方案属于未来解决办法，写入 `recommended_solution` 和 `business_solution_points`。工作假设与待确认事项保持不确定状态。

## Context JSON 写入

写入前完整读取 `references/context-schema.md`。JSON 只从完成的 Markdown 投影；校验失败时只修改 JSON。运行：

```bash
node {skill_dir}/scripts/validate-context.js spark-output/context/problem-framing.json
```

## 预览交接

正式产物完成后，用户明确确认需要预览时，再交给 `preview-renderer`。预览不改变正式 Markdown、Context、主链流转或 Handoff。

## Handoff · 固定下一步

正式产物写入并校验通过后，运行：

```bash
node shared-workflow/generate-progress-preview.js
```

失败时记录告警并继续 Handoff。只检查以下产物是否存在；存在时在名称后追加“（已产出）”：

- 用户故事：`spark-output/stories.md` 或 `spark-output/context/stories.json`
- 用户旅程：`spark-output/journey_analysis.md` 或 `spark-output/context/journey-analysis.json`

固定输出：

```text
问题与业务方案已完成。你可以继续：
1. 用户故事（推荐）
2. 用户旅程（推荐）

可选增强：
- UXB：形成项目级体验策略与关键体验取舍

你回复对应名称即可。
```

等待用户选择，不自动执行下一步。

## 质量标准

- 正式问题、主要角色、当前现状、目标结果和关键约束可追溯。
- 候选方案具有实质业务差异；单一可行方向说明排除依据。
- 主推荐方案可被下游承接，且没有扩展成完整 PRD 或交互方案。
- 当前事实、未来方案、工作假设和待确认事项保持分层。
- JSON 是 Markdown 投影，不补造事实或结论。
