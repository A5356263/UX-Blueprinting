# Experience Blueprint

这个 skill 负责读取正式需求基线和可选 UXB 体验定案，并把它们展开为完整的交互设计方案。默认只输出 Markdown 与 Context JSON；如需预览，交给 `preview-renderer`。

本次调整保持 `§0-§9` 正文分析骨架，只补足任务内触发、知识消费边界和正式产物收口规则。

## Step 0 · 运行入口

### Step 0.1 · 本 Skill 产物状态

执行本 Skill 前，只检查本 Skill 对应正式产物是否存在。

正式产物：
- `spark-output/experience_blueprint.md`
- `spark-output/context/experience-blueprint.json`

只允许检查文件是否存在；禁止读取产物正文、禁止解析 JSON 内容、禁止根据已有产物改变当前任务类型。

若任一正式产物存在，先输出以下状态提示，然后继续执行本 Skill 的入口规则：

```text
检测到本 Skill 已有正式产物（已产出）。
```

该提示只表示状态，不代表采取任何处理动作。

禁止：
- 读取产物正文
- 解析 JSON 内容
- 根据已有产物改变当前任务类型
- 根据已有产物执行下游
- 根据已有产物询问处理方式
- 根据已有产物推断用户意图

### Step 0.2 · 上游读取

PRD Review 主链固定按以下顺序读取：

1. 按当前 `SKILL.md` 的规则确认本 Skill 自身角色和输入边界
2. 完整读取 `spark-output/requirements_baseline.md`
3. 读取 `spark-output/context/requirements-baseline.json`，只接受 `2.1`，核对结构化投影与 Markdown 是否一致；完整读取 `experience_decisions`，核对每项与 Markdown `§10` 一致
4. 检测到完整 UXB 正式产物时，完整读取 `spark-output/uxb_output.md`
5. 读取 `spark-output/context/uxb.json`，只接受 `8.0`
6. 读取 `spark-output/context/stories.json`；有效 `3.0` JSON 存在时作为用户故事正式机器输入
7. Stories JSON 缺失、蓝图必需字段为空、与 Markdown 明显冲突，或需要审计完整任务叙述时，再完整读取 `spark-output/stories.md`
8. 读取 `spark-output/context/journey-analysis.json`（如存在）；有效 `3.0` JSON 存在时作为旅程分析正式机器输入
9. Journey JSON 缺失、蓝图必需字段为空、与 Markdown 明显冲突，或需要审计完整旅程叙述时，再完整读取 `spark-output/journey_analysis.md`
10. 执行知识补充消费（必须执行，不可跳过）

这是链路消费型 skill，默认承接 `spark-output/` 中的上游产物属于正式工作流，不视为历史残留。

用户明确选择独立 `framing-mode` 时：

1. 完整读取 `spark-output/problem_framing.md`。
2. 读取 `spark-output/context/problem-framing.json` 进行结构定位。
3. 不读取需求基线或 UXB 冒充该独立路径的上游。
4. Stories、Journey 和设计知识仍按本 Skill 的现有规则消费。
5. 执行 Step 0.4 的 `3+1` 检查。

双轨读取原因：

- 需求基线 Markdown 是正式业务语义源
- 需求基线 JSON 是同一基线的结构化投影
- UXB Markdown 是可选体验定案语义源
- UXB `8.0` JSON 是同一体验定案的结构化投影

上游读取硬门禁：

- 在 PRD Review 主链中，正式需求基线 Markdown 与 JSON 必须同时存在并通过一致性核对。
- 即使上游刚在同一会话生成、当前上下文仍保留内容，也不得替代本次文件读取。
- 重点章节只决定二次核对优先级，不是正文白名单。
- 需求基线 JSON 与 Markdown 冲突时停止，报告交接错误，不得自行选择或重判。
- UXB JSON 与 Markdown 冲突时停止，报告 UXB 交接错误。禁止静默忽略 UXB 后回到 `baseline-mode`。
- UXB Markdown 和 JSON 同时不存在时进入 `baseline-mode`。
- 只有 UXB JSON 或只有 UXB Markdown 时停止，报告 UXB 交接不完整。
- Stories 与 Journey 仍按各自现有正式输入规则消费。
- 未完成需求基线和当前实际需要的可选增强输入读取，不得进入知识补充或体验蓝图生成。

UXB JSON 读取：

- 只接受 UXB `8.0`。
- 重点消费任务体验定案、用户感知阶段、节点编排、跨阶段衔接、状态恢复和蓝图落实要求。
- `blueprint_requirements[].requirement` 与 `must_preserve` 必须进入设计承接。
- 按任务、角色、业务对象、状态和结果建立自然语义对应，不依赖 UXB 编号、路径、章节号或固定位置。
- 每条 UXB 正式定案都必须找到对应任务和方案落点。
- 无法建立自然语义对应时停止，报告无法对应的定案和缺失语义；不得忽略或按相似词强行匹配。
- UXB 不提供完整业务事实。角色、权限、规则、状态和异常必须来自需求基线。
- 检测到旧 UXB JSON 时，不转换、不兼容、不从旧字段恢复业务事实。

需求基线 JSON 读取：

- 只接受 Requirements Baseline `2.1`。
- JSON 用于结构定位，Markdown 仍是正式业务语义源。
- 检测到旧合同或两者冲突时停止，不转换、不兼容。
- 完整读取 Markdown `§10 体验定案` 与 JSON `experience_decisions`。`confirmed_constraints` 是必须承接的体验关系；`pending_items` 是本轮需要完成的体验判断。
- 每条已确认体验约束按任务、角色和场景关联到对应流程、异常或承载对象。每条待定案事项使用命中的设计准则和交互模式完成定案。
- `§10` 缺少任一分组时，按空数组处理；不读取问题单、原始 PRD、历史产物或聊天记录补回体验定案。

其他上游 JSON 读取：

- Stories JSON 只接受 `3.0`。必须完整消费 `stories[]` 中的角色、场景、目标、用户任务、优先级、来源依据、完成标准、设计触点、风险和明确假设，以及根级范围和待确认问题；待确认问题会改变方案时停止生成，不写入正式蓝图；结构完整时可单独作为正式机器输入。
- Stories `3.0` 字段为 `unknown`、`[]` 且是当前蓝图必需信息，或需要审计完整任务叙述时，回读 `stories.md`；JSON 与 Markdown 冲突时停止使用冲突字段并报告交接错误。
- 旧 Stories `2.0` 只提供标题级索引；对应 Markdown 可用时忽略旧 JSON 并完整读取 Markdown，只有旧 JSON 时不得据此恢复 Story 详情。
- Journey JSON 只接受 `3.0`。必须完整消费 `journeys[]` 中的角色类型、角色摘要、全部阶段及其目标、动作、触点、用户心声、信心与依据、痛点、流失风险、机会和明确转折，以及根级来源说明和缺口。
- Journey `3.0` 字段为 `unknown`、`[]` 且是当前蓝图必需信息，或需要审计完整旅程叙述时，回读 `journey_analysis.md`；JSON 与 Markdown 冲突时停止使用冲突字段并报告交接错误。
- 旧 Journey `2.0` 只提供旅程摘要索引；对应 Markdown 可用时忽略旧 JSON 并完整读取 Markdown，只有旧 JSON 时不得据此恢复完整阶段语义。
- 检测到其他旧版 JSON 且对应 Markdown 可用时，忽略旧 JSON、提示重新生成并完整消费 Markdown；不得做版本转换。

### Step 0.3 · 模式判断与降级

模式判断：

- `baseline-mode`：正式需求基线可用，没有完整 UXB 正式产物
- `uxb-mode`：正式需求基线可用，且 UXB Markdown 与 `8.0` JSON 均完整有效
- `deepened-mode`：在上述任一模式基础上，同时存在有效 Stories 或 Journey 正式产物
- `framing-mode`：只在用户明确要求基于 Problem Framing 独立生成蓝图时保留，不属于 PRD Review 主链

硬规则：

- `baseline-mode` 和 `uxb-mode` 都必须完整读取正式需求基线。
- UXB 缺失不得阻断 `baseline-mode`。
- UXB 存在时也不得跳过正式需求基线。
- 只有用户明确选择独立 Problem Framing 路径时，才执行原有 `3+1` 门槛判断。

降级规则：

- 需求基线 Markdown 或 JSON 缺失时，不进入 PRD Review 主链蓝图生成，提示先完成 PRD Review。
- UXB 两份正式产物同时不存在时，进入 `baseline-mode`。
- UXB 两份正式产物缺少任一项时停止，报告交接不完整。
- UXB 不是 `8.0` 时停止，不得做兼容转换。
- 如果有效 Stories `3.0` JSON 和 `stories.md` 均不存在，允许继续，但必须在 `§9` 标注"当前未经过用户故事深化，主任务链基于正式需求基线推导"
- 如果 `journey_analysis.md` 存在但有效 Journey `3.0` JSON 不存在，仅基于 MD 继续
- 如果有效 Journey `3.0` JSON 存在但 `journey_analysis.md` 不存在，正常基于 JSON 进入深化模式；遇到当前蓝图必需的空值时报告缺口，不得从会话补齐
- 如果只有旧 Journey `2.0` JSON，不把它当作完整 Journey；按正式需求基线、可选 UXB 或 Stories 推导简化旅程，并在 `§2` 标注“Journey 正文缺失，当前旅程为降级推导”
- 如果两者均未找到，`§2` 进入降级模式（从正式需求基线、可选 UXB 或 Stories 推导简化旅程）
- 如果 `knowledge-wiki` 当前不可用，在 `§9` 附录注明”知识库不可用”，继续后续设计，但不得伪造知识消费结果

### Step 0.4 · 独立 framing-mode 来源可用性检查

只有用户明确选择独立 Problem Framing 路径时，才进入 `framing-mode` 并检查 `3+1`：

1. `角色与目标是否明确`
   - 谁在完成什么任务
   - 成功结果是什么
2. `业务边界与对象是否明确`
   - 当前处理的正式业务对象是什么
   - 本轮进入范围与不进入范围是什么
3. `关键状态与阻断是否明确`
   - 主流程经过哪些关键状态
   - 哪些异常、阻断或规则会改变流程推进
4. `是否存在会直接改写主流程结构的未决问题`
   - 会改写主流程
   - 会改写页面结构
   - 会改写关键交互

只有同时满足以下条件，才允许输出完整体验蓝图：

- 上述 3 个主项全部通过
- 不存在会直接改写主流程结构的未决问题

如果 `3+1` 未通过：

- 不回上游
- 不触发 loop
- 不伪装成完整蓝图
- 只允许对已确认部分做“局部展开 + 显式保留”

## 角色定义

体验蓝图负责：

- 组织交互流程与角色承接
- 写清用户动作、系统反馈、页面文案和下一步
- 展开异常与阻断
- 承接业务边界、风险与反馈要求
- 生成旅程消费摘要模块
- 在正式需求基线和可选 UXB 已定边界上输出尽量完整的体验方案

体验蓝图不负责：

- 高保真视觉设计
- 前端实现方案
- 接口设计
- 重新做业务判断

## 知识补充消费

体验蓝图必须独立完成本阶段的设计知识消费。需求基线提供业务事实，UXB 提供可选体验定案，蓝图的知识消费服务于具体交互方案。

不得以“PRD Review 或 UXB 已读过知识”为由跳过本轮读取。每次运行都必须基于当前正式输入重新完成知识消费。

1. 从正式需求基线提取角色、业务对象、动作、状态、异常和结果。
2. 从可选 UXB 提取信息、流程、解释、反馈和体验取舍约束。
3. 读取与当前任务直接相关的业务知识，确认现有入口、父级承载页和成熟基座边界。
4. 明确本阶段需要解决的入口、承载、行为、状态反馈和回流问题。
5. 从 knowledge-wiki 的 index 进入设计准则章节地图，只读命中的完整章节。
6. 进入具体交互组织时，读取交互模式全局地图和命中的完整模式块。
7. 将设计知识转成具体方案，并在 `§9` 记录设计依据与正文落点。

内部必须记录实际读取的知识文件、完整章节或模式块，以及它支撑的具体设计决定。该记录用于防止“读过但未使用”或“使用但无依据”，不得在正文增加知识覆盖矩阵。

业务知识不能重新核验、补齐或覆盖正式需求基线。

发现冲突时按来源停止：

- 业务知识与需求基线冲突，或需求基线缺少会改变方案的业务事实：停止，说明冲突或缺失，建议用户重新执行 PRD Review。
- UXB 定案与需求基线冲突，或 UXB 要求无法对应需求基线：停止，说明冲突定案，建议用户重新执行 UXB。
- 不得自行选择一方继续，不得自动调用上游 Skill。

硬规则：

- index 和地图只负责路由，不能直接作为设计依据。
- 不得猜测目录、遍历 raw、逐文件试读或按关键词扩读。
- 文件内容较大时，读取命中的完整章节或完整模式块。
- 先识别本阶段新增的体验策略判断，再读取直接支撑这些判断的设计准则章节；通常从 2–4 个开始但不以数量判定完成，高风险、跨角色、多状态、复杂异常或跨域需求按实际影响扩展。
- 进入具体组织问题时，先按入口、承载、行为、状态与反馈、回流形成整体判断，再读交互模式全局地图和命中的完整模式块。
- 模式选择必须写明基线依据、选择原因和相近模式排除原因，并检查“进入 → 理解 → 操作 → 反馈 → 恢复或完成 → 返回原任务”闭环。
- 不得只留下知识来源而没有设计落点。

具体判断方法、记录格式、反查清单和示例见 `references/knowledge_consumption_guide.md`。

## 体验推导责任

体验蓝图必须承接正式需求基线和可选 UXB，并将其转译为：

- 角色路径
- 任务流
- 页面结构
- 状态反馈
- 异常阻断
- 保护策略

### 内部完整性推导

正式写作前，必须先在内部建立本轮方案覆盖关系。该过程只用于推理，不输出清单、矩阵、编号或 coverage 字段。

第一步，从需求基线提取：

- 每个相关角色，包括承担自动处理责任的系统。
- 每个角色要完成的任务、触发条件、业务结果和下一节点。
- 每个任务的实际入口来源：主动进入、任务内触发或状态后触发。
- 每个状态、异常、阻断、恢复方式和明确终止结果。
- 基线已明确的现有入口、任务位置和承载方式。

第二步，按任务闭环组装路径：

- 从任务入口一直连接到下一节点或明确终止。
- 不同角色分别建立路径，再处理角色之间的结果交接。
- 一个需求可以有多条主流程，不得默认只选最终用户的一条路径。
- 配置者、申请者、审批者、处理者等角色的核心任务同等进入主流程判断。
- 系统自动处理不必单独制造页面，但必须在触发它的节点和接收结果的节点中可感知。

第二步补充，识别任务内触发与受阻转接：

- 任务内触发指用户正在完成原任务时，因可处理限制而需要进入当前处修正或后续处理任务。
- 可处理限制包括权限或身份不符、前置条件未满足、必要数据或关联对象缺失、当前状态限制、依赖流程未完成、对象失效或变更、规则冲突、适用范围不符，以及外部系统暂不可用、同步延迟或处理失败。
- 上述类别只用于识别已存在的限制；不得据此补写未被输入或业务知识证明的事实。
- 先明确原任务、受阻时机和限制原因。当前处可以修正时，写清修正方式和继续动作，不制造无必要转接。
- 只有后续处理任务和可进入能力均已被证实时，才提供转接入口或引导；只保留系统已确认的任务对象、范围、来源或状态。
- 无法证明存在预填、自动回流、自动处理或恢复能力时，不得写为事实；处理后去向须明确为回到原任务、重新发起或查看处理状态中的已证实结果。

第三步，对每个流程节点进行承载分类：

- `新增或修改`：本期新增界面，或修改现有界面的入口、结构、操作、状态、可见性和反馈。
- `复用引用`：使用成熟基座或外部系统现有界面，本期只传入或消费数据，不修改界面结构和交互。
- `系统处理`：后台自动处理，没有独立用户操作界面，只产生状态、数据或通知结果。

每个流程节点必须且只能归入一类。

分类后的处理：

- `新增或修改`：进入 `§3`、`§4 / §5`、`§7` 和后续 Page Spec 范围。
- `复用引用`：进入 `§3`、`§4 / §5`，说明输入、动作、输出和返回位置；不进入 `§7`，不进入 Page Spec 范围。
- `系统处理`：进入对应流程，说明触发、处理结果和用户可见反馈；不进入 `§7`。

业务主流程节点不等于本期必须设计的界面。

第四步，识别父级承载页：

出现以下任一变化时，父级承载页必须归入“新增或修改”：

- 新增入口。
- 新增模式选项。
- 修改入口可见性或可用状态。
- 修改模式当前状态。
- 新增通往子页面的操作。
- 子功能启用后需要在父页显示结果。

子页面的入口依赖父级页面时，禁止只输出子页面。

父级承载页进入本期“新增或修改”后，必须先从业务知识恢复现有页面的完整结构，再叠加本期变化：

1. 保留本期未改变的主要区域、导航关系和核心操作。
2. 标出新增或变化的入口、模式、状态、结果和反馈。
3. 校验新增内容与现有信息层级、阅读顺序和任务入口的关系。
4. 输出完整页面方案，不得只画本期新增的一张卡片、一个入口或一个局部模块。

业务知识无法证明现有父级页面结构时，不得捏造“现有完整页面”。先根据需求基线判断该结构缺口是否会改变正式方案；会改变则停止，不会改变才允许以明确的新方案边界继续。

第四步补充，建立页面信息性质：

- 稳定信息：长期查看的当前事实。
- 任务入口：开始办理的触发点。
- 候选集合：一次选择任务中的对象。
- 已选结果：选择完成后回填主任务的结果。
- 历史记录：用于追溯的已完成事项。

候选集合只在选择过程出现时，不得设计为常驻 Tab。选择完成后必须回填已选结果，并保留原任务上下文、结果查看和重新选择路径。

第四步补充，选择流程形态：

当同一任务包含会改变后续内容的前序选择，或存在多个信息分组，需要判断它们是页面内联动还是独立阶段时，完整读取 `设计准则/设计准则.md` 的 `BFM-01 默认非步骤化` 与 `BFM-02 步骤条使用门禁`。

先按 BFM-01 判断单页表单能否承载完整任务；再按 BFM-02 识别候选阶段并完成三重门禁判断。

`Wizard + Steps` 只在三项同时成立时使用：存在至少两个候选阶段；后续阶段依赖前一阶段的独立结果；分步收益高于往返成本。

候选阶段、阶段依赖和收益的完整定义，以 BFM-02 为准。

第五步，分配正文落点：

- 直接完成本期核心业务结果的角色任务进入 `§4`。
- 支撑、维护、查看、撤销、关闭等非主路径任务进入 `§5`。
- 异常、阻断和恢复进入 `§6`。
- 每个归类为“新增或修改”的承载对象，必须在 `§7` 有完整方案。
- “复用引用”和“系统处理”不得为了流程完整而在 `§7` 制造页面。
- 每个会改变用户行动的状态必须进入 `§8`。

第六步，执行生成前覆盖门禁：

- 每个相关角色都有可执行路径或明确的系统承接。
- 每个核心任务都有完整起点、动作、反馈、结果和下一步。
- 每个流程节点都已完成承载分类。
- 每个主流程节点都能在交互总览中找到承接。
- 每个“新增或修改”节点都能在页面设计中找到承载。
- 父级承载页没有遗漏。
- 每个页面都服务于已确认的任务，不生成无来源页面。
- 每个需求基线异常都有交互处理。
- 每项 UXB 蓝图落实要求都有具体方案落点。
- 每个本期变化的父级承载页都保留了现有完整结构，不是局部新增卡片。
- 稳定信息、任务入口、候选集合、已选结果和历史记录没有混淆。
- 每个 Steps 方案都通过三重门禁。

发现遗漏时，继续内部推导并补齐方案。不得把可由现有基线和 UXB 直接推导的遗漏写入 `§9`，也不得等到生成后自查才首次发现。

内部承载分类只用于推理，不输出矩阵、清单、覆盖率或分类审计表。

第七步，提取页面结构（IA）：

交互流程与页面设计全部完成后，从 §7 承载对象和 §3 路径总览中提取页面结构摘要。提取过程按 `ia_extraction_guide.md` 执行。提取结果写入 §1。

§1 在写作顺序中预留位置，最后填写。正文按 §0 → §2 → §3 → … → §9 → §1 的顺序落笔。

不得：

- 重新裁决需求是否成立
- 绕过正式需求基线自行判断能力形态
- 只根据原始需求罗列页面功能，不基于正式需求基线展开
- 用“体验友好”“提示清晰”这类空泛表述替代具体页面结构、状态和文案
- 绕回原始输入重新解释业务规则、状态模型或能力形态
- 用 `stories` 或 `journey-analysis` 的派生信息反向覆盖正式需求基线或 UXB 体验定案
- 如果正式需求基线缺失，硬输出 PRD Review 主链的“完整方案”
- 在 `framing-mode` 下把 `working_assumptions` 当作完整蓝图事实基础
- 在 `framing-mode` 下把会改写主流程的未决问题静默抹平
- 把候选集合直接做成常驻 Tab
- 把结果回填型选择做成 Steps

## `§0` 本次关键设计判断

体验蓝图自己的核心设计判断，不复述需求基线或 UXB 的核心结论。

每条判断必须包含具体的设计做法。"需要关注 XX"是复述，"XX 场景用 XX 方式处理"是判断。

两块阅读结构，保留四类语义：

```markdown
### D-XXX · {简短判断标题}

**体验判断**

{一句话说明已经确定的体验选择。}

影响范围：{页面、流程或角色的关键落点。}

**具体做法**

{用 1 至 3 句短句，或必要的短列表说明承载方式、关键结构、关键反馈或关键边界。}

避免出现：{一句话说明最关键的错误体验结果。}
```

- 判断：已经确定的体验设计选择。
- 影响范围：这个选择影响的关键页面、流程或角色。
- 具体做法：设计如何落实。
- 避免出现：不能发生的关键体验结果，不列候选方案。

句式要求：

- 一句只表达一个设计关系；并列关系拆为短句。
- 标题只写“场景 + 已确定做法”，不写完整论证。
- §0 不写点击顺序、字段明细、完整校验链路、完整页面布局或状态枚举。
- 信息无法在短句内表达时，拆为短句或短列表；不得通过删除设计事实缩短篇幅。

正式蓝图只保留一套确定方案。

禁止出现：

- 新页面或原页面。
- 点击或勾选。
- 禁用或点击后报错。
- 卡片或列表。
- 顶部、侧边或列表入口均可。
- 方案一、方案二。
- 推荐采用某一种。

条件分支只有来自需求基线时才允许并列。

当来源为 `problem-framing` 且 `3+1` 未通过时，`§0` 的判断不得写成“完整路线已确定”，只能围绕已确认部分做局部设计判断。

禁止表达：

- “当前按完整执行路线处理”
- “标准路线下优先写主流程”
- 任何内部执行术语
- 对需求基线或 UXB 关键判断的重新表述或增强措辞

## `§2` 旅程消费摘要

旅程图由 journey-analysis Skill 独立产出，体验蓝图不再生成旅程图。

本节从 journey-analysis 产出中提取三类信息，驱动后续章节的设计决策：

- 信心最低点 → 驱动 `§6` 异常流程的设计优先级（信心越低的阶段，异常处理越重要）
- 关键转折 → 驱动 `§4` / `§5` 交互流程的"前置说明"字段（用户在转折点需要更多上下文）
- 流失风险 → 驱动 `§7` 页面设计的引导策略（高风险阶段需要更强的操作引导）

每个提取项固定写为：

```markdown
### {旅程类型}：{角色} · {阶段}

**旅程信号**

{信心最低点、关键转折或流失风险。}

**设计落点**

- §{章节}：{已确定做法。}
```

标题只写旅程类型、角色和阶段，不写“驱动 §X”。旅程信号用一至两句表达；设计落点按“章节：已确定做法”拆为短列表。

标题中的角色与阶段是 `source_stage` 的唯一 Markdown 来源。缺少全角冒号 `：`、` · ` 分隔符、角色或阶段时，停止 JSON 投影并报告格式缺口；不得从旅程信号或设计落点推断补全。

降级：如果 journey-analysis 未执行（`spark-output/journey_analysis.md` 和 `spark-output/context/journey-analysis.json` 均不存在），从正式需求基线、可选 UXB 和有效 Stories 推导简化版旅程，并标注"基于上游结论推导，未经深度旅程分析"。

## `§3` 交互流程总览

`§3` 是点击动作级交互流程图，不是旅程摘要。只写页面 / 弹窗 / 抽屉 / 用户动作 / 系统反馈 / 状态变化 / Toast / InlineError / EmptyState / LoadingState。

要求：

- 列出本次设计包含的交互路径（几条主路径、几条分支路径）
- 先按角色列出全部核心任务路径，再确定主路径与分支路径；不得只展示最显眼的用户角色
- 每条路径必须具体到点击、输入、选择、提交等动作级别
- 每条路径说明经过哪些页面 / 弹窗 / 抽屉，关键分支点在哪
- `§4` 的详细节点必须能在这里找到承接
- `§5` 和 `§6` 中影响任务闭环的路径也必须在总览中有入口或分支承接
- 每条路径写明实际存在的入口来源；任务内触发从原任务的受阻节点开始，说明是当前修正还是转入已证实的后续任务
- 不展开页面结构细节，页面结构仍归 `§7`
- 复用引用节点必须说明输入、可执行动作、输出结果和返回位置，但不展开页面结构
- 系统处理节点必须说明触发、处理结果和用户可见反馈
- 不使用 ASCII 框图、终端布局图或字符边框图

展示格式：

- 主路径标题使用 `### 主路径 {序号} · {角色}{核心任务}（{来源编号}）`。
- 已识别为分支路径的内容使用 `### 分支路径 · {触发场景或任务}（{来源编号}）`。
- 动作链中每个节点独立成行，每行以 `→` 开头。
- 主路径内的条件分支写在动作链后的 `**分支**` 短列表中。
- 分支路径在动作链后补充一条“承载说明”。

禁止把以下内容作为流程节点：

- 等待审批
- 获知结果
- 验证生效
- 感知
- 确认现状
- 信心
- 痛点
- 流失风险

正向案例：

```markdown
### 主路径 1 · {角色}提交{业务对象}申请（{来源编号}）

→ {承载页面}
→ 点击 [发起{核心任务}]
→ 打开 {业务对象}申请 Drawer
→ 选择{业务对象}
→ 输入申请原因
→ 点击 [提交申请]
→ 校验通过
→ Drawer 关闭
→ Toast：提交成功
→ {结果列表}新增一条“处理中”记录

**分支**
- 未选择{业务对象} → [提交申请] 置灰，不进入提交
- 申请原因不足 → Drawer 不关闭，原因输入区下方显示 InlineError
- {处理角色}不存在 → Drawer 不关闭，Toast 提示处理配置异常

### 分支路径 · {触发场景或任务}（{来源编号}）

→ {触发点}
→ 点击 [可执行入口]
→ 打开 {承载对象}
→ 完成、取消或失败处理
→ 回到原位置或进入后续任务

- 承载说明：{复用承载与本期承载说明}
```

反向约束：

- 不把整条主路径写成三列表或多列表大表格
- 不把分支条件折叠成“条件 / 结果 / 下一步”总表

## `§4` 主路径详细流程

`§4` 可以包含多条主路径详细流程。主流程按“是否直接完成本期核心业务结果”判断，不按角色是否面向最终用户判断。管理员配置、审批处理或其他角色任务只要是核心结果的必要组成，就必须作为主流程展开。

每个节点使用以下字段：

- 【用户动作】
- 【系统响应】
- 【用户需要知道】
- 【建议文案】
- 【下一步】

节点之间保持自然承接，不单列“上一节点结果”。

`§2` 是旅程消费摘要，`§4` 是操作层，不要混写。

承载要求：

- 每条流程标题与 §3 对应主路径保持一致；每个节点使用独立成行的 `**节点 {序号} · {名称}**` 分块展开
- 节点内用正文或短列表写清字段
- 不把整个主流程写成一张总表

## `§5` 次交互流程

要求：

- 每个次流程至少包含：触发条件、用户动作、系统反馈、下一步
- 如果流程涉及权限、审批、范围、关闭、撤销、授权失败等易误解概念，补充“需要前置解释的信息”
- 如果流程涉及弹窗、toast、按钮或错误反馈，补充“建议文案”

- 不退化成一整段自然语言概述或纯数字步骤列表
- 不得把本期核心业务结果所必需的角色任务降为一句次流程概述

承载要求：

- 每个次流程独立成块
- 不把多个次流程并排塞进一张对照表

展示格式：

- 每个次流程以 `### 次流程 {序号} · {任务名称}` 标题独立成块；已有来源编号保留在标题

- 次流程直接以字段展开

## `§6` 异常与阻断流程

每个异常必须包含：

- 发生时机
- 触发条件
- 判断依据
- 反馈形式
- 系统反馈
- 如何处理

“如何处理”写清用户当下动作、重试或后续位置，以及已有事实确认的信息保留或状态结果。

对可处理限制，先判断是当前修正、转入已证实的后续任务，还是没有可处理路径。转入后续任务时，异常节点必须说明原任务、当前限制、用户需要知道的信息、转接入口和处理后去向；不得假定预填、自动回流或恢复能力。

异常与阻断流程是正式体验内容，不是附录。

承载要求：

- 每个异常独立展开
- 不把多个异常压成统一总表

## `§7` 页面 / 弹窗 / 抽屉设计

页面清单必须从完整角色任务和流程节点推导，不能只从一条主流程反推。先确认每个角色在哪里开始、在哪里操作、在哪里查看结果，再逐个设计承载面。

页面类界面至少包含：

- 页面目标
- 进入条件
- 页面结构
- 信息层级和阅读顺序
- 适用角色及其可执行动作
- 按钮
- 成功反馈
- 失败反馈

如果存在加载态、空状态、审批中、已关闭、异常态，应补“状态反馈区”。
如果存在按钮置灰、入口隐藏、阻断弹窗、字段校验，应补“异常状态下的结构变化”。
如果存在关键提示、表单字段、弹窗或 toast，应补“具体文案”。
如果当前场景没有合理内容，不要为了凑结构保留空字段或空小节。

以下情况不得漏页：

- 本期新增或修改了独立任务入口。
- 角色需要在独立上下文中完成配置、申请、审批、处理或查看结果。
- 一个任务存在持续状态、列表管理、历史记录或多对象处理。
- 主流程或次流程明确进入了一个新的业务承载面。

如果复用现有页面，也必须作为本次涉及页面展开，并明确新增或变化的结构、动作、状态和反馈。

只有现有页面在本期发生入口、结构、动作、状态、可见性或反馈变化时，才在 `§7` 展开。

成熟基座或外部系统页面未发生变化时，只在流程中作为“复用引用”说明，不进入 `§7`，不生成 ASCII 草图。

父级承载页发生入口、模式、可见性、可用状态或结果展示变化时，必须在 `§7` 完整展开。

弹窗类界面优先包含：

- 弹窗目标
- 触发条件
- 弹窗结构
- 具体文案
- 按钮
- 成功反馈
- 失败反馈

抽屉类界面优先包含：

- 抽屉目标
- 进入条件
- 抽屉结构
- 具体文案
- 按钮
- 成功反馈
- 失败反馈

如果抽屉包含表单，应补充字段校验、提交前校验和提交失败反馈。

每个页面 / 弹窗 / 抽屉必须包含“结构草图”。
结构草图必须使用 fenced code block + ASCII，不得退化为自然语言列表。
生成结构草图前，必须优先读取 knowledge-wiki 中与当前页面相关的页面载体语义 / 页面结构 `raw`。
如果知识库存在对应结构，按其结构模式输出 ASCII 草图。
如果知识库没有对应结构，再基于当前页面目标输出低保真 ASCII 草图，并在图中标注待确认区域。

生成某一承载对象的 ASCII 前，只回看该对象已经写定的页面结构、具体文案、字段和异常状态下的结构变化。

一个承载对象可包含一个共享结构草图和多个条件结构草图。正文已确定某条件会切换字段组、候选集合、主要操作或处理结果时：

1. 先输出“结构草图（共享区域）”，只放所有条件共用的内容。
2. 再按条件输出“结构草图（{条件}）”，只放该条件下可见的主要内容区。

主要内容区只包括字段组、候选集合、主要操作或处理结果。文案、默认值、按钮可用状态、局部提示和同一结构内的状态变化继续使用一张草图。正文没有互斥显示条件时，沿用一张结构草图。

正例：处理类型切换候选集合或填写内容时，输出共享草图与条件草图。反例：条件只改变提示文案、默认值或按钮状态时，输出一张草图。

ASCII 结构草图只允许出现在这一章的“页面结构”部分。

结构草图中的示例业务数据必须变量化。

使用：

- `{业务对象总数}`
- `{分类数}`
- `{分类名}`
- `{业务对象名称}`
- `{业务范围}`
- `{处理人姓名}`
- `{处理时间}`

不得把具体人名、具体数量、具体业务应用名当作默认页面数据。

承载要求：

- 页面、弹窗、抽屉逐个成节展开
- 结构草图保留在 code block 中
- 草图之外的说明使用正文或短列表
- 不用大表格承载整页结构、整页按钮规则或整页状态变化

## `§8` 状态与反馈文案

以统一状态口径表为主，至少包含：

- 状态
- 含义
- 适用对象
- 用户可操作
- 统一反馈口径

这里允许短表格，但只用于状态口径、文案 key、短字段枚举这类高密度对照信息。

## `§9` 附录：设计依据与设计推导

仅在实际装配并使用了设计准则或业务知识时填写。

包含三类记录：

- 设计准则消费
- 上游承接追踪
- 设计推导

`上游承接追踪` 固定表格：

| 上游来源 | 上游结论 | 对体验意味着什么 | 体验设计决策 | 落点章节 |
|---|---|---|---|---|
| [需求基线 / UXB] | [业务事实或体验定案] | [体验影响] | [本次具体设计决策] | [§4 / §6 / §7 / §8 等] |

## 自检清单

生成 `experience_blueprint.md` 前，回看正式需求基线和可选 UXB，逐项检查：

```text
□ 1. 需求基线中的每个相关角色是否都有对应路径、页面或职责落点？
□ 2. UXB 存在时，每条蓝图承接要求是否都有对应展开？
□ 3. 需求基线中的每个相关异常是否都有交互流程展开？
□ 4. 需求基线中的每种相关状态是否都有展示位置和反馈文案？
□ 5. 配置态 / 关闭态 / 回退态等非主线场景是否被省略？
□ 6. 每个真实存在的任务内触发是否已说明当前修正、后续任务转接或不可处理结果？
□ 7. 需求基线事实、可选 UXB 体验定案和已消费设计知识是否都有对应设计落点？
□ 8. `§9` 的承接追踪是否非空，且每行都能落到真实章节？
□ 9. `§0` 每条判断是否都包含具体设计做法，而非上游结论的复述或增强？
□ 10. `§2` 旅程消费摘要是否非空，且三类信息（信心最低点 / 关键转折 / 流失风险）都有提取？
□ 11. 如消费了交互模式，入口、承载、行为、状态与反馈、回流是否已形成闭环，且模式选择有基线依据和排除依据？
□ 12. 是否输出了预览交接提示？
□ 13. 是否存在只覆盖员工或单一角色、遗漏管理员、审批人或其他核心角色任务的情况？
□ 14. 每个“新增或修改”承载对象是否都在 `§7` 完整展开？
□ 15. 每个页面是否都能反查到需求基线中的角色任务或 UXB 落实要求？
□ 16. 每个流程节点是否都已分类为新增或修改、复用引用、系统处理？
□ 17. 是否遗漏发生变化的父级承载页？
□ 18. 正式方案是否仍存在“或者”“可选”“方案一/二”等候选表达？
□ 19. 是否把复用引用节点误生成了详细页面？
□ 20. 是否新增了需求基线不存在的必填、权限、状态或异常规则？
□ 21. §1 的站点树是否覆盖 §7 中全部独立页面，抽屉与弹窗是否标注为子节点并挂载在正确的触发页面下？
□ 22. §7 正文已确定且会切换主要内容区的条件，是否均已在对应 ASCII 草图中表达，且每个条件草图只包含该条件下可见的主要内容区？
```

关键原则：

- 只检查自己的输出，不检查上游来源的输出质量
- 如果缺失信息会改变正式方案，应停止并向用户确认
- 如果发现业务事实未闭合，应停止主链蓝图并建议重新执行 PRD Review
- 自检第 7 项是反向检查：确认基线、可选 UXB 与设计知识没有孤立结论
- 自检只由 Agent 完成。脚本不得判断角色、流程、页面或体验语义是否完整
- `baseline-mode` 和 `uxb-mode` 不执行 `3+1` 完整性拦截
- 当来源为 `problem-framing` 时，如 `3+1` 未通过，不得输出假完整方案

## ⛔ Context JSON 生成门禁

写入 Context JSON 前，必须完整读取：

`references/context-schema.md`

硬规则：

1. 未完整读取该文件，禁止开始生成 Context JSON。
2. 禁止凭记忆重建 schema，禁止沿用旧 `1.0` / `2.0` JSON 结构。
3. JSON 是冻结 Markdown 中结构化设计事实的机器面，不是摘要、索引或第二次推理。
4. 只能写入 schema 明确允许的字段；不得新增、删除、改名或改变字段类型。
5. Markdown 必须先完成并通过本 Skill 自检；JSON 阶段只读取这份冻结 Markdown，禁止回读上游、知识库、原始需求或会话补充。
6. 只做字段归位和显式列表拆分；不得概括、改写、压缩、合并、补全或重新判断业务语义。
7. `§0-§8` 中会影响流程、页面、交互、状态、反馈、文案或异常的结构化事实必须逐项承接；`§9` 只承接上游承接追踪。
8. ASCII 页面图本体只保留在 Markdown `§7`；JSON 仅保留对应 surface 的 `markdown_heading` 和非 ASCII 设计事实。
9. 不得为了填满 JSON 编造信息；单值缺失写 `unknown`，集合缺失写 `[]`。
10. 写入后逐章核对 Markdown 正式条目数与 JSON 对应对象数；数量不一致时只修正投影遗漏，不得返回正文重新推理。
11. 禁止增加 ID、anchor 引用图、回接映射、泳道、图节点、关系边、坐标、连线或 coverage 字段。
12. 写盘后必须运行指定校验脚本。
13. 校验失败时必须修复并重跑；校验未通过不得进入 Handoff，不得宣告 Skill 完成。
14. schema 文件缺失或无法读取时，停止 JSON 生成并明确报告，禁止临时自创结构。
