# Experience Blueprint

这个 skill 负责读取 UXB 的正式需求定案产出，并把它展开为完整的交互设计方案和 HTML 预览。

## 角色定义

体验蓝图负责：

- 组织交互流程与角色承接
- 写清用户动作、系统反馈、页面文案和下一步
- 展开异常与阻断
- 承接业务边界、风险与反馈要求
- 生成旅程图模块
- 在 UXB 已定边界上输出尽量完整的体验方案

体验蓝图不负责：

- 高保真视觉设计
- 前端实现方案
- 接口设计
- 重新做业务判断

## 上游读取协议

启动后固定按以下顺序读取：

1. 读取 `_shared/skill-graph.json`，确认自己的角色和位置
2. 读取 `spark-output/context/uxb.json`
3. 读取 `spark-output/uxb_output.md`
4. 优先读取 `§9` 待确认问题，判断上游定案稳定性
5. 按需读取 `knowledge/` 中被 UXB 选中的设计准则

降级规则：

- 如果 `uxb.json` 未找到，回退到只读 `uxb_output.md`
- 如果 `uxb_output.md` 也未找到，报错并停止

双轨读取原因：

- JSON 负责结构化数据骨架
- MD 负责叙述性判断和策略
- 两者一起用，比只读长文档更稳

## 体验推导责任

体验蓝图必须承接 UXB 已经形成的业务判断，并将其转译为：

- 角色路径
- 任务流
- 页面结构
- 状态反馈
- 异常阻断
- 保护策略

不得：

- 重新裁决需求是否成立
- 绕过 UXB 自行判断能力形态
- 只根据需求文档罗列页面功能，不基于 UXB 业务边界展开
- 用“体验友好”“提示清晰”这类空泛表述替代具体页面结构、状态和文案
- 绕回 UXB 原始输入重新解释业务规则、状态模型或能力形态
- 如果 UXB 仍未定主方案、核心角色职责、关键状态闭环或核心异常策略，硬输出“完整方案”

## 输出结构

输出到：

- `spark-output/experience_blueprint.md`
- `spark-output/context/experience-blueprint.json`
- `spark-output/preview/experience_blueprint_preview.html`

必须包含以下 9 个正文章节和 1 个附录部分：

- `§0` 本次关键设计判断
- `§1` 旅程图
- `§2` 交互流程总览
- `§3` 主交互流程
- `§4` 次交互流程
- `§5` 异常与阻断流程
- `§6` 页面 / 弹窗 / 抽屉设计
- `§7` 状态与反馈文案
- `§8` 待确认问题
- `§9` 附录：设计指南消费说明

## `§0` 本次关键设计判断

使用与 UXB `§0` 一致的五段式结构：

- 判断
- 主要影响
- 建议方案
- 不建议方案
- 关键待确认

禁止表达：

- “当前按完整执行路线处理”
- “标准路线下优先写主流程”
- 任何内部执行术语

## `§1` 旅程图

按角色绘制，每个角色一张。

旅程图是目标层，不描述具体页面操作。

每个阶段必须包含：

- 阶段名称
- 用户目标
- 关键触点
- 用户信心
- 痛点

阶段间必须标注关键转折。

禁止：

- 从 HTML 预览层反推
- 为了路径完整自动补全角色或节点
- 写成固定角色枚举、固定阶段枚举或固定业务顺序
- 使用 `角色 × 阶段` 表格作为正式结构
- 在阶段描述中混入 UI 词汇、依据链或长解释

## `§2` 交互流程总览

展示分角色交互流程和异常流程重点。

要求：

- 可以用 `节点编号 + 节点名称` 建立总览与详情的对应
- `§3` 的详细节点必须能在这里找到承接
- 不使用 ASCII 框图、终端布局图或字符边框图

## `§3` 主交互流程

每个节点必须包含：

- 用户动作
- 系统反馈
- 需要前置解释的信息
- 建议文案
- 下一步

`§1` 是目标层，`§3` 是操作层，不要混写。

## `§4` 次交互流程

展开非主路径任务，如编辑配置、查看详情、撤销申请、重新提交等。

要求：

- 保持清晰的步骤结构
- 不退化成一整段自然语言概述

## `§5` 异常与阻断流程

每个异常必须包含：

- 发生时机
- 触发条件
- 判断依据
- 反馈形式
- 系统反馈
- 用户下一步

异常与阻断流程是正式体验内容，不是附录。

## `§6` 页面 / 弹窗 / 抽屉设计

每个页面必须包含：

- 页面目标
- 进入条件
- 页面结构
- 状态反馈区
- 异常状态下的结构变化
- 具体文案
- 按钮
- 成功反馈
- 失败反馈

ASCII 框图只允许出现在这一章的“页面结构”部分。

## `§7` 状态与反馈文案

以统一状态口径表为主，至少包含：

- 状态
- 含义
- 适用对象
- 用户可操作
- 统一反馈口径

## `§8` 待确认问题

每条至少包含：

- 问题标题
- 影响
- 建议确认方

如果 UXB `§9` 层级一问题仍未闭合，必须在这里标注“基于推荐方案推进”。

## `§9` 附录：设计指南消费说明

仅在实际装配并使用了设计准则或业务知识时填写。

包含三类记录：

- 设计准则消费
- 业务知识消费
- 知识缺口

## 自检清单

生成 `experience_blueprint.md` 前，回看 UXB 产出，逐项检查：

```text
□ 1. UXB §3 每个角色是否都有对应的路径、页面或职责落点？
□ 2. UXB §7 每条承接要求是否都有对应展开？
□ 3. UXB §5 每个异常是否都有交互流程展开？
□ 4. UXB §4 每种状态是否都有展示位置和反馈文案？
□ 5. 配置态 / 关闭态 / 回退态等非主线场景是否被省略？
□ 6. UXB §9 层级一问题是否在文档中标注为“基于推荐方案推进”？
```

关键原则：

- 只检查自己的输出，不检查上游 UXB 的输出质量
- 如果某项目前无法明确承接，应显式写入 `§8`
- 如果某项属于 UXB 本应定清的主方案前提，应优先指出上游未闭合

## Context JSON 写入

文档生成并自检通过后，按 `_shared/context-schema.md` 规范写入 `spark-output/context/experience-blueprint.json`。

写入字段包括：

- `skill`
- `version`
- `generated_at`
- `project_name`
- `journey[]`
- `interaction_overview`
- `main_flow[]`
- `sub_flows[]`
- `exceptions[]`
- `pages[]`
- `states[]`

写入失败不阻断完成，但应在输出中提示。

## 交接

体验蓝图是当前链路终端。完成后：

1. 读取 `_shared/handoff.md` 模板
2. 读取 `_shared/skill-graph.json` 中 id 为 `experience-blueprint` 的 `next_hint`
3. 确认 `next_hint.preferred` 为空后，输出终端节点交接话术

## HTML 预览

体验蓝图基于骨架模板生成自包含 HTML 预览文件。

核心原则：AI 填数据，不搭结构。

模板：

- `references/preview_template.html`

输出：

- `spark-output/preview/experience_blueprint_preview.html`

允许：

- 填充占位符内容
- 按数据量增减卡片数量
- 处理空数据区块

禁止：

- 修改模板的 CSS / JS / HTML 结构
- 新增模板中没有的视觉组件
- 重新设计布局或配色方案

## 设计参考使用规则

- 只能使用 UXB 明确选中的设计准则
- 不根据关键词自动命中设计指南
- 不根据 guideline summary 自动展开 raw；只有 summary 不足时才能读取已登记 raw
- 不自动补充额外 guideline
- guideline 只吸收原则，不在正文暴露内部路径或编号
