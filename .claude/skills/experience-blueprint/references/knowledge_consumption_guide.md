## 1. 业务与设计知识细则

### 1.1 业务知识跨域读取

体验蓝图从命中的 raw 中提取：

- 规则边界
- 状态分支
- 异常处理细节
- 体验策略所需的时序、角色、治理和来源信息

权限新增、修改、删除涉及审批时，权限管理是主域；先确认权限任务、规则与治理状态，再按需补读审批管理的流程或角色机制，最后回到权限域确认授予事实、生效结果、异常与审计。普通权限查询不自动读取审批管理。

### 1.2 设计准则章节选择

选择章节时依次判断：

1. 当前业务事实影响哪些角色、对象、状态和风险
2. 已选体验策略需要解决什么判断问题
3. 哪些设计准则章节能直接支撑该判断
4. 是否已进入入口、容器、状态或恢复等具体组织问题；若是，继续读取对应交互模式

通常从 2–4 个直接相关章节开始，但数量不是完成条件。简单需求可以更少；高风险、跨角色、多状态、复杂异常或跨域需求按实际影响扩展。不得为了满足数量读取无关章节。

章节读取以二级标题为边界：从命中 `##` 标题开始，读取到下一个 `##` 标题之前。不得只摘取单句原则后脱离其风险与例外。

### 1.3 设计准则与交互模式的分工

体验蓝图阶段的设计知识分两层消费：

- `设计准则`：回答为什么这样判断
- `交互模式`：回答这类任务通常怎么组织、用什么方式承载

默认顺序：

```text
从 index 进入设计准则章节地图
→ 只读取命中章节
→ 再判断是否需要交互模式
→ 如需要，先读交互模式全局地图并形成五维问题结构
→ 再读实际命中的完整模式块
→ 回看整体交互链是否闭合
→ 再进入体验推导
```

交互模式的五维问题结构固定为：

1. 入口：从哪里发起、如何发现，角色和对象状态是否改变入口
2. 承载：使用页面、弹窗、抽屉还是工作区，是否需要保留原上下文
3. 行为：核心动作、顺序、依赖、中断与恢复如何组织
4. 状态与反馈：操作前、中、后的状态、结果、异常、阻断和恢复路径
5. 回流：完成、取消或失败后返回哪里，原任务如何继续

这五个维度用于建立整体问题结构，不是机械检查表。相关维度继续读取对应模式；不相关维度必须有当前业务依据；信息不足进入待确认。不得只因材料没有出现“状态”“回流”等词就默认该维度不存在。

交互模式以三级标题为完整模式块边界：从命中的 `###` 标题开始，读取到下一个 `###` 标题之前。采用模式时必须结合当前业务证据说明选择原因，并排除至少一个相近模式；不得只读适用条件、组件名称或快速判断表后直接生成方案。

以下场景通常需要补读 `交互模式`：

- 新手指引与任务引导如何区分
- 任务前说明、任务后承接如何组织
- 报错、阻断、恢复路径如何组织
- 结果反馈后如何承接下一步
- `Inline / Banner / Message / Modal / Tooltip / Tour` 等承载形式如何取舍
- 页面信息复杂，需判断哪些信息应常驻、哪些应局部、哪些应分层展示

### 1.4 常见必读场景

- 审批管理：审批超时、转派、交接、催办、审批人缺失
- 治理模式：关闭能力后的影响、回收策略、与其他治理模式的共存
- 权限来源：来源解释、来源追溯、状态变化后的展示口径
- 状态模型：中间态、终态、回退态、异常态

## 2. 体验相关性判断法

判断一份知识是否与当前体验设计相关，优先看它是否影响以下任一方面：

- 某个角色的操作路径
- 某个页面的信息结构
- 某个状态的反馈策略
- 某个异常或阻断的处理方式
- 某个治理动作的风险提示、确认链路或结果说明
- 某个来源标签、解释文案或追溯能力

如果当前问题已经从“原则判断”进入“任务组织与承载形式判断”，不能停在设计准则层，应继续补读 `交互模式`。

如果都不影响，记录为“扫描后判断不相关”并停止；判断相关后按 `SKILL.md` 的对应知识规则读取。

## 3. 体验策略提取法

从 raw 中提取的不是“原文摘要”，而是“这条知识对体验设计意味着什么”。

推荐转换模板：

1. 先写知识中的关键规则 / 事实
2. 再写它转成了什么体验策略
3. 最后写它落到正文的哪个章节 / 节点 / 页面

推荐句式：

- 关键规则：`……`
- 体验策略：`因此在体验蓝图中，需要……`
- 落点：`对应正文 §X / 节点 X-X / 页面 PX`

## 4. 附录记录格式

### 4.1 设计准则消费

建议字段：

- 使用依据
- 命中章节
- 转换结果
- 落点
- 是否新增补充

“是否新增补充”用于区分：

- 直接承接 UXB 已选条目
- 体验阶段新增补充条目

如果补读了 `交互模式`，建议在同一附录中并列记录：

- 使用依据
- 五维整体判断
- 命中模式与业务证据
- 排除的相近模式及原因
- 装配结果
- 落点
- 是否新增补充

### 4.2 业务知识消费

建议字段：

- 主域与知识来源
- 条件依赖域与触发依据
- 已读 raw / 章节范围
- 未扩读领域及业务理由
- 关键规则 / 事实
- 转换成的体验策略
- 落点

### 4.3 知识缺口

当命中的 raw 不能支撑当前设计时，记入知识缺口。建议字段：

- 缺口主题
- 当前缺什么
- 影响哪个章节 / 节点
- 建议确认方

## 5. 孤儿判断反查清单

### 5.1 从 UXB §0 回看

- 每条关键判断是否在体验蓝图 `§0` 或正文中被承接
- 如果正文用了推荐方案推进，是否在 `§8` 明确标注

### 5.2 从规则边界回看

- UXB 的状态边界，是否进入 `§7`
- UXB 的异常边界，是否进入 `§5`
- UXB 的治理操作边界，是否进入 `§3 / §4 / §6`

### 5.3 从附录消费表回看

- 每条“设计准则消费”是否指向了真实章节
- 每条“业务知识消费”是否指向了真实章节 / 节点 / 页面
- 每条跨域消费是否写明主域、依赖触发依据，并回到主域闭合状态与结果
- 是否存在“有来源、无落点”的孤儿条目

### 5.4 从正文反查来源

- 正文里所有明显依赖外部规则的关键设计，是否在附录里能反查到来源
- 是否存在“有落点、无来源”的设计结论

## 6. 示例

### 6.1 路由命中后读取 Raw

- 知识来源：审批管理入口
- 判断：路由入口只负责定位，不作为正式事实
- 处理：读取 raw，提取超时、催办、转派、审批人失效等细节
- 落点：`§5 审批超时`、`§5 审批人不存在`、审批人相关页面或状态说明

### 6.2 UXB 未读，但体验阶段必须补读

- 知识来源：审批管理 raw
- 上游状态：UXB 未读
- 体验阶段判断：审批人操作链路、异常反馈、结果通知强依赖该知识
- 处理：补读 raw，在附录中明确标记为“体验阶段新增补充”

### 6.3 设计准则按章节读取

- 任务信号：审批、权限、延迟生效与高风险配置
- 命中章节：治理、可用性、反馈与引导
- 处理：只读取上述章节；进入审批状态与恢复组织时，再补读对应交互模式
- 落点：权限范围说明、审批状态、异常恢复与结果反馈
