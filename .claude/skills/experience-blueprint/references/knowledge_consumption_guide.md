## 1. 上游与设计知识细则

### 1.1 业务事实来源

体验蓝图只从正式需求基线提取：

- 角色与任务。
- 业务对象与规则边界。
- 状态与异常。
- 业务结果和验收约束。

UXB 存在时，只补充信息组织、流程编排、解释、反馈和体验取舍。不得从 UXB 恢复完整业务事实。

出现以下任一具体需要时，读取与当前主题直接相关的业务知识完整规则块：

- 确认现有任务入口或父级承载页。
- 确认成熟基座的输入、输出和返回关系。
- 确认现有页面模式或状态表达。
- 确认任务内触发所依赖的既有处理入口或处理能力。

没有上述具体需要时，不为覆盖率读取业务知识。当前设计决定已获得足够证据后停止，不扩展到整个业务域。

本轮必须独立读取。不得引用 PRD Review 或 UXB 的读取行为代替本阶段消费。

内部逐项记录：

- 实际读取的知识文件。
- 实际读取的完整章节或模式块。
- 该知识支撑的具体设计决定。
- 该决定在正文中的落点。

业务知识不能新增、修改或覆盖需求基线。

发现冲突时：

- 业务知识与需求基线冲突，或缺少会改变方案的业务事实：停止并建议重新执行 PRD Review。
- UXB 与需求基线冲突，或无法建立任务、角色、对象、状态和结果的自然对应：停止并建议重新执行 UXB。
- 不得自行选择一方继续，不得自动调用上游 Skill。

### 1.2 设计准则章节选择

选择章节时依次判断：

1. 需求基线中的业务事实影响哪些角色、对象、状态和风险
2. 已选体验策略需要解决什么判断问题
3. 哪些设计准则章节能直接支撑该判断
4. 是否已进入入口、容器、状态或恢复等具体组织问题；若是，继续读取对应交互模式

通常从 2–4 个直接相关章节开始，但数量不是完成条件。简单需求可以更少；高风险、跨角色、多状态、复杂异常或跨域需求按实际影响扩展。不得为了满足数量读取无关章节。

当前设计决定已有足够依据时停止读取设计准则或交互模式；不因“设计知识应尽量完整”扩展到全部章节或模式。

章节读取以二级标题为边界：从命中 `##` 标题开始，读取到下一个 `##` 标题之前。不得只摘取单句原则后脱离其风险与例外。

### 1.3 设计准则与交互模式的分工

体验蓝图阶段的设计知识分两层消费：

- `设计准则`：回答为什么这样判断
- `交互模式`：回答这类任务通常怎么组织、用什么方式承载

默认顺序：

```text
从 index 进入设计准则章节地图
→ 只读取命中章节
→ 再判断是否需要交互模式
→ 如需要，先读交互模式全局地图并形成五维问题结构
→ 再读实际命中的完整模式块
→ 回看整体交互链是否闭合
→ 再进入体验推导
```

交互模式的五维问题结构固定为：

1. 入口：从哪里发起、如何发现，角色和对象状态是否改变入口
2. 承载：使用页面、弹窗、抽屉还是工作区，是否需要保留原上下文
3. 行为：核心动作、顺序、依赖、中断与恢复如何组织
4. 状态与反馈：操作前、中、后的状态、结果、异常、阻断和恢复路径
5. 回流：完成、取消或失败后返回哪里，原任务如何继续

这五个维度用于建立整体问题结构，不是机械检查表。相关维度继续读取对应模式；不相关维度必须有当前业务依据；信息不足且会改变方案时停止当前方案生成。不得只因材料没有出现“状态”“回流”等词就默认该维度不存在。

交互模式以三级标题为完整模式块边界：从命中的 `###` 标题开始，读取到下一个 `###` 标题之前。采用模式时必须结合当前业务证据说明选择原因，并排除至少一个相近模式；不得只读适用条件、组件名称或快速判断表后直接生成方案。

以下场景通常需要补读 `交互模式`：

- 新手指引与任务引导如何区分
- 任务前说明、任务后承接如何组织
- 报错、阻断、恢复路径如何组织
- 结果反馈后如何承接下一步
- `Inline / Banner / Message / Modal / Tooltip / Tour` 等承载形式如何取舍
- 页面信息复杂，需判断哪些信息应常驻、哪些应局部、哪些应分层展示
- 候选集合与已选结果如何承接
- 单页、连续操作与 `Wizard + Steps` 如何取舍

进入页面信息组织前，必须读取并应用：

- `IA-04 稳定信息与任务过程分离`
- 当前场景命中的入口与可发现性准则

涉及分步或选择流程时，必须读取并应用 `BFM-01` 至 `BFM-04`。不得只因步骤多、字段多、低频或高风险而选择 Steps。

### 1.4 常见必读场景

- 审批管理：本期改变的审批交接、回写和结果；未改变的成熟 OA 页面只引用
- 治理模式：关闭能力后的影响、回收策略、与其他治理模式的共存
- 权限来源：来源解释、来源追溯、状态变化后的展示口径
- 状态模型：中间态、终态、回退态、异常态
- 父级承载：新增入口、模式选项、可见性、可用状态和子页面入口

## 2. 体验相关性判断法

判断一份知识是否与当前体验设计相关，优先看它是否影响以下任一方面：

- 某个角色的操作路径
- 某个页面的信息结构
- 某个状态的反馈策略
- 某个异常或阻断的处理方式
- 某个治理动作的风险提示、确认链路或结果说明
- 某个来源标签、解释文案或追溯能力

如果当前问题已经从“原则判断”进入“任务组织与承载形式判断”，不能停在设计准则层，应继续补读 `交互模式`。

如果都不影响，记录为“扫描后判断不相关”并停止；判断相关后按 `SKILL.md` 的对应知识规则读取。

## 3. 体验策略提取法

从 raw 中提取的不是“原文摘要”，而是“这条知识对体验设计意味着什么”。

推荐转换模板：

1. 先写知识中的关键规则 / 事实
2. 再写它转成了什么体验策略
3. 最后写它落到正文的哪个章节 / 节点 / 页面

推荐句式：

- 关键规则：`……`
- 体验策略：`因此在体验蓝图中，需要……`
- 落点：`对应正文 §X / 节点 X-X / 页面 PX`

## 4. 附录记录格式

### 4.1 设计准则消费

建议字段：

- 使用依据
- 命中章节
- 转换结果
- 落点
- 是否新增补充

“是否新增补充”用于区分：

- 直接承接 UXB 已定体验策略
- 体验阶段新增补充条目

如果补读了 `交互模式`，建议在同一附录中并列记录：

- 使用依据
- 五维整体判断
- 命中模式与业务证据
- 排除的相近模式及原因
- 装配结果
- 落点
- 是否新增补充

### 4.2 上游承接

建议字段：

- 上游来源：需求基线或 UXB
- 上游结论
- 对体验的影响
- 具体设计决策
- 正文落点

### 4.3 知识缺口

当命中的 raw 不能支撑当前设计时，记入知识缺口。建议字段：

- 缺口主题
- 当前缺什么
- 影响哪个章节 / 节点
- 建议确认方

## 5. 孤儿判断反查清单

### 5.1 从需求基线与 UXB 回看

- 需求基线中的相关业务事实是否有设计落点
- UXB 存在时，其蓝图承接要求是否有设计落点

### 5.2 从规则边界回看

- 需求基线的状态边界，是否进入 `§7`
- 需求基线的异常边界，是否进入 `§5`
- 需求基线的治理操作边界，是否进入 `§3 / §4 / §6`

### 5.3 从附录消费表回看

- 每条“设计准则消费”是否指向了真实章节
- 每条“上游承接”是否指向了真实章节 / 节点 / 页面
- 是否存在“有来源、无落点”的孤儿条目

### 5.4 从正文反查来源

- 正文里所有明显依赖外部规则的关键设计，是否在附录里能反查到来源
- 是否存在“有落点、无来源”的设计结论

## 6. 示例

### 6.1 需求基线提供业务事实

- 上游来源：正式需求基线
- 业务事实：审批超时、转派、审批人失效的业务结果
- 处理：直接作为交互流程和异常设计依据，不再跨域补读业务知识
- 落点：`§5 审批超时`、`§5 审批人不存在`、审批人相关页面或状态说明

### 6.2 UXB 缺失

- 上游状态：正式需求基线完整，UXB 未执行
- 处理：进入 `baseline-mode`
- 体验阶段判断：基于需求基线和设计知识直接形成具体交互方案
- 限制：不得因 UXB 缺失而重新补做体验定案文档

### 6.3 设计准则按章节读取

- 任务信号：审批、权限、延迟生效与高风险配置
- 命中章节：治理、可用性、反馈与引导
- 处理：只读取上述设计准则章节；进入审批状态与恢复组织时，再补读对应交互模式
- 落点：权限范围说明、审批状态、异常恢复与结果反馈
