# 体验蓝图输出写作指南

这份指南只负责一件事：

**把 `experience_blueprint.md` 的写法固定下来。**

## 写作红线

1. 不重新裁决需求是否成立
2. 不绕过正式需求基线自行判断能力形态
3. 不省略需求基线中的配置态、关闭态、回退态
4. 不用空泛表述替代具体页面结构和文案
5. 不在 `§7` 之外使用 ASCII 框图
6. 旅程消费摘要只提取对当前交互方案有影响的信息，不重新生成旅程图
7. 次交互流程保持步骤结构，不退化为概述
8. 状态文案使用统一口径表
9. 正文不暴露内部执行术语
10. 异常与阻断流程是正式内容，不是附录
11. 不新增需求基线不存在的必填、权限、状态、异常或数据规则
12. 正式蓝图不保留待确认问题；会改变方案的业务信息缺失时停止，体验取舍直接定案，成熟外部基座仅作复用引用

## 失败条件

1. 缺少旅程消费摘要、任一核心角色主流程或关键异常流程
2. 把设计参考写成自动路由或内部判断说明
3. 页面文案是元指令而不是用户可见文本
4. 依赖未装配知识或自行脑补 guideline
5. 只展开单一路径主流程，异常与阻断明显薄弱
6. 在 `§7` 之外使用 ASCII 框图
7. 通过体验蓝图重新判断需求是否成立、业务规则或能力形态
8. 页面设计停留在功能罗列，没有结构和反馈落点
9. 旅程消费摘要脱离正式上游凭空推测
10. 状态模块是长段流程复述而非统一口径表
11. 只覆盖员工或最显眼角色，遗漏管理员、审批人或其他核心角色任务
12. “新增或修改”承载对象没有在 `§7` 完整展开
13. 复用引用节点被误生成详细页面
14. 新增入口或模式选项，但遗漏发生变化的父级承载页
15. 正式方案仍保留多个候选方向
16. 父级承载页只画本期新增卡片或入口，遗漏现有主要区域
17. 把任务候选集合设计成常驻 Tab
18. 未通过三重门禁就使用 Steps
19. 在正式蓝图中保留待确认问题、未选择方向或未被证实的外部能力
20. §1 缺少站点树或主导航
21. §1 的页面名称与 §7 承载对象不一致

## 合格标准

1. 读完后能清晰知道谁在什么场景下做什么、系统如何响应
2. 主流程、次流程、异常与页面承接清晰
3. 旅程消费摘要能说明来源角色、阶段和本蓝图落点
4. 状态模块为统一口径表，而非长段流程复述
5. 正文不暴露内部执行术语
6. `§6` 不是附录，且至少说明触发条件、系统反馈、用户下一步
7. `§7` 的 ASCII 能体现结构化空间、信息层级、阅读顺序和按钮，正文能体现反馈、文案和异常状态下的结构变化
8. ASCII 框图只出现在 `§7`
9. 明确承接需求基线；UXB 存在时，继续承接其体验策略与取舍
10. 需求基线中的每个核心角色、任务、状态和异常都有交互方案落点
11. 所有“新增或修改”页面、弹窗、抽屉均在 `§7` 完整展开
12. 复用引用节点在流程中闭环，但不生成无必要页面方案
13. 正式产物只有一套确定方案
14. 发生变化的父级承载页保留现有完整结构，并清楚标出本期变化
15. 候选集合、已选结果和稳定信息使用不同承载关系
16. Steps 只用于通过实质阶段、阶段依赖和分步收益三重门禁的任务
17. 可处理限制在当前修正、后续任务转接或不可处理结果中形成明确去向
18. §1 站点树覆盖全部独立页面，抽屉和弹窗挂载关系与 §7 进入条件吻合

## 各章节写法

### `§0` 本次关键设计判断

- 每项按独立成行的加粗标签“体验判断、具体做法”两个视觉主块输出
- “体验判断”先用一句话写明已经确定的设计判断，再以“影响范围：”保留关键落点
- “具体做法”用短句或必要的短列表说明承载方式、关键结构、关键反馈或关键边界，再以“避免出现：”保留错误体验结果
- 不写点击顺序、字段明细、完整校验链路、完整页面布局或状态枚举；这些内容仍由后续章节承载
- 不输出未决项；信息缺失且会改变方案时停止生成
- 禁止列出未选择方案或候选方向
- 开头只保留用户需要优先阅读的判断，不在 `§0` 展示完整承接追踪表

### `§1` 页面结构

- 站点树在前，主导航在后，两部分各有固定格式
- 站点树按功能域或承载页分组，使用缩进树形结构，每个节点一行；独立页面、子页面和子节点按真实归属与触发关系逐级挂载
- 抽屉、弹窗、复用展示、跨应用入口和“不独立成页”等必要关系，在对应节点的括号中简短说明
- 主导航使用有序列表，每项写明 label、route 和 icon_hint，有子项时展开 children
- §1 只列结构和导航，不展开页面内部细节，不写交互流程，不写状态文案
- 站点树后不追加覆盖范围、复用关系、排除对象或其他重复说明；相关事实仍由 §3、§4、§7 承载
- §3 交互流程总览中的每个页面名称与 §1 站点树节点保持一致
- §7 页面设计中的每个独立页面在 §1 站点树中有对应节点
- 提取过程按 `ia_extraction_guide.md` 执行
- §1 是最后一个落笔的章节，从已完成的交互设计中提取

### `§2` 旅程消费摘要

- 提取信心最低点、关键转折和流失风险；每项标题固定为“旅程类型：角色 · 阶段”
- 每项使用独立成行的加粗标签“旅程信号、设计落点”两个视觉主块；旅程信号用一至两句，设计落点按“章节：已确定做法”写短列表
- 标题不写“驱动 §X”，不再单列来源角色与阶段；角色与阶段由标题承载并投影至既有 `source_stage`
- 没有 Journey 正式产物时，按主 Skill 的降级规则推导
- 不重新生成完整旅程图

### `§3` 交互流程总览

- 先从需求基线提取全部相关角色和核心任务，再展示分角色交互流程
- 一个需求允许存在多条主路径，不得默认只保留员工或最终用户路径
- 每个流程节点在内部分类为“新增或修改”“复用引用”或“系统处理”
- 对每个任务确认实际存在的入口来源：主动进入、任务内触发或状态后触发
- 任务内触发从原任务的受阻节点开始，明确当前修正或转入已证实的后续任务
- 正式输入存在互斥条件，且不同条件对应不同字段、入口、内容或结果时，分别写清各条件下的动作和结果
- 复用引用节点写清输入、动作、输出和返回位置，不展开页面结构
- 系统处理节点写清触发、处理结果和用户可见反馈
- 单列异常流程重点
- `§4`、`§5`、`§6` 的关键节点均应在总览中找到入口或分支承接
- 主路径和已识别的分支路径分别使用“`### 主路径 {序号} · …`”和“`### 分支路径 · …`”标题
- 动作链中每个节点独立成行，每行以 `→` 开头；主路径内条件分支写在独立成行的“**分支**”短列表中，分支路径末尾补一条“承载说明”

### `§4` 主路径详细流程

- 每条流程标题与 §3 对应主路径保持一致；节点使用独立成行的 `**节点 {序号} · {名称}**`
- 节点字段使用 `【用户动作】`、`【系统响应】`、`【用户需要知道】`、`【建议文案】`、`【下一步】`，字段内容与标签同一行
- 节点是完整任务，不是单次点击
- 操作发起审批、同步或其他异步环节时，分别写提交后的当前状态、恢复条件满足前可进行的查看或等待、恢复条件满足后的下一步；提交成功不等于业务结果已完成
- 采用“对象选择与回填”模式时，按选择入口、打开选择承载、选择确认、返回主任务、已选摘要和继续提交的顺序展开
- 必须覆盖需求基线定义的相关角色和功能单元
- 管理员配置、审批处理等任务只要直接支撑本期核心结果，就按独立主流程展开
- 节点之间保持自然承接，不单列“上一节点结果”
- OA 审批等成熟基座仍属于业务主流程；本期未修改其页面时，写清输入、审批动作、输出和回到业务任务的位置，不在 `§7` 生成页面
- 复用引用只描述业务知识已经证明的能力；不得从“复用”推断配置节点、编辑页面、预填或自动回流能力

### `§5` 次交互流程

- 每个次流程至少包含：触发条件、用户动作、系统反馈、下一步
- 异步次流程的“下一步”只写当前状态下用户可执行的查看、等待或跟进动作；恢复条件满足后再写回到原任务或进入后续任务
- 任务内触发的次流程补充原任务、限制原因、用户需要知道的信息和处理后去向
- 复杂流程按需补充：需要前置解释的信息、建议文案
- 不需要为了凑格式把每个次流程都写满所有字段
- 不退化成纯数字步骤列表或概述段落
- 不把核心角色的必要任务压缩成一句次流程
- 每个次流程以 `### 次流程 {序号} · {任务名称}` 标题独立成块；已有来源编号保留在标题
- 字段使用 `【字段名】：内容`，标签与内容同一行；次流程直接以字段展开

### `§6` 异常与阻断流程

- 每个异常写发生时机、触发条件、判断依据、反馈形式、系统反馈、如何处理
- 必须覆盖需求基线中对体验有影响的关键异常与阻断
- 对可处理限制，区分当前修正、转入已证实的后续任务和不可处理结果；不得用转接替代当前可修正动作，也不得虚构转接能力
- “如何处理”写清用户当下动作、重试或后续位置，以及已有事实确认的信息保留或状态结果

### `§7` 页面 / 弹窗 / 抽屉设计

- 页面清单从完整角色任务和流程节点推导，不只从单一主流程反推
- 只展开“新增或修改”承载对象
- 页面、弹窗、抽屉按实际事实依次写明：目标、进入或触发条件、适用角色、结构草图、成功反馈、失败反馈、异常状态下的结构变化、具体文案；不存在对应事实的字段省略
- `适用角色` 保留角色、可见范围和操作边界；页面内可见动作写入结构草图，动作结果写入流程或反馈字段
- 有加载态、空状态、审批中、已关闭、异常态时，应补“状态反馈区”
- 有按钮置灰、入口隐藏、阻断弹窗、错误校验时，应补“异常状态下的结构变化”
- 有关键提示、字段、弹窗或 toast 时，应补“具体文案”
- 表单类抽屉应补字段校验、提交前校验和提交失败反馈
- 采用“对象选择与回填”模式时，主任务写选择入口与已选摘要；选择模态弹窗写候选浏览、搜索、筛选、选择和确认。已有复用选择器时，按其已有承载方式和返回规则引用
- 成功反馈保留触发结果、反馈形式、承载位置、页面去向和状态或数据变化；失败反馈保留失败条件、反馈位置与形式、用户可见结果、信息保留情况和后续动作
- 异常结构写明相对正常状态新增、隐藏、禁用、替换或只读的具体区域和组件；具体文案保留准确文案或模板、变量、出现位置和适用状态
- 将长句拆成直接事实，保留条件、依据、因果关系、适用范围和结果；只删除不携带新增事实的套话和完全重复的句子
- 没有对应事实时省略该字段，不写“无”；不得为了省略字段而删除已有事实
- 页面结构部分可使用 ASCII 框图
- 生成结构草图前先冻结页面结构、信息层级、阅读顺序、可见动作、具体文案、字段和异常结构事实；ASCII 只投影已确定事实
- 草图与正文冲突时，按已确定的正文事实重写草图，不改变正文语义
- 信息层级、阅读顺序和按钮统一在 ASCII 中表达，不再单列同名字段
- 区域排列等于阅读顺序；按钮或入口使用准确文案，并保留已确认的类型、位置、条件和状态
- 未确认按钮类型时使用中性按钮或入口标记，不自行定案
- 输出前逐项核对信息层级、阅读顺序和按钮；缺失项先补入 ASCII，不用概括说明替代
- 内部承载分类不在 §7 输出，也不写入 ASCII
- 复用现有页面且本期发生变化时，必须说明新增或变化的结构、动作、状态和反馈
- 成熟基座或外部页面未发生变化时，只在流程中引用，不在本节展开
- 新增入口、模式选项、可见性或状态变化时，必须展开对应父级承载页
- 子页面依赖父级入口时，禁止只展开子页面
- 父级承载页必须先保留业务知识能够证明的现有主要区域、导航关系和核心操作，再叠加本期变化
- 不得只输出本期新增卡片、入口或局部模块
- 业务知识无法证明现有完整结构时，不得捏造；缺失会改变方案时停止生成
- 稳定信息可以常驻；候选集合只在选择任务中出现；选择完成后回填已选结果并保留原任务上下文
- 已确认跨任务入口同时具备原任务受阻、可执行入口和目标去向，但没有具体父级承载页时，在 `§7` 使用跨任务引用大白板：

  ```text
  {当前应用或任务}
  ┌────────────────────────────┐
  │ {当前操作入口}             │
  │                            │
  │ {阻断说明}                 │
  │ [{可执行入口}]             │
  └────────────────────────────┘
                 ↓
          {打开目标}
  ```

- 已知具体父级承载页时，按该页展开，不使用跨任务引用大白板。原任务、入口动作或目标去向缺少任一项时，不输出大白板。
- 候选集合本身没有长期管理价值时，不得设计为常驻 Tab
- 使用 Steps 前必须同时满足：至少两个实质阶段、阶段间存在强依赖或独立校验/提交、分步收益高于往返成本
- 自动检查、只读说明、默认值、最终摘要和一次确认不算独立阶段
- 结果回填型选择不形成独立业务状态且无需阶段提交时，不使用 Steps

权限模式类需求中，如果在“权限管理模式选择页”新增模式入口，必须先展开该父级页面，再展开模式配置子页面。

### `§8` 状态与反馈文案

- 用统一状态口径表
- 不重复完整流程说明
- 必须覆盖需求基线中的核心状态；UXB 存在时承接其反馈策略
- 能归属具体页面、弹窗或抽屉的操作反馈写入 §7，不在 §8 重复
- 迁移操作反馈时保留触发操作、条件、反馈形式、准确文案、承载结果、状态或数据变化、信息保留情况和后续动作
- 只有无法归属单一承载对象的跨页面反馈，才在状态口径表后使用短表格补充

### `§9` 附录：设计依据与设计推导

- 记录设计准则如何转成体验策略
- 记录需求基线和可选 UXB 如何影响设计判断
- 记录已有输入如何形成当前体验决定
- 命中设计知识后，从 index 进入设计准则或交互模式，只读明确命中的完整章节或模式块
- 要能回看“需求基线 / UXB → 设计转译 → 正文落点”是否闭环
- 在附录中新增 `上游承接追踪` 表，固定包含：`上游来源 / 上游结论 / 对体验意味着什么 / 体验设计决策 / 落点章节`
