# Page Spec

这个 skill 只做一件事：把设计材料整理成页面生成契约，过滤掉页面生成无关的叙事和说服性内容，输出一份干净的、可直接用于页面生成的规格文档。主要输入是体验蓝图，也接受用户直接上传的设计材料。

## Step 0 · 运行入口

### Step 0.1 · 本 Skill 产物状态

执行本 Skill 前，只检查本 Skill 对应正式产物是否存在。

正式产物：
- `spark-output/page_spec.md`
- `spark-output/context/page-spec.json`

只允许检查文件是否存在；禁止读取产物正文、禁止解析 JSON 内容、禁止根据已有产物改变当前任务类型。

若任一正式产物存在，先输出以下状态提示，然后继续执行本 Skill 的入口规则：

```text
检测到本 Skill 已有正式产物（已产出）。
```

该提示只表示状态，不代表采取任何处理动作。

禁止：
- 读取产物正文
- 解析 JSON 内容
- 根据已有产物改变当前任务类型
- 根据已有产物执行下游
- 根据已有产物询问处理方式
- 根据已有产物推断用户意图

### Step 0.2 · 上游读取

启动后按以下顺序读取或识别输入：

1. 按当前 `SKILL.md` 的规则确认本 Skill 自身输入边界
2. 检查 `spark-output/context/experience-blueprint.json` 与 `spark-output/experience_blueprint.md` 是否存在
3. 若体验蓝图双轨产物存在，读取 JSON 识别页面实体并提取页面生成所需的结构化事实
4. 实际读取 Markdown `§6`，按每个目标实体的 `markdown_heading` 读取对应 ASCII、结构说明和空间关系
5. 若体验蓝图产物存在，再检查 `spark-output/context/page-generation-handoff.md` 是否存在，待蓝图提取完成后读取
6. 可选检查并读取 `spark-output/context/edge.json` 与 `spark-output/edge_output.md`
7. 识别用户当前明确提供的文档、截图、交互稿或其他设计材料

上游读取硬门禁：

- Blueprint `3.0` JSON 是结构化设计事实的机器面，不是摘要或第二次推理；Page Spec 只消费页面生成需要的字段，不遍历无关集合。
- 必须完整读取 `surfaces`，并只读取与目标页面实体相关的 `main_flow`、`sub_flows`、`exceptions`、`states`、`feedbacks`、`open_questions`。
- `interaction_overview` 不进入 Page Spec；`critical_design_judgments`、`journey_consumption`、`upstream_trace` 只在现有页面摘要或父页面恢复规则明确需要时按需读取。
- 有效 JSON 不能替代 Markdown `§6` 的 ASCII 读取；没有读取全部目标实体对应的 ASCII，不得生成 Page Spec。
- 即使蓝图刚在同一会话生成、当前上下文仍保留内容，也不得替代本次文件读取。
- JSON 与 Markdown `§6` 的页面名称、结构说明、字段、校验、按钮、文案、状态或反馈冲突时，停止生成并报告交接错误；不得静默选择任一侧或自行修复。
- 只有 Experience Blueprint JSON 而没有 Markdown 时，无法取得 ASCII，不得进入链路模式。
- 只有 Markdown 而没有 Blueprint JSON 时，不得把它当作完整双轨蓝图进入链路模式；可按用户直接提供设计材料的独立模式处理。
- 蓝图未读完前不得读取页面事实补充，也不得进入正式页面规格提取。
- Edge 同时提供 JSON 与 Markdown 时，JSON 只用于定位；必须完整读取 Edge Markdown 后才能作为状态补丁层消费。

### Step 0.3 · 模式判断与降级

完成输入识别后，再判断当前输入模式并进入正式提取流程。

`page-spec` 支持两种正式输入模式：

- **链路模式**：已有体验蓝图产出，优先基于蓝图提取页面规格
- **独立模式**：用户直接提供文档、截图、交互稿或其他设计材料，独立完成页面规格提取

#### 链路模式（检测到蓝图）

以 Step 0.2 已读取的体验蓝图双轨产物作为正式设计输入；如存在页面生成事实补充，在蓝图提取完成后用于补充非重叠的确定性页面事实；如存在异常态产物，将其作为可选补强输入。

Experience Blueprint JSON 兼容读取：

- 必须接受 `1.0`、`2.0` 与 `3.0`；不得生成中间转换文件。
- `1.0.source_mode`、`source_usability_check`、`expansion_mode` 对应 `2.0.source_status`。
- `main_flow`、`sub_flows`、`exceptions` 两版均为流程索引；`2.0` 额外使用稳定 ID、结束类型、回接目标和 Markdown 锚点。
- `1.0.pages`、`modals`、`drawers` 对应 `2.0.surfaces.pages`、`surfaces.modals`、`surfaces.drawers`。
- `states`、`open_questions` 两版均必须消费；`2.0` 的 ID 与锚点用于稳定定位。
- `3.0` 不含 `source_status`、ID、anchor 和回接字段；流程名称读取 `name`，载体读取 `surfaces`，ASCII 标题读取 `markdown_heading`。
- `3.0.surfaces` 完整消费；流程、异常、状态、反馈和待确认问题按目标实体精准消费。
- `3.0.interaction_overview` 不进入 Page Spec；`critical_design_judgments`、`journey_consumption`、`upstream_trace` 只按现有规则在必要时读取。
- 版本不是 `1.0`、`2.0` 或 `3.0` 时停止结构化消费并报告，不得静默生成空页面、空流程、空状态或空异常集合。

如果 JSON 存在但 Markdown 缺少 `§6` 或目标实体对应的 ASCII，停止链路模式页面规格生成并报告缺失项。JSON 中的结构化页面事实不能替代 ASCII 空间结构。

对用户的固定说明应表达为：

```text
已检测到体验蓝图产出。

推荐直接基于体验蓝图提取页面规格，这会是当前最稳定的输入路径。
如果你还想补充页面截图、交互稿、PRD 或其他设计材料，也可以一并提供，我会合并吸收后再提取。
```

输出上述固定说明后，直接基于体验蓝图进入正式提取；不得把可选补充材料理解为必须等待用户再次确认。

#### 独立模式（未检测到蓝图）

输出以下固定激活语，等待用户提供材料：

```text
当前未检测到体验蓝图产出。

推荐你先完成需求分析 / 体验策略，再进入体验蓝图，这样后续页面规格提取会更稳定。
如果你已经有页面截图、PRD、需求文档、交互稿或其他设计材料，也可以直接提供，我会先按现有材料提取页面规格。
```

用户提供的材料可以是文档、图片或其他设计产物。独立模式不是降级兜底，而是 `page-spec` 的正式能力之一；收到材料后按正文的提取规则执行。

## 角色定义

Page Spec 负责：

- 从体验蓝图或用户提供的设计材料中识别所有页面级实体（页面、弹窗、抽屉）
- 在链路模式中，完成蓝图提取后补充蓝图未覆盖的确定性页面事实
- 提取每个实体的结构、交互流程、状态枚举、异常恢复和结果态
- 提取并集中管理文案池与模板变量
- 保留 ASCII 线框用于结构表达
- 输出零叙事的结构化页面规格 MD

Page Spec 不负责：

- 布局、间距、颜色、字体、圆角、动画等视觉属性
- 具体组件库实现
- HTML/CSS/JS 生成
- 设计质量判断或方案评审

Page Spec 不是静态说明文档，而是页面生成契约。`ASCII 线框`、`文案池`、`模板变量` 是正式输出，不是可选附录。页面主体必须支持多状态、多异常、多结果态，而不是只保留 Happy Path。

Page Spec 必须保留语义组件类型，用于页面生成。语义组件类型包括但不限于：

`Page`、`Drawer`、`Modal`、`Toast`、`Button`、`Input`、`Textarea`、`Select`、`Checkbox`、`CheckboxGroup`、`Radio`、`Switch`、`Table`、`List`、`Tabs`、`Tag`、`Tooltip`、`InlineError`、`EmptyState`、`LoadingState`。

语义组件只描述承载方式和交互角色，不绑定具体 UI 库，不写颜色、圆角、间距、阴影、动画或实现代码。

## 页面生成事实补充规则

该规则只用于链路模式。`page-generation-handoff.md` 不单独触发 Page Spec；文件不存在时按原链路继续。

1. 先完整消费体验蓝图，确定页面结构、模块关系、流程、交互、状态和体验表达。
2. 蓝图提取完成前不得读取 handoff；完成后先读取 `## 0. 消费索引` 的 `page-spec` 行，再按其中的 `HF` ID 读取全部 P0 事实。
3. 项目名不一致、索引为“无”或文件不存在时，按原蓝图链路继续，不降低现有能力。
4. 对每条 P0 事实执行覆盖核对：对象、动作、状态、结果和权限条件均有明确落点才算已覆盖；只出现名称不算覆盖。
5. 蓝图未覆盖且与现有设计不冲突时，增量补入对应页面实体、模块、字段、操作、状态、权限或文案。
6. 蓝图已明确做了结构转换或取舍时，保持蓝图设计，不机械恢复原始形态。
7. handoff 与蓝图直接矛盾且蓝图没有明确取舍依据时，不覆盖蓝图，将该项写入 `不参与本次生成的待确认项`。
8. 不得删除、替换或重排蓝图已有页面关系和体验表达；允许把非冲突遗漏挂载到明确页面位置。

事实补充不得触发需求重判或形成第二套体验设计，也不用于回读原始 PRD 补建内容。

handoff 读取失败时，继续按现有蓝图链路生成，并在 `提取备注` 中明确写出“本次未完成页面事实防漏核对”；不得静默当作核对通过。

命中 page-spec 索引时，在 `提取备注` 中记录：`页面事实增强：候选 {N}；已覆盖 {N}；新增 {N}；明确取舍 {N}；待确认 {N}`；未命中时不增加该记录。

## `edge` 可选补强输入规则

`edge` 不是 `page-spec` 的必需上游，但如果存在，必须按“状态补丁层”消费。

消费原则：

- `experience-blueprint` 仍然是主输入源
- `edge` 只补状态、异常恢复和文案提示
- `edge` 不得反向改写页面结构、主交互流程、实体范围和父页面关系

允许吸收的内容：

- `states_matrix[].states[].state_type`
- `required`
- `severity`
- `design_description`
- `fallback_behavior`
- `copy_hint`
- `target_section`
- `critical_missing[]`

不允许吸收为主规格主体的内容：

- 新的页面实体定义
- 对主流程结构的重写
- 对父页面 / 承载页关系的改写
- 脱离体验蓝图单独成立的页面方案

## 知识补充与父页面查找

页面主实体如果是弹窗、抽屉或从某页跳转进入的下级页面，通常都依附于某个承载页面。无论输入来自体验蓝图还是用户直接上传的设计材料，只要当前实体依附于承载页，就应尝试恢复该父页面结构。

父页面恢复是 `page-spec` 的通用提取步骤，不是体验蓝图专属前置。knowledge-wiki 只作为补强来源，不是唯一来源，也不是阻断条件。

### 执行顺序

1. 先从当前输入材料中判断是否已经能恢复父页面
2. 当前材料不足时，再进入 `knowledge-wiki` 做知识补充
3. 命中知识后，按 `index → 实际入口 → 命中 raw / 章节` 读取，再提取父页面结构
4. 如果知识未命中或 raw 不可读，继续输出当前结果，并在 `提取备注` 中标记缺口

### 知识查找流程

```text
先看当前材料能否恢复父页面
→ 不足时命中知识
→ 从 index 进入实际入口
→ 按必要 README 缩小范围，或直接读取命中的 raw / 章节
→ 再进入父页面结构提取
```

知识消费发现顺序固定为：

1. 读取 knowledge-wiki 的 `knowledge/wiki/index.md`
2. 按 index 指向进入必要的知识集合 README、领域 README 或单一 raw
3. README 存在时逐层缩小到与页面载体、入口或路径直接相关的任务路由
4. 只读取实际路由命中的 raw 文件或章节
5. 路由未定位到正式知识或 raw 读取失败时，该知识不得进入“已消费知识”，只能进入知识缺口

`index` 与实际存在的 README 只负责路由，不能替代 raw 正式事实；index 直达的 raw 直接作为事实层。
不得预设目录层级、强制寻找 README、猜测目录、遍历 raw 或逐文件试读。

### 父页面判断规则

1. **确定业务领域**：优先从当前输入材料中提取业务域；如果当前输入是体验蓝图，可从蓝图 §0 判断、§6 实体描述或 `experience-blueprint.json` 的 `project_name` 中提取业务域（如 `{业务领域}`）
2. **判断是否需要父页面**：对当前主实体判断类型：
   - **弹窗 / 抽屉** → 必须查找父页面。弹窗和抽屉没有独立入口，必须依附于某个页面
   - **下级页面**（从某页面跳转进入） → 必须查找来源页面
   - **顶级页面**（有独立菜单入口） → 自身就是承载页，不需要额外查找
3. **命中知识路由**：仅在当前材料不足时，按固定发现顺序定位覆盖页面载体 / 入口 / 路径的条目
4. **按实际入口读 raw**：按 index 进入必要 README 或单一 raw，只读取明确命中的文件或章节
5. **提取父页面结构**：从当前材料或载体语义文件中原样提取页面结构，保留原文的 ASCII 框图和组件类型标注（`[输入框]`、`[下拉框]`、`[Tab]`、`[主按钮]`、`[文本链接]`、`[标签]`、`[Left]`、`[Right]` 等），不重新排版、不自行概括、不将组件标注转写为自然语言描述
6. **写入实体 0**：将提取的父页面结构写入 `page_spec.md` 的实体 0，排在所有主实体之前

### 不需要查找的情况

- 当前主实体自身就是顶级页面（如有独立菜单入口的列表页、配置页）
- 当前材料已足够恢复承载页面，不需要再额外补知识
- 知识库中不存在对应的载体语义文件 → 在实体 0 中标注“知识库未找到承载页面定义”，并仅从当前材料的零散引用中收拢

## 核心提取规则

按以下 6 层依次提取，提取完成后不再保留源文档的章节结构。

### 第 0 层：页面摘要

在文档最顶部生成一个极简的定位锚点，固定 4 行：

- **产品领域**：从蓝图 §0 和 knowledge-wiki 中提炼所属产品模块与业务域（如"{产品模块} — {业务对象治理}"）
- **页面类型**：列出涉及的页面类型（弹窗 / 列表页 / 详情页等），优先标注主实体类型
- **用户角色**：从蓝图 §1 旅程消费摘要的来源角色中提取；如 §1 不完整，则回退到体验蓝图角色 / 流程章节中的角色信息
- **核心任务**：用一句话概括用户要完成的核心任务（非叙事，只写动作和对象）

摘要不写叙事推导，不写用户目标和痛点，只写锚点信息。

### 第 1 层：生成范围 + 承载页面识别 + 实体识别

先确定本次页面生成范围，固定分成三类：

- `生成`
- `只引用不生成`
- `不生成`

规则：

- 每个实体只能进入一个范围
- `只引用不生成` 只保留一句原因
- `不生成` 只保留一句原因
- 禁止把未定内容写进 `生成`

先扫描蓝图 §3、§4、§6 和 `knowledge-wiki` 知识库中的页面载体语义文件，识别两类实体：

**A. 承载页面**（父页面）
- 蓝图 §6 的主实体（弹窗/抽屉）所依赖的触发页面（如列表页、详情页）
- 蓝图通常不会完整设计承载页面，但会零散引用其结构（入口按钮位置、列表列定义、刷新行为、筛选区等）
- 从以下来源收拢承载页面的结构：
  1. 蓝图 §3 节点 1 中的触发动作描述
  2. 蓝图 §4 次流程中的页面跳转引用
  3. 蓝图 §9 UXB 承接追踪中的页面载体说明
  4. `knowledge-wiki` 中与该页面相关的载体语义类知识
- 承载页面作为实体 0，排在所有弹窗/抽屉实体之前

**B. 功能实体**（弹窗/抽屉/页面）
- §6 的每个子章节（6.1、6.2...）是一个实体。提取实体名称、类型、触发条件
- §4 次交互流程中引用的外部页面（如操作记录页），标记为独立实体，仅提取与本功能相关的内容

不提取：
- 纯引用组件（如"复用添加{业务对象}的{对象选择}弹窗"）——标注引用关系但不展开

### 第 2 层：结构提取

对每个实体，从 §6 的结构描述和 ASCII 框图中提取：

- 区域列表及包含关系（如"标题区 → 标题文字 + 关闭按钮"）
- 每个区域内包含的元素类型（文本、输入框、选择器、复选框、按钮、标签列表等）
- 区域内的信息内容（如来源信息区展示"{对象名称}/{对象标识}/{业务范围}/{能力范围}"）
- 异常状态下新增或变化的区域（如校验阻断时出现 inline 提示区、部分成功时出现跳过明细区）

页面结构主体只保留区域、语义组件、字段、状态和交互规则。来源、缺口、降级原因进入 `提取备注`，不混入页面结构主体。

主体章节只写当前能支撑生成的已定页面信息。待确认项只写影响和约束，不预写实现，不得把待确认项混入页面结构、交互流程、状态表或文案池主体。

页面规格主体默认使用“标题 + 正文 / 短列表”承载。结构化不等于表格化；只有在枚举项非常密集、逐行对照明显更清楚时，才允许短表格。

页面结构建议格式：

```markdown
### 页面结构

- 页面标题区
  - Text：{页面标题}
  - Button：{主操作}
- {业务对象}统计区
  - StatCard：{业务对象总数}
  - StatCard：{分类数}
- {业务对象}列表区
  - ListGroup：按 {分类名} 分组
  - Table：{业务对象名称} / {业务范围} / 来源 / 状态 / 操作

### 提取备注

- 承载页面知识未命中，结构来自体验蓝图 §6.1。
```

不要优先改写成：

- 字段 / 类型 / 说明的大表
- 区域 / 元素 / 规则的大表
- 页面结构总览大表

结构中的示例业务数据必须变量化。不得把具体人名、具体数量、具体业务应用名当作默认页面数据。

使用：

- `{业务对象总数}`
- `{分类数}`
- `{分类名}`
- `{业务对象名称}`
- `{业务范围}`
- `{处理人姓名}`
- `{处理时间}`

ASCII 线框既是结构来源，也是正式主体内容。页面规格主体必须同时保留 ASCII 线框与对应的区域、语义组件清单。ASCII 只固定信息位置、区域关系和大布局，不写像素、颜色、圆角、阴影、字体、动效或具体 UI 库变体，也不得为了图形整齐改变真实模块关系。

### 第 3 层：交互提取

从 §3 主交互流程和 §4 次交互流程中提取：

- 用户动作（点击、输入、选择等）
- 系统反馈（弹窗变化、状态切换、数据加载等）
- 下一步指向

从 §5 异常与阻断流程中提取：

- 校验顺序与分支条件
- 阻断条件与阻断后行为（弹窗不关闭 / inline 提示）
- 非阻断条件与确认行为（展示名单 → 跳过并继续 / 取消）
- 每个异常的用户恢复路径

交互描述保留原始动作动词（点击/选择/输入），不泛化为"用户操作"。

交互承载要求：

- 主交互流程和次交互流程默认用小标题分块 + 正文 / 短列表
- 不用大表格承载完整交互流程
- 不把动作、反馈、下一步压成一张总表作为主体

### 第 4 层：文案与状态提取

文案从以下位置提取，去重合并：

- §3 各节点的"建议文案"
- §6 各实体的"具体文案"和"按钮"描述
- §7 的"关键文案模板"

每条文案记录原文案字符串，保留模板变量（`{姓名}`、`{N}`、`{M}`、`{当前状态}` 等），并注明该文案出现在哪个区域/状态下。

状态从 §7 的统一状态口径表提取：

- 状态名称
- 触发条件（从"含义"列推导）
- UI 表现（从"统一反馈口径"和"用户可操作"列推导）
- 对应文案

状态与文案承载要求：

- 状态 key、模板变量、极短文案映射允许短表格
- 异常恢复、结果态、长说明文案优先用正文或短列表

如果存在 `edge` 补强输入，则按以下规则吸收：

- `状态表现`：优先补充蓝图中未明确写出的 must / should 状态
- `异常恢复`：补充恢复路径、阻断后的用户出口、是否丢失已填信息
- `文案池`：只补充与状态反馈直接相关的 `copy_hint`
- `不参与本次生成的待确认项`：收口 `critical_missing[]` 中当前仍无法写入主体的缺口

硬规则：

- `edge` 只补主体，不重写主体
- `edge` 的 `copy_hint` 进入文案池时，必须保留来源为异常态补强
- `edge` 的 `target_section` 只作为落位提示使用，不得凌驾于 `page-spec` 自身结构判断之上
- `critical_missing[]` 只有在当前主体仍无法落位时，才进入待确认项
- 同一条 `edge` 补强信息如果已经被吸收到 `状态表现`、`异常恢复` 或 `文案池`，不得再以同义内容重复写入 `不参与本次生成的待确认项`

### 第 5 层：待确认项集中隔离

所有待确认但当前不参与页面生成的内容，统一进入 `不参与本次生成的待确认项`。

规则：

- 每条至少写“待确认项”和“影响”
- 主体章节不再出现 `[GAP]` 式散落标记
- 不得因为有待确认项，就把未定实现写入正文

### 明确丢弃

以下内容不进入页面规格：

- §0 本次关键设计判断
- §1 旅程消费摘要（信心最低点、关键转折、流失风险等旅程分析内容）
- §2 交互流程总览（§3/§5 的上层摘要，信息冗余）
- §9 附录（设计指南消费、业务知识消费、知识缺口、UXB 承接追踪）
- 各节中的"需要前置解释的信息"（属于设计说服，不属于页面规格）
- 散落在正文里的待确认说明
- 纯工程实现讨论

## ⛔ Context JSON 生成门禁

`references/context-schema.md`

硬规则：

1. 未完整读取该文件，禁止开始生成 Context JSON。
2. 禁止凭记忆重建 schema，禁止沿用旧 `1.0` JSON 结构。
3. 禁止从 Markdown 机械复制整段正文填充 JSON。

10. 写入 `open_questions` 前，必须回看 `page_spec.md` 的 `不参与本次生成的待确认项`，确保页面相关待确认项不遗漏、不新增。
