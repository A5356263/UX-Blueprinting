# Page Spec

这个 skill 只做一件事：把体验蓝图 MD 里的"杂志内容"过滤掉，输出一份干净的、可直接用于页面生成的规格文档。

## 角色定义

Page Spec 负责：

- 从体验蓝图 MD 中识别所有页面级实体（页面、弹窗、抽屉）
- 提取每个实体的结构、交互流程、状态枚举和文案
- 输出零叙事的结构化页面规格 MD

Page Spec 不负责：

- 布局、间距、颜色、字体、圆角、动画等视觉属性
- 具体组件库实现
- HTML/CSS/JS 生成
- 设计质量判断或方案评审

Page Spec 必须保留语义组件类型，用于页面生成。语义组件类型包括但不限于：

`Page`、`Drawer`、`Modal`、`Toast`、`Button`、`Input`、`Textarea`、`Select`、`Checkbox`、`CheckboxGroup`、`Radio`、`Switch`、`Table`、`List`、`Tabs`、`Tag`、`Tooltip`、`InlineError`、`EmptyState`、`LoadingState`。

语义组件只描述承载方式和交互角色，不绑定具体 UI 库，不写颜色、圆角、间距、阴影、动画或实现代码。

## 上游读取协议

启动后固定按以下顺序读取：

1. 读取 `shared-workflow/skill-graph.json`
2. 读取 `spark-output/context/experience-blueprint.json`（如有）
3. 读取 `spark-output/experience_blueprint.md`

这是链路消费型 skill，默认承接 `spark-output/` 中的上游产物属于正式工作流。

降级规则：

- 如果 `experience_blueprint.md` 未找到，终止并提示"未找到体验蓝图产出，无法提取页面规格"
- 如果 JSON 存在但 MD 不完整（缺少 §3/§5/§6/§7 中的任一章节），在输出开头标注缺失项，继续提取已有部分

## 知识库父页面查找（强制步骤）

蓝图的主实体通常是弹窗、抽屉或下级页面，它们浮在某个承载页面之上。蓝图不会完整设计承载页面，但承载页面的结构（列定义、操作入口、筛选区、刷新行为）对页面生成至关重要。

此步骤在读取蓝图后、进入核心提取规则前强制执行。

### 查找流程

```text
先命中知识
→ 先读 summary（路由层）
→ 再读该 summary 对应的 raw（事实层）
→ 再进入父页面结构提取
```

知识消费发现顺序固定为：

1. 读取当前可用 knowledge-wiki 的知识索引 / overview / index
2. 从索引中定位目标领域的 summaries 入口
3. 读取命中的 summary
4. 根据 summary 中记录的 source_path / raw 指向读取对应 raw
5. raw 读取失败时，该知识不得进入“已消费知识”，只能进入知识缺口

`summary` 只负责路由，不能作为正式判断依据。
`raw` 以知识索引或 summary 中的指向为准。
不得用猜测目录名、README 替代 summary、直接广读 raw 的方式绕过索引路由。

1. **确定业务领域**：从蓝图的 §0 判断、§6 实体描述或 `experience-blueprint.json` 的 `project_name` 中提取业务域（如 `权限管理`、`组织架构`、`应用管理` 等）

2. **命中知识路由**：按固定发现顺序定位覆盖页面载体 / 入口 / 路径的条目

3. **读 summary → 读 raw**：先读命中的 summary，再按 summary 中记录的 source_path / raw 指向读取对应 raw

4. **判断是否需要父页面**：对蓝图 §6 的每个主实体判断类型：
   - **弹窗 / 抽屉** → 必须查找父页面。弹窗和抽屉没有独立入口，必须依附于某个页面
   - **下级页面**（从某页面跳转进入） → 必须查找来源页面
   - **顶级页面**（有独立菜单入口） → 自身就是承载页，不需要额外查找

5. **提取父页面结构**：从载体语义文件中原样提取页面结构，保留原文的 ASCII 框图和组件类型标注（`[输入框]`、`[下拉框]`、`[Tab]`、`[主按钮]`、`[文本链接]`、`[标签]`、`[Left]`、`[Right]` 等），不重新排版、不自行概括、不将组件标注转写为自然语言描述

6. **写入实体 0**：将提取的父页面结构写入 `page_spec.md` 的实体 0，排在所有蓝图主实体之前

### 不需要查找的情况

- 蓝图主实体自身就是顶级页面（如有独立菜单入口的列表页、配置页）
- 知识库中不存在对应的载体语义文件 → 在实体 0 中标注"知识库未找到承载页面定义"，仅从蓝图零散引用中收拢

## 核心提取规则

按以下 5 层依次提取，提取完成后不再保留源文档的章节结构。

### 第 0 层：页面摘要

在文档最顶部生成一个极简的定位锚点，固定 4 行：

- **产品领域**：从蓝图 §0 和 knowledge-wiki 中提炼所属产品模块与业务域（如"企业权限管理 — 子管理员治理"）
- **页面类型**：列出涉及的页面类型（弹窗 / 列表页 / 详情页等），优先标注主实体类型
- **用户角色**：从蓝图 §1 旅程消费摘要的来源角色中提取；如 §1 不完整，则回退到体验蓝图角色 / 流程章节中的角色信息
- **核心任务**：用一句话概括用户要完成的核心任务（非叙事，只写动作和对象）

摘要不写叙事推导，不写用户目标和痛点，只写锚点信息。

### 第 1 层：承载页面识别 + 实体识别

先扫描蓝图 §3、§4、§6 和 `knowledge-wiki` 知识库中的页面载体语义文件，识别两类实体：

**A. 承载页面**（父页面）
- 蓝图 §6 的主实体（弹窗/抽屉）所依赖的触发页面（如列表页、详情页）
- 蓝图通常不会完整设计承载页面，但会零散引用其结构（入口按钮位置、列表列定义、刷新行为、筛选区等）
- 从以下来源收拢承载页面的结构：
  1. 蓝图 §3 节点 1 中的触发动作描述
  2. 蓝图 §4 次流程中的页面跳转引用
  3. 蓝图 §9 UXB 承接追踪中的页面载体说明
  4. `knowledge-wiki` 中与该页面相关的载体语义类知识
- 承载页面作为实体 0，排在所有弹窗/抽屉实体之前

**B. 功能实体**（弹窗/抽屉/页面）
- §6 的每个子章节（6.1、6.2...）是一个实体。提取实体名称、类型、触发条件
- §4 次交互流程中引用的外部页面（如操作记录页），标记为独立实体，仅提取与本功能相关的内容

不提取：
- 纯引用组件（如"复用添加子管理员的员工选择弹窗"）——标注引用关系但不展开

### 第 2 层：结构提取

对每个实体，从 §6 的结构描述和 ASCII 框图中提取：

- 区域列表及包含关系（如"标题区 → 标题文字 + 关闭按钮"）
- 每个区域内包含的元素类型（文本、输入框、选择器、复选框、按钮、标签列表等）
- 区域内的信息内容（如来源信息区展示"姓名/手机号/组织范围/功能范围"）
- 异常状态下新增或变化的区域（如校验阻断时出现 inline 提示区、部分成功时出现跳过明细区）

页面结构主体只保留区域、语义组件、字段、状态和交互规则。来源、缺口、降级原因进入 `提取备注`，不混入页面结构主体。

页面规格主体默认使用“标题 + 正文 / 短列表”承载。结构化不等于表格化；只有在枚举项非常密集、逐行对照明显更清楚时，才允许短表格。

页面结构建议格式：

```markdown
### 页面结构

- 页面标题区
  - Text：{页面标题}
  - Button：{主操作}
- 权限统计区
  - StatCard：{权限总数}
  - StatCard：{应用数}
- 权限列表区
  - ListGroup：按 {应用名} 分组
  - Table：{权限名} / {数据范围} / 来源 / 状态 / 操作

### 提取备注

- 承载页面知识未命中，结构来自体验蓝图 §6.1。
```

不要优先改写成：

- 字段 / 类型 / 说明的大表
- 区域 / 元素 / 规则的大表
- 页面结构总览大表

结构中的示例业务数据必须变量化。不得把具体人名、具体数量、具体业务应用名当作默认页面数据。

使用：

- `{权限总数}`
- `{应用数}`
- `{应用名}`
- `{权限名}`
- `{数据范围}`
- `{审批人姓名}`
- `{处理时间}`

ASCII 框图可作为结构来源，但页面规格主体必须提取为区域与语义组件清单。

### 第 3 层：交互提取

从 §3 主交互流程和 §4 次交互流程中提取：

- 用户动作（点击、输入、选择等）
- 系统反馈（弹窗变化、状态切换、数据加载等）
- 下一步指向

从 §5 异常与阻断流程中提取：

- 校验顺序与分支条件
- 阻断条件与阻断后行为（弹窗不关闭 / inline 提示）
- 非阻断条件与确认行为（展示名单 → 跳过并继续 / 取消）
- 每个异常的用户恢复路径

交互描述保留原始动作动词（点击/选择/输入），不泛化为"用户操作"。

交互承载要求：

- 主交互流程和次交互流程默认用小标题分块 + 正文 / 短列表
- 不用大表格承载完整交互流程
- 不把动作、反馈、下一步压成一张总表作为主体

### 第 4 层：文案与状态提取

文案从以下位置提取，去重合并：

- §3 各节点的"建议文案"
- §6 各实体的"具体文案"和"按钮"描述
- §7 的"关键文案模板"

每条文案记录原文案字符串，保留模板变量（`{姓名}`、`{N}`、`{M}`、`{当前状态}` 等），并注明该文案出现在哪个区域/状态下。

状态从 §7 的统一状态口径表提取：

- 状态名称
- 触发条件（从"含义"列推导）
- UI 表现（从"统一反馈口径"和"用户可操作"列推导）
- 对应文案

状态与文案承载要求：

- 状态 key、模板变量、极短文案映射允许短表格
- 异常恢复、结果态、长说明文案优先用正文或短列表

### 明确丢弃

以下内容不进入页面规格：

- §0 本次关键设计判断
- §1 旅程消费摘要（信心最低点、关键转折、流失风险等旅程分析内容）
- §2 交互流程总览（§3/§5 的上层摘要，信息冗余）
- §8 待确认问题
- §9 附录（设计指南消费、业务知识消费、知识缺口、UXB 承接追踪）
- 各节中的"需要前置解释的信息"（属于设计说服，不属于页面规格）
- ASCII 框图本身（只提取其中描述的结构关系）
- [GAP] 标记的未闭合内容（在输出中标注但留空）

主体承载限制：

- 页面结构、交互流程、异常恢复三部分不得整章表格化
- 表格只保留在状态 key、模板变量、文案池、待确认项、极短字段对照等高密度枚举区域
- 未明确允许的章节，不用 Markdown 表格承载主体内容

生成范围规则：

- `生成`：本次页面生成必须覆盖的实体
- `只引用不生成`：用于交互跳转、状态来源或上下文承接，但不生成页面
- `不生成`：蓝图未给出结构、超出本次任务范围或属于已有系统能力
- 每个实体只能归入一个范围
- `只引用不生成` / `不生成` 最多写一句原因

## Context JSON 写入

文档生成后，写入 `spark-output/context/page-spec.json`：

- `skill`
- `version`
- `generated_at`
- `project_name`
- `entities[]`：每个实体的 `name`、`type`
- `extraction_summary`：`entities_count`、`states_count`、`copy_count`、`exceptions_count`

写入失败不阻断完成，但应在输出中提示。

4. 如果 `next_hint.preferred` 非空，按标准三层结构输出
