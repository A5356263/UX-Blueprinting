# Page Spec

这个 skill 只做一件事：把设计材料整理成页面生成契约，过滤掉页面生成无关的叙事和说服性内容，输出一份干净的、可直接用于页面生成的规格文档。主要输入是体验蓝图，也接受用户直接上传的设计材料。

## Step 0 · 运行入口

### Step 0.1 · 本 Skill 产物状态

执行本 Skill 前，只检查本 Skill 对应正式产物是否存在。

正式产物：
- `spark-output/page_spec.md`
- `spark-output/context/page-spec.json`

只允许检查文件是否存在；禁止读取产物正文、禁止解析 JSON 内容、禁止根据已有产物改变当前任务类型。

若任一正式产物存在，先输出以下状态提示，然后继续执行本 Skill 的入口规则：

```text
检测到本 Skill 已有正式产物（已产出）。
```

该提示只表示状态，不代表采取任何处理动作。

禁止：
- 读取产物正文
- 解析 JSON 内容
- 根据已有产物改变当前任务类型
- 根据已有产物执行下游
- 根据已有产物询问处理方式
- 根据已有产物推断用户意图

### Step 0.2 · 上游读取

启动后按以下顺序读取或识别输入：

1. 按当前 `SKILL.md` 的规则确认本 Skill 自身输入边界
2. 检查 `spark-output/context/experience-blueprint.json` 与 `spark-output/experience_blueprint.md` 是否存在
3. 若体验蓝图双轨产物存在，先读取 JSON，定位页面实体和相关结构化事实
4. 完整读取 `spark-output/experience_blueprint.md`；Markdown 是正式语义源，不得只读取 `§6` 或目标实体局部
5. 读取 `§6` 中全部目标实体对应的 ASCII、结构说明和空间关系
6. 可选检查并读取 `spark-output/context/edge.json` 与 `spark-output/edge_output.md`
7. 识别用户当前明确提供的文档、截图、交互稿或其他设计材料

上游读取硬门禁：

- Blueprint JSON 只用于定位页面实体和结构化事实；Blueprint Markdown 是正式语义源。
- 必须完整读取 `surfaces`，并只读取与目标页面实体相关的 `main_flow`、`sub_flows`、`exceptions`、`states`、`feedbacks`、`open_questions`。
- 必须完整读取 Blueprint Markdown `§0-§9`：`§0` 用于设计取舍，`§1` 用于页面结构与入口，`§2` 用于旅程消费摘要，`§3-§6` 用于流程和异常，`§7` 用于页面与 ASCII，`§8` 用于状态与文案，`§9` 用于追溯依据。
- 完整读取不等于全量复制；只提取页面生成需要的结构、流程、状态、异常、文案和空间关系。
- 有效 JSON 不能替代 Markdown 全文和 `§6` ASCII；没有读取完整 Markdown 及全部目标实体 ASCII，不得生成 Page Spec。
- 即使蓝图刚在同一会话生成、当前上下文仍保留内容，也不得替代本次文件读取。
- JSON 与 Markdown 不一致时，按 Markdown 生成，并在`提取备注`中记录“蓝图 JSON 交接不一致”；不得用 JSON 覆盖 Markdown。
- 只有 Markdown 缺少目标实体或对应 ASCII，导致页面空间结构无法恢复时，才停止该实体生成并进入待确认。
- 只有 Experience Blueprint JSON 而没有 Markdown 时，无法取得 ASCII，不得进入链路模式。
- 只有 Markdown 而没有 Blueprint JSON 时，不得把它当作完整双轨蓝图进入链路模式；可按用户直接提供设计材料的独立模式处理。
- Edge 同时提供 JSON 与 Markdown 时，JSON 只用于定位；必须完整读取 Edge Markdown 后才能作为状态补丁层消费。

### Step 0.3 · 模式判断与降级

完成输入识别后，再判断当前输入模式并进入正式提取流程。

`page-spec` 支持两种正式输入模式：

- **链路模式**：已有体验蓝图产出，优先基于蓝图提取页面规格
- **独立模式**：用户直接提供文档、截图、交互稿或其他设计材料，独立完成页面规格提取

#### 链路模式（检测到蓝图）

以 Step 0.2 已读取的体验蓝图双轨产物作为正式设计输入；JSON 用于定位，Markdown 承担正式语义；如存在异常态产物，将其作为可选补强输入。

Experience Blueprint JSON 兼容读取：

- 必须接受 `1.0`、`2.0` 与 `3.0`；不得生成中间转换文件。
- `1.0.source_mode`、`source_usability_check`、`expansion_mode` 对应 `2.0.source_status`。
- `main_flow`、`sub_flows`、`exceptions` 两版均为流程索引；`2.0` 额外使用稳定 ID、结束类型、回接目标和 Markdown 锚点。
- `1.0.pages`、`modals`、`drawers` 对应 `2.0.surfaces.pages`、`surfaces.modals`、`surfaces.drawers`。
- `states`、`open_questions` 两版均必须消费；`2.0` 的 ID 与锚点用于稳定定位。
- `3.0` 不含 `source_status`、ID、anchor 和回接字段；流程名称读取 `name`，载体读取 `surfaces`，ASCII 标题读取 `markdown_heading`。
- `3.0.surfaces` 完整消费；流程、异常、状态、反馈和待确认问题按目标实体精准消费。
- `3.0.interaction_overview` 不进入 Page Spec；`critical_design_judgments`、`journey_consumption`、`upstream_trace` 只按现有规则在必要时读取。
- 版本不是 `1.0`、`2.0` 或 `3.0` 时停止结构化消费并报告，不得静默生成空页面、空流程、空状态或空异常集合。

如果 JSON 存在但 Markdown 缺少 `§7` 或目标实体对应的 ASCII，停止链路模式页面规格生成并报告缺失项。JSON 中的结构化页面事实不能替代 ASCII 空间结构。

对用户的固定说明应表达为：

```text
已检测到体验蓝图产出。

推荐直接基于体验蓝图提取页面规格，这会是当前最稳定的输入路径。
如果你还想补充页面截图、交互稿、PRD 或其他设计材料，也可以一并提供，我会合并吸收后再提取。
```

输出上述固定说明后，直接基于体验蓝图进入正式提取；不得把可选补充材料理解为必须等待用户再次确认。

#### 独立模式（未检测到蓝图）

输出以下固定激活语，等待用户提供材料：

```text
当前未检测到体验蓝图产出。

推荐你先完成需求分析 / 体验策略，再进入体验蓝图，这样后续页面规格提取会更稳定。
如果你已经有页面截图、PRD、需求文档、交互稿或其他设计材料，也可以直接提供，我会先按现有材料提取页面规格。
```

用户提供的材料可以是文档、图片或其他设计产物。独立模式不是降级兜底，而是 `page-spec` 的正式能力之一；收到材料后按正文的提取规则执行。

## 角色定义

Page Spec 负责：

- 从体验蓝图或用户提供的设计材料中识别所有页面级实体（页面、弹窗、抽屉）
- 提取每个实体的结构、交互流程、状态枚举、异常恢复和结果态
- 提取并集中管理文案池与模板变量
- 保留 ASCII 线框用于结构表达
- 输出零叙事的结构化页面规格 MD

Page Spec 不负责：

- 布局、间距、颜色、字体、圆角、动画等视觉属性
- 具体组件库实现
- HTML/CSS/JS 生成
- 设计质量判断或方案评审

Page Spec 不是静态说明文档，而是页面生成契约。`ASCII 线框`、`文案池`、`模板变量` 是正式输出，不是可选附录。页面主体必须支持多状态、多异常、多结果态，而不是只保留 Happy Path。

Page Spec 必须保留语义组件类型，用于页面生成。语义组件类型包括但不限于：

`Page`、`Drawer`、`Modal`、`Toast`、`Button`、`Input`、`Textarea`、`Select`、`Checkbox`、`CheckboxGroup`、`Radio`、`Switch`、`Table`、`List`、`Tabs`、`Tag`、`Tooltip`、`InlineError`、`EmptyState`、`LoadingState`。

语义组件只描述承载方式和交互角色，不绑定具体 UI 库，不写颜色、圆角、间距、阴影、动画或实现代码。

## `edge` 可选补强输入规则

`edge` 不是 `page-spec` 的必需上游，但如果存在，必须按“状态补丁层”消费。

消费原则：

- `experience-blueprint` 仍然是主输入源
- `edge` 只补状态、异常恢复和文案提示
- `edge` 不得反向改写页面结构、主交互流程、实体范围和父页面关系

允许吸收的内容：

- `states_matrix[].states[].state_type`
- `required`
- `severity`
- `design_description`
- `fallback_behavior`
- `copy_hint`
- `target_section`
- `critical_missing[]`

不允许吸收为主规格主体的内容：

- 新的页面实体定义
- 对主流程结构的重写
- 对父页面 / 承载页关系的改写
- 脱离体验蓝图单独成立的页面方案

## 知识补充与父页面查找

页面主实体如果是弹窗、抽屉或从某页跳转进入的下级页面，通常都依附于某个承载页面。无论输入来自体验蓝图还是用户直接上传的设计材料，只要当前实体依附于承载页，就应尝试恢复该父页面结构。

父页面恢复是 `page-spec` 的通用提取步骤，不是体验蓝图专属前置。knowledge-wiki 只作为补强来源，不是唯一来源，也不是阻断条件。

### 执行顺序

1. 先从当前输入材料中判断是否已经能恢复父页面
2. 当前材料不足时，再进入 `knowledge-wiki` 做知识补充
3. 命中知识后，按 `index → 业务领域 README 或明确直达的单一设计知识 → 正式文件 → 顶部导航命中章节` 读取，再提取父页面结构
4. 如果知识未命中或 raw 不可读，继续输出当前结果，并在 `提取备注` 中标记缺口

### 知识查找流程

```text
先看当前材料能否恢复父页面
→ 不足时命中知识
→ 从 index 进入实际入口
→ 业务知识按领域 README 选择文件；明确直达的单一设计知识直接进入
→ 按目标文件顶部导航读取命中章节
→ 再进入父页面结构提取
```

知识消费发现顺序固定为：

1. 读取 knowledge-wiki 的 `knowledge/wiki/index.md`
2. 业务入口进入领域 README；index 明确直达的单一设计知识直接进入
3. 学习 README 中与页面载体、入口或路径相关的实际文件路由
4. 进入目标文件后按顶部导航只读取命中章节
5. 路由未定位到正式知识或 raw 读取失败时，该知识不得进入“已消费知识”，只能进入知识缺口

`index` 与 README 只负责路由，不能替代 raw 正式事实；index 明确直达的单一设计知识直接作为事实层。
不得猜测目录、遍历 raw 或逐文件试读。

- 停止条件：命中局部知识后不得停止；问题涉及的主体、动作、条件、例外、结果及已触发依赖均有正式依据后再输出。
- 封闭枚举：仅以完整正式清单作答；未命中完整清单时，不得把局部事实表述为全集。
- 输出边界：以上仅作内部检查，不展示读取过程或检查项；证据不足影响正确性时，只说明必要边界。

### 父页面判断规则

1. **确定业务领域**：优先从当前输入材料中提取业务域；如果当前输入是体验蓝图，可从蓝图 §0 判断、§6 实体描述或 `experience-blueprint.json` 的 `project_name` 中提取业务域（如 `{业务领域}`）
2. **判断是否需要父页面**：对当前主实体判断类型：
   - **弹窗 / 抽屉** → 必须查找父页面。弹窗和抽屉没有独立入口，必须依附于某个页面
   - **下级页面**（从某页面跳转进入） → 必须查找来源页面
   - **顶级页面**（有独立菜单入口） → 自身就是承载页，不需要额外查找
3. **命中知识路由**：仅在当前材料不足时，按固定发现顺序定位覆盖页面载体 / 入口 / 路径的条目
4. **按实际入口读 raw**：业务知识按领域 README 选文件，明确直达的单一设计知识直接进入，再按顶部导航只读取命中章节
5. **提取父页面结构**：从当前材料或载体语义文件中原样提取页面结构，保留原文的 ASCII 框图和组件类型标注（`[输入框]`、`[下拉框]`、`[Tab]`、`[主按钮]`、`[文本链接]`、`[标签]`、`[Left]`、`[Right]` 等），不重新排版、不自行概括、不将组件标注转写为自然语言描述
6. **写入实体 0**：将提取的父页面结构写入 `page_spec.md` 的实体 0，排在所有主实体之前

### 不需要查找的情况

- 当前主实体自身就是顶级页面（如有独立菜单入口的列表页、配置页）
- 当前材料已足够恢复承载页面，不需要再额外补知识
- 知识库中不存在对应的载体语义文件 → 在实体 0 中标注“知识库未找到承载页面定义”，并仅从当前材料的零散引用中收拢

## 核心提取规则

按以下 6 层依次提取，提取完成后不再保留源文档的章节结构。

### 第 0 层：页面摘要

在文档最顶部生成一个极简的定位锚点，固定 4 行：

- **产品领域**：从蓝图 §0 和 knowledge-wiki 中提炼所属产品模块与业务域（如"{产品模块} — {业务对象治理}"）
- **页面类型**：列出涉及的页面类型（弹窗 / 列表页 / 详情页等），优先标注主实体类型
- **用户角色**：优先读取 `journey_consumption[].source_stage` 中的角色；Markdown 回读时从蓝图 §2 旅程消费摘要标题的角色部分读取同一信息。如 §2 不完整，则回退到体验蓝图角色 / 流程章节中的角色信息
- **核心任务**：用一句话概括用户要完成的核心任务（非叙事，只写动作和对象）

摘要不写叙事推导，不写用户目标和痛点，只写锚点信息。

### 第 1 层：生成范围 + 承载页面识别 + 实体识别

当前任务闭环从用户进入本次任务的承载页面开始，到用户获得成功、失败、阻断或取消结果并返回稳定界面为止。期间用户必须看到或操作的界面载体和独立界面状态都属于当前任务闭环。

实体登记与范围分类必须严格分开：

1. **完整登记**：从 Blueprint JSON `surfaces`、Markdown `§6` 及 Markdown 全文登记实体候选；再扫描 `§2～§5` 的流程、异常、状态和反馈，识别所有新界面载体与独立界面状态。此步骤不得判断生成范围或提前过滤。
2. **统一分类**：完成登记、去重、信息收拢和父子关系建立后，才允许判断`生成`、`只引用不生成`或`不生成`。

登记时先判断载体是否变化，再按固定规则区分实体与状态：

- 离开原载体、关闭原载体后打开新载体，或在原载体上叠加新的页面、弹窗、抽屉、Popover、选择器，登记为独立实体。
- 原载体不关闭，仅在内部切换内容、按钮、结果或错误表现，登记为所属实体的必须生成状态或子视图，不得创建新实体。
- 标题或名称与交互描述冲突时，以载体行为为准；章节标题、实体名称不能单独证明存在新实体。
- Toast、InlineError、Loading、EmptyState 等不单独登记实体，但必须进入所属实体的状态规格。
- 纯展示组件既不产生新载体，也没有独立操作和返回结果时，不单独登记实体。

“知道了”“关闭”“返回”“重试”等单一操作仍属于用户操作。确认、阻断、失败或结果信息只要由新载体承接，就必须登记为独立实体，不得降级为普通流程文字。

最低信息标准固定为：

- 页面或子页面：入口或触发条件、主要区域、核心操作、完成或返回结果。
- 弹窗、抽屉、Popover 或选择器：触发条件、关键内容、用户操作、关闭或返回结果。
- 实体状态：触发条件、可见变化、用户出口或后续结果。

达到最低信息标准时必须进入结构提取。未达到时仍须登记，归入`不生成`并写明缺少的必要信息，同时将同一缺失项写入现有待确认章节；不得静默忽略或补造内容。

实体按两类组织：

**A. 承载页面**（父页面）
- 蓝图 §7 的主实体（弹窗/抽屉）所依赖的触发页面（如列表页、详情页）
- 蓝图通常不会完整设计承载页面，但会零散引用其结构（入口按钮位置、列表列定义、刷新行为、筛选区等）
- 从以下来源收拢承载页面的结构：
  1. 蓝图 §3 节点 1 中的触发动作描述
  2. 蓝图 §4 次流程中的页面跳转引用
  3. 蓝图 §9 UXB 承接追踪中的页面载体说明
  4. `knowledge-wiki` 中与该页面相关的载体语义类知识
- 承载页面作为实体 0，排在所有弹窗/抽屉实体之前

**B. 功能实体**（弹窗/抽屉/页面）
- `§6` 的每个子章节（6.1、6.2...）是实体候选；必须结合触发和载体行为判断为独立实体或所属实体状态。
- `§2～§5` 中发现的新界面载体即使没有独立 `§6.x` 标题或未进入 JSON，也必须登记。
- 次交互流程中的外部页面标记为独立实体，仅提取与本功能相关的内容。

完整实体清单建立后，固定分成三类：

- `生成`：满足以下任一条件的实体：承载当前任务入口或操作上下文的父级页面；用户需要输入、选择、编辑、确认、取消、重试、关闭或返回；用户需要查看会影响当前操作的阻断、失败、确认、结果或恢复信息；移除后会造成入口、操作、反馈、恢复或结果断点。
- `只引用不生成`：满足以下任一路径：
  1. 目标属于其他独立业务模块、其他应用或外部系统；当前原型不需要在目标界面继续执行本次任务；当前任务可以在跳转入口处结束，或只需描述跳转目标及返回结果。
  2. 蓝图已明确为跨任务引用，且同时提供原任务受阻、可执行入口、目标去向；当前材料未给出具体父级承载页。
- `不生成`：蓝图明确排除、属于后台计算或接口调用等非可见界面，或未达到上述最低信息标准；信息不足时必须同步进入待确认章节。

硬规则：

- 每个实体只能进入一个范围；实体状态随所属实体生成，不单独参与三类归类。
- 新载体必须作为独立生成实体；原载体内变化必须作为所属生成实体的必须生成状态。两者都必须进入正式规格，不能只保留在流程、异常、状态或文案文字中。
- 任务闭环内的父级页面、操作、确认、阻断、失败、恢复和结果界面必须归入`生成`；完整满足跨任务引用路径的外部任务容器只记录为`只引用不生成`，不创建页面实体。
- 未满足任一条`只引用不生成`路径的完整条件时，不得归入`只引用不生成`。
- 复用、已有系统能力、嵌套、次流程、异常流程、失败流程、低频、简单提示、只有一个按钮、已在流程中描述或 JSON 未登记，均不能作为排除任务闭环内实体或状态的依据。
- `只引用不生成`和`不生成`各只保留一句符合上述定义的原因；禁止把未定内容写进`生成`。
- 完成分类后逐条反查主流程、次流程和异常流程；每个用户动作都必须有生成实体、生成状态或完整跨任务引用承接，不得只保留入口、按钮或文字描述。

### 第 2 层：结构提取

对每个已识别实体，从蓝图全文的明确结构事实中提取；`§6` 是优先来源但不是唯一来源。不得改变本层输出格式、结构推理方法和以下提取项：

- 区域列表及包含关系（如"标题区 → 标题文字 + 关闭按钮"）
- 每个区域内包含的元素类型（文本、输入框、选择器、复选框、按钮、标签列表等）
- 区域内的信息内容（如来源信息区展示"{对象名称}/{对象标识}/{业务范围}/{能力范围}"）
- 异常状态下新增或变化的区域（如校验阻断时出现 inline 提示区、部分成功时出现跳过明细区）

实体没有独立 `§6.x` 标题或 ASCII，但已达到对应最低信息标准时，按蓝图明确事实形成最小可生成结构；不得忽略实体或补造蓝图未提供的业务内容。`§6` 已有 ASCII 时必须原样保留。

页面结构主体只保留区域、语义组件、字段、状态和交互规则。来源、缺口、降级原因进入 `提取备注`，不混入页面结构主体。

主体章节只写当前能支撑生成的已定页面信息。待确认项只写影响和约束，不预写实现，不得把待确认项混入页面结构、交互流程、状态表或文案池主体。

页面规格主体默认使用“标题 + 正文 / 短列表”承载。结构化不等于表格化；只有在枚举项非常密集、逐行对照明显更清楚时，才允许短表格。

页面结构建议格式：

```markdown
### 页面结构

- 页面标题区
  - Text：{页面标题}
  - Button：{主操作}
- {业务对象}统计区
  - StatCard：{业务对象总数}
  - StatCard：{分类数}
- {业务对象}列表区
  - ListGroup：按 {分类名} 分组
  - Table：{业务对象名称} / {业务范围} / 来源 / 状态 / 操作

### 提取备注

- 承载页面知识未命中，结构来自体验蓝图 §6.1。
```

不要优先改写成：

- 字段 / 类型 / 说明的大表
- 区域 / 元素 / 规则的大表
- 页面结构总览大表

结构中的示例业务数据必须变量化。不得把具体人名、具体数量、具体业务应用名当作默认页面数据。

使用：

- `{业务对象总数}`
- `{分类数}`
- `{分类名}`
- `{业务对象名称}`
- `{业务范围}`
- `{处理人姓名}`
- `{处理时间}`

ASCII 线框既是结构来源，也是正式主体内容。页面规格主体必须同时保留 ASCII 线框与对应的区域、语义组件清单。ASCII 只固定信息位置、区域关系和大布局，不写像素、颜色、圆角、阴影、字体、动效或具体 UI 库变体，也不得为了图形整齐改变真实模块关系。

### 第 3 层：交互提取

从 §3 主交互流程和 §4 次交互流程中提取：

- 用户动作（点击、输入、选择等）
- 系统反馈（弹窗变化、状态切换、数据加载等）
- 下一步指向

从 §5 异常与阻断流程中提取：

- 校验顺序与分支条件
- 阻断条件与阻断后行为（弹窗不关闭 / inline 提示）
- 非阻断条件与确认行为（展示名单 → 跳过并继续 / 取消）
- 每个异常的用户恢复路径

交互描述保留原始动作动词（点击/选择/输入），不泛化为"用户操作"。

交互承载要求：

- 主交互流程和次交互流程默认用小标题分块 + 正文 / 短列表
- 不用大表格承载完整交互流程
- 不把动作、反馈、下一步压成一张总表作为主体

### 第 4 层：文案与状态提取

文案从以下位置提取，去重合并：

- §3 各节点的"建议文案"
- §6 各实体的"具体文案"和"按钮"描述
- §7 的"关键文案模板"

每条文案记录原文案字符串，保留模板变量（`{姓名}`、`{N}`、`{M}`、`{当前状态}` 等），并注明该文案出现在哪个区域/状态下。

状态从 §7 的统一状态口径表提取：

- 状态名称
- 触发条件（从"含义"列推导）
- UI 表现（从"统一反馈口径"和"用户可操作"列推导）
- 对应文案

状态与文案承载要求：

- 状态 key、模板变量、极短文案映射允许短表格
- 异常恢复、结果态、长说明文案优先用正文或短列表

如果存在 `edge` 补强输入，则按以下规则吸收：

- `状态表现`：优先补充蓝图中未明确写出的 must / should 状态
- `异常恢复`：补充恢复路径、阻断后的用户出口、是否丢失已填信息
- `文案池`：只补充与状态反馈直接相关的 `copy_hint`
- `不参与本次生成的待确认项`：收口 `critical_missing[]` 中当前仍无法写入主体的缺口

硬规则：

- `edge` 只补主体，不重写主体
- `edge` 的 `copy_hint` 进入文案池时，必须保留来源为异常态补强
- `edge` 的 `target_section` 只作为落位提示使用，不得凌驾于 `page-spec` 自身结构判断之上
- `critical_missing[]` 只有在当前主体仍无法落位时，才进入待确认项
- 同一条 `edge` 补强信息如果已经被吸收到 `状态表现`、`异常恢复` 或 `文案池`，不得再以同义内容重复写入 `不参与本次生成的待确认项`

### 第 5 层：待确认项集中隔离

所有待确认但当前不参与页面生成的内容，统一进入 `不参与本次生成的待确认项`。

规则：

- 每条至少写“待确认项”和“影响”
- 主体章节不再出现 `[GAP]` 式散落标记
- 不得因为有待确认项，就把未定实现写入正文
- 已知复用页面、复用组件、外部处理页，以及满足跨任务引用条件的内容，写入`只引用不生成`，不进入本章节。
- 仅当当前页面的入口、字段、状态、关键操作或结构依赖未知事实，且无法通过已知复用能力或完整跨任务引用表达时，才写入本章节。

### 明确丢弃

以下内容不进入页面规格：

- §0 本次关键设计判断
- §2 旅程消费摘要（信心最低点、关键转折、流失风险等旅程分析内容）

- §9 附录（设计指南消费、业务知识消费、知识缺口、UXB 承接追踪）

- 散落在正文里的待确认说明
- 纯工程实现讨论

## Phase B · 页面事实定点补漏

该阶段只用于链路模式，必须在 `page_spec.md` 按原有规则首次写盘并完成上述自检后执行。首次写盘前禁止检查或读取 `spark-output/context/page-generation-handoff.md`；首次写入的 Markdown 不得包含 HF 记录。

执行顺序：

1. 确认 `page_spec.md` 已首次写盘，再检查并读取 `spark-output/context/page-generation-handoff.md`。
2. 文件不存在、读取失败，或项目名、需求来源明显不匹配时，不修改 Markdown，向用户报告本次未完成事实补漏。
3. 文件有效时，按 HF-ID 顺序核对全部事实，不做消费者索引筛选。
4. 只处理正文缺失事实和真实冲突；不得输出全部 HF 的覆盖分类表。
5. 补漏完成后更新同一个 `page_spec.md`，再进入 Context JSON 生成。

完整覆盖标准：

- 页面、Tab、模块：所属层级、主要内容和可见条件均有正式落点。
- 弹窗、抽屉：触发条件、结构、关键内容、按钮和操作结果均有正式落点。

- 字段、文案：所属实体、出现位置、约束或触发状态均有正式落点。

只出现名称、入口、按钮、流程节点、文案池记录或 Context JSON 实体，一律不算完整覆盖。

定点补丁规则：

- 页面、Tab、模块、字段、按钮和文案：追加到所属实体的对应小节末尾。
- 动作和结果：追加到所属实体交互或主次流程的对应小节末尾。
- 校验和异常恢复：追加到对应校验、状态或异常章节末尾。
- 权限和显示条件：追加到所属实体或状态章节末尾。
- 对应小节不存在时，在所属实体末尾、下一个同级实体或分隔线之前追加与现有模板一致的标准小节；禁止插入其他实体内部或只写入文档尾部补漏记录。
- 不得为统一表达而改写、移动或重排已有正文。

新增正式实体必须作为一个原子结果，在 Phase B 完成前同时满足：

1. 在`生成`列表末尾追加实体。
2. 在`页面实体关系`末尾追加父实体或触发入口到该实体的关系。
3. 在父实体中追加`嵌套实体：{名称}`正式章节，包含触发条件、结构、关键内容、按钮和结果；不得修改父实体已有 ASCII。

三项是否同时存在是完成标准，不以工具调用次数判断。任一项写入失败时，不得将该实体记录为已补充，不得进入 Context JSON 生成。新增实体追加到`生成`和实体关系属于允许的新增，不属于改变 Phase A 已有生成范围或已有关系。

实体已在`只引用不生成`或`不生成`中，且 handoff 已满足完整覆盖标准时，只允许：

1. 仅移除该实体原归类行。
2. 将同名实体追加到`生成`列表末尾。
3. 追加缺失的实体关系和正式规格。

不得修改其他实体归类、已有关系或已有正文。该操作属于单向升级，不允许反向降级。

- handoff 只补充已有实体事实、原子新增实体或执行上述单向升级，不得产生其他生成范围变更。
- 蓝图未提到、只提名称或只给流程，不算冲突；直接按遗漏补充。
- 只有蓝图对同一事实明确否定、替换或结构转换且有可追溯依据时，才保留蓝图，并将冲突正文追加到`不参与本次生成的待确认项`。

禁止整体重写 `page_spec.md`，禁止删除、替换、压缩、重排、重新编号或改写首次写盘的正文。除新增实体追加和同一实体单向升级外，禁止改变任何已有生成范围结果；新增关系只能追加，已有关系不得修改或删除。补漏事实必须进入正式章节，文档尾部记录只承担 HF 来源追踪，不承担页面生成语义。

实际发生补漏或真实冲突时，在文档尾部追加：

```markdown
## 需求事实补充记录

handoff 核对范围：HF-001～HF-{N}；实际补充 {N} 条；真实冲突 {N} 条。

- HF-XXX：补充{内容}，落点 §X。
- HF-XXX：真实冲突，已保留蓝图，见`不参与本次生成的待确认项`。
```

补充数和冲突数必须分别等于实际记录条数。未发生补漏且没有真实冲突时，不输出空记录。

Phase B 完成后必须复查：

1. 首次写盘正文没有被删除、降级、重排、重新编号或改写。
2. 每个新增实体同时存在于`生成`、实体关系和正式实体章节。
3. 每个升级实体只发生一次精确归类移动，且每个实体仍只属于一个范围。
4. 所有补充事实均进入对应正式章节，文档尾部记录不是唯一落点。
5. 核对范围覆盖 handoff 文件头声明的全部 HF 事实。
6. Context JSON 尚未生成；必须基于补漏后的最终 Markdown 生成。

## ⛔ Context JSON 生成门禁

写入 Context JSON 前，必须完整读取：

`references/context-schema.md`

硬规则：

1. 未完整读取该文件，禁止开始生成 Context JSON。
2. 禁止凭记忆重建 schema，禁止沿用旧 `1.0` JSON 结构。
3. 禁止从 Markdown 机械复制整段正文填充 JSON。
4. 只能写入 schema 明确允许的字段；不得新增、删除、改名或改变字段类型。
5. Markdown 必须先完成并通过本 Skill 自检，再从已确认内容映射 JSON。
6. `page_spec.md` 继续保留页面、流程、校验、状态、异常、结果态和文案的完整事实；不得为了精简 JSON 同步删减 Markdown。
7. 不得为了填满 JSON 编造信息；缺失值按 schema 的可空规则处理。
8. 写入 `generation_scope` 与 `entities` 前，必须回看 `page_spec.md` 的 `## 2. 生成范围`，确保三段分类完全一致，不得遗漏 `不生成` 实体。
9. 写入 `entity_relationships` 前，必须回看 `page_spec.md` 的 `## 3. 页面实体关系`，只写真实实体之间的关系；外部入口或未纳入实体清单的对象不得借用无关实体承接。
10. 写入 `open_questions` 前，必须回看 `page_spec.md` 的 `不参与本次生成的待确认项`，确保页面相关待确认项不遗漏、不新增；正文未输出该章节时写入空数组。
11. 写盘后必须运行指定校验脚本。
12. 校验失败时必须修复并重跑；校验未通过不得进入 Handoff，不得宣告 Skill 完成。
13. schema 文件缺失或无法读取时，停止 JSON 生成并明确报告，禁止临时自创结构。
