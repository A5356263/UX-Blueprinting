# 输入处理与隐私规则

## 来源与反馈单元

支持工单、群聊、客服或运营记录、问卷开放题、访谈摘录、应用评论、社媒反馈、内嵌反馈和客户成功记录。原始系统日志、埋点、漏斗和路径数据不属于本技能。

把材料拆成最小可理解反馈单元，同时保留上下文：

- 工单：区分用户原话、客服转述、处理记录和解决状态。
- 群聊：按 thread 合并提问、追问、答复和结果确认。
- 访谈：保留问题、回答和必要追问，不把句子拆到失去语境。
- 问卷与评论：一条回答或评论可以拆出多个明确议题，但必须共享 source ref。
- 运营 QA：把原始会话与人工整理的问答拆成两个通道；问答只能作为已知主题或知识候选参考。
- 服务日志：只提取明确客户原声字段；活动记录作为情境因素交给证据互证环节。

标准化反馈单元至少包含：`item_id`、`source_ref`、`thread_ref`、`channel`、`timestamp`、`speaker_role`、`redacted_text`、`language` 和 `privacy_flags`。

## 工单语义分层

含 `descpScene`、`descpQuestion`、`descpAppeal` 的工单按语义拆分：

- `descpScene`：提取发生位置和操作上下文。
- `descpQuestion`：提取现象；其中的报错原文标记为用户或客服引用的系统消息。
- `descpAppeal`：提取用户希望得到的结果，不代替问题描述。

高度重复时保留信息最完整的一段并记录合并；三段均空时标记 `insufficient_context`。

同一来源配置多个文本字段时，按声明顺序带字段标签拼接，不得只取第一个非空字段。结构化场景、问题、诉求和其他风险分别保留；缺失内容不得由模型补写成用户事实。

## 去重与线程合并

按稳定优先级使用：明确 duplicate ref；同一 thread；同一匿名主体、相近时间和高度相似文本；复制粘贴传播。必须区分：同一用户重复追问、多人独立反馈、同一事件传播和真正重复记录。

输出输入量、有效量、重复量、排除量、去重单位和线程完整性。无法稳定识别主体时不要声称独立用户数。

## 隐私与脱敏

检查：姓名、手机号、邮箱、证件号、地址、微信号、个人账号或用户 ID、统一社会信用代码、合同号、订单号、客户编号、商户号、银行账号、支付流水、金额明细、内部人员、群名、工单号、带敏感参数的后台链接、验证码、token、密钥、临时链接、权限细节和漏洞信息。企业编号和企业名称可在授权范围内作为关联与分群字段保留，不按个人隐私字段自动删除。

使用稳定占位符：

```text
[PERSON_1] [PHONE_1] [EMAIL_1] [COMPANY_1] [TICKET_1]
[ACCOUNT_1] [CONTRACT_1] [INTERNAL_STAFF_1] [SECRET_1]
```

同一实体在同一包内使用同一占位符。正式产物不得保存未脱敏原文。无法安全脱敏时只保存风险类型和 source ref，并设 `manual_review_required=true`。

`scene_descriptor.who` 只允许包含：`actor_role`、`user_segment`、`stable_redacted_entity_ref`。企业编号和企业名称应留在受控分群字段中，不复制到该描述；不得包含个人名、个人账号 ID 或工单号。

## 语言处理

保留脱敏后的原语言引用。需要翻译时把译文用于分析说明，不能替换原引用；方言、讽刺、缩写或机器翻译不稳定时降低情绪和主题置信度。

## 质量状态

- `ready`：关键来源、时间窗、文本和去重口径可用。
- `ready_with_caveats`：可分析但存在渠道、字段、样本或语义限制。
- `needs_user_input`：范围或关键字段有多种解释且会改变结果。
- `blocked`：材料不可读、全部无法安全处理或没有主观反馈内容。
