# 知识候选说明

当用户纠正知识、确认诊断结论可复用，或要求把某条内容沉淀为后续稳定知识时，用这份说明。

## 定位

知识候选区是正式知识库之前的缓冲层。
它的作用是：

- 先把值得沉淀的内容整理出来
- 让用户确认内容是不是稳定知识
- 给后续正式入库提供更干净的待入库知识卡片

它不是：

- 正式 knowledge
- UXB 正式需求定案产物
- 双 Skill 正式主链路的输入
- `spark-output/` 下的正式交付件
- 审批系统
- 人工流程单

知识候选区文件是“待入库知识卡片”，不是人工流程审批单。
如果没有工程化消费机制，不要把候选编号、创建时间、当前状态、是否已入库、用户确认记录、入库处理记录写入候选正文。

## 目录结构

仓库根目录下统一使用：

```text
知识候选区/
├─ 知识问答/
├─ 诊断咨询/
└─ 新需求文档/
```

规则：

1. 根目录没有 `知识候选区/` 时，可以按需创建。
2. 子目录不存在时，可以按需创建。
3. 每条候选知识单独一个 Markdown 文件。
4. 一个文件只记录一条候选知识。

## 文件命名

推荐格式：

```text
YYYY-MM-DD_HHMM_业务域_简短主题.md
```

示例：

```text
2026-05-07_2130_权限管理_权限配置前置企业认证.md
```

如果业务域不明确，可以用：

```text
YYYY-MM-DD_HHMM_待归类_候选主题.md
```

## 模板

默认使用：

```text
assets/knowledge_candidate.template.md
```

这里指的是“当前 UXB skill 的 assets 模板”，不要把某个宿主目录名当成正式依赖。

候选正文应收敛为 4 个主段落：

1. 知识讨论背景
2. 候选知识
3. 影响范围
4. 不确定点

要求：

- 不复制完整聊天原文
- 写成可复用、可判断、可入库的语义化知识
- 标清影响范围和不确定点
- 不写候选编号、状态、用户确认记录、入库处理记录

## 候选文件内容范围

候选文件只记录可沉淀的知识变化，不记录流程管理信息。

允许写入：

- 可复用业务事实
- 稳定规则
- 菜单、路径、页面、字段、状态、权限、流程变化
- 现有 knowledge 中需要修正的旧知识
- 与现有 knowledge 冲突的知识
- 当前 knowledge 缺失但影响后续判断的知识缺口
- 必要的背景说明

不得写入：

- 聊天原文
- 用户确认过程
- 入库执行日志
- 蓝图全文
- 需求文档全文
- 临时方案
- 一次性任务目标
- AI 推测但未确认的事实

## 影响范围字段怎么写

`影响范围` 里至少写清楚：

- 变更类型
- 涉及领域
- 影响对象
- 旧表述线索
- 新表述线索
- 已知命中文件
- 建议更新位置

这些内容的作用是给后续入库提供扫描种子，不是列出完整执行清单。

候选文件中的“涉及领域、影响对象、旧表述线索、新表述线索、已知命中文件”只作为入库扫描种子，不代表完整更新范围。
正式入库时，应由 `knowledge-ingestion` 基于这些线索做定向影响面扫描，决定最终更新范围。

## 涉及领域必须写清楚

生成候选知识时，必须尽量写清楚涉及领域。

涉及领域用于限制 `knowledge-ingestion` 的扫描范围，避免全库无目标扫描。

涉及领域可以是一个或多个，例如：

- 成员管理
- 组织管理
- 权限管理
- 审批管理
- 项目背景
- 设计准则/信息架构

如果领域无法判断，写“待归类”，但必须在不确定点中说明原因。

## 不确定点标记

候选区统一沿用 knowledge 子系统已有的三类标记：

- `[GAP]`：信息缺口。缺少必要信息，但不影响已知事实先沉淀。
- `[QUESTION]`：待确认问题。影响适用范围、归属或边界，不能先写成确定事实。
- `[CONFLICT]`：知识冲突。新结论与现有 knowledge 不一致，入库时不得静默覆盖。

示例：

```md
[GAP] 成员作为独立一级菜单后的完整新路径待补充。
[QUESTION] 外部人员入口是否也随成员模块独立出来，待确认。
[CONFLICT] 蓝图结论认为成员为独立一级菜单，但现有 raw 仍记录为“组织 -> 成员管理”。
```

如果没有不确定项，统一写“暂无”。

## 什么时候创建候选

不要过度沉淀。

只有满足下面任一条件时才创建候选文件：

1. 用户明确说“记录 / 记一个 / 更新知识库 / 写入知识库”。
2. 用户纠正了知识，AI 询问是否记录，用户同意。
3. 诊断咨询出现稳定结论，AI 建议沉淀，用户同意。
4. 新需求蓝图完成后，AI 提取候选，用户同意。
5. 用户明确要求把某条内容沉淀为后续可复用知识。

不要因为 AI 自己觉得有价值，就擅自创建大量候选文件。

## 不同场景下怎么触发

### 知识问答

默认不创建候选。

如果用户纠错，先修正当前回答，再自然询问是否记录到知识候选区。

推荐话术：

```text
我先按这个纠正修正当前答案。这条看起来像稳定规则，要不要我先记到知识候选区，等你确认后再入库？
```

### 诊断咨询

诊断过程中不要频繁创建候选。

当阶段性结论已经比较稳时，可以轻提示：

```text
这条判断后续可能会复用。需要的话，我可以先记到知识候选区，不直接入库。
```

### 新需求文档

蓝图完成后，不是直接提取蓝图全文，而是先做知识变更检查。

重点看：

- 有没有新增长期知识
- 有没有现有知识需要修正
- 有没有与现有 raw 冲突的地方
- 有没有知识缺口需要补记

确认有价值后，再提议提取到 `知识候选区/新需求文档/`。
不要把整份蓝图直接入库。

### 直接知识维护

如果用户直接说“更新知识库”，先整理候选，再让用户确认，不要直接写 `knowledge/`。

## 正式入库规则

知识候选区只是缓冲区。正式入库必须同时满足：

1. 用户确认该候选可以作为稳定知识。
2. 候选内容已经语义化整理，不是聊天原文。
3. 已经给出建议写入位置。
4. 不确定点已处理，或明确保留待确认标记。
5. 入库后运行 knowledge 子系统更新逻辑。

## 建议入库位置

如果业务域明确：

```text
knowledge/raw/业务/<domain>/
```

如果更像体验指南：

```text
knowledge/raw/设计准则/
```

如果暂时无法归类：

```text
knowledge/raw/inbox/
```

## 入库后动作

通常执行：

```bash
python knowledge/scripts/update_wiki.py --apply
```

如果只更新单个 raw：

```bash
python knowledge/scripts/update_wiki.py --apply --only <raw-file-path>
```

## 不允许行为

不要这样做：

- 未经确认直接写 `knowledge`
- 把聊天原文整段写进候选文件
- 把候选当正式知识直接引用
- 因为“看起来有价值”就批量造候选
- 把候选区接进双 Skill 正式主链路
- 把候选文件写成状态流转单或审批单
