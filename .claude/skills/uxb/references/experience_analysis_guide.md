## 1. 目的与边界

本文件用于决定 UXB 应分析哪些体验问题、展开到什么范围。

前提：

- 正式需求基线已经冻结。
- 业务对象、角色、权限、规则、状态和异常已经闭环。

本文件不能用于：

- 重新审查 PRD。
- 补写业务事实。
- 判断产品方向是否成立。
- 输出具体页面方案。

## 2. 体验压力维度

### 2.1 多角色压力

检查：

- 各角色在同一任务中的目标是否不同。
- 上一角色的结果能否被下一角色理解和继续处理。
- 同一状态对不同角色是否需要不同解释。
- 角色切换是否造成信息、责任或行动断点。

重点不是角色数量，而是角色之间是否存在体验视角冲突。

### 2.2 信息理解压力

检查：

- 用户必须理解哪些对象、关系、条件和影响。
- 信息是否超过一次判断能够承受的范围。
- 哪些信息是决策依据，哪些是结果，哪些只是辅助。
- 业务结构和用户理解顺序是否一致。

信息多不等于必须分层。只有理解顺序或决策负担发生变化时，才形成体验压力。

### 2.3 异常与分支压力

检查：

- 哪些分支会改变用户下一步。
- 部分成功、失败、阻断或不可恢复结果是否难以理解。
- 用户是否知道失败后能否继续、重试或返回。
- 主流程与异常结果是否仍属于同一任务。

异常数量不是判断标准。一个不可逆异常也可能需要完整体验定案。

### 2.4 跨节点与跨端压力

检查：

- 任务是否跨页面、模块、系统、角色或终端继续。
- 用户能否识别前后节点属于同一任务。
- 中断后是否知道从哪里恢复。
- 不同渠道是否保持相同状态语义和结果认知。

### 2.5 概念边界压力

检查：

- 新概念是否与用户已有认知冲突。
- 相近概念是否容易混淆。
- 系统对象关系是否难以转成用户语言。
- 用户是否可能把状态、权限或结果理解成另一种含义。

### 2.6 风险与不可逆压力

检查：

- 用户是否能在操作前理解影响。
- 操作中是否需要知道处理状态。
- 操作后是否能确认结果和后续限制。
- 效率目标是否会压缩必要的判断时间。

## 3. 分析范围判断

不输出低、中、高复杂度，也不让用户选择分析模式。

### 3.1 聚焦关键节点

适用特征：

- 体验压力集中在一个或少量节点。
- 不改变前后任务顺序。
- 不影响其他角色继续任务。
- 异常结果不会扩散到后续节点。

仍需检查：

```text
触发
→ 理解
→ 操作
→ 反馈
→ 恢复或完成
```

### 3.2 展开完整任务链

命中任一情况时，分析完整任务链：

- 当前节点会改变后续状态或角色任务。
- 需要调整任务顺序或触发时机。
- 异常会中断、回退或重新进入任务。
- 任务跨系统、跨端或跨角色继续。
- 一个体验取舍会影响多个节点。

完整任务链只分析体验组织和连续性，不重新建立业务流程。

### 3.3 展开多角色连续性

命中任一情况时，分别检查关键角色：

- 不同角色依赖彼此结果。
- 同一业务状态产生不同操作责任。
- 一方完成后，另一方需要理解、确认或继续。
- 角色看到的信息范围不同，但必须保持同一结果认知。

## 4. 关键角色任务可达性

对每个关键角色检查：

```text
任务如何触发
→ 是否知道发生了什么
→ 是否理解当前条件和影响
→ 是否能完成应执行动作
→ 是否收到明确结果
→ 失败时是否知道如何恢复
→ 完成后是否能继续原任务或进入下一任务
```

发现断点时，先区分：

- 业务事实缺失：停止 UXB，回到 PRD Review。
- 体验组织不清：进入 UXB 定案。
- 具体页面实现未定：交给 Experience Blueprint。

## 5. 体验断点

按实际任务识别：

- 发现断点：不知道入口、任务已发生或需要处理。
- 理解断点：看到了信息，但不能建立正确认知。
- 决策断点：缺少判断依据，无法选择。
- 操作断点：知道要做什么，但任务顺序或触发不自然。
- 反馈断点：操作后不知道是否成功、处于何种结果。
- 恢复断点：失败后不知道能否重试、返回或继续。
- 连续性断点：跨角色、节点、系统或端后无法接续。

断点必须能指向需求基线中的任务、状态、异常或结果。不能凭空制造体验问题。

## 6. 5 Why 使用边界

只有同时满足以下条件时使用：

- 已发现明确体验症状。
- 症状原因仍不清楚。
- 不继续追问会导致体验策略停留在表面修补。

使用方式：

1. 从具体体验症状开始。
2. 每次追问上一层原因。
3. 区分业务事实、用户理解和设计组织问题。
4. 找到能改变体验策略的原因后停止。

停止条件：

- 追到未确认业务事实：停止 UXB，回到 PRD Review。
- 追到需求方向是否成立：停止 UXB，转 Problem Framing。
- 已找到可由信息、流程、解释或反馈策略解决的原因。
- 继续追问不会改变体验定案。

不要求机械追问五次。

## 7. 压力与定案维度映射

| 体验压力 | 优先分析 |
|---|---|
| 多角色压力 | 角色连续性、状态理解、交接关系 |
| 信息理解压力 | 信息架构、阅读顺序、概念区分 |
| 异常与分支压力 | 流程编排、反馈策略、恢复连续性 |
| 跨节点与跨端压力 | 任务连续性、状态一致性、回流 |
| 概念边界压力 | 解释内容、解释时机、信息命名方向 |
| 风险与不可逆压力 | 决策依据、操作前中后解释、结果确认 |

映射只决定分析重点。不能根据表格直接生成结论。

## 8. 校准案例

### 8.1 小改动但需要完整体验判断

需求只增加一个“作废”状态，但它会改变报销、结算和重新推送认知。

分析重点：

- 已作废与删除、失败的概念区分。
- 操作前的不可逆影响。
- 操作后的结果和下一步。
- 不同角色对已作废的共同理解。

不能因为只增加一个状态而缩减分析。

### 8.2 规则多但只需聚焦节点

需求包含多条已冻结规则，但体验方向已经明确，只有某个结果节点的解释顺序需要定案。

分析重点：

- 聚焦结果节点。
- 检查前后任务是否受影响。
- 不重复分析完整业务规则。

不能因为规则多而机械展开全部体验维度。

### 8.3 批量操作

批量能力复用现有业务规则，但存在部分成功和失败。

分析重点：

- 提交前的影响理解。
- 处理中对进度和范围的认知。
- 结果如何区分成功、失败和可恢复项。
- 用户如何继续未完成任务。

### 8.4 角色化入口

角色首页只改变入口展示时，重点是发现性和理解。

如果还影响应用可见范围、角色切换和跨端分发，必须展开多角色与跨端连续性。

业务边界是否改变由需求基线决定，UXB 不重新判断。

## 9. 自检与禁止事项

自检：

- 每个关键角色的任务可达性已检查。
- 已选择关键节点或完整任务链，并有体验影响依据。
- 每个体验断点都能指向需求基线。
- 分析重点覆盖实际体验压力。
- 5 Why 没有越过业务或产品方向边界。
- 结论能落入 UXB 正式章节。

禁止：

- 用页面数量、规则数量或角色数量机械决定深度。
- 为显得完整而展开无关体验维度。
- 把领域复杂度当体验复杂度。
- 把业务异常重新设计成新的业务规则。
- 把具体页面、组件或文案写成体验定案。
