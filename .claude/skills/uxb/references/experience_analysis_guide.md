## 1. 目的与边界

本文件用于决定 UXB 应分析哪些体验问题、展开到什么范围。

前提：

- 正式需求基线已经冻结。
- 业务对象、角色、权限、规则、状态和异常已经闭环。

本文件不能用于：

- 重新审查 PRD。
- 补写业务事实。
- 判断产品方向是否成立。
- 输出具体页面方案。

## 2. 完整任务扫描与分析视角

### 2.0 完整任务扫描

先从需求基线提取全部核心任务。每项任务必须记录：

- 用户目标。
- 参与角色。
- 业务对象。
- 需求发生事件。
- 业务触发条件。
- 本期支持的进入渠道。
- 业务节点。
- 状态变化。
- 成功结果。
- 拒绝、中断和异常结果。
- 角色交接。
- 系统交接。

全部核心任务完成扫描前，不得只聚焦员工主流程，也不得宣布某个体验维度不适用。

以下分析视角是内部推理框架，不是并列输出模块。只有形成真实体验定案的内容才进入正式产物。

### 2.1 多角色压力

检查：

- 各角色在同一任务中的目标是否不同。
- 上一角色的结果能否被下一角色理解和继续处理。
- 同一状态对不同角色是否需要不同解释。
- 角色切换是否造成信息、责任或行动断点。

重点不是角色数量，而是角色之间是否存在体验视角冲突。

### 2.2 信息理解压力

检查：

- 用户必须理解哪些对象、关系、条件和影响。
- 信息是否超过一次判断能够承受的范围。
- 哪些信息是决策依据，哪些是结果，哪些只是辅助。
- 业务结构和用户理解顺序是否一致。

信息多不等于必须分层。只有理解顺序或决策负担发生变化时，才形成体验压力。

### 2.3 异常与分支压力

检查：

- 哪些分支会改变用户下一步。
- 部分成功、失败、阻断或不可恢复结果是否难以理解。
- 用户是否知道失败后能否继续、重试或返回。
- 主流程与异常结果是否仍属于同一任务。

异常数量不是判断标准。一个不可逆异常也可能需要完整体验定案。

### 2.4 跨节点与跨端压力

检查：

- 任务是否跨页面、模块、系统、角色或终端继续。
- 用户能否识别前后节点属于同一任务。
- 中断后是否知道从哪里恢复。
- 不同渠道是否保持相同状态语义和结果认知。

### 2.5 概念边界压力

检查：

- 新概念是否与用户已有认知冲突。
- 相近概念是否容易混淆。
- 系统对象关系是否难以转成用户语言。
- 用户是否可能把状态、权限或结果理解成另一种含义。

允许将技术术语转成用户语言，但不得抹掉会改变可申请内容、权限范围、操作条件或业务结果的必要分类。

### 2.6 风险与不可逆压力

检查：

- 用户是否能在操作前理解影响。
- 操作中是否需要知道处理状态。
- 操作后是否能确认结果和后续限制。
- 效率目标是否会压缩必要的判断时间。

### 2.7 入口与任务可达性压力

检查：

- 用户是否知道任务已经发生。
- 用户是否知道从哪里开始。
- 入口出现的时机是否符合任务发生时机。
- 入口传达的任务对象、状态和行动是否足以支持下一步。

必须分别判断三种发现方式：

1. 阻断点恢复：用户已经在原任务中遇到权限、状态、配置或条件阻碍时，能否从当前上下文继续解决。
2. 稳定主动入口：用户未遇到阻断时，能否主动、重复地找到并发起任务。
3. 首次认知曝光：用户首次接触新能力时，是否需要知道能力存在及其用途。

三种方式解决的问题不同，不能互相替代。

- 当前阻断已经发生且用户可自行解除时，优先形成阻断点恢复定案。
- 任务需要主动重复发起时，必须检查稳定主动入口。
- 只有用户无法在任务现场自然理解新能力，且必须先建立整体认知时，才考虑首次认知曝光。
- 首次认知曝光不能代替稳定入口。
- UXB 只确定发现机制和信息目的，不确定按钮、入口位置、页面或组件。

### 2.8 流程与节点衔接压力

检查：

- 前一节点的结果是否能自然承接下一节点。
- 用户是否知道当前内容为何发生变化。
- 进入下一节点时，原任务对象和关键上下文是否仍可识别。
- 节点结束后，下一步行动或终止结果是否明确。

节点衔接定案至少覆盖：

1. 前一节点产生了什么结果。
2. 下一节点承接什么内容。
3. 用户如何知道结果已经发生。
4. 哪些上下文必须保留。
5. 用户接下来能做什么。

### 2.9 状态可见性与恢复压力

检查：

- 用户是否能区分处理中、成功、失败、部分成功和终止状态。
- 状态变化是否会改变可执行动作。
- 异常发生后，用户是否知道原因、影响和可恢复方式。
- 恢复后是否能回到原任务，而不是重新理解全部上下文。

### 2.10 术语、文案方向与决策负担压力

检查：

- 关键术语是否会造成错误业务认知。
- 信息是否缺少解释层次，导致用户自行拼接业务含义。
- 用户是否需要在一个节点同时完成过多判断。
- 必要的风险、条件或结果是否出现在错误时机。

UXB 只确定文案需要表达什么、何时表达。最终文案和具体载体由 Experience Blueprint 决定。

### 2.11 稳定信息与任务过程压力

先分类：

- 稳定信息：用户需要长期查看的当前事实。
- 任务入口：用户开始办理的触发点。
- 候选集合：用户在一次任务中用于选择的对象。
- 已选结果：候选选择完成后回到主任务的结果。
- 历史记录：已完成事项的追溯信息。

只有稳定信息或需要长期浏览、管理、追踪的集合，才可能成为常驻视图。

候选集合默认属于任务过程。选择完成后必须回填已选结果，并保留主任务上下文、结果查看和重新选择能力。

出现以下任一情况时，不得把候选集合定为常驻信息视图：

- 只在一次办理过程中使用。
- 选择后必须回到原任务继续。
- 候选集合本身不产生独立业务状态。
- 用户真正需要长期查看的是已选结果。

UXB 只定案信息性质和任务关系，不指定 Tab、页面、弹窗或抽屉。

## 3. 用户感知阶段与输出范围

不输出低、中、高复杂度，也不让用户选择分析模式。

### 3.1 建立用户感知阶段

对每个业务节点判断：

- 用户当前要完成什么目标。
- 用户需要理解什么。
- 用户需要作出什么决定。
- 用户是否需要等待。
- 用户是否需要确认结果。
- 用户是否需要恢复任务。
- 是否发生角色或系统交接。

用户感知阶段不是业务状态的改名。一个感知阶段可以承接多个业务节点，一个业务节点也可以因独立目标被拆成多个感知阶段。

每个正式感知阶段必须记录：

- 对应业务任务。
- 承接的业务节点。
- 执行角色。
- 用户目标。
- 阶段开始和结束条件。

### 3.2 全量扫描与按需输出

内部必须扫描全部核心任务。

正式产物只输出存在真实体验断点并形成体验决定的任务和阶段。

体验压力只集中在少量阶段时：

- 其他任务仍需完成内部扫描。
- 正式产物聚焦有体验决定的阶段。
- 禁止重复输出没有体验增量的任务事实。

体验决定影响后续状态、角色、系统或任务时，必须展开受影响的完整任务链，不能只输出局部节点。

### 3.3 多角色连续性

出现以下任一情况时，必须分别检查相关角色：

- 不同角色依赖彼此结果。
- 同一业务状态产生不同操作责任。
- 一方完成后，另一方需要理解、确认或继续。
- 角色看到的信息范围不同，但必须保持同一结果认知。

## 4. 关键角色任务可达性

对每个关键角色检查：

```text
需求为何发生
→ 任务如何被发现
→ 是否知道发生了什么
→ 是否理解当前条件和影响
→ 是否能完成应执行动作
→ 是否收到明确结果
→ 失败时是否知道如何恢复
→ 完成后是否能继续原任务或进入下一任务
```

发现断点时，先区分：

- 业务事实缺失：停止 UXB，说明缺失事实和影响，建议用户重新执行 PRD Review；不得自动调用。
- 体验组织不清：进入 UXB 定案。
- 具体页面实现未定：交给 Experience Blueprint。

## 5. 体验断点与编排规则

### 5.1 体验断点

按实际任务识别：

- 发现断点：不知道入口、任务已发生或需要处理。
- 理解断点：看到了信息，但不能建立正确认知。
- 决策断点：缺少判断依据，无法选择。
- 操作断点：知道要做什么，但任务顺序或触发不自然。
- 反馈断点：操作后不知道是否成功、处于何种结果。
- 恢复断点：失败后不知道能否重试、返回或继续。
- 连续性断点：跨角色、节点、系统或端后无法接续。

断点必须能指向需求基线中的任务、状态、异常或结果。不能凭空制造体验问题。

发现断点必须进一步归类为阻断点恢复、稳定主动入口或首次认知曝光。不能只写“入口需要更清晰”。

### 5.2 合并业务节点

多个业务节点同时满足以下条件时，应合并为一个用户感知阶段：

- 执行角色相同。
- 用户目标相同。
- 操作上下文连续。
- 中间没有独立等待。
- 中间没有不可逆提交。
- 中间没有高风险确认。
- 后一节点只解释、补充或延续前一节点结果。

合并只改变用户如何感知任务，不删除需求基线中的业务状态和结果。

### 5.3 拆分用户阶段

出现以下任一条件时，必须拆分：

- 执行角色变化。
- 进入独立异步等待。
- 产生独立业务状态。
- 即将执行不可撤销或高风险操作。
- 用户需要作出新的独立决定。
- 失败后存在独立恢复路径。
- 用户必须明确感知任务已经进入下一阶段。

拆分后必须定案：

- 上一阶段如何结束。
- 下一阶段如何开始。
- 需要传递哪些信息。
- 用户如何识别当前阶段。

### 5.4 保留或重排

不满足合并或拆分条件时，保留原阶段。

只有当前顺序造成信息出现过晚、决策依据缺失或上下文断裂时，才允许重排。

重排不得改变需求基线中的业务前置条件、状态流转和责任关系。

### 5.5 编排决定有效性

“更简洁”“更自然”“减少步骤”不能单独构成编排理由。

有效理由必须指向：

- 用户目标连续性。
- 独立业务结果。
- 决策风险。
- 等待和恢复。
- 角色或系统交接。
- 信息理解顺序。

每项编排决定必须转成 Blueprint 可执行要求，但不得指定页面、弹窗、抽屉或组件。

### 5.6 状态语义与结果合并

简化用户感知状态前必须：

1. 列出需求基线中的全部业务结果。
2. 判断用户是否需要区分这些结果。
3. 为需要区分的结果保留独立含义。
4. 验证每种结果的下一步和可执行动作。

只有不同业务结果对用户的含义、下一步和可执行动作都相同时，才允许合并为同一用户感知状态。

禁止：

- 将系统终止归入用户撤回。
- 将管理员关闭归入审批人拒绝。
- 将失效归入完成。
- 将技术中断归入业务失败，除非需求基线明确如此定义。

业务状态名称相同但触发原因和用户下一步不同，也必须保留可区分的结果语义。

### 5.7 任务过程与稳定视图判断

先问：

1. 用户是在查看长期事实，还是完成一次任务。
2. 当前内容是候选集合，还是已选结果。
3. 操作完成后是否回到原任务继续。
4. 当前节点是否形成独立业务状态。
5. 用户未来需要长期查看、管理或追踪什么。

满足以下全部条件时，内容才可定为稳定视图：

- 内容需要长期存在。
- 用户会重复浏览、管理或追踪。
- 内容脱离本次办理仍有独立价值。

不满足时，按任务过程处理。候选选择完成后回填结果，不把候选集合升级为常驻视图。

本节只能输出信息关系和任务连续性要求。不得输出 Tab、Wizard、Steps、页面、弹窗或抽屉。

## 6. 5 Why 使用边界

只有同时满足以下条件时使用：

- 已发现明确体验症状。
- 症状原因仍不清楚。
- 不继续追问会导致体验策略停留在表面修补。

使用方式：

1. 从具体体验症状开始。
2. 每次追问上一层原因。
3. 区分业务事实、用户理解和设计组织问题。
4. 找到能改变体验策略的原因后停止。

停止条件：

- 追到未确认业务事实：停止 UXB，回到 PRD Review。
- 追到需求方向是否成立：停止 UXB，转 Problem Framing。
- 已找到可由信息、流程、解释或反馈策略解决的原因。
- 继续追问不会改变体验定案。

不要求机械追问五次。

## 7. 压力与定案维度映射

| 体验压力 | 优先分析 |
|---|---|
| 多角色压力 | 角色连续性、状态理解、交接关系 |
| 信息理解压力 | 信息架构、阅读顺序、概念区分 |
| 异常与分支压力 | 流程编排、反馈策略、恢复连续性 |
| 跨节点与跨端压力 | 任务连续性、状态一致性、回流 |
| 概念边界压力 | 解释内容、解释时机、信息命名方向 |
| 风险与不可逆压力 | 决策依据、操作前中后解释、结果确认 |
| 入口与任务可达性压力 | 入口认知、任务对象、行动提示 |
| 流程与节点衔接压力 | 流程顺序、节点转换、上下文保留 |
| 状态可见性与恢复压力 | 状态反馈、行动变化、异常恢复 |
| 术语与决策负担压力 | 解释层次、文案方向、信息优先级 |

映射只决定分析重点。不能根据表格直接生成结论。

## 8. 校准案例

### 8.1 小改动但需要完整体验判断

需求只增加一个“作废”状态，但它会改变报销、结算和重新推送认知。

分析重点：

- 已作废与删除、失败的概念区分。
- 操作前的不可逆影响。
- 操作后的结果和下一步。
- 不同角色对已作废的共同理解。

不能因为只增加一个状态而缩减分析。

### 8.2 规则多但只需聚焦节点

需求包含多条已冻结规则，但体验方向已经明确，只有某个结果节点的解释顺序需要定案。

分析重点：

- 聚焦结果节点。
- 检查前后任务是否受影响。
- 不重复分析完整业务规则。

不能因为规则多而机械展开全部体验维度。

### 8.3 批量操作

批量能力复用现有业务规则，但存在部分成功和失败。

分析重点：

- 提交前的影响理解。
- 处理中对进度和范围的认知。
- 结果如何区分成功、失败和可恢复项。
- 用户如何继续未完成任务。

### 8.4 角色化入口

角色首页只改变入口展示时，重点是发现性和理解。

如果还影响应用可见范围、角色切换和跨端分发，必须展开多角色与跨端连续性。

业务边界是否改变由需求基线决定，UXB 不重新判断。

## 9. 自检与禁止事项

自检：

- 全部核心角色和任务已完成内部扫描。
- 每个正式定案都已建立用户感知阶段。
- 节点合并、拆分、保留或重排符合明确条件。
- 状态简化能覆盖全部业务结果，没有语义碰撞。
- 用户语言转译没有抹掉必要业务分类。
- 三种任务发现方式已按实际场景分别判断。
- 稳定信息、任务入口、候选集合、已选结果和历史记录已正确分类。
- 候选集合没有被误定为常驻视图。
- 每个体验断点都能指向需求基线。
- 分析重点覆盖实际体验压力。
- 5 Why 没有越过业务或产品方向边界。
- 结论能落入 UXB 正式章节。

禁止：

- 用页面数量、规则数量或角色数量机械决定深度。
- 为显得完整而展开无关体验维度。
- 把领域复杂度当体验复杂度。
- 把业务异常重新设计成新的业务规则。
- 把具体页面、组件或文案写成体验定案。
- 把 Tab、Wizard、Steps、弹窗或抽屉写成体验定案。

## 10. 正式定案有效性

每项正式定案必须形成完整链路：

```text
需求基线中的任务事实
→ 业务任务链
→ 用户感知阶段
→ 体验断点
→ UXB 作出的编排与体验决定
→ Experience Blueprint 必须落实的要求
```

每项决策至少改变以下一项：

- 用户感知阶段。
- 信息顺序。
- 流程顺序。
- 节点衔接。
- 解释时机。
- 状态可见性。
- 反馈与恢复。
- 多角色或跨端连续性。

如果一项判断不会改变 Experience Blueprint 的设计约束，则不进入正式产物。

没有真实体验压力时：

- 不制造体验问题。
- 不为了章节完整而生成空泛策略。
- 明确说明本需求无需独立体验取舍。
- 只要求 Experience Blueprint 忠实落实需求基线。
