# UXB 用户确认表达

## 1. 目的

UXB 只保留一次设计师主确认。用户侧先看到体验定案草案，确认后才生成正式产物。

草案默认只在聊天中展示。不得默认写入 `spark-output/uxb_draft.md`，不得生成草案 Context，也不得把草案交给下游。

只有用户明确要求保存草案时才可落盘。保存的草案仍不是正式体验定案，不能用于 Handoff。

## 2. 草案结构

```markdown
# 体验定案草案

## 按任务链的体验定案

- {角色与任务}
  - 用户感知阶段：{阶段及对应业务节点}
  - 任务发现：{阻断点恢复、稳定主动入口或首次认知曝光；不适用时省略}
  - 体验断点：{具体问题}
  - 体验决定：{合并、拆分、保留、重排、信息或状态决定}
  - 蓝图要求：{必须落实的体验结果}

## 跨阶段、状态与连续性

- {节点衔接、解释时机、状态反馈或角色连续性中的关键定案}

## 体验蓝图承接要求

- {蓝图必须落实的具体体验约束}
```

只展示本次有决策价值的内容。不复制需求基线，不写成需求摘要。

每项草案结论必须说明：

- 用户在哪个任务和感知阶段遇到什么体验断点。
- 该感知阶段对应哪些业务节点。
- 用户需要理解什么。
- 已确定什么编排或体验决定。
- 蓝图必须落实什么。

草案只展示已选择方向，不展示未选择方向和内部比较过程。

没有真实体验压力时，草案只说明无需独立体验取舍及其业务理由，不制造体验建议。

## 3. 确认语

草案后固定输出：

```text
请确认这版体验方向：

1. 确认并生成正式体验定案
2. 调整部分体验判断
```

不得增加“补业务前提”“探索业务方案”等旧路径。

## 4. 用户确认

以下表达可视为明确确认：

- 确认。
- 接受。
- 按这版生成。
- 选择 1。

只要用户同时提出修改，就先吸收修改，不视为确认。

## 5. 用户调整

用户提出调整时：

1. 说明受影响的体验结论。
2. 只更新相关部分。
3. 保持其他已接受结论不变。
4. 重新展示完整草案。
5. 再次等待明确确认。

不重做 PRD Review，不新增业务事实，不把体验调整写回需求基线。

## 6. 业务问题回流

如果用户指出需求基线存在业务错误、规则冲突或未闭环：

- 说明该问题属于需求基线。
- 停止正式 UXB 生成。
- 建议重新执行 PRD Review。
- 不在 UXB 内代替产品关闭问题。

## 7. 表达规则

- 先结论，后理由。
- 使用短句。
- 标题不跳级。
- 并列内容使用无序列表。
- 不输出内部状态名、评分或完整推理过程。
- 不输出页面、组件、布局和最终文案。
- 不输出 Tab、Wizard、Steps、弹窗或抽屉。
