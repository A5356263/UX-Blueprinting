# UXB 统一文档写作指南

这份指南只负责一件事：

**把 `uxb_output.md` 的目标结构和写法固定下来。**

## 写作红线

1. 先分析后收敛，不直接把需求文档改写成结论。
2. UXB 只做业务判断、边界、规则、状态、异常和承接要求，不输出页面结构与具体交互方案。
3. 正文不记录推理过程，不暴露内部执行术语。
4. `§0` 必须短、准、可独立阅读，不超过 300 字。
5. `§7` 只写体验蓝图必须承接的问题，不写页面、组件、文案方案。
6. `§9` 必须分层，不平铺。
7. 附录负责事实、知识与判断追踪，正文优先使用业务语言。

## 失败条件

1. 缺少任何一章或附录。
2. `§1` 把原始输入直接改写成体验方案。
3. `§2` 缺少“判断错误会带来的影响”。
4. `§3` 只写收益，不写系统代价或替代路径。
5. `§4` 混入页面方案、组件方案。
6. `§5` 角色、功能、规则只有标题，没有输入输出或处理闭环。
7. `§6` 状态、异常没有用户下一步，或只写“提示清晰”“友好报错”。
8. `§7` 写成具体体验方案。
9. `§9` 没有分层，或没有影响与建议确认方。

## 合格标准

1. 读完后能清晰知道这项需求在业务上到底是什么、值不值得做、建议边界是什么。
2. 事实、判断、缺口边界清晰。
3. 角色、功能、规则、状态、异常能形成闭环。
4. 体验蓝图拿到 `§7` 后，能明确知道自己必须承接什么，不能重判什么。
5. 附录可追溯“原始输入事实 / 知识支撑 / AI 判断 / 未确认 GAP”。

## 章节结构

`uxb_output.md` 固定为：

- `§0` 本次关键判断
- `§1` 需求输入摘要
- `§2` 业务场景判断
- `§3` 需求成立性判断
- `§4` 推荐业务边界
- `§5` 角色、功能、规则范围
- `§6` 状态、异常与边界
- `§7` 体验蓝图承接要求
- `§8` 约束与不做什么
- `§9` 待确认问题
- `附录` 事实、知识与判断追踪

## 各章节写法

### `§0` 本次关键判断

- 用一句话给总判断。
- 再写关键业务判断、推荐方向、不建议方向、最高优先级待确认问题。
- 不写页面结构、交互流程、控件选择。

### `§1` 需求输入摘要

- 写清需求背景、目标用户、业务目标、产品目标、功能范围、明确约束、PRD 缺口。
- 区分“原始输入明确说明”和“基于知识或分析得出的推断”。
- 只做事实整理，不给体验方案。

### `§2` 业务场景判断

- 回答这项需求在现有业务体系中的位置：新增、扩展、替代、互斥，或暂时未知。
- 写清与现有能力的关系、是否改变治理模式、最大业务不确定性。
- 必须补一句：如果这个判断错了，后续哪些方案要重做。

### `§3` 需求成立性判断

- 判断用户问题是否真实、业务价值是否成立、系统代价是否可接受。
- 必须同时写收益、代价、更低成本替代方案。
- 最后明确是否建议进入正式体验设计。

### `§4` 推荐业务边界

- 写推荐能力形态、不推荐能力形态、与现有能力的边界、要复用什么、不该新增什么。
- 这里写的是业务能力边界，不是页面方案。
- 禁止出现“抽屉 / Tab / 步骤条 / 弹窗”等组件词。

### `§5` 角色、功能、规则范围

- 列角色清单，并写清每个角色的职责。
- 列功能单元，并写清输入、输出、结果。
- 列关键业务规则，并写清触发条件、处理结果、不满足时的处理。
- 不允许只列标题。

### `§6` 状态、异常与边界

- 写核心状态列表、关键状态流转、异常清单。
- 每个异常至少写：触发条件、系统处理结果、用户下一步。
- 缺失状态或异常闭环时，明确标为 GAP。

### `§7` 体验蓝图承接要求

- 固定表达方式：`业务判断 → 对体验设计的影响 → 下游必须承接的问题 → 禁止下游重判`
- 优先用表格写。
- 只写承接问题，不写页面设计方案、组件方案、文案方案。

### `§8` 约束与不做什么

- 写硬约束、依赖项、不做什么、不可突破的安全或业务边界。
- 不要和 `§4` 重复。

### `§9` 待确认问题

- 分层为：
  - 层级一：影响主方案是否成立的问题
  - 层级二：影响局部体验设计的问题
- 每个问题必须写影响和建议确认方。
- 层级一控制在最关键的少量问题，不要平铺。

### `附录` 事实、知识与判断追踪

- 记录原始输入事实。
- 记录知识库支撑了哪些判断。
- 记录 AI 当前做了哪些设计判断。
- 记录仍未确认的 GAP。
- 原始知识术语尽量只留在附录。
