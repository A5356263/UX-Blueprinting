## 1. 目的与边界

知识用于解释既有业务语境和校准体验方向，不用于补充、纠正或覆盖本轮正式输入。

- 正式输入是本轮业务事实来源。
- 业务知识解释正式输入没有展开的既有机制、状态、系统边界和领域术语。
- 设计准则与交互模式帮助选择任务发现、节点关系、信息主次、解释时机、状态反馈、恢复、交接、风险和效率方向。
- 本文件不识别体验压力，不形成最终体验决定，也不定义正式输出结构。

## 2. 消费顺序

只按以下顺序使用知识：

```text
任务生命周期扫描
→ 具体体验压力
→ 判断是否缺少业务语境
→ 按需读取业务知识
→ 检查对应设计准则或交互模式
→ 按需比较体验方向
→ 形成体验决定
→ 记录实际产生作用的知识
```

读取前在内部明确：

- 当前体验压力是什么。
- 当前判断缺少业务语境，还是需要设计依据。
- 知识会影响哪个节点、时机、状态、结果、恢复或交接关系。

没有具体体验压力时，不启动设计知识读取。正式输入已经完整解释当前业务语境时，不读取业务知识。

不能先形成最终体验决定，再读取知识装饰引用。

## 3. 正式知识源

只从 `.claude/skills/knowledge-wiki/knowledge/` 读取正式知识。

读取规则：

- 先使用正式索引和领域路由定位主题。
- 读取能够回答当前问题的必要完整规则块。
- 不根据单个检索命中句直接形成结论。
- 一个体验压力可以命中多个知识主题，但不因此读取整个目录或整个业务域。
- 索引、README、标题和组件示例不能直接作为体验决定。
- 不复制 Knowledge Wiki 内容到 UXB reference。
- 来源名称和路径必须真实。

## 4. 业务知识读取

### 4.1 触发条件

正式输入不能解释以下内容，且该内容会改变体验方向时，读取业务知识：

- 既有机制如何运作。
- 状态在现有系统中的业务含义。
- 角色、权限和处理责任的既有关系。
- 系统交接边界和返回结果。
- 领域术语和业务对象关系。
- 当前需求是在新增、修改、移除还是复用既有能力。
- 规则之间的继承、覆盖、互斥、优先级或来源关系。

业务知识不用于证明体验决定“足够重要”，也不用于扩大体验问题数量。

### 4.2 主题完整、领域不全量

按以下方式控制读取范围：

1. 从当前体验压力识别对象、状态、机制、系统或规则关系。
2. 通过正式索引定位一个或多个知识主题。
3. 读取足以还原该主题完整语义的相关规则块。
4. 主题涉及多个相互依赖文件时，读取这些必要文件。
5. 不读取与当前判断无关的角色、对象、流程和历史规则。
6. 当前语境足以支持体验方向时停止。

“主题完整”表示不能只读一句结论；“领域不全量”表示不能遍历整个业务域。

### 4.3 读取目标

业务知识只回答当前语境问题，例如：

- 这个对象在既有系统中如何识别。
- 这个状态对不同角色意味着什么。
- 哪个系统负责处理，当前产品接收什么结果。
- 当前规则与既有规则是什么关系。
- 当前需求是否明确改变了既有能力。

不要用业务知识推导正式输入未确认的新角色、权限、规则、状态、异常、恢复能力和系统行为。

### 4.4 停止条件

出现以下任一情况时停止业务知识读取：

- 当前语境已经足以形成体验方向。
- 新增知识不再改变对象、状态、边界和责任理解。
- 后续内容只涉及当前体验压力以外的业务域。
- 继续读取只能增加背景，不能改变定案。

## 5. 设计准则和交互模式

### 5.1 硬检查节点

每个具体体验压力形成 ED 前，必须检查对应的设计准则或交互模式。

硬检查表示必须完成知识校准，不表示每条 ED 必须引用知识，也不表示必须找到特定模式名称。

按体验压力的实际含义路由：

| 体验压力 | 优先检查方向 | 检查目标 |
|---|---|---|
| 任务发现、触发和阻断 | 可发现性、信息气味、任务入口、阻断恢复、上下文承接 | 确定主动发现、受阻恢复和首次认知关系 |
| 节点连续、独立和顺序 | 任务连续性、渐进呈现、提交边界、结果回填 | 确定用户感知任务和独立结果边界 |
| 信息主次和解释时机 | 信息架构、渐进披露、错误预防、认知负担 | 确定默认理解、按需查看和解释节点 |
| 状态、结果和异常 | 状态可见性、结果反馈、错误恢复、可执行恢复 | 确定结果含义、下一步和恢复关系 |
| 跨角色和跨系统 | 任务交接、责任可见性、上下文保留、同步反馈 | 确定接手信息、等待关系和返回结果 |
| 复杂规则和数据关系 | 可解释性、信息分层、来源和影响范围 | 确定结论、关键依据和详细规则的层级 |
| 高风险和不可逆操作 | 风险前置、影响预览、确认、留痕和反馈闭环 | 确定决定前后的理解要求 |
| 高频和批量任务 | 操作效率、批量处理、默认值、重复成本和错误控制 | 平衡效率、判断成本和误操作风险 |
| 新功能和规则变化 | 首次认知、变化告知、影响范围和持续方式 | 确定告知对象、任务节点、时机和持续关系 |

路由依据是体验压力，不是任务名称、标题或关键词。

### 5.2 消费方式

读取设计知识后，检查它是否：

- 帮助选择任务发现或恢复方向。
- 改变节点连续、独立或顺序关系。
- 改变信息主次、默认或按需理解范围。
- 改变解释时机和结果反馈。
- 明确跨角色、跨节点或跨系统的承接内容。
- 限定风险、批量和效率方向。
- 排除一个不符合任务目标或责任边界的方向。

知识产生上述作用时，记录到本轮知识使用记录。只重复普通设计常识、没有改变或校准当前方向时，不记录为正式消费来源。

### 5.3 未找到直接模式

未找到直接对应的交互模式时：

1. 使用正式业务事实和相关通用设计准则继续判断。
2. 不虚构模式名称或来源。
3. 不把个人偏好写成业务规则。
4. 不因缺少特定模式而删除有效体验压力。

如果连通用设计准则也不能支持选择，但不同方向只涉及体验取舍，由 UXB 根据任务连续性、信息理解、状态结果、恢复、责任和风险选择一个方向。只有选择会改变业务事实时才停止。

## 6. 方向比较

方向比较按需执行，不是每条 ED 的必经产物。

存在真实取舍时，内部比较最多两个方向：

- 默认理解与按需查看。
- 节点连续与独立。
- 直接承接与处理指引。
- 规则前置与条件触发解释。
- 普通确认与影响预览。

正式事实和设计知识已经给出明显方向时，直接定案。不要为了证明分析过程制造无效反方向。

方向比较只修正体验方向，不能用于否定或删除已经识别的体验压力。

## 7. 知识使用记录

对实际产生作用的知识，在内部记录：

| ED | 知识来源 | 知识类型 | 对定案的作用 |
|---|---|---|---|
| ED-001 | {真实知识名称和路径} | 业务知识、设计准则或交互模式 | {选择、校准或限制了什么方向} |

记录规则：

- 每项来源对应一个或多个真实 ED。
- 作用必须指向节点、时机、信息、状态、结果、恢复、交接、风险或效率关系。
- 多个 ED 使用同一来源时可以合并记录。
- 一个 ED 使用多个来源时可以分别记录。
- 记录只服务正式 Markdown 底部的知识消费清单，不独立落盘。

以下内容不记录：

- 只被读取但没有影响决定的知识。
- 索引、README、目录名称和检索词。
- 搜索过程、覆盖率和未采用方向。
- 为满足引用数量而添加的来源。
- 大段知识原文。

## 8. 冲突、缺失和停止

- 正式输入明确新增、修改或移除既有能力时，以正式输入作为本轮事实。旧知识不能阻断明确变化。
- 无法判断差异是需求变更还是输入错误，且差异会改变体验方向时，停止受影响定案并要求核对正式输入。
- 找不到相关业务知识，但正式输入已经说明完整事实时，继续定案。
- 找不到直接设计模式时，使用通用设计准则继续，不虚构来源。
- 正式输入缺少完成体验定案所需的业务事实时，停止受影响定案，不用更多知识检索代替业务确认。
- 多个方向依赖尚未确定的业务选择时，停止受影响定案。
- 多个方向只涉及体验取舍时，由 UXB 选择一个，不停止。
- 新增知识不再改变当前判断时立即停止读取。

停止时说明缺少的事实、冲突位置和对体验方向的影响。不要补写事实，不要自动调用其他 Skill。
