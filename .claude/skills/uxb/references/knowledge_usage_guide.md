# 知识使用说明

这份说明只负责一件事：

**明确 UXB 在分析阶段怎么读知识。**

## 核心目标

不是读得越多越好，而是：

1. 先明确当前要回答什么判断问题
2. 再选择能提供证据的知识入口
3. 先读 `summary`
4. 再读该 `summary` 对应的 `raw`
5. 再进入具体分析

## 知识选择起点

知识选择不是从“这个需求像什么”开始，而是从“当前要判断什么”开始。

默认先问这类问题：

1. 这次要确认的核心业务对象是什么
2. 哪些角色会主动发起、处理、感知或承接这件事
3. 哪些规则、状态或责任关系会影响当前判断
4. 是否存在跨领域动作会改变任务链路、体验断点或策略边界

不得只根据以下内容直接选知识：

1. 需求标题
2. 功能名称
3. 页面名称
4. 单个业务关键词

只有把待判断问题说清，后面的 summary / raw 读取才算有效命中。

## 唯一现行协议

当前只保留这一条知识消费协议：

```text
先命中知识
→ 先读 summary
→ 再读该 summary 对应的 raw
→ 再进入具体分析
```

这里不再保留下面这些旧心智：

- `summary 不够再读 raw`
- `感觉 summary 够了就停`
- `先看一眼 summary，后面按情况再说`

`summary` 是路由层，不是停留层。

这里的核心不是“知识怎么选得更复杂”，而是“先按待判断问题命中对，再按顺序读对”。

## 什么时候触发

只要进入下面任一场景，就按这条协议读知识：

1. 需求分析
2. 体验诊断
3. 正式任务成型
4. 正式写判断单前的知识选择

## Step 1 与 Step 2 的知识职责

默认分工是：

```text
Step 1：业务知识主导
Step 2：业务知识提供边界，设计知识帮助诊断体验问题
```

Step 1 读业务知识的目的主要是：

1. 理解领域术语
2. 避免误解业务对象
3. 识别明显规则边界
4. 判断需求是不是重复已有能力
5. 发现明显错误前提
6. 识别当前需求是否涉及发起、处理、审批、生效、回写、反馈、异常恢复或审计追溯等业务动作链

Step 2 默认复用 Step 1 已读过的业务知识，不从零重读。

## Step 1 到 Step 2 的结论分型

知识转成分析结论时，至少区分这四类：

1. 已确认事实
   - 用户明确确认，或知识明确支持且适用于当前需求
2. 知识支持的推断
   - 由现有知识和上下文推出来，但仍可能被当前场景差异修正
3. 设计判断
   - AI 为诊断问题或收敛策略提出的方向，不是业务事实
4. 必须确认的缺口
   - 现有信息和知识无法稳定推出，且不同答案会改变核心判断、任务链路、体验断点或策略边界

默认规则：

1. 需求文档里的方案描述不自动升级成已确认事实
2. 领域基线不自动等于当前场景事实
3. 设计判断不得写入已确认事实
4. 同一事项不得同时写成已确认事实和必须确认缺口
5. Step 2 继承 Step 1 时，优先继承结论类型，而不是继承表面确定性

## 读取顺序

默认顺序固定为：

1. 从 `knowledge/wiki/index.md` 命中领域
2. 找到最相关的 `summary`
3. 读这个 `summary`
4. 继续读它对应的 `raw`
5. 再进入 `Step 1` 或后续分析

如果一个 `summary` 对应多个 `raw`，优先选择：

1. 最直接支撑当前判断点的
2. 最小必要集合

不要因为“保险”就全读一遍。

## 读取边界

这次要避免的不是“读 raw”，而是：

1. 不命中就乱读
2. 命中了却停在 summary
3. 读一堆 raw 但说不清支撑了什么判断

所以要求是：

1. 先说清当前要确认什么
2. 再说明命中了哪份 summary
3. 再进入对应 raw
4. 最后把知识转成当前判断的证据

如果某个动作由另一个领域控制，也必须把该领域作为关联领域候选，而不是只停在主领域。

## Step 2 什么时候补读业务知识

只有以下三个条件同时成立时，`Step 2` 才补读业务知识：

1. 角色、业务对象、规则、状态或责任关系存在不确定性
2. 该不确定性会改变任务链路、体验问题判断或策略方向
3. 项目业务知识里存在可能提供事实依据的内容

以下情况不触发补读：

1. 只影响页面表现
2. 只影响组件选择
3. 只影响实现细节
4. 不会改变当前体验判断
5. 现有知识已足以形成稳定结论

如果需要补读，顺序仍然是：

```text
先明确当前要确认什么
→ 命中最相关 summary
→ 读取对应 raw
→ 将知识转成当前判断依据
```

补读完成后，也必须把新增结论重新归入：已确认事实 / 知识支持的推断 / 设计判断 / 必须确认的缺口，而不是直接把新增信息整体当成已确认事实。

## 文件角色

读取时先分清这些角色：

1. `knowledge/wiki/index.md`
   - 全局知识入口
2. `knowledge/wiki/summaries/**`
   - 路由层
3. `knowledge/raw/业务/<领域>/README.md`
   - 领域入口
4. `knowledge/raw/业务/<领域>/00_领域概述.md`
   - 领域事实总览
5. 其他具体 `knowledge/raw/**`
   - 规则、流程、对象关系、状态、异常等事实层
6. `knowledge/templates/**`
   - 知识模板，不参与 UXB 正式知识消费

## 生成需求定案前的知识回顾

当用户确认生成需求定案后，在生成文档前，先回顾本次分析中已消费的知识：

1. 汇总 Step 1 和 Step 2 中已读取的 summary 和 raw 文件
2. 确认这些知识是否足以支撑文档中的判断
3. 如有判断依据不足的部分，补读对应知识
4. 在文档附录”知识追踪”中记录实际消费的业务知识和设计准则

不要把”命中某个 summary”直接当成”这个问题已经判断完了”。

进入 `Step 2` 并确定本次重点体验维度后，必须在输出 `Step 2` 前完成对应设计知识的定向读取，不把这个问题留给后续阶段。

`Step 2` 读取设计知识的原则是：

1. 只对被选中的重点体验维度定向消费对应设计知识
2. 先读设计 `summary`
3. 再读对应设计 `raw`
4. 只读取支撑当前判断的最小必要集合
5. 不得为了保险全量读取所有设计准则
6. 设计知识不替代业务事实和业务规则判断
7. 设计知识不得直接决定具体页面和组件方案

执行顺序同样固定为：

```text
先读设计 summary
→ 再读对应设计 raw
→ 再进入 Step 2 或正式交接
```

## 在回答里怎么使用知识

理想状态是：

1. 用户能感受到你参考了业务知识
2. 但输出主体仍然是在判断这次需求
3. 不是在复述知识文件

优先这样写：

```text
按当前项目知识看，这里真正变化的不是入口多了一个按钮，而是权限来源和审批闭环发生了变化。
```

避免这样写：

1. 大段贴原文
2. 机械报路径
3. 把知识库当搜索结果列表扔给用户
