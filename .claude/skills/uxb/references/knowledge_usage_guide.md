# UXB 设计知识使用

## 1. 目的

设计知识只用于提高体验定案质量，不用于补充或纠正业务事实。

读取设计知识前，先按 `experience_analysis_guide.md` 确定体验压力、分析范围和主要断点。

正式业务事实只来自：

- `spark-output/requirements_baseline.md`

## 2. 正式知识源

只从 `.claude/skills/knowledge-wiki/knowledge/` 读取正式设计知识。

优先读取：

- 设计准则。
- 交互模式。

不读取领域业务知识重新核验需求基线。

## 3. 读取顺序

```text
完整读取需求基线
→ 识别具体体验压力
→ 从知识索引进入设计准则路由
→ 读取命中的完整准则章节
→ 需要比较交互组织方式时，再进入交互模式地图
→ 读取命中的完整模式块
→ 回到本次体验定案
```

索引和地图只负责路由，不能直接作为设计结论。

## 4. 命中依据

按体验问题选择知识，不按需求标题或业务领域固定路由。

常见体验压力包括：

- 信息理解困难。
- 信息层级不清。
- 任务顺序不自然。
- 触发时机存在取舍。
- 操作影响难以预判。
- 状态和结果不透明。
- 异常后不知道下一步。
- 多角色对同一结果理解不一致。
- 跨节点或跨端任务中断。
- 高风险或不可逆操作缺少决策依据。

体验压力与知识方向：

- 多角色压力：角色连续性、状态理解和交接。
- 信息理解压力：信息架构、阅读顺序和概念区分。
- 异常与分支压力：流程、反馈和恢复。
- 跨节点与跨端压力：连续性、状态一致性和回流。
- 风险与不可逆压力：决策依据和操作前中后解释。

映射只决定读取方向，不能替代当前场景判断。

## 5. 最小充分读取

- 只读能直接支撑当前体验判断的章节。
- 同一判断需要多个准则时，读取最小必要集合。
- 命中交互模式时读取完整模式块，避免只取局部建议。
- 不为显示“读得多”而扩读相邻内容。
- 不遍历整个知识目录。

## 6. 使用方式

设计知识可以帮助：

- 比较体验方向。
- 说明取舍理由。
- 发现体验策略之间的冲突。
- 约束信息、流程、解释和反馈方向。

设计知识不可以：

- 新增业务角色、权限、规则、状态或异常。
- 推翻需求基线。
- 把通用准则当成页面方案。
- 直接复制模式中的组件或布局。
- 代替设计师确认体验取舍。

## 7. 知识与基线冲突

设计准则与需求基线描述的业务事实不在同一层级。

发生表面冲突时：

1. 保留需求基线中的业务事实。
2. 分析该事实带来的体验压力。
3. 在体验策略层寻找可行方向。
4. 不得修改基线或生成业务问题。

如果业务事实本身明显错误，停止 UXB，并建议重新执行 PRD Review。

## 8. 输出规则

- 正文写体验结论，不写知识检索过程。
- 必要时简述支撑原则，不大段引用原文。
- 不输出知识覆盖率。
- 不输出固定知识路由。
- 不把知识文件路径写成体验结论。

## 9. 停止条件

满足以下条件即可停止读取：

- 关键体验压力均有足够判断依据。
- 需要比较的体验方向已经能够定案。
- 新增知识不会改变核心体验结论。

不得追求全量知识覆盖。
