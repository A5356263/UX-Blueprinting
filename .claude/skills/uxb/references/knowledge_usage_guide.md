# UXB 业务与设计知识使用

## 1. 目的

知识只用于提高体验定案质量，不用于补充或纠正需求基线。

正式业务事实只来自：

- `spark-output/requirements_baseline.md`

需求基线中的业务约束决定体验定案的边界。UXB 必须先理解相关任务、角色、状态、结果和限制，再选择设计知识。

## 2. 正式知识源

只从当前 Skill 同级的 `knowledge-wiki/knowledge/` 读取正式知识。

必须读取：

- 与任务、角色、对象、状态和交接直接相关的业务知识。
- 与真实体验断点相关的设计准则。
- 与真实体验断点相关的交互模式。

业务知识用于理解约束和既有机制，不用于重新审核需求基线。

## 3. 读取顺序

```text
完整读取需求基线
→ 建立任务、角色、对象、状态和交接清单
→ 从知识索引进入业务领域路由
→ 读取全部相关业务知识
→ 建立用户感知阶段
→ 识别具体体验断点
→ 从知识索引进入设计准则路由
→ 读取命中的完整准则章节
→ 需要比较交互组织方式时，再进入交互模式地图
→ 读取命中的完整模式块
→ 回到本次体验定案
```

索引和地图只负责路由，不能直接作为设计结论。

业务知识读取规则：

- 不按需求标题固定路由。
- 先进入知识索引和领域 README。
- 同一任务主题命中多个正式文件时，读取全部命中文件。
- 读取与当前任务有关的完整章节，不读取孤立句子。
- 不遍历整个知识库。
- 未被需求基线触发的相邻知识不扩入。

发现业务知识与需求基线冲突时，停止 UXB，说明冲突及其影响，建议用户重新执行 PRD Review，并等待用户决定。不得选择其中一方继续定案，也不得自动调用 PRD Review。

## 4. 命中依据

按体验问题选择知识，不按需求标题或业务领域固定路由。

常见体验压力包括：

- 用户不知道任务已经发生或如何发现任务。
- 阻断发生后没有就地恢复路径。
- 只有首次曝光，没有稳定主动入口。
- 信息理解困难。
- 信息层级不清。
- 稳定信息、候选集合和已选结果混在同一视图。
- 结果回填型选择被误拆成独立阶段。
- 任务顺序不自然。
- 触发时机存在取舍。
- 操作影响难以预判。
- 状态和结果不透明。
- 异常后不知道下一步。
- 多角色对同一结果理解不一致。
- 跨节点或跨端任务中断。
- 高风险或不可逆操作缺少决策依据。

体验压力与知识方向：

- 任务发现压力：优先读取 `U-09`、`F-04` 和信息气味相关准则。
- 稳定信息与任务过程压力：优先读取 `IA-04`。
- 结果回填型选择和分步压力：优先读取 `BFM-01` 至 `BFM-04`。
- 多角色压力：角色连续性、状态理解和交接。
- 信息理解压力：信息架构、阅读顺序和概念区分。
- 异常与分支压力：流程、反馈和恢复。
- 跨节点与跨端压力：连续性、状态一致性和回流。
- 风险与不可逆压力：决策依据和操作前中后解释。

映射只决定读取方向，不能替代当前场景判断。

## 5. 读取停止条件

业务知识只有同时满足以下条件才停止读取：

- 全部核心任务均已覆盖。
- 相关角色、对象、状态和交接均有足够业务语境。
- 继续读取不会改变体验约束理解。

设计知识按最小充分原则停止：

- 只读能直接支撑当前体验判断的章节。
- 同一判断需要多个准则时，读取最小必要集合。
- 命中交互模式时读取完整模式块，避免只取局部建议。
- 不为显示“读得多”而扩读相邻内容。

## 6. 使用方式

设计知识可以帮助：

- 比较体验方向。
- 说明取舍理由。
- 发现体验策略之间的冲突。
- 约束信息、流程、解释和反馈方向。

每次使用知识都必须回到当前业务场景：

```text
需求基线中的业务约束
→ 真实体验压力
→ 命中的设计原则或模式
→ 本需求的明确体验决策
→ 蓝图必须落实的要求
```

知识只能支撑决策，不能成为正文摘要。无法改变本需求体验决策的知识不进入正式产物。

设计知识不可以：

- 新增业务角色、权限、规则、状态或异常。
- 推翻需求基线。
- 把通用准则当成页面方案。
- 直接复制模式中的组件或布局。
- 因知识出现 `Tab`、`Wizard`、`Steps`、弹窗或抽屉示例，就把组件形式写进 UXB 定案。
- 代替设计师确认体验取舍。
- 只输出正确但无法改变设计的通用建议。

## 7. 知识与基线冲突

设计准则与需求基线描述的业务事实不在同一层级。

发生表面冲突时：

1. 保留需求基线中的业务事实。
2. 分析该事实带来的体验压力。
3. 在体验策略层寻找可行方向。
4. 不得修改基线或生成业务问题。

如果业务事实本身明显错误，停止 UXB，并建议重新执行 PRD Review。

## 8. 输出规则

- 正文写体验结论，不写知识检索过程。
- 必要时简述支撑原则，不大段引用原文。
- 不输出知识覆盖率。
- 不输出固定知识路由。
- 不把知识文件路径写成体验结论。

## 9. 停止条件

满足以下条件即可停止读取：

- 全部核心任务的相关业务知识已经覆盖。
- 关键体验压力均有足够判断依据。
- 需要比较的体验方向已经能够定案。
- 新增知识不会改变核心体验结论。

业务知识覆盖本需求直接相关内容，不通读整个业务域。设计知识不追求全量覆盖。
