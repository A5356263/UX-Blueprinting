# 知识使用说明

这份说明只负责一件事：

**明确 UXB 在分析阶段怎么读知识。**

## 核心目标

不是读得越多越好，而是：

1. 先找到命中的知识入口
2. 先读 `summary`
3. 再读该 `summary` 对应的 `raw`
4. 再进入具体分析

## 唯一现行协议

当前只保留这一条知识消费协议：

```text
先命中知识
→ 先读 summary
→ 再读该 summary 对应的 raw
→ 再进入具体分析
```

这里不再保留下面这些旧心智：

- `summary 不够再读 raw`
- `感觉 summary 够了就停`
- `先看一眼 summary，后面按情况再说`

`summary` 是路由层，不是停留层。

这里的核心不是“知识怎么选得更复杂”，而是“命中之后必须按顺序读对”。

## 什么时候触发

只要进入下面任一场景，就按这条协议读知识：

1. 需求分析
2. 体验诊断
3. 正式任务成型
4. 正式写判断单前的知识选择

## 读取顺序

默认顺序固定为：

1. 从 `knowledge/wiki/index.md` 命中领域
2. 找到最相关的 `summary`
3. 读这个 `summary`
4. 继续读它对应的 `raw`
5. 再进入 `Step 1` 或后续分析

如果一个 `summary` 对应多个 `raw`，优先选择：

1. 最直接支撑当前判断点的
2. 最小必要集合

不要因为“保险”就全读一遍。

## 读取边界

这次要避免的不是“读 raw”，而是：

1. 不命中就乱读
2. 命中了却停在 summary
3. 读一堆 raw 但说不清支撑了什么判断

所以要求是：

1. 先说清当前要确认什么
2. 再说明命中了哪份 summary
3. 再进入对应 raw
4. 最后把知识转成当前判断的证据

## 文件角色

读取时先分清这些角色：

1. `knowledge/wiki/index.md`
   - 全局知识入口
2. `knowledge/wiki/summaries/**`
   - 路由层
3. `knowledge/raw/业务/<领域>/README.md`
   - 领域入口
4. `knowledge/raw/业务/<领域>/00_领域概述.md`
   - 领域事实总览
5. 其他具体 `knowledge/raw/**`
   - 规则、流程、对象关系、状态、异常等事实层
6. `knowledge/templates/**`
   - 知识模板，不参与 UXB 正式知识消费

## 正式任务前的知识选择

当用户确认进入正式蓝图任务后，UXB 需要先完成知识选择，并写入：

- `projects/<project-id>/runtime/uxb_route_decision.json`

这里的要求是：

1. 先命中 summary
2. 再补对应 raw
3. 再把要消费的最小文件集合写进 `knowledge_selection.files`
4. 用 `knowledge_selection.reasoning` 说明为什么选这些资料

不要把“命中某个 summary”直接当成“这个问题已经判断完了”。

如果后续大概率会进入 `experience_blueprint.md`，设计知识必须在分析阶段就读入，再由判断单收住，不把这个问题留给工程主链路兜底。

执行顺序同样固定为：

```text
先读设计 summary
→ 再读对应设计 raw
→ 再进入 Step 2 或正式交接
```

## 在回答里怎么使用知识

理想状态是：

1. 用户能感受到你参考了业务知识
2. 但输出主体仍然是在判断这次需求
3. 不是在复述知识文件

优先这样写：

```text
按当前项目知识看，这里真正变化的不是入口多了一个按钮，而是权限来源和审批闭环发生了变化。
```

避免这样写：

1. 大段贴原文
2. 机械报路径
3. 把知识库当搜索结果列表扔给用户
