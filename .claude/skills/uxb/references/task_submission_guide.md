# Task Submission Guide

当咨询已经成熟到可以变成正式 UXB 任务时，用这个 guide。

## 核心规则

聊天记录不是正式输入。

正式输入必须先被整理成一份用户可确认的任务摘要，再进入主链路。

## 为什么一定要先写摘要

原始聊天通常混着这些东西：

- 临时想法
- 反复修改
- 口语化表达
- 还没定的判断
- 背景信息
- 真正要执行的目标

不要把原始聊天直接倒进 `projects/`。

## 什么时候该写任务摘要

满足下面任一类情况，就该先整理摘要：

1. 用户给出了比较完整的新需求或需求文档。
2. 诊断咨询后，用户明确认可判断，并要求输出正式蓝图。
3. 用户明确说要“走主链路 / 创建任务 / 输出正式材料”。
4. 现有信息已经足够形成一个真实 UXB 任务。

不满足这些条件时，优先停留在知识问答或诊断咨询，不要硬转任务。

## 从诊断咨询转正式任务

从诊断转正式任务时，至少要同时满足：

- 用户已经认可当前诊断方向，或明确接受你给出的切入点。
- 本轮目标已经清楚到可以写成产物。
- 你能说明这轮是要输出业务蓝图、体验蓝图，还是更浅层的正式材料。

推荐话术：

```text
如果你认可这个判断，我可以先把它整理成一份正式 UXB 任务。你确认后，我再开始输出业务蓝图和体验蓝图。
```

不要问用户“是否切换到正式蓝图任务态”。

## 新需求文档转正式任务

用户给需求文档时，不要直接执行。

先做这几步：

1. 先阅读文档。
2. 先指出明显风险、缺口、未决点。
3. 判断当前信息是否已经足够转成正式任务。
4. 整理任务摘要。
5. 等用户确认后再执行。

## 任务摘要必须覆盖什么

即使对用户的话术很自然，摘要也必须覆盖这些内容：

1. 本次任务要解决什么。
2. 用户真正关心什么。
3. 目前已经明确的事实。
4. 哪些点还不确定，但不阻塞先做。
5. 建议执行深度：
   - facts
   - business
   - experience
   - full chain
6. 建议任务名。
7. 建议 `project-id`。

## 确认门槛

只有用户明确表达下面这类确认意图后，才能开始执行：

- 好，开始
- 确认
- 创建任务
- 走主链路
- 开始生成正式产物

在确认之前：

- 不创建项目目录
- 不写正式任务产物
- 不运行 UXB 主链路

## 正式产物与知识库的边界

正式任务的产物进入：

```text
projects/<project-id>/
```

正式任务产物不自动进入 knowledge。

如果蓝图中有值得复用的稳定规则、流程依赖或体验原则：

1. 先提取为知识候选。
2. 放进 `知识候选区/` 对应子目录。
3. 等用户确认后，再进入正式知识库维护。

不要把蓝图整份直接入库。

## 正式蓝图完成后的知识变更检查

当正式蓝图任务完成后，必须做一次知识变更检查。

检查目标不是复制需求文档，也不是复制蓝图，而是识别本次需求对长期知识库的影响。

必须检查四类变化：

### 1. 新增知识

- 是否新增业务能力
- 是否新增菜单、页面、入口
- 是否新增字段、状态、流程
- 是否新增权限、角色、数据范围
- 是否新增异常处理、限制条件、校验规则

### 2. 修正知识

- 是否发现现有 knowledge 中的旧路径需要更新
- 是否发现旧菜单结构、旧页面结构需要修正
- 是否发现旧规则、旧状态、旧权限说明已经不适用
- 是否发现 summary 指向的 raw 内容已经过时

### 3. 冲突知识

- 蓝图结论是否与现有 raw 冲突
- 新需求是否推翻历史规则
- 不同 raw 文件之间是否出现口径不一致

冲突内容必须使用 `[CONFLICT]` 标记，不得静默覆盖。

### 4. 补缺知识

- 是否发现 knowledge 缺少必要业务规则
- 是否缺少完整操作路径
- 是否缺少权限边界
- 是否缺少状态流转说明
- 是否缺少页面、字段、菜单解释

缺口内容必须使用 `[GAP]` 或 `[QUESTION]` 标记。

## 蓝图完成后的收尾动作

如果发现候选知识：

1. 先输出候选清单。
2. 清单只列新增 / 修正 / 冲突 / 补缺，不复述整份蓝图。
3. 等用户确认后，再写入 `知识候选区/新需求文档/`。

推荐话术：

```text
本次蓝图完成后，我发现以下内容可能需要进入知识候选区：

1. xxx
2. xxx
3. xxx

这些不是蓝图全文，而是对长期知识库有影响的新增、修正、冲突或补缺内容。
是否需要我整理到「知识候选区/新需求文档/」？
```

如果没有发现候选知识，明确收尾：

```text
本次蓝图主要是一次性方案，没有发现需要沉淀或修正的长期知识。
```

## 不得提取为候选的内容

蓝图完成后，不得将以下内容写入知识候选区：

- 需求文档全文
- 蓝图全文
- 一次性项目目标
- 临时方案
- 过程讨论
- 未经确认的猜测
- 只服务当前页面的局部设计细节
- 没有长期复用价值的实现限制

## 用户可感知的话术

不要把摘要写成冷冰冰的 intake 表单。

应该更像：

- 这次主要要解决什么
- 你真正关心什么
- 目前哪些已经明确
- 哪些还不确定但不影响先推进
- 我建议这轮先做到什么程度
