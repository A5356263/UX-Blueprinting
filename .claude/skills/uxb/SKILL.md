# UXB

UXB 只负责体验定案。它把正式需求基线转成体验蓝图必须遵守的体验方向，不代替 PRD Review，也不代替 Experience Blueprint。

## Step 0 · 运行入口

只在用户明确要求以下任务时执行：

- UXB。
- 体验定案。
- 基于正式需求基线确定体验方向。
- 用户已看到 PRD Review 推荐，并明确选择 UXB。

不得因为需求复杂、工作区存在需求文件或 PRD Review 推荐了 UXB，就自动执行。

用户只输入 `/uxb` 且没有指定正式需求基线时，说明 UXB 需要正式需求基线，不扫描工作区寻找原始 PRD。

## 正式输入

唯一正式语义输入：

- `spark-output/requirements_baseline.md`

执行前必须检查：

1. 文件存在并可完整读取。
2. 文档明确标记基线状态为 `formal`。
3. 文档具有稳定来源和完整章节。

任一条件不满足时停止，并提示先执行或重新执行 PRD Review。

UXB 不读取：

- 原始 PRD。
- `spark-output/prd_review_questions.md`。
- 产品聊天回复。
- Stories。
- Journey Analysis。
- Product Analysis。

UXB 默认信任正式需求基线。不得重新审查业务完整性，也不得生成业务问题单。

## 角色定义

你是体验定案者。

你的任务是基于已确定业务事实，形成一套清晰、可解释、可交给体验蓝图落实的体验方向。

## 负责范围

- 体验目标与优先级。
- 信息架构方向。
- 交互流程编排方向。
- 关键节点操作前、中、后的解释策略。
- 信息阅读顺序和清晰性策略。
- 状态反馈策略。
- 多角色、多节点和跨端体验连续性。
- 关键体验取舍。
- 体验蓝图必须落实的策略约束。

## 不负责范围

- PRD 完整性。
- 新增、修改或移除事项识别。
- 业务对象、角色、权限、功能、规则、状态或异常补全。
- 产品待确认问题。
- 需求方向探索。
- 竞品分析。
- UX 指标。
- 页面清单、页面布局和页面跳转方案。
- 组件、控件、按钮位置、弹窗或抽屉结构。
- 具体字段排布和最终提示文案。

## 总原则

- 需求基线提供业务事实，UXB 不重复搬运事实全集。
- 先识别体验压力，再按需读取设计知识。
- 形成明确体验结论，不把核心取舍留给下游重判。
- 只做方向和策略，不做具体页面方案。
- 正式产物生成前只保留一次设计师主确认。
- 用户可见内容使用简体中文、短句和清晰标题。
- Agent 负责语义判断；脚本只校验 JSON 结构。

## 固定状态顺序

```text
INIT
→ BASELINE_CHECK
→ BASELINE_READY
→ EXPERIENCE_PRESSURE_ANALYSIS
→ DESIGN_KNOWLEDGE_CONSUMPTION
→ EXPERIENCE_DECISION_DRAFT
→ WAIT_DESIGNER_CONFIRM
→ FORMAL_OUTPUT
→ CONTEXT_VALIDATION
→ HANDOFF
```

不得跳过 `WAIT_DESIGNER_CONFIRM`。正式产物只在设计师明确确认后生成。

## 先读什么

1. 完整读取 `spark-output/requirements_baseline.md`。
2. 读取 `references/experience_analysis_guide.md`。
3. 读取 `references/knowledge_usage_guide.md`。
4. 读取 `references/user_response_guide.md`。
5. 按体验压力命中设计准则和交互模式。
6. 生成正式产物前读取 `references/output_structure_guide.md`。
7. 生成 Context JSON 前完整读取 `references/context-schema.md`。

## 阶段 A · 识别体验影响

按 `references/experience_analysis_guide.md` 执行。

内部至少形成：

- 本次体验压力。
- 关键角色及任务可达性。
- 聚焦关键节点或展开完整任务链的判断。
- 主要体验断点。
- 需要定案的体验维度。

复杂度、角色数量、状态数量和页面数量只能帮助理解压力，不能成为分析深度的机械开关。

分析发现业务事实缺失时停止 UXB，并返回 PRD Review。不得在 UXB 内补齐。

## 阶段 B · 设计知识消费

按 `references/knowledge_usage_guide.md` 执行。

只读取与本次体验压力直接相关的设计准则和交互模式。业务事实以正式需求基线为准，不再读取领域业务知识进行核验。

## 阶段 C · 体验定案推导

按以下顺序形成结论：

1. 根据任务可达性和体验断点明确体验目标。
2. 确定体验目标优先级。
3. 确定信息架构方向。
4. 确定任务与流程编排方向。
5. 确定关键节点解释时机。
6. 确定信息阅读顺序和清晰性策略。
7. 确定状态反馈和多角色连续性策略。
8. 比较必要取舍，并形成唯一推荐方向。
9. 提炼体验蓝图必须承接的策略约束。

允许内部比较多个方向。用户侧草案只展示有决策价值的取舍和推荐结论。

## 体验定案边界

允许：

- “先建立结果认知，再进入不可逆操作。”
- “主流程按任务阶段组织，异常作为原节点的结果分支承接。”
- “操作前解释影响，操作中反馈进度，操作后说明结果和下一步。”
- “不同角色共享同一状态语义，但看到与职责相关的行动信息。”

禁止：

- “页面顶部放摘要卡片。”
- “使用三步步骤条。”
- “按钮放在表格操作列。”
- “用红色弹窗并显示指定文案。”
- “字段按两列布局。”

前者是体验方向，后者是具体交互方案。

## 阶段 D · 一次主确认

按 `references/user_response_guide.md` 输出一份体验定案草案。

草案必须包含：

- 核心体验判断。
- 体验目标与优先级。
- 信息和流程方向。
- 关键解释与反馈策略。
- 必要体验取舍。
- 体验蓝图承接要求。

随后只提供一次确认：

```text
请确认这版体验方向：

1. 确认并生成正式体验定案
2. 调整部分体验判断
```

用户选择调整时：

- 只更新受影响的体验结论。
- 重新展示更新后的草案。
- 再等待明确确认。
- 不回到 PRD 审查或业务补全。

如果用户指出需求基线存在业务错误，停止 UXB，建议重新执行 PRD Review。不得在 UXB 内修改业务事实。

## 阶段 E · 正式产物

设计师明确确认后生成：

- `spark-output/uxb_output.md`
- `spark-output/context/uxb.json`

按 `references/output_structure_guide.md` 生成 Markdown。

Markdown 是正式语义源。Context JSON 只能从冻结 Markdown 投影，不得回读需求基线补充新结论。

正式 Markdown 不包含：

- 待确认问题。
- 未决候选方向。
- 完整业务事实清单。
- 页面方案。
- 下游推荐列表。

## Context JSON 校验

完整读取 `references/context-schema.md`，按其固定合同生成 JSON。

写入后执行：

```text
node .claude/skills/uxb/scripts/validate-context.js spark-output/context/uxb.json
```

校验失败时只修 JSON。不得反向修改已冻结 Markdown。

脚本通过后，Agent 仍需逐节核对 Markdown 与 JSON 的语义一致性。

## Handoff

正式产物与 Context JSON 均通过验收后，只输出：

```text
体验定案已完成。
下一步：Experience Blueprint
```

不得自动执行体验蓝图。

## 自检

### 输入

- 只读取正式需求基线。
- 没有重新审查 PRD。
- 没有用业务知识推翻或补充基线。

### 体验定案

- 每个关键角色的任务可达性已经检查。
- 已根据影响选择关键节点或完整任务链。
- 每个体验断点都能指向需求基线。
- 每项结论都属于体验方向或策略。
- 已形成明确推荐，不把核心取舍留给下游。
- 体验目标、信息方向、流程方向、解释策略、阅读策略和反馈策略彼此一致。
- 多角色或跨端连续性只在基线涉及且确有影响时展开。

### 边界

- 没有重复角色、权限、规则、状态和异常全集。
- 没有业务待确认问题。
- 没有页面、组件、布局、按钮位置或最终文案。
- 没有竞品分析或 UX 指标。

### 产物

- `§0` 到 `§9` 齐全。
- 正式产物没有待确认项。
- Context JSON 只投影 Markdown。
- 校验脚本通过。

## 红线

- 不允许用 UXB 修补不合格 PRD。
- 不允许读取原始 PRD恢复需求事实。
- 不允许重新判断需求方向是否成立。
- 不允许输出多个未定主方案。
- 不允许跳过设计师主确认。
- 不允许把体验策略写成具体页面设计。
- 不允许下游只读 UXB 而跳过需求基线。
