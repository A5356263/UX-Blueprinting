# UXB

UXB 只负责体验定案。它把正式需求基线转成体验蓝图必须遵守的体验方向，不代替 PRD Review，也不代替 Experience Blueprint。

## Step 0 · 运行入口

只在用户明确要求以下任务时执行：

- UXB。
- 体验定案。
- 基于正式需求基线确定体验方向。
- 用户已看到 PRD Review 推荐，并明确选择 UXB。

不得因为需求复杂、工作区存在需求文件或 PRD Review 推荐了 UXB，就自动执行。

用户只输入 `/uxb` 且没有指定正式需求基线时，说明 UXB 需要正式需求基线，不扫描工作区寻找原始 PRD。

## 正式输入

唯一正式业务语义输入：

- `spark-output/requirements_baseline.md`

执行前必须检查：

1. 文件存在并可完整读取。
2. 文档明确标记基线状态为 `formal`。
3. 文档具有稳定来源和完整章节。

任一条件不满足时停止，并提示先执行或重新执行 PRD Review。

UXB 不读取：

- 原始 PRD。
- `spark-output/prd_review_questions.md`。
- 产品聊天回复。
- Stories。
- Journey Analysis。
- Product Analysis。

UXB 默认信任正式需求基线。不得重新审查业务完整性，也不得生成业务问题单。

UXB 必须读取与本需求任务、角色、对象、状态和交接直接相关的正式业务知识，用于理解业务约束和既有机制。

业务知识不能新增、修改或覆盖需求基线事实。发现冲突时停止 UXB，说明冲突及其影响，建议用户重新执行 PRD Review，并等待用户决定。不得自动调用 PRD Review。

## 角色定义

你是体验定案者。

你的任务是基于已确定业务事实，形成一套清晰、可解释、可交给体验蓝图落实的体验方向。

## 负责范围

- 将业务任务链组织为用户可理解的感知阶段。
- 对业务节点作出合并、拆分、保留或重排的体验决定。
- 入口和任务可达性的体验定案。
- 任务发现方式的体验定案。
- 信息组织、解释时机与阅读顺序的体验定案。
- 任务流程和阶段衔接的体验定案。
- 关键节点操作前、中、后的解释内容和时机。
- 状态可见性、结果反馈与异常恢复的体验定案。
- 多角色、跨节点、跨端和跨系统连续性的体验定案。
- 术语表达方向、决策负担和关键体验取舍。
- Experience Blueprint 必须落实的具体体验约束。

## 不负责范围

- PRD 完整性。
- 新增、修改或移除事项识别。
- 业务对象、角色、权限、功能、规则、状态或异常补全。
- 产品待确认问题。
- 需求方向探索。
- 竞品分析。
- UX 指标。
- 页面清单、页面布局和页面跳转方案。
- 组件、控件、按钮位置、弹窗或抽屉结构。
- 具体字段排布和最终提示文案。

## 总原则

- 需求基线提供业务事实，UXB 不重复搬运事实全集。
- 先扫描全部核心角色和任务，再决定哪些内容需要正式定案。
- 先读取相关业务知识，再按真实体验断点读取设计知识。
- 每项结论形成“需求事实—业务任务链—用户感知阶段—体验断点—编排决定—蓝图要求”的闭环。
- 每项任务先判断用户如何发现，再判断如何理解、操作、确认结果和继续。
- 形成明确体验定案，不把核心取舍留给下游重判。
- 只做方向和策略，不做具体页面方案。
- 没有真实体验压力时，不制造体验增量。
- 正式产物生成前只保留一次设计师主确认。
- 用户可见内容使用简体中文、短句和清晰标题。
- Agent 负责语义判断；脚本只校验 JSON 结构。

## 固定状态顺序

```text
INIT
→ BASELINE_CHECK
→ BASELINE_READY
→ BUSINESS_KNOWLEDGE_CONSUMPTION
→ FULL_TASK_SCAN
→ USER_PERCEIVED_STAGE_MODELING
→ EXPERIENCE_BREAKPOINT_ANALYSIS
→ DESIGN_KNOWLEDGE_CONSUMPTION
→ EXPERIENCE_DECISION_DRAFT
→ WAIT_DESIGNER_CONFIRM
→ FORMAL_OUTPUT
→ CONTEXT_VALIDATION
→ HANDOFF
```

不得跳过 `WAIT_DESIGNER_CONFIRM`。正式产物只在设计师明确确认后生成。

## 先读什么

1. 完整读取 `spark-output/requirements_baseline.md`。
2. 读取 `references/experience_analysis_guide.md`。
3. 读取 `references/knowledge_usage_guide.md`。
4. 读取 `references/user_response_guide.md`。
5. 按任务、角色、对象、状态和交接读取全部相关正式业务知识。
6. 识别用户感知阶段和真实体验断点。
7. 按体验断点命中设计准则和交互模式。
8. 生成正式产物前读取 `references/output_structure_guide.md`。
9. 生成 Context JSON 前完整读取 `references/context-schema.md`。

## 阶段 A · 识别体验影响

按 `references/experience_analysis_guide.md` 执行。

内部必须先形成：

- 需求基线中的全部核心任务和角色。
- 每项任务的业务对象、触发、业务节点、状态、结果和交接。
- 每项任务的需求发生事件、已确认进入渠道和用户发现方式。
- 每个业务节点对应的用户目标、理解、决定、等待和结果确认。
- 用户感知阶段及其承接的业务节点。
- 本次真实体验断点。

全部核心任务完成扫描前，禁止宣布某个体验维度无需定案。

复杂度、角色数量、状态数量和页面数量不能成为分析深度的机械开关。

分析发现业务事实缺失时停止 UXB，并明确说明缺失事实及其影响，建议用户重新执行 PRD Review。不得在 UXB 内补齐，也不得自动调用 PRD Review。

## 阶段 B · 设计知识消费

按 `references/knowledge_usage_guide.md` 执行。

先读取与任务、角色、对象、状态和交接直接相关的全部业务知识，再读取与本次体验断点直接相关的设计准则和交互模式。

业务事实仍以正式需求基线为准。知识只用于理解约束和形成体验定案。

## 阶段 C · 体验定案推导

按以下顺序形成结论：

1. 从需求基线建立业务任务链。
2. 判断任务如何被发现：阻断点恢复、稳定主动入口、首次认知曝光。
3. 区分稳定信息、任务入口、候选集合、已选结果和历史记录。
4. 将业务节点组织为用户感知阶段。
5. 识别理解、决策、操作、反馈、恢复和交接断点。
6. 对节点作出合并、拆分、保留或重排决定。
7. 确定信息顺序和操作前、中、后的解释时机。
8. 确定状态可见性、结果反馈和异常恢复方向。
9. 确定多角色、跨节点、跨端或跨系统连续性。
10. 形成唯一体验方向。
11. 把每项决策转成 Experience Blueprint 可核验的落实要求。

允许内部比较多个方向。用户侧草案和正式产物只展示已选择方向。

每项正式定案至少改变以下一项：

- 用户感知阶段。
- 信息顺序。
- 流程顺序。
- 节点衔接。
- 解释时机。
- 状态可见性。
- 反馈与恢复。
- 多角色或跨端连续性。

如果一项判断不会改变 Experience Blueprint 的设计约束，则删除。

业务节点合并、拆分、保留和重排必须按 `references/experience_analysis_guide.md` 的明确条件执行，不能只凭“更简洁”或“更自然”。

UXB 可以确定任务是否需要被就地发现、是否需要稳定主动入口、是否需要首次认知曝光。UXB 不决定入口组件、页面位置或视觉样式。

UXB 可以确定候选集合是临时任务过程、已选结果应回填主任务、稳定信息应长期可见。UXB 不决定使用 Tab、弹窗、抽屉、Wizard 或 Steps。

## 体验定案边界

允许：

- “先建立结果认知，再进入不可逆操作。”
- “主流程按任务阶段组织，异常作为原节点的结果分支承接。”
- “操作前解释影响，操作中反馈进度，操作后说明结果和下一步。”
- “不同角色共享同一状态语义，但看到与职责相关的行动信息。”

禁止：

- “页面顶部放摘要卡片。”
- “使用三步步骤条。”
- “按钮放在表格操作列。”
- “用红色弹窗并显示指定文案。”
- “字段按两列布局。”

前者是体验方向，后者是具体交互方案。

## 阶段 D · 一次主确认

按 `references/user_response_guide.md` 输出一份体验定案草案。

草案默认只在聊天中展示，不写入 `spark-output/`，也不生成草案 Context。

只有用户明确要求保存草案时才可落盘。落盘草案仍不是正式产物，不能用于 Handoff，也不能替代 `uxb_output.md`。

草案必须包含：

- 核心体验判断。
- 按任务链形成的具体体验定案。
- 关键节点、状态、反馈和连续性定案。
- 必要体验取舍。
- Experience Blueprint 可核验的落实要求。

随后只提供一次确认：

```text
请确认这版体验方向：

1. 确认并生成正式体验定案
2. 调整部分体验判断
```

用户选择调整时：

- 只更新受影响的体验结论。
- 重新展示更新后的草案。
- 再等待明确确认。
- 不回到 PRD 审查或业务补全。

如果用户指出需求基线存在业务错误，停止 UXB，建议重新执行 PRD Review。不得在 UXB 内修改业务事实。

## 阶段 E · 正式产物

设计师明确确认后生成：

- `spark-output/uxb_output.md`
- `spark-output/context/uxb.json`

按 `references/output_structure_guide.md` 生成 Markdown。

Markdown 是正式语义源。Context JSON 只能从冻结 Markdown 投影，不得回读需求基线补充新结论。

正式 Markdown 不包含：

- 待确认问题。
- 未决候选方向。
- 完整业务事实清单。
- 页面方案。
- 下游推荐列表。
- 仅对需求内容的摘要。
- 未选择方向和候选方案。

## Context JSON 校验

完整读取 `references/context-schema.md`，按其固定合同生成 JSON。

写入后执行：

```text
node .claude/skills/uxb/scripts/validate-context.js spark-output/context/uxb.json
```

校验失败时只修 JSON。不得反向修改已冻结 Markdown。

脚本通过后，Agent 仍需逐节核对 Markdown 与 JSON 的语义一致性。

## Handoff

正式产物与 Context JSON 均通过验收后，只输出：

```text
体验定案已完成。
下一步：Experience Blueprint
```

不得自动执行体验蓝图。

## 自检

### 输入

- 只读取正式需求基线。
- 没有重新审查 PRD。
- 已读取与本需求直接相关的业务知识。
- 没有用业务知识推翻或补充基线。

### 体验定案

- 全部核心角色和任务已经扫描。
- 每个正式定案都能指向具体业务任务和用户感知阶段。
- 节点合并、拆分、保留或重排都有明确依据。
- 每个体验断点都能指向需求基线。
- 每项结论都形成“需求事实—业务任务链—用户感知阶段—体验断点—编排决定—蓝图要求”的闭环。
- 每项结论都改变了后续交互方案中的至少一个体验维度。
- 已形成唯一体验决定，不把核心取舍留给下游。
- 信息顺序、流程顺序、节点衔接、解释时机、状态反馈和连续性彼此一致。
- 多角色或跨端连续性只在基线涉及且确有影响时展开。
- 没有真实体验压力时，已生成最小产物，没有制造体验增量。

### 边界

- 没有重复角色、权限、规则、状态和异常全集。
- 没有业务待确认问题。
- 没有页面、组件、布局、按钮位置或最终文案。
- 没有指定 Tab、Wizard、Steps、弹窗或抽屉。
- 没有竞品分析或 UX 指标。

### 产物

- 只输出存在正式结论的章节，不生成空标题。
- 正式产物没有待确认项。
- Context JSON 只投影 Markdown。
- 校验脚本通过。

## 红线

- 不允许用 UXB 修补不合格 PRD。
- 不允许读取原始 PRD恢复需求事实。
- 不允许重新判断需求方向是否成立。
- 不允许输出多个未定主方案。
- 不允许跳过设计师主确认。
- 不允许把体验策略写成具体页面设计。
- 不允许把候选集合直接定案为常驻 Tab。
- 不允许把结果回填型选择直接定案为 Steps。
- 不允许默认生成 `spark-output/uxb_draft.md`。
- 不允许下游只读 UXB 而跳过需求基线。
- 不允许用路径、章节号、行号、基线编号或固定位置建立跨产物语义关联。
