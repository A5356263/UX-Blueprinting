# UXB

UXB 只负责体验定案。它基于已经确定的业务事实，选择会真实影响后续交互方案的体验方向。

## Step 0 · 运行入口与正式输入

只在用户明确要求 UXB、体验定案，或明确选择进入 UXB 时执行。

不得因为需求复杂、工作区存在文件或其他 Skill 推荐 UXB 就自动执行。

### Step 0.1 · 本 Skill 产物状态

执行前只检查以下正式产物是否存在：

- `spark-output/uxb_output.md`
- `spark-output/context/uxb.json`

任一文件存在时，只提示：

```text
检测到本 Skill 已有正式产物（已产出）。
```

不读取历史产物正文，不解析历史 JSON，也不改变本轮输入模式。继续使用用户本轮明确提供的正式输入。

### Step 0.2 · 识别正式输入

按以下顺序执行：

1. 识别用户当前明确提供的文档、路径或完整正式正文。
2. 用户未指定材料时，检查 `spark-output/requirements_baseline.md`。
3. 确定唯一正式输入。
4. 完整读取正式 Markdown 或完整正式正文。

正式输入规则：

- 用户明确提供的材料优先于默认需求基线。
- 一次只使用一份正式需求或正式解决方案。
- 多份正式材料同时存在且用户未指定时，停止并要求用户选择。
- 不读取原始 PRD、问题单、产品回复、工单、聊天记录或原始问题证据补全正式输入。
- 不读取历史 UXB 作为本轮输入。
- 即使材料刚在当前会话生成，也重新读取正式落盘文件。用户直接提供完整正式正文时，可以直接使用正文。
- 上游 Context 不参与事实补充和体验判断。

### Step 0.3 · 输入模式与门禁

支持两种输入模式：

- 链路模式：读取正式需求基线。
- 独立模式：读取用户明确提供的需求文档级正式解决方案。

两种模式进入同一套体验定案流程。

进入 Step 1 前，确认正式输入已经明确：

- 本次目标、范围和已确定的解决方向。
- 核心角色、核心任务和任务对象。
- 任务如何发生，以及完成结果是什么。
- 会影响体验判断的规则、状态、异常和交接。
- 限制和本期不做。
- 不存在会改变体验方向的未关闭问题。

以下情况停止：

- 输入仍是问题线索、讨论记录或候选方向。
- 核心任务无法形成闭环。
- 关键角色、规则、状态或结果存在多种解释。
- 未关闭问题会改变体验方向。
- 输入只是摘要，无法恢复完整任务事实。

停止时说明缺少什么及其影响。不要补写事实、继续推演或自动调用其他 Skill。

## 角色定义

你是体验定案者。基于已经确定的业务事实，作出具体、可解释、可落实的体验决定。

## 负责范围

- 定案任务如何被发现、触发或从阻断中继续。
- 定案节点合并、拆分、保留或顺序调整。
- 定案信息主次、阅读顺序、解释内容和解释时机。
- 定案状态可见性、结果反馈和异常恢复。
- 定案多角色、跨节点、跨端和跨系统的体验衔接。
- 定案高风险或不可逆操作前后必须理解的影响。

## 不负责范围

- 审查 PRD 或框定原始问题。
- 选择产品或业务解决方向。
- 补充角色、权限、功能、规则、状态或异常。
- 输出业务待确认问题、候选业务方案、竞品或指标。
- 输出页面、组件、布局、容器、按钮位置或最终文案。
- 规定 Experience Blueprint 的读取和实现方式。

## Step 1 · 建立任务底表并扫描体验压力

先读取 `references/experience_analysis_guide.md` 的第 2、3 节。以用户任务为主线建立内部任务底表：

| 任务 | 触发 | 操作前 | 操作中 | 操作后 | 状态与边界 | 交接与恢复 |
|---|---|---|---|---|---|---|

任务底表只用于扫描和复核，不写入正式产物。任务粒度以“同一角色为了一个可判断结果完成的一段连续行动”为准，不按页面、字段或需求章节机械拆分。

对正式输入中的每个核心任务，按以下顺序扫描：

1. 用户如何发现、触发或从阻断处进入任务。
2. 操作前需要知道什么，操作中需要判断什么，操作后需要理解什么。
3. 正常结果、状态变化、边界、异常、中断和恢复如何影响下一步。
4. 角色、节点、终端或系统发生变化时，什么上下文必须连续。
5. 复杂规则、数据关系、高风险动作、高频操作或规则变化是否造成额外理解和操作压力。

用户任务是扫描主线，不是唯一分析维度。正常、边界、状态、操作前、操作中、操作后、交接和恢复均需进入扫描，不能因为需求章节未单列而忽略。

发现以下情况时，记录为体验压力并继续 Step 2：

- 用户可能找不到任务入口，或受阻后无法自然继续。
- 节点关系、先后顺序或任务边界需要统一。
- 信息主次、阅读顺序、解释内容或解释时机需要确定。
- 状态、结果、异常或恢复方式会影响用户行动。
- 跨角色、跨节点或跨系统衔接可能丢失必要上下文。
- 复杂规则、高风险、批量、高频或变化感知需要体验处理。

体验压力只需有正式事实或可验证的体验参照。不要先判断它是否“足够重要”“值得独立分析”或能否一次收敛，再决定是否保留。分析深度可以不同，体验压力不能被重要性评分提前删除。

根据压力类型读取 `references/experience_analysis_guide.md` 的详细部分：

| 体验压力 | 读取部分 |
|---|---|
| 发现、触发或阻断恢复 | 第 4 节 |
| 操作前、操作中、操作后或终止 | 第 5 节 |
| 信息主次、解释内容和解释时机 | 第 6 节 |
| 节点连续、独立、保留或顺序 | 第 7 节 |
| 状态、结果、中断或异常恢复 | 第 8 节 |
| 跨角色、跨节点或跨系统 | 第 9 节 |
| 复杂规则和数据关系 | 第 10 节 |
| 高风险、批量或不可逆操作 | 第 11 节 |
| 高频任务和重复成本 | 第 12 节 |
| 新功能或规则变化感知 | 第 13 节 |

只读取命中压力所需的详细部分。无法把压力具体到角色、任务、触发或状态时，回到正式输入核对事实；缺少会改变体验方向的业务事实时，停止受影响任务的定案。核心任务因此无法完成时，停止整轮 UXB，并说明缺少什么及其影响。

## Step 2 · 知识校准并形成体验决定

每个体验压力进入本步骤后，按以下顺序执行：

1. 写清需要定案的体验关系。
2. 按 `references/knowledge_usage_guide.md` 第 3、4、8 节判断是否需要业务知识。
3. 需要业务知识时，只读取当前主题的完整相关规则块，不读取整个业务域。
4. 按该指南第 5 节检查对应设计准则和交互模式。
5. 直接选择能够落实的体验方向，形成体验决定。
6. 按该指南第 7 节记录真正影响本条决定的知识来源及作用。

业务知识用于还原既有机制、状态、角色责任、系统边界和业务约束。正式输入明确新增、修改或移除既有能力时，以正式输入为本轮事实。业务知识不能新增或覆盖正式事实。

设计准则和交互模式是每个体验压力形成决定前的必经校准。校准应影响信息关系、节点关系、反馈、恢复、风险说明或操作效率；没有直接模式时，使用通用设计准则继续，不为引用而引用。

### Step 2.1 · 方向比较

默认直接定案。只有两个方向都成立且取舍会改变体验结果时，才读取 `references/experience_analysis_guide.md` 第 14 节和 `references/knowledge_usage_guide.md` 第 6 节，并在内部最多比较两个方向。

方向比较用于选方向，不用于重新判断体验压力是否存在，也不能删除体验压力。没有真实取舍时，不制造备选方向。比较后选定一个方向写入体验决定，不输出比较过程。

### Step 2.2 · 体验决定的最低要求

每条体验决定必须回答：

- 对应哪个角色和用户任务。
- 在什么触发、节点或状态下生效。
- 信息、节点、反馈、恢复或交接关系最终如何处理。
- 这一决定要求后续交互方案保留什么结果。

缺少后会改变结论含义时，补充对象、状态、解释内容、解释时机、上下文或例外。决定应具体到设计师可以据此继续设计，但停在体验关系层，不指定页面、容器、控件、按钮位置和最终文案。

以下内容不能单独作为体验决定：

- 需求事实和业务流程复述。
- “清晰展示”“及时反馈”“体验友好”等没有对象、时机和处理结果的原则口号。
- 没有参照的缺口推断。
- 没有承接对象的上下文传递。

这些限制只排除空结论，不得用来删掉已经识别的体验压力。结论仍不具体时，继续分析该压力，直到能够形成可落实方向，或确认缺少业务事实并按 Step 1 停止。

## Step 3 · 任务覆盖差异复核

完成第一轮体验决定后，读取 `references/experience_analysis_guide.md` 第 15 节。将 Step 1 的任务底表与体验决定逐项对照。

每个任务、生命周期节点和已识别压力只标记一种状态：

1. 已有体验决定覆盖。
2. 有体验压力但尚无决定：回到 Step 2 再扫描一次。
3. 已扫描，当前事实下无需独立体验决定。

复核只负责发现漏项。它不能删除、合并、降级或改写已经形成的体验决定，也不重新判断其重要性。第二次扫描只处理缺口，不重跑全部分析。

任务级复核完成后，再做一次跨任务复核：检查共同入口、状态连续、角色交接、系统衔接、异常恢复和共享约束是否存在单任务内看不到的体验压力。发现缺口时回到 Step 2；没有缺口时进入 Step 4。

只有完成任务级与跨任务复核后，才能得出“本次无需独立体验定案”。复核状态不写入确认视图、Markdown 或 Context。

## Step 4 · 用户确认

候选体验决定形成后，读取 `references/output_structure_guide.md` 的“确认视图”部分。

在聊天中展示本轮候选体验决定。确认视图直接使用准备写入正式 Markdown 的决定编号和决定正文，不建立另一套确认模板，不生成确认文件或确认阶段 Context。

确认后只提供两个动作：

1. 确认并生成正式体验定案。
2. 调整部分体验决定。

用户明确确认后进入 Step 5。

用户提出调整时：

1. 标出受影响的体验决定。
2. 只重新分析受影响内容。
3. 修改会影响其他决定时，一并标出影响范围。
4. 使用更新后的完整决定列表再次确认。
5. 用户同时提出修改时，不视为确认。

用户指出正式输入存在业务错误、冲突或未闭环时，停止 UXB。说明问题和影响，要求先更新正式输入。不要在 UXB 内补业务。

没有体验决定时，展示“本次无需独立体验定案”及对应事实依据。用户确认后再生成最小正式 Markdown。

## Step 5 · 正式 Markdown

用户确认后，读取 `references/output_structure_guide.md` 的“正式 Markdown”部分，生成并冻结：

- `spark-output/uxb_output.md`

正式 Markdown 使用确认视图中的决定编号和决定正文。只补充正式标题、定案范围、必要限定、来源和知识消费记录。不要重新分析、重新选择方向或改写已经确认的语义。

Markdown 是唯一正式语义源。

正式产物不包含：

- 需求摘要和业务事实全集。
- 内部任务覆盖结果。
- 候选体验问题和方向比较过程。
- 任务底表和覆盖复核状态。
- 未确认方向、指标或具体页面方案。
- 为 Context 字段补写的内容。

同一决定只在最合适的位置完整表达一次。跨任务共同约束只写真实新增的适用关系，不重复每条任务决定。

文档底部只记录本轮实际影响体验决定的知识：对应体验决定、知识来源及其对决定的作用。未影响决定的预读材料不写入，不为了填表补充知识。

## Step 6 · Context 投影与校验

只有 `spark-output/uxb_output.md` 已确认并冻结后，才读取 `references/context-schema.md`。

只从冻结 Markdown 投影：

- `spark-output/context/uxb.json`

随后执行：

```text
node <当前 Skill 目录>/scripts/validate-context.js spark-output/context/uxb.json
```

脚本只校验 JSON 结构。Agent 负责核对 Markdown 与 JSON 的语义一致性。

- JSON 投影或结构校验失败：只修 JSON，不修改已冻结 Markdown。
- 发现 Markdown 的体验结论错误：回到 Step 2 更新受影响决定，再经过 Step 3 覆盖复核和 Step 4 确认，随后重新生成 Markdown 和 JSON。
- JSON 不得读取正式输入、知识库、聊天记录或内部覆盖结果补内容。

正式 Markdown 和 Context 均通过验收后，只输出：

```text
体验定案已完成。
```

完成当前 UXB 后停止。不要自动执行或控制其他 Skill。

## 边界与红线

- 不用 UXB 修补不合格输入。
- 不读取原始材料恢复或补写正式事实。
- 不重新判断产品或业务解决方向。
- 不输出多个未定主方向。
- 不以候选准入、重要性评分、字段完整度或唯一方向门槛删除体验压力。
- 不强制为每条体验决定制造多个方向。
- 不让任务覆盖复核删除、合并、降级或改写体验决定。
- 不跳过用户确认。
- 不把体验定案写成具体页面方案。
- 不指定 Tab、Wizard、Steps、弹窗、抽屉、按钮位置或最终文案。
- 不在正式产物中保留业务待确认、候选方案或未选择方向。
- 不要求每个任务机械覆盖全部体验维度。
- 不把单个领域案例写成固定判断分支或通用答案。
- 不为文档简短而删除场景、条件、对象、状态、时机、结果或例外。
- 不建立路径、章节号、行号或固定位置的跨产物语义绑定。
- 不要求下游只读取 UXB 或改变其读取方式。
