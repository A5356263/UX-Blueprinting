# 界面评估检查项与扣分逻辑

本文档以走查表为准，定义界面评估的检查项、涉及判断、问题单元计数、档位扣分、综合评分和置信度。核心目标是把“凭经验感觉扣分”改成“证据 -> 问题单元个数 -> 档位扣分 -> 加权得分”。

## 1. 评分总览

界面走查只使用两个一级维度：

| 一级维度 | 维度权重 | 检查元素 |
| --- | ---: | --- |
| 信息呈现 | 35% | 元素 1-4 |
| 操作体验 | 65% | 元素 5-11 |

计算顺序：

```text
是否涉及 = 涉及填 1，不涉及填 0；证据不足但任务需要时仍按涉及处理
元素内部权重 = 1 / 当前一级维度中涉及元素数量
单题扣分 = 1 / 2^(档位 - 1)
元素扣分 = 问题单元个数 * 单题扣分
元素原始分 = 100 - 元素扣分
元素分 = clamp(元素原始分, 0, 100)
一级维度分 = clamp(sum(元素分 * 元素内部权重) + 调整项分值, 0, 100)
走查总分 = 信息呈现分 * 0.35 + 操作体验分 * 0.65
```

如果当前对象确实只涉及一个一级维度，该维度权重改为 `1.0`，另一个维度权重为 `0`。完整业务界面通常两个一级维度都涉及。

## 2. 检查项

| 元素 | 一级维度 | 目的 | 内容 | 检查元素 |
| --- | --- | --- | --- | --- |
| 1 | 信息呈现 | 看得见 | 你可以找到你需要的信息 | 导航布局、信息结构合理，符合用户场景/业务逻辑，不影响用户的操作效率 |
| 2 | 信息呈现 | 看得懂 | 你明白这个产品/功能是做什么的 | 界面内容清晰传达了产品提供的服务/功能 |
| 3 | 信息呈现 | 看得懂 | 每一个词你都认识，每句话你都理解 | 信息传达有效，没有晦涩难懂的专业名词，没有不必要的中英文混杂；无法通俗化的专业名词能就近找到清晰解释 |
| 4 | 信息呈现 | 看得快 | 你能区分信息主次，快速扫描到关键信息 | 信息层级清晰，主次分明，能快速扫描到关键信息 |
| 5 | 操作体验 | 操作前：可感知 | 你知道哪些是可以操作的，哪些不能操作 | 可操作与不可操作的样式区分明显 |
| 6 | 操作体验 | 操作前：可感知 | 你知道该怎么操作 | 明示用户操作流程进度，明确用户的当前状态和下一步操作 |
| 7 | 操作体验 | 操作时：有提示 | 操作时你立即就有感知 | 操作时有明显的可感知状态或内容变化，指引用户达成目标 |
| 8 | 操作体验 | 操作时：有提示 | 操作顺畅，你没有挫败感 | 操作顺畅，没有干扰、反复尝试和中断；可以自主返回上级或中断流程，流程结束时也给出明确感知 |
| 9 | 操作体验 | 操作时：有提示 | 你能即时获得反馈 | 反馈快速；如果等待时间较长，能让用户感知进度 |
| 10 | 操作体验 | 操作时：有提示 | 报错提示清晰，对你有帮助 | 报错提示能定位错误位置和错误原因，并给予用户建设性帮助 |
| 11 | 操作体验 | 操作后：可撤销 | 允许你犯错，犯错后可纠正 | 有容错设计，区分可逆与不可逆操作，允许用户犯错后撤销或纠正 |

## 3. 涉及判断

使用三种状态记录检查元素：

| 状态 | 表格值 | 是否参与权重 | 使用场景 |
| --- | ---: | --- | --- |
| `applicable` | 1 | 是 | 当前页面/流程需要该能力，且证据足够判断 |
| `evidence_insufficient` | 1 | 是 | 当前任务需要该能力，但截图、DOM 或 runtime 没有展示完整状态 |
| `not_applicable` | 0 | 否 | 当前任务确实不需要该能力 |

规则：

- 证据不足不能当作不涉及。例如提交任务需要成功/失败反馈，但只提供默认态截图时，元素 7、9、10 仍应视为涉及，并降低置信度。
- 不涉及元素权重为 `0`，问题单元个数为 `0`，元素分写 `100`，不参与一级维度均分。
- 涉及元素在所属一级维度内均分权重。若信息呈现 4 个元素都涉及，每个元素权重为 `25%`；若只涉及 2 个，每个为 `50%`。

## 4. 如何客观计问题单元

`problem_count` 不是肉眼看到的瑕疵数量，也不是 issue 条数，而是标准化后的“问题单元”数量。一个问题单元必须是能被证据证明、能归属到检查元素、且会独立增加用户理解或操作成本的最小扣分单位。

一个问题单元用四元组定义：

```text
problem_unit = criterion_id + unit_scope + state_scope + evidence_test
```

字段含义：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `criterion_id` | 失败的客观检查标准 | `E1-03` 布局与任务对象匹配 |
| `unit_scope` | 被评价的最小对象范围 | `component:tbl_orders`、`region:filter_bar`、`flow:edit_customer:error_state` |
| `state_scope` | 证据所在状态 | `default`、`hover`、`loading`、`success`、`error`、`empty` |
| `evidence_test` | 期望与实际证据的比较方式 | “主任务对象与主操作不在同一区域，且无可见连接关系” |

一个问题单元必须同时满足五点：

1. 能引用可定位证据路径，例如 `dsl.pages[0].regions[1]`、`dsl.pages[0].components[3]`、`dsl.interactions[0]` 或 `dsl.uncertain[0]`。
2. 能明确对应到某一个检查元素的检查语句。
3. 能写出期望标准 `expected` 与实际观察 `actual`，且二者存在可验证差距。
4. 与当前用户任务相关；纯审美偏好、品牌风格偏好或无法证明会影响理解的差异不计问题单元。
5. 是独立根因；同一根因在同一元素内只计 1 个问题单元。

问题单元计数不是严重度计数。严重度只用于排序和门禁，不决定单题扣分。

JSON 中只要填写 `problem_count`，就必须同时填写：

```json
{
  "criterion_id": "E1-03",
  "unit_scope": "region:r_main/component:tbl_orders",
  "state_scope": "default",
  "expected": "主任务对象附近应有可见处理入口或可见连接关系。",
  "actual": "截图中异常订单表格可见，但行级处理入口不可见。",
  "evidence_test": "任务对象 tbl_orders 与处理动作不在同一区域，且没有可见的操作列、按钮或链接。"
}
```

### 颗粒度统一规则

用以下规则保持不同评估者的计数一致：

| 场景 | 计数规则 |
| --- | --- |
| 单个组件违反一个标准 | 1 个问题单元 |
| 同一根因在同一元素内影响多个重复项 | 合并为 1 个批量问题单元，`unit_scope` 写模板或区域 |
| 同一根因影响多个检查元素 | 可在不同元素分别计 1 个问题单元，但必须写明不同 `criterion_id` 和不同影响路径 |
| 同一组件在不同状态分别失败 | 每个任务关键状态可计 1 个问题单元，例如 default 和 error 各 1 个 |
| 同一页面多个不同任务对象分别失败 | 每个任务对象可计 1 个问题单元 |
| 截图/DOM 无法证明是否失败 | 不计问题单元，写入 `uncertain`；若任务需要该能力，则元素状态用 `evidence_insufficient` |
| 只有“看起来不好看”但无任务影响 | 不计问题单元 |

禁止计数方式：

- 不按行数、按钮数量、文字数量机械计数，除非每个对象对应不同任务结果。
- 不把同一证据在同一元素下拆成多个同义问题，例如“入口不明显”“入口不好找”“入口弱”只能算 1 个。
- 不用严重度放大 `problem_count`。严重度由 `issues[].severity` 表达。

### 客观检查标准

下面的 `criterion_id` 是问题单元的唯一来源；若问题无法落到这些标准之一，不进入扣分。

| 标准 | 所属元素 | 客观失败条件 | 可接受证据 |
| --- | --- | --- | --- |
| `E1-01` | 看得见 | 当前页面/区域的身份、当前位置或对象范围不可见 | 缺少页面标题、选中导航、面包屑、表格标题、筛选摘要；证据路径指向 `navigation`、`regions`、`components` |
| `E1-02` | 看得见 | 关键入口或关键筛选不在首屏、主区域或任务对象附近，且没有可见引导 | 入口 bbox 不在 viewport；入口在折叠菜单；任务对象和入口不相邻；截图/DOM 可证明 |
| `E1-03` | 看得见 | 布局与业务任务对象不匹配：主任务对象、主操作、状态反馈不在同一任务区域，且无可见连接关系 | region/component 结构显示对象与操作分离；操作列缺失；区域命名与任务不一致 |
| `E1-04` | 看得见 | 关键信息被次要内容挤压：关键对象可见面积、位置或优先级低于次要内容，导致首屏无法定位主要任务 | bbox 面积/位置；首屏主要面积被公告/广告/装饰/次要卡片占用；关键对象不在视觉优先级前列 |
| `E2-01` | 看得懂功能 | 页面或模块标题不能说明服务/功能/任务对象 | 标题为空、泛化为“详情/管理/首页”、只写品牌不写能力 |
| `E2-02` | 看得懂功能 | 用户无法从界面判断操作会得到什么结果 | CTA/说明缺少结果对象；只有“提交/确定/处理”但无处理对象或结果 |
| `E3-01` | 词句理解 | 专业术语、缩写或内部代号无就近解释 | 文案含术语；周边无 tooltip、注释、帮助链接、示例 |
| `E3-02` | 词句理解 | 按钮、标签、提示文案过泛，不能表达动作对象或结果 | “确定/提交/处理/查看”重复出现且无对象；多个相同链接无可区分上下文 |
| `E3-03` | 词句理解 | 同一概念在同一任务中使用不同名称 | 文案中同对象多名称，例如客户/用户/账户混用且无解释 |
| `E4-01` | 看得快 | 缺少标题、分组、排序、状态标签或视觉层级，导致主次不可扫读 | heading 层级缺失；表格无优先列；状态字段不突出 |
| `E4-02` | 看得快 | 关键信息没有优先级标记，用户无法快速判断处理顺序 | 异常/优先级/风险/待办状态不可见或不突出 |
| `E4-03` | 看得快 | 表格/列表字段过多且无冻结、分组、排序或摘要 | `th` 数量多、关键列远离对象列、无排序/筛选状态 |
| `E5-01` | 可操作性 | 可操作、禁用、只读、普通文本样式不可区分 | button/link/text 样式相近；disabled/readonly 无视觉差异 |
| `E5-02` | 可操作性 | 禁用、无权限、不可选状态没有原因或解决方式 | disabled/aria-disabled 存在，但无 title、tooltip、相邻说明 |
| `E5-03` | 可操作性 | 权限或限制在操作前不可见，只能点击后才知道 | runtime 事件显示点击后才报无权限；默认态无权限提示 |
| `E6-01` | 操作指引 | 当前状态、步骤、进度或所处流程不可见 | 多步骤任务无 steps/progress/current 标记 |
| `E6-02` | 操作指引 | 下一步操作不可见、不靠近任务对象或文案不能说明下一步 | 主 CTA 缺失、远离任务区域、或文案无法说明动作结果 |
| `E6-03` | 操作指引 | 必填条件、前置条件、业务规则、依赖关系不可见 | required 字段无说明；提交前规则不可见；依赖字段无提示 |
| `E7-01` | 操作反馈 | 用户操作后没有立即可感知状态变化 | runtime 无 loading/selected/toast/inline feedback；点击后状态不变 |
| `E7-02` | 操作反馈 | 反馈远离触发点或任务对象，用户难以关联 | feedback bbox 与触发组件分离；DOM/截图显示反馈在不相关区域 |
| `E8-01` | 操作顺畅 | 非必要跳转、弹窗、重复确认或重复输入打断任务 | flow/interactions 显示多次确认、跨页绕路、重复填表 |
| `E8-02` | 操作顺畅 | 返回、取消、中断、继续路径不可见 | 流程状态中缺少返回/取消/保存草稿/继续入口 |
| `E8-03` | 操作顺畅 | 流程结束状态不清，用户不知道是否完成或下一步去哪 | success/end state 无结果、记录、下一步入口 |
| `E9-01` | 等待反馈 | 异步等待没有 loading、进度、队列或预计时间 | runtime 或截图显示等待态缺失 |
| `E9-02` | 等待反馈 | 等待时仍可重复提交或误操作 | loading 时按钮未禁用；runtime 出现重复事件 |
| `E9-03` | 等待反馈 | 长任务或后台任务完成后无通知或结果入口 | 无 notification、结果页、状态更新 |
| `E10-01` | 报错帮助 | 错误不能定位到字段、区域或操作对象 | 只有全局错误；字段旁无 inline error；无 aria-invalid |
| `E10-02` | 报错帮助 | 错误不说明原因 | 文案只有“失败/异常/错误”，无原因 |
| `E10-03` | 报错帮助 | 错误不给修正建议、示例、重试或帮助入口 | 无下一步、示例、重试按钮、帮助链接 |
| `E10-04` | 报错帮助 | 修错后已输入信息丢失或需要重新开始 | runtime/flow 证明失败后表单重置、返回后值丢失 |
| `E11-01` | 可撤销 | 高风险或不可逆操作无确认、预览或风险说明 | 删除/支付/审批/提交等无 dialog/summary/confirmation |
| `E11-02` | 可撤销 | 误操作后无撤销、编辑、重试、取消或返回修正入口 | 成功/失败/详情页缺少恢复入口 |
| `E11-03` | 可撤销 | 成功后无结果、记录、凭证、审计或状态更新 | success state 无编号、记录链接、状态变化 |

评估时不得再使用“层级不清晰”“布局不匹配”“关键信息被挤压”这类未展开短语直接扣分。必须改写成上表中的具体 `criterion_id`，并用 `expected`、`actual`、`evidence_test` 证明失败条件。例如：

- 不写“布局与业务对象不匹配”，改写为 `E1-03`：主任务对象、主操作、状态反馈不在同一任务区域，且无可见连接关系。
- 不写“关键信息被次要内容挤压”，改写为 `E1-04`：关键对象可见面积、位置或视觉优先级低于次要内容，导致首屏无法定位主要任务。
- 不写“层级范围不清晰”，先判断是 `E1-01` 当前页面/对象范围不可见，还是 `E4-01` 标题/分组/视觉层级缺失。

重复计数规则：

- 同一按钮文案不清，在元素 3 内只计 1 个问题；如果它同时导致用户不知道下一步，可在元素 6 再计 1 个问题，并说明不同影响路径。
- 同一类轻微问题在多个相同表格行重复出现，默认合并为 1 个批量问题；若分别影响不同关键任务点，可分开计数。
- 行为数据和界面证据指向同一根因时，不重复扣分；行为数据只提高置信度或严重度。

大问题与小问题的处理：

- 小问题通常只形成 1 个问题单元，严重度多为 `Low` 或 `Medium`。
- 大问题如果只破坏一个检查目标，仍只形成 1 个问题单元，但用 `High` 或 `Critical` 影响 gate。
- 大问题如果同时破坏多个检查目标，可以在不同元素下分别计问题单元。例如“没有行级处理入口”可能同时影响元素 1 看得见、元素 5 可操作性、元素 6 下一步明确性和元素 8 操作顺畅。
- `Critical` 不靠增加扣分表达严重性，而是直接触发 `fail`；`High` 至少触发 `review`，避免高风险问题被高总分掩盖。

## 5. 档位扣分

档位由本次走查范围大小决定，默认整份报告使用同一档位。范围越大，单个问题对总分的影响越小。

| 档位 | 适用范围 | 单题扣分 |
| ---: | --- | ---: |
| 1 | 单组件、单状态、局部截图 | 1 |
| 2 | 一个小面板、弹窗、表单片段 | 0.5 |
| 3 | 一个完整页面的主任务区域 | 0.25 |
| 4 | 一个完整页面，包含多个区域和状态 | 0.125 |
| 5 | 多页面或多状态任务流程 | 0.0625 |
| 6 | 复杂产品、批量页面、跨流程评估 | 0.03125 |

### 档位逻辑审计

这套档位的本质是“范围归一化”：评估范围越大，同一个问题单元对单个元素分的影响越小。它能避免大范围批量走查被少量问题拉得过低，但也有明显风险。

优点：

- 与截图表一致，计算透明，人工和脚本都容易复核。
- 支持不同评估范围，局部走查用高敏感度，大范围走查用低敏感度。
- 可以把严重度从算术扣分里拆出来，严重问题由 gate 处理。

主要风险：

- **高档位过度稀释**：6 档每个问题只扣 `0.03125`，即 32 个问题才扣 1 分，容易让大范围报告虚高。
- **双重稀释**：评估范围越大，问题被合并得越多，同时单题扣分又变小，可能低估真实清晰度风险。
- **跨报告不可比**：同一界面若一次用 1 档、一次用 4 档，分数不可直接比较。
- **问题单元主观性仍存在**：如果没有统一拆分规则，评估者仍可能把一个复杂根因拆成 1 个或 10 个问题单元。
- **严重度不进算式**：大问题和小问题单题扣分相同，必须依赖 `High/Critical` gate 防止误判。

使用约束：

- 同一个改版前后对比必须使用同一档位。
- 单页面界面评估默认不应高于 3 档；多状态完整页面默认不应高于 4 档。
- 5-6 档只用于批量巡检或产品级抽样，不适合输出精细界面得分。
- 选择 4-6 档时必须在报告中写明 `scale_rationale`，解释为什么不使用更敏感档位。
- 若总问题单元很多但扣分很少，应在“不确定项/复核项”里提示“高档位稀释风险”。

公式：

```text
points_per_problem = 1 / 2^(scale_level - 1)
deduction_points = problem_count * points_per_problem
raw_element_score = 100 - deduction_points + adjustment
element_score = clamp(raw_element_score, 0, 100)
```

JSON 记录方式：

```json
{
  "issue_id": "iss_1",
  "problem_count": 6,
  "scale_level": 1,
  "points_per_problem": 1,
  "points": 6,
  "reason": "表格字段主次不清，影响快速扫读。"
}
```

若一个元素下有多类独立问题，可以写多条 `deductions[]`；元素扣分等于这些 `points` 之和。`points` 必须是正数，人工表里写“扣 -6 分”时，JSON 写 `"points": 6`。

## 6. 0 分与负分处理

实际输出分数永远限制在 `0-100`：

```text
raw_element_score = 100 - sum(points) + adjustment
element_score = clamp(raw_element_score, 0, 100)
```

因此不会出现负分。若 `raw_element_score < 0`，报告中的元素分显示为 `0`，并说明“触发 0 分下限”。这不影响评估有效性，前提是：

- 每个问题单元都有可定位证据。
- 问题单元没有把同一根因在同一元素内重复计算。
- 档位选择符合评估范围。
- 置信度没有被写成高于证据实际覆盖程度。

0 分代表该检查元素在当前证据和任务下基本失效；它不是报告无效。报告无效只发生在没有足够界面证据、没有任何涉及维度、证据路径不可定位、或关键结论主要依赖假设时。

## 7. 调整项

调整项用于截图表中的“调整项分值”，默认只放在一级维度上：

```text
一级维度分 = clamp(sum(元素分 * 元素内部权重) + 调整项分值, 0, 100)
```

使用规则：

- 没有明确证据时，调整项填 `0`。
- 调整项可正可负，必须写 `adjustment_reason` 和 `adjustment_evidence`。
- 单个一级维度调整项建议控制在 `-10` 到 `+10`。
- 调整项不能抵消阻塞核心任务、不可逆风险无确认、错误无恢复等关键问题。

## 8. UCATS 清晰度映射

界面走查分只对应 UCATS 的 `clarity`。11 个检查元素都只能作为清晰度证据，不能映射到 `usability`、`task_completion`、`acceptance` 或 `stability`。

```text
ucats.dimensions.clarity.score = ucats.walkthrough.overall_score
```

原因：

- 当前检查项评估的是界面信息是否看得见、看得懂、看得快，以及操作线索是否表达清楚。
- 这些检查项可以证明“界面表达是否清晰”，不能证明真实易用性、真实任务完成率、真实接受度或系统稳定性。
- 非清晰度维度必须来自独立产品/行为证据，例如完成率、完成时长、重复点击、活跃率、满意度、错误率、性能或工单数据。

五维 UCATS 综合分只有在五个维度都有独立证据时才输出：

```text
UCATS 综合分 = usability*0.20 + clarity*0.20 + task_completion*0.25 + acceptance*0.15 + stability*0.20
```

如果只有界面证据：

- 输出 `clarity_score` 和 `ucats.dimensions.clarity`。
- 不输出完整 `ucats.overall_score`，或写为 `null`。
- 报告文案写“UCATS 清晰度得分”，不能写成完整 UCATS 综合得分。

非清晰度维度的证据要求：

| UCATS 维度 | 可接受证据 | 不可接受证据 |
| --- | --- | --- |
| `usability` | 页面满意度、问题处理时长、无效点击、重复点击、操作耗时 | 仅凭按钮样式、布局、文案 |
| `task_completion` | 任务完成率、完成时长、漏斗流失、访问深度 | 仅凭是否有 CTA 或反馈文案 |
| `acceptance` | PV/UV、活跃率、核心功能使用率、留存或调研 | 仅凭视觉专业感或信任文案 |
| `stability` | 性能指标、错误率、崩溃率、接口失败、工单 | 仅凭截图中有 loading 或错误提示 |

## 9. 置信度

置信度表示“这次评分证据是否足够”，不是界面好坏。

建议计算一个内部置信度指数：

```text
confidence_index =
  source_strength * 0.35 +
  state_coverage * 0.30 +
  traceability * 0.25 +
  context_clarity * 0.10
```

取值规则：

| 因子 | 评分方式 |
| --- | --- |
| `source_strength` | mixed 且清晰为 1；DOM/A11Y/runtime 充分为 0.9；清晰单截图为 0.75；裁切/低清截图为 0.55 |
| `state_coverage` | 关键默认态、操作中、成功、失败、空态等已覆盖比例 |
| `traceability` | 有可定位 evidence 路径的问题和评分占比 |
| `context_clarity` | 目标用户、任务、对象、预期结果是否明确 |

映射：

| 置信度 | 条件 |
| --- | --- |
| `high` | `confidence_index >= 0.80`，关键状态完整，证据直接支撑评分 |
| `medium` | `0.55 <= confidence_index < 0.80`，部分状态或上下文缺失 |
| `low` | `< 0.55`，关键状态不可见、文本不可读或结论主要依赖假设 |

证据不足时只能根据可见证据评分，把缺失项写入 `dsl.uncertain[]`，并降低相关维度置信度。

## 10. 门禁

门禁不改变分数，只改变结论：

- `fail`：清晰度分或完整 UCATS 综合分 `<65`，或存在 `Critical`，或已评估的 `task_completion.confidence == low`。
- `review`：清晰度分或完整 UCATS 综合分 `<80`，或存在 `High`，或任一已评估 UCATS 维度置信度为 `medium`。
- `pass`：不触发以上条件。
