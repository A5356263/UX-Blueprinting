# 示例

## 行内 Browser Mode 评估提示

上游系统提供 DOM、Accessibility Tree、runtime 事件和任务上下文：

> user: 运营管理员
> task: 审核异常订单并提交处理结果
> interface_capabilities: 搜索、筛选、查看异常原因、提交处理结果、查看错误反馈
> expected_result: 异常订单被成功处理并展示确认状态

预期行为：

1. 执行 `DOM/Accessibility/runtime + 提示词上下文 -> 自动生成 Page DSL`。
2. 将 `user`、`task`、`interface_capabilities`、`expected_result` 写入 `task_context`。
3. 对不可由结构化证据证明的视觉判断标记为 `uncertain` 或降低置信度。
4. 输出 `input.type = "browser"` 的规范 JSON，并使用 `source_refs` 指向 DOM/A11Y/runtime 来源。

## 单截图评估提示

用户提供一张后台看板截图并说：

> 评估这个后台首页的可用性，输出 JSON。
> user: 运营管理员
> task: 发现异常订单并处理
> interface_capabilities: 查看异常订单、筛选、导出、处理异常
> expected_result: 异常订单被定位并完成处理

预期行为：

1. 执行 `截图 + 提示词上下文 -> 自动生成 Page DSL`。
2. 将提示词上下文写入 `task_context`，但只有截图可见的控件才写入 `components`。
3. 将未知流程和隐藏状态标记为 `uncertain`。
4. 只输出 UCATS 清晰度评分；不要把界面检查项映射到其他 UCATS 维度。
5. 输出规范 JSON；如果已保存到磁盘，则执行校验。

## 多截图流程提示

用户提供 `01-list.png`、`02-edit-drawer.png`、`03-error.png` 并说：

> 评估编辑客户信息这条流程，重点看界面表达是否清楚，错误恢复相关内容只作为清晰度证据。

预期行为：

1. 为每张截图构建 Page DSL。
2. 基于可见顺序构建 Flow DSL。
3. 为错误状态构建 Interaction DSL。
4. 更严格地检查下一步、反馈、报错和恢复说明是否清楚，但分数仍只写入 UCATS clarity。

## 改版前后提示

用户提供两张截图并说：

> 比较改版前后哪个更好。

预期行为：

1. 独立评估改版前与改版后的截图。
2. 对比维度分差与问题数量变化。
3. 如果截图上下文或顺序不确定，不要声称体验改进。

## 完整业务首页截图案例

用户提供一张已渲染的企业门户首页截图，并要求“直接界面评估”。

预期行为：

1. 将案例归类为 `screenshot` 主输入和“完整业务界面”，不是固定的首页模板。
2. 从截图中抽取导航、公告、内容模块、应用入口、列表信息、反馈状态和视觉层级。
3. 结合提示词上下文生成 Page DSL；若用户没有说明目标用户和任务，应把任务目标标记为 `uncertain`，不能默认所有模块都同等重要。
4. 可以评估信息架构、模块主次、入口可发现性、文案理解、扫读效率、可操作状态和反馈显著性。
5. 不声称真实点击率、PV/UV、完成率、完成时长或满意度；除非用户另行提供行为数据。

## `view-source`/SPA 壳层源码案例

用户提供保存下来的 `view-source` HTML 或只有根节点、loading、脚本引用的 SPA 初始 HTML，并要求界面评估。

预期行为：

1. 将案例归类为 `browser` 证据下的“壳层/源码/加载页”，不是完整业务界面。
2. 只评估源码可证明的内容：页面标题、根节点、加载提示、无脚本兜底、鉴权跳转、资源失败风险、可访问性占位和失败恢复。
3. 不评价未渲染出的业务导航、资讯模块、任务入口、首页视觉层级或具体业务流程。
4. 若用户需要完整门户评估，应要求提供渲染后 DOM/A11Y/runtime 或截图。
5. 输出 JSON 时，`input.type` 仍为 `browser`；`dsl.pages[].source.mode` 与 `generation.method` 必须匹配 browser 规则。

## 行为数据补充案例

用户提供核心任务完成率低、完成时长高或重复点击高，并同时提供页面截图或 DOM。

预期行为：

1. 主输入仍归类为 `browser`、`screenshot` 或 `mixed`，行为数据写入 `input.behavior_metrics`。
2. 先校验指标口径、样本、时间范围、基准线和异常点。
3. 将行为异常关联到页面、任务、步骤、组件事件或提示信息来源。
4. 若界面证据和行为数据指向同一根因，不重复扣分；界面证据用于 clarity，行为数据可单独支撑非清晰度 UCATS 维度。
5. 若只有行为数据，没有界面证据，只输出产品级定位方向，不生成本 skill 的规范界面 JSON。
