# Intent Model（需求解析）

由 agent 手工构造，不需要脚本。目的：在匹配任何资产之前，先把"这个页面要解决什么问题"说清楚。

## 输出字段

| 字段 | 说明 | 正例 | 反例 |
|------|------|------|------|
| `page_goal` | 页面要完成什么任务（一句话） | "采购员查看合同详情并决定是否发起变更" | "展示合同详情"（只说展示不说目的） |
| `business_object` | 业务对象 | 采购合同、报销单、药品、员工档案 | 单据、数据（太泛） |
| `user_role` | 当前查看者角色 | 采购员、部门主管、财务审批人 | 用户、管理员（太泛） |
| `object_status` | 单据/对象当前状态 | 待审批、已驳回、履行中、已归档 | 正常（无信息量） |
| `primary_actions` | 用户最可能做的 1-2 个主要操作 | 发起变更、审批通过 | 查看、返回（太弱，不是"行动"） |
| `secondary_actions` | 次要操作 | 导出 PDF、查看操作记录、复制 | — |
| `data_groups` | 信息自然分组（按业务语义） | 合同基本信息、付款条款、履约记录、附件 | 基本信息、其他信息（分组无意义） |
| `interaction_needs` | 所需的交互形态 | 弹窗确认变更原因、抽屉查看关联采购单、审批流状态更新 | 弹窗、抽屉（只有形态没内容） |

## 自检清单

构造完成后逐项确认：

1. **替换业务对象测试**：把 business_object 换成另一个（如"合同"→"员工档案"），data_groups 和 primary_actions 是否需要大幅调整？不需要 → Intent 太泛，重新构造。
2. **角色差异测试**：同一个业务对象，换一个角色（如"采购员"→"财务审批人"），page_goal 是否变了？不变 → 没有真正理解角色。
3. **状态差异测试**：同一个业务对象，换一个状态（如"待审批"→"已归档"），interaction_needs 是否变了？不变 → 没有真正理解状态。
