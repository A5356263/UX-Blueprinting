Operation Record Module 操作记录模块

操作记录模块用于展示详情对象的修改历史、操作日志、变更记录或审计记录。 它是详情页的可选公共模块，适用于基础详情、表格详情、左右布局和上下布局。

适用场景

当业务对象存在修改历史、操作审计、字段变更、状态变更、审批操作、系统操作或人工操作记录时使用。 常见于合同详情、商品详情、报账详情、付款详情、审批详情、配置详情、主数据详情等页面。

展示变体

操作记录摘要表格

当操作信息较多、每条记录存在较多变更字段，或变更详情不适合直接全部展示时， 使用摘要表格展示操作人、操作时间和详情入口。

结构顺序
  1. 操作人或修改人
  2. 操作时间或修改时间
  3. 操作详情入口
推荐列
  • 修改人
  • 修改时间
  • 修改详情
交互规则
  • 当单条操作记录包含较多字段变更时，修改详情列展示“详情”链接。
  • 点击“详情”后，可打开弹窗、抽屉或展开区域展示本次修改的详细内容。
  • 详情入口应使用弱操作样式，避免与页面主操作混淆。
  • 如果详情页已有右侧抽屉体系，优先使用 Drawer 展示操作详情。
  • 如果详情内容较少，也可以使用 Modal 展示。
结构示例
修改人 修改时间 修改详情
张三 2024-12-22 22:22:00 详情
张三三 2024-12-10 10:00:02 详情
校验规则
  • 摘要表格必须包含操作人或修改人。
  • 摘要表格必须包含操作时间或修改时间。
  • 当存在多字段变更时，必须提供详情入口。
  • 详情入口文案建议使用“详情”，不建议使用过长操作文案。
常见错误
  • 不要把大量字段变更直接堆在摘要表格中，导致行高过大。
  • 不要只有“详情”入口，却没有可展示的明细内容。
  • 不要把“详情”做成主按钮样式。
  • 不要缺少修改时间，导致记录无法排序和追溯。
操作记录详情表格

操作记录详情表格用于展示一次操作中的具体变更内容。 它通常由摘要表格中的“详情”入口触发，也可以在操作记录分组中直接展开展示。

结构顺序
  1. 修改模块
  2. 原信息
  3. 修改后信息
  4. 修改人
  5. 修改时间
推荐列
  • 修改模块
  • 原信息
  • 修改后信息
  • 修改人
  • 修改时间
布局规则
  • 操作记录详情表格应独占整行，不应压缩在描述列表的 value 单元格中。
  • 如果放在左右布局详情中，应位于左侧主内容区，不放入右侧审批流区域。
  • 如果字段变更内容较长，原信息和修改后信息列应允许换行展示。
  • 如果修改记录较多，可支持分页或按时间倒序展示。
结构示例
修改模块 原信息 修改后信息 修改人 修改时间
基础信息 药品种类：中药 药品种类：西药 张西西 2023-12-12 22:22
基础信息 单价是否含税：是 单价是否含税：否 张西西 2023-12-12 22:22
商品明细-行号1 单价：¥293.23 单价：¥293.23 张西西 2023-12-12 22:22
关联发票 发票号码：200047843323 发票号码：200047840909 王大大 2023-12-12 22:22
校验规则
  • 必须展示修改模块，便于定位变更发生在哪个业务区域。
  • 必须展示原信息和修改后信息，便于对比。
  • 必须展示修改人和修改时间，便于审计追溯。
  • 原信息和修改后信息应保持同一字段语义，不应出现前后字段不对应。
常见错误
  • 不要只展示修改后信息而缺少原信息。
  • 不要只展示修改内容而缺少修改人和修改时间。
  • 不要把多个字段变更合并成一段难以比较的长文本。
  • 不要让原信息和修改后信息列语义不一致。
单点操作记录行

当一次操作信息较少，只有单点操作、单字段变更或简单状态变更时， 可以直接在表格中单行展示，不必再提供“详情”入口。

结构顺序
  1. 操作模块或操作类型
  2. 操作内容
  3. 操作人
  4. 操作时间
交互规则
  • 单点操作记录可以直接单行展示。
  • 如果操作内容已经完整表达，不需要提供“详情”链接。
  • 如果后续扩展为多字段变更，应切换为“操作记录摘要表格 + 详情入口”模式。
校验规则
  • 单行记录必须能完整表达本次操作的对象、内容、操作人和操作时间。
  • 如果单行内容过长，应考虑进入详情展示模式。
  • 单点操作不应强行生成空的详情入口。
常见错误
  • 不要每一条单点操作都强制生成“详情”链接。
  • 不要把复杂多字段变更压缩成单行展示。
  • 不要缺少操作人或操作时间。

放置规则

  • 操作记录可以作为详情页的独立分组展示。
  • 上下布局中，操作记录通常放在基础信息、业务信息、关联明细之后。
  • 左右布局中，操作记录可以放在左侧主内容区底部，也可以作为右侧辅助信息，但不应与审批流混淆。
  • 如果操作记录是审计性质，建议放在页面后部。
  • 如果操作记录与审批流强相关，可以靠近审批流展示，但仍需保持模块边界。

组件组合

  • Table 表格
  • Typography 排版
  • Button 或 Text Button 文本按钮
  • Drawer 抽屉，可用于展示操作详情
  • Modal 弹窗，可用于展示轻量操作详情
  • Pagination 分页，可用于大量操作记录
  • Tag 标签，可用于标识操作类型或操作状态

Token 规则（继承 data-table 标准）

操作记录表格（.op-log-table）继承 data-table 组件全部规范：

  • 表头文字：color 95% #132240（--color-text-neutral-gray50），font-size 14px（--font-size-regular），font-weight bold。
  • 表格正文：color 85% #132240（--color-text-neutral-gray40），font-size 14px（--font-size-regular）。
  • 行高：固定 40px（height: 40px），padding 左右 16px（--spacing-4）。
  • 边框：四边 1px 实线 + 圆角 6px（border-collapse: separate + border-spacing: 0 + border-radius: --border-radius-regular）。
  • 溢出：white-space: nowrap + overflow: hidden + text-overflow: ellipsis。
  • 操作内容列额外限制 max-width: 360px 并用 .op-log-content 承载省略。

全局校验规则

  • 操作记录模块不是详情页必需模块，应根据业务需求展示。
  • 当存在操作记录时，必须至少展示操作人和操作时间。
  • 当一条操作记录包含多项变更时，应提供详情入口。
  • 当一条操作记录只是单点操作时，可以单行展示，不需要详情入口。
  • 操作详情中必须能体现原信息与修改后信息的对比。
  • 操作记录应按时间倒序或业务指定顺序排列。
