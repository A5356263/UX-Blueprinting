# PRD Review 输出结构

## 1. 双路径产物关系

```text
完整审查
→ 零阻断：直接生成正式需求基线
→ 存在阻断：生成问题单并停止
                  ↓
              产品回复
                  ↓
              全部关闭后生成正式需求基线
```

问题单和需求基线不能在存在阻断时同时生成。

## 2. 阻断问题单

### 2.1 输出路径

- `spark-output/prd_review_questions.md`

### 2.2 生成条件

只在 `SKILL.md` 的 P8 已经确定需要生成问题单或审核记录时写入。本文件不得自行判断是否存在阻断或建议，也不得在 P8 前提前输出。

### 2.3 文档状态

- 存在未关闭问题：`waiting_response`
- 全部问题关闭：`closed`
- 没有阻断问题，只有建议：`no_confirmation_required`

### 2.4 固定结构

```markdown
# 需要和产品确认的问题

- 项目：{项目名}
- 状态：waiting_response
- 审查输入：{PRD 文件名或需求标识}

## 需要产品确认

### 场景一：{角色 + 触发 + 任务}

场景：{一句话说明任务从哪里开始、要完成什么}

#### 谁来做、能做什么

##### Q-001【待确认】{问题主题}
- 为什么需要确认：{直接影响的业务结果或任务闭环}
- 需要确认：
  1. {只要求一个业务决定的短问题}
- 产品回复：
  1. 待回复
- 关闭状态：
  1. open
- 问题组状态：unresolved

#### 任务怎么完成

#### 规则和状态怎么处理

#### 异常时怎么办

### 跨场景规则

## 建议新增

### 场景：{对应任务场景}

- S-A-001：{基于唯一事实需要补入的内容}
- 依据：{PRD、正式知识或产品回复}

## 建议修改

### 场景：{对应任务场景}

- S-M-001：{基于唯一事实需要修正的内容}
- 依据：{PRD、正式知识或产品回复}
```

没有问题的分组不要输出空标题。

只有建议新增或建议修改时：

- 文档标题改为 `# PRD 审核记录`。
- 状态写 `no_confirmation_required`。
- 不输出“需要产品确认”标题。
- 记录建议后继续生成需求基线。
- 不等待产品回复。

存在阻断问题时，建议项可以写入同一文件，但不参与关闭状态。

### 2.5 分组规则

- 第一层按处理类型排列：需要产品确认、建议新增、建议修改。
- 第二层按用户实际任务场景排列。
- 场景标题必须包含角色、触发和任务。
- 场景说明只写一句。
- 待确认问题在场景内按“谁来做、能做什么”“任务怎么完成”“规则和状态怎么处理”“异常时怎么办”归类。
- 没有问题的类别不得输出空标题。
- 一个问题只放在一个场景。
- 同一问题影响多个场景且无法归属单一节点时，放入“跨场景规则”。
- “跨场景规则”为空时不输出。
- 禁止按 Agent 的审查步骤分组。

### 2.6 问题编号

- 使用 `Q-001`、`Q-002` 顺序编号。
- 同一份问题文件内编号唯一。
- 回复更新时不得重排或复用编号。
- 新产生的阻断问题追加新编号。
- 不因分组变化修改旧编号。
- 问题组内的列表项按首次出现顺序编号。
- 回复更新时不得重排、合并或复用列表项序号。
- 新增待确认项追加在原列表末尾。
- 原子项是否拆分只按 `review_rules.md` 第 3.8 节判断。本文件只规定编号和展示顺序。
- 一个已确定的原子项对应一条产品回复和一个关闭状态。
- 建议新增使用 `S-A-001`、`S-A-002` 顺序编号。
- 建议修改使用 `S-M-001`、`S-M-002` 顺序编号。
- 建议编号不参与问题关闭状态。

## 3. 三类处理标签

三类处理的语义和硬分界只按 `review_rules.md` 第 15 节判断。本节只规定标签写法。

### 3.1 待确认

语义结论为“待确认”时，按以下格式写：

```markdown
### Q-001【待确认】同号订单重新推送
- 问题：作废后重新推送的订单与旧记录关系未定义。
- 为什么需要确认：无法确定新旧订单的数据与审计关系。
- 需要确认：
  1. 重新推送后，新旧记录按什么关系保存？
- 产品回复：
  1. 待回复
- 关闭状态：
  1. open
- 问题组状态：unresolved
```

没有正式来源证明有限选项时，不要自行列举候选答案。

### 3.2 建议修改

语义结论为“建议修改”时，按以下格式写：

```markdown
## 建议修改

### 场景：管理员关闭权限申请模式

- S-M-001：将“等待管理员启用”修正为“审批通过后立即生效”。
- 依据：PRD 已明确审批通过后立即生效。
```

### 3.3 建议新增

语义结论为“建议新增”时，按以下格式写：

```markdown
## 建议新增

### 场景：管理员关闭权限申请模式

- S-A-001：补充“关闭后，处理中申请统一进入已拒绝结果”。
- 依据：PRD 的关闭规则已经明确该结果。
```

## 4. 问题写作规则

一个问题组只处理一个业务主题。

每个列表项只处理一个能够由同一条回复完整确认、内部不能独立变化的最小业务结论。

必须做到：

- 使用短句。
- 先写问题，再写直接影响。
- 同主题多个决定使用有序列表。
- 提问必须可以被明确回答。
- 列表项保持稳定顺序。

禁止：

- 输出完整推理过程。
- 重复大段 PRD 原文。
- 输出知识路由过程。
- 输出没有唯一事实依据的建议。
- 输出体验机会。
- 输出竞品、指标或页面方案。
- 使用“建议产品完善一下”等笼统表达。
- 为凑数量制造理论问题。

## 5. 有限选项

是否允许列出有限选项只按 `review_rules.md` 第 16 节判断。

已判定允许列出时，格式必须满足：

- 保持原始业务含义。
- 标明选项依据。
- 不推荐其中一项。

## 6. 产品回复记录

设计师可以在聊天窗口按编号提供产品回复：

```text
Q-001：
1. ……
2. ……

Q-002：
1. ……
```

第二次运行更新同一问题文件：

```markdown
### Q-001【待确认】{问题主题}
- 问题：……
- 为什么需要确认：……
- 需要确认：
  1. ……
  2. ……
- 产品回复：
  1. {保留第 1 项原始回复}
  2. 待回复
- 关闭状态：
  1. closed
  2. open
- 关闭依据：
  1. 产品明确确认
  2. 待确认
- 问题组状态：unresolved
```

记录规则：

- `S-A-` 和 `S-M-` 项不接收回复，不参与关闭状态。
- 保留原问题，不删除、不改写、不覆盖。
- 保留产品回复原意，不替产品润色成新决定。
- 以正式知识、本期范围或不适用证据关闭时，保留已有产品原话；没有产品回复时写“未回复”，不得伪造回复。
- 每个列表项分别记录回复和状态。
- 按 `review_rules.md` 第 17 节已经确定的结论填写 `open`、`closed`、关闭依据和问题组状态。本文件不得重新判断。
- 全部关闭后，文档标题改为“需求确认记录”，原 `【待确认】` 标签改为 `【已关闭】`。
- 不建立独立回复文件或问题版本系统。

复核发现正式问题本身不成立时，从问题集合中移出，并在文档末尾增加：

```markdown
## 问题移出记录

- 原编号：Q-001
- 移出依据：{问题为何不成立}
- 证据来源：{PRD 或正式知识位置}
```

问题移出记录不使用 `open` 或 `closed`，不参与整体关闭状态，也不生成需求事实。

围绕基座内部细节产生的问题已经按正式规则判定移出时，记录格式为：

- 移出依据只写“该规则由基座内部承接，本需求不定义”。
- 证据来源必须能够定位正式知识和当前业务边界。
- 不写“本期已启用”。
- 不写“本期继承某项具体策略”。

## 7. 回复复核规则

回复是否关闭、是否产生新候选问题以及何时严格停止，只按 `review_rules.md` 第 17 节判断。

本文件只负责把已经确定的复核结果写入第 6 节定义的位置。完成记录后返回 `SKILL.md` 的 P9 门禁。

## 8. 正式需求基线结构

### 8.1 输出路径

- `spark-output/requirements_baseline.md`
- `spark-output/context/requirements-baseline.json`

### 8.2 生成门禁

只有 `SKILL.md` 的 P10 基线门禁已经通过时才生成。本文件不重新判断阻断项、问题关闭或事实来源是否有效。

不能生成“待确认版”“草稿版”或带假设的需求基线。

### 8.3 Markdown 固定结构

```markdown
# 正式需求基线

## §0 基线状态与来源

## §1 本期目标和范围

## §2 业务对象

## §3 谁来做、能做什么

## §4 任务与完成结果

## §5 业务规则

## §6 状态变化

## §7 异常情况与处理结果

## §8 数据与系统影响

## §9 限制与本期不做

## §10 完成标准

## §11 来源追溯
```

不适用的章节保留标题，并明确写“本期无”或“不适用”。不得静默省略。

### 8.4 §0 基线状态与来源

必须包含：

- 项目名。
- 基线状态：`formal`。
- 基线生成路径：零阻断直接生成，或产品回复关闭后生成。
- 原始 PRD 文件名或需求标识。
- 审核文件路径；没有生成审核文件时写“不适用”。
- 纳入基线的产品回复编号；零阻断时写“不适用”。
- 正式知识来源清单。

### 8.5 §1 本期目标和范围

写清：

- 要解决的业务问题。
- 本期业务目标。
- 本期包含范围。
- 本期不包含范围。
- 业务成功结果。

不写体验目标、UX 指标或方案价值判断。

### 8.6 §2 业务对象

写清：

- 核心业务对象。
- 对象之间的关系。
- 对象进入本期能力的条件。
- 对象不进入本期能力的条件。
- 新增、修改、移除的对象事实。

### 8.7 §3 谁来做、能做什么

每个角色写清：

- 角色名称。
- 角色责任。
- 可执行动作。
- 权限前提。
- 数据或业务范围。
- 不允许执行的动作。

没有独立权限要求时，明确写“沿用现有权限”，并给出正式来源。

### 8.8 §4 任务与完成结果

按需求任务组织，包括用户任务和系统任务，不按页面组织。每项任务写清：

- 功能编号。
- 执行角色。
- 需求发生事件。
- 业务触发条件。
- 本期支持的进入渠道。
- 前置条件。
- 主任务步骤。
- 成功结果。
- 失败或拒绝结果。
- 下一业务节点或明确终态。

“本期支持的进入渠道”只在 PRD、正式知识、现有系统或产品回复能够唯一证明时写入。

正式来源已经证明现有任务位置或页面载体时，再补充：

- 现有任务位置。
- 现有页面或载体。
- 现有入口。

这些内容只记录现状事实。

不得补写 Agent 推测的页面、菜单、布局、组件或字段方案。

没有正式来源时省略，不写“待确认”或占位值。

以下表达不得写入正式需求基线：

- 进入申请入口。
- 进入配置入口。
- 进入相关页面。
- 使用系统入口。
- 按现有方式进入。
- 从对应模块发起。

这些表达无法证明任务从哪里开始，只是占位语。

不得设计新的页面布局、组件、交互载体或视觉样式。

### 8.9 §5 业务规则

每条规则写清：

- 规则编号。
- 适用对象。
- 触发条件。
- 判断条件。
- 业务结果。
- 优先级或互斥关系；不适用时省略。
- 来源。

规则只表达业务决定，不表达体验策略。

### 8.10 §6 状态变化

按业务对象分别描述：

- 状态名称。
- 状态含义。
- 进入条件。
- 允许动作。
- 禁止动作。
- 下一状态。
- 不可逆性；不适用时写“否”。

状态名称沿用已确认业务用语，不创造近义状态。

### 8.11 §7 异常情况与处理结果

每项写清：

- 触发场景。
- 业务判定。
- 对用户任务的结果。
- 对对象状态的结果。
- 是否允许重试或恢复。
- 后续处理责任方；有明确责任方时填写。

只定义业务结果。不设计错误提示、弹窗或恢复交互。

### 8.12 §8 数据与系统影响

按适用范围写清：

- 新增、修改、移除的数据事实。
- 上下游系统影响。
- 同步、重复、并发和失败处理。
- 操作人、时间、原因等审计事实。
- 历史数据处理。

### 8.13 §9 限制与本期不做

只记录已由 PRD、正式知识或产品回复确认的：

- 业务约束。
- 技术或外部依赖约束。
- 本期明确不做。
- 后续考虑但本期不承诺的内容。

不得把 Agent 建议写成约束。

### 8.14 §10 完成标准

产品不需要单独编写完成标准。

PRD Review 只把已确认业务事实改写为完成标准。

每条完成标准必须包含：

- 对应目标、任务、规则、状态或异常。
- 前提。
- 用户或系统动作。
- 可观察结果。

完成标准至少覆盖：

- 每个主要任务的成功结果。
- 会阻断主任务的关键拒绝结果。
- 核心状态变化。

不得增加：

- 新规则。
- 新阈值。
- 新范围。
- 技术实现方式。
- 页面布局。
- Agent 建议。

不得使用“体验良好”“操作顺畅”等不可直接判定的表述。

### 8.15 §11 来源追溯

至少包含：

- PRD 来源。
- 正式知识来源。
- 产品回复来源。

产品回复使用问题编号追溯。不得只写“产品已确认”。

每条业务事实都必须能够定位到上述一种来源。只有章节级来源、无法对应具体事实时，不得视为追溯完成。

### 8.16 事实合并规则

基线内容按以下优先关系整理：

1. 产品明确回复用于关闭对应阻断问题。
2. PRD 定义本期目标状态。
3. 正式知识补充未被本期改变的当前事实。

发生冲突时：

- 产品回复只能覆盖其明确回答的范围。
- PRD 明确新增、修改、移除的目标事实，不得被旧知识覆盖。
- 未被产品回复关闭的冲突不得进入基线。
- Agent 不得用推理补写缺失事实。

每条事实写入前依次检查：

事实来源是否有效只按 `review_rules.md` 第 3.2 节判断；成熟基座事实是否能够写入只按 `knowledge_usage_guide.md` 第 10 节判断。本文件只将已通过判断的事实按上述优先关系整理，不重新执行语义门禁。

### 8.17 基线文案规则

- 使用确定语气。
- 一条只表达一个业务事实。
- 并列事实使用无序列表。
- 有执行顺序时使用有序列表。
- 使用稳定编号引用功能、规则和问题。
- 不复制问题讨论过程。
- 不保留“建议”“可能”“待确认”等讨论语气。
- 不写下一步推荐。
- 不写 UXB 或体验蓝图结论。

## 9. 来源追溯

问题单与基线的依据只允许来自：

- PRD 原文位置。
- 正式知识文件与章节。
- 已存在的问题编号和产品回复。

来源可以简写，但必须可定位。

## 10. Handoff 建议格式

### 10.1 生成前提

只有正式需求基线生成后，才给出下一步建议。

主链始终展示：

- `UXB`
- `Experience Blueprint`

UXB 只能标记为“推荐”或“可选”。

Experience Blueprint 始终展示，不使用推荐标签。

Handoff 建议不写入问题单、需求基线或 Context JSON。

### 10.2 推荐结论来源

UXB 标记为“推荐”或“可选”的判断只按 `SKILL.md` 的 P10 执行。本文件不定义推荐信号、辅助信号或不确定时的处理规则。

### 10.6 用户可见格式

推荐 UXB：

```text
下一步：

1. UXB（推荐）
   需要先确定关键节点的信息顺序、状态反馈和体验取舍。

2. Experience Blueprint
   直接进入具体交互方案。

请回复要进入的阶段。
```

UXB 可选：

```text
下一步：

1. UXB（可选）
   可选体验定案。

2. Experience Blueprint
   生成确定的具体交互方案。

请回复要进入的阶段。
```

理由只写一句。完整判断依据只供 Agent 内部消费。

两个主链入口之后固定增加：

```text
可选增强：

- Stories
- Journey Analysis
```

不判断增强能力是否适用，不规定调用顺序。

### 10.7 人工决定

展示后的停止与人工选择规则只按 `SKILL.md` 的 P10 执行。本文件不得根据用户可见格式自动触发下游。

## 11. 用户可见文案规范

- 一句话只表达一个意思。
- 并列事实使用无序列表。
- 执行步骤使用有序列表。
- 标题不跳级。
- 不输出与产品沟通无关的信息。

## 12. Markdown 自检

- 文档状态与问题状态一致。
- 问题编号唯一且连续追加。
- 每个问题都有处理标签。
- 每个问题组只处理一个业务主题。
- 每个列表项只要求一个完整触发条件下的最小业务结论。
- 没有把由同一规则和同一证据完整覆盖的条件机械拆分。
- 回复和关闭状态与列表项一一对应。
- 不按回复数量、编号数量或上下文相邻推断问题关闭。
- 没有因推进意图绕过已识别的证据缺口。
- 本期任一阻断项未获得有效证据时不生成正式需求基线。
- 每条基线事实都有可定位来源。
- 没有把基座可选能力写成本期事实。
- 没有增加来源中不存在的动作、角色、字段、条件、状态、异常、恢复路径或数据影响。
- 核心任务的进入渠道不存在占位语。
- 内部来源追溯能够定位 PRD 或正式知识。
- 建议新增和建议修改都有唯一事实依据。
- 没有输出体验策略或页面方案。
- 没有长句、重复背景或内部推理。

## 13. 禁止输出内容

- 知识读取日志。
- 内部覆盖矩阵。
- 完整语义模型。
- Agent 思维过程。
- 没有唯一事实依据的优化建议。
- 体验策略。
- 页面、组件、布局和具体文案。
- UX 指标。
- 竞品分析。
