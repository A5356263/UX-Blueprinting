# PRD Review 输出结构

## 1. 双路径产物关系

```text
完整审查
→ 零阻断：直接生成正式需求基线
→ 存在阻断：生成问题单并停止
                  ↓
              产品回复
                  ↓
              全部关闭后生成正式需求基线
```

问题单和需求基线不能在存在阻断时同时生成。

## 2. 阻断问题单

### 2.1 输出路径

- `spark-output/prd_review_questions.md`

### 2.2 生成条件

- 只在存在阻断问题时生成。
- 完成本轮全部语义审查和知识覆盖后，一次性写入。
- 零阻断时不生成空问题单。

### 2.3 文档状态

- 存在未关闭问题：`waiting_response`
- 全部问题关闭：`closed`

### 2.4 固定结构

```markdown
# PRD 阻断问题

- 项目：{项目名}
- 状态：waiting_response
- 审查输入：{PRD 文件名或需求标识}

## 目标与范围

### Q-001【待确认】
- 问题：{缺少或冲突的业务结论}
- 位置：{PRD 章节、标题或表格位置}
- 为什么阻断：{影响的业务闭环}
- 需要确认：{产品需要明确回答的内容}

## 对象、角色与权限

## 任务、规则与状态

## 异常与业务结果

## 数据、系统、审计与验收
```

没有问题的分组不要输出空标题。

### 2.5 分组规则

- 目标与范围。
- 对象、角色与权限。
- 任务、规则与状态。
- 异常与业务结果。
- 数据、系统、审计与验收。

按业务问题归属分组，不按 Agent 的审查步骤分组。

### 2.6 问题编号

- 使用 `Q-001`、`Q-002` 顺序编号。
- 同一份问题文件内编号唯一。
- 回复更新时不得重排或复用编号。
- 新产生的阻断问题追加新编号。
- 不因分组变化修改旧编号。

## 3. 三类处理标签

### 3.1 待确认

适用：

- 缺少明确产品决定。
- 存在多个可能业务结论。
- 正式来源不能证明唯一答案。

写法：

```markdown
### Q-001【待确认】
- 问题：作废后重新推送的订单与旧记录关系未定义。
- 位置：“订单重复校验”段落。
- 为什么阻断：无法确定新旧订单的数据与审计关系。
- 需要确认：重新推送后是生成新记录，还是恢复并更新原记录？
```

没有正式来源证明有限选项时，不要自行列举候选答案。

### 3.2 建议修改

适用：

- PRD 前后目标状态冲突。
- PRD 声称沿用现有能力，但与正式当前事实不一致。
- 当前描述无法执行或验收。

写法：

```markdown
### Q-002【建议修改】
- 问题：“仅满足条件时展示按钮”与“不满足条件时展示禁用按钮”互相冲突。
- 位置：“订单作废功能”按钮规则。
- 为什么阻断：无法确定按钮最终展示规则。
- 建议修改：统一描述按钮在满足和不满足条件时的展示状态。
- 需要确认：最终采用哪套展示业务规则？
```

只建议修改业务表达。不要给出页面布局、组件或具体交互方案。

### 3.3 建议新增

适用：

- PRD 缺少业务闭环必须具备的说明。

写法：

```markdown
### Q-003【建议新增】
- 问题：订单作废与提报、结算并发时的业务结果未定义。
- 位置：“订单作废功能”前置条件。
- 为什么阻断：并发结果会改变订单是否可继续报销或结算。
- 建议新增：补充并发校验时点、互斥结果和失败后的订单状态。
- 需要确认：并发发生时哪项操作生效，另一项返回什么业务结果？
```

不要建议新增未经产品决定的能力、页面、组件、提示或交互机制。

## 4. 问题写作规则

每个问题只处理一个可独立回答的业务决定。

必须做到：

- 使用短句。
- 先写问题，再写必要依据。
- 指明 PRD 位置。
- 只解释直接阻断影响。
- 提问必须可以被明确回答。
- 有正式知识依据时，引用文件与章节。

禁止：

- 输出完整推理过程。
- 重复大段 PRD 原文。
- 输出知识路由过程。
- 输出非阻断建议。
- 输出体验机会。
- 输出竞品、指标或页面方案。
- 使用“建议产品完善一下”等笼统表达。
- 为凑数量制造理论问题。

## 5. 有限选项

只有 PRD、正式知识或现有系统能够证明选项集合有限时，才列选项。

列出选项时：

- 保持原始业务含义。
- 标明选项依据。
- 不推荐其中一项。

无法证明有限选项时，只问需要明确的业务结论。

## 6. 产品回复记录

设计师可以在聊天窗口按编号提供产品回复：

```text
Q-001：……
Q-002：……
```

第二次运行更新同一问题文件：

```markdown
### Q-001【待确认】
- 问题：……
- 位置：……
- 为什么阻断：……
- 需要确认：……
- 产品回复：{保留原始回复}
- 关闭状态：closed
```

规则：

- 保留原问题，不删除、不改写、不覆盖。
- 保留产品回复原意，不替产品润色成新决定。
- 明确关闭时写 `closed`。
- 回复不完整、冲突或产生新缺口时写 `unresolved`。
- 无法映射到问题编号时，不自动关闭。
- 全部关闭后，文件状态改为 `closed`。
- 存在任一 `unresolved` 时，整体状态保持 `waiting_response`。
- 新阻断问题追加在对应分组末尾，并使用新编号。
- 不建立独立回复文件或问题版本系统。

## 7. 回复复核规则

每条回复检查：

1. 是否对应明确问题。
2. 是否给出确定业务结论。
3. 是否与本期其他目标状态一致。
4. 是否关闭原阻断影响。
5. 是否产生新的业务缺口。

Agent 只能复核关闭状态，不能替产品补写答案。

## 8. 正式需求基线结构

### 8.1 输出路径

- `spark-output/requirements_baseline.md`
- `spark-output/context/requirements-baseline.json`

### 8.2 生成门禁

只有以下任一路径成立时才生成：

1. 首次完整审查后，阻断问题为零。
2. 产品回复复核后，全部阻断问题关闭，且没有产生新阻断。

不能生成“待确认版”“草稿版”或带假设的需求基线。

### 8.3 Markdown 固定结构

```markdown
# 正式需求基线

## §0 基线状态与来源

## §1 需求目标与本期范围

## §2 业务对象与业务边界

## §3 角色、责任与权限

## §4 功能清单与任务闭环

## §5 业务规则

## §6 状态与流转

## §7 异常、边界与业务结果

## §8 数据、系统与审计影响

## §9 约束与明确不做

## §10 验收条件

## §11 来源追溯
```

不适用的章节保留标题，并明确写“本期无”或“不适用”。不得静默省略。

### 8.4 §0 基线状态与来源

必须包含：

- 项目名。
- 基线状态：`formal`。
- 基线生成路径：零阻断直接生成，或产品回复关闭后生成。
- 原始 PRD 文件名或需求标识。
- 问题单路径；零阻断时写“不适用”。
- 纳入基线的产品回复编号；零阻断时写“不适用”。
- 正式知识来源清单。

### 8.5 §1 需求目标与本期范围

写清：

- 要解决的业务问题。
- 本期业务目标。
- 本期包含范围。
- 本期不包含范围。
- 业务成功结果。

不写体验目标、UX 指标或方案价值判断。

### 8.6 §2 业务对象与业务边界

写清：

- 核心业务对象。
- 对象之间的关系。
- 对象进入本期能力的条件。
- 对象不进入本期能力的条件。
- 新增、修改、移除的对象事实。

### 8.7 §3 角色、责任与权限

每个角色写清：

- 角色名称。
- 角色责任。
- 可执行动作。
- 权限前提。
- 数据或业务范围。
- 不允许执行的动作。

没有独立权限要求时，明确写“沿用现有权限”，并给出正式来源。

### 8.8 §4 功能清单与任务闭环

按用户任务组织，不按页面组织。每项功能写清：

- 功能编号。
- 执行角色。
- 触发条件。
- 主任务步骤。
- 成功结果。
- 失败或拒绝结果。
- 下一业务节点。

不得写页面布局、组件、交互载体或视觉样式。

### 8.9 §5 业务规则

每条规则写清：

- 规则编号。
- 适用对象。
- 触发条件。
- 判断条件。
- 业务结果。
- 优先级或互斥关系；不适用时省略。
- 来源。

规则只表达业务决定，不表达体验策略。

### 8.10 §6 状态与流转

按业务对象分别描述：

- 状态名称。
- 状态含义。
- 进入条件。
- 允许动作。
- 禁止动作。
- 下一状态。
- 不可逆性；不适用时写“否”。

状态名称沿用已确认业务用语，不创造近义状态。

### 8.11 §7 异常、边界与业务结果

每项写清：

- 触发场景。
- 业务判定。
- 对用户任务的结果。
- 对对象状态的结果。
- 是否允许重试或恢复。
- 后续处理责任方；有明确责任方时填写。

只定义业务结果。不设计错误提示、弹窗或恢复交互。

### 8.12 §8 数据、系统与审计影响

按适用范围写清：

- 新增、修改、移除的数据事实。
- 上下游系统影响。
- 同步、重复、并发和失败处理。
- 操作人、时间、原因等审计事实。
- 历史数据处理。

### 8.13 §9 约束与明确不做

只记录已由 PRD、正式知识或产品回复确认的：

- 业务约束。
- 技术或外部依赖约束。
- 本期明确不做。
- 后续考虑但本期不承诺的内容。

不得把 Agent 建议写成约束。

### 8.14 §10 验收条件

验收条件必须：

- 对应目标、功能、规则、状态或异常。
- 有明确前置条件。
- 有可观察的业务结果。
- 能判断通过或不通过。

不得使用“体验良好”“操作顺畅”等不可直接判定的表述。

### 8.15 §11 来源追溯

至少包含：

- PRD 来源。
- 正式知识来源。
- 产品回复来源。

产品回复使用问题编号追溯。不得只写“产品已确认”。

### 8.16 事实合并规则

基线内容按以下优先关系整理：

1. 产品明确回复用于关闭对应阻断问题。
2. PRD 定义本期目标状态。
3. 正式知识补充未被本期改变的当前事实。

发生冲突时：

- 产品回复只能覆盖其明确回答的范围。
- PRD 明确新增、修改、移除的目标事实，不得被旧知识覆盖。
- 未被产品回复关闭的冲突不得进入基线。
- Agent 不得用推理补写缺失事实。

### 8.17 基线文案规则

- 使用确定语气。
- 一条只表达一个业务事实。
- 并列事实使用无序列表。
- 有执行顺序时使用有序列表。
- 使用稳定编号引用功能、规则和问题。
- 不复制问题讨论过程。
- 不保留“建议”“可能”“待确认”等讨论语气。
- 不写下一步推荐。
- 不写 UXB 或体验蓝图结论。

## 9. 来源追溯

问题单与基线的依据只允许来自：

- PRD 原文位置。
- 正式知识文件与章节。
- 已存在的问题编号和产品回复。

来源可以简写，但必须可定位。

## 10. Handoff 建议格式

### 10.1 生成前提

只有正式需求基线生成后，才给出下一步建议。

主链只推荐：

- `UXB`
- `Experience Blueprint`

Handoff 建议不写入问题单、需求基线或 Context JSON。

### 10.2 推荐 UXB 的主要信号

先读取 `review_calibration_guide.md` 的路由校准部分。复杂度只作为辅助背景，不得替代体验取舍判断。

发现以下任一具体体验决策时，可以推荐 UXB：

- 存在多个合理体验方向，需要比较和定案。
- 信息解释的内容、位置或时机需要独立讨论。
- 操作触发节点需要重新选择。
- 任务顺序或流程编排需要调整。
- 多角色、多节点或多渠道的体验关系需要统一。
- 用户理解方式与业务结构存在明显差异。
- 直接设计页面会被迫提前决定体验方向。
- 需要先形成体验观点，再与产品讨论。
- 直接进入具体方案容易产生方向性返工。

这些信号用于辅助发现体验取舍，不要求穷举。

### 10.3 辅助信号

以下因素只能增加 UXB 推荐的必要性，不能单独决定：

- 业务链路长。
- 角色、状态或异常较多。
- 信息量较大。
- 涉及跨系统或跨端任务。
- 涉及高风险或不可逆操作。
- 新能力改变用户原有认知。
- 小改动影响主任务路径。
- 现有设计模式不能直接复用。

需求大小、页面数量和规则数量都不是硬门槛。

至少执行一次反例检查：

- 简单需求是否存在需要独立定案的体验取舍。
- 复杂需求是否已经具备明确体验方向，可以直接进入体验蓝图。

### 10.4 推荐 Experience Blueprint

满足以下情况时，可以直接推荐 `Experience Blueprint`：

- 业务事实已经闭环。
- 体验目标和方向明确。
- 没有需要先比较的体验方向。
- 不需要调整解释节点、触发时机或任务顺序。
- 可以直接复用成熟设计模式。
- 剩余工作主要是具体页面、组件、状态呈现和反馈设计。

复杂需求在体验方向明确时，也可以直接进入体验蓝图。简单需求存在体验取舍时，也可以推荐 UXB。

### 10.5 不确定时

- 已发现具体体验取舍，但影响程度不明确：推荐 UXB。
- 没有发现具体体验取舍：推荐 `Experience Blueprint`。
- 不得为了保险默认推荐 UXB。
- 不做评分，不设置数量阈值。

### 10.6 用户可见格式

推荐 UXB：

```text
下一步：UXB（推荐：存在信息解释节点和操作时机的体验取舍）
```

推荐体验蓝图：

```text
下一步：Experience Blueprint（体验方向明确，可直接落实具体方案）
```

理由只写一句。完整判断依据只供 Agent 内部消费。

固定增加：

```text
可选增强：Stories｜Journey Analysis
```

不判断增强能力是否适用，不规定调用顺序。

### 10.7 人工决定

- 推荐不是门禁。
- 设计师可以直接采用推荐。
- 设计师可以无理由跳过 UXB。
- 设计师也可以在未被推荐时主动使用 UXB。
- PRD Review 不记录跳过原因。
- Handoff 阶段不输出体验策略。

## 11. 用户可见文案规范

- 一句话只表达一个意思。
- 并列事实使用无序列表。
- 执行步骤使用有序列表。
- 标题不跳级。
- 不输出与产品沟通无关的信息。

## 12. Markdown 自检

- 文档状态与问题状态一致。
- 问题编号唯一且连续追加。
- 每个问题都有处理标签。
- 每个问题都能被明确回答。
- 每个问题都有 PRD 位置。
- 有知识依据时能够定位原文。
- 没有输出非阻断项。
- 没有输出体验策略或页面方案。
- 没有长句、重复背景或内部推理。

## 13. 禁止输出内容

- 知识读取日志。
- 内部覆盖矩阵。
- 完整语义模型。
- Agent 思维过程。
- 非阻断优化建议。
- 体验策略。
- 页面、组件、布局和具体文案。
- UX 指标。
- 竞品分析。
