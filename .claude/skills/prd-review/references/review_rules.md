# PRD Review 审查规则

## 1. 文档目的与适用边界

本文件定义合格 PRD 的业务闭环标准、内部语义模型、阻断判定和回复关闭规则。

只审查本次需求涉及的业务对象、动作和依赖。不要扩展整个业务域。

只判断产品决定是否表达完整、无冲突、可执行、可验证。不要判断需求方向是否值得做，也不要生成体验策略或页面方案。

## 2. 合格 PRD 定义

合格 PRD 必须让设计和实现能够确定：

- 为什么做，以及本期解决什么。
- 本期新增、修改、移除或沿用什么。
- 谁在什么条件下执行什么动作。
- 动作成功和失败后分别发生什么。
- 任务如何进入下一节点并最终结束。
- 权限、规则、状态、异常和依赖如何影响结果。
- 哪些内容明确不做。
- 如何验证业务结果。

PRD 不要求使用统一模板。排版、章节名称和表达风格不作为阻断理由。

## 3. 内部需求语义模型

### 3.1 建模范围

按本次需求建立以下关系：

```text
目标与范围
→ 业务对象及关系
→ 角色与责任
→ 功能与动作
→ 权限
→ 前置条件与业务规则
→ 状态与流转
→ 异常与恢复结果
→ 数据、系统与审计影响
→ 验收条件
```

### 3.2 事实来源状态

每项内部事实必须标记为：

- `PRD 明确描述`
- `正式知识证明`
- `产品回复确认`
- `尚未确认`

Agent 推理不能成为事实来源。

### 3.3 当前状态与目标状态

- 正式知识描述当前系统事实。
- PRD 与产品回复定义本期目标状态。
- PRD 明确新增、修改或移除时，不因目标状态不同于当前事实而阻断。
- PRD 声称沿用现有能力时，必须与当前事实一致。
- 需求必须说明新增、修改、移除或沿用的关系及影响。

### 3.4 内部闭环矩阵

按实际触发范围检查：

- 角色 × 动作 × 权限。
- 状态 × 允许动作 × 状态结果。
- 规则 × 触发条件 × 成功或失败结果。
- 依赖 × 成功或失败 × 责任主体与恢复结果。

矩阵只用于内部检查，不作为用户产物。

### 3.5 语义结论

每个被触发的审查维度必须得到一种结论：

- `已闭环`
- `存在阻断`
- `不适用`

`不适用`必须有明确理由，只在内部记录。

### 3.6 问题类型

- `缺失`：业务闭环需要的信息没有明确来源。
- `冲突`：两个目标状态结论不能同时成立。
- `无法验证`：表述无法转为确定条件或可观察结果。
- `影响未闭环`：主规则已明确，但关联角色、状态、数据、系统或下游结果没有落实。

### 3.7 业务骨架变化六问

对每项新增、修改或移除，检查：

1. 是否改变业务对象或对象关系。
2. 是否改变业务规则。
3. 是否改变状态及流转。
4. 是否改变生效、失效、审批、定时或回滚机制。
5. 是否改变统计、归属、保密、隔离或汇总口径。
6. 是否改变外部同步、回写、对账或归档链路。

每项得到一种内部结论：

- 明确改变：展开对应审查维度。
- 明确不改变：保留正式依据。
- 无法确定：进入对应阻断判断。

六问用于确定审查范围，不输出复杂度等级。

具体跨域边界和领域误判案例见 `review_calibration_guide.md`。其中内容只用于反查，不能成为需求事实。

## 4. 目标与范围审查

检查：

- 需求目标是否明确。
- 本期范围是否明确。
- 明确不做的内容是否与本期目标一致。
- 功能是否能够支撑目标。
- 是否能判断本次属于新增、修改、移除还是沿用。
- 修改或移除时，受影响的旧能力和生效范围是否明确。

以下情况阻断：

- 无法确定本期到底解决什么。
- 目标和功能互相矛盾。
- 无法判断目标状态。
- 变更范围或旧规则处理不清。

没有历史版本或正式当前状态时，不得声称某项是“新增”“修改”或“移除”。

## 5. 业务对象审查

检查：

- 操作对象是什么。
- 对象之间是什么关系。
- 对象如何创建、变化和终止。
- 核心标识和关联关系是否清楚。
- 新旧对象或重复对象如何区分。

以下情况阻断：

- 核心对象无法确定。
- 对象关系影响任务结果但没有定义。
- 同一名称指向多个业务对象。
- 对象终止、替换或重新生成后的关系不清。

## 6. 角色与责任审查

检查：

- 谁发起。
- 谁操作。
- 谁查看。
- 谁配置。
- 谁承担业务结果。
- 谁处理失败和恢复。
- 下一节点由谁继续。

以下情况阻断：

- 关键动作没有明确执行角色。
- 多角色责任重叠或断开。
- 下一节点没有责任主体。
- 异常发生后没有处理责任主体。

不要把用户画像、用户动机或体验偏好作为合格 PRD 的必备角色信息。

## 7. 权限审查

检查：

- 哪个角色拥有功能权限。
- 权限由谁配置。
- 权限作用于哪些数据范围。
- 权限何时生效或失效。
- 无权限时业务结果是什么。
- 功能权限、数据权限和操作条件是否被混用。

以下情况阻断：

- 关键操作没有权限主体。
- 权限和角色关系不清。
- 无权限结果会影响任务闭环但没有定义。
- 历史客户、默认配置或迁移策略影响可用性但没有说明。

## 8. 功能与任务闭环审查

对每个主任务检查：

```text
触发
→ 前置条件
→ 执行动作
→ 成功结果
→ 下一节点
→ 最终结束
```

同时检查失败结果和恢复方式。

以下情况阻断：

- 入口或触发方式无法确定。
- 缺少关键前置条件。
- 动作完成后没有明确结果。
- 下一节点不清。
- 失败后任务悬空。
- 一条业务链无法到达结束状态。

## 9. 业务规则审查

每条关键规则检查：

- 触发条件。
- 判断条件。
- 规则优先级。
- 满足条件后的结果。
- 不满足条件后的结果。
- 与其他规则的关系。
- 生效范围和生效时间。

以下情况阻断：

- 条件和结果不成对。
- 多条目标规则互相冲突。
- 使用“特定情况”“适当”“合理”等无法执行的表达。
- 修改规则但没有说明旧规则如何处理。
- 规则影响下游但没有说明影响结果。

## 10. 状态与流转审查

检查：

- 初始状态。
- 状态含义。
- 进入条件。
- 退出条件。
- 是否可逆。
- 每种状态允许和禁止的动作。
- 多个状态维度之间的关系。
- 状态变化后的数据和下游影响。

以下情况阻断：

- 核心状态含义不清。
- 状态名称相同但语义不同。
- 状态变化没有触发条件。
- 状态允许动作互相矛盾。
- 不可逆状态没有明确业务结果。
- 将多个独立状态维度混成一个状态。

## 11. 异常与边界审查

只审查会改变业务结果或任务闭环的异常：

- 重复操作。
- 并发变化。
- 外部系统失败。
- 部分成功。
- 数据已经被下游使用。
- 不可逆操作。
- 历史数据兼容。
- 空值、上限、下限和唯一性。
- 恢复条件和责任主体。

每个被触发的异常至少明确：

```text
触发条件
→ 业务结果
→ 是否可恢复
→ 恢复责任主体
→ 恢复后的状态
```

不要审查加载动画、控件样式、错误文案位置等页面异常设计。

## 12. 数据、系统与审计审查

检查：

- 数据来源和去向。
- 核心字段或记录变化。
- 外部系统依赖。
- 同步和回写结果。
- 重复校验。
- 下游业务影响。
- 报表、接口和审计影响。
- 操作人、时间和原因等审计记录。

以下情况阻断：

- 外部系统失败会改变业务结果但没有处理结论。
- 上下游数据状态可能不一致但没有责任边界。
- 修改或删除数据后，下游影响不清。
- 高风险操作没有必要的业务审计要求。

## 13. 验收审查

检查：

- 成功结果是否可观察。
- 失败结果是否可观察。
- 关键规则是否可测试。
- 数值、条件和枚举是否明确。
- 角色、状态和数据变化能否被验证。

适用时可以在基线中使用 Given / When / Then，但不强制所有需求采用。

以下情况阻断：

- 无法判断功能是否完成。
- 核心规则没有明确预期结果。
- 验收条件依赖主观形容词。
- 验收内容和需求目标不一致。

## 14. 阻断判定

只有同时满足以下条件，才形成阻断问题：

1. 信息属于标准 PRD 的业务闭环。
2. 缺失、冲突或无法验证会影响业务结果、任务继续或验收。
3. PRD、正式知识和已有产品回复都不能提供唯一明确结论。
4. 问题不属于体验策略或具体页面方案。

典型阻断：

- 目标或本期范围无法确定。
- 核心对象或关系无法确定。
- 关键角色、责任或权限无法确定。
- 主任务缺少触发、过程、结果或下一节点。
- 核心规则缺失或冲突。
- 核心状态含义或流转不清。
- 异常改变业务结果，但处理结果未定义。
- 数据、系统或审计影响未闭环。
- 验收条件无法验证业务结果。

以下内容不能作为阻断：

- 页面布局。
- 组件形式。
- 按钮位置。
- 具体提示文案。
- 信息架构方案。
- 交互流程编排方案。
- 体验取舍。
- UX 指标。
- 竞品比较。
- 需求方向是否值得做。

## 15. 待确认、建议修改、建议新增

### 待确认

用于缺少明确产品决定，且正式来源不能证明唯一结论的阻断问题。

### 建议修改

用于：

- PRD 前后目标状态冲突。
- PRD 声称沿用现有能力，但描述与当前事实不一致。
- 当前表述无法执行或验收。

只建议修改业务描述。不要提出体验方案。

### 建议新增

用于 PRD 缺少业务闭环必须具备的角色、权限、规则、状态、异常、数据、系统影响或验收说明。

不要建议新增未经产品决定的业务能力、页面或交互机制。

三类问题只要形成阻断，都必须由产品明确回复后才能关闭。

## 16. 有限选项规则

只有 PRD、正式知识或现有系统能够证明选项集合有限时，才向产品列出选项。

无法证明选项有限时，只描述需要确认的问题，不生成候选答案。

## 17. 回复关闭规则

问题只有同时满足以下条件才关闭：

1. 回复能够对应明确问题编号。
2. 回复给出确定业务结论。
3. 回复与本期其他目标状态结论一致。
4. 回复没有产生新的业务缺口。
5. 设计师确认产品回复已经收集完整。

“按现有逻辑”“后面再看”“先设计”等回复不能关闭问题。

## 18. 自检清单

完成语义审查后逐项检查：

- 是否只审查本次需求范围。
- 是否区分当前状态和目标状态。
- 是否区分事实来源和 Agent 推理。
- 是否覆盖被触发的角色、权限、任务、规则、状态、异常和依赖。
- 每个被触发维度是否得到已闭环、阻断或不适用结论。
- 是否把体验问题误判为业务阻断。
- 是否因正式知识与目标状态不同而错误阻断。
- 是否遗漏修改、移除或例外对现有能力的影响。
- 是否只保留真正影响业务闭环的问题。
- 是否由 Agent 完成全部语义判断。
