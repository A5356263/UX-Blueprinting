# PRD Review 审查规则

## 1. 文档目的与适用边界

本文件定义合格 PRD 的业务闭环标准、内部语义模型、阻断判定和回复关闭规则。

本文件不决定执行顺序。调用节点、强制读取范围和返回位置只以 `../SKILL.md` 为准。

只审查本次需求涉及的业务对象、动作和依赖。不要扩展整个业务域。

只判断产品决定是否表达完整、无冲突、可执行、可验证。不要判断需求方向是否值得做，也不要生成体验策略或页面方案。

## 2. 合格 PRD 定义

合格 PRD 必须让设计和实现能够确定：

- 为什么做，以及本期解决什么。
- 本期新增、修改、移除或沿用什么。
- 谁在什么条件下执行什么动作。
- 动作成功和失败后分别发生什么。
- 任务如何进入下一节点并最终结束。
- 权限、规则、状态、异常和依赖如何影响结果。
- 哪些内容明确不做。
- 如何验证业务结果。

PRD 不要求使用统一模板。排版、章节名称和表达风格不作为阻断理由。

## 3. 内部需求语义模型

### 3.1 建模范围

按本次需求建立以下关系：

```text
目标与范围
→ 业务对象及关系
→ 角色与责任
→ 功能与动作
→ 权限
→ 前置条件与业务规则
→ 状态与流转
→ 异常与恢复结果
→ 数据、系统与审计影响
→ 完成标准
```

### 3.2 事实来源状态

每项内部事实必须标记为：

- `PRD 明确描述`
- `正式知识证明`
- `产品回复确认`
- `尚未确认`

Agent 推理不能成为事实来源。

进入正式需求基线前，每条事实必须反查：

1. 来源位置。
2. 来源是否唯一支持该结论。
3. 事实是否属于本期。
4. 是否增加了来源中不存在的信息。

`尚未确认`的事实不能进入需求基线。

允许将口语或分散描述整理为等价事实，但不能增加新动作、角色、字段、条件、状态、异常、恢复路径或数据影响。存在两个以上合理解释时，不得执行等价整理。

任一事实无法通过反查时，不得写入需求基线；影响业务闭环时恢复为待确认阻断。

### 3.3 当前状态与目标状态

- 正式知识描述当前系统事实。
- PRD 与产品回复定义本期目标状态。
- PRD 明确新增、修改或移除时，不因目标状态不同于当前事实而阻断。
- PRD 声称沿用现有能力时，必须与当前事实一致。
- 需求必须说明新增、修改、移除或沿用的关系及影响。

### 3.4 内部闭环矩阵

先按角色建立真实任务场景：

```text
角色
→ 需求发生事件
→ 业务触发条件
→ 本期支持的进入渠道
→ 前置条件
→ 核心动作
→ 成功结果
→ 失败结果
→ 下一业务节点
→ 最终结束
```

需求发生事件说明用户为什么在此时产生任务。

业务触发条件说明什么业务事实使任务成立。

进入渠道只确定本期支持从哪个业务位置或场景开始任务，不确定按钮、弹窗、抽屉、页面布局等交互形式。

PRD Review 可以确认“权限不足时直接申请”或“仅从固定权限管理入口主动申请”。不得确认入口控件放在哪里、用什么组件承载。

再在每个场景内按实际触发范围检查：

- 角色 × 动作 × 权限。
- 状态 × 允许动作 × 状态结果。
- 规则 × 触发条件 × 成功或失败结果。
- 依赖 × 成功或失败 × 责任主体与恢复结果。

矩阵只用于内部检查，不作为用户产物。

问题必须归回具体任务场景。禁止先按权限、状态、异常等抽象维度生成问题，再让产品自行判断问题发生在哪里。

### 3.5 语义结论

每个被触发的审查维度必须得到一种结论：

- `已闭环`
- `存在阻断`
- `不适用`

`不适用`必须有明确理由，只在内部记录。

### 3.6 问题类型

- `缺失`：业务闭环需要的信息没有明确来源。
- `冲突`：两个目标状态结论不能同时成立。
- `无法验证`：表述无法转为确定条件或可观察结果。
- `影响未闭环`：主规则已明确，但关联角色、状态、数据、系统或下游结果没有落实。

### 3.7 业务骨架变化六问

对每项新增、修改或移除，检查：

1. 是否改变业务对象或对象关系。
2. 是否改变业务规则。
3. 是否改变状态及流转。
4. 是否改变生效、失效、审批、定时或回滚机制。
5. 是否改变统计、归属、保密、隔离或汇总口径。
6. 是否改变外部同步、回写、对账或归档链路。

每项得到一种内部结论：

- 明确改变：展开对应审查维度。
- 明确不改变：保留正式依据。
- 无法确定：进入对应阻断判断。

六问用于确定审查范围，不输出复杂度等级。

具体跨域边界和领域误判案例见 `review_calibration_guide.md`。其中内容只用于反查，不能成为需求事实。

### 3.8 问题组与原子项

同一任务场景可以组成一个问题组。

问题组中的每个待确认项只承载一个完整触发条件下的最小业务结论。

完整触发条件是一组能够唯一限定当前业务决定适用范围的前置事实。业务对象、对象状态、操作角色、前置条件、历史动作或分支不同，只作为拆分检查信号。

最小业务结论必须能够由同一条回复完整确认，内部不能独立变化。业务决定和直接结果能够被分别回答或独立变化时，必须拆分。

出现以下任一情况，必须拆成多个编号项：

- 条件差异可能产生不同业务决定或系统结果。
- 产品可能只回答其中一部分。
- 正式证据只能覆盖其中一个条件。
- 两部分由不同角色或负责人确认。
- 两部分会分别改变不同业务规则、状态或处理结果。

多个条件由同一规则和同一证据完整覆盖时，可以保留为一个原子项。

以下内容不能混成一个待确认项：

- 支持什么。
- 不支持什么。
- 谁可以操作。
- 在什么条件下操作。
- 成功后发生什么。
- 失败后发生什么。
- 多久算超时。
- 找不到责任人时怎么办。

待确认项按原顺序编号。

产品回复后逐项复核。

一个编号必须对应一个完整触发条件、一个最小业务结论、一条回复记录和一个关闭状态。

回复记录可以是产品原始回复或“未回复”。以正式知识、本期范围或不适用证据关闭时，不得伪造产品回复。

一个问题组只有在全部待确认项关闭后才能关闭。

### 3.9 候选问题事实回查

每个候选问题输出前依次检查：

1. PRD 是否直接说明。
2. PRD 的流程、规则或示例是否只能得到一个结论。
3. 正式知识是否已说明，且本需求没有改变。
4. 其他候选问题是否已经覆盖。
5. 是否属于本期。
6. 是否只要求一个业务决定。
7. 命中复用基座时，是否已完成 3.10 的继承审查。

第 1 至 4 项只有在来源或其他候选问题能够唯一回答同一适用条件下的同一完整业务结论时，才删除重复问题。终态结论不能替代中间状态、对象关系或上下游影响。

不属于本期且已有明确证据时，不进入正式问题单。

命中复用基座时，只有正式知识证明该内容属于固定继承，且本期没有修改、关闭或覆盖，才删除相关问题。

禁止把“查看范围”和“申请范围”、“功能权限”和“数据权限”等不同业务关系混为一个问题。

### 3.10 复用基座继承

需求使用现有审批、通知、权限、支付、组织、消息或其他成熟基座时，进入本节。

本节只审查复用范围，不能替代 3.4 的完整业务闭环矩阵，也不能过滤与复用无关的角色、任务、规则、状态和异常问题。

复用基座的读取要求、输入/输出/配置边界、固定继承、条件继承、当前需求决定、知识缺口和候选问题移出，统一按 `knowledge_usage_guide.md` 第 10 节执行。本文件不重复定义。

执行完继承审查后必须返回 3.4 完成当前业务事务闭环，再按 3.9 回查候选问题。没有命中复用关系时，不得使用基座边界过滤问题。

### 3.11 场景审核记录分流

初次审核记录只使用以下三种场景内表达：

- 业务事实补充。
- 需要产品确认。
- 体验定案事项。

它们只决定审核记录如何呈现，不新增问题类型、关闭状态或事实来源。既有“缺失、冲突、无法验证、影响未闭环”和“待确认、建议修改、建议新增”规则继续适用。

先以 3.4 的完整任务链建立每个场景。场景必须能依次说明：

```text
角色
→ 触发或进入条件
→ 前置条件
→ 核心任务或系统处理
→ 成功、拒绝、中断或异常结果
→ 下一责任方、下一业务节点或明确终态
```

每项业务事实补充、待确认或体验定案事项都必须附着到该链中的一个具体节点。不得让场景停在“提交”“处理中”“已触发”等中间状态。

缺少触发、结果或后续交接时：正式知识能唯一证明时形成业务事实补充；否则形成待确认；不得归入体验定案事项。

#### 业务事实补充

只有同时满足以下条件，才可在审核记录中写为业务事实补充：

1. PRD 未写明该事实，或未把该事实写入当前任务。
2. 正式知识直接证明同一对象、关系、角色、条件和结果。
3. 该结论固定且唯一，不依赖本期选择或配置。
4. 知识未标记 `[GAP]`、`[QUESTION]` 或 `[CONFLICT]`。
5. PRD 没有明确新增、修改、移除或覆盖该事实。
6. 原文不是“支持”“可配置”“可选”“开启后可用”等能力描述。
7. 补入后不新增角色、动作、条件、状态、异常、数据影响或产品决定。

不满足任一条件时，不得写为业务事实补充。若影响闭环，进入待确认；不影响闭环，只在内部记录。

业务事实补充必须直接回应当前场景已识别的一个业务缺口。结论句只写可补入需求基线的事实；不得输出领域概念、完整链路复述或与当前场景无直接关系的知识摘要。

#### 需要产品确认

需要产品确认只承载影响业务闭环、但 PRD、正式知识和已有有效回复均不能唯一证明的业务结论。具体阻断条件以第 14 节为准。

每个待确认只询问一个最小业务决定。不得用“还有哪些”“其他是否需要”“请补充完整流程”等开放式兜底问题要求产品补写 PRD。

PRD、正式知识或有效产品回复已经明确业务动作、业务结果或状态结果时，不得继续询问系统内部如何实现。只有缺少会改变业务结果的范围、条件、责任、对象关系或异常结果时，才可保留待确认。

#### 体验定案事项

只有同时满足以下条件，才可标记体验定案事项：

1. 已知该事项对应的角色、业务对象、用户任务和业务目标。
2. 缺失内容只涉及任务如何被发现、如何被理解、信息如何组织、任务顺序如何编排、状态如何解释、反馈如何交接或任务如何连续完成。
3. 该缺失不改变角色资格、触发条件、可处理范围、业务输入、责任归属、状态结果、系统交接或业务终态。
4. PRD、正式知识和现有系统没有唯一限定具体体验定法。
5. 当前场景中的其他待确认不会改变第 1 至 3 项中与本事项直接相关的事实。
6. 该事项不是单纯的组件、视觉、布局或具体文案选择。

体验定案事项是审核缺口分类，不是 UXB 推荐、自动路由或产品待确认。它不写候选方向、推荐结论、组件名称、页面结构或具体交互做法；不要求产品回复；不进入需求基线、Context、页面事实或下游事实协议。

#### 进入渠道的统一边界

当业务的发起者、触发条件、后续任务和结果已确定，只缺发现方式、体验承载或交互组织时，标记为体验定案事项。

当入口会改变角色、可发起范围、业务触发、业务输入、系统交接、任务前后关系或业务结果时，形成待确认。

“存在入口”与“入口如何承载”必须分开判断。前者属于业务闭环；后者属于体验定案。

同一缺口只能选择一个去向。该缺口缺少业务决定时，必须归为待确认，不得转为体验定案事项。场景中的其他待确认不影响独立体验缺口的分类，除非它会改变该体验缺口的角色、任务、目标或业务结果。

### 3.12 待确认二次对账

只对准备输出的待确认执行本节。不得对全部知识、全部场景、全部内部事实、建议修改或体验定案事项做交叉比较。

每个待确认还原为以下业务语义后再检查：

```text
业务对象
→ 关系或动作
→ 角色
→ 适用条件
→ 需要决定的业务结果
```

按以下顺序处理：

1. PRD、正式知识或业务事实补充已经唯一覆盖同一适用条件下的同一业务结论：删除待确认。
2. 另一个待确认的同一条产品回复能够完整关闭当前结论：合并为一个待确认。
3. 两个待确认只共享对象、角色或上下文，但答案可以独立变化：分别保留。
4. 待确认混入两个可独立回答的业务决定：交给第 3.8 节拆分。
5. 已明确业务动作、业务结果或状态结果，只在询问系统内部实现：删除待确认。
6. 无法证明唯一覆盖，且仍缺少会改变业务结果的范围、条件、责任、对象关系或异常结果：保留待确认。

“同一条产品回复能够完整关闭”必须同时覆盖业务对象、关系或动作、角色、适用条件和业务结果。只共享关键词、对象名称或场景名称时不得合并。

删除、合并、拆分或保留的依据只在内部使用；正式审核记录不展示对账过程。

## 4. 目标与范围审查

检查：

- 需求目标是否明确。
- 本期范围是否明确。
- 明确不做的内容是否与本期目标一致。
- 功能是否能够支撑目标。
- 是否能判断本次属于新增、修改、移除还是沿用。
- 修改或移除时，受影响的旧能力和生效范围是否明确。

以下情况阻断：

- 无法确定本期到底解决什么。
- 目标和功能互相矛盾。
- 无法判断目标状态。
- 变更范围或旧规则处理不清。

没有历史版本或正式当前状态时，不得声称某项是“新增”“修改”或“移除”。

## 5. 业务对象审查

检查：

- 操作对象是什么。
- 对象之间是什么关系。
- 对象如何创建、变化和终止。
- 核心标识和关联关系是否清楚。
- 新旧对象或重复对象如何区分。

以下情况阻断：

- 核心对象无法确定。
- 对象关系影响任务结果但没有定义。
- 同一名称指向多个业务对象。
- 对象终止、替换或重新生成后的关系不清。

## 6. 角色与责任审查

检查：

- 谁发起。
- 谁操作。
- 谁查看。
- 谁配置。
- 谁承担业务结果。
- 谁处理本需求新增或改变的失败和恢复。
- 下一节点由谁继续。

以下情况阻断：

- 关键动作没有明确执行角色。
- 多角色责任重叠或断开。
- 下一节点没有责任主体。
- 异常发生后没有处理责任主体。

不要把用户画像、用户动机或体验偏好作为合格 PRD 的必备角色信息。

## 7. 权限审查

检查：

- 哪个角色拥有功能权限。
- 权限由谁配置。
- 权限作用于哪些数据范围。
- 权限何时生效或失效。
- 无权限时业务结果是什么。
- 功能权限、数据权限和操作条件是否被混用。

以下情况阻断：

- 关键操作没有权限主体。
- 权限和角色关系不清。
- 无权限结果会影响任务闭环但没有定义。
- 历史客户、默认配置或迁移策略影响可用性但没有说明。

## 8. 功能与任务闭环审查

对每个主任务检查：

```text
需求发生事件
→ 业务触发条件
→ 本期支持的进入渠道
→ 前置条件
→ 执行动作
→ 成功结果
→ 失败结果
→ 下一节点
→ 最终结束
```

同时检查失败结果和恢复方式。

满足以下全部条件时，进入渠道缺失属于阻断问题：

1. 本期核心任务需要用户主动发起。
2. PRD、正式知识和现有系统均不能证明进入渠道。
3. 不同进入渠道会改变本期能力范围、角色范围或任务是否能够开始。

仅缺少按钮位置、页面布局或承载组件时不阻断。该问题属于后续体验定案或交互方案。

以下表达属于占位语，不是已确认的进入渠道：

- 进入申请入口。
- 进入配置入口。
- 进入相关页面。
- 使用系统入口。
- 按现有方式进入。
- 从对应模块发起。

占位语不能关闭阻断问题，也不能进入正式需求基线。

以下情况阻断：

- 缺少关键前置条件。
- 动作完成后没有明确结果。
- 下一节点不清。
- 失败后任务悬空。
- 一条业务链无法到达结束状态。

## 9. 业务规则审查

每条关键规则检查：

- 触发条件。
- 判断条件。
- 规则优先级。
- 满足条件后的结果。
- 不满足条件后的结果。
- 与其他规则的关系。
- 生效范围和生效时间。

以下情况阻断：

- 条件和结果不成对。
- 多条目标规则互相冲突。
- 使用“特定情况”“适当”“合理”等无法执行的表达。
- 修改规则但没有说明旧规则如何处理。
- 规则影响下游但没有说明影响结果。

## 10. 状态与流转审查

检查：

- 初始状态。
- 状态含义。
- 进入条件。
- 退出条件。
- 是否可逆。
- 每种状态允许和禁止的动作。
- 多个状态维度之间的关系。
- 状态变化后的数据和下游影响。

以下情况阻断：

- 核心状态含义不清。
- 状态名称相同但语义不同。
- 状态变化没有触发条件。
- 状态允许动作互相矛盾。
- 不可逆状态没有明确业务结果。
- 将多个独立状态维度混成一个状态。

## 11. 异常与边界审查

只审查会改变业务结果或任务闭环的异常：

- 重复操作。
- 并发变化。
- 本需求新增或改变的外部系统失败。
- 部分成功。
- 数据已经被下游使用。
- 不可逆操作。
- 历史数据兼容。
- 空值、上限、下限和唯一性。
- 恢复条件和责任主体。

每个被触发的异常至少明确：

```text
触发条件
→ 业务结果
→ 是否可恢复
→ 恢复责任主体
→ 恢复后的状态
```

不要审查加载动画、控件样式、错误文案位置等页面异常设计。

成熟基座内部已经承担的异常不属于本需求阻断。只有本需求改变基座行为，或基座结果无法闭合当前任务时，才进入异常审查。

## 12. 数据、系统与审计审查

检查：

- 数据来源和去向。
- 核心字段或记录变化。
- 外部系统依赖。
- 同步和回写结果。
- 重复校验。
- 下游业务影响。
- 报表、接口和审计影响。
- 操作人、时间和原因等审计记录。

以下情况阻断：

- 本需求改变外部系统交接，且失败会改变业务结果但没有处理结论。
- 上下游数据状态可能不一致但没有责任边界。
- 修改或删除数据后，下游影响不清。
- 高风险操作没有必要的业务审计要求。

## 13. 完成标准审查

检查：

- 成功结果是否可观察。
- 失败结果是否可观察。
- 关键规则是否可测试。
- 数值、条件和枚举是否明确。
- 角色、状态和数据变化能否被验证。

产品不需要单独编写“完成标准”章节。

PRD Review 可以把已确认的前提、动作和业务结果改写为可观察完成标准。

改写时不得增加新规则、新阈值或新范围。

适用时可以在基线中使用 Given / When / Then，但不强制所有需求采用。

以下情况阻断：

- 已有事实仍无法判断功能是否完成。
- 核心规则没有明确预期结果。
- 业务结果依赖主观形容词。
- 完成结果和需求目标不一致。

以下情况不阻断：

- PRD 没有单独的完成标准章节。
- 已确认事实足以生成前提、动作和可观察结果。

## 14. 阻断判定

只有同时满足以下条件，才形成阻断问题：

1. 信息属于标准 PRD 的业务闭环。
2. 缺失、冲突或无法验证会影响业务结果、任务继续或验收。
3. PRD、正式知识和已有产品回复都不能提供唯一明确结论。
4. 问题不属于体验策略或具体页面方案。

典型阻断：

- 目标或本期范围无法确定。
- 核心对象或关系无法确定。
- 关键角色、责任或权限无法确定。
- 主任务缺少触发、过程、结果或下一节点。
- 核心规则缺失或冲突。
- 核心状态含义或流转不清。
- 异常改变业务结果，但处理结果未定义。
- 数据、系统或审计影响未闭环。
- 缺少可验证的业务结果。

以下内容不能作为阻断：

- 页面布局。
- 组件形式。
- 按钮位置。
- 具体提示文案。
- 信息架构方案。
- 交互流程编排方案。
- 体验取舍。
- UX 指标。
- 竞品比较。
- 需求方向是否值得做。

## 15. 待确认、建议修改、建议新增

### 待确认

用于缺少明确产品决定，且正式来源不能证明唯一结论的阻断问题。

### 建议修改

只用于已有唯一事实，但 PRD 其他位置使用了不一致、过时或不准确的表达。

修改只纠正文档，不改变角色、任务、规则、状态、结果、数据或系统影响。

### 建议新增

只用于 PRD、正式知识或产品回复已经给出唯一事实，但 PRD 没有把该事实写入对应任务。

补入后不得产生新的产品决策。

初次审核记录中，满足 3.11“业务事实补充”条件的建议新增，按“业务事实补充”展示，并保留正式知识来源。它不是新的关闭状态。

“体验定案事项”不是建议新增、建议修改或待确认的一种。它只标识审核中发现的体验层缺口，不承担 UXB 路由、产品回复或业务事实职责。

### 三类处理的硬分界

出现以下任一情况，必须归为“待确认”，不得归为建议：

- 需要产品选择。
- 存在两个及以上合理业务结果。
- 会改变角色权限。
- 会改变任务步骤。
- 会新增或删除状态。
- 会改变成功、失败或中断结果。
- 会改变数据或系统影响。
- 知识与本期需求冲突，且无法判断是否为明确变更。

正式问题只有获得 17.2 定义的有效证据后才能关闭。

“建议修改”和“建议新增”不阻断基线生成。Agent 按已有唯一事实修正文档；产品明确否定时，将回复视为新事实并重新审查。

## 16. 有限选项规则

只有 PRD、正式知识或现有系统能够证明选项集合有限时，才向产品列出选项。

无法证明选项有限时，只描述需要确认的问题，不生成候选答案。

## 17. 回复关闭规则

### 17.1 逐项复核

每个编号项必须单独保留原问题、产品原始回复和关闭状态。

回复条数、编号数量或上下文相邻不能替代语义对应检查。

禁止把一条回复扩展为多个未被明确确认的结论。

收到回复后必须分开判断：

1. 原问题是否获得有效证据。
2. 回复是否产生新的独立候选问题。

### 17.2 待确认项关闭条件

正式问题只允许依据以下方式关闭：

1. 产品明确确认。
2. 正式知识证明由基座固定继承。
3. 有明确证据证明不属于本期。
4. 有明确证据证明不适用。

“不属于本期”和“不适用”只接受以下证据：

- PRD 明确排除。
- 产品明确回复。
- 正式知识与已确认业务边界共同证明该事项不属于本期。
- 已确认的业务前提证明该场景不会发生。

产品回复关闭原问题时必须同时满足：

1. 回复能够对应明确问题组和列表项。
2. 回复给出确定业务结论。
3. 回复可以写成稳定需求事实。
4. 回复与本期其他目标状态一致。
5. 回复不依赖 Agent 补充。

不是每个问题都必须包含条件、阈值和兜底。只有缺失内容会使当前答案无法形成稳定事实时，原问题才保持 `open`。

### 17.3 新候选问题

原问题复核完成后，再检查回复新增的信息：

- 暴露独立业务缺口：回到 3.9 执行候选问题回查，通过后使用新编号。
- 与已有问题重复：合并，不新增编号。
- 已由 PRD 或正式知识回答：不新增。
- 不影响业务闭环：不进入问题单。

新候选问题不能反向污染已经完整回答的原问题。

只有新增信息直接改变、限制或否定原答案，使原事实仍不完整时，原问题才保持 `open`。

### 17.4 问题组关闭条件

问题组只有在全部待确认项均为 `closed` 时才关闭。

只回答部分列表项时：

- 已回答项可以标记 `closed`。
- 未回答项保持 `open`。
- 问题组保持 `unresolved`。
- 整份问题单保持 `waiting_response`。
- 不生成需求基线。

### 17.5 不完整回复

以下回复不能关闭对应待确认项：

- 只给方向，没有明确结果。
- 只说明会超时，没有说明必要的时限、时限来源或配置方式。
- 只说复用现有能力，但现有能力范围不明确。
- 反问或存在多种合理解释。
- 只回答复合问题的一部分。
- 新增条件直接改变原答案，但没有定义完整结果。
- “按现有逻辑”“后面再看”“先设计”。

Agent 一旦识别回复没有覆盖完整触发条件、存在两种以上合理解释，或需要补充新条件、动作、状态或结果才能形成事实，当前原子项必须保持 `open`。

“继续”“先做”“不要再问”“避免继续追问”等只表达推进意图，不能成为关闭依据。用户明确给出业务结论或范围决定时，仍按 17.2 的四种关闭依据复核。

处理方式：

1. 保留原问题和原列表项。
2. 保留产品原始回复。
3. 只追加仍未关闭的短问题。
4. 状态保持 `open`。
5. 严格停止。

### 17.6 问题移出

复核发现问题本身不成立时：

- 未进入正式问题单：直接删除。
- 已误入正式问题单：移出问题集合并记录原编号、移出依据和来源。
- 不标记为产品已确认。
- 不生成需求事实。
- 不计入未关闭阻断项。

围绕仍没有唯一答案的基座内部细节产生的候选问题，只有满足 `knowledge_usage_guide.md` 10.4 的全部条件时才能移出。固定继承已经唯一回答的问题不执行此处移出。移出依据只记录“该规则由基座内部承接，本需求不定义”及可定位证据，不得转写为本期已启用或继承某项具体策略。

问题移出不是第五种关闭状态。

### 17.7 禁止推断关闭

产品回复只关闭其明确回答的范围。

示例：

产品回复“本期只包含角色权限和功能权限”，可以确认数据权限不在本期。

不能据此推导：

- 不支持批量申请。
- 不支持移动端。
- 不支持多次申请。

## 18. 自检清单

完成语义审查后逐项检查：

- 是否只审查本次需求范围。
- 是否区分当前状态和目标状态。
- 是否区分事实来源和 Agent 推理。
- 是否覆盖被触发的角色、权限、任务、规则、状态、异常和依赖。
- 每个被触发维度是否得到已闭环、阻断或不适用结论。
- 是否把体验问题误判为业务阻断。
- 是否因正式知识与目标状态不同而错误阻断。
- 是否遗漏修改、移除或例外对现有能力的影响。
- 是否只保留真正影响业务闭环的问题。
- 是否按具体任务场景组织问题。
- 核心任务是否说明需求发生事件与本期支持的进入渠道。
- 是否把“进入相关页面”等占位语误当作进入渠道。
- 是否每个编号只包含一个完整触发条件下的最小业务结论。
- 是否只在条件差异可能产生不同结论、独立回复或证据覆盖差异时拆分。
- 是否每条产品回复都与原问题一一对应。
- 是否存在只回答一部分却被整体关闭的问题。
- 是否因用户希望推进或避免继续追问而绕过已识别的证据缺口。
- 是否重复询问 PRD 已明确事实。
- 是否把复用基座内部能力误判为本需求阻断。
- 建议新增和建议修改是否具备唯一事实依据。
- 是否由 Agent 完成全部语义判断。
