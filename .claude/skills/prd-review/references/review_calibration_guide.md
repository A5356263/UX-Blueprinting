## 1. 目的与边界

本文件用于提高审查敏感度和路由判断稳定性。

它只能提供：

- 容易遗漏的检查方向。
- 领域风险启发。
- 误判边界。
- 路由校准案例。

它不能提供：

- 当前业务事实。
- 固定领域路由。
- 阻断问题答案。
- 复杂度评分。
- 体验策略。

正式事实仍只来自 PRD、正式知识和产品回复。

## 2. 使用顺序

只在 `SKILL.md` 的两个固定节点使用本文件：

1. P6：根据已经完成的业务事务模型，读取相关跨域边界、领域启发和证据门禁用例，反查遗漏或误删；随后返回正式证据验证，再进入 P7。
2. P10：只读取第 6 节的 Handoff 反例，完成校准后返回 P10。

不得先看领域词，再决定只读取某个固定领域。

本文件不能覆盖正式规则，也不能独立驱动审查、问题关闭或 Handoff。

## 3. 通用变化校准

业务骨架变化的六项正式检查统一使用 `review_rules.md` 第 3.7 节。本节只保留误判提醒。

局部界面变化也要先证明没有改变业务骨架。业务名称看起来复杂，也不能直接推断业务骨架发生变化。

## 4. 容易误判的跨域边界

### 4.1 非标准人员身份

涉及外部人员、外包人员、顾问或供应商人员时，检查：

- 是新增展示对象，还是进入员工主数据。
- 是否进入组织、汇报、账号、权限或审批体系。
- 是否与正式员工共用字段、状态和生命周期。
- 退出或失效后，关联权限与任务如何收口。

### 4.2 角色化首页与入口分发

涉及不同角色看到不同首页、入口或工作台时，检查：

- 只改变展示，还是改变应用可见范围。
- 多角色用户如何命中、合并或切换。
- PC、移动端和其他渠道是否共享分发规则。
- 深链、身份和权限变化是否影响入口。

### 4.3 统一待办与任务中心

涉及统一待办、统一任务中心或统一任务视图时，检查：

- 只是聚合入口，还是统一任务对象。
- 状态语义、操作权限和回写责任是否统一。
- 来源系统失败时，任务状态由谁负责。
- 完成、撤回、转交和过期如何同步。

### 4.4 权限配置范围

同一需求同时出现角色权限、功能权限和数据权限时，先区分业务关系：

- 可以查看什么。
- 可以申请什么。
- 管理员可以配置什么。
- 审批通过后实际授予什么。

一个范围被用于查看，不等于它也属于申请范围。

PRD 已明确申请配置只包含角色和功能权限时，禁止再次询问数据权限是否可申请。

### 4.5 复用成熟基座

复用成熟基座的完整规则统一使用 `knowledge_usage_guide.md` 第 10 节。以下内容只用于识别误判：

误判提醒：

- “基座支持”不等于“本期启用”。
- “复用基座”不等于“完整继承所有能力”。
- 审批人等业务角色属于当前任务闭环，但不代表 PRD 必须重新定义基座内部页面和通用操作。
- 三个边界只用于复用继承，不能替代完整业务审查。

## 5. 领域审查启发

以下内容只帮助发现风险。命中后必须回到正式知识验证。

### 5.1 协同办公

重点关注：

- 任务、审批、消息和业务单据的关系。
- 发起、路由、通知、处理和归档链路。
- 参与角色、节点状态、截止时间和来源应用。

业务骨架变化信号：

- 改流程对象或状态机。
- 改流程定义权或可见范围。
- 改跨系统状态回写。
- 统一多个应用的任务模型。

局部扩展示例：

- 在既有规则内增加催办、转交、批量处理或超时提醒。

误判提醒：

- 不能因为出现审批、待办或消息就判定业务骨架改变。
- 必须确认是展示扩展，还是对象、状态或回写变化。

### 5.2 人事服务

重点关注：

- 员工、组织、岗位、法人、任职和合同关系。
- 入职、转正、调岗、离职等生命周期。
- 敏感信息和关联权限。

业务骨架变化信号：

- 改员工生命周期状态机。
- 改员工与组织、法人、岗位或项目关系。
- 统一外部人员与员工模型。
- 人事异动联动薪资、考勤、权限或门户。

局部扩展示例：

- 在既有人事流程内增加材料补传、自助维护、批量处理或通知。

误判提醒：

- 页面字段变化不能直接推断主数据变化。
- 非标准人员身份必须按 4.1 反查。

### 5.3 薪税代发

重点关注：

- 员工、薪资项、计税规则、税务主体和银行账户。
- 采集、算薪、核薪、报税、代发、工资单和对账链路。
- 批次状态、保密范围和失败结果。

业务骨架变化信号：

- 改算薪或计税规则。
- 改批次状态、审批或生效机制。
- 改多主体申报、银行付款或对账回写。
- 改工资明细保密和数据隔离。

局部扩展示例：

- 在既有批次和计算规则内增加失败明细、结果解释或局部操作。

误判提醒：

- 出现工资、税局或银行不等于业务骨架一定改变。
- 必须确认是否只是展示既有结果。

### 5.4 财务费控

重点关注：

- 申请、预算、发票、报销、付款、凭证和档案关系。
- 申请、消费、报销、审批、付款、入账和归档链路。
- 预算、付款、入账、归档和凭证状态。

业务骨架变化信号：

- 改预算占用、释放、结转或冲回。
- 改发票验真、付款、入账或凭证映射。
- 改电子归档、银企直联或总账回写。
- 统一费用、采购、付款和档案模型。

局部扩展示例：

- 在既有预算和审批框架内增加费用类型、批量操作、提醒或差异查看。

误判提醒：

- 出现报销、发票或付款不等于必须扩大审查范围。
- 必须根据当前对象、规则和依赖决定。

### 5.5 平台门户

重点关注：

- 身份、应用目录、可见范围、入口分组和深链。
- 身份识别、入口分发、应用启动、任务返回和常用沉淀。
- PC、移动端和其他渠道的一致性。

业务骨架变化信号：

- 改角色可见性、身份识别或应用分发。
- 改 SSO、启动上下文或深链规则。
- 建设可配置工作台或跨企业应用共享。
- 统一多端入口规则。

局部扩展示例：

- 在现有身份和分发规则内增加分组、常用入口、搜索或推荐内容。

误判提醒：

- 卡片、分组和首页名称变化通常不能证明分发模型变化。
- 角色首页必须按 4.2 反查。

### 5.6 管理后台

重点关注：

- 租户、身份、权限、配置、版本、日志和密钥。
- 配置、审核、发布、生效、监控、审计和回滚链路。
- 生效范围、生效时间、操作人和版本关系。

业务骨架变化信号：

- 改权限或数据隔离边界。
- 改配置生效、审核、定时或灰度机制。
- 改多租户、多法人或多项目隔离。
- 改审计、日志、密钥或回滚机制。

局部扩展示例：

- 复用现有生效和权限模型，增加配置项、批量操作、模板或查询。

误判提醒：

- 出现后台、权限或配置不等于业务骨架改变。
- 必须确认是否改变生效、隔离、审计或回滚。

## 6. Handoff 校准案例

Handoff 的推荐判断只使用 `SKILL.md` 的 P10。本节只保留需求大小与体验取舍不一致的反例：

校准案例：

- 调整一个字段，但字段会改变用户对状态的理解：可以推荐 UXB。
- 新增不可逆操作，但解释内容和时机尚未定：可以推荐 UXB。
- 重构复杂状态链，但上游已明确体验顺序和反馈原则：UXB 可以标记为“可选”。
- 仅调整字段顺序，且没有新的理解或流程取舍：UXB 可以标记为“可选”。

判断完成后返回 `SKILL.md` 的 P10。不得从案例生成新的推荐规则。

## 7. 证据与场景分流校准用例

以下用例只用于回归规则，不提供当前需求事实。

问题原子性统一使用 `review_rules.md` 第 3.8 节。以下用例只检查该规则是否被正确执行。

### 7.1 固定继承

输入：

- PRD 明确复用现有审批任务。
- 正式知识明确拒绝操作固定要求填写原因。
- 本期不修改该规则。

预期：

- 不询问拒绝原因是否必填。
- 审核记录在对应场景写为业务事实补充，并定位正式知识来源。
- 需求基线只记录当前任务需要理解的继承结论。

### 7.2 条件继承

输入：

- 基座支持拒绝原因。
- 是否必填可配置。
- 不同配置会改变审批任务完成条件。
- PRD 没有说明本期配置。

预期：

- 形成一个原子待确认项。
- 不把“支持”写成“本期必填”。

### 7.3 与复用无关的业务缺口

输入：

- PRD 没有复用外部基座。
- 任务成功后的下一业务节点没有定义。

预期：

- 按完整业务闭环规则形成阻断问题。
- 不使用输入、输出、配置边界排除该问题。

### 7.4 原问题关闭并产生新问题

原问题：

```text
审批人按什么规则确定？
```

产品回复：

```text
按申请人所在组织负责人确定；审批通过后如果授权失败，后续处理暂未确定。
```

预期：

- 原问题关闭。
- 授权失败处理形成新的原子候选问题。
- 新问题不反向污染已确认的审批人规则。

### 7.5 模糊回复

原问题：

```text
同一权限正在审批时，再次提交如何处理？
```

产品回复：

```text
提交后怎么可能还有这个权限？
```

预期：

- 保存产品原话。
- 原问题保持 `open`。
- 即使随后只收到“继续”或“不要再问”等推进性表达，仍保持 `open` 并严格停止。
- 用户明确给出业务结论或范围决定时，重新按现有关闭依据复核。
- 不生成“禁止重复提交”等事实。

### 7.6 问题移出与无来源事实

输入：

- Agent 误问基座内部细节。正式知识和当前业务边界能够共同证明：当前需求不配置该细节，不提供相关输入，不识别或处理该细节产生的差异结果，且该细节不改变当前任务的成功、失败、状态或下一节点。
- PRD 只说明失败为终态，没有恢复机制。

预期：

- 错误问题移出，只记录“该规则由基座内部承接，本需求不定义”，不标记为产品确认，也不生成具体继承事实。
- “失败后可以重试或联系管理员”不能进入需求基线。

### 7.7 体验定案事项与待确认的边界

输入：

- 员工、权限阻碍触发条件、提交结果和后续处理均已确定。
- 可申请范围的配置规则尚未确定。
- PRD 未说明员工从哪个体验位置发现并进入申请任务。

预期：

- 可申请范围的配置规则形成待确认。
- 在审核记录中标记体验定案事项。
- 待确认与体验定案事项可以同时出现在同一场景。
- 不向产品询问入口控件、页面位置或组件形式。
- 不写候选方向或推荐结论。

若入口会改变谁能发起、什么条件下可发起、可申请范围、需要传递的业务上下文或后续处理结果，则形成待确认，不标记体验定案事项。

### 7.8 场景不能停在中间节点

输入：

- PRD 只说明用户提交任务。
- 未说明提交后的成功、拒绝、中断或下一责任方。

预期：

- 正式知识能唯一证明缺失节点时，写为业务事实补充。
- 否则形成待确认。
- 不得因为后续可以由 UXB 设计而标记体验定案事项。

### 7.9 需求初识不补全事实

输入：

- PRD 说明目标和主要任务。
- PRD 未说明当前处理方式和完成结果。

预期：

- 需求初识中对应五问写“PRD 未说明”。
- 不读取知识补写五问，也不在该步骤产生待确认、业务事实补充或体验定案事项。
- 后续审查仍按正式规则识别是否存在业务缺口。

### 7.10 已知事实覆盖待确认

输入：

- 正式知识唯一证明某项固定业务结果。
- 审核记录已形成对应业务事实补充。
- 候选待确认以另一种表述询问同一对象、条件和结果。

预期：

- 删除候选待确认。
- 不因标题不同、场景不同或对象名称相同而机械合并其他事项。

### 7.11 明确结果与实现机制

输入：

- PRD 已明确动作完成后的业务结果。
- 候选待确认只追问系统内部采用什么方式完成该结果。

预期：

- 删除候选待确认。
- 若不同对象、范围或异常会产生不同业务结果，只询问该业务差异，不询问内部实现。

### 7.12 开放式兜底提问

输入：

- Agent 未定位到具体业务缺口。
- 候选问题为“是否还有其他规则”或“请补充完整流程”。

预期：

- 删除候选问题。
- 不要求产品替 Agent 执行笼统补全。

## 8. 禁止事项

- 不输出领域复杂度评分。
- 不让领域名称决定审查深度。
- 不把本文件内容写入需求基线。
- 不用案例替代 PRD、正式知识或产品回复。
- 不因卡片未覆盖某领域而降低审查强度。
- 不在 PRD Review 中展开体验策略。
