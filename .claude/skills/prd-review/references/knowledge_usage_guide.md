# PRD Review 知识消费规则

本文件只定义正式知识如何定位、读取、覆盖和用于证据判断。主流程顺序、调用节点和返回位置只以 `../SKILL.md` 为准。

## 1. 正式知识来源和权威边界

正式消费根目录：

- `.claude/skills/knowledge-wiki/knowledge/`

各类内容的作用：

- `wiki/index.md`：只负责选择知识类型、业务集合或主领域。
- 业务集合 README、领域 README：只负责边界、文件路由、条件依赖和停止条件。
- `raw/业务/**` 中承担任务、能力、规则、状态、对象、页面或字段等事实责任的文件：正式业务事实来源；只以当前领域实际存在的责任文件为准。
- `问答与差异.md`：操作指引、排障、帮助入口、外部动态、收费协议、差异追溯和检索线索。普通问答正文不是正式业务事实证据。
- `问答与差异.md` 中出现“正式事实”链接时：链接目标才是事实证据，必须读取目标责任文件；问答摘要不能替代目标正文。
- `wiki/questions.md`：显式知识缺口入口，不能作为确定事实。
- `candidates/**`：非正式候选，不得进入需求基线。
- `templates/**`：知识维护模板，不进入消费路径。
- 项目外 FAQ、历史问答或讨论材料：只能作为检索线索，不能因进入 `raw/` 的问答文件而自动成为正式事实。

PRD Review 只消费业务知识。不要读取设计准则和交互模式完成业务审查。

## 2. 消费目标

知识消费只服务一个目标：

> 判断当前需求涉及的业务闭环是否完整。

具体用于：

- 确认当前系统事实。
- 识别本次新增、修改、移除或沿用的对象。
- 发现受影响的角色、权限、规则、状态、异常、数据和依赖。
- 验证 PRD 对当前能力的描述是否准确。
- 发现 PRD 漏写的变化影响。

知识不能用于：

- 否定产品明确提出的目标变化。
- 替产品决定新规则。
- 生成体验策略。
- 生成页面或交互方案。

## 3. 初步定界模型

完整读取 PRD 后，先建立只用于知识路由的初步定界模型：

- 业务对象。
- 关键动作。
- 当前状态与目标状态关系。
- 角色和适用范围。
- 预期业务结果。
- 已明确的外部依赖。

初步定界模型建立后再选择主领域。

本节不判断完整业务闭环，不生成候选问题，也不替代 `review_rules.md` 第 3 节的完整业务事务模型。完成主领域和实际依赖领域定位后，返回 `SKILL.md` 的 P3。

不得只根据需求标题、页面名或单个关键词确定领域。

## 4. 主领域定位

按以下顺序执行：

```text
读取 wiki/index.md
→ 根据业务对象、动作和结果选择主领域
→ 进入主领域 README
→ 学习实际文件路由
→ 读取承担当前事实责任的 raw 文件
→ 按顶部导航读取命中章节
```

规则：

- index 和 README 不是业务事实。
- 不得把关键词固定映射成唯一文件。
- 不得猜测不存在的目录或文件。
- 不得遍历 `raw/` 或逐文件试读。
- 路由没有命中正式知识时，记录知识缺口。

## 5. 依赖领域触发条件

只有以下条件同时成立时，进入依赖领域：

1. 主领域 README 或正式原文明示依赖。
2. 当前需求实际触发该依赖。
3. 依赖事实会改变对象、角色、权限、规则、状态、异常、结果或审计结论。
4. 主领域知识不能独立解释该任务结果。

读取依赖领域后，必须回到主领域完成闭环。

不得因为业务相邻、关键词相似或“可能有关”无限扩读。

## 6. 正式原文读取规则

- 长文档先读顶部适用范围和快速导航。
- 只读完整命中章节，不读孤立句子。
- 只有正式责任文件存在冲突、缺口，或当前任务需要操作、排障、外部动态、收费协议或来源追溯时，才读取 FAQ 或问答文件的命中问题块及必要上下文。
- 不得用 FAQ 或问答普通正文关闭业务缺口、删除候选问题或写入需求基线。
- 页面与字段类文件只读命中页面或对象章节。
- 命中局部知识后，不得在必要关联事实尚未闭环时停止。
- 未被当前需求触发的相邻知识不得扩入。

每项用于审查的知识必须能说明：

- 支撑哪个当前事实。
- 适用哪个对象和角色。
- 适用范围、条件和例外是什么。
- 会影响哪个审查结论。

## 7. 知识覆盖模型

### 7.1 动态补读

先从当前事务定位承担直接事实责任的正式章节。每读完一个命中章节，基于当前需求已明确的对象、角色、动作、状态和结果，依次判断是否必须补读：

1. 动作受资格、权限、条件、数量、计算口径或配置生效范围影响：读取对应规则章节。
2. 动作改变状态，或存在失败、拒绝、部分成功、不可恢复或恢复结果：读取对应状态章节。
3. 动作产生下一任务、支付、对账、报销、同步、数据或审计结果：读取对应任务章节和实际触发的依赖领域。
4. 正式责任文件不能证明当前对象关系、结果或依赖：记录知识缺口；不得用问答、常识或相邻主题补齐。

本节是按当前事务扩读，不是预设业务动作清单。未被当前需求触发的相邻能力、规则、状态或领域不得扩入。

先按角色和任务场景建立知识主题，再按当前需求实际触发范围覆盖：

```text
业务对象
→ 角色
→ 动作
→ 权限
→ 状态
→ 规则
→ 异常
→ 业务结果
→ 依赖系统
→ 数据与审计
```

“覆盖全部相关知识”不是通读整个领域，而是所有会改变本次闭环结论的相关事实都得到核验。

主领域中只要直接影响本次业务闭环，就必须读取对应的完整命中章节。

同一知识主题命中多个正式文件时，必须读取全部命中文件，禁止读取第一个文件后停止。

每个任务场景必须核对：

- 执行角色和权限。
- 业务对象和动作。
- 当前规则和状态。
- 成功、拒绝、中断和终态。
- 实际触发的系统、数据和审计影响。

依赖领域只读取当前需求实际使用的机制，不审查该领域的完整能力。

成熟基座只读取本需求使用的输入、输出和差异。未被本需求改变的转派、委托、超时和内部异常机制不展开审查。

## 8. 覆盖记录

Agent 在内部维护：

| 覆盖节点 | PRD 目标描述 | 当前正式事实 | 关系 | 审查结果 |
|---|---|---|---|---|
| 对象、角色、动作等 | PRD 原文位置 | raw 文件与章节 | 沿用、新增、修改、移除、无法确定 | 已闭环、阻断、不适用 |

覆盖记录只用于内部检查和来源追溯，不作为用户产物。

## 9. 当前事实与目标状态关系

### 沿用

PRD 声称沿用当前能力时：

- 目标描述必须与正式当前事实一致。
- 不一致且未说明变化时，形成阻断。

### 新增

检查：

- 新能力与当前对象和规则如何关联。
- 是否产生新角色、权限、状态或依赖。
- 当前能力是否需要同步调整。

### 修改

检查：

- 修改前后的目标差异。
- 适用范围和生效条件。
- 旧规则如何处理。
- 历史数据和下游影响。

### 移除

检查：

- 被移除能力的替代或终止结果。
- 历史数据处理。
- 仍依赖该能力的角色和下游。
- 权限、状态、接口和审计如何收口。

正式知识不同于目标状态，不等于冲突。只有变化关系和影响无法闭环时才阻断。

## 10. 复用基座继承审查

需求明确复用现有能力，或当前任务依赖成熟审批、通知、权限、支付、组织、消息等基座时，执行本节。

本节是知识消费的条件子流程。它不能替代角色、任务、规则、状态、异常、数据和结果审查，也不能过滤与复用无关的业务缺口。

### 10.1 读取要求

按领域 README 的实际路由，读取能够证明以下内容的正式文件：

- 基座能力范围。
- 固定规则。
- 可配置能力。
- 当前任务使用的输入。
- 当前系统消费的输出。
- 已知缺口。

README 只负责路由。README 已指向具体文件时，未读取对应文件不得停止。

### 10.2 三个边界

- 输入边界：当前系统需要向基座提供什么，哪些输入会改变任务能否开始、处理或完成。
- 输出边界：当前系统需要消费什么结果，哪些结果会改变当前业务状态、结果或下一任务。
- 配置边界：当前需求是否需要选择、修改或覆盖基座配置。

三个边界只用于复用继承审查。

### 10.3 继承结论

- `固定继承`：正式知识证明为固定行为，不依赖当前需求选择，且本期没有修改、关闭或覆盖。直接继承。
- `条件继承`：基座支持多个结果、规则可配置、是否启用由当前业务选择，或不同配置会改变当前任务。PRD 未明确时进入阻断判断。
- `当前需求决定`：触发原因、发起角色、业务对象、业务输入、结果回写和当前系统后续处理。PRD 未明确且影响闭环时进入阻断判断。

“支持”“可配置”“开启后可用”不能证明当前需求已经启用。

### 10.4 基座内部候选问题移出边界

先完成 10.3 的三类继承判断。

正式知识已经以固定继承唯一回答的候选问题，继续按现有事实回查规则删除，并保留当前任务需要理解的固定继承事实，不执行本节的问题移出。

本节只处理完成三类继承判断后仍没有唯一答案的基座内部细节，用于判断围绕该细节产生的候选问题是否属于当前需求。以下条件不新增继承类型，也不改变三类继承结论。

只有同时满足以下条件，候选问题才可移出问题集合：

1. 当前需求不选择、修改或覆盖相关配置。
2. 当前系统不需要向基座提供与该细节有关的业务输入。
3. 当前系统不需要识别该细节产生的结果差异，也不需要依据差异执行不同的状态更新、后续动作或责任处理。
4. 该细节不改变当前任务的成功、失败、状态或下一节点。

仅消费基座标准最终结果，不等于消费该内部细节。

是否影响当前业务闭环，按现有完整任务链和阻断判定规则判断。页面是否展示该细节不能作为移出依据。

移出只表示“该规则由基座内部承接，本需求不定义”。不得据此写成“本期已启用”或“本期继承某项具体策略”。

任一条件不满足，且该细节影响输入、输出、配置或当前业务闭环时，进入现有阻断判断。

### 10.5 知识缺口

出现以下任一情况时，不得自行推断继承范围：

- 正式知识不存在。
- 正式知识只说明能力存在，没有说明固定规则。
- 正式知识标记为 `[GAP]`、`[QUESTION]` 或 `[CONFLICT]`。
- 不同正式文件相互冲突。

影响输入、输出或配置边界时形成阻断问题。不影响当前任务闭环时只在内部记录。

## 11. 反向检索

对关键动作执行反向检索，补充正常路径容易遗漏的限制。

触发条件：

- 动作不可逆。
- 动作受权限控制。
- 动作改变关键状态。
- 动作影响下游。
- 正向知识不能证明完整结果。

围绕当前动作，在已经命中的正式文件和明确依赖中定位：

- 禁止或不支持。
- 不可撤回或不可恢复。
- 已关联或已被使用。
- 权限限制。
- 状态限制。
- 重复与并发。
- 外部失败和部分成功。

反向检索仍须遵守正式路由。不得为搜索这些词遍历整个 raw。

## 12. 证据一致性

每条知识结论必须与原文保持相同的：

- 对象。
- 关系。
- 角色。
- 适用范围。
- 条件。
- 例外。
- 表达强度。

禁止：

- 把局部场景提升为全局规则。
- 把“可配置”“开启后”“支持”改写为固定前提。
- 互换不同角色或业务主体。
- 把示例、典型路径或局部 FAQ 当作完整清单。
- 根据文件更新时间自行选择冲突一方。

封闭枚举只有在命中承担当前问题直接事实责任的完整正式清单时才能成立。

## 13. 知识缺口与显式问题

出现以下情况时记录知识缺口：

- index 或 README 无法定位正式事实。
- 正式原文缺少当前能力说明。
- `[GAP]`、`[QUESTION]` 或 `[CONFLICT]` 影响本次审查。
- 正式事实的对象、范围或条件无法与 PRD 对齐。

处理方式：

- 影响业务闭环：形成阻断问题。
- 不影响本次业务闭环：不纳入问题单。
- 不得遍历 raw 补救。
- 不得用 Agent 常识补齐。

## 14. 停止条件

同时满足以下条件才停止知识读取：

1. 核心对象和关系已覆盖。
2. 关键角色、动作和权限已覆盖。
3. 核心状态和规则已覆盖。
4. 会改变业务结果的异常已覆盖。
5. 被触发的系统、数据和审计依赖已覆盖。
6. 当前事实与目标状态的变化关系已明确。
7. 所有影响闭环的知识缺口都已进入阻断判断。
8. 继续读取不会改变审查结论。

全部条件满足后，返回 `SKILL.md` 的 P4 建立完整业务事务模型。任一条件不满足时，不得提前返回，也不得开始生成问题。

## 15. 失败与阻断处理

- 正式知识无法访问：说明缺失位置；影响闭环时阻断。
- 路由存在但目标文件不存在：记录知识缺口；不得猜测替代文件。
- 正式文件存在冲突：保留双方来源；影响目标判断时阻断。
- 非正式材料与正式知识不同：不能覆盖正式知识，只能触发核验。
- PRD 明确改变当前规则：按目标状态审查，不把差异本身当作阻断。

## 16. 禁止事项

- 不读取设计准则或交互模式完成 PRD 审查。
- 不固定费控、人事或其他领域的绝对路由。
- 不设置领域优先级。
- 不限制最多读取几个相关领域。
- 不计算知识覆盖率或可信度分数。
- 不自动判断知识时效。
- 不把行业惯例、竞品或 Agent 经验当作知识。
- 不向用户展示知识路由、覆盖矩阵或完整推理过程。
- 不使用脚本判断知识是否适用、是否冲突或是否足够。
