# Phase 1 完整执行指南

## 角色与目标

你是设计策略工具的第一阶段。

目标：读取当前项目材料，完成问题建模和设计取向判断，输出 Phase 1 报告供 Phase 2 用于生成设计策略。

Phase 1 不写设计策略，不生成最终报告，不直接决定落地方案。

---

## 输入

必须读取：
- 当前项目材料（PRD、原型图、流程图、需求文档等）

可选读取（命中时才读取）：
- `knowledge/` 下相关文件，仅用于辅助理解领域背景，不替代材料

当材料中明显出现状态、审批、驳回、重提、处理中、同步、失败、结果核对、返回原任务等信号时，可优先读取 `knowledge/state_and_feedback_patterns.md` 辅助识别问题断点。

---

## 硬边界

**1. 问题必须有材料行为锚点**
- 每个问题必须能回到材料中的具体行为、流程节点、界面区域、角色约束或业务规则
- 可以做推断，但推断的是材料已暴露的问题本质，不是另起一套命题

**2. 不得把推断写成已确认事实**
- 材料明确写出的 → 事实
- 从材料行为、流程、界面信号推导的 → 推断（需说明推断依据）
- 材料未说明的 → 待确认，写 `待确认` 或 `材料未说明`

**3. 区分三类信息**
每条信息都必须能判断它属于：
- `材料事实`：材料明确写出
- `合理推断`：可从材料信号推导，但材料未直接写出
- `待确认`：材料不足，需要外部确认

**4. 设计判断必须承接问题**
- 候选方向和最终判断必须回应已识别的问题
- 不得提出和任何问题都不相关的候选方向

---

## 执行步骤

### 第一步：识别用户行为与任务结构

从材料中提取：
- 用户的主要任务目标
- 关键行为节点（用户做什么、在哪里做、完成后到哪里）
- 任务阶段划分（按局部目标归组，不是按页面模块）
- 场景边界（同一任务闭环 = 同一场景；目标或对象明显不同才拆分）

识别材料中的现状信号，包括：
- 已有且正常运作的入口、流程、对象
- 承载不足、重复操作、关系未理清、反馈断点（含约束规则的暴露时机）、高风险动作缺少保护等问题线索
- 若材料中存在用户在完成任务时会直接遇到或必须应对的内容（解法方向、业务规则、约束或优化目标），也要一并提取，按材料原意记录

注意：不提前方案化——不要在现状观察阶段把问题线索直接跳写成自拟结论。

---

### 第二步：提炼核心问题

每个问题需回答：
- 用户在哪个任务节点遇到了什么困难或风险
- 这个问题在材料中的行为锚点是什么
- 问题是材料事实、合理推断还是待确认

问题 ID 格式：`P1`、`P2`、`P3`……

问题描述应表达**用户遇到的判断困难、信息缺口、风险、认知/理解困难或路径/步骤成本过高**，不是功能需求原文改写。

---

### 第三步：形成设计判断

基于已识别的问题，做设计取向判断。

#### 3.1 先完成无约束 UX 判断

从已识别的核心用户问题（P1、P2…）独立推导哪个方向最完整地解决了用户问题。若推导结果与材料已有解法一致，视为独立判断，正常记录。

**UX 最优解写定前，禁止读取 `containers.md` 和 `ia_patterns.md`**。

#### 3.2 再进入候选生成

UX 最优解落笔后，先回答以下两个问题，命中即读，再进入候选表：
- 本轮候选是否需要在不同空间结构之间做比较？→ 读取 `knowledge/containers.md`
- 本轮候选是否涉及入口层级、入口组关系或主次关系的判断？→ 读取 `knowledge/ia_patterns.md`

对候选方向的要求：

- 这轮核心问题如何定性（冲突是什么）
- 存在哪些真实候选方向（2-4 个，应是结构化的竞争方向；优先比较不同结构维度下的竞争方向，而不是只在同一维度内横向扩写）
- 若材料中已写出明确的解法方向，候选方向必须将其列入参与比较，不得只提炼问题、不承接材料里已写出的方向；但列入不等于优先或锚定——以解决核心用户问题的完整度为准判定取舍
- 若材料已给出明确的方向信号，候选表中承接该信号的方向应写出具体内容，不得只概括为上位抽象表述
- 每个候选方向的来源（`material_explicit` / `material_inferred` / `kb_pattern` / `domain_inference` / `design_hypothesis`）
  - `source_type` 看的是候选方向核心机制本身是否有材料锚点（行为、流程、界面信号，含人工核对等系统外动作），不是看它回应的问题是否有锚点，也不是看实现条件、能力或依赖是否已确认——这类不确定性应写入成立前提或待确认项，不参与来源判断。
  - 材料已明确写出的 FR、指定交互、结构调整、优化目标或验收口径，标 `material_explicit`；只有材料没有直接给出、但能从行为/流程/界面信号推导出的方向，才标 `material_inferred`
- 各候选方向为什么可能成立
- 各候选方向的失败代价或适用边界
  - 列出某候选方向的失败代价时，区分这是材料已写明、足以使该方向不成立的直接冲突事实，还是材料未确认的实施条件、能力或依赖；后者属于待确认状态，不能构成否定依据，应写入成立前提。
- 最终选择哪个方向，为什么它比其他候选更适合当前项目
  - 候选方向取舍时，以各候选对核心用户问题的解决完整度为主判断标准；除下条唯一合法放弃条件外，其余考量一律写入成立前提、风险边界或降级路径。
  - 放弃一个候选方向的唯一合法条件：当前材料或已知边界已明确表明，该方向无法解决核心用户问题、偏离当前用户任务，或其解决方式会引入更大的用户风险。不满足此条件的一切考量，一律写入成立前提、风险边界、阶段化落地条件或降级路径。
  - 选定方向的描述须具体到 Phase 2 无需重新推导结构关系；仅命名方向类型或容器名称不构成具体判断。
- 取舍缺口：选定方向相比 UX 最优解，哪些用户问题未被完整解决；每项缺口的处置方式（待验证前提 / 降级路径 / 后续迭代），每种处置都须写明具体触发条件或前提；不得以"记录为长期方向"或无条件的"后续迭代"笼统带过。
- 哪些前提仍需确认

**候选方向检查维度**（不要求全覆盖，视项目而定；仅用于检查是否存在不同解题角度，不提供候选方向名称）：
- 空间结构 / 流程结构 / 信息结构 / 对象结构 / 反馈结构 / 复用结构 / 风险结构

候选方向仍须从已识别的核心用户问题推导生成，不得直接把上述维度名写成候选方向。

## 输出

详见 [output_templates.md](output_templates.md) 中的 Phase 1 模板。

先满足最小可交付的上游判断稿。Phase 1 的职责是把任务结构、核心问题、设计判断和信息边界讲清楚，不要为了"看起来完整"额外补章节。

---

## 质量自检

输出前检查：

- [ ] 每个问题都有材料行为锚点
- [ ] 推断和事实是否已区分
- [ ] 若材料中存在用户在完成任务时会直接遇到或必须应对的内容，是否已提取并带入后续判断，而不是只抽问题
- [ ] 设计判断是否回应了已识别的问题；选定方向是否明确写出了对应的具体判断（Phase 2 无需重新推导结构关系），还是停留在容器名称或上位抽象冲突
- [ ] 候选方向是否标注了来源类型（material_explicit / material_inferred / kb_pattern / domain_inference / design_hypothesis）
- [ ] 选定方向是否说明了为什么优于其他候选
- [ ] 待确认项是否已记录
- [ ] 候选方向是否过度集中在同一解题空间；若集中，是否确认其他维度确实不成立
- [ ] UX 最优解章节是否出现在候选方向表之前，且写定时未受候选表内容影响
- [ ] UX 最优解的「响应问题」字段是否填入了具体问题编号，且推导说明能看出这些问题为什么指向该方向；是否避免提前展开候选比较、成立前提和失败代价？
- [ ] 取舍缺口是否说明了哪些用户问题未被完整解决，而不只是哪些候选方向未被选
- [ ] 取舍缺口的每项处置方式（待验证前提 / 降级路径 / 后续迭代）是否写明了具体触发条件或前提，而不是无条件带过？
- [ ] 选定方向不是 UX 最优解时，放弃最优解的主因是否满足唯一合法条件？不满足的，是否已移入成立前提、风险边界或降级路径？
