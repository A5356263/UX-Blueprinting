# Page Spec

本 Skill 同时负责页面级方案推导与交付规格。设计推理必须完成，但正式产物只写已决定、可定位、可生成的页面事实，不输出体验蓝图式长叙事。正式产物为页面设计规格 Markdown。

先按输入契约验证事实和增强材料，再读取知识、推导方案、核对页面事实并自检，最后返回页面规格。

## Step 0 · 运行入口与来源门禁

### Step 0.2 · 绑定本轮来源

先确定用户本轮明确指定的文件、附件或上游产物及其需求身份，再选择输入模式。不得扫描 input/ 自选文件，也不得把不同需求的基线、增强产物或 Handoff 拼接为同一轮事实。当前会话记忆不能代替本轮正式文件读取。

- 正式基线直达：只消费工作台绑定的本轮同源正式基线。完整读取 Markdown 全文及 §10 体验定案；重点章节不是正文白名单。§10 已确认约束必须关联到角色任务、页面、状态或异常；待定案的页面体验取舍在本 Skill 内结合设计知识完成。业务事实仍以基线为权威。
- 用户指定原始需求或设计材料：用户可以不经 PRD Review 指定 PRD、截图、交互稿或其他材料。标明其实际证据身份，不冒充正式基线。只有角色与任务、起止与对象关系、范围权限、会影响页面的规则和字段约束、状态异常、动作结果与反馈足以闭环，且没有会改写主流程或页面实体的未决事实，才能称完整交付。只够局部设计时明确可确认范围与待确认项；关键事实不足以形成可靠页面方案时停止并请用户补充。未经 PRD Review 本身不是自动降级理由。
- Problem Framing 独立路径：只在用户明确指定这一来源时，完整读取同源 problem_framing.md；不得用其他需求的基线或 UXB 冒充该路径。按 Step 0.4 执行 3+1 门禁。

正式基线与用户指定材料同时存在时，以本轮指定来源绑定需求身份；同一需求的正式基线是已确认业务事实权威。出现实质冲突时停止并报告，不静默选择。原始需求不得反向覆盖正式基线。

### Step 0.3 · 可选增强及冲突处理

UXB、Stories、Journey 只有本轮明确采用、来源与本轮需求一致且各自门禁通过时才消费。Edge 是可选状态补强：已有与本轮需求同源且有效的正式产物时按下述边界消费，用户明确排除时不消费。任何增强产物的存在都不自动触发其他 Skill；正式基线模式在这些增强均缺失时仍可执行。

- UXB：完整读取同源 `uxb_output.md`，承接已确认的整体方向、必要局部策略、业务触点与信息架构承载、关键情境中的信息与选择范围、结果理解、必要的跨触点衔接及依赖；逐项核对适用于本轮页面的体验决定有页面或流程落点，再推导页面内呈现与交互。不把 UXB 当业务规则来源或现成页面结构。
- Stories：完整读取同源 `stories.md`，消费来源与方向、全部 Story 的角色、场景、目标、优先级、来源依据、完成标准、设计触点、风险或假设、范围与待确认问题；会改变方案的待确认项未关闭时停止。
- Journey：完整读取同源 `journey_analysis.md`，消费全部角色、阶段、目标、行动、触点、痛点、信心依据、风险、机会与转折；不能只读取阶段摘要。
- Edge：核对 edge_output.md 的需求身份和状态补丁范围，确认同源后完整读取；只补状态、异常恢复和文案，不改变主实体、父页、流程或页面结构。具体吸收边界见 references/edge_consumption_guide.md。
- 任何增强不得覆盖本轮正式基线；与基线冲突时停止并报告相应交接错误，不自动调用上游。未采用的历史产物一律不读取。

### Step 0.4 · Problem Framing 独立来源 3+1

仅在用户明确选择 Problem Framing 独立路径时检查：角色与成功目标、业务对象及本轮范围、关键状态与阻断三项是否明确，以及是否仍有会改写主流程、页面结构或关键交互的未决项。前三项全部通过且第四项不存在，才允许完整 Page Spec；否则只对已确认部分局部展开并显式保留，不宣称完整方案，不自动回跑上游，也不把 working_assumptions 当作已确认业务事实。正式基线直达和普通用户材料模式不机械套用此 3+1 门禁。

## Step 1 · 正式知识消费

正式基线提供业务事实，可选 UXB 提供体验约束，正式知识用于本轮现有产品承载、页面模式和具体交互选择。本 Skill 必须独立消费需要的知识；不得以 PRD Review、UXB 已读过为由跳过。只读取 knowledge-wiki Skill 内的正式 knowledge/，不触发其问答或入库流程。

先从本轮材料提取角色、对象、动作、状态、异常、结果及现有入口；当前材料不足以恢复父级承载页、成熟基座或现有能力时，从 `.agents/skills/knowledge-wiki/knowledge/wiki/index.md` 进入，按业务领域 README 或明确直达的设计知识 → 正式文件顶部导航，读取命中的完整规则块。index、README 和地图只负责路由，不能替代正式事实；不得猜目录、遍历 raw 或逐文件试读。

针对本轮入口、承载、行为、状态与反馈、回流的判断，从设计准则章节地图读取命中的完整章节。进入具体组织问题时，再读交互模式全局地图和命中的完整模式块。模式选择须结合本轮证据说明采用原因、排除相近模式，并检查“进入 → 理解 → 操作 → 反馈 → 恢复或完成 → 返回原任务”。只读支撑实际判断的信息，足以定案即停；高风险或跨角色、多状态任务按影响扩展，不按固定章节数量凑覆盖。

命中页面信息组织时应用 IA-04；涉及分步或选择时读取 BFM-01～BFM-04 及命中的选择模式，不能只凭字段数或整项任务最终提交而推出 Steps。需要设计知识选择、完整块边界、记录和反查时，读取 references/knowledge_consumption_guide.md 的对应小节。内部记录读取的文件、章节和具体决定及其页面落点，正式文档不展示知识覆盖表。

业务知识与正式基线冲突、UXB 与基线冲突、或缺少会改变方案的业务事实时停止并说明来源问题；不得自行补造业务规则。正式知识暂不可用时，报告知识缺口；只有缺口不改变本轮页面方案才可在明确边界下继续。

## Step 2 · 内部设计推导

在组织正式页面规格前，完整读取 references/design_reasoning_guide.md。按其顺序从全部角色与任务建立起点、动作、系统响应、异常恢复、结果、跨角色交接与稳定终点；识别任务内触发；将流程节点分为新增或修改、复用引用、系统处理；恢复发生变化的父级承载页；区分稳定信息、任务入口、候选集合、已选结果和历史记录；执行 Steps 门禁和生成前覆盖检查。只在内部保留推导与依据关系，不输出清单、矩阵、D 编号、旅程摘要或设计依据长表。

每一次选择都以该选择动作本身判断候选量与可枚举性、搜索或比较需要、后续联动和原任务上下文，决定直接展示、下拉或独立选择承载；不能把整项提交任务当作一次选择，也不设固定数量阈值。使用独立承载时，明确进入、选中、确认、回填、查看、重选和返回。把已选摘要、提交前核对与提交后业务结果分开判断；最终结果要有业务状态、反馈位置、信息保留、后续动作和稳定界面，不预设必须是独立结果页。

页面级设计可以确定承载、布局、入口和反馈；不得新增字段必填、权限、审批条件、业务状态、异常处理或数据保留规则。缺少会改变正式方案的业务事实时停止。内部推导完成后，按下文的完整实体登记、三类生成范围、结构、流程、文案与唯一职责规则形成一套确定方案。

## 页面交付边界与 Edge 状态补强

Page Spec 是页面生成契约，ASCII 线框、精确文案和模板变量都是正式内容。使用 Page、Drawer、Modal、Toast、Button、Input、Textarea、Select、Checkbox、CheckboxGroup、Radio、Switch、Table、List、Tabs、Tag、Tooltip、InlineError、EmptyState、LoadingState 等语义组件描述承载与交互角色，不绑定 UI 库、像素、颜色、字体或实现代码，也不负责高保真视觉和前端实现。

父页恢复先看本轮权威材料，足够时不重复查知识；不足时按 Step 1 的正式路由读取载体语义。弹窗和抽屉必须有父页，下级页面须有来源页；有独立菜单入口的顶级页面无需额外父页。材料或知识已给出的既有父页 ASCII、语义组件、主要区域、导航和操作应保留原有结构，再叠加本期变化，不凭局部新增区块重画整页；父页作为实体 0 排在子实体之前。知识未命中时不捏造既有结构；缺口会改变方案则停止，不改变时写明可确定的边界和影响生成的待确认项。

Edge 仅在 Step 0 确认同源且有效后作为状态补强。消费时读取 references/edge_consumption_guide.md；不得由 Edge 增加独立页面实体、改写父页关系、主流程或主方案。

## 页面事实组织规则

按以下 6 层组织本轮权威材料与内部设计结果；不保留上游材料章节结构。

### 第 0 层：页面摘要

在文档最顶部生成一个极简的定位锚点，固定 4 行：

- **产品领域**：从本轮权威材料和命中的正式知识中提炼所属产品模块与业务域（如"{产品模块} — {业务对象治理}"）
- **页面类型**：列出涉及的页面类型（弹窗 / 列表页 / 详情页等），优先标注主实体类型
- **用户角色**：从本轮权威材料的完整角色任务清单确定；合法采用的 Stories 或 Journey 只可补充，不得覆盖基线
- **核心任务**：用一句话概括用户要完成的核心任务（非叙事，只写动作和对象）

摘要不写叙事推导，不写用户目标和痛点，只写锚点信息。

### 第 1 层：生成范围 + 承载页面识别 + 实体识别

当前任务闭环从用户进入本次任务的承载页面开始，到用户获得成功、失败、阻断或取消结果并返回稳定界面为止。期间用户必须看到或操作的界面载体和独立界面状态都属于当前任务闭环。

实体登记与范围分类必须严格分开：

1. **完整登记**：从本轮权威材料与 Step 2 内部方案登记全部角色路径、入口、页面、弹窗、抽屉、父子关系、系统处理、复用引用、异常中的新载体及独立界面状态；将每个状态和反馈归属到对应实体。此步骤不得判断生成范围或提前过滤。
2. **统一分类**：完成登记、去重、信息收拢和父子关系建立后，才允许判断`生成`、`只引用不生成`或`不生成`。

完整登记须沿每条任务路径逐次核对载体转换，包括提交、确认、结果、阻断、失败和恢复；每次均明确原载体的去留、目标载体或内部变化、退出与稳定结果，再进行实体与状态判定。

登记时先判断载体是否变化，再按固定规则区分实体与状态：

- 离开原载体、关闭原载体后打开新载体，或在原载体上叠加新的页面、弹窗、抽屉、Popover、选择器，登记为独立实体。
- 原载体不关闭，仅在内部切换内容、按钮、结果或错误表现，登记为所属实体的必须生成状态或子视图，不得创建新实体。
- 标题或名称与交互描述冲突时，以载体行为为准；章节标题、实体名称不能单独证明存在新实体。
- Toast、InlineError、Loading、EmptyState 等不单独登记实体，但必须进入所属实体的状态规格。
- 纯展示组件既不产生新载体，也没有独立操作和返回结果时，不单独登记实体。

全部路径登记后才跨路径去重。不同入口可指向同一实体，但须有载体行为与交互契约依据：任务目标、主要操作、完成语义和退出关系一致，差异只需预填数据或同一载体内的条件状态表达。任务目标、主要操作或完成结果不同，或已确认分别打开的窗口具有不同结构与操作时，保留独立实体；共用组件、字段、标题、视觉框架、同一任务或时间相邻均不能单独作为合并依据。载体去留不明且会改变实体划分时，停止并说明待确认的转换，不默认合并。

“知道了”“关闭”“返回”“重试”等单一操作仍属于用户操作。确认、阻断、失败或结果信息只要由新载体承接，就必须登记为独立实体，不得降级为普通流程文字。

最低信息标准固定为：

- 页面或子页面：入口或触发条件、主要区域、核心操作、完成或返回结果。
- 弹窗、抽屉、Popover 或选择器：触发条件、关键内容、用户操作、关闭或返回结果。
- 实体状态：触发条件、可见变化、用户出口或后续结果。

达到最低信息标准时必须进入结构提取。未达到时仍须登记，归入`不生成`并写明缺少的必要信息，同时将同一缺失项写入现有待确认章节；不得静默忽略或补造内容。

实体按两类组织：

**A. 承载页面**（父页面）
- 本轮弹窗、抽屉或下级页面所依赖的触发页面（如列表页、详情页）
- 先从本轮权威材料及已确认设计事实恢复父页；当前材料仍不足时按 Step 1 读取正式载体知识
- 收拢入口、父子关系、页面动作、结果、返回位置、现有结构和本期可见变化；不得用局部新增模块冒充完整父页
- 承载页面作为实体 0，排在所有弹窗/抽屉实体之前

**B. 功能实体**（弹窗/抽屉/页面）
- 本轮任务中每个页面、弹窗、抽屉、Popover 或选择器都是实体候选；必须结合触发和载体行为判断为独立实体或所属实体状态。
- 主次任务与异常中的新载体，即使权威材料未单列标题，也必须登记。
- 次交互流程中的外部页面标记为独立实体，仅提取与本功能相关的内容。

完整实体清单建立后，固定分成三类：

- `生成`：满足以下任一条件的实体：承载当前任务入口或操作上下文的父级页面；用户需要输入、选择、编辑、确认、取消、重试、关闭或返回；用户需要查看会影响当前操作的阻断、失败、确认、结果或恢复信息；移除后会造成入口、操作、反馈、恢复或结果断点。
- `只引用不生成`：满足以下任一路径：
  1. 目标属于其他独立业务模块、其他应用或外部系统；当前原型不需要在目标界面继续执行本次任务；当前任务可以在跳转入口处结束，或只需描述跳转目标及返回结果。
  2. 本轮权威材料已明确跨任务引用，且同时提供原任务受阻、可执行入口、目标去向；当前材料未给出具体父级承载页。
- `不生成`：本轮权威材料明确排除、属于后台计算或接口调用等非可见界面，或未达到上述最低信息标准；信息不足时必须同步进入待确认章节。

硬规则：

- 每个实体只能进入一个范围；实体状态随所属实体生成，不单独参与三类归类。
- 新载体必须作为独立生成实体；原载体内变化必须作为所属生成实体的必须生成状态。两者都必须进入正式规格，不能只保留在流程、异常、状态或文案文字中。
- 任务闭环内的父级页面、操作、确认、阻断、失败、恢复和结果界面必须归入`生成`；完整满足跨任务引用路径的外部任务容器只记录为`只引用不生成`，不创建页面实体。
- 未满足任一条`只引用不生成`路径的完整条件时，不得归入`只引用不生成`。
- 复用、已有系统能力、嵌套、次流程、异常流程、失败流程、低频、简单提示、只有一个按钮、已在任务路径中描述或未被单列，均不能作为排除任务闭环内实体或状态的依据。
- `只引用不生成`和`不生成`各只保留一句符合上述定义的原因；禁止把未定内容写进`生成`。
- 完成分类后逐条反查主流程、次流程和异常流程；每个用户动作都必须有生成实体、生成状态或完整跨任务引用承接，不得只保留入口、按钮或文字描述。

实体关系在分类完成后内部核对，正式连接进入第 3 章跨实体任务流程，不另输出静态关系清单：

1. 以本轮权威材料和已确定的入口、父子关系为骨架，用内部任务路径的触发、跳转和进入条件核对。
2. 内部关系两端必须是生成范围中已登记的真实实体；跨独立模块的目标按`只引用不生成`门禁单独核对。
3. 相同来源、目标和触发动作只保留一次。
4. Tab、区域、卡片、提示区和实体内部状态不登记为独立实体：结构进入所属实体的页面结构，内部动作进入关键操作，业务状态与异常进入所属实体的相应小节或条件结构。
5. 写盘前 Handoff 如发现遗漏实体，先同步修正生成范围、内部关系、第 3 章流程和正式实体结构，再首次写盘。

### 第 2 层：结构提取

对每个已识别实体，从本轮权威事实和 Step 2 已确定的页面方案形成结构；不得改变本层输出格式、结构推理方法和以下提取项：

- 区域列表及包含关系（如"标题区 → 标题文字 + 关闭按钮"）
- 每个区域内包含的元素类型（文本、输入框、选择器、复选框、按钮、标签列表等）
- 区域内的信息内容（如来源信息区展示"{对象名称}/{对象标识}/{业务范围}/{能力范围}"）
- 异常状态下新增或变化的区域（如校验阻断时出现 inline 提示区、部分成功时出现跳过明细区）

实体即使在输入材料中没有独立标题或 ASCII，只要达到最低信息标准，也要按已确认事实形成最小可生成结构；不得忽略实体或补造业务内容。用户明确提供的有效 ASCII 应保留其已确认结构语义；异常材料只提供条件、反馈和处理依据，不能据此补造页面空间事实。

页面结构主体只保留区域、语义组件、字段、状态和交互规则。知识命中过程、设计判断编号和不影响生成的推理说明不输出；影响页面生成且无法由正式输入确定的缺口进入`不参与本次生成的待确认项`。

主体章节只写当前能支撑生成的已定页面信息。待确认项只写影响和约束，不预写实现，不得把待确认项混入页面结构、交互流程、状态或精确文案主体。

除页面结构与条件结构的字符线框外，页面规格主体默认使用“标题 + 正文 / 短列表”承载。结构化不等于表格化；只有在枚举项非常密集、逐行对照明显更清楚时，才允许短表格。

页面结构示例仅说明字符线框的表达方式；具体区域和相对位置须由本轮权威材料与已确定方案决定，不照搬示例：

````markdown
### 页面结构

```text
+------------------------------------------+
| {上方区域：短标签 / 操作}                 |
+--------------------+---------------------+
| {左侧区域}         | {右侧区域}          |
+--------------------+---------------------+
| {后续区域：信息或操作}                   |
+------------------------------------------+
```
````

示例中的并排只表示一种可能的区域关系；来源未确认或方案不需要并排时，不得为了套用示例制造并排布局。字符线框表达区域的包含、顺序和必要的相对位置，不要求精确列宽或比例，也不替代对应的区域与语义组件说明。

不要优先改写成：

- 字段 / 类型 / 说明的大表
- 区域 / 元素 / 规则的大表
- 页面结构总览大表

结构中的示例业务数据必须变量化。不得把具体人名、具体数量、具体业务应用名当作默认页面数据。

使用：

- `{业务对象总数}`
- `{分类数}`
- `{分类名}`
- `{业务对象名称}`
- `{业务范围}`
- `{处理人姓名}`
- `{处理时间}`

ASCII 线框既是结构来源，也是正式主体内容。页面规格主体必须同时保留 ASCII 线框与对应的区域、语义组件清单。ASCII 只固定信息位置、区域关系和大布局，不写像素、颜色、圆角、阴影、字体、动效或具体 UI 库变体，也不得为了图形整齐改变真实模块关系。已确认的既有父级承载页，其本期未改变的区域、顺序、并列及包含关系必须在主结构中可直接辨认，不得缩成只列元素的文字清单。ASCII 只呈现默认状态和条件触发后实际变化的可见结构；动作因果、业务规则及完整文案仍由所属章节表达，不在图中重复。

每个实体先输出默认状态的 ASCII 主结构。触发后没有打开新载体，且当前实体出现区域或组件新增、隐藏、替换、禁用、加载、空状态、错误状态、内联反馈、失败明细、内部确认，或已填内容与上下文保留的可见变化时，紧随主结构输出对应条件结构；满足这些条件即输出，不再判断变化是否足够重要。优先只画发生变化的区域并标明主结构锚点，影响整体布局时才画完整条件态。

输出前先按上述定义判断是否属于条件结构；不符合定义时不输出条件结构标题，其有效事实按“输出信息唯一职责”进入一个正确章节，已有完整落点时不重复。

条件结构按可见结构去重：反馈位置、组件类型、按钮状态、内容保留和区域布局均相同时共用一个条件结构，由所属实体的校验说明或真实文案 key 区分原因；任一不同则分别输出。Toast、全局 Message 等不改变实体内部结构的瞬时反馈不生成条件结构；Loading 只有造成区域占位、骨架屏、内容替换或按钮状态变化时才进入条件结构。文案 key 不是模板变量，最终产物不得保留占位 key。

条件结构只表达区域、组件、位置、显隐、禁用和布局变化；所属实体的`状态与异常恢复`保留状态名称、触发条件、业务含义和可执行操作，引用真实条件结构名称，不重复完整布局。先执行既有实体判定：新页面、弹窗、抽屉、Popover 或选择器继续作为独立实体；只有当前实体内部展开、没有新载体承接的确认区域才属于确认状态条件结构。

条件结构固定使用以下格式，不得使用自然语言段落代替 ASCII：

````markdown
### 条件结构（{条件或状态}）

```text
{局部 ASCII}
```
````

每个实体按真实内容选择性输出`信息与字段`：列表列、表单与筛选字段、详情展示项、卡片动态信息、状态标签，以及生成必须识别的提示信息类型。页面结构负责区域、卡片、入口和容器关系；`信息与字段`负责其中的字段、信息类型与动态内容。只写上游明确的名称、类型、枚举、格式、校验和显示条件，不补齐未知维度；没有独立信息项时不输出空章节。

### 第 3 层：交互提取

从本轮权威材料与 Step 2 内部方案，核对入口、载体、动作链和显式分支；主次任务均保留用户动作、系统响应、反馈和下一步；异常保留发生时机、触发条件、判断依据、系统反馈、阻断后行为、非阻断确认及恢复路径。

交互描述保留原始动作动词（点击/选择/输入），不泛化为"用户操作"。

交互承载要求：

- 每个实体的`关键操作`只写当前实体内的用户动作、直接系统响应、下一实体或返回位置，以及内部必要状态变化
- 第 3 章`跨实体任务流程`按真实任务分组，用简短连接表达来源实体、触发动作、必要条件、目标或停留状态、返回位置和最终稳定结果；原内部关系中的有效连接都须有落点
- 分支只有在进入不同实体、返回不同实体、因阻断停留当前实体、结束于不同稳定界面，或原任务上下文保留情况变化时，才进入第 3 章；跨模块的`只引用不生成`任务要标明身份和回到本任务的结果
- 只改变校验原因、提示文案或实体内部状态的分支，进入所属实体的校验、状态、恢复或文案，不在第 3 章复述
- 第 3 章默认用任务小标题和“来源实体 —动作／条件→ 目标实体或稳定状态（返回／结果）”的短句；一个连接可包含必要结果，不另写静态边清单或后置完整流程
- 不用大表格承载完整交互流程
- 不把动作、反馈、下一步压成一张总表作为主体

短连接写法示例只示范颗粒度，不预设任务或页面结构；正式输出须换成真实任务、实体与动作，且只写实际存在的连接：

```markdown
### 完成任务

- E0 —点击“开始”→ E1；取消返回 E0。
- E1 —点击“选择”→ E2；确认后回填 E1，取消返回 E1。
- E1 —提交成功→ E0 已更新状态；校验未通过时停留 E1。
```

### 第 4 层：文案与状态提取

文案从本轮正式输入、已确定的主次任务、异常反馈、页面结构和统一状态口径中汇总去重；用户明确给出的准确文案与有效 ASCII 可见文字必须保留。设计需要补充的文案不得捏造业务规则。

每条文案记录原文案字符串，保留模板变量（`{姓名}`、`{N}`、`{M}`、`{当前状态}` 等），并注明该文案出现在哪个区域/状态下。

精确文案是正式合同，必须覆盖标题、按钮、文字入口、字段名称、占位文案、辅助说明、状态与空状态、校验与异常反馈、Toast、二次确认文案和动态文案。页面专属文案在所属实体的`文案与变量`中完整记录一次；确实被多个实体共用的文案才进入末尾的共用文案区。每条包含稳定 key、完整字符串、适用位置或状态、模板变量及其含义和取值；无变量时标明无。

重复文案固定按以下方式处理：

- ASCII 保留结构判断所需的真实短标签；长说明、校验、Toast 与异常反馈可在相应位置用本页已定义的文案 key 指向就近完整字符串。用户已给出的准确文案不得因此丢失，不得留下无定义 key。
- `信息与字段`保留字段名、信息类型、枚举和显示条件。
- `关键操作`保留按钮或入口名称、动作、反馈类型和结果；完整提示字符串使用文案 key。
- 第 3 章只保留触发按钮或入口名称，不写 Toast、校验提示和异常提示的完整字符串。
- 所属实体的校验、状态和异常恢复保留各自完整语义，使用本页或共用文案 key 指向精确字符串。
- 同一长字符串只在文案落点完整出现一次；短标签为保持 ASCII 可读而重复展示时，不能与唯一文案落点出现不同口径。

状态从本轮已确认状态模型与内部设计结果提取：

- 状态名称
- 含义与适用对象
- 触发条件（对应本轮权威事实和已确定任务路径，不得新增业务条件）
- UI 表现（从"统一反馈口径"和"用户可操作"列提取）
- 对应文案

状态与文案承载要求：

- 状态 key、模板变量、极短文案映射允许短表格
- 异常恢复、实际结果与长说明文案优先用正文或短列表

### 第 5 层：待确认项集中隔离

所有待确认但当前不参与页面生成的内容，统一进入 `不参与本次生成的待确认项`。

规则：

- 每条至少写“待确认项”和“影响”
- 主体章节不再出现 `[GAP]` 式散落标记
- 不得因为有待确认项，就把未定实现写入正文
- 已知复用页面、复用组件、外部处理页，以及满足跨任务引用条件的内容，写入`只引用不生成`，不进入本章节。
- 仅当当前页面的入口、字段、状态、关键操作或结构依赖未知事实，且无法通过已知复用能力或完整跨任务引用表达时，才写入本章节。

### 明确丢弃

以下内容不复制进页面规格主体，但其有效事实仍须按本 Skill 已定义的职责消化：内部设计判断过程、旅程摘要、设计说服、依据长表、散落的待确认说明和纯工程实现讨论。角色、任务、入口、状态或结果事实必须落入相应页面章节，未定事项集中隔离。

### 输出信息唯一职责

- 生成范围：实体清单与生成方式。
- 第 3 章跨实体任务流程：独立实体的触发、跳转、返回和稳定结果；内部实体关系仅作核对。
- 页面结构或区域结构：区域、包含、排列和 ASCII。
- 信息与字段：字段、信息类型和动态内容。
- 关键操作：当前实体内操作及直接响应。
- 所属实体的校验与反馈：本实体触发、判断、阻断或放行及反馈。
- 所属实体的状态与异常恢复：本实体可见状态、业务含义、异常出口和恢复；跨实体变化由第 3 章连接。
- 独立结果界面归入生成实体，当前实体内部结果变化归入条件结构与状态；不另设全局结果态。
- 所属实体的文案与变量：页面专属的精确字符串及变量；多实体共用文案仅在末尾共用区完整定义。
- 不参与本次生成的待确认项：影响生成的未知事实和冲突。

同一事实只在唯一职责章节完整展开，其他章节仅用真实章节名或文案 key 建立连接。删除标题或重复内容前，必须先确认全部有效事实已有正式落点。

上游编号不得成为 Page Spec 正文中的未定义引用。吸收后的事实按上述唯一职责落位；需要连接时只引用 Page Spec 自身真实存在的章节、实体编号或文案 key。HF 只用于内部逐事实核对，不另加尾部追踪正文。

## Step 3 · 首次正式写盘前核对页面事实 Handoff

仅当本轮来源于 PRD Review 的正式需求基线时，完成内部页面方案草稿后、首次写入 page_spec.md 前，检查随本轮交接提供的页面事实索引。先核对需求来源、项目与基线身份，以及文件头和 HF-ID 是否可逐项核对。Handoff 只充当基线页面事实的覆盖索引，不取代完整基线，也不含 §10 体验定案。

- 文件不存在、读取失败或身份不匹配时，不伪造“已完成 HF 核对”；继续用完整基线执行自身覆盖检查，并在完成说明中报告此次 Handoff 核对未完成。PRD Review 原有投影失败不阻断基线的边界仍成立。
- 文件有效时，按全部 HF-ID 逐项核对，不按消费者索引筛选，也不输出覆盖分类长表。
- Handoff 与正式基线或 §10 已确认事实有实质冲突时停止并报告交接错误，不静默选边、不以 Handoff 覆盖基线。
- 发现正文事实缺失时直接修正尚未写盘的内部草稿，重新核对实体范围、关系、结构、字段、动作、状态、文案及自检后再首次写盘。没有“首次写盘后只许追加”的限制，也不保留错误首稿或尾部补丁日志。

逐事实完整覆盖标准保持不变：

- 页面、Tab、模块：所属层级、主要内容和可见条件均有正式落点。
- 弹窗、抽屉：触发条件、结构、关键内容、按钮和操作结果均有正式落点。
- 动作：入口、动作、系统结果和必要反馈均有正式落点。
- 状态：触发条件、页面表现、可执行操作和下一步均有正式落点。
- 权限：角色、可见性、可操作范围和无权限表现均有正式落点。
- 字段、文案：所属实体、出现位置、约束或触发状态均有正式落点。

只出现名称、入口、按钮、流程节点或文案记录，一律不算完整覆盖。新增实体必须同时有生成范围归类、真实父子或触发关系、完整正式结构；原有实体需要升级时先修正唯一范围归类和全部相关章节。HF 缺口不能只留在待确认或完成说明中。写盘后再对全部 HF-ID 反查正式落点；输出自检仍须独立完成。
