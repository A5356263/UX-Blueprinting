# 页面设计内部推导细则

本文件规定多角色任务、承载、父页、选择回填和写盘前覆盖的内部推理。仅在 Page Spec 输入来源检查完成后读取；所有检查只在内部执行，正式产物按 Page Spec 的页面事实结构输出。

## 内部完整性推导

正式写作前，必须先在内部建立本轮方案覆盖关系。该过程只用于推理，不输出清单、矩阵、编号或 coverage 字段。

第一步，从本轮权威材料提取；正式基线模式以完整需求基线为业务事实权威：

- 每个相关角色，包括承担自动处理责任的系统。
- 每个角色要完成的任务、触发条件、业务结果和下一节点。
- 每个任务的实际入口来源：主动进入、任务内触发或状态后触发。
- 每个状态、异常、阻断、恢复方式和明确终止结果。
- 基线已明确的现有入口、任务位置和承载方式。

第二步，按任务闭环组装路径：

- 从任务入口一直连接到下一节点或明确终止。
- 不同角色分别建立路径，再处理角色之间的结果交接。
- 一个需求可以有多条主流程，不得默认只选最终用户的一条路径。
- 配置者、申请者、审批者、处理者等角色的核心任务同等进入主流程判断。
- 系统自动处理不必单独制造页面，但必须在触发它的节点和接收结果的节点中可感知。

第二步补充，识别任务内触发与受阻转接：

- 任务内触发指用户正在完成原任务时，因可处理限制而需要进入当前处修正或后续处理任务。
- 可处理限制包括权限或身份不符、前置条件未满足、必要数据或关联对象缺失、当前状态限制、依赖流程未完成、对象失效或变更、规则冲突、适用范围不符，以及外部系统暂不可用、同步延迟或处理失败。
- 上述类别只用于识别已存在的限制；不得据此补写未被输入或业务知识证明的事实。
- 先明确原任务、受阻时机和限制原因。当前处可以修正时，写清修正方式和继续动作，不制造无必要转接。
- 只有后续处理任务和可进入能力均已被证实时，才提供转接入口或引导；只保留系统已确认的任务对象、范围、来源或状态。
- 无法证明存在预填、自动回流、自动处理或恢复能力时，不得写为事实；处理后去向须明确为回到原任务、重新发起或查看处理状态中的已证实结果。

进入承载分类前，沿每条主次任务及异常恢复路径走到稳定出口，逐次确认`原载体 → 动作／条件 → 原载体去留 → 新载体或内部变化 → 返回／结果`；提交、确认、取消、阻断、失败和恢复均须覆盖。该核对只用于内部推导，不输出新清单或表格。

第三步，对每个流程节点进行承载分类：

- `新增或修改`：本期新增界面，或修改现有界面的入口、结构、操作、状态、可见性和反馈。
- `复用引用`：使用成熟基座或外部系统现有界面，本期只传入或消费数据，不修改界面结构和交互。
- `系统处理`：后台自动处理，没有独立用户操作界面，只产生状态、数据或通知结果。

每个流程节点必须且只能归入一类。

分类后的处理：

- `新增或修改`：进入完整实体登记、三类生成范围与实体正式规格；任务路径进入关键操作或第 3 章跨实体任务流程。
- `复用引用`：保留输入、可执行动作、输出和返回位置；本期未改的外部界面不展开页面结构。
- `系统处理`：保留触发、处理结果和用户可见反馈，不凭后台处理制造页面。

业务主流程节点不等于本期必须设计的界面。

第四步，识别父级承载页：

出现以下任一变化时，父级承载页必须归入“新增或修改”：

- 新增入口。
- 新增模式选项。
- 修改入口可见性或可用状态。
- 修改模式当前状态。
- 新增通往子页面的操作。
- 子功能启用后需要在父页显示结果。

子页面的入口依赖父级页面时，禁止只输出子页面。

父级承载页进入本期“新增或修改”后，先从本轮权威材料恢复现有页面结构；不足时按主文件 Step 1 查正式知识。完成既有结构核对后，再叠加本期变化：

1. 保留本期未改变的主要区域、导航关系和核心操作。
2. 标出新增或变化的入口、模式、状态、结果和反馈。
3. 校验新增内容与现有信息层级、阅读顺序和任务入口的关系。
4. 输出完整页面方案，不得只画本期新增的一张卡片、一个入口或一个局部模块。

业务知识无法证明现有父级页面结构时，不得捏造“现有完整页面”。先根据本轮权威事实判断该结构缺口是否会改变正式方案；会改变则停止，不会改变才允许以明确的新方案边界继续。

第四步补充，建立页面信息性质：

- 稳定信息：长期查看的当前事实。
- 任务入口：开始办理的触发点。
- 候选集合：一次选择任务中的对象。
- 已选结果：选择完成后回填主任务的结果。
- 历史记录：用于追溯的已完成事项。

候选集合只在选择过程出现时，不得设计为常驻 Tab。选择完成后必须回填已选结果，并保留原任务上下文、结果查看和重新选择路径。

第四步补充，选择流程形态：

当同一任务包含会改变后续内容的前序选择，或存在多个信息分组，需要判断它们是页面内联动还是独立阶段时，完整读取 `设计准则/设计准则.md` 的 `BFM-01 默认非步骤化` 与 `BFM-02 步骤条使用门禁`。

先按 BFM-01 判断单页表单能否承载完整任务；再按 BFM-02 识别候选阶段并完成三重门禁判断。

`Wizard + Steps` 只在三项同时成立时使用：存在至少两个候选阶段；后续阶段依赖前一阶段的独立结果；分步收益高于往返成本。

候选阶段、阶段依赖和收益的完整定义，以 BFM-02 为准。

第五步，分配正式页面事实落点：

- 直接完成核心结果的角色任务与支撑、维护、查看、撤销、关闭等任务均先形成内部路径；跨实体连接进入第 3 章跨实体任务流程，实体内动作进入关键操作。
- 异常、阻断与恢复进入所属实体的条件结构或`状态与异常恢复`；系统处理说明触发、用户可见结果及接收位置。
- 每个“新增或修改”承载对象进入完整实体规格；本期未改的复用引用不制造页面。
- 会改变用户行动的状态进入所属实体的`状态与异常恢复`，并指向实际可见实体或条件结构。

第六步，执行生成前覆盖门禁：

- 每个相关角色都有可执行路径或明确的系统承接。
- 每个核心任务都有完整起点、动作、反馈、结果和下一步。
- 每个流程节点都已完成承载分类。
- 每个主流程节点都能在实体关键操作、跨页面连接或系统可见反馈中找到承接。
- 每个“新增或修改”节点都能在页面设计中找到承载。
- 父级承载页没有遗漏。
- 每个页面都服务于已确认的任务，不生成无来源页面。
- 每个需求基线异常都有交互处理。
- 每项合法采用的 UXB 页面落实要求都有具体方案落点。
- 每个本期变化的父级承载页都保留了现有完整结构，不是局部新增卡片。
- 稳定信息、任务入口、候选集合、已选结果和历史记录没有混淆。
- 每个 Steps 方案都通过三重门禁。

发现遗漏时，继续内部推导并补齐方案。不得把可由已确认事实和设计知识推导的遗漏伪装成待确认，也不得等到正式写盘后才首次发现。

内部承载分类只用于推理，不输出矩阵、清单、覆盖率或分类审计表。

第七步，核对页面层级与关系：

完成各角色路径和承载判断后，从真实父页、独立页面、弹窗与抽屉内部核对实体关系。关系两端都须是已登记且纳入生成的实体；入口、父子关系与返回位置须和正式第 3 章`跨实体任务流程`一致。关系图不另成正式章节。不额外输出站点树、主导航、route 或 icon_hint；不得按标题关键词制造导航或系统级组件。

不得：

- 重新裁决需求是否成立
- 绕过正式需求基线自行判断能力形态
- 只罗列原始需求功能，不按本轮来源身份和事实完整度展开
- 用“体验友好”“提示清晰”这类空泛表述替代具体页面结构、状态和文案
- 绕回原始输入重新解释业务规则、状态模型或能力形态
- 用 `stories` 或 `journey-analysis` 的派生信息反向覆盖正式需求基线或 UXB 体验定案
- 当本轮应承接正式基线而基线缺失时，硬输出 PRD Review 主链的“完整方案”
- 在 framing-mode 下把 working_assumptions 当作完整 Page Spec 事实基础
- 在 `framing-mode` 下把会改写主流程的未决问题静默抹平
- 把候选集合直接做成常驻 Tab
- 把结果回填型选择做成 Steps


## 异步结果、选择回填与反馈落点

- 发起审批、同步或其他异步动作后，分别确定提交后的当前状态、恢复条件满足前可执行的查看或等待、恢复条件满足后的下一步；提交成功不等于业务结果完成。
- 单次对象选择按候选浏览或直接显示、选择确认、返回主任务、已选摘要和继续操作串联；已有复用选择器按已证实的承载与返回规则引用。
- 成功反馈保留触发结果、反馈形式、承载位置、页面去向和状态或数据变化；失败反馈保留失败条件、位置与形式、信息保留和后续动作。
- 互斥条件确实切换字段组、候选集合、主要操作或结果结构时分别表达条件结构；只改文案、默认值或无结构变化的瞬时提示不重复画整页。
- 具体文案使用用户可见文本、变量、出现位置和适用状态；不得把内部推理术语或未选择的候选方案写进正式产物。
