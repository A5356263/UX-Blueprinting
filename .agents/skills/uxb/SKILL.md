# UXB

UXB 形成项目级体验策略。它确定需要保留的体验结果，不展开具体交互方案。

## Step 0 · 运行入口与正式输入

只在用户明确要求 UXB、体验策略，或明确选择进入 UXB 时执行。

### Step 0.1 · 本 Skill 产物状态

执行前只检查以下正式产物是否存在：

- `spark-output/uxb_output.md`
- `spark-output/context/uxb.json`

任一文件存在时，提示：

```text
检测到本 Skill 已有正式产物（已产出）。
```

历史产物不作为本轮输入。继续读取用户本轮明确提供的正式输入。

### Step 0.2 · 确定正式主输入

按以下顺序执行：

1. 用户明确指定文档、路径或完整正式正文时，以该材料为唯一正式主输入。
2. 用户未指定时，只检查 `spark-output/requirements_baseline.md`。
3. 完整读取正式主输入。

正式主输入可以是：

- PRD Review 生成的正式需求基线。
- 用户明确指定的正式问题与解决方向。
- 用户直接提供的同等级完整正式正文。

一次只使用一份正式主输入。多个正式材料同时存在且用户未指定时，停止并要求用户选择。

问题驱动路线由用户明确指定正式问题与解决方向文件。本 Skill 不自动把 `problem_framing.md` 视为已完成的正式输入。

不读取原始 PRD、工单、聊天记录、候选根因、数据分析、诊断记录或历史 UXB 补全正式主输入。

### Step 0.3 · 输入门禁

进入 Step 1 前，确认正式主输入已明确：

- 要解决的问题或业务目标。
- 目标用户、关键任务或受影响对象。
- 已确认的解决方向或能力范围。
- 本轮范围和不做内容。
- 不会改变体验策略的假设、限制和未决项。

任一信息缺失且会改变体验策略时，停止。说明缺少内容和影响，等待上游更新正式输入。

### Step 0.4 · 读取可选体验证据

可选体验证据包括：

- `spark-output/context/stories.json` 或 `spark-output/stories.md`
- `spark-output/context/journey-analysis.json` 或 `spark-output/journey_analysis.md`

读取规则：

1. 用户明确指定文件时，优先读取用户指定文件。
2. 用户未指定时，只检查上述四个标准路径。
3. Stories JSON 只接受 `3.0`。结构完整时读取角色、任务、目标、完成结果、优先级、设计触点、风险和来源；字段为 `unknown`、`[]`、与 Markdown 冲突，或当前策略需要完整任务叙述时，完整读取 `stories.md`。
4. Journey JSON 只接受 `3.0`。结构完整时读取阶段、触点、痛点、信心低点、关键转折、流失风险和机会；字段为 `unknown`、`[]`、与 Markdown 冲突，或当前策略需要完整旅程叙述时，完整读取 `journey_analysis.md`。
5. 用户明确说明文件属于当前项目时，直接采用该归属关系。
6. 用户未说明时，Context 的 `project_name` 必须与正式主输入项目名一致；只有 Markdown 时，标题或来源段必须明确指向同一项目。
7. 无法确认项目归属时，不消费该文件；在确认视图列出未采用文件和原因。
8. 可选输入与正式主输入冲突时，停止受影响策略；冲突影响整体策略时停止本轮 UXB。

Stories 和 Journey 是体验证据，不覆盖正式主输入中的业务事实、范围和解决方向。缺少两者时，基于正式主输入继续。

## 角色与边界

你是体验策略制定者。

负责：

- 提炼项目级体验矛盾。
- 形成体验策略、设计标准和策略边界。
- 明确后续交互方案需要保留的体验结果。

不负责：

- 审查 PRD、验证原始证据或选择产品方向。
- 补充角色、权限、规则、状态、异常和业务能力。
- 输出页面、容器、组件、控件、按钮位置和最终文案。
- 规定其他 Skill 的读取和实现方式。

## Step 1 · 提取策略依据

读取 `references/experience_strategy_guide.md` 的“策略依据”和“体验矛盾识别”。

从正式主输入和已采用的可选证据中提取：

- 问题或目标。
- 用户与关键任务。
- 解决方向与能力边界。
- 关键阶段、信心低点、转折和流失风险。
- 跨角色、跨系统或跨阶段的共同关系。
- 已确认限制和不做内容。

本步骤只建立策略依据。不建立任务底表，不逐项扫描操作前、操作中和操作后。

## Step 2 · 识别关键体验矛盾

按策略指南识别项目级体验矛盾。

以下任一信号可以进入策略候选：

- 同一问题影响多个任务或多个旅程阶段。
- 多个角色或系统需要形成一致理解或连续衔接。
- 旅程证据出现明显信心低点、关键转折或流失风险。
- 新能力改变用户原有心智，需要统一学习或引导方向。
- 复杂规则需要转成一致的用户理解方式。
- 状态、风险、责任或进度需要跨节点持续可见。
- 高频任务存在共同重复成本，需要统一效率方向。
- 单个核心任务跨越多个体验阶段，或影响用户心智、学习、信任、风险认知和长期使用方式。

单个页面、字段、一次反馈或局部控件选择由 Experience Blueprint 处理。任务数量为一不能单独排除策略候选。

## Step 3 · 形成体验策略

对每个关键体验矛盾：

1. 读取 `references/knowledge_usage_guide.md`，确定当前策略需要的业务语境和设计依据。
2. 读取 `references/experience_strategy_guide.md` 的“策略形成方法”和“设计标准”。
3. 形成一个策略方向。
4. 写出策略主张、解决的矛盾、适用范围、预期结果、方案承接结果、依据与置信度。

只有两个方向都成立且选择会改变项目级体验结果时，内部比较两个方向。比较后只保留一个方向，不输出候选方案。

策略数量由真实矛盾决定。通常为 2 至 5 条；只有 1 条时保留 1 条；没有策略级矛盾时形成“本次无需独立体验策略”的结论。

“方案承接结果”只描述后续交互方案需要实现的体验结果。例如：用户在原任务受阻处能理解原因并继续处理。它不指定页面、容器、控件或文案。

## Step 4 · 用户确认

读取 `references/output_structure_guide.md` 的“确认视图”。

在聊天中展示完整候选策略。确认视图使用将要写入 Markdown 的编号和正文。

用户可选择：

1. 确认并生成正式体验策略。
2. 调整部分策略。

用户提出调整时，只重新分析受影响策略及关联设计标准和边界。用户指出正式输入错误、冲突或未闭环时，停止 UXB，等待上游更新。

低置信度策略必须获得用户逐条确认后，才能写入正式 Markdown。

## Step 5 · 正式 Markdown

用户确认后，读取 `references/output_structure_guide.md` 的“正式 Markdown”，生成并冻结：

- `spark-output/uxb_output.md`

Markdown 是唯一正式语义源。正式写入阶段只组织已确认内容，不重新分析、增加策略或改变确认语义。

## Step 6 · Context 投影与校验

Markdown 冻结后，读取 `references/context-schema.md`，生成：

- `spark-output/context/uxb.json`

JSON 只从冻结 Markdown 投影。随后执行：

```text
node <当前 Skill 目录>/scripts/validate-context.js spark-output/context/uxb.json
```

脚本只检查 JSON 结构、枚举和引用关系。Agent 负责核对 Markdown 与 JSON 的语义一致性。

结构校验失败时，只修 JSON。Markdown 结论错误时，回到 Step 3，重新确认后再生成 Markdown 和 JSON。

完成后停止。不要自动执行或控制其他 Skill。

## 红线

- 不用 UXB 修补不合格正式输入。
- 不把候选根因和原始证据写成正式事实。
- 不把任务级交互分析恢复为 UXB 主流程。
- 不为固定维度或数量补写策略。
- 不让业务知识、Stories 或 Journey 覆盖正式主输入。
- 不让 JSON 反向决定 Markdown。
- 不在 UXB 内处理 Experience Blueprint 的页面方案。
- 不修改 PRD Review、Experience Blueprint、Stories、Journey、Problem Framing、Page Spec 或 `shared-workflow/`。
