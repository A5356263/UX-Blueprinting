## 1. 目的与边界

本文件组织已经形成、准备交设计师确认的体验决策，不新增策略判断。

确认视图在聊天中展示。用户确认后，正式产物写入 `spark-output/uxb_output.md`。Markdown 是唯一正式语义源。

## 2. 确认视图

按下列语义顺序呈现准备写入正式文档的内容；不存在的局部策略、跨触点关系或独立标准不生成空章。确认视图可比正式文档更紧凑，但不能省略需要设计师决定的方向、触点、依赖或边界。

```markdown
请确认以下体验策略：

## 策略前提与范围

{本轮明确问题或目标、相关角色任务、范围与已确认限制}

## 整体主推方向

{一个整体方向、解决本轮体验阻碍的简短理由、待验证的用户表现；若没有独立局部策略，在此写清关键触点或用户可感知约束}

## 必要局部策略

### ES-001 · {局部策略标题}

适用情境：{相关角色、任务、阻碍}

策略决定：{业务触点或信息关系，以及在关键情境下用户应理解的信息、选择、限制或结果；只写实际相关的维度}

Page Spec 承接：{页面方案必须保留的体验约束，不预定页面内实现}

预期表现：{与该策略对应、尚待验证的用户表现}

## 必要的跨触点衔接

{确实影响整体策略的角色、触点或阶段关系；无此关系则省略}

## 依赖与边界

{会影响策略成立的新能力、待确认事项或适用限制；无此内容则省略}
```

设计标准仅在具有独立约束价值时写在对应局部策略旁，不强制单列。确认视图不展示候选方案、内部比较、检索过程和任务级分析过程。低置信度推导及尚未确认的依赖须明确呈现其身份，不暗示既有能力。

用户确认后，整体方向、局部决策、依赖和边界保持同一语义；未获确认不得写正式 Markdown。

## 3. 正式 Markdown

正式 Markdown 使用与确认视图相同的决策顺序，并补充真实来源。标题可以承载不同数量的局部策略，不为满足模板制造内容。

```markdown
# UXB 体验策略：{项目名}

## 策略前提与范围

{正式主输入身份、问题或目标、角色任务、范围及已确认限制}

## 整体主推方向

{一个整体方向、简短理由和待验证的用户表现；若没有独立局部策略，在此写清关键触点或用户可感知约束}

## 必要局部策略

### ES-001 · {策略标题}

适用情境：{角色任务和实际体验阻碍}

策略决定：{触点、信息关系与关键时刻的体验做法}

Page Spec 承接：{需要落实的体验约束}

预期表现：{待验证的用户表现}

## 必要的跨触点衔接

{有实际关系时写；无则省略本章}

## 依赖与边界

{有真实依赖或适用边界时写；无则省略本章}

## 来源

- {正式主输入的真实名称或路径及其作用}
- {实际改变或限制策略的同源体验证据、正式知识、设计师确认及其作用}
```

“策略决定”应具体到 Page Spec 无需重猜用户在关键情境中需要理解什么、能够选择什么、受到什么限制或如何识别结果；只写本轮问题确实涉及的维度，不套固定句式，也不列页面元素。跨触点衔接只表达必要关系，不复述全部局部策略。来源只保留实际影响决策的材料，不复述原始分析。

## 4. 表达规则

- 先写结论，再写必要依据。
- 使用短句、短段落和必要列表。
- 同一策略只完整表达一次。
- 策略标题直接表达已选择的体验方向；“清晰、友好、合理、及时”等词不能单独作为策略。
- 正式正文只保留已确认的体验决策与必要理由，不独立输出“关键体验判断”、候选比较、检索和推理过程。
- 预期表现是待验证目标，不写改善数值或已验证成效。
- 不写页面内区域、容器、控件、按钮位置、逐状态交互和最终文案；独立设计标准仅在确有约束价值时并入对应策略。
- 同一事实只在一个位置完整表达，其他位置简短引用。

## 5. 无独立体验策略

没有独立体验策略时，设计师仍须确认这一结论；确认后输出最小 Markdown：

```markdown
# UXB 体验策略：{项目名}

## 策略前提与范围

{正式输入、问题、角色任务与范围}

## 结论

本次无需独立体验策略；{简述关键页面问题可由 Page Spec 承接，或本轮未形成独立体验取舍的依据}。

## 来源

- {实际采用的正式主输入和设计师确认}
```

此场景不输出空洞的整体方向、局部策略、设计标准和边界；存在策略级事实缺口或输入仍只有症状时，不得借最小结论掩盖阻断。
