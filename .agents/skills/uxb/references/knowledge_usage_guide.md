## 1. 目的与边界

知识用于理解现有业务触点并校准体验策略，不替代本轮已确认的业务事实。

- 正式主输入决定本轮问题或目标、角色任务、范围及已确认事实；体验解决方向可由 UXB 提议并交设计师确认。
- 业务知识解释已涉及的既有机制、状态、责任、系统边界和领域术语。
- 设计知识帮助判断真实体验阻碍及策略级取舍。
- 页面、容器、组件和控件模式由 Page Spec 消费。

## 2. 消费顺序

按以下顺序使用知识：

```text
正式主输入与同源体验证据
→ 当前角色任务中的体验阻碍
→ 影响策略的现有机制、触点或设计依据缺口
→ 必要知识规则块
→ 整体方向与必要局部策略
→ 实际使用来源记录
```

尚未辨认界面体验可着力的问题时，不为寻找策略而遍历设计知识。正式输入已足以解释相关业务语境与现有触点时，不重复读取业务知识。读到足以作当前决策即停。

## 3. 正式知识源

只从 `.agents/skills/knowledge-wiki/knowledge/` 读取正式知识。

先从 `knowledge/wiki/index.md` 判断知识类型；业务主题进入领域 README，再按正式文件顶部导航读取支持当前判断的完整规则块。设计准则按章节地图、交互模式按全局地图定位命中内容。索引与地图只负责路由，来源名称和路径必须真实；不猜目录或遍历 `raw/`。

不把索引、README、目录名、检索词或单句命中直接写成策略依据。

## 4. 业务知识

本轮正式输入不能解释以下内容，且该内容会改变策略时，读取对应业务知识：

- 既有机制如何运作。
- 状态在系统中的含义。
- 角色责任和系统交接边界。
- 领域术语和对象关系。
- 当前需求与既有能力的新增、修改、移除或复用关系。
- 已有任务入口、业务承载页和跨角色触点关系。

读取当前主题的必要完整规则块。主题涉及相互依赖文件时，读取这些文件；不遍历整个业务域。

正式输入明确新增、修改或移除既有能力时，以本轮已确认输入为目标状态；知识用于解释当前状态。不能从现有知识唯一推出新业务能力时，记录待确认依赖。知识冲突会改变策略时，停止受影响决策并报告来源冲突。

## 5. 设计知识

先说明当前体验阻碍要求决定什么，再按正式设计知识的章节地图或模式地图读取直接相关的完整规则块。读取结果应说明如何改变、限制或校准策略；只与页面内控件和布局有关的模式留给 Page Spec 自行消费。未找到直接模式时，可使用相关通用设计准则继续，不虚构专门模式。设计知识不能替代正式输入决定权限、状态、数据和业务方向。

## 6. 来源记录与停止

只记录实际改变、限制或校准策略的来源。每项来源需说明：

- 对应整体方向、局部策略或确有独立价值的设计标准。
- 来源类型和真实名称。
- 对策略选择的作用。

出现以下情况时停止读取：

- 当前策略已能解释角色任务、现有触点、必要限制和体验关系。
- 新知识不再改变策略或独立设计标准。
- 后续内容转入当前策略之外的业务域或页面细节。

找不到业务知识但正式输入已足够时，继续形成策略。找不到直接设计模式时，使用通用准则，不虚构来源。
