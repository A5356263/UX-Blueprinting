## 1. 目的与边界

本文件帮助 UXB 从本轮需求或明确的体验问题中形成可确认的体验决策。

它不执行任务生命周期扫描，不输出页面方案，也不把每个局部交互问题提升为策略。策略须服务于实际体验阻碍，并决定后续设计不能自行猜测的触点、信息关系或体验约束。

一个问题涉及多角色、多任务或多触点时，策略可统领它们的体验关系；一个核心任务若先要决定业务触点、信息架构、风险认知或结果理解方式，也可能需要独立策略。数量本身不是判断依据。

## 2. 策略依据与层级判断

策略依据来自：

1. 正式主输入中的问题或目标、角色任务、可行动的体验阻碍、范围及已确认限制。解决方向可以在本 Skill 中形成，不作为输入必需项。
2. Stories 中的任务、目标、完成结果、设计触点和风险。
3. Journey 中的阶段、触点、痛点、信心低点、转折和流失风险。
4. 实际读取且改变、限制或校准判断的正式业务知识、设计准则和策略级模式。

正式需求基线及其他已确认材料是本轮业务事实来源。Stories 和 Journey 是体验证据，不补造业务规则。知识库解释已存在的业务机制和承载约束；UXB 提出的新触点或体验做法是待设计师确认的方案，不自动成为现有产品能力。

需要独立策略的信号是：若不先作体验决定，后续页面会在业务触点、信息组织、角色之间的理解、风险告知或任务结果的可理解性上出现实质不同的方案。只需决定某个字段、控件、页面内位置或单次局部反馈时，交给 Page Spec；不因任务只有一个就排除策略，也不因任务数量多就强制输出策略。

将候选主张从最终页面方案中拿掉，再问：后续设计是否仍能根据正式输入作出同样的关键选择？若能，该主张可能只是目标复述、业务事实或页面做法；应合并、交给 Page Spec，或不输出。若不能，说明它为何属于 UXB 的方向性取舍。

## 3. 形成整体方向与必要局部策略

先围绕整个问题推荐一个整体体验方向，简要说明它如何解决本轮主要体验阻碍。局部策略仅在存在独立取舍时形成，可按任务阶段、业务触点、模块或跨角色关系组织，但不能照搬功能目录或凑固定条数。若整体方向已包含唯一体验决定，就在整体方向中写明触点或用户可感知约束，不制造局部策略；有局部结论时须服务整体方向，相互冲突则先解决冲突再进入确认。

局部策略从本轮角色、任务和实际限制出发，说清会改变什么：相关信息应在什么关键时机被用户感知，哪些选择或行动应让用户可知，限制如何被理解，行动后的结果与下一步如何被识别。按实际问题取舍这些维度，不套固定清单。只写“更清晰”“更便捷”“及时反馈”等目标，不能构成策略；照搬权限、状态或业务规则也不能构成策略。

预期表现须与所选体验决定相连，作为待验证目标，不宣称已有改善或编造数值。对跨触点影响只追踪有来源支持的关系；未确定的数据、业务或技术能力标为依赖，不写成既有事实。只有真实存在有效替代且取舍影响体验结果时，才在内部比较；不为展示思考过程而输出候选清单。

## 4. 触点与 Page Spec 边界

UXB 决定影响策略成败的业务触点和信息架构承载，以及用户在关键情境中必须理解的选择、限制、风险或结果。已确认的现有产品承载约束必须遵守来源；新触点是设计建议，不自动成为既有能力。

Page Spec 在已定触点内决定页面实体、区域、相对位置、容器、控件、逐状态交互、反馈形式和最终文案。UXB 可以说明风险必须在行动前被理解、受限选择应在决策时得到解释；不要把某一种控件状态、窗口形式或具体位置写成所有需求的固定策略答案。

## 5. 设计标准、依赖与来源

只有某条设计标准相较对应策略具有独立约束价值、会影响下游设计且已获确认时，才单列。只重述策略目标或预期表现的标准并入策略，不为每条策略强行配置标准。

记录实际影响策略的正式输入、同源体验证据和正式知识；来源用于说明前提与判断依据，不复述原始分析。业务事实、设计建议、待验证表现与待确认依赖必须保持身份分明。设计师确认策略不能把未经产品确认的新业务规则变为既有事实。
