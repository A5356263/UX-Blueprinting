# 需求类型判断指引

这份指引用来帮助 UXB 在 `Step 2` 内部先把需求类型、影响层面和建议处理方式判断清楚。

它不是唯一判断入口。正式判断时，优先读取：

1. `references/complexity/00_core_complexity_judgment.md`
2. `references/complexity/01_domain_router.md`
3. 必要时读取对应领域卡片
4. 判断不准时读取 `references/complexity/02_uncertain_judgment_questioning.md`

## 判断顺序

1. 先判断这次改动到底改了什么。
2. 再判断底层业务骨架是否变化：
   - 对象关系
   - 业务规则
   - 状态机
   - 生效机制
   - 数据口径
   - 外部回写
3. 再判断体验设计压力：
   - 角色数量
   - 信息密度
   - 异常与分支
   - 跨端
   - 概念边界
4. 最后判断是低、中、高复杂度，还是信息不足。

这些判断主要服务 `Step 2` 的内部分类结果，不要求逐条向用户完整展示。

## 需求类型

- 局部体验优化
- 信息结构与概念澄清
- 既有能力扩展
- 复杂业务需求
- 信息不足，需要补充判断

## 关键判断问题

在进入下面的问题前，先做一个很短的自检：

- 用户给的是事实、判断、抱怨、目标，还是已经带结论的方案
- 当前判断是在确认“问题本质”，还是只是在复述需求表面
- 如果顺着用户字面继续走，最可能遗漏的前提、冲突或断点是什么


### 1. 这次改动改了什么

- 改页面表现。
- 改业务能力。
- 改规则边界。
- 改概念定义。
- 改任务路径。

### 2. 是否改变底层业务骨架

- 是否新增或改变核心业务对象关系。
- 是否改变业务规则、计算规则、审批规则、可见规则。
- 是否新增状态、状态流转或失败分支。
- 是否改变结果何时生效，是否需要审批、定时或回写。
- 是否改变统计、汇总、保密、归属或范围口径。
- 是否联动银行、税局、ERP、总账、电子档案等外部系统。

### 3. 体验设计压力落在什么地方

- 是否牵涉多个角色。
- 是否包含高信息密度页面或结果。
- 是否有较多异常、分支或部分成功反馈。
- 是否需要跨端保持一致。
- 是否存在容易混淆的概念边界。

### 4. 有没有被需求表面带偏

- 用户说的是“想怎么做”，还是“现在真实发生了什么”
- 当前问题更像页面表现问题，还是业务判断、规则边界、状态语义没有先说清
- 如果把它直接判成低复杂度体验优化，会不会掩盖业务对象、规则、生效方式或口径变化
- 如果把它直接判成复杂业务需求，会不会其实只是承接、表达、异常反馈没有设计清楚

## 处理建议

### 低复杂度

适用于：

- 不改对象、规则、状态、生效、口径、回写。
- 只改布局、展示、字段、文案、反馈、视觉强调。

建议表达：

这次主要是局部体验优化，不改变底层业务规则。重点会放在展示层级、交互边界和提示说明上。我建议直接输出体验策略，并补一段必要的业务依据。

### 中等复杂度

适用于：

- 复用现有业务逻辑。
- 在既有能力上新增局部操作、批量能力、异常处理或角色化入口。
- 明显改变任务路径或信息结构，但不改底层业务骨架。

建议表达：

这次是既有能力扩展，不是底层业务重构。我建议先做一版轻量业务判断，再输出体验方案。重点会放在流程承接、状态反馈、异常处理和用户下一步上。

### 高复杂度

适用于：

- 改变主数据模型或对象关系。
- 改变状态机、审批机制或生效机制。
- 改变数据口径、隔离边界或外部回写链路。
- 跨模块或跨领域统一模型。

建议表达：

这次属于复杂业务需求，已经超出局部体验优化。我建议先梳理完整业务判断，再输出体验蓝图。重点会放在角色、对象、规则、状态、风险和页面承接上。

### 信息不足

适用于：

- 无法确认是否改变底层业务骨架。
- 无法确认只是复用现有逻辑，还是改变逻辑本身。

建议表达：

现在还不能直接判断复杂度。需要先确认对象、规则、状态、生效、口径或回写中的关键边界，再决定是轻量处理还是完整蓝图。

## 禁止事项

- 不让用户自己选择 `fast / standard / full`。
- 不把内部分类结果或结构化数据原样展示给用户。
- 不只靠关键词命中做最终判断。
- 不一看到“权限、审批、财务、税务”就直接判复杂。
- 不一看到“文案、字段、页面调整”就直接判低复杂度。
- 不在没有业务依据时说“这不涉及业务规则”。
- 不把用户给出的方案、术语或需求标题直接当成问题本质。
