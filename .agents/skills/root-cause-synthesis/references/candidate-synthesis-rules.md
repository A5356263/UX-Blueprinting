# 候选根因综合规则

## 适用时机

只在 `candidate_synthesis` 模式读取。输入必须来自 Evidence Govern 面向 Root Cause 的消费者专属 Handoff。

## 推理顺序

严格区分：

```text
observed_symptom
→ evidence_fact
→ mechanism_hypothesis
→ candidate_root_cause
```

指标变化、报错、咨询增加、页面风险和用户“不理解”都只是症状或事实，不能直接写成根因。

## 对齐检查

检查证据在以下维度是否可比较：

- 时间窗口；
- 任务、旅程和节点；
- 角色、分群和对象状态；
- 业务场景与版本；
- 指标、问题和规则口径；
- 来源独立性。

只在主题上相似而范围不一致时，不得形成强机制链。

## 反证

每个候选至少记录一次反证检查。优先检查：

- 相似分群是否表现正常；
- 异常是否早于候选原因；
- 候选问题存在时是否仍有大量顺利完成；
- 主观感知是否与客观行为相反；
- 页面风险是否缺少真实行为对应；
- 变更撤回或故障恢复后问题是否持续；
- 口径变化是否足以解释现象。

没有发现反证不等于反证不存在；记录检查范围并使用 `unknown`。

## 替代解释

每个候选至少保留一个竞争解释。常见类型包括数据质量、指标定义、客群变化、规则或权限变化、故障、运营活动、季节性、正常业务阻断和未知外部因素。

只有存在明确证据时才能标记 `ruled_out`。若替代解释 `stronger_than_primary`，原候选不得继续作为首要候选。

## 因果置信度上限

不计算综合分，只使用上限门禁：

- `insufficient`：不生成正常候选；
- 单一来源、未解决冲突、强反证、强混杂或更强替代解释：最高 `low`；
- 多来源但关键范围只部分对齐：最高 `medium`；
- 多来源独立、范围一致、反证已处理、混杂低：最高可为 `high`。

`high` 仍只表示高置信候选根因。`forbidden_uses` 包含 `causal_claim` 时最高为 `low`。

## 业务规则

继承 Handoff 中精确 `business_rule_basis_ref`。区分：

- 规则导致的正常阻断；
- 规则暴露过晚、理解成本高或与预期冲突的体验问题候选；
- 规则本身需要人工裁决。

不得因为 Wiki 未命中就断言规则不存在。
