# PRD Review 知识消费规则

本文件只定义正式知识的适用范围、覆盖要求和证据判断。主流程顺序、调用节点和返回位置只以 `../SKILL.md` 为准。

## 1. 正式知识来源和权威边界

检索已发布的业务知识。将承担任务、能力、规则、状态、对象、页面或字段事实责任的正式知识作为依据。

- 领域说明和概念用于定位范围及依赖。事实证据须回到承担相应事实责任的原文。
- 问答与差异、FAQ 和历史材料用于操作指引、排障、差异追溯与检索线索。其中引用的事实须由承担相应责任的正式来源证实。
- 候选、维护模板、知识缺口和未裁决冲突不得作为确定事实。

PRD Review 只消费业务知识。不要读取设计准则和交互模式完成业务审查。

## 2. 消费目标

知识消费只服务一个目标：

> 判断当前需求涉及的业务闭环是否完整。

具体用于：

- 确认当前系统事实。
- 识别本次新增、修改、移除或沿用的对象。
- 发现受影响的角色、权限、规则、状态、异常、数据和依赖。
- 验证 PRD 对当前能力的描述是否准确。
- 发现 PRD 漏写的变化影响。

知识不能用于：

- 否定产品明确提出的目标变化。
- 替产品决定新规则。
- 生成体验策略。
- 生成页面或交互方案。

## 3. 初步定界模型

完整读取 PRD 后，先建立用于界定所需业务事实的初步定界模型：

- 业务对象。
- 关键动作。
- 当前状态与目标状态关系。
- 角色和适用范围。
- 预期业务结果。
- 已明确的外部依赖。

初步定界模型建立后再选择主领域。

本节不判断完整业务闭环，不生成候选问题，也不替代 `review_rules.md` 第 3 节的完整业务事务模型。完成主领域和实际依赖领域定位后，返回 `SKILL.md` 的“阶段 A · 需求语义建模与审查”。

不得只根据需求标题、页面名或单个关键词确定领域。

## 4. 主领域定位

从业务对象、动作和结果确定主领域，检索对应的正式业务事实。用角色、适用范围和当前结果排除同名对象，概念说明不足以证明具体规则时，仍需正式规则依据。主领域以实际承担当前事实责任的业务范围为准。未命中正式事实时记录知识缺口。

## 5. 依赖领域触发条件

只有以下条件同时成立时，进入依赖领域：

1. 主领域说明或正式原文明示依赖。
2. 当前需求实际触发该依赖。
3. 依赖事实会改变对象、角色、权限、规则、状态、异常、结果或审计结论。
4. 主领域知识不能独立解释该任务结果。

依赖领域的事实须与主领域的对象、状态和结果共同支撑闭环。

不得因为业务相邻、关键词相似或“可能有关”无限扩读。

## 6. 正式知识的证据要求
- 核对命中规则的角色、适用范围、条件、结果及例外，并引用可定位的正式来源；摘要与缺少条件的片段只能作为线索；需确认缺少的条件后才能采用。
- FAQ 或问答仅在正式事实冲突或缺失，或任务需要操作、排障、外部动态、收费协议或来源追溯时用作辅助线索。
- 不得用 FAQ 或问答普通正文关闭业务缺口、删除候选问题或写入需求基线。
- 页面与字段依据须对应本轮涉及的页面或对象。
- 命中局部知识后，不得在必要关联事实尚未闭环时停止。
- 未被当前需求触发的相邻知识不得扩入。

每项用于审查的知识必须能说明：

- 支撑哪个当前事实。
- 适用哪个对象和角色。
- 适用范围、条件和例外是什么。
- 会影响哪个审查结论。

## 7. 知识覆盖模型

### 7.1 事务证据覆盖

根据当前事务已明确的对象、角色、动作、状态和结果，判断还需要哪些正式依据：

1. 动作受资格、权限、条件、数量、计算口径或配置生效范围影响：需要对应的业务规则依据。
2. 动作改变状态，或存在失败、拒绝、部分成功、不可恢复或恢复结果：需要对应的状态和异常结果依据。
3. 动作产生下一任务、支付、对账、报销、同步、数据或审计结果：需要对应的任务结果和实际触发的依赖事实。
4. 正式来源不能证明当前对象关系、结果或依赖：记录知识缺口；不得用问答、常识或相邻主题补齐。

证据范围以当前事务为准。未被当前需求触发的相邻能力、规则、状态或领域不得扩入。

先按角色和任务场景建立知识主题，再按当前需求实际触发范围覆盖：

```text
业务对象
→ 角色
→ 动作
→ 权限
→ 状态
→ 规则
→ 异常
→ 业务结果
→ 依赖系统
→ 数据与审计
```

“覆盖全部相关知识”不是通读整个领域，而是所有会改变本次闭环结论的相关事实都得到核验。

影响本次业务闭环的主领域事实须有完整、适用的依据。

同一主题命中多个正式来源时，核对各来源中影响本轮判断的规则、条件和例外。依据缺少必要事实时，明确缺失内容，发现矛盾时保留双方出处。

每个任务场景必须核对：

- 执行角色和权限。
- 业务对象和动作。
- 当前规则和状态。
- 成功、拒绝、中断和终态。
- 实际触发的系统、数据和审计影响。

依赖领域的证据范围限于当前需求实际使用的机制，不审查该领域的完整能力。

成熟基座的核对范围限于本需求使用的输入、输出和差异。未被本需求改变的转派、委托、超时和内部异常机制不展开审查。

## 8. 覆盖记录

Agent 在内部维护：

| 覆盖节点 | PRD 目标描述 | 当前正式事实 | 关系 | 审查结果 |
|---|---|---|---|---|
| 对象、角色、动作等 | PRD 原文位置 | 可追溯的正式来源 | 沿用、新增、修改、移除、无法确定 | 已闭环、阻断、不适用 |

覆盖记录只用于内部检查和来源追溯，不作为用户产物。

## 9. 当前事实与目标状态关系

### 沿用

PRD 声称沿用当前能力时：

- 目标描述必须与正式当前事实一致。
- 不一致且未说明变化时，形成阻断。

### 新增

检查：

- 新能力与当前对象和规则如何关联。
- 是否产生新角色、权限、状态或依赖。
- 当前能力是否需要同步调整。

### 修改

检查：

- 修改前后的目标差异。
- 适用范围和生效条件。
- 旧规则如何处理。
- 历史数据和下游影响。

### 移除

检查：

- 被移除能力的替代或终止结果。
- 历史数据处理。
- 仍依赖该能力的角色和下游。
- 权限、状态、接口和审计如何收口。

正式知识不同于目标状态，不等于冲突。只有变化关系和影响无法闭环时才阻断。

## 10. 复用基座继承审查

需求明确复用现有能力，或当前任务依赖成熟审批、通知、权限、支付、组织、消息等基座时，执行本节。

本节是知识消费的条件子流程。它不能替代角色、任务、规则、状态、异常、数据和结果审查，也不能过滤与复用无关的业务缺口。

### 10.1 所需证据

复用判断需要能够证明以下内容的正式依据：

- 基座能力范围。
- 固定规则。
- 可配置能力。
- 当前任务使用的输入。
- 当前系统消费的输出。
- 已知缺口。

概述或线索不足以证明复用成立。会改变输入、输出或配置的关联条件须有正式依据。

### 10.2 三个边界

- 输入边界：当前系统需要向基座提供什么，哪些输入会改变任务能否开始、处理或完成。
- 输出边界：当前系统需要消费什么结果，哪些结果会改变当前业务状态、结果或下一任务。
- 配置边界：当前需求是否需要选择、修改或覆盖基座配置。

三个边界只用于复用继承审查。

### 10.3 继承结论

- `固定继承`：正式知识证明为固定行为，不依赖当前需求选择，且本期没有修改、关闭或覆盖。直接继承。
- `条件继承`：基座支持多个结果、规则可配置、是否启用由当前业务选择，或不同配置会改变当前任务。PRD 未明确时进入阻断判断。
- `当前需求决定`：触发原因、发起角色、业务对象、业务输入、结果回写和当前系统后续处理。PRD 未明确且影响闭环时进入阻断判断。

“支持”“可配置”“开启后可用”不能证明当前需求已经启用。

### 10.4 基座内部候选问题移出边界

先完成 10.3 的三类继承判断。

正式知识已经以固定继承唯一回答的候选问题，继续按现有事实回查规则删除，并保留当前任务需要理解的固定继承事实，不执行本节的问题移出。

本节只处理完成三类继承判断后仍没有唯一答案的基座内部细节，用于判断围绕该细节产生的候选问题是否属于当前需求。以下条件不新增继承类型，也不改变三类继承结论。

只有同时满足以下条件，候选问题才可移出问题集合：

1. 当前需求不选择、修改或覆盖相关配置。
2. 当前系统不需要向基座提供与该细节有关的业务输入。
3. 当前系统不需要识别该细节产生的结果差异，也不需要依据差异执行不同的状态更新、后续动作或责任处理。
4. 该细节不改变当前任务的成功、失败、状态或下一节点。

仅消费基座标准最终结果，不等于消费该内部细节。

是否影响当前业务闭环，按现有完整任务链和阻断判定规则判断。页面是否展示该细节不能作为移出依据。

移出只表示“该规则由基座内部承接，本需求不定义”。不得据此写成“本期已启用”或“本期继承某项具体策略”。

任一条件不满足，且该细节影响输入、输出、配置或当前业务闭环时，进入现有阻断判断。

### 10.5 知识缺口

出现以下任一情况时，不得自行推断继承范围：

- 正式知识不存在。
- 正式知识只说明能力存在，没有说明固定规则。
- 正式知识标记为 `[GAP]`、`[QUESTION]` 或 `[CONFLICT]`。
- 不同正式文件相互冲突。

影响输入、输出或配置边界时形成阻断问题。不影响当前任务闭环时只在内部记录。

## 11. 关键动作的限制与例外

核对关键动作在正常路径之外的限制、例外和失败条件。

触发条件：

- 动作不可逆。
- 动作受权限控制。
- 动作改变关键状态。
- 动作影响下游。
- 正向知识不能证明完整结果。

围绕当前动作，在已经命中的正式文件和明确依赖中定位：

- 禁止或不支持。
- 不可撤回或不可恢复。
- 已关联或已被使用。
- 权限限制。
- 状态限制。
- 重复与并发。
- 外部失败和部分成功。

限制与例外的核对范围为当前动作、适用对象与必要依赖。

## 12. 证据一致性

每条知识结论必须与原文保持相同的：

- 对象。
- 关系。
- 角色。
- 适用范围。
- 条件。
- 例外。
- 表达强度。

禁止：

- 把局部场景提升为全局规则。
- 把“可配置”“开启后”“支持”改写为固定前提。
- 互换不同角色或业务主体。
- 把示例、典型路径或局部 FAQ 当作完整清单。
- 根据文件更新时间自行选择冲突一方。

封闭枚举只有在命中承担当前问题直接事实责任的完整正式清单时才能成立。

### 12.1 业务事实补充的知识准入

“业务事实补充”只可使用承担当前问题直接事实责任的正式知识。导航、摘要、示例、FAQ 或能力概述不能单独证明固定业务事实。

写入前逐项确认：

1. 原文直接覆盖当前对象、关系、角色、条件和结果。
2. 原文结论是固定继承，不依赖配置、本期选择或其他未确认前提。
3. 原文未标记 `[GAP]`、`[QUESTION]` 或 `[CONFLICT]`，且不存在相互冲突的正式结论。
4. PRD 未明确新增、修改、移除或覆盖该结论。
5. 原文表达强度不是“支持”“可配置”“可选”“开启后可用”等能力存在描述。

任一项不满足时，不得将知识写为业务事实补充。影响当前业务闭环时，按既有阻断规则形成待确认；不影响闭环时，不输出。

本节只判断知识能否作为固定事实，不判断事项应否交给 UXB。体验定案事项的判断只以 `review_rules.md` 3.11 为准。

## 13. 知识缺口与显式问题

出现以下情况时记录知识缺口：

- 缺少可追溯的正式事实。
- 正式原文缺少当前能力说明。
- `[GAP]`、`[QUESTION]` 或 `[CONFLICT]` 影响本次审查。
- 正式事实的对象、范围或条件无法与 PRD 对齐。

处理方式：

- 影响业务闭环：形成阻断问题。
- 不影响本次业务闭环：不纳入问题单。
- 知识缺口须指向当前对象及会影响结论的必要关联。
- 不得用 Agent 常识补齐。

## 14. 停止条件

同时满足以下条件，知识核对才可收口：

1. 核心对象和关系已覆盖。
2. 关键角色、动作和权限已覆盖。
3. 核心状态和规则已覆盖。
4. 会改变业务结果的异常已覆盖。
5. 被触发的系统、数据和审计依赖已覆盖。
6. 当前事实与目标状态的变化关系已明确。
7. 所有影响闭环的知识缺口都已进入阻断判断。
8. 已核对的依据足以判断所有会改变审查结论的业务事实，无法核实的事项已按第 7 项处理。

全部条件满足后，返回 `SKILL.md` 的“阶段 A · 需求语义建模与审查”建立完整业务事务模型。任一条件不满足时，不得提前返回，也不得开始生成问题。

## 15. 失败与阻断处理

- 正式知识无法取得：说明缺失的事实及影响。影响闭环时阻断。
- 引用的正式出处不可取得时，记录知识缺口，不以不相关结果替代。
- 正式文件存在冲突：保留双方来源；影响目标判断时阻断。
- 非正式材料与正式知识不同：不能覆盖正式知识，只能触发核验。
- PRD 明确改变当前规则：按目标状态审查，不把差异本身当作阻断。

## 16. 禁止事项

- 不读取设计准则或交互模式完成 PRD 审查。
- 不计算知识覆盖率或可信度分数。
- 不自动判断知识时效。
- 不把行业惯例、竞品或 Agent 经验当作知识。
- 不向用户展示知识路由、覆盖矩阵或完整推理过程。
- 不使用脚本判断知识是否适用、是否冲突或是否足够。
