# PRD Review 输出结构

## 1. 初次审核记录与基线关系

```text
完整审查
→ 审查结果
   ├─ 存在阻断：生成初次审核记录 → 等待产品回复 → 全部关闭后生成正式需求基线
   ├─ 零阻断但有建议：生成初次审核记录 → 生成正式需求基线
   └─ 零阻断且无建议：直接生成正式需求基线
```

存在阻断时，审核记录和需求基线不得同时生成。

## 2. 初次审核记录

### 2.1 输出路径

- `spark-output/prd_review_questions.md`

### 2.2 生成条件

只在 `SKILL.md` 的“问题单生成”满足生成条件后写入。本文件不得自行判断阻断、知识适用性或体验定案事项，也不得在门禁通过前提前输出。

### 2.3 文档状态

- 存在未关闭待确认：`waiting_response`
- 所有待确认已关闭：`closed`
- 没有待确认：`no_confirmation_required`

业务事实补充、体验定案事项和建议修改不参与状态计算。

### 2.4 固定结构

```markdown
# PRD 审核记录

- 项目：{项目名}
- 状态：{waiting_response | no_confirmation_required}
- 审查输入：{PRD 文件名或需求标识}

## 需求初识

- **谁遇到什么问题**：{仅按 PRD 概括}
- **当前如何处理**：{仅按 PRD 概括；PRD 未说明时写“PRD 未说明”}
- **为什么本期需要处理**：{仅按 PRD 概括；PRD 未说明时写“PRD 未说明”}
- **什么结果算完成**：{仅按 PRD 概括；PRD 未说明时写“PRD 未说明”}
- **有什么约束**：{仅按 PRD 概括；PRD 未说明时写“PRD 未说明”}

## 审核结论

### 业务事实补充

- F-001 · {适用场景}：{事实}
  - 依据：{正式知识的可定位来源}

### 待产品确认

#### Q-001 · {场景} · {问题主题}

{可独立回答的最小业务决定}

- 产品回复：待回复

### 待体验定案

- E-001 · {适用场景}：{待完成的体验判断}

### 建议修改

- S-M-001 · {适用场景}：{可直接修正的 PRD 内容}
  - 依据：{可定位来源}

## 你还需要补充什么吗？

可直接补充本期已知的业务流程、真实使用场景、角色、规则、状态、异常或现有系统限制。
```

五问每项最多两句。只概括已读取的 PRD，不读取知识，不填补缺失，不提出问题或建议。

### 2.5 分组规则

- 依次输出“需求初识”“审核结论”“你还需要补充什么吗？”。“审核结论”保留各条目的完整内容及后续回复。每条只出现一次，不另设“场景审核”或首轮快照。会话展示时也使用标题和列表，保留编号和子项顺序。
- “审核结论”依次列出业务事实补充、待产品确认、待体验定案、建议修改。没有内容的分类不输出，不写空标题、“无”或只有编号的条目。
- 每条写清适用场景和独立可理解的正文。待确认标题使用“编号 · 场景 · 问题主题”。同一问题影响多个场景且无法归属单一节点时，场景写“跨场景规则”。必要的角色、触发条件、任务、例外或来源随该条目记录。
- 同一场景可以同时有待确认和体验定案事项。待确认只在会改变该体验事项直接相关业务事实时，才影响体验定案事项的输出。
- “你还需要补充什么吗？”始终输出，保留原提示，不参与编号和状态计算。
- 审核记录正文只保留可定位的短出处，例如 PRD 章节、正式知识的文件名和章节或规则编号、产品回复的问题编号和子项。文件名有歧义时补最短可区分路径。会话默认省略独立依据行，理解问题所需的事实仍放在问题正文。按第 6 节需要说明关闭依据时，保留必要的一句复核结论。

### 2.6 编号

- 业务事实补充使用 `F-001`、`F-002` 顺序编号。
- 待确认问题组使用 `Q-001`、`Q-002` 顺序编号；一个 Q 只处理一个业务主题。
- 体验定案事项使用 `E-001`、`E-002` 顺序编号。
- 建议修改使用 `S-M-001`、`S-M-002` 顺序编号。
- 同一份审核记录内每类编号唯一；更新时不得重排或复用已有编号。
- 新业务主题追加新 Q 编号；同一主题新增原子项追加到该 Q 末尾。单项组转为多项组时，原问题保留为第 1 项。拆分依据仍为 `review_rules.md` 第 3.8 节。
- 每个原子项的产品回复、复核状态及必要的依据都记录在该项下。F、E、S-M 不接收产品回复，不参与关闭状态。

## 3. 审核条目写法

标签语义和硬分界只按 `review_rules.md` 3.11、3.12 和第 15 节判断。本节只规定写法。

### 3.1 业务事实补充

写出事实、适用场景及可定位的正式知识来源。不得把能力描述、条件继承或 Agent 推理写为业务事实补充。

### 3.2 待确认

单项组在标题下直接写问题和回复。多项组用有序列表，回复紧跟各子项。只在缺少上下文会妨碍作答时补一句背景；保留决定成立所需的条件和适用范围。

没有正式来源证明有限选项时，不得自行列举候选条件、状态、示例或答案。括号、“或”、“如”、“例如”中的内容同样受此限制。

### 3.3 体验定案事项

一条 E 只描述一个可独立判断的体验层缺口。发现、填写、状态解释、结果反馈等可独立处理的缺口不得合并为一条。

只说明适用场景和待完成的体验判断，不写候选方向、推荐结论、页面、组件、布局或文案。不得写“建议进入 UXB”“等待产品确认”或“由产品决定”，不得要求产品回复。

### 3.4 建议修改

记录对应场景、具体改法和可定位依据。

## 4. 问题写作规则

一个问题组只处理一个业务主题。

每个列表项只处理一个能够由同一条回复完整确认、内部不能独立变化的最小业务结论。

必须做到：

- 使用短句。
- 必要的问题背景用最多两句说明缺失结论及其直接影响。
- 不单独输出“为什么需要确认”。
- 同主题多个决定使用有序列表；每个列表项必须可独立回复、关闭或保持 open。
- 提问必须可以被明确回答。
- 列表项保持稳定顺序。

禁止：

- 输出完整推理过程。
- 重复大段 PRD 原文。
- 输出知识路由过程。
- 输出没有唯一事实依据的建议。
- 输出体验方案或体验机会清单。
- 使用“还有哪些”“其他是否需要”“请补充完整流程”等开放式兜底提问。
- 对已明确业务结果追问系统内部实现方式。
- 输出竞品、指标或页面方案。
- 使用“建议产品完善一下”等笼统表达。
- 为凑数量制造理论问题。

## 5. 有限选项

是否允许列出有限选项只按 `review_rules.md` 第 16 节判断。

已判定允许列出时，格式必须满足：

- 保持原始业务含义。
- 标明选项依据。
- 不推荐其中一项。

## 6. 产品回复记录

设计师可以在聊天窗口按编号提供产品回复：

```text
Q-001：
1. ……
2. ……

Q-002：
1. ……
```

第二次及后续运行更新同一审核记录：

```markdown
#### Q-002 · 管理员编辑申请配置 · 在途申请处理

1. 编辑角色或应用范围后，变更前已提交且在审批中的申请按哪个范围处理？
   - 产品回复（已确认）：按照已提交时的范围进行审批
2. 修改审批流程后，修改前已提交且在审批中的申请按哪个流程审批？
   - 产品回复（仍待确认）：待回复
```

记录规则：

- 在原编号和原子项下追加产品原始回复，保留原问题、顺序和回复原意。
- 首轮未回复写“产品回复：待回复”；产品明确回答并关闭，写“产品回复（已确认）”；有回复但尚不足以关闭时，写“产品回复（仍待确认）”并保留原话。复核时仍未答的子项也可用“产品回复（仍待确认）：待回复”明确标记。
- 按本期范围、正式知识或不适用证据关闭，写“产品回复（已关闭）”并保留已有原话，无原话写“未回复”。在该项下另用一句“复核结论”说明具体依据。产品明确本期不做时，写清“不属于本期”及所指能力，保留范围决定。
- 按 `review_rules.md` 第 17 节确定逐项的 `open` 或 `closed`；以上写法只呈现判断结果。省略独立的“关闭状态”“关闭依据”“问题组状态”区块，不另写重复的“产品明确确认”。
- 读取旧格式的审核记录时，从详细条目按原编号和子项顺序对应原问题、原回复、状态与依据。概要只用于定位，不据其顺序推断关闭。写回时合并到“审核结论”，保留逐项结果和可定位依据。旧记录信息不足时仍按现行规则复核。
- 保留初次审核的“需求初识”和所有未被业务事实变化影响的条目。
- 全部待确认关闭后，文档标题改为“需求确认记录”，文档状态改为 `closed`。
- 产品回复改变所在场景的业务事实时，重新按规则复核相关的 F、E 和 S-M，不将它们写成回复项。
- “你还需要补充什么吗？”保留用户原始补充文字，不因基线转写删除或改写。
- 用户补充明确关闭某条 E 时，在该 E 后追加“转写结果：EC-xxx”；E 不再转写到基线“待定案事项”。
- 不建立独立回复文件或问题版本系统。

复核发现正式问题本身不成立时，从问题集合中移出，并在文档末尾增加：

```markdown
## 问题移出记录

- 原编号：Q-001
- 移出依据：{问题为何不成立}
- 证据来源：{PRD 或正式知识位置}
```

问题移出记录不使用 `open` 或 `closed`，不参与整体关闭状态，也不生成需求事实。

围绕基座内部细节产生的问题已经按正式规则判定移出时，记录格式为：

- 移出依据只写“该规则由基座内部承接，本需求不定义”。
- 证据来源必须能够定位正式知识和当前业务边界。
- 不写“本期已启用”。
- 不写“本期继承某项具体策略”。

## 7. 回复复核规则

回复是否关闭、是否产生新候选问题以及何时严格停止，只按 `review_rules.md` 第 17 节判断。

本文件只负责把已经确定的复核结果写入第 6 节定义的位置。完成记录后，按 `SKILL.md` 的“阶段 B · 回复吸收与复核”决定严格停止或进入正式需求基线生成。

## 8. 正式需求基线结构

### 8.1 输出路径

- `spark-output/requirements_baseline.md`

### 8.2 生成门禁

只有 `SKILL.md` 的“正式需求基线生成”门禁已经通过时才生成。本文件不重新判断阻断项、问题关闭或事实来源是否有效。

不能生成“待确认版”“草稿版”或带假设的需求基线。

### 8.3 Markdown 固定结构

```markdown
# 正式需求基线

- 项目：{项目名}
- 基线状态：`formal`
- 原始 PRD：{文件名或需求标识}
- 审核记录：{存在时填写路径}

## §1 背景与目标

## §2 功能与变更清单

## §3 谁能做什么

## §4 每件事怎么完成

## §5 要遵守什么规则

## §6 会出现哪些状态

## §7 遇到特殊情况怎么办

## §8 会影响哪些记录和系统

## §9 这次明确不做什么

## §10 体验定案

### 已确认体验约束

### 待定案事项

## §11 做成后应该看到什么结果
```

沿用 §1 至 §11 的编号。不适用的章节保留标题，并明确写“本期无”或“不适用”。§10 按 8.14 节在无内容时省略。

### 8.3.1 事实唯一主落点

每条已确认业务事实只能在一个章节完整展开。其他章节确有依赖时，只写稳定编号或不重复含义的必要短句；不得为了章节完整而重写该事实。

| 事实类型 | 完整主落点 | 其他章节允许写法 |
|---|---|---|
| 角色权限、可做与不可做动作 | §3 | 在 §4 写执行角色或任务前提，不重复权限清单。 |
| 任务触发、关键动作、成功或拒绝结果、下一节点 | §4 | 在 §5、§6、§7 只表达对应规则、状态或异常，不复制任务步骤。 |
| 条件判断、互斥、范围限制 | §5 | 在 §4、§6、§7 只写当前结论所必需的最短条件。 |
| 状态集合和状态转换 | §6 | 在 §4、§7 只写影响任务结果的状态结论。 |
| 异常和处理责任 | §7 | 在 §4 只写主任务的拒绝结果，不扩写异常处理。 |
| 数据字段、记录、系统或审批承接 | §8 | 在 §2 只写对象关系或新增变更；在 §4 只写任务产生的结果。 |
| 已确认体验约束、待定案事项 | §10 | 不重复业务事实；体验关系与待定判断只在本节完整表达。 |
| 可观察验收结果 | §11 | 不反向补充新的业务事实。 |

### 8.4 基线标题下的项目与来源

直接在标题下写项目名、基线状态 `formal` 和原始 PRD 文件名或需求标识。存在审核记录时，写明其文件路径。其他实际纳入的输入仅在相关时短列，并标明用途，例如辅助原型仅作形态参考。正式知识和产品回复按 8.16 节随事实标注。
### 8.5 §1 背景与目标

写清：

- 本期必要性与当前处理方式。
- 本期业务目标。
- 本期包含范围。
- 本期不包含范围。

按以下顺序组织：

```markdown
## §1 背景与目标

### 为什么现在做
{使用短段落说明谁遇到什么问题、问题在什么背景下发生、当前如何处理，以及产生什么直接影响。}

### 本期目标
{使用短段落说明本期要达成的业务改变。}

### 本期范围

本期包含：

- {本期包含事项}

本期不包含（非目标）：

- {本期不包含事项}

```

表达规则：

- “为什么现在做”可以使用短段落，但必须保留问题对象、发生背景、当前处理方式和直接影响。
- “本期目标”使用短段落说明业务改变，不重复“本期范围”或 §2 中的具体能力清单。
- “本期范围”的包含项与不包含项存在多个独立事实时，分别使用无序列表。
- “本期不包含”只写已确认范围，不吸收 Agent 建议。
- §11 仍负责逐项可观察结果；不得在 §1 反向补充新的业务事实。
- 不把本节改成一句摘要，不为缩短篇幅删除原因、目标和范围。

不写体验目标、UX 指标或方案价值判断。

### 8.6 §2 功能与变更清单

只写本期新增、修改、移除，或发生明确关系变化的业务记录、配置项和权限对象。每项写清：

- 是什么。
- 本期发生什么变化。
- 与哪个对象存在已确认关系。

按实际存在的变化类型组织。没有内容的小标题不输出：

```markdown
## §2 功能与变更清单

### 新增

#### {业务对象、配置项或权限对象}

- 本期变化：{新增内容及适用范围}
- 对象关系：{与现有对象的已确认关系}

### 修改

#### {业务对象、配置项或权限对象}

- 本期变化：{修改前后发生的明确变化}
- 对象关系：{与现有对象的已确认关系}

### 移除

#### {业务对象、配置项或权限对象}

- 本期变化：{本期移除的内容及影响范围}

### 复用能力

- 复用：{本期直接复用的现有能力}
```

组织规则：

- “新增、修改、移除”依据正式来源中的本期变化事实分类，不根据标题数量补齐内容。
- 同一对象存在多项变化时，分点写清各自的变化内容、条件和对象关系，不合并成概括句。
- “复用能力”只写正式来源已经确认，且直接影响本期变化理解的现有能力。
- §2 说明对象和关系发生了什么变化。系统与数据影响仍在 §8 表达，本期不做仍在 §9 表达。
- 正式来源没有证明的信息不写入，也不为保留结构而创建空标题或占位句。

禁止把纯角色列为本节对象。员工、管理员、审批人等只在 §3 出现，除非正式来源明确该角色本身被新增、删除或发生数据结构变化。

不得在本节重复任务步骤、角色责任、完整字段展示规则、状态流转或异常处理。对象自身的适用条件可在本节写最短条件；其他条件统一在 §5 完整表达。

### 8.7 §3 谁能做什么

每个角色写清：

- 角色名称。
- 角色责任。
- 可执行动作。
- 权限前提。
- 数据或业务范围。
- 不允许执行的动作。

“可执行动作”只表示该角色获得授权后可实施的业务动作边界，不是用户操作旅程。

不得写任务步骤、任务触发、成功结果、下一业务节点、页面位置或交互顺序。这些信息统一在 §4 表达。

没有独立权限要求时，明确写“沿用现有权限”，并给出正式来源。

### 8.8 §4 每件事怎么完成

按需求任务组织，包括用户任务和系统任务，不按页面组织。每项任务写清：

- 功能编号。
- 执行角色。
- 需求发生事件。
- 业务触发条件。
- 本期支持的进入渠道。
- 前置条件。
- 主任务步骤。
- 成功结果。
- 失败或拒绝结果。
- 下一业务节点或明确终态。

每项任务按以下顺序表达。没有正式事实的小标题整体省略，不写占位内容：

```markdown
### {功能编号} · {执行角色} · {任务名称}

#### 什么时候开始

- 需求发生事件：{事件}
- 业务触发条件：{条件}
- 前置条件：{条件}

#### 从哪里进入

- 本期支持的进入渠道：{已确认渠道}
- 现有任务位置：{已确认位置}
- 现有页面或载体：{已确认载体}
- 现有入口：{已确认入口}

#### 怎么完成

1. {主任务步骤}
2. {主任务步骤}

#### 完成后发生什么

- 成功结果：{结果}
- 失败或拒绝结果：{结果}
- 下一步：{下一业务节点或明确终态}
```

字段落点固定如下。调整表达结构时，不得删除或合并这些事实：

| 原字段 | 输出位置 |
|---|---|
| 功能编号 | 任务标题 |
| 执行角色 | 任务标题 |
| 需求发生事件 | 什么时候开始 |
| 业务触发条件 | 什么时候开始 |
| 前置条件 | 什么时候开始 |
| 本期支持的进入渠道 | 从哪里进入 |
| 现有任务位置 | 从哪里进入 |
| 现有页面或载体 | 从哪里进入 |
| 现有入口 | 从哪里进入 |
| 主任务步骤 | 怎么完成 |
| 成功结果 | 完成后发生什么 |
| 失败或拒绝结果 | 完成后发生什么 |
| 下一业务节点或明确终态 | 完成后发生什么 |

组织规则：

- “需求发生事件、业务触发条件、前置条件”分别表达事件、触发判断和任务开始前必须成立的条件，不合并成一句。
- “怎么完成”只在动作确有先后依赖时使用有序列表；没有先后关系时使用无序列表。
- 正式来源已定义系统自动动作时，将其放在实际发生的位置，不因没有用户操作而省略。
- 成功结果、失败或拒绝结果、下一业务节点或终态分别表达，不用一个“完成结果”概括。
- 同一任务存在不同条件、分支或结果时，分别写清条件与对应结果，不把分支压缩成模糊总结。
- 同一角色承担多个独立任务时分别成节。系统任务与用户任务使用相同的事实完整度。
- 将正式来源已明确、影响操作或验收的页面事实直接转写到所属章节，无需等到审查发现问题才写。§4 按任务保留入口与载体、Tab 及其层级、字段、选项、操作及顺序、交互时机与结果和固定文案。保留明确的数量、适用条件和源文指定的反馈形式。判断条件、默认值及校验归 §5，状态归 §6，异常及恢复归 §7。来源未确定的组件、布局和交互方案由 Page Spec 定义。
- 字段化信息使用“字段名：内容”的完整形式。字段名不得缺失、截断、与相邻内容拼接或被内容替代。
- 任务块生成后，逐项检查任务标题、什么时候开始、从哪里进入、怎么完成、完成后发生什么中的字段归属；发现字段错位、残缺句或无法判断归属的内容时，返回当前任务块修正。

“本期支持的进入渠道”只在 PRD、正式知识、现有系统或产品回复能够唯一证明时写入。

正式来源已经证明现有任务位置或页面载体时，再补充：

- 现有任务位置。
- 现有页面或载体。
- 现有入口。

这些内容只记录现状事实。

不得补写 Agent 推测的页面、菜单、布局、组件或字段方案。

没有正式来源时省略，不写“待确认”或占位值。

以下表达不得写入正式需求基线：

- 进入申请入口。
- 进入配置入口。
- 进入相关页面。
- 使用系统入口。
- 按现有方式进入。
- 从对应模块发起。

这些表达无法证明任务从哪里开始，只是占位语。

页面布局、视觉样式、组件选型和交互载体由下游设计。已由正式来源明确的交互事实及约束按前述职责写入，不把原型中的示意内容写成需求。

### 8.9 §5 要遵守什么规则

每条规则写清：

- 规则编号。
- 适用对象。
- 触发条件。
- 判断条件。
- 业务结果。
- 优先级或互斥关系；不适用时省略。
- 来源。

按以下结构输出每条规则。字段不适用时省略该字段，不使用占位内容：

```markdown
### BR-001 · {规则名称}

- 适用对象：{对象}
- 触发条件：{触发事件或场景}
- 判断条件：{判断条件}
- 业务结果：{允许、拒绝、限制、写入或其他已确认结果}
- 优先级或互斥关系：{已确认关系}
- 来源：{可定位来源}
```

- 标题只放规则编号和名称，不在标题中塞入完整规则结论。
- 适用对象、触发条件、判断条件、业务结果、来源为适用时的独立字段，不压成一个 BR 单行。
- 同一规则存在多个条件与结果对应关系时，使用并列子项表达“条件 → 结果”。
- 互斥、优先级或顺序只在正式来源明确时输出；不能因该字段不适用而删除其他已确认字段。

规则只表达业务决定，不表达体验策略。

### 8.10 §6 会出现哪些状态

先使用 `review_rules.md` 已确认的状态归属。对象自身生命周期才使用以下完整字段：

按业务对象分别描述：

- 状态名称。
- 状态含义。
- 进入条件。
- 允许动作。
- 禁止动作。
- 下一状态。
- 不可逆性；不适用时写“否”。

记录的处理状态只写状态取值、更新事件、终止后是否更新和来源；不得写“流程流转”“下一状态”“终态”或独立状态机语义。

状态名称沿用已确认业务用语，不创造近义状态。

### 8.11 §7 遇到特殊情况怎么办

每项写清：

- 触发场景。
- 业务判定。
- 对用户任务的结果。
- 对对象状态的结果。
- 是否允许重试或恢复。
- 后续处理责任方；有明确责任方时填写。

按以下结构输出每项异常。字段不适用时省略该字段，不使用占位内容：

```markdown
### EX-001 · {异常名称}

- 触发场景：{已确认场景}
- 业务判定：{系统或业务如何判断}
- 对用户任务的结果：{任务被阻断、结束、继续或其他结果}
- 对对象状态的结果：{状态、记录或数据结果}
- 是否允许重试或恢复：{已确认结论}
- 后续处理责任方：{已确认责任方}
- 来源：{可定位来源}
```

- 标题只放异常编号和名称。
- 单一异常存在多个触发条件时，分别写清条件与对应判定和结果。
- 没有正式来源的恢复方式或责任方不补写；仅在字段不适用时省略该字段。
- 已确认的异常处理结论保留原意、适用范围和可定位来源，不为改善措辞改变结论。

写清业务结果，保留正式来源已确认的提示文案、触发载体及恢复动作。未知的提示或交互方案由下游设计。

### 8.12 §8 会影响哪些记录和系统

按适用范围写清实际保存或处理的数据和系统影响。页面展示字段在所属任务 §4 写清，本节按需引用。

- 新增、修改、移除的数据事实。
- 上下游系统影响。
- 同步、重复、并发和失败处理。
- 操作人、时间、原因等审计事实。
- 历史数据处理。

记录的处理状态必须写明保存内容和已确认的更新事件。不得补写来源未明确的同步机制、回写机制、审批任务关系或数据生命周期。

### 8.13 §9 这次明确不做什么

只记录已由 PRD、正式知识或产品回复确认的：

- 业务约束。
- 技术或外部依赖约束。
- 本期明确不做。
- 后续考虑但本期不承诺的内容。

不得把 Agent 建议写成约束。

### 8.14 §10 体验定案

本节承接问题单分类后的体验内容，不承接原始补充全文。

按以下顺序输出。没有内容的二级标题不输出；两类内容均不存在时，整个 §10 不输出。

```markdown
## §10 体验定案

### 已确认体验约束

#### EC-001 · {适用任务或场景}

- 必须保留的体验关系：{用户明确输入的体验关系}
- 来源：{问题单补充位置}

### 待定案事项

#### E-001 · {适用任务或场景}

- 需要完成的体验判断：{审核发现的体验缺口}
- 来源：{可定位来源}
```

已确认体验约束只写下游必须保持的体验关系。待定案事项只写待完成的判断，不写候选方案。两者均不写页面布局、视觉样式、未确认字段、业务规则或具体文案。

### 8.15 §11 做成后应该看到什么结果

产品不需要单独编写本节结果。

PRD Review 只把已确认业务事实改写为可观察结果。

每条结果必须包含：

- 对应目标、任务、规则、状态或异常。
- 前提。
- 用户或系统动作。
- 可观察结果。

本节至少覆盖：

- 每个主要任务的成功结果。
- 会阻断主任务的关键拒绝结果。
- 核心状态变化。

每个验收场景使用一个列表项，在同一行写清对应事实、前提、动作和可观察结果。

```markdown
- **AC-001（{对应目标、任务、规则、状态或异常编号}）** {已确认前提}下，{用户或系统动作}，{可直接判断的结果}。
```

- 一条 AC 只表达一个可验证场景。存在多个前提分支时，分别建立 AC。
- 每个主要任务至少有一条成功结果；每个会阻断主要任务且已有明确业务结果的关键拒绝或异常，至少有一条结果；每个影响主任务的核心状态变化，至少有一条结果。
- AC 只引用既有目标、FN、BR、EX 或状态事实，不新增业务事实。

不得增加：

- 新规则。
- 新阈值。
- 新范围。
- 技术实现方式。
- 页面布局。
- Agent 建议。

不得使用“体验良好”“操作顺畅”等不可直接判定的表述。

### 8.16 事实级来源

在结论旁标出可定位的短出处，例如 PRD 章节、正式知识文件及章节或规则编号、产品回复的问题编号及子项。每条业务事实都要能定位其依据。共用出处可写一次，阅读时应能明确它覆盖哪些事实。
### 8.17 事实合并规则

基线内容按以下优先关系整理：

1. 产品明确回复用于关闭对应阻断问题。
2. PRD 定义本期目标状态。
3. 审核记录中的业务事实补充，用于补入已被正式知识唯一证明且未被本期改变的当前事实。

发生冲突时：

- 产品回复只能覆盖其明确回答的范围。
- PRD 明确新增、修改、移除的目标事实，不得被旧知识覆盖。
- 未被产品回复关闭的冲突不得进入基线。
- Agent 不得用推理补写缺失事实。

“需求初识”只用于建立审查认知，不是需求事实。体验定案按本文件 §10 与 `review_rules.md` 的分类规则写入基线；原始补充、候选方案与页面方案不写入。

每条事实写入前依次检查：

事实来源是否有效只按 `review_rules.md` 第 3.2 节判断；成熟基座事实是否能够写入只按 `knowledge_usage_guide.md` 第 10 节判断。本文件只将已通过判断的事实按上述优先关系整理，不重新执行语义门禁。

同一对象不得同时被写为“记录状态不更新”与“记录状态按流程流转”。发现矛盾时返回状态归属判断，不得生成正式基线。

### 8.18 基线文案规则

- 使用确定语气。
- 一条只表达一个业务事实。
- 并列事实使用无序列表。
- 有执行顺序时使用有序列表。
- 使用稳定编号引用功能、规则和问题。
- 优先使用设计师和业务人员能够直接理解的业务用语。
- 标题直接说明当前信息回答什么问题，不使用“基本信息”“相关内容”“其他说明”等空泛标题。
- 长段落优先拆成主结论、条件和并列事实，不删除条件和例外。
- 一个列表项表达一个完整业务关系。条件、动作和结果共同构成一项事实时，保持正确对应，不为短句强行拆散。
- 不同条件、状态、结果、责任方或业务对象分别保留，不合并成模糊结论。
- 不设置固定字数、固定句数、固定列表项数量或篇幅上限。文档变短不是目标，事实完整和语义守恒优先。
- 删除重复时，只删除语义、条件、对象、状态、结果和来源完全相同的重复表达。
- 不复制问题讨论过程。
- 不保留“建议”“可能”“待确认”等讨论语气。
- 不写下一步推荐。
- 不写 UXB 或 Page Spec 的设计结论。

## 9. 来源追溯

审核记录与基线的依据只允许来自：

- PRD 原文位置。
- 正式知识文件与章节。
- 已存在的问题编号和产品回复。

来源可以简写，但必须可定位。

## 10. Handoff 建议格式

### 10.1 生成前提

只有正式需求基线生成后，才给出下一步建议。

Page Spec 是唯一推荐主链。UXB 和 Journey Analysis 固定列为 Page Spec 前的可选增强。

Handoff 建议不写入问题单或需求基线。

### 10.2 用户可见格式

```text
下一步：

1. Page Spec（推荐）
   将正式需求基线直接转为交付级页面设计文档。

可选增强：

- UXB：形成粗颗粒度的体验方向与取舍
- Journey Analysis：补充旅程阶段、断点与风险

以上增强产物仅在本轮明确采用并满足门禁时由 Page Spec 承接。

你回复对应名称即可。
```

主推荐和增强说明使用短句，不补充需求级动态判断。增强能力由用户选择，不规定调用顺序，不自动执行。

### 10.3 人工决定

展示后的停止与人工选择规则只按 `SKILL.md` 的“Handoff · 下一步建议”执行。本文件不得根据用户可见格式自动触发下游。

## 11. 用户可见文案规范

- 一句话只表达一个意思。
- 并列事实使用无序列表。
- 执行步骤使用有序列表。
- 标题不跳级。
- 不输出与产品沟通无关的信息。

## 12. Markdown 自检

- 文档状态与问题状态一致。
- 审核结论位于需求初识之后、用户补充之前。F、Q、E、S-M 各条目只出现一次，场景、必要条件和依据随对应条目保留。
- Q 原编号、原问题和子项顺序保留，回复及复核结果紧跟对应项。用户补充原文保留在固定入口，不参与编号与状态计算。
- 问题编号唯一且连续追加。
- 每个待确认项均能从对应回复行识别复核结果。
- 每个问题组只处理一个业务主题。
- 每个列表项只要求一个完整触发条件下的最小业务结论。
- 没有把由同一规则和同一证据完整覆盖的条件机械拆分。
- 回复和关闭状态与列表项一一对应。
- 不按回复数量、编号数量或上下文相邻推断问题关闭。
- 没有因推进意图绕过已识别的证据缺口。
- 本期任一阻断项未获得有效证据时不生成正式需求基线。
- 每条基线事实都有可定位来源。
- 没有把基座可选能力写成本期事实。
- 没有增加来源中不存在的动作、角色、字段、条件、状态、异常、恢复路径或数据影响。
- 核心任务的进入渠道不存在占位语。
- 内部来源追溯能够定位 PRD 或正式知识。
- 业务事实补充和建议修改都有唯一事实依据。
- 体验定案事项没有写成体验方案或页面方案。
- 没有长句、重复背景或内部推理。
- 冻结基线前，在现有一轮自检中，从本轮已读的有效来源逐项向草稿核对，复用内部事实表。每项同时检查是否写入、章节归属是否正确、字段与选项成员、数量、默认值、触发时机、交互结果、反馈形式和固定文案是否保留，以及草稿是否补写了未经确认的内容。概括后丢失条件或结果的视为漏项，补回对应章节。未决冲突和关键事实缺口沿用原审核门禁。
- 拆分长句后，原有条件、对象、状态、结果、下一节点、例外和来源仍然完整。
- 合并重复表达时，没有合并条件、对象、状态或结果不同的事实。
- §4 每项任务保留所有适用字段；没有证据的可选字段按规则省略，不使用占位内容。
- §4 已输出的字段均有完整字段名、冒号和内容；不存在字段错位、残缺句或内容串入相邻字段。
- §5 每条规则保留所有适用字段：适用对象、触发条件、判断条件、业务结果、优先级或互斥关系、来源。
- §7 每项异常保留所有适用字段：触发场景、业务判定、任务结果、对象状态、重试或恢复、责任方、来源。
- §10 的每条 EC 或 E 均能定位适用任务或场景与来源。
- §11 每条结果均能定位对应事实，且包含前提、动作和可观察结果。
- §11 覆盖所有主要任务成功结果、关键阻断或拒绝结果、核心状态变化。
- 新增小标题只用于帮助阅读，没有改变章节职责或事实归属。
- 没有通过固定字数、句数、列表项数量或篇幅上限压缩语义。

语义检查由 Agent 完成。脚本不得判断事实是否等价、内容是否啰嗦或大白话是否合格。

- 体验策略。
