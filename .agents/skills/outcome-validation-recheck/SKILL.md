# 结果验证与回检

判断“方案是否已经具备验证条件、是否产生预期效果、效果能否归因于本次干预、是否持续且无关键伤害”，并把判断写成一份可审阅的 Markdown 报告。本技能不发明方案，也不把一次指标变化直接写成因果结论。

## 适用与边界

适用：

- 上线前或演示阶段：判断是否具备进入下一验证阶段的条件，即基线、观察窗口、暴露、实施到位和测量是否可确认。
- 试点或上线后：判断核心指标与护栏是否改善、变化能否归因于本次干预、关键分群是否受损。
- 长期或回归阶段：判断效果是否持续、是否衰减或回归，并评估已提供的回归监测结果。

边界：

- 不设计或补全干预方案；方案版本、来源、范围、人群和预期作用机制来自已批准方案或用户明确确认。
- 不重算客观分析的统计量，不重新解释原始数据；新主观反馈或体验走查证据必须先经证据治理放行。
- 不自行设定业务阈值、告警频率和通知人；不持续拉数、不建定时任务、不配置线上监控、不自动回滚、不自动重跑完整分析链。
- 不直接修改证据、候选根因、知识库或归档状态；根因反馈须先经证据治理吸收。
- 只做效果与验证判断，不做方案设计、价值估算和界面表达；需要价值重估、图表或归档时由相应环节承接。

## Step 0 · 运行入口与来源门禁

输入只来自用户本轮明确给出或上游正式放行的结论。不扫描历史目录猜测“最新材料”，不自动沿用上一次结论，也不因为已有产物而改变本轮阶段或跳过门禁。

必须同时具备：

- 候选根因面向本技能的正式放行结论，来源可定位、版本与摘要可核对。
- 已批准的干预方案：干预版本、来源、关联的候选根因、预期作用机制、变更范围、目标人群、当前验证阶段、暴露与实施到位定义、目标指标与护栏引用、批准状态和遗留限制。
- 试点以后还必须具备证据治理面向本技能放行的验证证据。

放行缺失、审核未批准、引用无法解析或绑定不一致时宁可不出结论，且只阻断受影响范围，不扩大到整个流程。门禁结果只有五种：阻断、需用户补充、部分完成、带保留项放行、放行；放行只表示允许评估，不预设有效。

用户只给出问题结论而没有确认方案时，用业务语言说明一次：

> 我可以帮你判断优化是否有效，但需要先确认验证的是哪一版方案、覆盖了哪些用户，以及这些用户是否真正体验到了完整改动。

一次只确认一个会改变范围、规则解释或验证阶段的问题；不询问内部字段、字段映射或门禁细节。

### 上游交接核对

在本轮关联的 `spark-output/root-cause-synthesis.md`、已批准干预方案和 `spark-output/evidence-governance.md` 放行的验证证据中核对同一候选、干预版本、验证窗口和允许用途。宿主明确传入报告时，以传入文件为准，并核对报告身份。「精准回流、监测要求与证据缺口」按编号写清拟反馈给证据治理的证据变更、触发依据和待确认事项，由证据治理决定如何吸收。

## 分析规则

更细的准备度、效果与归因、护栏与回流、报告与风险细则，见同目录 `references/` 下的四份规则说明，按当前模式读取，不必一次全部加载。

**一次只用一种模式。** 上线前/演示只判断准备度，不输出效果结论；试点/上线后判断效果、归因、护栏与分群；长期/回归才判断持续性与回归。三种模式不混合执行。

**准备度分维判断。** 基线、观察窗口、暴露、实施到位、测量五项分别给出就绪、未就绪、未知或不适用，缺哪一项就明确写出，不用总分掩盖缺口。上线前与演示阶段只回答“能否进入下一阶段”。

**效果与归因是两道独立门。** “结果变好”和“由本次方案导致”必须分开判断。指标改善但同时存在版本、运营、培训、故障、季节或口径变化时，只能作相关性归因；混杂风险低且证据设计足以支持时，才可声明因果支持，其余写相关性或未知。暴露不足或实施不到位时结论是不可评估，不是无效。

**结果等级。**

- 有效：主要结果改善、关键护栏无实质伤害、准备度满足；
- 部分有效：部分目标达成，但范围或持续性受限；
- 混合：正负结果并存，尤其是关键分群或护栏受损；
- 有害：净影响明确偏负；
- 无效：实施与暴露充分、观察条件有效，但目标未改善；
- 不可评估：输入、准备度或测量不足。

**伤害、混杂与问题迁移。** 核心指标改善不等于体验整体改善：必须检查关键分群是否受损、报错、投诉、人工介入或时长是否被转移到其他环节、原问题是否换一种形式出现、新副作用是否超过可接受边界。关键护栏或关键分群恶化时，不得给出单纯有效。

**只消费正式结论。** 客观分析提供统计结果、分群结果、基线比较、样本可靠性与影响规模，本技能引用而不重算；主观反馈与体验走查的新证据须先经证据治理放行；业务影响给出的价值结论只作补充解释，不能替代主客观效果证据。

**效果事实的粒度。** 每条效果事实绑定指标、粒度、维度、基线窗口和比较窗口；问卷量表按回复粒度、企业状态变化按企业或企业×业务板块粒度。不同粒度不得合并成一个效果值，预测值不得当成实测效果。

**监测与回流。** 只形成监测要求并评估已提供的监测结果，不拉数、不调度、不配置平台；阈值、频率、通知人必须来自正式政策引用，不能自设，政策齐备也只能标记为可交由后续自动化，当前不可调度。回流只覆盖受影响范围：数据、口径或分群问题回到对应分析环节；证据强弱、冲突或陈旧回到证据治理；根因反馈先经证据治理吸收再回到候选根因；价值重估需要已验证的效果。整链自动重跑始终关闭。

**人工审核。** 审核缺失、被拒或绑定不一致时只阻断对应结论，审核不伪装成技能回流。

**隐私与脱敏。** 只输出聚合汇总或脱敏引用，不复制原始服务日志、逐条工单、明细用户或企业标识、原始反馈正文和敏感字段。必须保留原始报错文本时，先移除身份标识、令牌、密钥、联系方式、账户、设备、网络地址、完整请求体和其他可回溯参数。

**知识边界。** 不直接发布知识；单次效果、单次回归和未经复核的机制不能进入知识库。

## 输出（Markdown）

正式产物为 `spark-output/outcome-validation-recheck.md`。在正文记录本轮任务、范围或时间窗、输入来源和产物身份。消费上游时读取本轮明确关联的完整 Markdown，核对所属项目或需求、分析范围、来源、可用结论及限制。同一路径的旧产物只有在本轮明确关联时才可采用。需要放行或审核的内容，以报告中可定位的条目及明确授权为准。

必须输出一份完整、可直接阅读的中文 Markdown 文档，作为本技能的唯一产物；判断、数字、限制与缺口全部写在文档内，不另建运行目录或结构化事实文件。章节依次为：

```markdown
## 1. 验证判断与结论边界
## 2. 验证范围、方案版本与准备度
## 3. 核心指标、护栏与分群结果
## 4. 归因强度与混杂因素
## 5. 副作用与问题迁移
## 6. 持续性与回归观察
## 7. 精准回流、监测要求与证据缺口
```

写作要求：

- 每章先给判断句，再给依据、窗口和限制；数字能在文内追到来源，不补造。
- 上线前或演示阶段只完整填写准备度相关章节，其余章节保留标题并写明当前阶段不适用，不提前给效果结论。
- 证据不足、阶段不适用或无法评估时写明原因和影响范围，不省略、不用空话填充。
- 效果与归因分开表述，不用“证明”“导致”描述相关性结果，预测和情景不写成已实现。
- 不写设计方案、具体改法、预算排期、负责人和告警配置；需要图表时另行发起可视化。
- 全文不出现明细身份信息、敏感参数和可回溯的原始数据。

## 自检

- 模式与阶段是否匹配，且一次只执行了一种模式？
- 方案版本、范围、人群、暴露与实施到位是否可识别？
- 试点以后是否只使用了证据治理放行的验证证据？
- 是否没有重算客观分析的统计量？
- 效果与归因是否分开判断，高混杂风险下是否只作相关性表达？
- 关键分群与护栏伤害是否没有被总体改善掩盖？
- 根因反馈是否先经证据治理吸收？
- 监测要求是否只引用正式阈值与频率，且没有调度、回滚或自动重跑？
- 文档是否章节齐全，缺失与不适用都写明了原因？
- 是否没有输出明细身份信息、敏感参数或可回溯原始数据？
