# 知识入库主合同

本文件是 `knowledge-wiki` 的唯一完整入库流程。任何直接入库、候选促进、覆盖修正或整包知识启动都必须遵守。

## 底线

- `knowledge/raw/**` 是唯一正式事实源。
- 用户只负责提供材料和回复必要确认；Agent 自动整理、归类、分流、写入、刷新和校验。
- 信息不足时宁可进入结构化候选，不模糊写入正式知识。
- 文件所在位置不代表事实权。放在 raw 的未整理材料也必须经过本合同。
- 不把当前项目的业务集合、领域名或目录深度当成通用标准；业务领域内部统一使用固定八类载体。
- 过程中的证据块和知识原子只是内部处理结构，不新建第二套持久知识层。
- 无论材料来自何种渠道，未完成本文件第 12 项的逐单元入库安全验收，不得写入 `knowledge/raw/**`。

## 五阶段主流程（十二项检查）

### 第一阶段：证据接收

#### 1. 材料盘点与来源登记

在用户指定的对话、附件、文件或文件夹范围内自动盘点，不要求用户搬运或改名。至少识别：

- 材料位置、类型、可读性、重复和缺失。
- 提供者、确认者、时间、版本和适用环境，如可得。
- 用户是要记录线索、正式入库、覆盖修正还是批量启动。
- 材料是否混合现状、目标、历史、外部参考和推断。

用户指定文件夹时，自动处理该范围，不扩展到未授权目录。原始材料或可追溯引用必须保留在用户授权的材料范围或既有归档中；不得只留 Agent 整理稿。正式设计规范正文不写入原始材料来源路径，也不为来源追踪建立额外映射文件。

#### 2. 证据块提取

按 `input-adaptation.md` 读取文字、图片、文件和混合材料。临时证据块必须保留来源位置、可见内容、适用线索和不确定性。

只有清晰可见或文本明确表达的内容才可继续作为事实证据。推断、模糊数字、不明状态、无证据的多图顺序和不可辨认内容不得进入正式事实。

#### 3. 材料分类

将证据块分为：

- 当前正式事实。
- 范围受限事实。
- 目标方案或候选。
- 历史口径。
- 冲突。
- 缺口或问题。
- 重复。
- 噪音或不入库内容。

需求目标、讨论方案、竞品做法、营销表达、一次性交付和 AI 推断不得写成当前事实。

### 第二阶段：事实构建

#### 4. 无损拆解与闭合

先在内部拆分：主体、对象、动作、前置条件、核心规则、状态变化、生效结果、异常结果、恢复方式、权限责任、例外限制、审计要求、适用范围、表达强度、来源依据和不确定项。

按 `SKILL.md` 的统一事实边界判断事实身份和事实边界。只有二者均相同，才允许比较是否重复或冲突；任一不同都必须分别保留，不得为追求表面一致而合并。

不要求每条填满全部维度；但涉及权限、审批、状态、支付、安全或数据处理时，不得省略会改变结果的条件、生效、失败、例外和审计语义。

不得把跨场景通用规则错误归入单个功能或流程。

只对边界客观且可机械复核的内容严格计数：

- 带 ID 的功能表和普通结构化表格：每条独立记录。
- FAQ：每个完整问答块。
- 状态表和规则表：每条明确记录。
- 流程图：每个明确节点、分支和转换。
- 编号操作步骤：每个明确步骤。

每个严格计数单元必须且只能归入正式入库、无损合并、完全重复、进入候选或明确不入库之一，且处理结果数量之和必须等于源计数单元总数。

同一批材料出现多个可计数表达时，先核对事实身份、事实边界和直接事实责任。事实身份或事实边界无法确认时标记 `[QUESTION]`；三者相同但集合不一致时标记 `[CONFLICT]`。流程、页面、示例或 FAQ 中的局部表达，应保留自身范围并链接主要事实责任章节，不得增补流程节点或删减正式清单来强行对齐。

普通正文、无编号说明、图片和截图不得主观计算“知识原子总数”。按源章节核对主体与角色、业务对象、动作与任务、前置条件、规则与优先级、状态与转换、成功结果、失败与恢复、例外与限制、权限与审计、适用范围、来源与不确定性；每项只允许标记为已处理、源材料未提供或证据不足。

长表格、大批量 FAQ、流程和长正文必须按自然批次处理：一个完整功能表、一个 FAQ 二级主题、一张完整流程图或一个稳定正文二级章节为一批。当前批次未完成闭合和复核，不得进入下一批；不得一次处理整份大文件后只给总体摘要。

#### 5. 来源强度与适用范围

来源强度从高到低参考：当前正式产品或制度真源、产品或业务所有者确认、当前操作手册或帮助中心、已确认会议结论、可复验运行或界面证据、FAQ 与运营口径、需求目标与假设、历史材料、外部资料、AI 推断。

来源顺序不是自动覆盖顺序。覆盖前必须同时确认对象、版本、范围、条件强度、替代关系和旧事实是否仍在部分场景有效。事实身份或事实边界无法确认时保留 `[QUESTION]`；事实身份、事实边界与直接事实责任相同但无法裁决时保留 `[CONFLICT]`。

范围受限、冲突、覆盖、废弃和高风险规则必须在对应正文中保留简洁来源与适用范围。不新建逐事实关系库或 manifest。

### 第三阶段：可信分流

#### 6. 知识集合与主域归属

先读取 `knowledge/LLM.md`、`knowledge/wiki/index.md` 和命中的本地路由合同，再决定知识集合、主域、条件依赖域和排除域。

先判断本次入库目标属于业务知识、设计准则、交互模式还是设计规范。业务知识继续使用八类固定载体；设计规范读取 `../templates/设计规范入库/README.md` 和 `知识对象划分指南.md`，按样式、组件、典型页面或场景模式确定主分类，不读取业务知识八类模板作为文件选择依据。设计准则和交互模式继续遵守各自既有维护结构，不从设计规范入库任务中自动改写。

用户明确指定的产品、业务集合、应用、领域或业务主题分类优先级最高，不得擅自改名或改变语义边界。用户明确要求物理隔离时按其要求处理；否则分类名称优先作为八类文件内的稳定章节，不能因材料已有文件夹就自动建立物理子域。只有材料未分类、用户明确现有分类只是临时整理，或用户明确要求重新梳理时，才读取 `../templates/业务知识入库/领域划分指南.md` 执行领域划分。

主域是拥有当前对象最终状态和结果解释权的知识单元。依赖域只记录自己的输入或机制，不复制主域结论。

新业务集合只能基于稳定的产品、系统、地区、组织、客户范围或独立维护责任建立；不得按批次、文件来源或临时不确定性建立。无法稳定解释新集合的责任和消费入口时，先进入候选。

#### 7. 定向影响扫描

候选和用户直接输入使用同一套扫描线索：对象、角色、动作、状态、页面、字段、菜单、路径、旧表述、新表述、同义词、历史称呼、FAQ 和显式问题标记。

先读明确命中的 raw，再对受影响知识集合做定向文本搜索。不得只改输入点名的文件，也不得因全库文本命中顺手修改无关知识。结果固定分为：必须更新、命中但不更新、保留冲突、补充缺口或问题、不属于本次范围。

#### 8. 直接入库、候选与不入库分流

直接入库必须同时满足：

- 能确认是当前事实。
- 来源与适用范围清晰。
- 知识集合、主域和落点唯一。
- 无未解决冲突或未授权高风险覆盖。
- 不依赖猜测。
- 会改变结果的条件、状态、例外、生效和失败语义足够完整。

任意一项不满足，默认进入结构化候选。已完整覆盖的内容标记重复；方案、噪音、过程或无事实依据推断标记不入库。

来源是 FAQ、操作指引、外部材料或讨论记录，不决定其是否属于正式事实。每个自然语义单元先按其对角色、任务、规则、状态、结果、边界和上下游依赖的影响判断责任类型；仅保留操作、排障、帮助、外部动态或收费协议用途的内容，才进入辅助资料。

用一次对外回执按源章节、处理结果和正式落点分组汇总严格计数结果与正文语义闭合结果；只有跨落点、冲突、候选、重复、不入库和无法证明等价的内容逐项展开。回执不复制知识正文，不形成长期台账。请用户回复“确认处理”；覆盖、删除、冲突、新建顶层知识集合或大范围结构变更单独请求“确认覆盖”或对应确认。

### 第四阶段：责任落点与写入

#### 9. 变更类型与落点

每个知识原子选择：新增、补充、修正、替代、废弃、冲突、缺口、问题、重复或不入库。

如果本次目标是设计规范，先按以下顺序确定落点：

1. 按问题主体进入样式、组件、典型页面或场景模式。
2. 合入对应主题文件的现有章节。
3. 现有主题可以无损承载时增加边界明确的新章节，并同步顶部导航。
4. 只有对象可独立路由、回答和维护，且增加章节仍会造成范围混淆时，才建立核心名称明确的新主题文件。
5. 一个来源文件混合多个稳定对象时按对象拆分；多个来源文件回答同一对象时无损合并为唯一正文。
6. 同步设计规范根 README、分类 README、主题顶部导航和必要的全局 index；全局 index 不建立逐主题入口。
7. 逐章节执行 `../templates/设计规范入库/来源语义验收清单.md`。不得摘要化，条件、数值、状态、例外、结构、步骤、反馈和恢复路径必须保留。

设计规范文件名只表达核心对象，不重复上级目录已有的“规范”“组件”或“场景”语义。README 只维护契约、路由、依赖和停止条件，不复制主题正文。正式设计规范不保留来源路径、CSV 检索表、问答脚本、Prompt、回答模板或 AI 检索元数据。

设计规范入库检查发现可归入设计准则或交互模式的信息时，原始信息继续完整保留在设计规范。只在当次聊天窗口列出信息位置、核心内容、判断依据和建议归属，等待用户决定是否另行更新；不得自动迁移或修改设计准则、交互模式，不得创建候选文件、未入库记录、映射表或其他持久化状态。

如果本次目标是业务知识，再执行以下八类载体落点规则。

确定主域后读取 `../templates/业务知识入库/信息类型目录.md`，按知识回答的判断问题选择八类中的唯一类型；不得按文件排列、历史编号或当前领域文件清单反推类型。

落点顺序：

1. 合入对应固定文件的现有章节。
2. 在对应固定文件中增加边界明确的新章节。
3. 固定文件不存在且该类型已有正式事实时，按固定文件名建立文件。
4. 同一类型的多个模块或主题优先形成可精准导航的大文件，不得按模块重复建同类型文件。
5. 同一领域内的应用、模块、对象和业务主题优先作为固定文件章节；只有同时通过物理子域四项门禁时才新建子域，不得用子域规避同类型单文件规则。
6. 八类无法无损承载时进入第九类例外审批；七项门槛未全部满足或用户未明确确认时留在候选。
7. 未确认信息留在候选。

行数不是拆分依据。大文件可以保留，但必须具备定位、适用范围、场景路由、快速导航、稳定章节、未决项和维护边界。

建立物理子域必须同时满足：

1. 拥有父域无法替代的核心对象、最终状态或结果解释权。
2. 角色、规则、状态和任务能够在子域内形成稳定业务闭环。
3. 具有独立维护责任和可单独命中的主要消费任务，而不是只因菜单、模块名、来源文件或内容较多而独立。
4. 合入父域八类文件后仍会造成适用范围混淆或无法精准导航，且增加章节与快速导航不能解决。

任一项不满足，不得建立物理子域；保留业务分类名称，在父域同类型文件中建立明确章节。用户明确要求物理隔离时记录其分类依据并执行，不得擅自改回章节。

功能级知识命中“功能与操作清单”时，清单只拥有“系统明确支持什么功能或操作”的事实。源记录明确提供的角色、终端、对象、状态、条件、结果、例外和标识必须保留；规则、权限、状态或流程存在更完整真源时，只建立定向链接，不复制为第二真源。不得按单条功能或单个 FAQ 建文件，也不得形成跨维护责任且无法导航的巨型文件。

每个业务领域及具备独立消费责任的子域必须有 `README.md`。README 只维护领域契约、文件级路由、条件依赖和停止条件；不得复制正文或维护长文件章节目录。

#### 10. 外科式写入或候选生成

确认后只修改必要章节，保持本地标题、术语和文案风格。不重写无关正文，不删除条件、例外、否定规则、状态、失败、恢复、审计和显式未决项。硬规则使用“必须、不得、仅当、否则”等清晰表达。

候选按 `candidate.md` 和候选模板生成。候选不是原始材料堆积；必须准确说明已确认内容和不确定性。

设计规范中的准则或模式建议不属于候选生成场景，只在当次聊天窗口提示。用户确认后另行启动对应知识类型的独立维护任务。

脚本只允许只读提取、机械计数、路径与编码检查和结果验证；不得决定语义分类、重复关系、主事实落点或冲突裁决，不得批量改写、格式化或重新保存知识 Markdown。

#### 11. 路由同步

- 检查业务领域及通过四项门禁的独立子域 README 的契约、任务信号、正式知识清单、依赖和停止条件。
- 检查设计规范根 README 与分类 README 的契约、任务信号、正式知识清单、依赖和停止条件，确保每个主题由唯一分类 README 路由。
- 新增可独立命中的大文件章节、FAQ 问题块、页面语义、状态或规则时更新顶部导航。
- 只有顶层知识类型、业务集合、可直接消费的领域或大文件变化时才更新 index。
- README 不得复制正文或章节目录；目标文件的章节定位由其顶部快速导航负责。

### 第五阶段：验证收尾

#### 12. 发布前入库安全验收、校验与收尾

所有实际入库渠道都必须先对准备写入的正式知识文本完成逐单元验收，通过后才可写入正式 raw；如已在工作区形成草稿，未通过不得将其视为正式入库结果：

- 逐一核对源材料的自然语义单元，确认原始事实、条件、否定、例外、状态、范围和表达强度未被删减、合并或拔高。
- 确认每个单元落在唯一责任文件，或被明确标为候选、重复、不入库或冲突；不得以“已处理”替代具体处理结论。
- 确认新增、修正、替代、废弃之间的关系明确；未获授权不得静默覆盖或删除旧事实。
- 确认正式知识可以通过领域 README、目标文件顶部导航和必要条件依赖被定位；辅助资料不承担正式事实真源。
- 设计规范必须能够通过全局 index、根 README、分类 README、主题文件和顶部导航定位；整理不得减少条件、数值、状态、例外、结构、步骤、反馈和恢复路径。
- 设计规范中的准则或模式建议只允许出现在当次聊天窗口；确认未修改两类正式知识，也未生成候选文件或其他持久化记录。
- 对可严格计数的来源，处理结果数量必须与源计数一致；对普通正文、图片和截图，必须按源章节完成语义维度闭合。
- 验收结果只能是通过、退回候选、保留冲突或停止请求确认。任一单元不通过，不得发布对应正式 raw 修改。

再按 `validation.md` 执行机械校验、语义复核和必要的一次性路由抽查。不为普通入库建立长期场景库、消费轨迹、路由反馈系统或召回指标平台。

## 全流程硬停止条件

命中以下任一情况时停止正式写入，转入候选或请求必要确认：

- 无法确认现状与目标。
- 关键来源冲突无裁决依据。
- 无法确定最终状态与结果的知识所有权。
- 缺少会改变结果的对象、条件、状态或范围。
- 输入只有标题、模糊图片或不可辨认内容。
- 无法确定是否需要新顶层知识类型或业务集合。
- 覆盖、删除、批量迁移、目录重构或移动用户直接放入 raw 的材料尚未获得明确确认。
