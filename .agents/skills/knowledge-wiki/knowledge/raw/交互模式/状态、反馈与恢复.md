# 状态、反馈与恢复模式库

供 Phase 1 辅助识别状态链、结果承接和反馈断点，供 Phase 2 辅助展开状态表达、返回原任务的设计和异常处理。

**使用方式**：当材料中出现审批、驳回、处理中、同步、失败、结果核对、返回原任务、重提、待处理等信号时，参考本库判断哪些状态和反馈需要前置表达、哪些结果不能后置处理。不替代当前项目材料形成固定结论。

**阅读提醒**：以下模式用于对照判断状态可见性、反馈时机和结果承接方式，不是固定流程模板；是否需要新增状态表达、确认层或返回原任务的动作，仍应回到当前材料中的任务风险、修复成本和上下游依赖判断。

**装配要求**：选中模式后，必须结合当前业务证据写清当前状态、触发动作、状态变化、反馈时机与承载形式、用户可执行动作、异常恢复和返回原任务；不得只输出状态名、组件名或通用提示。若进入具体反馈、报错或引导设计，继续读取本文对应模式与承载形式，不能停在状态判断。

## 状态与反馈模式

### 状态前置可见
**适用**：对象存在多个中间状态，且状态会影响用户下一步动作、可见范围或可编辑范围；用户在发起前就需要知道当前是否可操作  
**不适用**：状态只作为后台记录，不影响当前任务判断；单次短流程用户可自然感知当前所处阶段  
**常见误用**：把真正影响后续动作的状态藏到详情页或提交后才暴露  
**失败代价**：用户在错误前提下继续操作，直到提交或同步阶段才发现当前状态不允许

### 驳回不是普通编辑
**适用**：驳回、退回、补充材料、重新提交等动作需要先理解原因，再定位修正点并重走部分流程  
**不适用**：用户只是补充一个不影响流程判断的轻量字段；修改动作不改变后续审批或同步链  
**常见误用**：把驳回后处理直接当作普通编辑页复开，不说明驳回原因、影响范围和需重新确认的内容  
**失败代价**：用户不知道该改哪里，重复提交失败，或误以为小改即可恢复原流程

### 结果返回原任务
**适用**：子流程完成后用户需要回到原任务继续处理；结果会改变父任务的下一步可操作项、状态或显示内容  
**不适用**：子流程本身已经形成独立闭环，完成后无需回到触发链路  
**常见误用**：子流程成功后只给成功提示，不告诉用户结果如何作用回原任务  
**失败代价**：用户完成子流程后失去原任务位置，不知道是否已生效、还要去哪里继续

### 同步结果分层表达
**适用**：存在系统同步、外部接口处理、审批后下游回写、异步生成等非即时完成结果  
**不适用**：操作结果即时确定，且没有下游依赖  
**常见误用**：把“已提交”“同步中”“同步失败”“已完成”压成一个成功结果  
**失败代价**：用户误以为流程已彻底完成，实际上还停在处理中或失败待修正阶段

### 结果核对前置
**适用**：任务包含公式、规则、配置、批量处理、差异比对等需要在提交前判断结果是否正确的场景  
**不适用**：任务主要目标是一次性收集输入，且结果无需中途核对  
**常见误用**：把结果检查完全后置到提交或发布之后  
**失败代价**：用户在错误路径上走得更远才发现问题，修复成本明显放大

### 高风险动作反馈闭环
**适用**：删除、撤回、停用、批量处理、不可逆提交等动作需要确认对象、范围和影响  
**不适用**：低风险高频动作，过强反馈会打断节奏  
**常见误用**：只有确认，没有结果反馈；或只有结果 toast，没有说明影响范围  
**失败代价**：用户既不确定是否执行成功，也不清楚执行后哪些对象受到影响

### 异常修正可执行
**适用**：存在失败、异常、校验不通过、同步出错等需要用户继续修正的场景  
**不适用**：异常只需系统后台重试，用户无须参与处理  
**常见误用**：异常只提示“失败”或“请重试”，不告诉用户当前卡在哪、能做什么  
**失败代价**：用户只能反复尝试或外部求助，无法形成自助修复闭环

### 待处理聚合与下一步引导
**适用**：任务完成后仍有待办、后续审批、补资料、查看结果等下一步动作；或用户需要在多个处理中对象间切换  
**不适用**：任务完成即终点，且结果在当前页面已充分可见  
**常见误用**：完成后只提示成功，不说明后续还有哪些对象待处理、待核对或待跟进  
**失败代价**：任务链断在中间，用户不知道是否真正完成整轮业务目标

## 使用提示

### 更适合 Phase 1 读取的情况

- 材料中大量出现状态、进度、审批节点、同步、驳回、重提、失败等词，但问题还没有被清晰识别
- 当前需求的主要摩擦看起来不是入口或布局，而是用户不知道“现在处于什么状态、接下来做什么”
- 需要判断某个分支是否应该被视为独立问题，例如“驳回后处理”“同步失败后修正”“结果核对”

### 更适合 Phase 2 读取的情况

- Phase 1 已识别到状态断点、反馈后置、结果承接不清，但还需要展开为策略
- 需要判断策略是否应该包含状态标签、处理中反馈、结果核对区、返回原任务说明或异常处理闭环
- 需要校准“高风险动作确认”和“结果反馈”是不是同一个策略单元

---

## 常见问题提醒

- 不要因为材料里出现了 `状态` 就自动加状态标签；先判断状态是否真的影响用户下一步动作
- 不要因为存在 `驳回` 就默认必须独立成新场景；先判断它是不是独立任务闭环，还是主任务中的修正分支
- 不要把 `成功反馈` 和 `结果完成` 混为一谈；尤其在异步处理和下游同步场景中，二者经常不是同一时点
- 不要把 `异常提示` 当作完整反馈；完整反馈至少应让用户知道当前卡在哪里、为什么卡住、接下来能做什么

## 反馈、报错与引导模式

### 使用方式

按以下顺序读取：

1. 先判断当前属于反馈还是引导
2. 再判断它发生在操作前、操作中还是操作后
3. 最后选择更合适的承载形式

以下内容用于帮助判断某类任务更适合用哪种反馈或引导方式组织。它不是上位原则正文；读取前应先回到相关设计准则确认问题类型与判断依据。

### 1. 新手指引

- 目标：帮助用户认识某项功能是什么、为什么存在、主要能做什么。
- 适用场景：首次进入复杂功能、新能力首次曝光、整体功能理解门槛高。
- 不适用场景：用户已经在执行具体任务，只缺当前一步的支持。
- 常见承载形式：对话框、轻量说明层、可主动触发的帮助入口、必要时的 Tour。
- 核心结构：功能目的 -> 关键能力 -> 主要路径 -> 退出或稍后查看。
- 风险点：过度教学、打断任务、把操作说明和功能介绍混写。

### 2. 任务开始前引导

- 目标：让用户在开始执行前理解准备条件、路径顺序和风险点。
- 适用场景：任务复杂、前置条件多、执行顺序错误成本高。
- 不适用场景：用户只需要一个局部字段说明或一个即时反馈。
- 常见承载形式：页面顶部说明、卡片、步骤条、对话框、说明区。
- 核心结构：任务目标 -> 前置条件 -> 关键步骤 -> 风险提醒 -> 开始执行。
- 风险点：把所有帮助都堆到开始前，导致用户还没开始就信息过载。

### 3. 任务结束后引导

- 目标：在任务结果出现后，承接后续动作、相关任务或复核动作。
- 适用场景：任务完成后还存在下一步处理、结果需要分流、完成后会触发其他动作。
- 不适用场景：用户只需要知道成功或失败，不存在后续承接。
- 常见承载形式：结果页提示、卡片、对话框、页面内下一步提示、轻量消息配链接。
- 核心结构：结果说明 -> 当前状态 -> 可选下一步 -> 跳转或留在当前页。
- 风险点：把结果反馈和引导混成一条冗长提示，导致主次不清。

### 4. 字段级校验反馈

- 目标：帮助用户在原位置快速发现并修正输入问题。
- 适用场景：必填、格式、长度、单字段数值、上传属性校验。
- 不适用场景：跨字段复杂关系、整页失败、重大业务阻断。
- 常见承载形式：字段附近提示、上传区域提示、集中校验区。
- 核心结构：指出问题字段 -> 说明错误原因 -> 给出正确格式或修正方向。
- 风险点：只告诉用户“有错”，不告诉用户错在哪里。

### 5. 操作结果反馈

- 目标：解释一次操作刚刚发生的结果，并帮助用户决定下一步。
- 适用场景：成功、失败、部分成功、异步处理中、重复操作已处理。
- 不适用场景：持续状态限制、长周期任务路径教学。
- 常见承载形式：Message、局部结果区、结果页、对话框、状态区。
- 核心结构：结果 -> 原因或影响 -> 下一步。
- 风险点：成功提示太长、失败提示太空、把恢复路径遗漏。

### 6. 页面级失败反馈

- 目标：处理整页无法继续加载、访问或完成的情况，并提供清晰退路。
- 适用场景：加载失败、数据不存在、页面无权限、配置缺失。
- 不适用场景：局部字段错误、一次轻量提交失败。
- 常见承载形式：页面占位、空状态、失败状态区、必要时的对话框。
- 核心结构：当前页为什么不可用 -> 是否可恢复 -> 返回或处理路径。
- 风险点：建议“刷新试试”但刷新并不能解决问题。

### 7. 状态阻断反馈

- 目标：解释为何当前状态不允许继续执行，以及何时才能恢复。
- 适用场景：流程中、处理中、已锁定、已冻结、已结账、状态不允许。
- 不适用场景：一次性瞬时失败、首次认知介绍。
- 常见承载形式：状态区、Banner、入口说明、必要时的兜底对话框。
- 核心结构：当前状态 -> 影响动作 -> 恢复条件或责任角色。
- 风险点：只说“不可操作”，不说当前状态与允许条件。

### 8. 恢复与下一步引导

- 目标：当任务被中断或完成后，帮助用户找到最短恢复路径。
- 适用场景：失败后重试、权限不足去申请、配置缺失去设置、结果后继续下一任务。
- 不适用场景：仅为解释当前状态、不需要用户继续动作。
- 常见承载形式：按钮、链接、说明卡片、结果页承接、状态区引导。
- 核心结构：问题说明 -> 可执行动作 -> 替代路径或等待条件。
- 风险点：把恢复路径藏在长文案里，或根本不给路径。

## 承载形式选择

### A. Inline

- 适合：字段级问题、局部说明、就地修正。
- 不适合：整页失败、复杂关系说明、高风险确认。
- 常见对应模式：字段级校验反馈、局部状态说明。

### B. Banner / 页面提示

- 适合：持续状态、页面级限制、需要长期可见的提醒。
- 不适合：瞬时成功提示、纯字段错误。
- 常见对应模式：状态阻断反馈、页面级失败反馈、任务开始前准备说明。

### C. Message / Toast

- 适合：轻量结果反馈、短时成功或失败提示、重复操作已处理。
- 不适合：复杂原因解释、多个后续动作分流、持续状态说明。
- 常见对应模式：操作结果反馈、轻量恢复提示。

### D. Modal / Dialog

- 适合：高风险确认、不可逆后果、复杂失败说明、阻断式指引。
- 不适合：字段校验、普通成功提示、持续状态提醒。
- 常见对应模式：强阻断反馈、新手指引、复杂任务前说明。

### E. Tooltip / Popover

- 适合：局部释义、轻量说明、非强制辅助引导。
- 不适合：关键路径唯一说明、重大失败解释、长流程承接。
- 常见对应模式：局部帮助、非阻断式引导。

### F. Tour

- 适合：需要依次认识多个界面区域、建立整体操作心智的引导。
- 不适合：单一步骤修正、结果反馈、页面本该靠结构自解释的问题。
- 常见对应模式：新手指引、少量复杂功能的首次认知引导。

### G. 卡片 / 步骤条 / 空状态

- 适合：任务路径展示、准备条件说明、结果后承接、页面不可用时的退路。
- 不适合：瞬时提示、极轻量反馈。
- 常见对应模式：任务开始前引导、任务结束后引导、页面级失败反馈。

## 快速判断表

| 当前问题 | 所处阶段 | 信息目标 | 推荐模式 | 常见承载形式 |
| --- | --- | --- | --- | --- |
| 用户不知道功能是什么 | 首次进入 | 建立整体认知 | 新手指引 | 对话框、帮助入口、必要时 Tour |
| 用户准备开始复杂任务 | 操作前 | 明确准备条件与顺序 | 任务开始前引导 | 说明区、卡片、步骤条、对话框 |
| 用户提交后成功但还有后续动作 | 操作后 | 承接下一步 | 任务结束后引导 | 结果区、卡片、对话框、链接 |
| 字段填写有误 | 输入中 / 提交后 | 就地修正 | 字段级校验反馈 | Inline、集中校验区 |
| 整页数据无法加载或不存在 | 进入页面 | 解释当前不可用并给退路 | 页面级失败反馈 | 空状态、页面占位、状态区 |
| 当前状态不允许操作 | 操作前 / 操作中 | 解释限制和恢复条件 | 状态阻断反馈 | Banner、入口说明、兜底对话框 |
| 轻量提交成功或失败 | 操作后 | 快速说明结果 | 操作结果反馈 | Message、局部结果提示 |
| 失败后需要给恢复路径 | 操作后 | 帮助继续推进任务 | 恢复与下一步引导 | 按钮、链接、卡片、结果区 |

## 反馈与引导常见误用

- 把新手指引当成所有任务帮助的总入口，导致教学内容过长。
- 把任务引导做成组件介绍，而不是围绕任务路径组织。
- 把字段问题升级成对话框，增加修正成本。
- 把所有异常都做成 Message，导致复杂问题无处承载。
- 把 Tour 用来弥补页面结构本身不清晰的问题。
- 把结果反馈和后续引导混成一段长文案，用户抓不到重点。
