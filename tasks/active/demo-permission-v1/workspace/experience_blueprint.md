# Experience Blueprint

## 体验目标

- 让陈晨在一次查看中就能理解当前结果属于哪一层失败，而不是只能得到模糊的“未生效”结论
- 降低排查成本，让管理员能区分“入口可见”“功能已授予”“数据为空”“超出边界”四种不同状态
- 让后续处理动作清晰，例如补数据范围、回到本区授权、或找超管调整管辖范围

### 体验交付目标
- 让解释结果可以直接支持排查，而不是只作为状态提示
- 让不同失败原因拥有稳定的一致表达，便于跨模块、跨角色沟通

## 关键场景

- 场景 1：陈晨进入销售分析应用时，需要确认自己为什么能看到入口，对应 F-02
- 场景 2：陈晨点击导出后发现结果不可用，需要理解问题卡在数据范围层，对应 F-03、F-04、F-07
- 场景 3：陈晨给华南区成员授权失败，需要理解这是边界限制而不是系统异常，对应 F-01、F-05、F-06
- 场景 4：陈晨需要知道接下来应该补什么信息或找谁处理，对应 F-08

### 场景优先级
- 高优先：导出不可用与跨区授权失败，因为这两类问题最容易被误判为系统故障
- 中优先：入口可见解释，因为它决定用户是否理解“已配置但未完全可用”的前提

## 体验要求

- 必须先给结论，再给原因，再给下一步动作，避免用户只看到抽象原因码
- 对可见但导出不可用的结果，要明确说明“已授予功能权限，但数据范围为空”，承接 F-03、F-04
- 对跨区授权失败的结果，要明确说明“当前身份仅能管理华东区”，承接 F-01、F-05、F-06
- 对所有异常结果，都要给出失败层级标签，例如“数据范围”或“管理边界”，承接 F-07
- 说明中禁止混用“权限未开通”“未生效”“没有数据”三个概念，避免与 F-07 冲突
- 需要为后续排查保留追溯信息入口，例如来源类型、原因码、规则引用与责任边界，承接 F-08

### 推荐解释框架
- 结果层：当前能做什么、不能做什么
- 原因层：失败发生在哪一层，命中了哪个原因码
- 责任层：当前该由谁处理
- 下一步层：用户可以立即采取什么动作

## 原则引用

- 引用事实：F-01, F-02, F-03, F-04, F-05, F-06, F-07, F-08
- 引用原则：U-01, U-02, R-01, R-02
- U-01：状态必须可见，当前要明确展示“可见”“已授予”“数据为空”“超出边界”分别是什么状态
- U-02：解释应贴近业务语义，用“华东区管理范围”“导出数据为空”替代系统内部术语
- R-01：说明文案要先结论后细节，避免一大段抽象规则说明
- R-02：状态名、动作名、原因表达需要统一，不能一会儿叫“未生效”，一会儿叫“没开通”

### 原则落地方式
- 用 U-01 保证状态可见，让“可见 / 已授予 / 数据为空 / 超出边界”成为可区分结果
- 用 U-02 保证表达贴近业务语义，不把内部规则直接抛给用户
- 用 R-01 保证说明可以扫读，先给结论再展开
- 用 R-02 保证跨入口表达一致，减少认知迁移成本

## 风险与保护

- 风险：用户把 F-04 的数据范围问题误解为功能没开通
- 保护：在结果层同时显示“功能已授予”和“数据范围为空”两个并列事实
- 风险：用户把 F-05 的边界限制误解为系统报错
- 保护：把失败原因直接表述为“超出当前子管理员管辖范围”，并给出应联系的责任角色
- 风险：用户不知道下一步找谁
- 保护：对每类失败结果都补充建议动作，例如“补充数据范围配置”或“联系超管调整范围”
- 风险：多个失败原因混杂后，体验文案失去一致性
- 保护：统一按“结果层级 + 原因 + 下一步”的结构输出解释

### 最低体验交接要求
- 每个失败结果都应至少带出一个结论、一条原因说明、一个建议动作
- 每个解释都应能回指到业务规则，而不是依赖临时文案发挥

## 开放问题

- OQ-01: 当前演示仅定义解释策略，尚未确认现网是否已有统一的状态标签与责任人展示位置
- OQ-02: 若后续要支持按变更查，还需补充审批与审计视角下的解释要求
