# 需求事实提炼合同（正式替换稿）

## 目标

定义如何从任务输入中生成 `facts.md`，并将 facts（事实层）正式定义为 **structured extraction layer（结构化提取层）**。

本阶段的核心目标不再是“高层摘要”，而是把原始需求文档、背景信息与显式引用知识中的可确认内容，整理为可被后续 business blueprint（业务蓝图层）稳定消费的 **atomic facts（原子事实）**、rule structures（规则结构）、state structures（状态结构）、dependency structures（依赖结构） 与 gap structures（缺口结构）。

本合同兼容当前仓库三阶段主链路，不改变既有主文件命名、主阶段顺序与归档方式，只提升 facts（事实层）的提取粒度、可追溯性与可编译性。

## 阶段定位

事实提炼阶段是主链路的第一个业务阶段。

它负责：

- 识别任务意图与业务对象
- 从输入中提取 atomic facts（原子事实）
- 提取角色、对象、状态、动作、规则、异常、依赖、范围与缺口
- 对输入中的术语进行最小必要的 terminology normalization（术语校准）
- 将 facts（事实）组织为后续业务判断可消费的结构单元
- 明确每条事实的来源与可追溯关系

它不负责：

- 给出业务立场结论
- 判断需求是否合理
- 判断能力应独立还是合并
- 输出体验方案、页面方案或交互方案
- 输出视觉稿建议
- 输出研发实现方案
- 用行业常识补造文档中未被确认的事实

## 输入前置条件

进入本阶段前，至少应具备：

- `projects/<project-id>/source/task_card.md`
- `projects/<project-id>/source/requirement.md`
- `projects/<project-id>/source/background.md`
- `projects/<project-id>/runtime/task_card_resolved.json`
- `projects/<project-id>/runtime/context_manifest.json`

如果任务显式引用了以下内容，则这些引用在进入本阶段前也应已可读：

- Wiki（维基）页面
- business knowledge（业务知识）
- guideline knowledge（原则知识）
- 模板与合同文件

如果原始输入只是聊天文本、会议纪要、图片转写或零散片段，必须先整理并落盘到 `source/requirement.md` 与 `source/background.md`，再进入本阶段。

## 输入质量标准

进入本阶段前，输入至少应能支撑回答以下问题中的大部分：

- 这次任务要解决的核心问题是什么
- 主要角色是谁，谁触发、谁审批、谁配置、谁受影响
- 申请或变更的对象是什么
- 已知流程、状态、规则、校验与异常是什么
- 哪些信息是已确认的，哪些仍待确认

如果输入只能支撑主题描述，不能支撑结构化提取，则本阶段可以继续，但必须显式输出 warning（警告）与 gap（缺口），不得伪造完整事实结构。

## 知识使用边界

本阶段遵循 **input-first extraction（输入优先提取）** 原则。

### 1. 输入是主数据源

事实提炼必须以 `requirement.md`、`background.md` 及任务显式输入为主。

### 2. 知识库是 calibration layer（校准层）

当任务显式引用 Wiki（维基）或知识库时，本阶段可以读取这些引用，但只允许用于：

- 术语校准
- 概念边界校准
- 冲突识别
- 缺口识别
- 事实分类辅助

### 3. 禁止把知识补写成已确认事实

如果某条内容没有在当前任务输入中被确认，即使知识库中存在相似结论，也不得直接写成当前任务的已确认事实。

### 4. 来源必须显式标注

facts（事实层）中的每条事实都应能区分其主要来源类型：

- 来自任务输入
- 来自引用知识的术语校准
- 来自冲突检查后的保留说明

## 工作规则

### 1. 只提炼，不扩写

本阶段只整理和编排事实，不得把推测、建议、偏好或高层判断伪装成已确认事实。

### 2. 事实必须原子化

每条事实应尽量只表达一个明确业务结论，不应把多个不同层级的事实压缩为一条摘要句。

以下写法不合格：

- “申请角色时需要配置角色范围及自动加入设置”

以下写法更合格：

- 申请路径支持“申请角色”和“申请功能权限”两种模式
- 两种申请路径为单选互斥
- 申请角色路径下需要配置角色范围
- 角色范围支持“全部角色 / 部分角色”
- 后续新增角色自动加入为独立设置项

### 3. facts（事实）必须按结构单元组织

本阶段不能只输出散列表式事实，还必须按以下结构维度提炼：

- actor facts（角色事实）
- object facts（对象事实）
- state facts（状态事实）
- action facts（动作事实）
- rule facts（规则事实）
- exception facts（异常事实）
- dependency facts（依赖事实）
- scope facts（范围事实）
- gap facts（缺口事实）

### 4. 规则与流程要分开表达

流程链路描述不能替代规则表达；规则表达也不能替代流程链路。

### 5. 显式区分“已确认”与“待确认”

facts（事实层）必须显式区分：

- confirmed facts（已确认事实）
- known constraints（已知约束）
- open questions（开放问题）
- gaps（缺口）

### 6. 允许最小必要的术语统一

当输入中同一概念出现多种叫法时，可以在不改变原意的前提下统一术语，但不得改写业务含义。

### 7. 异常与拦截必须单列

所有失败条件、拦截条件、报错条件、关闭失败、启用失败、审批失败等内容，不得被埋在普通事实里，必须单独提炼。

### 8. 依赖必须单列

审批引擎、帮助文档、组织负责人、外部表单、OA、角色库、应用库等依赖对象必须显式列出。

### 9. 范围与非范围必须单列

facts（事实层）应提炼首版上线范围、明确包含项、明确不包含项或暂不展开项。

### 10. 缺口必须保留

当输入不足以确认重要信息时，必须输出 gap（缺口）或开放问题，而不是自行补齐。

## 输出要求

本阶段至少输出：

- `projects/<project-id>/workspace/facts.md`

如存在明显信息缺口，建议同时输出：

- `projects/<project-id>/workspace/gap_list.md`

## facts.md 结构要求

`facts.md` 必须至少包含以下部分：

- `任务意图`
- `事实来源说明`
- `术语与对象边界`
- `角色与对象清单`
- `原子事实清单`
- `规则矩阵`
- `状态模型`
- `动作与流程事实`
- `异常与拦截清单`
- `依赖清单`
- `范围与非范围`
- `开放问题与缺口`
- `追踪映射`

### 结构说明

#### 任务意图

用于说明这次任务要解决什么问题，任务边界是什么。

#### 事实来源说明

用于说明本次 facts（事实层）主要依赖哪些输入文件、引用文件与知识校准来源。

#### 术语与对象边界

用于统一当前任务中的关键术语、对象与边界，避免同一概念在后续阶段被重新发明。

#### 角色与对象清单

用于明确角色、对象、操作对象、审批对象、配置对象等。

#### 原子事实清单

用于列出 F-xx 编号的 confirmed facts（已确认事实）。每条只表达一个业务结论。

#### 规则矩阵

用于把规则拆成可消费的结构，建议至少包含：

- rule_id
- 规则名称
- trigger（触发条件）
- subject（作用对象）
- precondition（前置条件）
- result（结果）
- failure / block（失败或拦截）
- source_ref（来源）

#### 状态模型

用于列出状态集合、状态切换条件与阻断条件。

#### 动作与流程事实

用于列出角色发起的关键动作链与审批链，但不得把流程描述写成体验方案。

#### 异常与拦截清单

用于列出失败条件、报错条件、不可操作条件、冲突条件、关闭失败条件等。

#### 依赖清单

用于列出外部系统、外部能力、预设对象、组织边界、数据来源等依赖项。

#### 范围与非范围

用于列出首版明确包含内容、明确不包含内容、暂缓展开内容。

#### 开放问题与缺口

用于列出必须带入下一阶段的待确认项，并区分 open question（开放问题）与 blocking gap（阻断性缺口）。

#### 追踪映射

用于建立事实与来源的映射关系。建议至少支持：

- F-xx -> requirement section / background section / reference file
- R-xx -> source
- S-xx -> source
- EX-xx -> source

## 编号要求

建议在 facts（事实层）中使用以下编号前缀：

- `F-xx`：原子事实
- `C-xx`：约束
- `R-xx`：规则
- `S-xx`：状态
- `A-xx`：动作 / 流程节点
- `EX-xx`：异常 / 拦截
- `D-xx`：依赖
- `SC-xx`：范围 / 非范围
- `OQ-xx`：开放问题
- `GAP-xx`：缺口

项目可以在不破坏可读性的前提下扩展编号，但不得取消事实与规则的显式编号。

## 合格标准

一个合格的 `facts.md` 至少满足：

- 任务意图已明确
- 关键角色、对象、状态、动作、规则、异常、依赖已被显式提炼
- 原始输入中的重要业务细节没有被压缩成高层摘要
- 事实与规则、状态、异常被分开表达
- 每条核心事实都可回溯到输入或引用来源
- 无法确认的信息没有被伪装成已确认事实
- 重要缺口与开放问题已显式记录
- 术语已最小必要统一
- 后续 business blueprint（业务蓝图层）可基于本文件做稳定判断

## 进入下一阶段的准入条件

只有当以下条件成立时，才应进入 business blueprint（业务蓝图层）：

- `facts.md` 已生成
- 关键角色与对象已明确
- 关键规则、状态、异常与依赖已被提炼
- 主要缺口已显式保留
- 不存在明显越权内容
- 提炼结果足以支撑业务判断，而非仅能支撑主题概述

## Warning 条件

以下情况可进入下一阶段，但必须带着 warning（警告）：

- 存在少量非关键背景缺失
- 事实结构完整，但个别规则来源仍为目录级知识引用
- 部分异常、状态或依赖仍较粗粒度，但主链路已可判断
- 存在 gap（缺口），但不阻断核心业务判断

## 失败条件

- `facts.md` 缺失
- 事实阶段输出直接混入业务立场、体验方案或实现方案
- 输出主要是高层摘要，缺少原子事实与结构化提炼
- 关键规则、状态、异常、依赖缺失
- 缺失关键信息却未显式记录
- 事实无来源或来源不可追溯
- 使用知识库内容直接补造当前任务事实
- 事实不足以支持后续业务判断

## 对模板与检查器的约束

本合同升级后，以下模块必须同步更新：

- `templates/facts.template.md`
- facts gate（事实关卡）
- `check_report.md` 的 facts 覆盖检查逻辑
- `task_card_resolved.json` 中对 facts 输出结构的要求
- `context_manifest.json` 中对知识使用边界的说明

如果合同已升级而模板、关卡、检查器未同步升级，则不得认为本合同已真正落地。
