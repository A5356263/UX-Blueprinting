# Facts

## 任务概述

本次任务来自 [requirement.md](../source/requirement.md)（第2节"目标"、第3节"用户与角色"），目标是构建一个统一的权限查询视图，帮助管理员从"按人、按角色、按功能权限反查"三个维度穿透查看权限归属关系。需求背景来自 requirement.md 第1节对整个权限分散现状的描述。

涉及三类使用角色（来自 requirement.md 第3节）：
- 权限管理员：日常核对、调整员工或角色权限
- 超级管理员：全局权限审计、异常排查和权限治理
- 审计/安全管理人员：核对人员权限、角色权限和高风险权限分布

核心使用场景包括权限核对、离职交接、权限审计和安全排查。当前管理员需要在不同设置页面之间切换逐项核对，缺少统一查询视角。

## 功能范围

### 按人查权限
（来源：requirement.md 第4.1节 + knowledge/raw/业务/权限管理/12_查询与配置路径.md 第1.1节）

查询某个用户当前拥有哪些权限，包括功能权限、数据权限、表单权限、字段权限、报表权限。输入为具体人员，输出为该人员的完整权限清单。这是当前已可用的查询维度，现有承载链路为：权限查询页 → 按用户查询结果页 → 权限详情弹窗（页面语义来自 15_页面载体语义.md 第6节）。

### 按角色查权限
（来源：requirement.md 第4.2节 + knowledge/raw/业务/权限管理/12_查询与配置路径.md 第1.2节）

查询某个角色包含哪些成员、承载哪些权限模板。输入为具体角色，输出为该角色关联的全部权限清单（覆盖五类权限）。当前通过角色管理页可查看角色成员与配置入口，但缺少独立的按角色查询页和独立的结果视图，现有可行性为"部分可行"。

### 按功能权限反查
（来源：requirement.md 第4.3节 + knowledge/raw/业务/权限管理/12_查询与配置路径.md 第1.5节）

反查某项功能权限被哪些人员和角色持有。支持两个层级（来自 requirement.md 第4.3节用户确认）：
- 功能点维度：按具体操作点反查（如"谁能删除员工"）
- 应用/菜单维度：按页面或菜单入口反查（如"谁有这个页面的权限"）

输出为该权限项的全部持有人和持有角色列表。12_查询与配置路径.md 第1.5节明确标记为 [GAP]，现有页面事实中未见对应承载页。

### 查询范围
（来源：requirement.md 第5节 + 用户确认）
覆盖全部五类权限：功能权限（应用、菜单、页面、操作）、数据权限、表单权限、字段权限、报表权限。

## 关键业务规则

### 查询与配置职责分离
（来源：knowledge/raw/业务/权限管理/10_能力地图.md 第3节 + 15_页面载体语义.md 第6节）
查询链路承担解释职责，不承担配置职责。权限查询页、按用户查询结果页、权限详情弹窗均只做只读展示和解释，不提供权限增删改能力。配置链路（用户授权、角色管理、治理模式等）与查询链路在页面职责和入口上需要明确区分。

### 权限结果判定链路
（来源：knowledge/raw/业务/权限管理/20_决策链契约.md + 04_对象关系.md）
权限最终结果按 L0-L4 分层判定：L0 可见性门槛（不可见即不可达）、L1 功能权限（末级菜单或操作点粒度）、L2 数据权限（建立在功能权限前提下，按全部/部分/无与条件组模型计算）、L3 治理与生效（审批、互审、子管理员隔离等影响是否已生效）。最终生效规则为：可见性门槛 AND 功能权限授予 AND 数据范围 AND 治理状态。

### 角色化可见边界
（来源：knowledge/raw/业务/权限管理/14_角色边界.md）
不同管理员角色在查询结果中看到的内容受可见边界约束：
- 超级管理员：默认可见完整权限域，可查看全部人员、角色和权限关系
- 子管理员：可见范围受限于组织管辖范围与应用管辖范围的交叉边界，只能在其授权范围内查询
- 审计/安全管理人员：以只读方式访问，可见范围取决于被授予的查询权限

可见边界不等于可操作边界，查询结果中需要明确标注当前角色的查看范围是否存在截断。

### 权限来源叠加规则
（来源：knowledge/raw/业务/权限管理/04_对象关系.md 第3节 + 21_来源模型.md）
个人直授与角色授予可叠加参与功能权限解释。当查询某人的权限时，结果需要同时展示通过角色间接获得和直接授予的权限，并标注来源。多个来源叠加时，数据范围按"全部/部分/无"与条件组模型计算最终结果。

## 状态流转

（来源：本次需求为只读查询，不引入新状态。现有状态信息来自 20_决策链契约.md 第3节和 03_业务对象.md）

本次查询功能为只读操作，不引入新的权限状态流转。查询结果的展示依赖于现有权限模型中的状态信息：
- 权限是否已生效（取决于是否经过审批、是否受治理模式影响）
- 角色是否已停用
- 应用是否已停用或不可见
- 成员的加入状态和实名认证状态

这些状态由现有权限配置链路管理，查询视图需要实时反映当前生效状态。

## 异常与边界

### 空结果
管理员查询某个人员时，该人员可能未被加入任何权限配置范围，或仅通过全员默认权限获得基础可见性。此时结果页不应直接显示"无权限"，而应说明：该人员当前无单独配置的权限记录，如存在全员默认权限，需引导查看。

### 角色可见边界截断
子管理员查询时，其组织管辖范围外的成员、角色和权限关系不可见。查询结果需要显式提示"当前查看范围受限于您的管理边界"，避免管理员误以为查询结果是全局完整的。

### 按功能权限反查的颗粒度差异
反查维度在"功能点"和"应用/菜单"两个层级之间存在包含关系。按菜单反查时，结果应包含该菜单下所有功能点的持有人汇总；按功能点反查时，结果只包含该具体操作点的持有人。两者之间的层级关系需要在查询入口和结果中解释清楚。

### 跨颗粒度权限聚合
功能权限、数据权限、表单权限、字段权限、报表权限具有不同的颗粒度和表达方式，统一查询结果中如何分组、排序和展示存在设计挑战。如果按人员查询时将这些权限混排在同一列表中，可能造成管理员难以区分不同权限类型。具体聚合策略尚未在产品侧确认，标记为 [GAP]。

### 权限变更未生效
如果权限变更处于审批中或治理模式阻断状态，查询结果中展示的是当前生效状态而非待生效状态。需要在结果中标注"存在待生效的权限变更"，并提供跳转查看审批进度的入口。

## 依赖与前置条件

- 依赖现有权限模型中的主体、资源、动作、范围、来源、修饰因子、状态七类对象
- 依赖组织底座提供成员主体、组织视图和组织管辖范围输入
- 依赖审批域提供权限变更审批状态
- 依赖应用域提供应用可见性和应用状态信息
- 查询入口定位依赖通用权限管理一级菜单
