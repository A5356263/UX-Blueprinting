# 轻量业务蓝图

## 0. 本次关键业务判断

**判断：**

本次在既有权限体系上新建独立的查询解释层，不改底层权限模型和规则引擎，但需要先定清查询边界、结果契约和角色可见性三项关键业务决策，体验才有稳定的承接底座。

**主要影响：**

1. 查询能力边界直接影响信息架构设计——哪些维度进本期、哪些延后、哪些独立，决定了导航结构和入口组织
2. 查询结果契约决定了每个查询视图必须展示哪些字段，体验层面不能自行裁减
3. 角色可见性约束决定了不同管理员看到的结果集差异，空结果提示和权限提示文案必须分场景处理

**建议方案：**

- 优先交付按人查（数据链路最完整、使用频次最高），按角色查作为第二优先级，按权限反查在数据链路确认前标记为 GAP 并暂不入本期范围
- 查询结果最小契约：每条结果必须带权限名称、资源类型、动作、来源（直授/角色继承/协作可见）、生效状态、数据范围
- 查询页独立于配置页存在，导航上分开，但每条结果旁提供「去配置」入口

**本阶段先定清：**

- 查询维度优先级和分期策略——避免体验设计时把所有维度揉在一起导致哪个都做不深
- 查询结果字段契约——这是体验设计的信息密度和布局依据，不确定则页面无法落地
- 子管理员查询可见边界的具体规则——这决定了查询结果的过滤逻辑和空结果提示策略

**需要重新判断的信号：**

1. 按权限反查数据链路被确认闭环——届时需要重新评估该维度是否纳入本期或下一期
2. 审计场景需求被确认为需要独立的历史快照和变更台账能力——届时需要拆分独立任务

## 1. 一句话结论

可以做。建议分维度、分期交付：先按人查（链路最完整），再按角色查，按权限反查待数据链路确认后再定。核心不是「做一个统一查询页」，而是在权限体系中新建独立的解释层，查询与配置在信息架构上分开，查询结果必须可解释（带来源、状态、范围）。

## 2. 关键业务规则

**前提判断：**

当前需求方向成立的前提是——权限管理员确实需要跨配置页拼凑信息的场景长期存在，且现有单条配置路径上的信息完整性不足以替代独立查询视角。如果未来各配置页自身已经能完整展示权限归属关系，则查询页的价值会被削弱。但鉴于权限来源多样（直授、角色、协作）且分散在不同功能域，这个前提在可预见的周期内不会消失。

**核心规则：**

- 查询与配置职责分离：查询页只做展示和解释，不做编辑。配置操作一律跳转到对应的配置页完成。这不是功能限制，而是防止误操作和保证审计可追溯的安全边界
- 查询结果必须展开来源：同一人员通过直授、角色继承、协作可见三条路径获得的同一权限，查询结果中必须分开展示、标注来源，不得合并为一条。这是审计和管理判断的基础
- 子管理员可见范围约束：查询时应用「组织范围 × 应用范围」交叉过滤。子管理员查询超出管理范围的人员时，系统返回「当前结果受您的管理范围限制」而非「未查询到权限记录」
- 协作可见性独立标注：通过协作关系产生的可见权限，在结果中必须与正式授权权限区分标注，避免审计误判
- 查询维度各自独立设计结果视图：按人查的结果以人员为中心组织，按角色查的结果以角色为中心组织，不强行合并为统一视图

**规则边界说明：**

- 不改变现有权限授予逻辑、角色继承逻辑和决策链
- 不改变现有审批流程
- 不新增权限类型或权限颗粒度
- 查询能力是只读层，不产生新的权限变更记录

## 3. 边界与风险

**不能放开的限制：**

- 查询页不得提供直接授权、回收、转移权限的操作入口
- 子管理员不得通过查询页绕过组织范围限制看到全局权限数据
- 查询结果不得隐藏或合并权限来源信息
- 审计场景的变更台账不纳入本次查询能力范围，变化记录仍以审批域和操作日志为准

**最关键的风险：**

1. **按权限反查数据链路不完整**：若强行上线，结果残缺，用户不会被告知哪些权限未被索引。应对策略：本期不纳入该维度，待链路确认后再独立迭代
2. **按角色查与角色管理页功能重叠**：若查询视图与角色管理页高度重复，管理员会困惑两者的区别。应对策略：按角色查询聚焦「该角色下所有权限的完整展开视图」，与角色管理页的配置视角形成互补
3. **子管理员空结果歧义**：查不到结果时无法区分「真的没有」和「没权限看」。应对策略：在查询结果区域显式告知当前查询范围边界
4. **查询结果量过大**：大型企业按人查可能返回数百条记录。应对策略：默认分页展示，提供按资源类型、来源、状态的筛选和搜索，以及全量导出

**对应保护策略：**

- 查询操作记入操作日志，但不替代审计记录
- 导出操作需二次确认，导出文件带水印和时间戳
- 敏感权限（如超级管理员权限）在查询结果中高亮标注

## 4. 体验承接要求

**角色：**

- 权限管理员（主角色）：日常核对、快速定位、查完即改是核心任务路径
- 超级管理员：全局视角、无范围限制、需要导出和异常标注能力
- 审计/安全人员：需要导出、需要来源追溯、不需要配置跳转

**流程：**

- 主流程：进入查询页 → 选择查询维度（按人/按角色） → 输入查询条件 → 查看结果列表 → 筛选/搜索缩小范围 → 展开单条查看详情（含来源路径） → 跳转配置页或导出
- 子流程（空结果）：输入查询条件 → 无匹配结果 → 看到空结果提示（区分真无结果和范围受限）
- 子流程（导出）：在结果页点击导出 → 二次确认 → 下载带水印的权限清单文件

**进度与结果状态：**

- 查询加载态：数据量大时展示加载进度或骨架屏
- 有结果态：按维度组织的结果列表，每条结果摘要展示权限名+来源+状态，展开后完整展示来源路径、生效条件、数据范围
- 空结果态：区分两种情况——真无权限 vs 受管理范围限制
- 部分结果态：当某些权限来源路径数据不完整时，在对应条目旁标注数据完整性问题

**异常：**

- 查询超时：提示缩小查询范围或稍后重试，不建议自动缩小范围
- 查询结果中某条来源数据缺失：在该条目旁标注「来源数据不完整」，不隐藏该条目
- 导出文件生成失败：提示重试，不静默失败
- 无查询页访问权限：拦截并提示向管理员申请权限

**反馈：**

- 查询操作：即时反馈，查询中显示加载态，查询完成后显示结果数量
- 导出操作：二次确认弹窗，导出成功后通知，导出失败提示重试
- 范围限制：子管理员进入查询页时，在页面顶部常驻提示当前管理范围
- 跳转配置：从查询结果跳转到配置页时，若配置页需要加载，显示过渡态

**文案：**

- 空结果（真无权限）：「未查询到该人员的权限记录」
- 空结果（范围受限）：「当前结果受您的管理范围限制，可能未展示全部权限。如需扩大查询范围，请联系超级管理员」
- 来源标注：「直接授予」「通过角色「XXX」继承」「通过协作关系可见」
- 数据不完整标注：「该条来源信息不完整，可能影响权限判断」
- 导出确认：「确认导出当前查询结果？导出文件包含当前范围内的所有权限记录」

## 5. 升级信号

- 按权限反查数据链路被确认闭环：需要重新评估需求范围，可能新增一个独立查询维度
- 审计场景需求被确认需要独立的历史快照和变更台账：需拆分为独立任务，不在本任务内扩展
- 权限对象模型或决策链发生变更：需重新评估查询结果契约是否需要调整
- 用户反馈按角色查询与角色管理页功能重叠严重：需重新设计按角色查询的差异化价值

## 6. 待确认问题

- 按角色查询的独立结果视图：角色管理页已可查看角色下权限，独立查询页需要提供什么差异化信息？（建议：展开每个权限的完整来源路径和被授予人员数量）
- 查询结果中「数据范围」的展示粒度：当前权限的数据范围字段格式不统一（有的用组织树、有的用标签），查询结果中如何统一呈现需确认
- 导出文件的格式和内容层级：是否需要区分按人导出和按查询结果导出？导出文件是否需要包含查询条件元信息（查询时间、查询人、查询范围）？
