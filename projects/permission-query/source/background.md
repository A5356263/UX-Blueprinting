# 背景与分析上下文

## 分析结论

### 需求性质判断

这是一次涉及信息架构调整的业务能力补齐。核心不是"做一个查询页"，而是在现有权限体系上新建一个独立的"可解释层"——把分散在配置路径里的查询诉求，提取成结构化的查询能力。

### 根因

产品演进长期偏向"配置功能完整性"，权限的"可解释性"从第一天就没被设计成独立能力。配置路径和查询路径没有分离设计，导致所有查询诉求都要在各配置页之间拼凑。

### 真正要解决的三个问题

1. **配置页绑死了查询路径**：信息架构上没有区分配置层和解释层
2. **不同查询维度的信息组织逻辑根本不同**：按人查、按角色查、按权限反查、按变更查，四者的数据组织方式和结果视图各不相同
3. **查到的结果如果不可解释，等于白查**：必须带出来源、生效状态、范围边界

### 关键体验风险

1. 「统一查询」可能掩盖数据路径的结构性缺口（按角色查和按权限反查的底层链路目前不完整）
2. 查询结果不解释来源会制造新困惑
3. 查询和配置的职责边界不清会导致误操作或操作断流
4. 子管理员的可见边界在查询中容易被忽略
5. 审计场景要的是可追溯记录，不是实时查询页

### 建议路径

分三层推进：
1. 先定查询能力的边界和结果契约（按维度分别定义，每条结果必须带来源/生效状态/范围边界）
2. 设计查完怎么办的衔接（查询页不做编辑，但提供"去配置"入口）
3. 角色视角约束（超管全量，子管理员受组织范围×应用范围约束）

### 当前 GAP

- 按权限/功能点反查的底层数据路径是否已闭环（知识库标注为 GAP）
- 按角色独立查询的语义和结果视图是否已定义
- 子管理员在查询场景下的可见范围规则是否已明确
- 审计人员的需求是实时查询还是导出+历史快照

### 复杂度判断

中等复杂度：复用现有权限业务逻辑，在既有能力上新增查询解释层，不改底层业务骨架，但明显改变信息架构和用户任务路径。
