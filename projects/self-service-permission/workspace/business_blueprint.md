# Business Blueprint

> 基于 facts.md 和权限管理领域知识做的业务判断。用业务分析师的自然语言，不做 UI 方案，不填表，不用 ID 编号。

## 0. 本次关键设计判断

- 路线说明：需求类型为功能新增，route 判为 full，压力集中在权限治理风险（high）和状态异常压力（high）。业务判断重点放在模式边界、状态机闭环和安全保护策略。
- 建议方案：作为权限治理体系的新增模式扩展，复用现有审批链和权限授予引擎，不建独立系统。
- 不建议方案：不建独立的自助申请产品模块，不与审批系统做深度耦合。
- 核心理由：自建审批链和权限授予引擎的代价远超复用现有基础设施；但审批对接必须完成闭环，否则该模式会有结构性断链风险。
- 必须确认：自助申请模式与已有治理模式（双管理员/子管理员/权限变更审批）的互斥关系。

## 1. 一句话结论

可以推进。建议作为权限治理体系的扩展模式来做——复用现有审批基础设施和权限授予引擎，新增管理端配置页、员工端权限查看/申请入口和审批视图。关键的不可跳过步骤：先确认模式互斥规则，再进入详细设计。

## 2. 需求是否成立

**判断：成立。**

依据 facts 中的任务概述，当前企业权限分配完全依赖管理员集中处理，中大型企业员工多、流动性高，每次权限变动都需要管理员操作。这种集中授权模式在小型企业里可行，但在 200 人以上、月均权限变动超过 20 次的企业里，效率和体验都会明显下降。

这个需求不是凭空创建新概念，而是把权限治理链条里"谁可以成为权限变更发起方"这个环节从管理员扩展到了员工。权限域的对象模型（subject→source→action→resource→scope）天然支持多种来源路径，员工自助申请可以作为 source 的新枚举值接入。

竞品参考（金蝶）也验证了这个方向的合理性。

## 3. 值不值得做

**综合判断：值得做，但需要先确定模式互斥规则和审批对接方式。**

收益：
- 对 200 人以上企业，月均权限变动场景可以从管理员集中响应变为员工自助发起。每次变更节省管理员约 5 分钟响应和操作时间，员工也不需要等待。
- 权限申请流程从线下沟通（员工找老板/管理员）变成线上可追踪，减少私下授权带来的安全风险。
- 该能力可作为权限治理体系的标准组件，不限于某一类客户。

成本：
- 需新增管理端配置页（自助申请模式开关、可申请范围配置、审批规则设置）、员工端权限查看页和申请入口、审批视图。
- 审批对接如复用现有审批基础设施，开发成本可控；如需适配不同客户的审批系统，对接成本会上升。
- 培训成本：员工端需要自解释设计降低理解门槛，但初期仍需要帮助文档和引导。尤其对于小企业或人员流动性大的客户，每次有新员工入职都可能需要重新培训。
- 认知负担：新增一种治理模式会让管理端的配置逻辑更复杂。管理员需要在多种治理模式之间做选择。

收益大于成本的判断前提是复用现有审批基础设施。如果审批对接需要从零搭建，需要重新评估。

## 4. 应该做成什么能力形态

**路径 A：作为权限治理体系的新增模式扩展（推荐）**

在现有权限治理体系下增加一个新的治理模式开关——"员工自助申请权限"。管理端在已有治理配置区域新增一个配置区块，员工端在合适的入口新增权限查看和申请能力。审批对接复用现有审批流程基础设施，权限授予复用现有授予引擎。

理由：
- 符合 facts 中的约束——"自助申请权限能力应属于权限治理能力的一部分，不应脱离现有权限体系单独存在"
- 不引入新的独立系统，治理、审计和排障可以沿用现有框架
- 与双管理员、子管理员、权限变更审批等已有模式共享配置上下文，模式互斥关系可以在同一配置页中表达

**路径 B：作为独立的自助申请模块（不推荐）**

单独建设一个"员工自助权限中心"，有独立的页面、流程和审批引擎，通过接口与权限系统对接。

不推荐理由：
- 违反 facts 中的约束 1——不应脱离现有权限体系单独存在
- 引入独立的审批引擎和授予链路，增加系统复杂度和维护成本
- 与已有治理模式的关系会更难表达，互斥检查需要跨系统协调
- 权限来源解释（"这个权限是谁通过什么方式授予的"）在多系统之间会难以统一

**结论：推荐路径 A。**

## 5. 推荐业务方案

### 角色与职责

| 角色 | 职责 |
| --- | --- |
| 超级管理员 | 开启/关闭自助申请能力；配置可申请范围和审批方式；不受子管理员范围限制 |
| 子管理员（如已启用） | 在其组织管辖范围和应用管辖范围内，配置自助申请能力的相关设置（取决于超管授权范围） |
| 员工 | 查看自己的权限；发起权限申请；查看申请记录和审批状态 |
| 审批人 | 查看申请内容和原因；审批同意或拒绝；审批人角色来源待确认（可能是组织负责人、指定管理员或自定义审批流程） |

### 主流程闭环

**配置阶段**（管理端）：
1. 管理员进入权限治理配置区
2. 系统检查当前已开启的治理模式，如有互斥则先提示
3. 管理员设置可申请范围（按角色/按功能权限/按数据权限的组合，具体粒度待确认）
4. 管理员设置审批方式（对接已有审批流程或指定审批人）
5. 确认开启，系统完成配置并记录操作日志

**申请阶段**（员工端）：
1. 员工进入"我的权限"页面，查看已有权限
2. 发现缺少权限后，点击申请入口
3. 在可申请范围内选择需要的角色或权限，填写申请原因
4. 提交申请，系统创建申请单并触发审批流程

**审批阶段**（审批端）：
1. 审批人收到待审批通知
2. 查看申请内容：申请人、申请原因、申请的具体权限
3. 同意或拒绝
4. 同意后系统自动执行授权；拒绝后员工权限不变
5. 审批结果通知员工

**关闭阶段**（管理端）：
1. 管理员决定关闭自助申请能力
2. 系统检查是否存在审批中的申请
3. 如存在，提示管理员处理方式选项（待确认：批量拒绝/等待全部完成/强制关闭）
4. 确认关闭后，员工端入口消失，已授权限的处理方式按既定规则执行（待确认）

### 前置配置

- 管理员必须在开启前完成可申请范围和审批方式的配置，二者缺一则不能开启
- 系统需要在开启前检查与已有治理模式的互斥关系

### 结果回写与记录沉淀

- 每次申请、审批、授权操作均记录操作日志，包含操作人、操作时间、操作内容
- 通过自助申请获得的权限，来源标记为"自助申请"，与管理员直接授予区分开来
- 模式开启、关闭、配置变更均记录操作日志

## 6. 必须守住的规则和边界

### 不能放开的限制

- **员工不能申请所有权限**。管理员必须先限定可申请范围，这是开启能力的前置条件。来源于 facts 第6节约束2。
- **员工提交后不能直接自动授权**。所有申请必须经过审批。来源于 facts 第6节约束3。
- **员工只能看到自己的权限和申请记录**。来源于 facts 第6节约束6。
- **只有最高权限管理员可以开关能力**。来源于 facts 第7.1节。

### 必须审批的场景

- 所有权限申请都必须审批，无一例外
- 审批人不能是申请人自己
- 审批人缺失时申请不能自动通过，必须有兜底机制（兜底方式待确认）

### 必须二次确认的操作

- 管理员开启自助申请能力时，弹窗确认配置是否正确（范围 + 审批方式）
- 管理员关闭自助申请能力时，如存在审批中申请，二次确认处理方式
- 审批人拒绝申请时，建议二次确认（防止误操作）

### 必须前置说明的信息

- 员工申请权限前，需要能理解自己当前有哪些权限、缺少哪些权限
- 员工提交申请前，需要知道审批人大致是谁、预计周期
- 管理员开启能力前，需要知道与已有模式的互斥关系

## 7. 主要风险与保护策略

### 风险 1：模式互斥导致配置冲突

- 风险：自助申请模式与已有治理模式（双管理员/子管理员/权限变更审批）同时开启导致权限来源冲突或审批链重叠。
- 影响：权限结果不可解释，排障困难；审批流程可能重复或空转。
- 缓解：开启前系统主动检查已有模式，如有互斥则提示管理员并阻止开启。互斥规则需在进入开发前由产品确认。

### 风险 2：审批链断裂

- 风险：管理员配置的审批人不存在、已被移除或审批链配置错误，导致申请永久卡在审批中。
- 影响：员工提交的申请无人处理，权限需求得不到满足，体验恶化。
- 缓解：（a）管理端配置审批方式时校验审批人是否存在；（b）审批链异常时自动通知管理员；（c）管理员应能手动转交或关闭僵死申请。具体兜底机制待确认。

### 风险 3：可申请范围设置过宽

- 风险：管理员配置的可申请范围过宽或未正确排除敏感权限，员工可以申请到不合适的权限。
- 影响：企业数据安全风险；审批人也可能因为不熟悉业务而误批。
- 缓解：（a）管理端配置页需要有范围预览和风险提示；（b）审批视图需清晰展示申请的权限内容和风险等级；（c）系统应支持敏感角色/权限标记，标记后的权限默认不可申请。敏感标记机制待确认。

### 风险 4：关闭能力后的权限生命周期不明确

- 风险：管理员关闭能力后，已有权限是否保留、审批中申请如何处理不明确。
- 影响：如果保留，相当于留下了一批"特殊来源"的权限，治理复杂度增加；如果不保留，批量回收可能影响正常业务。
- 缓解：建议区分两个维度——（a）已授权限保留，但来源标记保持为"自助申请"，后续可按来源统一回收；（b）审批中申请给管理员选项：等待完成、批量拒绝、或转由管理员手动处理。具体策略需产品确认。

### 风险 5：培训成本和认知负担

- 风险：小企业或人员流动性大的企业，员工不知道如何查看权限、如何申请，管理员不知道如何配置。
- 影响：功能上线后使用率低，管理员仍需手动处理大部分权限请求。
- 缓解：员工端做自解释设计（权限来源说明、可申请范围清晰可见、申请流程指引）；管理端提供配置引导和帮助文档入口。

## 8. 方案承接要求

后续 experience 阶段必须承接以下内容。

### 必须覆盖的角色

- 配置方：超级管理员、子管理员（管理端配置页）
- 申请方：普通员工（员工端权限查看页和申请入口）
- 审批方：审批人（审批视图）

### 必须闭环的主流程

- 管理端：进入治理配置 → 检查互斥 → 设置范围 → 设置审批 → 确认开启 → 记录日志
- 员工端：查看已有权限 → 发现缺口 → 选择申请项 → 填写原因 → 提交 → 查看申请状态
- 审批端：收到通知 → 查看申请内容 → 同意/拒绝 → 触发授权/通知
- 管理端关闭：进入配置 → 点击关闭 → 检查未完成申请 → 选择处理方式 → 确认关闭

### 必须处理的异常

- 开启时模式互斥冲突：阻断开启，提示互斥的具体模式，引导管理员先去关闭冲突模式
- 开启时配置不完整：阻断开启，明确提示缺少哪项配置
- 审批人不存在：申请进入异常状态，通知管理员介入
- 审批超时或僵死：系统可检测并提示管理员或申请人
- 管理员关闭能力时存在审批中申请：列出未完成申请，提供处理选项
- 员工尝试申请不可申请的权限：申请表单中不展示不可申请项（范围控制在前端）；或提交时校验拦截（后端保护）

### 必须解释的状态

- 自助申请能力的开关状态：已开启/已关闭
- 申请单状态：审批中/已通过/已拒绝/已生效/已撤销（如有撤销能力）
- 权限来源标记：管理员授予/自助申请/角色继承/其他
- 各状态对应的可见角色和可操作动作：员工能看到什么、审批人能看到什么、管理员能看到什么

### 必须保护的风险

- 范围安全：可申请范围配置时需要预览效果；员工端不展示不可申请的权限
- 审批安全：审批视图需清晰展示申请的完整内容和原因，防止误批
- 关闭安全：关闭时需显式处理未完成申请和已有权限的生命周期

### 可作为设计建议的内容

- 员工端入口位置：建议放在员工工作台或全局导航中与权限相关的区域
- 权限来源展示：建议在"我的权限"页面展示每条权限的来源（有助于员工理解权限结构）
- 申请统计：建议给管理员提供申请数量、审批时效等基础统计

### 报错或阻断场景中业务依据的状态

- 已足够支持体验方案的：模式互斥阻断（已有明确依据：history.md 中"子管理员模式与双管理员模式不能同时开启"）、配置不完整阻断
- 仍需确认的：审批人缺失兜底、申请单是否可撤销、关闭后已授权限生命周期

## 9. 待确认问题

仅保留会影响后续方案方向的重要问题，按优先级排列：

**第一优先（阻塞方案结构）**：

1. **模式互斥规则**：自助申请模式与双管理员、子管理员、权限变更审批模式各自的关系是什么？哪些互斥、哪些可共存？——影响管理端配置页的结构和开启流程。
2. **审批对接方式**：审批是内置能力还是外部审批中台？审批人默认来源是什么？——影响申请提交流程和审批视图的设计范围。
3. **可申请范围粒度**：按角色配置、按功能权限配置还是两者均可？是否需要支持数据权限范围？——影响管理端配置页和员工端申请表单的信息架构。

**第二优先（影响局部设计）**：

4. **审批人缺失兜底**：审批人不存在或审批链异常时的具体兜底机制。
5. **关闭能力的影响**：已授权限是否保留、审批中申请如何处理。
6. **申请单撤销能力**：审批中的申请是否支持员工主动撤销。

**第三优先（影响细节）**：

7. **敏感角色/权限排除机制**：是否需要专门的敏感标记和默认排除。
8. **申请附件**：是否需要支持上传附件。
9. **服务人员范围**：服务人员是否纳入。
10. **员工端入口位置**：具体放在哪里。
