# Requirement

- Project ID: self-service-permission
- Task Name: 员工自助申请权限
- Domain: 权限管理

## 1. 需求背景

目前企业员工的权限分配主要由权限管理员或超级管理员集中处理。在中大型企业中，员工数量多、人员流动频繁，权限新增、变更、核对的工作量较大，沟通成本高，授权时效不稳定。

本次希望新增"员工自助申请权限"能力，把部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对申请范围和审批流程的控制。

## 2. 目标

使员工可以：查看自己当前拥有的权限、主动申请所需权限、通过审批后自动获得权限、查看自己的申请记录和审批状态。

使管理员可以控制：是否允许员工自助申请权限、员工可以申请哪些权限范围、申请提交后走什么审批流程、是否关闭或调整该能力。

## 3. 用户与角色

- 超级管理员 / 权限管理员：配置是否开启自助申请，控制可申请范围和审批规则
- 员工：查看自己的权限，发现缺少权限时主动发起申请
- 审批人：处理员工提交的权限申请，决定是否同意授权

## 4. 核心场景

1. 管理员配置自助申请权限：开启模式，圈定可申请范围，设置审批流程
2. 员工查看自己的权限：知道自己当前有哪些功能权限、数据权限或角色
3. 员工申请权限：发现缺少某项权限后，直接提交申请并说明原因
4. 审批人处理申请：查看申请内容和原因，决定同意或拒绝；审批通过后系统自动授权
5. 管理员关闭自助申请能力：关闭能力时不影响已生效权限和审批中的申请

## 5. 功能范围

- 管理员开启或关闭员工自助申请权限
- 管理员圈定可申请范围（角色和功能权限，标记敏感/受限项不可申请）
- 员工查看自己已有权限
- 员工发起权限申请的入口和表单
- 审批人审批权限申请
- 员工查看申请记录和审批状态
- 记录关键操作日志
- 数据埋点

## 6. 已确认的业务决策

### 6.1 与现有治理模式的关系

自助申请是一种新的权限来源路径，不是治理模式，不与现有双管理员模式、子管理员模式、权限变更审批模式互斥。两者不在同一维度：
- 现有治理模式解决的是"管理员侧怎么管"
- 自助申请解决的是"谁能发起权限变更"

自助申请的审批流程独立于双管理员模式，审批人由管理员在配置时指定。子管理员的范围隔离仍然生效。

### 6.2 员工可申请范围

- 同时支持申请角色和功能权限，范围由管理员预先圈定
- 不可申请项：超级管理员角色、管理员标记为"敏感"或"受限"的角色和权限
- 数据权限范围不开放员工自选，由管理员预设默认数据范围，审批通过后按预设范围自动授予
- 服务人员暂不开放该能力

### 6.3 管理员关闭能力后的处理

- 已通过并生效的权限：保留，记录来源为"自助申请"
- 审批中的申请：继续走完审批流程
- 能力重新开启后：已获得的权限继续有效，新申请按最新配置规则执行

## 7. 关键业务约束

1. 员工申请权限是现有权限体系的一部分
2. 权限申请范围需要管控
3. 申请权限必须经过审批才可以生效
4. 明确员工可申请和可见的范围
5. 服务人员暂不开放
6. 管理员关闭能力时，已生效权限保留，审批中的申请继续走完

2. 审批人不存在或审批流程异常时如何处理？
3. 审批中的申请是否可以撤销？
4. 是否需要支持上传附件？
5. 员工端入口应该放在哪里？
6. 是否需要给员工展示权限来源？
7. 是否需要给管理员提供申请统计或使用情况？
