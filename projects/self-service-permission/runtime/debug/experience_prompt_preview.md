## 3. facts 摘要

- > 来源：source/requirement.md（员工自助申请权限需求文档）、source/background.md（领域上下文与复杂度判断依据）
- 当前状态：企业员工的所有权限由权限管理员或超级管理员集中分配。员工需要权限时只能私下找管理员或老板处理，沟通成本高、授权时效不稳定。
- 痛点：中大型企业员工数量多、人员流动频繁，权限新增、变更、核对的工作量集中在少数管理员身上，管理压力大，员工获取权限的路径长且不可预期。
- 方案方向：新增一种"员工自助申请权限"能力，把权限查看和申请工作从管理员侧分散到员工侧。员工可以自己查看已有权限、发现缺口后主动发起申请、通过审批后自动获得权限、随时查看申请进度。管理员保留管控能力——控制能力的开关、可申请范围、审批流程。
- 涉及角色：
- 超级管理员 / 权限管理员：配置自助申请能力是否开启，控制可申请的范围和审批规则
- 员工：查看自己的权限，发现缺少权限时主动发起申请
- 审批人：处理员工提交的权限申请，决定同意或拒绝
- 主要场景：
- 1. 管理员开启并配置自助申请权限模式
- 2. 员工查看自己已有的权限
- 3. 员工发起权限申请

## 4. business 核心判断与承接要求

### 5. 推荐业务方案
- | 角色 | 职责 |
- | --- | --- |
- | 超级管理员 | 开启/关闭自助申请能力；配置可申请范围和审批方式；不受子管理员范围限制 |
- | 子管理员（如已启用） | 在其组织管辖范围和应用管辖范围内，配置自助申请能力的相关设置（取决于超管授权范围） |
- | 员工 | 查看自己的权限；发起权限申请；查看申请记录和审批状态 |
- | 审批人 | 查看申请内容和原因；审批同意或拒绝；审批人角色来源待确认（可能是组织负责人、指定管理员或自定义审批流程） |
- **配置阶段**（管理端）：
- 1. 管理员进入权限治理配置区
- 2. 系统检查当前已开启的治理模式，如有互斥则先提示
- 3. 管理员设置可申请范围（按角色/按功能权限/按数据权限的组合，具体粒度待确认）
- 4. 管理员设置审批方式（对接已有审批流程或指定审批人）
- 5. 确认开启，系统完成配置并记录操作日志

### 6. 必须守住的规则和边界
- **员工不能申请所有权限**。管理员必须先限定可申请范围，这是开启能力的前置条件。来源于 facts 第6节约束2。
- **员工提交后不能直接自动授权**。所有申请必须经过审批。来源于 facts 第6节约束3。
- **员工只能看到自己的权限和申请记录**。来源于 facts 第6节约束6。
- **只有最高权限管理员可以开关能力**。来源于 facts 第7.1节。
- 所有权限申请都必须审批，无一例外
- 审批人不能是申请人自己
- 审批人缺失时申请不能自动通过，必须有兜底机制（兜底方式待确认）
- 管理员开启自助申请能力时，弹窗确认配置是否正确（范围 + 审批方式）
- 管理员关闭自助申请能力时，如存在审批中申请，二次确认处理方式
- 审批人拒绝申请时，建议二次确认（防止误操作）
- 员工申请权限前，需要能理解自己当前有哪些权限、缺少哪些权限
- 员工提交申请前，需要知道审批人大致是谁、预计周期

### 7. 主要风险与保护策略
- 风险：自助申请模式与已有治理模式（双管理员/子管理员/权限变更审批）同时开启导致权限来源冲突或审批链重叠。
- 影响：权限结果不可解释，排障困难；审批流程可能重复或空转。
- 缓解：开启前系统主动检查已有模式，如有互斥则提示管理员并阻止开启。互斥规则需在进入开发前由产品确认。
- 风险：管理员配置的审批人不存在、已被移除或审批链配置错误，导致申请永久卡在审批中。
- 影响：员工提交的申请无人处理，权限需求得不到满足，体验恶化。
- 缓解：（a）管理端配置审批方式时校验审批人是否存在；（b）审批链异常时自动通知管理员；（c）管理员应能手动转交或关闭僵死申请。具体兜底机制待确认。
- 风险：管理员配置的可申请范围过宽或未正确排除敏感权限，员工可以申请到不合适的权限。
- 影响：企业数据安全风险；审批人也可能因为不熟悉业务而误批。
- 缓解：（a）管理端配置页需要有范围预览和风险提示；（b）审批视图需清晰展示申请的权限内容和风险等级；（c）系统应支持敏感角色/权限标记，标记后的权限默认不可申请。敏感标记机制待确认。
- 风险：管理员关闭能力后，已有权限是否保留、审批中申请如何处理不明确。
- 影响：如果保留，相当于留下了一批"特殊来源"的权限，治理复杂度增加；如果不保留，批量回收可能影响正常业务。
- 缓解：建议区分两个维度——（a）已授权限保留，但来源标记保持为"自助申请"，后续可按来源统一回收；（b）审批中申请给管理员选项：等待完成、批量拒绝、或转由管理员手动处理。具体策略需产品确认。

### 8. 方案承接要求
- 后续 experience 阶段必须承接以下内容。
- 配置方：超级管理员、子管理员（管理端配置页）
- 申请方：普通员工（员工端权限查看页和申请入口）
- 审批方：审批人（审批视图）
- 管理端：进入治理配置 → 检查互斥 → 设置范围 → 设置审批 → 确认开启 → 记录日志
- 员工端：查看已有权限 → 发现缺口 → 选择申请项 → 填写原因 → 提交 → 查看申请状态
- 审批端：收到通知 → 查看申请内容 → 同意/拒绝 → 触发授权/通知
- 管理端关闭：进入配置 → 点击关闭 → 检查未完成申请 → 选择处理方式 → 确认关闭
- 开启时模式互斥冲突：阻断开启，提示互斥的具体模式，引导管理员先去关闭冲突模式
- 开启时配置不完整：阻断开启，明确提示缺少哪项配置
- 审批人不存在：申请进入异常状态，通知管理员介入
- 审批超时或僵死：系统可检测并提示管理员或申请人

### 9. 待确认问题
- 仅保留会影响后续方案方向的重要问题，按优先级排列：
- **第一优先（阻塞方案结构）**：
- 1. **模式互斥规则**：自助申请模式与双管理员、子管理员、权限变更审批模式各自的关系是什么？哪些互斥、哪些可共存？——影响管理端配置页的结构和开启流程。
- 2. **审批对接方式**：审批是内置能力还是外部审批中台？审批人默认来源是什么？——影响申请提交流程和审批视图的设计范围。
- 3. **可申请范围粒度**：按角色配置、按功能权限配置还是两者均可？是否需要支持数据权限范围？——影响管理端配置页和员工端申请表单的信息架构。
- **第二优先（影响局部设计）**：
- 4. **审批人缺失兜底**：审批人不存在或审批链异常时的具体兜底机制。
- 5. **关闭能力的影响**：已授权限是否保留、审批中申请如何处理。
- 6. **申请单撤销能力**：审批中的申请是否支持员工主动撤销。
- **第三优先（影响细节）**：
- 7. **敏感角色/权限排除机制**：是否需要专门的敏感标记和默认排除。
- 8. **申请附件**：是否需要支持上传附件。
