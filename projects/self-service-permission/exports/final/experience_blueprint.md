# Experience Blueprint

> 基于 facts.md 和 business_blueprint.md 展开的体验设计。用UX设计师的语言写清用户动作、系统反馈、页面文案和异常处理。

## 0. 本次关键设计判断

- 路线说明：全链路（full），跨管理端、员工端、审批端三个端，重点在状态可见性、操作入口自解释、异常兜底反馈三个方面展开设计。
- 建议方案：管理端配置区采用"开关 + 配置内嵌"模式，员工端入口放在工作台及相关功能页面，审批端复用现有审批视图但增加权限申请专属内容区。
- 不建议方案：不建独立的自助权限中心页面、不为审批端新建独立审批工具。
- 核心理由：三个端的用户心智不同——管理员关心管控效果、员工关心"我能申请什么"、审批人关心"该不该批"。体验设计需要分别承接这三类心智。
- 必须确认：员工端入口位置、审批人不存在时的兜底反馈形式。

## 1. 交互流程总览

本次体验围绕以下角色展开：

- 配置方（超级管理员/子管理员）：进入权限治理配置 → 检查互斥 → 设置范围和审批 → 开启能力 → 后续可编辑配置或关闭
- 申请方（普通员工）：进入我的权限 → 查看已有权限 → 发现缺口 → 发起申请 → 填写原因 → 提交 → 跟踪申请状态
- 审批方（审批人）：收到审批通知 → 查看申请内容和原因 → 审批同意或拒绝 → 系统自动授权或通知拒绝

主流程：
- 管理端配置流程：进入治理配置区 → 开启自助申请 → 设置可申请范围 → 设置审批方式 → 确认开启
- 员工端申请流程：进入我的权限 → 查看已有权限 → 点击申请 → 选择权限 → 填写原因 → 提交 → 查看状态
- 审批流程：收到待审批通知 → 打开审批详情 → 查看申请 → 同意/拒绝 → 结果通知
- 管理端关闭流程：进入配置区 → 点击关闭 → 系统检查 → 处理未完成申请 → 确认关闭

异常流程重点关注：
- 开启时与已有治理模式互斥
- 开启时配置不完整
- 审批人不存在或审批链异常
- 管理员关闭时存在审批中申请
- 员工尝试查看或申请不可申请的权限

## 2. 主交互流程

### 2.1 管理端：开启自助申请能力

#### 节点 A1：进入权限治理配置区

用户动作：
管理员（超级管理员或子管理员）从管理后台导航进入权限治理相关配置页面。当前页面展示已有的治理模式状态（双管理员、子管理员、权限变更审批），以及"员工自助申请权限"入口。

系统反馈：
页面展示已有治理模式的状态列表。每个模式显示名称、当前状态（已开启/已关闭）和简要说明。"员工自助申请权限"显示为未开启，旁边有"开启"按钮。

本节点需要前置解释：
管理员需要知道当前系统已开启了哪些治理模式，以及它们之间是否有互斥关系。如果已有模式与自助申请互斥，应在开启前就提示。

建议页面文案：
- 页面标题："权限治理"
- 模式卡片标题："员工自助申请权限"
- 卡片描述："允许员工查看自己的权限并发起权限申请。申请需经审批后自动授权。"
- 状态标签："未开启"
- 按钮文字："开启"

下一步：
点击"开启"进入配置步骤。

#### 节点 A2：模式互斥检查

用户动作：
管理员点击"开启"按钮。

系统反馈：
系统检查当前已开启的治理模式。如果有与自助申请模式互斥的模式，弹出提示弹窗阻断操作；如果没有互斥，直接进入配置页面。

建议页面文案：
- 互斥阻断弹窗标题："无法同时开启"
- 弹窗正文："员工自助申请权限与以下已开启模式存在互斥：<模式名称>。如需开启自助申请，请先关闭以上模式后再操作。"
- 按钮："知道了"（主按钮）、"前往关闭"（次按钮）

本节点需要前置解释：
互斥的具体组合规则目前待确认，本设计按"任一互斥则阻断"的前提展开。如果后续确认某些模式可共存，需调整此节点。

下一步：
如果无互斥，进入配置步骤。

#### 节点 A3：设置可申请范围

用户动作：
管理员进入自助申请配置页。首先设置"可申请范围"——决定员工在申请页能看到哪些权限、能申请哪些权限。

系统反馈：
配置区提供范围选择方式（按角色/按功能权限，具体粒度待确认）。管理员可以勾选、搜索、排除。已选择的项在右侧或下方形成预览区。如果有敏感标记的项，用警示样式标出。

建议页面文案：
- 配置区标题："可申请范围"
- 配置区说明："员工只能申请你在此处选择的角色或权限。未被选中的内容不会在员工端展示。"
- 搜索占位符："搜索角色或权限"
- 预览区标题："已选范围（共 N 项）"
- 敏感项标签："建议限制"
- 空状态提示："尚未选择可申请范围，选择完成后才能开启"

本节点需要前置解释：
管理员需要理解：这里选的是"员工可以申请的上限"，不是"直接授予"。员工即使看到某项权限，也需要提交申请并经审批才能获得。

下一步：
设置审批方式。

#### 节点 A4：设置审批方式

用户动作：
管理员设置员工提交申请后走什么审批流程。可以是"指定审批人"或"对接已有审批流程"。

系统反馈：
- 如果选择"指定审批人"，提供人员搜索和选择器，支持选择一个或多个审批人。
- 如果选择"对接已有审批流程"，列出可用审批流程模板供选择。
- 如果审批人不存在或审批流程配置异常，在提交时校验并提示。

建议页面文案：
- 配置区标题："审批方式"
- 配置区说明："员工提交权限申请后，由谁负责审批。"
- 选项一："指定审批人"（单人选或多选）
- 选项二："使用审批流程"（选择已有审批模板）
- 审批人搜索占位符："搜索成员"
- 无审批人提示："请至少设置一位审批人"
- 审批流程选择提示："选择审批流程模板"

本节点需要前置解释：
审批方式不是可选的——管理员必须在两个选项中选一个并完成配置，否则"确认开启"按钮不可用。

下一步：
确认并开启。

#### 节点 A5：确认开启

用户动作：
管理员完成范围和审批配置后，点击"确认开启"。

系统反馈：
系统弹出二次确认弹窗，汇总配置内容（可申请范围概要 + 审批方式概要）。管理员确认后，系统开启自助申请能力，记录操作日志。员工端入口生效。

建议页面文案：
- 确认弹窗标题："确认开启员工自助申请权限"
- 弹窗内容："开启后，员工将可以在以下范围内自行申请权限：<范围概要>。申请将经过以下审批：<审批方式概要>。确认开启吗？"
- 主按钮："确认开启"
- 次按钮："再检查一下"
- 成功反馈 toast："员工自助申请权限已开启"
- 失败反馈 toast："开启失败，请重试"

下一步：
回到治理配置页，模式状态变为"已开启"。管理员可以"编辑配置"或"关闭能力"。

### 2.2 员工端：查看权限并发起申请

#### 节点 B1：进入"我的权限"

用户动作：
员工从工作台或导航入口进入"我的权限"页面。

系统反馈：
页面展示员工当前拥有的所有权限，分为角色和功能权限（如果有数据权限也展示）。每条权限显示名称和来源（管理员授予/角色继承/自助申请获得）。页面顶部有"申请权限"按钮。

建议页面文案：
- 页面标题："我的权限"
- 页面说明："以下是你当前拥有的权限。如果发现缺少所需权限，可以申请。"
- 权限来源标签："管理员授予"、"角色继承"、"自助申请"
- 按钮文字："申请权限"
- 空状态（无权限时）："你当前没有任何权限。如需使用系统功能，请联系管理员或申请权限。"

本节点需要前置解释：
员工需要知道权限来源的含义，否则看到"角色继承"会觉得困惑。来源标签旁应有简短的解释文字或 tooltip。

下一步：
点击"申请权限"进入申请流程。或浏览已有权限。

#### 节点 B2：选择要申请的权限

用户动作：
员工点击"申请权限"后，进入申请表单。首先看到可申请的权限列表（即管理员配置的可申请范围中，员工当前未拥有的部分）。

系统反馈：
展示权限列表，按角色/功能权限分组。已拥有的权限标为"已有"，不可重复申请。每条可申请的权限显示名称和说明。支持搜索。

建议页面文案：
- 页面标题："申请权限"
- 页面说明："以下是你可申请的权限。选择需要申请的权限后填写申请原因。"
- 已拥有标签："已有"
- 搜索占位符："搜索权限"
- 无可用权限提示："当前没有你可以申请的权限。如有需要，请联系管理员。"
- 列表项格式："<权限名称> — <简要说明>"

本节点需要前置解释：
员工需要能区分"已有权限"和"可申请权限"。如果不解释清楚，员工可能会困惑为什么有些权限看得到但不能申请，或者为什么有些权限完全看不到。

下一步：
选择权限后进入下一步（填写申请原因）。

#### 节点 B3：填写申请原因并提交

用户动作：
员工选好权限后，填写申请原因。

系统反馈：
表单展示已选权限列表（可删除单项），以及申请原因输入框。下方展示将要提交到的审批人信息（如果系统能确定审批人）。提交按钮在原因不为空时可用。提交成功后跳转到申请记录页。

建议页面文案：
- 已选权限区标题："申请内容"
- 原因输入框占位符："请说明申请原因，审批人将根据此内容判断是否通过"
- 审批信息提示："提交后将由 <审批人姓名> 审批"
- 审批人不确定时提示："提交后将进入审批流程"
- 主按钮："提交申请"
- 次按钮："返回选择"
- 提交成功 toast："申请已提交，请等待审批。"
- 提交失败 toast："提交失败，请重试。"

本节点需要前置解释：
员工提交前应该知道审批人大致是谁、预计需要多长时间。如果系统无法确定审批人，至少说明"进入审批流程"而不是留下空白。

下一步：
提交成功后进入申请记录页，可以看到刚才提交的申请状态为"审批中"。

### 2.3 审批端：处理权限申请

#### 节点 C1：查看待审批申请

用户动作：
审批人从待办列表或通知入口进入审批详情，查看员工提交的权限申请。

系统反馈：
审批详情展示申请人姓名、申请时间、申请的权限列表、申请原因。如果是敏感权限或高风险权限，增加警示标记。

建议页面文案：
- 详情标题："权限申请"
- 申请人信息："申请人：<姓名> | 申请时间：<日期>"
- 申请内容区标题："申请权限"（列表展示）
- 申请原因区标题："申请原因"（展示员工填写的原因原文）
- 敏感权限标签："此权限涉及较高风险，请谨慎审批"
- 主按钮："同意"
- 次按钮："拒绝"

本节点需要前置解释：
审批人需要能从申请内容中判断这个权限是否合适。审批视图应该清晰展示"谁、要什么、为什么"三个核心信息。如果是敏感权限，应有额外提醒。

下一步：
同意或拒绝。

#### 节点 C2：审批同意

用户动作：
审批人点击"同意"。

系统反馈：
弹出二次确认（可选，根据 facts 业务约束中"建议二次确认"的建议）。确认后系统自动执行授权，申请单状态变为"已通过"并生效。通知员工审批结果。记录操作日志。

建议页面文案：
- 确认弹窗标题："确认同意？"
- 弹窗内容："同意后系统将自动为 <申请人> 授予以下权限：<权限列表>"
- 主按钮："确认同意"
- 次按钮："再想想"
- 员工通知标题："权限申请已通过"
- 员工通知内容："你申请的 <权限名称> 已通过审批并生效。"
- 同意成功 toast："已同意并授权"

下一步：
回到待办列表或审批详情（状态已更新）。

#### 节点 C3：审批拒绝

用户动作：
审批人点击"拒绝"。

系统反馈：
弹出拒绝原因输入框（可选是否必须填写原因）。确认拒绝后，申请单状态变为"已拒绝"，员工权限不变。通知员工审批结果。

建议页面文案：
- 拒绝原因输入框标题："拒绝原因（选填）"
- 拒绝原因占位符："建议说明拒绝原因，帮助员工理解"
- 确认弹窗标题："确认拒绝？"
- 弹窗内容："拒绝后 <申请人> 将不会获得申请的权限。"
- 主按钮："确认拒绝"
- 员工通知标题："权限申请未通过"
- 员工通知内容（有原因时）："你申请的 <权限名称> 审批未通过。原因：<拒绝原因>"
- 员工通知内容（无原因时）："你申请的 <权限名称> 审批未通过。如有疑问可联系审批人。"
- 拒绝成功 toast："已拒绝"

下一步：
回到待办列表。

### 2.4 管理端：关闭自助申请能力

#### 节点 D1：点击关闭

用户动作：
管理员在治理配置页点击"关闭"按钮。

系统反馈：
系统检查当前是否有审批中的申请单。如果有，弹出处理选项供管理员选择。如果没有，直接弹出关闭确认弹窗。

建议页面文案：
- 有审批中申请的弹窗标题："有待处理的权限申请"
- 弹窗内容："当前有 N 条权限申请仍在审批中。请在关闭前选择处理方式："
- 选项一："等待全部审批完成后自动关闭"（能力保持开启直到全部完成，完成后自动关闭）
- 选项二："将审批中的申请全部拒绝后关闭"（批量拒绝并通知申请人）
- 选项三："关闭入口但保留审批中的申请继续流转"（员工不再能提交新申请，审批中的继续处理）
- 选项四："强制关闭并取消全部审批中的申请"
- 无审批中申请的弹窗标题："确认关闭员工自助申请权限"
- 弹窗内容："关闭后员工将无法查看和申请权限。通过自助申请获得的权限<保留/不保留>（具体策略待确认）。确认关闭吗？"
- 主按钮："确认关闭"
- 次按钮："取消"
- 关闭成功 toast："员工自助申请权限已关闭"

本节点需要前置解释：
管理员需要提前知道关闭的影响——员工还能不能看到已有权限、审批中的申请会怎样、已通过申请获得的权限会怎样。这些信息应该在关闭确认弹窗中明确写出来。

下一步：
确认关闭后，治理配置页状态更新为"已关闭"。员工端入口消失（或变为不可用状态）。

## 3. 次交互流程

### 3.1 员工查看申请记录

员工进入"申请记录"页面，看到自己历史提交的所有申请。每条显示申请的权限、提交时间、当前状态、审批人信息。支持按状态筛选（全部/审批中/已通过/已拒绝）。

- 页面标题："申请记录"
- 空状态："还没有提交过权限申请。去申请权限"（带跳转按钮）
- 状态标签："审批中"、"已通过"、"已拒绝"、"已生效"
- 列表项信息：权限名称、提交时间、审批状态、审批人

### 3.2 员工撤销审批中的申请

（前提：产品确认支持撤销）员工在申请记录中找到审批中的申请，点击"撤销申请"，弹出二次确认弹窗确认撤销。撤销后申请单状态变为"已撤销"，通知审批人该申请已被撤销。

- 撤销确认弹窗："确认撤销此申请吗？撤销后审批流程将终止。"
- 撤销成功 toast："申请已撤销"

### 3.3 管理端编辑配置

管理员在自助申请能力开启状态下，进入配置页调整可申请范围或审批方式。调整范围后不影响已提交但未审批的申请（原则是变更不溯及既往，除非产品另有规定）。调整审批方式后，仅影响新提交的申请。

- 保存成功 toast："配置已更新"
- 提示信息："调整后仅对新提交的申请生效，不影响已有申请。"

### 3.4 员工查看申请详情

员工在申请记录中点击某条申请，进入详情页。展示申请的完整信息：权限内容、申请原因、提交时间、当前状态、审批人、审批时间（如已处理）、拒绝原因（如被拒绝）。

### 3.5 审批人查看已处理申请

审批人在审批视图可以看到自己已处理的申请记录，包含审批时间、审批结果。支持按同意/拒绝筛选。

## 4. 异常与阻断流程

### 异常 4.1：开启时与已有治理模式互斥

发生时机：管理员在治理配置页点击"开启"。
触发条件：当前系统已开启与自助申请模式互斥的治理模式。
判断依据：facts 业务约束8 + business 第6/7节的互斥规则。
反馈形式：弹窗阻断，不允许继续配置。
系统反馈：弹窗标题"无法同时开启"。正文："员工自助申请权限与以下已开启模式存在互斥：<模式名称>。如需开启自助申请，请先关闭以上模式后再操作。"主按钮"知道了"，次按钮"前往关闭"（点击后跳转到对应模式的配置区）。
用户下一步：先关闭互斥模式，再回来开启自助申请。

### 异常 4.2：开启时配置不完整

发生时机：管理员未设置可申请范围或未设置审批方式时点击"确认开启"。
触发条件：可申请范围为空，或审批方式未配置。
判断依据：facts 第7.1节"开启前需要设置可申请范围和审批方式"。
反馈形式：按钮置灰 + 内联提示。
系统反馈：在"确认开启"按钮旁或上方显示提示文字"请先完成可申请范围的设置"或"请先设置审批方式"。按钮保持不可用状态直到两项配置均完成。
用户下一步：完成缺失配置后按钮自动变为可用。

### 异常 4.3：审批人不存在

发生时机：员工提交申请后，系统尝试路由到审批人时发现审批人不存在或已被移除。
触发条件：管理员配置的默认审批人离职、被删除、或审批链中的节点为空。
判断依据：facts 异常与边界"审批人缺失"段 + business 风险2。
反馈形式：
- 对审批人缺失的申请人：[GAP] 当前未确定——可能是自动通知管理员介入，或申请进入异常待处理状态
- 对管理员：系统的监控提示，告知有申请因审批人缺失无法流转

（以下为条件型建议——事实不足以确定方案）
**方案A（推荐方向）**：审批人不存在时，系统自动通知管理员，并将该申请标记为"审批异常"状态。管理员可从治理配置或专门的异常处理入口手动转交审批人或关闭申请。
**方案B**：审批人不存在时，系统直接跳过该审批节点，按审批链下一节点处理。

建议页面文案（按方案A）：
- 对管理员的通知："有 N 条权限申请因审批人缺失无法处理，请前往处理。"
- 异常申请列表中的状态标签："审批异常"
- 异常申请详情中的提示："审批人不存在或已被移除，请联系管理员处理。"

用户下一步：
- 员工：等待管理员处理，或联系管理员
- 管理员：进入异常处理入口，手动转交或关闭

### 异常 4.4：管理员关闭时存在审批中申请

发生时机：管理员在治理配置页点击"关闭"。
触发条件：存在状态为"审批中"的申请单。
判断依据：facts 异常与边界"关闭时存在未完成申请"段 + business 风险4。
反馈形式：弹窗展示处理选项。
系统反馈：见主流程节点 D1。
用户下一步：选择处理方式后确认关闭。

### 异常 4.5：员工在可申请范围内看不到期望的权限

发生时机：员工进入申请页后发现自己需要的权限不在列表中。
触发条件：管理员未将该权限纳入可申请范围。
判断依据：facts 安全约束规则"管理员必须能控制范围"。
反馈形式：页面空状态或在列表底部提示。
系统反馈：如果搜索不到某个权限，展示提示"没有找到 '<搜索词>'。如果确实需要此权限，请联系管理员。"页面底部或空状态中给出联系管理员的方式。
用户下一步：联系管理员，请求将需要的权限加入可申请范围。

### 异常 4.6：提交时权限范围已变更

发生时机：员工正在填写申请时，管理员调整了可申请范围，员工选择的某项权限已不在范围中。
触发条件：管理员在员工填写申请期间更新了可申请范围配置。
判断依据：[GAP: facts 和 business 均未明确此场景]
反馈形式：提交时后端校验拦截，前端提示。
系统反馈：提交失败，提示"申请内容中的 <权限名称> 当前不可申请（申请范围可能已调整）。请返回重新选择。"已选列表中被移除的项标红并置灰。
用户下一步：返回选择页重新选择可申请的权限。

### 异常 4.7：提交申请时网络异常或系统错误

发生时机：员工点击"提交申请"。
触发条件：网络不可用或服务端错误。
判断依据：通用体验原则，非需求特有。
反馈形式：表单页面上方 toast。
系统反馈：toast 文字"提交失败，请检查网络后重试。"表单内容保留不丢失。
用户下一步：检查网络后重试。

## 6. 状态与反馈文案

- 状态：自助申请能力 - 已关闭
  - 含义：员工自助申请权限能力未开启，员工端无相关入口
  - 谁可见：管理员可在治理配置页看到此状态；员工端不展示任何自助申请相关内容
  - 管理员可做：点击"开启"发起配置流程
  - 页面反馈（管理端）：模式卡片上显示"未开启"标签，旁边有"开启"按钮

- 状态：自助申请能力 - 已开启
  - 含义：能力正在运行中，员工可查看权限并发起申请
  - 谁可见：管理员在治理配置页看到此状态；员工端展示"我的权限"入口和"申请权限"功能
  - 管理员可做：编辑配置、关闭能力
  - 页面反馈（管理端）：模式卡片上显示"已开启"标签，旁边有"编辑配置"和"关闭能力"按钮
  - 页面反馈（员工端）：展示"我的权限"页面入口和"申请权限"按钮

- 状态：申请单 - 审批中
  - 含义：员工已提交申请，正在等待审批人处理
  - 谁可见：申请人（在申请记录中）、审批人（在待审批列表中）、管理员（可在管理端查看所有申请）
  - 申请人可做：查看详情；（如支持撤销）撤销申请
  - 审批人可做：同意或拒绝
  - 页面反馈（员工端）：状态标签"审批中"，辅助文字"预计由 <审批人> 审批"
  - 页面反馈（审批端）：出现在待审批列表中

- 状态：申请单 - 已通过
  - 含义：审批人同意申请，系统已完成自动授权
  - 谁可见：申请人、审批人、管理员
  - 申请人可做：查看详情和已获得的权限
  - 审批人可做：查看已处理的审批记录
  - 页面反馈（员工端）：状态标签"已通过"，辅助文字"权限已生效"
  - 页面反馈（审批端）：出现在已处理列表中，标注"已同意"

- 状态：申请单 - 已拒绝
  - 含义：审批人拒绝了申请，员工权限不变
  - 谁可见：申请人、审批人
  - 申请人可做：查看拒绝原因；重新申请
  - 审批人可做：查看已处理的审批记录
  - 页面反馈（员工端）：状态标签"已拒绝"，如有拒绝原因则显示"原因：<拒绝原因>"
  - 页面反馈（审批端）：出现在已处理列表中，标注"已拒绝"

- 状态：申请单 - 审批异常
  - 含义：申请因审批人缺失或审批链异常而无法流转
  - 谁可见：申请人、管理员
  - 申请人可做：等待或联系管理员
  - 管理员可做：查看异常申请并手动处理（转交审批人或关闭申请）
  - 页面反馈（员工端）：状态标签"处理中"，辅助文字"审批流程异常，请耐心等待或联系管理员"
  - 页面反馈（管理端）：异常提示"有 N 条申请审批异常"

- 状态：申请单 - 已撤销
  - 含义：员工在审批通过前主动撤销了申请（前提：产品确认支持撤销）
  - 谁可见：申请人
  - 申请人可做：查看详情；重新提交申请
  - 页面反馈（员工端）：状态标签"已撤销"

## 7. 待确认问题

1. **模式互斥具体规则**：自助申请模式与双管理员、子管理员、权限变更审批各自的互斥关系——影响管理端开启流程中的阻断逻辑和提示文案。建议由产品确认。

2. **审批人缺失兜底机制**：审批人不存在时，申请是自动通知管理员、进入异常状态还是跳过该审批节点——影响审批异常状态的反馈形式和文案。建议由产品和审批系统对接方共同确认。

3. **关闭后已授权限生命周期**：管理员关闭能力后，已通过自助申请获得的权限是保留还是回收——影响关闭确认弹窗的文案和员工端的权限展示。建议由产品确认。

4. **申请单是否支持撤销**：审批中的申请可否由员工主动撤销——影响员工端申请记录页的操作能力和状态机。建议由产品确认。

5. **可申请范围粒度**：按角色、按功能权限还是两者均可——影响管理端配置页的设计和员工端申请表单的权限分组方式。建议由产品确认。

6. **员工端入口位置**：放在工作台、全局导航还是权限相关页面的子入口——影响导航设计和员工发现路径。建议由产品和 UED 共同确认。

7. **敏感权限标记机制**：是否需要系统级的敏感权限标记和自动排除——影响管理端配置时的默认行为和审批端的风险提示。建议由产品和安全团队确认。

- 信息架构（跨端入口的信息组织方式）
- 认知（自解释设计和认知负担控制）

### 转译到方案

- 可前置判断的限制（如模式互斥、范围不足），优先在操作前通过阻断弹窗说明
- 审批中状态不只展示"审批中"，还需要说明审批人是谁
- 关闭能力的确认弹窗不只说"确认关闭"，需要说明关闭后的具体影响
- 权限来源标签用自然语言（"管理员授予"而不是系统内部标识）
- 异常状态不只给错误提示，需要告知用户下一步可以做什么、联系谁
