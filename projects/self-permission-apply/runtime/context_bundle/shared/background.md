# 正式任务分析收敛总结：员工自助申请权限

## 1. 核心需求事实

- 当前权限授予只有"管理员主动配置"一条单向通路，员工没有自助请求通道
- 员工与管理员之间依赖线下沟通（微信、当面、电话），无标准化流程、无记录、无追踪
- 现有权限体系已有四条来源（直授 ACL_DIRECT、角色 RBAC_ROLE、应用可见性 APP_VISIBILITY、协作可见性 COLLAB_VISIBILITY）和一个治理修饰因子（GOVERNANCE_MODE）
- 权限判断决策链固定为：VisibilityGate → FunctionGrant → DataScope → GovernanceState
- 审批流程已有基础能力，但"权限申请"作为一个业务类型是否被现有审批对象支持尚不确定

## 2. 需求涉及能力范围

| 能力 | 说明 |
|------|------|
| 可申请范围配置 | 管理员预定义权限模板（本质是功能权限组合+可选数据范围） |
| 员工权限查看 | 聚合展示员工当前拥有的权限（跨来源聚合） |
| 权限申请提交 | 员工选择权限模板→填写原因→提交申请 |
| 审批处理 | 审批人查看→通过/拒绝→通过后自动授权 |
| 能力开关 | 管理员开启/关闭自助申请能力 |
| 申请记录追踪 | 员工查看申请记录和审批状态 |

## 3. 关键业务规则 / 待定规则

### 已确认
- 申请通过的权限落地为直授（ACL_DIRECT），附加治理修饰因子（GOVERNANCE_MODE）标记
- 可申请范围按权限模板配置，不对员工暴露单个功能权限点
- 关闭策略分两步：先停新申请入口，已提交申请正常处理完成
- 审批流应服从现有治理规则（双管理员/审批互审覆盖自助申请）

### 待定
- 现有审批对象是否支持"权限申请"业务类型
- 权限写入接口是否已支持自动授权
- "可申请范围"配置页归属（现有权限管理页加配置 vs 独立配置页）
- 治理模式与自助申请审批流冲突时的覆盖优先级

## 4. 状态流转

```
员工提交 → 审批中 →┳→ 审批通过 → 自动授权 → 权限生效
                    ┗→ 审批拒绝 → 关闭（可附原因）
```

进行中申请的状态：提交→审批中→通过/拒绝→已关闭（终态）
关闭能力操作不影响进行中申请。

## 5. 异常与边界

| 异常场景 | 处理策略 |
|----------|----------|
| 审批超时无响应 | 需确认超时阈值后是否自动退回或转交 |
| 审批拒绝无原因 | 员工体验差，建议审批时强制填写拒绝原因 |
| 申请部分通过 | 如果申请包含多个权限模板，部分通过部分拒绝需要支持 |
| 申请时权限模板已发生变化 | 以提交时的模板配置为准，还是以审批时的为准？需要产品决策 |
| 关闭能力时存在进行中申请 | 允许继续完成，不受开关影响 |
| 员工离职后已有申请记录 | 属于权限审计范畴，应保留历史记录 |

## 6. 依赖与前置条件

- 现有审批流程底层能力需确认是否支持"权限申请"业务类型和自动授权回调
- 权限来源写入接口（ACL_DIRECT 写入）需确认是否支持从外部系统（审批系统）自动调用
- 现有权限查询接口需支持跨来源聚合展示（直授+角色权限），以便员工看到完整的"我当前的权限"

## 7. GAP / 待确认

- 治理模式与自助申请审批流的覆盖优先级（谁覆盖谁）需产品策略拍板
- 可申请范围配置页的形式归属（管理后台的哪个模块）需进一步设计
- 员工侧权限列表的数据源聚合逻辑需工程确认
- 权限模板的粒度定义（是按角色映射还是按功能点组合）需产品策略定案
- 申请单作为业务对象的字段模型（申请人、权限模板列表、原因、状态、审批人、结果等）需定义

## 8. 体验设计承接重点

- 员工侧必须做"权限概念翻译"：可申请范围展示为业务语言（如"人事管理权限"），不暴露直授/角色/来源等内部模型
- 申请状态可追踪：员工提交后能在统一入口看到审批进度
- 审批拒绝原因可读性：拒绝原因必须用员工能理解的业务语言，而不是技术描述
- 审批通过后与现有权限的叠加解释：如果员工原有角色权限 + 新申请的直授权限共同生效，需展示合并后的结果
- 可解释性：如果审批通过后员工仍无法看到某功能（因为应用可见性拦截），必须在页面给出明确解释

## 9. 设计知识引用

本次分析参考了以下设计准则：
- **G-01 最小惊讶**：覆盖规则必须可解释，员工不能遇到"审批通过了但看不到"而不知道原因
- **G-04 最小授权**：默认收敛可申请范围，扩大范围需要管理员显式配置并确认
- **TR-001 可解释性优先**：必须回答"为什么有/为什么没有/来自哪里/谁改的/何时生效"
- **RISK-002 权限来源不透明**：自助申请作为一条新的授予来源，需要在员工侧有清晰的解释入口
