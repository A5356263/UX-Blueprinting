0. 本次关键业务判断

判断：

员工自助申请权限这件事的核心矛盾，是权限分配中"发起"和"审核"两个角色没有分离——当前管理员既要接收需求、又要判断合理性、还要执行操作，三个角色压在同一个人身上。自助申请模式把发起还给员工，把审核还给业务主管，把执行交给系统。

主要影响：

  1. 新增一种权限来源渠道（员工自申请→审批→系统自动分配），来源模型需要扩展，但不修改既有来源
  2. 超管角色从"执行者"转变为"规则制定者"，配置能力直接影响功能价值
  3. 员工端的认知和操作成本决定功能实际使用率

建议方案：

  • 以"权限管理模式"层级的配置入口承接，与双管理员互审、权限变更审批并列
  • 员工端区分"申请角色"和"申请功能权限"两种方式，超管按企业管理习惯选择

本阶段先定清：

  • 审批通过后分配的权限，来源上需要和直授区分（对应新增APPROVAL类型，复用现有决策链计算）
  • 审批人不可用的兜底不继续阻塞，标记为待确认，体验阶段做承载预留

需要重新判断的信号：

  1. 如果发现当前已有互审/审批模式的大客户占比过高，可能实际目标客户群比预期窄
  2. 如果调研中"培训成本高"的反对意见导致种子客户试用意愿低，需重新评估功能上线策略

1. 一句话结论

可以做。员工自助申请权限是权限管理域的合理能力扩展，不改变核心对象关系和既有机制。建议按"管理端配置→员工申请→审批自动分配→结果可查"的主链路推进，重点把超管的范围控制精度和员工的过程安全感设计清楚。

2. 关键业务规则

  • 互斥成立的前提： 自助申请模式与双管理员互审、权限变更审批互斥，但互斥是模式级别的——已开启其中一个时，不可再自助申请模式，而不是"已经走了互审流程的单子不能再走自助申请"。这个前提影响超管配置入口的说明方式
  • 申请方式选择影响后续范围控制： 选择"申请角色"时，超管配置角色范围；选择"申请功能权限"时，配置应用范围。这是两个独立的管理口径，体验上不能混用
  • 可申请范围的"全部"不等于"所有"： 选择全部角色时，实际可申请的只包括已启用角色；选择全部应用时，包括已启用+已停用，但停用应用的前台可见性仍受应用可见性模型控制。体验上用"全部"做选项标签可能导致超管误判实际效果
  • 数据权限默认全量（DataScope=all）： 员工申请功能权限时默认获得该功能所有数据权限。是否允许超管配置为部分数据权限，待定但不阻断当前执行；体验段需预留扩展空间
  • 申请单审批通过后的自动分配刷新时机： 分配是瞬间生效还是需要页面刷新，影响"我的权限"列表的更新体验

3. 边界与风险

风险说明保护策略
培训成本抑制使用率调研中1/10的反对意见是培训成本高；员工需要理解"角色""功能权限"等概念才能自主申请默认推荐"申请角色"方式（概念更直观）；在申请入口提供明确的能力清单预览，不让员工盲填
来源不可解释如果通过审批分配的权限不区分来源，员工和管理员排障时无法判断权限怎么来的必须新增来源标记，在权限详情中展示"通过自助申请获得"
审批链路可靠性组织负责人不可用时申请卡死在审批中审批人不可用场景标注为GAP，体验端预留"撤单重申请"或"联系管理员"的出口
超管配置失误超管误选了"全部角色"但实际不应开放某些敏感角色提供"敏感角色不可申请"的保护机制（参考金蝶的敏感角色配置），让超管在开放时可定点排除

4. 体验承接要求

角色：

  • 超级管理员（配置模式、设置范围、查看启用状态）
  • 员工（申请权限、查看我的权限、查看申请记录）
  • 审批人（审批待办、查看申请详情）
  • 服务人员（无此功能，全局排除）

流程：

  • 主流程：超管开启模式→配置范围→员工查看可申请清单→提交申请→审批人审批→通过后系统自动分配→员工查看结果
  • 关闭流程：超管关闭模式→校验在途流程→关闭成功/失败反馈
  • 异常流程：资金用户校验失败、子管理员模式校验失败、互斥模式冲突

进度与结果状态：

  • 申请单状态：审批中→已通过/已拒绝/已撤销，每个状态对应员工可见反馈
  • 模式状态：未开启→设置中→已启用（可编辑/可关闭）→关闭失败时的维持状态
  • 审批中必须展示当前审批人和等待时长预期

异常：

  • 互斥模式冲突：在宣传页和启用按钮两个入口都需要前置说明和阻断提示
  • 在途流程阻塞关闭：弹窗说明不可强制关闭，等审批完成再操作
  • 资金用户校验/子管理员模式校验：提交时实时校验，不在提交后才报错

反馈：

  • 申请前：展示可申请范围清单，让员工知道"我能申请什么"
  • 申请中：提交后明确告知"已进入审批，审批人为XX，预计X时间内完成"
  • 申请后：状态变化时主动通知（通过审批/被拒绝），拒绝时说明原因
  • 关闭模式时：有在途流程时详细告知哪些申请单未完成

文案：

  • "申请角色"vs"申请功能权限"的说明文案需让非IT人员能理解差异
  • 审批拒绝时需要审批人填写拒绝原因，否则员工不知道被拒理由
  • 模式互斥提示要告诉用户"先关闭已有模式"的具体路径

5. 升级信号

  • 出现以下变化时，应停止当前轻量执行并请求 UXB 重新判断：
  • 发现已有客户实际需要同时开启自助申请和互审/审批模式 → 互斥策略需要重新评估
  • 种子客户试点后反馈员工端使用率极低（培训成本问题超出预期） → 需要补充产品策略
  • 审批兜底策略最终定为需要新建审批角色或委托机制 → 将提升复杂度，需重新判断

6. 待确认问题

  • 功能权限申请时，是否允许超管将默认的数据权限从"全量"改为"部分"？如允许，需要在管理端配置页增加对应的配置项
  • 可申请范围中"后续新增角色/应用自动加入"的自动触发时机是实时还是定时？建议确认后补充到规则描述
  • 申请单审批通过后，系统自动分配的刷新时机：是即时生效还是需要一定延迟？影响"我的权限"页面的数据展示策略

0. 本次关键设计判断

判断：

自助申请权限本质上是把权限分配从"管理员统一管控"变成"规则制定+业务判断+系统执行"三层分工。体验方案要同时服务好三个角色：超管要能精准划定开放边界而不被配置项淹没，员工要能在不培训的情况下独立完成申请，审批人要能快速判断申请是否合理。

主要影响：

  1. 最复杂的体验设计不在员工端，而在管理端的范围配置——超管需要理解"申请角色"和"申请功能权限"的差异，并做出适合企业的选择
  2. 员工端最大的体验风险不是操作路径长，而是"不知道能申请什么"和"提交后不知道卡在哪"
  3. 审批人的决策信息充分度直接决定审批效率——只看到"某某申请了角色A"是不够的

建议方案：

  • 管理端配置用步骤引导（三步）降低超管认知负担，每一步伴随明确的说明文案
  • 员工端申请前展示完整的可申请清单，审批中展示流转进度，驳回时展示原因
  • 审批人侧与OA审批流程一致，不做独立审批页

不建议方案：

  • 不要把"申请角色"和"申请功能权限"做成员工端的主动选择——这个选择应该在管理端配置时定死，员工端只面对单一入口
  • 不要把审批功能独立实现在权限模块内——应复用流程引擎

关键待确认：

  1. 审批人不可用时的兜底策略（影响审批流程的完整性）
  2. 功能权限申请时数据权限默认全量是否允许超管覆盖（影响员工端申请表单的字段配置）

3. 主交互流程

节点 3.1：超管开启自助申请权限模式

用户动作：

超管进入权限管理模式 → 看到"自助申请权限模式"卡片（含说明文案） → 点击"立即启用"

系统反馈：

校验"双管理员互审模式"和"权限变更审批模式"是否已开启。

  • 未开启：进入设置页面，此时模式仍为未开启状态
  • 已开启任一模式：弹出提示"企业已开启「双管理员互审模式」，不能同时开启此模式"，阻断进入设置

需要前置解释的信息：

三种权限管理模式的区别和互斥关系，帮助超管理解为什么不能同时开启

建议文案：

模式卡片说明："员工可自助申请权限，工作流审批通过后，系统将自动分配权限"
阻断提示："企业已开启「XXX模式」，不能同时开启此模式"

下一步：

设置页面（通过校验时）/ 继续使用现有模式（被阻断时）

节点 3.2：超管配置申请范围和审批流程

用户动作：

第一步选择申请方式（申请角色/申请功能权限），第二步设置范围（全部/部分），第三步查看或修改审批流程 → 点击"启用"

系统反馈：

  • 第一步选中"申请角色"→第二步展示角色范围配置；选中"申请功能权限"→第二步展示应用范围配置
  • 选择"部分范围"时打开选择弹窗（支持搜索、分页、多选）
  • 审批流程默认展示组织负责人，可点击修改跳转至表单编辑
  • 点击"启用"前再次校验互斥模式

需要前置解释的信息：

  • 两种申请方式的差异：角色方式适合已启用角色管理的企业，功能权限方式适合直接按应用授权的企业
  • 选择全部角色时实际只包括已启用角色
  • "后续新增角色自动加入"的默认含义

建议文案：

申请角色下方提示："1. 申请通过后，员工将自动关联上申请角色 2. 如果企业常用角色进行授权，建议采用此方式"
申请功能权限下方提示："1. 申请通过后，员工将自动授权功能权限 2. 如果企业常用用户直接授权的方式，建议采用此方式"
审批流程说明："系统已预设了员工申请权限时的审批流程，预设审批人为员工所在组织的组织负责人"

下一步：

启用成功 → toast提示 + 页面刷新为已开启状态 / 启用失败 → 阻断提示

节点 3.3：员工申请权限

用户动作：

在个人中心点击"申请权限" → 抽屉打开申请表单 → 查看可申请清单 → 勾选需要的内容 → 填写申请原因 → 点击提交

系统反馈：

  • 抽屉默认显示当前员工可申请的内容（由超管配置的范围决定）
  • 选择内容后，校验特殊身份（资金用户/子管理员模式）
  • 提交成功：创建申请单，状态为"审批中"，出发审批流程
  • 校验失败：阻断提交，提示具体原因

需要前置解释的信息：

  • "我能申请什么"——可申请清单比员工想象的可能窄，需要清晰展示
  • "申请角色"时员工获得的是完整的角色权限；"申请功能权限"时默认获得该功能的所有数据权限
  • 功能权限申请时的提示："提交申请后，默认申请功能的所有数据权限。如需申请部分数据权限，请联系企业管理员授权。"

建议文案：

申请原因placeholder："请填写申请原因"
提交按钮文案："提交申请"
资金用户校验失败："您当前身份不支持申请代发付款权限"
子管理员校验失败："子管理员不能授予子管理员模式权限"

下一步：

提交成功 → 跳转至申请记录页面 / 留在当前页面

节点 3.4：审批人审批

用户动作：

收到待办通知 → 查看申请详情（申请人、申请原因、申请内容） → 同意或驳回

系统反馈：

  • 审批通过：系统自动分配权限，申请单状态变更为"已通过"，通知员工
  • 审批驳回：申请单状态变更为"已拒绝"，通知员工（含驳回原因）

需要前置解释的信息：

  • 申请详情中展示申请人的当前权限摘要，帮助审批人判断"是否已经有过类似权限"
  • 审批人可以看到申请人的组织信息，以便确认该员工是否属于自己管辖

建议文案：

审批详情页标题："权限申请审批"
审批通过确认文案："确认后，系统将自动为申请人分配所选权限"
驳回提示（必填）："请填写驳回原因"

下一步：

审批完成 → 返回待办列表

5. 异常与阻断流程

异常 5.1：互斥模式阻断启用

发生时机： 超管点击"立即启用"或"启用"时
触发条件： 企业已开启"双管理员互审模式"或"权限变更审批模式"
判断依据： facts.md 关键业务规则 3.1
反馈形式： 弹窗提示
建议文案： "企业已开启「双管理员互审模式」，不能同时开启此模式"
用户下一步： 如需继续，可先关闭已开启的互斥模式后再尝试

异常 5.2：在途流程阻塞关闭模式

发生时机： 超管点击"关闭模式"并确认关闭后
触发条件： 存在此模式的未完成审批的申请单
判断依据： facts.md 状态流转表
反馈形式： 弹窗提示
建议文案： 弹窗标题"关闭失败"；内容"当前有申请流程未完成审批，请联系审批人审批完成，再关闭模式"
用户下一步： 等待审批完成或联系审批人加速处理

异常 5.3：资金用户/子管理员校验失败

发生时机： 员工提交申请时
触发条件： 为非资金用户授予代发付款权限，或子管理员授予子管理员模式权限
判断依据： facts.md 关键业务规则 3.6
反馈形式： 提交时表单校验提示
建议文案： "您当前身份不支持申请代发付款权限" / "子管理员不能授予子管理员模式权限"
用户下一步： 更换申请内容或联系企业管理员

异常 5.4：申请内容超出可申请范围

发生时机： 员工在申请权限表单中选择申请内容时
触发条件： 员工尝试申请超出超管配置的可申请范围
判断依据： business_blueprint_lite 规则边界说明
反馈形式： 前置范围控制——员工不可见不可选不允许的内容
用户下一步： 无可操作项，只能在允许范围内申请

异常 5.5：审批人不可用导致申请卡住

发生时机： 审批人长期未处理
触发条件： 组织负责人离职、出差、不在岗
判断依据： facts.md GAP表
反馈形式： 申请记录中显示"审批中"状态，无进展
用户下一步： [GAP] 当前无自动补救路径；体验建议在申请记录中提供"联系管理员"的入口或提示

异常 5.6：未开启模式的企业员工无入口

发生时机： 员工访问个人中心
触发条件： 企业未开启自助申请权限模式
判断依据： facts.md 异常与边界表
反馈形式： 不展示"我的权限"入口
用户下一步： 无可操作项

8. 待确认问题

  1. 审批人不可用的兜底策略

影响：当组织负责人离职、出差或不在岗时，申请单卡在"审批中"状态，员工无法获得权限，且当前无自动补救路径。体验上需要在申请记录中预留告知和引导位。
建议确认方：产品 / 业务

  1. 功能权限的数据权限是否允许超管改为部分数据权限

影响：当前设计是"默认全量数据权限"，但对数据敏感型企业可能权限过于宽泛。如果允许超管配置为部分，管理端的配置表单和员工端的申请说明文案都需要调整。
建议确认方：产品 / 设计

  1. 审批人侧展示的信息丰富度

影响：审批人看到的申请详情是否包含申请人的当前权限摘要、组织归属等上下文信息，直接影响审批效率。目前默认展示申请人、原因、内容三个字段，补充信息需要确认。
建议确认方：产品 / 设计

  1. 员工如何知道"现在可以申请权限了"

影响：如果员工不知道企业已开启此模式，"我的权限"入口可能会被忽略。是否需要首次开启时的全员通知，文档未说明。
建议确认方：产品 / 运营

附录：设计指南消费说明

1. 设计指南消费

体验蓝图参考了权限管理域的以下设计原则：

  • 可解释性优先原则（TR-001）：员工的每条申请记录和审批结果都应能回答"为什么有/为什么没有/来自哪里/谁审批的"。在"申请记录"页、"我的权限"页和审批通知中均体现了状态解释和原因展示。
  • 概念不增殖原则（TR-003）：未新增独立权限数据类型，未新增审批引擎，审批复用已存在流程引擎，权限分配复用现有决策链。
  • 查询闭环原则（TR-005）：通过"我的权限"提供按人查权限的闭环，通过"申请记录"提供按变更查状态的闭环。
  • 安全第一原则（TR-006）：关闭模式时的在途流程拦截、互斥模式校验、资金用户/子管理员校验均体现了安全保护策略。
