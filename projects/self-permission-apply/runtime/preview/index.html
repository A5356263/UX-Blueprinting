0. 本次关键设计判断

判断：

这是一个成立的需求，建议按新增治理能力而非局部功能扩展来处理。

主要影响：

  1. 引入了一条新的权限获得路径——从"只能由管理员分配"变为"员工可以主动发起，审批通过后自动获得"
  2. 需要新增一种治理模式配置能力，与现有权限变更审批模式需要明确互斥关系
  3. 三个角色的日常任务流都会发生变化：管理员多了配置和监控职责、员工多了查看和申请入口、审批人多了权限类审批单处理

建议方案：

  • 作为权限治理模式的一种新选项，与现有权限变更审批模式互斥，与双管理员模式可共存
  • 审批完全复用现有审批系统，不做独立审批引擎
  • 首期只支持员工申请角色，功能权限申请和数据范围选择留到后续迭代

不建议方案：

  • 不把它做成独立于现有权限体系的"权限商城"——脱离现有角色和授权模型会导致两条授权路径不一致，排障和审计成本大幅上升
  • 不做成"申请人自己选审批人"——会绕过管理员的审批管控

关键待确认：

  1. 自助申请模式与权限变更审批模式的互斥关系需要产品最终确认
  2. 敏感角色和权限的默认排除名单需要产品与安全侧共同确认

1. 一句话结论

可以做，建议作为现有权限治理能力的一种新模式来建设。核心策略是"管理员守住范围和审批规则，员工在限定范围内自主发起，审批通过后自动生效"。当前最关键的判断是：这个能力与现有权限变更审批模式应该互斥，避免两条审批链路同时存在造成管理混乱。

2. 需求是否成立

判断：成立。

这个需求解决的是一个真实且普遍的问题：在中大型企业中，权限分配集中压在管理员侧，员工获取权限的路径长、效率低。

具体来说，需求成立基于以下几点：

  • 当前员工想获得权限，只能私下联系管理员或超管，没有正式的、可追踪的申请路径
  • 管理员处理大量权限请求时没有统一入口，无法批量评估和管理
  • 审批通过后还需要管理员手动操作授权，多了一步重复劳动

需求不成立的前提条件：

以下情况出现任意一项，需求的优先级或范围需要重新评估：

  • 如果目标客户主要是小微企业（员工数少、权限变更频次低），集中管理已经够用，新增自助申请反而增加认知负担
  • 如果现有审批系统不支持与权限授权系统联动（审批通过后无法自动授权），则需要先补审批与授权的自动化能力
  • 如果企业主要使用角色自动授权规则（如按组织自动分配角色），员工很少需要额外申请权限，则需求优先级降低

不存在重复建设或局部诉求扩大化：

现有权限变更审批模式解决的是"管理员改权限需要审批"的问题——发起方是管理员。本次需求解决的是"员工自己申请权限"的问题——发起方是员工。两者的发起角色和适用场景不同，不是重复建设。但它们共享"权限变更需要审批"这一机制，因此建议在治理模式层面互斥，而不是在审批层面共存。

3. 值不值得做

收益：

  • 减少员工与管理员的线下沟通成本。员工有了正式的、可追踪的申请路径，不需要私下找管理员
  • 提升权限分配时效。审批通过后自动授权，省去管理员手动操作环节
  • 规范化权限申请流程。每次申请都有记录、有审批、有结果，便于后续审计和排障
  • 减轻管理员压力。把"发现缺权限→找人→等处理"的环节从管理员身上卸掉，管理员只需在开启时配置一次规则

成本：

  • 开发成本：需要新建管理端配置页、员工端申请入口和查看页、审批端处理页，以及申请记录和状态管理
  • 维护成本：新增一种治理模式意味着权限排障时多了一种"来源路径"需要解释，客服和运营需要掌握新的话术
  • 培训成本：需求文档已提到一线反馈的担忧——小企业或人员流动性大的企业可能需要额外的员工培训
  • 认知负担：员工需要理解"角色"和"功能权限"的区别才能正确申请，审批人需要判断"这个人应不应该有这个权限"

系统代价：

  • 链路复杂度增加：权限获得路径从"管理员直授"和"角色自动分配"两条变为三条，权限查询和来源解释需要多覆盖一条路径
  • 管理配置成本：管理员需要额外学习一套配置流程（开启模式、设置范围、排除敏感项、配置审批规则），配置错误可能导致安全风险
  • 审计成本：新增申请记录和审批记录需要纳入审计范围，权限来源追溯需要覆盖自助申请来源

综合判断：值得做，但范围需要收敛。

首期聚焦"角色申请 + 审批自动授权"，不扩展到功能权限申请、数据范围选择和附件上传。这样既能验证核心价值（员工能否通过自助申请获得权限），又能控制链路复杂度和认知负担。后续根据使用数据和客户反馈决定是否扩展。

4. 应该做成什么能力形态

路径一：独立功能模块

在管理后台和员工端各建一个独立模块，承载完整的自助申请配置、申请、审批、记录查看能力。

优点：功能边界清晰，不影响现有权限管理页面。

缺点：与现有权限管理、审批管理的能力重叠部分（如授权操作、审批流转）需要重复建设或深度耦合。

路径二：扩展现有权限治理模式

在现有"权限管理模式"配置中新增一个选项——"员工自助申请"。管理端的配置能力挂在现有权限管理模式页下，员工端作为独立入口，审批完全复用现有审批系统。

优点：复用现有治理模式的配置框架和审批系统，不引入新的基础设施；管理员的认知模型一致（"这就是一种治理模式"）。

缺点：员工端入口需要新建，不能在管理后台里做；如果未来需要功能权限申请等扩展，治理模式的配置页可能会膨胀。

推荐：路径二——作为治理模式扩展。

理由：

  • 自助申请本质上就是一种治理模式选择——"让员工自己申请 vs 让管理员集中分配"。放在权限治理模式配置中，管理员的认知最自然
  • 复用审批系统是强制要求——自建审批引擎会引入大量冗余工作和维护成本
  • 员工端入口独立建设是必要的——员工不应进入管理后台，需要一个面向员工的权限中心
  • 现有治理模式配置页已有三种模式（普通、双管理员、权限变更审批），新增第四种不会显著增加页面复杂度

暂不产品化的能力：

  • 员工自行选择数据权限范围——认知门槛太高，安全风险太大，首期不做
  • 员工申请功能权限（非角色）——首期仅支持角色申请，功能权限申请后续评估
  • 附件上传——使用频率预期很低，首期不做

5. 推荐业务方案

角色与职责

超级管理员 / 权限管理员：

  • 在"权限管理模式"配置页中，新增"员工自助申请"模式选项
  • 开启前必须完成：选择可申请的角色范围、设置不可申请的敏感角色排除项、配置审批人来源和审批规则
  • 开启后可以查看申请统计数据（申请总数、通过率、拒绝率、平均审批耗时）
  • 关闭时需要确认处理方式（审批中申请全部拒绝或转管理员手动处理），确认页展示当前审批中的申请清单
  • 关闭后可随时重新开启，历史配置保留

员工：

  • 在工作台或全局导航中有独立入口"我的权限"或"权限中心"
  • 可以查看自己当前拥有的所有权限，每条权限标注来源和生效时间
  • 可以从管理员开放的可申请范围中选择角色发起申请，填写申请原因
  • 可以查看自己提交过的所有申请记录及审批状态
  • 可以在"待审批"状态下撤销自己的申请

审批人：

  • 默认审批人为申请人的直属组织负责人
  • 在审批待办中收到权限申请，查看申请详情（申请人、申请角色、申请原因、申请人当前已有权限）
  • 做出同意或拒绝的决定，填写审批意见
  • 审批通过后系统自动完成授权

主流程闭环

配置流程：

管理员进入权限管理模式页 → 选择"员工自助申请"模式 → 系统检查是否与"权限变更审批模式"冲突，如冲突则阻断并提示 → 管理员设置可申请角色范围、敏感排除项、审批人来源 → 管理员确认开启 → 系统记录开启操作 → 员工端入口生效

申请流程：

员工进入"我的权限" → 查看当前已有权限 → 点击"申请权限" → 系统展示可申请的角色列表（已自动过滤不可申请的敏感角色）→ 员工选择角色，填写申请原因 → 提交 → 系统生成申请单，进入审批流程，通知对应审批人

审批流程（复用审批系统）：

审批人收到待办 → 查看申请详情 → 同意：系统自动调用授权接口，将角色授予申请人，权限生效，申请单状态变为"已生效"，通知申请人 → 拒绝：填写拒绝原因，申请单状态变为"已拒绝"，通知申请人

关闭流程：

管理员在配置页点击"关闭自助申请" → 系统检查当前是否有审批中的申请 → 如有：展示确认页，列出所有审批中申请，管理员选择处理方式（全部拒绝 / 转管理员手动处理）→ 管理员确认关闭 → 系统执行收尾操作 → 员工端入口隐藏 → 已生效权限保留

前置配置

管理员的配置项需要在开启前完成，缺一不可：

  • 可申请角色范围：从系统已有角色中选择，支持多选
  • 敏感角色排除：标记哪些角色不可通过自助申请获得，系统默认建议排除超管角色和含权限管理配置的角色
  • 审批人来源：选择审批人类型（直属负责人 / 指定角色 / 指定成员组等），默认直属组织负责人
  • 审批超时策略：设置超时时长和处理方式（默认提醒后转派超管）

结果回写与记录沉淀

  • 每次申请提交、审批通过、审批拒绝、申请撤销、模式开启、模式关闭等关键操作都应记录
  • 审批通过后的授权操作应回写到权限记录中，来源标记为"自助申请"
  • 关闭模式后员工的申请记录应保留，不可删除，来源标注为"自助申请（已关闭）"
  • 申请统计数据（申请总数、通过率、拒绝率、平均耗时）应持续更新，不受模式关闭影响

6. 必须守住的规则和边界

不能放开的限制：

  • 员工只能申请管理员开放的角色，不在可申请范围内的角色在申请界面不可见、不可选
  • 被标记为敏感排除的角色，即使在全球可申请范围内也对员工不可见
  • 员工不能自行选择审批人，审批人来源由管理员在配置中统一设定
  • 员工不能自行选择数据权限范围，申请通过后的数据范围默认为本人数据或所在部门数据

必须审批的场景：

  • 所有权限申请都必须经过审批才能生效，不存在"免审批"的自助申请
  • 审批人不能是自己（申请人不能审批自己的申请）

必须二次确认的操作：

  • 管理员关闭自助申请能力时，如果存在审批中的申请，必须先确认处理方式才能关闭
  • 管理员开启自助申请能力时，如果与"权限变更审批模式"冲突，必须确认切换并提示影响
  • 员工撤销申请时，需要二次确认

必须前置说明的信息：

  • 管理员开启前，需要说明：开启后员工将可以主动申请权限、审批通过后会自动授权、关闭后已授权限保留
  • 员工提交申请前，需要说明：申请需要审批、审批通过后权限会自动生效、审批期间可以撤销
  • 审批人处理申请前，需要看到：申请人的基本信息、申请人当前已有权限、申请的角色包含哪些具体权限

7. 主要风险与保护策略

风险一：权限安全风险

如果管理员配置的可申请范围过宽，或者忘记排除敏感角色，员工可能通过自助申请获得不合适的权限。

影响：越权访问敏感数据或操作。

保护策略：

  • 系统预设敏感角色排除建议（超管角色、含权限管理配置的角色），管理员可以调整但不能忽视
  • 开启前做一次配置检查，如果可申请范围包含系统建议的高危角色，给出警告提示
  • 审批人在审批详情中可以看到申请人当前已有权限，辅助判断"这个人是否需要这个权限"
  • 所有申请和审批操作有完整记录，可审计追溯

风险二：审批流程断裂

如果审批人不存在、离职、请假，或者审批链路配置错误，申请单可能无法流转，员工一直等不到结果。

影响：员工体验差，权限申请卡死，业务受阻。

保护策略：

  • 审批人不存在时自动向上查找（直属上级 → 上级的上级 → 超管）
  • 向上查找也找不到时，申请单进入"待分配审批人"状态，通知超管介入
  • 支持审批超时策略，超时后自动转派
  • 复用审批系统的动态流程能力，在审批人变更时自动重新计算

风险三：模式互斥冲突

如果自助申请模式和权限变更审批模式同时开启，管理员和员工都在发起权限变更审批，审批人很难区分审的是什么、标准是什么。

影响：审批管理混乱，权限治理失控。

保护策略：

  • 系统层面检查互斥关系，两个模式不允许同时开启
  • 切换时清晰提示影响范围和当前审批中的数据如何处理
  • 开启自助申请前必须确认关闭权限变更审批模式

风险四：关闭能力后的数据悬空

管理员关闭自助申请能力时，如果审批中的申请没有妥当处理，员工的申请记录和权限状态会不一致。

影响：数据一致性问题，员工困惑。

保护策略：

  • 关闭前强制展示确认页，包含所有审批中申请的清单
  • 提供明确的收尾选项（全部拒绝或转管理员处理），不允许不处理就直接关闭
  • 关闭后已生效权限保留，申请记录保留，来源标记更新

风险五：培训和支持成本

一线反馈担心小企业或流动性大的企业需要额外培训员工使用。

影响：客户成功成本上升。

保护策略：

  • 申请流程尽量简洁，减少员工的学习成本
  • 申请界面提供清晰的引导说明（如角色说明、申请原因示例）
  • 默认不开启，由管理员评估后主动开启
  • 申请统计数据帮助管理员判断使用情况，及时调整

8. 方案承接要求

后续体验阶段必须承接以下内容：

必须覆盖的角色：

  • 超级管理员 / 权限管理员：配置页（模式选择、范围设置、排除项、审批规则、统计数据）
  • 员工：权限查看页、申请入口、申请表单、申请记录列表和详情
  • 审批人：权限申请审批详情页（含申请人信息、已有权限、申请角色详情）

必须闭环的主流程：

  • 管理员配置并开启自助申请
  • 员工查看权限并发起申请
  • 审批人处理申请（同意 / 拒绝）
  • 审批通过后自动授权，结果反馈给员工
  • 管理员关闭自助申请，处理审批中的申请

必须处理的异常：

  • 审批人不存在或审批链路异常
  • 审批超时
  • 员工尝试申请不在可申请范围内的权限
  • 管理员尝试同时开启互斥的治理模式
  • 关闭能力时存在审批中的申请
  • 员工在待审批状态下撤销申请

必须解释的状态：

  • 申请单的状态含义（待审批、已通过、已生效、已拒绝、已撤销）及状态变化的触发条件
  • 权限来源的展示方式（角色分配、管理员直授、自助申请获得）
  • 关闭能力后权限状态的变化（已授权限保留、来源标记更新）

必须保护的风险：

  • 敏感角色和权限的申请拦截
  • 审批链路断裂时的降级处理
  • 模式互斥时的阻断和提示
  • 关闭能力时的数据收尾

可作为设计建议的内容：

  • 员工端入口在工作台中的位置和命名
  • 申请统计看板的展示形式
  • 空状态和引导文案

9. 待确认问题

  1. 自助申请模式与权限变更审批模式是否互斥？

影响：直接决定管理端配置页的开关逻辑、互斥提示设计、以及两个模式切换时审批中数据的处理方式。如果确认互斥，需要定义切换流程和过渡期处理规则。
建议确认方：产品

  1. 敏感角色和权限的默认排除名单由谁来定？

影响：决定管理端配置页是否需要预设排除项、预设哪些项、管理员是否可以取消预设排除。如果完全由管理员自定义，需要确保管理员理解排除的必要性。
建议确认方：产品 + 安全

  1. 审批超时的默认策略和时长？

影响：决定审批流程的超时处理设计、员工侧等待状态的说明、超管侧的通知频率。如果超时策略过于激进（如超时自动拒绝），可能影响员工体验。
建议确认方：产品

  1. 员工离职时自助申请获得的权限如何回收？

影响：决定权限回收机制的触发条件、回收后申请记录的保留策略、以及权限来源在回收后的展示方式。需求文档未提及，但属于必须明确的规则。
建议确认方：产品

  1. 员工转岗期间已发起但未完成审批的申请如何处理？

影响：决定是否需要在自助申请审批中开启动态流程（审批人随组织变化自动变更）、转岗后审批通过的角色是否仍适合新岗位。
建议确认方：产品

  1. 是否需要支持审批人变更（如审批人请假、离职时的临时转派）？

影响：决定是否需要复用审批系统现有的转派和交接能力。如果支持，需要在审批详情页中暴露转派入口并明确权限。
建议确认方：产品

  1. 被拒绝的申请是否可以重新提交？是否有冷却期或次数限制？

影响：决定申请表单的提交校验逻辑、申请记录的展示方式。如果不限制，可能出现员工反复提交相同申请的情况。
建议确认方：产品

  1. 首期是否仅支持角色申请？功能权限申请和数据范围选择何时评估？

影响：决定申请表单的设计复杂度、管理员配置页的范围选择方式。如果首期仅做角色申请，表单和配置都可以简化很多。
建议确认方：产品

0. 本次关键设计判断

判断：

本次体验方案的重点不是多做页面，而是把三个角色的差异化路径、状态变化时的反馈、以及异常阻断后的补救路径讲清楚。

主要影响：

  1. 管理员的配置体验直接影响安全——配置错误（范围过宽、忘排除敏感角色）会导致越权，所以配置页需要引导和校验，不能只是"几个开关"
  2. 员工从"被动等管理员给权限"变为"主动申请"，这是一个心智转变，需要清晰的路径引导和状态说明
  3. 审批人的决策信息要充分——只看到"谁申请了什么角色"不够，还需要看到这个人当前已有权限，帮他判断"该不该给"

建议方案：

  • 管理员配置页做成"向导式"——先检查互斥、再设范围、再设排除、再配审批，分步引导
  • 员工端入口放工作台，定位为"我的权限"，同时承载查看和申请两个核心任务
  • 审批详情页整合申请人已有权限信息和申请角色详情，降低审批人的判断成本

不建议方案：

  • 不建议把员工申请入口藏在管理后台深处——这会让员工找不到入口，重新走线下找管理员的老路
  • 不建议在审批详情页只展示申请内容不展示申请人已有权限——缺少参照信息，审批人无法判断"这个人缺不缺这个角色"

关键待确认：

  1. 员工端入口是放工作台还是全局导航，影响员工的发现路径和日常使用频率
  2. 审批详情页是否需要展示申请人所在部门和岗位，影响审批人判断的信息充分度

3. 主交互流程

节点 3.1：管理员检查治理模式冲突

用户动作：

管理员在"权限管理模式"配置页中，看到当前已开启的模式（如"权限变更审批模式"），然后选择"员工自助申请"模式。

系统反馈：

如果当前已开启"权限变更审批模式"，系统直接阻断，弹出提示告知两个模式不能同时开启。弹窗中说明为什么互斥（两者都涉及"权限变更需要审批"，同时开启会导致审批链路混乱），并引导管理员先关闭当前模式再开启新模式。
如果当前开启了"双管理员模式"，系统不阻断但给出提醒：自助申请的审批链路将与双管理员互审各自独立运行，请确认审批规则配置。
如果当前没有任何互斥模式，直接进入配置步骤。

需要前置解释的信息：

  • 为什么自助申请和权限变更审批不能同时开启
  • 关闭当前模式的影响范围（如有审批中的数据如何处理）

建议文案：

  • 提示标题：不能同时开启"权限变更审批"和"员工自助申请"
  • 提示正文：这两个模式都涉及"权限变更需要审批"，同时开启会让管理员和审批人难以区分审批类型和管理标准。如需开启员工自助申请，请先关闭权限变更审批模式。
  • 按钮：去关闭权限变更审批 / 取消

下一步：

关闭冲突模式后，进入配置可申请范围（节点 3.2）。

节点 3.2：管理员配置可申请范围和敏感排除

用户动作：

管理员在配置页中看到系统已有的角色列表，勾选允许员工申请的角色。同时在敏感排除区看到系统建议排除的角色（超管角色、含权限管理配置能力的角色），可以选择接受建议或调整。

系统反馈：

角色列表展示每个角色的名称和简要说明。已被标记为敏感排除的角色默认不勾选并带有警告标记。
如果管理员将系统建议排除的高危角色加入可申请范围，系统给出二次确认提醒："该角色包含核心管理权限，开放申请可能带来安全风险，确认开放？"
如果管理员没有选择任何角色就尝试进入下一步，系统阻断并提示"请至少选择一个可申请的角色"。

需要前置解释的信息：

  • 什么是敏感角色，为什么需要排除
  • 每个可选角色的简要说明（包含哪些主要能力）

建议文案：

  • 区域标题：选择可申请的角色
  • 敏感排除区标题：不可申请的角色（系统建议）
  • 敏感排除说明：以下角色包含核心管理权限，建议不开放员工自助申请。您可以根据企业实际情况调整。
  • 高危角色确认弹窗：该角色包含权限管理配置能力，开放申请后员工可能通过审批获得管理权限。确认将此角色加入可申请范围吗？
  • 按钮：确认开放 / 取消

下一步：

配置审批人来源和超时策略（节点 3.3）。

节点 3.3：管理员配置审批规则

用户动作：

管理员选择审批人来源类型（直属负责人 / 指定角色成员 / 指定成员组等），设置超时时长和处理方式。

系统反馈：

审批人来源展示为下拉选择或单选组。选择"直属负责人"时，系统自动展示审批链路预览：员工 → 直属上级 → 上级的上级（降级链路）。选择其他来源时展示对应的审批人预览。
超时策略展示超时时长输入和四选一处理方式（提醒 / 转派 / 通过 / 拒绝）。设置完成后，下方展示审批流程的简要预览图，帮助管理员确认配置无误。

需要前置解释的信息：

  • 每种审批人来源的含义和适用场景
  • 审批人不存在时系统会怎么处理（向上查找降级链路）
  • 超时时长建议值（如 3 个工作日）

建议文案：

  • 审批人来源标签：审批人
  • 默认选项说明：直属负责人（推荐）—— 申请人的直属上级作为审批人，上级不存在时自动向上查找
  • 超时策略标签：审批超时处理
  • 超时说明：审批人在设置时长内未处理，系统将自动提醒。超过最长等待时间后，将自动转派给超级管理员处理。
  • 预览标题：审批流程预览

下一步：

确认配置并开启自助申请。

节点 3.4：员工查看自己的权限

用户动作：

员工从工作台点击"我的权限"入口，进入权限查看页面。

系统反馈：

页面展示员工当前拥有的所有权限列表。每条权限展示：权限名称（角色名或功能权限名）、来源说明（如"通过角色「销售专员」获得"或"由管理员直接授予"或"通过自助申请获得"）、生效时间。
如果当前没有任何权限，展示空状态：说明简洁的解释和引导，引导按钮指向"申请权限"入口。

需要前置解释的信息：

  • 权限来源的含义（角色分配 vs 直授 vs 自助申请）
  • 为什么要展示权限来源

建议文案：

  • 页面标题：我的权限
  • 页面说明：以下是你当前拥有的所有权限。如果发现缺少某个权限，可以发起[权限申请]。
  • 空状态标题：暂无权限
  • 空状态说明：你当前没有任何功能权限。如果你需要访问某些功能，可以申请权限，或联系管理员。
  • 空状态按钮：申请权限
  • 来源说明示例：通过角色「销售专员」获得 · 2025-03-01 生效 / 通过自助申请获得 · 2025-06-15 生效 / 由管理员直接授予 · 2025-01-10 生效

下一步：

点击"申请权限"进入申请流程（节点 3.5），或点击某条权限查看详情。

节点 3.5：员工发起权限申请

用户动作：

员工在"我的权限"页面点击"申请权限"，进入申请表单。表单中展示可申请的角色列表（已自动过滤不可申请的敏感角色），员工选择一个角色，填写申请原因，提交申请。

系统反馈：

角色列表展示每个角色的名称和简要说明（包含哪些主要能力）。员工选中角色后，下方展开申请原因输入框。
提交按钮点击后，系统校验申请原因不为空。提交成功则显示成功反馈，申请单进入"待审批"状态。同时系统通知对应审批人。
提交失败时（如网络异常或系统错误），显示失败提示并保留已填写的内容。

需要前置解释的信息：

  • 每个可选角色包含哪些能力
  • 申请提交后需要审批才能生效
  • 审批期间可以撤销申请

建议文案：

  • 页面标题：申请权限
  • 表单说明：选择你需要申请的角色并说明原因，提交后将由审批人处理。审批通过后权限会自动生效。
  • 角色选择区标签：选择角色
  • 申请原因标签：申请原因
  • 申请原因占位文字：请说明为什么需要这个权限，例如工作需要访问某个功能模块
  • 提交按钮：提交申请
  • 成功反馈：申请已提交，请等待审批人处理。你可以在"申请记录"中查看进度。
  • 失败反馈：提交失败，请稍后重试。如多次失败，请联系管理员。

下一步：

提交后跳转到申请记录页（节点 4.2）查看申请状态。

节点 3.6：审批人查看申请详情

用户动作：

审批人在审批待办列表中点击某条权限申请，进入审批详情页。

系统反馈：

审批详情页分为三个信息区：申请人信息区（姓名、部门、岗位）、申请内容区（申请的角色名称、角色包含的具体权限列表）、申请人已有权限区（申请人当前已拥有的所有权限列表，帮助审批人判断是否需要这个角色）。
如果申请人已有的权限中已经包含了申请角色的部分或全部能力，系统在已有权限区用视觉区分标记出来，提示审批人"此人已有部分该角色的能力"。

需要前置解释的信息：

  • 申请人已有的权限可能来自多种来源（角色分配、管理员直授、其他自助申请）
  • 如果不同意申请，需要填写拒绝原因

建议文案：

  • 页面标题：权限申请审批
  • 申请人信息标签：申请人、部门、岗位、申请时间
  • 申请内容区标题：申请内容
  • 角色能力说明：该角色包含以下权限
  • 已有权限区标题：申请人当前已有权限
  • 已有权限提示：申请人已拥有该角色的部分权限（如有重叠）

下一步：

做出审批决定——同意或拒绝（节点 3.7）。

节点 3.7：审批人做出审批决定

用户动作：

审批人查看完申请详情后，选择"同意"或"拒绝"，填写审批意见，提交审批结果。

系统反馈：

同意：系统自动调用授权接口，将角色授予申请人。授权成功后申请单状态变为"已生效"，通知申请人"你的权限申请已通过，权限已生效"。
拒绝：申请单状态变为"已拒绝"，通知申请人"你的权限申请未通过"，附带审批人填写的拒绝原因。
如果自动授权失败（如系统异常），显示"授权失败"提示，申请单不改变状态，审批人可重试。

需要前置解释的信息：

  • 同意后系统会自动授权，不需要手动操作
  • 拒绝时需要填写原因，帮助申请人理解

建议文案：

  • 同意按钮：同意申请
  • 拒绝按钮：拒绝申请
  • 审批意见标签：审批意见（选填）
  • 拒绝原因标签：拒绝原因（必填）
  • 拒绝原因占位文字：请说明拒绝原因，申请人可以看到
  • 同意后成功反馈：已同意，权限已自动授予申请人
  • 同意后通知申请人：你的"销售专员"角色权限申请已通过审批，权限已生效。
  • 拒绝后通知申请人：你的"销售专员"角色权限申请未通过审批。拒绝原因：[审批人填写的拒绝原因]。你可以重新提交申请。

下一步：

审批完成后返回审批待办列表。

4. 次交互流程

节点 4.1：管理员关闭自助申请并处理审批中申请

用户动作：

管理员在配置页中点击"关闭自助申请"。如果当前存在审批中的申请，系统弹出确认窗口，展示审批中申请的清单和处理选项。

系统反馈：

确认窗口展示：当前审批中的申请数量、每条申请的摘要（申请人、申请角色、提交时间）、两个处理选项（全部拒绝 / 转为管理员手动处理）。
管理员选择处理方式并确认后，系统执行收尾操作。关闭后员工端入口隐藏，员工已有的申请记录保留，来源标记更新为"自助申请（已关闭）"。

建议文案：

  • 确认窗口标题：关闭前请处理审批中的申请
  • 确认窗口说明：当前有 X 条权限申请仍在审批中。关闭自助申请前，需要先处理这些申请。
  • 选项一：全部拒绝 —— 拒绝所有审批中的申请，申请人会收到拒绝通知
  • 选项二：转为管理员手动处理 —— 审批中的申请将转为待办，由管理员手动决定是否授权
  • 确认按钮：确认关闭
  • 取消按钮：暂不关闭

下一步：

关闭后返回配置页，展示关闭状态。员工端入口同步隐藏。

节点 4.2：员工查看申请记录

用户动作：

员工在"我的权限"页面点击"申请记录"标签或入口，查看自己提交过的所有申请。

系统反馈：

申请记录列表展示每条申请的基本信息：申请的角色名称、提交时间、当前状态（待审批 / 已通过 / 已生效 / 已拒绝 / 已撤销）。支持按状态筛选。点击某条记录进入详情页，展示完整的申请信息、审批进度、审批人意见。

建议文案：

  • 页面标题：申请记录
  • 状态筛选标签：全部 / 待审批 / 已通过 / 已拒绝 / 已撤销
  • 记录卡片信息：申请角色、提交时间、当前状态
  • 详情页-审批进度：提交申请 → 待审批 → 已通过 → 已生效

下一步：

从详情页可以查看审批结果，被拒绝的申请可以从这里重新发起。

节点 4.3：员工撤销申请

用户动作：

员工在申请记录详情页中，对状态为"待审批"的申请，点击"撤销申请"。

系统反馈：

弹出二次确认窗口："撤销后该申请将不再被审批，如需申请请重新提交"。确认后，申请单状态变为"已撤销"，审批人待办中该申请消失。撤销记录保留在申请记录中。
如果申请状态已变更为"已通过"或"已拒绝"（在员工点击撤销前审批人已处理），撤销按钮不可用，显示当前状态。

建议文案：

  • 撤销确认标题：确认撤销申请
  • 撤销确认说明：撤销后该申请将不再被审批。如仍需该权限，请重新提交申请。
  • 确认按钮：确认撤销
  • 取消按钮：暂不撤销
  • 撤销成功反馈：申请已撤销

下一步：

撤销后返回申请记录列表。

5. 异常与阻断流程

异常 X1：审批人不存在或审批链路异常

发生时机： 员工提交申请后，系统自动分配审批人时。

触发条件： 管理员配置的审批人来源找不到对应的人——直属上级不存在、指定角色下无成员、或整个查找链路为空。

判断依据： business_blueprint.md 风险二"审批流程断裂"的保护策略。

反馈形式： 对员工：申请提交后状态展示为"待分配审批人"，并给出说明。对超管：站内消息或待办通知"有权限申请缺少审批人，请处理"。

系统反馈：

  • 员工侧：申请已提交，当前正在为您分配审批人。如有疑问请联系管理员。
  • 超管侧：以下权限申请缺少审批人，请手动分配或处理：申请人 [姓名]、申请角色 [角色名]、提交时间 [时间]。

用户下一步： 员工等待超管分配审批人；超管进入申请详情手动分配审批人或自行审批。

异常 X2：审批超时无人处理

发生时机： 申请进入"待审批"状态后，审批人在设定时长内未处理。

触发条件： 审批时间超过管理员配置的超时时长。

判断依据： facts.md 异常与边界"审批超时" + business_blueprint.md 风险二保护策略。

反馈形式： 对审批人：超时前发送催办通知。对超管：超时后发送转派通知。

系统反馈：

  • 催办通知（超时前）：你有一条权限申请已等待 X 天，请尽快处理。申请人：[姓名]，申请角色：[角色名]。
  • 转派通知（超时后）：权限申请已超时未处理，已自动转派给您。申请人：[姓名]，申请角色：[角色名]。请尽快处理。

用户下一步： 审批人在催办后尽快处理；超管在转派后接手审批。

异常 X3：管理员开启时检测到治理模式互斥

发生时机： 管理员在配置页中尝试开启"员工自助申请"时。

触发条件： 当前已开启"权限变更审批模式"。

判断依据： business_blueprint.md 风险三"模式互斥冲突"的保护策略。

反馈形式： 弹窗阻断，不允许直接开启。

系统反馈：

  • 弹窗标题：不能同时开启两个审批模式
  • 弹窗正文："员工自助申请"和"权限变更审批"都涉及"权限变更需要审批"，同时开启会导致两条审批链路交叉，管理员和审批人难以区分管理标准。如需开启员工自助申请，请先关闭"权限变更审批"模式。
  • 按钮：去关闭权限变更审批 / 取消

用户下一步： 点击"去关闭"跳转关闭权限变更审批模式，或取消保持当前状态。

异常 X4：员工尝试申请被排除的敏感角色

发生时机： 员工进入申请表单，查看可申请角色列表时。

触发条件： 管理员已将某些角色标记为"不可申请"（敏感排除）。

判断依据： business_blueprint.md 风险一"权限安全风险"的保护策略。

反馈形式： 入口过滤——被排除的角色在角色列表中直接不可见。

系统反馈： 列表只展示可申请的角色，被排除的角色不出现在列表的任何位置。申请人无法通过搜索或直接输入找到这些角色。

用户下一步： 从可申请角色中选择；如需申请被排除的角色，需联系管理员通过手动授权路径处理。

异常 X5：自动授权失败

发生时机： 审批人点击"同意"后，系统尝试自动授权时。

触发条件： 授权接口调用失败（如系统异常、权限数据冲突等）。

判断依据： business_blueprint.md 推荐方案中"审批通过后自动授权"的实现约束。

反馈形式： 对审批人：弹窗提示授权失败。申请单状态不变更。

系统反馈：

  • 弹窗标题：授权失败
  • 弹窗正文：权限授予过程中出现异常，申请单状态未变更。请稍后重试，如多次失败请联系技术支持。
  • 按钮：重试 / 稍后处理

用户下一步： 审批人点击重试；如持续失败，提交技术支持处理。此时申请单仍处于"待审批"状态，不会丢失。

异常 X6：管理员关闭时存在审批中的申请

发生时机： 管理员在配置页中点击"关闭自助申请"时。

触发条件： 当前存在状态为"待审批"的申请。

判断依据： business_blueprint.md 风险四"关闭能力后的数据悬空"的保护策略。

反馈形式： 弹窗阻断，强制要求选择收尾方式后才允许关闭。

系统反馈：

  • 弹窗标题：关闭前请处理审批中的申请
  • 弹窗正文：当前有 [X] 条权限申请仍在审批中。关闭自助申请前，请选择处理方式。
  • 选项一及说明：全部拒绝 —— 拒绝所有审批中的申请，申请人会收到拒绝通知。
  • 选项二及说明：转为管理员手动处理 —— 审批中的申请将转为您的手动待办，由您逐一决定是否授权。
  • 确认按钮：确认关闭（选择处理方式后才可点击）
  • 取消按钮：暂不关闭

用户下一步： 选择处理方式后确认关闭；或取消返回。

异常 X7：员工离职或转岗时的申请处理 [GAP]

发生时机： 员工离职或转岗时，存在该员工发起的待审批申请或已生效的申请获得权限。

触发条件： 成员管理系统触发离职或转岗操作。

判断依据： facts.md 开放问题与缺口中的 [GAP] 项。

反馈形式： [GAP] 离职时权限回收的具体时机、通知方式和申请记录保留策略待确认。

系统反馈： [GAP] 建议离职时自助申请获得的权限随账号停用一并回收，通知形式待定。

用户下一步： [GAP] 待产品确认回收策略后设计。

8. 待确认问题

  1. 员工端入口是放工作台还是全局导航？

影响：决定员工的发现路径。工作台入口适合高频使用但依赖管理员配置工作台卡片；全局导航入口稳定但可能与现有导航结构冲突。入口位置还影响权限中心的定位——是独立的服务中心还是工作台的一个卡片。
建议确认方：产品 + 设计

  1. 审批详情页是否需要展示申请人部门和岗位？

影响：审批人的判断信息充分度。如果不展示部门和岗位，审批人可能需要额外确认申请人的身份和业务范围。建议展示，但需要确认字段口径。
建议确认方：产品

  1. 审批通过和拒绝后，员工通过什么方式收到通知？

影响：员工是否及时知道申请结果。站内消息 + 审批通知是默认方案，是否需要短信需要评估成本和场景。
建议确认方：产品

  1. 被拒绝的申请，员工从什么入口重新提交？

影响：决定"申请记录详情页"是否需要"重新申请"按钮，还是让员工回到申请入口从头填。建议支持从拒绝记录直接重新发起。
建议确认方：设计

  1. 关闭能力后，员工的申请记录页是否还可见？

影响：决定关闭后员工端的信息架构。建议保留查看但隐藏申请入口，来源标记如实展示"自助申请（已关闭）"。
建议确认方：产品

  1. 员工离职时权限回收的通知方式？

影响：影响离职流程的完整性和员工的知情权。如果自动回收不通知，员工可能困惑为什么权限消失了。
建议确认方：产品

  1. 管理端统计数据的更新频率？

影响：管理员看数据时的预期。实时更新可以反映最新状态但可能增加系统压力，定时更新（如每小时）需要明确标注数据截止时间。
建议确认方：技术 + 产品
