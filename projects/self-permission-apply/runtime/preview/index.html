轻量业务蓝图

0. 本次关键业务判断

判断：

这次不是在权限体系上加一个功能入口，而是为一整条以前不存在的权限获取路径——"员工感知需求 → 发起申请 → 审批关卡 → 自动生效"——补齐来源归属、治理状态、审批链路和查询解释的闭环。适合按轻量业务蓝图承接，因为底层模型不变（来源枚举、状态机、决策链均不改），但需要把新路径在每个模型层中的位置显式定义清楚。

主要影响：

  1. 权限的来源解释从"管理员给的 / 角色带的 / 应用可见的"三条变成四条，新增"自助申请审批获得"作为治理修饰标记
  2. 权限治理的触发方从管理员扩展到员工，审批中台的"发起人"语义需要兼容员工角色
  3. 员工侧首次出现权限查询和申请能力，需要定义与管理员侧权限视图的关系和隔离边界

建议方案：

  • 自助申请作为现有"权限变更审批模式"的员工侧触发端，复用决策链契约（L0→L1→L2→L3）和治理状态机（draft→pending→approved→effective→revoked）
  • 权限来源仍归入 ACL_DIRECT，通过治理修饰因子"自助申请审批获得"区分于管理员手动直授
  • 可申请范围默认按角色配置，敏感角色（高危操作、资金操作、超管）默认排除在可申请范围外
  • 审批链路复用 OA 审批中台完整能力，默认审批人指向组织架构负责人

本阶段先定清：

  • 自助申请权限在来源模型和决策链中的解释路径（哪些层不变、哪些层新增判定分支）
  • 与现有治理模式的叠加规则矩阵（共存 / 高风险标注 / 互斥）
  • 关闭能力时对三种状态（已生效 / 审批中 / 草稿）的差异化处理

需要重新判断的信号：

  1. 如果后续需要开放功能权限级申请（而非仅角色），需重新评估员工侧信息架构复杂度
  2. 如果后续需要支持员工自选数据权限范围，需重新评估决策链 L2 的配置路径

1. 一句话结论

能做。建议首期按角色申请、复用 OA 审批中台和现有治理状态机，权限来源归入 ACL_DIRECT + 治理修饰标记"自助申请审批获得"。核心工作不在新功能开发，而在于让新路径在来源解释、状态流转、审批链路和查询闭环四个维度上都有明确位置且可被审计。

2. 关键业务规则

前提判断：当前需求成立的条件

  • 企业在权限管理上已经使用了角色体系，角色定义相对清晰。如果企业角色混乱或未启用角色管理，自助申请的价值会大打折扣——因为员工无法理解"我能申请什么"
  • 管理员愿意且有能力完成可申请范围的初始配置。如果管理员不配置就直接开启，员工端将看不到任何可申请的权限，能力形同虚设
  • OA 审批中台已可用且审批链路可配置。如果审批中台尚未就绪，自助申请的审批环节无法闭环

关键规则：影响体验承接的必须项

  • 可申请范围 = 管理员勾选的角色集合 - 敏感角色默认排除集合。不在范围内的角色，员工端不展示、不可搜索、不可申请
  • 同一角色同一时间一个员工只能有一条 active 申请（draft / pending）。已有该角色的权限（无论来源）时不提供申请入口
  • 审批通过后自动授权，权限来源标注为"自助申请审批获得"。如果自动授权失败（如角色被删除），申请异常终止并通知管理员
  • 关闭能力 = 已生效权限保留 + pending 全部终止通知 + draft 归档。关闭操作需审计日志
  • 员工端权限列表必须标注每项权限的来源（管理员授予 / 来自 XX 角色 / 自助申请 / 协作可见），对应 RISK-002

规则边界与执行优先级

  • 决策链契约的层级顺序不变：先判可见性（L0），再判功能权限（L1），再判数据范围（L2），最后判治理状态（L3）。自助申请只影响 L3（从 pending 到 effective 的状态流转），不改变 L0-L2 的判定逻辑
  • 自助申请与子管理员模式可共存（子管理员可在管辖范围内审批员工申请）
  • 自助申请与双管理员模式不互斥，但叠加时配置页需显式高风险警告
  • R-009 的互斥关系（子管理 + 双管理）不受自助申请影响

3. 边界与风险

不能放开的限制

  • 权限来源枚举不新增顶层分类。自助申请审批通过后的权限来源仍为 ACL_DIRECT，不在 ACL_DIRECT / RBAC_ROLE / APP_VISIBILITY / COLLAB_VISIBILITY 之外新增
  • 治理状态机不新增状态节点。复用 draft / pending / approved / rejected / effective / revoked 六个状态
  • 不另建审批引擎。审批流程设计、审批操作、超时处理、转派交接、数据管理全部复用 OA 审批中台
  • 不另建统计分析面板。统计数据接入 OA 审批已有智能分析面板
  • 服务人员明确不开放（3 个月有效期 + 资金操作硬隔离不支持自助权限扩展）

最关键的风险

  1. 权限来源解释更不透明（RISK-002 加剧）：如果"自助申请审批获得"和"管理员手动直授"在权限查询页显示为相同的来源，排错时无法区分，员工会说"我明明申请通过了为什么还看不到"而管理员也无法判断权限到底怎么来的
  2. 覆盖规则导致反直觉结果（RISK-003）：员工申请角色审批通过、权限已生效，但应用可见性范围未覆盖导致入口不可达。这是自助申请场景下挫败感最强的体验——比管理员直授场景更严重，因为员工付出了"主动申请 + 等待审批"的成本
  3. 可申请范围配置质量决定能力生死：范围过宽 → 权限失控；范围过窄 → 员工申了也白申。而管理员对角色体系的理解正是当前系统里最薄弱的环节之一
  4. 关闭能力时的批量终止操作：如果审批中的申请量大，批量终止属于高危及批量操作（RISK-007），必须有确认步骤和完整的通知覆盖

对应保护策略

  • 权限查询页必须展示"获取方式"字段，与"来源类型"并列，确保自助申请和管理员直授可区分
  • 权限详情页在权限已生效但应用不可见时，必须显式解释"你已获得 XX 角色的功能权限，但该角色对应的应用当前对你不可见，请联系管理员调整应用可见范围"
  • 管理员首次开启自助申请时，提供配置向导：先引导勾选可申请角色，再引导设置审批流程，再引导预览员工端效果
  • 关闭能力时强制二次确认，并展示受影响申请数量（"当前有 N 条审批中的申请将被终止"）

4. 体验承接要求

角色：

  • 普通员工：需覆盖"查看我的权限"和"发起权限申请"两个场景。后者需在"发现自己缺权限"的时刻自然触达（无权限提示页嵌入），也需要独立入口（工作台"我的权限"）
  • 审批人：需覆盖"审批权限申请"场景。审批时能看到申请人的已有权限概览，用于判断申请合理性
  • 超级管理员 / 权限管理员：需覆盖"配置自助申请能力"和"查看申请统计"两个场景。配置需向导式引导

流程：

  • 员工端主流程：发现缺权限（或主动进入"我的权限"）→ 浏览可申请角色 → 选择角色 → 填写申请原因 → 提交 → 查看审批进度 → 审批通过后权限自动出现在"我的权限"列表中
  • 审批端主流程：收到待办 → 查看申请人信息、申请角色、申请原因、已有权限概览 → 同意（自动授权）/ 拒绝（必填原因）
  • 管理端主流程：进入权限管理模式 → 开启自助申请 → 配置可申请角色（向导式）→ 配置审批流程 → 发布生效

进度与结果状态：

  • 申请提交后的每个状态变化都必须有通知：提交成功 → 审批中（告知审批人是谁）→ 审批通过 → 权限已生效（告知在哪可以看到和使用）
  • 拒绝时必须让员工看到拒绝原因
  • 撤销后必须让审批人知道申请已撤回
  • 关闭能力时双方都必须收到通知

异常：

  • 审批人不存在：提交时阻止并引导联系管理员
  • 自动授权失败：通知管理员介入，告知员工"授权处理中"
  • 可申请角色被删除：自动终止并通知申请人
  • 应用不可见导致权限不可达：在"我的权限"详情中显式解释原因
  • 审批超时：按 OA 审批中台规则，不自动通过

反馈：

  • 关键操作（提交申请、审批通过/拒绝、关闭能力）必须有明确的结果反馈
  • 状态变更需通过通知触达（客户端弹框 + 移动端推送 + 微信公众号），复用 OA 审批已有通知通道
  • 错误和阻断必须给出下一步指引，不只说"操作失败"

文案：

  • "我的权限"页面需解释"权限来源"的含义，帮助员工理解"为什么我有/没有这个权限"
  • 无权限提示页的申请入口文案方向："你暂无此功能的权限，如果认为自己需要，可以申请以下角色"（而非干巴巴的"无权限"）
  • 审批详情页需展示申请人身份和已有权限，帮助审批人快速判断
  • 关闭能力时的确认弹窗需说明受影响范围（"关闭后，N 条审批中的申请将被终止，已生效的权限不受影响"）

5. 升级信号

出现以下变化时，应停止当前轻量执行并请求 UXB 重新判断：

  1. 需求范围从"按角色申请"扩展到"按功能权限申请"——员工侧信息架构和认知负担显著上升，需重新评估复杂度
  2. 需求范围从"不选数据范围"扩展到"员工自选数据范围"——决策链 L2 复杂度直接暴露给员工，需重新评估数据权限配置路径
  3. 自助申请被要求与双管理员模式强制互斥（而非高风险标注）——需在设计上增加模式互斥校验
  4. 需求扩展到服务人员——服务人员的 3 个月有效期和资金操作硬隔离与自助申请的逻辑需要重新对齐

6. 待确认问题

  • 可申请角色勾选清单中，"敏感角色"的判定标准由产品侧还是实施侧定义？影响首次开启时的默认排除范围
  • 审批人已查看申请但未处理时，是否允许员工撤销？影响撤销按钮的可用状态设计
  • 申请时是否需要支持上传附件（如证明材料）？OA 审批已支持，首期做管理员可配置项即可，但需确认是否纳入首期

0. 本次关键设计判断

判断：

这次体验设计的核心不是"做一个好看的申请表单"，而是让三个角色在一条全新的权限获取路径上，每个关键节点都能看到自己需要的信息、做出有依据的判断。重点投入在"解释性设计"——让员工知道能申请什么、为什么有/没有权限、申请走到哪了；让审批人能判断该不该批；让管理员敢开、会配、能关。

主要影响：

  1. 员工侧需要两个入口（缺权限时的自然触达 + 主动查看的固定入口），不能只放一个菜单项
  2. 审批侧需要嵌入"申请人已有权限概览"，这是审批人判断申请合理性的关键信息
  3. 管理员侧的配置体验决定这个能力会不会被用起来——如果配置门槛太高，管理员不配或配错，能力形同虚设

建议方案：

  • 员工端"我的权限"作为信息聚合页，权限来源标注为最核心的解释字段
  • 无权限提示页嵌入申请入口，从"发现问题"到"发起解决"一步直达
  • 审批详情在标准审批信息基础上增加"申请人已有权限概览"模块
  • 管理员首次开启时走配置向导（选角色 → 设审批 → 预览效果），降低认知门槛
  • 关闭能力和批量终止操作必须有确认步骤和受影响数量展示

不建议方案：

  • 不在工作台直接放一个孤立的"申请权限"按钮（缺少上下文时员工不知道能申请什么、该不该申请）
  • 不把权限来源混在一起展示而不做区分（会导致排障不可持续）

关键待确认：

  1. 无权限提示页当前是否存在？如果不存在，需要新增页面承载，影响入口方案
  2. 审批人在移动端审批时是否需要查看申请人已有权限概览？影响移动端审批详情的信息结构

2. 交互流程总览

普通员工（申请路径）
遇到无权限页面→点击"申请权限"→3.1 浏览可申请角色列表→3.2 选择角色并填写申请→提交确认→查看申请记录→收到审批结果通知→在"我的权限"中看到新权限
普通员工（查看路径）
进入"我的权限"→查看已有权限列表（含来源标注）→查看可申请角色→3.1 发起申请
审批人
收到待办通知→进入审批详情→3.3 查看申请人信息与已有权限→同意或拒绝→确认操作
超级管理员
进入权限管理模式→开启自助申请开关→4.1 配置向导（勾选可申请角色）→4.2 配置审批流程→发布→4.3 查看统计数据

异常流程重点：

  • 提交申请时审批人不存在 → 阻止提交，引导联系管理员
  • 审批通过后自动授权失败 → 管理员介入，告知员工处理中
  • 审批进行中管理员关闭能力 → 批量终止所有审批中申请并通知
  • 审批通过后应用不可见导致权限不可达 → 在权限详情中显式解释原因
  • 可申请角色在审批中被删除 → 自动终止申请并通知

3. 主交互流程

节点 3.1：员工浏览可申请角色并选择

用户动作：

员工从无权限提示页或"我的权限"页进入可申请角色列表，浏览有哪些角色可以申请，选择一个目标角色。

系统反馈：

展示可申请角色列表，每项显示角色名称、角色简要说明。员工已有权限的角色标注"已拥有"且不可点击申请。员工已有审批中申请的角色标注"审批中"且不可重复提交。不在管理员开放范围内的角色不展示。

需要前置解释的信息：

  • 这里展示的是管理员开放申请的角色，不是你一定能看到的所有角色
  • 申请审批通过后，权限会自动生效，不需要再找管理员手动开通
  • 如果找不到你需要的角色，请联系管理员确认是否已开放申请

建议文案：

  • 页面标题："申请权限"
  • 列表空态："当前没有可申请的角色。如果认为需要某个权限，请联系管理员。"
  • 已有权限标注："已拥有——你已通过其他方式获得此权限"
  • 审批中标注："审批中——你已有此角色的待审批申请"

下一步：

选择一个可申请的角色，进入节点 3.2 填写申请。

节点 3.2：员工填写并提交申请

用户动作：

在角色详情/申请页查看角色说明，填写申请原因，点击提交。

系统反馈：

提交前校验审批链路完整性。如果审批人不存在，阻止提交并给出明确提示。提交成功后，展示提交成功反馈，告知预计审批人和审批路径。同时发送通知给审批人。

需要前置解释的信息：

  • 提交后需要等待审批人处理，审批通过后权限自动生效
  • 审批期间你可以在"我的申请"中查看进度
  • 如果需要加急处理，可以直接联系审批人

建议文案：

  • 页面标题：显示所选角色名称
  • 角色说明区：展示角色包含的主要权限范围
  • 申请原因输入框占位："请简要说明为什么需要此权限，帮助审批人了解你的使用场景"
  • 提交按钮："提交申请"
  • 提交成功反馈："申请已提交。审批人：[审批人姓名]。你可以在"我的申请"中查看审批进度。"
  • 审批人不存在阻断："当前审批流程尚未配置完整，无法提交申请。请联系管理员完成审批流程配置。"

下一步：

提交后跳转到申请记录列表，可查看刚刚提交的申请状态。

节点 3.3：审批人查看并处理权限申请

用户动作：

从待办列表进入审批详情页，查看申请人信息、申请角色、申请原因、申请人已有权限概览，判断该申请是否合理，选择同意或拒绝。

系统反馈：

审批详情展示完整申请信息和申请人已有权限概览。同意后，系统自动完成授权并通知申请人权限已生效。拒绝时弹出拒绝原因输入框（必填），提交后通知申请人。

需要前置解释的信息：

  • 申请人已有权限列表帮助你判断是否需要额外授权
  • 同意后权限会自动生效，无需手动配置
  • 超时未处理不会自动通过（权限审批为安全敏感操作）

建议文案：

  • 审批详情-申请人已有权限模块标题："申请人当前已有权限"
  • 若无已有权限："该员工当前无任何权限"
  • 同意按钮："同意授权"
  • 拒绝按钮："拒绝"
  • 拒绝原因输入框占位："请填写拒绝原因，申请人将看到此说明"
  • 同意后反馈："已同意，权限已自动生效并通知申请人"
  • 拒绝后反馈："已拒绝，申请人将收到通知和拒绝原因"

下一步：

审批完成后返回待办列表。如有下一节点审批人，系统自动流转。

4. 次交互流程

节点 4.1：管理员首次开启自助申请——配置可申请角色

用户动作：

在权限管理模式页开启自助申请开关后，进入配置向导第一步，从角色列表中勾选需要开放申请的角色。

系统反馈：

展示完整角色列表（含不可勾选的高敏感角色，标注"此角色不支持自助申请"）。默认排除：含高危批量操作的角色、涉及资金操作的角色、超管角色。勾选后实时显示已选数量。敏感角色旁有风险等级标注作为辅助判断。

建议文案：

向导标题："配置可申请角色——选择员工可以自助申请的角色范围"。高敏感角色标注："此角色因涉及敏感操作，不支持员工自助申请"。空选择态提示："至少需要选择一个角色，否则员工端将看不到任何可申请内容"。

下一步：

点击"下一步"进入审批流程配置。

节点 4.2：管理员配置审批流程

用户动作：

在向导第二步中设置审批流程，选择审批人类型或跳转至 OA 审批中台进行详细流程设计。

系统反馈：

默认展示推荐配置（审批人 = 组织架构负责人）。提供"使用推荐配置"快速完成和"自定义审批流程"跳转 OA 审批中台两个选项。选择自定义时，新标签页打开 OA 审批中台。

建议文案：

向导标题："配置审批流程——设置员工提交申请后的审批规则"。推荐配置说明："默认由申请人的组织架构负责人审批。如果员工没有组织负责人，审批将转给权限管理员。"。

下一步：

点击"下一步"进入预览确认。

节点 4.3：管理员预览并发布

用户动作：

在向导最后一步预览配置效果，确认无误后点击发布。

系统反馈：

展示配置摘要（已选角色数量、审批方式、预估影响范围）。发布成功后，自助申请能力正式生效，员工端入口出现。如果此时有双管理员模式开启，展示高风险警告："你同时开启了双管理员模式，员工的每一条权限申请都需要两位管理员审批通过才能生效，审批周期会变长。"

建议文案：

发布成功反馈："自助申请权限能力已开启。员工可以在工作台查看和申请权限。如需调整配置，可随时在此页面修改。"

下一步：

返回权限管理模式页，可查看运行状态和统计数据。

节点 4.4：管理员关闭自助申请能力

用户动作：

在权限管理模式页关闭自助申请开关。

系统反馈：

弹出确认弹窗，展示受影响数据（"当前有 N 条审批中的申请将被终止"）。确认后执行：已生效权限保留，所有 pending 申请终止并通知双方，draft 归档，员工端入口隐藏。关闭操作写入审计日志。

建议文案：

确认弹窗标题："确认关闭员工自助申请权限？"。弹窗正文："关闭后：已生效的权限不受影响；当前 N 条审批中的申请将被终止，申请人和审批人都会收到通知；员工端将不再显示申请入口。此操作不可撤销，但你可以随时重新开启。"

下一步：

关闭完成后，可在审计日志中查看操作记录。

节点 4.5：员工查看申请记录与撤销申请

用户动作：

进入"我的申请"列表，查看历史申请和当前状态。对 pending 状态的申请，可选择撤销。

系统反馈：

列表展示每条申请的角色、提交时间、当前状态、审批人。撤销操作需二次确认。撤销后状态标为 revoked，审批人收到撤回通知。

建议文案：

列表标题："我的申请"。撤销确认弹窗："确定撤销此申请？撤销后审批人将收到通知。如果之后仍需要此权限，可以重新提交申请。"

下一步：

撤销后可重新申请同一角色。

节点 4.6：员工在"我的权限"中查看权限详情

用户动作：

在"我的权限"页面点击某项权限，查看详细信息。

系统反馈：

展示权限详情：权限名称、来源（管理员授予 / 来自 XX 角色 / 自助申请 / 协作可见）、获取时间、数据权限范围。对于自助申请获得的权限，额外展示原申请记录链接。对于已生效但因应用不可见导致不可达的权限，显式展示原因说明。

建议文案：

权限来源-自助申请标注："通过自助申请审批获得（查看申请记录）"。应用不可见说明："你已获得此权限，但因对应应用当前对你不可见，暂时无法使用。如需使用，请联系管理员调整应用可见范围。"

下一步：

可从详情返回列表。

5. 异常与阻断流程

异常 A：提交申请时审批人不存在

发生时机： 员工点击"提交申请"时
触发条件： 审批链路中任一节点无有效审批人（组织负责人未设置、审批人已离职等）
判断依据： business_blueprint_lite 关键规则中的"审批人不存在处理"规则
反馈形式： 页面阻断提示
系统反馈： "当前审批流程尚未配置完整，无法提交申请。请联系管理员完成审批流程配置。"
用户下一步： 联系管理员。管理员需在 OA 审批中台补完审批人配置，或更换审批方式。

异常 B：审批通过后自动授权失败

发生时机： 审批人点击同意后，系统尝试自动授权时
触发条件： 目标角色已被删除、权限系统不可用、数据一致性问题等
判断依据： business_blueprint_lite 关键规则中的自动授权失败处理
反馈形式： 审批人侧弹窗提示异常；员工侧通知"授权处理中"
系统反馈（审批人）： "授权操作未能自动完成，已通知管理员处理。申请状态将保持为"已通过待生效"。"
系统反馈（员工）： "你的权限申请已通过审批，系统正在处理授权，请稍候。"
用户下一步： 管理员需在用户授权页手动完成授权，或将申请关联的角色重新配置后重试。

异常 C：审批进行中管理员关闭自助申请能力

发生时机： 管理员在权限管理模式页点击关闭时
触发条件： 存在 pending 状态的申请
判断依据： business_blueprint_lite 边界与风险中的"关闭能力时的批量终止操作"
反馈形式： 管理员侧弹窗确认，展示受影响数量。执行后通知所有受影响员工和审批人
系统反馈（管理员确认弹窗）： "当前有 N 条审批中的申请将被终止。关闭后已生效权限不受影响。"
系统反馈（员工通知）： "管理员已关闭自助申请权限能力，你提交的 [角色名称] 申请已被终止。如仍需要此权限，请联系管理员。"
用户下一步： 员工需等待能力重新开启后重新申请，或直接联系管理员。

异常 D：审批通过但应用不可见导致权限不可达

发生时机： 员工在"我的权限"中看到已生效权限，但实际无法使用对应应用
触发条件： 应用可见范围未覆盖该员工（对应 RISK-003）
判断依据： 决策链契约 L0 可见性门槛；business_blueprint_lite 风险项"覆盖规则导致反直觉结果"
反馈形式： 权限详情页显式说明
系统反馈： "你已获得 XX 角色的功能权限（通过自助申请审批获得），但该角色对应的应用当前对你不可见，暂时无法使用。如需使用，请联系管理员调整应用可见范围。"
用户下一步： 联系管理员调整应用可见范围。管理员可在应用管理中调整。

异常 E：可申请角色在审批中被删除

发生时机： 员工申请提交后、审批完成前
触发条件： 管理员在角色管理中删除了员工正在申请的角色
判断依据： facts 异常与边界表
反馈形式： 申请自动终止，通知申请人和审批人
系统反馈（员工）： "你申请的角色 [角色名称] 已被管理员移除，申请已自动终止。请查看其他可申请角色或联系管理员。"
系统反馈（审批人）： "[员工姓名] 申请的 [角色名称] 权限申请已因角色被删除而自动终止。"
用户下一步： 员工可选择其他角色申请或联系管理员。

异常 F：审批超时

发生时机： 审批人在配置的超时时间内未处理
触发条件： 超时时间到达
判断依据： OA 审批中台超时处理能力；business_blueprint_lite 明确"不自动通过"
反馈形式： 按 OA 审批中台已有超时规则（超时提醒 → 超时转派），不做超时自动通过
系统反馈（审批人）： "你有一条待审批的权限申请已超时，请尽快处理。"（按 OA 审批超时提醒规则）
用户下一步： 审批人仍可手动处理；员工可通过 OA 审批催办功能提醒审批人。

  • 可申请角色列表中的角色项：主操作按钮为"申请"（仅在"可申请"状态下显示）
  • 我的申请列表中 pending 项：次操作按钮为"撤销申请"

失败反馈： 自动授权失败时："授权操作未能自动完成，已通知管理员处理。"

页面 6.4：管理员端——自助申请配置页

页面目标： 让管理员在权限管理模式下完成自助申请能力的开启、配置和关闭。

进入条件： 超管或权限管理员从权限管理模式页进入。

页面结构：

+-------------------------------------------------------+
| 顶部区：页面标题"员工自助申请权限" |
| 总开关："启用员工自助申请权限" [开关] |
+-------------------------------------------------------+
| 配置区（能力开启后展示）： |
| - 可申请角色：[查看/修改] → 打开角色勾选面板 |

| - 审批流程：[查看/修改] → 打开审批配置或跳转 OA 审批中台 |
| 当前：组织架构负责人审批 / 自定义 |
+-------------------------------------------------------+
| 运行状态区（能力开启后展示）： |
| - 累计申请数 / 审批通过率 / 平均审批耗时 |
| - 高频申请角色排行 |
| - [查看完整统计] → 跳转 OA 审批智能分析面板 |
+-------------------------------------------------------+
| 关闭操作区： |
| - "关闭员工自助申请权限" [按钮] |

| 将被终止。" |
+-------------------------------------------------------+

状态反馈区： 开关状态和统计数据即为实时反馈。配置变更后 toast 提示已保存。

异常状态下的结构变化：

  • 双管理员模式同时开启时：在页面顶部展示高风险警告横幅
  • 审批中台不可用时：审批流程配置入口展示"暂不可用"状态

具体文案：

  • 页面标题："员工自助申请权限"
  • 总开关标签："启用员工自助申请权限"
  • 可申请角色配置项："可申请角色——已选 X 个"
  • 审批流程配置项："审批流程——当前：XXX"
  • 关闭按钮："关闭员工自助申请权限"
  • 关闭说明："关闭后，已生效的权限不受影响，审批中的申请将被终止。"
  • 高风险警告横幅："你同时开启了双管理员模式，员工的每一条权限申请都需要两位管理员审批通过才能生效，审批周期会变长。你可以选择关闭双管理员模式以简化审批流程。"

按钮：

  • 主按钮：总开关
  • 配置区操作：查看/修改（链接或按钮）
  • 关闭操作：危险按钮"关闭员工自助申请权限"

成功反馈： 配置保存 toast："配置已保存"。能力开启 toast："员工自助申请权限能力已开启"。能力关闭 toast："能力已关闭，N 条审批中的申请已终止。"

失败反馈： 操作失败时 toast，引导重试或联系技术支持。

8. 待确认问题

  1. 无权限提示页的当前存在形态

影响：员工端"发现缺权限→发起申请"的自然触达路径依赖此页面的存在和结构。如果不存在，需要新增页面；如果存在但结构不兼容，需要改造。
建议确认方：产品 / 设计

  1. 审批人移动端已有权限概览展示

影响：审批人在移动端审批时能否看到"申请人已有权限概览"模块，影响审批详情的信息架构和移动端适配策略。如果移动端空间不足，可能需要折叠或分层展示。
建议确认方：设计 / 技术

  1. 敏感角色的判定标准

影响：管理员首次开启自助申请时，哪些角色默认排除在可申请范围外。如果产品侧不定义标准，管理员需要自行判断，配置门槛上升。
建议确认方：产品 / 业务

  1. 申请时附件上传是否纳入首期

影响：申请表单的字段数量和信息结构。OA 审批中台已支持附件控件，首期建议做管理员可配置项（默认关闭），但需确认技术实现和测试范围。
建议确认方：产品 / 技术

  1. 审批人已查看但未处理时是否允许员工撤销

影响：员工端"我的申请"列表中 pending 状态申请的撤销按钮可用条件。如果允许任意撤销，审批人体验受影响；如果完全不允许，员工灵活性受限。
建议确认方：产品

  1. 自助申请与双管理员模式叠加时的前端警告强度

影响：管理员配置页的高风险警告是横幅提示还是弹窗阻断。如果仅是横幅，管理员可能忽略；如果是弹窗，可能过于强势。
建议确认方：产品 / 设计
