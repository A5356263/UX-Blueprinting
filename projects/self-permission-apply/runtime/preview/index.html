业务蓝图：员工自助申请权限

0. 本次关键设计判断

判断：

员工自助申请权限是一个成立且值得正式做的需求，但它的核心不是"做一个申请页面"，而是在现有权限管理体系中新增一种权限来源方式和生效机制。必须先在业务层面定义清楚新来源的定位、范围和边界，才能保证后续的体验方案不跑偏。

主要影响：

  1. 权限来源模型需要扩展，新增"员工自助申请"作为一种独立的权限获得方式，与管理员直授、角色授予并列
  2. 生效机制从"配置即生效"变为"审批后自动授权"，需要在现有判断链路中插入审批生效条件
  3. 员工端的权限认知模型需要建立"我的权限"和"我可以申请的权限"两条信息线

建议方案：

  • 将自助申请定位为"管理员可控范围内的员工自服务通道"，而不是完全开放的权限市场
  • 可申请范围与现有角色体系共用同一套口径，减少概念增殖
  • 审批人由管理员在配置时指定，既可以固定人，也可以走审批中台流程

不建议方案：

  • 不建议把自助申请做成"员工随便选，管理员只要审批"的完全开放模式——可申请范围必须由管理员提前限定
  • 不建议让员工按数据范围申请——当前只需覆盖角色和功能权限

关键待确认：

  1. 员工申请时是按角色申请（一次性获得角色下所有功能权限），还是按功能权限点逐个申请——这直接影响管理端配置和员工端申请交互

> 更多待确认问题详见 ## 9. 待确认问题。

1. 一句话结论

能做，建议做。但它的落地顺序应该是：先定义来源模型定位和管理端配置能力，再做员工端申请链路。管理端的边界定义清楚了，员工端的体验才不会反复改。

2. 这件事为什么值得正式做

现在的问题不是"没有申请页面"，而是"权限申请没有标准化的业务路径"：

  • 员工不知道找谁、等多久
  • 管理员被频繁打断，授权动作没有留痕
  • 中大型企业人员越多，这个问题越严重

这次方案成立需要满足的前提是：管理员始终保留对申请范围的控制权，审批通过后自动授权是可靠的，且不与现有治理模式冲突。当前这几个前提都已确认可满足。

哪些情况下需要降级做：如果企业内部组织架构不清晰、角色体系尚未建立，自助申请的价值会大打折扣，建议先完善角色体系再开启。

3. 值不值得做

收益：

  • 降低管理员重复劳动——员工自助申请+审批后自动授权，管理员不需要手动配权限
  • 缩短授权时效——员工不再需要等管理员有空才能获得权限
  • 增加审计可追溯性——所有申请有记录、有审批、有结果
  • 提升员工自主性——员工可自行查看权限和申请进度，减少沟通成本

成本：

  • 开发成本——来源模型扩展、状态机新增、审批后自动授权链路
  • 管理成本——管理员需要配置可申请范围和审批人，增加初始设置负担
  • 认知成本——员工需要理解"我有什么权限"和"我能申请什么权限"的区别

系统代价：

  • 链路复杂度增加——权限判断链路需要增加来源类型和审批生效条件判断
  • 审计范围扩大——需要追踪申请单和授权结果的对应关系
  • 对既有流程的破坏风险——如果切入不当，可能干扰现有的权限治理流程

综合判断：
收益显著大于成本，特别是对于中大型企业。但必须保证管理端的配置能力先到位，避免出现"开放了但控制不住"的局面。

4. 应该做成什么能力形态

比较两条路径：

路径 A：独立功能模块

  • 在管理后台新增"自助申请配置"独立模块，统一管理开关、范围、审批人
  • 员工端在工作台或应用入口新增"权限申请"入口
  • 优点：边界清晰，不影响现有权限页面结构
  • 缺点：独立模块可能成为"配置孤岛"，与现有的角色管理、用户授权页面脱节

路径 B：扩展现有能力

  • 在现有的角色管理/用户授权等页面中嵌入自助申请配置能力
  • 员工端与现有"我的权限"查询页面共用入口
  • 优点：配置路径与现有权限管理一致，管理员不需要学习独立模块
  • 缺点：现有页面结构和交互需要调整，改动面较大

推荐：路径 A（独立功能模块）

理由：

  • 自助申请配置与现有的权限配置（角色管理、用户授权）面向不同的操作者和目的——前者是"控制员工可以申请什么"，后者是"管理员直接分配什么"
  • 独立模块可以保证关闭时一刀切干净，不影响其他配置
  • 等模式稳定后，可以在适当时机与现有权限配置页面做入口聚合，但初始阶段不建议耦合

5. 推荐业务方案

角色与职责

角色职责
超级管理员开启/关闭自助申请，配置可申请范围和审批人
审批人处理员工提交的权限申请，通过或拒绝
员工查看已有权限，提交权限申请，查看申请进度

主流程闭环

管理员配置
  → 开启自助申请
  → 设置可申请范围（选择哪些角色/功能权限允许申请）
  → 指定审批人
  → 上线

员工申请
  → 登录后看到"权限申请"入口
  → 查看已有权限
  → 在可申请范围内选择需要的权限
  → 填写申请原因
  → 提交

审批处理
  → 审批人收到待处理通知
  → 查看申请内容和原因
  → 通过：系统自动授权 → 员工收到通知
  → 拒绝：填写拒绝原因 → 员工收到通知

前置配置

管理员在开启前必须完成：

  1. 勾选允许员工申请的角色或功能权限
  2. 指定至少一个审批人（可多选）

缺少任一项，系统应提示不可开启。

结果回写与记录沉淀

  • 每笔申请形成一条申请记录，包含申请人、申请内容、申请原因、审批人、审批结果、授权结果
  • 授权结果需要与权限来源模型打通——授权成功后，在权限来源中标记为"自助申请"
  • 申请记录可用于审计核验

6. 必须守住的规则和边界

不能放开的限制：

  • 可申请范围必须由管理员预设，不开放"全量权限可申请"的默认选项
  • 关闭能力后，已审批通过但尚未授权的申请仍需完成授权

必须审批的场景：

  • 所有员工提交的权限申请都必须经过审批，不存在免审批通道
  • 审批人不能是申请人本人

必须二次确认的操作：

  • 管理员关闭自助申请能力时，如存在在途申请，需二次确认

必须前置说明的信息：

  • 员工提交申请前，应清楚知道申请的权限是什么、审批通过后会获得什么
  • 员工应知道当前审批人是谁、预计处理时长（如有）

7. 主要风险与保护策略

风险影响缓解策略
可申请范围配置过宽，员工申请到不合适权限权限安全配置时提示"建议按最小必要原则配置"；审批人把关
审批人缺失（未配置/离职/出差）申请无法流转配置阶段校验至少一个审批人；提供默认兜底到超管的选项
审批通过但自动授权失败权限不生效，产生矛盾状态标记异常并通知管理员手动介入；提供重试机制
员工频繁提交重复或无效申请审批人负担提交频率限制或去重判断（可选）

8. 方案承接要求

后续 experience 阶段必须承接以下内容：

必须覆盖的角色：

  • 超级管理员（配置和控制）
  • 审批人（审批处理）
  • 员工（查看和申请）

必须闭环的主流程：

  • 管理员配置→上线→员工申请→审批→自动授权→完成通知
  • 管理员关闭→存量在途处理→下线

必须处理的异常：

  • 审批人缺失或无法处理
  • 审批通过但授权失败
  • 员工提交超出范围的申请
  • 关闭时存在在途申请

必须解释的状态：

  • 申请全生命周期状态（申请中、审批中、已通过、已拒绝、已撤销）
  • 权限的"待审批生效"状态解释

必须保护的风险：

  • 可申请范围的安全控制
  • 审批链路断裂的兜底

可作为设计建议的内容：

  • 员工端"已有权限"和"可申请权限"的信息组织方式
  • 申请记录列表的筛选和排序
  • 通知方式（应用内通知/消息/邮件）

9. 待确认问题

  1. 员工申请时按角色申请还是按功能权限点申请

影响：两种方式会导致管理端配置交互和员工端申请交互完全不同。按角色申请更简单（选角色→申请→获批后获得角色下全部权限），但灵活度低；按功能权限点申请更灵活，但配置成本和认知负担更高。
建议确认方：产品 / 业务

  1. 是否需要与审批中台打通，还是固定审批人作为长期方案

影响：固定审批人模式实现简单，适合 MVP；与审批中台打通后可以支持更复杂的审批链路（多级审批、条件路由、超时自动转交等），但会增加对接成本。
建议确认方：技术 / 产品

  1. 新来源类型在来源模型中的优先级和覆盖规则

影响：如果员工通过自助申请获得的权限与管理员直授或角色授予的权限发生范围重叠，谁覆盖谁、怎么合并展示，需要在来源模型中明确定义。
建议确认方：业务 / 技术

体验蓝图：员工自助申请权限

0. 本次关键设计判断

判断：

这次体验方案的核心不是设计一个漂亮的申请表单，而是让三类角色（管理员、审批人、员工）各自清楚自己的职责边界，并且在每个关键节点都能获得明确的系统反馈。管理端要能控得住，员工端要能看得懂，审批端要能处理得完。

主要影响：

  1. 管理员配置页需要同时承载开关、范围选择、审批人指定三项职责，信息密度较高
  2. 员工端需要建立三条信息线：我有什么、我能申请什么、我的申请到哪了
  3. 审批人的处理体验容易被忽略——审批人可能不常登录系统，需要通知触达

建议方案：

  • 管理端采用独立配置页，"开关+范围+审批人"三步完成配置
  • 员工端在权限查询结果页嵌入申请入口，降低认知切换成本
  • 审批人通过待办或通知进入审批页，审批通过后系统静默完成授权

不建议方案：

  • 不建议把管理员配置页做成弹窗或侧边栏——配置项较多，独立页面更清晰
  • 不建议员工端独立做一个"权限申请中心"——与现有"我的权限"查询入口聚合更自然

关键待确认：

  1. 员工申请时按角色还是按功能权限点——直接影响申请页面的交互形式

1. 旅程图

超级管理员
识别需要开放自助申请→开启配置（设范围、定审批人）→确认能力上线
员工
发现缺少权限→查看已有权限确认确实没有→在可申请范围内选择→填写理由提交→等待审批→收到结果通知
审批人
收到待审批通知→查看申请内容→判断并决定（通过/拒绝）→确认处理完成

旅程缺口

  • 员工"发现缺少权限"的触发场景不明确——是主动查看还是使用受阻后才知道需要申请
  • 缺少"审批人超时未处理"的升级机制定义
  • 缺少"授权失败"后员工和审批人如何获知结果的通知规则

2. 交互流程总览

超级管理员
进入管理后台配置页→开启自助申请开关→选择可申请范围（角色/功能权限）→指定审批人→保存生效
员工
进入权限查询页面→查看已有权限→切换到"可申请权限"列表→选择需要的权限→填写申请原因→提交申请→在申请记录中查看进度→收到结果通知
审批人
收到待审批通知消息→进入审批列表→查看申请详情→通过或拒绝→确认处理结果

异常流程重点：

  • 管理员开启时未指定审批人 → 系统提示并阻止开启
  • 员工提交的申请审批人不复存在（已离职/已变更）→ 申请卡住，需要兜底
  • 审批通过后自动授权失败 → 授权状态异常，管理员介入
  • 管理员关闭能力时存在在途申请 → 二次确认后继续关闭

3. 主交互流程

节点 3.1：管理员开启自助申请配置

用户动作：

进入权限管理 → 找到"自助申请配置"入口 → 开启开关

系统反馈：

进入配置页，展示配置表单：可申请范围选择区（树形多选：按角色分类/按功能权限分类）+ 审批人指定区（人员选择器）

需要前置解释的信息：

  • 开启后员工将在工作台看到"权限申请"入口
  • 可申请范围建议按最小必要原则配置
  • 未指定审批人时无法开启

建议文案：

"开启后，员工可以按配置范围申请权限，审批通过后系统自动授权。"
"可申请范围决定员工能申请哪些权限，建议按最小必要原则配置。"

下一步：

配置完成后保存 → 系统提示"自助申请已开启" → 能力上线

节点 3.2：员工提交权限申请

用户动作：

进入"我的权限"页面 → 查看已有权限 → 切换到"可申请权限"列表 → 浏览或搜索可申请的权限 → 选择目标权限 → 填写申请原因 → 点击提交

系统反馈：

提交成功 → 状态变为"审批中" → 进入申请记录列表

需要前置解释的信息：

  • 可申请范围由管理员配置，不在范围内的权限无法申请
  • 审批通过后才能获得权限，审批人由管理员指定
  • 建议填写真实的申请原因，有助于审批人判断

建议文案：

申请按钮："提交申请"
提交成功："申请已提交，等待审批人处理"
列表空态："当前没有可申请的权限，如需其他权限请联系管理员"

下一步：

等待审批 → 在申请记录中查看进度

节点 3.3：审批人处理申请

用户动作：

收到待审批通知 → 进入审批列表（或直接通过通知进入申请详情）→ 查看申请内容和原因 → 点击"通过"或"拒绝" → 如拒绝需填写原因

系统反馈：

  • 通过：系统自动执行授权 → 授权成功后更新状态为"已通过" → 通知员工
  • 拒绝：状态更新为"已拒绝" + 拒绝原因 → 通知员工

需要前置解释的信息：

  • 审批通过后系统自动完成授权，不需要审批人手动配置
  • 如果授权失败，审批人会收到异常通知

建议文案：

审批页标题："权限申请审批"
通过按钮："同意授权"
拒绝按钮："拒绝"
拒绝原因提示："请说明拒绝原因，申请人将收到反馈"

下一步：

处理完成后返回审批列表

节点 3.4：管理员关闭自助申请

用户动作：

进入自助申请配置页 → 关闭开关

系统反馈：

检测是否存在在途申请 → 如有：弹出二次确认弹窗"当前有 X 笔审批中的申请，关闭后新申请将无法提交，已在审批中的申请将继续完成。确认关闭？" → 确认后能力下线

需要前置解释的信息：

  • 关闭后员工端不再显示申请入口
  • 已在审批中的申请不受影响

建议文案：

"关闭后，员工将无法提交新的权限申请。已在审批中的申请将继续正常处理。"
二次确认弹窗标题："确认关闭自助申请？"

下一步：

能力下线 → 员工端入口消失

4. 次交互流程

节点 4.1：员工查看已有权限

用户动作：

进入"我的权限"页面 → 查看按应用或角色聚合的权限清单

系统反馈：

展示当前已生效的权限列表，包含来源说明（管理员授予/角色分配/自助申请获得）

下一步：

如需更多权限，切换到申请入口

节点 4.2：员工撤销申请

用户动作：

在申请记录中找到审批中的申请 → 点击"撤销申请"

系统反馈：

确认后状态更新为"已撤销" → 通知审批人
**前置条件：** 仅限状态为"审批中"的申请

建议文案：

撤销确认："确定撤销该申请？撤销后审批人将收到取消通知。"

节点 4.3：员工查看申请记录

用户动作：

进入申请记录列表 → 按状态筛选或搜索 → 点击查看详情

系统反馈：

展示申请内容、当前状态、审批意见（如有）、处理时间线

下一步：

被拒绝后可重新申请或联系管理员

5. 异常与阻断流程

异常 5.1：审批人缺失

发生时机： 管理员开启配置时 / 申请流转时
触发条件： 管理员未指定审批人；或指定的审批人已离职/不可用
判断依据： business 规则——审批人由管理员配置时指定
反馈形式： 配置阶段——字段提示；运行时——申请卡住
系统反馈： 配置时提示"请至少指定一位审批人"并阻止开启；运行时系统标记"审批人不可用"并通知超管
用户下一步： 管理员重新指定审批人

异常 5.2：审批通过但授权失败

发生时机： 审批人点击"通过"后
触发条件： 自动授权接口异常或权限冲突
判断依据： business 风险策略
反馈形式： 系统异常通知
系统反馈： 授权失败 → 申请状态标记为"已通过（授权异常）" → 通知管理员和审批人
用户下一步： 管理员手动介入或等待系统重试

异常 5.3：员工申请超出可申请范围

发生时机： 员工提交申请时
触发条件： 员工选择的权限不在管理员配置的可申请范围内
判断依据： business 规则——可申请范围由管理员预设
反馈形式： 提交时拦截提示
系统反馈： "该权限不在可申请范围内，如需申请请联系管理员"
用户下一步： 联系管理员或选择范围内的其他权限

异常 5.4：关闭能力时存在在途申请

发生时机： 管理员关闭自助申请能力时
触发条件： 存在状态为"审批中"的申请
判断依据： business 规则——关闭时关新不关旧
反馈形式： 二次确认弹窗
系统反馈： 弹窗列出在途申请数量，确认后方可关闭
用户下一步： 确认关闭（在途继续处理）或取消操作

8. 待确认问题

  1. 员工申请时按角色申请还是按功能权限点申请

影响：两种方式导致申请页面交互完全不同。按角色申请只需选择角色→提交；按功能权限点申请需要提供可搜索的权限列表+多选。同时也影响管理端的范围配置交互。
建议确认方：产品 / 设计

  1. "我的权限"页面的入口位置

影响：员工从哪里进入"我的权限"页面——工作台、应用内、个人中心？这决定了是否需要在现有导航中新增入口或扩展现有入口。
建议确认方：产品 / 设计

  1. 审批人通知方式

影响：审批人如何收到待审批通知——应用内消息、短信、邮件、企业微信/钉钉？不通知到位可能导致申请长期无人处理。
建议确认方：产品 / 技术

  1. 员工端是否需要移动端适配

影响：如果员工主要通过移动端操作，申请页面的交互和布局需要单独设计。
建议确认方：产品 / 设计
