# 员工自助申请权限

- Project ID: self-permission-apply
- Task Name: 员工自助申请权限
- Domain: 权限管理

## 需求背景

目前企业员工的权限分配主要由权限管理员或超级管理员集中处理。在中大型企业中，员工数量多、人员流动频繁，权限新增、变更、核对的工作量较大。部分企业的超级管理员可能是老板本人，业务人员或经办人员需要权限时，需要私下找老板或管理员处理，沟通成本高，授权时效不稳定。

希望通过支持员工自助查看和申请权限，把部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对申请范围和审批流程的控制。

## 目标

本次希望新增一种"员工自助申请权限"的能力，使员工可以：

- 查看自己当前拥有的权限
- 主动申请所需权限
- 通过审批后自动获得权限
- 查看自己的申请记录和审批状态

同时，管理员可以控制：

- 是否允许员工自助申请权限
- 员工可以申请哪些权限范围
- 申请提交后走什么审批流程
- 是否关闭或调整该能力

## 用户与角色

- 超级管理员 / 权限管理员：负责配置是否开启员工自助申请权限，并控制可申请范围和审批规则
- 员工：查看自己的权限，发现缺少权限时主动发起申请
- 审批人：处理员工提交的权限申请，决定是否同意授权

## 核心场景

1. 管理员配置自助申请权限：开启模式、限制可申请范围、设置审批流程
2. 员工查看自己的权限：知道自己当前有哪些功能权限、数据权限或角色
3. 员工申请权限：发现自己缺少某项权限后，提交申请说明原因
4. 审批人处理申请：查看申请内容和原因，决定同意或拒绝，审批通过后系统自动授权
5. 管理员关闭自助申请能力：关闭能力时需处理在途申请

## 功能范围

- 管理员开启或关闭员工自助申请权限的能力
- 员工查看自己已有权限
- 员工发起权限申请的入口和表单
- 审批人审批申请权限的流程
- 员工查看申请权限的记录和申请状态
- 记录模式开启、关闭、申请、审批等关键操作
- 数据埋点，统计功能使用情况和转化情况

## 关键业务约束

1. 员工申请权限是术语权限体系的一部分
2. 权限申请范围需要管控
3. 申请权限必须要审批才可以生效
4. 要明确员工可申请和可见的范围
5. 服务人员是否可以使用该能力需要进一步确认，当前倾向为不开放
6. 该能力可能与已有权限治理模式存在互斥关系，需要明确规则

## 初步业务规则

### 管理端
- 只有具备最高权限的管理员可以开启或关闭自助申请权限能力
- 开启前需要设置可申请范围和审批方式
- 可申请范围可以按角色或功能权限配置，但具体采用哪种方式需要进一步设计
- 管理员应可以后续调整配置
- 管理员关闭能力时需要明确在途申请和已授权结果的处理

## 已知风险

- 培训成本：把申请能力开放给员工，需要教会更多人使用
- 权限安全风险：可申请范围设置过宽可能导致员工申请到不合适的权限
- 审批流程风险：默认审批人不存在或审批链路配置错误可能导致申请无法流转
- 模式互斥风险：与已有权限治理模式可能产生冲突

## 不明确事项

1. 自助申请权限模式与现有权限治理模式是否互斥？互斥范围是什么？
2. 员工可以申请角色、功能权限，还是两者都支持？
3. 哪些角色或权限不能被员工申请？
4. 是否需要支持"敏感角色"或"敏感权限"排除？
5. 申请权限时是否需要支持上传附件？
6. 员工申请权限时是否可以选择数据权限范围？
7. 审批人默认是谁？组织负责人、管理员，还是自定义审批流程？
8. 审批人不存在或审批流程异常时如何处理？
9. 审批中的申请是否可以撤销？
10. 管理员关闭能力后，已通过申请获得的权限是否保留？
11. 管理员关闭能力时，正在审批中的申请如何处理？
12. 员工端入口应该放在哪里更合适？
13. 是否需要给员工展示权限来源？
14. 是否需要给管理员提供申请统计或使用情况？
15. 服务人员是否完全不支持该能力？
