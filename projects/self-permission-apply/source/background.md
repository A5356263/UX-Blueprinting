# Background

## 正式任务分析收敛总结

### 1. 核心判断

这是一个权限治理模式新增，不是局部功能新增。自助申请的本质是把权限判断权从超管转移到审批人，需要配套的审批人判断力保障、自动生效可靠性和出错可追溯能力。

### 2. Step 1 确认要点

**问题定性**：这是一份带解决方案的需求文档。问题（管理员工作量大）被简要提及，但"为什么自助申请是合适的解法"没有被论证。

**三类角色的利益差异**：
- 超管：想要管得过来（可控制范围、可追溯）
- 员工：想要不用求人（申请流程清晰、时效可知）
- 审批人：夹在中间（需要足够的判断依据）

**方案成立的前提**：不在"员工会不会填"，而在审批人能否判断申请是否合理、自动生效是否可靠、出错能否追溯。

### 3. Step 2 确认要点

#### 复杂度分析结论：高复杂度

**底层业务改动**：
- 改变生效机制：管理员直授 → 审批通过后自动生效
- 扩展来源模型：新增「自助申请」作为权限来源类型
- 新增状态机：自助申请权限模式状态（开启/关闭/在途）+ 申请单状态（审批中/通过/拒绝/撤销）
- 新增业务规则：范围规则、互斥规则、特殊校验规则（资金用户、子管理员等）

**体验设计压力**：
- 3个角色（超管、员工、审批人）
- 异常分支较多（模式互斥校验、在途流程校验、多个特殊校验点）
- 概念边界模糊（角色 vs 功能权限、可申请范围 vs 已有权限）

#### 5 Why 根因收敛

核心问题链：
1. 超管授权工作量大 → 因为权限变更汇集到一人
2. 不能由他人分担 → 因为子管理员配置门槛高，放权缺安全机制
3. 放权怕失控 → 因为缺审计链和回收保障
4. 本质矛盾：审批人比超管更了解业务上下文，但不如超管了解权限含义和风险

**根因**：自助申请成立的真正前提是审批人具备足够的判断依据和风险意识，且出错后有追溯和补救能力。

### 4. 已确认的业务边界

- 与「双管理员互审模式」「权限变更审批模式」互斥，不可同时开启
- 申请方式二选一：申请角色 / 申请功能权限（由超管在开启时选定，不可并行）
- 角色范围：已启用+已停用角色；可限制为全部或部分角色
- 应用范围：已添加的应用（已启用+已停用）；可限制为全部或部分应用
- 后续新增角色/应用默认自动加入可申请范围（可关闭）
- 资金用户校验、子管理员模式校验、特殊身份默认权限、实名要求
- 有在途流程时不能关闭模式
- 模式开启后变为不可编辑状态，编辑需进入编辑态

### 5. 关键状态流转

**自助申请权限模式状态**：未开启 → 开启（不可编辑） → 编辑中 → 关闭
- 关闭条件：无在途申请流程

**申请单生命周期**：草稿（可选） → 审批中 → 已通过 / 已拒绝 / 已撤销
- 审批通过后：系统自动分配权限
- 审批拒绝后：员工收到通知
- 审批中可撤销

### 6. 依赖与前置条件

- 依赖流程引擎 / OA审批中台（审批后自动分配需对接）
- 依赖现有权限判断链路的能力扩展
- 依赖现有功能权限设置组件的复用

### 7. GAP / 待确认

- **[GAP] 审批人判断力**：组织负责人看到的申请详情是否足够支撑判断？当前文档只覆盖了申请原因+角色名，未覆盖审批人侧的信息呈现设计
- **[GAP] 自动生效异常闭环**：审批通过但授权失败时的补偿机制未定义（重试？人工介入？通知谁？）
- **[GAP] 回收路径**：员工通过自助申请获得的权限，超管能否手动回收？回收后对员工的可解释性
- **[GAP] 申请方式选择依据**：超管在开启时选"申请角色"还是"申请功能权限"的依据是什么？切换成本如何
- **[GAP] 数据权限**：当前文档提到"申请功能权限时默认申请所有数据权限"，但未覆盖数据权限的粒度和后续扩展可能性
