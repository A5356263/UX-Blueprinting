# 业务蓝图

> 基于 facts.md 的事实梳理，结合权限管理域和审批管理域的业务知识，输出自助申请权限功能的完整业务判断。

## 0. 本次关键设计判断

**判断：**

这是一个成立且值得做的需求。在企业客户中，权限管理员处理压力大、沟通链路长的问题是真实痛点。自助申请权限可以将部分权限分配工作从管理员侧分散到员工侧，同时保留管理员的控制权。但这不是一个纯粹的员工端功能，它依赖权限管理域的治理模式和审批管理域的能力支撑，需要作为跨域能力来设计，不能简化成仅员工侧功能。

**主要影响：**

1. 新增"自助申请模式"作为权限治理的第四种模式，与双管理员模式、权限变更审批模式、子管理员模式并列
2. 改变权限生效链路：从"管理员直接授予"变为"员工申请→审批→自动生效"
3. 需要三端联动：管理后台（配置）、员工端（申请）、审批端（处理）

**建议方案：**

- 在现有"权限管理模式"配置区新增"自助申请模式"开关和配置项
- 可申请范围支持角色和功能权限两种粒度，管理员分别配置
- 审批流程复用现有 OA 审批引擎，默认审批人为组织架构负责人
- 审批通过后系统自动完成授权，权限来源标记为"自助申请"

**不建议方案：**

- 不建议做成独立于现有权限体系之外的"临时授权"——必须与现有权限模型的来源、状态、查询和审计体系一致
- 不建议绕过审批引擎直接授权——必须保留审批环节以保障权限安全
- 不建议初期就支持数据权限粒度的申请——数据权限的条件组模型复杂度高，建议后续迭代

**关键待确认：**

1. 自助申请模式与双管理员模式的具体互斥规则
2. 服务人员是否完全不支持该能力
3. 员工申请时是否需要支持上传附件

## 1. 一句话结论

可以做，建议作为权限治理模式的扩展来实现。这不是单纯的员工端功能，而是权限管理域新增一种治理模式，同时联动审批管理域和员工端入口。当前信息足以支撑完整业务蓝图，但存在 3 个需要产品确认的关键边界。

## 2. 需求是否成立

### 解决什么问题

- 权限管理员处理压力大：中大型企业员工多、权限变更频繁，集中管理模式下管理员负担重
- 沟通成本高：员工需要权限时需要私下找管理员，时效不稳定
- 缺乏自助渠道：员工不知道自己有什么权限，需要什么权限，只能反复询问

### 影响哪些角色

- 权限管理员：从"每次都要我来操作"变为"我只需要配置规则和监控"
- 员工：从"被动等待"变为"主动申请，透明可追踪"
- 审批人：新增处理申请的职责，但审批流程由管理员配置，审批人只需做业务判断

### 判断：成立

需求背景真实，价值方向正确。现有权限管理域和审批管理域已有成熟能力支撑，不是从零建设的空中楼阁。但存在两个前提：
1. 不是所有企业都适用——对员工数量少、权限变更不频繁的小企业价值有限
2. 需要培训成本——员工需要理解"权限可以自己申请"这件事

这两个前提不影响需求成立，但会影响优先级和推广策略。

## 3. 值不值得做

### 收益

- 权限管理员效率提升：从逐人处理转向一次性配置规则，长期减少重复劳动
- 员工体验提升：透明化权限信息，减少向管理员的反复询问
- 授权流程规范化：所有申请经过审批，留下完整记录，满足审计需求
- 需求文档提到的价值指标：至少推动 3 家客户使用

### 成本

- 开发成本：涉及权限管理域（新增治理模式）、审批管理域（配置审批流关联）、员工端（新入口和页面），属于中等偏上投入
- 培训成本：管理员需要理解如何配置可申请范围和审批流程；员工需要知道如何发起申请
- 认知负担：员工需要理解"权限"的概念，对非技术用户可能存在理解门槛

### 系统代价

- 权限来源模型需要扩展：审批通过后的授权需要标记来源路径
- 治理模式互斥逻辑需要开发和维护
- 审批流程与权限治理的联动增加了链路复杂度

### 综合判断

值得做。收益集中在"减少管理员压力"和"规范化授权流程"两个维度，与现有权限体系的治理方向一致。成本主要在初始开发和用户教育，长期看是正向投入。

## 4. 应该做成什么能力形态

### 方案 A（推荐）：作为权限治理模式扩展

在现有"权限管理模式"配置区新增"自助申请模式"，与双管理员模式、权限变更审批模式、子管理员模式同级。开启后激活员工端申请入口和配置项。

**优点**：
- 与现有治理模式体系一致，用户已经在"权限管理模式"中理解和使用过类似配置
- 可以清晰处理模式互斥逻辑
- 配置入口集中，管理员不需要在多个模块间跳转

**缺点**：
- 权限管理模式当前只在管理后台，感知度可能不如直接在员工端配置
- 需要先在管理后台完成配置，员工端才能使用

### 方案 B：在员工端设置独立申请页面

在员工端工作台或设置页新增"权限申请"独立入口，管理端只在后台简单开关。

**优点**：
- 员工端体验更直接
- 管理端的配置成本更低

**缺点**：
- 缺乏与现有治理模式的联动
- 可申请范围、敏感权限排除等配置无法集中管理
- 无法处理模式互斥逻辑
- 与现有权限管理体系的割裂，增加后续维护成本

### 方案 C：不做产品化，仅作为管理员的代办功能

管理员在后台配置"允许员工发起申请"，由管理员自己处理所有申请。

**优点**：
- 实现成本最低

**缺点**：
- 没有解决"减轻管理员压力"的核心问题
- 管理员仍然需要逐个处理，相当于把线下沟通变成了线上转达

### 推荐

**方案 A**，理由：与现有权限治理体系一致，可扩展、可维护、可解释。方案 B 虽然员工端体验更好，但会破坏治理模式的统一性。方案 C 没解决核心问题。

## 5. 推荐业务方案

### 角色与职责

| 角色 | 职责 |
|------|------|
| 超级管理员/权限管理员 | 开启/关闭自助申请模式、配置可申请范围和审批流程、配置敏感权限排除列表 |
| 员工 | 查看已有权限、发起权限申请、查看申请记录和状态 |
| 审批人 | 接收审批通知、查看申请详情、同意/拒绝申请 |

### 主流程闭环

```
管理员开启自助申请模式
    ↓
管理员配置可申请范围（角色/功能权限）
    ↓
管理员配置审批流程（默认组织架构负责人/自定义）
    ↓
员工查看权限 → 发现缺少权限 → 选择要申请的权限 → 填写申请原因 → 提交
    ↓
审批人收到通知 → 查看申请详情 → 同意/拒绝
    ↓
[同意] 系统自动完成授权 → 员工获得权限 → 申请状态更新为"已通过"
[拒绝] 申请状态更新为"已拒绝" → 员工可查看拒绝原因
```

### 前置配置

管理员开启自助申请模式前必须完成：
1. 设置可申请范围（至少选择一种：角色、功能权限）
2. 设置审批流程（可使用默认审批流或自定义）

如果未完成配置，开关不可用。

### 结果回写与记录沉淀

- 审批通过后，系统自动执行授权操作，权限来源记录为"自助申请"
- 所有申请记录在员工端可见（申请时间、内容、状态、审批意见）
- 建议在管理后台提供申请统计（申请量、通过率、热门申请等），非 MVP 必选项

## 6. 必须守住的规则和边界

### 不能放开的限制

- **范围限制**：员工只能申请管理员已配置为可申请的权限，不在范围内的权限不可见
- **敏感权限排除**：管理员配置的敏感权限不可申请，列表外的权限也受默认排除规则限制（超管角色、全局配置权限、财务/税务敏感权限）
- **服务人员排除**：需求文档倾向不开放，服务人员不应看到申请入口
- **审批不可跳过**：所有权限申请必须经过审批才能生效

### 必须审批的场景

- 所有自助申请提交后必须经过审批人审批
- 审批通过后系统自动授权，无需二次确认
- 审批拒绝后需告知员工拒绝原因

### 必须二次确认的操作

- 管理员关闭自助申请模式时，如果有正在审批中的申请，需要二次确认
- 管理员修改可申请范围后，建议提示已有申请不受影响

### 必须前置说明的信息

- 员工提交申请前需告知：申请需要审批、审批通过后才能使用、审批需要一定时间
- 员工查看权限时需说明：展示的是当前已有权限，未涵盖可申请但尚未申请的权限

## 7. 主要风险与保护策略

### R1：可申请范围设置过宽

**风险**：管理员配置时如果不谨慎，可能把敏感权限开放给员工申请

**影响**：员工可能申请到不合适或不应拥有的权限

**缓解**：
- 默认敏感权限排除列表（超管角色、全局配置权限、财务/税务敏感权限）
- 新建配置时建议提供"安全默认值"
- 审批环节作为第二道防线

### R2：审批人配置不完整

**风险**：默认审批人（组织架构负责人）未配置，或自定义审批流程存在断点

**影响**：员工申请无法流转，申请被卡住

**缓解**：
- 开启前校验审批人是否有效
- 无可用审批人时阻止提交并给出明确提示
- 审批超时策略（来自 OA 审批引擎的能力）

### R3：模式互斥导致认知混乱

**风险**：双管理员模式和自助申请模式同时开启时，管理员不清楚哪个规则优先

**影响**：权限管理出现冲突或不可预期的行为

**缓解**：
- 设置明确的互斥规则（不能同时开启，或限制双管理员模式下自助申请范围受限）
- 启动冲突检测，配置时即提示

## 8. 方案承接要求

以下为后续体验设计阶段必须承接的内容：

### 必须覆盖的角色

- 管理员端配置页面
- 员工端权限查看和申请页面
- 审批端申请处理页面

### 必须闭环的主流程

- 管理员开启配置→设置范围→设置审批流→激活
- 员工查权限→选权限→填原因→提交→看状态
- 审批人收通知→查看→同意/拒绝

### 必须处理的异常

- E1：审批人不存在 / 未配置
- E2：关闭模式时存在进行中的申请
- E3：申请敏感权限（在列表中不可见）
- E4：模式冲突检测和提示
- E5：审批超时未处理

### 必须解释的状态

- 申请：审批中、已通过、已拒绝
- 权限：已生效、审批中（通过来源标记区分）

### 必须保护的风险

- R1 范围过宽风险：配置页需展示安全默认值
- R2 审批人配置风险：开启前校验

### 可作为设计建议的内容

- 员工端入口位置建议：工作台、个人中心或权限管理页
- 权限来源展示方案
- 申请统计管理端看板（非 MVP）

## 9. 待确认问题

1. **自助申请模式与双管理员模式的互斥规则**

   影响：影响配置页面的互斥提示设计和功能开关逻辑。建议互斥——开启双管理员模式时不能开启自助申请模式，反之亦然。如果允许共存，需要定义冲突时谁的规则优先。

   建议确认方：产品 / 业务

2. **服务人员是否完全不支持自助申请**

   影响：影响员工身份的判定逻辑和入口可见性控制。如果完全不支持，需要在员工端根据身份隐藏入口；如果部分支持，需要定义支持范围。

   建议确认方：产品 / 业务

3. **员工申请时是否需要支持上传附件**

   影响：影响申请表单字段设计和审批详情页展示。如支持，需要确定上传文件类型和大小限制。

   建议确认方：产品

4. **员工提交申请后是否支持撤销**

   影响：影响申请状态机和审批人处理逻辑。如支持撤销，需要定义撤销条件（仅在审批人处理前可撤销）。

   建议确认方：产品

5. **员工角色变更（调岗）后，通过自助申请获得的权限如何处理**

   影响：影响权限生命周期管理。建议作为后续迭代，MVP 阶段可先记录但不做自动回收。

   建议确认方：产品 / 业务

6. **是否需要提供管理员端的使用统计**

   影响：非 MVP 必选，但影响后续迭代规划。如需要，建议统计申请量、通过率、热门申请权限等指标。

   建议确认方：产品

7. **员工端入口位置**

   影响：影响导航设计和技术方案。建议选项：工作台快捷入口、个人中心权限管理、独立"权限申请"模块。

   建议确认方：产品 / 设计
