# 业务蓝图

> 本蓝图基于 `workspace/facts.md` 中澄清的需求事实，结合已有权限体系和审批管理的业务知识，独立完成业务判断。需求文档和业务知识作为证据材料，不代表最终结论。

## 0. 本次关键设计判断

**判断：**

需求成立。这不是一个局部页面调整，而是改变了权限获得的基本方式——在管理员分配之外新增了员工主动申请的路径。需要先讲清业务规则和边界，再做体验方案。

**主要影响：**

1. 权限获得方式从「管理员单向分配」扩展为「管理员分配 + 员工申请」双路径，需要明确两条路径的优先级和互不干扰规则
2. 管理员需要新增一个能力开关和两项配置（可申请角色范围、审批流程绑定），这是管理员权限治理面的新增负担
3. 员工首次面对「看懂自己有什么权限、判断自己缺什么、主动发起申请」的全新认知链路，体验承接压力大

**建议方案：**

- 以角色为申请单位，构建在已有角色体系和审批体系之上，不另起炉灶
- 管理员控制面收敛在现有权限管理模式页中，不新增独立配置入口
- 关闭能力时不回收已授权限，审批中申请统一退回，降低企业管理风险顾虑
- 一期只覆盖员工角色，不做服务人员扩展

**不建议方案：**

- 不建议让员工直接申请功能权限或自选数据权限范围——认知门槛太高，管理员的配置和维护成本也会成倍增加
- 不建议自建审批引擎——已有审批管理能力完善，复用即可，重复建设只会增加系统复杂度

**关键待确认：**

1. 员工端入口放在工作台还是个人信息区，影响首页信息架构和入口分发策略
2. 「敏感角色」排除的具体名单范围和判断标准

> 更多待确认问题详见 `## 9. 待确认问题`。

## 1. 一句话结论

能做。建议作为已有权限体系的扩展能力构建：以角色为申请单位、复用已有审批引擎、管理员控制开关和范围、关闭时不回收已授权限。核心判断是：这件事的价值不在于「又做了一种授权方式」，而在于填补了「管理员预料不到的个体权限需求」这个真实缺口。

## 2. 需求是否成立

### 解决的问题

企业权限由管理员集中分配。现有三条权限获得路径——管理员直授、角色批量分发、角色自动授权规则——的发起人和维护人始终是管理员。角色自动授权规则可以处理可预测的规则化分发（按部门、职务、成员组匹配），但覆盖不了跨部门协作、临时项目组、特殊报表权限等「管理员预料不到但员工自己知道缺什么」的场景。

这些场景下员工只能线下找人沟通，在中大型企业里沟通成本高、授权时效不稳定。部分企业超管就是老板本人，业务人员频繁找老板要权限既不现实也不高效。

### 是否成立

**成立。** 这个需求解决的是一个真实问题，不是伪需求。

在以下前提下需求不成立，但当前这些前提都不成立：

- 如果企业中所有权限需求都可以被自动授权规则预测和覆盖，则不需要员工自助申请。但在实际业务中，临时协作、跨部门项目、个性化报表权限等不可预测场景始终存在。
- 如果管理员可以实时响应每一个权限需求，则不需要。但在中大型企业里这不可行。

需求没有出现局部诉求扩大化的问题。文档中明确划定了一期范围——只做角色申请、不做功能权限和数据权限自选、服务人员不支持——范围控制是克制的。

### 判断依据

- 从已有权限体系的10个任务场景来看，员工在所有现有场景中都是被动接收方，确实缺少主动发起路径
- 竞品参考中金蝶已有相近功能方向，说明行业中存在同类需求
- 初步价值指标「至少3家客户使用」说明需求方对价值验证本身也持谨慎态度，没有夸大

## 3. 值不值得做

### 收益

- **减少线下沟通成本**：员工不需要每次缺权限都找管理员，从「找人」变成「走流程」
- **提升授权时效**：审批流程标准化后，授权速度不再取决于管理员个人响应时间
- **权限需求可见化**：申请记录本身就是一份「员工实际需要什么权限」的数据来源，后续可以用来优化角色设计
- **管理员减负**：把不可预测的零散权限需求从管理员手动操作中剥离出来

### 系统代价

- **配置面增加**：管理员需要在每个角色上维护一个「允许员工申请」开关，这是一个新增的管理负担。角色数量越多，维护成本越高
- **审批链路叠加**：新增一种审批场景类型，审批人需要理解「权限申请」和「其他审批」的区别，增加认知负担
- **权限来源复杂度**：权限来源从两类（直授、角色授予）增加到三类（直授、角色授予、自助申请），查询排障和审计时需要区分，增加系统解释成本
- **关闭语义的边界处理**：「关闭不回收」虽然降低了企业顾虑，但也意味着关闭后的权限残留需要单独治理

### 综合判断

**值得做。** 收益集中在解决真实痛点，系统代价虽然存在但可控。最大的代价——权限来源复杂度增加——是「员工能看到来源」这个正向体验的自然代价，不是无谓的复杂度。配置面增加可以通过好的默认值（全部角色默认不可申请）和批量操作来缓解。

## 4. 应该做成什么能力形态

比较三种路径：

### 路径A：独立功能模块

在权限管理之外新建一个独立的自助申请模块，包含自己的配置页、申请页、审批页和记录页。

- 优点：隔离性好，不影响现有权限管理
- 缺点：和已有权限体系割裂，角色数据需要同步，权限来源需要跨模块解释，员工在两个地方看权限。建设成本高、后续维护成本也高

### 路径B：扩展现有权限治理模式（推荐）

在已有权限管理模式页中新增「员工自助申请」开关和配套配置。员工端在现有权限视图上扩展申请入口和记录区。审批侧复用已有审批管理能力。

- 优点：构建在已有体系之上，不引入新的模型隔离；角色、权限、来源、审计等能力直接复用；管理员在一个地方管理所有权限模式
- 缺点：权限管理模式页的信息密度进一步增加，需要做好信息层级

### 路径C：暂不产品化，先做审批流程模板

只提供一个审批流程模板，管理员如果需要让员工申请权限，自己配置审批流程并结合角色自动授权规则模拟。

- 优点：零开发成本
- 缺点：解决不了核心痛点——员工没有发起入口，管理员仍然需要手动维护每个角色的适用范围。本质上是用旧工具拼凑新场景

### 推荐

**路径B：扩展现有权限治理模式。** 这是唯一能在合理成本内解决核心痛点的路径。构建在已有体系之上，避免重复建设，同时保证管理员在统一的地方管理所有权限模式。

## 5. 推荐业务方案

### 角色与职责

**超级管理员/权限管理员：**

- 在权限管理模式页中开启或关闭「员工自助申请权限」能力
- 在角色管理中标记每个角色是否允许员工申请（默认关闭）
- 绑定审批流程（从已有审批流程中选择或新建）
- 查看申请记录和审计日志

**员工：**

- 在「我的权限」页面查看自己当前拥有的所有权限及每条权限的来源（角色自带 / 管理员直授 / 自助申请）
- 在可申请角色列表中看到管理员已标记为可申请、且自己尚未拥有的角色
- 选择一个角色、填写申请原因、提交申请
- 查看自己所有申请的状态（审批中 / 已通过 / 已拒绝 / 已撤销 / 已退回）
- 撤销状态为审批中的申请

**审批人：**

- 在审批待办中看到权限申请，包含申请人、申请角色、角色包含的权限说明、申请原因
- 同意或拒绝
- 审批通过后，系统自动将对应角色授予申请人

### 主流程闭环

完整流程分为四个阶段：

**第一阶段：管理员开启能力**

1. 管理员进入权限管理模式页
2. 开启「员工自助申请权限」
3. 系统检查：是否已有审批流程可用。若无，提示先配置审批流程
4. 管理员进入角色管理页，逐个标记「允许员工申请」的角色。系统预置拦截：超级管理员角色、含删除/批量操作/财务数据等高危功能点的角色不可标记
5. 管理员在自助申请设置中绑定审批流程（默认建议直属上级单级审批）
6. 能力生效，员工端出现申请入口

**第二阶段：员工申请**

1. 员工进入「我的权限」页面，查看已有权限及来源
2. 点击「申请权限」，看到可申请角色列表
3. 选择一个角色，查看角色说明（包含哪些功能权限）
4. 填写申请原因，提交申请
5. 申请进入审批流程，状态变为「审批中」

**第三阶段：审批与授权**

1. 审批人收到待办
2. 查看申请详情：申请人、申请角色、角色权限说明、申请原因
3. 同意 → 系统自动将角色授予申请人，权限即刻生效，申请状态变为「已通过」
4. 拒绝 → 申请状态变为「已拒绝」，流程结束

**第四阶段：员工查看结果**

1. 员工在「我的申请」中看到状态更新
2. 已通过：在「我的权限」中可以看到新获得的角色，来源标注为「自助申请」
3. 已拒绝：可查看拒绝原因，可重新发起申请

### 前置配置

管理员在开启能力前必须完成：

- 至少标记一个角色为「允许员工申请」
- 绑定一个有效的审批流程

两项未完成时，系统不允开启，并提示缺失项。

### 结果回写与记录沉淀

- **授权记录**：审批通过后自动授权，记录到审计日志（谁、对谁、授予什么角色、来源为自助申请、关联申请单编号、操作时间）
- **申请记录**：每笔申请全程留痕，包括提交时间、审批人、审批时间、审批结果、授权结果
- **操作日志**：能力开启/关闭、角色标记变更均记录到操作日志

## 6. 必须守住的规则和边界

### 不能放开的限制

1. **敏感角色不可申请**：超管角色、含删除/批量操作/财务数据等高危功能点的角色，系统预置拦截，不可标记为可申请。排除名单需由产品和安全方确认
2. **审批必须存在**：开启能力前必须绑定审批流程。若审批流程后续被删除，能力自动关闭，但已授权限不回收
3. **员工只能申请角色，不能直接申请功能权限或选择数据权限范围**：数据范围由管理员在角色中预定义，或审批通过后管理员单独补充
4. **员工只能看到和申请自己尚未拥有的角色**
5. **服务人员不可使用此能力**

### 必须审批的场景

- 所有权限申请都必须经过审批，不存在免审批通道
- 员工不能以任何方式绕过审批直接获得权限

### 必须二次确认的操作

- 管理员关闭自助申请能力：弹窗告知关闭后果（不再接受新申请、审批中申请将被退回、已授权限保留），需二次确认
- 员工撤销申请：弹窗告知撤销后不可恢复，需二次确认

### 必须前置说明的信息

- 开启能力前，向管理员说明该能力与已有权限治理模式的关系：不是互斥关系，但依赖审批流程已配置
- 员工申请前，展示角色的权限说明，让员工理解申请的是什么
- 审批人处理前，展示申请人、申请角色、角色权限详情和申请原因
- 关闭能力时，向管理员明确三种后果：新申请阻断、进行中申请退回、已授权限保留

## 7. 主要风险与保护策略

### 风险一：可申请范围设置过宽导致安全风险

- **风险**：管理员将过多角色（甚至含敏感权限的角色）标记为可申请，员工可能申请到不合适的权限
- **影响**：数据安全、功能滥用、合规风险
- **缓解**：系统预置敏感角色排除名单，阻止标记；建议在角色列表中以视觉区分「建议开放」和「需谨慎开放」的角色

### 风险二：审批流程配置错误或审批人不存在

- **风险**：审批链路配置错误导致申请无法流转，或默认审批人字段为空导致无人处理
- **影响**：申请积压、员工体验差、管理员需要手动干预
- **缓解**：开启能力时校验审批流程有效性；审批人不存在时向上查找（直属上级→部门负责人→超管兜底）；复用审批管理的超时提醒和自动升级策略

### 风险三：关闭能力时的边界处理不当

- **风险**：管理员关闭能力后发现审批中的申请不知如何处理，或担心已授权权限会成为安全隐患
- **影响**：企业不敢使用该能力，或关闭后产生遗留问题
- **缓解**：「关闭不回收」语义明确且在产品中清晰告知；审批中申请统一退回并附说明；已授权限如需回收通过现有权限工具单独操作

### 风险四：员工认知门槛和培训成本

- **风险**：员工不熟悉权限体系，不理解角色的含义，可能随意申请或不知道申请什么
- **影响**：无效申请增加审批人负担、员工体验差、培训成本上升
- **缓解**：角色需有清晰的权限说明文案；可申请列表展示角色名称和简要说明；申请时展示角色包含的具体权限

### 风险五：权限来源复杂度增加

- **风险**：权限来源从两类变成三类，员工和管理员在查权限、排故障时需要区分来源
- **影响**：查询排障效率下降、审计复杂度增加
- **缓解**：员工权限视图强制展示每条权限的来源标签；审计日志中关联申请单编号；这是正向体验的合理代价

## 8. 方案承接要求

后续体验设计阶段必须承接以下内容。

### 必须覆盖的角色

- 超级管理员/权限管理员：能力开关、角色标记、流程绑定、关闭确认
- 员工：权限查看、发起申请、申请记录、撤销申请
- 审批人：审批待办、申请详情、同意/拒绝

### 必须闭环的主流程

- 管理员开启能力 → 标记角色 → 绑定流程 → 能力生效
- 员工查看权限 → 选择角色 → 提交申请 → 等待审批
- 审批人查看申请 → 处理 → 系统自动授权或拒绝
- 员工查看结果 → 确认权限生效
- 管理员关闭能力 → 退回审批中申请 → 能力关闭

### 必须处理的异常

- 可申请列表为空（无已标记角色或员工已拥有全部）
- 提交时审批流程不可用
- 审批人不存在时的兜底流转
- 关闭能力时审批中申请被退回的通知
- 敏感角色被尝试标记时的阻断提示
- 申请时角色已被管理员直接授予（重复授权）
- 员工状态变化（离职/停用）时审批中申请的处理

### 必须解释的状态

- 申请单的每个状态（审批中、已通过、已拒绝、已撤销、已退回）及其含义
- 权限来源的三种类型（角色自带、管理员直授、自助申请）及其区别
- 能力开启和关闭对员工端的不同影响
- 审批通过后权限「即刻生效」的含义

### 必须保护的风险

- 角色权限说明不清晰导致员工误申请 → 角色列表需展示权限详情
- 关闭能力后员工的困惑 → 关闭时发送通知说明
- 申请被拒绝后的重复提交 → 可重新申请，但需提示审批结果和拒绝原因
- 管理员忘记标记角色 → 能力开启后若无可申请角色，管理员端提示

### 可作为设计建议的内容

- 员工端入口位置：建议放在工作台或个人中心，具体位置由体验阶段确定
- 角色列表的信息层级：角色名称 → 角色说明 → 包含权限数 → 可展开查看详情
- 审批人视图的信息层级：申请人信息 → 申请角色 → 角色权限详情 → 申请原因 → 操作按钮

## 9. 待确认问题

1. **敏感角色排除名单的具体范围**

   影响：决定哪些角色系统预置拦截、哪些由管理员自行判断。名单过宽增加管理员配置负担，过窄存在安全风险。
   建议确认方：产品 + 安全

2. **员工端入口位置**

   影响：决定首页信息架构、入口分发策略和员工发现路径。工作台入口曝光高但可能喧宾夺主，个人信息区入口低调但可能发现率低。
   建议确认方：产品 + 设计

3. **申请原因是否必填、字数上限**

   影响：必填可提升审批质量但增加申请阻力，字数过少可能信息不足。
   建议确认方：产品

4. **员工离职或停用时审批中申请的处理**

### 业务知识引用

以下判断使用了已装配的业务知识：

- **权限来源模型**（`21_来源模型`）：用于判断新增的「自助申请」在已有来源体系（直授、角色授予）中的位置——作为第三种权限获得路径，不改变已有来源的优先级和计算规则
- **决策链契约**（`20_决策链契约`）：用于确认 L0 可见性 → L1 功能权限 → L2 数据权限 → L3 治理与生效的层级关系在自助申请场景中仍然完整适用
- **规则契约 R-009 治理模式互斥**（`23_规则契约`）：用于判断自助申请与子管理员、双管理员等已有治理模式的关系——不互斥，但依赖权限变更审批模式的前置配置
- **规则契约 R-007 治理影响生效**（`23_规则契约`）：用于设计审批通过后自动授权、权限即刻生效的机制——审批是治理手段，不改变授予事实，但决定何时生效
- **治理状态模型**（`24_治理状态模型`）：用于设计申请单的状态机——草稿→审批中→已通过/已拒绝/已撤销→已生效，以及每个状态的 actor responsibility
- **角色边界**（`14_角色边界`）：用于确认员工在现有体系中的默认定位（被动接收方），以及自助申请对员工角色的改变
- **审批管理体系**（`审批管理/10_审批管理`）：用于确认复用已有审批能力的可行性——审批人来源、超时策略、多人审批方式均可直接复用

### 关键判断推导

- 「需求成立」的判断来自：已有任务场景中员工无主动发起路径的 gap + 不可预测权限需求的真实存在 + 竞品方向验证
- 「以角色为申请单位」的判断来自：员工认知门槛 + 管理员配置成本 + 与已有角色体系的契合度
- 「关闭不回收」的判断来自：降低企业使用顾虑 + 权限回收应通过已有工具而非能力开关
- 「路径B 扩展既有体系」的判断来自：避免重复建设 + 权限来源统一解释 + 管理面统一入口
