# 业务蓝图：员工自助申请权限

## 0. 本次关键设计判断

本次需求不是新增一个页面入口，而是在现有权限来源模型上引入一条"员工请求→审批→自动授权"的新生效链路。核心业务判断如下：

1. **这不是局部体验优化**。它改变了权限的生效方式——从仅有"管理员配置→立即/定时生效"，增加了"请求→审批→自动授权"新通路。这涉及新的业务规则（可申请范围）、新的状态（申请单流转）和新的治理关系（与现有治理模式的互斥）。
2. **权限落点已确认**：申请通过的权限走"个人直授"来源，附加"自助申请"标记，便于后续查询、排障和统一撤销。
3. **审批流应服从现有治理规则**：企业已开启双管理员或审批互审时，自助申请的审批流自动被治理覆盖，不作为独立流程运行。
4. **可申请范围按权限模板配置**：不对员工暴露单点功能权限，而是由管理员预定义具有业务意义的权限组合。

**关键待确认：** 权限模板的配置粒度（按角色映射还是按功能点组合）是影响管理员配置体验和员工理解成本的核心问题，建议在 business 阶段优先定案。更多待确认问题详见 ## 9. 待确认问题。

## 1. 一句话结论

在企业当前权限体系上增加一条员工自助申请通道——员工在管理员预先配置的权限模板范围内发起申请，通过审批后系统自动通过直授授予权限，并受现有治理规则约束。

## 2. 这件事为什么值得正式做

- **当前卡点是真实的、高频的**：中大型企业员工多、权限变更频繁，管理员（尤其是老板兼任超管的企业）被线下请求频繁打断，授权无标准流程、无记录。
- **本质上是一个流程缺失，不是页面缺失**：当前缺的不是"申请按钮"，而是"谁可以请求什么权限→经过谁审批→审批后落成什么来源"这一组规则定义。一旦这组规则定下来，后续就是三端的体验承接工作，不会反复翻盘。
- **成立的前提**：现有审批流程底层能力支持"权限申请"业务类型；权限来源写入接口支持从审批系统自动调用；治理模式覆盖规则明确。
- **什么情况下先别往下做**：如果现有审批系统不支持自定义业务类型扩展，或权限写入接口不支持外部调用，那么"自动授权"这条链路就无法走通，此时应先解决底层能力缺口，再推进方案设计。

## 3. 值不值得做

**收益：**
- 减少管理员和员工之间的线下沟通成本，授权过程标准化、可追踪
- 员工可以自助了解自己有什么权限、缺什么权限，减少反复询问
- 审批通过后自动授权，减少管理员手工配置的等待时间和出错风险
- 申请记录可审计，有利于合规追溯

**系统代价：**
- 需要在权限来源模型上附加治理修饰因子，影响现有权限查询和排障的逻辑（需要区分"管理员直授"和"自助申请获得"的权限）
- 可申请范围的配置模块需要新增，增加了管理后台的配置项
- 审批流程底层可能需要支持一种新的业务类型——"权限申请"
- 如果企业已经开启了双管理员等治理模式，需要确认审批流覆盖规则

**综合判断：** 值得做。收益集中在减少高频摩擦和标准化流程上，代价可控且不破坏现有权限模型。但三个前提条件（审批底层支持、写入接口支持、治理规则明确）必须先打通。

## 4. 应该做成什么能力形态

### 4.1 形态定位

这应该是一个"管控下的自助通道"，而不是完全开放的自助市场。关键特征：

- **管理员控制入口和范围**：不是员工想申请什么就申请什么
- **审批作为必经环节**：不绕过审批直接授权
- **治理规则覆盖**：不独立于企业现有的治理体系运行
- **员工侧做语义翻译**：不暴露权限的内部模型

### 4.2 必须包含的核心能力

| 能力 | 说明 | 优先级 |
|------|------|--------|
| 可申请范围配置 | 管理员创建权限模板并关联审批流 | P0 |
| 员工权限查看 | 员工能看到自己当前已有的权限（跨来源聚合） | P0 |
| 权限申请提交 | 员工选择模板→填写原因→提交→审批人收到任务 | P0 |
| 审批处理 | 审批人查看申请→通过（自动授权）或拒绝 | P0 |
| 能力开关 | 管理员开启/关闭自助申请入口 | P0 |
| 申请记录追踪 | 员工查看历史申请和审批状态 | P1 |
| 拒绝原因说明 | 审批人拒绝时强制填写原因，员工侧可读展示 | P1 |

### 4.3 不适合纳入本期

- 权限模板市场或跨企业共享模板
- 员工主动归还权限
- 基于角色自动推荐的权限申请

## 5. 推荐业务方案

### 5.1 权限模板：配置粒度推荐

**推荐方案：按"业务场景功能包"组合，而非直接映射角色。**

理由：
- 按角色映射：员工申请一个角色，等于同时获得角色关联的所有权限，粒度太粗，且修改角色会影响所有角色成员
- 按单点功能权限：员工选择负担重、容易选错，管理员需要逐个配置，管理成本高
- 按业务场景功能包：管理员预设若干个具有业务含义的权限组合（如"人事管理权限包"包含员工查看、编辑、导出功能），员工看到的是业务语言，不需要理解底层权限模型

功能包的技术本质是一组功能权限点的预定义集合 + 可选的数据范围约束，与角色的区别在于：功能包不作为独立的授权单元复用，每个员工申请后获得的是独立的直授记录。

### 5.2 权限落点方案

申请通过后的权限写入链路：

```
审批通过 → 系统调用个人直授的权限写入接口 → 为员工追加功能权限/数据权限
                                         → 同时写入"自助申请"修饰标记
                                         → 记录操作日志（申请人、审批人、时间、权限明细）
```

这条链路的好处：
- 不创建新的来源类型，复用个人直授通道
- 通过修饰标记来区分"管理员直授"和"自助申请获得"，便于统一查询和批量撤销
- 操作日志完整，可直接对接审计需求

### 5.3 审批流方案

**推荐方案：两级可选**

1. **默认路径**：服从现有治理规则。如果企业已开启双管理员/审批互审，自助申请的审批自动遵循这些规则
2. **独立路径**：管理员可以选择为自助申请设置独立的审批流程（不影响其他业务审批）

当治理规则与独立审批流冲突时，治理规则优先。例如：双管理员模式下，即使独立审批流只设了一个审批人，仍然需要第二人确认。

### 5.4 关闭方案

分两阶段：
1. **关闭入口**：员工端不再显示"申请"入口，"我的申请记录"仍然可查看
2. **存量处理**：进行中的申请不受影响，允许完成到终态。如需强制中止，管理员需显式确认并批量拒绝，记录操作日志

已通过的权限不自动撤销（因为权限已经在生效状态）。管理员可以在关闭后通过常规权限管理入口撤销。

## 6. 必须守住的规则和边界

### 不变规则
1. **不新增独立的第五种权限来源**。自助申请获得的权限走已有的个人直授来源，不创建新的来源类型
2. **不改变现有决策链**。可见性判断→功能权限判断→数据范围判断→治理状态判断的顺序不变
3. **不改变现有查询排障入口**。已在排障链路中的"按人查权限"逻辑需兼容新增的治理标记
4. **可申请范围不对等全量权限**。员工不能申请任何不在管理员配置范围内的权限

### 需要新增的规则
1. **申请单与权限的关联规则**：申请单关闭/撤销后，通过该申请授予的权限如何处理（默认不自动回收）
2. **权限模板的生命周期**：管理员修改或删除模板时，已提交但未审批的申请如何处理
3. **申请频次限制**：同一员工是否可以反复申请同一权限（默认应阻止重复申请）

## 7. 主要风险与保护策略

| 风险 | 描述 | 保护策略 |
|------|------|----------|
| 可申请范围过宽 | 管理员配置了过大的权限模板，员工申请后获得不应有的权限 | 默认收敛：新建模板只包含最基础权限；每次扩大模板需要管理员显式确认；审批作为二次拦截 |
| 审批流程配置错误 | 审批人不存在或链路断裂，导致申请无法流转 | 配置时校验审批人有效性；审批人离职或变更时触发告警 |
| 员工批量申请 | 员工一次性申请大量权限，审批人负担重 | 可在申请端设置单次申请上限（如最多同时申请3个模板） |
| 治理模式冲突 | 新增自助申请与现有治理规则互斥 | 治理规则优先：开启双管理员时，审批流自动遵循；模式冲突时提示管理员调整 |
| 员工不理解自己申请了什么 | 员工看到的是"人事管理权限包"但不知道具体包含什么 | 权限模板必须附带详细说明（包含的功能点和数据范围），申请前明确告知 |

## 8. 方案承接要求

以下要求直接面向 experience 阶段：

1. **员工端的权限展示必须做概念翻译**。员工看到的不应该是"功能权限：员工管理-查看、员工管理-编辑"，而应该是"你当前拥有：人事管理权限（可查看和编辑员工信息）"。翻译规则：将同一业务域的功能权限点归组展示，用业务语言描述。
2. **可申请范围的展示必须附带模板说明**。员工在选择权限模板时，必须能展开查看该模板包含的具体权限明细，避免"申请了但不知道会获得什么"。
3. **审批拒绝必须有可读的拒绝原因**。拒绝原因输入框不应只是"原因"二字，应提示审批人："请说明拒绝原因，以便员工了解为什么不通过"。
4. **审批通过后的效果必须可验证**。员工在申请记录中看到"已生效"后，应能点击查看"我现在有什么权限"，与申请前对比。
5. **审批超时需要提示**。如果审批人长时间未处理，员工端应能看到"待审批"的状态提示，并可催办（如果需要）。
6. **能力关闭时的状态说明**。如果管理员关闭了自助申请能力，员工端应显示"该功能已由管理员关闭"，而不是404或空白页。

## 9. 待确认问题

### 影响业务方案方向的问题

**1. 审批流程底层能力是否支持"权限申请"业务类型**
- 影响：如果审批系统不支持自定义业务类型，需要先扩展审批对象
- 建议确认方：工程 / 审批产品

**2. 权限写入接口是否支持从审批系统自动调用**
- 影响：如果 ACL_DIRECT 写入接口只支持管理员手动操作，需要新增自动化接口
- 建议确认方：工程

**3. 治理模式与自助申请审批流的覆盖优先级**
- 影响：影响审批流设计和管理员配置逻辑
- 建议确认方：产品策略

### 影响体验方案局部策略的问题

**4. 审批超时的阈值和处理策略**
- 影响：超时后自动退回还是自动转交，影响员工和审批人的体验
- 建议确认方：产品

**5. 员工权限列表的跨来源聚合数据源**
- 影响：影响"我当前的权限"页面的数据来源和展示方式
- 建议确认方：工程

**6. 可申请范围配置页的归属模块**
- 影响：影响管理员发现路径和操作习惯
- 建议确认方：产品 / 设计

**7. 申请单字段模型**
- 影响：申请单需要哪些字段（模板列表、原因、审批历史等）需定案
- 建议确认方：产品 / 工程
