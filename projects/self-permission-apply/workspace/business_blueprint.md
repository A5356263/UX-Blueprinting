# 业务蓝图：员工自助申请权限

## 0. 本次关键设计判断

**判断：**

员工自助申请权限是一个成立且值得正式做的需求，但它的核心不是"做一个申请页面"，而是在现有权限管理体系中新增一种权限来源方式和生效机制。必须先在业务层面定义清楚新来源的定位、范围和边界，才能保证后续的体验方案不跑偏。

**主要影响：**

1. 权限来源模型需要扩展，新增"员工自助申请"作为一种独立的权限获得方式，与管理员直授、角色授予并列
2. 生效机制从"配置即生效"变为"审批后自动授权"，需要在现有判断链路中插入审批生效条件
3. 员工端的权限认知模型需要建立"我的权限"和"我可以申请的权限"两条信息线

**建议方案：**

- 将自助申请定位为"管理员可控范围内的员工自服务通道"，而不是完全开放的权限市场
- 可申请范围与现有角色体系共用同一套口径，减少概念增殖
- 审批人由管理员在配置时指定，既可以固定人，也可以走审批中台流程

**不建议方案：**

- 不建议把自助申请做成"员工随便选，管理员只要审批"的完全开放模式——可申请范围必须由管理员提前限定
- 不建议让员工按数据范围申请——当前只需覆盖角色和功能权限

**关键待确认：**

1. 员工申请时是按角色申请（一次性获得角色下所有功能权限），还是按功能权限点逐个申请——这直接影响管理端配置和员工端申请交互

> 更多待确认问题详见 `## 9. 待确认问题`。

## 1. 一句话结论

能做，建议做。但它的落地顺序应该是：先定义来源模型定位和管理端配置能力，再做员工端申请链路。管理端的边界定义清楚了，员工端的体验才不会反复改。

## 2. 这件事为什么值得正式做

现在的问题不是"没有申请页面"，而是"权限申请没有标准化的业务路径"：

- 员工不知道找谁、等多久
- 管理员被频繁打断，授权动作没有留痕
- 中大型企业人员越多，这个问题越严重

这次方案成立需要满足的前提是：管理员始终保留对申请范围的控制权，审批通过后自动授权是可靠的，且不与现有治理模式冲突。当前这几个前提都已确认可满足。

哪些情况下需要降级做：如果企业内部组织架构不清晰、角色体系尚未建立，自助申请的价值会大打折扣，建议先完善角色体系再开启。

## 3. 值不值得做

**收益：**
- 降低管理员重复劳动——员工自助申请+审批后自动授权，管理员不需要手动配权限
- 缩短授权时效——员工不再需要等管理员有空才能获得权限
- 增加审计可追溯性——所有申请有记录、有审批、有结果
- 提升员工自主性——员工可自行查看权限和申请进度，减少沟通成本

**成本：**
- 开发成本——来源模型扩展、状态机新增、审批后自动授权链路
- 管理成本——管理员需要配置可申请范围和审批人，增加初始设置负担
- 认知成本——员工需要理解"我有什么权限"和"我能申请什么权限"的区别

**系统代价：**
- 链路复杂度增加——权限判断链路需要增加来源类型和审批生效条件判断
- 审计范围扩大——需要追踪申请单和授权结果的对应关系
- 对既有流程的破坏风险——如果切入不当，可能干扰现有的权限治理流程

**综合判断：**
收益显著大于成本，特别是对于中大型企业。但必须保证管理端的配置能力先到位，避免出现"开放了但控制不住"的局面。

## 4. 应该做成什么能力形态

比较两条路径：

**路径 A：独立功能模块**
- 在管理后台新增"自助申请配置"独立模块，统一管理开关、范围、审批人
- 员工端在工作台或应用入口新增"权限申请"入口
- 优点：边界清晰，不影响现有权限页面结构
- 缺点：独立模块可能成为"配置孤岛"，与现有的角色管理、用户授权页面脱节

**路径 B：扩展现有能力**
- 在现有的角色管理/用户授权等页面中嵌入自助申请配置能力
- 员工端与现有"我的权限"查询页面共用入口
- 优点：配置路径与现有权限管理一致，管理员不需要学习独立模块
- 缺点：现有页面结构和交互需要调整，改动面较大

**推荐：路径 A（独立功能模块）**

理由：
- 自助申请配置与现有的权限配置（角色管理、用户授权）面向不同的操作者和目的——前者是"控制员工可以申请什么"，后者是"管理员直接分配什么"
- 独立模块可以保证关闭时一刀切干净，不影响其他配置
- 等模式稳定后，可以在适当时机与现有权限配置页面做入口聚合，但初始阶段不建议耦合

## 5. 推荐业务方案

### 角色与职责

| 角色 | 职责 |
|------|------|
| 超级管理员 | 开启/关闭自助申请，配置可申请范围和审批人 |
| 审批人 | 处理员工提交的权限申请，通过或拒绝 |
| 员工 | 查看已有权限，提交权限申请，查看申请进度 |

### 主流程闭环

```
管理员配置
  → 开启自助申请
  → 设置可申请范围（选择哪些角色/功能权限允许申请）
  → 指定审批人
  → 上线

员工申请
  → 登录后看到"权限申请"入口
  → 查看已有权限
  → 在可申请范围内选择需要的权限
  → 填写申请原因
  → 提交

审批处理
  → 审批人收到待处理通知
  → 查看申请内容和原因
  → 通过：系统自动授权 → 员工收到通知
  → 拒绝：填写拒绝原因 → 员工收到通知
```

### 前置配置

管理员在开启前必须完成：
1. 勾选允许员工申请的角色或功能权限
2. 指定至少一个审批人（可多选）

缺少任一项，系统应提示不可开启。

### 结果回写与记录沉淀

- 每笔申请形成一条申请记录，包含申请人、申请内容、申请原因、审批人、审批结果、授权结果
- 授权结果需要与权限来源模型打通——授权成功后，在权限来源中标记为"自助申请"
- 申请记录可用于审计核验

## 6. 必须守住的规则和边界

**不能放开的限制：**
- 可申请范围必须由管理员预设，不开放"全量权限可申请"的默认选项
- 关闭能力后，已审批通过但尚未授权的申请仍需完成授权

**必须审批的场景：**
- 所有员工提交的权限申请都必须经过审批，不存在免审批通道
- 审批人不能是申请人本人

**必须二次确认的操作：**
- 管理员关闭自助申请能力时，如存在在途申请，需二次确认

**必须前置说明的信息：**
- 员工提交申请前，应清楚知道申请的权限是什么、审批通过后会获得什么
- 员工应知道当前审批人是谁、预计处理时长（如有）

## 7. 主要风险与保护策略

| 风险 | 影响 | 缓解策略 |
|------|------|----------|
| 可申请范围配置过宽，员工申请到不合适权限 | 权限安全 | 配置时提示"建议按最小必要原则配置"；审批人把关 |
| 审批人缺失（未配置/离职/出差） | 申请无法流转 | 配置阶段校验至少一个审批人；提供默认兜底到超管的选项 |
| 审批通过但自动授权失败 | 权限不生效，产生矛盾状态 | 标记异常并通知管理员手动介入；提供重试机制 |
| 员工频繁提交重复或无效申请 | 审批人负担 | 提交频率限制或去重判断（可选） |

## 8. 方案承接要求

后续 experience 阶段必须承接以下内容：

**必须覆盖的角色：**
- 超级管理员（配置和控制）
- 审批人（审批处理）
- 员工（查看和申请）

**必须闭环的主流程：**
- 管理员配置→上线→员工申请→审批→自动授权→完成通知
- 管理员关闭→存量在途处理→下线

**必须处理的异常：**
- 审批人缺失或无法处理
- 审批通过但授权失败
- 员工提交超出范围的申请
- 关闭时存在在途申请

**必须解释的状态：**
- 申请全生命周期状态（申请中、审批中、已通过、已拒绝、已撤销）
- 权限的"待审批生效"状态解释

**必须保护的风险：**
- 可申请范围的安全控制
- 审批链路断裂的兜底

**可作为设计建议的内容：**
- 员工端"已有权限"和"可申请权限"的信息组织方式
- 申请记录列表的筛选和排序
- 通知方式（应用内通知/消息/邮件）

## 9. 待确认问题

1. **员工申请时按角色申请还是按功能权限点申请**

   影响：两种方式会导致管理端配置交互和员工端申请交互完全不同。按角色申请更简单（选角色→申请→获批后获得角色下全部权限），但灵活度低；按功能权限点申请更灵活，但配置成本和认知负担更高。
   建议确认方：产品 / 业务

2. **是否需要与审批中台打通，还是固定审批人作为长期方案**

   影响：固定审批人模式实现简单，适合 MVP；与审批中台打通后可以支持更复杂的审批链路（多级审批、条件路由、超时自动转交等），但会增加对接成本。
   建议确认方：技术 / 产品

3. **新来源类型在来源模型中的优先级和覆盖规则**

   影响：如果员工通过自助申请获得的权限与管理员直授或角色授予的权限发生范围重叠，谁覆盖谁、怎么合并展示，需要在来源模型中明确定义。
   建议确认方：业务 / 技术
