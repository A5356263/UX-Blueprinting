# 轻量业务蓝图

## 0. 本次关键业务判断

**判断：**

这次不是在权限体系上加一个功能入口，而是为一整条以前不存在的权限获取路径——"员工感知需求 → 发起申请 → 审批关卡 → 自动生效"——补齐来源归属、治理状态、审批链路和查询解释的闭环。适合按轻量业务蓝图承接，因为底层模型不变（来源枚举、状态机、决策链均不改），但需要把新路径在每个模型层中的位置显式定义清楚。

**主要影响：**

1. 权限的来源解释从"管理员给的 / 角色带的 / 应用可见的"三条变成四条，新增"自助申请审批获得"作为治理修饰标记
2. 权限治理的触发方从管理员扩展到员工，审批中台的"发起人"语义需要兼容员工角色
3. 员工侧首次出现权限查询和申请能力，需要定义与管理员侧权限视图的关系和隔离边界

**建议方案：**

- 自助申请作为现有"权限变更审批模式"的员工侧触发端，复用决策链契约（L0→L1→L2→L3）和治理状态机（draft→pending→approved→effective→revoked）
- 权限来源仍归入 ACL_DIRECT，通过治理修饰因子"自助申请审批获得"区分于管理员手动直授
- 可申请范围默认按角色配置，敏感角色（高危操作、资金操作、超管）默认排除在可申请范围外
- 审批链路复用 OA 审批中台完整能力，默认审批人指向组织架构负责人

**本阶段先定清：**

- 自助申请权限在来源模型和决策链中的解释路径（哪些层不变、哪些层新增判定分支）
- 与现有治理模式的叠加规则矩阵（共存 / 高风险标注 / 互斥）
- 关闭能力时对三种状态（已生效 / 审批中 / 草稿）的差异化处理

**需要重新判断的信号：**

1. 如果后续需要开放功能权限级申请（而非仅角色），需重新评估员工侧信息架构复杂度
2. 如果后续需要支持员工自选数据权限范围，需重新评估决策链 L2 的配置路径

## 1. 一句话结论

能做。建议首期按角色申请、复用 OA 审批中台和现有治理状态机，权限来源归入 ACL_DIRECT + 治理修饰标记"自助申请审批获得"。核心工作不在新功能开发，而在于让新路径在来源解释、状态流转、审批链路和查询闭环四个维度上都有明确位置且可被审计。

## 2. 关键业务规则

**前提判断：当前需求成立的条件**

- 企业在权限管理上已经使用了角色体系，角色定义相对清晰。如果企业角色混乱或未启用角色管理，自助申请的价值会大打折扣——因为员工无法理解"我能申请什么"
- 管理员愿意且有能力完成可申请范围的初始配置。如果管理员不配置就直接开启，员工端将看不到任何可申请的权限，能力形同虚设
- OA 审批中台已可用且审批链路可配置。如果审批中台尚未就绪，自助申请的审批环节无法闭环

**关键规则：影响体验承接的必须项**

- 可申请范围 = 管理员勾选的角色集合 - 敏感角色默认排除集合。不在范围内的角色，员工端不展示、不可搜索、不可申请
- 同一角色同一时间一个员工只能有一条 active 申请（draft / pending）。已有该角色的权限（无论来源）时不提供申请入口
- 审批通过后自动授权，权限来源标注为"自助申请审批获得"。如果自动授权失败（如角色被删除），申请异常终止并通知管理员
- 关闭能力 = 已生效权限保留 + pending 全部终止通知 + draft 归档。关闭操作需审计日志
- 员工端权限列表必须标注每项权限的来源（管理员授予 / 来自 XX 角色 / 自助申请 / 协作可见），对应 RISK-002

**规则边界与执行优先级**

- 决策链契约的层级顺序不变：先判可见性（L0），再判功能权限（L1），再判数据范围（L2），最后判治理状态（L3）。自助申请只影响 L3（从 pending 到 effective 的状态流转），不改变 L0-L2 的判定逻辑
- 自助申请与子管理员模式可共存（子管理员可在管辖范围内审批员工申请）
- 自助申请与双管理员模式不互斥，但叠加时配置页需显式高风险警告
- R-009 的互斥关系（子管理 + 双管理）不受自助申请影响

## 3. 边界与风险

**不能放开的限制**

- 权限来源枚举不新增顶层分类。自助申请审批通过后的权限来源仍为 ACL_DIRECT，不在 ACL_DIRECT / RBAC_ROLE / APP_VISIBILITY / COLLAB_VISIBILITY 之外新增
- 治理状态机不新增状态节点。复用 draft / pending / approved / rejected / effective / revoked 六个状态
- 不另建审批引擎。审批流程设计、审批操作、超时处理、转派交接、数据管理全部复用 OA 审批中台
- 不另建统计分析面板。统计数据接入 OA 审批已有智能分析面板
- 服务人员明确不开放（3 个月有效期 + 资金操作硬隔离不支持自助权限扩展）

**最关键的风险**

1. **权限来源解释更不透明（RISK-002 加剧）**：如果"自助申请审批获得"和"管理员手动直授"在权限查询页显示为相同的来源，排错时无法区分，员工会说"我明明申请通过了为什么还看不到"而管理员也无法判断权限到底怎么来的
2. **覆盖规则导致反直觉结果（RISK-003）**：员工申请角色审批通过、权限已生效，但应用可见性范围未覆盖导致入口不可达。这是自助申请场景下挫败感最强的体验——比管理员直授场景更严重，因为员工付出了"主动申请 + 等待审批"的成本
3. **可申请范围配置质量决定能力生死**：范围过宽 → 权限失控；范围过窄 → 员工申了也白申。而管理员对角色体系的理解正是当前系统里最薄弱的环节之一
4. **关闭能力时的批量终止操作**：如果审批中的申请量大，批量终止属于高危及批量操作（RISK-007），必须有确认步骤和完整的通知覆盖

**对应保护策略**

- 权限查询页必须展示"获取方式"字段，与"来源类型"并列，确保自助申请和管理员直授可区分
- 权限详情页在权限已生效但应用不可见时，必须显式解释"你已获得 XX 角色的功能权限，但该角色对应的应用当前对你不可见，请联系管理员调整应用可见范围"
- 管理员首次开启自助申请时，提供配置向导：先引导勾选可申请角色，再引导设置审批流程，再引导预览员工端效果
- 关闭能力时强制二次确认，并展示受影响申请数量（"当前有 N 条审批中的申请将被终止"）

## 4. 体验承接要求

**角色：**

- 普通员工：需覆盖"查看我的权限"和"发起权限申请"两个场景。后者需在"发现自己缺权限"的时刻自然触达（无权限提示页嵌入），也需要独立入口（工作台"我的权限"）
- 审批人：需覆盖"审批权限申请"场景。审批时能看到申请人的已有权限概览，用于判断申请合理性
- 超级管理员 / 权限管理员：需覆盖"配置自助申请能力"和"查看申请统计"两个场景。配置需向导式引导

**流程：**

- 员工端主流程：发现缺权限（或主动进入"我的权限"）→ 浏览可申请角色 → 选择角色 → 填写申请原因 → 提交 → 查看审批进度 → 审批通过后权限自动出现在"我的权限"列表中
- 审批端主流程：收到待办 → 查看申请人信息、申请角色、申请原因、已有权限概览 → 同意（自动授权）/ 拒绝（必填原因）
- 管理端主流程：进入权限管理模式 → 开启自助申请 → 配置可申请角色（向导式）→ 配置审批流程 → 发布生效

**进度与结果状态：**

- 申请提交后的每个状态变化都必须有通知：提交成功 → 审批中（告知审批人是谁）→ 审批通过 → 权限已生效（告知在哪可以看到和使用）
- 拒绝时必须让员工看到拒绝原因
- 撤销后必须让审批人知道申请已撤回
- 关闭能力时双方都必须收到通知

**异常：**

- 审批人不存在：提交时阻止并引导联系管理员
- 自动授权失败：通知管理员介入，告知员工"授权处理中"
- 可申请角色被删除：自动终止并通知申请人
- 应用不可见导致权限不可达：在"我的权限"详情中显式解释原因
- 审批超时：按 OA 审批中台规则，不自动通过

**反馈：**

- 关键操作（提交申请、审批通过/拒绝、关闭能力）必须有明确的结果反馈
- 状态变更需通过通知触达（客户端弹框 + 移动端推送 + 微信公众号），复用 OA 审批已有通知通道
- 错误和阻断必须给出下一步指引，不只说"操作失败"

**文案：**

- "我的权限"页面需解释"权限来源"的含义，帮助员工理解"为什么我有/没有这个权限"
- 无权限提示页的申请入口文案方向："你暂无此功能的权限，如果认为自己需要，可以申请以下角色"（而非干巴巴的"无权限"）
- 审批详情页需展示申请人身份和已有权限，帮助审批人快速判断
- 关闭能力时的确认弹窗需说明受影响范围（"关闭后，N 条审批中的申请将被终止，已生效的权限不受影响"）

## 5. 升级信号

出现以下变化时，应停止当前轻量执行并请求 UXB 重新判断：

1. 需求范围从"按角色申请"扩展到"按功能权限申请"——员工侧信息架构和认知负担显著上升，需重新评估复杂度
2. 需求范围从"不选数据范围"扩展到"员工自选数据范围"——决策链 L2 复杂度直接暴露给员工，需重新评估数据权限配置路径
3. 自助申请被要求与双管理员模式强制互斥（而非高风险标注）——需在设计上增加模式互斥校验
4. 需求扩展到服务人员——服务人员的 3 个月有效期和资金操作硬隔离与自助申请的逻辑需要重新对齐

## 6. 待确认问题

- 审批人已查看申请但未处理时，是否允许员工撤销？影响撤销按钮的可用状态设计
- 申请时是否需要支持上传附件（如证明材料）？OA 审批已支持，首期做管理员可配置项即可，但需确认是否纳入首期
