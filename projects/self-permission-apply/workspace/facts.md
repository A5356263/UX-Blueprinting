# 事实澄清

> 本文基于 `source/requirement.md`（需求文档_员工自助申请权限）整理，补充来自权限管理域和审批管理域已有业务知识的事实支撑。

## 任务概述

### 要解决什么问题

目前企业员工的权限分配完全由权限管理员或超级管理员集中处理。在中大型企业中，员工数量多、人员流动频繁，权限变更沟通成本高、授权时效不稳定。本需求希望通过支持员工自助查看和申请权限，把部分权限申请工作从管理员侧分散到员工侧，同时保留管理员对申请范围和审批流程的控制。

### 涉及哪些角色

- **超级管理员 / 权限管理员**：负责配置是否开启员工自助申请权限，控制可申请范围和审批规则。只有具备最高权限的管理员可以操作。
- **员工**：查看自己的权限，发现缺少权限时主动发起申请。需求文档倾向对服务人员不开放该能力。
- **审批人**：处理员工提交的权限申请，决定是否同意授权。默认审批人为员工的直接上级（组织架构负责人），支持自定义。

### 主要场景是什么

1. 管理员开启自助申请能力并配置可申请范围和审批流程
2. 员工查看自己当前拥有的权限
3. 员工申请所需权限（选权限→填原因→提交）
4. 审批人处理申请（同意/拒绝），审批通过后系统自动完成授权
5. 管理员关闭该能力，并处理关闭时正在审批中的申请

## 功能范围

### 管理端：开启/关闭自助申请权限能力

管理员在权限管理模式中新增"自助申请模式"开关。开启前必须完成两项配置：设置可申请范围、设置审批方式。开启后员工端出现申请入口。关闭时需处理正在审批中的申请（允许完成），且已授予的权限不受影响。

**适用角色**：超级管理员 / 权限管理员
**来源依据**：需求文档 4.1 / 7.1

### 管理端：配置可申请范围

管理员可以分别设置可申请的角色列表和可申请的功能权限列表。同时可以设置敏感权限排除列表，默认排除超管角色、管理后台全局配置类权限、涉及财务/税务敏感数据的权限。

**适用角色**：超级管理员 / 权限管理员
**来源依据**：需求文档 7.1 / UXB 判断

### 管理端：配置审批流程

管理员可以设置审批流程，默认审批人为员工的直接上级（组织架构负责人）。支持复用现有OA审批引擎的高级配置（自定义审批人、分支条件、超时处理等）。

**适用角色**：超级管理员 / 权限管理员
**来源依据**：需求文档 7.1 / 审批管理域知识

### 员工端：查看已有权限

员工可以查看自己当前拥有的功能权限和数据权限。展示内容包括权限名称、权限来源（管理员授予/角色授予/自助申请）、权限状态（已生效/审批中/已拒绝）、有效期限（如果适用）。

**适用角色**：员工
**来源依据**：需求文档 4.2 / 权限管理域-来源模型

### 员工端：申请权限

员工发现自己缺少某项权限后，可以从可申请范围中选择所需权限，填写申请原因，提交申请。提交后申请进入审批流程，员工可以查看申请记录和当前审批状态。

**适用角色**：员工
**来源依据**：需求文档 4.3

### 员工端：查看申请记录

员工可以查看自己提交过的所有权限申请记录，包括申请时间、申请内容、当前状态（审批中/已通过/已拒绝）、审批人、审批意见。

**适用角色**：员工
**来源依据**：需求文档 4.3 / 4.5

### 审批端：处理权限申请

审批人收到员工的权限申请后，可以查看申请详情（申请权限、申请原因、申请人信息），决定同意或拒绝。审批通过后系统自动完成授权。

**适用角色**：审批人
**来源依据**：需求文档 4.4

## 关键业务规则

### B1：自助申请模式开启规则

只有超级管理员或权限管理员可以开启或关闭自助申请模式。开启前必须设置可申请范围和审批流程，否则不能开启。

### B2：可申请范围规则

员工只能申请管理员已配置为"可申请"的角色或功能权限。不在可申请列表中的权限对员工不可见、不可搜索、不可申请。

### B3：敏感权限排除规则

管理员可以配置敏感权限排除列表。被排除的权限即使属于可申请范围，也不能被员工申请。默认排除超管角色、管理后台全局配置权限、涉及财务/税务敏感数据的权限。

### B4：审批生效规则

员工提交申请后必须经过审批才能生效。审批通过后系统自动完成授权，不需要管理员手动干预。审批拒绝后权限不授予，员工可查看拒绝原因。

### B5：关闭时的状态处理规则

管理员关闭自助申请模式时：
- 已通过并生效的权限保留不变（权限来源标记为"自助申请"但不影响已生效状态）
- 正在审批中的申请允许继续完成审批
- 新申请入口关闭，员工不能再提交新申请

### B6：模式互斥规则

自助申请模式与权限变更审批模式可共存（目标不同）。与双管理员模式存在冲突（双管理员要求两个管理员确认，自助申请只需一个审批人），建议设置为互斥。与子管理员模式可共存。[GAP] 互斥的具体规则和冲突时的用户提示策略需要产品确认。

### B7：服务人员排除规则

需求文档倾向对服务人员不开放自助申请能力。服务人员登录后不应看到申请入口。[GAP] 服务人员的判定标准和是否完全排除需要在业务蓝图中确认。

## 状态流转

### 权限申请生命周期

```
员工提交申请 → 审批中（pending）
                    ↓
           ┌── 审批人处理 ──┐
           ↓                ↓
        通过（approved）    拒绝（rejected）
           ↓
        已生效（effective）
```

**说明**：申请提交后进入"审批中"状态，审批人同意后变为"已通过"，系统自动完成授权后变为"已生效"。审批人拒绝后变为"已拒绝"。员工可以在审批中状态撤销申请（[GAP] 是否需要支持撤销待确认）。

### 治理状态的兼容性

现有权限治理状态模型定义了 draft → pending → approved → effective → rejected → revoked 六类状态。自助申请的审批生命周期（pending → approved → effective / rejected）可以直接使用现有状态模型，不需要新增状态类型。

**来源依据**：权限管理域-治理状态模型

## 异常与边界

### E1：审批人不存在

管理员未配置审批流程，且员工的直接上级（组织架构负责人）未设置时，申请无法提交。应提示"当前无可用审批人，请联系管理员配置审批流程"。

### E2：关闭能力时存在进行中的申请

管理员关闭自助申请模式时，如果有正在审批中的申请，系统提示管理员"当前有 X 个申请正在审批中，关闭后这些申请将不再接收新的申请，但已有申请仍可继续处理"。关闭不影响进行中的申请流转。

### E3：申请已提交后无法修改

员工提交申请后，在审批人处理前不能修改申请内容。[GAP] 是否需要支持撤销功能（员工在审批人处理前主动撤回申请）待确认。

### E4：申请敏感权限

如果员工尝试申请管理员已配置为敏感权限（被排除）的权限，该权限在申请列表中不可见。如果通过其他入口尝试申请，应阻断并提示"该权限不允许自助申请"。

### E5：模式冲突检测

当管理员尝试同时开启双管理员模式和自助申请模式时，系统应提示两种模式存在冲突，并给出选择建议。[GAP] 冲突时的处理策略是需要允许管理员选择还是强制互斥，待产品确认。

### E6：员工离职或角色变更

员工离职后，通过自助申请获得的权限应随账号状态变化处理（与普通权限一致）。员工角色变更（调岗）后，已申请的与岗位相关的权限是否需要重新评估，需进一步判断。[GAP]

## 依赖与前置条件

- 权限管理域已有治理状态模型（draft → pending → approved → effective → rejected → revoked）和来源模型（ACL_DIRECT / RBAC_ROLE / APP_VISIBILITY / COLLAB_VISIBILITY）
- 审批管理域已有OA审批引擎，支持六种审批人来源、五种节点类型、超时处理策略
- 组织架构数据：需要组织架构负责人信息作为默认审批人来源
- 员工主体数据：作为权限承受者的主体身份
- 服务人员身份标记：[GAP] 服务人员的身份判定数据源待确认

## 开放问题与缺口

- [GAP] 自助申请模式与双管理员模式的具体互斥规则和冲突处理策略
- [GAP] 员工提交申请后是否支持撤销
- [GAP] 服务人员的判定标准及是否完全排除
- [GAP] 员工端入口位置（工作台、权限管理页、个人中心）
- [GAP] 是否需要展示权限来源（如"由 XX 在 YY 时间通过自助申请授予"）
- [GAP] 是否需要提供管理员端的使用统计（申请量、通过率、热门申请权限等）
- [GAP] 申请时是否支持上传附件
- [GAP] 是否需要支持"敏感角色""敏感权限"自动识别规则
- [GAP] 员工角色变更（调岗）后，通过自助申请获得的权限是否需要重新评估
