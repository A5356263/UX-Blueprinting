# 业务蓝图

> 本蓝图基于 source/requirement.md 和 source/background.md 的事实输入，结合权限管理领域知识做出独立业务判断。

## 0. 本次关键设计判断

**判断：**

需求成立，应按「新增能力域」而非「扩展现有功能」来处理，但必须深度复用现有角色、审批和来源解释体系，不做独立权限子系统。

**主要影响：**

1. 权限来源模型需要扩展——系统需要能说明某个权限「是通过自助申请获得的」，并和「管理员分配」「角色授予」等已有方式区分开
2. 新增一条完整的状态链路——从员工提交、审批人处理到最终授权生效，每个节点的可见者和可操作者需要明确定义
3. 管理端、员工端、审批端三端的信息结构和操作路径各不相同，体验方案需要为每个角色独立设计

**建议方案：**

- 员工只申请角色，不直接申请功能权限或数据权限
- 审批后系统自动授权，不需要管理员手动操作
- 与现有治理模式（子管理员、双管理员、权限变更审批）均不互斥，作为独立能力运行
- 能力关闭时不影响已有授权和审批中的申请

**不建议方案：**

- 不支持员工直接申请单个功能权限——会让权限来源叠加逻辑过于复杂，排错成本高
- 不支持员工在申请时选择数据权限范围——数据权限的条件组计算规则员工无法理解
- 不做多级审批——第一版保持一级审批，降低流程复杂度

**关键待确认：**

1. 同一员工对同一角色是否有申请频率限制？当前判断不影响核心设计方案，上线后根据运营数据决定
2. 管理员通过其他途径在审批期间给员工分配了同一角色时，在途申请是否需要自动失效？影响状态机设计

> 更多待确认问题详见 `## 9. 待确认问题`。

## 1. 一句话结论

能做，建议做成独立能力域——员工自助申请角色权限，审批通过后自动授权。核心原则是：员工只和「角色」打交道，管理员完全控制范围和流程，系统自动完成授权和审计。不能做成独立权限子系统，必须深度复用现有的角色体系、审批中台和来源解释能力。

## 2. 需求是否成立

### 解决的问题

当前权限获取只有一条路：管理员主动分配。在中大型企业里，员工需要权限时得私下找管理员或老板，沟通成本高、时效不稳定。超级管理员可能是老板本人，权限管理工作挤占了其他管理事务。

### 影响哪些角色

- 员工：从被动等权限变成主动申请
- 管理员：从逐个处理变成集中配置 + 审批，释放带宽
- 审批人：代替管理员做授权决策，分担管理压力

### 判断：成立

需求真实存在，解决的痛点清楚。关键前提是：自助申请不能变成「随便申请」，管理员必须完全控制范围和审批。这个前提是可以实现的。

### 可能不成立的情况

如果企业规模很小（不到 10 人），员工和超管之间可以直接沟通，自助申请反而增加了不必要的流程环节。但这不是需求本身不成立——只是说能力应该可以按需开启，不是强制使用。管理员可以选择不开启。

### 不存在伪需求或重复建设

现有体系没有同类能力。权限变更审批模式是管理员发起变更需要审批，跟员工自助申请是不同的业务路径。不是重复建设。

## 3. 值不值得做

### 收益

- 业务价值：把管理员从逐人授权的重复劳动中解放出来，对中大型企业有明显的效率提升
- 员工体验：员工不需要私下找人，在系统里就能看到自己缺什么权限、能申请什么、申请到哪一步了
- 规范化：权限获取从私下沟通变成有记录、可追踪、可审计的正式流程

### 成本

- 开发成本：需要新增管理端配置页、员工端申请和查看页、审批端处理页，以及在现有角色管理和权限查询中做适配
- 维护成本：新增一套配置逻辑和状态管理，但因为是独立能力域，维护边界清楚
- 培训成本：管理员需要理解如何配置可申请范围和审批规则。员工侧学习成本低——看到角色、点击申请、填写原因、等审批，路径自然
- 认知负担：新增了一个权限来源概念，需要在查询和排错时能区分和解释。但这是可控的——把来源解释做好就行

### 系统代价

- 链路复杂度：新增一条申请→审批→授权的链路，但依赖现有审批中台可以降低复杂度
- 管理成本：新增可申请范围的配置维护，但相比管理员逐人授权的成本，配置维护成本更低
- 审计成本：新增审计日志条目，但日志格式可复用现有操作记录体系
- 对既有流程的破坏：几乎为零，因为是独立能力域，可以按需开启，不开则完全不感知

### 综合判断

值得做。尤其对员工多、人员流动快的企业，价值明显。对小型企业，不开就行，不会成为负担。

## 4. 应该做成什么能力形态

### 路径比较

**路径 A：独立新增能力域**

在权限管理后台新增一个独立的「员工自助申请权限」模块，包含管理端配置、员工端申请和审批端处理。

优点：边界清晰，不影响现存能力；可按需开启关闭；后续扩展独立迭代。
缺点：新增一套页面体系。

**路径 B：扩展角色管理**

在现有的角色管理页面里增加「允许员工自助申请」的标记，让员工在角色列表里直接申请。

优点：开发量少，和角色管理紧耦合。
缺点：打破了角色管理作为管理员专属配置区的定位；员工的申请行为和审批人的处理行为需要新建页面承接，实际开发量并不比路径 A 少；边界不清晰，后续容易和管理员操作混淆。

**路径 C：仅在配置区做开关，不新建模块**

在权限管理模式页加一个开关，员工通过现有的权限查询页看到可申请的角色。

优点：开发量最少。
缺点：员工侧体验割裂——在查询页看到可申请角色却不知道在哪申请；缺少独立的申请记录和状态追踪；管理员缺少统计和监控手段。

### 推荐：路径 A

独立新增能力域，但深度复用现有能力。具体做法：
- 管理端：在权限管理后台新增「自助申请权限」配置入口，负责能力开关、可申请范围、审批规则配置
- 员工端：在工作台或个人信息区新增「我的权限」入口，承担查看已有权限、发起申请、跟踪申请记录
- 审批端：复用审批中台的审批列表和审批详情页，通过审批类型区分「员工申请」和「管理员变更」

## 5. 推荐业务方案

### 角色与职责

- **超级管理员/权限管理员**：开启或关闭自助申请能力；配置可申请的角色范围（勾选哪些角色允许员工申请）；标记敏感角色；指定默认审批人（可覆盖直属上级）；查看申请统计数据；在必要时批量回收通过自助申请获得的权限。不能申请自己管理范围内的权限——自己是管理员，不走员工通道。
- **员工**：查看自己已有权限和权限来源；在可申请角色列表中看到哪些可以申请（含已拥有标记和敏感角色提示）；提交申请并填写原因；查看所有申请记录和当前状态；审批中的申请可以撤销。不能申请自己已拥有的角色；不能申请标注为「不可申请」的角色；不能在能力关闭时提交新申请。
- **审批人**：查看待审批申请列表；查看单条申请的完整内容（申请人、申请角色、申请原因、提交时间）；同意或拒绝申请，可选填写审批意见。审批人的审批范围由管理员在开启配置中设定。
- **系统**：审批通过后自动将员工加入对应角色的成员列表；记录所有关键操作的操作日志；提供申请统计数据。

### 主流程闭环

**管理员配置流程**：
1. 管理员进入「自助申请权限」配置页
2. 如果能力尚未开启，看到开启入口；如果已开启，看到当前配置概览
3. 开启前，系统引导管理员先完成：勾选可申请角色（至少一个）、设置审批方式（默认审批人）
4. 配置完成后点击开启，系统确认「开启后员工将可以在工作台看到自助申请入口」
5. 开启后，管理员可以随时修改配置（增减可申请角色、调整审批人、标记敏感角色）
6. 关闭时，系统提示关闭影响（员工无法提交新申请，在途申请不受影响，已有授权保留），管理员确认后关闭
7. 关闭后，管理员可以看到「批量回收通过自助申请获得的权限」的操作入口

**员工申请流程**：
1. 员工进入「我的权限」页面
2. 看到自己当前拥有的所有权限，每条标注来源（管理员分配 / 自助申请 / 角色授予）
3. 页面上有「申请权限」入口，点击后看到可申请的角色列表
4. 列表中每个角色标注：角色名称和简介、是否已拥有、是否为敏感角色（敏感角色标注「需联系管理员分配」且不可点击申请）
5. 员工点击可申请的角色，进入申请表单
6. 填写申请原因（必填），确认提交
7. 提交后，页面跳转到「我的申请」列表，新申请显示为「审批中」
8. 员工可以随时查看申请详情和当前审批状态
9. 审批中的申请，员工可以点击「撤销申请」撤回

**审批人处理流程**：
1. 审批人在审批列表（审批中台）看到待处理的权限申请
2. 每条申请标注「员工申请」类型，与其他审批类型区分
3. 点击进入审批详情，看到：申请人姓名和部门、申请的角色名称和简介、申请原因、提交时间
4. 审批人可以同意或拒绝
5. 同意时可选填写审批意见，点击确认后：申请状态变为已通过，系统自动将员工加入对应角色成员列表
6. 拒绝时建议填写拒绝原因，点击确认后：申请状态变为已拒绝，流程结束

### 前置配置

管理员在开启能力前必须完成：
- 至少勾选一个可申请角色（默认全部不勾选）
- 设置审批方式（默认审批人 = 员工直属上级，管理员可以选择改为指定某个人）
- 可选：标记敏感角色（被标记的角色在员工端展示但不可申请）
- 可选：为每个可申请角色填写简介（帮助员工理解这个角色能做什么）

### 结果回写与记录沉淀

- 审批通过 → 系统自动将员工加入角色成员 → 权限生效 → 权限来源标记为「自助申请」
- 审批拒绝 → 申请记录保留，不做授权
- 员工撤销 → 申请记录保留，不做授权
- 管理员关闭能力 → 操作记录保留
- 管理员批量回收 → 每条回收操作独立记录
- 所有关键操作（开启、关闭、修改配置、提交、审批、撤销、授权、回收）均记录操作日志

## 6. 必须守住的规则和边界

### 不能放开的限制

- 只有超管或权限管理员可以开启/关闭能力和配置可申请范围，子管理员不能操作
- 超管角色默认不可申请，系统在配置页给出明确提示
- 员工只能申请角色，不能申请单个功能权限或数据权限
- 员工只能看到和申请管理员开放的角色，不能看到未开放的角色
- 员工不能申请自己已经拥有的角色
- 同一员工对同一角色不能同时有多个审批中的申请
- 能力关闭后，员工不能提交新申请

### 必须审批的场景

- 所有员工提交的权限申请都必须走审批，不允许免审批直接授权
- 审批人不能审批自己提交的申请（如果是管理员用员工身份申请，应由另一位管理员审批）
- 管理员关闭能力本身不需要审批，即时生效

### 必须二次确认的操作

- 管理员关闭能力——提示关闭影响后再确认
- 管理员批量回收权限——提示回收数量和影响员工后再确认
- 审批人拒绝申请——建议填写拒绝原因，但不强制
- 员工撤销申请——提示「撤销后如需该权限需重新申请」

### 必须前置说明的信息

- 管理员开启能力前，说明开启后员工会看到什么、对现有权限体系有什么影响
- 员工提交申请前，说明申请的角色能做什么、审批人是谁、大概多久能生效
- 审批人处理申请前，能看到申请角色的权限说明，帮助做出知情判断

## 7. 主要风险与保护策略

### 风险 1：权限安全风险——可申请范围设置过宽

**影响**：员工可能申请到超出工作需要的角色权限，造成权限过度授予。

**缓解**：
- 默认所有角色不开放申请，管理员必须主动勾选才能开放
- 支持敏感角色标记——被标记的角色在员工端展示但不可申请
- 所有申请必须经过审批，审批人可以看到申请角色的权限说明
- 建议管理员定期审查自助申请获得权限的员工列表

### 风险 2：审批链路断裂——审批人不存在或不合适

**影响**：申请提交后无人处理，员工迟迟得不到授权，体验恶化。

**缓解**：
- 员工提交时检查直属上级是否存在，不存在则自动转给权限管理员
- 审批人账号异常（停用/离职）时系统提醒管理员手动转交
- 建议管理员在开启能力时确认默认审批人的合理性
- 管理员端统计数据中应展示当前在途申请数，帮助发现积压

### 风险 3：概念增殖导致认知混乱

**影响**：新增权限获取方式，管理员和员工需要理解新的概念和操作路径。

**缓解**：
- 员工侧只暴露「角色」概念，不引入功能权限、数据权限、来源模型等术语
- 权限列表中用自然语言区分来源——「管理员分配」「自助申请」，不让用户理解技术术语
- 管理端配置页的语言保持简洁，只暴露必要选项
- 不新增独立的权限管理页面——员工所有权限仍在同一个「我的权限」页面展示

### 风险 4：与现有治理模式交互的未知问题

**影响**：企业可能同时开启子管理员模式、双管理员模式或权限变更审批模式，多种治理模式同时运行时可能出现预期外的交互。

**缓解**：
- 设计上明确各模式独立运行，不互斥
- 自助申请的审批类型与权限变更审批类型的审批列表中以标签区分
- 子管理员不能配置自助申请能力（只能由超管操作），避免子管理员擅自开放权限申请
- 建议在测试阶段覆盖多种治理模式组合的场景

### 风险 5：培训和支持成本

**影响**：需求文档中提到，一线反馈担心把申请能力开放给员工会增加培训成本。

**缓解**：
- 能力默认关闭，企业自己决定何时开启
- 员工侧路径自然：看权限 → 发现缺权限 → 点申请 → 填原因 → 等审批
- 管理端配置页提供清晰的引导说明
- 产品帮助文档覆盖管理员配置和员工申请两个场景

## 8. 方案承接要求

以下内容是体验设计阶段必须承接的。建议在阅读 `facts.md` 和本蓝图后，重点围绕这些要求展开体验方案。

### 必须覆盖的角色

- 管理员：配置页（能力开关、可申请角色选择、审批规则、统计查看）
- 员工：我的权限页（已有权限列表+来源）、申请页（可申请角色列表+申请表单）、申请记录页
- 审批人：审批列表（区分审批类型）、审批详情页

### 必须闭环的主流程

- 管理员首次开启 → 配置 → 开启的全流程引导
- 员工浏览权限 → 发现缺权限 → 选择角色 → 填原因 → 提交 → 等审批 → 查看状态的完整路径
- 审批人收到审批 → 查看详情 → 做决定（同意/拒绝）→ 审批意见的路径
- 管理员关闭能力 → 确认影响 → 处理后续（在途申请、已有权限）的路径

### 必须处理的异常

- 员工无直属上级 → 提示并自动转交
- 重复申请同一角色 → 阻止并提示
- 可申请角色被管理员在审批中移除 → 在途申请不受影响
- 管理员在审批期间直接给员工分配了同一角色 → 需要在体验方案中给出处理建议
- 能力关闭时员工正在填写申请 → 提示能力已关闭

### 必须解释的状态

- 申请单各状态（已提交/审批中/已通过/已拒绝/已撤销）及对应可操作项
- 能力开启/关闭状态及对应员工端表现
- 权限来源（管理员分配 vs 自助申请）及区分方式

### 必须保护的风险

- 可申请范围过宽 → 通过配置页的默认行为和提示保护
- 审批链路断裂 → 通过兜底机制和异常提醒保护
- 概念增殖 → 通过界面语言和操作路径保护

### 可作为设计建议的内容

- 员工端入口位置（建议与「我的权限」在一起）
- 申请原因的输入框设计（建议不限制字数，但给出填写引导）
- 审批列表中的类型区分方式（建议用标签或图标）
- 管理员统计页面的数据展示方式

## 9. 待确认问题

1. **管理员在审批期间通过其他途径给员工分配了同一角色，在途申请如何处理？**

   影响：影响申请状态机的设计——是需要新增「自动关闭」状态，还是保留两条独立的权限记录。
   建议确认方：产品

2. **同一员工对同一角色的申请是否需要频率限制？例如 N 天内不能重复申请已获批的角色？**

   影响：影响申请提交逻辑和员工端提示。当前判断为不阻断设计，但产品侧需要给出态度。
   建议确认方：产品

3. **自助申请获得的权限，在员工离职或转岗时是否自动回收？**

   影响：影响权限生命周期管理的完整性。按当前设计，自助申请来源的权限在授权后就等同于管理员分配的权限，离职和转岗的回收规则应与此一致。但需要确认是否需要特殊处理。
   建议确认方：产品 + 业务

4. **审批超时（如超过 30 天未审批）是否需要自动处理？**

   影响：影响审批流设计和管理员提醒机制。第一版建议不做自动处理，但需要在管理员统计面板上暴露积压情况。
   建议确认方：产品

5. **敏感角色在员工端是否直接不展示，还是展示但标注不可申请？**

   影响：影响员工端可申请列表的设计。当前建议为展示但标注「需联系管理员」，让员工明确知道这个角色存在。如果产品侧认为不展示更安全，可以调整。
   建议确认方：产品 + 安全
