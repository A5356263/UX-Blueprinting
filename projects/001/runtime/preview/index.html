Business Blueprint

1. 一句话结论

需求成立，值得做。建议将"自助申请权限"作为一个独立功能模块来建设，包含管理端配置、员工端查看和申请、审批端处理三条角色链路。核心风险点在互斥模式校验、在途流程阻断、以及审批规则的细则缺口。

2. 需求是否成立

成立。

解决的问题是真实存在的：中大型企业中，超管集中管理权限的负担重。员工数量多、流动大，每次权限变动都要超管操作，效率低。支持员工自助申请和查看，能将工作分散到各员工端，同时保持审批管控。

用户调研中 10 名实施同事有 6 名认为有价值，且竞品金蝶已支持类似功能（角色权限申请 + 工作流审批），说明市场有验证。

但有一个值得注意的反对声音：小企业和流动性大的企业，培训成本高——教全员比教 1 个超管更难。这意味着功能的适用场景偏向中大型、组织相对稳定的企业，产品定位和推广策略需要考虑这一点。

3. 值不值得做

收益：

  • 降低超管集中授权的工作量，提升权限分配效率
  • 员工可以自助查看自己拥有的权限，减少"我不知道我有没有这个权限"的沟通成本
  • 审批链路保留管控，不会因为放权而失控
  • 竞品已有先例，不做可能成为功能短板

成本：

  • 开发成本：需要新增管理端配置页、员工端权限查看和申请、审批流程对接、申请记录
  • 培训成本：员工需要学习如何申请权限，流动率高的企业可能反复培训。可通过页面引导和帮助文档降低
  • 认知负担：新增一个"模式"概念，需要向企业超管解释它与现有权限管理的关系

综合判断：收益大于成本。培训成本是可控的——好的页面设计和文案可以大幅降低学习门槛。建议在体验设计上投入额外精力，让员工无需培训就能理解如何操作。

4. 应该做成什么能力形态

比较两种路径：

路径 A — 独立功能模块：作为权限管理下的一个独立子模块，有独立的设置页、员工端入口、申请记录。边界清晰，后续可单独迭代。

路径 B — 扩展现有权限管理：在现有的权限分配流程中增加"允许员工申请"的选项，不作为独立模块。

推荐路径 A。理由：

  • 需求包含三个角色的完整闭环（管理员配置 → 员工申请 → 审批人审批），对象和流程复杂度足够支撑一个独立模块
  • 有独立的状态机（未启用/设置中/已开启/编辑中/关闭失败）和互斥规则
  • 如果嵌入现有流程，互斥校验、范围配置、审批流程这些概念会混入现有的权限分配界面，增加认知负担

5. 推荐业务方案

角色与职责：

  • 超管：开启和配置自助申请权限模式。选择申请方式（角色/功能权限）、配置可申请范围、配置审批流程。可以关闭模式和编辑配置。
  • 员工：在个人中心查看自己的权限（功能权限/数据权限/角色）。提交权限申请，查看申请记录，撤销审批中的申请。
  • 审批人（预设为组织负责人）：收到审批待办，同意或拒绝申请。审批通过后系统自动分配权限。

主流程闭环：

1. 超管进入权限管理模式 → 点击"立即启用" → 校验互斥模式 → 配置申请方式、范围、审批流程 → 点击"开启" → 再次校验 → 模式生效
2. 员工进入个人中心 → 查看"我的权限" → 点击"申请权限" → 选择角色或功能权限 → 填写申请原因 → 提交 → 进入审批
3. 审批人收到待办 → 同意/拒绝 → 系统自动处理结果
4. 员工查看申请记录，了解审批状态

前置配置：超管必须先完成自助申请权限模式的设置（申请方式 + 范围 + 审批流程），员工端才能使用。

结果回写与记录：审批通过后系统自动分配权限，操作记录和埋点数据同步写入。

6. 必须守住的规则和边界

  • 自助申请权限模式与双管理员互审模式、权限变更审批模式互斥，不能同时开启。启用和开启时都需要校验。
  • 关闭模式时如果存在在途审批流程，必须阻断关闭，提示等待审批完成。
  • 员工只能申请管理员配置范围内的角色或应用。已停用的角色不在可申请范围内。
  • 审批流程不可绕过。即使超管开启了模式，员工申请也必须经过审批。
  • 资金用户、子管理员权限、实名要求等特殊校验必须在提交时生效，不能静默通过。
  • 服务人员不能看到"我的权限"入口。
  • 只有审批中的申请可以撤销，已通过/已拒绝/已撤销的申请不可撤销。

7. 主要风险与保护策略

  • 互斥模式冲突导致功能不可用：如果企业已开启互斥模式，超管要么放弃使用自助申请，要么关闭互斥模式。关闭互斥模式可能引入其他治理风险。保护策略：在启用前清晰提示冲突原因，让超管做出知情决策。
  • 在途流程阻断关闭：超管想关闭模式但还有申请没审批完，会感到被"卡住"。保护策略：明确告知有几个在途流程、涉及哪些审批人，帮助超管推动处理。
  • 申请内容超出授权范围：员工可能尝试申请不在范围内的角色或权限。保护策略：前端只展示可申请的内容，提交时后端再次校验。
  • 培训成本导致功能使用率低：小企业或流动性高的企业可能不愿意推广。保护策略：页面设计要足够直观，让员工无培训也能完成操作；提供清晰的帮助文档入口。
  • 审批规则不明确：需求中未明确审批是多级还是一级、是否支持会签、审批超时如何处理。[GAP] 这些规则在对接审批引擎前需要确认。

8. 方案承接要求

后续 experience 阶段必须承接以下内容：

必须覆盖的角色：超管（配置端）、员工（申请端和查看端）、审批人（审批端）

必须闭环的主流程：

  • 超管：进入管理模式 → 校验互斥 → 配置三步设置 → 开启 → 已开启状态
  • 员工：进入个人中心 → 我的权限 → 申请权限 → 填写内容 → 提交 → 等待结果
  • 审批人：收到待办 → 同意/拒绝

必须处理的异常：

  • 互斥模式冲突（启用阻断）
  • 在途流程未完成（关闭阻断）
  • 提交校验失败（资金用户、子管理员、实名等）
  • 空状态（无权限数据时）

必须解释的状态：

  • 自助申请权限模式：未启用、设置中、已开启、编辑中
  • 权限申请：审批中、已通过、已拒绝、已撤销
  • 关闭失败

必须保护的风险：互斥冲突阻断、在途流程阻断、申请范围约束、特殊身份校验

设计建议：

  • 设置页采用步骤式引导（第一步/第二步/第三步），降低超管的配置认知负担
  • 申请权限抽屉要前置说明"申请通过后会自动分配权限"和"默认申请全部数据权限"
  • 空状态不仅展示文案，还应引导员工去申请权限（如果有申请入口的话）

  • 埋点具体口径和事件清单未提供。
  • 操作记录需要记录哪些字段、如何展示？需求只提到"功能新增"。

Experience Blueprint

1. 交互流程总览

本次体验围绕三类用户展开：

超管 / 权限管理员：在权限管理模式中开启并配置"自助申请权限模式"，决定员工能申请什么类型的权限、能申请哪些角色或应用、由谁审批。

员工：在个人中心查看自己当前拥有的权限，在需要时提交权限申请，跟踪申请进度。

审批人：收到审批待办后，同意或拒绝员工的权限申请。

主流程分为三条：

  • 超管配置流程：进入权限管理模式 → 点击立即启用 → 选择申请方式 → 配置可申请范围 → 配置审批流程 → 开启成功
  • 员工申请流程：进入个人中心 → 我的权限 → 申请权限 → 填写申请内容 → 提交申请 → 查看申请记录
  • 审批人审批流程：收到待办 → 同意或拒绝

异常流程重点关注：

  • 互斥模式已开启时不能启用自助申请权限模式
  • 关闭模式时存在在途审批流程，关闭失败
  • 员工提交申请时校验不通过
  • 申请记录的各种状态反馈（审批中、已通过、已拒绝、已撤销）

4. 异常与阻断流程

### 异常 1：互斥模式已开启，不能启用

发生时机：超管点击"立即启用"或"开启"时。

触发条件：企业已开启"双管理员互审模式"或"权限变更审批模式"。

系统反馈：
```
企业已开启「双管理员互审模式」，不能同时开启此模式。
```

用户下一步：超管需要先关闭互斥模式，再重新尝试启用自助申请权限模式。

---

### 异常 2：关闭模式时存在在途审批

发生时机：超管点击"关闭模式"并确认关闭。

触发条件：当前存在申请流程未完成审批。

弹窗反馈：
标题：关闭失败
正文：当前有申请流程未完成审批，请联系审批人审批完成，再关闭模式。
按钮：知道了

用户下一步：等待审批人处理完在途流程后，再次尝试关闭模式。

---

### 异常 3：提交申请时校验不通过

发生时机：员工点击"提交"时。

触发条件：

  • 非资金用户申请"代发付款"
  • 子管理员申请子管理员模式权限
  • 不满足实名要求
  • 特殊身份默认权限冲突

系统反馈：
```
当前申请内容不满足授权条件，请调整申请内容后重新提交。
```

用户下一步：员工根据提示调整申请内容，重新提交。如果涉及无法自行处理的问题（如实名要求），需要联系管理员。

---

### 异常 4：申请记录为空

发生时机：员工进入申请记录页，但从未提交过申请。

系统反馈：展示空状态提示和占位图。

建议文案：
```
暂无申请记录。如需申请权限，请点击"申请权限"。
```

  • 列表区：申请时间、申请原因、申请内容、审批状态、操作
  • 分页

审批状态选项：审批中、已通过、已拒绝、已撤销

操作规则：审批中状态展示"撤销"按钮，其他状态不展示。

6. 状态与反馈文案

  • 超管：可以编辑配置、关闭模式
  • 员工：可以在个人中心查看和申请权限
  • 审批人：可以收到并处理审批待办

7. 待确认问题

  • 审批流程的具体规则未明确（是否支持多级审批、会签、超时处理等），会影响审批端的交互设计和状态定义
  • 敏感角色和敏感组织清单未提供，如需在可申请范围中排除，需要对应配置界面
  • 埋点具体口径未提供，当前体验方案暂不涉及埋点交互
  • 操作记录的展示方式和字段未明确，当前体验方案暂不涉及
  • 帮助文档内容需要产品侧补充，当前暂用"了解更多"和"帮助文档"占位链接
  • OA 审批中"可发起人去掉"和"默认复核人员风险"两个备注的含义和处理方式需要确认
