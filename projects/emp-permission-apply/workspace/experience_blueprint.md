# 体验蓝图

> 输入依据：`business_blueprint_lite.md`

## 0. 本次关键设计判断

**判断：**

本次体验方案按三端三视图展开：管理员配置端（开启/设范围/设审批）、员工申请端（查看/申请/追踪）、审批人处理端（审核/决策）。核心挑战不是各端自己的页面怎么做，而是三端的流程衔接、状态同步和异常兜底。

**主要影响：**

1. 员工端的"查看权限"和"申请权限"是两类不同心智的任务，入口需要分开设计，否则员工会混淆"查看已有的"和"申请还没有的"
2. 审批人端的体验容易被忽视——如果审批人收到申请但缺乏申请上下文（申请人权限现状、申请原因），决策质量会下降
3. 关闭自助申请后的存量权限处理不明确，直接影响关闭流程的体验设计

**建议方案：**

- 管理员配置采用单页表单+分区折叠，不做步骤条（配置项无强依赖关系）
- 员工端将"我的权限"（查看）和"申请权限"（提交）设计为两个相邻但功能独立的入口
- 审批流通知默认走系统内通知，审批人可在审批页面看到申请人当前的权限概况

**不建议方案：**

- 不建议将员工端入口做成统一的"权限中心"大页面——查看和申请是两种不同频率和心智的任务
- 不建议审批流程完全依赖邮件通知——审批时效性要求高的场景，系统内通知更可靠

**关键待确认：**

1. 审批中台就绪状态——影响审批页面的实现方式（复用 vs 新建）
2. 可申请范围的配置方式——决定员工端可申请权限的选择器交互

## 1. 旅程图

```md
- 管理员（配置端）：识别需要开放自助申请 → 进入权限管理 → 开启并配置范围/审批流 → 确认生效
- 员工（申请端）：发现自己缺少某权限 → 进入申请入口 → 选择权限并填写原因 → 提交 → 等待审批 → 收到结果 → 确认权限已生效或重新申请
- 审批人（审批端）：收到审批通知 → 查看申请详情和申请人权限概况 → 同意/拒绝 → 确认结果已通知
```

### 旅程缺口

- 缺少员工"发现自己缺少权限"的触发入口——员工怎么知道自己缺什么权限？是主动去"我的权限"查看后对比得知，还是在使用某个功能被拦截时才知道。后者可能更真实。
- 缺少审批超时或审批人失联的兜底通知机制

## 2. 交互流程总览

**分角色交互流程：**

- 管理员（配置端）：进入权限管理模式 → 开启"自助申请"开关 → 配置可申请范围 → 配置审批流程 → 保存生效
- 管理员（关闭端）：进入权限管理模式 → 关闭"自助申请"开关 → 确认不影响进行中申请 → 关闭完成
- 员工（查看权限）：进入"我的权限" → 查看已拥有的功能权限和数据权限列表 → 按应用/角色归类浏览
- 员工（申请权限）：进入"申请权限" → 浏览可申请列表 → 选择需要的权限 → 填写申请原因 → 提交 → 在"我的申请"中查看进度
- 审批人（处理申请）：收到审批通知 → 进入审批列表 → 查看申请详情（申请人/申请权限/原因/权限现状）→ 同意或拒绝 → 填写审批意见 → 确认

**异常流程重点：**

- 员工提交超出可申请范围的权限 → 前端实时校验并阻断
- 审批人不存在或已离职 → 申请卡在"审批中"，需管理员干预
- 审批通过但自动授权失败 → 状态停留在"已通过"但未生效，需人工介入
- 管理员关闭能力时仍有审批中的申请 → 展示受影响的申请数量，确认后不影响已有流程

## 3. 主交互流程

```text
节点 3.1：管理员开启并配置自助申请

用户动作：
进入权限管理模式，找到"自助申请权限"配置区，开启开关后展开配置表单。先配置可申请范围（按角色选择/按功能权限勾选/按模板选择），再配置审批流程（选择审批人或审批角色）。

系统反馈：
- 开关关闭时，配置区置灰并提示"请先开启自助申请功能"
- 保存时校验：可申请范围和审批流程至少配置一项，否则保存失败并提示
- 保存成功后，员工端出现申请入口

需要前置解释的信息：
- 可申请范围的影响说明："员工只能申请您在此设置的范围内的权限"
- 审批流程的影响说明："员工提交申请后将按此流程流转"

建议文案：
- 开关："员工自助申请权限"
- 范围配置说明："设置员工可申请的权限范围"
- 审批流程说明："设置审批申请的流程"

下一步：
管理员确认配置生效
```

```text
节点 3.2：员工申请权限

用户动作：
进入"申请权限"页面，浏览可申请的权限列表（按功能权限或角色分组）。选择需要的一项或多项权限，填写申请原因，提交申请。

系统反馈：
- 选择权限时实时显示该权限的简要说明
- 提交时校验是否在可申请范围内
- 提交成功后显示"申请已提交，等待审批"，并在"我的申请"列表中新增一条记录

需要前置建议的信息：
- 当前已有权限的简要说明（已有权限不显示在可申请列表中，或标为"已拥有"）
- 申请的预期处理时长说明（如"通常 1-3 个工作日内处理"）

建议文案：
- 页面标题："申请权限"
- 可申请列表空态："当前没有可申请的权限，如需其他权限请联系管理员"
- 提交按钮："提交申请"
- 提交成功："申请已提交，等待审批人处理"

下一步：
员工进入"我的申请"查看进度，或继续浏览其他功能
```

```text
节点 3.3：审批人处理申请

用户动作：
收到审批通知（系统内通知），进入审批列表或直接打开申请详情。查看申请人信息、申请的权限内容和原因、申请人当前的权限概况。做出同意或拒绝的决定，填写审批意见。

系统反馈：
- 同意：系统自动执行授权，完成后状态更新为"已通过→已生效"
- 拒绝：状态更新为"已拒绝"，申请人和管理员收到通知
- 授权执行失败：状态停留在"已通过"，标记异常，通知管理人工处理

需要前置解释的信息：
- 申请人当前的权限概况（便于审批人判断申请是否合理）
- 该权限是否已被其他来源授予（避免重复授权）

建议文案：
- 审批页面标题："权限申请审批"
- 申请人当前权限："该员工当前已有以下权限：..."
- 同意按钮："同意授权"
- 拒绝按钮："拒绝"
- 审批意见占位："请填写审批意见（选填）"

下一步：
审批人返回审批列表，或处理下一项申请
```

## 4. 次交互流程

- [GAP] 已通过自助申请获得的权限的处理方式未定义

下一步：
管理员确认关闭结果

## 5. 异常与阻断流程

```text
异常 5.1：申请超出可申请范围

发生时机：员工选择权限并提交时
触发条件：员工选择的权限不在管理员配置的可申请范围内
判断依据：facts.md 3.2 可申请范围管控规则
反馈形式：字段级提示
系统反馈："该权限不在当前可申请范围内，请重新选择"
用户下一步：重新选择范围内的权限
```

```text
异常 5.2：审批人缺失（不存在/已离职）

发生时机：员工提交申请后，系统尝试路由到审批人
触发条件：配置的审批人或审批角色在当前组织架构中无效
判断依据：facts.md 5.0 异常表
反馈形式：系统拦截+管理员通知
系统反馈：系统检测到审批人配置异常，自动通知管理员"当前自助申请的审批流程配置无效，请重新设置审批人"
用户下一步：管理员重新配置审批人；员工端申请状态显示"审批人配置异常，请联系管理员"
```

```text
异常 5.3：审批通过但自动授权失败

发生时机：审批人同意后，系统执行自动授权时
触发条件：权限系统内部错误或冲突导致授权无法完成
判断依据：facts.md 5.0 异常表
反馈形式：状态异常标记+管理员通知
系统反馈：申请状态在审批人端显示"已通过"，在系统端标记"授权异常"，管理员收到"授权执行失败，请手动处理"通知
用户下一步：管理员在后台手动完成授权或排查失败原因
```

```text
异常 5.4：管理员关闭时仍有审批中的申请

发生时机：管理员关闭自助申请开关时
触发条件：当前存在状态为"审批中"的申请
判断依据：facts.md 3.4 关闭时的存量处理
反馈形式：弹窗确认
系统反馈：弹窗显示"当前有 N 个申请正在审批中。关闭后正在进行中的申请不受影响，但员工将无法提交新申请。确认关闭？"
用户下一步：管理员确认关闭或取消操作
```

## 7. 状态与反馈文案

| 状态 | 含义 | 适用对象 | 用户可操作 | 统一反馈口径 |
|---|---|---|---|---|
| 草稿 | 已填写但未提交 | 员工 | 编辑、提交、删除 | "待提交" |
| 审批中 | 已提交，等待审批人处理 | 员工、审批人 | 员工可撤销（审批人未处理时） | "审批中" |
| 已通过 | 审批人同意，待系统授权 | 员工、审批人 | 无 | "已通过，授权中" |
| 已拒绝 | 审批人不同意 | 员工、审批人 | 员工可重新申请 | "已拒绝" |
| 已生效 | 系统自动授权完成 | 员工 | 无 | "已生效" |
| 已撤销 | 员工自行撤销或被回收 | 员工 | 可重新申请 | "已撤销" |
| 已失效 | 关闭后存量权限被回收 | 员工 | 无 | "已失效" |
| 配置异常 | 审批人配置无效 | 管理员 | 重新配置审批人 | "审批人配置异常，请联系管理员" |

## 8. 待确认问题

1. **审批中台就绪状态**

   影响：影响审批页面的实现方式。若审批中台不可用，需要重新设计审批流程的实现方案，影响整体排期。
   建议确认方：产品 / 技术

2. **可申请范围的配置方式**

   影响：决定员工端"申请权限"页面的选择器交互。按角色选、按功能权限勾选、按模板选三种方式对应完全不同的 UI 方案。
   建议确认方：产品

3. **关闭自助申请后的存量权限策略**

   影响：影响关闭流程的体验设计和状态定义。保留策略下员工继续拥有已有权限，回收策略下需要设计回收通知和过渡期。
   建议确认方：产品

4. **审批超时策略**

   影响：长期未处理的申请需要超时提醒或自动升级机制，避免申请卡死在"审批中"状态。
   建议确认方：产品 / 业务

## 附录：设计指南消费说明

### 1. 设计指南消费

| 使用依据 | 转换结果 | 落点 |
|---|---|---|
| 流程模式选择原则 | 管理员配置页采用单页表单+分区折叠而非步骤条，因为配置项之间无强依赖关系 | 节点 3.1、页面 6.1 |
| 可用性原则-系统状态可见 | 申请提交流程各节点状态必须清晰展示给员工和审批人 | 节点 3.2、3.3、状态表 |
| 认知原则-减少外在认知负荷 | 员工申请时展示已有权限信息，避免重复申请；审批人查看申请人权限概况 | 页面 6.5 |
| 治理原则-默认收敛授权范围 | 可申请范围必须有管理员前置配置，不允许自由申请 | 节点 3.1、异常 5.1 |
| 反馈与报错指南 | 所有阻断场景提供"为什么不能继续"和"下一步怎么办" | 异常 5.1-5.4 |
| 信息架构原则 | 员工端"我的权限"和"申请权限"设计为相邻但功能独立的入口 | 旅程图、页面 6.2/6.3 |

### 2. 业务知识消费

| 业务知识 | 关键规则 / 事实 | 转换成的体验策略 | 落点 |
|---|---|---|---|
| 权限管理-任务场景 | 权限查看和权限配置是两类不同链路，不能混写 | 员工端"我的权限"只读、"申请权限"可提交 | 页面 6.2、6.3 |
| 权限管理-治理状态模型 | 状态模型至少包含发起/待处理/通过/拒绝/生效/撤销六类状态 | 申请状态表覆盖全部六类状态 | 状态表 |
| 权限管理-体验风险模式 | 权限体验核心不是能不能配，而是能不能解释、能不能验证 | 每个状态绑定责任人、可操作、下一步 | 状态表、各节点 |
| 权限管理-体验翻译需求 | 涉及审批/生效/撤销时必说明状态责任人与下一步 | 各节点均标注系统反馈和用户下一步 | 全部交互节点 |
