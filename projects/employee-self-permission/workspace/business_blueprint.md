# Business Blueprint

## 0. 本次关键设计判断

- **建议方案**：将自助申请权限作为权限治理模式的新增选项，纳入"权限管理模式"页面统一管理，与现有治理模式（子管理、双管理员互审、权限变更审批）互斥——企业一次只能启用一种治理模式。
- **不建议方案**：做成脱离治理模式体系外的独立功能模块。这会绕过现有权限管控机制，且与 facts 中"不应脱离现有权限体系单独存在"的约束直接冲突。
- **核心理由**：管理员需要"控制是否允许自助申请"，这本身就是治理模式选择行为。嵌入现有治理模式体系意味着复用已有的模式互斥保护、操作记录和审计链路，不需要重新发明一套隔离机制。
- **必须确认**：与现有权限变更审批模式是否可以共存（例如自助申请 + 审批变更同时生效），还是完全互斥；高风险权限排除清单由谁维护、如何维护。

## 1. 一句话结论

可以做，且建议做。推荐做成权限治理模式体系下的新选项——"员工自助申请模式"，与现有治理模式互斥，管理员在企业层面一次性配置可申请范围和审批流后，员工即可在个人端查看权限并发起申请。

## 2. 需求是否成立

**判断：成立。**

需求要解决的问题是真实的：中大型企业中，权限变更集中在超管或权限管理员侧，企业规模越大、人员流动越频繁，这个矛盾越突出。员工端缺乏"我有什么权限"的可见性，也缺乏"我要申请权限"的标准化通道，只能线下找管理员，沟通成本高且授权时效不稳定。

受影响的角色明确：超管和权限管理员（减轻处理压力）、员工（获得自助能力）、审批人（新增审批场景）。

竞品参考（金蝶已有相近功能）印证了这个方向的行业合理性，不需要从零验证市场可行性。

## 3. 值不值得做

**收益：**

- 超管和权限管理员的集中处理压力可以分摊。以 200 人企业、月均 20 次权限变更估算，每次变更节省管理员约 5 分钟操作时间，月度节省约 1.7 小时。
- 员工无需等待管理员响应即可发起申请，等待时间从"不确定"变成"审批流程时长"，可预期性提升。
- 权限申请从线下沟通变成有记录、可追踪的标准化流程，治理可审计性提高。

**成本：**

- 开发范围：管理端新增模式配置页（可申请范围配置 + 审批流配置）、员工端新增"我的权限"页和"申请权限"页、审批端对接现有审批中台、申请记录页。整体属于中等开发量。
- 维护成本：模式本身不复杂，主要维护点在可申请范围配置和审批流配置的易用性持续优化。
- 培训成本：facts 提到一线反馈的培训顾虑有合理性。缓解方式是在管理端配置页提供足够的引导说明，在员工端提供自解释的页面设计。属于可控风险。
- 认知负担：仅对管理员有新增学习成本（理解新模式与现有模式的区别），对员工是解决既有痛点的正向体验。

**综合判断：收益大于成本。培训风险属于可控范围，不是阻塞性因素。建议推进，但需要先落实高风险权限排除和审批异常兜底两个关键设计点。**

## 4. 应该做成什么能力形态

比较两种路径：

**路径 A：作为权限治理模式的新增选项（推荐）**

将"员工自助申请权限"定义为第四种权限治理模式，纳入"权限管理模式"页面统一管理。与子管理、双管理员互审、权限变更审批三种已有模式并列，企业一次只能启用一种。

- 优点：复用现有治理模式体系的安全保护（模式切换需超管操作、操作有记录、关闭时有检查逻辑），不重复建设安全隔离机制。管理员理解和配置的心智模型与现有治理模式一致——"选择一种治理方式，配上范围和规则"。
- 缺点：如果未来需要"自助申请 + 子管理"同时生效（如子管理员代为审批员工申请），当前互斥设计会成为限制。但这是未来假设性需求，不应基于假设过度设计。

**路径 B：作为独立功能模块，与治理模式无关**

做成一个独立的"员工自助申请"功能，有自己的开关和配置入口，不与治理模式互斥。

- 优点：灵活，可以与任何治理模式叠加使用。
- 缺点：绕过了现有治理模式体系的保护——如果企业同时启用子管理模式和自助申请，子管理员的授权范围可能与员工自助申请范围产生交叉或冲突，需要额外设计叠加规则，复杂度显著上升。且与 facts 中"不应脱离现有权限体系单独存在"的约束冲突。

**推荐路径 A。** 初版先做互斥，确保规则清晰、不被滥用。如果后续有客户明确需要叠加场景，再基于实际案例放开。

## 5. 推荐业务方案

### 5.1 角色与职责

- **超级管理员 / 权限管理员**：在企业层面决定是否启用自助申请模式；配置可申请权限范围（按角色或功能权限划定）；配置审批流程；关闭模式并处理进行中的申请。这是配置方。
- **员工**：查看自己已有的权限列表；发现缺少权限后发起申请，填写申请原因；查看自己的申请记录和审批状态。员工不是审批方，也不能配置范围。
- **审批人**：收到员工申请后，查看申请人、申请内容、申请原因；决定同意或拒绝。审批人由审批流配置决定，不固定为特定角色。
- **系统**：审批同意后自动完成授权；审批拒绝后权限不变；记录所有关键操作；处理审批超时升级。

### 5.2 主流程闭环

**第一条链路：管理员开启模式**

1. 超管或权限管理员进入"权限管理模式"页面。
2. 在现有治理模式选项中，选择"员工自助申请模式"。
3. 系统检查当前是否有其他治理模式启用。如有，提示需要先关闭当前模式，并说明关闭影响。
4. 管理员确认后，系统引导进入配置：设置可申请范围（从已有角色和功能权限中选择可被申请的项）、设置审批流程。
5. 配置完成后，管理员确认开启。系统记录操作日志，模式状态变更为"已开启"。

**第二条链路：员工查看权限**

1. 员工通过导航入口进入"我的权限"页面。
2. 页面展示员工当前拥有的权限列表，按应用或功能域分组。每条权限标明来源（如"通过角色 xxx 获得""管理员直授""自助申请"），帮助员工理解已有权限。
3. 如果员工需要额外权限，页面提供"申请权限"入口。

**第三条链路：员工申请权限**

1. 员工在"我的权限"页点击"申请权限"，进入申请表单。
2. 申请表单展示管理员配置的可申请范围——员工只能从已开放的范围中选择，不能自由输入。员工选择目标权限或角色，填写申请原因。
3. 员工提交申请。系统校验：是否已有该权限（如有则提示无需申请）、是否有同权限的审批中申请（如有则提示勿重复提交）。
4. 提交成功后，申请单进入"审批中"状态，员工可在"申请记录"中追踪。

**第四条链路：审批人处理申请**

1. 审批人收到待审批的权限申请。
2. 审批人查看申请详情：申请人姓名和部门、申请的权限或角色、申请原因。
3. 审批人决定同意或拒绝：
   - 同意：申请单变为"已通过"，系统自动完成授权，员工收到通过通知。
   - 拒绝：申请单变为"已拒绝"，权限不变，审批人可填写拒绝原因，员工收到拒绝通知及原因。
4. 审批结果记入操作日志。

**第五条链路：员工查看申请记录**

1. 员工进入"申请记录"页，看到自己提交的所有申请列表，每条显示：申请的权限或角色、提交时间、当前状态、审批人和审批时间。
2. 员工可点击单条申请查看详情。审批中的申请支持撤销（如确认支持撤销功能）。

**第六条链路：管理员关闭模式**

1. 超管或权限管理员进入"权限管理模式"页面，选择关闭自助申请模式。
2. 系统检查当前是否有审批中的申请。如有，提示管理员处理，提供选项：等待全部申请审批完成后自动关闭（推荐），或立即关闭并批量拒绝所有审批中申请。
3. 管理员确认关闭方案后执行。模式状态变更为"已关闭"。
4. 已通过该模式获得的权限默认保留——回收权限应通过权限移除路径处理，不应与模式开关耦合。
5. 关闭后，员工端"我的权限"页不变，但"申请权限"入口关闭或置灰。

### 5.3 前置配置

- **可申请范围**：从已有角色和功能权限中勾选可被员工申请的项。默认不勾选任何项，管理员必须主动选择。系统对平台级高危操作（删除企业、修改安全设置、管理其他管理员等）做显式标注和默认排除。
- **审批流程**：对接审批中台配置审批人或审批规则。至少需设置一个有效的审批链路，审批人不存在或链路不完整时拒绝保存。
- **员工端入口**：建议在员工工作台或全局导航中新增"我的权限"入口，与"申请权限""申请记录"共用入口。

### 5.4 结果回写与记录沉淀

- 模式开启、配置修改、关闭操作写入操作日志。
- 每次申请提交、审批同意或拒绝写入操作日志。
- 审批同意后的授权结果写入权限记录，权限来源标记为"自助申请"。
- 申请单本身保留为独立业务记录，不随权限回收而删除。

## 6. 必须守住的规则和边界

**不能放开的限制：**

- 可申请范围必须由管理员预先配置，员工不能自由搜索和申请范围外的权限。
- 管理员配置可申请范围时，系统应显式标注平台级高危操作并默认排除。高风险权限的最终排除清单需要产品确认 [QUESTION]，但在确认前，系统至少应排除删除企业、修改安全设置、管理管理员等基础高危项。

**必须审批的场景：**

- 所有自助申请无一例外必须经过审批。不存在"低风险权限免审批"的通道。降低门槛应通过加快审批流程实现，不能取消审批。

**必须二次确认的操作：**

- 管理员关闭模式时，必须二次确认并告知关闭后的影响。
- 管理员修改已生效的配置时，需确认修改对审批中申请的影响。
- 管理员选择"立即关闭并批量拒绝"时，需额外确认并填写原因。

**必须前置说明的信息：**

- 管理员首次进入配置页时，说明该模式的工作原理、与现有治理模式的关系（互斥）、关闭后的影响。
- 员工首次进入"申请权限"页时，说明申请流程和预计审批时效。

**员工可见性边界：**

- 员工只能查看自己的权限和申请记录，这是数据层面的隔离要求。
- 审批人只能看到自己审批范围内的申请。

**防重限制：**

- 员工不能对同一权限重复提交申请（当前已有审批中申请，或已拥有该权限时）。
- 对不同权限的多条申请应被允许，不应限制。

## 7. 主要风险与保护策略

**风险一：可申请范围配置过宽**

- 风险：管理员将敏感角色或高危权限纳入可申请范围，员工可能通过申请获得不适当的权限，突破安全边界。
- 缓解：（1）配置界面显式标注高危权限并默认排除；（2）审批环节是第二道防线，审批人需对申请内容做判断而非机械通过；（3）操作日志记录每次授权结果，事后可审计。审批责任不可被 UI 提示替代——这个风险本质是业务规则问题，不是反馈形式问题。

**风险二：审批链路中断或失效**

- 风险：审批人离职、岗位变更、审批流配置错误导致申请卡死在"审批中"，员工等待无果。这是流程设计问题，需要流程层面的兜底，不能只靠提示。
- 缓解：（1）配置审批流时校验审批人有效性，无效则拒绝保存；（2）审批超时自动提醒审批人并抄送管理员；（3）超时超阈值（建议 7 个工作日 [QUESTION]）后，系统自动升级到管理员处理。

**风险三：模式互斥引发切换摩擦**

- 风险：企业从现有治理模式切换到自助申请模式时，管理员因不了解切换后果而不敢操作。
- 缓解：模式切换时系统显式列出当前生效规则和进行中的流程，告知切换后处理方式。切换需二次确认。

**风险四：培训成本导致中小客户不启用**

- 风险：facts 提到一线反馈——开放给员工需要教会更多人使用，小企业或流动性大的企业可能不愿启用。
- 缓解：这是体验设计需要重点解决的问题，不是阻塞性业务风险。管理端和员工端都需要做到自解释。管理端需清晰的配置引导，员工端需让流程自然可理解。

**风险五：关闭模式后审批中申请引发员工不满**

- 风险：管理员强制关闭并批量拒绝时，已提交申请但被拒的员工可能对系统失去信任。
- 缓解：默认推荐"等待审批中的申请自然处理完再关闭"，仅在紧急情况下提供强制关闭选项并二次确认。关闭前通知受影响的员工。

## 8. 方案承接要求

后续 experience 阶段必须承接以下内容：

**必须覆盖的角色：**
- 配置方：超级管理员 / 权限管理员（管理端配置和查看模式状态）
- 申请方：员工（员工端查看权限、发起申请、追踪记录）
- 审批方：审批人（审批端处理申请、查看详情）

**必须闭环的主流程：**
- 管理员：进入权限管理模式页 → 选择自助申请模式 → 配置可申请范围 → 配置审批流 → 确认开启 → 查看模式状态和操作记录
- 管理员：进入权限管理模式页 → 关闭模式 → 系统检查进行中申请 → 选择处理方式 → 确认关闭
- 员工：进入我的权限页 → 查看已有权限 → 点击申请权限 → 从可申请范围中选择 → 填写原因 → 提交 → 看到提交成功反馈 → 在申请记录中追踪
- 审批人：收到审批通知 → 查看申请详情 → 同意或拒绝 → 看到处理结果 → 系统自动授权（如同意）
- 员工：收到审批结果通知 → 查看权限变化（如通过）或拒绝原因（如拒绝）

**必须处理的异常：**
- 管理员配置可申请范围时，系统标注高风险项并引导排除。配置不完整时不允许开启。
- 管理员配置审批流时，审批规则无效则拒绝保存并给出具体无效原因。
- 员工申请时，系统校验是否已有该权限或有同权限审批中的申请，给出明确提示。
- 审批超时后系统自动升级处理，通知管理员介入。
- 管理员关闭模式时检测到审批中申请，提供两种处理方案。强制关闭需二次确认。
- 员工越权访问他人数据时，数据层拦截。

**必须解释的状态：**
- 模式状态：已关闭 / 配置中 / 已开启
- 申请单状态：审批中 / 已通过 / 已拒绝 / 已撤销 / 已关闭
- 权限来源标记：自助申请 / 管理员直授 / 角色关联

**必须保护的风险：**
- 越权申请（范围外权限不可申请）
- 重复申请（同权限防重校验）
- 审批链路失效（审批人有效性校验 + 超时升级机制）
- 模式关闭时的状态丢失（关闭前处理进行中申请，已授权权限不回收）

**可作为设计建议：**
- 员工端"我的权限"页展示权限来源、按应用分组
- 首版不支持申请附件上传，降低复杂度
- 审批人不修改申请内容，只同意或拒绝
- 首版仅支持角色和功能权限的申请，暂不支持数据权限范围选择
- 审批中的申请支持员工主动撤销

**报错或阻断的业务依据判断：**
- 员工申请范围外权限：属于权限模型问题，系统应阻止提交，提示"该权限不在可申请范围内，请联系管理员"
- 审批人失效导致申请卡死：属于流程设计问题，已通过超时升级机制在业务方案层解决，experience 阶段只需设计通知和升级入口
- 管理员强制关闭时被拒绝的申请：属于业务规则问题，员工看到的反馈应说明"企业已关闭自助申请权限"而非仅说"申请被拒绝"

## 9. 待确认问题

**1. [QUESTION] 自助申请模式与现有权限变更审批模式是否可以共存？**

当前方案假设完全互斥。但存在场景：企业希望管理员侧的权限变更仍走审批，同时员工可自助申请。如果需共存，互斥设计需要调整。建议产品侧确认策略。

**2. [QUESTION] 哪些角色或权限属于高风险、不可申请范围？**

决定配置界面的默认排除逻辑。在没有正式名单前，建议系统至少排除删除企业、修改安全设置、管理其他管理员等基础高危项。

**3. [QUESTION] 审批超时升级的阈值是多少？**

当前建议约 7 个工作日。不同企业审批节奏差异大，是否需要支持管理员自定义阈值也需要确认。

**4. [QUESTION] 审批中的申请是否支持员工主动撤销？**

当前方案倾向于支持。但需确认是否符合整体审批产品的设计惯例。

**5. [QUESTION] 服务人员是否完全不支持该能力？**

facts 中倾向不开放，但未最终确认。如果服务人员也需要申请权限访问企业内部资源，此限制需重新评估。

## 附录：事实、知识与判断追踪

本文档的关键判断均基于以下事实和知识依据。

**需求成立判断** → 依据 facts 中的任务概述（管理员集中处理的痛点、员工线下沟通的成本）和竞品参考（金蝶已有相近功能，行业方向已验证）。

**值得做的判断** → 依据 facts 中的价值判断（200 人企业典型场景、月均 20 次权限变动、至少 3 家客户的目标）和已知风险中的培训成本反馈（一线顾虑）。成本估算基于 facts 功能范围列出的 7 项功能模块。

**能力形态推荐（路径 A / 治理模式方案）** → 依据 facts 中关键业务约束第 1 条（不应脱离现有权限体系）和第 8 条（可能与已有治理模式互斥），结合知识库中的能力地图（三种已有治理模式的页面承载方式）和查询与配置路径（治理配置路径的现有结构）。路径 B 被排除的原因是与 facts 约束第 1 条直接冲突。

**高风险权限排除** → 依据 facts 中关键业务约束第 2 条（不能让员工申请所有高风险权限）和开放问题第 3、4 条。系统默认排除的具体项（删除企业、修改安全设置、管理管理员）参考了知识库中角色边界一节对超管权限范围的描述——这些权限仅超管持有，不应开放给员工申请。

**模式互斥设计** → 依据 facts 中已知风险第 4 条（模式互斥风险）和开放问题第 1 条。互斥设计的架构依据来自知识库中的查询与配置路径——现有三种治理模式均通过同一个"权限管理模式"页面承载，模式之间不叠加。

**审批异常兜底（超时升级）** → 依据 facts 中初步业务规则第 7.3 节第 4 条（审批人缺失或异常时需兜底）。超时升级策略为本阶段业务判断，阈值需产品确认。
