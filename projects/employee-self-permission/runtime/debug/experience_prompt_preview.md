## 2. facts 摘要

- > 输入来源：`projects/employee-self-permission/source/requirement.md`（原始需求文档）、`projects/employee-self-permission/source/background.md`（背景资料）。本文档基于以上输入理解重述，信息不足处已标记 [GAP]。
- 当前状态：企业员工的权限由超级管理员或权限管理员集中分配。员工不知道自己有什么权限，需要权限时只能私下找管理员处理。
- 痛点：中大型企业员工数量多、人员流动频繁，权限新增、变更、核对的工作量集中在管理员侧。部分企业的超管就是老板本人，业务人员需要权限时要线下找人，沟通成本高、授权时效不稳定。
- 方案方向：新增一种"员工自助申请权限"能力，让员工可以自己查看已有权限、主动申请所需权限、追踪申请状态。管理员保留对是否开启、可申请范围、审批流程的完全控制。申请必须经过审批后才自动授权。
- 涉及角色：超级管理员、权限管理员、员工、审批人。
- 主要场景：管理员配置自助申请模式 → 员工查看自己权限 → 员工提交权限申请 → 审批人处理申请 → 管理员关闭自助申请能力。
- 本次任务类型为新建能力，覆盖全链路（facts → business → experience）。
- ---
- **自助申请权限模式开关**
- 由超级管理员或权限管理员控制。开启时需要先设置可申请范围和审批方式；关闭时需要检查是否存在未完成的申请。这是整个自助申请能力的总闸门。
- **我的权限**
- 员工侧功能。员工可以查看自己当前拥有的权限（功能权限、数据权限、角色），减少向管理员的反复确认。员工只能看到自己的权限，不能查看他人。

## 3. business 核心判断与承接要求

### 5. 推荐业务方案
- **超级管理员 / 权限管理员**：在企业层面决定是否启用自助申请模式；配置可申请权限范围（按角色或功能权限划定）；配置审批流程；关闭模式并处理进行中的申请。这是配置方。
- **员工**：查看自己已有的权限列表；发现缺少权限后发起申请，填写申请原因；查看自己的申请记录和审批状态。员工不是审批方，也不能配置范围。
- **审批人**：收到员工申请后，查看申请人、申请内容、申请原因；决定同意或拒绝。审批人由审批流配置决定，不固定为特定角色。
- **系统**：审批同意后自动完成授权；审批拒绝后权限不变；记录所有关键操作；处理审批超时升级。
- **第一条链路：管理员开启模式**
- 1. 超管或权限管理员进入"权限管理模式"页面。
- 2. 在现有治理模式选项中，选择"员工自助申请模式"。
- 3. 系统检查当前是否有其他治理模式启用。如有，提示需要先关闭当前模式，并说明关闭影响。
- 4. 管理员确认后，系统引导进入配置：设置可申请范围（从已有角色和功能权限中选择可被申请的项）、设置审批流程。
- 5. 配置完成后，管理员确认开启。系统记录操作日志，模式状态变更为"已开启"。
- **第二条链路：员工查看权限**
- 1. 员工通过导航入口进入"我的权限"页面。

### 6. 必须守住的规则和边界
- **不能放开的限制：**
- 可申请范围必须由管理员预先配置，员工不能自由搜索和申请范围外的权限。
- 管理员配置可申请范围时，系统应显式标注平台级高危操作并默认排除。高风险权限的最终排除清单需要产品确认 [QUESTION]，但在确认前，系统至少应排除删除企业、修改安全设置、管理管理员等基础高危项。
- **必须审批的场景：**
- 所有自助申请无一例外必须经过审批。不存在"低风险权限免审批"的通道。降低门槛应通过加快审批流程实现，不能取消审批。
- **必须二次确认的操作：**
- 管理员关闭模式时，必须二次确认并告知关闭后的影响。
- 管理员修改已生效的配置时，需确认修改对审批中申请的影响。
- 管理员选择"立即关闭并批量拒绝"时，需额外确认并填写原因。
- **必须前置说明的信息：**
- 管理员首次进入配置页时，说明该模式的工作原理、与现有治理模式的关系（互斥）、关闭后的影响。
- 员工首次进入"申请权限"页时，说明申请流程和预计审批时效。

### 7. 主要风险与保护策略
- **风险一：可申请范围配置过宽**
- 风险：管理员将敏感角色或高危权限纳入可申请范围，员工可能通过申请获得不适当的权限，突破安全边界。
- 缓解：（1）配置界面显式标注高危权限并默认排除；（2）审批环节是第二道防线，审批人需对申请内容做判断而非机械通过；（3）操作日志记录每次授权结果，事后可审计。审批责任不可被 UI 提示替代——这个风险本质是业务规则问题，不是反馈形式问题。
- **风险二：审批链路中断或失效**
- 风险：审批人离职、岗位变更、审批流配置错误导致申请卡死在"审批中"，员工等待无果。这是流程设计问题，需要流程层面的兜底，不能只靠提示。
- 缓解：（1）配置审批流时校验审批人有效性，无效则拒绝保存；（2）审批超时自动提醒审批人并抄送管理员；（3）超时超阈值（建议 7 个工作日 [QUESTION]）后，系统自动升级到管理员处理。
- **风险三：模式互斥引发切换摩擦**
- 风险：企业从现有治理模式切换到自助申请模式时，管理员因不了解切换后果而不敢操作。
- 缓解：模式切换时系统显式列出当前生效规则和进行中的流程，告知切换后处理方式。切换需二次确认。
- **风险四：培训成本导致中小客户不启用**
- 风险：facts 提到一线反馈——开放给员工需要教会更多人使用，小企业或流动性大的企业可能不愿启用。
- 缓解：这是体验设计需要重点解决的问题，不是阻塞性业务风险。管理端和员工端都需要做到自解释。管理端需清晰的配置引导，员工端需让流程自然可理解。

### 8. 方案承接要求
- 后续 experience 阶段必须承接以下内容：
- **必须覆盖的角色：**
- 配置方：超级管理员 / 权限管理员（管理端配置和查看模式状态）
- 申请方：员工（员工端查看权限、发起申请、追踪记录）
- 审批方：审批人（审批端处理申请、查看详情）
- **必须闭环的主流程：**
- 管理员：进入权限管理模式页 → 选择自助申请模式 → 配置可申请范围 → 配置审批流 → 确认开启 → 查看模式状态和操作记录
- 管理员：进入权限管理模式页 → 关闭模式 → 系统检查进行中申请 → 选择处理方式 → 确认关闭
- 员工：进入我的权限页 → 查看已有权限 → 点击申请权限 → 从可申请范围中选择 → 填写原因 → 提交 → 看到提交成功反馈 → 在申请记录中追踪
- 审批人：收到审批通知 → 查看申请详情 → 同意或拒绝 → 看到处理结果 → 系统自动授权（如同意）
- 员工：收到审批结果通知 → 查看权限变化（如通过）或拒绝原因（如拒绝）

### 9. 待确认问题
- **1. [QUESTION] 自助申请模式与现有权限变更审批模式是否可以共存？**
- 当前方案假设完全互斥。但存在场景：企业希望管理员侧的权限变更仍走审批，同时员工可自助申请。如果需共存，互斥设计需要调整。建议产品侧确认策略。
- **2. [QUESTION] 哪些角色或权限属于高风险、不可申请范围？**
- 决定配置界面的默认排除逻辑。在没有正式名单前，建议系统至少排除删除企业、修改安全设置、管理其他管理员等基础高危项。
- **3. [QUESTION] 审批超时升级的阈值是多少？**
- 当前建议约 7 个工作日。不同企业审批节奏差异大，是否需要支持管理员自定义阈值也需要确认。
- **4. [QUESTION] 审批中的申请是否支持员工主动撤销？**
- 当前方案倾向于支持。但需确认是否符合整体审批产品的设计惯例。
- **5. [QUESTION] 服务人员是否完全不支持该能力？**
- facts 中倾向不开放，但未最终确认。如果服务人员也需要申请权限访问企业内部资源，此限制需重新评估。
