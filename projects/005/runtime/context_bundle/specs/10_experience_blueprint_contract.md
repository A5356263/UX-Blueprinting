# 体验蓝图构建合同（正式替换稿）

## 目标

定义如何基于 `business_blueprint.md`、`facts.md`、业务知识与设计指南生成 `experience_blueprint.md`，并将 experience blueprint（体验蓝图层）正式定义为 **experience architecture layer（体验架构层）** 与 **UI-ready blueprint layer（可进入 UI 设计的蓝图层）**。

本阶段的核心目标不再只是“把业务翻译成几条体验要求”，而是把已经通过 business judgment（业务判断）的能力，进一步转译为可参与页面与交互方案讨论的体验蓝图，使体验设计师、产品经理与相关业务方能够基于该蓝图讨论并推进以下问题：

- information architecture（信息架构）应如何组织
- task flow（任务流）应如何串联
- page set（页面集合）与 window set（窗口集合）应如何划分
- 页面中哪些信息应优先展示，哪些应延后展示
- page region（页面区块）应如何分配
- 各页面的核心内容、状态反馈、异常提示与引导信息应如何安排
- copy contract（文案合同）应如何定义，才能减少歧义、疑惑与误解
- 哪些内容必须显性解释，哪些内容不应打断主任务

本合同兼容当前仓库三阶段主链路，不改变既有主文件命名、主阶段顺序与归档方式；只升级 experience blueprint（体验蓝图层）的输出深度、表达形态与下游可用性。

## 阶段定位

体验蓝图阶段是主链路的第三个业务阶段。

它负责：

- 基于通过业务审视的 `business_blueprint.md` 建立体验立场
- 将业务规则、边界、依赖与风险转译为信息架构与任务流
- 定义页面 / 抽屉 / 弹窗 / 子页等交互载体的角色分工
- 定义页面级与窗口级的信息优先级、区块安排与主要状态
- 定义关键场景下的页面内容合同、反馈合同与文案合同
- 说明用户在当前任务链路中为什么会困惑，以及系统应如何解释
- 为后续 UI 设计、原型设计与详细方案讨论提供中低保真蓝图基础

它不负责：

- 重写业务规则或推翻业务立场
- 发明未被 business（业务层）确认的能力
- 输出高保真视觉稿
- 输出像素级布局稿
- 输出品牌样式、色彩、动效、组件库选型
- 输出前端实现方案或研发架构方案

## 输入前置条件

进入本阶段前，至少应具备：

- `projects/<project-id>/workspace/facts.md`
- `projects/<project-id>/workspace/business_blueprint.md`
- 任务显式引用的 business knowledge（业务知识）
- 任务显式引用的 guideline knowledge（设计指南）
- 任务显式引用的 Wiki（维基）
- 当前阶段模板与合同文件

如存在以下文件，也应优先读取：

- `projects/<project-id>/workspace/gap_list.md`
- `projects/<project-id>/runtime/context_manifest.json`
- `projects/<project-id>/runtime/task_card_resolved.json`
- `projects/<project-id>/runtime/gates/business_gate_status.json`
- `projects/<project-id>/runtime/gates/business_gate_report.md`

## 输入质量标准

进入体验阶段前，`business_blueprint.md` 至少应达到：

- 评审对象与任务边界明确
- 领域基线明确
- 合理性判断、能力归位判断与最终业务立场明确
- 关键规则、依赖与风险已稳定
- 不阻断体验推导的 gap（缺口）已显式保留
- 能够回答“该能力为什么成立、放在哪层成立、哪些风险必须被体验承接”

如果 `business_blueprint.md` 仍停留在摘要级复述，无法支撑 IA（信息架构）与页面层决策，则必须先回到 business（业务层）补齐，而不是硬写体验蓝图。

## 知识使用边界

本阶段必须同时读取任务显式引用的 business knowledge（业务知识）与 guideline knowledge（设计指南），但要遵循以下边界：

### 1. business-first translation（先业务，后体验转译）

体验蓝图中的任何页面、流程、信息安排与文案要求，都必须先有稳定的 business stance（业务立场）作为依据。

### 2. 业务知识用于守住业务语义

业务知识在本阶段主要用于：

- 防止体验方案偏离领域逻辑
- 防止用体验便利绕过治理约束
- 防止把查询、申请、审批、授权、审计等不同层级混写
- 校准角色责任、风险边界与结果语义

### 3. 设计指南用于建立体验推导依据

设计指南在本阶段主要用于：

- 选择合适的任务结构与页面承载方式
- 判断应先解释、先选择、先确认还是先展示结果
- 判断哪些信息需要前置暴露，哪些可以渐进披露
- 判断文案、提示、反馈与保护策略的表达方式
- 判断页面区块、流程节奏与错误防护的设计原则

### 4. 只读取命中的指南，不整包展开

构建体验蓝图时，应优先通过 Wiki 命中相关 guideline 主题，再回查命中的 `knowledge/raw/guidelines/<topic>.md` 原文；不应整包展开全部指南。

### 5. 不得用设计偏好替代业务约束

页面“更顺手”并不天然优先于治理规则、审批闭环、边界控制与审计要求。本阶段不得为了视觉或交互简洁而消解关键业务保护。

## 构建规则

### 体验承接优先级

experience 阶段不需要承接所有 facts 和 business judgments。

但必须优先承接会影响以下内容的上游判断：

- 页面入口与承载方式
- 主任务流与分支流程
- 状态变化与结果反馈
- 异常阻断与失败解释
- 风险保护与二次确认
- 文案解释责任
- 帮助入口与补充说明

如果某个 business judgment 涉及治理规则、依赖条件、状态闭环、异常阻断或风险保护，experience 应优先判断它是否需要落到页面、流程、状态矩阵、风险保护或文案合同中。

### 1. 体验必须承接 business blueprint（业务蓝图）

体验蓝图中的每个页面、窗口、任务流节点、信息区块与文案要求，都应能追溯到：

- `business_blueprint.md` 中的最终业务立场、能力归位判断与关键规则
- `facts.md` 中的关键事实、状态、依赖与异常
- 已命中的 guideline principles（设计原则）

### 2. 输出必须从“要求”升级到“蓝图”

本阶段不应只输出抽象体验要求，而应给出可讨论的蓝图结构，包括但不限于：

- IA（信息架构）
- task flow（任务流）
- page inventory（页面清单）
- page-region layout（页面区块布局）
- content contract（内容合同）
- copy contract（文案合同）
- state and feedback matrix（状态与反馈矩阵）

### 3. 核心区不用表格，附录保留表格与追踪

体验蓝图核心区（1-6）不能按材料清单堆表格，必须按交互流程组织可读内容。

核心区应优先使用：

- 结构化列表
- 节点分层标题（`### 节点 / 流程 / 异常 / 页面`）
- 文本流程描述
- 文本区块图（如 ` ```text `）

附录区（A-E）保留结构化表格与机器追踪字段，用于审计和回溯。

### 4. 先确定承载，再写内容

必须先明确该信息或动作应由什么承载体承接：

- 独立页面
- 配置页
- 详情页
- 抽屉
- 弹窗
- 二次确认弹窗
- 子页面
- 内嵌区块

不得在承载体未定义时直接堆叠体验要求。

### 5. 先确定主任务，再安排信息优先级

体验蓝图必须显式说明：

- 当前页面的 primary task（主任务）
- 次任务与辅助任务
- 哪些信息应首屏暴露
- 哪些信息可延迟到下一步或辅助层
- 哪些信息必须通过状态反馈或提示文案显式解释

### 6. 页面要回答“看什么、做什么、为什么这样排”

每个关键页面 / 窗口都必须至少回答：

- 用户进入该载体后首先看到什么
- 用户在这里要完成什么动作
- 哪些信息是决策必需信息
- 哪些信息是风险提醒
- 哪些信息是状态反馈
- 为什么要这样排序

### 7. 文案不是装饰，而是解释系统语义

文案合同必须覆盖：

- 页面标题
- 说明文案
- 字段标签
- 空状态文案
- 提示文案
- 校验文案
- 错误文案
- 成功反馈文案
- 状态标签文案
- 二次确认文案

并明确其职责是：解释规则、减少歧义、降低误解、引导决策，而不是单纯装饰页面。

### 8. 风险与保护必须落到页面/流程/文案

business（业务层）暴露的风险不能停留在抽象层。本阶段必须说明这些风险在体验层如何被承接，例如：

- 通过信息前置暴露规避误解
- 通过流程拆分避免误操作
- 通过状态反馈帮助用户理解结果
- 通过阻断提示、帮助链接、解释文案降低困惑

### 9. 页面与流程需覆盖主状态与异常状态

不能只描述 happy path（顺利路径）。体验蓝图必须覆盖：

- 初始态
- 空态
- 已配置态
- 不可操作态
- 校验失败态
- 审批中 / 处理中状态
- 操作成功态
- 操作失败态
- 在途阻断 / 冲突提示态

### 10. 不越权到高保真视觉稿与实现稿

本阶段允许输出低到中保真的页面区块图与文本线框，但不得输出：

- 高保真视觉设计稿
- 品牌样式说明
- 精确像素与栅格规范
- 组件开发实现说明
- 前端技术栈或接口设计

## 输出要求

本阶段至少输出：

- `projects/<project-id>/workspace/experience_blueprint.md`
- `projects/<project-id>/workspace/interaction_map.json`（作为核心区首选渲染输入）

如体验层存在重要缺口，也可以同步补充：

- `projects/<project-id>/workspace/gap_list.md`

如果缺少 `interaction_map.json`，允许使用代码兜底渲染 `experience_blueprint.md`，但必须显式标注 fallback 告警，不得伪装为正式体验地图。

## experience_blueprint.md 结构要求

`experience_blueprint.md` 必须至少包含以下部分：

- `1. 交互流程总览`
- `2. 主交互流程`
- `3. 次交互流程`
- `4. 异常与阻断流程`
- `5. 页面 / 弹窗 / 抽屉设计`
- `6. 状态与反馈文案`
- `附录 A：上游依据`
- `附录 B：原始信息架构与页面清单`
- `附录 C：页面 / 流程追踪映射`
- `附录 D：设计原则引用`
- `附录 E：原始状态 / 文案 / 风险矩阵`

- 核心区（1-6）优先服务人工评审，必须使用体验设计师可直接理解的大白话。
- 核心区（1-6）不是原始 `ExperienceModel` 字段的直接展开，必须经过可读化整理后输出。
- 推荐页面和入口不再单独成章，必须融入流程节点。
- 交互流程节点写文案策略；页面/弹窗/抽屉设计写具体文案草案。
- 核心区禁止使用表格；附录区（A-E）保留 `P-xx / TF-xx / PR-xx / TR-xx / J-xx / F-xx / source_path / trace / coverage / warning / gap` 等机器可读信息。
- 页面名称和流程说明必须由当前 facts / business judgment 动态生成，不得写死具体业务域页面名。

### 结构说明

#### 1. 交互流程总览

说明主流程、次流程、异常流程及其衔接关系，先建立整体阅读路径。

#### 2. 主交互流程

按节点展开主路径，至少包含用户动作、系统反馈、下一步、前置解释和异常关注。

#### 3. 次交互流程

承接查看说明、查看记录、补充信息、修改、撤回、重试等非主路径任务。

#### 4. 异常与阻断流程

说明失败/不可操作/条件不满足等场景的发生时机、用户困惑、解释责任和可执行下一步。

#### 5. 页面 / 弹窗 / 抽屉设计

逐个承载体展开页面目标、进入条件、结构、首屏重点、操作、状态反馈、异常反馈、具体文案和完成后去向。

#### 6. 状态与反馈文案

汇总关键状态的含义、出现位置、用户可做、系统反馈、建议文案与后续去向。

#### 附录 A：上游依据

保留承接的业务判断、规则、风险、开放问题与缺口。

#### 附录 B：原始信息架构与页面清单

保留 IA 明细、页面清单、区块布局示意和信息优先级合同。

#### 附录 C：页面 / 流程追踪映射

保留页面、流程、文案对象到业务判断/事实/原则的追踪关系。

#### 附录 D：设计原则引用

保留命中的 `PR-xx`、命中原因和作用位置。

#### 附录 E：原始状态 / 文案 / 风险矩阵

保留 coverage、warning、gap 以及状态/文案/风险原始矩阵。

## 表达形态要求

体验蓝图必须优先使用最利于下游消费的表达方式，不得通篇只写散文式说明。

- 核心区（1-6）使用节点化标题 + 结构化列表 + 文本流程说明，不使用表格。
- 附录区（A-E）可使用表格、文本流程图、文本区块图、矩阵与编号追踪。

## 合格标准

一个合格的 `experience_blueprint.md` 至少满足：

- 能够承接稳定的 business（业务层）立场
- 已给出明确的信息架构与任务流
- 已明确关键页面 / 窗口集合
- 已说明页面级信息优先级与区块安排
- 已把关键风险落实为页面、流程或文案保护
- 已给出关键文案的语义要求
- 已覆盖主要状态与异常状态
- 表达形态不只是一段段纯文案
- 未越权到高保真视觉稿或前端实现

## 阶段完成标准

体验阶段可视为完成，当以下条件同时满足：

- `experience_blueprint.md` 已生成
- 关键页面、流程、区块与文案合同已可讨论
- 下游 UI 设计无需重新发明主结构即可继续工作
- 关键风险与保护策略已落地到页面 / 流程 / 文案层
- 主要 gap（缺口）已显式暴露
- 无明显越权内容

## Warning 条件

以下情况可进入正式检查，但必须带着 warning：

- 个别页面区块仍偏粗，需要在 UI 设计阶段继续细化
- 文案合同已定义语义目标，但示例文案仍待补充
- 个别异常状态已识别，但具体承载方式仍待确认
- IA（信息架构）已成立，但入口归属仍待补齐
- 已命中设计原则，但原则映射尚未展开到全部页面

## 失败条件

- `experience_blueprint.md` 缺失
- 体验蓝图无法追溯到 `business_blueprint.md` 或 `facts.md`
- 输出仍停留在抽象体验要求，没有形成页面/流程/信息蓝图
- 没有信息架构、任务流、页面清单或区块安排
- 没有关键状态与异常态设计
- 没有文案合同或解释策略
- 只写 happy path（顺利路径），未覆盖阻断与失败
- 直接越权到高保真视觉稿、前端实现或技术方案

## 与其他模块的同步要求

本合同替换后，至少应同步检查以下模块是否需要升级：

- `templates/experience_blueprint.template.md`
- `packages/gate-experience/*`
- `packages/validate/*`
- `docs/runbook/external_ai_quickstart.md`
- 任何直接引用“体验蓝图只写体验要求、不写页面蓝图”的说明文档

如果合同已升级，但模板与 gate（闸门）仍按旧标准检查，会导致体验蓝图继续被压缩为抽象总结，无法发挥本合同的效果。
