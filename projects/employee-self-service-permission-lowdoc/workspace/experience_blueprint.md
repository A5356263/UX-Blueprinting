# Experience Blueprint

> 输入来源：`workspace/facts.md`、`workspace/business_blueprint.md`、`runtime/uxb_route_decision.json`

## 0. 本次关键设计判断

**判断：**

本次体验方案的核心是"把配置端和申请端拆开，用清晰的状态链路串联四角色协作"，重点放在状态可见性、异常兜底和管理员的配置安全感上。

**主要影响：**

1. 四角色视角分离（超管配置、权限管理员维护、员工申请查看、审批人处理），每个角色有其独立的任务路径和状态视图
2. 管理后台需要在现有全局治理配置中增加新模式开关和范围配置，信息密度较高，需注意配置引导
3. 员工端的核心体验不在"申请表单多好看"，而在"我缺了什么权限"→"能申请什么"→"申请后什么状态"这条链路
4. 异常分支多（审批人缺失升级、模式互斥提示、关闭能力时审批中申请的冲突、敏感权限过滤），需要把每条异常的处理说清楚
5. 审批通过后自动授权是无感操作，需要让员工明确感知到"权限已生效"

**建议方案：**

- 管理后台：在现有权限管理模式页增加"自助申请"模式卡片，开启前先检测双管理员模式状态并给出引导
- 管理后台：可申请范围配置用左侧候选池+右侧已选列表的双栏模式，敏感权限灰显不可选
- 员工端：在"我的权限"页面增加申请入口，同时在因无权限被拦截的页面直接提供"申请此权限"入口
- 审批端：复用现有 OA 审批待办列表，权限申请类型的卡片展示申请人、申请权限、申请原因
- 统一用"审批中/已通过/已拒绝/已撤销"四状态标签贯穿所有角色的列表和详情

**不建议方案：**

- 不建议把管理员配置和员工申请放在同一个页面，角色差异太大，混在一起会互相干扰
- 不建议申请时让员工选数据范围，第一期聚焦角色和功能权限，降低员工认知负担

**关键待确认：**

1. 员工端“我的权限”页面是否已存在；如不存在，是否接受新增页面承载申请入口
2. 因无权限被拦截时是否能在当前页直接提供申请入口，且前后端链路可行
3. 审批通过后的通知方式是否是本次核心体验策略的一部分

> 更多待确认问题详见 `## 8. 待确认问题`。

## 1. 旅程图

- 管理员：判断是否开放申请 → 完成开放配置 → 关注审批异常与白名单变化 → 确认能力稳定运行
- 员工：发现自己缺少所需权限 → 说明申请原因并发起申请 → 跟踪处理进度或撤销申请 → 确认权限已经生效
- 审批人：识别待处理申请 → 判断申请是否合理 → 给出同意或拒绝结果 → 确认结果已通知员工

### 旅程缺口

- 缺少员工离职或停用后的统一处理策略确认，影响“已关闭”状态的细化表达。
- 缺少拒绝后是否存在冷却期的最终规则，影响“重新申请”的约束边界。

## 2. 交互流程总览

**主交互节点总览：**

- 超级管理员 / 权限管理员：节点 2.1 管理员首次开启自助申请模式 → 节点 2.1a 管理员设置可申请范围 → 节点 2.1b 管理员设置审批规则
- 员工：节点 2.2 员工查看权限并发现缺口 → 节点 2.3 员工发起权限申请 → 节点 2.4 员工查看申请状态与结果
- 审批人：节点 2.5 审批人处理权限申请

**异常流程重点：**

- 管理员开启时检测到双管理员模式互斥 → 提示关闭双管理员模式
- 审批人缺失 → 逐级升级并通知
- 管理员关闭能力时存在审批中申请 → 允许走完或一键拒绝
- 员工申请了敏感权限（前端已过滤，但后端兜底） → 拒绝并说明原因
- 员工重复申请已有权限 → 提示"你已拥有此权限"
- 审批流程中员工离职或停用 → 申请自动关闭

## 3. 主交互流程

### 节点 2.1：管理员首次开启自助申请模式

**用户动作：**

管理员进入"管理后台 → 权限 → 权限管理模式"页面，看到当前已有模式的列表。点击"自助申请权限"卡片上的"开启"按钮。

**系统反馈：**

系统检测当前是否已开启双管理员模式：
- 正常：进入配置向导第一步——设置可申请范围
- 互斥冲突：弹窗提示"当前已开启双管理员模式。自助申请模式与双管理员模式互斥，如需开启请先关闭双管理员模式。"，提供"前往关闭双管理员模式"按钮，不直接替管理员操作

**需要前置解释的信息：**

- 自助申请模式是什么：允许员工自行查看权限并发起权限申请，审批通过后自动授权
- 开启前必须完成：①设置可申请范围（白名单）②设置审批规则
- 与双管理员模式互斥的影响：开启后双管理员模式将不可用，已通过双管理员模式分配的权限不受影响

**建议文案：**

- 卡片标题："员工自助申请权限"
- 卡片描述："允许员工查看自己的权限并主动申请所需权限，审批通过后自动授权"
- 状态标签（未开启）："未开启"
- 开启按钮："开启"
- 互斥提示弹窗标题："无法同时开启两个模式"

**下一步：**

配置向导 → 设置可申请范围（节点 2.1a）

### 节点 2.1a：管理员设置可申请范围（白名单配置）

**用户动作：**

管理员在配置向导中看到双栏布局——左侧是所有可配置的权限列表（按角色和功能权限分Tab），右侧是已加入白名单的权限。管理员从左侧勾选权限，点击"添加"移入右侧白名单。

敏感权限（如超管角色、审计相关权限）在左侧以灰显状态展示，无法勾选，旁边有提示"系统保护权限，不可申请"。

**系统反馈：**

- 管理员从左侧添加权限到右侧时，右侧列表实时更新
- 右侧白名单为空时显示空状态提示"尚未添加任何可申请权限，员工将无法发起申请"
- 管理员点击"下一步"进入审批设置

**建议文案：**

- 左侧标题："可配置的权限"
- 右侧标题："已开放申请的权限"
- 左侧搜索占位符："搜索权限名称"
- 敏感权限灰显提示："受系统保护，不支持申请"
- 右侧空状态："暂未添加可申请权限"
- 底部按钮："上一步"/"下一步：设置审批"

**下一步：**

配置向导 → 设置审批规则（节点 2.1b）

### 节点 2.1b：管理员设置审批规则

**用户动作：**

管理员在配置向导第三步看到审批规则设置。系统已默认填入审批人规则（直属上级→部门负责人→权限管理员逐级升级），管理员可以在此基础上调整。
管理员确认后点击"开启自助申请"完成配置。

**系统反馈：**

- 审批规则展示为可读的自然语言："申请提交后，由申请人的直属上级审批。如直属上级不存在，依次升级至部门负责人、权限管理员。"
- 管理员可选择"允许员工在审批人未处理前撤销申请"（默认开启）
- 点击"开启自助申请"后：
  - 成功：显示开启成功提示，跳转回权限管理模式页，卡片状态变为"已开启"
  - 失败：显示具体失败原因

**建议文案：**

- 页面标题："设置审批规则"
- 审批规则标签："审批人规则"
- 默认规则说明："申请提交后，由申请人的直属上级审批。如直属上级不存在，依次升级至部门负责人、权限管理员。"
- 撤销开关："允许员工在审批人未处理前撤销申请"
- 底部按钮："上一步"/"开启自助申请"
- 成功反馈："自助申请权限已开启，员工可在「我的权限」页面发起申请。"

**下一步：**

返回权限管理模式页，卡片状态变为"已开启"

### 节点 2.2：员工查看权限并发现缺口

**用户动作：**

员工从个人中心或导航进入"我的权限"页面，查看自己当前拥有的权限列表，并判断是否缺少完成工作所需的权限。

**系统反馈：**

页面加载权限列表，每个权限项显示：权限名称、权限类型（角色/功能权限）、获得方式（管理员分配/角色继承）、获得时间。
顶部有一个"申请权限"按钮。
当员工发现自己缺少所需权限时，页面明确提供下一步申请入口，不要求再去别处查找。

**需要前置解释的信息：**

- 员工首次进入时，可以有一个简短引导"这里展示你当前拥有的所有权限。如果发现缺少某个权限，可以点击「申请权限」发起申请。"

**建议文案：**

- 页面标题："我的权限"
- 申请按钮："申请权限"
- 权限来源标签："管理员分配"/"角色继承"
- 空状态（如员工尚无任何权限）："暂无权限记录。如需要使用特定功能，请联系管理员或申请权限。"
- 列表为空时的申请引导按钮："申请权限"

**下一步：**

- 点击"申请权限"→ 进入权限申请流程（节点 2.3）
- 点击某个权限项 → 查看权限详情

### 节点 2.3：员工发起权限申请

**用户动作：**

员工点击"申请权限"后进入申请页面。页面展示可申请的权限列表（即管理员配置的白名单，已过滤掉员工已有权限和敏感权限）。
员工选择要申请的权限（支持多选），填写申请原因，点击"提交申请"。

**系统反馈：**

- 权限列表加载白名单内容，过滤规则：①排除员工已有权限 ②排除系统敏感权限
- 选择权限后，右侧/下方显示已选权限的摘要
- 提交前校验：至少选择一个权限 + 申请原因不为空
- 提交成功：弹出成功提示"申请已提交，请等待审批"，跳转到申请记录列表
- 提交失败：显示失败原因

**需要前置解释的信息：**

可申请的权限由管理员配置，如果找不到需要的权限，请联系管理员。

**建议文案：**

- 页面标题："申请权限"
- 权限选择区标题："选择要申请的权限"
- 搜索占位符："搜索权限"
- 已选摘要标题："已选择 X 个权限"
- 申请原因标签："申请原因"
- 申请原因占位符："请简要说明申请该权限的原因"
- 提交按钮："提交申请"
- 成功提示："申请已提交，请等待审批"
- 空状态（无可申请权限时）："当前暂无可申请的权限，如有需要请联系管理员"
- 校验提示——未选权限："请至少选择一项权限"
- 校验提示——未填原因："请填写申请原因"

**下一步：**

提交成功后跳转到"我的申请"页面（节点 2.4）

### 节点 2.4：员工查看申请记录和状态

**用户动作：**

员工进入"我的申请"页面，查看所有申请记录。列表按提交时间倒序排列，每条显示申请权限名称、提交时间、当前状态（审批中/已通过/已拒绝/已撤销）。
支持按状态筛选。

**系统反馈：**

- 点击某条申请 → 进入申请详情页，查看完整申请内容、审批进度和审批意见
- 审批中状态的申请，如果管理员开启了撤销功能，详情页展示"撤销申请"按钮
- 已拒绝状态的申请，详情页展示拒绝原因，以及"重新申请"按钮
- 已通过状态的申请，详情页展示权限已生效的确认信息

**建议文案：**

- 页面标题："我的申请"
- 状态筛选项："全部"/"审批中"/"已通过"/"已拒绝"/"已撤销"
- 审批中标签：黄色"审批中"
- 已通过标签：绿色"已通过"，附带"权限已生效"
- 已拒绝标签：红色"已拒绝"
- 已撤销标签：灰色"已撤销"
- 撤销按钮："撤销申请"
- 撤销确认弹窗标题："确认撤销"
- 撤销确认弹窗内容："撤销后该申请将不再进入审批流程，确定要撤销吗？"
- 重新申请按钮："重新申请"
- 列表空状态："暂无申请记录"

**下一步：**

- 已通过 → 回到"我的权限"查看新增的权限
- 已拒绝 → 可重新申请
- 审批中 → 可撤销（如允许）

### 节点 2.5：审批人处理权限申请

**用户动作：**

审批人在OA审批待办列表中收到权限申请类型的待办卡片。卡片展示：申请人姓名、申请权限名称、申请时间、申请原因摘要。
审批人点击进入详情页，查看完整申请内容后，选择"同意"或"拒绝"。拒绝时需要填写拒绝原因。

**系统反馈：**

- 同意：提交后系统自动授权，向员工发送审批通过通知。审批人回到待办列表。
- 拒绝：提交后系统不授权，向员工发送拒绝通知（含拒绝原因）。审批人回到待办列表。
- 审批详情页应展示申请人信息、申请权限列表、申请原因、提交时间

**建议文案：**

- 审批详情页标题：申请的权限名称
- 申请人信息："申请人：XXX"
- 申请时间："提交时间：YYYY-MM-DD HH:mm"
- 申请原因："申请原因：XXX"
- 同意按钮："同意"
- 拒绝按钮："拒绝"
- 拒绝原因占位符："请填写拒绝原因"
- 同意后成功反馈："已同意该申请，系统已自动为申请人授权"
- 拒绝后成功反馈："已拒绝该申请，申请人将收到通知"

**下一步：**

审批完成后回到审批待办列表

## 4. 次交互流程

### 节点 3.1：管理员调整白名单配置

**用户动作：**

管理员在自助申请模式已开启的状态下，进入配置页修改白名单。从右侧"已开放申请"列表中移除某个权限，或从左侧添加新权限。

**系统反馈：**

- 从白名单移除权限时：系统提示"移除后，该权限将不再对员工开放申请。已有审批中的申请不受影响。"
- 添加新权限时：立即生效，员工端可申请列表同步更新

**建议文案：**

- 移除确认弹窗标题："确认移除"
- 移除确认内容："移除「XXX」后，员工将无法再申请此权限。已有审批中的申请不受影响。"

### 节点 3.2：管理员关闭自助申请能力

**用户动作：**

管理员在权限管理模式页点击自助申请卡片的"关闭"按钮。

**系统反馈：**

系统检测是否存在正在审批中的申请：
- 无审批中申请：直接关闭，卡片状态变为"未开启"
- 有审批中申请：弹窗提示"当前有 X 条正在审批中的申请。关闭后不再接受新申请，审批中的申请将允许正常走完。你也可以选择一键拒绝所有审批中的申请。"

**建议文案：**

- 关闭按钮："关闭"
- 关闭确认弹窗标题："确认关闭员工自助申请权限"
- 关闭确认弹窗内容（无审批中申请时）："关闭后员工将无法发起新的权限申请。已通过申请获得的权限将保留。确定要关闭吗？"
- 关闭确认弹窗内容（有审批中申请时）："当前有 X 条正在审批中的申请。关闭后不再接受新申请，审批中的申请将允许正常走完。"
- 一键拒绝按钮（可选项）："一键拒绝所有审批中的申请"
- 关闭后卡片状态标签："未开启"

### 节点 3.3：员工撤销审批中的申请

**用户动作：**

员工在"我的申请"详情页点击"撤销申请"按钮。仅审批中状态的申请可以撤销。

**系统反馈：**

弹窗确认后，申请状态变更为"已撤销"，审批人待办中移除该申请。

**建议文案：**

- 撤销确认弹窗标题："确认撤销申请"
- 撤销确认弹窗内容："撤销后该申请将不再进入审批流程。确定要撤销吗？"
- 撤销成功提示："申请已撤销"

### 节点 3.4：审批人缺失时的自动升级

**用户动作：**

无用户主动动作。系统在员工提交申请后自动检测审批人状态。

**系统反馈：**

- 直属上级存在且在职 → 正常分配审批任务，发送审批通知
- 直属上级不存在/已离职 → 系统自动上溯到部门负责人，发送审批通知，并向员工发送提示"你的直属上级暂不可用，申请已自动转交给部门负责人 XXX"
- 部门负责人也不存在 → 系统自动转交给权限管理员
- 每次升级都需通知员工和被转交的审批人

**建议文案：**

- 员工通知（审批人升级）："你的直属上级暂不可用，申请已自动转交给部门负责人「XXX」处理。"
- 审批人通知（转交）："由于「XXX」的直属上级不可用，该权限申请已自动转交给你处理。"

### 节点 3.5：因无权限被拦截时的申请入口

**用户动作：**

员工在访问某个功能时被系统拦截（无权限），拦截页面除了显示"暂无权限"外，增加"申请此权限"按钮。

**系统反馈：**

点击"申请此权限"后，直接跳转到申请页面，并自动选中被拦截的权限项（如果该权限在白名单内）。如果该权限不在白名单内或为敏感权限，则显示"该权限暂不支持自助申请，请联系管理员"。

**建议文案：**

- 拦截提示："暂无权限访问此功能"
- 申请按钮（权限在白名单内）："申请此权限"
- 申请按钮替代文案（权限不在白名单内）："暂无权限，请联系管理员"

## 5. 异常与阻断流程

### 异常 X1：双管理员模式互斥

- **发生时机：** 管理员点击"开启自助申请权限"时
- **触发条件：** 当前已开启双管理员模式
- **判断依据：** facts 关键业务规则 —— 治理模式互斥；business 规则与边界 —— 模式互斥约束
- **反馈形式：** 弹窗阻断
- **系统反馈：** "当前已开启双管理员模式。自助申请模式与双管理员模式互斥，如需开启请先关闭双管理员模式。"
- **用户下一步：** 点击"前往关闭双管理员模式"按钮跳转到对应设置页，或点击"取消"回到权限管理模式页

### 异常 X2：敏感权限被尝试申请（后端兜底）

- **发生时机：** 员工提交申请时
- **触发条件：** 前端白名单已过滤敏感权限，但后端收到包含敏感权限的申请请求（如通过接口直接调用）
- **判断依据：** facts 关键业务规则 —— 敏感权限硬排除
- **反馈形式：** 提交失败，字段级提示
- **系统反馈：** "申请中包含不支持自助申请的权限：XXX。请从申请中移除后重新提交。"
- **用户下一步：** 移除敏感权限后重新提交

### 异常 X3：员工重复申请已有权限

- **发生时机：** 员工提交申请时
- **触发条件：** 申请的权限中包含了员工当前已经拥有的权限
- **判断依据：** facts 异常与边界 —— 员工申请已有权限
- **反馈形式：** 提交前弹窗提示
- **系统反馈：** "你已拥有以下权限：XXX。是否确认仍然提交申请？（已拥有的权限将从申请中自动移除）"
- **用户下一步：** 确认后已拥有权限自动移除，仅提交确实缺少的权限

### 异常 X4：审批流程中员工离职或停用

- **发生时机：** 员工提交申请后、审批人处理前
- **触发条件：** 员工状态变为停用或离职
- **判断依据：** facts 异常与边界 —— 员工已离职或停用
- **反馈形式：** 申请状态变更 + 通知审批人
- **系统反馈：** 申请自动关闭，状态变为"已撤销"。审批人收到通知："XXX 已离职/停用，该权限申请已自动关闭。"员工端不展示该申请（或展示为已关闭状态）。
- **用户下一步：** 审批人无需处理，该申请从待办列表移除

### 异常 X5：管理员关闭能力时存在审批中申请

- **发生时机：** 管理员点击"关闭自助申请权限"时
- **触发条件：** 存在状态为"审批中"的申请
- **判断依据：** facts 关键业务规则 —— 管理员关闭能力后的处理
- **反馈形式：** 弹窗确认
- **系统反馈：** "当前有 X 条正在审批中的申请。关闭后不再接受新申请，审批中的申请将允许正常走完。你也可以选择一键拒绝所有审批中的申请。"
- **用户下一步：** 选择"允许走完"关闭，或选择"一键拒绝"后关闭，或点击"取消"

### 异常 X6：管理员修改白名单时移除已被申请的权限

- **发生时机：** 管理员从白名单中移除权限时
- **触发条件：** 该权限当前有审批中的申请
- **判断依据：** facts 开放问题 —— 管理员修改白名单时是否影响审批中的申请
- **反馈形式：** 弹窗提示
- **系统反馈：** "以下权限当前有 X 条审批中的申请：XXX。移除后，这些申请将不受影响。新申请将无法选择此权限。确定要移除吗？"
- **用户下一步：** 确认移除或取消

## 7. 状态与反馈文案

| 状态名 | 含义 | 适用对象 | 用户可操作 | 统一反馈口径 |
| --- | --- | --- | --- | --- |
| 审批中 | 申请已提交，正在等待当前审批人处理；若默认审批人缺失，系统会自动升级并转交。 | 员工、审批人 | 员工可查看详情；在管理员允许时可撤销；审批人可同意或拒绝。 | 黄色标签“审批中”；详情页展示当前审批人、提单时间和审批进度；发生升级时明确提示“已自动转交给 XXX”。 |
| 已通过 | 审批人已同意申请，系统已经完成自动授权，权限应立即在“我的权限”中可见。 | 员工、审批人 | 员工回到“我的权限”确认生效；审批人仅查看处理结果。 | 绿色标签“已通过”；详情页显示“权限已生效”；向员工发送通过通知并说明已自动授权。 |
| 已拒绝 | 审批人拒绝了申请，权限不会授予，拒绝原因必须可追溯。 | 员工、审批人 | 员工查看拒绝原因，并按策略重新申请；审批人可回看自己填写的拒绝意见。 | 红色标签“已拒绝”；详情页显示拒绝原因和审批人；提供“重新申请”入口。 |
| 已撤销 | 员工在审批人处理前主动撤回申请，审批链路就此终止。 | 员工、审批人 | 员工查看撤销记录，可重新发起新申请；审批人无需再处理。 | 灰色标签“已撤销”；详情页显示撤销时间；审批待办中移除该申请。 |
| 已关闭 | 申请因员工离职/停用或治理策略变化被系统关闭，不再继续流转。 | 员工、审批人、管理员 | 员工只能查看关闭原因；审批人不可继续处理；管理员可追溯关闭原因。 | 灰色标签“已关闭”；详情页说明关闭原因，例如“员工已离职，申请自动关闭”。 |
| 管理模式-已开启 | 企业已开放员工自助申请权限，员工入口可见，管理员可继续维护治理规则。 | 管理员 | 调整白名单、修改审批规则、关闭能力。 | 绿色状态“已开启”；卡片显示“配置”“关闭”；必要时展示当前开放范围摘要。 |
| 管理模式-未开启 | 企业尚未开放该能力，员工不能发起新申请。 | 管理员 | 点击“开启”进入配置向导。 | 灰色状态“未开启”；卡片显示“开启”；若与双管理员模式互斥，先展示阻断提示。 |

## 8. 待确认问题

1. **员工端“我的权限”页面是否已存在？**

   影响：如果不存在，需要新增页面承载入口与申请记录，影响页面结构和前端开发投入。
   建议确认方：产品

2. **因无权限被拦截时的申请入口技术可行性如何？**

   影响：影响拦截页是否能直接承接申请主流程，以及前后端是否需要补充白名单判断和动态按钮展示能力。
   建议确认方：前后端技术负责人

3. **审批通过后的通知方式是什么？**

   影响：影响员工对“权限已生效”的感知强度，以及消息触达链路的体验策略。
   建议确认方：产品 / 运营

4. **管理员关闭能力时是否提供“一键拒绝审批中申请”？**

   影响：影响管理员关闭流程的操作复杂度，也影响审批中申请的收口方式。
   建议确认方：产品

5. **申请被拒绝后是否允许重新申请，是否设置冷却期？**

   影响：影响重新申请入口、异常提示文案和申请频率控制策略。
   建议确认方：产品

## 附录：设计指南消费说明

### 设计指南消费

- `流程模式` 被用于把管理员配置、员工申请、审批处理拆成三条清晰链路，并在旅程图和交互流程里保持“先识别缺口，再进入申请，再确认结果”的一致顺序。
- `反馈与报错` 被用于定义互斥阻断、敏感权限拦截、审批升级、关闭能力确认等异常反馈形式，确保每个阻断都带有下一步动作，而不是只报错不指路。
- 这些设计原则最终落在 `## 1. 旅程图`、`## 3. 主交互流程`、`## 5. 异常与阻断流程`、`## 7. 状态与反馈文案` 四个模块中。

### 业务知识消费

- `权限管理/21_来源模型` 与 `24_治理状态模型` 被翻译成“申请通过后自动授权、并以新来源类型记录”的体验策略，因此员工端必须能看到状态变化，审批端必须闭环到授权结果。
- `权限管理/14_角色边界` 被翻译成多角色分视角表达，因此旅程图按“管理员 / 员工 / 审批人”拆行，而不是混成单一路径。
- `审批管理/10_审批管理` 被翻译成“复用既有审批中台，而非新造审批系统”的体验策略，因此审批人继续在既有待办中处理，体验蓝图只补权限申请类型的卡片和详情。
- 这些业务知识最终落在 `## 1. 旅程图`、`## 2. 交互流程总览`、`## 4. 次交互流程` 和 `## 6. 页面 / 弹窗 / 抽屉设计` 中。

### 知识缺口

- 员工离职/停用后的申请关闭策略，目前在蓝图中按“自动关闭”处理，但仍建议产品确认是否需要显示为独立的“已关闭”状态。
- “一键拒绝所有审批中申请”是否必须提供，当前作为可选策略保留，未被写死为固定规则。
