# 业务蓝图构建合同

## 目标

基于 `facts.md` 与业务知识，做出可评审的业务判断，输出 `business_blueprint.md`。

本阶段的核心是：**用业务分析师的语言回答"这需求成立吗？值不值得做？做成什么样？必须守住什么？"**

## 阶段定位

业务蓝图阶段负责：

- 判断需求是否成立、是否值得做
- 推导能力形态（独立功能 / 扩展既有功能 / 配置化 / 暂不产品化）
- 给出推荐业务方案（角色、流程闭环、关键规则）
- 明确必须守住的规则边界和风险保护策略
- 输出方案承接要求，作为 experience 阶段的输入

业务蓝图阶段不负责：

- 页面结构设计
- 具体交互细节
- 视觉方案
- 前端或后端实现方案

## 输入

- `projects/<project-id>/workspace/facts.md`
- 任务显式引用的 Wiki / 业务知识

## 输出

- `projects/<project-id>/workspace/business_blueprint.md`

## 核心写作原则

### 1. 业务大白话

核心区必须使用自然的业务语言。禁止复制 facts 中的原文碎片、禁止出现流程箭头符号（→、-->）、禁止出现 Mermaid 节点 ID。

### 2. 判断必须有依据

每个判断必须引用 facts 中的至少一个具体功能或规则作为依据。禁止用"基于需求文档的整体分析"这类不可追溯的表述。依据应使用自然语言（如"根据 facts 中 3.1 节描述的互斥校验规则..."），而不是 ID 编号。

### 3. 区分事实、判断和建议

读者应该能清楚分辨：哪句是已确认的事实、哪句是你的业务判断、哪句是对后续阶段的建议。

### 4. 不确定就说不确定

无法形成稳定判断时，写入"待确认问题"，不得硬凑结论。

### 5. 禁止 ID 编号体系

不使用 J-xx、BL-xx、OPT-xx、RSK-xx 等编号。用自然语言组织。

### 6. 正反例对照

以下以"值不值得做"一节为例，展示正确和错误的写法。

**结构骨架**（用 `< >` 标记的是需要从当前需求中填入的内容）：

```text
收益：<具体收益点，能估算的给出量化参考>。
成本：<开发范围> + <维护代价> + <培训/迁移等隐性成本>。
综合判断：<收益和成本权衡后的结论，不能只说"收益大于成本">。
```

> 以上为结构格式。下面是填好后的效果（示例来自本仓库已有的权限域需求，**仅作格式参考**，不绑定领域）：

```text
收益：超管集中授权的工作量可以分摊。以 200 人企业、月均 20 次权限变动估算，
每次节省超管约 5 分钟操作时间。员工无需等待超管响应即可发起申请。
成本：需新增管理端配置页、员工端权限查看和申请页、审批流程对接。
培训成本可通过页面引导和帮助文档降低。
综合判断：收益大于成本，培训风险属于可控范围，建议推进。
```

**错误**——模板填空，无具体分析：

```text
收益与价值：
- 独立成型能力：边界清晰，便于持续迭代
- 放到已有功能里扩展：沿用现有入口，使用和维护成本更低
成本与代价：
- 独立成型能力：模块数量与建模成本会上升
综合判断：收益大于成本。
```

错误写法的问题：没有结合当前需求的具体内容做判断。任何需求都可以填这套话。"边界清晰""使用成本更低"没有和 facts 中的任何具体功能或规则建立关联。

### 7. 先写关键判断摘要

正文开始前先给出 `## 0. 本次关键设计判断`，只用于让评审人先看到本次最关键的业务判断。

写法要求：

- 每项 1-2 句话即可
- 只写本次最关键的判断，不写成长篇分析
- 摘要不替代正文，正文仍需展开理由、方案、风险和边界
- "必须确认"只写真正会影响方案落地的问题

### 8. 输出重点动态分配

保持固定章节结构，但不要平均用力。

生成前先判断本需求的主要设计压力：

- 用户最容易卡在哪里
- 业务、权限或治理风险主要出现在哪里
- 哪些状态、异常、审批、校验会决定方案成败
- 哪些信息如果不解释清楚，评审人会误解方案

然后按判断分配篇幅：

- 重点章节要写清判断、理由、流程、边界和风险
- 非重点章节可以简写结论，不要为了完整性展开套话
- 不要为了凑完整性去补泛化风险、泛化异常、泛化待确认问题
- 不要做无依据的收益数字估算

### 9. 需求原文不是默认正确答案

AI 不应默认把需求原文直接当成最终业务方案。

当需求原文存在更优解、边界不清、风险过高或体验不合理时，必须明确写出：

- 为什么不直接采纳原文
- 建议改成什么方案
- 判断依据来自 facts、业务知识还是已有知识
- 哪些内容已经可以判断，哪些问题必须产品确认

能判断的内容要明确给建议，不要全部推给"待确认问题"。

## `business_blueprint.md` 结构要求

- **0. 本次关键设计判断**：用极简摘要说明建议方案、不建议方案、核心理由、必须确认
- **1. 一句话结论**：直接回答能不能做、建议怎么做
- **2. 需求是否成立**：解决什么问题、影响哪些角色、判断成立/部分成立/暂不成立/信息不足
- **3. 值不值得做**：收益（业务价值、效率提升）与成本（开发、维护、培训、认知负担）
- **4. 应该做成什么能力形态**：比较至少两种路径，给出推荐和理由
- **5. 推荐业务方案**：角色与职责、主流程闭环、前置配置、结果回写
- **6. 必须守住的规则和边界**：不能放开的限制、必须审批的场景、必须二次确认的操作
- **7. 主要风险与保护策略**：风险描述、影响、缓解方式
- **8. 方案承接要求**：后续 experience 阶段必须承接的角色、流程、异常、状态、文案职责
- **9. 待确认问题**：会影响后续方案的重要不确定项

## 合格标准

- 能回答需求是否成立、值不值得做、做成什么形态
- 推荐方案是具体的、可执行的业务描述，不是泛泛的"做成独立功能"
- 规则边界和风险保护策略明确
- 方案承接要求清晰具体，experience 阶段能直接据此展开设计
- 开头摘要能让评审人快速看到本次最关键的业务判断
- 重点章节和非重点章节的篇幅轻重合理，不是所有章节平均展开
- 当需求原文不应直接采纳时，文中能明确说明原因和替代建议

**方案承接要求的正反例**：

错误（不具体，experience 阶段无法据此设计）：
```
后续方案需覆盖角色、流程、异常、状态
```

正确（具体，experience 阶段可以直接对应到页面和交互）：
```
- 必须覆盖的角色：配置方（<角色名>）、申请方（<角色名>）、审批方（<角色名>）
- 必须闭环的主流程：<步骤1> → <步骤2> → <步骤3>
- 必须处理的异常：<异常A>（<阻断原因和处理方式>）、<异常B>
- 必须解释的状态：<状态1>/<状态2>/<状态3>
```

- 全篇使用自然业务语言，无 ID 编号、无原文碎片拼接
- 附录（如有）只放补充信息，不替代核心区内容

## 失败条件

- 核心区出现大量原文碎片或 ID 编号
- 判断结论是泛化的模板答案（如"独立成型能力最优"无任何具体理由）
- 关键业务规则或风险缺失
- 方案承接要求只有分类标签（如"覆盖角色、流程、异常"）而无具体内容，无法指导 experience 阶段
