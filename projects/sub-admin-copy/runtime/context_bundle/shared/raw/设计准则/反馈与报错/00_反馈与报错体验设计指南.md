## 范围与边界

### 覆盖的信息

- 报错或阻断的业务/体验类型。
- 用户在什么任务中遇到该问题。
- 当前反馈为什么影响体验。
- 推荐反馈形式和适用场景。
- 可复用的用户可见文案模板。
- 需要业务或产品确认的信息。
- 可能影响的体验方向。

### 不覆盖的信息

- 不定义报错治理系统。
- 不定义前后端实现方案。
- 不定义固定指标系统。
- 不承诺具体提升数值。
- 不把“某类报错必须固定使用某种形式”写成硬规则。

## 1. 总体原则

### 1.1 先诊断，再选形式，最后写文案

不要把报错直接当成文案问题。体验蓝图应先判断：

- 用户为什么会走到失败点；
- 这是业务规则限制、流程设计问题、状态表达问题、反馈形式问题，还是纯文案问题；
- 用户看到反馈后是否有明确下一步。

### 1.2 能在操作前说明，就不要等失败后再解释

如果业务规则、状态或权限已经决定某个操作不可用，体验方案应让限制在用户尝试前可见，减少“点击后才知道不能做”的无效操作。

### 1.3 反馈必须说明原因和下一步

合格反馈至少回答两件事：

- 为什么现在不能继续；
- 用户下一步可以做什么。

如果用户不能在当前页面解决，必须给出去向，例如返回列表、前往设置、联系某个角色或等待某个流程结束。

### 1.4 技术信息要转成用户语言

用户不需要看到内部字段名、接口、token、签名、HTTP 状态码、英文错误、数据库字段等信息。体验蓝图应把这些内容转成用户能理解的业务对象、状态、原因和行动建议。

### 1.5 不要把所有异常都做成弹窗

弹窗适合强阻断、高风险、不可逆、需要用户明确确认或需要展示复杂关系的场景。字段错误、轻量失败、终态提醒、持续状态、页面空状态等，不应默认使用弹窗。

## 7. 优化影响描述方式

体验蓝图可以描述可能影响的体验方向，不写成指标系统，不承诺具体提升数值。

可写：

```text
该优化主要减少用户点击后才发现不能操作的情况。
该优化有助于减少反复提交和返工。
该优化能降低弹窗打断感，让用户更快理解失败原因和下一步。
实际效果需要上线后结合真实数据验证。
```

不写：

```text
预计提升完成率 30%。
预计报错压降 50%。
该方案会显著提升满意度。
```
