Business Blueprint

0. 本次关键设计判断

  • 路线说明：需求类型为复杂需求（新增跨域统一查询能力，涉及概念模型统一、规则边界定义、访问控制分层），走完整业务蓝图。重点维度为跨域统一查询模型、权限来源追溯与结果可解释性、查询能力的访问控制与审计边界。
  • 建议方案：独立统一查询中心，分三期建设。一期先做用户维度和角色维度，权限维度紧随其后，OA 表单和报表维度作为二期。所有维度共用一套查询结果模型，以来源追溯为核心特征。
  • 不建议方案：不建议把五个维度拆成五个独立页面各自实现。这会延续"跨模块散落导致查询分裂"的已知体验风险，还会导致来源口径不一致。
  • 核心理由：五个维度的查询口径如果不同，管理员的核对结果会互相矛盾，反而增加误判风险。统一查询模型是本次需求的核心价值，不能因为分期建设就放弃。
  • 必须确认：间接授权是否纳入查询结果；查询入口的访问控制范围（哪些管理员能查、能查什么范围）；一期和二期的具体分界。

1. 一句话结论

可以做，值得做，但必须分期。一期聚焦用户维度和角色维度，建立统一的查询结果模型和访问控制框架。权限维度紧随其后。OA 表单和报表维度等跨域数据口径统一后再纳入。

2. 需求是否成立

判断：部分成立。

成立的部分：

  • 管理员确实需要在多个功能域之间切换核对权限，效率问题真实存在。知识库中"跨模块散落导致查询分裂"已被标记为权限域的已知体验风险模式，"按权限反查"也是已识别的明确缺口。
  • 高安全诉求企业对权限审计和透明度有刚性需求，这不是锦上添花的功能。

需要分期建设的部分：

  • 五个维度的数据就绪程度不同。用户维度和角色维度的数据已经在权限管理域内闭环，直接可查。权限维度的反查逻辑需要明确间接授权口径后才能落地。OA 表单和报表维度的数据分散在审批域和报表域，跨域数据口径统一是前置条件，不应在一期强行纳入。
  • 如果五个维度在同一期全部上线，但口径不一致，反而会产生更严重的信任问题——管理员在不同维度查到不同的结果，会更困惑。

影响角色：权限管理员（日常核对）、超级管理员（全局审计）、审计/安全人员（风险排查）。其中权限管理员是最高频使用者，应优先满足其核心场景（按人查、按角色查）。

3. 值不值得做

收益：

  • 权限核对效率：将管理员从"在多个页面之间切换逐项核对"变成"在一个入口多维度查看"，单次核对时间预计从分钟级降到秒级。
  • 审计能力：补齐按权限反查和跨域查询的能力缺口，让安全审计从"靠管理员经验"变成"有系统工具支撑"。
  • 风险发现：异常授权、过度授权、敏感权限扩散等问题在统一查询视角下更容易暴露。

成本：

  • 开发成本：一期涉及统一查询入口建设、用户和角色维度的查询接口对接、查询结果模型设计、访问控制配置。二期涉及跨域权限数据聚合、OA 表单域和报表域的数据源接入。
  • 维护成本：查询口径需要随各域权限模型的变化同步调整，特别是数据权限的展示口径变化频繁。
  • 认知负担：管理员需要理解"不同域的权限看起来不一样是正常的"，这对查询结果的解释设计提出了较高要求。

综合判断：
收益大于成本，但前提是分期建设、口径统一。一期的投入产出比最清晰——用户维度和角色维度覆盖了最高频的核对场景，数据源已在权限域内闭环，可以直接验证统一查询模型是否成立。不建议为了"五个维度一起上"而牺牲口径质量。

4. 应该做成什么能力形态

路径 A：独立统一查询中心

在权限管理域内新增独立查询入口，五个维度统一收纳，共用一套查询结果模型和访问控制框架。

优点：入口明确，概念统一，方便后续扩展新维度。查询页的"解释不配置"边界清晰。缺点：需要对现有权限管理导航做调整，新增一个一级或二级入口。

路径 B：在各域页面内扩展查询能力

在用户授权页加按用户查、在角色管理页加按角色查、在各业务域页面加对应维度的查询，不设统一入口。

优点：改动范围小，每个维度独立迭代。缺点：这正是当前"跨模块散落导致查询分裂"的延续。五个维度的查询口径会各自为政，管理员仍然需要在不同页面之间切换来拼凑完整图景。知识库中已明确这个风险模式，不应再用这种方式。

推荐：路径 A（独立统一查询中心）。

路径 B 虽然改动小，但违背了本次需求的核心目标——统一查询视角。如果只是为了在现有页面加一个搜索框，那不是这次要解决的问题。

统一查询中心的具体形态建议：

  • 作为权限管理域内的独立功能模块，与用户授权、角色管理、权限查询（现有）并列
  • 入口对权限管理员和超级管理员可见，审计人员按需开放
  • 五个维度通过统一的维度切换组件承载，不设五个独立页面
  • 查询结果共用一套结构化模型（主体、资源、动作、范围、来源、状态），但允许按域差异展示不同字段

5. 推荐业务方案

角色与职责

角色查询范围限制
权限管理员所管理范围内的用户和角色权限不能查看超级管理员的完整权限清单；不能查看超出自身管理范围的用户
超级管理员全企业所有用户和角色的权限无范围限制，但查询操作可能需记录日志 [GAP]
审计/安全人员按需申请查询范围，或默认只读全局权限分布统计不能查看具体用户的完整权限清单（除非获得授权）；是否单独设置审计角色待确认 [GAP]

主流程闭环

一期（用户维度 + 角色维度）：

  1. 管理员进入统一查询中心，选择查询维度（用户 / 角色）。
  2. 输入查询对象（用户名或角色名），系统校验输入对象是否存在、管理员是否有权查询该对象。
  3. 系统返回查询结果，按权限类型分组展示（功能权限、数据权限），每条结果标注来源（直接授权 / 角色授权 / 应用可见性 / 协作可见性）和生效状态。
  4. 管理员查看结果，如有疑问可通过来源标注追溯到授权配置页（是否跳转待确认 [GAP]）。
  5. 查询结束。如有需要，管理员可切换维度继续查询。

二期（权限维度 + OA 表单维度 + 报表维度）：

流程同上，但数据源扩展至审批域和报表域，查询结果中按域区分权限来源。

前置配置

  • 查询入口的可见性需与管理员角色绑定，不是所有管理员默认可见 [GAP]
  • 管理员的查询范围（能查哪些用户、哪些角色）需在角色配置中定义 [GAP]
  • 如果查询操作需要记录日志，需在审计配置中开启 [GAP]

结果回写与记录

  • 查询结果本身不产生权限变更，不回写任何配置数据
  • 如果查询操作需要留痕，记录内容包括：谁在什么时间查询了什么对象的什么维度 [GAP]

6. 必须守住的规则和边界

以下规则基于 facts 关键业务规则和已知风险章节，以及知识库中权限域的来源模型和对象关系。

查询不等于配置（基于 facts 关键业务规则"查询与配置职责分离"）： 查询页不能提供任何直接修改权限的能力。如果查询结果揭示了一个问题（如某人权限过多），管理员需要回到授权页或角色管理页去调整。可以在结果中提供跳转入口，但不能在查询页嵌入修改能力。这是知识库能力地图中"查询页负责解释，不负责配置"的稳定边界。

访问控制是硬约束（基于 facts 关键业务规则"查询入口与访问控制"）： 查询入口不得对普通用户开放。根据 facts 中三类使用者的定义（权限管理员、超级管理员、审计/安全人员），不同角色的查询范围必须可区分、可配置。超级管理员的全局查询权限不能默认下放给所有管理员。访问控制必须做两层——入口可见性和查询范围限制。如果访问控制做不好，这个功能本身就是安全漏洞。

来源追溯不可省略（基于 facts 关键业务规则"查询结果来源展示"和知识库来源模型）： 查询结果必须标注每条权限的来源类型，对应知识库中 source_enum 的四类来源（ACL_DIRECT / RBAC_ROLE / APP_VISIBILITY / COLLAB_VISIBILITY），不能只给"有/没有"。治理修饰因子（GOVERNANCE_MODE）影响生效状态但不改变授予事实，展示时需与来源区分。

间接授权的纳入需在查询结果中显式说明（基于 facts 开放问题#1-#2）： 如果一期不纳入间接授权，查询结果必须显式告知管理员"当前仅展示直接授权和角色授权结果，不包含组织授权和岗位授权"。如果一期纳入角色授权，需要标注"通过角色XX获得"。不得让管理员自行猜测查询范围。

跨域权限颗粒度不得强行统一（基于 facts 关键业务规则"跨域权限结构差异"）： 管理类权限的颗粒度（应用/菜单/页面/操作/数据）和 OA 表单权限的颗粒度（表单/字段/表单管理/数据）本质不同。查询结果不应强行套用同一个字段模板，应允许按域展示不同的权限描述字段。

不支持的能力不应留入口（基于 facts 关键业务规则"不支持的能力"）： 导出、模糊搜索、权限验证模式这些已确认不支持的能力，不应在页面上留下灰掉或"即将上线"的入口，避免给管理员制造错误预期。

治理状态必须可见（基于知识库对象关系中的生效修饰逻辑）： 如果某条权限被治理模式（如双管理员模式、审批未完成）暂停或覆盖，查询结果必须明确标注，不能显示为"有权限"让管理员产生误判。

查询结果必须区分"无权限"和"查询失败"（基于 facts 异常与边界）： 空结果和系统异常是两种本质不同的情况，反馈文案和用户下一步处理方式不同，不得混用同一提示。

7. 主要风险与保护策略

风险一：查询口径不一致导致结果矛盾。

  • 影响：管理员在用户维度查到某人有某权限，但在权限维度查同一权限时找不到这个人，产生信任危机。
  • 真实原因：这是跨域数据口径问题——用户维度的数据来自权限域，权限维度的数据可能需要聚合多个域，口径不一致会导致结果不一致。
  • 缓解策略：在一期仅开放数据源闭环的维度（用户、角色），避免跨域口径不一致的问题。在查询结果中明确标注数据来源域和查询口径说明，让管理员知道"不同维度查到的范围可能不同，这是正常的"。

风险二：来源展示过于复杂导致管理员放弃理解。

  • 影响：如果每条权限标注了完整的来源链路（直接授权→来自角色X→角色X由管理员Y在Z时间配置），信息密度过高，管理员反而会忽略来源信息，退化为只看"有/没有"。
  • 真实原因：这是信息架构和认知负担的平衡问题，不是业务规则问题。
  • 缓解策略：采用渐进披露——默认展示来源类型（一行标签），点击展开来源链路详情。不要把完整链路平铺在结果列表里。

风险三：查询入口本身变成权限泄露渠道。

  • 影响：如果访问控制配置不当或存在越权漏洞，任何能访问查询入口的用户都可能看到全员权限分布，包括超级管理员的权限清单和高风险权限的持有人。
  • 真实原因：查询入口的访问控制依赖已有角色体系，如果角色体系的配置本身有疏漏，查询入口会放大这个问题。
  • 缓解策略：查询入口的访问控制必须做两层——第一层是入口可见性（有没有这个菜单），第二层是查询范围限制（能查哪些人、哪些角色）。超级管理员的权限清单和高风险权限的持有人信息应被视为敏感数据，默认不向权限管理员开放 [GAP]。

风险四：大批量结果导致页面不可用。

  • 影响：查询超级管理员或"全员"角色时，结果可能包含数百条权限和数千个用户，一次性全部展示会导致页面卡顿或管理员无法定位。
  • 真实原因：这是查询结果的数据量问题。
  • 缓解策略：结果按权限类型分组折叠展示，默认只展开第一组。用户列表超过一定数量时分批加载或提供筛选。具体的分页/折叠阈值和策略由 experience 阶段细化。

8. 方案承接要求

后续 experience 阶段必须承接以下内容：

必须覆盖的角色：

  • 权限管理员（高频使用者，查询范围受限）
  • 超级管理员（全局审计，查询范围不受限）
  • 审计/安全人员（按需开放，查询范围待定义 [GAP]）

必须闭环的主流程：

  • 选择查询维度 → 输入查询对象 → 校验输入合法性 → 校验查询权限 → 展示查询结果 → 查看权限详情与来源 → （可选）跳转至配置页 → 切换维度或结束查询

必须处理的异常：

  • 查询权限不足：管理员试图查询超出自身管理范围的用户或角色时，明确告知"你没有权限查看该对象的权限信息"，并说明可联系谁申请 [GAP]
  • 查询对象不存在：输入的用户或角色在系统中不存在时，提示"未找到该用户/角色"
  • 查询结果为空：合法查询但对应对象无任何权限时，提示"该用户/角色当前没有任何权限"，与查询失败区分
  • 数据加载失败：系统异常时提供重试入口

必须解释的状态：

  • 权限生效状态（已生效 / 未生效 / 被治理暂停）
  • 权限来源类型（直接授权 / 角色授权 / 应用可见性 / 协作可见性）
  • 如果是角色授权，标注来源角色名称

必须保护的风险：

  • 查询入口的访问控制：入口不可见时不在导航中显示，不可通过 URL 直接访问
  • 查询范围的二次校验：即使入口可见，查询特定对象时仍需校验管理员是否有权查看该对象
  • 敏感权限标注：如果某权限被标记为敏感（如删除权限、全员数据导出权限），在结果中需有视觉区分 [GAP]

可自行设计的内容（不需要等业务确认）：

  • 五个维度的切换方式（Tab / 下拉 / 单选组）
  • 查询结果的布局（列表 / 卡片 / 分组折叠）
  • 来源的渐进披露交互（hover 展开 / 点击展开 / 侧边栏）
  • 查询历史是否保留在本地（不涉及服务端日志的前提下）

报错和阻断场景中的业务依据状态：

  • "查询权限不足"：业务依据充分（访问控制是硬约束），可直接进入体验设计
  • "查询对象不存在"：业务依据充分，可直接进入体验设计
  • "查询结果为空"：需区分"无权限"和"查询失败"，业务依据充分
  • "大批量结果"：分页/折叠策略需要经验数据支撑，建议 experience 阶段先做保守设计（默认折叠、分批加载），后续根据实际数据量调整 [GAP]

9. 待确认问题

以下问题会影响后续方案的具体落地，建议在进入 experience 阶段或开发前确认：

  1. 间接授权是否纳入查询结果？ 如果张三通过"华东区管理员"角色拿到了报表权限，按用户查张三时是否展示？这会影响查询结果的数据量和来源展示逻辑。建议：一期先纳入角色授权（这是最常见的管理场景），组织授权和岗位授权等数据源就绪后再扩展。
  1. 查询入口的访问控制范围？ 权限管理员和超级管理员的查询范围是否一致？如果权限管理员被限制只能查自己管理范围内的人，这个"管理范围"如何定义——是按组织架构还是按角色分组？建议：一期以组织架构范围作为权限管理员的查询边界。
  1. 一期和二期的具体分界？ 建议一期=用户维度+角色维度，权限维度在间接授权口径确认后纳入一期后半段，OA表单和报表维度作为二期。是否同意这个分期方式？
  1. 权限来源展示粒度？ 默认展示来源类型（标签），点击展开来源链路。是否接受这个渐进披露方案？
  1. 查询操作是否需要记录日志？ 如果需要，日志的范围是仅记录"谁查了谁"还是记录完整的查询条件和结果摘要？
  1. 查询结果是否提供跳转至权限调整页面的入口？ 建议提供——查询的终点往往是"发现问题需要调整"，如果不给跳转，管理员需要记住查询结果再导航到配置页，流程断裂。

Experience Blueprint

0. 本次关键设计判断

  • 路线说明：需求类型为复杂需求（跨域统一权限查询），走完整业务蓝图。体验阶段重点承接 business 中四个核心维度——统一查询模型的信息架构、权限来源的渐进披露交互、访问控制的阻断反馈、查询结果的差异化工位设计。
  • 建议方案：单一查询入口 + 维度 Tab 切换 + 统一结果卡片模型，来源采用"标签 + 点击展开"的渐进披露，访问被拒时在操作前说明原因和申诉路径。
  • 不建议方案：五个维度各自独立页面（违背统一查询的核心目标）；来源链路全部平铺在结果列表（信息密度过高，违背渐进披露原则）。
  • 核心理由：管理员的核对效率取决于能否在一个心智模型下完成跨维度查询。来源追溯是本次体验的核心差异点——既要可见，又不能淹没主要结果。
  • 必须确认：一期具体维度的范围（当前按用户+角色设计，权限维度加入时机）；查询结果是否提供跳转至配置页的入口（当前按"提供"设计）。

1. 交互流程总览

本次体验围绕以下角色展开：

权限管理员：进入统一查询中心 → 选择查询维度 → 输入查询对象 → 查看查询结果（含来源标注） → 按需展开来源详情 → 可选跳转至配置页。这是最高频的主流程。

超级管理员：路径同权限管理员，但查询范围不受限，可以查询企业内任意用户或角色。查询入口和结果页一致，仅查询权限校验逻辑不同。

审计/安全人员：路径同权限管理员，但查询范围按需配置。入口不一定默认可见，可能通过授权开通 [GAP]。

主流程：

  • 维度查询主流程：进入查询中心 → 选择维度 → 输入对象 → 查看结果 → 展开来源 → 后续动作

次流程：

  • 切换查询维度继续查询
  • 从查询结果跳转至权限配置页 [GAP]
  • 在结果中切换分组展开/折叠

异常流程重点关注：

  • 查询权限不足（被拦截在查询执行前）
  • 查询对象不存在
  • 查询结果为空（区别于查询失败）
  • 查询服务异常（系统错误）

2. 主交互流程

以下按一期范围（用户维度 + 角色维度）展开。权限维度、OA 表单维度、报表维度在二期补充，流程框架复用。

节点 A1：进入统一查询中心

用户动作：
权限管理员在权限管理导航中点击"权限查询"，进入统一查询中心。

系统反馈：
页面加载，展示查询维度选择区和查询输入区。默认选中"用户维度"。页面标题区显示功能名称和简短说明。

本节点需要前置解释：
管理员需要知道这个页面能查什么、不能查什么。在页面顶部用一行说明解释查询范围——当前查询的是"谁有什么权限"和"某个角色包含什么权限"，不包含导出和批量对比能力。

建议页面文案：

  • 页面标题：权限查询
  • 页面说明：从用户或角色维度查看权限归属关系，查询结果仅用于核对和审计，不提供直接修改权限的能力。
  • 维度 Tab 标签：按用户查 / 按角色查

下一步：
管理员选择维度后进入输入环节（节点 A2）。如果管理员因访问控制看不到某些维度，对应 Tab 不显示。

节点 A2：输入查询对象

用户动作：
管理员在搜索框中输入用户名或角色名。系统在输入过程中提供匹配建议（基于管理员有权查看的用户/角色范围）。

系统反馈：

  • 正常结果：输入框下方出现匹配建议列表，每项显示名称和简要标识（如用户显示所属部门，角色显示成员数量预览）。
  • 异常结果：若输入内容无匹配结果，建议列表为空，输入框下方提示"未找到匹配的用户或角色"。

本节点需要前置解释：
搜索范围受管理员自身权限限制——只能搜索自己管理范围内的用户和角色。如果管理员不确定某人是否在管理范围内，可以先输入看看是否能匹配到。

建议页面文案：

  • 用户维度输入框占位符：输入用户名搜索
  • 角色维度输入框占位符：输入角色名搜索
  • 无匹配提示：未找到匹配的用户，请检查输入是否正确，或确认该用户是否在你的管理范围内
  • 匹配建议中用户附属信息：所属部门 · 在职
  • 匹配建议中角色附属信息：成员 128 人

下一步：
管理员选中匹配结果后进入查询等待和结果展示（节点 A3）。

节点 A3：查询执行与结果展示

用户动作：
管理员从匹配建议中选中目标，系统开始查询。加载过程中管理员等待。

系统反馈：

  • 正常结果（有数据）：查询完成后展示结果页。结果按权限类型分组——功能权限、数据权限、其他权限——每组默认折叠，组标题显示该组权限数量。每组展开后以卡片列表展示，每条卡片包含：权限名称、权限描述、来源标签、生效状态标签。
  • 正常结果（无数据）：展示空结果状态，明确说明该对象当前没有任何权限，与查询失败区分。
  • 异常结果（查询失败）：展示错误状态，提供重试入口。

本节点需要前置解释：
结果中每条权限会标注来源（如"直接授权""通过角色 XX 获得""应用可见性"），这是理解权限从哪来的关键信息。同一权限可能有多个来源，展示时合并标注。如果权限因治理模式被暂停或未生效，会在状态标签中体现。

建议页面文案：

  • 结果页标题："张三"的权限清单
  • 结果页副标题：共 23 条权限 · 来自 3 个来源
  • 分组标题示例：功能权限（15）、数据权限（6）、其他权限（2）
  • 卡片-权限名称示例：删除员工档案
  • 卡片-来源标签示例：直接授权 / 通过 华东区管理员 获得 / 应用可见性
  • 卡片-生效状态标签：已生效 / 未生效（审批中）/ 已暂停（双管理员模式）
  • 空结果提示：该用户当前没有任何权限
  • 空结果说明：可能的原因：该用户尚未被分配任何权限，或所有权限已被收回。如需为该用户添加权限，请前往用户授权页面。
  • 错误状态提示：查询失败，请重试
  • 错误状态操作按钮：重新查询
  • 加载中状态：正在查询...

下一步：
管理员查看结果后，可以展开具体权限的来源详情（节点 A4），或切换维度继续查询（回到节点 A2），或跳转至配置页 [GAP]（次流程）。

节点 A4：查看权限来源详情

用户动作：
管理员点击某条权限的来源标签，展开来源详情。

系统反馈：
来源详情以浮层或内嵌展开的方式展示，不跳转页面。内容包含：来源类型、来源对象名称（如具体角色名）、如果可追溯到授权人则展示授权人姓名和授权时间 [GAP]。如果同一权限有多个来源，全部列出并标注优先级关系。

本节点需要前置解释：
如果权限来自角色，这里展示角色名称。如果需要调整权限，应去对应的角色管理页操作，而不是在这里直接改。如果权限来源涉及系统默认规则或自动授权规则，也会在此说明。

建议页面文案：

  • 来源详情标题：权限来源
  • 来源条目示例：通过角色"华东区管理员"获得 · 由 李四 配置 · 2024-01-15
  • 来源条目示例2：直接授权 · 由 王五 配置 · 2024-03-20
  • 多来源说明：该权限来自多个来源，最终结果取并集
  • 跳转入口（如 business 确认支持）：前往角色管理页调整 → [GAP]
  • 关闭方式：点击来源标签或浮层外部关闭

下一步：
管理员查看完来源详情后关闭浮层，回到结果列表。可以继续查看其他权限的来源，或进行下一步操作。

3. 次交互流程

节点 B1：切换查询维度

用户动作：
管理员在当前结果页切换到另一个维度的 Tab（如从"按用户查"切换到"按角色查"）。

系统反馈：
清空当前查询输入和结果，回到输入状态。输入框占位符随维度变化。不保留上一次的查询结果（避免误以为不同维度的结果可以直接对比）。

节点 B2：从查询结果跳转至权限配置页 [GAP]

前提：business 中"查询结果是否提供跳转入口"待确认。本节点按"提供跳转"的前提设计。

用户动作：
管理员在结果页点击某条权限旁的"调整"或"去配置"入口。

系统反馈：
新标签页打开对应的权限配置页面（如用户授权页、角色管理页），定位到对应条目。查询页保留当前状态，管理员可以配置完成后再切回来对照。

节点 B3：折叠/展开结果分组

用户动作：
管理员点击结果分组标题，切换该组的折叠/展开状态。

系统反馈：
点击折叠时，组内卡片收起，组标题保留权限数量。点击展开时，组内卡片展开。默认第一组展开，其余折叠。

4. 异常与阻断流程

异常 E1：查询权限不足

发生时机：
管理员输入查询对象并提交查询时。

触发条件：
管理员尝试查询超出自身管理范围的用户或角色。例如，权限管理员只能查自己部门内的人，但尝试查另一个部门的员工或超级管理员的权限。

判断依据：
基于 business "访问控制是硬约束"规则——查询入口的访问控制必须做两层：入口可见性 + 查询范围限制。

反馈形式：
在输入阶段，超出范围的用户/角色不会出现在匹配建议中。但如果管理员通过精确输入绕过了建议列表（例如输入了完整用户名），提交后返回阻断提示。使用页面内嵌提示（非弹窗），位置在输入框下方。

系统反馈：
无法查询该用户的权限，该用户不在你的管理范围内。如需查询，请联系超级管理员或具有更广查询权限的管理员。

用户下一步：
管理员可以联系超级管理员申请扩大查询范围，或输入其他用户。

异常 E2：查询对象不存在

发生时机：
管理员输入用户名或角色名并提交查询时。

触发条件：
输入的名称在系统中不存在。

判断依据：
基于 facts 异常与边界中"查询对象不存在"场景。

反馈形式：
输入框下方内嵌提示。

系统反馈：
未找到名为"XXX"的用户。请检查输入是否正确。

用户下一步：
修改输入内容重试，或联系管理员确认该用户是否已离职/已删除。

异常 E3：查询结果为空

发生时机：
查询成功执行但该对象确实没有任何权限。

触发条件：
查询对象存在且管理员有权查看，但该对象当前没有任何已生效的权限。

判断依据：
基于 business "查询结果必须区分'无权限'和'查询失败'"规则。

反馈形式：
结果区域展示空状态页，配说明文字和操作建议。

系统反馈：
标题：该用户当前没有任何权限
说明：该用户尚未被分配权限，或所有权限已被收回、暂停或未生效。
操作按钮：前往用户授权（打开用户授权页）

用户下一步：
如确认该用户应该有权限，可前往用户授权页为其分配权限。

异常 E4：查询服务异常

发生时机：
查询提交后，服务端返回错误。

触发条件：
网络超时、服务异常、数据源不可用等。

判断依据：
通用系统异常处理。

反馈形式：
结果区域展示错误状态，配重试按钮。使用页面内嵌状态而非 toast，因为查询失败导致整个结果区域不可用，toast 不够显著。

系统反馈：
标题：查询失败
说明：服务暂时不可用，请稍后重试。如持续失败，请联系技术支持。
操作按钮：重新查询

用户下一步：
点击重试，或等待后重新查询。

5. 页面 / 弹窗 / 抽屉设计

页面：统一查询中心（权限查询）

页面目标：
为管理员提供一站式权限查询入口，支持跨维度查询和权限来源追溯。管理员在此完成"输入对象 → 查看结果 → 理解来源"的完整核对任务。

页面结构（从上到下）：

1. 页面标题区

  • 标题：权限查询
  • 说明文字：从用户或角色维度查看权限归属关系，查询结果仅用于核对和审计，不提供直接修改权限的能力。

2. 查询维度切换

  • Tab 组件：按用户查 | 按角色查（一期）
  • 选中的 Tab 高亮
  • 切换时清空输入和结果

3. 查询输入区

  • 搜索框（带搜索图标），占位符随维度变化
  • 输入过程中展示匹配建议下拉列表
  • 匹配建议每项展示名称 + 附属信息（部门/角色成员数）
  • 输入无匹配时展示"未找到匹配项"提示

4. 结果区（查询后展示）

有结果时：

  • 结果摘要栏：对象名称 · 共 N 条权限 · 来自 M 个来源
  • 权限分组列表（默认第一组展开）：
  • 组标题：权限类型名称（数量）
  • 组内容：权限卡片列表
  • 每张卡片：权限名称 | 权限描述（可选行） | 来源标签（可点击展开） | 生效状态标签
  • 来源标签点击后内嵌展开来源详情（不弹出浮层，在卡片内展开）

空结果时：

  • 空状态插图区
  • 标题："该用户当前没有任何权限"
  • 说明文字
  • 操作按钮："前往用户授权"

查询失败时：

  • 错误状态插图区
  • 标题："查询失败"
  • 说明文字
  • 操作按钮："重新查询"

5. 页面底部（可选）

  • 查询辅助说明链接："了解权限来源的含义"
  • 反馈入口（如企业有反馈渠道）

具体文案：

  • 页面标题：权限查询
  • 页面说明：从用户或角色维度查看权限归属关系，查询结果仅用于核对和审计。
  • Tab 标签：按用户查、按角色查
  • 搜索框占位符（用户维度）：输入用户名搜索
  • 搜索框占位符（角色维度）：输入角色名搜索
  • 结果摘要："{对象名}"的权限清单 · 共 {N} 条权限 · 来自 {M} 个来源
  • 分组标题：功能权限（{N}）、数据权限（{N}）
  • 来源标签：直接授权、通过"{角色名}"获得、应用可见性、协作可见性
  • 生效状态标签：已生效、未生效、已暂停
  • 来源详情展开-角色来源：通过角色"{角色名}"获得 · 由 {授权人} 配置 · {日期}
  • 来源详情展开-直接授权：直接授权 · 由 {授权人} 配置 · {日期}
  • 空结果标题：该用户当前没有任何权限
  • 空结果说明：该用户尚未被分配权限，或所有权限已被收回、暂停或未生效。
  • 空结果按钮：前往用户授权
  • 错误标题：查询失败
  • 错误说明：服务暂时不可用，请稍后重试。如持续失败，请联系技术支持。
  • 错误按钮：重新查询
  • 权限不足提示：无法查询该用户的权限，该用户不在你的管理范围内。如需查询，请联系具有更广查询权限的管理员。
  • 对象不存在提示：未找到名为"{输入}"的{用户/角色}，请检查输入是否正确。

按钮：

  • 主按钮：重新查询（错误态）、前往用户授权（空结果态）
  • 链接按钮：来源标签（可点击展开详情）、了解权限来源的含义

成功反馈：

  • 加载完成后平滑过渡到结果区，不需要额外的成功提示

失败反馈：

  • 查询失败时结果区展示错误状态
  • 权限不足时输入框下方展示内嵌提示
  • 对象不存在时输入框下方展示内嵌提示

组件：来源详情内嵌展开区

组件目标：
在权限卡片内展开来源详情，让管理员理解权限从哪来，而不需要跳转到其他页面。

组件结构：

  • 卡片底部增加展开区域（默认收起）
  • 展开后显示来源列表，每条来源一行
  • 包含：来源类型标签 + 来源对象名称 + 授权人姓名 + 授权时间
  • 如有多条来源，按来源优先级排列（直接授权 > 角色授权 > 应用可见性 > 协作可见性）
  • 如有跳转配置页入口，放在展开区底部 [GAP]

具体文案：

  • 来源展开区标题：权限来源
  • 来源条目格式：{来源类型标签}"{来源对象名}" · 由 {授权人} 配置 · {YYYY-MM-DD}
  • 多来源说明：该权限来自 {N} 个来源，最终结果为取并集
  • 跳转入口（如支持）：前往 {角色管理页/用户授权页} 调整

6. 状态与反馈文案

查询输入状态

状态含义用户可做页面反馈
待输入尚未开始查询选择维度，输入查询对象搜索框展示占位符"输入用户名搜索"或"输入角色名搜索"，结果区为空
输入中正在输入查询对象继续输入，或从匹配建议中选择搜索框下方展示匹配建议列表
无匹配输入内容在系统中无对应对象修改输入或确认对象是否存在搜索框下方提示"未找到匹配的{用户/角色}"
权限不足-输入输入的对象不在管理范围内修改输入或联系上级管理员搜索框中不展示该对象或提交后返回阻断提示

查询执行状态

状态含义用户可做页面反馈
加载中查询请求已提交，等待结果等待结果区展示加载动画和"正在查询..."
查询成功（有结果）查询完成，返回权限列表查看结果，展开来源详情，切换维度继续查结果摘要 + 分组权限卡片列表
查询成功（空结果）查询完成，但对象无任何权限确认是否需要为该对象分配权限空状态页："该用户当前没有任何权限" + "前往用户授权"按钮
查询失败服务异常，查询未完成重试或等待错误状态页："查询失败，请重试" + "重新查询"按钮

权限生效状态

状态含义用户可做页面反馈
已生效权限当前生效中正常查看，如需调整去配置页绿色标签"已生效"
未生效权限已授予但尚未生效（如审批中）了解原因后等待或跟进审批橙色标签"未生效" + hover 展开"审批中，预计 {时间} 前生效"
已暂停权限被治理模式暂停（如双管理员模式互审中）了解暂停原因后联系对应管理员灰色标签"已暂停" + hover 展开"被双管理员模式暂停，请联系 {管理员} 确认"

权限来源标签

来源类型标签文案含义

RBAC_ROLE通过"{角色名}"获得权限来自角色授予
APP_VISIBILITY应用可见性权限来自应用可见范围
COLLAB_VISIBILITY协作可见性权限来自协作范围配置

查无权限时的空结果

含义：查询对象存在且管理员有权查看，但该对象当前没有任何已生效的权限。
用户可做：前往用户授权页为该对象分配权限（如有权限），或确认该结果是否符合预期。
页面反馈：标题"该用户当前没有任何权限"，说明"该用户尚未被分配权限，或所有权限已被收回、暂停或未生效"，按钮"前往用户授权"。

查询权限不足时的阻断

含义：管理员尝试查询超出自身管理范围的用户或角色。
用户可做：修改查询对象，或联系具有更广查询权限的管理员申请扩大范围。
页面反馈：输入框下方内嵌提示"无法查询该用户的权限，该用户不在你的管理范围内。如需查询，请联系具有更广查询权限的管理员。"

7. 待确认问题

  1. 查询结果是否提供跳转至权限配置页的入口？ 影响结果卡片上是否需要"调整"或"去配置"按钮，以及来源展开区是否需要跳转入口。当前方案按"提供"设计，如确认不提供则需移除相关入口和次流程。建议由产品确认。
  1. 权限来源展示粒度？ 当前方案按"默认展示来源类型标签 + 点击展开链路详情"设计。如果确认只展示来源类型不展示链路详情，则需移除展开交互，改为不可点击的标签。如果确认展示完整链路，则需重新考虑信息密度问题。建议由产品和设计共同确认。
  1. 一期维度范围？ 当前方案按用户维度和角色维度设计页面交互。如果权限维度在一期内纳入，需补充权限维度的查询输入方式和结果展示差异。建议由产品确认分期计划。
  1. 访问控制的"管理范围"如何定义？ 当前方案中权限管理员的查询范围按"组织架构范围"假设。如果管理范围按角色分组或其他维度定义，输入匹配建议的过滤逻辑需要调整。建议由产品确认。
  1. 查询历史是否保留？ 当前方案不设查询历史功能。如果管理员需要回顾之前的查询结果，是否需要在本地保留最近查询记录？建议由产品和设计共同确认。

附录：设计指南消费说明

本次命中的体验问题：

  • 多维度查询入口的信息架构设计（如何让五个维度在一个页面内清晰切换）
  • 权限来源的渐进披露（如何让管理员既能看到来源，又不被信息密度淹没）
  • 查询权限不足的阻断反馈（操作用户前告知限制，而非点击后弹窗）
  • 空结果与查询失败的区分（两种"没结果"的含义和下一步完全不同）
  • 大批量结果的分组折叠策略

消费的设计指南：

  • 信息架构与可发现性原则（IA-02 分块）：查询结果按权限类型分组折叠，组标题表达组意图，同组权限强相关
  • 反馈与报错体验设计指南（反馈形式选择原则）：权限不足在操作前通过匹配范围控制提示，不在提交后弹窗；字段级问题贴近输入框，页面内容无法展示用空状态，系统异常用页面内嵌状态
  • 认知与决策原则（C-04 渐进披露）：来源标签默认展示类型，点击展开链路详情，先主后高级
  • 可用性原则（U-01 系统状态可见）：查询加载态、空结果态、错误态、成功态四种结果状态完整覆盖
  • 可用性原则（U-09 可行动的错误恢复）：查询失败和权限不足时，不只说"不能查"，还给管理员下一步可以做什么

转译到方案：

  • 查询结果分组按任务语义（功能权限/数据权限）而非数据结构，每组标题携带数量线索
  • 权限不足通过"搜索范围受管理范围限制"的前置说明 + 匹配建议过滤 + 精确输入后阻断提示三层，而非等提交后弹窗
  • 来源采用"默认标签 + 点击展开链路"的渐进披露，避免完整链路平铺导致认知过载
  • 空结果和查询失败使用不同的页面状态，配不同的说明文案和操作按钮，不让管理员猜测
