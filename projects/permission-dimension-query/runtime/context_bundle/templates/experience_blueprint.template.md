# Experience Blueprint

> 本模板定义 `experience_blueprint.md` 的输出结构。
> 核心原则：用 UX 设计师的语言写清楚——谁做什么、系统怎么回应、页面上写什么文案、失败时怎么处理。
> 参考示例：`test/Experience_Blueprint 理想效果.md`

## 0. 本次关键设计判断

- 路线说明：
- 建议方案：
- 不建议方案：
- 核心理由：
- 必须确认：

写作要求：

- 每项 1-2 句话即可
- 只前置呈现关键判断
- 不替代后文完整体验方案

## 1. 交互流程总览

按角色概述本次涉及的所有交互流程。

```text
本次体验围绕以下角色展开：

<角色A>：<核心任务路径>
<角色B>：<核心任务路径>

主流程：
- <流程A名称>：<简要路径>
- <流程B名称>：<简要路径>

异常流程重点关注：
- <异常场景1>
- <异常场景2>
```

## 2. 主交互流程

按角色和路径逐节点展开。每个节点必须包含以下内容：

```text
节点 X1：<节点名称>

用户动作：
<用户做了什么>

系统反馈：
<系统如何响应。区分正常结果和异常结果>

本节点需要前置解释：
<用户在操作前需要知道什么信息>

建议页面文案：
<具体的页面文本，可直接展示>

下一步：
<用户接下来去哪>
```

### 写作要求

- 每个节点用自然语言命名（如"进入设置页"、"选择配置项"、"填写表单"）
- 文案必须是可以直接放在页面上的文本
- 禁止写元指令（如"页面文案要负责解释边界"）
- 异常结果要写清楚系统反馈什么文案、用户下一步怎么办

## 3. 次交互流程

展开非主路径任务：编辑配置、查看详情、撤销申请、重新提交等。

写法与主流程一致。

## 4. 异常与阻断流程

每个异常说明：

```text
异常 X：<异常名称>

发生时机：<在什么操作时触发>
触发条件：<什么情况下会命中>
判断依据：<来自 facts 或 business 的哪条业务依据>
反馈形式：<操作入口提示 / 字段提示 / 页面状态 / toast / 空状态 / 弹窗等>
系统反馈：<具体的提示文案>
用户下一步：<用户应该怎么做>
```

写作要求：

- 先判断用户为什么会走到失败点，再选择反馈形式，最后写文案
- 不要看到权限不足就直接写置灰、看到参数为空就直接写 inline、看到网络异常就直接写 toast
- 事实不足时写条件型建议或待确认问题，不要给确定方案
- 优化影响只能写可能减少无效操作、返工、打断感或理解成本，不写具体提升数值

## 5. 页面 / 弹窗 / 抽屉设计

每个页面/弹窗/抽屉说明：

```text
页面/弹窗/抽屉：<名称>

页面目标：<这个页面要完成什么任务>
页面结构：<包含哪些信息区和操作区>
具体文案：<标题、说明文字、按钮文字>
按钮：<主要按钮和次要按钮>
成功反馈：<操作成功后的反馈文案>
失败反馈：<操作失败后的反馈文案>
```

### 写作要求

- 页面名必须有意义（如"设置页"、"详情抽屉"、"二次确认弹窗"）
- 文案必须是具体文本
- 按钮区分主按钮和次按钮

## 6. 状态与反馈文案

汇总关键状态：

```text
状态：<状态名称>

含义：<这个状态意味着什么>
用户可做：<用户在这个状态下能做什么>
页面反馈：<页面上的具体反馈文本>
```

## 7. 待确认问题

列出当前仍不确定且会影响体验方案的事项。每项说明：
- 问题是什么
- 影响什么
- 建议由谁确认

## 附录：设计指南消费说明

仅在 `knowledge_usage_report.json` 记录了实际消费时填写。保持 3-6 条要点，不贴 raw 原文，不暴露大段理论。

```text
本次命中的体验问题：
- <例如：部分成功反馈、审批延迟生效、复制对象为空校验>

消费的设计指南：
- <guideline summary 名称>
- <guideline raw 名称或主题>

转译到方案：
- <例如：可前置判断的限制，优先在操作前说明>
- <例如：部分成功不只给 toast，需要展示成功/失败明细>
- <例如：审批中状态需要说明何时生效和下一步>
```
