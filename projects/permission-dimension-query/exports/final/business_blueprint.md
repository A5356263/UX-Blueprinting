# Business Blueprint

> 输入来源：projects/permission-dimension-query/workspace/facts.md，以及知识库中权限域的对象模型、来源模型、查询路径缺口和体验风险模式。

## 0. 本次关键设计判断

- 路线说明：需求类型为复杂需求（新增跨域统一查询能力，涉及概念模型统一、规则边界定义、访问控制分层），走完整业务蓝图。重点维度为跨域统一查询模型、权限来源追溯与结果可解释性、查询能力的访问控制与审计边界。
- 建议方案：独立统一查询中心，分三期建设。一期先做用户维度和角色维度，权限维度紧随其后，OA 表单和报表维度作为二期。所有维度共用一套查询结果模型，以来源追溯为核心特征。
- 不建议方案：不建议把五个维度拆成五个独立页面各自实现。这会延续"跨模块散落导致查询分裂"的已知体验风险，还会导致来源口径不一致。
- 核心理由：五个维度的查询口径如果不同，管理员的核对结果会互相矛盾，反而增加误判风险。统一查询模型是本次需求的核心价值，不能因为分期建设就放弃。
- 必须确认：间接授权是否纳入查询结果；查询入口的访问控制范围（哪些管理员能查、能查什么范围）；一期和二期的具体分界。

## 1. 一句话结论

可以做，值得做，但必须分期。一期聚焦用户维度和角色维度，建立统一的查询结果模型和访问控制框架。权限维度紧随其后。OA 表单和报表维度等跨域数据口径统一后再纳入。

## 2. 需求是否成立

**判断：部分成立。**

成立的部分：
- 管理员确实需要在多个功能域之间切换核对权限，效率问题真实存在。知识库中"跨模块散落导致查询分裂"已被标记为权限域的已知体验风险模式，"按权限反查"也是已识别的明确缺口。
- 高安全诉求企业对权限审计和透明度有刚性需求，这不是锦上添花的功能。

需要分期建设的部分：
- 五个维度的数据就绪程度不同。用户维度和角色维度的数据已经在权限管理域内闭环，直接可查。权限维度的反查逻辑需要明确间接授权口径后才能落地。OA 表单和报表维度的数据分散在审批域和报表域，跨域数据口径统一是前置条件，不应在一期强行纳入。
- 如果五个维度在同一期全部上线，但口径不一致，反而会产生更严重的信任问题——管理员在不同维度查到不同的结果，会更困惑。

影响角色：权限管理员（日常核对）、超级管理员（全局审计）、审计/安全人员（风险排查）。其中权限管理员是最高频使用者，应优先满足其核心场景（按人查、按角色查）。

## 3. 值不值得做

**收益：**
- 权限核对效率：将管理员从"在多个页面之间切换逐项核对"变成"在一个入口多维度查看"，单次核对时间预计从分钟级降到秒级。
- 审计能力：补齐按权限反查和跨域查询的能力缺口，让安全审计从"靠管理员经验"变成"有系统工具支撑"。
- 风险发现：异常授权、过度授权、敏感权限扩散等问题在统一查询视角下更容易暴露。

**成本：**
- 开发成本：一期涉及统一查询入口建设、用户和角色维度的查询接口对接、查询结果模型设计、访问控制配置。二期涉及跨域权限数据聚合、OA 表单域和报表域的数据源接入。
- 维护成本：查询口径需要随各域权限模型的变化同步调整，特别是数据权限的展示口径变化频繁。
- 认知负担：管理员需要理解"不同域的权限看起来不一样是正常的"，这对查询结果的解释设计提出了较高要求。

**综合判断：**
收益大于成本，但前提是分期建设、口径统一。一期的投入产出比最清晰——用户维度和角色维度覆盖了最高频的核对场景，数据源已在权限域内闭环，可以直接验证统一查询模型是否成立。不建议为了"五个维度一起上"而牺牲口径质量。

## 4. 应该做成什么能力形态

**路径 A：独立统一查询中心**

在权限管理域内新增独立查询入口，五个维度统一收纳，共用一套查询结果模型和访问控制框架。

优点：入口明确，概念统一，方便后续扩展新维度。查询页的"解释不配置"边界清晰。缺点：需要对现有权限管理导航做调整，新增一个一级或二级入口。

**路径 B：在各域页面内扩展查询能力**

在用户授权页加按用户查、在角色管理页加按角色查、在各业务域页面加对应维度的查询，不设统一入口。

优点：改动范围小，每个维度独立迭代。缺点：这正是当前"跨模块散落导致查询分裂"的延续。五个维度的查询口径会各自为政，管理员仍然需要在不同页面之间切换来拼凑完整图景。知识库中已明确这个风险模式，不应再用这种方式。

**推荐：路径 A（独立统一查询中心）。**

路径 B 虽然改动小，但违背了本次需求的核心目标——统一查询视角。如果只是为了在现有页面加一个搜索框，那不是这次要解决的问题。

统一查询中心的具体形态建议：
- 作为权限管理域内的独立功能模块，与用户授权、角色管理、权限查询（现有）并列
- 入口对权限管理员和超级管理员可见，审计人员按需开放
- 五个维度通过统一的维度切换组件承载，不设五个独立页面
- 查询结果共用一套结构化模型（主体、资源、动作、范围、来源、状态），但允许按域差异展示不同字段

## 5. 推荐业务方案

### 角色与职责

| 角色 | 查询范围 | 限制 |
| --- | --- | --- |
| 权限管理员 | 所管理范围内的用户和角色权限 | 不能查看超级管理员的完整权限清单；不能查看超出自身管理范围的用户 |
| 超级管理员 | 全企业所有用户和角色的权限 | 无范围限制，但查询操作可能需记录日志 [GAP] |
| 审计/安全人员 | 按需申请查询范围，或默认只读全局权限分布统计 | 不能查看具体用户的完整权限清单（除非获得授权）；是否单独设置审计角色待确认 [GAP] |

### 主流程闭环

**一期（用户维度 + 角色维度）：**

1. 管理员进入统一查询中心，选择查询维度（用户 / 角色）。
2. 输入查询对象（用户名或角色名），系统校验输入对象是否存在、管理员是否有权查询该对象。
3. 系统返回查询结果，按权限类型分组展示（功能权限、数据权限），每条结果标注来源（直接授权 / 角色授权 / 应用可见性 / 协作可见性）和生效状态。
4. 管理员查看结果，如有疑问可通过来源标注追溯到授权配置页（是否跳转待确认 [GAP]）。
5. 查询结束。如有需要，管理员可切换维度继续查询。

**二期（权限维度 + OA 表单维度 + 报表维度）：**

流程同上，但数据源扩展至审批域和报表域，查询结果中按域区分权限来源。

### 前置配置

- 查询入口的可见性需与管理员角色绑定，不是所有管理员默认可见 [GAP]
- 管理员的查询范围（能查哪些用户、哪些角色）需在角色配置中定义 [GAP]
- 如果查询操作需要记录日志，需在审计配置中开启 [GAP]

### 结果回写与记录

- 查询结果本身不产生权限变更，不回写任何配置数据
- 如果查询操作需要留痕，记录内容包括：谁在什么时间查询了什么对象的什么维度 [GAP]

## 6. 必须守住的规则和边界

以下规则基于 facts 关键业务规则和已知风险章节，以及知识库中权限域的来源模型和对象关系。

**查询不等于配置（基于 facts 关键业务规则"查询与配置职责分离"）：** 查询页不能提供任何直接修改权限的能力。如果查询结果揭示了一个问题（如某人权限过多），管理员需要回到授权页或角色管理页去调整。可以在结果中提供跳转入口，但不能在查询页嵌入修改能力。这是知识库能力地图中"查询页负责解释，不负责配置"的稳定边界。

**访问控制是硬约束（基于 facts 关键业务规则"查询入口与访问控制"）：** 查询入口不得对普通用户开放。根据 facts 中三类使用者的定义（权限管理员、超级管理员、审计/安全人员），不同角色的查询范围必须可区分、可配置。超级管理员的全局查询权限不能默认下放给所有管理员。访问控制必须做两层——入口可见性和查询范围限制。如果访问控制做不好，这个功能本身就是安全漏洞。

**来源追溯不可省略（基于 facts 关键业务规则"查询结果来源展示"和知识库来源模型）：** 查询结果必须标注每条权限的来源类型，对应知识库中 source_enum 的四类来源（ACL_DIRECT / RBAC_ROLE / APP_VISIBILITY / COLLAB_VISIBILITY），不能只给"有/没有"。治理修饰因子（GOVERNANCE_MODE）影响生效状态但不改变授予事实，展示时需与来源区分。

**间接授权的纳入需在查询结果中显式说明（基于 facts 开放问题#1-#2）：** 如果一期不纳入间接授权，查询结果必须显式告知管理员"当前仅展示直接授权和角色授权结果，不包含组织授权和岗位授权"。如果一期纳入角色授权，需要标注"通过角色XX获得"。不得让管理员自行猜测查询范围。

**跨域权限颗粒度不得强行统一（基于 facts 关键业务规则"跨域权限结构差异"）：** 管理类权限的颗粒度（应用/菜单/页面/操作/数据）和 OA 表单权限的颗粒度（表单/字段/表单管理/数据）本质不同。查询结果不应强行套用同一个字段模板，应允许按域展示不同的权限描述字段。

**不支持的能力不应留入口（基于 facts 关键业务规则"不支持的能力"）：** 导出、模糊搜索、权限验证模式这些已确认不支持的能力，不应在页面上留下灰掉或"即将上线"的入口，避免给管理员制造错误预期。

**治理状态必须可见（基于知识库对象关系中的生效修饰逻辑）：** 如果某条权限被治理模式（如双管理员模式、审批未完成）暂停或覆盖，查询结果必须明确标注，不能显示为"有权限"让管理员产生误判。

**查询结果必须区分"无权限"和"查询失败"（基于 facts 异常与边界）：** 空结果和系统异常是两种本质不同的情况，反馈文案和用户下一步处理方式不同，不得混用同一提示。

## 7. 主要风险与保护策略

**风险一：查询口径不一致导致结果矛盾。**
- 影响：管理员在用户维度查到某人有某权限，但在权限维度查同一权限时找不到这个人，产生信任危机。
- 真实原因：这是跨域数据口径问题——用户维度的数据来自权限域，权限维度的数据可能需要聚合多个域，口径不一致会导致结果不一致。
- 缓解策略：在一期仅开放数据源闭环的维度（用户、角色），避免跨域口径不一致的问题。在查询结果中明确标注数据来源域和查询口径说明，让管理员知道"不同维度查到的范围可能不同，这是正常的"。

**风险二：来源展示过于复杂导致管理员放弃理解。**
- 影响：如果每条权限标注了完整的来源链路（直接授权→来自角色X→角色X由管理员Y在Z时间配置），信息密度过高，管理员反而会忽略来源信息，退化为只看"有/没有"。
- 真实原因：这是信息架构和认知负担的平衡问题，不是业务规则问题。
- 缓解策略：采用渐进披露——默认展示来源类型（一行标签），点击展开来源链路详情。不要把完整链路平铺在结果列表里。

**风险三：查询入口本身变成权限泄露渠道。**
- 影响：如果访问控制配置不当或存在越权漏洞，任何能访问查询入口的用户都可能看到全员权限分布，包括超级管理员的权限清单和高风险权限的持有人。
- 真实原因：查询入口的访问控制依赖已有角色体系，如果角色体系的配置本身有疏漏，查询入口会放大这个问题。
- 缓解策略：查询入口的访问控制必须做两层——第一层是入口可见性（有没有这个菜单），第二层是查询范围限制（能查哪些人、哪些角色）。超级管理员的权限清单和高风险权限的持有人信息应被视为敏感数据，默认不向权限管理员开放 [GAP]。

**风险四：大批量结果导致页面不可用。**
- 影响：查询超级管理员或"全员"角色时，结果可能包含数百条权限和数千个用户，一次性全部展示会导致页面卡顿或管理员无法定位。
- 真实原因：这是查询结果的数据量问题。
- 缓解策略：结果按权限类型分组折叠展示，默认只展开第一组。用户列表超过一定数量时分批加载或提供筛选。具体的分页/折叠阈值和策略由 experience 阶段细化。

## 8. 方案承接要求

后续 experience 阶段必须承接以下内容：

**必须覆盖的角色：**
- 权限管理员（高频使用者，查询范围受限）
- 超级管理员（全局审计，查询范围不受限）
- 审计/安全人员（按需开放，查询范围待定义 [GAP]）

**必须闭环的主流程：**
- 选择查询维度 → 输入查询对象 → 校验输入合法性 → 校验查询权限 → 展示查询结果 → 查看权限详情与来源 → （可选）跳转至配置页 → 切换维度或结束查询

**必须处理的异常：**
- 查询权限不足：管理员试图查询超出自身管理范围的用户或角色时，明确告知"你没有权限查看该对象的权限信息"，并说明可联系谁申请 [GAP]
- 查询对象不存在：输入的用户或角色在系统中不存在时，提示"未找到该用户/角色"
- 查询结果为空：合法查询但对应对象无任何权限时，提示"该用户/角色当前没有任何权限"，与查询失败区分
- 数据加载失败：系统异常时提供重试入口

**必须解释的状态：**
- 权限生效状态（已生效 / 未生效 / 被治理暂停）
- 权限来源类型（直接授权 / 角色授权 / 应用可见性 / 协作可见性）
- 如果是角色授权，标注来源角色名称

**必须保护的风险：**
- 查询入口的访问控制：入口不可见时不在导航中显示，不可通过 URL 直接访问
- 查询范围的二次校验：即使入口可见，查询特定对象时仍需校验管理员是否有权查看该对象
- 敏感权限标注：如果某权限被标记为敏感（如删除权限、全员数据导出权限），在结果中需有视觉区分 [GAP]

**可自行设计的内容（不需要等业务确认）：**
- 五个维度的切换方式（Tab / 下拉 / 单选组）
- 查询结果的布局（列表 / 卡片 / 分组折叠）
- 来源的渐进披露交互（hover 展开 / 点击展开 / 侧边栏）
- 查询历史是否保留在本地（不涉及服务端日志的前提下）

**报错和阻断场景中的业务依据状态：**
- "查询权限不足"：业务依据充分（访问控制是硬约束），可直接进入体验设计
- "查询对象不存在"：业务依据充分，可直接进入体验设计
- "查询结果为空"：需区分"无权限"和"查询失败"，业务依据充分
- "大批量结果"：分页/折叠策略需要经验数据支撑，建议 experience 阶段先做保守设计（默认折叠、分批加载），后续根据实际数据量调整 [GAP]

## 9. 待确认问题

以下问题会影响后续方案的具体落地，建议在进入 experience 阶段或开发前确认：

1. **间接授权是否纳入查询结果？** 如果张三通过"华东区管理员"角色拿到了报表权限，按用户查张三时是否展示？这会影响查询结果的数据量和来源展示逻辑。建议：一期先纳入角色授权（这是最常见的管理场景），组织授权和岗位授权等数据源就绪后再扩展。

2. **查询入口的访问控制范围？** 权限管理员和超级管理员的查询范围是否一致？如果权限管理员被限制只能查自己管理范围内的人，这个"管理范围"如何定义——是按组织架构还是按角色分组？建议：一期以组织架构范围作为权限管理员的查询边界。

3. **一期和二期的具体分界？** 建议一期=用户维度+角色维度，权限维度在间接授权口径确认后纳入一期后半段，OA表单和报表维度作为二期。是否同意这个分期方式？

4. **权限来源展示粒度？** 默认展示来源类型（标签），点击展开来源链路。是否接受这个渐进披露方案？

5. **查询操作是否需要记录日志？** 如果需要，日志的范围是仅记录"谁查了谁"还是记录完整的查询条件和结果摘要？

6. **查询结果是否提供跳转至权限调整页面的入口？** 建议提供——查询的终点往往是"发现问题需要调整"，如果不给跳转，管理员需要记住查询结果再导航到配置页，流程断裂。
