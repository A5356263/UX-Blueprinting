# 业务蓝图

> 输入来源：projects/permission-dimension-query/workspace/facts.md，以及知识库中权限域的对象模型、来源模型、查询路径缺口和体验风险模式。

## 0. 本次关键设计判断

**判断：**

需求方向成立，但必须分期建设。一期聚焦用户维度和角色维度，建立统一的查询结果模型和访问控制框架，权限维度紧随其后，OA 表单和报表维度作为二期。不建议五个维度在同一期全部上线——各域数据就绪程度不同，强行一起上会导致查询口径不一致，反而破坏管理员对系统的信任。

**主要影响：**

1. 需要在权限管理域内新增独立查询入口，而非在各域页面内分别扩展查询列表
2. 查询结果的统一解释模型是本次核心设计资产——来源追溯、生效状态、跨域权限差异必须在结果中可读
3. 访问控制需要与查询能力同步设计，查询入口本身就是敏感能力

**建议方案：**

- 独立统一查询中心，五个维度通过统一的维度切换组件承载
- 一期覆盖用户维度和角色维度，权限维度在间接授权口径确认后纳入
- 查询结果以来源追溯为核心特征，采用"默认标签 + 点击展开链路"的渐进披露策略

**不建议方案：**

- 不建议把五个维度拆成五个独立页面各自实现——这会延续"跨模块散落导致查询分裂"的已知体验风险
- 不建议五个维度同一期全部上线——各域数据口径尚未统一，强行聚合会导致不同维度查到矛盾结果

**关键待确认：**

1. 间接授权（通过角色、组织、岗位等获得的权限）是否纳入查询结果
2. 查询入口的访问控制范围——管理范围按组织架构还是角色分组定义

> 更多待确认问题详见 `## 9. 待确认问题`。

## 1. 一句话结论

可以做，值得做，但必须分期。一期聚焦用户维度和角色维度，建立统一的查询结果模型和访问控制框架。权限维度紧随其后。OA 表单和报表维度等跨域数据口径统一后再纳入。

## 2. 这件事为什么值得正式做

现在的问题是：管理员要核对一个人的完整权限，需要在权限管理、应用管理、审批管理、报表管理、OA 表单等多个设置页面之间切换查找。每个域的权限结构不一样，管理员需要自己把碎片信息拼凑成完整结论。这在权限审计和离职交接等场景下尤其危险——漏查一个域就可能漏掉一条关键权限。

这件事不能靠线下来解决。权限核对是高频操作（权限管理员几乎每天都会用到），也是高风险的（漏查可能导致安全漏洞）。继续让管理员在各域页面之间手动切换兜底，效率和准确性都无法保证。

方案成立的前提：
- 一期只能在数据源已在权限域内闭环的维度上建设（用户维度和角色维度），这是查询口径一致性的前提
- 访问控制框架必须与查询能力同步设计，不能先做查询再补安全
- 知识库已有的对象模型和来源模型可以直接作为查询结果解释框架的底座

如果间接授权口径无法在短期内确认、或访问控制的角色范围无法定义，应先限定一期范围（只做直接授权的用户和角色查询），后续再扩展。

## 3. 值不值得做

**收益：**

- 权限核对效率：将管理员从"在多个页面之间切换逐项核对"变成"在一个入口多维度查看"，单次核对时间大幅缩短
- 审计能力：补齐按权限反查和跨域查询的能力缺口，让安全审计从"靠管理员个人经验"变成"有系统工具支撑"
- 风险发现：异常授权、过度授权、敏感权限扩散等问题在统一查询视角下更容易暴露
- 信任感提升：对高安全诉求企业来说，权限透明度本身就是竞争力

**成本：**

- 开发成本：一期涉及统一查询入口建设、用户和角色维度的查询接口对接、查询结果模型设计、访问控制配置。二期涉及跨域权限数据聚合、审批域和报表域的数据源接入
- 维护成本：查询口径需要随各域权限模型的变化同步调整，特别是数据权限的展示口径变化频繁
- 认知负担：管理员需要理解"不同域的权限看起来不一样是正常的"，这对查询结果的解释设计提出了较高要求

**系统代价：**

- 链路复杂度增加：统一查询中心需要聚合来自多个功能域的数据，查询链路的稳定性和性能依赖各域数据源的可用性
- 访问控制管理成本：查询入口的访问控制需要与已有角色体系对接，管理范围的定义和维护会增加管理员配置工作量
- 口径维护成本：各域权限定义变化时，查询口径层的映射需要同步更新

**综合判断：**

收益大于成本，但前提是分期建设、口径统一。一期的投入产出比最清晰——用户维度和角色维度覆盖了最高频的核对场景，数据源已在权限域内闭环，可以直接验证统一查询模型是否成立。

## 4. 应该做成什么能力形态

**路径 A：独立统一查询中心。**

在权限管理域内新增独立查询入口，五个维度统一收纳，共用一套查询结果模型和访问控制框架。

优点：入口明确，概念统一，方便后续扩展新维度。查询页的"解释不配置"边界清晰，不会和已有配置页的功能混淆。缺点：需要在权限管理导航中新增入口，对现有信息架构有一定影响。

**路径 B：在各域页面内扩展查询能力。**

在用户授权页加按用户查、在角色管理页加按角色查、在各业务域页面加对应维度的查询，不设统一入口。

优点：改动范围小，每个维度独立迭代。缺点：这正是现有"跨模块散落导致查询分裂"模式的延续。五个维度的查询口径会各自为政，管理员仍然需要在不同页面之间切换来拼凑完整图景。

**推荐：路径 A（独立统一查询中心）。**

路径 B 虽然改动小，但违背了本次需求的核心目标——统一查询视角。如果只是为了在现有页面加一个搜索框，那不是这次要解决的问题。

统一查询中心的具体形态：
- 作为权限管理域内的独立功能模块，与用户授权、角色管理、权限查询（现有）并列
- 入口对权限管理员和超级管理员可见，审计人员按需开放
- 五个维度通过统一的维度切换组件承载，不设五个独立页面
- 查询结果共用一套结构化模型，但允许按域差异展示不同字段组合

## 5. 推荐业务方案

### 角色与职责

| 角色 | 查询范围 | 限制 |
| --- | --- | --- |
| 权限管理员 | 所管理范围内的用户和角色权限 | 不能查看超级管理员的完整权限清单；不能查看超出自身管理范围的用户 |
| 超级管理员 | 全企业所有用户和角色的权限 | 无范围限制；查询操作是否记录日志待确认 |
| 审计/安全人员 | 按需申请查询范围，或默认只读全局权限分布统计 | 不能查看具体用户的完整权限清单（除非获得授权）；是否单独设置审计角色待确认 |

### 主流程闭环

**一期（用户维度 + 角色维度）：**

1. 管理员进入统一查询中心，选择查询维度（用户 / 角色）
2. 输入查询对象（用户名或角色名），系统校验输入对象是否存在、管理员是否有权查询该对象
3. 系统返回查询结果，按权限类型分组展示（功能权限、数据权限），每条结果标注来源和生效状态
4. 管理员查看结果，可通过来源标注了解权限从哪来
5. 查询结束。如有需要，管理员可切换维度继续查询

**二期（权限维度 + OA 表单维度 + 报表维度）：**

流程同上，但数据源扩展至审批域和报表域，查询结果中按域区分权限来源。

### 前置配置

- 查询入口的可见性需与管理员角色绑定，非所有管理员默认可见
- 管理员的查询范围（能查哪些用户、哪些角色）需在角色配置中定义，具体按组织架构范围还是角色分组定义待确认
- 如果查询操作需要记录日志，需在审计配置中开启

### 结果回写与记录沉淀

- 查询结果本身不产生权限变更，不回写任何配置数据
- 如果查询操作需要留痕，记录内容包括：谁在什么时间查询了什么对象的什么维度

## 6. 必须守住的规则和边界

**查询不等于配置：** 查询页不能提供任何直接修改权限的能力。如果查询结果揭示了一个问题（如某人权限过多），管理员需要回到授权页或角色管理页去调整。可以在结果中提供跳转入口，但不能在查询页嵌入修改能力。

**访问控制是硬约束：** 查询入口不得对普通用户开放。不同管理员角色的查询范围必须可配置、可区分。超级管理员的全局查询权限不能默认下放给所有管理员。访问控制必须做两层——入口可见性（菜单是否展示）和查询范围限制（能查哪些人、哪些角色）。

**来源追溯不可省略：** 查询结果必须标注每条权限是通过什么方式获得的——是直接授予这个人的，还是通过某个角色获得的，还是因为应用或协作范围自动可见的。不能只给"有/没有"的二元结论。标注到哪个粒度（只标获得方式类型还是展示完整链路）需要确认，但至少必须标注获得方式类型。

**跨域权限颗粒度不得强行统一：** 管理类权限关心的是"这个菜单能不能点"，OA 表单权限关心的是"这个字段能不能看"，报表权限关心的是"这个报表能不能导出"。它们的描述方式天然不同，不应强行套用同一个字段模板。

**不支持的能力不应留入口：** 导出、模糊搜索、权限验证模式这些已确认不支持的能力，不应在页面上留下灰掉或"即将上线"的入口。

**权限的生效状态必须可见：** 如果某条权限因为审批未完成或管理规则暂停而实际不能使用，查询结果必须明确标注，不能显示为"有权限"让管理员误判。

## 7. 主要风险与保护策略

**风险一：查询口径不一致导致结果矛盾。**

影响：管理员在用户维度查到某人有某权限，但在权限维度查同一权限时找不到这个人，产生信任危机。

真实原因：这是跨域数据口径问题——用户维度的数据来自权限域，权限维度的数据可能需要聚合多个域，口径不一致会导致结果不一致。

缓解策略：在一期仅开放数据源闭环的维度（用户、角色），避免跨域口径不一致的问题。在查询结果中明确标注数据来源域和查询口径说明，让管理员知道"不同维度查到的范围可能不同，这是正常的"。

**风险二：来源信息过于复杂导致管理员放弃理解。**

影响：如果每条权限标注了完整的来源链路（直接授予→来自角色 X→角色 X 由管理员 Y 在某时间配置），信息密度过高，管理员反而会忽略来源信息。

缓解策略：采用渐进披露——默认展示获得方式类型（一行标签），点击展开完整链路。不要把完整来源链路平铺在结果列表里。

**风险三：查询入口本身变成权限泄露渠道。**

影响：如果访问控制配置不当或存在越权漏洞，任何能访问查询入口的用户都可能看到全员权限分布。

缓解策略：查询入口的访问控制必须做两层校验——入口可见性 + 查询范围限制。超级管理员的权限清单和高风险权限的持有人信息应被视为敏感数据，默认不向权限管理员开放。

**风险四：大批量结果导致页面不可用。**

影响：查询超级管理员或大型角色时，结果可能包含数百条权限和数千个用户，一次性全部展示会导致页面卡顿或管理员无法定位。

缓解策略：结果按权限类型分组折叠展示，默认只展开第一组。用户列表超过一定数量时分批加载或提供筛选。具体的分页和折叠策略由 experience 阶段细化。

## 8. 方案承接要求

后续 experience 阶段必须承接以下内容：

**必须覆盖的角色：**
- 权限管理员（高频使用者，查询范围受限）
- 超级管理员（全局审计，查询范围不受限）
- 审计/安全人员（按需开放，查询范围待定义）

**必须闭环的主流程：**
- 选择查询维度 → 输入查询对象 → 校验输入合法性 → 校验查询权限 → 展示查询结果 → 查看权限详情与来源 → （可选）跳转至配置页 → 切换维度或结束查询

**必须处理的异常：**
- 查询权限不足：管理员试图查询超出自身管理范围的用户或角色时，在操作前通过匹配范围控制提示，提交后被阻断时告知原因和申诉路径
- 查询对象不存在：输入的用户或角色在系统中不存在时，提示"未找到该用户/角色"
- 查询结果为空：合法查询但对应对象无任何权限时，提示"该用户/角色当前没有任何权限"，与查询失败区分
- 数据加载失败：系统异常时提供重试入口

**必须解释的状态：**
- 权限生效状态（已生效 / 未生效 / 因管理规则暂停）
- 权限获得方式（直接授予 / 通过角色获得 / 应用可见范围 / 协作可见范围）
- 如果是通过角色获得的，标注来源角色名称

**必须保护的风险：**
- 查询入口的访问控制：入口不可见时不在导航中显示，不可通过 URL 直接访问
- 查询范围的二次校验：即使入口可见，查询特定对象时仍需校验管理员是否有权查看该对象
- 敏感权限标注：如果某权限被标记为敏感（如删除权限、全员数据导出权限），在结果中需有视觉区分

**可作为设计建议的内容（不需要等业务确认）：**
- 五个维度的切换方式（Tab / 下拉 / 单选组）
- 查询结果的布局（列表 / 卡片 / 分组折叠）
- 来源的渐进披露交互（hover 展开 / 点击展开 / 侧边栏）
- 查询历史是否保留在本地（不涉及服务端日志的前提下）

## 9. 待确认问题

1. **间接授权是否纳入查询结果？**

   影响：如果纳入，通过角色、组织、岗位等渠道获得的权限都会出现在个人查询结果中，数据量更大但更完整。如果不纳入，查询结果只展示直接授予个人的权限，遗漏了最常见的权限获取方式。
   建议：一期先纳入角色授权（这是最常见的管理场景），组织授权和岗位授权等数据源就绪后再扩展。
   建议确认方：产品

2. **查询入口的访问控制范围如何定义？**

   影响：决定权限管理员能查哪些人——是按组织架构（本部门及下属部门），还是按角色分组（被分配了某类管理角色的人），还是两者的组合。这直接影响查询的匹配建议过滤逻辑和阻断规则的实现。
   建议确认方：产品

3. **查询结果是否提供跳转到权限调整页面的入口？**

   影响：查询的终点往往是"发现问题需要调整"。如果不给跳转，管理员需要记住查询结果再导航到配置页，流程断裂。如果给跳转，需要在结果卡片上增加操作入口。
   建议确认方：产品

4. **权限来源展示粒度？**

   影响：只展示获得方式类型（如"通过角色获得"），还是展示完整链路（如"通过角色'华东区管理员'获得 → 由管理员李四在 2024-01-15 配置"）。前者信息密度低但信息量少，后者可追溯性强但可能造成信息过载。
   建议确认方：产品、设计

5. **查询操作是否需要记录日志？**

   影响：如果需要，日志的范围是仅记录"谁查了谁"还是记录完整的查询条件和结果摘要。这会影响查询能力的审计合规性，也会增加系统复杂度。
   建议确认方：安全、产品

6. **权限维度查询的最终优先级？**

   影响：需求文档内部存在矛盾（截图标注为高优先级，汇总表标注为中优先级）。如果实际为高优先级，应在一期内纳入（在间接授权口径确认后），而不是等到二期。
   建议确认方：产品

7. **一期和二期的具体分界？**

   影响：当前建议一期=用户维度+角色维度，权限维度在间接授权口径确认后纳入一期后半段，OA 表单和报表维度作为二期。分界方式需要产品确认。
   建议确认方：产品

### 业务知识转译说明

正文中已将以下知识术语转译为业务语言：

- 来源类型：`ACL_DIRECT` → "直接授予"、`RBAC_ROLE` → "通过角色获得"、`APP_VISIBILITY` → "应用可见范围"、`COLLAB_VISIBILITY` → "协作可见范围"
- 修饰因子：`GOVERNANCE_MODE` → "管理规则暂停"
- 对象模型：`主体/资源/动作/范围/来源/修饰因子/状态` → 查询结果中"谁、能做什么、在什么范围、通过什么方式、是否生效"的解释框架
- 体验风险模式：`RISK-002（来源不透明）` → 来源标签 + 渐进披露策略、`RISK-005（查询分裂）` → 统一查询入口而非五个独立页面
