# 通用复杂度判断标准

## 核心公式

复杂度 = 底层业务改动程度 + 体验设计压力

先判断底层业务骨架是否变化，再判断体验设计压力落在什么地方。

不要把领域词、风险词或功能名直接等同于复杂度结论。

## 底层业务改动六问

1. 是否改变业务对象关系？
2. 是否改变业务规则？
3. 是否改变状态机？
4. 是否改变生效机制？
5. 是否改变数据口径？
6. 是否涉及外部回写链路？

只要其中一项不清楚，就不能草率给出确定复杂度结论。

## 体验设计压力五问

1. 涉及多少角色？
2. 信息密度是否高？
3. 异常与分支是否多？
4. 是否跨端？
5. 概念边界是否模糊？

体验设计压力高，不等于底层业务一定复杂；但它会决定体验方案需要展开到什么程度。

## 低复杂度

适用于：

- 不改对象、规则、状态、生效、口径、回写。
- 只改展示、布局、字段、文案、反馈、视觉强调、收纳方式。

典型内容：

- 页面布局调整
- 字段顺序调整
- 分组折叠
- 空状态和提示文案
- 结果态视觉强调
- 局部交互反馈优化

处理方式：

- 直接输出体验策略。
- 补一段必要业务依据。
- 重点写展示、交互、反馈和极限状态。

## 中等复杂度

适用于：

- 复用现有业务逻辑。
- 在既有能力上新增局部操作、批量能力、异常处理、消息提醒、角色化入口。
- 不改底层业务骨架，但明显改变任务路径、信息结构或状态反馈。

典型内容：

- 新增复制、批量、催办、转交等操作
- 增加失败明细查看
- 增加批量确认或结果汇总
- 新增角色化入口，但不改可见性模型
- 新增局部异常反馈或轻分支

处理方式：

- 先补轻量业务判断。
- 再输出体验策略。
- 重点写入口、流程、边界、异常、反馈和下一步。

## 高复杂度

适用于：

- 改变主数据模型或对象关系
- 改变状态机
- 改变审批或生效机制
- 改变数据口径或隔离边界
- 引入或改变外部回写链路
- 跨模块或跨领域统一模型

典型内容：

- 主数据关系重构
- 审批后生效、定时生效或回滚机制改造
- 银行代发、税局申报、ERP / 总账回写
- 统一待办模型
- 多租户、多法人、多项目隔离模型变化

处理方式：

- 先做完整业务判断。
- 再输出体验蓝图。
- 重点写角色、对象、规则、状态、风险、页面承接和待确认项。

## 判断边界提醒

- 不因为“权限、审批、财务、税务”直接判高复杂度。
- 不因为“文案、页面、字段”直接判低复杂度。
- 不用规则替代 UXB 的业务与体验判断。
- 判断不准时，先提问，不硬猜。
