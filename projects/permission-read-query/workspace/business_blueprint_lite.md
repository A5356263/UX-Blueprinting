# 轻量业务蓝图

## 0. 路线说明

**判断：**

这次是给现有的权限体系补一个统一的只读查询视图，不改权限对象、授权规则、生效机制和状态流转，适合按轻量业务蓝图承接。

**主要影响：**

1. 查询维度的业务定义需要明确——按人查、按角色查、按权限反查三个入口各自返回什么、不返回什么
2. 三种角色的查看范围边界需要写清，否则体验方案无法设计差异化的查询入口和结果页
3. 不同权限颗粒度（功能权限、数据权限、表单权限、字段权限、报表权限）在结果中的分组和层级关系需要统一

**建议方案：**

- 先以"查询结果是什么、从哪来、谁可以看到什么范围"为主线，写清业务规则
- 再把角色边界、权限来源归属、颗粒度分组作为体验承接的硬约束交给 experience 阶段
- 按权限反查的结果承载方式（人员列表 vs 角色→人员层级）优先选择按人员列表直展，角色信息作为每行的附属字段

**需要重新判断的信号：**

1. 后续如果要加入"从查询结果直接跳转到授权编辑"，说明从只读变成了读写联动
2. 后续如果要加入导出、变更记录、权限对比等功能，说明从查询扩展到了审计工具

## 1. 一句话结论

可以做。在现有权限数据之上建立一个纯查询的统一视图，不改动任何底层权限逻辑。核心工作是定义三个查询维度的输入输出规格、统一五种权限颗粒度的结果展示方式，以及按角色区分查看范围。

## 2. 关键业务规则

- 查询是只读操作。从查询结果页不提供任何权限增删改入口，不触发任何权限变更、审批或生效流程。
- 三个查询维度各自独立，但共用同一套权限数据源：
  - 按人查：输入一个人员，输出该人员的全部权限清单，包含直接授权和角色继承两类来源
  - 按角色查：输入一个角色，输出该角色包含的全部权限项，以及当前拥有该角色的人员数量
  - 按权限反查：输入一项具体权限，输出拥有该权限的全部人员列表，标注每人的获取方式
- 每项权限在结果中至少携带：权限名称、权限类型、所属应用或模块、获取方式（直接授权 / 角色继承）、生效状态。
- 权限类型按五类分组展示：功能权限、数据权限、表单权限、字段权限、报表权限。分组顺序固定，不按应用不同而变动。
- 获取方式只区分两种：直接授权（管理员将权限直接授予该人员）和角色继承（人员因拥有某角色而获得该权限）。如果同一权限同时来自两种来源，以直接授权为准展示。
- 角色查看范围：
  - 权限管理员：只能查询所管辖范围内的人员和角色。管辖范围由组织架构中的管理范围决定。
  - 超级管理员：可查询全组织范围内的人员、角色和权限。
  - 审计人员：查看范围同超级管理员（全组织），但界面需在视觉上标识"只读"身份，且不出现任何配置入口。
- 权限颗粒度不一致是正常现象。不同应用可以只有菜单级权限而无操作级权限，结果中不做补齐或隐藏，只如实呈现。

## 3. 边界与风险

**边界（本次不做）：**

- 不提供从查询结果跳转到授权编辑的能力
- 不提供导出功能
- 不提供权限变更记录查看
- 不提供权限对比（两人之间或两角色之间）
- 不提供权限快照或历史版本
- 不改变任何权限数据，纯展示

**关键风险：**

- 权限数据源本身的不一致风险：如果同一人员在两个系统中权限数据不同步，查询结果可能不完整。但这个风险属于数据层，不在本次体验设计范围内。查询结果页应如实展示当前系统数据，并标注数据来源。
- 按角色查的语义模糊风险：知识库中按角色查标记为"部分可行"，意味着当前角色管理页可能不包含完整的权限明细视图。本次需要独立定义按角色查询的结果结构，不依赖现有角色管理页的展示逻辑。
- 角色边界理解偏差风险：权限管理员的"所辖范围"定义如果与组织架构中的管辖范围不一致，会导致查询结果范围争议。本次以组织架构中的管辖范围为唯一依据。

## 4. 体验承接要求

**角色：**

- 必须覆盖权限管理员、超级管理员、审计人员三种角色
- 权限管理员和超级管理员的差异在于查询范围，不在功能入口
- 审计人员的界面需有"只读"身份标识

**流程：**

- 主流程：进入查询页 → 选择查询维度（按人/按角色/按权限）→ 输入查询条件 → 查看结果 → 切换维度或修改条件重新查询
- 三个维度之间的切换不要求回到首页，支持在当前页直接切换

**进度与结果状态：**

- 本次为纯查询，不涉及业务流程状态变化
- 查询结果有两种状态：有结果、无结果
- 有结果时按权限类型分组展示
- 无结果时需给出明确提示，区分"该对象确实无权限"和"查询条件无法匹配"

**异常：**

- 查询无结果：区分是人员无权限、角色无权限项、还是权限无人拥有，给出不同的空状态说明
- 权限颗粒度差异：当某应用只有粗粒度权限而无细粒度权限时，在结果中做视觉区分，避免管理员误认为数据缺失
- 跨应用权限来源不一致：同一人员在不同应用中的同一类权限可能来自不同角色，结果中需清晰标注

**反馈：**

- 查询结果加载过程中需有明确的状态反馈（加载中 / 已加载 / 加载失败）
- 查询条件输入时提供搜索建议或模糊匹配
- 如果查询范围受角色限制（如权限管理员只能看所辖范围），在界面上告知当前查看范围

**文案：**

- 权限类型名称统一使用：功能权限、数据权限、表单权限、字段权限、报表权限
- 获取方式统一使用：直接授权、角色继承
- 避免使用"可见性""治理状态"等内部术语，面向管理员用"能否看到""是否生效"

## 5. 升级信号

出现以下任一变化时，应停止当前轻量执行并请求 UXB 重新判断：

- 需求方要求从查询结果直接跳转到编辑或授权页面
- 需求方要求加入导出、批量操作、权限对比、变更记录等功能
- 需求方要求新增权限类型（超出当前五种）
- 需求方要求修改权限管理员"所辖范围"的定义方式
- 发现权限数据源本身存在结构性问题，导致查询结果不可信
