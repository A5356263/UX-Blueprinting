# 背景与分析收敛

## 项目上下文

### 已有系统状态

当前产品已有一套权限管理能力体系，包括：

- 按人直授（ACL_DIRECT）、按角色授权（RBAC_ROLE）、应用可见性（APP_VISIBILITY）、协作可见性（COLLAB_VISIBILITY）四类权限来源
- 权限变更审批模式、子管理员模式、双管理员互审模式三类治理机制
- 权限查询排障链路（按用户查询结果、权限详情）
- 审批管理中台的通用审批能力

### 本次需求定位

在已有权限体系中新增"员工自助申请权限"能力，核心变化是：

**权限获取方式从纯管理端推送，扩展到员工端可主动拉取，穿过审批后自动落到授权。**

这不止是新增一个申请页面，而是权限治理模型的一次扩张。

## 分析总结收敛

### 已明确的关键判断

1. **业务对象层面**：需要新增"权限申请单"这一中间对象，承载"员工发起申请→审批→自动授权"的完整生命周期。申请单不是权限本身，是权限获取的中间态载体。

2. **状态机层面**：申请单有自己的状态流转（发起→待审批→通过/拒绝→已授权/已关闭），且需要和已有的治理状态模型（已授予、已生效）之间有明确的交接关系。

3. **生效机制层面**：权限从"管理员直授即生效"扩展到包含"员工申请→审批通过→系统自动授权生效"的新路径。`ACL_DIRECT` 来源需要能追溯区分"管理员手动直授"和"自助申请后自动直授"。

4. **角色层面**：涉及四类角色——超管（开关与配置）、子管理员（受组织范围约束的配置与审批）、员工（查看已有权限、发起申请、追踪状态）、审批人（审批处理）。

5. **体验层面**：核心断点不在"提交申请"，而在申请前（员工不知道能申请什么）、审批中（申请石沉大海）、完成后（是否生效、从哪里看到）。

### 必须在方案中解决的问题

1. 员工端"可申请权限"的可见范围必须和管理端"可申请范围配置"形成可解释的闭环
2. 审批链路必须在配置阶段做可达性校验，而非等第一单卡住才暴露
3. 申请单状态需向申请人和审批人双向透明，且和最终授权结果可追溯
4. "关闭自助申请能力"时进行中申请的处理规则必须明确定义
5. 员工端、审批端业务规则需要从零补齐

### 仍在悬空的 GAP

- **[阻断型] 自助申请与已有权限治理模式的关系**：叠加还是互斥？如果产品侧还没有结论，这是配置端信息架构设计前必须关闭的前提。
- **[非阻断型] 可申请范围按角色还是按功能权限配置**：影响管理端配置页的信息结构，但不影响整体任务方向。
- **[非阻断型] 员工端规则和审批端规则**：文档空白，设计阶段需要基于产品规则补充。

### 设计知识消费

本次已消费以下设计准则：

- 治理、信任与可解释性原则（G-01 最小惊讶、G-02 可解释性、G-03 可追溯、G-04 最小授权）
- 认知与决策原则（C-01 选择越多越慢、C-02 工作记忆有限、C-04 渐进披露、C-05 默认效应、C-06 损失厌恶、C-07 峰终定律）
- 流程模式选择原则（步骤条仅用于真实分步流程）
- 反馈与报错体验设计指南（反馈形式选择、报错文案要求）
