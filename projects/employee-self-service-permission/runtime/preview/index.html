Business Blueprint

0. 本次关键设计判断

判断：

这是一个需要完整业务方案的高复杂度需求。核心挑战不是"做一个申请表单"，而是在现有权限体系的来源模型、治理状态模型和角色边界中，新增一条完整的权限获取通道，同时保证与现有治理模式的互斥约束不产生冲突。

主要影响：

  1. 权限来源模型需要扩展新的 source 枚举值（自助申请），并定义其与 ACL_DIRECT、RBAC_ROLE 的优先级关系
  2. 治理状态模型需要在现有 draft→pending→approved→rejected→effective→revoked 状态机中，承载自助申请特有的状态流转和审批后自动生效的写回链路
  3. 全局治理配置页需要新增模式卡片和互斥检测逻辑，现有双管理员模式的开启状态成为前置校验条件
  4. 审批中台的审批表单模板、审批人规则、超时策略需要为"权限申请"这一新业务类型做专属配置

建议方案：

  • 在现有权限来源模型（source_enum）中新增 SELF_SERVICE_APPLY 来源类型，优先级低于管理员直授（ACL_DIRECT），与角色授予（RBAC_ROLE）同级叠加
  • 复用现有审批中台的审批引擎，为权限申请创建专属审批表单模板，审批人默认规则为"直属上级→部门负责人→权限管理员"逐级升级
  • 在白名单配置中，敏感权限（超管角色、审计相关权限）系统级硬编码排除为禁区名单，对管理员可见但不可编辑
  • 审批通过后走现有权限分配管线完成自动授权，记录来源为 SELF_SERVICE_APPLY

不建议方案：

  • 不建议另建独立审批引擎——增加维护成本且与现有审批待办列表割裂
  • 不建议把可申请范围做成黑名单模式——安全风险高，白名单模式更可控
  • 不建议把自助申请权限做成完全独立于现有权限体系的新模块——应复用现有权限查询、排障和审计能力

需要确认：

  1. 审批通过后的自动授权，是否需要保留审批记录和授权日志的关联关系，用于后续审计追溯
  2. 子管理员的组织管辖范围是否应约束到可申请范围的白名单配置能力
  3. 权限被回收后（如管理员手动收回），是否需要在员工的申请历史中标记

1. 一句话结论

能做，建议做。核心是把自助申请作为一种新的权限治理模式，在现有权限体系中以"白名单+审批必达+自动授权"的闭环实现。关键是守住三条底线：与双管理员模式互斥、敏感权限硬排除、审批链路必须闭环不可跳过。

2. 需求是否成立

  • 解决什么问题： 中大型企业员工权限获取效率低，每次权限变更都要找管理员或老板，沟通成本高，时效不稳定
  • 影响哪些角色： 超级管理员/权限管理员（配置和管控）、员工（申请和使用）、审批人（审批处理）
  • 判断：成立。 这不是一个拍脑袋的需求——有明确的痛点场景（员工多、流动大、权限变更频繁）、有竞品参考（金蝶已有类似能力）、有清晰的价值指标（至少 3 家客户使用）。核心价值是把权限申请的入口从"找管理员"变成"走流程"，同时保留管理员对范围和审批的控制权

3. 值不值得做

  • 收益：
  • 业务价值：降低权限管理的沟通成本，让权限分配从"私下沟通"变成"流程化处理"
  • 效率提升：员工自助查看权限减少了向管理员确认的成本，批量申请场景下效率提升更明显
  • 用户价值：对中大型企业客户是刚需级别的差异化能力，目前主流协同办公产品暂未提供
  • 成本：
  • 开发：涉及管理后台、员工端、审批端三端改造 + 审批中台配置 + 权限体系扩展，工程量中等偏大
  • 维护：新增一种治理模式意味着后续的排障、审计、培训都需要多覆盖一条链路
  • 培训：一线反馈提到员工培训成本可能上升（参见需求文档 8.1），需要做好员工端的引导和帮助文案
  • 综合判断：值得做。 收益面覆盖了效率、体验和竞争差异化，成本可控（复用审批中台和权限管线，不另起炉灶），风险主要在培训和安全，均可通过配置约束和体验设计缓解

4. 应该做成什么能力形态

  • 路径一：独立功能模块。 在管理后台独立建一个"自助申请权限"模块，不从属于现有权限管理模式。优点是完全解耦、不干扰现有配置；缺点是与现有权限治理体系割裂，管理员需要在两个地方管理权限
  • 路径二（推荐）：扩展既有权限治理模式。 在现有"权限管理模式"页面中新增一种"员工自助申请权限"模式卡片，与其他治理模式（如双管理员模式）并列。优点是管理员在同一个地方管理所有权限治理配置，一致性高；缺点是需要处理模式互斥的交互逻辑
  • 路径三：纯配置化。 不新增独立页面，完全在现有权限配置中增加开关和参数。优点是最小改动；缺点是配置分散、管理员难以形成完整的模式认知

推荐路径二。 理由：自助申请本质是一种新的权限治理模式，与其他治理模式具有同等的概念层级和配置复杂度，放在"权限管理模式"页中并列展示是最自然的信息架构。模式互斥的交互虽然需要额外设计，但这是业务规则必须承载的，不是路径选择带来的额外成本。

5. 推荐业务方案

5.1 角色与职责

  • 超级管理员： 默认拥有开启/关闭自助申请模式的权限，可配置白名单和审批规则。继承系统级全量功能权限。新任超管自动继承该配置能力
  • 权限管理员（子管理员）： 能否配置自助申请模式取决于超管赋予的组织管辖范围和应用管辖范围。如果管辖范围内包含权限管理应用，则可配置
  • 员工： 可查看自己的权限、发起权限申请、查看申请记录。仅面向正式员工，服务人员第一期不开放
  • 审批人： 默认由申请人的直属上级担任。支持超管在配置时替换为指定角色或指定人员。审批人负责对申请做同意或拒绝的决定

5.2 主流程闭环

  1. 管理员配置阶段： 进入权限管理模式页 → 检测双管理员模式互斥 → 设置可申请范围白名单 → 设置审批规则 → 确认开启
  2. 员工申请阶段： 进入我的权限 → 查看已有权限 → 发现缺口 → 发起申请（选择权限+填写原因）→ 提交
  3. 审批处理阶段： 审批人收到待办 → 查看申请详情 → 同意或拒绝 → 同意则系统自动走授权管线
  4. 结果确认阶段： 员工收到通知 → 查看申请状态 → 已通过则在"我的权限"中确认新权限生效

5.3 前置配置

管理员在开启自助申请前必须完成两项配置：

  • 可申请范围（白名单）： 从所有角色和功能权限中勾选允许员工申请的权限。敏感权限系统级硬排除，灰显不可选
  • 审批规则： 默认审批人为申请人的直属上级，兜底链路为部门负责人→权限管理员逐级升级。管理员可调整审批人来源

5.4 结果回写与记录沉淀

  • 审批通过后自动调用权限分配管线，为申请人授予所申请权限，权限来源标记为 SELF_SERVICE_APPLY
  • 审批拒绝不产生权限变更，拒绝原因随申请记录保存
  • 模式开启、关闭、白名单修改、申请提交、审批处理等关键操作均需记录操作日志，纳入现有审计体系
  • 申请记录在权限查询页中应可被追溯（按人查询时展示权限来源含"自助申请"）

6. 必须守住的规则和边界

不能放开的限制

  • 敏感权限硬排除： 超管角色、审计相关权限等，不可被纳入白名单，不可被申请。禁区名单对管理员可见但不可编辑
  • 与双管理员模式互斥： 两种模式不可同时开启。开启自助申请前必须确保双管理员模式已关闭
  • 仅面向正式员工： 服务人员、外部人员第一期不可使用该能力

必须审批的场景

  • 所有权限申请必须经过审批才能生效，不可跳过
  • 审批人可以是直属上级、部门负责人、指定角色、指定人员或权限管理员，但不可为空
  • 审批人缺失时必须逐级升级，不可让申请处于无人处理的状态

必须二次确认的操作

  • 管理员关闭自助申请能力（尤其存在审批中申请时）
  • 管理员从白名单中移除已有审批中申请的权限
  • 员工撤销审批中的申请

必须前置说明的信息

  • 开启前：告知管理员该模式与双管理员模式互斥
  • 员工申请页：说明可申请的范围由管理员配置，如果找不到需要的权限请联系管理员
  • 关闭时：告知管理员关闭后对已获权限和审批中申请的处理策略

7. 主要风险与保护策略

风险 7.1：权限越权申请

  • 风险是什么： 如果白名单配置过宽或敏感权限过滤遗漏，员工可能申请到不应拥有的高权限
  • 影响什么： 数据安全、系统安全、合规风险
  • 如何缓解：
  • 白名单默认全部不可申请，管理员主动勾选才开放
  • 敏感权限系统级硬排除，前端灰显 + 后端校验双重保障
  • 审批链路必须闭环，不可跳过
  • 审批通过后的授权走现有权限分配管线，不绕过既有的权限校验逻辑

风险 7.2：审批链路断链

  • 风险是什么： 默认审批人（直属上级）不存在、已离职或审批流程配置错误，导致申请无法流转
  • 影响什么： 员工申请卡死、体验差、可能需要管理员手动干预
  • 如何缓解：
  • 审批人逐级升级机制：直属上级→部门负责人→权限管理员
  • 升级时通知员工和被转交的审批人，避免无人知晓
  • 管理员可在审批管理后台监控超时申请并手动干预

风险 7.3：模式互斥处理不当

  • 风险是什么： 管理员不理解互斥逻辑，强行开启导致权限分配冲突
  • 影响什么： 权限来源混乱、治理规则失效
  • 如何缓解：
  • 开启前系统检测双管理员模式状态，互斥时弹窗阻断并提供"前往关闭"的引导
  • 在权限管理模式页的卡片描述中明确说明互斥关系
  • 操作日志记录模式切换行为，便于审计

风险 7.4：培训成本和认知负担

  • 风险是什么： 员工不了解如何申请权限、申请后流程是什么、为什么被拒绝
  • 影响什么： 申请错误率高、重复申请、员工对流程不信任
  • 如何缓解：
  • 员工首次进入"我的权限"页面时提供简短引导
  • 申请原因字段给出填写提示
  • 拒绝时要求审批人填写原因，让员工知道为什么被拒绝
  • 帮助文档覆盖常见问题（如何申请、审批多久、被拒绝怎么办）

8. 方案承接要求

后续 experience 阶段必须承接的内容：

必须覆盖的角色

  • 超级管理员 / 权限管理员：配置视角
  • 员工：申请与查看视角
  • 审批人：审批处理视角

必须闭环的主流程

  • 管理员首次配置流程（含互斥检测→白名单配置→审批规则设置→确认开启）
  • 员工查看权限 → 发现缺口 → 发起申请 → 提交确认
  • 审批人待办 → 查看详情 → 同意/拒绝 → 自动授权或通知
  • 员工查看申请记录 → 详情和状态 → 撤销或重新申请

必须处理的异常

  • 双管理员模式互斥阻断
  • 敏感权限后端兜底拦截
  • 审批人缺失逐级升级
  • 员工离职或停用时的申请处理
  • 管理员关闭能力时审批中申请的冲突
  • 白名单修改时已有审批中申请的影响提示
  • 员工重复申请已有权限的检测

必须解释的状态

  • 申请单的五个状态：审批中、已通过、已拒绝、已撤销、已关闭（员工离职触发）
  • 管理模式的开启/未开启两个状态
  • 每个状态的可见性、可操作性和下一步

必须保护的风险

  • 权限越权申请 → 白名单 + 敏感权限硬排除 + 审批必达
  • 审批链路断链 → 逐级升级 + 通知 + 超时监控
  • 模式互斥 → 开启前检测 + 阻断提示 + 引导关闭

可作为设计建议的内容

  • 员工端入口位置和因无权限拦截时的申请入口
  • 审批端卡片的信息展示优先级
  • 通知方式的选择（企微消息/站内信/短信）

报错或阻断场景中的依据状态

以下场景业务依据已足够支持体验方案：

  • 双管理员模式互斥时的阻断流程（规则明确：互斥，不可同时开启）
  • 敏感权限拦截（规则明确：系统级硬排除，不可申请）
  • 审批人缺失升级（规则明确：三级逐级升级链路）
  • 关闭时审批中申请的处理（规则明确：允许走完当前批次）

以下场景仍需确认：

  • 员工离职或停用时的申请处理（是自动关闭还是挂起，需求文档未说明）
  • 申请被拒绝后是否允许再次申请、是否有冷却期（需求文档未说明）

9. 待确认问题

  1. 审批通过后的自动授权，是否需要审批记录和授权日志的关联？ 影响审计追溯的完整性。建议由安全/合规确认。
  2. 子管理员的组织管辖范围是否约束可申请范围配置能力？ 影响权限管理员角色的功能边界。建议由权限域产品负责人确认。
  3. 权限被管理员回收后，员工申请历史中的对应记录是否需要标记？ 影响权限查询页的信息完整性。建议由产品和开发共同确认实现成本。
  4. 员工离职或停用时的审批中申请，是自动关闭还是挂起等待？ 影响状态机设计。建议参考现有审批中台对该场景的处理方式保持一致。
  5. 申请被拒绝后是否允许重新申请同一权限？是否有冷却期？ 影响员工端交互。建议由产品确认策略。

  6. 来源模型扩展 SELF_SERVICE_APPLY —— 依据来源：知识库权限管理/21_来源模型（现有 source_enum 包含 ACL_DIRECT、RBAC_ROLE、APP_VISIBILITY、COLLAB_VISIBILITY，需要新增自助申请来源）；知识库权限管理/24_治理状态模型（治理模式不改变授予事实，只影响是否生效、谁能改、何时生效）

Experience Blueprint

0. 本次关键设计判断

判断：

本次体验方案的核心是"把配置端和申请端拆开，用清晰的状态链路串联四角色协作"，重点放在状态可见性、异常兜底和管理员的配置安全感上。

主要影响：

  1. 四角色视角分离（超管配置、权限管理员维护、员工申请查看、审批人处理），每个角色有其独立的任务路径和状态视图
  2. 管理后台需要在现有全局治理配置中增加新模式开关和范围配置，信息密度较高，需注意配置引导
  3. 员工端的核心体验不在"申请表单多好看"，而在"我缺了什么权限"→"能申请什么"→"申请后什么状态"这条链路
  4. 异常分支多（审批人缺失升级、模式互斥提示、关闭能力时审批中申请的冲突、敏感权限过滤），需要把每条异常的处理说清楚
  5. 审批通过后自动授权是无感操作，需要让员工明确感知到"权限已生效"

建议方案：

  • 管理后台：在现有权限管理模式页增加"自助申请"模式卡片，开启前先检测双管理员模式状态并给出引导
  • 管理后台：可申请范围配置用左侧候选池+右侧已选列表的双栏模式，敏感权限灰显不可选
  • 员工端：在"我的权限"页面增加申请入口，同时在因无权限被拦截的页面直接提供"申请此权限"入口
  • 审批端：复用现有 OA 审批待办列表，权限申请类型的卡片展示申请人、申请权限、申请原因
  • 统一用"审批中/已通过/已拒绝/已撤销"四状态标签贯穿所有角色的列表和详情

不建议方案：

  • 不建议把管理员配置和员工申请放在同一个页面，角色差异太大，混在一起会互相干扰
  • 不建议申请时让员工选数据范围，第一期聚焦角色和功能权限，降低员工认知负担

需要确认：

  1. 员工端入口——"我的权限"页面是否已存在？如不存在，需要新建页面的设计投入
  2. 因无权限被拦截时弹出申请入口——实现上需要前后端配合，确认技术可行性
  3. 审批通过的自动授权——授权结果的通知方式是用企微消息、站内信还是两者都有

1. 交互流程总览

涉及角色：

  • 超级管理员 / 权限管理员：进入管理后台 → 权限管理模式 → 开启自助申请 → 配置白名单和审批规则 → 监控申请统计
  • 员工：进入我的权限 → 查看已有权限 → 发现缺口 → 发起申请 → 跟踪申请状态 → 权限生效后使用
  • 审批人：收到审批待办 → 查看申请详情 → 同意或拒绝 → （可选）填写审批意见

主流程：

  1. 管理员配置自助申请模式（首次配置子流程：模式检测→范围设置→审批设置→确认开启）
  2. 员工查看我的权限列表
  3. 员工发起权限申请（选择权限→填写原因→提交→确认）
  4. 审批人处理申请（待办列表→查看详情→同意/拒绝→提交）
  5. 员工查看申请状态（申请记录列表→详情→状态和结果）
  6. 管理员查看申请统计或关闭能力（可选子流程）

异常流程重点：

  • 管理员开启时检测到双管理员模式互斥 → 提示关闭双管理员模式
  • 审批人缺失 → 逐级升级并通知
  • 管理员关闭能力时存在审批中申请 → 允许走完或一键拒绝
  • 员工申请了敏感权限（前端已过滤，但后端兜底） → 拒绝并说明原因
  • 员工重复申请已有权限 → 提示"你已拥有此权限"
  • 审批流程中员工离职或停用 → 申请自动关闭

2. 主交互流程

节点 2.1：管理员首次开启自助申请模式

用户动作：

管理员进入"管理后台 → 权限 → 权限管理模式"页面，看到当前已有模式的列表。点击"自助申请权限"卡片上的"开启"按钮。

系统反馈：

系统检测当前是否已开启双管理员模式：

  • 正常：进入配置向导第一步——设置可申请范围
  • 互斥冲突：弹窗提示"当前已开启双管理员模式。自助申请模式与双管理员模式互斥，如需开启请先关闭双管理员模式。"，提供"前往关闭双管理员模式"按钮，不直接替管理员操作

需要前置解释的信息：

  • 自助申请模式是什么：允许员工自行查看权限并发起权限申请，审批通过后自动授权
  • 开启前必须完成：①设置可申请范围（白名单）②设置审批规则
  • 与双管理员模式互斥的影响：开启后双管理员模式将不可用，已通过双管理员模式分配的权限不受影响

建议文案：

  • 卡片标题："员工自助申请权限"
  • 卡片描述："允许员工查看自己的权限并主动申请所需权限，审批通过后自动授权"
  • 状态标签（未开启）："未开启"
  • 开启按钮："开启"
  • 互斥提示弹窗标题："无法同时开启两个模式"

下一步：

配置向导 → 设置可申请范围（节点 2.1a）

节点 2.1a：管理员设置可申请范围（白名单配置）

用户动作：

管理员在配置向导中看到双栏布局——左侧是所有可配置的权限列表（按角色和功能权限分Tab），右侧是已加入白名单的权限。管理员从左侧勾选权限，点击"添加"移入右侧白名单。

敏感权限（如超管角色、审计相关权限）在左侧以灰显状态展示，无法勾选，旁边有提示"系统保护权限，不可申请"。

系统反馈：

  • 管理员从左侧添加权限到右侧时，右侧列表实时更新
  • 右侧白名单为空时显示空状态提示"尚未添加任何可申请权限，员工将无法发起申请"

  • 底部按钮："上一步"/"下一步：设置审批"

用户动作：

  • 失败：显示具体失败原因

系统反馈：

  • 直属上级存在且在职 → 正常分配审批任务，发送审批通知
  • 直属上级不存在/已离职 → 系统自动上溯到部门负责人，发送审批通知，并向员工发送提示"你的直属上级暂不可用，申请已自动转交给部门负责人 XXX"
  • 部门负责人也不存在 → 系统自动转交给权限管理员
  • 每次升级都需通知员工和被转交的审批人

建议文案：

  • 员工通知（审批人升级）："你的直属上级暂不可用，申请已自动转交给部门负责人「XXX」处理。"
  • 审批人通知（转交）："由于「XXX」的直属上级不可用，该权限申请已自动转交给你处理。"

节点 3.5：因无权限被拦截时的申请入口

用户动作：

员工在访问某个功能时被系统拦截（无权限），拦截页面除了显示"暂无权限"外，增加"申请此权限"按钮。

系统反馈：

点击"申请此权限"后，直接跳转到申请页面，并自动选中被拦截的权限项（如果该权限在白名单内）。如果该权限不在白名单内或为敏感权限，则显示"该权限暂不支持自助申请，请联系管理员"。

建议文案：

  • 拦截提示："暂无权限访问此功能"
  • 申请按钮（权限在白名单内）："申请此权限"
  • 申请按钮替代文案（权限不在白名单内）："暂无权限，请联系管理员"

4. 异常与阻断流程

异常 X1：双管理员模式互斥

  • 发生时机： 管理员点击"开启自助申请权限"时
  • 触发条件： 当前已开启双管理员模式
  • 判断依据： facts 关键业务规则 —— 治理模式互斥；business 规则与边界 —— 模式互斥约束
  • 反馈形式： 弹窗阻断
  • 系统反馈： "当前已开启双管理员模式。自助申请模式与双管理员模式互斥，如需开启请先关闭双管理员模式。"
  • 用户下一步： 点击"前往关闭双管理员模式"按钮跳转到对应设置页，或点击"取消"回到权限管理模式页

异常 X2：敏感权限被尝试申请（后端兜底）

  • 发生时机： 员工提交申请时
  • 触发条件： 前端白名单已过滤敏感权限，但后端收到包含敏感权限的申请请求（如通过接口直接调用）
  • 判断依据： facts 关键业务规则 —— 敏感权限硬排除
  • 反馈形式： 提交失败，字段级提示
  • 系统反馈： "申请中包含不支持自助申请的权限：XXX。请从申请中移除后重新提交。"
  • 用户下一步： 移除敏感权限后重新提交

异常 X3：员工重复申请已有权限

  • 发生时机： 员工提交申请时
  • 触发条件： 申请的权限中包含了员工当前已经拥有的权限
  • 判断依据： facts 异常与边界 —— 员工申请已有权限
  • 反馈形式： 提交前弹窗提示
  • 系统反馈： "你已拥有以下权限：XXX。是否确认仍然提交申请？（已拥有的权限将从申请中自动移除）"
  • 用户下一步： 确认后已拥有权限自动移除，仅提交确实缺少的权限

异常 X4：审批流程中员工离职或停用

  • 发生时机： 员工提交申请后、审批人处理前
  • 触发条件： 员工状态变为停用或离职
  • 判断依据： facts 异常与边界 —— 员工已离职或停用
  • 反馈形式： 申请状态变更 + 通知审批人
  • 系统反馈： 申请自动关闭，状态变为"已撤销"。审批人收到通知："XXX 已离职/停用，该权限申请已自动关闭。"员工端不展示该申请（或展示为已关闭状态）。
  • 用户下一步： 审批人无需处理，该申请从待办列表移除

异常 X5：管理员关闭能力时存在审批中申请

  • 发生时机： 管理员点击"关闭自助申请权限"时
  • 触发条件： 存在状态为"审批中"的申请
  • 判断依据： facts 关键业务规则 —— 管理员关闭能力后的处理
  • 反馈形式： 弹窗确认
  • 系统反馈： "当前有 X 条正在审批中的申请。关闭后不再接受新申请，审批中的申请将允许正常走完。你也可以选择一键拒绝所有审批中的申请。"
  • 用户下一步： 选择"允许走完"关闭，或选择"一键拒绝"后关闭，或点击"取消"

异常 X6：管理员修改白名单时移除已被申请的权限

  • 发生时机： 管理员从白名单中移除权限时
  • 触发条件： 该权限当前有审批中的申请
  • 判断依据： facts 开放问题 —— 管理员修改白名单时是否影响审批中的申请
  • 反馈形式： 弹窗提示
  • 系统反馈： "以下权限当前有 X 条审批中的申请：XXX。移除后，这些申请将不受影响。新申请将无法选择此权限。确定要移除吗？"
  • 用户下一步： 确认移除或取消

6. 状态与反馈文案

状态 S1：审批中

  • 含义： 申请已提交，等待审批人处理
  • 用户可做： 查看申请详情，如管理员允许撤销则可撤销申请
  • 页面反馈： 黄色标签"审批中"，详情页显示当前审批人信息，列表页展示"提交于 YYYY-MM-DD"

状态 S2：已通过

  • 含义： 审批人已同意申请，权限已自动生效
  • 用户可做： 查看申请详情，回到"我的权限"页面确认新权限已生效
  • 页面反馈： 绿色标签"已通过"，详情页显示"权限已生效"确认信息和审批意见

状态 S3：已拒绝

  • 含义： 审批人已拒绝申请，权限不授予
  • 用户可做： 查看拒绝原因，可选择重新申请
  • 页面反馈： 红色标签"已拒绝"，详情页显示拒绝原因和审批人，提供"重新申请"按钮

状态 S4：已撤销

  • 含义： 员工在审批人处理前主动撤回了申请
  • 用户可做： 查看申请详情，可重新发起新申请
  • 页面反馈： 灰色标签"已撤销"，详情页显示撤销时间

状态 S5：管理模式 - 已开启

  • 含义： 自助申请权限功能已对企业开启，员工可以发起申请
  • 用户可做（管理员）： 调整白名单配置、修改审批规则、关闭能力
  • 页面反馈： 卡片状态标签显示"已开启"（绿色），展示"配置"和"关闭"按钮

状态 S6：管理模式 - 未开启

  • 含义： 自助申请权限功能未对企业开启，员工无法发起申请
  • 用户可做（管理员）： 点击"开启"启动配置向导
  • 页面反馈： 卡片状态标签显示"未开启"（灰色），展示"开启"按钮

7. 待确认问题

  1. 员工端"我的权限"页面是否已存在？ 如果不存在，需要新建页面，影响前端开发工作量。建议由产品确认。
  2. 因无权限被拦截时的申请入口技术可行性？ 需要在拦截逻辑中判断权限是否在白名单内，并动态展示申请按钮。建议由前后端技术负责人确认。
  3. 审批通过后的通知方式？ 企微消息、站内信还是两者都有，影响通知触达率。建议由产品和运营确认。
  4. 管理员关闭时"一键拒绝"是否做？ 我们建议作为可选项提供，但不强制。最终由产品确认。
  5. 申请被拒绝后允许重新申请是否有冷却期？ 我们建议不设冷却期，但可限制重复申请的频率。由产品确认。

附录：设计指南消费说明

本次重点承接的体验问题：

  • 多角色协作的流程清晰性：将四角色（超管、权限管理员、员工、审批人）的任务路径拆成独立的主交互节点，确保每个角色的用户动作、系统反馈和下一步不交叉混淆。参考了流程模式的设计原则。
  • 异常场景的反馈完整性：针对 6 个关键异常（模式互斥、敏感权限拦截、重复申请、审批人缺失升级、关闭能力冲突、员工离职/停用），分别定义了触发条件、反馈形式和用户补救路径。参考了反馈与报错体验设计指南的"触发场景→系统反馈→用户下一步"结构。
  • 状态可见性贯穿全局：定义了 6 个核心状态（审批中/已通过/已拒绝/已撤销/已开启/未开启），统一了标签颜色和文案口径，确保管理员、员工、审批人三端对同一状态的理解一致。

实际使用的设计参考主题：

  • 流程模式：多步骤流程的组织方式——配置向导分步、申请提交流程的状态可见性、审批处理的操作后反馈
  • 反馈与报错：异常阻断的反馈形式选择——弹窗用于互斥和关闭确认的高风险操作、toast 用于提交成功的轻反馈、页面状态用于列表和详情的信息展示

这些原则如何转成页面、流程、反馈方案：

  • 流程模式的"分步不跳跃"原则 → 管理员配置向导采用三步结构（模式检测→范围设置→审批设置），每步有明确的"上一步/下一步"，不跳过前置条件
  • 反馈与报错的"补救路径必须可见"原则 → 每个异常阻断都提供了明确的"用户下一步"，不只是告知错误，而是给出可操作的处理方案（如"前往关闭双管理员模式""重新申请""联系管理员"）
