## 0. 本次关键设计判断

**判断：**

需求成立，属于复杂业务需求，需要按完整业务蓝图处理。核心是权限分配模型从"纯管理员集中分配"变成"员工可自助申请+审批后自动授权"，涉及新增业务对象、新状态机、新权限来源和新模式互斥规则。

**主要影响：**

1. 业务对象：新增"申请单"对象，需要在权限体系中建立申请单与权限、角色、用户、审批单的关系
2. 权限来源：新增"自助申请"来源类型，需要融入现有来源模型并与管理员直接分配区分口径
3. 治理模式：新增"自助申请权限模式"，与已有治理模式互斥，需要设计模式切换规则
4. 审批链路：申请必须走审批，审批通过后自动授权，需要复用现有审批引擎

**建议方案：**

- 将自助申请权限作为现有权限治理体系的一种新模式，与双管理员模式、权限变更审批模式同级互斥
- 申请单复用现有审批中台，不自建审批引擎
- 权限来源枚举新增 `SELF_SERVICE_APPLY`，与 `ACL_DIRECT`、`RBAC_ROLE` 区分
- 敏感排除复用了现有角色边界规则，按用户身份限制可申请范围
- 关闭能力时已授权权限保留，在途申请按管理员选择处理

**不建议方案：**

- 不自建独立的审批系统——复用现有审批中台是更安全且成本更低的选择
- 不把自助申请做成独立于现有权限体系的外部模块——会埋下来源混淆和维护分裂的长期隐患
- 不让员工申请绕过审批直接授权——与业务约束冲突

**需要确认：**

1. 关闭时在途申请的处理方式：批量拒绝、等待当前审批结束、还是由管理员逐单处理
2. 审批中的申请是否支持撤销：影响申请状态机的分支设计
3. 敏感排除的具体规则：哪些角色/权限需按什么身份条件排除

## 1. 一句话结论

可以做，建议作为现有权限治理体系下的新模式实现。核心是在不改变权限底层对象关系的前提下，新增"申请单"对象和"自助申请"来源，复用审批引擎完成授权闭环。关键是处理好模式互斥规则、敏感排除机制和审批异常兜底。

## 2. 需求是否成立

**判断：成立**

解决的问题：中大型企业中员工权限新增、变更、核对的工作量大，管理员集中处理效率低，员工和管理员之间的线下沟通成本高。

受影响的角色：
- 员工：从被动等待变为主动申请，减少沟通成本
- 权限管理员/超管：从集中处理变为配置+审批监督，减少日常分配工作量
- 审批人（组织负责人）：新增审批任务

判断依据：
- 竞品（金蝶）已有相近能力，方向可行
- 复用现有权限体系和审批引擎，技术可行性高
- 有明确的管理员控制机制（范围限制、审批必须、敏感排除），安全风险可控
- 模式互斥设计可以避免与现有治理模式冲突
- 服务人员暂不开放、敏感排除等约束可以控制扩散风险

## 3. 值不值得做

**收益：**
- 业务价值：权限获取从"找人"变为"走流程"，规范化权限申请
- 效率提升：减少员工-管理员线下沟通环节，审批通过即自动授权
- 用户价值：员工可以随时查看自己的权限和申请状态，透明度提升
- 管理价值：管理员从"分配执行者"变为"规则设定者+审批监督者"

**成本：**
- 开发：需要新增申请单模型、申请/审批/授权链路、管理端配置、员工端页面
- 维护：新增权限来源类型需要在后续权限查询和审计中持续维护
- 培训：员工需要学习自助申请的使用方式，尤其是权限概念理解
- 认知负担：新的权限来源可能让权限溯源变复杂

**综合判断：值得做。** 优先面向员工多、权限变更频繁、管理员压力大的企业。初期可作为可选能力，由管理员决定是否开启。后续根据使用情况和客户反馈决定是否默认启用。

## 4. 应该做成什么能力形态

### 路径比较

**路径一：独立功能模块（不推荐）**
- 优点：开发隔离，不影响现有权限体系
- 缺点：可能与现有权限体系产生数据不一致、来源混淆、权限冲突；长期维护成本高

**路径二：扩展现有权限治理模式（推荐）**
- 优点：融入现有权限体系，复用对象模型、来源模型和治理框架；权限来源可统一追溯；审批复用现有引擎
- 缺点：需要与现有治理模式做互斥处理，开启前需做前置检查

**路径三：纯配置化（不适用）**
- 当前权限治理体系的配置化程度不足以支撑自助申请，需要新增申请单模型和审批对接

**推荐：路径二。** 将"自助申请权限模式"作为与"双管理员模式""权限变更审批模式"同级的新治理模式。三者互斥，管理员在权限治理设置中选择其一。

## 5. 推荐业务方案

### 角色与职责

| 角色 | 职责 |
| --- | --- |
| 超级管理员 / 权限管理员 | 开启/关闭自助申请模式；配置可申请范围（角色+功能权限）；设置审批方式（默认组织负责人，可改选）；处理关闭时的在途申请 |
| 员工 | 查看自己已有权限；提交权限申请（选择角色或功能权限+填写原因）；查看申请记录和审批状态 |
| 审批人（默认组织负责人） | 查看申请内容（申请人、原因、申请的权限）；同意或拒绝申请 |

### 主流程闭环

**管理端配置流程：**
1. 管理员进入权限治理设置 → 选择"自助申请权限模式"
2. 系统检查当前是否已开启互斥模式 → 如有，阻断并提示先关闭
3. 管理员配置可申请范围（选择可申请的角色和功能权限，受敏感排除约束）
4. 管理员配置审批方式（默认组织负责人，支持改选其他审批人）
5. 管理员确认开启
6. 系统记录操作日志

**员工端申请流程：**
1. 员工进入"我的权限"页面 → 查看已有权限
2. 员工点击"申请权限" → 进入申请页面
3. 员工选择要申请的角色或功能权限（仅展示可申请范围内且未被敏感排除的选项）
4. 员工填写申请原因 → 提交
5. 系统创建申请单 → 进入审批流程 → 通知审批人
6. 审批人处理 → 同意/拒绝
7. 同意 → 系统自动授权 → 通知员工
8. 拒绝 → 员工权限不变 → 通知员工

**关闭流程：**
1. 管理员进入权限治理设置 → 关闭自助申请模式
2. 系统检查是否存在审批中的申请
3. 如有在途申请 → 提示管理员选择处理方式 [GAP：具体选项待确认]
4. 确认关闭 → 已授权权限保留 → 记录操作日志

### 前置配置

管理员在开启前必须完成：
1. 可申请范围设置（哪些角色、哪些功能权限可被申请）
2. 审批方式设置（审批人来源、是否支持员工改选审批人）
3. 敏感排除规则确认（哪些身份不可申请哪些权限）

### 结果回写与记录沉淀

- 申请记录：每条申请生成申请单，记录申请人、申请内容、原因、提交时间、审批结果、授权结果
- 权限来源标记：通过自助申请获得的权限，来源标记为 `SELF_SERVICE_APPLY`
- 操作日志：开启/关闭操作、申请提交、审批操作、自动授权均记录操作日志
- 数据埋点：记录申请发起量、审批通过率、平均审批耗时、申请取消率

## 6. 必须守住的规则和边界

### 不能放开的限制

1. **模式互斥**：自助申请模式与双管理员模式、权限变更审批模式不能同时开启
2. **服务人员排除**：服务人员不能使用自助申请能力
3. **敏感排除**：被标记为敏感的角色或权限，特定身份用户不可申请
4. **权限隔离**：员工只能查看自己的权限和申请记录

### 必须审批的场景

1. 所有自助申请必须经过审批，不能直接授权
2. 审批人缺失时，申请不能自动通过，必须有兜底处理

### 必须二次确认的操作

1. 管理员关闭自助申请能力时，如有在途申请，需要二次确认处理方式
2. 管理员开启能力前，需要确认已配置可申请范围和审批方式

### 必须前置说明的信息

1. 开启前向管理员说明：模式互斥关系、关闭后已授权权限的处理方式
2. 申请前向员工说明：可申请范围、审批流程、预计审批人、审批通过后权限何时生效

## 7. 主要风险与保护策略

### 风险一：权限安全风险
- 风险：可申请范围设置过宽，员工申请到不合适的权限
- 影响：权限失控、数据泄露
- 缓解：三层保护——①配置端限制可申请范围；②审批端人工审核；③敏感排除机制按身份自动拦截

### 风险二：审批流程断裂
- 风险：审批人不存在、审批链路配置错误导致申请无法流转
- 影响：申请单积压、员工无法获得权限
- 缓解：①开启时校验审批人有效性；②审批超时自动提醒/转派；③管理员可查看和处理异常申请单

### 风险三：模式互斥冲突
- 风险：与现有治理模式同时开启导致权限治理规则冲突
- 影响：权限来源混乱、治理规则失效
- 缓解：开启前强制检查互斥模式；切换模式时要求先关闭当前模式

### 风险四：关闭时在途申请处理不当
- 风险：关闭后审批中的申请悬空
- 影响：申请人和审批人困惑、权限状态不一致
- 缓解：关闭时检测在途申请，强制管理员选择处理方式后再关闭

### 风险五：权限来源混淆
- 风险：员工权限同时来自管理员分配和自助申请，难以区分和追溯
- 影响：权限审计困难、权限回收时遗漏
- 缓解：来源标记 `SELF_SERVICE_APPLY` 与 `ACL_DIRECT` 区分；权限查看页展示来源

## 8. 方案承接要求

后续 experience 阶段必须承接：

### 必须覆盖的角色
- 超级管理员 / 权限管理员（管理端配置和操作）
- 员工（查看权限、申请权限、查看申请记录）
- 审批人（处理审批）

### 必须闭环的主流程
- 管理员配置和开启自助申请模式
- 员工查看权限 → 申请权限 → 提交
- 审批人查看申请 → 同意/拒绝 → 自动授权
- 管理员关闭自助申请模式

### 必须处理的异常
- 模式互斥阻断（开启时检测到互斥模式）
- 敏感排除阻断（员工申请被排除的权限）
- 审批人缺失（审批流程无法继续）
- 关闭时在途申请（管理员关闭时存在审批中的申请）

### 必须解释的状态
- 申请单状态：待审批、已通过、已拒绝、[GAP: 是否支持撤销]
- 自助申请模式状态：未开启、已开启
- 权限来源：管理员分配 vs 自助申请

### 必须保护的风险
- 权限安全：三层校验（配置+审批+敏感排除）
- 审批异常：超时和缺失的兜底机制
- 模式互斥：开启前强制检查和阻断

### 可作为设计建议的内容
- 员工端入口建议放在"我的"或"设置"区域
- 管理端配置建议放在权限治理设置页
- 审批端复用现有审批待办列表

### 报错或阻断场景的设计依据
- 模式互斥阻断：依据为治理状态模型的模式互斥规则
- 敏感排除阻断：依据为角色边界和敏感排除机制
- 审批人缺失：依据为审批管理中的审批人来源配置
- 关闭时在途申请：依据为模式关闭保护规则
