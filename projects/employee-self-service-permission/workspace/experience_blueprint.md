# Experience Blueprint

## 0. 本次关键设计判断

**判断：**

把“员工自助申请权限”设计成一个受控、可解释、可追踪的申请闭环，而不是一个让员工自行加权的快捷入口。

**主要影响：**

1. 员工在发起申请前，必须先理解自己已有权限和可申请范围。
2. 审批通过不等于权限立刻可用，界面要把审批结果和授权结果分开表达。
3. 管理员配置开关与范围时，必须同时理解对员工端入口和在途申请的影响。

**建议方案：**

- 员工侧采用“先看已有权限，再发起申请”的双入口结构。
- 审批侧采用“申请内容 + 申请原因 + 风险提示 + 处理动作”同屏决策结构。
- 管理侧采用“模式开关 + 可申请范围 + 审批规则 + 关闭影响提醒”的配置结构。

**不建议方案：**

- 不建议把申请入口直接放成一个无前置解释的通用按钮。
- 不建议把“审批通过”和“已授权”合并成一个状态，避免误导员工。

**需要确认：**

1. 员工申请对象到底支持角色、功能权限，还是两者都支持？
2. 数据范围是否需要在申请时由员工主动选择？
3. 关闭能力后，在途申请是继续处理还是统一终止？

## 1. 交互流程总览

```text
**涉及角色：**

- 员工：查看我的权限 -> 判断缺口 -> 发起权限申请 -> 查看审批与授权结果
- 审批人：接收申请 -> 查看申请原因与权限内容 -> 同意或拒绝
- 管理员：开启模式 -> 配置可申请范围和审批规则 -> 关闭模式并处理存量影响

**主流程：**

1. 管理员开启员工自助申请模式并配置申请范围与审批规则
2. 员工进入“我的权限”查看已有权限和当前可申请项
3. 员工提交权限申请并填写申请原因
4. 审批人处理申请
5. 系统在审批通过后自动授权并把结果反馈给员工

**异常流程重点：**

- 当前没有开放可申请权限
- 审批链异常或审批人缺失
- 自动授权失败
- 管理员关闭模式时仍存在在途申请
```

## 2. 主交互流程

```text
**节点 1：员工进入“我的权限”**

**用户动作：**

员工进入个人权限页，查看自己当前已有的角色、功能权限和数据范围说明。

**系统反馈：**

页面先展示“我当前已拥有的权限”，再展示“当前可申请的权限”区域；如果该企业未开启该能力，则不展示申请入口。

**需要前置解释的信息：**

员工需要知道：已有权限来自既有授权结果，可申请权限来自管理员开放范围，不是所有权限都能申请。

**建议文案：**

标题：我的权限
说明：查看你当前已拥有的权限，并在需要时申请开放范围内的额外权限。

**下一步：**

员工决定是否进入申请流程。
```

```text
**节点 2：员工发起权限申请**

**用户动作：**

员工从“可申请权限”中选择目标权限，填写申请原因并提交。

**系统反馈：**

系统在提交前展示申请对象、申请原因、预计审批流程和提交后不可直接生效的提示；提交后生成申请单。

**需要前置解释的信息：**

员工需要知道：提交申请后还要审批，通过后系统才会自动授权；如果当前权限不在开放范围内，则无法提交。

**建议文案：**

标题：申请权限
说明：请说明为什么需要该权限，提交后将进入审批流程，审批通过后系统自动开通权限。

**下一步：**

员工进入申请记录，等待审批结果。
```

```text
**节点 3：审批人处理申请**

**用户动作：**

审批人查看申请人、申请权限、申请原因、适用范围和风险提示，选择同意或拒绝。

**系统反馈：**

同意后申请进入“审批通过待授权”；拒绝后进入“已拒绝”，并把结果回传给员工。

**需要前置解释的信息：**

审批人需要知道：通过只是允许系统执行授权，最终是否生效还取决于后续授权结果。

**建议文案：**

说明：审批通过后系统将自动授予对应权限，请确认该申请符合岗位职责和最小权限原则。

**下一步：**

系统执行自动授权，并继续回写申请状态。
```

```text
**节点 4：系统自动授权并反馈结果**

**用户动作：**

员工查看申请记录；管理员或审批人关注授权是否顺利完成。

**系统反馈：**

如果授权成功，申请状态变为“已授权”；如果授权失败，状态变为“授权失败”，并给出补救提示。

**需要前置解释的信息：**

用户需要区分“审批结果”和“权限是否已真正可用”。

**建议文案：**

成功提示：权限已开通，你现在可以使用对应能力。
失败提示：审批已通过，但系统授权失败，请联系管理员处理。

**下一步：**

员工返回我的权限重新确认是否已生效；管理员处理失败补救。
```

## 3. 次交互流程

- 管理员配置流程：进入权限治理设置页，开启或关闭员工自助申请模式，选择可申请范围，配置审批规则，保存时看到对员工入口和在途申请的影响提醒。
- 员工查看申请记录：员工进入申请记录页，按状态查看待审批、已拒绝、已授权和授权失败的申请。
- 员工重新发起申请：对于已拒绝或授权失败的申请，员工可以查看原因后重新发起，避免直接复制旧申请造成误导。[GAP]
- 管理员关闭模式：管理员关闭能力时，系统先提醒存在在途申请，再要求明确处理口径后才允许确认关闭。[GAP]

## 4. 异常与阻断流程

```text
异常 X1：当前没有开放可申请权限

**发生时机：** 员工进入“我的权限”并尝试找申请入口时
**触发条件：** 管理员未开放申请范围，或员工当前没有匹配可申请项
**判断依据：** facts 中“员工只能申请管理员开放范围内的权限”
**反馈形式：** 页面空状态
**系统反馈：** 当前没有开放可申请的权限。如你仍有工作需要，请联系管理员确认范围配置。
**用户下一步：** 返回查看已有权限，或联系管理员确认是否应开放申请范围
```

```text
异常 X2：申请的权限不在开放范围内

**发生时机：** 员工选择权限并提交申请时
**触发条件：** 申请项不在管理员配置的可申请范围内
**判断依据：** business_note 中“员工不能申请管理员未开放的权限”
**反馈形式：** 字段级提示 + 表单顶部阻断提示
**系统反馈：** 该权限当前不支持自助申请，请联系管理员确认申请范围。
**用户下一步：** 改选可申请项，或退出并联系管理员
```

```text
异常 X3：审批链异常

**发生时机：** 申请提交后准备进入审批流程时
**触发条件：** 审批人不存在、审批链配置缺失或审批服务异常
**判断依据：** facts 中“审批链配置错误会导致流程阻塞”
**反馈形式：** 提交后状态提示 + 管理侧告警
**系统反馈：** 申请已记录，但当前审批流程异常，系统暂时无法继续处理，请联系管理员检查审批配置。
**用户下一步：** 员工查看申请记录等待处理；管理员修复审批配置
```

```text
异常 X4：自动授权失败

**发生时机：** 审批通过后系统执行授权时
**触发条件：** 授权服务失败、权限对象失效或数据同步异常
**判断依据：** facts 中“审批通过后需要自动授权，失败时不能直接当作成功”
**反馈形式：** 申请记录状态提示 + toast / 消息提醒
**系统反馈：** 审批已通过，但系统授权失败，权限暂未生效，请联系管理员处理。
**用户下一步：** 员工等待补救；管理员进入处理链路修复授权问题
```

## 5. 页面 / 弹窗 / 抽屉设计

```text
**页面：我的权限**

**页面目标：** 让员工理解自己当前有哪些权限，以及还能申请什么
**页面结构：** 已有权限区、可申请权限区、申请记录入口、说明区
**具体文案：** 标题“我的权限”；说明“查看你当前已拥有的权限，并申请开放范围内的额外权限”
**按钮：** 主按钮“申请权限”；次按钮“查看申请记录”
**成功反馈：** 无需单独成功提示，重点展示已更新的权限状态
**失败反馈：** 无开放范围时展示空状态说明
```

```text
**页面：申请权限**

**页面目标：** 让员工完整理解申请对象、填写申请原因并提交
**页面结构：** 申请权限选择区、申请原因区、审批说明区、提交操作区
**具体文案：** 标题“申请权限”；说明“提交后将进入审批流程，审批通过后系统自动开通权限”
**按钮：** 主按钮“提交申请”；次按钮“取消”
**成功反馈：** “申请已提交，可在申请记录中查看审批进度”
**失败反馈：** “当前无法提交申请，请检查权限范围或稍后重试”
```

```text
**页面：申请记录**

**页面目标：** 让员工持续理解申请进度和结果
**页面结构：** 状态筛选、申请列表、结果说明、失败补救提示
**具体文案：** 标题“申请记录”；说明“查看你的权限申请进度、审批结果和授权结果”
**按钮：** 主按钮“重新申请”；次按钮“查看我的权限”
**成功反馈：** “权限已开通，你现在可以使用对应能力”
**失败反馈：** “审批已通过，但授权失败，权限暂未生效”
```

```text
**页面：自助申请配置**

**页面目标：** 让管理员安全开启、调整或关闭员工自助申请模式
**页面结构：** 模式开关区、可申请范围区、审批规则区、关闭影响提醒区
**具体文案：** 标题“员工自助申请权限”；说明“配置员工可申请的权限范围和对应审批规则”
**按钮：** 主按钮“保存配置”；危险按钮“关闭能力”
**成功反馈：** “配置已更新，将影响后续新发起的申请”
**失败反馈：** “当前存在需要确认的在途申请，请先处理后再关闭能力”
```

## 6. 状态与反馈文案

- 状态：待审批
  含义：员工已提交申请，正在等待审批人处理。
  用户可做：查看申请详情与当前进度。
  页面反馈：你的申请已提交，正在等待审批。

- 状态：审批通过待授权
  含义：审批人已经同意，但系统还未完成授权。
  用户可做：等待系统完成开通，不建议重复提交。
  页面反馈：审批已通过，系统正在开通权限，请稍后查看结果。

- 状态：已授权
  含义：审批通过且系统已完成授权，权限已经生效。
  用户可做：返回对应业务入口开始使用。
  页面反馈：权限已开通，你现在可以使用对应能力。

- 状态：已拒绝
  含义：审批人未同意当前申请。
  用户可做：查看拒绝原因，并在必要时重新申请。
  页面反馈：申请未通过，请根据审批意见调整后再提交。

- 状态：授权失败
  含义：审批通过，但系统开通权限时失败。
  用户可做：等待管理员补救或联系管理员确认处理结果。
  页面反馈：审批已通过，但系统授权失败，权限暂未生效。

## 7. 待确认问题

- 申请表单是否需要按角色申请、功能权限申请、数据范围申请拆成不同结构？
- 敏感权限的排除规则是统一配置还是随审批规则配置？
- 申请记录里是否需要展示更细的权限来源、审批意见和补救进度？
- 员工是否支持撤销申请、补充附件、重新提交时复用上次原因？
- 管理员关闭能力时，在途申请采用继续处理、统一终止，还是分状态处理？

## 附录：依据与追踪

- 事实依据一：需求输入已经明确员工、审批人、管理员三类角色，以及查看权限、申请权限、审批处理、关闭能力四段核心场景。
- 事实依据二：业务约束已经明确申请必须审批、审批通过后自动授权、员工不能看到他人权限、管理员必须控制可申请范围。
- 业务承接一：因此体验方案必须把“可申请范围”和“审批后才生效”作为前置解释，而不是让员工直接理解为自助开权。
- 业务承接二：因此状态设计必须拆开“待审批”“审批通过待授权”“已授权”“已拒绝”“授权失败”，避免审批结果和授权结果混淆。
- 未决追踪：角色 / 功能权限 / 数据范围的申请粒度、审批流兜底方式、关闭能力后的在途申请处理，仍需后续明确。
