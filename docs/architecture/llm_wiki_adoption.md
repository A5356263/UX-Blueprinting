# LLM Wiki 落地方案

## 目标

在不改动当前主链路的前提下，为本仓库补一层可持续维护的知识编译层。

当前主链路仍然保持：

1. 原始需求输入
2. 需求事实提炼
3. 业务蓝图构建
4. 体验蓝图构建
5. 检查与归档

LLM Wiki 的作用不是替代 `facts.md`、`business_blueprint.md`、`experience_blueprint.md`，而是作为这些产物的长期上游知识底座。

## 为什么适合当前仓库

- 当前项目已经具备大量稳定资料，且会被多任务反复消费
- 当前仓库已有 `knowledge/`、`templates/`、`checks/`、`scripts/` 的工程骨架
- 当前 `assemble_context.py` 已具备上下文装配能力，但主要复制引用资料，尚未引入“编译后的领域 Wiki”
- 权限、页面承载、治理模式、路由关系等主题天然适合沉淀为长期知识页

## 在当前仓库中的定位

建议将仓库理解为四层：

### L1 原始资料层

- `tasks/active/<task-id>/inputs/`
- 外部截图、会议纪要、需求原文、页面描述、原始知识材料

这一层是事实来源，不直接承担高质量回答或蓝图推导。

### L2 Wiki 编译层

- `knowledge/wiki/`

这一层用于存放经 LLM 持续整理后的稳定知识页，是长期资产。

### L2.5 任务上下文层

- `tasks/active/<task-id>/artifacts/context_bundle/`

这一层是按任务挑选后的最小知识子集，不是知识真源，只是执行快照。

### L3 输出层

- `tasks/active/<task-id>/workspace/`
- `artifacts/<task-id>/final/`

这一层面向交付，继续产出 `facts.md`、`business_blueprint.md`、`experience_blueprint.md` 等结果文件。

## 目标目录结构

建议新增并长期维护以下结构：

```text
knowledge/
  business/
  guidelines/
  wiki/
    README.md
    entities/
    concepts/
    topics/
    relations/
    indices/
```

各目录建议承担如下职责：

- `entities/`：实体页。承载角色、应用、页面、组织对象、审批对象等相对稳定对象
- `concepts/`：概念页。承载功能权限、数据权限、应用可见性、协作可见性等概念定义
- `topics/`：专题页。承载页面承载语义、治理模式对比、路由图、任务场景等综合性主题
- `relations/`：关系页。承载实体之间的映射、依赖、上下游、边界对照
- `indices/`：索引页。承载领域入口、知识导航、主题地图

## 与现有 knowledge 的关系

当前 `knowledge/business/` 与 `knowledge/guidelines/` 不需要废弃。

建议采用以下分工：

- `knowledge/business/`：保留当前稳定业务知识包，适合任务直接引用
- `knowledge/guidelines/`：保留设计原则与通用指南
- `knowledge/wiki/`：补充跨材料编译后的长期知识页，承接演化、合并、冲突标注、索引链接

也就是说，Wiki 层是对现有知识包的增强，而不是替换。

## 推荐首批沉淀对象

对于当前仓库，建议优先沉淀以下类型：

1. 概念页
- 功能权限
- 数据权限
- 应用可见性
- 管理授权
- 协作可见性
- 查询与解释职责

2. 实体页
- 用户授权
- 角色管理
- 权限管理模式
- 应用管理
- 应用设置页

3. 专题页
- 页面承载语义
- 任务场景到页面路径映射
- 配置链路与解释链路
- 全局治理模式对比

4. 关系页
- 应用可见性 vs 功能权限
- 协作可见性 vs 管理授权
- 查询页 vs 配置页职责边界

## 推荐演进方式

### Phase 0

只建目录、规格和模板，不改现有主链路。

### Phase 1

手工沉淀少量高价值 Wiki 页面，并在新任务中显式引用这些页面。

### Phase 2

把任务输入先整理为“候选结论 + 证据片段”，再增量更新 `knowledge/wiki/` 页面。

### Phase 3

升级上下文装配逻辑，让任务不再直接复制整包资料，而是按任务主题优先挑选 Wiki 页面和其关联页。

## 当前建议边界

当前阶段不建议做：

- 重型知识图数据库
- 自动全库重编译
- 复杂多 Agent 协同写库
- 在线 Web Wiki 工作台
- 直接用 Wiki 替代正式蓝图交付

## 最小落地原则

- 主链路不变
- 新增 Wiki 层只做增强
- 先做少量高复用页
- 先做手工编译，再考虑脚本化
- 所有 Wiki 页面保留来源、缺口、冲突状态

## 结果预期

落地后，仓库会从“任务驱动的资料装配仓”升级为“带长期记忆的知识编译仓”。

这样可以获得三类收益：

- 降低每次任务都要重新阅读长资料的成本
- 提高跨任务的一致性与边界稳定性
- 让复杂领域知识先被编译，再被蓝图和体验方案消费
