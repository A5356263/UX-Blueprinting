# 信息消费不足与自然语言自检修复优化方案

> 适用项目：UX-Blueprinting  
> 适用分支语境：`origin/研发版模式`  
> 目标问题：当前检查结果提示 business / experience 消费不足，但其中大量问题来自旧 ID / trace 检查口径与当前“人话版产物规范”不一致。  
> 基本原则：需求分析型项目优先保持自然语言质量，不为了机器精准消费牺牲灵活性，不回到 F-xx / J-xx / P-xx / TR-xx 编号体系。

---

## 1. 背景

当前项目已经明确从早期的机器编号、trace matrix、强结构消费，转向更适合需求分析型工作的自然语言产物。

当前模板已强调：

- `business_blueprint.md`：用业务分析师的自然语言做判断，不填表，不复制 facts 碎片，不用 ID 编号。
- `experience_blueprint.md`：用 UX 设计师语言写清谁做什么、系统怎么回应、页面上写什么文案、失败时怎么处理。

这说明项目的基调不是构建机器可读知识图谱，而是生成产品、设计、开发团队能直接评审的人话方案。

---

## 2. 当前问题

### 2.1 现象

在 `projects/employee-self-permission` 本次测试中，最终检查出现多项 warning，例如：

```text
facts_covered_by_business: 0
facts_covered_by_experience: 0
business_judgments_consumed_by_experience: 0
business_blueprint.md 未形成显式业务判断
experience_blueprint.md 页面级消费不足
```

但从人工阅读看：

- `business_blueprint.md` 已经写了需求是否成立、值不值得做、推荐业务方案、规则边界、风险保护、方案承接要求。
- `experience_blueprint.md` 也写了超管、员工、审批人三类角色，覆盖主流程、异常流程、页面/弹窗/抽屉、状态反馈。

因此不能简单认为“产物完全没有消费”。

### 2.2 根因

根因是两类问题混在一起：

#### 问题 A：旧机器检查口径残留

当前 validate 中仍保留旧的 ID / trace 识别逻辑，例如：

```text
FACT_ID_PATTERN
JUDGMENT_ID_PATTERN
PAGE_ID_PATTERN
FLOW_ID_PATTERN
TRACE_ID_PATTERN
```

这类逻辑依赖：

```text
F-xx
J-xx
P-xx
TF-xx
TR-xx
```

但当前正式模板已经要求不使用编号体系。

所以自然语言产物越符合新模板，旧检查指标越可能显示为 0。

#### 问题 B：真实自然语言质量不足仍可能存在

虽然旧指标误报明显，但这不代表所有 warning 都应忽略。

真实问题应该用自然语言维度判断，例如：

- business 强调审批人体验是重点，experience 是否真的把审批详情页写充分？
- business 强调敏感权限绕过风险，experience 是否在配置、申请、审批中体现保护？
- business 强调模式互斥认知盲区，experience 是否在提示文案中解释原因？
- business 强调申请功能权限默认全部数据权限，experience 是否在员工提交前明确提示？
- business 强调状态需要解释，experience 是否覆盖审批中、已通过、已拒绝、已撤销、权限生效等状态？

这些问题应该被检查和修复，但不应该通过编号 trace 解决。

---

## 3. 优化目标

本次优化的目标是：

1. 移除旧 ID / trace 指标，不再用 F/J/P/TR 编号判断消费是否充分。
2. 改为自然语言维度检查，判断 business 的关键要求是否被 experience 转译成流程、页面、状态、异常和文案。
3. 检查结果继续进入现有 repair_loop，由 repair_loop 组织局部修复。
4. 保留人读版 `check_report.md` 和 `repair_summary.md`，但机器真源仍是 JSON 状态文件。
5. 不新增机器承接表，不要求产物补编号，不要求 experience 输出 trace matrix。

---

## 4. 旧 ID / trace 指标处理方案

### 4.1 结论：移除，不是降级

不建议继续保留以下指标作为 warning 判断依据：

```text
facts_covered_by_business
facts_covered_by_experience
business_judgments_consumed_by_experience
orphan_fact_count
orphan_judgment_count
critical_judgment_traced_count
```

如果这些指标依赖 F-xx / J-xx / P-xx / TR-xx，则应从正式 warning 体系中移除。

### 4.2 允许保留的内容

可以保留结构完整性检查，例如：

- 必需章节是否存在
- 是否出现明显占位符
- 是否越过阶段边界
- 是否出现禁止内容
- 是否存在元指令
- 是否缺失用户可见文案
- 是否缺少状态或异常处理

这些检查不依赖编号，不会倒逼产物机器化。

### 4.3 不允许的倒退

不允许为了让 coverage 数字好看而要求：

```text
business_blueprint.md 增加 J-xx
facts.md 增加 F-xx
experience_blueprint.md 增加 P-xx
experience_blueprint.md 增加 trace mapping 表
```

这会破坏当前项目“人话版需求分析”的基调。

---

## 5. 自然语言维度检查方案

### 5.1 检查对象

自然语言检查不检查编号，而检查业务含义是否被体验方案吸收。

重点对象包括：

```text
business_blueprint.md
experience_blueprint.md
specs/10_experience_blueprint_contract.md
knowledge_usage_report.json
```

### 5.2 检查维度

建议至少检查以下维度：

#### 角色覆盖

检查 business 中要求覆盖的角色，experience 是否都给出清晰路径。

示例：

```text
business 要求覆盖超管、员工、审批人；
experience 应分别写清三类角色的主任务路径。
```

#### 主流程闭环

检查 business 中定义的业务闭环，experience 是否转译为可操作流程。

示例：

```text
超管配置 → 员工申请 → 系统校验 → 审批人审批 → 自动授权 / 拒绝 → 员工收到结果
```

#### 异常与阻断

检查 business 中提到的异常、阻断、失败场景，experience 是否给出触发条件、系统反馈、用户下一步。

示例：

```text
互斥模式冲突
关闭模式时存在在途流程
资金用户校验失败
子管理员模式拦截
实名认证失败
```

#### 状态与反馈

检查 business 中提到的状态，experience 是否解释状态含义和用户可做动作。

示例：

```text
未启用
已启用
审批中
已通过
已拒绝
已撤销
权限生效中
```

#### 风险保护

检查 business 中的关键风险，experience 是否转译成用户可见保护策略。

示例：

```text
审批人负担过重
敏感权限绕过
模式互斥认知盲区
员工误解数据权限范围
```

#### 设计指南消费

检查 experience 是否根据场景实际消费了设计指南，并在 `knowledge_usage_report.json` 中留下记录。

示例：

```text
异常阻断场景 → 应消费异常反馈或状态反馈相关指南
申请权限抽屉 → 应消费承载容器、表单文案相关指南
审批详情页 → 应消费信息架构、认知负担、状态反馈相关指南
```

### 5.3 检查输出方式

自然语言检查应输出人能看懂的问题，而不是机器指标。

不推荐：

```text
business_judgments_consumed_by_experience = 0
```

推荐：

```text
business_blueprint.md 中强调“审批人侧体验是重点”，但 experience_blueprint.md 的审批详情页只列出申请人、申请时间、申请原因，缺少“当前已有权限 / 申请后新增权限 / 风险提示 / 审批判断辅助”。建议局部补强审批详情页。
```

## 6. 与 repair_loop 的关系

### 6.1 结论

自然语言检查不需要新建一套大机制，应成为 validate / gate 的新检查口径，然后继续复用现有 repair_loop。

合理链路是：

```text
生成 experience_blueprint.md
        ↓
运行自然语言版 experience validate
        ↓
发现问题
        ↓
进入 repair_loop
        ↓
生成 issue_index.json / remediation_plan.json / retry_scope.json / repair_summary.md
        ↓
局部修复对应段落
        ↓
重跑 gate-experience / validate
        ↓
问题关闭
```

### 6.2 repair_loop 负责什么

repair_loop 负责：

- 收集自然语言检查发现的问题；
- 把问题转成标准 issue；
- 判断是局部补修还是回退上游；
- 生成修复计划；
- 给出重跑范围；
- 重跑后关闭问题。

### 6.3 repair_loop 不负责什么

repair_loop 不负责：

- 自动重写整篇 experience；
- 替代 facts / business / experience 主生成；
- 重新决定业务立场；
- 增加编号 trace；
- 把人话产物改回机器产物。

### 6.4 修复方式

自然语言消费不足进入 repair_loop 后，默认修复方式应优先是：

```text
patch_current_section
```

也就是只修局部段落。

示例：

```text
问题：审批人侧体验承接不足。
目标文件：experience_blueprint.md。
修复范围：审批人处理审批流程、审批详情页。
修复目标：补充当前已有权限、申请后新增权限、风险提示、审批判断辅助文案。
禁止动作：不要重写整篇，不要新增编号，不要新增 trace 表。
```

## 7. 人读版本与机器真源分工

### 7.1 现有分工应保留

检查链路应继续保留：

```text
check_status.json
→ 机器正式判断依据

check_report.md
→ check_status.json 的人读说明版
```

repair_loop 应继续保留：

```text
issue_index.json
remediation_plan.json
retry_scope.json
→ 机器正式依据

repair_summary.md
→ 这些 repair JSON 的人读说明版
```

不需要新增：

```text
check_report.json
repair_summary.json
```

### 7.2 Markdown 不参与主链路判断

`check_report.md` 和 `repair_summary.md` 可以被人阅读，也可以作为补充证据来源，但不能替代 JSON 成为正式状态真源。

主链路判断仍以以下文件为准：

```text
workspace/check_status.json
runtime/gates/*_gate_status.json
runtime/remediation/issue_index.json
runtime/remediation/remediation_plan.json
runtime/remediation/retry_scope.json
```

### 7.3 人读文档顶部必须声明来源

`check_report.md` 顶部建议固定为：

```md
# Check Report｜人读说明版

> 本文件是 `projects/<project-id>/workspace/check_status.json` 的人读说明版。
> 它只用于帮助理解检查结果，不作为 gate / validate / repair 的机器判断依据。
> 机器判断请以 `check_status.json` 为准。
```

`repair_summary.md` 顶部建议固定为：

```md
# Repair Summary｜人读说明版

> 本文件是以下机器状态文件的人读说明版：
>
> - `projects/<project-id>/runtime/remediation/issue_index.json`
> - `projects/<project-id>/runtime/remediation/remediation_plan.json`
> - `projects/<project-id>/runtime/remediation/retry_scope.json`
>
> 它只用于帮助理解修复任务，不作为 repair loop 的机器判断依据。
> 机器判断请以上述 JSON 文件为准。
```

## 8. 具体改造点

### 8.1 `packages/validate/core.py`

移除或停用 ID / trace 相关 pattern 对正式 warning 的影响：

```text
FACT_ID_PATTERN
JUDGMENT_ID_PATTERN
PAGE_ID_PATTERN
FLOW_ID_PATTERN
TRACE_ID_PATTERN
```

尤其要移除基于这些 pattern 计算的正式消费指标。

### 8.2 `specs/06_check_contract.md`

将检查范围从：

```text
事实与蓝图的覆盖关系
```

调整为更贴合当前项目的表述：

```text
自然语言承接质量：检查 business 中的关键角色、流程、异常、状态、风险和承接要求，是否被 experience 转译为可评审的流程、页面、状态、异常和文案。
```

同时明确：

```text
不得要求产物使用 F-xx / J-xx / P-xx / TR-xx 编号作为合格条件。
```

### 8.3 `specs/10_experience_blueprint_contract.md`

强化“承接 business，不重做 business”的检查口径：

```text
体验阶段不是用编号追踪 business，而是要把 business 中的角色、流程、异常、状态、风险和承接要求，转译为用户可感知的流程、页面、系统反馈和文案。
```

### 8.4 `repair_loop`

保留现有机制，但 issue 分类建议新增或替换为更自然语言的分类：

```text
experience_business_consumption_gap
experience_guideline_consumption_gap
experience_copy_not_user_visible
experience_state_feedback_gap
experience_exception_handling_gap
experience_role_path_gap
```

这些分类比 `trace_missing` 更符合当前项目基调。

## 9. 验收标准

### 9.1 不再误报旧指标

对于符合当前模板、无编号的 `business_blueprint.md` / `experience_blueprint.md`，不得因为缺少 F/J/P/TR 编号而产生 warning。

不应再出现：

```text
business_judgments_consumed_by_experience: 0
facts_covered_by_experience: 0
未发现页面 ID
缺少 J-xx / P-xx / TR-xx
```

### 9.2 能发现真实自然语言问题

如果 business 明确提出某个关键要求，而 experience 没有自然语言承接，应产生可读 warning。

示例：

```text
business_blueprint.md 中强调“关闭模式时存在在途流程必须阻断”，但 experience_blueprint.md 没有说明阻断发生时机、触发条件、提示文案和用户下一步。
```

### 9.3 修复建议必须局部可执行

不合格：

```text
优化一下体验蓝图。
```

合格：

```text
补强 experience_blueprint.md 中“关闭模式 - 在途流程校验”节点，补充关闭失败弹窗的标题、内容、按钮、用户下一步，不要重写其他章节。
```

### 9.4 人读文档不污染主链路

`check_report.md` 和 `repair_summary.md` 必须在顶部说明自己对应的机器文件，并声明不作为机器判断依据。

---

## 10. 推荐实施顺序

1. 从 `validate/core.py` 移除旧 ID / trace 相关 warning 逻辑。
2. 更新 `specs/06_check_contract.md`，明确自然语言检查口径。
3. 更新 `specs/10_experience_blueprint_contract.md`，强化自然语言承接要求。
4. 调整 check_report 输出模板，使 warning 从“指标为 0”改为“具体自然语言问题”。
5. 调整 repair_loop issue 分类，减少 `trace_missing`，增加自然语言体验质量分类。
6. 用 `projects/employee-self-permission` 重跑：
   - gate-business
   - gate-experience
   - validate
   - repair-plan
7. 验证：
   - 不再因缺少编号误报；
   - 真实缺失能被自然语言指出；
   - repair_summary 能定位局部修复范围；
   - check_report / repair_summary 顶部有机器文件对应关系说明。

---

## 11. 最终结论

信息消费不足问题不能通过恢复编号、trace 表、承接矩阵来解决。

正确方向是：

```text
移除旧 ID / trace 检查；
改为自然语言质量检查；
发现问题后复用 repair_loop 做局部修复；
check_report.md 和 repair_summary.md 做人读说明；
JSON 状态文件继续作为机器真源；
正式产物继续保持人话、灵活、可评审。
```

这符合 UX-Blueprinting 当前“需求分析型项目”的基本基调：让机器辅助发现问题和组织修复，但不让产物为了机器而牺牲表达质量。
