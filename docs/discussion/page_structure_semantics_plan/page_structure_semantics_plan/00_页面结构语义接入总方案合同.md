# 页面结构语义接入总方案合同

## 1. 文档目的

本合同用于定义 UX-Blueprinting 当前项目中“页面结构语义”的正式接入方案。

这里的页面结构语义，不是新增一个重量级页面结构系统，也不是高保真视觉稿，不是前端布局方案，更不是组件树。它只承担一个目标：

**让后续 AI 在分析真实需求文档时，能够基于知识库判断新增或优化的信息、功能、解释、风险提示、辅助模块，是否会引起页面结构层面的变化，并把这种变化正式表达在 `experience_blueprint.md` 中。**

预览层只是后续派生展示，不是本次接入的主驱动力。

## 2. 当前项目现状基线

### 2.1 主链路现状

当前执行中枢已经明确三阶段主链路为：

`assemble -> generate-facts -> generate-business -> generate-experience -> gate-* -> validate -> coverage -> archive`

archive 成功后才自动执行 preview。

因此，本次接入必须保持：

- 不新增第四个正式业务阶段
- 不改变 `facts -> business -> experience` 的顺序
- 不把 preview 变成主链路正式产物

### 2.2 体验蓝图合同现状

当前 `specs/10_experience_blueprint_contract.md` 已经要求体验蓝图输出：

- `关键页面蓝图`
- `区块布局示意`
- `内容与信息优先级合同`
- `状态与反馈矩阵`
- `文案合同`
- `体验追踪映射`

并明确允许使用：

- 表格
- 文本流程图
- 文本区块图
- 页面区块示意
- ASCII / text diagram

说明项目现在并不排斥页面区块表达，缺的是“如何把知识库里的结构语义稳定带入推导”。

### 2.3 Wiki 子系统现状

当前 Wiki 子系统规范已经明确：

- 主项目默认消费 `knowledge/wiki/`
- 主项目不应默认直接消费 `knowledge/raw/`
- 当 Wiki 不足时，应触发 Wiki 子系统维护，而不是主链路自行回查 Raw

因此，本次优化不能把“RAW 里有结构语义”当作主链路可直接消费的前提。

### 2.4 Context Assemble 现状

当前 `packages/context_assemble/core.py` 会把 task card 解析后的 `knowledge_refs / wiki_refs / template_refs / check_refs` 复制进 `context_bundle`，并同时写出：

- `context_manifest.json`
- `knowledge_usage_report.json`

其中 `knowledge_usage_report.json` 中显式写死：

- `mainline_knowledge_policy = wiki_pages_only`

所以本次必须让 Wiki 页本身能够保留足够的页面结构语义，不能指望主链路自动 fallback 到 RAW。

### 2.5 Validate / Coverage 现状

当前 `packages/validate/core.py` 已经会检查体验蓝图是否包含：

- `关键页面蓝图`
- `区块布局示意`
- `内容与信息优先级合同`
- `体验追踪映射`

并会把 `区块布局示意` 中的文本图计入 `region_map_count`。

但它当前还不会检查：

- 页面结构语义是否真正参与了新增 / 优化需求推导
- 页面结构变化是否被正确表达成结构变化，而非纯文本新增功能说明
- `15_page_carrier_semantics.md` 或其 Wiki 编译结果是否被显式消费

### 2.6 Preview 现状

当前预览层已经是正式 capability，且有独立合同 `specs/14_experience_preview_contract.md`。

但现有实现仍然存在两个明显局限：

1. `build_preview_model.py` 只会把区块图拆成线性的 `sketch_blocks[]`
2. `render_html.py` 只会把 `sketch_blocks[]` 渲染成顺序排列的 block，不会真正还原 left / right / main / side / footer 关系

因此 preview 必须同步优化，但它是后置派生消费层，不是主驱动层。

## 3. 本次优化的正式目标

本次优化完成后，项目必须具备以下能力：

### 3.1 面向知识库的能力

页面结构语义可在 RAW 中补充，并由 Wiki 子系统自动编译到正式 Wiki 页；正式 Wiki 页必须尽可能保留：

- 页面主区块
- 区块相对关系
- 首屏视觉中心
- 主次层级
- 常见布局关系（上下 / 左右 / 主从 / footer）

### 3.2 面向需求推导的能力

当真实需求文档进入主链路后，AI 在生成 `experience_blueprint.md` 时，必须能回答：

- 该新增能力是否改变现有页面结构语义
- 该优化是否只是文案 / 规则变化，还是会引起区块变化
- 新模块应进入主区、侧区、步骤头、说明区还是底部动作区
- 某信息是新增独立区块，还是并入既有区块
- 某变化是结构变化，还是不涉及结构变化

### 3.3 面向正式蓝图输出的能力

`experience_blueprint.md` 必须在以下场景显式表达结构变化：

- 新增区块
- 区块重排
- 主次关系调整
- 左右关系调整
- 说明区前置 / 后置
- 风险提示从隐藏改为显式暴露
- 结构保持不变，仅内容 / 文案 / 规则变化

### 3.4 面向预览层的能力

预览层要把正式蓝图里已有的结构关系更真实地还原出来，而不是把页面草图机械地从上到下堆叠。

## 4. 不做什么

本次优化明确不做：

- 不新增主链路正式阶段
- 不新增独立 `page_structure_semantics.md` 主产物
- 不把页面结构语义扩张为完整布局系统
- 不引入像素、栅格、宽度、响应式规则
- 不引入组件树、容器树、前端实现结构
- 不引入高保真视觉稿
- 不让 preview 成为主链路 gate 的前置条件

## 5. 页面结构语义的正式边界

### 5.1 它表达什么

页面结构语义只表达：

- 页面视觉中心
- 页面主要区块
- 区块相对位置关系
- 主次层级
- 基础阅读顺序
- 与页面目标相匹配的结构理由

### 5.2 它不表达什么

页面结构语义不得表达：

- 宽度、列数、填充、栅格
- 精确对齐与响应式
- 容器实现结构
- 组件树
- 交互动效实现
- 前端实现方案

### 5.3 允许的关系表达

允许保留以下结构概念：

- Header
- Filter
- Action
- Main
- Side
- Footer
- Menu
- Tab
- Step
- Info
- Alert
- Left / Right
- Top / Bottom

### 5.4 禁止的表达

禁止写入以下明显偏实现层的结构词：

- Root Container
- Section Container
- Left Container
- Right Container
- Global Container
- 任意组件级容器名

原因：

页面结构语义表达的是“页面关系”，不是“实现容器”。

## 6. 主链路中的正式定位

### 6.1 知识真源定位

页面结构语义的初始事实仍可由：

`knowledge/raw/business/permission/15_page_carrier_semantics.md`

承担。

### 6.2 主项目消费定位

主项目默认不直接消费 RAW，而是消费编译后的 Wiki 页。

因此：

**RAW 是真源，Wiki 是主链路默认消费入口。**

### 6.3 体验阶段定位

页面结构语义在体验阶段中属于：

- 页面承载语义的补充输入
- 帮助完成 page-region 推导的正式依据
- 结构变化判断的知识底座

### 6.4 Preview 定位

preview 只消费正式蓝图和预览合同定义的中间模型，不回写正式蓝图，不新增业务语义。

## 7. 变化表达规则

本项目从本次起，体验蓝图在面对新增需求时，必须首先判断该变化属于哪一类：

### 7.1 不涉及结构变化

适用于：

- 仅文案优化
- 仅规则解释补充
- 仅错误提示优化
- 仅状态命名调整
- 仅原有区块内字段增删

此时蓝图可以显式写：

- `页面结构语义不变`
- `仅在现有区块内补充内容`

### 7.2 涉及结构变化

适用于：

- 新增独立说明区
- 新增侧边帮助区
- 新增步骤头
- 将风险提示从隐式移到显式首屏区
- 将次要信息移入折叠或辅助区
- 把原本同层内容改为主从结构
- 新增新的操作条、筛选区、结果区、页内摘要区

此时蓝图必须显式给出结构层变化，而不是只写“新增功能 / 新增模块”。

## 8. 必须同步更新的模块

本次优化必须同步更新以下层级：

1. Wiki 子系统页面编译与正式页表达
2. `specs/10_experience_blueprint_contract.md`
3. `templates/experience_blueprint.template.md`
4. 体验蓝图生成逻辑
5. `packages/context_assemble/core.py`
6. `packages/validate/core.py`
7. 相关 gate / coverage / trace 检查逻辑
8. `specs/14_experience_preview_contract.md`
9. `packages/experience_preview/build_preview_model.py`
10. `packages/experience_preview/render_html.py`

## 9. 交付物要求

本次优化的正式文档包至少应包括：

- 总方案合同
- Wiki 子系统页面结构语义保真规范
- 体验蓝图页面结构语义推导规范
- 执行中枢与检查链路同步规范
- 预览层页面结构关系渲染规范
- 实施清单、目标文件映射与验收标准

## 10. 一句话决策

**页面结构语义本次接入的主目标，是让需求文档进入主链路后，体验蓝图能够基于知识库判断并表达结构级变化；Wiki 负责保真承接，体验蓝图负责正式推导输出，执行中枢负责强制消费与检查，preview 负责更真实地展示既有结构关系。**
