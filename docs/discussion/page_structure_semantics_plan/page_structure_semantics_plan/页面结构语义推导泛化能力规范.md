# 页面结构语义推导泛化能力规范

## 1. 文档目的

本规范用于定义如何将当前已在权限域跑通的“页面结构语义推导”能力，升级为可跨领域复用的通用能力。

本规范解决的问题不是“如何继续补权限域规则”，而是：

- 如何让页面影响识别器不依赖权限域词汇
- 如何让页面结构基线提取可作用于多领域页面
- 如何让结构变化判断与结构落位判断具备跨领域复用能力
- 如何在不破坏现有主链路的前提下，实现生成内核的通用化升级

## 2. 当前问题定义

当前系统已经在权限域完成以下能力：

- 基于 Wiki 页面结构语义识别候选页面
- 结合任务输入动态命中页面
- 对命中页面输出结构变化判断
- 在体验蓝图中表达结构落位
- 让 preview 消费结构关系结果

但当前实现仍然带有明显的权限域特征，主要表现为：

1. 默认结构语义来源仍有 `permission` 域特判
2. 页面识别逻辑仍容易依赖权限域页面名、对象名、动作词
3. 结构变化判断仍可能受权限域语言习惯影响
4. 泛化验证样本不足，尚未证明其可跨领域稳定使用

因此，本次规范的目标是将“权限域可用”升级为“多领域可复用”。

## 3. 泛化改造目标

本次泛化改造后的系统，应达到以下能力：

1. 不依赖权限域专属词汇也能识别页面影响范围
2. 不写死权限域页面集合、页面 ID、页面对象
3. 能从不同领域的 Wiki 页面知识中提取页面结构基线
4. 能基于通用信息类型做结构变化判断，而非基于特定领域词
5. 能将新增内容映射到通用区块语义，而非映射到某个领域页面模板
6. 能在保持现有主链路不变的情况下完成升级

## 4. 非目标

本次不做以下事项：

- 不新增正式主链路阶段
- 不将页面结构语义扩展成高保真页面系统
- 不引入组件级、DOM 级、前端实现级描述
- 不把领域知识直接硬编码进生成核心
- 不让 preview 反向主导结构判断
- 不将 RAW 作为主链路默认消费源

## 5. 泛化原则

### 5.1 通用结构语义优先于领域术语

生成核心只应理解“通用页面结构语义”，而不应理解“权限域专用页面”。

允许的通用结构槽位固定为：

- Header
- Intro
- Filter
- Action
- Menu
- Tab
- Step
- Main
- Side
- Footer
- Alert
- Info

允许的通用关系固定为：

- left
- right
- stack
- main_side
- split_lr
- footer_actions
- header_with_actions
- single

### 5.2 领域知识只提供候选页与信号，不进入核心判断硬编码

领域差异应通过知识输入提供，而不是通过 `packages/generation/core.py` 写死。

领域知识允许提供：

- 页面索引
- 页面别名
- 页面主任务
- 页面面向角色
- 页面承载对象
- 页面上下游关系
- 页面结构语义摘要

但不允许在核心逻辑中写：

- `if domain == permission`
- `if 命中申请/审批/权限`
- 固定映射到权限域页面集合

### 5.3 生成核心应保持“通用推导 + 领域适配输入”

核心层负责：

- 页面候选页召回
- 页面影响识别
- 页面结构基线提取
- 结构变化判断
- 结构落位判断

领域层负责：

- 提供候选页面知识
- 提供页面别名与对象信号
- 提供结构语义摘要
- 提供领域页面索引页

## 6. 泛化后目标架构

```text
任务输入
+ requirement.md
+ background.md
+ facts.md
+ business_blueprint.md
+ context_manifest.json
+ Wiki 领域页面索引
+ Wiki 页面结构语义页
        ↓
候选页面召回
        ↓
页面影响识别
        ↓
页面结构基线提取
        ↓
结构变化判断
        ↓
结构落位判断
        ↓
experience_blueprint.md
```

## 7. 需要泛化的核心能力

### 7.1 候选页面召回器

目标：
先从领域知识中召回“可能被当前任务影响的页面”，而不是直接写死页面列表。

输入：
- 领域页面索引页
- 页面承载语义页
- 相关实体页
- 任务上下文

输出：
- 候选页面列表
- 每个候选页面的命中证据
- 候选优先级

要求：
召回依据应尽量来自：

- 页面名
- 页面别名
- 主任务
- 页面承载对象
- 角色
- 上下游关系
- 结构语义摘要

不得只依赖页面中文名做硬匹配。

### 7.2 页面影响识别器

目标：
在候选页面中识别真正受当前任务影响的页面集合。

输入：
- 候选页面列表
- `facts.md`
- `business_blueprint.md`
- `requirement.md`
- 页面结构语义摘要

输出：
- 命中页面列表
- 每页命中原因
- 是否为主页面 / 子页面 / 抽屉 / 弹窗

通用识别维度：
必须支持以下通用打分维度：

1. 页面别名命中
2. 承载对象命中
3. 主任务命中
4. 角色命中
5. 上下游关系命中
6. 结构语义摘要命中
7. 业务判断命中
8. 事实规则命中

要求：
最终命中应采用“多信号加权命中”，而不是单一关键词判断。

### 7.3 页面结构基线提取器

目标：
从 Wiki 页面知识中提取命中页面的“通用结构基线”。

输入：
- 页面结构语义页
- 页面实体页
- 命中页面列表

输出：
- 视觉中心
- 主要区块
- 区块关系
- 默认主次关系
- 默认阅读顺序

要求：
输出必须保持在“粗粒度页面结构”层，不进入实现层。

允许表达：
- Header
- Intro
- Filter
- Action
- Menu
- Tab
- Step
- Main
- Side
- Footer
- Alert
- Info
- Left / Right

禁止表达：
- Root Container
- Section Container
- Left Container
- Right Container
- 任意容器树
- 宽度百分比
- 精确列数
- 响应式断点

### 7.4 结构变化判断器

目标：
对每个命中页面判断本次任务是否引起结构变化。

标准输出字段：
- 页面结构语义基线
- 本次是否涉及结构变化
- 变化类型
- 变化说明
- 变化理由
- 不这样做的风险

通用变化类型：
- 结构不变
- 新增区块
- 区块并入
- 区块前置
- 区块后置
- 主次调整
- 左右关系调整
- 说明区显性化
- 风险提示前置

判断依据：
必须基于以下三类输入综合判断：

1. 信息新增类型
2. 页面原有结构基线
3. 业务语义变化强度

不得只根据“出现新增”就直接判定结构变化。

### 7.5 结构落位判断器

目标：
将新增或优化的信息映射到页面既有区块或新增区块。

需要支持的通用信息类型：
- 风险提示
- 规则解释
- 帮助说明
- 结果说明
- 新增入口
- 新增配置项
- 状态提示
- 摘要信息
- 下一步引导
- 辅助追溯

通用映射原则：
- 首屏必须理解的信息 -> Header / Intro / Summary
- 动作前必须知道的限制 -> Alert / Intro / Info
- 主任务直接操作对象 -> Main
- 对象切换或索引切换 -> Menu / Left / Tab
- 流程步骤切换 -> Step
- 帮助说明 / 追溯信息 -> Side / Info
- 结果后续动作 -> Footer
- 辅助动作集合 -> Action

输出要求：
体验蓝图必须显式写出：

- 推荐位置
- 结构落位
- 触发时机
- 不展示风险

## 8. 领域适配层规范

### 8.1 领域适配层的职责

每个领域应提供一个最小页面知识集，供通用生成核心消费。

最小需要内容：
- 领域页面索引页
- 页面结构语义专题页
- 关键页面实体页
- 页面别名
- 页面主任务
- 页面角色
- 页面承载对象
- 页面上下游关系

### 8.2 不允许的适配方式

不允许直接在核心中增加：

- 针对某一领域的硬编码页面 ID
- 针对某一领域的关键词优先级写死
- `if domain == xxx` 的结构判断逻辑

领域适配层只能“喂知识”，不能“改核心推导逻辑”。

## 9. 代码落位建议

### 9.1 核心逻辑
主要改造位于：

- `packages/generation/core.py`

建议拆分为内部方法：

- `build_page_candidates(...)`
- `identify_impacted_pages(...)`
- `extract_page_structure_baseline(...)`
- `judge_structure_change(...)`
- `judge_structure_slot(...)`

### 9.2 保持不变的外围模块
以下模块原则上只需接口对齐，不应承载领域推导：

- `packages/context_assemble/core.py`
- `packages/validate/core.py`
- `packages/experience_preview/build_preview_model.py`
- `packages/experience_preview/render_html.py`

### 9.3 可选新增目录
若后续泛化规模扩大，可新增：

```text
packages/generation/page_reasoning/
  candidate_recall.py
  impact_identify.py
  structure_baseline.py
  structure_change.py
  structure_slot.py
```

但这不是本轮必须项。

## 10. 实施顺序

### Step 1
抽离当前权限域相关的页面识别逻辑，明确哪些属于通用逻辑，哪些属于领域知识输入。

### Step 2
实现候选页面召回器，先从 Wiki 页面知识中构造候选集合。

### Step 3
实现页面影响识别器，用多信号打分决定真实命中页面。

### Step 4
实现页面结构基线提取器，统一输出通用结构槽位。

### Step 5
实现结构变化判断器，保证逐页输出结构变化或结构不变。

### Step 6
实现结构落位判断器，让新增信息稳定进入 `内容与信息优先级合同`。

### Step 7
增加跨领域回归集，至少验证 2~3 个非权限域任务。

## 11. 验收标准

泛化能力完成后，至少应满足：

1. 不再写死权限域页面集合
2. 页面影响识别器不依赖权限域专属词汇才能工作
3. 页面结构基线来自 Wiki 页面知识，而不是固定模板
4. 结构变化判断能对多个领域页面工作
5. 结构落位输出使用统一通用区块语义
6. 体验蓝图输出仍符合现有合同与模板
7. preview 只消费生成结果，不反向发明页面结构
8. 至少在 2~3 个不同领域任务上回归通过

## 12. 风险与控制

### 风险 1：泛化后命中精度下降
控制：
先用多信号打分，不急于完全去掉领域别名；先降权，不要直接删除。

### 风险 2：通用化后表达过空
控制：
保留领域知识页提供的页面别名、对象和主任务，确保通用核心仍有足够信号。

### 风险 3：核心再次被领域特判侵蚀
控制：
规定领域逻辑只进入 Wiki / 适配层，不进入核心判断器。

### 风险 4：泛化后 validate 与 generation 口径失配
控制：
每次改动后都必须回归检查：
- `structure_judgment_count`
- `layout_delta_item_count`
- `structure_slot_count`
- `orphan_page_count`

## 13. 一句话决策

本次泛化改造的正式决策是：

**将当前“权限域可用”的页面结构语义推导能力，升级为“通用结构推导核心 + 领域知识适配输入”的架构；核心只理解通用页面结构、结构变化与结构落位，领域差异只通过 Wiki 页面知识提供，不再写死在生成内核里。**
