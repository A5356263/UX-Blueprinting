## 3. `15_page_carrier_semantics.md` 的直接整改建议

### 3.1 继续保留页面结构语义字段

字段名称不必改，继续使用：

- `页面结构语义（仅代表该页面基本结构语义，不代表所有状态）`

### 3.2 统一整改原则

#### 保留

- left / right 关系
- main / side 关系
- top / bottom 关系
- step / tab / footer 关系

#### 删除

- Root Container
- Section Container
- Global Container
- 任意实现层容器命名

#### 收敛

- 过多动作项只保留对结构判断有意义的动作组
- 不要把所有字段名都塞进结构图

## 4. Code Agent 执行清单

你可以让 code agent 按下面顺序执行：

### 4.1 先做 Wiki 层

1. 替换 `knowledge/raw/business/permission/15_page_carrier_semantics.md`
2. 修改 Wiki 自动编译逻辑，识别 `页面结构语义`
3. 给对应 topic / entity 页增加结构语义保真区块
4. 跑一次 Wiki 自动更新
5. 抽查编译结果是否丢失 left / right / main / side

### 4.2 再做体验蓝图层

1. 更新 `specs/10_experience_blueprint_contract.md`
2. 更新 `templates/experience_blueprint.template.md`
3. 更新体验蓝图生成逻辑
4. 要求蓝图对“结构变化 / 结构不变”做显式判断
5. 把新增或优化信息落到结构语义上表达

### 4.3 再做检查链路

1. 更新 `specs/01_execution_hub_spec.md`
2. 更新 `packages/context_assemble/core.py`
3. 更新 `packages/validate/core.py`
4. 增加结构参与推导、结构落位、结构不变、实现层容器污染检查
5. 更新 coverage 统计项

### 4.4 最后做 preview

1. 更新 `specs/14_experience_preview_contract.md`
2. 更新 `packages/experience_preview/build_preview_model.py`
3. 更新 `packages/experience_preview/render_html.py`
4. 让草图支持 left / right / main / side / footer
5. 运行 preview 验证渲染结果

## 5. 回归验证建议

至少验证以下两类任务：

### 5.1 不涉及结构变化的任务

预期：

- 蓝图显式写 `结构不变`
- 只在内容合同 / 文案合同 / 状态矩阵中体现变化
- preview 页面草图不发生结构级变化

### 5.2 涉及结构变化的任务

预期：

- 蓝图显式表达新增区块或区块重排
- `关键页面蓝图` 与 `区块布局示意` 同时体现
- `内容与信息优先级合同` 能看到落位
- preview 能读出真实结构关系

## 6. 最终验收标准

### 6.1 Wiki 层

- 页面结构语义可从 RAW 编译进入 Wiki
- Wiki 页未吃掉关键结构关系
- 主链路默认只读 Wiki 时仍能获得结构依据

### 6.2 体验蓝图层

- AI 能判断新增 / 优化信息是否引起结构变化
- 结构变化能在蓝图中正式表达
- 不涉及结构变化时不强行表达结构变化
- 蓝图不出现实现层容器词

### 6.3 检查链路

- validate 能检测结构变化是否被正确表达
- coverage 能统计结构语义参与度
- gate 能阻断明显缺失或错误表达

### 6.4 preview 层

- 页面草图能表达结构关系
- 不再只从上到下堆叠
- 与正式蓝图表达一致
- 不新增业务语义

## 7. 一句话执行策略

**先解决 Wiki 是否保真，再解决蓝图是否真正消费，再解决检查链路是否能强制约束，最后才解决 preview 是否看起来更真实。**
