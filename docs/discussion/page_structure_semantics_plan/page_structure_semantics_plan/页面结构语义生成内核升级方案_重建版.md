# 页面结构语义生成内核升级方案

## 1. 问题定义

当前项目已经完成外围链路升级，包括：

- Wiki 侧开始保真页面结构语义
- 体验蓝图合同与模板已要求输出结构变化判断、结构不变与结构落位
- assemble 已能暴露结构语义来源可见性
- validate / coverage 已开始检查结构语义是否参与推导
- preview 已支持结构关系渲染

但生成内核仍未完成同等级升级。当前 `packages/generation/core.py` 仍以“保底模板 + 关键词启发式判断”为主，只是在旧生成方式上附加了新口径，尚未成为真正基于知识库做页面结构推导的核心。

---

## 2. 改造目标

本次改造目标是：

将体验蓝图生成内核从“固定模板填充器”升级为“基于知识库、业务判断与页面结构语义做页面级推导的生成器”。

改造后，系统在读取真实需求文档时，应能够：

1. 识别需求影响的是哪些页面 / 窗口 / 区块
2. 判断本次变更是否引起页面结构变化
3. 判断变化属于哪一类结构变化
4. 判断新增或优化的信息应落到哪个既有区块
5. 若无需改结构，也能显式输出“结构不变，仅在既有区块内补充”
6. 将上述判断稳定写入 `experience_blueprint.md`

---

## 3. 非目标

本次不做以下事项：

- 不新增主链路正式阶段
- 不引入高保真视觉稿系统
- 不引入像素、栅格、响应式布局规则
- 不把页面结构语义扩张成组件级或前端实现级 DSL
- 不让 preview 反向驱动主链路
- 不把 RAW 作为主链路默认读取入口

---

## 4. 当前根因

当前生成内核的问题不是“完全不支持结构语义”，而是支持方式仍然过浅，主要表现为：

### 4.1 页面集合不是从知识与任务中稳定推导出来
当前生成逻辑仍然偏向固定页面骨架，不能根据任务真实命中的页面对象稳定产出页面集合。

### 4.2 结构变化判断仍以关键词启发为主
当前对“新增说明 / 帮助文档 / 风险提示 / 新增模块 / 新增入口”等关键词做启发式判断，这只能作为兜底，不能作为主推导逻辑。

### 4.3 页面结构语义只是被“引用”，还没有深度参与页面级推导
现在更多是把结构语义当作背景摘要，而不是把它当成“页面结构基线”。

### 4.4 结构落位还不稳定
系统还没有形成稳定的“信息类型 -> 区块位置”判断规则，例如：

- 风险提示进入 Intro / Alert 还是 Side
- 新帮助说明进入 Info 还是 Side
- 新结果说明进入 Summary 还是 Main
- 新配置入口进入 Action 还是 Step

### 4.5 生成层与验证层完成度不一致
外围链路已经在检查“有没有结构变化判断”，但生成层还没真正具备稳定产出能力，导致系统容易进入“合同升级了，但核心推导还没升级”的状态。

---

## 5. 目标架构

改造后的生成内核应形成以下结构：

```text
输入需求
+ facts.md
+ business_blueprint.md
+ task_card / context_manifest
+ Wiki 页面结构语义页
        ↓
页面影响识别
        ↓
页面结构基线提取
        ↓
变更类型判断
        ↓
结构落位判断
        ↓
体验蓝图正式输出
```

其中核心新增能力有四个：

1. 页面影响识别器
2. 页面结构基线提取器
3. 结构变化判断器
4. 结构落位判断器

---

## 6. 具体改造方案

## 6.1 页面影响识别器

### 目标
先判断本次需求影响哪些页面，而不是直接写死 `P-01 / P-02 / P-03`。

### 输入
- `facts.md`
- `business_blueprint.md`
- 任务上下文中的 Wiki 引用
- 页面承载语义与实体页

### 输出
- 命中的页面清单
- 每个页面的影响说明
- 是否为主页面 / 子页 / 抽屉 / 弹窗

### 要求
必须优先依据：
- 页面名
- 承载对象
- 主任务
- 上下游关系
- 页面结构语义摘要

不得只靠关键词拍脑袋绑定页面。

---

## 6.2 页面结构基线提取器

### 目标
把 Wiki 中保真的页面结构语义变成生成器可消费的页面基线。

### 输入
- `knowledge/wiki/topics/page-carrier-semantics-map.md`
- 相关实体页
- 命中的页面对象

### 输出
每个页面的结构基线，例如：

- 视觉中心
- 主要区块
- 区块相对关系
- 当前默认主次关系
- 可承载的信息类型

### 要求
这一步只提取粗粒度结构基线，不进入实现层容器。

允许的区块语义保持为：

- Header
- Intro
- Filter
- Action
- Menu
- Tab
- Step
- Main
- Side
- Footer
- Alert
- Info
- Left / Right

禁止生成：

- Root Container
- Section Container
- Left Container
- Right Container
- 任何实现层容器树

---

## 6.3 结构变化判断器

### 目标
对每个命中页面做正式判断：

- 是否涉及结构变化
- 如果变化，属于什么变化
- 如果不变，为什么不变

### 标准输出字段
- 页面结构语义基线
- 本次是否涉及结构变化
- 变化类型
- 变化说明
- 变化理由
- 不这样做的风险

### 推荐变化类型
- 结构不变
- 新增区块
- 区块并入
- 区块前置
- 区块后置
- 主次调整
- 左右关系调整
- 说明区显性化
- 风险提示前置

### 要求
判断必须综合以下三类信息：

1. 业务变化
2. 信息新增类型
3. 页面原有结构基线

不能再只根据“出现了新增”就一律判成“新增区块”。

---

## 6.4 结构落位判断器

### 目标
当需求新增内容或优化内容时，判断其应进入哪个既有区块或新增区块。

### 需要判断的典型内容
- 风险提示
- 规则解释
- 帮助信息
- 结果说明
- 新增入口
- 新增配置项
- 状态提示
- 辅助说明
- 下一步引导

### 输出要求
在 `内容与信息优先级合同` 中必须稳定写出：

- 推荐位置
- 结构落位
- 触发时机
- 不展示风险

### 推荐判断原则
- 当前页面首先要理解的内容 -> Header / Intro / Summary
- 当前动作前必须知道的限制 -> Alert / Intro / Info
- 主任务直接操作对象 -> Main
- 辅助解释 / 帮助 / 追溯 -> Side / Info
- 结果后下一步动作 -> Footer
- 流程步骤切换 -> Step / Tab
- 对象切换 / 索引切换 -> Menu / Left

---

## 6.5 体验蓝图输出器重构

### 目标
让 `experience_blueprint.md` 的页面内容不再是固定骨架，而是“页面影响识别 + 结构基线 + 结构判断 + 结构落位”的组合结果。

### 要求
- `关键页面蓝图` 按真实命中页面展开
- `区块布局示意` 与结构变化判断一致
- `内容与信息优先级合同` 显式承接结构落位
- 若页面未变化，也必须写出结构不变
- 若需求变化影响多个页面，每个页面分别判断，不允许全局只写一句“结构有变化”

---

## 7. 与其他模块的联动边界

## 7.1 需要联动，但不是重构它们
本次主改动在生成内核，但会轻度依赖以下模块：

- `packages/context_assemble/core.py`
  - 提供结构语义来源可见性
- `templates/experience_blueprint.template.md`
  - 提供正式输出骨架
- `specs/10_experience_blueprint_contract.md`
  - 提供正式判断口径
- `packages/validate/core.py`
  - 检查是否真的参与推导
- `knowledge/wiki/...`
  - 提供正式结构语义基线

## 7.2 联动原则
这些模块只需保持接口一致，不应反向侵入生成核心判断逻辑。

也就是说：

- Wiki 不负责替 generation 做最终判断
- validate 不负责替 generation 推导结构
- preview 不负责发明页面结构
- generation 才是正式的结构推导中心

---

## 8. 实施顺序

建议按以下顺序实施：

### Step 1
重构 `packages/generation/core.py`，先拆出：

- 页面影响识别
- 页面结构基线提取
- 结构变化判断
- 结构落位判断

### Step 2
让 `run_generate_experience()` 不再写死固定页面骨架，而是根据命中页面动态生成 `页面 / 窗口清单` 与 `关键页面蓝图`

### Step 3
让 `区块布局示意` 与 `结构变化判断` 使用同一份结构判断结果，避免前后矛盾

### Step 4
对齐 `validate/core.py` 的检查项，确保新生成逻辑输出满足现有新合同

### Step 5
用真实任务回归验证，优先跑权限域任务，确认：
- 结构变化判断是否稳定
- 结构不变是否被显式表达
- 结构落位是否能被消费
- preview 是否正确还原结构关系

---

## 9. 验收标准

改造完成后，至少满足：

1. 体验蓝图不再固定输出写死的页面骨架
2. 页面集合由任务与知识库共同推导得出
3. 每个关键页面都能显式写出结构变化判断
4. 当需求不改结构时，能明确写出“结构不变，仅在既有区块补充”
5. 当需求新增解释、风险、帮助、入口、配置项时，能判断结构落位
6. 区块布局示意不再只是通用模板，而是跟页面基线和本次变化一致
7. validate 不再只是检查“有没有这几个字段”，而是能检出明显的结构判断缺失或前后矛盾
8. preview 只消费生成结果，不反向发明结构

---

## 10. 风险与控制

## 风险 1：生成器复杂度上升
### 控制
不要一步上 DSL，只做粗粒度结构推导。

## 风险 2：结构语义判断过拟合权限域
### 控制
先在权限域落稳，但抽象出通用接口，不把页面名写死在核心逻辑里。

## 风险 3：生成与校验口径再次不一致
### 控制
每改一轮生成逻辑，就同步回归 `validate/core.py` 的检查项。

## 风险 4：结构落位越来越像实现稿
### 控制
始终限制在体验蓝图层，不进入容器树、栅格、像素、前端实现。

---

## 11. 一句话决策

本次不是继续补外围配套，而是要把 `packages/generation/core.py` 从“旧保底模板生成器”升级为“基于 Wiki 页面结构语义、业务判断与任务输入做页面级结构推导的正式生成内核”，并以此真正支撑体验蓝图中的结构变化判断、结构不变表达与结构落位输出。
