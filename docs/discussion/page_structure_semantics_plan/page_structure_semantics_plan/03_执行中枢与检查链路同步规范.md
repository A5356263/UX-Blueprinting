# 执行中枢与检查链路同步规范

## 1. 文档目的

本规范用于约束当前项目中的执行中枢、context assemble、gate、validate、coverage 如何同步支持页面结构语义参与体验推导。

## 2. 当前链路事实

### 2.1 执行顺序事实

当前执行中枢规范已经固定：

- `assemble`
- `generate-facts`
- `generate-business`
- `generate-experience`
- `gate-*`
- `validate`
- `coverage`
- `archive`
- `preview`

因此本次只能在既有步骤中补逻辑，不能插新正式阶段。

### 2.2 context assemble 事实

当前 `packages/context_assemble/core.py` 会把解析后的 `knowledge_refs / wiki_refs / template_refs / check_refs` 复制到 `context_bundle`，并生成：

- `context_manifest.json`
- `knowledge_usage_report.json`

其中 `knowledge_usage_report.json` 已经明确：

- `mainline_knowledge_policy = wiki_pages_only`

这意味着：

- 体验阶段默认只能稳定读取 Wiki
- 如果 Wiki 不保真，体验阶段就会吃薄页面结构语义

## 3. 执行中枢层需要同步的内容

### 3.1 `specs/01_execution_hub_spec.md`

需补充说明：

- 体验阶段除消费业务知识、设计指南外，还应消费 Wiki 中保留的页面结构语义
- 页面结构语义属于体验推导输入，不属于新增正式阶段
- preview 的结构关系渲染依赖正式体验蓝图中的结构表达，不得直接绕回 RAW

### 3.2 `packages/context_assemble/core.py`

当前逻辑本身无需改为直接读 RAW，但需要增加两类信息：

#### A. 可见性确认

在 `context_manifest.json` 或 `knowledge_usage_report.json` 中加入对页面结构语义的显式声明，例如：

- 是否存在页面结构语义来源
- 相关 wiki refs 是否包含结构语义页
- 若引用的 wiki 未命中结构语义，给出 warning

#### B. 风险提示

如果 task 引用权限域页面知识，但对应 Wiki 页未保留结构语义，应在 assemble 阶段直接给 warning，避免体验阶段无感丢失。

## 4. Generate Experience 层需要同步的内容

体验蓝图生成逻辑必须新增一条显式推导要求：

- 当读取到页面结构语义后，对每一条新增或优化需求判断是否涉及结构变化
- 若涉及，写入 `关键页面蓝图` 与 `区块布局示意`
- 若不涉及，写入 `结构不变`

不能只把结构语义当静态参考背景。

## 5. Validate 层需要新增的检查

当前 `packages/validate/core.py` 已经会检查：

- 栏目是否存在
- `region_map_count` 是否大于 0
- 是否有逐页展开的页面蓝图

但本次还需要新增更强的检查：

### 5.1 结构参与推导检查

当体验蓝图中出现以下词时：

- 新增模块
- 新增入口
- 新增说明区
- 新增风险提示
- 新增帮助区
- 新增摘要区
- 优化页面结构
- 调整页面布局

validate 必须继续判断：

- 是否同时存在结构变化判断
- 是否在 `区块布局示意` 中看到对应落位
- 是否在 `关键页面蓝图` 中解释结构变化原因

### 5.2 结构不变检查

如果需求明显涉及页面功能变化，但蓝图没有写结构变化，必须至少出现：

- `结构不变`
- `仅在既有区块内补充`

否则应给 warning，避免 AI 完全跳过结构判断。

### 5.3 页面结构语义来源承接检查

建议新增：

- 体验蓝图是否显式承接页面结构语义来源
- 追踪映射中是否能看到结构级设计依据

### 5.4 禁止实现层容器渗透

若体验蓝图中出现：

- Root Container
- Section Container
- Left Container
- Right Container

应直接给 warning 或 blocker。

## 6. Coverage 层需要新增的检查

coverage 不应只统计：

- facts 被承接多少
- judgments 被承接多少
- pages / flows 数量

还应补充：

### 6.1 结构变化覆盖率

统计以下指标：

- `structure_change_item_count`
- `structure_unchanged_item_count`
- `structure_semantics_trace_count`
- `layout_delta_item_count`

### 6.2 结构落位一致性

如果某条新增功能被写成结构变化，则必须同时能在：

- `关键页面蓝图`
- `区块布局示意`
- `内容与信息优先级合同`

中找到一致表达。

## 7. Gate 层需要新增的判断

### 7.1 experience gate

建议新增 warning / blocker 规则：

#### blocker

- 蓝图声称新增页面区块，但 `区块布局示意` 中无对应表达
- 结构变化写入了实现层容器概念
- 结构变化与页面目标明显矛盾

#### warning

- 需求涉及新增页面信息，但蓝图未判断结构是否变化
- 页面结构语义来源缺失
- 结构变化说明存在，但 `内容与信息优先级合同` 未写落位

## 8. Trace 需要同步

### 8.1 体验追踪映射

追踪映射应允许出现结构级对象，例如：

- `P-01 / Header 风险说明区`
- `P-03 / Left 角色索引`
- `P-05 / Step 导航`

但仍保持粗粒度，不进入实现层。

### 8.2 追踪对象最小单位

允许追踪到：

- 页面
- 页内区块
- 流程节点
- 文案对象

不追踪到组件级或 DOM 级。

## 9. 目标文件清单

建议 code agent 至少检查并按需更新：

- `specs/01_execution_hub_spec.md`
- `specs/10_experience_blueprint_contract.md`
- `templates/experience_blueprint.template.md`
- `packages/context_assemble/core.py`
- `packages/validate/core.py`
- 体验蓝图生成入口与对应 prompt / 规则文件
- 与体验阶段相关的 runbook

## 10. 验收标准

1. 不新增正式主阶段
2. 主链路仍按既有顺序执行
3. assemble 能提示页面结构语义是否可用
4. experience 阶段能把结构语义参与推导
5. gate / validate / coverage 能检测结构变化是否被正确表达
6. 不允许实现层容器概念污染正式蓝图
