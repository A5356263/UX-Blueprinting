# 体验蓝图页面结构语义推导规范

## 1. 文档目的

本规范用于约束 `experience_blueprint.md` 如何正式消费页面结构语义，并把“需求变化是否引发页面结构变化”的判断输出到体验蓝图中。

## 2. 核心原则

### 2.1 页面结构语义不是为了画图好看

它的主职责不是服务 preview，而是服务：

- 页面结构推导
- 新增 / 优化能力落位
- 信息优先级变化判断
- 区块增删与重排判断

### 2.2 不是所有需求都必须写结构变化

如果某次需求不影响页面结构语义，就不要强行写结构变化。

应允许显式输出：

- `页面结构语义不变`
- `本次仅在既有区块内补充内容 / 文案 / 状态`

### 2.3 一旦涉及结构变化，就必须正式表达

如果新增或优化改变了页面结构上的任何一项，体验蓝图必须显式表达：

- 新增区块
- 区块移动
- 主次关系调整
- 左右关系调整
- 说明区前置
- 风险提示显性化
- 原有区块承担职责变化

## 3. 体验阶段输入边界

体验阶段正式输入应包括：

- `facts.md`
- `business_blueprint.md`
- task 明确引用的 Wiki 页
- guideline
- 模板
- 由 Wiki 编译保留下来的页面结构语义

注意：

- 主项目默认不直接消费 RAW
- 页面结构语义应优先从 Wiki 正式页读取
- 只有在你未来显式改规则时，体验阶段才允许补读指定 RAW

## 4. 合同层需要新增或强化的要求

需要在 `specs/10_experience_blueprint_contract.md` 中补强以下要求：

### 4.1 新增输入说明

在“输入前置条件”或“知识使用边界”中新增：

- 页面结构语义是体验阶段可消费的正式知识之一
- 页面结构语义用于判断页面区块安排、结构变化与新增能力落位

### 4.2 新增构建规则

建议新增一条正式构建规则：

**当需求涉及新增能力、优化点、解释信息、风险提示或辅助模块时，体验蓝图必须判断该变化是否引起页面结构语义变化；若引起变化，必须在关键页面蓝图与区块布局示意中显式表达。**

### 4.3 新增非目标说明

需同时声明：

- 页面结构语义不等于视觉稿
- 不进入像素布局与实现层
- 不允许把容器概念当正式输出语言

## 5. 模板层需要同步的内容

### 5.1 `关键页面蓝图` 中新增结构判断

每个关键页面建议补一小节：

```md
#### 结构变化判断

- 页面结构语义基线：<引用已有页面结构语义>
- 本次是否涉及结构变化：<是 / 否>
- 若是：<新增区块 / 重排 / 主次调整 / 关系调整>
- 若否：<仅内容 / 文案 / 状态变化>
```

### 5.2 `区块布局示意` 中输出结构变化后的结果

`区块布局示意` 不应只抄知识库基线，也不应只画原始旧页面。

它必须输出：

- 当前需求影响后的目标页面结构语义
- 新增或优化内容如何落位
- 结构不变时，显式说明结构保持不变

### 5.3 `内容与信息优先级合同` 中增加关联

推荐新增一列：

- `结构落位`

用于说明某条新增信息应进入：

- Header
- Step
- Main
- Side
- Footer
- Alert
- Info

## 6. 推导规则

体验阶段在面对每条需求变化时，必须至少做以下判断：

### 6.1 变化类型判断

先判断该变化属于：

- 业务规则变化
- 状态反馈变化
- 文案解释变化
- 页面结构变化
- 组合变化

### 6.2 结构影响判断

若变化属于后 3 类，必须继续判断：

- 是否新增独立区块
- 是否进入既有区块
- 是否改变首屏视觉中心
- 是否改变主任务路径
- 是否改变主 / 辅 / 说明 / 风险的相对关系

### 6.3 结构表达判断

若结构确有变化，必须输出：

- 变更前基线
- 变更后结构
- 变更理由
- 不这样做的风险

## 7. 正式表达规范

### 7.1 可用结构变化标签

建议统一使用：

- `结构不变`
- `新增区块`
- `区块并入`
- `区块前置`
- `区块后置`
- `主次调整`
- `左右关系调整`
- `说明区显性化`
- `风险提示前置`

### 7.2 蓝图中的写法示例

```md
#### 结构变化判断

- 页面结构语义基线：筛选区在上，操作区在中，主列表在下
- 本次是否涉及结构变化：是
- 变化类型：新增区块
- 变化说明：在 Header 下新增风险说明区，用于前置解释“权限复制”对目标用户范围的影响
- 变化理由：该信息属于动作前必须理解的信息，继续藏在帮助入口中会导致误配置
```

### 7.3 不涉及结构变化的写法示例

```md
#### 结构变化判断

- 页面结构语义基线：保持现有主从结构
- 本次是否涉及结构变化：否
- 说明：本次仅在既有 Main 区块内补充结果状态与错误文案，不新增区块，也不改变左右关系
```

## 8. 什么情况下必须写进 `关键页面蓝图`

以下场景必须写：

1. 页面结构有变化
2. 首屏理解顺序有变化
3. 风险提示从隐式变显式
4. 新增模块不是普通字段，而是独立信息块
5. 新功能影响主区 / 辅区边界

## 9. 什么情况下只写在 `内容与信息优先级合同`

以下场景可不写结构变化，只写内容合同：

1. 原区块内字段新增
2. 原提示文案补充
3. 原错误反馈更清晰
4. 状态标签变更
5. 不影响页面区块关系

## 10. Gate / Validate 需要检查什么

体验阶段检查需要新增以下能力：

1. 当蓝图写出新增模块时，必须判断是否写明结构落位
2. 当蓝图声称新增页面区块时，必须能在 `区块布局示意` 中看到对应表达
3. 当蓝图未涉及结构变化时，必须显式说明 `结构不变`
4. 当需求影响首屏优先级时，必须在 `关键页面蓝图` 中显式表达
5. 不允许把“新增功能”全部压缩成纯文本总结而不表达落位

## 11. 验收标准

当以下条件满足时，可视为体验蓝图已真正接入页面结构语义：

1. AI 能基于知识库判断结构是否变化
2. `experience_blueprint.md` 能把变化表达成结构变化或结构不变
3. `关键页面蓝图` 与 `区块布局示意` 之间结构表达一致
4. `内容与信息优先级合同` 能说明新增信息落位
5. 不会把所有需求都强行写成结构变化
