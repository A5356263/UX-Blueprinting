# Plugin 模式在本项目中的引入草案

## 基本信息

- Topic: plugin-mode
- Version: `v0.1`
- Status: `draft`
- Target Spec: `docs/sdd/` 下待定

## 讨论目标

- 判断 plugin 模式在当前项目中是否合理
- 明确 plugin 在本项目中的角色边界
- 收敛 plugin 能解决的问题、带来的收益与潜在风险
- 为后续具体落地细节讨论提供统一起点

## 当前背景

- 当前项目主线已经形成：
  - `knowledge/business/`：业务真源
  - `knowledge/guidelines/`：设计原则真源
  - `knowledge/wiki/`：知识编译层 / 消费层
  - `skills/`：AI 执行方式
  - `scripts/`：确定性脚本
  - `docs/sdd/`：正式规范
- 当前项目强调轻量工程化、文档主导、主链路稳定
- 当前项目仍在持续演进，后续会不断出现新的检查、装配、同步、转换类能力
- 这些能力如果继续散落在 prompt、skill、agent 逻辑和临时脚本中，后期会带来耦合与治理问题

## 当前方案

### 1. 对 plugin 的基本定位

- plugin 是标准化扩展单元
- plugin 用于把原本分散在 prompt、agent 逻辑和临时脚本里的能力，收敛成可声明、可加载、可治理、可复用的能力模块
- plugin 本质上不是“再加一段 prompt”，而是稳定扩展面
- 系统应尽量面向 capability 工作，而不是面向偶然实现细节工作

### 2. 在本项目中的角色

- plugin 不替代主线
- plugin 不替代知识真源
- plugin 不替代正式规范
- plugin 只承担“能力扩展层”的角色

当前建议分工：

- `knowledge/business/`：维护业务真源
- `knowledge/guidelines/`：维护原则真源
- `knowledge/wiki/`：维护编译后的任务消费层
- `skills/`：维护主线执行方式
- `scripts/`：维护核心确定性脚本
- `plugins/`：承载可插拔、可治理、可演进的扩展能力

### 3. 解决的问题

当前认为 plugin 能解决以下问题：

- 把高频能力模块化复用
- 让 workflow / agent 不再强耦合具体实现
- 支持官方、实验性、项目本地三层扩展
- 在插件缺失、不兼容、失效时显式报告，而不是静默退化
- 给实验能力一个比“临时脚本”更稳定的位置

### 4. 当前推荐范围

当前更适合插件化的是“能力”，不是“知识真源”。

适合优先插件化的方向：

- `command`：任务创建增强、上下文装配增强、wiki 同步检查、导出器
- `hook`：挂在 `new_task`、`assemble_context`、`validate_outputs`、`archive_artifacts` 周围的扩展点
- `policy`：输出边界检查、wiki 过期检查、兼容性检查、失败显式化
- `skill`：后续再讨论，当前不作为第一优先级

### 5. 当前不建议插件化的内容

- 业务知识真源本身
- 设计原则真源本身
- 项目主线语义本身
- 讨论稿与 SDD 规范本身
- 最核心的主链路脚本定义

## 备选方案

### 方案 A：继续维持当前方式，不引入 plugin

优点：

- 结构简单
- 当前学习成本最低
- 不增加抽象层

缺点：

- 扩展能力会继续散落在脚本和 skill 中
- 缺能力时更容易静默退化
- 后续实验能力难治理
- 多项目/多业务域复用会越来越弱

### 方案 B：引入轻量 plugin 层，只承载扩展能力

优点：

- 不破坏当前主线
- 可以逐步接入
- 扩展能力更清晰
- 失败可见性更强

缺点：

- 需要新增一层 manifest 和加载逻辑
- 需要额外定义兼容性与状态模型

### 方案 C：大规模插件化，把主线能力整体收编

优点：

- 理论上最统一

缺点：

- 当前项目阶段过重
- 会显著增加抽象成本
- 有较高概率破坏目前轻量、清晰的优势

当前倾向：

- 优先选择方案 B

## 关键取舍

### 取舍 1：要不要引入 plugin

- 当前结论：可以引入
- 原因：项目正在持续演进，未来会不断出现“值得复用但不应直接并入主线”的能力

### 取舍 2：plugin 是不是主线

- 当前结论：不是
- 原因：本项目仍应以知识真源、Wiki 编译层、skills、scripts 为主线；plugin 只是扩展层

### 取舍 3：是否要插件化知识

- 当前结论：不建议
- 原因：知识真源和原则真源已经具备较好的 AI 消费结构，不应被能力抽象层替代

### 取舍 4：是否要自动同步 plugin 与主线

- 当前结论：后续要显式治理兼容性和失效信号
- 当前判断：应优先做“显式检查和报错”，而不是“静默自动兜底”

## 当前结论

- plugin 模式在本项目中使用是合理的
- 但合理的前提是：plugin 被严格定位为能力扩展层，而不是新主线
- plugin 最大价值在于：
  - 抽离高频扩展能力
  - 降低 workflow 与实现耦合
  - 承载实验性能力
  - 显式表达兼容性、状态与失败
- 当前最适合先从 `command / hook / policy` 三类能力切入
- `skill plugin` 是否需要引入，建议后续单独讨论

## 开放问题

- 本项目是否真的需要完整的 plugin 运行时，还是只需要轻量 manifest + loader
- plugin 应放在哪个目录，是否使用统一 `plugins/` 根目录
- `plugin.json` 最小字段集合在本项目中应精简到什么程度
- workflow 与 plugin 的绑定关系如何声明
- plugin 失败时应该在哪一层输出：脚本、检查报告、任务产物还是运行日志
- plugin 状态是否需要区分：official / experimental / local
- plugin 与现有 `skills/` 的边界是否需要进一步细拆
