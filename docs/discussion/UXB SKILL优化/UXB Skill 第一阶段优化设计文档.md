# UXB Skill 第一阶段优化设计文档

> 适用范围：`.codex/skills/uxb`  
> 目标读者：AI Code / 维护 UXB skill 的开发者 / 后续审阅者  
> 文档目的：指导第一阶段优化 UXB skill 的工作机制，让用户在知识问答、诊断咨询、新需求蓝图、知识沉淀等场景中使用得更自然、清晰、顺畅。

---

## 1. 背景

当前 `.codex/skills/uxb` 已经具备三个基本定位：

1. 业务与体验咨询入口；
2. UXB 任务成型入口；
3. 用户确认后的 UXB 主链路启动器。

但从实际使用体验看，目前存在几个明显问题：

1. **场景状态不够清楚**  
   用户只是问业务知识时，AI 可能误以为要进入正式 UXB 任务；用户只是想做诊断咨询时，AI 也可能过早引导任务创建。

2. **咨询与正式任务边界不够自然**  
   “问答 / 诊断 / 新需求 / 知识维护”之间缺少明确但不生硬的切换机制。

3. **知识库纠错和知识沉淀没有稳定入口**  
   用户纠正知识、确认诊断结论、确认新需求蓝图后，缺少一个自然、可追踪、可确认的知识候选机制。

4. **咨询回答容易过长**  
   当前 AI 容易一次性输出大量分析，用户阅读成本高。咨询与诊断场景更应该像设计师日常交流：先给结论，再给必要判断逻辑，最后给最少但有用的建议。

---

## 2. 第一阶段优化目标

第一阶段不重构 UXB 主链路，不重构 knowledge 子系统，不调整 `packages/` 的核心执行逻辑。

本阶段重点优化：

```text
让 UXB 从“流程型 skill”变成“自然交流型业务/体验顾问入口”。
```

优化后，用户体验应当是：

```text
问知识，就直接答清楚。
看问题，就先给判断。
有价值，再建议沉淀。
要产物，再整理任务。
要入库，先进候选区。
```

用户不需要先理解 UXB 的内部术语，也不需要主动选择模式。AI 应根据用户表达自动判断当前工作状态，并用自然语言推进。

## 4. 核心工作机制：四种工作状态

UXB skill 应在每次用户请求到达后，先进行轻量意图判断。判断不应暴露给用户，不应让用户先选择模式。

### 4.1 知识问答态

#### 适用场景

用户只是想了解当前业务知识、操作方式、规则、前置条件、模块依赖、流程关系等。

典型表达：

```text
这个模块怎么操作？
权限配置需要哪些前置条件？
这个流程和哪些流程有强关系？
这个状态为什么不能操作？
这个规则现在是怎么生效的？
```

#### 行为规则

1. 直接回答用户问题。
2. 根据需要读取 `knowledge/wiki/index.md`、summary、必要时回查 raw。
3. 不创建 UXB 项目。
4. 不输出业务蓝图 / 体验蓝图。
5. 不主动引导走主链路，除非用户明确希望进一步分析或沉淀方案。
6. 如果发现知识疑似错误、用户纠正知识、用户要求记录，则进入知识候选机制。

#### 回答风格

默认短答：

```text
结论：
...

关键原因：
- ...
- ...

你现在只需要注意：
- ...
```

不要把知识库内容机械倒出来。

---

### 4.2 诊断咨询态

#### 适用场景

用户希望 AI 分析现有业务流程、页面、体验、规则解释、状态反馈、流程断点等问题。

典型表达：

```text
这个流程是不是有问题？
这个页面用户会不会看不懂？
这个权限流程为什么感觉很绕？
你帮我看看这个流程哪里体验不好。
我不抛问题，你直接帮我判断有没有问题。
```

#### 行为规则

1. 先从业务和体验角度给判断。
2. 默认不创建 UXB 项目。
3. 默认不输出正式蓝图。
4. 只有当用户明确要沉淀方案、输出材料、走主链路时，才进入任务成型。
5. 阶段性诊断结论稳定后，可以建议提取到知识候选区，但不要打断咨询。

#### 回答风格

诊断咨询必须像设计师日常交流，简洁、直接、准确。

推荐结构：

```text
我判断这里的核心问题是：...

原因就两个：
1. ...
2. ...

建议先改这几处：
- ...
- ...
```

避免报告腔，不要一次性展开所有可能性。

---

### 4.3 正式蓝图任务态

#### 适用场景

用户提供完整新需求、详细功能描述、需求文档，或者在诊断咨询后确认需要输出业务蓝图 / 体验蓝图。

典型表达：

```text
我给你一份新需求，帮我输出业务蓝图和体验蓝图。
基于刚才的诊断，帮我走主链路。
这个优化方向确认了，帮我产出正式材料。
这份需求文档帮我分析并输出蓝图。
```

#### 行为规则

1. 不要直接执行。
2. 先阅读需求或诊断结论。
3. 先判断是否足够形成正式 UXB 任务。
4. 输出任务摘要，等待用户确认。
5. 用户明确确认后，才通过 `python -m packages` 或仓库允许的转发脚本进入主链路。
6. 正式产物仍放在 `projects/<project-id>/` 下。
7. 新需求蓝图完成后，不自动写入知识库，只能提取候选知识，等待用户确认。

#### 任务摘要必须包含

- 本次任务要解决什么；
- 用户真正关心什么；
- 已知信息；
- 不阻塞的不确定点；
- 建议执行深度；
- 建议任务名；
- 建议 `project-id`。

---

### 4.4 知识维护态

#### 适用场景

用户纠正知识、要求更新知识库、确认某些诊断结论可以沉淀、确认新需求蓝图里的部分内容可复用。

典型表达：

```text
这个不对，实际是……
这个规则改了。
把这个更新到知识库。
这个结论以后要复用。
这份蓝图里的规则可以沉淀。
这个流程已经变了，记一下。
```

#### 行为规则

1. 不要直接写 `knowledge/`。
2. 不要把聊天原文直接写入知识库。
3. 先整理成“知识候选”。
4. 将候选写入根目录 `知识候选区/`。
5. 用户确认候选可以作为稳定知识后，才进入正式知识库更新。
6. 正式入库时，遵循 knowledge 子系统逻辑：写入 `knowledge/raw/**` 或 `knowledge/raw/inbox/**`，再刷新 wiki。

## 5. 知识候选区机制

### 5.1 目录结构

在仓库根目录建立统一知识候选区：

```text
知识候选区/
├── 知识问答/
├── 诊断咨询/
└── 新需求文档/
```

规则：

1. 如果根目录没有 `知识候选区/`，AI 可以自动创建。
2. 如果没有对应子文件夹，AI 可以自动创建。
3. 每条候选知识单独一个 Markdown 文件。
4. 一个文件只记录一条候选知识。
5. 候选知识不是正式知识库内容，不能直接作为后续任务的稳定依据。
6. 候选入库前必须经过用户确认。

### 5.2 文件命名

推荐命名格式：

```text
YYYY-MM-DD_HHMM_业务域_简短主题.md
```

示例：

```text
2026-05-07_2130_权限管理_权限配置前置企业认证.md
```

如果业务域不明确，可使用：

```text
2026-05-07_2130_待归类_候选主题.md
```

### 5.3 候选状态

候选文件的状态只使用以下五种：

```text
待确认
已确认待入库
已入库
暂缓
已拒绝
```

状态含义：

| 状态 | 含义 |
|---|---|
| 待确认 | AI 认为可能有沉淀价值，但用户尚未确认 |
| 已确认待入库 | 用户确认这条可以作为稳定知识，等待正式写入 knowledge |
| 已入库 | 已写入 `knowledge/raw/**` 或 `knowledge/raw/inbox/**`，并刷新 wiki |
| 暂缓 | 当前保留，不判断为稳定知识 |
| 已拒绝 | 用户明确不需要沉淀 |

### 5.4 候选 MD 模板

建议新增：

```text
.codex/skills/uxb/assets/knowledge_candidate.template.md
```

模板内容建议：

```md
# {{候选主题}}

- 候选编号：{{KC-YYYYMMDD-HHMM-序号}}
- 来源场景：{{知识问答 / 诊断咨询 / 新需求文档}}
- 创建时间：{{YYYY-MM-DD HH:mm}}
- 当前状态：待确认
- 涉及业务域：{{业务域}}
- 建议写入位置：{{knowledge/raw/** 或 knowledge/raw/inbox/**}}
- 是否已入库：否

## 1. 触发来源

{{用简洁语言说明这条候选来自哪里。不要复制完整聊天原文。}}

## 2. 候选知识

{{写成可复用、可判断的语义化知识。}}

## 3. 影响范围

- {{影响模块 / 流程 / 状态 / 规则 / 页面 / 文案}}

## 4. 不确定点

- {{仍需确认的问题}}
- {{如果没有，写“暂无”。}}

## 5. 用户确认记录

- {{时间}}：{{用户确认 / 暂缓 / 拒绝 / 修改意见}}

## 6. 入库处理记录

- 暂未写入 knowledge。
```

### 5.5 何时创建候选文件

不要过度沉淀。

只有满足以下任一条件时才创建候选文件：

1. 用户明确说“记录 / 记一下 / 更新知识库 / 写入知识库”；
2. 用户纠正了知识，AI 询问是否记录，用户同意；
3. 诊断咨询出现稳定结论，AI 建议沉淀，用户同意；
4. 新需求蓝图完成后，AI 提取候选，用户同意；
5. 用户直接要求将某条内容沉淀为后续可复用知识。

不要因为 AI 自己觉得有价值，就擅自创建大量候选文件。

## 6. 不同场景下的知识候选触发方式

### 6.1 知识问答中的触发方式

用户只是问问题时，默认不创建候选。

当用户纠错时：

```text
用户：不对，现在权限配置前必须先完成企业认证。
AI：明白，我先按这个纠正修正当前答案。这个信息看起来是稳定业务规则，要不要我先记到「知识候选区 / 知识问答」，状态标为待确认？
```

用户确认后，创建候选文件。

如果用户直接说“更新知识库”，AI 应先复述候选内容：

```text
可以。我先把要写入的内容整理成候选，你确认无误后再入库：

- 涉及模块：权限管理、企业认证
- 候选知识：企业未完成认证时，不能完成权限配置
- 影响范围：权限配置入口、保存动作、异常提示
- 不确定点：是不能进入，还是能进入但不能保存？

你确认这条作为稳定知识吗？
```

---

### 6.2 诊断咨询中的触发方式

诊断过程中不要频繁创建候选。

阶段性结论稳定后，AI 可以自然提示：

```text
这次诊断里有 2 条结论后续可能会复用。我建议先放到「知识候选区 / 诊断咨询」，状态标为待确认，不直接入库。需要我记录吗？
```

如果用户说“记录”，则创建候选文件。

如果用户说“走主链路”，则先整理 UXB 任务摘要，完成正式蓝图后再判断哪些内容可沉淀。

---

### 6.3 新需求文档中的触发方式

新需求不应自动写入知识库。

蓝图完成后，AI 可以提示：

```text
这份是新需求蓝图，我不建议整份自动入库。可以先提取“已确认规则 / 流程依赖 / 体验原则”作为知识候选，放到「知识候选区 / 新需求文档」。你确认后再决定哪些入库。
```

如果用户确认，则创建候选文件。

注意：还未评审通过的新方案，不应写成稳定知识。可以先进入候选区，状态为“待确认”或“暂缓”。

---

### 6.4 直接知识维护中的触发方式

用户明确要求更新知识库时：

```text
用户：把这个更新到知识库。
AI：可以。我先整理成知识候选，不会直接把聊天原文写入知识库。你确认候选内容后，我再执行入库。
```

随后创建或更新候选，状态可设为：

```text
已确认待入库
```

如果仍存在关键不确定点，则保持：

```text
待确认
```

## 7. 候选入库规则

知识候选区只是缓冲区。

正式入库必须满足：

1. 用户确认该候选可以作为后续稳定知识；
2. 候选内容已语义化整理，不是聊天原文；
3. 明确建议写入位置；
4. 不确定点已处理，或明确以 `[QUESTION]` / 待确认形式保留；
5. 入库后运行 knowledge 子系统更新逻辑。

### 7.1 入库位置建议

如果知道明确业务域：

```text
knowledge/raw/business/<domain>/
```

如果是体验指南：

```text
knowledge/raw/guidelines/
```

如果暂时无法归类：

```text
knowledge/raw/inbox/
```

### 7.2 入库后动作

入库后应运行知识库更新逻辑。根据现有 knowledge 子系统，通常是：

```bash
python knowledge/scripts/update_wiki.py --apply
```

如只更新单个 raw，可使用：

```bash
python knowledge/scripts/update_wiki.py --apply --only <raw-file-path>
```

入库处理记录需要回写到候选文件：

```md
## 6. 入库处理记录

- 2026-05-07 21:45：已写入 knowledge/raw/business/权限管理/xxx.md
- 2026-05-07 21:46：已运行 update_wiki.py --apply
- 当前状态：已入库
```

## 8. 咨询与诊断回答风格优化

这是第一阶段最重要的体验优化之一。

### 8.1 总原则

咨询和诊断场景必须：

```text
默认短答，必要时再展开。
```

AI 应像设计师日常交流，而不是写报告。

### 8.2 推荐回答结构

默认使用：

```text
结论：
一句话说明问题本质。

为什么：
用 2-3 条说清关键判断逻辑。

建议：
只给当前最应该做的 1-3 个动作。
```

如果用户只问一个具体知识点，甚至可以更短：

```text
可以 / 不可以 / 需要 / 不需要。

原因是：...
你只需要注意：...
```

### 8.3 禁止倾向

避免：

1. 一次性输出长篇报告；
2. 把所有可能性全部列完；
3. 机械复述知识库；
4. 输出大量背景铺垫；
5. 使用“流程化客服话术”；
6. 使用太多内部术语；
7. 在用户没要求时主动解释 task card、context manifest、gates、repair loop 等内部机制；
8. 用复杂概念替代直接判断。

### 8.4 什么时候可以展开

只有以下情况才展开：

1. 用户明确要求“详细分析”；
2. 问题本身涉及多个业务域，短答会误导；
3. 存在高风险规则、权限、审批、数据边界；
4. 需要给正式任务摘要；
5. 需要输出正式蓝图或候选知识文件。

## 9. 自然确认机制

确认对象不要设计成“是否启动流程”，而应设计成用户能理解的判断。

### 9.1 知识候选确认

推荐问法：

```text
这条以后可以作为稳定知识使用吗？
```

不要问：

```text
是否进入知识维护态？
```

### 9.2 任务确认

推荐问法：

```text
我先把这件事整理成可执行任务。你确认后，我再创建 UXB 任务。
```

不要问：

```text
是否执行 mainline？
```

### 9.3 诊断后是否进入任务

推荐问法：

```text
如果你认可这个判断，我可以把它整理成一份正式 UXB 任务，用来输出业务蓝图和体验蓝图。
```

不要问：

```text
是否从诊断咨询态切换到正式蓝图任务态？
```

## 12. 验收标准

第一阶段完成后，至少满足以下验收用例。

### 用例 1：纯知识问答

用户：

```text
权限配置需要哪些前置条件？
```

期望：

1. AI 直接回答。
2. 不创建 UXB 任务。
3. 不输出任务摘要。
4. 不问是否走主链路。
5. 如果知识不足，说明不确定点。

---

### 用例 2：用户纠错

用户：

```text
不对，现在还必须完成企业认证。
```

期望：

1. AI 先修正当前答案。
2. AI 用一句自然话术询问是否记录到知识候选区。
3. 用户确认后，AI 创建：

```text
知识候选区/知识问答/xxxx.md
```

4. 状态为“待确认”或“已确认待入库”。

---

### 用例 3：诊断咨询

用户：

```text
你帮我看看这个权限流程哪里体验不好。
```

期望：

1. AI 给核心判断。
2. 回答简短，不写长篇报告。
3. 不默认创建任务。
4. 如果诊断结论有沉淀价值，可以在结尾轻提示：

```text
这条判断后续可能会复用，需要的话我可以先记到知识候选区。
```

---

### 用例 4：诊断转正式任务

用户：

```text
这个判断我认可，帮我走主链路输出业务蓝图和体验蓝图。
```

期望：

1. AI 先整理任务摘要。
2. 等用户确认。
3. 确认后才执行。
4. 正式产物进入 `projects/<project-id>/`。

---

### 用例 5：新需求文档

用户上传或粘贴新需求文档。

期望：

1. AI 先阅读和评估需求。
2. 指出明显风险和缺口。
3. 整理任务摘要。
4. 用户确认后进入正式任务。
5. 产物完成后，不自动入库，只建议提取候选知识。

---

### 用例 6：蓝图产物反哺知识库

用户：

```text
这份蓝图里的规则可以沉淀。
```

期望：

1. AI 不直接写 knowledge。
2. AI 提取候选知识。
3. 写入：

```text
知识候选区/新需求文档/xxxx.md
```

或：

```text
知识候选区/诊断咨询/xxxx.md
```

4. 用户确认后才正式写入 knowledge。

## 13. 明确不做的事情

第一阶段不做：

1. 不改 `packages/` 主链路；
2. 不改 `specs/` 正式契约；
3. 不重构 knowledge 子系统；
4. 不自动把蓝图内容写入知识库；
5. 不让 AI 自动创建大量知识候选；
6. 不把聊天原文直接写入候选文件；
7. 不让用户必须理解内部状态名；
8. 不把咨询回答改成报告型长文。
9. 知识候选区只是人工 / AI 协作记录区，不参与 packages 执行中枢，不参与 run-main，不参与 gate / validate / archive / preview，不被 specs / templates 消费，也不作为 projects/<project-id>/ 的正式产物。知识候选区的文件只有在用户明确要求“入库 / 更新知识库”时，才由 AI 按 knowledge 子系统逻辑处理；这个动作不走 UXB 主链路。

## 14. 最终目标效果

优化后的 UXB 应该给用户这种感觉：

1. 我只是问个问题，AI 就直接答清楚了。
2. 我让 AI 看问题，它能像设计师一样给核心判断，不绕。
3. 真的值得沉淀时，AI 会自然提醒我。
4. 要输出正式材料时，AI 会先帮我整理任务摘要。
5. 要更新知识库时，AI 不会乱写，而是先放到候选区让我确认。
6. 我不用懂内部流程，也能顺畅使用 UXB。

--- 

## 15. 一句话总结

第一阶段优化的核心不是增加流程，而是让 UXB 的状态判断、知识候选、确认方式和回答风格变得自然、清晰、克制。
