# `projects/` 模式在本项目中的适用性草案

## 基本信息

- Topic: projects-mode
- Version: `v0.1`
- Status: `draft`
- Target Spec: `docs/sdd/` 下待定

## 讨论目标

- 评估 `projects/` 作为上层目录容器，是否适合当前项目
- 明确 `projects/` 与当前 `tasks/`、`artifacts/`、`knowledge/` 等结构的关系
- 收敛当前阶段是否应该引入 `projects/`
- 为后续项目层与任务层分层设计保留讨论起点

## 当前背景

- 当前仓库已经有较清晰的主结构：
  - `knowledge/business/`：业务真源
  - `knowledge/guidelines/`：设计原则真源
  - `knowledge/wiki/`：知识编译层 / 消费层
  - `tasks/active/<task-id>/`：单次任务工作区
  - `artifacts/<task-id>/`：任务归档产物
  - `docs/`：架构、运行手册、讨论稿、SDD 规范
  - `scripts/`、`checks/`、`templates/`、`skills/`：平台公共能力
- 当前项目更像“一个平台仓库 + 多个任务实例”
- 当前任务单位已经能较好承载输入、工作区、上下文快照、归档结果

## 当前方案

### 1. 对 `projects/` 的基本理解

- `projects/` 是一种按项目分仓管理的目录组织方式
- 它不是业务逻辑，不是协议，不是数据库，而是工作区结构设计
- 它的目标是给多个长期并存、相互隔离的项目提供容器层

### 2. 在本项目中的判断

- 当前仓库已经部分具备 `projects/` 模式想解决的问题
- 但当前最高层的稳定单位更像是 `task`，而不是 `project`
- 如果现在直接上 `projects/`，会出现 `project` 和 `task` 边界重叠的问题

### 3. 当前推荐结论

- 当前阶段不建议把整个仓库主结构改造成 `projects/`
- 当前更应继续打磨 `tasks/ + artifacts/ + shared knowledge` 的主线
- `projects/` 更适合在未来作为“上层容器层”引入，而不是立即替代现有结构

## 备选方案

### 方案 A：维持当前结构，不引入 `projects/`

优点：

- 不增加抽象层
- 与当前任务主线一致
- 认知成本最低

缺点：

- 当未来出现多个长期独立项目时，缺少显式项目层

### 方案 B：现在就把主结构改成 `projects/`

优点：

- 提前为多项目管理做准备
- 项目边界会更显性

缺点：

- 当前项目阶段可能过早
- 会与 `tasks/` 形成概念重叠
- 会增加目录层级与心智负担

### 方案 C：保持当前结构，但把 `projects/` 作为未来预留能力

优点：

- 当前不破坏主线
- 未来可平滑演进
- 适合在“多长期项目”真正出现后再引入

缺点：

- 需要提前想清楚未来 `project` 与 `task` 的关系

当前倾向：

- 优先选择方案 C

## 关键取舍

### 取舍 1：当前最高层单位是什么

- 当前结论：更接近 `task`
- 原因：当前仓库的实际运行与归档都是围绕任务实例展开，而不是围绕多个长期项目展开

### 取舍 2：`projects/` 是否能直接替代 `tasks/`

- 当前结论：不能
- 原因：`projects/` 是项目容器层，`tasks/` 是执行实例层，二者不是同一层级概念

### 取舍 3：未来是否值得引入 `projects/`

- 当前结论：值得预留
- 原因：如果后续同仓库里要管理多个长期项目，`projects/` 会比继续只靠 `tasks/` 更清晰

## 当前结论

- `projects/` 这个模式本身是合理的
- 但它更适合“多长期独立项目并存”的仓库，而不是当前这个“单平台 + 多任务实例”的阶段
- 当前不建议立即把根结构切换为 `projects/`
- 更合理的方向是：
  - 当前继续围绕 `tasks/` 打磨执行主线
  - 未来出现多个长期项目后，再把 `projects/` 作为上层容器层引入

## 开放问题

- 本项目未来的“项目”边界到底是什么：
  - 客户项目
  - 业务域
  - 长期蓝图工程
  - 产品线
- 若未来引入 `projects/`，`knowledge/` 与 `wiki/` 是保留全局共享，还是按项目分层
- 若未来引入 `projects/`，`tasks/` 是迁入 `projects/<project-id>/tasks/`，还是继续保持根级
- 项目级元信息是否需要 `meta.json`
- 项目级归档、导出、权限与状态是否需要单独设计
