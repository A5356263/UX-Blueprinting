# 项目重构方案 v1

## 基本信息

- Topic: architecture-refactor-v1
- Version: `v0.1`
- Status: `draft`
- Target Spec: 待收敛后迁移到 `specs/` 与少量 `docs/` 说明文档

## 重构目标

把当前仓库从“可工作但层次偏多、职责有些分散”的状态，收敛成一套更清晰的分层架构。

本次重构的目标不是增加能力，而是减少并行概念，明确真源、执行、项目产物之间的边界。

## 当前判断

当前仓库的问题不是主线错误，而是层次开始变多：

- `docs/sdd/`、`specs/`、`scripts/`、`checks/`、`skills/` 都在承载一部分流程含义
- `tasks/` 与根级 `artifacts/` 分别保存项目真相，结果分散
- 对一个只有两个核心业务阶段的项目来说，当前目录和概念已经开始偏重

对本项目而言，真正需要长期稳定的只有三类东西：

- 规则法典
- 执行中枢
- 项目真相

## 本项目的业务现实

本项目只有两个核心业务阶段：

1. 业务蓝图阶段
2. 体验蓝图阶段

其他能力都不应该被视为“业务阶段”，而应该被视为执行中枢步骤，例如：

- 任务创建
- 任务解析
- 上下文装配
- 检查
- 归档

因此本项目后续的架构必须围绕“两个业务阶段 + 一套执行中枢”来设计，而不是继续扩展更多平行层。

## 目标架构

### 1. `specs/`

唯一规则法典层。

职责：

- 定义任务入口规则
- 定义两个业务阶段的输入输出合同
- 定义检查规则与状态规则
- 定义归档规则
- 定义执行中枢的固定步骤

不负责：

- 存放讨论稿
- 存放业务知识正文
- 存放平台专属用法

### 2. `packages/`

唯一执行中枢层。

职责：

- 承载固定逻辑实现
- 读取 `specs/`
- 按步骤执行、校验、失败、归档
- 为不同 AI 平台提供统一的本地执行能力

典型能力：

- `task_bootstrap`
- `task_card_resolve`
- `context_assemble`
- `validate`
- `archive`

不负责：

- 业务判断
- 体验推导
- 业务知识存储

### 3. `projects/`

唯一项目真相层。

职责：

- 保存每个项目自己的输入
- 保存每个项目执行中的正式产物
- 保存每个项目的最终交付物
- 保存每个项目的运行快照与状态文件

后续设计师与其他 AI 工具主要围绕这一层使用项目。

### 4. `knowledge/`

共享知识真源层。

职责：

- 保存业务真源
- 保存设计原则真源
- 保存 Wiki 编译层

本层继续保留，但不再承担执行中枢职责。

### 5. `templates/`

共享模板层。

职责：

- 保存输出模板
- 保存状态模板
- 保存协议模板

当前阶段建议继续独立保留，不急于并入 `packages/`。

### 6. `docs/`

解释与讨论层。

职责：

- 架构说明
- runbook
- discussion 草稿

不再作为执行法典真源。

## 目标目录结构

建议收敛为：

```text
specs/
packages/
projects/
knowledge/
templates/
docs/
```

其中一个项目的最小结构建议为：

```text
projects/
  <project-id>/
    source/
      task_card.md
      requirement.md
      background.md
      attachments/
    workspace/
      facts.md
      business_blueprint.md
      experience_blueprint.md
      gap_list.md
      check_report.md
      check_status.json
    runtime/
      context_bundle/
      context_manifest.json
      task_card_resolved.json
      run_logs/
      snapshots/
    exports/
      final/
    meta.json
```

## 当前结构到目标结构的映射

### 规则层

- 当前：`docs/sdd/` + `specs/`
- 目标：以 `specs/` 为唯一正式法典入口

处理建议：

- `docs/sdd/` 逐步弱化为解释性文档，或并入 `docs/architecture/`
- 新规则原则上不再进入 `docs/sdd/`

### 执行层

- 当前：`scripts/` + `checks/` + 部分 `skills/`
- 目标：统一收敛到 `packages/`

处理建议：

- `scripts/` 中稳定保留的逻辑迁入 `packages/`
- `checks/` 不再作为独立执行层，而作为 `packages/validate` 的一部分
- `skills/` 降级为平台适配层，不再承载主线规则

### 项目层

- 当前：`tasks/` + 根级 `artifacts/`
- 目标：统一收敛到 `projects/`

处理建议：

- `tasks/active/<task-id>/` 迁为 `projects/<project-id>/`
- 根级 `artifacts/<task-id>/` 的最终归档收进项目自身的 `exports/final/`
- 不再让项目产物分散在两个根目录

## 当前需要停止继续放大的部分

以下方向应暂停继续扩展，先等待主架构收敛：

- 继续加重 `docs/sdd/`
- 继续把 `scripts/`、`checks/` 当平行核心层扩写
- 继续把 `tasks/` 与根级 `artifacts/` 双轨并行做大
- 继续在当前结构上扩复杂 plugin 方案

## 重构原则

### 原则 1：规则只能有一个正式入口

正式执行法典只能认 `specs/`。

### 原则 2：固定逻辑只能有一个正式承载层

固定逻辑只能逐步归到 `packages/`。

### 原则 3：项目真相只能有一个正式落点

项目输入、过程产物、最终产物都应尽量收在 `projects/` 内。

### 原则 4：两个业务阶段保持绝对清晰

项目主线只保留：

- 业务蓝图
- 体验蓝图

其他都视为执行步骤，不另立业务阶段。

### 原则 5：平台能力只能增强，不能主导

`skills/`、未来的 `plugins/` 都不能成为主线唯一入口。

## 分阶段迁移方案

### Phase A：架构收口

目标：

- 确认 `specs / packages / projects / knowledge / templates / docs` 为目标结构

动作：

- 停止继续新增 `docs/sdd/` 型正式规则
- 停止继续扩张 `tasks/ + artifacts/` 双根结构
- 以本方案作为后续迁移依据

### Phase B：执行层改名与收敛

目标：

- 把 `scripts/` 和 `checks/` 开始收敛到 `packages/`

动作：

- 新建 `packages/`
- 把现有稳定脚本按职责重组
- 先保留兼容入口，不立即删除旧脚本

### Phase C：项目层统一

目标：

- 把 `tasks/` 与根级 `artifacts/` 合并为 `projects/`

动作：

- 定义项目目录最小结构
- 迁移当前任务目录
- 迁移归档目录到项目内部

### Phase D：规则层收口

目标：

- 让 `specs/` 成为唯一正式规则真源

动作：

- 把仍留在 `docs/sdd/` 中的执行规则迁入 `specs/`
- `docs/` 只保留解释与讨论

### Phase E：平台层降级

目标：

- 把 `skills/` 彻底降级为平台适配层

动作：

- skill 不再定义主规则
- skill 只负责“如何在当前平台上调用 packages”

## 我对本项目的最终建议

本项目可以按这种架构优化，而且这样会比当前状态更合适。

原因是：

- 你的业务阶段天然很少，适合收敛
- 你不想做重后端或重 App，更需要目录级真相与轻执行中枢
- 你最终是希望“别的设计师在别的 AI 工具里也能用”，这更需要稳定分层，而不是更多平台特定机制

## 当前结论

本项目的目标架构建议正式收敛为：

- `specs/`：规则法典
- `packages/`：执行中枢
- `projects/`：项目真相
- `knowledge/`：共享知识真源
- `templates/`：共享模板
- `docs/`：解释与讨论

## 下一步

如果采纳本方案，后续第一步不应该继续零碎补规则，而应该直接开始：

1. 建立 `packages/` 目录骨架
2. 设计 `projects/` 目录最小结构
3. 输出“当前目录 -> 目标目录”的迁移清单
