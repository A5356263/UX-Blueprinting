## 本轮目标

在不迁移现有数据的前提下，先搭出目标结构骨架，并明确“当前目录 -> 目标目录”的迁移清单。

本轮只做两件事：

1. 建立 `packages/` 与 `projects/` 骨架
2. 输出正式迁移清单

## 已建立的目录骨架

### `packages/`

已建立：

- `packages/README.md`
- `packages/task_bootstrap/`
- `packages/task_card_resolve/`
- `packages/context_assemble/`
- `packages/validate/`
- `packages/archive/`

当前定位：

- 仅作为执行中枢目标结构
- 暂不替换现有 `scripts/`

### `projects/`

已建立：

- `projects/README.md`
- `projects/_template/`

模板内已建立：

- `source/`
- `workspace/`
- `runtime/`
- `exports/`
- `meta.json`

当前定位：

- 仅作为项目真相目标结构
- 暂不替换现有 `tasks/` 与根级 `artifacts/`

## 当前目录到目标目录的迁移清单

### 1. 规则层

- `specs/` -> `specs/`
  - 保留为正式规则法典入口
  - 后续继续增强

- `docs/sdd/` -> `docs/`
  - 目标是弱化为解释性文档
  - 其中真正的执行规则后续迁入 `specs/`

### 2. 执行层

- `scripts/new_task.py` -> `packages/task_bootstrap/`
- `scripts/assemble_context.py` -> `packages/context_assemble/`
- `scripts/validate_outputs.py` -> `packages/validate/`
- `scripts/coverage_check.py` -> `packages/validate/`
- 未来归档脚本 -> `packages/archive/`

迁移原则：

- 先复制并重组职责
- 再保留兼容入口
- 最后再逐步废弃旧脚本入口

### 3. 检查层

- `checks/` -> `packages/validate/` 的内部规则依赖

迁移原则：

- 不再把 `checks/` 视为平行执行层
- 后续只作为校验规则输入存在

### 4. 项目层

- `tasks/active/<task-id>/task_card.md` -> `projects/<project-id>/source/task_card.md`
- `tasks/active/<task-id>/inputs/requirement.md` -> `projects/<project-id>/source/requirement.md`

- `tasks/active/<task-id>/workspace/facts.md` -> `projects/<project-id>/workspace/facts.md`

## 当前仓库的第一批实际迁移对象

建议先以 `demo-permission-v1` 为首个迁移试点。

对应关系：

- `tasks/active/demo-permission-v1/` -> `projects/demo-permission-v1/`
- `artifacts/demo-permission-v1/` -> `projects/demo-permission-v1/exports/` 与 `runtime/`

## 建议迁移顺序

1. 先迁执行层：`scripts/` -> `packages/`
2. 再迁项目层：`tasks/` + `artifacts/` -> `projects/`
3. 最后收口规则层：`docs/sdd/` 中执行规则 -> `specs/`

## 当前边界

本轮不做以下动作：

- 不移动现有 `tasks/` 数据
- 不移动现有根级 `artifacts/` 数据
- 不删除现有 `scripts/`
- 不删除现有 `checks/`
- 不修改 `knowledge/` 目录结构

## 下一步

如果沿本方案继续，下一步最合适的是：

1. 开始把 `scripts/` 逻辑映射到 `packages/`
2. 选 `demo-permission-v1` 做首个 `projects/` 迁移试点
