# 体验蓝图预览功能 V2 正式规范

- 文档状态：正式规范
- 版本：V2.0
- 适用范围：`Experience Preview` 能力的第二阶段优化
- 文档目标：在不改变主链路定位的前提下，明确预览层第二阶段必须完成的聚合、流程、展示与验收要求，使 Code Agent 可直接按本规范实施。

---

## 1. 文档定位

本规范是对现有预览层合同的 V2 优化补充与执行收敛文档。

本规范不重写预览层的基础定位，以下基础约束继续有效：

- 预览层是正式体验蓝图的只读派生扩展层
- 预览层不属于主链路正式产物
- 预览层不参与正式 Gate / Validate
- 预览层不回写正式体验蓝图
- 预览层在主链路完成后执行
- 预览层运行产物继续落在 `projects/<project-id>/runtime/preview/`
- 预览服务可访问后，仍必须输出完整本地 URL

V2 的任务不是改定位，而是修正 V1 的信息组织方式，使预览层从“能运行”提升到“能准确还原体验蓝图”。

---

## 2. V2 要解决的核心问题

V2 必须解决以下问题：

1. 当前预览模型不是以 `page_id` 为中心聚合全文信息，而是以章节片段和模糊匹配为主，导致大量页面信息没有被挂到正确页面下。
2. 当前全局流程图按页面顺序串联，无法表达按角色、按链路、按依赖关系的真实体验流。
3. 当前渲染层存在重复表达，例如页面标题与页面 ID 在同名时重复展示。
4. 当前“全局说明”语义过于宽泛，成为兜底信息池，无法让人快速理解哪些是全局原则、哪些是全局依赖、哪些是开放问题、哪些是缺口。
5. 当前开放问题与缺口虽然有局部展示，但没有稳定、完整地恢复蓝图中的原始信息。
6. 当前页面卡中的大量“无直接项”与默认降级提示喧宾夺主，削弱了体验蓝图预览的阅读价值。

---

## 3. V2 范围与非目标

### 3.1 本次必须完成

本次 V2 必须完成以下三类工作：

#### A. 重构数据聚合逻辑

- 以 `page_id` 为中心聚合全文信息
- 以 `flow_id + role` 重构全局流程图
- 不再按原 Markdown 章节顺序直接渲染

#### B. 补齐展示缺口

- 去掉重复文案与重复标识
- 补开放问题与缺口
- 明确全局说明的拆分方式

#### C. 保持运行合同不变

- 继续通过现有命令入口执行
- 继续产出 `runtime/preview/` 下的静态文件和运行信息
- 继续在聊天窗口输出本地预览地址

### 3.2 本次明确不做

以下内容不属于本次 V2 必做范围：

- 页面大布局语义增强，例如 topbar、sider、左中右分栏
- 高保真或低保真视觉优化
- 组件级草图精细化
- 交互状态模拟
- 对主链路正式体验蓝图合同的改写

说明：页面大布局语义是后续阶段能力，不是本次 V2 的阻断项。

---

## 4. V2 目标定义

V2 完成后，预览层必须达到以下目标：

1. 页面预览卡以页面为中心，而不是以章节为中心。
2. 一个页面在蓝图中涉及的所有信息，必须尽可能完整地被聚合到该页面卡下。
3. 全局流程总览必须表达“谁在做、属于哪条链路、是否依赖其他链路、哪些节点存在阻断或回退”。
4. 页面卡不得出现明显重复表达。
5. 开放问题与缺口必须可见，且分清页面级与全局级。
6. 全局说明必须拆分为明确语义区，而不是保留一个宽泛的“全局说明”信息池。

---

## 5. 基础运行合同

V2 继续沿用现有运行合同，不另起第二套目录与入口。

### 5.1 输入

预览层标准输入继续为：

1. `projects/<project-id>/exports/final/experience_blueprint.md`
2. `projects/<project-id>/workspace/experience_blueprint.md`

优先读取 `exports/final/experience_blueprint.md`，仅在归档版不存在时允许降级读取 `workspace/experience_blueprint.md`。

### 5.2 输出

运行产物继续落在：

```text
projects/<project-id>/runtime/preview/
```

最小输出集合继续为：

```text
projects/<project-id>/runtime/preview/index.html
projects/<project-id>/runtime/preview/assets/style.css
projects/<project-id>/runtime/preview/preview_model.json
projects/<project-id>/runtime/preview/preview_runtime.json
projects/<project-id>/runtime/preview/preview_build_log.md
```

### 5.3 地址输出

服务可访问后，聊天窗口或命令输出必须明确给出：

```text

http://127.0.0.1:<port>/
```

不得仅输出路径、目录、端口号或“服务已启动”。

## 6. V2 中间模型合同

V2 不再使用仅由 `global_notes[]` 兜底的信息结构。

### 6.1 顶层模型

V2 预览模型应升级为：

```text
preview_document_v2
- project_id
- meta
- global_flow
- page_views[]
- global_context
- unresolved_items[]
- source_refs[]
```

### 6.2 global_flow 结构

`global_flow` 必须至少包含：

```text
global_flow
- lanes[]
- chains[]
- nodes[]
- edges[]
- dependencies[]
- blockers[]
```

约束如下：

- `lanes[]`：按角色分泳道，最小粒度是角色，不允许只保留“全部节点一排串联”的单行流。
- `chains[]`：按 `flow_id` 或等价任务流分链路。
- `nodes[]`：节点必须保留 `node_id / name / type / role / chain_id / goal`。
- `edges[]`：边必须保留 `from / to / path_type / label / role / chain_id`。
- `dependencies[]`：用于表达一条链路依赖另一条链路，而不是把所有节点画成单根主线。
- `blockers[]`：用于表达流程级阻断，不允许只在页面卡里出现而流程总览中完全缺失。

### 6.3 page_views 结构

`page_views[]` 中每一项必须至少包含：

```text
page_view
- page_id
- view_name
- view_type
- roles[]
- summary
- entry
- exit
- upstream_links[]
- downstream_links[]
- sketch_blocks[]
- key_understanding[]
- states[]
- copy_items[]
- risks[]
- blockers[]
- principles[]
- design_patterns[]
- trace_items[]
- open_items[]
- gap_items[]
- source_refs[]
```

约束如下：

- `page_id` 是页面聚合的主键。
- `view_name` 只负责对人显示，不承担唯一标识。
- `roles[]` 表示该页面面向的角色集合。
- `entry / exit / upstream_links / downstream_links` 必须优先从正式蓝图抽取，不允许完全缺席。
- `design_patterns[]` 用于承接“设计模式、承载模式、页面类型判断”等信息。
- `source_refs[]` 必须保留来源章节或来源对象，便于排查聚合结果。

### 6.4 global_context 结构

V2 禁止再用一个宽泛的 `global_notes[]` 承接所有未归属信息。

必须拆分为：

```text
global_context
- principles[]
- dependencies[]
- risks[]
- open_questions[]
- gaps[]
- notes[]
```

约束如下：

- `principles[]`：只放全局原则，不放页面级原则。
- `dependencies[]`：只放跨页面或跨链路依赖，不放局部跳转。
- `risks[]`：只放无法稳定归属到单页面的全局风险。
- `open_questions[]`：只放全局开放问题。
- `gaps[]`：只放全局缺口。
- `notes[]`：仅作为最后兜底项，且必须有明确类型说明。

## 7. V2 聚合规则

### 7.1 总原则

预览层必须先做全文语义聚合，再做展示渲染。

禁止做法：

- 直接按 Markdown 章节顺序输出页面内容
- 先渲染页面，再靠样式弥补信息结构问题
- 只扫少数几个章节就认定页面信息已完整

### 7.2 聚合主键

V2 页面聚合的主键必须是 `page_id`。

允许以下降级匹配顺序：

1. 精确 `page_id`
2. 精确页面名称
3. 页面别名
4. 页面名称归一化匹配
5. 模糊匹配

其中：

- 只要能稳定命中 `page_id`，就不得再降级到模糊匹配。
- 模糊匹配只能作为最后手段，不得成为主聚合逻辑。

### 7.3 全文扫描对象

V2 必须扫描整个体验蓝图，而不是只扫描固定少数章节。

至少应覆盖以下内容来源：

- 信息架构总览
- 任务流蓝图
- 页面 / 窗口清单
- 关键页面蓝图
- 区块布局示意
- 内容与信息优先级合同
- 状态与反馈矩阵
- 文案合同
- 风险、疑惑点与保护策略
- 开放问题与缺口
- 体验追踪映射
- 其他出现 `page_id / flow_id / principle_id / copy_id / risk_id / trace_id` 的章节

### 7.4 页面绑定规则

页面绑定分为三类：

#### A. 强绑定

以下内容只要出现明确 `page_id`，必须直接挂到对应页面：

- 页面摘要
- 页面目标
- 首屏必须理解
- 决策必需信息
- 区块布局示意
- 页面级状态
- 页面级文案
- 页面级风险
- 页面级原则
- 页面级追踪映射
- 页面级开放问题
- 页面级缺口

#### B. 弱绑定

以下内容若无明确 `page_id`，允许根据 `view_name / alias / flow context` 绑定到最近相关页面：

- 与页面目标强相关但未写 `page_id` 的状态
- 与页面操作强相关但未写 `page_id` 的文案
- 与页面误解点强相关但未写 `page_id` 的风险

#### C. 全局归属

若某条内容无法稳定归属到页面，必须进入 `global_context` 或 `unresolved_items`，不得硬塞进任意页面。

### 7.5 流程绑定规则

流程图必须以 `flow_id + role` 为核心组织方式。

#### 必须要求

- 同一 `flow_id` 可包含多个节点
- 同一角色可拥有多条链路
- 同一页面可在多条链路中重复出现，但节点实例必须区分链路上下文
- 允许出现依赖链路，不得强行串成单根主线

#### 至少支持的链路类型

- 主成功链路
- 辅助链路
- 依赖链路
- 阻断链路
- 回退链路

### 7.6 开放问题与缺口规则

V2 必须区分：

- 页面级开放问题 / 缺口
- 全局开放问题 / 缺口
- 解析时新增的技术性待确认项

约束如下：

- 蓝图原文中的开放问题与缺口优先级高于渲染器自动生成的降级提示。
- 自动生成的缺口提示只能作为补充，不得覆盖原始开放问题与缺口。
- 页面卡的“开放问题 / 缺口”区域必须优先展示蓝图原始项，再展示解析降级项。

## 8. V2 渲染规则

### 8.1 页面卡固定顺序

每张页面卡必须按以下固定顺序渲染：

1. 页面摘要
2. 线框草图
3. 关键理解
4. 状态
5. 文案
6. 风险与阻断
7. 原则、设计模式与追踪
8. 开放问题 / 缺口
9. 来源说明（可折叠）

说明：第 9 项为 V2 新增建议项，用于排查页面聚合来源。

### 8.2 去重规则

V2 必须实现页面内去重。

至少包含以下规则：

1. 若 `page_id == view_name`，不得再单独输出一行重复 ID。
2. 若 `summary` 与标题语义完全相同，不再重复输出同句摘要。
3. 同一条文案若已在文案区展示，不得再以完全相同的文句重复出现在摘要区。
4. 同一条开放问题或缺口不得在页面区和全局区重复各展示一次；若同时存在页面级与全局级版本，必须明确区分。
5. 自动降级提示不得重复堆叠输出。

### 8.3 页面卡空状态规则

V2 允许空状态，但必须克制。

要求如下：

- 只有在该字段经过全文扫描后仍无稳定结果时，才允许显示“无直接项”。
- 不得默认给每个页面批量塞入技术性降级提示。
- 技术性提示应放在“来源说明”或“待人工确认”中，不得压过蓝图原文内容。

### 8.4 全局区块拆分规则

V2 禁止继续保留单一的“全局说明”大杂烩区块。

应拆为以下明确区块：

1. 全局流程总览
2. 全局原则
3. 全局依赖 / 前提
4. 全局风险
5. 全局开放问题
6. 全局缺口
7. 待人工确认

只有无法归入以上任一区块的少量残留项，才允许进入 `global_context.notes[]`。

### 8.5 全局流程展示规则

V2 全局流程总览必须满足：

- 先按角色分泳道
- 再按链路分组
- 链路之间允许通过依赖线连接
- 阻断 / 回退 / 依赖必须有明确边类型
- 不得把所有页面仅按出现顺序串成一根线

### 8.6 预览模型原文展示规则

V1 中直接在页面末尾大段输出完整 `preview_model.json` 的方式，不再作为默认主展示。

V2 要求：

- `preview_model.json` 仍继续落盘
- 页面中默认不展示整段 JSON
- 如需保留调试信息，必须折叠到“调试信息”区域，默认收起

## 9. V2 降级与失败隔离

### 9.1 降级原则

当信息不足时，允许降级，但必须遵守：

- 先保留原始信息
- 再补技术性缺口说明
- 不得用技术性占位内容覆盖原始蓝图语义
- 不得伪造页面内容、流程关系或文案内容

### 9.2 无法稳定归属时的处理顺序

1. 尝试 `page_id` 精确归属
2. 尝试页面名 / 别名归属
3. 尝试 flow context 归属
4. 归入 `global_context`
5. 仍无法归属则进入 `unresolved_items`

### 9.3 失败隔离

V2 继续遵守失败隔离原则：

- 主链路正式产物不受影响
- 预览层失败不得表述成主链路失败
- 不得输出不可访问的伪地址

## 10. 实施改造要求

V2 实施时，至少应调整以下文件：

```text
specs/14_experience_preview_contract.md
packages/experience_preview/build_preview_model.py
packages/experience_preview/render_html.py
projects/<project-id>/runtime/preview/preview_model.json
projects/<project-id>/runtime/preview/index.html
```

说明：

- `specs/14_experience_preview_contract.md` 用于同步 V2 的中间模型和展示规则
- `build_preview_model.py` 负责从“章节抽取”升级为“页面中心全文聚合”
- `render_html.py` 负责从“顺序渲染”升级为“角色流程 + 页面中心渲染 + 去重展示”

## 11. 验收标准

满足以下条件，方可判定 V2 完成：

### 11.1 数据聚合验收

- `page_views[]` 中每个页面都以 `page_id` 为主键
- 蓝图中与某页面明确相关的状态、文案、风险、原则、追踪、开放问题、缺口，能稳定挂到该页面下
- 不再只依赖少数章节构建页面卡

### 11.2 流程图验收

- 全局流程总览按角色分泳道
- 至少能表达两条以上链路
- 能表达依赖链路
- 不再是简单单线串联页面

### 11.3 展示层验收

- 页面标题与页面 ID 不重复
- 页面摘要不重复标题语义
- 页面内文案、开放问题、缺口可见
- 全局区块已拆分，不再只保留“全局说明”
- 默认页面不再直接展示整段 JSON

### 11.4 运行层验收

- 仍可通过既有入口执行
- 仍产出 `runtime/preview/` 最小文件集合
- 仍能输出本地预览地址
- 预览层失败不会影响主链路正式产物

---

## 12. 对 Code Agent 的执行指令

Code Agent 在执行本规范时，必须遵守以下顺序：

1. 先保持现有运行入口、输出目录与地址输出合同不变。
2. 先修改 `build_preview_model.py`，完成页面中心全文聚合与流程模型重建。
3. 再修改 `render_html.py`，完成全局区块拆分、页面卡去重和默认 JSON 收起。
4. 最后用真实项目重新生成 `preview_model.json` 与 `index.html`，对照本规范验收。

禁止：

- 只改样式，不改聚合模型
- 只改 HTML，不改中间模型
- 用更多默认占位内容掩盖聚合失败
- 把本次 V2 目标扩散为页面大布局语义重构

---

## 13. 一句话结论

V2 的本质不是“继续美化预览页”，而是把预览层从“章节顺序渲染器”升级为“页面中心 + 角色流程中心”的体验蓝图还原器。
