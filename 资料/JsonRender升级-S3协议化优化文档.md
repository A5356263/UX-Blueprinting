# JsonRender 升级-S3协议化优化文档

## 0. 文档定位
这份文档只解决一件事：
把 `S3` 从“偏 tree 的设计文档助手”，升级成“面向新协议输出页面关系信息的产品经理层”。

它服务的不是单独的文档优化，而是整个 JsonRender 协议迁移能否真正完成。

---

## 1. 当前已确认结论

### 1.1 S3 属于本次升级范围
如果目标只是“新 renderer 能跑”，S3 可以后置。
如果目标是“真正的升级完成”，S3 不能后置。

原因很直接：
- 新协议真正消费的是页面关系、状态、交互，不是旧 tree 施工图
- 如果 S3 不改，S4 仍然要大量靠兼容层、修补层和猜测逻辑
- 那样只能算运行时升级了，不能算整条链路升级完成了

### 1.2 S3 的新定位
S3 不再是：
- tree 施工图助手
- 帮后面拼最终容器层级的文档整理器

S3 更应该是：
- 产品经理层
- 页面信息架构层
- 面向新协议的统一上游输出层

一句话：
S3 以后重点不是“把页面一层层拼出来”，而是“把页面关系讲清楚”。

### 1.3 第一阶段先收缩范围
当前阶段不做大而全拆分，先按下面的方式收口：
- 纯文本输入：直接进入产品经理层
- 带图输入：先走图解析 Agent，再交给产品经理层
- 产品经理层：统一整合文本目标与图片事实，再输出给 S4

当前不单独拆文本 Agent。
这是为了先把主链路做稳，避免上下文和任务边界继续膨胀。

### 1.4 S2 当前保持独立
S2 当前仍然是独立 Agent。
它可以作为上游业务理解能力，但不在这一轮和产品经理层强行合并重构。

### 1.5 route / 预处理 / skills 的边界
- skills 适合沉淀规则、预处理策略、输入归一策略、产品调性规则
- route 负责真实线上编排：判断输入、调用谁、把结果交给谁

所以当前方向不是“skills 代替 route”，而是“skills 管规则，route 管编排”。

---

## 2. 为什么 S3 必须协议化
旧链路的主要问题不是文档不能写，而是：
- S3 输出长期偏向旧 tree 思维
- S4 长期被迫承担过多理解和修补责任
- children 放错、层级挂错、容器关系不稳，都会被放大

新协议下，真正要稳定的不是“完整最终树”，而是：
- 页面骨架
- 区域归属
- 模块职责
- 状态
- 交互

所以 S3 的协议化，本质上是在把“关系信息”提前说明白。

---

## 3. 新协议下 S3 的职责
S3 最终要交付给 S4 的，不是最终代码，也不是最终 tree，而是可稳定消费的页面说明。

### 3.1 必须输出的信息
1. 页面骨架
- 这是后台页、工作台页、列表页、表单页还是详情页
- 页面是 `header_sider_content`、双列工作区、单列流式页，还是浮层承载页

2. 区域归属
- 哪些模块属于顶部
- 哪些模块属于左侧
- 哪些模块属于右侧
- 哪些模块属于内容区
- 哪些模块属于工具区、筛选区、详情区

3. 模块职责
- 模块是什么
- 模块做什么
- 模块属于哪里
- 模块的关键内容和关键动作是什么

4. 表单与数据展示要求
- 表单有哪些字段、校验、默认值、选项
- 表格有哪些列、操作列、分页要求
- 树/菜单有哪些层级和默认选中要求

5. 浮层与附加承载
- Modal / Drawer / Dropdown / Popover 等
- 触发源是什么
- 内容职责是什么
- 底部操作和关闭方式是什么

6. 页面状态
- 当前上下文状态
- 当前选中态
- 弹层开关状态
- 当前详情对象
- 当前筛选/切换状态

7. 交互规则
- 谁触发什么动作
- 影响哪个目标
- 用户看到什么反馈
- 成功后结果是什么

8. GAP
- 信息不明确时必须显式标记，不允许假装确定

### 3.2 不再重点输出的信息
S3 以后不再重点强调：
- `Layout > Header > Content > children...` 这种施工图级层级
- 最终每一层容器到底是 `Row / Col / Flex / div`
- 每个节点如何深层嵌套到最终 tree
- 设计软件级别的样式施工细节

一句话：
少写“怎么一层层拼”，多写“页面由哪些关系组成”。

---

## 4. 输入架构

### 4.1 第一阶段目标架构
1. 纯文本输入
- 直接交给产品经理层

2. 带图输入
- 先由图解析 Agent 提取：页面骨架、区域关系、模块位置、布局对齐事实
- 再交给产品经理层

3. 产品经理层
- 统一整合文本目标与图片事实
- 输出面向 S4 的页面说明

4. S4 / JSONAgent
- 只吃这一份统一上游

### 4.2 长期方向
长期最合理的结构不是“文本一路、图片一路、S4 硬接两路”，而是：
- 多种输入先汇总成统一的产品经理层输出
- S4 只面对一种输入契约

也就是说：
图解析不会消失，但它更适合作为统一上游的一种输入能力，而不是长期独立主链路。

---

## 5. S3 输出契约
当前目标不是直接输出 JSON，而是先输出 Markdown 版页面说明，并在第 10 章给 S4 一份稳定摘要。

### 5.1 当前约定的关键字段
第 10 章必须包含：
- `page_id`
- `page_name`
- `flow_pattern`
- `page_shell_specs`
- `region_specs`
- `module_specs`
- `form_specs`
- `overlays`
- `state_specs`
- `interaction_specs`
- `不得擅自补全项`

### 5.2 当前约定的输出格式
第 10 章必须使用固定的 Markdown Key-List 结构：
- 字段名必须使用英文
- 字段名后必须使用半角 `:`
- 复合列表必须使用包装项，例如：
  - `region`
  - `module`
  - `form`
  - `overlay`
  - `state`
  - `interaction`

这样做的目的只有一个：
让 S4 能稳定抽取摘要，而不是继续对整篇文档做自由理解。

---

## 6. S3 需要改什么

### 6.1 改大脑定位
从：
- 设计文档整理器
- tree 施工图辅助器

改成：
- 产品经理层
- 页面关系定义层
- 面向协议输出的统一上游

### 6.2 改提示词
提示词重点从：
- 容器
- 层级
- children
- 最终 tree

改成：
- 页面骨架
- 区域归属
- 模块职责
- 状态
- 交互
- GAP

### 6.3 改 route
route 不应只是转发文本，而应承担：
- 输入归一
- 多来源信息装配
- 最小结构补齐
- 输出校验
- 面向 S4 的交接口径统一

### 6.4 改输出契约
S3 的目标输出不是“自由描述型 markdown”，而是“可被 S4 稳定抽取摘要的 markdown”。

## 7. 当前实现进展
这部分是已经落地到代码里的，不是纯讨论。

1. `S3 route` 已支持两种输入方式
- 传统 `messages`
- 第一阶段 `structured_input`

2. `structured_input` 已支持统一装配
- 纯文本需求
- 业务蓝图
- 图片解析事实
- 图片补充说明

3. 当前页面内的 `S2 -> S3` 已改为结构化传入
- 不再把整段业务输出直接塞进 message
- 改为通过 `structured_input.business_blueprint` 传入

4. `S3 prompt` 已切换为产品经理层模式
- 重点输出页面骨架、区域归属、模块职责、状态、交互
- 不再把 tree 施工图作为主目标

5. S3 第 10 章摘要解析已落地
- 当前已能从设计文档中提取 `page_id / flow_pattern / page_shell_specs / region_specs / module_specs / form_specs / overlays / state_specs / interaction_specs`
- 并归一为 `design_doc_summary`

6. 页面侧 `S3 -> S4` 已开始同时传递两份内容
- `design_doc`
- `design_doc_summary`

7. `/api/json` 在 `upstream_source=s3` 时会自动补齐摘要
这意味着：
- 页面调用可以用
- 直接 API 调用也开始具备相同口径

8. 当前 S4 的口径已经开始变化
- 优先消费 `design_doc_summary`
- 原始 `design_doc` 只作为补充说明

9. 已经对 S3 文档做了一次减负
- 进入 S4 前会裁掉第 11 章“存档说明”
- 目的是减少无关长文本对 S4 的干扰

10. 当前 `next build` 已通过
- 说明本轮 S3 协议化改造没有打断主工程编译

---

## 8. 当前主阻断
当前最大的剩余问题，不再是运行时接不上，而是：
`S3 DesignDoc -> S4 (Migration Spec)` 这一跳还不稳定。

目前已确认：
- `S3 DesignDoc` 本身已经能真实跑通
- `S1.5 -> S4 (Migration Spec)` 也已通过
- 当前主阻断收敛在 `S3` 产物交给 `S4` 后的真实生成稳定性

这意味着：
- S3 已经不是“完全没改好”
- 但还没达到“可以放心切默认”的程度

---

## 9. 下一步最合理的工作
接下来不应该再泛化扩范围，而应该盯住这一跳继续收敛：

1. 继续缩短和净化 S3 下发给 S4 的内容
- 让 S4 更依赖 `design_doc_summary`
- 让原始 `design_doc` 更像补充材料，而不是主输入

2. 继续增强第 10 章摘要的稳定性
- 保证字段完整
- 保证格式固定
- 保证易解析

3. 继续跑真实验证
- 不再用“旧测试口径”误判 S3
- 持续验证真实的 `S3 -> S4` 主链路

4. 当前不扩大范围去拆文本 Agent
- 先把产品经理层主链路做稳
- 再决定是否单独拆文本理解层

---

## 10. 一句话结论
S3 当前已经进入“协议化改造实装阶段”，不再只是讨论阶段。
接下来最核心的任务，不是继续解释 S3 应该是什么，而是把 `S3 DesignDoc -> S4` 这一跳真正跑稳。
