# JsonRender 稳定升级任务规划文档

## 0. 文档定位
这份文档是本次 JsonRender 协议迁移的总台账。
它不是一次性说明文档，而是后续每次优化后都要继续更新的执行文档。

当前目标只有一个：
在不出现重大错误的前提下，把 JsonRender 升级真正做完，而不是只把运行时接起来。

---

## 1. 当前事实与已确认决策

### 1.1 当前项目现状
当前项目核心依赖：
- `@json-render/core`: `0.3.0`
- `@json-render/react`: `0.2.0`
- `react`: `19.2.3`

当前升级目标：
- `@json-render/core`: `0.14.0`
- `@json-render/react`: `0.14.0`
- `react`: `19.2.4`

### 1.2 当前路线已确认
已确认本次升级不是“兼容升包”，而是“协议迁移”。

这意味着：
- 不是只改依赖版本
- 不是只改 renderer 接法
- 而是要把整条链路从旧 tree / ProtoJSON 思维，迁到更适合新协议的方式

### 1.3 旧数据策略已确认
- 不背旧数据
- 不以历史旧 JSON 兼容为目标
- 迁移后的系统以新协议为干净目标

### 1.4 离线页与离线导出策略已确认
- `/offline`
- `/offline-export`

这两条链路必须与主预览同批迁移，不能后补。

### 1.5 验收样例策略已确认
当前已确认两层样例：
1. 默认技术样例
- 双列表单页
- 用于技术基线验收

2. 真实业务样例
- `S3-S4可测试1.md`
- 已作为真实业务样本纳入验证

### 1.6 阻断项策略已确认
- 升级期间必须维护阻断项清单
- 不允许在阻断项未清零时直接切默认版本

## 2. 总目标
本次升级的总目标不是“文档写完”或“页面能显示”，而是：
新协议已跑通，关键链路已验证，阻断项已清零，回滚方案已确认，可在可控风险下切默认版本。

### 2.1 业务目标
1. `S3 -> S4` 可稳定生成
2. `S1.5 -> S4` 可稳定生成
3. 主预览、离线页、离线导出三条链路尽量共用同一协议
4. 关键交互可用
5. 后续输入文本、图片、文档+图片时，长期能归到统一的产品经理层收口

### 2.2 技术目标
1. 新版 JsonRender 运行时接通
2. 新协议 `spec_draft` 可被稳定消费
3. 旧协议不再是唯一主路径
4. 主预览、`/offline`、`/offline-export` 均可承接新协议
5. 维持回滚能力，直到默认切换验证完成

## 3. 完工、试点、上线定义

### 3.1 完工定义
“完工”表示迁移工作本身已完成，新协议、新运行时和主链路已接通，具备进入试点验证的条件。

至少满足以下条件：
- 影响面清单、样例库、阻断项清单已完成
- breaking change 清单已完成
- 新版目标 spec、动作规则、状态规则已定稿
- 旧协议到新协议的映射规则已定稿
- 新版运行时 PoC 已跑通
- S4 输出协议、预检、修复逻辑已切到新协议
- 主预览页、组件注册预览页已跑通
- 离线页、离线导出页已跑通，且与主预览同批完成
- 任务文档与进度台账已同步到可交付状态

补充：
完工不等于允许切默认版本，只代表迁移实施完成并具备试点条件。

### 3.2 试点通过定义
“试点通过”表示新链路已经具备小范围真实验证价值，但暂不直接切默认版本。

建议至少满足以下条件：
- 默认双列表单样本全链路通过
- 主预览页可用
- 离线页可用
- 离线导出页可用
- 新协议输出可稳定通过预检
- 至少 1 个真实业务样本跑通
- 无阻断级问题未处理

### 3.3 上线定义
“上线”表示关键链路验证通过，阻断项已清零，回滚方案已确认，可放心切为默认版本。

至少满足以下条件：
- `S3 -> S4` 可用
- `S1.5 -> S4` 可用
- 主预览页可用
- 离线页可用
- 离线导出页可用
- 关键交互可用，至少包含 `Modal`、`Drawer`、`Dropdown`、`Table`、`Form`
- 默认双列表单样本全链路通过
- 新协议输出可稳定通过预检
- 无阻断级问题未处理
- 回滚方案已准备并验证通过

## 4. 目标架构

### 4.1 旧思路
旧思路更像：
- 上游尽量把页面写成完整 tree
- JSONAgent 尽量一次性拼最终结构
- 后面通过大量修补和兼容逻辑兜底

### 4.2 新思路
新思路更像：
- 上游先输出页面关系说明
- JSONAgent 按新协议生成结构化页面协议
- JsonRender 作为运行时执行协议

### 4.3 多 Agent 长期方向
长期更合理的结构是：
- 不同输入由不同 Agent 分工处理
- 文本、图片、文档+图的理解先分开
- 最后统一交给产品经理层整合
- 产品经理层作为唯一直接上游交给 S4

当前第一阶段先收缩范围：
- 纯文本：直接进产品经理层
- 带图：先走图解析 Agent，再交给产品经理层
- `S2` 当前保持独立，不在本轮和产品经理层强合并

- 把所有上游 Agent 在本轮全部拆细
- 保留历史旧 JSON 的完整兼容回放能力
- 在没有验证前直接删光旧兜底逻辑

## 6. 核心风险

### 6.1 架构风险
- 旧 tree 依赖点太多
- 旧 interactions 与新协议表达方式不一致
- 旧预检、修复、离线导出、编辑器逻辑绑定旧结构

### 6.2 业务风险
- 页面能显示但行为不对
- 主预览正常但离线页或导出页坏掉
- 动态注册组件或 slot 结构在迁移中失真

### 6.3 生成链路风险
- S4 仍然依赖过多猜测
- S3 输出结构不稳定
- 旧测试口径误导新链路判断

### 6.4 过程风险
- 任务太长，容易忘记前面做过的事
- 如果不持续维护台账，后续判断会失真

---

## 7. 迁移原则
1. 稳定优先，不为追求“原生纯净”而提前砍掉安全垫
2. 先建立样本和基线，再切主链路
3. 先双轨并行，再默认切换
4. 先保证主预览、离线页、导出三链路一致，再谈上线
5. 业务门禁、预检、幻觉防御不能因为升级而默认删除
6. 每做完一轮优化，都要回写文档台账

---

## 8. 分阶段规划

### Phase 0：基线与样本
目标：把判断标准先立住。

已做：
- 影响面清单
- breaking change 清单 v1
- 默认双列表单样本
- 真实业务样本 `S3-S4可测试1.md`
- 三链路回归清单

### Phase 1：新运行时 PoC
目标：证明新 JsonRender 运行时可独立工作。

已做：
- 双版本并行
- 隔离 PoC 页面
- 默认 fixture 跑通

### Phase 2：桥接与主预览接入
目标：主预览开始承接新协议。

已做：
- 旧 `UITree -> Spec` 映射骨架
- bridge registry 承接关键组件
- 主预览与组件注册预览可试渲染

### Phase 3：S4 协议迁移
目标：S4 开始生成新协议。

已做：
- `spec_draft` 并行链路
- 新协议归一化、交互修复、协议预检
- 服务端双协议识别
- 非默认试产出入口

### Phase 4：离线页与导出迁移
目标：三链路同批承接新协议。

已做：
- `/offline` 支持双协议
- `/offline-export` 支持双协议
- 导出 payload 带 `specDraft/outputProtocol`
- 动态 registry 快照带入导出

### Phase 5：技术样本与试点样本回归
目标：不是只搭底座，而是用样本逼出真实缺口。

已做：
- 默认技术样本三链路 smoke
- `customer-approval-workbench`
- `registry-ops-console`
- 动态注册组件、FilterBar、overlay footer 等试点覆盖

### Phase 6：真实业务样本
目标：至少 1 个真实业务样本跑通。

已做：
- `org-member-management` 真实业务样本三链路 smoke 通过

### Phase 7：S3 协议化
目标：让 S3 真正成为新协议的稳定上游。

已做：
- `/api/designdoc` 支持 `structured_input`
- 当前 `S2 -> S3` 改为结构化传入
- S3 prompt 重写为产品经理层模式
- 第 10 章结构化摘要约束
- `design_doc_summary` 解析与注入
- `/api/json` 在 `upstream_source=s3` 时自动补齐摘要
- 进入 S4 前裁掉第 11 章存档说明

当前主攻方向：
- 继续收敛 `S3 DesignDoc -> S4 (Migration Spec)` 这一跳
