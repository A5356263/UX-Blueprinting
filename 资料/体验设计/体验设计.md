1. 0. 快速对齐（摘要）
- 需求目标（1句话）[REQ]：支持员工自行查询和申请权限角色，提交后进入工作流审批，审批通过后系统自动分配权限。
- 核心用户与角色（列点）[REQ]：
    1.  超级管理员：配置和管理“自助申请权限模式”。
    2.  员工：在企业启用“自助申请权限模式”后，可使用“我的权限”查询、使用“申请权限”功能。
- 本次必须支持的“任务闭环”（列 3-8 个）[REQ]：
    1.  超管启用/关闭并配置“自助申请权限模式”。
    2.  员工查询自己已有的权限（功能/数据/角色）。
    3.  员工申请新的功能权限或角色。
    4.  员工查看自己的申请记录及状态。
    5.  员工在审核中状态下撤销申请。
    6.  （系统）对员工提交的申请进行基础校验并触发审批流程。
- 关键约束/互斥/不可做（列点）[REQ]/[KB]：
    1.  “自助申请权限模式”不能与“双管理员互审模式”或“权限变更审批模式”同时开启。[REQ]
    2.  员工仅能申请超管在设置中指定的“应用范围”和“角色范围”。[REQ]
    3.  员工申请功能权限时，默认获得该功能下的所有数据权限。[REQ]
    4.  非资金用户、子管理员模式、特殊身份默认权限、实名要求等场景下，申请特定权限会失败。[REQ]
    5.  存在“应用不可见覆盖个人维度权限”等判定链路，可能影响申请结果的可解释性。[KB] RISK-002, RISK-003
2. 1.1 信息架构放置：新增菜单 vs 嵌入现有模块
- 选项A：“自助申请权限模式设置页”作为独立配置项，置于现有“权限管理模式”相关配置入口。
- 选项B：“自助申请权限模式设置页”嵌入到“应用管理”或“角色管理”的全局设置中。
- 判断依据（仅用 REQ/KB）：
    - [REQ] 功能由超管配置，与“双管理员互审模式”等互斥，属于权限治理范畴。
    - [KB] 权限域入口分区中，“权限管理模式 (Governance)”是独立的入口分区，用于管理变更治理与隔离。自助申请作为一种新的权限授予与变更方式，逻辑上应归于此类。[KB] `permission/30_ia_skeleton.md`
- 推荐：选项A。将“自助申请权限模式”作为“权限管理模式”下的一个子项或同级选项进行配置。
- 取舍与风险：
    - 优势：符合业务语义（治理模式），便于超管理解和统一管理所有权限变更规则。
    - 风险：如果“权限管理模式”入口本身隐蔽或认知负荷高，可能增加发现成本。
- 需要补齐的信息（若有）[GAP]：无。
【追溯依据｜不下发S3】
判断依据详述：需求明确此功能是超管配置的“模式”，且与现有治理模式（双管理员互审、权限变更审批）互斥。根据业务知识库，治理模式是独立的入口分区，用于管理权限变更的流程与边界。因此，将此配置放在治理模式入口下，最能保持概念一致性和可发现性。嵌入应用或角色管理会割裂其作为“全局申请策略”的语义。
【/追溯依据｜不下发S3】
3. 1.2 承载形态：页面 vs 抽屉 vs 弹窗 vs 分步向导
- 选项A：按S1指定——“设置页”为页面，“申请抽屉”为抽屉，“审批流程编辑”为子页，“申请记录”列表待定。
- 选项B：将“申请抽屉”改为独立申请页面。
- 判断依据（信息量/操作可中断/是否高风险/是否需要跨页追踪）：
    - [REQ] S1明确指定“申请权限抽屉”和“表单编辑子页”。
    - [REQ] “我的权限页”是独立页面，申请作为其延伸操作，抽屉能保留上下文（用户正在查看自身权限）。
    - [GAP] “申请记录列表”承载形态未明确。
- 推荐：遵循S1指定：“设置页”(Page)，“申请抽屉”(Drawer)，“编辑子页”(SubPage)。将“申请记录列表”假设为独立页面（Page）或“我的权限页”内的子模块（待确认）。
- 取舍与风险：
    - 优势：抽屉轻量、快速，符合“从某个页面发起一个辅助操作”的交互模式。
    - 风险：若申请时需要选择的内容很多（如大量应用或角色），抽屉空间可能局促。需确保组件在抽屉内体验良好。
- 需要补齐的信息（若有）[GAP]：“申请记录列表”的承载形态（独立页面/子模块）？[见开放问题 J-3]
【追溯依据｜不下发S3】
S1已明确指定了各部分的承载形态，业务方案应首先遵循。抽屉形式能有效保留“我的权限”页面的上下文，符合“识别优于回忆”原则(U-06)。对于申请记录，若为高频查看内容，独立页面更合适；若为低频辅助信息，可作为子模块。此缺口需确认。
【/追溯依据｜不下发S3】
4. 1.3 流程编排：是否分步、如何拆分
- 拆分触发条件（什么时候必须分步）[REQ]/[KB]：
    - 后续步骤强依赖前一步结果。[GAP] 申请抽屉中，“功能权限申请”和“角色申请”是否互斥？根据申请方式（申请角色/申请功能权限）二选一？[REQ] 申请方式在设置页配置，员工申请时是否可见此选择？
    - 存在阶段性的独立提交或校验。[REQ] 无。
    - 一次性、高风险、不可逆任务。[KB] RISK-007 申请权限属于高风险操作，但可被审批流程和撤销动作补救。
- 推荐步骤（只写步骤名 + 每步目的）：
    - 根据原则BFM-01/BFM-02，员工申请权限更可能是一个相对高频、可逆（可撤销）、字段间无强依赖的任务。推荐使用单页表单（抽屉内），而非步骤条向导。
    - 若“申请方式”需要员工选择，则流程为：1. 选择申请类型（功能/角色）→ 2. 选择具体项并填写原因。否则，直接进入选择与填写。
- 风险与补救（如：中断恢复、重复提交）：
    - 中断：抽屉关闭即中断，无暂存。符合轻量操作预期。
    - 重复提交：前端防重（提交后按钮禁用）；后端需校验是否已有相同内容（相同权限/角色）的“审核中”状态申请，若有则提示“已有相同申请在审核中，请勿重复提交”。
【追溯依据｜不下发S3】
依据原则BFM-01（B端专家场景默认非步骤化）和BFM-02（步骤条使用门禁）。员工申请权限，虽非专家但任务相对简单明确，字段少（申请人、申请项、原因），且无强步骤依赖（除非申请类型选择影响后续字段）。因此优先采用单页表单，提升填写和修改效率。撤销申请和审批流程提供了容错机制。
【/追溯依据｜不下发S3】
5. 1.4 反馈与下一步指引策略（状态可见）
- 操作中反馈（加载/处理中/在途）：
    - 提交申请时：抽屉内按钮变为加载态，防止重复点击。
    - 撤销申请时：行内“撤销”按钮变为加载态。
- 操作后反馈（成功/失败/部分成功）：
    - 提交成功：Toast提示“提交成功，申请已进入审批流程”。自动关闭抽屉。
    - 提交失败：根据校验结果（G-校验4/5/6/7/8），在抽屉内对应字段或顶部给出具体错误提示（原因、字数超限、权限冲突等）。
    - 撤销成功：Toast提示“撤销成功”。列表记录状态更新为“已撤销”。
    - 关闭模式失败：弹窗提示“关闭失败”，并说明原因（有待审批申请）。[REQ]
- 下一步指引（下一步去哪/做什么/如何确认生效）：
    - 提交成功后，Toast可附加文案“您可以在【申请记录】中查看进度”。
    - 审批通过后，通过通知告知员工“权限已生效”。
    - 申请记录列表是状态追踪的核心页面。
6. 1.5 信息层级与凸显策略（内容组织）
- 核心信息（必须第一眼看到）：
    - 设置页：“已启用/未启用”状态开关、与现有治理模式的互斥提醒（如存在）。
    - 我的权限页：当前选中的Tab（功能/数据/角色）下的权限清单。
    - 申请抽屉：申请原因输入框、可选择的应用/角色列表。
    - 申请记录列表：申请时间、申请内容、审核状态。
- 次要信息（折叠/二级呈现/详情页承载）：
    - 设置页：“角色范围”和“应用范围”选择后的详情列表（部分角色/应用名称），可收纳或滚动展示。
    - 我的权限页：权限的“来源”信息（根据KB RISK-002，应展示权限来源，但S1未提，属[GAP]）。
    - 申请记录详情抽屉：申请时的静态快照，作为审计追溯。
- 风险信息（需要解释/确认/强调的位置与时机）：
    - 设置页-启用时：校验并提示与其他治理模式的互斥关系。[REQ]
    - 设置页-关闭时：二次确认弹窗，并校验是否存在待审批申请。[REQ]
    - 申请抽屉：明确提示“申请功能权限将默认获得所有数据权限”。[REQ]
    - 申请提交前：若检测到申请项与已有权限冲突，应提前预警。[KB] RISK-004

11. 3. 用户旅程与流程（Flow）
- 主流程（按角色拆分：每步=动作→系统反馈→去向）[REQ]：
    1.  员工申请权限：
        - 动作：员工进入`PG-EMP-01`，点击“申请权限”。
        - 反馈：打开`DR-EMP-01`。
        - 动作：选择要申请的功能/角色，填写申请原因，点击“提交”。
        - 系统反馈：校验通过后，Toast提示“提交成功，申请已进入审批流程”，抽屉关闭。
        - 去向：员工可前往`PG-EMP-02`查看申请记录。
    2.  超管启用自助申请模式：
        - 动作：超管进入`PG-ADMIN-01`，点击“启用”。
