# 体验蓝图构建合同

## 目标

基于 `facts.md`、`business_blueprint.md` 与 UXB 已确认判断，生成可评审的 `experience_blueprint.md`。

## 阶段定位

experience 阶段负责：

- 组织交互流程与角色承接
- 写清用户动作、系统反馈、页面文案和下一步
- 展开异常与阻断
- 承接业务边界、风险与反馈要求
- 正式生成旅程图模块

experience 阶段不负责：

- 高保真视觉设计
- 前端实现方案
- 接口设计
- 重新做业务判断

## 输入

- `projects/<project-id>/workspace/facts.md`
- `projects/<project-id>/workspace/business_blueprint.md`
- `projects/<project-id>/runtime/uxb_route_decision.json`
- 已装配进 `runtime/context_bundle/` 的 guideline / business / complexity refs

## 设计参考使用规则

- 只能使用 UXB 明确选中的 `guideline_refs`
- 不根据关键词自动命中设计指南
- 不根据 guideline summary 自动展开 raw
- 不自动补充额外 guideline
- guideline 只吸收原则，不在正文暴露内部路径或编号

## 与 UXB 判断的关系

- experience 可以参考 `judgment.experience_output`、`judgment.reason`
- 可以参考 `complexity_judgment.experience_pressure`、`uncertainties`
- 这些信息只能转写成业务或体验语言，不得原样暴露执行字段

## 关键设计判断摘要

`## 0. 本次关键设计判断` 应放在最前，表达本次体验方案的核心处理方式。

允许表达：

- 当前重点不是多做页面，而是先把异常反馈说明清楚
- 本次需要重点承接多角色协作和状态变化

禁止表达：

- `route 判断为 full`
- `标准路线下优先写主流程`
- `matched_signals 显示存在 guardrail`

## 结构要求

`experience_blueprint.md` 必须包含：

- `## 0. 本次关键设计判断`
- `## 1. 旅程图`
- `## 2. 交互流程总览`
- `## 3. 主交互流程`
- `## 4. 次交互流程`
- `## 5. 异常与阻断流程`
- `## 6. 页面 / 弹窗 / 抽屉设计`
- `## 7. 状态与反馈文案`
- `## 8. 待确认问题`
- `## 附录：设计指南消费说明`

说明：

- `## 1. 旅程图` 是正式模块
- `## 附录：设计指南消费说明` 可沿用当前标题，但附录内容应同时支持设计指南消费与业务知识消费说明

## 关键待确认规则

`## 0. 本次关键设计判断` 中的“关键待确认”只保留影响体验策略方向的问题，例如：

- 入口是否存在
- 是否需要新建页面
- 是否复用既有页面、流程或系统
- 核心角色路径是否成立
- 主流程起点或页面承载是否明确

不应放入“关键待确认”的内容，例如：

- 按钮文案最终叫什么
- 列表排序
- 一般性提示文案
- 非关键状态样式细节

完整待确认问题继续放入 `## 8. 待确认问题`。  
`## 0` 不得复制 `## 8` 的完整清单。
前置“关键待确认”下方建议补一句引导文案：`更多待确认问题详见 ## 8. 待确认问题。`

## 旅程图要求

旅程图模块必须：

- 在体验蓝图阶段正式生成
- 表达角色 / 对象的旅程路径
- 使用 `角色：节点 → 节点 → 节点` 的路径表达
- 各角色的路径节点数量由当前业务自然生成，不要求为了形式对齐而强行补齐
- 节点保持短语级表达，不展开成完整交互步骤块
- 依据不足时显式进入“旅程缺口”
- 不重复页面结构、按钮文案、详细状态变化和完整交互步骤

旅程图模块不得：

- 从 HTML 预览层反推
- 为了路径完整自动补全角色或节点
- 写成固定角色枚举、固定阶段枚举或固定业务顺序
- 继续使用 `角色 × 阶段` 表格作为正式结构
- 在路径节点中混入 `依据：`、`source_refs`、`GAP / CONFLICT / QUESTION`、长解释或旅程缺口

## 待确认问题结构

`## 8. 待确认问题` 建议使用分块结构，每条至少包含：

- 问题标题
- 影响
- 建议确认方

## 预览表达要求

- HTML 中旅程图只保留一份 CSS 视觉版，不再重复显示原始 Markdown 路径列表
- 交互流程可视化只作用于 `## 2. 交互流程总览`
- `## 3. 主交互流程` 与 `## 4. 次交互流程` 保持正文说明，不新增流程卡片或 flow visual

## 状态与反馈文案要求

`## 7. 状态与反馈文案` 应以统一状态口径表为主，至少包含：

- 状态
- 含义
- 适用对象
- 用户可操作
- 统一反馈口径

不应再重复完整流程说明、页面布局和异常补救步骤。

## 附录：设计指南消费说明

该附录只在实际装配并消费了 guideline refs 或业务知识时填写，可记录：

- 实际使用的 guideline 主题
- 业务知识中的关键规则 / 事实
- 这些内容如何被翻译成页面、流程、反馈或状态策略
- 影响本次判断的知识缺口

不得记录：

- 自动命中过程
- `summary -> raw` 链式消费过程
- guideline 或知识原文大段摘录

## 合格标准

- 读完后能清晰知道谁在什么场景下做什么、系统如何响应
- 主流程、次流程、异常与页面承接清晰
- 旅程图正式存在，且其内容能在正文或附录中找到依据支撑
- 状态模块为统一口径表，而非长段流程复述
- 正文不暴露内部执行术语

## 失败条件

- 缺少旅程图、主流程或异常流程
- 把设计参考写成自动路由、自动升级或内部判断说明
- 页面文案是元指令而不是用户可见文本
- 依赖未装配知识或自行脑补 guideline / 业务语义
