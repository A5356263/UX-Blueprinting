# 需求事实提炼合同

## 目标

定义如何从任务输入中生成 `facts.md`。

本阶段的唯一目标是：**充分理解需求文档，用你自己的话把需求讲清楚**，让后续的 business 和 experience 阶段能基于一份可靠的理解来工作，而不是基于一堆被切碎的原文句子。

## 阶段定位

事实提炼阶段负责：

- 理解需求的整体结构和业务含义
- 识别涉及的角色、功能、规则、状态、异常、依赖
- 用自然语言重述需求，保留所有关键业务细节
- 标记不确定的信息

事实提炼阶段不负责：

- 判断需求是否合理
- 给出业务立场或方案建议
- 输出 UI 设计或交互方案
- 把原文切碎后按表头分类填入

## 输入

- `projects/<project-id>/source/requirement.md`
- `projects/<project-id>/source/background.md`
- 任务显式引用的 Wiki / 业务知识（仅用于术语校准）

## 输出

- `projects/<project-id>/workspace/facts.md`

## 核心写作原则

### 1. 先理解，再重述

阅读完整需求文档后，先形成对需求的整体理解，再用自己的话组织输出。不要一边读一边切句子，不要先把原文拆成碎片再分类。

### 2. 禁止原文碎片

正确写法是理解需求后，用自己的话组织内容。使用"当前状态 → 痛点 → 方案方向"的结构来重述，而不是从原文中切句子粘贴。

**结构骨架**（用 `< >` 标记的是需要从当前需求中填入的内容）：

```text
当前状态：<谁>通过<什么方式>完成<什么事>。
痛点：<什么条件>下，<什么成本高/效率低/体验差>。
方案方向：把<什么能力>交给<谁>，<谁>保留<什么管控>。
```

> 以上为结构格式。下面是填好后的效果（示例来自本仓库已有的权限域需求，**仅作格式参考**，不绑定领域）：

```text
当前状态：企业权限由管理员集中分配。
痛点：中大型企业员工数量多、流动性高，每次权限变动都需要管理员操作，效率低。
方案方向：将权限申请和查看能力下放给员工，管理员保留审批和范围管控。
```

错误写法——直接复制原文长句作为"事实"：

```text
F-A01: 目前企业的员工权限分配均由权限管理员或超级管理员统一分配，
对于中大型企业来说，员工多、员工流动大，权限分配和核对的工作量比较大...
```

错误写法的问题：没有理解含义，只是把原文句子截断后贴进文档。ID 编号体系（F-A01）也是禁止的。

### 3. 禁止 ID 编号体系

不要在产出中使用 F-xx、R-xx、EV-xxx 等编号。用自然语言的段落、列表、小标题来组织内容。

### 4. 禁止把知识库内容写成已确认事实

知识库只用于术语校准。如果某条信息在需求文档中没有被确认，即使知识库中存在，也不得写成已确认事实。

### 5. 信息不足时显式标记

不确定的信息用 `[GAP]` 标记，并说明为什么不确定、影响什么。

### 6. 不臆造

不得添加需求文档中没有的业务事实。不要因为"这样更合理"而补写规则。

### 7. 报错、阻断和异常只提事实

涉及报错、阻断、异常、状态反馈时，facts 只负责把事实讲清楚，不负责设计体验方案。

必须尽量提炼：

- 报错或阻断发生在哪个用户任务中
- 用户执行了什么操作
- 触发对象是什么
- 当前角色是谁
- 当前业务状态是什么
- 触发条件是什么
- 系统现在如何反馈
- 用户是否有补救路径

缺失的信息必须标记为 `[GAP]`，不能用经验补齐。

错误写法：

```text
这里应该改成 toast。
```

正确写法：

```text
用户提交时被阻断，当前材料只说明“状态不允许操作”，但没有说明当前状态、允许状态和用户下一步。[GAP]
```

## `facts.md` 结构要求

必须包含以下章节（使用自然语言组织，不做表格强制要求）：

- **任务概述**：这次需求要解决什么问题，涉及哪些角色，主要场景是什么
- **功能范围**：本次包含哪些功能，每个功能做什么。按需求文档中的功能单元组织，每个功能用一小段说清楚
- **关键业务规则**：描述重要的业务规则、校验逻辑、权限边界。说明触发条件、结果、失败时怎么办
- **状态流转**：描述关键状态的变化过程。用自然语言说清楚什么条件下状态会变、变了之后影响什么
- **异常与边界**：描述什么情况下会失败、阻断、冲突。说明每种异常的系统反馈和处理方式
- **依赖与前置条件**：依赖哪些外部系统、配置、角色、数据
- **开放问题与缺口**：当前还不确定的信息，以及它们影响哪些后续判断

以上章节不要求全部以表格呈现。优先使用段落 + 结构化列表。表格只在确实能提升信息密度时使用（例如功能清单罗列）。

## 合格标准

- 读完后能清楚知道：需求要解决什么问题、包含哪些功能、有哪些关键规则、异常怎么处理
- 需求文档中列出的每个功能编号（如 3.1/3.2/3.3）在 facts 中均有对应的自然语言描述，不是只写标题
- 没有 ID 编号、没有原文碎片、没有 machine concat
- 不确定的信息已标记 [GAP]
- 后续 business 阶段可以直接基于本文档做判断，不需要回头翻需求原文

## 失败条件

- 产出主要是原文碎片拼接或表格填空
- 使用 ID 编号体系
- 关键角色、功能、规则、异常缺失
- 缺失关键信息但未标记 [GAP]
- 知识库内容被当作已确认事实写入
