# 业务蓝图构建合同

## 目标

基于 `facts.md` 与业务知识，做出可评审的业务判断，输出 `business_blueprint.md`。

本阶段的核心是：**用业务分析师的语言回答"这需求成立吗？值不值得做？做成什么样？必须守住什么？"**

## 阶段定位

业务蓝图阶段负责：

- 判断需求是否成立、是否值得做
- 推导能力形态（独立功能 / 扩展既有功能 / 配置化 / 暂不产品化）
- 给出推荐业务方案（角色、流程闭环、关键规则）
- 明确必须守住的规则边界和风险保护策略
- 输出方案承接要求，作为 experience 阶段的输入

业务蓝图阶段不负责：

- 页面结构设计
- 具体交互细节
- 视觉方案
- 前端或后端实现方案

## 输入

- `projects/<project-id>/workspace/facts.md`
- 任务显式引用的 Wiki / 业务知识

## 输出

- `projects/<project-id>/workspace/business_blueprint.md`

## 核心写作原则

### 1. 业务大白话

核心区必须使用自然的业务语言。禁止复制 facts 中的原文碎片、禁止出现流程箭头符号（→、-->）、禁止出现 Mermaid 节点 ID。

### 2. 判断必须有依据

每个判断要说清楚基于什么事实得出。但依据应该是自然语言的引用（"根据需求中关于审批流程的描述..."），而不是 ID 编号。

### 3. 区分事实、判断和建议

读者应该能清楚分辨：哪句是已确认的事实、哪句是你的业务判断、哪句是对后续阶段的建议。

### 4. 不确定就说不确定

无法形成稳定判断时，写入"待确认问题"，不得硬凑结论。

### 5. 禁止 ID 编号体系

不使用 J-xx、BL-xx、OPT-xx、RSK-xx 等编号。用自然语言组织。

## `business_blueprint.md` 结构要求

- **1. 一句话结论**：直接回答能不能做、建议怎么做
- **2. 需求是否成立**：解决什么问题、影响哪些角色、判断成立/部分成立/暂不成立/信息不足
- **3. 值不值得做**：收益（业务价值、效率提升）与成本（开发、维护、培训、认知负担）
- **4. 应该做成什么能力形态**：比较至少两种路径，给出推荐和理由
- **5. 推荐业务方案**：角色与职责、主流程闭环、前置配置、结果回写
- **6. 必须守住的规则和边界**：不能放开的限制、必须审批的场景、必须二次确认的操作
- **7. 主要风险与保护策略**：风险描述、影响、缓解方式
- **8. 方案承接要求**：后续 experience 阶段必须承接的角色、流程、异常、状态、文案职责
- **9. 待确认问题**：会影响后续方案的重要不确定项

## 合格标准

- 能回答需求是否成立、值不值得做、做成什么形态
- 推荐方案是具体的、可执行的业务描述，不是泛泛的"做成独立功能"
- 规则边界和风险保护策略明确
- 方案承接要求清晰具体，experience 阶段能直接据此展开设计
- 全篇使用自然业务语言，无 ID 编号、无原文碎片拼接
- 附录（如有）只放补充信息，不替代核心区内容

## 失败条件

- 核心区出现大量原文碎片或 ID 编号
- 判断结论是泛化的模板答案（如"独立成型能力最优"无任何具体理由）
- 关键业务规则或风险缺失
- 方案承接要求过于模糊，无法指导 experience 阶段

## 同步约束
