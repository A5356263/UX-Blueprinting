# 任务摘要说明

当咨询已经成熟到可以变成正式 UXB 任务时，先整理任务摘要，再进入主链路。

## 核心规则

聊天记录不是正式输入。正式输入必须先被整理成一份用户可确认的任务摘要。

## 什么时候该写任务摘要

满足下面任一情况，就先整理摘要：

1. 用户给出较完整的新需求或需求文档
2. 诊断咨询后，用户明确要求正式蓝图或正式材料
3. 用户明确说要“开始 / 创建任务 / 走主链路 / 输出正式产物”
4. 当前信息已经足够形成一个真实 UXB 任务

如果还不满足，就优先停留在知识问答或诊断咨询，不要硬转任务。

## 启动前判断

正式任务摘要里必须包含这三类判断：

1. 需求类型判断
2. 主要影响层面
3. 建议处理方式

判断时要先回答：

- 这次改的是页面表现，还是业务能力，还是规则边界，还是概念结构，还是任务路径
- 它会不会改变对象关系、业务规则、状态机、生效机制、数据口径或外部回写
- 它的主要压力落在业务骨架变化，还是体验设计压力
- 它是不是只能做局部体验优化，还是必须先做业务判断

如果这些边界还不清楚，就不要直接当成小需求。

## 摘要必须覆盖什么

默认摘要保持轻量，只覆盖：

1. 要解决的问题
2. 我的判断
3. 主要影响
4. 建议处理
5. 仍需确认

如果任务很复杂，可把更详细的已知事实、展开维度、任务名或 `project-id` 放进正式输入文件，不默认压在聊天摘要里。

默认模板见：

- [assets/task_summary.template.md](../assets/task_summary.template.md)

## 用户可见表达

摘要和启动引导都必须是用户看得懂的话。

展示给用户时：

- 不说 `fast / standard / full`
- 不说 `route_decision`
- 不说 `gate / validate / coverage`
- 不说 `run-routed-main`

除非用户明确追问内部实现。

## 确认门槛

只有用户明确表达下面这类确认意图后，才能开始正式执行：

- 好，开始
- 确认
- 创建任务
- 走主链路
- 开始生成正式产物

确认之前：

- 不创建项目目录
- 不写正式任务产物
- 不运行 UXB 主链路

## 摘要之后还要做什么

任务摘要只负责把需求整理清楚，不替代正式判断单。

用户确认正式执行后，还必须继续：

1. 创建 `projects/<project-id>/`
2. 写 `source/` 正式输入
3. 生成 `runtime/uxb_route_decision.json`
4. 再启动主链路

## 正式产物与知识库的边界

正式任务产物进入：

- `projects/<project-id>/`

不要把正式任务产物自动写进 `knowledge/`。

如果蓝图中有值得长期复用的稳定结论，先整理成知识候选，再等用户确认。
