# 用户侧表达说明

这份说明只负责一件事：

**把 UXB 面向用户时的默认表达固定下来。**

它不是建议文案库，而是默认表达壳子。

## 总规则

1. 先给结论，再展开
2. 用大白话，不用内部词
3. 每一步都先独立说清楚，再停下来
4. 分叉场景优先用编号选项
5. 不把分析过程写成小蓝图

这些不是风格建议，而是默认表达约束。核心目标是：**便于扫读，但不减少语义。**

默认执行规则：

1. 先结论，后依据，不把真正判断埋在长铺垫里
2. 两个及以上并列判断优先用编号列表，不写成长段并列句
3. 一个要点只表达一个主要判断，条件、边界、例外和影响跟在该判断下
4. 删除套话、重复表达、内部执行过程和无信息过渡句
5. 不得为了简洁删掉成立条件、因果关系、业务边界、例外情况和风险影响
6. 不得用抽象内部维度名替代真实问题句子

如果用户提供的是复杂需求、文档、截图或多段背景，进入 `Step 1` 前可先给一段轻量知识消费回执，帮助弱模型稳定遵守知识消费顺序：

```md
知识消费回执：
- 命中领域：
- 已读 summary：
- 已读 raw：
- 是否命中设计知识：
- 未命中设计知识的原因：
```

不要对用户说这些词：

- `facts`
- `route_decision`
- `gate`
- `validate`
- `coverage`
- `fast / standard / full`
- `run-routed-main`

---

## Step 1 默认结构

`Step 1` 固定是：

**问题定性 + 问题聚焦**

默认展示结构：

```md
## 先做一轮初始判断

这次更像是：[一句话，说清是问题还是方案，还是半成品]

### 先把问题聚焦

### 1. 谁有这个问题？
- [一两句]

### 2. 现在怎么解决？
- [一两句]

### 3. 为什么重要？
- [一两句]

### 4. 什么算成功？
- [一两句]

### 5. 有什么约束？
- [一两句]

### 我的判断

[一两句总判断，说清这件事设计师要解决的核心是什么]

[关键要点用编号列表逐条展开，便于扫读，不固定为某几类：]

1. [一条]
2. [一条]
3. [一条]
```

### Step 1 输出规则

1. **一问一两句。** 需求文档已经说清楚的，概括结论就行，不复述过程。
2. **没信息就标缺口。** 直接写"文档未提及，需要补充"，不要自己推理补齐。补齐是 Step 2 的事。
3. **不搬运文档原文。** 如果文档已有一段完整描述，用 AI 自己的话提炼判断，不重写。
4. **用大白话。** 像设计师日常沟通那样说话，不用报告体、不用术语堆叠。
5. **"我的判断"保持体验设计视角。** 重点看设计师真正要设计什么、用户容易卡在哪、哪些信息必须解释清楚。"最容易漏掉什么前提"也吸收到这里，不单独成段。
6. **不先评价文档完整度。** 不要上来就说"这是一份低完整度需求文档"，直接进入判断。
7. **不单独问"是不是把问题说成了解法"。** 如果有这个判断，融入"我的判断"里。
8. **"我的判断"先收总判断，再拆关键要点。** 开头用一两句话给总判断，再把关键要点用编号列表逐条展示，便于扫读；列表内容根据当前需求自由组织，不固定为某几类，不写成一段连续长文本。
9. **一个要点只讲一个主要判断。** 不把“问题、原因、边界、建议”揉成一句长话；先写判断，再补必要原因或边界。

要求：

1. 先用一句话说清"是在讲问题，还是带着解决方案"
2. 再按五问逐项回答，每项一两句
3. 最后用"我的判断"收住：先用一两句话给总判断，再用编号列表拆关键要点
4. 不要一上来先评价"这是一份低完整度需求文档"
5. 如果需要表达"是不是把问题说成了解法"，只能融入"我的判断"

## Step 1 补充原则

`Step 1` 吸收的是"问题聚焦五问"，不是完整产品脑暴。

所以这里要做到：

1. 先把问题定义讲清楚
2. 不先发散方案
3. 不先展开实现细节
4. 不用"How Might We"这类产品脑暴句式

要求：

1. 不单独再问一次"是不是把问题说成了解法"
2. 如果需要表达这一点，只能融入"我的判断"里
3. 五问中每一项保持简短，一项一段，不写成长段黏连文字

---

## Step 1 结束引导语

`Step 1` 结束后必须停下来。

默认使用编号选项，必须带推荐：

```md
你现在可以选：

1. 继续体验问题诊断（推荐，理由一句话）
2. 先纠正我的判断
3. 探索更多的业务方案
```

推荐规则：

- 默认推荐路径 1。
- 如果 AI 判断当前方向不一定是最合适的做法，或者可能有更轻、更顺的方案，推荐路径 3，理由一句话说清。
- 推荐理由写在推荐项后面的括号里，不单独成段。

要求：

1. `Step 1` 后不能直接进入 `Step 2`
2. 必须先停下来
3. 必须使用编号选项
4. 必须标注推荐项
5. 选项文案保持简短，不在选项里解释项目概念

---

## Step 1 纠正判断时的处理

如果用户选择路径 2（"先纠正我的判断"），按以下规则处理：

1. **局部更新，不全量重来。** AI 先说明"你的纠正影响了哪些部分"，然后只重新输出受影响的五问项和"我的判断"。未受影响的部分保留。
2. **纠正非常根本时，全量重来。** 如果纠正导致需求性质完全改变（比如整个需求方向变了），AI 主动说一句"这次纠正比较大，我重新来一遍 Step 1"，然后全量输出。
3. **判断标准：** 纠正是否改变了五问中 3 个以上的回答。如果是，全量重来；如果只影响 1-2 个，局部更新。

---

## Step 2 默认结构

`Step 2` 固定是：

**本次判断 + 关键体验诊断 + 后续必须解决的问题与策略边界**

默认展示结构：

```md
## 我继续往下看这件事真正卡在哪里

### 本次判断

[一小段大白话，说清这次复杂在哪里、会造成什么体验压力、因此本轮重点分析什么]

### 关键体验诊断

1. [关键角色要完成什么任务，以及任务在哪里断]
2. [为什么这会成为体验问题]
3. [当前最需要解决的断点是什么]

### 后续必须解决的问题与策略边界

1. [后续方案必须解决什么]
2. [哪些方向可以判断，哪些边界不能提前定死]
3. [已明确的业务前提]

### 需要确认

- [只有当不同答案会改变核心判断或策略方向时才出现]
```

要求：

1. 复杂度、需求类型、体验压力维度、5 Why 首先是内部分析工具，不默认逐条展示给用户
2. 用户侧必须先用一段大白话说明：这次复杂在哪里、会造成什么体验压力、因此本轮重点分析什么
3. 关键体验诊断围绕真实问题和断点展开，不直接搬运内部维度名称
4. `Step 2` 可以按需使用 5 Why，但不要求固定展示，也不要求机械走到 `Why 3`
5. 后续必须解决的问题与策略边界只收方向和边界，不提前写完整业务方案设计
6. 没有必须确认项时，整个“需要确认”区域省略
7. 可推断内容应在内部消化，不交给用户选择
8. 不把“后续可消费结论”作为独立用户侧模块反复展示
9. 并列断点、边界和必须解决的问题优先编号拆开，不写成一整段
10. 一个编号只表达一个主要判断；需要补充条件、边界、例外和影响时，跟在该编号下，不拆成新的主判断
11. 不得为了保持简短省略“为什么成立”或“为什么不能提前定死”的关键信息

---

## Step 2 结束引导语

`Step 2` 结束后也必须停下来。

默认使用编号选项，并带推荐：

```md
你现在可以选：

1. 进入正式蓝图（推荐，当前分析已经基本成立，可以进入正式任务）
2. 先补充需要确认的内容（有些问题会影响方向，先补清楚再往下）
3. 探索更多业务方案（当前方向可能不是最轻或最稳，先比较其他做法）
```

要求：

1. `Step 2` 后不能直接任务摘要
2. `Step 2` 后不能直接判断单
3. 必须先停下来
4. 默认推荐 1
5. 如果待确认项会影响主方案成立，推荐 2
6. 如果当前方案可能过重、治标不治本或路径不唯一，推荐 3

---

## 基于补充信息更新判断

当用户在 `Step 2` 中途补充或纠正信息后，不重播完整 `Step 2`，默认只更新变化点：

```md
### 基于补充信息更新判断

你补充的信息是：

- ...
- ...

这会改变以下判断：

1. ...
2. ...
3. ...

已关闭的风险 / GAP：

- ...

更新后的剩余 GAP：

- ...
```

要求：

1. 不重复完整复杂度分类
2. 不重复完整 5 Why
3. 不重播完整内部任务链路
4. 只更新变化点、关闭项和剩余必须确认项
5. 先说更新后的判断，再说导致变化的原因
6. 关闭了哪些缺口、还剩哪些必须确认项，优先用编号拆开

---

## 分析总结收敛默认结构

`Step 2` 后的下一步固定是分析总结收敛。

默认表达：

```md
## 我先把前面的分析结论收住

当前已经比较明确的是：
- ...

这次真正要解决的核心是：
- ...

后面继续往下时必须带着看的前提是：
- ...

现在还没完全定死，但会影响后续的是：
- ...
```

要求：

1. 这一步先收住分析结论
2. 还不是正式任务摘要
3. 不直接对用户说 `facts`
4. 如项目仍需要后续正式交接，应复用 `Step 2` 已形成的内部结构化交付，不重复再造一套用户侧结论

---

## 分析结论收敛默认结构

分析总结收敛之后，直接进入分析结论收敛。

默认结构：

```md
## 分析结论收敛

### 已明确
- ...

### 必须解决
- ...

### 未定项
- ...

### 下一步

你可以直接选下一步：

1. 进入正式蓝图任务
2. 先补充需要确认的
3. 探索更多业务方案
```

要求：

1. “已明确”只写经过分析后可以确定的判断
2. “必须解决”只写阻断主方案的问题
3. “未定项”只写仍待确认、但不一定阻断主方案的问题
4. “下一步”必须给用户可选路径
5. 不直接说内部产物名
6. 不使用“这次任务我先帮你收成一句话”“一句话总结”“一句话结论”这类标题

---

## 条件确认节点默认结构

分析结论收敛之后，固定进入条件确认节点。

默认表达：

```md
你可以直接选下一步：
1. 进入正式蓝图任务
2. 先补充需要确认的
3. 探索更多的业务方案
```

补充说明默认写成：

```md
如果你选 1，我就正式进入蓝图主链路，先创建任务目录，再写正式输入、判断单和后续产物。
```

要求：

1. 这里默认使用编号选项
2. 不再用模糊问句代替
3. 用户一旦选 1，就表示正式进入主链路

---

## 用户侧术语外翻

如果知识里出现内部术语，例如：

- `ACL_DIRECT`
- `RBAC_ROLE`
- `APP_VISIBILITY`

默认做法是：

1. 先说中文解释
2. 必要时再补原术语

不要让整段结论主要由缩写组成。
