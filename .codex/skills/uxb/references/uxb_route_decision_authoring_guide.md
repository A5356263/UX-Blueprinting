# UXB Route Decision Authoring Guide

## 目的

本文用于指导 UXB 在正式执行前生成：

- `projects/<project-id>/runtime/uxb_route_decision.json`

这个文件是 UXB 的判断单和资料选择单。执行中枢只读取它，不替 UXB 判断。

这份 guide 只负责回答“判断单怎么做、字段怎么想、什么时候阻断、输出深度怎么判”。
知识读取入口、summary/raw 分层和知识纠错处理，以 `references/knowledge_usage_guide.md` 为准；这里不再把整套知识消费规则重讲一遍。

## 生成时机

- 用户已经明确确认正式执行
- 准备调用执行中枢之前

如果这个文件缺失，不得启动主链路。

## 先记住一条原则

这个文件不是业务蓝图，也不是体验方案正文。

它只回答六件事：

1. 这次需求更像什么类型
2. 这次应做到什么输出深度
3. 哪些变化点真正值得警惕
4. 后续正式生成真正需要读哪些资料
5. 还有哪些不确定项
6. 现在能不能进入正式执行

## 判断前先问自己

写判断单前，不要急着填字段。先在内部回答下面四个问题：

1. 这次改动真正改变的是页面表现、局部流程，还是业务对象、规则、状态、生效方式？
2. 哪些不确定项只是会影响方案精细度，哪些不确定项会直接让正式产出失真？
3. 后续正式产物最需要补的是事实、业务判断，还是体验承接？
4. 为了支撑这些判断，最小需要读哪些资料？

如果这四个问题答不清，不要硬写成可执行。

再补一个反 happy path 自检：

- 我现在是在判断问题本质，还是只是顺着需求表面分类
- 用户给出的“想要做法”是不是偷带了前提，而这些前提还没被确认
- 如果我继续往下走，最容易遗漏的是哪个断点、冲突、阻断项或知识缺口


## 判断阶段边界

判断阶段只做：

1. 判断需求类型
2. 判断复杂度和主要压力点
3. 选择后续正式生成真正要读的资料
4. 写明选择理由
5. 写明不确定项
6. 判断是否允许执行主链路
7. 判断需要的正式输出

判断阶段不做：

1. 不写完整业务蓝图
2. 不写完整体验方案
3. 不通读整个 `knowledge/`
4. 不为了保险全量选资料
5. 不把知识原文复制进判断单

## 读取顺序

### 必读

1. `references/complexity/00_core_complexity_judgment.md`
2. `references/complexity/01_domain_router.md`
3. `references/knowledge_usage_guide.md`

### 按需读取

- 命中的领域卡片
- 业务 summary 或 README
- 设计指南 summary
- 必要 raw

这里的重点是“读哪些资料来支撑判断单”，不是完整讲解知识体系本身；如果你开始纠结入口型 README、`00_领域概述`、`knowledge/templates/**` 分别怎么用，回到 `references/knowledge_usage_guide.md`。

### 不允许

- 通读所有领域卡片
- 通读整个 `knowledge/`
- 因为出现领域词就整包带上该领域资料
- 因为“可能用得上”就把资料塞进判断单

## 复杂度判断

按这个顺序判断：

1. 这次改动到底改了什么
2. 是否改动底层业务骨架
3. 体验设计压力主要落在哪里
4. 更适合落到哪类正式输出

判断时优先看：

- 对象关系
- 业务规则
- 状态变化
- 生效方式
- 数据口径
- 外部回写

不要只靠关键词或领域名自动下结论。

## 不确定项：先分阻断与不阻断

不要把所有不确定项混在一起看。

先在内部分两类：

- 阻断型不确定项：如果不补清，就会让 facts、business 或 experience 明显失真
- 非阻断型不确定项：不影响当前正式执行，但会影响后续细化质量

写法要求：

- `complexity_judgment.uncertainties` 里写真正重要的不确定项
- `judgment.reason` 里顺手交代一句：为什么这些不确定项当前不阻断，或为什么它们已经阻断

如果存在阻断型不确定项，应优先：

1. 向用户追问 1-3 个关键问题
2. 把 `can_execute_mainline` 设为 `false`

## 知识选择规则

### 总原则

知识选择不是“把可能有用的都带上”，而是“选后续正式产物真正会消费的最小资料集合”。

- 选择知识前先判断当前到底要确认什么，不要因为需求像某个领域就机械缩到该领域后直接停下
- summary 命中不等于知识已经足够；只有当它足以支撑当前判断点时，才可以不升级 raw

### 先回答三个问题

在选任何 ref 之前，先回答：

1. 我这次要确认的是对象关系、规则边界、状态机，还是体验承接？
2. 为了确认这个问题，最小需要读到哪一层资料？
3. 这个资料会实际支撑 facts、business 还是 experience？

如果答不清，就不要选。

### 优先级

- 默认优先选文件级 ref
- 只有在需要先确认路由或索引入口时，才允许选 index / README / summary 入口
- 如果已经能确定具体文件，不要只停留在宽入口 ref

### 业务知识

优先回答：

1. 涉及哪些业务对象
2. 是否需要确认对象关系
3. 是否需要确认规则边界
4. 是否需要确认流程、角色、状态或异常
5. 是否需要确认现有能力边界

### 设计指南

只有当后续体验阶段真的需要承接下面问题时才选：

1. 信息结构
2. 表单、列表、弹窗、导航等交互组织
3. 反馈、报错、阻断、异常说明
4. 可读性、可用性、无障碍
5. 视觉层级或信息突出方式

不是为了“看起来完整”而选。

### complexity 资料

优先选：

1. 通用复杂度判断规则
2. 命中的领域路由资料
3. 明显能帮助判断深度的领域卡片

## knowledge_selection 写法

`knowledge_selection` 现在只保留两个正式字段：

```json
{
  "files": [
    "knowledge/wiki/summaries/业务/权限管理/15_页面载体语义.md",
    "knowledge/raw/业务/权限管理/15_页面载体语义.md",
    ".codex/skills/uxb/references/complexity/00_core_complexity_judgment.md"
  ],
  "reasoning": "先用 summary 缩小到页面载体语义，再补 raw 确认具体边界，并带一份 complexity 资料约束判断深度。"
}
```

填写要求：

1. `files` 只列这次真正计划读取的知识文件，保持最小集合
2. `reasoning` 用 3-5 句话说明整体思路，不再逐条写每个 ref 的工程理由
3. 不为了“更完整”把一整域 summary 或 raw 全量塞进去
4. raw 可以直接进入 `files`，前提是你说得清它为什么必要

## required_outputs 判断

不要先想“我想跑哪条路径”，而要先想“当前事实能支撑到什么深度”。

可以用这个判断顺序：

1. 现在是只需要先收敛边界和承接重点，还是已经足以形成稳定业务方案？
2. 业务对象、规则、状态机是否已经清楚到足以支撑更重输出？
3. 当前未定项会不会让更深输出明显失真？

一般判断：

- 只需先收敛边界、风险和承接重点：`business_note.md`
- 需要较稳定的业务方案，但还不到完整 full blueprint：`business_blueprint_lite.md`
- 已明显涉及对象关系、规则系统、状态机重构或完整业务方案：`business_blueprint.md`

不要因为用户直接要“正式方案”就自动走更深输出；先判断当前信息是否足以支撑该深度。

## can_execute_mainline 判断

可执行，不代表信息完整；只代表“当前信息足以支撑这次选定的正式输出”。

可以执行时通常满足：

- 需求目标清楚
- 关键对象关系基本清楚
- 输出深度有依据
- 不确定项不会让当前正式产出失真
- 资料选择有清晰原因

不可执行时常见情况：

- 需求目标不清
- 关键业务对象不清
- 生效方式不清
- 数据口径不清
- 外部回写不清
- 无法判断该读哪些关键资料

如果存在会直接让后续业务判断、体验承接或关键事实失真的阻断项，不要为了推进流程先写成 `true`。

## confirmed_by_user 判断

`confirmed_by_user=true` 不是“用户说了一句继续聊”，而是用户已经明确表达以下含义之一：

- 确认执行
- 开始正式任务
- 创建任务
- 走主链路
- 输出正式产物

如果只是确认某个想法、某个方向、某段总结，不要提前写成 `true`。

## judgment.reason 写法

不要只写一个泛泛的总结句。

至少覆盖这三点：

1. 为什么它属于当前需求类型
2. 为什么当前输出深度是合适的
3. 为什么当前可以执行，或为什么当前不能执行

如果用户原始表述里包含明显假设、结论或方案倾向，也要在这里说明你是否接受了这些前提，还是保留了判断。

## JSON 写入要求

写入路径：

- `projects/<project-id>/runtime/uxb_route_decision.json`

使用模板：

- `assets/uxb_route_decision.template.json`

不要把完整业务方案、完整体验方案或知识原文写进这个文件。它是判断单，不是蓝图正文。

## JSON 稳定写法

先复制模板，再只替换值，不要临时改字段结构。

必须遵守：

1. JSON 结构键名一律保持模板原样，不要自己改名，不要写别名
2. `knowledge_selection` 下的正式字段名只能是 `files` 和 `reasoning`
3. 不要把 `summary_refs`、`raw_escalation_plan`、`stage_refs`、`selection_reasons` 留在新文件里
4. 结构引号必须是 JSON 标准 ASCII 双引号 `"`
5. 字符串内容里如果想引用中文词语，优先用 `「」` 或 `“”`，不要再裸写一个未转义的 ASCII 双引号
6. 不要把“我来修复”“确认两个问题”“JSON 解析失败”等说明文字写进 JSON 文件
7. 不要输出代码围栏、解释段落或修复说明；文件内容本身只保留 JSON 对象

最常见的坏写法：

- 在 `reason`、`notes`、`uncertainties` 这类字符串里直接插入未转义的 `"`，导致 JSON 断裂
- 把 `files` / `reasoning` 又写回旧的 `summary_refs` / `raw_escalation_plan`
- 把报错信息、修复说明、检查结论一起写进 JSON 文件

如果已经写坏，不要在坏 JSON 上继续补丁式改字。正确做法是：

1. 重新复制 `assets/uxb_route_decision.template.json`
2. 按模板重填一次值
3. 保持键名完全不变
4. 再执行 `python -m packages route-decision <project-id>` 做一次结构校验
