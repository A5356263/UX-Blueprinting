# 需求类型判断指引

这份指引用来帮助 UXB 在正式任务启动前，先把需求类型、影响层面和建议处理方式判断清楚。

## 判断顺序

1. 先判断这次改动到底改了什么。
2. 再判断它会不会改变业务能力。
3. 再判断它会不会改变业务规则。
4. 再判断它会不会碰到权限、数据范围、审批、状态机等高风险边界。
5. 再判断它会不会改变用户任务路径。
6. 最后判断它是不是概念或信息结构问题。

## 需求类型

- 局部体验优化
- 布局交互优化
- 文案与信息表达优化
- 信息结构与概念澄清
- 既有能力扩展
- 业务流程调整
- 权限与治理风险
- 功能新增
- 功能重构
- 不确定，需要补充判断

## 关键判断问题

### 1. 这次改动改了什么

- 改页面表现。
- 改业务能力。
- 改规则边界。
- 改概念定义。
- 改任务路径。

### 2. 是否改变业务能力

- 是否新增一个用户能做的能力。
- 是否扩展现有能力。
- 是否重构现有能力。
- 是否只是现有能力里的局部体验问题。

### 3. 是否改变业务规则

- 是否新增可操作条件。
- 是否新增限制。
- 是否改变校验。
- 是否影响结果范围。
- 是否改变状态含义。

### 4. 是否涉及高风险因素

只要涉及下面这些，就不能草率判成小需求：

- 权限
- 数据范围
- 审批
- 导出
- 组织边界
- 敏感信息
- 审计
- 治理
- 状态生效
- 批量影响范围

但也不能一看到这些词就直接判成复杂需求。要继续判断它到底是：

- 在解释现有规则。
- 还是在改变规则本身。
- 在展示现有权限。
- 还是在改变权限模型。

### 5. 是否改变任务路径

- 用户步骤是不是变多了。
- 是否新增选择、确认、审批或结果查看。
- 是否新增失败处理。
- 是否改变完成任务的顺序。

### 6. 是否是概念或信息结构问题

- 是文案写得差，还是概念边界不清。
- 是提示不清，还是模块归属不清。
- 是命名问题，还是对象关系混乱。

## 处理建议

### 小需求

适用于：

- 局部文案
- 局部布局
- 局部提示
- 局部交互状态
- 不改变业务规则
- 不涉及权限、审批、数据范围、状态机

建议表达：

这次主要是局部体验优化，不涉及复杂规则变化。重点会放在页面表现、交互边界和提示说明上。我建议直接输出体验策略，并补一段必要的业务依据。

### 中等需求

适用于：

- 既有能力扩展
- 局部规则变化
- 状态、异常、校验需要判断
- 权限边界需要先澄清，但不需要完整重构

建议表达：

这次不是单纯页面调整，它会影响现有能力里的规则边界或异常处理。我建议先做一版轻量业务判断，再输出体验方案。重点会放在规则边界、状态反馈和用户下一步上。

### 复杂需求

适用于：

- 功能新增
- 功能重构
- 权限模型变化
- 审批治理变化
- 状态机复杂
- 概念边界不清

建议表达：

这次涉及业务能力、权限边界或流程结构变化，不能只按页面体验处理。我建议先梳理完整业务判断，再输出体验方案。重点会放在角色、规则、状态、风险和页面承接上。

### 信息不足

适用于：

- 是否影响权限不清。
- 是否影响数据范围不清。
- 是否影响审批不清。
- 是否影响状态机不清。

建议表达：

现在还不能直接当成局部体验优化，因为它可能影响权限、数据范围或状态规则。我建议先确认这个边界，再决定是轻量处理还是完整蓝图。

## 禁止事项

- 不让用户自己选择 `fast / standard / full`。
- 不直接把 `route_decision` JSON 展示给用户。
- 不只靠关键词命中做最终判断。
- 不一看到“权限”就直接判 full。
- 不一看到“文案”就直接判小需求。
- 不在没有业务依据时说“这不涉及业务规则”。
