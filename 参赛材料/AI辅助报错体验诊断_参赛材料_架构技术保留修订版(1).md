**项目简述：**

针对企业级产品报错体验差、人工治理效率低、治理链路长且增量问题持续产生的痛点，构建「AI 智能检测 + 零代码动态治理 + 全流程自动化编排」三位一体解决方案。

方案以“**事前预防—事中治理—事后验证**”为主线：在需求、设计、开发阶段通过 AI Skill 识别增量风险；对已上线问题，依托统一采集、AI 诊断和零代码动态治理机制分流处置；对治理结果进行持续回检并回流知识库。方案已在薪福通落地，并具备向企银、见微、开阳等产品复制的基础。

> **能力状态说明：** AI 批量检测、报错治理平台、零代码动态替换及部分监测能力已上线运行；需求、设计、开发 Skill 已完成局部场景验证；埋点 Skill、9 步工作流的全部自动执行及自动月报仍在建设中。本文将“已运行结果”“试点验证”和“建设目标”分别标注，不将规划能力表述为既成事实。

# 一、痛点与背景

## 1. 问题有多大：从一次报错到一条价值损失链

薪福通的报错问题并非只影响提示文案，而是会中断用户任务、引发重复操作与咨询，并最终增加服务和治理成本。现有监测数据显示，月均报错触发量为 **49,159 次**，不友好报错占比约 **60%**；报错相关运维支持投入约 **13 人天/月**。

| 损失链节点 | 具体表现 | 关注指标 |
|---|---|---|
| 报错发生 | 核心流程中出现规则、权限、交互或系统异常 | 报错触发次数、标准化报错率 |
| 用户困惑与流程中断 | 用户不知道发生了什么、下一步如何处理 | 不友好报错占比、引导覆盖率 |
| 任务失败或重复操作 | 用户反复尝试、绕路或退出 | 任务完成率、一次性任务完成率 |
| 寻求帮助 | 用户转向客服、运营或工单 | 报错相关咨询/工单占比 |
| 服务投入上升 | 运营、产品、研发重复处理同类问题 | 人工处理人天、治理周期 |
| 长期体验受损 | 问题累积影响使用意愿与满意度 | 满意度反馈、活跃与留存辅助指标 |

### 指标口径

- **报错触发次数**：统计周期内错误码被用户实际触发的总次数，用于衡量用户影响规模；不用于估算逐条评估工作量。
- **去重报错条目数**：按错误码、场景、端别及版本等口径去重后的待评估对象，用于衡量诊断与治理工作量。
- **受影响用户数**：统计周期内至少触发一次目标错误的去重用户数。
- **治理后效果**：优先对已纳入治理的同批错误码，比较治理前后相同观察周期内的标准化报错率、任务完成指标或咨询指标；需注明观察周期、样本范围及业务量变化。

## 2. 传统治理为何难以规模化

传统模式依赖人工发现、体验评估、协调排期和上线回检，问题主要集中在以下四点：

| 传统做法 | 核心局限 | 对应治理方向 |
|---|---|---|
| 逐条人工识别与评估 | 去重条目多、分析耗时长，处理能力受限于专家投入 | AI 批量诊断与优先级排序 |
| 仅依赖规范约束 | 同一报错的判断和建议易受个人经验影响 | 专家经验结构化、规则与 AI 协同 |
| 修改必须走开发发版 | 文案类问题也需要研发介入，治理周期长 | 零代码动态治理 |
| 线上出现后再修复 | 存量未清、增量持续产生，难以形成闭环 | 需求—设计—开发前置预防与上线后回检 |

因此，项目的核心不是把报错文案“改得更好”，而是将传统的人工、事后、离散治理升级为一套可持续运行的全周期机制。

# 二、核心洞察与治理策略

## 1. 报错需区分体验问题与根因问题

| 报错类型 | 问题性质 | 典型判断 | 处置路径 |
|---|---|---|---|
| **体验问题** | 报错本身合理，但用户无法理解或自行处理 | 说明不完整、缺少操作指引、技术术语难理解 | AI 生成建议 → 专家复核 → 文案治理平台发布 |
| **根因问题** | 报错本不应发生，或校验时机/规则不合理 | 重复校验、无效权限校验、规则缺陷、交互流程缺陷、Bug | 根因分析 → 三方确认 → 需求/代码迭代 → 上线回检 |

两类问题共享“发现—诊断—确认—治理—验证”的流程，但执行方式不同。文案类可由零代码治理平台快速生效；规则、权限、交互和 Bug 类则进入产品研发迭代，从源头消除问题。

## 2. 两条治理路径、三类核心能力与一个数据知识底座

| 构成 | 内容 | 作用 |
|---|---|---|
| **增量预防路径** | 需求 Skill、设计 Skill、开发 Skill | 在上线前识别遗漏、体验风险和代码风险 |
| **存量治理路径** | 错误码/埋点、客观行为数据、主观反馈、客户分群 | 对线上问题进行识别、优先级判断和治理 |
| **AI 诊断能力** | 场景识别、问题分类、根因候选、建议生成、优先级判断 | 找得准、说得清、给出候选方案 |
| **治理执行能力** | 文案治理平台、动态替换、灰度发布、需求排期 | 改得快、分流准确、可追踪 |
| **工作流编排能力** | 数据拉取、人工确认关卡、状态持久化、回检回流 | 让机制可持续运转 |
| **数据与知识底座** | 治理规范、案例库、报错台账、埋点与反馈数据 | 让结论可复核、规则可更新、能力可复用 |

# 三、整体方案全景：四层能力体系

## 1. 架构总览

本章回答“整体由什么构成、各部分如何协同”。方案以**增量预防**和**存量治理**两条路径覆盖线上前后，并由诊断、执行、编排与数据知识能力共同支撑；具体 Skill、9 步工作流及技术实现机制见第四章。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│              【治理工作流】统一编排、人工确认、状态追踪、效果回流            │
├─────────────────────────────────┬───────────────────────────────────────────┤
│      【前置预防层】              │           【存量治理层】                   │
│      增量拦截（线上前）          │           存量治理（线上后）               │
│  在需求、设计、开发阶段尽早发现  │  基于报错、行为与反馈持续发现问题           │
├─────────────────────────────────┴───────────────────────────────────────────┤
│                     【AI 诊断能力】识别、归因、分级、生成候选方案             │
├─────────────────────────────────────────────────────────────────────────────┤
│                【治理执行能力】动态治理、研发迭代、灰度验证、效果回检         │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. 层级说明与完成状态

| 能力层/路径 | 在整体方案中的作用 | 当前状态 |
|---|---|---|---|
| 前置预防层 | 将报错治理前移到需求、设计、开发阶段，降低问题进入线上概率 | 局部验证、持续完善 |
| 存量治理层 | 汇集线上报错、用户行为与主观反馈，识别高影响问题 | 部分已运行；行为埋点能力建设中 |
| AI 诊断能力 | 对问题进行体验与根因判断，形成可供人工确认的候选结论 | 三类 Skill 已验证；埋点 Skill 建设中 |
| 治理执行能力 | 按问题类型分流：可动态治理的问题快速生效，其余进入研发迭代 | 已上线运行 |
| 治理工作流（横向贯穿） | 串联发现、确认、执行、回检与知识回流，确保过程可追溯 | 流程已设计，部分节点需人工介入 |

## 3. 运行闭环

整体方案围绕“**发现—诊断—确认—治理—验证—回流**”运行：AI 负责规模化识别和生成候选结论；设计、产品、研发与运营在关键关卡完成判断；上线效果及确认结果回流到案例、规则和知识库，支撑下一轮治理和同源问题复用。

**人机协同原则：**

- 可由规则确认的问题可自动分流；AI 的概率性判断仅作为风险提示，不替代人工决策。
- 每个问题保留证据、确认意见、执行记录和回检结果，支持复核与持续优化。
- 各层能力的输入、输出、实现机制与验证结果在第四章展开说明。

# 四、技术方案详解：三大技术支柱与实现机制

本章回答“方案如何实现”。以下依次说明 AI 智能检测、零代码动态治理与全流程工作流的实现机制；并补充四个 AI Skill 的输入、输出、边界与验证结果。

## 1. AI 智能检测：开发 Skill 嵌入流水线

**核心流程：**

```text
代码提交/提测 → 触发柯南流水线 → 调用开发 Skill 扫描
       ↓
错误码定义采集 + 规则检测 + AI 风险提示 → 候选根因分析
       ↓
输出：检测报告、证据链接、优化建议、风险等级
       ↓
确定性规则不通过？→ 阻塞并人工确认 → 修复后继续发布
AI 风险提示？      → 进入人工评审，不直接阻塞发布
```

### 流水线对接关键实现

| 实现环节 | 技术方案 | 关键细节 |
|---|---|---|
| 流水线集成 | 在柯南流水线配置 Skill 扫描任务 | 编译完成后自动触发，减少人工提报 |
| 静态代码扫描 | 解析实现 `ISysErrorCode` / `IBizErrorCode` 的枚举类 | 提取错误码及上下文，通过 HTTP 上报治理平台 |
| 规则与 AI 协同 | 确定性规则与 AI 风险提示分层输出 | 规则问题可作为卡点；候选根因须人工确认 |
| 零侵入采集 | 流水线静态扫描 + 框架 SDK | 不消耗在线后端资源，不影响业务性能 |

### 开发 Skill 检测边界

| 能力 | 可输出内容 | 必需证据 |
|---|---|---|
| 场景识别 | 错误码对应业务场景、所属模块 | 错误码定义、代码路径、模块信息 |
| 组件分析 | 调用位置、相关组件和接口 | 调用链、接口定义、上下文代码 |
| 风险判断 | 权限、并发、规则或交互风险候选 | 业务规则、权限配置、日志/运行证据 |
| 优化建议 | 代码/规则/提示/流程的候选改进方案 | 历史案例、规范、人工确认反馈 |

### 有效性验证

| 验证场景 | 问题识别精准度 | 建议采纳率 | 说明 |
|---|---:|---:|---|
| 排班表 | 91.7% | 67% | 文案建议 2 条均被采纳 |
| 请假记录 | 待补充 | 待补充 | 按相同口径持续验证 |

## 3. 零代码动态治理框架

### 3.1 核心设计理念

报错信息动态治理框架是薪福通报错优化治理平台的核心执行引擎。它通过流水线静态扫描采集、框架 SDK 统一异常处理和治理平台配置，使已确认的**文案类问题**可在不改业务代码的情况下动态替换并灰度生效；根因问题仍按照研发治理流程处置。

### 3.2 三大核心组件

| 组件 | 功能 | 特点 |
|---|---|---|
| 办公网治理平台 | 单入口、多环境治理配置 | 支持开发/测试/生产环境的灰度验证与发布确认 |
| 框架动态替换 | 命中错误码后返回优化信息 | 文案类问题无需业务版本发版即可生效 |
| 灰度验证机制 | 在低风险环境先验证后全量发布 | 降低跨环境重复配置与发布风险 |

### 3.3 技术实现细节

**（1）全自动报错信息采集机制**

| 采集方式 | 技术方案 | 优势 |
|---|---|---|
| 流水线静态扫描 | 编译完成后解析 `ISysErrorCode` / `IBizErrorCode` 枚举类 | 零侵入，不消耗在线后端资源 |
| 前端埋点采集 | HTTP 统一请求与错误码埋点上报数仓 | 形成结构化数据，支持线上监测 |
| 框架 SDK 统一处理 | 后端框架统一捕获业务异常并返回标准响应体 | 为动态治理提供统一入口 |

**（2）框架动态治理核心流程**

```text
业务抛出异常 → 框架异常处理器统一捕获
       ↓
定时任务加载已审核的优化报错信息至本地缓存
       ↓
错误码命中动态缓存 → 替换为优化后的提示与处理指引
       ↓
前端收到最终报错信息；治理记录保留版本、环境与发布时间
```

**（3）治理分类处理策略**

| 问题类型 | 治理方式 | 生效方式 | 治理周期 |
|---|---|---|---|
| 文案类 | 文案治理平台 | 实时/准实时生效，无需业务代码修改 | 秒级至分钟级 |
| 规则/权限类 | 需求确认 + 研发排期 | 随版本迭代上线 | 数周 |
| 交互流程类 | 体验方案 + 研发排期 | 随版本迭代上线 | 数周 |
| Bug 类 | 代码修改、测试、发布 | 从源头修复后上线 | 数周至数月 |

**（4）跨环境互联方案**

```text
办公网治理平台（单一入口）
       ↓ 数据同步后端服务
开发/测试环境：验证与维护
       ↓ 动态治理框架
生产环境：经发布确认后生效
```

| 治理执行 | 零代码动态治理与研发迭代分流 | 报错信息管理平台 | 已运行 |
| 效果回检 | 看板监测与治理前后对比 | 圆方统计看板 | 持续完善 |
| 月报输出 | 自动汇总 + 人工审查后发送 | 体验管理组工作机制 | 自动化建设中 |

### 4.1 工作流节点与人机协同机制

工作流以状态持久化、人工确认关卡和结果回流为核心，而非仅将任务顺序串联。各节点的实现如下：

| Step | 环节 | 核心动作 | 自动化/人工边界 |
|---|---|---|---|
| Step 1 | 数据拉取 | 拉取客观数据、代码扫描结果、主观反馈、客户分群 | 已部分对接；数据完整性需校验 |
| Step 2 | AI 检测 | 调用对应 Skill，按时机、形式、Bug/交互/文案等维度分析 | 可自动执行；输出为候选结论 |
| Step 3 | 诊断确认 | 设计师、产品、研发确认根因与优先级 | 必须人工确认关卡 |
| Step 4 | 方案生成 | 生成 Markdown 方案、体验蓝图及原型输入 | 可辅助生成，方案需人工审阅 |
| Step 5 | 方案评审 | 设计师、产品、运营确认治理方案 | 必须人工决策关卡 |
| Step 6 | 执行发布 | 文案类进入治理平台；其他类进入需求与排期 | 文案发布可自动化；研发迭代需协同 |
| Step 7 | 回检成效 | 上线后按约定周期拉取数据，比较基线与治理后效果 | 数据拉取可自动化，归因需人工复核 |
| Step 8 | 台账更新 | 更新问题状态、责任人、版本、证据与效果 | 部分字段可自动回填 |
| Step 9 | 月报输出 | 汇总治理规模、进度、成效和风险 | 自动汇总建设中，发布前人工审查 |

**运行约束：**

- 确定性规则问题可自动分流；AI 概率性判断仅作为风险提示，不直接阻塞发布或替代人工决策。
- 每个问题保留输入证据、诊断版本、人工确认意见、执行记录和回检结果，支持暂停、恢复和复核。
- 上线回检结果回流案例库、规则库与 RAG 知识库，用于同源问题识别和能力优化。

# 五、落地实践与验证成效

## 1. 典型根因治理案例

### 1.1 薪资代发场景

| 人工确认与分流 | 确认为规则/流程根因问题，进入研发治理而非文案替换 |

| 回检结果 | 已治理场景下月均报错量降至 0；后续持续观察同源场景 |
| 沉淀资产 | 形成“切换主体后无效查询校验”的规则案例 |

# 七、项目创新与价值总结

## 1. 三项核心创新

| 创新点 | 说明 |
|---|---|
| 从文案优化到根因治理 | 不仅改写提示语，还识别校验必要性、时机、权限、规则、交互与 Bug 等问题，并分流到对应治理路径 |
| 从单次 AI 调用到可运行机制 | 形成“发现—诊断—人工确认—治理—发布—验证—沉淀—复用”的闭环，保留证据与状态，支持持续运行 |
| 从存量整改到增量预防 + 存量治理 | 上线前通过需求/设计/开发 Skill 降低新增风险；上线后通过数据与反馈识别阻塞问题，并将回检结果反哺知识库 |

## 2. 项目价值

| 价值维度 | 已形成的价值 |
|---|---|
| 用户体验 | 通过文案治理与根因治理降低用户理解和处理报错的成本；典型根因场景实现报错清零 |
| 治理效率 | AI 批量识别、优先级排序和建议生成，辅助体验专家将精力集中在高价值判断与确认 |
| 技术与机制 | 流水线扫描、统一错误码采集、框架动态替换、灰度发布、台账回检共同构成可复制的治理基础 |
| 组织复用 | 规范、案例库、Skill 与平台能力可服务企银、见微、开阳及后续产品线 |

## 3. 参赛结论

> 本项目不是用 AI 单点优化报错文案，而是以 AI 诊断、零代码动态治理和工作流编排，重构企业级产品从事后修补到事前预防、从离散治理到持续回检、从单产品经验到跨产品复用的报错体验治理机制。
