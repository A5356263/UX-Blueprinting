# 项目简介

**项目名称：** AI 原生产品体验架构师——B 端体验设计师工作新范式探索  
**项目方向：** AI 驱动的企业级产品体验设计与体验运营

**项目简述：**

AI 正在从单点辅助工具发展为具备分析、生成与协同能力的工作伙伴。传统 B 端体验设计师以界面和交互方案为主要交付，面对海量行为数据、跨渠道反馈、复杂业务规则与上线后效果验证时，容易出现分析覆盖不足、结论难以互证、方案交付与成效脱节等问题。

本项目探索将体验设计师转型为“AI 原生产品体验架构师”：由设计师定义 AI 技能的输入输出契约、能力边界、协作关系、知识规则与人工确认关卡，构建“需求洞察—体验诊断—方案生成—人工决策—上线验证—知识回流”的体验闭环。项目以企业级 B 端产品实践为载体，形成由设计助手、体验洞察、协同编排和质量治理组成的可运行体系，使 AI 负责规模化处理与结构化产出，使人聚焦业务判断、方案取舍和价值决策。创新不在于“用 AI 多画几张图”，而在于让体验设计从一次性交付升级为可追溯、可复用、可验证的持续运营能力。

# 项目背景、目的与意义

## 一、项目背景与痛点

企业级 B 端产品具有角色多、流程长、规则复杂、数据量大、业务风险高等特点。传统体验设计工作通常以需求评审、界面设计、设计走查和上线复盘为主，难以持续覆盖全量使用行为和多源问题信号。

| 典型痛点 | 具体表现 | 对业务与体验的影响 |
|---|---|---|
| 体验问题发现滞后 | 问题往往在上线后、咨询集中或负面反馈放大后才被发现 | 用户反复受阻，处理成本和风险上升 |
| 多源信息割裂 | 行为记录、咨询反馈、访谈和页面走查分散在不同工具与角色中 | 难以判断问题范围、优先级和可信度 |
| 人工分析覆盖有限 | 高频事件、长链路任务和多版本页面难以逐项分析 | 设计判断依赖抽样与个人经验，复用性不足 |
| 方案交付缺少闭环 | 设计师交付方案后，效果回检常由不同团队完成或被搁置 | 难证明设计价值，经验无法沉淀 |
| AI 输出难以直接信任 | 大模型可以快速生成结论，但可能混淆事实、推测和建议 | 若无约束直接进入决策，存在误判风险 |

## 二、项目目的

项目旨在探索 B 端体验设计师在 AI 时代的新工作范式：从“以界面为中心的方案产出者”，转型为“以体验系统为中心的 AI 原生产品体验架构师”。

具体目标包括：

1. 将需求、业务规则、行为记录、咨询反馈、访谈和页面等分散信号接入统一体验洞察链路，实现更早识别和更完整诊断。
2. 将体验专家的判断标准沉淀为 AI 可执行的技能、规则、知识库和验收场景，提升经验的可复制性。
3. 通过证据治理和人工确认关卡，确保 AI 输出“有来源、有边界、可复核”，不以概率性结论替代业务决策。
4. 建立从问题发现、解决到效果回检的持续闭环，让体验优化可量化、可追溯、可积累。

## 三、项目意义

对产品体验而言，项目使设计能力从有限抽样走向规模化洞察，并通过可验证的证据链提升结论可信度。对业务运营而言，项目将体验问题由“被动响应”前移为“主动发现与分层治理”，支持更合理地配置研发与运营资源。对组织能力而言，项目把专家个人经验转化为可复用的数字资产，为不同 B 端场景提供可迁移的 AI 体验治理框架。

# 价值分析

## 一、业务价值

项目建立了以事实和用户信号为基础的问题优先级机制：AI 对行为、反馈和界面风险进行规模化结构化处理，设计师结合业务影响、可靠性与改造成本进行人工裁定。这样可使有限的优化资源优先投向影响范围大、信号充分、可验证的体验问题，降低因“凭直觉排优先级”带来的资源错配风险。

在已开展的试点探索中，体系可识别高优先级体验风险、聚类高频用户诉求，并将客观行为、主观反馈和界面观察分别保留其适用边界；相关量化指标须以最终参赛材料中的经审核数据源为准，不将候选问题数量直接等同于实际业务损失。

## 二、效率价值

| 工作环节 | 传统模式 | AI 原生体验架构模式 | 预期改善 |
|---|---|---|---|
| 问题收集 | 人工汇总多系统信息 | 技能按统一契约读取、解析与结构化 | 减少重复整理和遗漏 |
| 体验诊断 | 抽样分析、经验判断 | 全量或大样本数据计算 + 分层分析 | 扩大覆盖面，提升定位速度 |
| 证据核验 | 反复跨团队查找来源 | 每条结论保留来源、版本、限制和关系 | 缩短复核与沟通链路 |
| 方案衔接 | 分析报告与设计方案常脱节 | 根因候选、问题框定、体验蓝图连续交接 | 提升方案可解释性 |
| 上线回检 | 临时复盘、口径不一 | 基线、护栏与回检规则前置定义 | 支持持续验证 |

## 三、成本与风险价值

项目不将“AI 自动决策”作为目标，而以降低错误决策风险为核心价值。通过口径确认、证据提升、根因确认和方案发布四类人工关卡，AI 在关键条件不满足时必须停止或降级输出；失败运行不覆盖既有成功结果；未经审核的候选结论不可被下游直接作为正式事实使用。该机制有助于控制 AI 幻觉、数据口径不一致和跨场景误用等风险。

# 项目方案

## 一、总体设计

项目以“四项核心能力 + 协同工作流 + 质量底座”构成整体方案。四项核心能力分别为需求理解、体验洞察、方案共创和效果验证；协同工作流负责智能体编排和标准交接；质量底座保证每次运行、每项结论和每个方案受控可追溯。

```text
需求 / 业务问题 / 真实数据 / 用户反馈 / 页面材料
                     │
      ┌──────────────┴──────────────┐
      │                             │
需求理解与体验设计                 体验洞察与效果验证
需求澄清 → 用户任务 →              行为信号 / 用户反馈 / 页面观察
旅程分析 → 体验蓝图 →              → 问题机会 → 方案假设
页面规格 / 异常态 / 视觉方向        → 方案验证 → 效果回检
      │                             │
      └──────────────┬──────────────┘
                     │
共享工作流：技能契约、依赖关系、制品登记、就绪判断、交接协议
                     │
质量底座：领域知识库、人工关卡、质量规则、验收场景、变更审计
```

## 二、产品方案

### （一）AI 技能体系：定义 AI 如何工作

AI 原生产品体验架构师的第一项工作，是把复杂的体验工作拆分为职责清晰的 AI Agent 技能。每项技能都定义输入、输出、可做事项、不可做事项及下游使用条件。例如，行为洞察负责识别任务路径、关键节点和人群差异；反馈洞察负责提炼主题与样本内信号；界面走查只输出可观察风险；问题综合只提出可被验证的问题假设，不自动确认因果。

这种“专业分工 + 明确契约”避免了一个泛化 AI 同时承担数据分析、界面判断、根因确认和业务决策所带来的能力越界。

### （二）证据治理：让 AI 输出可信可用

项目将各类分析产出统一为受控证据项，并为每项证据记录来源、版本、适用范围、可信度、用途限制和关联关系。治理过程分为三步：

1. **归一化与溯源：** 将客观、主观和启发式产出统一映射为结构化证据，并关联原始来源。
2. **关联与情境评估：** 区分佐证、反证、矛盾、范围限定和非独立等关系，标识产品变更、运营活动、培训或口径调整等混杂因素。
3. **生命周期与分级放行：** 将证据标记为候选、已发布、受限、被替代或归档；只有满足用途和审核条件的证据才能进入下游根因与方案环节。

### （三）人机协同关卡：定义 AI 不可逾越的边界

| 关卡 | 触发场景 | AI 的职责 | 人的职责 |
|---|---|---|---|
| 口径确认 | 指标分子、分母、任务边界存在歧义或变化 | 暂停关键计算并说明待确认项 | 确认业务口径 |
| 证据提升 | 分析发现需要成为正式依据 | 生成候选证据及限制说明 | 审核质量、来源、权限与适用范围 |
| 根因确认 | 候选根因将用于制定方案 | 提供症状—事实—机制—候选的推理链及反证 | 裁定根因、选择治理方向 |
| 方案发布 | 方案进入实施或对外传播 | 输出方案、风险与待决事项 | 审批实施与资源投入 |

### （四）领域知识工程：让专家经验成为可复用资产

项目将体验专家对业务流程、角色权限、字段口径、状态规则、常见风险和案例的隐性经验沉淀为结构化知识库。技能按“领域索引—领域入口—条目说明—原始知识”的最小必要路径读取知识，避免无关信息干扰。新发现的规律只能先形成知识候选，经人工审核后入库，确保知识库持续增长而不积累未经验证的“伪经验”。

## 三、技术架构

| 架构层 | 核心组成 | 主要作用 |
|---|---|---|
| 输入与接入层 | 需求文档、行为记录、服务反馈、页面材料、业务规则 | 提供多源体验信号 |
| AI 技能层 | 需求理解、任务分析、反馈洞察、界面走查、问题综合、体验蓝图、效果回检等 | 按边界完成专业化处理 |
| 共享编排层 | 技能拓扑、输入输出契约、制品登记、就绪判断、交接协议 | 管理依赖、版本和执行秩序 |
| 证据治理层 | 证据标准化、关系识别、情境评估、生命周期和审核放行 | 保证结论可追溯、可复核、可控使用 |
| 体验运营层 | 问题分级、方案治理、回检指标、知识回流、可视化报告 | 形成持续改进闭环 |
| 变更治理层 | 项目目标、不变量、验收场景、预检和回归验证 | 保证体系迭代不破坏既有能力 |

## 四、典型应用场景

以复杂业务流程体验优化为例：系统接入行为记录、服务反馈、业务规则和页面材料后，AI 识别任务路径、退出节点与常见诉求；再结合界面走查形成体验机会清单。各类信号保留来源和适用边界，供设计师判断问题优先级并提出可验证的方案假设。经人工确认后，方案进入设计与实施；上线后再以预先定义的基线和护栏指标回检效果。全过程中，AI 处理规模和结构，人负责判断、取舍和授权。

# 技术方案详解

## 一、技能套件架构：从"功能堆叠"到"契约化协作"

技能套件与"把多个 Skill 放在一起使用"的根本区别在于：套件中的每个 Skill 通过状态机驱动执行、版本化上下文契约和边界硬门禁三项机制，形成确定性的协作关系——上游的输出是下游的输入契约，每个 Skill 的职责边界不可逾越，执行顺序有推荐但不强制。这三项机制共同构成套件的"协作骨架"，使多个专精 Skill 能够像设计师团队一样分工协作，而非各自为战。

```text
              技能套件协作架构
              ─────────────────────────

  PRD 文档 ──→ prd-review ──→ experience-blueprint ──→ page-spec ──→ ux-proto-g
               需求审查         体验蓝图               页面规范        原型生成
                  │                │                    │               │
                  ▼                ▼                    ▼               ▼
              需求基线 .md       体验蓝图 .md         页面规范 .md    可交互原型
              需求基线 .json    体验蓝图 .json       页面规范 .json   代码评分
                  │                │                    │               │
                  └─── shared-workflow/ ──────────────────────────────┘
                       skill-graph.json   依赖关系声明
                       next-skill.md      就绪判断推荐
                       context-schema.md  数据交接契约
```

### （一）机制一：状态机驱动执行流程

每个 Skill 内部定义固定的阶段序列，每个阶段有明确的输入条件、输出物和完成判定。AI 不能跳过阶段、不能合并阶段、不能在条件不满足时强行进入下一阶段。

以需求审查 Skill 为例，其执行阶段为：

```text
INIT(初始化) → TARGET_BINDING(目标绑定) → KNOWLEDGE_COVERAGE(知识覆盖) → SEMANTIC_MODELING(语义建模) → OUTPUT(产出输出)

阶段                  动作                            完成条件
─────────────────────────────────────────────────────────────────────────
TARGET_BINDING        绑定目标 PRD 文件                用户显式提供路径或附件
KNOWLEDGE_COVERAGE    交叉引用业务知识库               相关知识文件已读取
SEMANTIC_MODELING     提取角色/任务/规则/边界/异常      语义结构完整
```

其中 TARGET_BINDING 阶段设有硬门禁：只接受用户显式提供的文件路径、附件或粘贴文本，禁止自动扫描项目目录。这确保了 AI 不会在未经授权的情况下读取不相关的文件。

状态机将"设计师脑中的工作流程"转化为可审计、可追溯的显式规则——AI 无法跳过知识覆盖直接生成结论，也无法忽略语义建模凭直觉推断。

### （二）机制二：双轨输出 + 版本化上下文契约

每个 Skill 同时输出两份产物：Markdown 正式语义文档（供人阅读评审）和 JSON 结构化投影（供下游 Skill 机器消费）。两份产物来自同一次生成，语义一致性由 Skill 内部逻辑保证。

所有 JSON 产物均标注版本号（如 requirements-baseline v2.0、experience-blueprint v4.0、page-spec v1.0/v2.0/v3.0）。下游 Skill 通过共享工作流层声明兼容的上游版本范围；版本不匹配时直接拒绝处理并报告，而非默默接收可能出错的数据。

```text
prd-review                 experience-blueprint             page-spec
┌─────────────┐            ┌─────────────┐                  ┌─────────────┐
│ 需求基线.md  │──人读──→  │ 体验蓝图.md  │──人读──→        │ 页面规范.md  │──人读──→
│ 需求基线.json│──机读──→  │ 体验蓝图.json│──机读──→        │ 页面规范.json│──机读──→
│  v2.0       │            │  v4.0       │                  │  v1.0-3.0   │
└─────────────┘            └─────────────┘                  └─────────────┘
       ▲                          ▲                              ▲
       │     版本契约校验           │      版本契约校验              │
       └── 不匹配则停报 ──────────┘── 不匹配则停报 ───────────────┘
```

双轨机制的目的是让设计师和 AI 在同一条信息链路上工作：设计师读 Markdown 判断语义是否正确，AI 读 JSON 获取结构化参数。两者面对的是同一份事实，版本契约防止上下游静默错位。

### （三）机制三：边界硬门禁

每个 Skill 的 SKILL.md 文件中明确定义"不负责范围"作为硬约束。例如：需求审查 Skill 负责语义建模和需求基线，但不替产品决定业务答案；体验蓝图 Skill 负责体验设计方案，但不负责页面组件选型或技术实现方案。当某个需求涉及多个 Skill 的职责交叉时，当前 Skill 标注"待确认"而非自行越界处理。

```text
  prd-review               experience-blueprint           page-spec
  ┌────────────────┐       ┌────────────────┐       ┌────────────────┐
  │ ✓ 语义建模      │       │ ✓ 体验策略      │       │ ✓ 交互细节      │
  │ ✓ 需求基线      │       │ ✓ 主/异常流程   │       │ ✓ 区域与字段    │
  │ ✓ 缺失识别      │       │ ✓ 页面方向      │       │ ✓ 线框图        │
  │                │       │                │       │                │
  │ ✗ 业务决策      │       │ ✗ 组件选型      │       │ ✗ 代码生成      │
  │  → [待确认]     │       │  → [待确认]     │       │  → [待确认]     │
  │   交产品经理    │       │   交下游Skill   │       │   交ux-proto-g  │
  └────────────────┘       └────────────────┘       └────────────────┘

  触发越界时：
  用户需求 → Skill 边界检查 → 超出范围？
                                ├─ 否 → 正常处理
                                └─ 是 → 标注 [待确认] + 归属建议 → 停止
```

边界规则不是抽象的原则描述，而是硬编码在 SKILL.md 中的可执行指令，AI 在生成过程中直接遵循。这有效防止了大模型常见的"万能倾向"——什么都想回答、什么都想覆盖。

## 二、四个 Skill 的职责边界与协作方式

| Skill | 输入 | 输出 | 核心职责 | 不负责 |
|---|---|---|---|---|
| prd-review（需求审查与基线） | PRD 文档 + 业务知识库 | 需求基线（.md + .json v2.0）+ 审查问题清单 | 语义建模、需求缺失识别、业务规则交叉验证 | 不替产品决定业务答案 |
| experience-blueprint（体验蓝图） | 需求基线 + 用户旅程 + 用户故事 + 业务知识库 + 设计策略 | 体验蓝图（.md + .json v4.0） | 体验策略制定、主/异常流程设计、页面方向定义 | 不做页面组件选型 |
| page-spec（页面规范） | 体验蓝图 + 设计语言 + 用户故事 | 页面规范（.md + .json v1.0-v3.0）+ 线框图 | 蓝图到页面的映射、交互细节、区域与字段定义 | 不生成可运行代码 |
| ux-proto-g（原型生成） | 页面规范 + 设计语言 + 体验蓝图 | 可交互 HTML 原型 + 代码评分反馈 | 前端代码生成、视觉还原、质量评估 | 不做体验策略判断 |

四个 Skill 有推荐的执行顺序（prd-review → experience-blueprint → page-spec → ux-proto-g），但不是强制的线性链路。设计师可以根据实际需要灵活调整：简单页面改版可以跳过需求审查直接从体验蓝图开始；紧急需求可以从任意环节切入，独立模式下每个 Skill 均可单独运行。这种弹性由共享工作流层的"推荐而非阻断"机制实现——共享工作流只告知"建议先做 X"，不阻止设计师直接启动 Y。

## 三、共享工作流层：协调而不控制

共享工作流层（shared-workflow/）是套件的中枢神经，由三个协议文件组成，分别负责 Skill 间的依赖声明、就绪判断和数据交接：

```text
shared-workflow/
├── skill-graph.json     ← 依赖关系图（静态参考）
│     定义 15 个 Skill 的上下游关系、
│     必需前置（required）和推荐流向（next_hint）
│
├── next-skill.md        ← 就绪推荐算法（动态判断）
│     扫描 spark-output/context/*.json →
│     构建已完成集合 → 判定哪些 Skill 可以启动
│
└── context-schema.md    ← 上下文契约规范（数据交接）
      定义每个 Skill 输出 JSON 的字段结构、
      类型约束和版本要求
```

skill-graph.json 是静态参考，描述 Skill 之间的拓扑关系和推荐流向；next-skill.md 定义就绪判断算法——扫描已有产物、构建已完成集合、输出可启动推荐；context-schema.md 规范跨 Skill 交接的数据结构，确保字段名、类型和版本约束一致。

这套机制的核心设计哲学是"协调而不控制"：共享工作流只提供建议和就绪判断，不设硬性阻断。所有推荐都是辅助性的，决策权始终在设计师手中。当上游 Skill 缺失时，系统给出柔性降级提示（如"建议先运行体验蓝图以获得更完整的输入"），而非报错停止。设计师可以选择接受建议，也可以在明确风险后直接继续。

## 四、质量治理：证据链与人工关卡

质量治理依赖两项核心机制：

证据链追溯——每个 Skill 的输出必须标注判断来源和依据，下游 Skill 消费上游产物时会验证其完整性，确保整条判断链透明可追溯。以商机中心案例为例，体验蓝图的每个设计判断都标注了来源（需求基线某条/知识库某文件/推导逻辑），页面规范的每个区域定义都标注了对应的蓝图章节，原型的每个页面都对应页面规范中的具体条目。

人工关卡——系统设置四类关卡（指标确认、证据提升、根因确认、方案放行），设计师在关键节点确认后才推进，AI 只在授权范围内工作。这确保了每个阶段性结论都经过人工审核，而非 AI 自行推进到最终输出。

# 落地实践与验证成效

## 一、典型案例：商机中心体验设计

商机中心是某企业财富管理平台的重点模块，涵盖商机策略管理、客户管理、数据复盘和跨系统（CRM）跳转四个核心场景。该需求由团队设计师使用 Skill 套件完成从 PRD 到可交互原型的全流程，经历了四个关键阶段：

```text
PRD 文档    需求基线       体验蓝图        页面规范×7      HTML 原型×7
+知识库  →  +问题清单   →  3 条关键判断 →  +线框图      →  评分 4.9/5
            5 条主流程      6 条异常流程
```

| 阶段 | 执行 Skill | 输入 | 关键产出 | 核心价值 |
|---|---|---|---|---|
| 需求审查 | prd-review | PRD 文档 + 业务知识库 | 需求基线（v2.0）+ 审查问题清单 | 语义建模识别 PRD 中多处定义空白，以"待确认"标注而非自行脑补 |
| 体验蓝图 | experience-blueprint | 需求基线 + 审查问题 + 知识库 | 体验蓝图（v4.0）：3 条关键判断 + 5 条主流程 + 6 条异常流程 | 做出"分层摘要 vs 平铺商机""状态分离"等关键体验判断 |
| 页面规范 | page-spec | 体验蓝图 + 设计语言 + 用户故事 | 7 个页面实体的结构化规范 + 线框图 | 蓝图到页面的精确映射，每个页面定义信息分区、字段结构和状态处理 |
| 原型生成 | ux-proto-g | 页面规范 + 设计语言 Token | 7 个可交互 HTML 页面 + CSS Token 系统 | 代码质量评分 4.9/5，品牌一致性完整 |

**阶段一：需求审查与基线建立。** prd-review Skill 读取商机中心 PRD 文档，交叉引用知识库中的权限模型、审批中台等相关文件，通过语义建模提取角色、任务、规则和边界。输出结构化的需求基线和审查问题清单，识别出 PRD 中多处定义空白——以"待确认"标注，交由产品经理裁定，而非 AI 自行填补。

**阶段二：体验蓝图制定。** experience-blueprint Skill 消费需求基线和审查问题清单，结合知识库做出三条关键设计判断：客户摘要采用分层展示（按角色聚合）而非平铺所有商机；商机状态与营销状态分离，允许独立推进；跨系统跳转失败作为体验问题而非纯技术问题处理。同时从角色旅程推导出 5 条主流程和 6 条异常流程的设计方向。

**阶段三：页面规范细化。** page-spec Skill 消费体验蓝图，将 7 个核心页面映射为结构化规范，每个页面定义信息分区、字段结构和状态处理规则，并附带线框图作为原型生成的直接参照。

**阶段四：原型生成与质量评估。** ux-proto-g Skill 消费页面规范和设计语言 Token 文件，生成 7 个可交互 HTML 页面，包含完整的 CSS Token 系统。原型在品牌色系、间距节奏和组件风格上与设计语言保持一致，自动代码质量评估得分 4.9/5。

值得关注的是，全流程中每个 Skill 的产出都基于上游 Skill 的结构化产物——需求审查的问题来自 PRD 与知识库的差异分析，蓝图的判断来自需求基线与知识库的交叉推导，页面规范来自蓝图的流程推导，原型来自规范和 Token。这条证据链确保了任何质量问题都可以向前追溯到具体环节。

如果没有套件机制，单独使用大模型容易出现以下问题：需求分析时自行脑补业务规则，体验设计时跳到组件选型而忽略体验层面判断，页面规范时遗漏异常状态处理，原型生成时偏离设计语言一致性。Skill 套件通过职责边界和版本化契约将这些行为限制在可控范围内。

## 二、已验证的能力数据

Skill 套件已在商机中心等真实业务需求中完成全流程验证，各项核心能力均已确认可用。具体量化数据（包括单需求处理耗时、覆盖页面数、与传统模式的效率对比等）将由团队后续补充。

## 三、套件的可复制性

整套 Skill 套件的协调规则以 JSON 和 Markdown 文件形式存在于项目仓库中，不依赖特定 AI 平台或运行时环境。理论上，任何支持 Skill 定义文件读写的 AI 平台均可接入这套协议。

其他团队复用该套件时，只需部署相同的 Skill 定义文件和共享工作流层。共享工作流层的文件（skill-graph.json、next-skill.md、context-schema.md）本身与业务无关，可原样复用；Skill 定义可根据团队需要灵活增减——通过版本化契约机制，新增 Skill 不会破坏已有 Skill 的协作链路。

# 项目创新总结（建议保留的自定义章节）

## 一、从“设计界面”到“设计 AI 如何设计”

项目将设计对象从单个页面上移到整个体验生产系统。设计师不只给出方案，还要定义 AI 的输入、输出、协作方式、边界和验收方法；核心交付物从静态方案扩展为可运行的技能体系与工作机制。

## 二、从“经验驱动”到“证据治理驱动”

项目不把 AI 生成内容直接视为结论，而是建立来源、版本、情境、关系、生命周期和用途约束组成的证据治理机制。设计师的质量把控也由走查单一页面，升级为走查贯穿分析、判断与决策的证据链。

## 三、从“单次交付”到“持续运营闭环”

项目将问题发现、优先级判断、方案设计、实施治理与效果回检连接为可重复运行的闭环。每轮运行产生的已审核知识和验证结果可在边界内回流，为下一轮体验优化提供更可靠的起点。

## 结语

本项目探索的不是“设计师如何更快地使用 AI”，而是“体验设计如何成为 AI 时代可治理的组织能力”。当设计师能够定义 AI 如何识别问题、如何形成证据、如何提出候选、何时交还人类并如何验证结果，B 端体验工作便可从手工作坊式交付，演进为面向复杂业务持续运行的体验架构能力。
