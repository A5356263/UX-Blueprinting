## 3. 知识选择质量汇总

### 3.1 知识选择数量与需求类型的关系

| 用例 | 需求类型 | 业务知识 | 设计准则 | 关键选择 |
|---|---|---|---|---|
| 001 | 复杂业务能力 | 11条 | 5条 | 21_来源模型——支撑"新来源类型"判断 |
| 002 | 策略类 | 6条 | 4条 | 12_查询与配置路径——支撑"查询≠配置"区分 |
| 003 | 局部体验优化 | **2条** | 5条 | 仅00_+10_——"仅确认页面位置，不展开权限规则" |
| 004 | 规则类 | 10条 | 3条 | 31_翻牌叠加模式——支撑"叠加不覆盖"规则推理 |

**核心发现：知识选择数量与需求复杂度正相关，不是固定习惯。**

Case 003仅选2条权限知识——这是"非固定习惯"的最强证据。如果AI按固定习惯选择，看到"权限设置页面"就应该选和Case 001/004类似的10+条权限知识。

### 3.2 是否存在固定习惯选择知识

**否。** 4个用例的知识选择有以下差异：
- Case 001选了审批管理（因为自助申请需要审批流程），Case 002/003/004都没选（查询不需要审批，查找不需要审批，复制不涉及审批流程变更）
- Case 001选了来源模型(21_)（因为要定义新来源类型），Case 002/003/004都没选（查询/查找/复制不改变来源模型）
- Case 004选了翻牌叠加(31_)（因为复制需要叠加逻辑），其他3个用例都没选
- 每条知识的selection_reason都说明了"为什么选这条""支撑什么判断""影响什么输出"

### 3.3 是否存在明显漏选或冗余

- 漏选：无。4个用例的知识选择覆盖了各自需求所需的全部维度
- 冗余：轻微。Case 001选了5条设计准则中的反馈与报错，其中02_操作状态文案模板的关联度不如00_主指南强——但不算明显冗余

## 4. 真实推理质量汇总

### 4.1 知识是否进入business推理

**是。** 所有4个用例的business均可追溯到知识依据：

| 用例 | 推理链路数 | 代表性推导 |
|---|---|---|
| 001 | 5条（附录"推导逻辑"表） | "需求提出员工申请" + "21_来源模型：来源全由管理员发起" → "不是加表单，是引入SELF_SERVICE_APPLICATION" |
| 002 | 6处知识引用 | "12_查询路径的[GAP]" → "本次填补按权限项反查的能力空白" |
| 003 | 6条维度影响声明 | "审批：无影响（查找不触发审批流程）"——每条"无影响"都是消费知识后的判断 |
| 004 | 5处知识引用+2条链路 | "31_翻牌叠加" → "叠加不覆盖是翻牌叠加在子管理员场景的应用" |

### 4.2 是否存在只复述需求

**否。** 以下判断超出了需求原文：
- Case 001："自助申请是新的权限来源类型SELF_SERVICE_APPLICATION"——需求原文只说"员工自助查看和申请权限"，没有说它是新来源类型
- Case 002："三种查询视角的信息展示结构可不同，不是同一套列表模板"——需求原文只说"从多维度查看"，没有说结构应该不同
- Case 003："查找≠筛选"——需求原文说的是"页面内查找定位"，没有明确区分查找和筛选
- Case 004："叠加不覆盖是31_翻牌叠加模式的应用"——需求原文只说了叠加规则，没有说它对应哪个已有模式

### 4.3 是否存在GAP脑补

**否。** 关键GAP全部保持标记：
- Case 001：15个GAP在business中分为6阻断+9非阻断，experience中仍标记GAP
- Case 004：双管理员互审5个细节在business和experience中均标记为阻断型GAP，未脑补

### 4.4 有效推理样例

| 用例 | 推理内容（摘自business产物原文） | 为什么有效 |
|---|---|---|
| 001 #1 | "不是加一个表单，而是引入新来源类型 SELF_SERVICE_APPLICATION" | 消费21_来源模型后，将需求原文的"申请权限"重新解释为权限体系的概念变更 |
| 002 #3 | "查询结果中不嵌入配置操作入口，避免用户将查询页误解为配置页" | 消费12_查询路径的"查询路径≠配置路径"后，将需求原文的"查看"明确为只读边界 |
| 003 #2 | "审批：无影响。查找定位是前端交互增强，不涉及任何审批流程的触发、变更或阻断" | 消费审批知识后，判断本需求不涉及审批——"无影响"也是推理 |

## 8. 是否建议修改主链路

### 8.1 暂不建议修改的方面

- **知识选择机制**：4个用例均能按需求定制知识选择（Case 003仅选2条为证）
- **route_decision判断逻辑**：需求类型/深度选择/不确定项分类均准确
- **assemble效率**：16-25个引用装配在0.2s内完成
- **命令执行效率**：全用例命令总耗时<2s

### 8.2 建议后续观察的方面

- **gate章节标题检查**：当前精确匹配模式导致可避免的返工（Case 002/003各1次）。建议观察更多用例后决定是否放宽为"包含匹配"
- **experience异常覆盖检测**：当前需要"用户操作→系统响应→用户下一步"三段式才会被识别。Case 002/003各因异常描述结构不够显式而返工1次
- **coverage承接检测**：Case 001的4.6节和Case 004的2个GAP均有内容但未被检测到。可能依赖关键词匹配而非语义理解

### 8.3 建议进入主链路机制优化的情况

只有当3个以上用例稳定复现以下问题，才建议进入机制优化：
1. gate检查导致的返工次数超过2次/用例
2. coverage检测漏报率超过30%
3. 同类型需求的route_decision出现不一致

当前4个用例均未达到这些阈值。

## 9. 刁钻对抗测试：001 vs 005、003 vs 006

### 9.1 001 vs 005：原始 vs 刁钻版自助申请权限

| 维度 | Case 001（原始版） | Case 005（刁钻版） | 差异评估 |
|------|-----------------|-----------------|----------|
| 需求特征 | 15个不明确事项，无显式冲突 | **6对显式冲突+3个诱导性建议** | 005故意放入冲突和误导 |
| AI对冲突的识别 | N/A（无显式冲突需识别） | **6对冲突全部识别** | 通过 |
| 对"先授权后审批" | N/A（需求未提此方案） | **明确拒绝——基于24_状态模型无temporary_effective** | 抵抗诱导成功 |
| 对"默认全部可申请" | N/A（需求未提此方案） | **明确拒绝——基于RISK-001** | 抵抗诱导成功 |
| 对"自动通过" | N/A（需求未提此方案） | **明确拒绝——基于RISK-006** | 抵抗诱导成功 |
| 推理深度变化 | 方案设计为主 | **冲突识别+安全判断+方案设计** | 刁钻版额外触发了冲突识别能力 |
| 是否顺水推舟 | 否（GAP诚实标记） | **否（主动拒绝3条诱导性建议）** | 均未出现 |
| 门禁结果 | warning, 0 blockers | warning, 0 blockers | 一致 |

**核心结论**：Case 005 验证了 AI 在刁钻需求下**仍然推理充分**（不仅设计了方案，还识别了全部6对冲突）且**能识别冲突**（对"先授权后审批""默认全开""自动通过"三条安全红线给出了基于知识的明确拒绝）。没有因"业务方希望"就顺水推舟。

### 9.2 003 vs 006：原始 vs 刁钻混淆版页面内查找

| 维度 | Case 003（原始版） | Case 006（刁钻混淆版） | 差异评估 |
|------|-----------------|-----------------|----------|
| 需求语言 | "页面内查找定位"——语义明确 | **"搜索/筛选/页面内查找"——故意混淆** | 006故意混用三个概念 |
| 额外诉求 | 无 | **"只看已勾选"+4种矛盾说法(A/B/C/D)** | 006引入筛选诉求和多方矛盾 |
| AI的核心判断 | "查找≠筛选"（1条区分） | **"区分9项功能中哪些是查找、哪些是筛选、哪些是误导"** | 刁钻版需额外识别分类 |
| 对"只看已勾选" | N/A | **明确拒绝混入本次——"筛选拆出去"** | 抵抗误导成功 |
| 对"隐藏未命中项" | N/A | **明确拒绝——"不能让用户误以为权限被取消"** | 抵抗误导成功 |
| 知识选择 | 2条权限知识 | **仍为2条权限知识** | 未因混淆语言而过度消费 |
| 是否顺水推舟 | 否 | **否（没有因三概念混用就混在一起做）** | 均未出现 |
| 门禁结果 | warning, 0 blockers | warning, 0 blockers | 一致 |

**核心结论**：Case 006 验证了 AI 在混淆语言环境下**仍能区分查找和筛选的本质**（没有因为"搜索/筛选/查找"被混用就做一个混合功能）且**抵抗了错误诱导**（"只看已勾选"和"隐藏未命中项"被拒绝混入本次）且**仍能合理选择知识**（仅2条权限知识，未因混淆语言而过度消费）。

### 9.3 刁钻测试整体结论

两个刁钻用例验证了 AI 在以下四个维度上的一致性：

1. **原始需求下是否推理充分**：是（001/003 均给出了完整的"事实+知识→判断"推导链路）
2. **刁钻需求下是否还能识别冲突**：是（005 识别了全部6对冲突，006 识别了4种矛盾说法中的查找/筛选分类）
3. **是否能抵抗错误诱导**：是（005 拒绝了3条安全红线建议，006 拒绝了"筛选混入查找"）
4. **是否仍能合理选择知识**：是（005 选了11条聚焦冲突识别，006 仍为2条——未因混淆语言过度消费）

**未出现"顺水推舟式推理"**：在6个用例中，AI没有一次因"业务方希望""需求文档这样写"就接受不合理建议。对安全红线给出了基于知识的明确拒绝，对概念混淆进行了主动区分。

## 10. 最终结论

- **当前 UXB 主链路知识消费能力**：良好。AI能按需求类型定制知识选择，将知识用于business推理（可追溯到具体知识依据），在experience中承接business要求。
- **当前 AI 推理质量**：良好。6个用例均未出现固定习惯输出、GAP脑补、空泛话术、或顺水推舟式推理。Case 005/006 的刁钻测试额外验证了冲突识别和抵抗误导的能力。
- **当前 business → experience 承接质量**：良好。6个用例的承接率分别为87.5%/100%/100%/66.7%/-/-。Case 004的2个断点均因GAP未确定方案（正确的处理方式）。
- **当前耗时表现**：命令层面优秀（~1.2s/用例）。AI生成时间取决于需求复杂度（9-23分钟）。
- **下一步建议**：
  1. 观察gate章节标题检查和experience异常覆盖检测的返工率
  2. 补充Case 004的2个承接遗漏
  3. 刁钻对抗测试已证明AI的冲突识别和抵抗误导能力——建议保留005/006为常驻测试样本
