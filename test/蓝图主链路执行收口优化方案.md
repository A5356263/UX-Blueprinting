# 蓝图主链路执行收口优化方案

> 重要：Code Agent 读完本文档后，必须先基于当前仓库代码快速核对这些问题是否仍真实存在；如果当前项目已修复其中某项，只需跳过该项，不要重复实现或引入新逻辑。  
> 适用项目：UX-Blueprinting  
> 目标读者：Code Agent / 项目维护者  
> 目标：修复主链路执行断点，让任务能自动完成 `facts → business → experience → preview`，并保持轻量、通用、可维护。  
> 核心原则：不恢复 `interaction_map`，不新增复杂中间产物，不让代码参与业务/体验推理，AI 负责生成，代码负责触发、检查、记录和展示。

---

## 1. 本次要解决的五个问题

本次只解决以下五项：

```text
1. Preview 自动生成，并在当前寄生 Code Agent 聊天窗口自动给用户可访问 URL
2. experience_blueprint.md 自动生成
3. Experience 阶段按需消费设计指南知识
4. Business 核心区机器化表达清理
5. generate-experience 没有真正触发 AI 读取并生成 experience_blueprint.md
```

其中第 2 点和第 5 点是同一个根因的两个表现：

```text
Experience 阶段的规范存在，但执行中枢没有真正触发 AI 生成正式产物。
```

---

## 2. 严格边界

本次禁止做：

```text
不恢复 interaction_map
不新增 experience_map_composer
不新增复杂 schema
不新增强中间产物
不让代码拼体验流程
不让代码生成具体文案
不做固定话术替换库
不写死权限场景
不把 Preview 变成正式产物
不让 Preview 失败影响主链路成功
```

必须保持主链路为：

```text
facts.md
↓
business_blueprint.md
↓
experience_blueprint.md
↓
runtime/preview/index.html
```

## 3. 问题一：Preview 自动生成并自动给 URL

### 3.1 是否要做

要做。

Preview 不是正式产物，但它是业务蓝图和体验蓝图的更好阅读形式。任务完成后应自动给用户可访问 URL，否则用户还要自己找文件或手动启动预览。

---

### 3.2 当前问题

如果主链路只用静态构建：

```text
serve=False
```

就只能生成：

```text
projects/<project-id>/runtime/preview/index.html
```

但不会启动服务，也不会输出：

```text
http://127.0.0.1:<port>/
```

---

### 3.3 正确方案

分两步：

```text
主链路完成后：
1. 自动生成 preview 静态文件
2. 自动启动 preview 服务，并把 URL 返回给当前 Code Agent 聊天窗口
```

Preview 失败不得影响主链路正式产物。

---

### 3.4 执行要求

`run-main` 结束后，如果未设置 `--skip-preview`，应执行：

```bash
python -m packages preview <project-id> --host 127.0.0.1 --port 0
```

并在聊天窗口输出：

```text
本地预览地址：http://127.0.0.1:<port>/
```

如果运行环境不能保持服务常驻，则至少输出静态文件位置：

```text
projects/<project-id>/runtime/preview/index.html
```

同时说明：

```text
Preview 已生成，但当前环境未启动本地服务。
```

---

### 3.5 输出要求

Preview 运行成功后必须写入：

```text
projects/<project-id>/runtime/preview/preview_runtime.json
```

至少包含：

```json
{
  "ready_state": "ready",
  "preview_url": "http://127.0.0.1:<port>/",
  "output_path": "projects/<project-id>/runtime/preview/index.html"
}
```

## 4. 问题二 / 五：experience_blueprint.md 自动生成

### 4.1 是否要做

必须做。

目标是：

```text
AI 自动走完 facts → business → experience
```

不能在 `generate-experience` 阶段停下来，让用户手动根据输入包生成。

---

### 4.2 当前问题

当前问题不是“缺少阅读说明”，而是：

```text
Experience 阶段有应该读什么的规范，
但 generate-experience 没有真正触发 AI 去读并生成 experience_blueprint.md。
```

所以不能再新增一层说明文件来解决。

---

### 4.3 正确方案

`generate-experience` 应真正成为 Experience Agent 执行点。

它必须：

```text
1. 读取 context_manifest.json
2. 读取 facts.md
3. 读取 business_blueprint.md
4. 读取 specs/10_experience_blueprint_contract.md
5. 读取 templates/experience_blueprint.template.md
6. 按需读取设计指南 wiki / raw
7. 由 AI 直接生成 workspace/experience_blueprint.md
```

代码只负责：

```text
触发 AI
提供权威文件路径
写入结果
检查章节
记录 provenance
```

代码不得：

```text
拼流程
补页面
生成具体文案
用模板硬凑体验蓝图
```

---

### 4.4 如果当前项目没有模型调用层

如果当前仓库没有独立模型调用能力，不要用代码伪造结果。

应改为：

```text
在寄生 Code Agent 的任务执行中，将 generate-experience 作为必须完成的 AI 写作步骤。
```

也就是 Code Agent 执行主链路时，不能只跑 Python 脚本后停住，而必须继续完成：

```text
读取权威文件
生成 experience_blueprint.md
写入 workspace
再执行 gate-experience / validate / preview
```

如果无法自动生成，则 `generate-experience` 不应静默成功，应明确失败或阻断：

```text
ERROR: experience_blueprint.md 未生成，generate-experience 未完成。
```

---

## 5. 关于 experience_blueprint_input.md

### 5.1 是否保留

不建议作为默认主链路产物保留。

它容易变成新的中间层：

```text
facts 二次摘要
business 二次摘要
guidelines 二次摘要
```

一旦摘要遗漏，体验蓝图就会遗漏，后续又会继续加规则修摘要，重新变重。

---

### 5.2 正确定位

如果确实需要排查，可以降级为 debug 文件：

```text
projects/<project-id>/runtime/debug/experience_prompt_preview.md
```

它只能用于调试，不作为主链路输入真源，不进入 workspace，不参与 preview，不作为正式评审材料。

---

### 5.3 Experience 的权威输入

Experience 应直接读取权威文件，而不是依赖二次摘要包：

```text
projects/<project-id>/runtime/context_manifest.json
projects/<project-id>/workspace/facts.md
projects/<project-id>/workspace/business_blueprint.md
specs/10_experience_blueprint_contract.md
templates/experience_blueprint.template.md
设计指南 wiki / raw
```

一句话：

```text
context_manifest 是地图；
facts / business / guidelines 是权威内容；
experience_blueprint_input 不应成为新的信息中间层。
```

## 6. 问题三：Experience 设计指南消费

### 6.1 是否要做

要做，但必须轻量。

设计指南不应像业务知识一样完全前置装订死。

正确方式是：

```text
业务知识：由 domain 决定，前置装配
设计指南：前置只提供导航，Experience 根据 Business 输出按需选择
```

---

### 6.2 实现方式

在 task card / context assemble 中支持：

```text
design_guidelines_refs
```

或在 `wiki_refs` 中放入设计指南导航，例如：

```text
knowledge/wiki/summaries/guidelines/README.md
knowledge/wiki/summaries/guidelines/interaction/README.md
knowledge/wiki/summaries/guidelines/copywriting/README.md
knowledge/wiki/summaries/guidelines/feedback/README.md
knowledge/wiki/summaries/guidelines/page_structure/README.md
```

只提供导航或 summary，不默认塞入全部 raw。

---

### 6.3 Experience 阶段选择规则

Experience 生成前必须先看 Business 的：

```text
推荐业务方案
必须守住的规则和边界
主要风险与保护策略
方案承接要求
待确认问题
```

再判断需要读哪些设计指南。

例如：

```text
涉及状态变化 → 读状态反馈指南
涉及失败/阻断 → 读异常反馈指南
涉及表单提交 → 读表单/文案指南
涉及弹窗/抽屉 → 读承载容器指南
涉及列表/记录 → 读列表/空状态/筛选指南
```

这些判断交给 AI，不写成代码硬规则。

---

### 6.4 记录要求

`knowledge_usage_report.json` 需要记录：

```json
{
  "stage_usage": {
    "experience": {
      "guideline_refs_used": [],
      "guideline_raw_refs_used": [],
      "guideline_selection_reason": []
    }
  }
}
```

这只是消费记录，不是复杂 schema，不参与生成推理。

---

## 7. 问题四：Business 机器化表达清理

### 7.1 是否要做

要做。

但不能做固定话术替换库。

---

### 7.2 正确方式

三层收口：

```text
1. spec 约束
2. AI 重写
3. 代码轻量检测
```

---

### 7.3 spec 约束

在 `specs/09_business_blueprint_contract.md` 和 `templates/business_blueprint.template.md` 中明确：

```text
Business 核心区必须是业务判断表达。
不得直接复制 facts 原文片段、流程箭头、source 标题、调研/竞品原句。
必须先理解含义，再用体验设计师能读懂的大白话改写。
无法稳定判断时，写入“待确认问题”，不得硬拼。
```

---

### 7.4 代码检测

`validate/core.py` 只做检测，不做替换。

核心区禁止大量出现：

```text
配置 支持配置
查看 查看权限
提交 目前企业的员工权限分配均由权限
M4_1 / M5 / Mermaid 节点
source_path
EV-xxx
用户调研规则
竞品分析规则
Runtime Task Goal
重复句
```

处理方式：

```text
少量出现：warning
核心区大量出现：blocker
```

然后由 AI 重新生成 Business，而不是代码修文案。

## 9. 验收标准

### 9.1 主链路验收

执行：

```bash
python -m packages run-main <project-id> --strict
```

通过标准：

```text
facts.md 自动生成
business_blueprint.md 自动生成
experience_blueprint.md 自动生成
gate / validate / coverage 正常执行
preview 自动生成
聊天窗口返回 Preview URL 或静态 index.html 路径
```

---

### 9.2 Experience 验收

通过标准：

```text
experience_blueprint.md 不需要手动生成
内容明显承接 business_blueprint.md 的推荐方案、规则边界、风险保护、方案承接要求
附录能说明使用了哪些事实、业务判断和设计指南
```

---

### 9.3 设计指南验收

通过标准：

```text
knowledge_usage_report.json 有 guideline_refs_used
如果读取 raw，则有 guideline_raw_refs_used
有 guideline_selection_reason
没有把全部设计指南 raw 一次性塞入 Experience
```

---

### 9.4 Business 表达验收

通过标准：

```text
business_blueprint.md 核心区没有明显机器化表达
推荐业务方案是自然业务语言
方案承接要求是可读业务骨架
调研/竞品信息被转写成业务判断，而不是原句搬运
```

---

### 9.5 Preview 验收

通过标准：

```text
runtime/preview/index.html 存在
聊天窗口能看到 URL 或静态路径
Preview 可切换 Business / Experience / 承接对照
Preview 不进入 workspace
Preview 失败不影响 facts / business / experience 正式产物
```

## 11. 最终结论

本次不是新增架构，而是修复执行断点：

```text
有规范 → 要真正自动执行
有 Preview → 要自动给用户
有设计指南 → 要让 Experience 按需消费
有大白话要求 → 要阻止机器化表达进入核心区
```

最终目标：

```text
AI 自动生成业务蓝图和体验蓝图；
代码只负责触发、检查、记录和预览。
```
