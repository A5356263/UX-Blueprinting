## 讨论结论

### 分享目标与听众

团队已经了解设计工作台能做什么。本次分享回答两个问题：DeepSeek Harness 的插件机制能扩展什么，我们为什么选择用插件承载 OpenFlow。表达优先用大白话，把每个技术概念落到一个动作或一份文件。

### 已确认的两页组合

1. **插件机制。** 用汽车选配引出按场景组合能力。车的例子说清楚「同一个底座可以选择装哪些东西」，再落到 Harness 的扩展能力：团队可以注册 Skill 和工具、挂自己的工作台页面、运行自己的业务逻辑。用「Skill 给方法、工具给动作、插件把这些能力装进同一个包」说明三者的关系。
2. **工作流的实现方式。** 用同一个问题比较三种做法：需求审核后，该等回复还是可以进入页面设计。往下讲清规则分别由谁执行、任务状态保存在哪里、下一步怎么拿到本任务的正式产物。现场直接从第二页切到插件实机演示。

### 为什么插件化

| 做法 | 稳定性由什么决定 |
|---|---|
| 将交接规则写进共享文件或封装成 Skill | 共享文件可以保存材料。在主要依赖自然语言规则的实现里，Agent 仍要选对能力、读对上下文、分清产物版本并主动执行下一步。漏读确认条件、把审核记录当成正式基线、误用旧任务文件，都可能改变结果。 |
| 将交接规则写成工作区脚本 | 给脚本相同的输入就能复用同一套判断。整条链路是否稳定还取决于触发机制、任务 ID 和文件参数从哪里来。若脚本由 Agent 自行决定何时调用，可能漏调、调晚或传错对象。把事件和参数约束接齐的工作区方案，也能实现稳定的交接。 |
| 将交接规则写成 Harness 插件 | 用户动作接到插件代码。工作台创建任务并给出任务 ID，登记工具按该 ID 和绑定会话写入产物，代码读取持久化记录来展示当前状态和下一步。团队可以按自己的业务定义状态、确认时机、产物登记条件和界面操作。 |

**演讲的核心倾向**是把「产品级」讲具体。流程能按需求定制，同时让同一条交接规则在相同条件下得到一致处理。Skill 继续负责审核、设计等专业判断。业务代码负责任务记录、状态校验和产物交接，下一步推荐由用户决定是否执行。这里的 **OpenFlow** 指团队这套设计工作流。 [工作台任务与产物运行逻辑](<E:/AI设计/体验蓝图构建思路/runtime/workbench.js:403>)

### 背景资料怎么用

- **Harness 教程**提供「汽车选配」类比。重点是从选择模块讲到团队可开发自己的能力和界面。
- **能力管理 HTML**提供「安装包 → 能力 → 本次调用」这个区分，借来解释插件、Skill 和工具。文章讨论的是能力有没有装上、能否被看见、这次是否用到。演示关注的是业务任务到哪一步、生成了什么、接下来能做什么。分享只用前一个区分作为第一页的解释。 [《Agent 能力管理：观测模型与原则》](<C:/Users/HP/Desktop/Agent 能力管理：观测模型与原则.html>)

### 实机演示的承接

沿用一条真实链路 **需求审核记录 → 用户回复 → 正式需求基线 → 页面规格**。在工作台上依次指出当前步骤、已登记的文件、下一步的「使用 Skill」入口。用这条链路把「状态有记录、下一步知道用哪份产物」讲实。
