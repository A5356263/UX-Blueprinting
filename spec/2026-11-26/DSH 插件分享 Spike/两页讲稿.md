## 第 1 页｜DeepSeek Harness 的插件是什么？

**像选汽车配置一样，可以给 Agent 按场景配能力。**

买车时，可以按需要选轮毂、HUD、座椅加热。配办公助手时，也可以按需要装上写作技能、文件工具和工作台界面。**Harness 的扩展还可以由团队自己开发**：我们可以新增一个专用页面、给模型一个能调用的工具，也可以写代码处理自己的业务流程。 [DSH 官方文档：客户端架构](https://deepseek-harness.github.io/deepseek-harness/reference/subsystems/web-client)

台上可以用你们自己的插件落地这三个概念：

- **Skill** 给模型一套做事方法，比如怎么审核需求。
- **工具** 给模型一个能执行的动作，比如登记一份正式基线。
- **插件** 把技能、工具、页面和背后的业务代码装进同一个安装包。

HTML 里最值得借用的是这句话的意思：**装的是插件包，用的是包里的具体能力。** 这样讲完，大家就知道为什么同一个 Harness 能装出不同的工作台。 [《Agent 能力管理：观测模型与原则》](<C:/Users/HP/Desktop/Agent 能力管理：观测模型与原则.html>)

## 第 2 页｜OpenFlow：谁来决定下一步？

用同一个问题对比：**需求审核做完了，系统怎么知道该等用户回复，还是可以进入页面设计？**

| 做法 | 这一步怎么发生 |
|---|---|
| **规则写进 Skill** | 模型要先选对 Skill，再从对话或文件里判断用户回没回、哪份是正式基线。任何一处读漏或认错，下一步就可能走偏。 |
| **代码放在 IDE 工作区** | 脚本只要被正确调用，同样可以稳定地检查状态。还要解决谁在什么时候调用它、怎么传对任务和文件。如果这一步仍由 Agent 自己决定，就可能漏调、晚调或传错文件。 |
| **做成 Harness 插件** | 用户点击执行，工作台直接调用自己的代码来创建任务。代码把任务和产物清单写到工作区，按任务 ID 关联起来。审核记录和正式基线分别登记，工作台读取这个记录来展示待确认事项或推荐下一步。 |

**台上可以这么讲：**  
「以前我写一句‘等用户回复后再生成正式基线’，模型每次都要自己弄清楚用户回没回、手上是哪一版。现在我们给任务建了一本账。审核记录存一条，正式基线存另一条。下一步要承接哪份文件，工作台按任务 ID 去拿。**专业判断继续交给 AI，流程的记录、校验和交接交给代码。** 所以我们既能自己定义状态、按钮和确认时机，也能让同一条规则每次按同样的方式执行。」 [任务创建与产物登记源码](<E:/AI设计/体验蓝图构建思路/runtime/workbench.js:403>)

讲完就切实机：**「我现在演示一遍，同一个任务的审核记录、正式基线和下一步，是怎么接起来的。」**
