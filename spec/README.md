# spec 文档归档规范

- 输出时间：2026-08-06 17:37:52 +08:00

## 1. 目录用途

`spec/` 用于保存 Skill、规则、流程和文档的优化依据与可执行实施文档。

每次优化必须保留两类文档：

1. 问题与讨论结论。
2. 具体优化实施文档。

## 2. 目录结构

```text
spec/
├─ README.md
└─ YYYY-MM-DD/
   ├─ {任务简洁名称}问题与讨论结论.md
   ├─ {任务简洁名称}优化V0实施文档.md
   └─ {任务简洁名称}优化V1实施文档.md
```

跨天产生的新优化，新增对应日期目录。日期使用 `YYYY-MM-DD`。

## 3. 文件命名与更新规则

### 3.1 问题与讨论结论

- 文件名：`{任务简洁名称}问题与讨论结论.md`。
- 同一天、同一任务的新增结论追加到同一文件。
- 每次追加使用二级标题，并在标题下写入本次输出时间。
- 只记录已确认的问题、依据、结论和边界。

### 3.2 优化实施文档

- 文件名：`{任务简洁名称}优化V{版本号}实施文档.md`。
- 每份实施文档单独创建，不覆盖上一版。
- 同一任务的多轮优化按 `V0`、`V1`、`V2` 递增。
- 是否为同一任务，以“任务简洁名称”是否相同判断。
- 每份文件标题下必须写入输出时间。

### 3.3 任务简洁名称

任务简洁名称应描述改动对象和主要目标，例如“对象选择与补充入口”。

名称保持简短、可区分。新增版本沿用同一名称；目标变化后使用新名称。

## 4. 具体优化实施文档写作规范

实施文档必须可直接交给 AI CODE 执行。只写最终结论和执行细节，不写任务摘要、讨论纪要或已否决方案。

### 4.1 核心要求

- 写清为什么改、改什么、在哪里改、如何改。
- 明确每个模块负责什么、不负责什么。
- 明确本次修改范围、依赖关系和执行顺序。
- 明确稳定规则、文件和模块中哪些不得修改。
- 信息不足时写入“待确认事项”，不自行补全未确认信息。
- 优先最小修改，不扩大职责，不顺带重构无关内容。
- 不使用“优化、完善、加强、调整”等抽象词代替具体动作。

### 4.2 固定结构

每份实施文档按以下顺序编写：

1. **背景**：说明当前实现、具体问题及影响。
2. **目标**：说明本次修改结果和不属于本次范围的内容。
3. **修改范围**：列出模块、目录或文件，说明每项修改目的；同时写明不修改范围。
4. **实施策略**：说明整体处理方式、模块协作关系、数据或状态流转和修改顺序。
5. **详细修改**：按模块或文件写清当前职责、具体新增或修改或删除或保留内容、输入输出和判断条件、上下游依赖、异常和边界、预期行为及不允许承担的职责。无法确认路径时，先写检查位置和判断标准，不编造路径。
6. **执行顺序**：按依赖关系列出实际步骤，并写明进入下一步的条件。
7. **红线**：明确稳定规则、不得扩大或迁移的职责、不得重复维护的逻辑、不得删除的依赖项、不得进行的无关重构，以及不得写成事实的未确认信息。
8. **注意事项**：说明兼容要求、上下游影响、修改前检查项，以及需要同步更新的配置、文档、示例或测试。
9. **验收方式**：说明检查哪些文件、运行哪些流程，并覆盖正常、异常和边界场景。
10. **验收标准**：用可判断通过或不通过的条件说明目标问题已解决、新旧流程符合预期、无关能力未受影响、红线未违反，且不存在职责越界、重复实现或无关改动。

### 4.3 输出要求

- 仅输出 Markdown 正式文档正文。
- 每项修改必须能追溯到明确问题和目标。
- 内容必须具体到 AI CODE 可以直接执行。
- 文档使用简体中文。
- 标题层级清楚；正文使用短段落、短句和必要列表。
- 每份文档在标题下写入输出时间，格式为 `YYYY-MM-DD HH:mm:ss +08:00`。

## 5. 写入前检查

1. 确认当天目录是否存在；不存在时创建。
2. 确认任务简洁名称和当前版本号。
3. 查找同一天、同一任务的问题与讨论结论文件；存在时追加，不存在时创建。
4. 为每次具体优化创建独立实施文档。
5. 写入后检查文件名、时间、标题层级和版本号。

## 6. Pack 资产修改统一红线

当实施目标是 UX Proto Pack 资产时，执行文档和实际修改必须同时遵守以下边界：

- 只允许修改目标 Pack 目录下的正式资产，包括该 Pack 的 `components/`、`templates/`、`patterns/`、`knowledge/`、`theme/` 和 `manifest.json`；未被实施文档列入修改范围的资产不得顺带修改。
- 不修改 Skill 本身的运行逻辑，包括 `SKILL.md`、命令入口、脚本、Core、runtime、构建器、上下文投递机制和工作区生成逻辑。
- 不修改 Ant Design、React、图标库及其他第三方依赖的组件源码、类型声明、运行时代码或 `node_modules/` 内容。
- 需要改变 Ant Design 组件表现时，只能在目标 Pack 的 Component、Template、Pattern、Knowledge 或主题配置中使用 Ant Design 已公开的 Props、语义样式、token 和公开类名能力完成。
- Ant Design 公开能力不能满足目标、必须侵入 Skill 或第三方组件才能实现时，停止该项并写入“待确认事项”，不得自行扩大修改范围。
- 不通过业务页面私有样式、物化后的页面副本或生成 HTML 代替正式 Pack 资产修改。

## 7. 当前 XFT 内容区布局契约（2026-09-04）

本节是当前 XFT Pack 的可执行资产契约。它取代 2026-09-03 文档中“业务页面模板各自提供主白板”的实现归属；历史文档保留为当时决策记录，不作为本契约的实现依据。

### 7.1 责任边界

- `XftApplicationFrame` 的 canvas 提供灰色工作区和四周 `--alias-space-4` 外部留白。
- `XftApplicationFrame` 在 canvas 内提供唯一白色工作表面；该表面只拥有白底、圆角、可用高度和外层滚动边界，内部 `padding` 固定为 `0`。
- 正式页面模板的根节点必须输出 `data-xft-workspace-layout="managed"`。框架检测到该根节点后，不为模板再包裹默认内容内边距。
- 模板根节点及其内部布局容器保持透明；模板只管理其正文、页面级贴边区和操作栏的位置。
- 未使用正式模板的页面不输出该标识。框架自动为其提供 `--alias-space-4` 的默认内容内边距。

### 7.2 内边距与可选区域

- 不根据是否出现 `Tabs` 组件改变框架或工作表面的内边距。
- 模板把明确的页面顶部贴边区域渲染在正文容器之外；正文中的 Tabs 必须作为正文内容渲染，正常受正文内边距约束。
- 模板正文容器自行使用所需的内边距。顶部贴边区、正文和底部 `XftContentActionBar` 由模板的固定 DOM 结构表达，不由框架猜测或由 Agent 判断。
- `XftContentActionBar` 的组件职责和样式不变。模板需要页面级底部操作栏时，将其作为正文的兄弟节点渲染；操作栏是否出现只影响该模板的布局，不影响框架的工作表面内边距。

### 7.3 代码级判定与验收

- 框架只以直接子节点的 `data-xft-workspace-layout="managed"` 判定是否取消默认内容内边距；不读取组件名称、props、Tabs 或 DOM 文本。
- 每个正式页面模板的根 DOM 都必须带该标识；这是一项源码和测试可检查的硬契约，不依赖提示词。
- 验收至少覆盖：普通未标识页面保留 16px 默认内边距；已标识模板的框架内容层为 0 padding；模板内部的 Tabs 位于顶部或正文中间时不会改变框架判定；底部操作栏不进入正文内边距。
