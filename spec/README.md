# spec 文档归档规范

- 输出时间：2026-08-06 17:37:52 +08:00

## 1. 目录用途

`spec/` 用于保存 Skill、规则、流程和文档的优化依据与可执行实施文档。

按任务需要选择文档，可以只写一类，也可以不单独建文档。

- **优化实施文档**：任务需要明确实施范围、执行顺序或独立验收时编写。用户明确要求时按要求编写。
- **问题与讨论结论**：仅在关键取舍、批准依据或跨会话协作结论需要独立追溯，或用户明确要求时编写。实施文档已能说明的常规决定可直接写在实施文档中。

## 2. 目录结构

以下是归档示例，按需创建对应文件。

```text
spec/
├─ README.md
└─ YYYY-MM-DD/
   ├─ {任务简洁名称}问题与讨论结论.md
   ├─ {任务简洁名称}优化V0实施文档.md
   └─ {任务简洁名称}优化V1实施文档.md
```

跨天产生的新优化，新增对应日期目录。日期使用 `YYYY-MM-DD`。

## 3. 文件命名与更新规则

### 3.1 问题与讨论结论

- 文件名：`{任务简洁名称}问题与讨论结论.md`。
- 同一天、同一任务的新增结论追加到同一文件。
- 每次追加使用二级标题，并在标题下写入本次输出时间。
- 只记录已确认的问题、依据、结论和边界。

### 3.2 优化实施文档

- 文件名：`{任务简洁名称}优化V{版本号}实施文档.md`。
- 每份实施文档单独创建，不覆盖上一版。
- 同一任务的多轮优化按 `V0`、`V1`、`V2` 递增。
- 是否为同一任务，以“任务简洁名称”是否相同判断。
- 每份文件标题下必须写入输出时间。

### 3.3 任务简洁名称

任务简洁名称应描述改动对象和主要目标，例如“对象选择与补充入口”。

名称保持简短、可区分。新增版本沿用同一名称；目标变化后使用新名称。

## 4. 具体优化实施文档写作规范

实施文档必须可直接交给 AI CODE 执行。只写最终结论和执行细节，不写任务摘要、讨论纪要或已否决方案。

### 4.1 核心要求

- 写清为什么改、改什么、在哪里改、如何改。
- 明确每个模块负责什么、不负责什么。
- 明确本次修改范围、依赖关系和执行顺序。
- 涉及跨模块交接、持久化格式或发布清单时，引用对应的正式合同或清单。只说明本次变化及其影响，避免重复维护字段、枚举和版本规则。
- 明确稳定规则、文件和模块中哪些不得修改。
- 信息不足时写入“待确认事项”，不自行补全未确认信息。
- 优先最小修改，不扩大职责，不顺带重构无关内容。
- 不使用“优化、完善、加强、调整”等抽象词代替具体动作。

### 4.2 写作检查清单

以下十项用于检查是否遗漏。普通任务可以合并重叠内容，只写清目标、改动、边界和验收。跨模块、跨分支、改变合同或涉及发布时，展开相关条目。

1. **背景**：说明当前实现、具体问题及影响。
2. **目标**：写清完成后可观察、可核验的结果和本次范围边界。实现步骤放在详细修改中。
3. **修改范围**：列出模块、目录或文件，说明每项修改目的；同时写明不修改范围。
4. **实施策略**：说明整体处理方式、模块协作关系、数据或状态流转和修改顺序。
5. **详细修改**：按模块或文件写清当前职责、具体新增或修改或删除或保留内容、输入输出和判断条件、上下游依赖、异常和边界、预期行为及不允许承担的职责。无法确认路径时，先写检查位置和判断标准，不编造路径。
6. **执行顺序**：按依赖关系列出实际步骤，并写明进入下一步的条件。
7. **红线**：明确稳定规则、不得扩大或迁移的职责、不得重复维护的逻辑、不得删除的依赖项、不得进行的无关重构，以及不得写成事实的未确认信息。
8. **注意事项**：说明兼容要求、上下游影响、修改前检查项，以及需要同步更新的配置、文档、示例或测试。
9. **验收方式**：写清要检查什么、如何检查，以及需要覆盖的正常、异常或边界场景。
10. **验收标准**：用可判断通过或不通过的条件说明目标问题已解决、新旧流程符合预期、无关能力未受影响、红线未违反，且不存在职责越界、重复实现或无关改动。

执行后简要记录实际验证结果，以及会影响判断的未验证事项。验收计划只写预期，结果只写已观察到的事实。涉及正式发布时，单独记录发布决定，实际发布须另获授权。

### 4.3 输出要求

- 仅输出 Markdown 正式文档正文。
- 每项修改必须能追溯到明确问题和目标。
- 内容必须具体到 AI CODE 可以直接执行。
- 文档使用简体中文。
- 标题层级清楚；正文使用短段落、短句和必要列表。
- 每份文档在标题下写入输出时间，格式为 `YYYY-MM-DD HH:mm:ss +08:00`。

## 5. 写入前检查

1. 先按目录用途判断需要哪类文档。同一未完成目标沿用原任务名称和版本规则。纯调查、故障定位或无可观察行为变化的局部修复，可按需记录，无需另建完整实施文档。
2. 确认需要写入后，再检查当天目录、任务简洁名称和版本号。
3. 需要独立记录讨论结论时，先查找同一天、同一任务已有记录。有新增结论就追加，首次需要记录时再创建。
4. 需要实施文档时，按版本规则新建独立文档。
5. 写入后检查文件名、时间、标题层级和适用的版本号。
