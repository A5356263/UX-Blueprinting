# Experience Blueprint 任务交互影响预判实施文档

## 1. 背景

Experience Blueprint 已具备角色任务、流程、页面、状态、异常、父级承载页和 Context 投影能力。近期测试中，需求已明确“按角色”与“按功能权限”两种可申请范围，蓝图在管理员配置流程中保留了该规则，但在员工申请流程中压缩为通用的“选择权限”，遗漏对象类型、候选来源和提交内容的交互差异，并自行写入未被证明的“单选”。

当前 `内部完整性推导` 先组装任务路径，再补充任务内触发与受阻转接。主路径容易先被固定为模块主动入口，原任务受阻后进入处理任务的场景未稳定进入流程总览、节点说明和页面承载。

当前 `§8` 使用“知识缺口”记录设计依据，部分文案会将蓝图已作出的体验决定表达为待确认事项，影响正式方案的确定性。

本次通过在既有路径组装前增加一项内部预判，保留现有主链和输出深度，使已确认的任务入口、交互分支和复用交接进入后续既有推导。

## 2. 目标

本次完成后，Experience Blueprint 应达到以下结果：

1. 每个已识别任务在组装路径前，完成主动入口、已证明的任务内受阻入口、状态后入口、交互分支和复用交接的内部判断。
2. 已确认的规则分支只要改变用户操作对象、候选来源、可见信息、提交内容或处理结果，均在流程与对应承载面落地。
3. 任务内触发在输入材料或已读取业务知识证明时，形成“原任务—受阻原因—处理入口—处理结果”的确定路径。
4. 复用能力按当前方案承载、复用能力、组件复用三层表达，当前页面入口与复用能力内部处理边界清楚。
5. `§8` 保留设计依据记录，使用“设计依据与适用边界”表达本次设计决定，不将体验判断写成待确认问题。

本次不处理：

- 不重写蓝图现有主推理链、章节骨架、页面设计规则、状态规则、父级承载页规则、知识消费机制或 Context 投影机制。
- 不修改 UXB、PRD Review、`shared-workflow/`、知识库正文、下游 Skill、Context Schema 或校验脚本。
- 不新增领域专属案例、固定页面、固定组件或固定业务分支。
- 不将未被正式输入或业务知识证明的能力写入蓝图。

## 4. 实施策略

### 4.1 保持现有主链

保留现有顺序：读取正式输入、读取当前需要的知识、内部完整性推导、流程与页面生成、Markdown 冻结、JSON 单向投影、结构校验。

本次只调整 `内部完整性推导` 的顺序：

```text
提取角色、任务、状态、异常与现有承载信息
→ 任务交互影响预判
→ 按任务闭环组装既有路径
→ 承载分类、父级页识别、页面信息性质与选择形态判断
→ 分配正文落点、生成前覆盖检查
```

“任务交互影响预判”是内部推理步骤。它不新增 Markdown 章节、Context 字段、JSON Schema、脚本校验或独立中间文件。

### 4.2 任务交互影响预判

对每个已识别的角色任务，按以下顺序判断：

1. 识别主动入口与状态后入口。
2. 检查输入事实和已读取业务知识是否证明：用户在另一原任务中会因可处理限制进入该任务。
3. 列出已确认的规则分支，判断每个分支是否改变用户操作对象、候选来源、可见信息、提交内容或处理结果。
4. 检查该任务是否使用已有页面、成熟基座或组件，并确认当前页面可提供的入口、已证实的输入输出和返回关系。

预判结果直接供现有“按任务闭环组装路径”“承载分类”“页面设计”和“生成前覆盖检查”使用。

### 4.3 证据与停止边界

- 输入事实或业务知识证明原任务受阻且存在当前处理或后续处理任务时，生成任务内触发路径。
- 已确认规则分支改变交互时，生成对应分支路径和承载面说明。
- 已有能力的输入、输出和返回关系被证明时，写入复用交接。
- 缺少会改变业务能力、任务结果、状态语义、权限、字段或承载方案的事实时，沿用既有停止规则返回上游。
- 体验层面的入口、解释时机、信息关系和任务编排由蓝图直接定案，并在 `§8` 记录依据与落点。

## 5. 详细修改

### 5.1 `.claude/skills/experience-blueprint/SKILL.md`

#### 当前职责

定义蓝图的输入读取、内部完整性推导、流程与页面生成、正式输出、自检和 Context 投影规则。

#### 具体修改

1. 将当前“第二步补充，识别任务内触发与受阻转接”移动到“第一步，从需求基线提取”之后、“第二步，按任务闭环组装路径”之前。

2. 将移动后的规则改写为“第二步，预判任务交互影响”，并写入以下固定判断顺序：

   1. 对每个已识别任务确认主动入口、状态后入口，以及输入已证明的任务内触发入口。
   2. 对每个已证明的任务内触发，确认原任务、受阻时机、限制原因、当前修正或已证明后续任务、已确认上下文与处理后去向。
   3. 对每个已确认规则分支，确认其是否改变用户操作对象、候选来源、可见信息、提交内容或处理结果。
   4. 对每个复用关系，确认当前方案承载的入口和结果、复用能力承担的内部处理、组件复用承担的内部交互。

3. 在“第二步，按任务闭环组装路径”中增加对预判结果的消费规则：

   - 已证明的任务内触发从原任务受阻节点进入路径，不从模块主动入口重新开始。
   - 会改变交互的规则分支分别形成路径节点或节点内明确分支。
   - 分支只改变说明文字时，写入对应的解释、反馈或文案，不额外制造路径。
   - 复用能力的当前方案入口、已知输入、结果承接和返回位置进入路径；复用能力内部页面和组件内部细节保持复用引用。

4. 在“第三步，对每个流程节点进行承载分类”后补充复用三层的分类说明：

   - 当前方案承载：本期页面或当前节点提供入口、说明、已知输入采集、结果展示或返回承接，按现有“新增或修改”规则处理。
   - 复用能力：已有基座或外部能力处理其内部配置、审批、选择或查询过程，按现有“复用引用”规则处理。
   - 组件复用：当前页面承载选择结果或触发入口，组件处理其内部检索、筛选与选择交互；组件不单独生成本期页面方案。

5. 在“第六步，执行生成前覆盖门禁”中增加两项检查：

   - 每个已确认、且会改变用户操作对象、候选来源、可见信息、提交内容或处理结果的规则分支，均能在 `§2` 找到流程承接，并在相关 `§3`、`§4` 或 `§6` 找到交互承接。
   - 每个已确认任务内触发均能在原任务路径中找到受阻节点、处理入口和处理后去向。

6. 更新 `§8` 附录的栏目名称和写法：

   - 将“知识缺口”替换为“设计依据与适用边界”。
   - 固定记录：本次设计决定、支持该决定的输入或知识依据、正文落点。
   - 对不复用未被证明的现有能力，说明本次采用的体验承载和依据。
   - 不使用“待确认”“知识缺口”“未完全证实”等表述替代体验决定。

#### 输入、输出及判断条件

- 输入保持现有正式输入协议和可选 UXB 输入方式。
- “任务交互影响预判”只消费本轮已提取的任务、规则、状态、异常、现有承载信息和必要知识。
- 输出保持现有 `§0-§8` 结构和 Markdown 先行、JSON 单向投影规则。
- 任务内触发、规则分支和复用交接只在证据满足时进入正式输出。

#### 上下游依赖

- 不新增对特定上游文件名、需求基线字段名或下游 Skill 的硬编码依赖。
- 不改变 Context JSON 结构、页面规格交接或下游消费方式。

#### 异常和边界处理

- 当前节点可修正的限制，继续使用当前节点处理并说明继续动作。
- 已证明存在后续处理任务且当前可进入时，输出原任务到后续任务的转接。
- 已证明限制存在但没有可处理路径时，输出限制结果和用户可见反馈。
- 单选、多选、预填、自动回流、跳转页、配置页、审批节点等信息只有在输入或业务知识证明时进入方案。

#### 修改后的预期行为

蓝图在不改变既有骨架的前提下，将需求中的任务起点和交互分支稳定转换为流程与页面方案。复用页面既能保留当前页面应提供的入口，也不会展开复用能力内部交互。

#### 不允许承担的职责

- 不审查、补全或推断业务需求。
- 不创建新的待确认清单、候选方案机制或 UXB 分析阶段。
- 不因任务内触发检查而为每个任务生成被动入口。
- 不将 JSON 作为前置推理步骤或反向约束 Markdown。

### 5.2 `.claude/skills/experience-blueprint/references/output_structure_guide.md`

#### 当前职责

定义正式蓝图的章节结构、流程节点写法、页面承载要求和附录记录方式。

#### 具体修改

1. 在 `§2` 交互流程总览中补充规则分支的正式写法：

   - 已确认规则分支改变用户操作对象、候选来源、可见信息、提交内容或处理结果时，在对应角色路径中写出分支。
   - 每个分支标明触发条件、用户处理对象、处理动作和结果。
   - 仅改变说明文案的规则在对应节点保留说明，不拆分为独立路径。

2. 在 `§3` 与 `§4` 中补充节点承接要求：

   - `§2` 已出现的交互分支，在对应主流程或次流程中说明具体对象、候选来源、用户动作、系统响应和下一步。
   - 任务内触发在原任务受阻节点说明限制、影响、处理入口与处理后去向。

3. 在 `§6` 页面 / 弹窗 / 抽屉设计中补充承载要求：

   - 规则分支导致对象类型、候选来源、可见信息、提交内容或处理结果变化时，页面写明条件内容或条件交互。
   - 当前页面使用复用组件时，写明入口、当前页面展示的选择结果和提交后的数据；复用组件内部结构继续不展开。
   - 当前页面进入复用能力时，写明入口、已知输入、返回结果或结果承接；复用能力内部页面继续不展开。

4. 在 `§8` 中将“知识缺口及影响模块”替换为“设计依据与适用边界”，并使用以下顺序记录：

   1. 设计决定。
   2. 输入事实、现有模式或设计知识依据。
   3. 正文落点。
   4. 适用边界：当前方案承载什么，复用能力或组件承载什么。

5. 保留 `§8` 的设计准则消费和上游承接追踪规则，不改变章节编号、表格字段或知识记录范围。

#### 输入、输出及判断条件

- 输出仍只写一套确定的交互方案。
- 规则分支的展开以已确认事实为条件，不以领域名称、关键词或案例套用为条件。
- 设计依据只记录已影响本次方案的来源和决定。

#### 上下游依赖

- 不新增上游输入字段、下游消费字段或输出文件。
- 不修改 JSON 投影规则。

#### 异常和边界处理

- 规则未改变用户可见交互时，不要求新增页面、节点或分支。
- 业务能力事实缺失且会影响正式方案时，沿用主 Skill 的停止规则；不在 `§8` 作为待确认项继续生成。

#### 修改后的预期行为

正式蓝图中，关键规则分支可被设计师和后续 Agent 从流程追溯到具体承载面；设计依据可读，但不再表现为未关闭问题。

#### 不允许承担的职责

- 不新增页面方案结构。
- 不改变现有主流程、次流程、异常、状态、页面和父级承载页的输出深度。
- 不将复用组件或成熟基座内部交互重新设计为本期页面。

## 7. 红线

1. 只修改本实施文档列出的两个 Skill 文件和两个 `spec/2026-08-05` 文档。任何其他文件变更都不属于本次任务。
2. 不删除、缩减、替换或重写现有角色任务、状态异常、父级承载页、页面设计、选择形态、Markdown 先行、JSON 单向投影和生成前覆盖规则。
3. “任务交互影响预判”只作为既有路径组装的前置输入；不新增正式章节、Context 字段、JSON Schema、校验脚本、独立文件或第二套分析流程。
4. 不将权限、审批、角色、功能、订单、人员或任何领域对象写入通用规则示例或固定分支。
5. 任务内触发必须建立在本轮输入或已读取业务知识证明的限制和处理任务之上；不得因常见场景、类比或关键词生成入口、跳转、申请、配置、预填、自动回流或恢复能力。
6. 规则分支只有改变用户操作对象、候选来源、可见信息、提交内容或处理结果时才展开。只改变说明文字的规则保持在对应节点，不新增流程、页面或章节。

8. 不因“复用”推断能力存在。具体入口、配置、审批、编辑、选择、返回、预填或自动处理只在输入或业务知识证明后写入。

10. 不改动知识消费指南、Context Schema 和脚本；不得增加脚本语义检查或将语义判断交给脚本。
11. 不为压缩文案删减条件、对象、状态、结果、异常、边界或交接关系。

## 8. 注意事项

1. 修改前记录当前两个 Skill 文件的章节和规则位置，修改后核对原有主链仍存在且顺序不变，只在路径组装前增加预判。
2. “按需读取”“必要时参考”等抽象表达不得作为本次新增规则的执行条件。新增内容应写清检查对象、成立条件、正式落点和停止位置。
3. “完整”“充分”“合理”等词只能描述目标，不能作为生成前覆盖门禁的唯一条件；门禁应检查可观察的任务、分支和承载落点。
4. 预判未命中任务内触发时，主流程保持现有主动入口或状态后入口，不因未命中降低流程深度。
5. 当前材料未证明选择数量时，流程只写已证实的选择对象、候选来源和提交结果，不补写单选、多选、默认值或选择规则。

7. 文档写入和修改后使用 UTF-8 读取检查，确认中文正文未出现乱码。

## 9. 验收方式

### 9.1 规则与结构检查

### 9.2 正常案例验证

使用一个同时包含多个角色、主动入口、状态结果入口、规则分支和复用能力的正式输入生成蓝图，检查：

- 每个核心角色任务仍有完整路径和承载面。
- 规则分支改变交互时，流程与页面均可找到对应落点。
- 当前页面入口、复用能力和组件复用的职责没有混写。
- `§8` 能看到设计决定、依据和正文落点。

### 9.3 任务内触发案例验证

使用一个已明确“用户在原任务中遇到限制后，可进入后续处理任务”的输入生成蓝图，检查：

- 总览从原任务受阻节点开始，不改写为单独的模块主动入口。
- 流程写明限制、用户需要知道的信息、可执行处理入口和处理后去向。
- 页面或节点只使用已知上下文；未出现自动预填、自动回流或未证明跳转。

### 9.4 分支与复用边界验证

使用一个已明确包含两种或以上对象范围、且各范围会改变候选来源或提交内容的输入生成蓝图，检查：

- 每种范围均有对象、候选来源、动作和结果的交互承接。
- 未明确的选择数量、默认值或自动处理没有被补写。
- 当前页面可提供进入复用能力或组件的入口；复用能力和组件内部页面结构未被生成。

### 9.5 回归检查

使用一个不含任务内触发、也不含影响交互的规则分支的输入生成蓝图，检查：

- 正常主动入口路径保持现有输出深度。
- 不生成无事实依据的被动入口、额外页面或冗余异常流程。
- Context 仍是 Markdown 冻结后的单向投影，且不修改 Context Schema 或脚本。
