# Experience Blueprint 最小补强实施文档

## 1. 背景

Experience Blueprint 已能从正式输入输出流程、异常、页面与状态方案，但近期测试显示三个明确缺口：

1. 流程推理默认用户从模块或页面主动进入，遗漏用户在执行原任务时被动触发后续任务的场景。
2. 成熟外部能力的引用缺少“能力已被证实”的前提，可能将复用关系写成未被证明的具体配置能力。
3. 正式蓝图保留 `§8 待确认问题`，使业务未关闭信息、体验决定和外部复用细节混在同一正式产物中。

现有知识消费机制具备正确职责划分，但需要明确业务知识和设计知识的读取触发与停止条件，避免遗漏必要知识或扩大为全量阅读。

## 2. 目标

本次修改完成后，Experience Blueprint 应：

- 在既有流程结构中识别主动入口、任务内触发和状态后触发三类任务起点。
- 对已被确认存在的后续处理任务，确定受阻时应说明的信息、转接入口、可传递上下文与后续去向。
- 仅引用业务知识能够证明的既有能力，不将复用关系扩写为未被证实的页面或操作能力。
- 不在正式蓝图中输出待确认问题。
- 在不重构知识消费机制的前提下，明确知识读取的触发条件与停止条件。
- 通过加粗流程字段提升正式 Markdown 的扫读体验。

本次不处理：

- UXB 的职责、规则、文件、产物或调用方式。
- PRD Review 的职责、规则、文件或输出。
- Experience Blueprint 的业务事实提取范围、主流程分类、页面设计结构、ASCII 草图规则或下游交接。
- 现有其他领域专属规则的泛化、删除或重写。
- 未被正式材料或知识证明的产品能力补全。

## 4. 实施策略

### 4.1 保持现有主流程

保留蓝图现有的“读取正式输入 → 读取必要知识 → 形成确定方案 → 输出 Markdown → 生成 JSON 投影 → 校验”流程。

本次只在既有的流程总览、节点展开、异常与阻断、知识消费、输出结构和 Context 投影位置补充明确动作。不得新建第二套体验分析阶段、UXB 依赖或候选方案机制。

### 4.2 任务内触发的处理关系

对每个已识别任务，在现有流程总览推理中确认其入口来源：

1. 主动入口：用户主动进入模块、页面或功能。
2. 任务内触发：用户执行原任务时遇到可处理限制。
3. 状态后触发：用户看到状态、结果或提醒后继续处理。

当任务内触发成立时：

1. 明确原任务、受阻时机和限制类型。
2. 判断限制能否在当前处修正；能修正时，不创建无必要转接。
3. 只有已确认存在后续处理任务且当前系统支持进入时，定案转接入口或引导。
4. 只传递系统已确认的任务对象、范围、来源或状态；无法证实时不写自动预填或自动回流。
5. 说明处理后用户应回到原任务、重新发起还是查看处理状态。

### 4.3 知识消费的处理关系

保留“正式输入是本轮业务事实来源”的现有边界。

- 当需要证明既有入口、父级承载页、成熟基座输入输出、返回位置或状态语义时，读取对应业务知识完整规则块。
- 当需要确定入口与导航、信息层级、表单填写、状态反馈、异常恢复或任务回流时，读取对应设计准则或交互模式完整章节。
- 证据已足以支撑当前设计决定后停止；不扩展到整个业务域或全部设计知识。
- 业务知识不能覆盖正式输入已确定的新增、修改或移除事实。

### 4.4 正式产物的处理关系

正式 Markdown 只包含已经确定的交互方案。

- 业务信息缺失且会改变交互方案时：停止本轮正式生成，并明确缺少的信息和影响。
- 体验取舍可由设计判断解决时：直接输出唯一确定方案。
- 成熟外部基座未变更时：在流程中作为复用引用说明，不生成页面方案，不输出待确认问题。

JSON 仅投影冻结后的 Markdown，不新增推理、事实或待确认事项。

## 5. 详细修改

### 5.1 `.claude/skills/experience-blueprint/SKILL.md`

#### 当前职责

定义 Experience Blueprint 的运行入口、输入读取、流程推理、页面方案、正式输出、自检和 Context 投影规则。

#### 具体修改

1. 在现有“交互流程总览”或其前置任务提取规则中，加入任务入口来源检查。
   
   - 对每个相关角色任务，检查其是主动入口、任务内触发还是状态后触发。
   - 不要求每个任务同时具备三种入口。
   - 不把页面名称、组件名称或领域案例写成固定答案。

2. 在现有“主交互流程”“次交互流程”和“异常与阻断流程”规则中，加入任务内触发的正向处理动作。
   
   - 当用户在原任务中遇到可处理限制时，写清原任务、限制原因、用户需要知道的信息、下一步处理入口和后续去向。
   - 可在当前处修正的限制，写当前修正方式与继续动作。
   - 已确认存在后续任务且支持进入时，写明确引导或入口。
   - 上下文只保留已被系统确认的对象、范围、来源或状态。
   - 未证明存在转接、预填、自动回流或恢复能力时，不写为事实。

3. 将流程节点字段格式改为加粗标签。
   
   - `用户动作`、`系统响应`、`用户需要知道`、`下一步` 在 Markdown 正文中统一使用加粗标签。
   - 保留现有字段语义和按需补充字段规则。
   - 页面设计、状态口径表和知识附录不强制使用该格式。

4. 删除 `§8 待确认问题` 的正式产物定义、写法要求和自检项。
   
   - 删除章节生成规则、字段模板、`§8` 自检项和与其相关的正式交接说明。
   - 将原本属于 `§8` 的三类情况改为明确分流：业务事实缺失则停止；体验取舍则定案；外部成熟基座则复用引用。
   - 调整后续章节编号和所有章节引用，确保不存在失效编号。

5. 收窄成熟基座的描述边界。
   
   - 复用引用必须写清已证实的输入、可执行动作、输出和返回位置。
   - 只有业务知识明确证明具体能力存在时，才可将该能力写入方案。
   - 不因“复用审批、复用外部系统或复用基座”推断存在配置节点、编辑表单、跳转页或自动处理能力。

#### 输入、输出与判断条件

- 输入保持现有正式输入协议，不新增对 UXB、PRD Review 或特定文件名的依赖。
- 输出保持 Markdown 正式蓝图与 JSON 投影；Markdown 不再包含 `§8`。
- 任务内触发仅在输入事实或已读取业务知识表明存在可处理限制时展开。
- 体验路径由蓝图定案；业务能力是否存在由正式输入和业务知识证明。

#### 上下游依赖

- 不改变上游输入协议。
- 不改变下游读取方式。
- JSON 继续是 Markdown 的单向投影；不得反向约束 Markdown 推理。

#### 异常与边界处理

- 缺少会改变任务转接、承载方案、状态语义或业务结果的事实时，停止受影响方案生成。
- 仅缺少成熟外部基座的内部页面细节时，写复用引用，不展开外部页面。
- 不得为了覆盖“任务内触发”而虚构后续处理任务。

#### 修改后的预期行为

蓝图能够覆盖用户主动进入和执行中被动触发的任务起点；正式产物只保留确定方案；复用边界基于证据；节点更易阅读。

#### 不允许承担的职责

- 不审查或补写业务需求。
- 不创建业务待确认清单。
- 不将 UXB 的分析阶段、筛选机制或产物迁入蓝图。
- 不新增领域专属固定分支。

### 5.2 `.claude/skills/experience-blueprint/references/knowledge_consumption_guide.md`

#### 当前职责

定义蓝图对正式输入、业务知识、设计准则和交互模式的消费边界与记录要求。

#### 具体修改

1. 在现有业务知识消费规则中补充四个明确触发条件：既有入口或父级承载页、成熟基座输入输出返回关系、既有状态语义、任务内触发所依赖的已有处理入口。
2. 对每个触发条件，明确读取目标为“当前主题的完整相关规则块”，不读取整个业务域。
3. 增加停止条件：当前设计决定已有足够证据时停止，不继续扩展检索。
4. 在设计知识消费规则中，将设计决定与知识类别对应：入口与导航、信息层级、表单填写、状态反馈、异常恢复、任务回流。
5. 保留现有知识来源记录机制；只记录实际影响方案的知识及其落点。

#### 输入、输出与判断条件

- 输入为当前蓝图已识别的具体设计问题。
- 输出为知识消费记录和被知识支持的正式方案。
- 没有具体设计问题或既有机制确认需求时，不触发额外读取。

#### 上下游依赖

- 不新增知识库目录、索引或脚本依赖。
- 不改变正式输入优先级。

#### 异常与边界处理

- 业务知识与正式输入冲突时，按现有冲突处理规则停止，不自行选择或改写事实。
- 知识库未证明能力存在时，不将其写入方案。

#### 修改后的预期行为

蓝图能读取必要知识并在证据充分后停止，避免全面读取、遗漏支撑或为引用而引用。

#### 不允许承担的职责

- 不将业务知识当作本轮新增业务事实来源。
- 不建立关键词机械路由。
- 不为知识消费增加独立分析产物。

- 外部成熟基座不完整时，按复用引用边界处理，不生成虚构页面。

#### 修改后的预期行为

#### 不允许承担的职责

## 8. 注意事项

1. 修改前先核对现有所有 `§8`、`open_questions`、章节引用和脚本断言，避免删字段后留下失效映射。
2. `§8` 删除后，原 `§9` 附录及后续引用必须同步编号；不得留下空章节或旧编号。
3. “任务内触发”是内部推理视角，不要求每个需求都新增一条流程。只有已确认存在可处理限制时才输出。
4. 当前处可修正的输入校验不应被强制改为跳转或新任务。
5. 外部基座页面未变更时，继续只在流程中引用；不得因为移除待确认章节而在 `§6` 补写外部页面。
6. 设计知识的“完整章节或模式块”是指已命中的单一主题，不等于读取所有设计准则或交互模式。
7. 结构脚本只验证格式和映射；任务入口、体验路径和知识证据仍由 Agent 进行语义判断。
8. 文案优化仅限字段标签加粗和移除失效章节；不得以阅读体验为由删减条件、对象、状态、结果或例外。

## 9. 验收方式

### 9.1 静态检查

- 搜索 Experience Blueprint 目录，确认正式输出规则、Schema 和脚本中不存在 `§8 待确认问题`、`open_questions` 或失效章节映射。
- 检查 `SKILL.md` 中任务入口来源规则不包含特定业务领域、上游文件名或硬编码页面名称。
- 检查知识消费指南仍以现有章节和职责为主，仅增加读取触发与停止条件。
- 检查流程节点模板中的四个字段标签使用加粗格式。

### 9.2 结构校验

- 运行 Experience Blueprint 现有 Context Schema 相关校验脚本。
- 验证 JSON Schema 不要求 `open_questions`，且 Markdown 与 JSON 章节映射一致。
- 对变更文件执行格式检查，确认无乱码、无失效链接、无章节编号跳号。

### 9.3 正常案例验证

使用一个包含主动入口、成熟外部基座复用、多个角色任务和状态反馈的正式输入生成蓝图，检查：

- 所有核心任务仍有流程与页面落点。
- 外部基座只作为复用引用，不生成未修改页面。
- 正式 Markdown 不包含待确认问题。
- 节点字段使用加粗标签。

### 9.4 任务内触发案例验证

使用一个用户在执行原任务时遇到已确认可处理限制、且存在已确认后续处理任务的正式输入，检查：

- 蓝图说明原任务和受阻时机。
- 蓝图说明限制原因、用户需要知道的信息与下一步。
- 存在后续处理入口时，输出明确转接。
- 仅传递输入已确认的上下文。
- 处理后去向明确，且不虚构自动回流。

### 9.5 边界案例验证

使用一个存在限制但没有已确认后续处理能力的输入，检查：

- 蓝图不虚构入口、跳转、申请、预填或恢复。
- 若信息缺失会改变方案，生成在正式产物前停止。
- 若只是外部成熟基座内部细节未知，蓝图保留复用引用，不展开、不提问。

## 10. 验收标准

以下条件全部满足才算通过：

1. 正式蓝图不再生成 `§8 待确认问题`，Context JSON 不再包含 `open_questions`，所有章节映射和脚本校验保持一致。
2. 蓝图能在正式输入出现可处理限制时，区分原地修正、明确转接和不可处理说明三种结果。
3. 蓝图只在后续任务和系统能力已被证明时输出转接、上下文传递或返回路径；未被证明时不写为事实。
4. 蓝图对成熟基座只描述被证实的输入、动作、输出和返回位置，不虚构具体配置能力。
5. 流程节点中的 `用户动作`、`系统响应`、`用户需要知道`、`下一步` 以加粗字段标签呈现，且不删除原有语义。
6. 知识消费仍保持最小必要：存在明确触发才读取，证据足够即停止；未出现全面读取业务知识或设计知识的规则。
7. 既有主流程、次流程、异常、页面、状态、父级承载页、ASCII 草图、Markdown 先行与 JSON 单向投影规则未被削弱。
8. 未修改 UXB、PRD Review、共享工作流、知识库正文、下游 Skill 或无关历史规则。
9. Context 结构校验通过；变更文件无乱码、无失效章节、无过时字段引用。
