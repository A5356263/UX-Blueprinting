## 1. 背景与目标

现有审核记录在「审核结论」中汇总问题，又在「场景审核」中展开同一问题、回复和状态。团队成员需要在两处来回查找，才能知道该回答哪一项。将问题、场景和产品回复放在同一处，保留按编号回复的方式。

验收目标是团队成员能直接找到待答项，产品回复不完整时能按原编号继续回答，产品明确本期不做时能关掉对应项。正式需求基线的精准度、覆盖范围、事实分类和来源追溯须保持。

## 3. 正式审核记录结构

```text
PRD 审核记录
├─ 项目、状态、审查输入
├─ 需求初识
├─ 审核结论
│  ├─ 业务事实补充
│  ├─ 待产品确认
│  ├─ 待体验定案
│  └─ 建议修改
└─ 你还需要补充什么吗？
```

- 保留顶部信息和需求初识五问。没有实际内容的分类按现行规则省略。「你还需要补充什么吗？」保留原提示及用户补充原文。
- 撤掉独立「场景审核」章节。将原场景内必要的触发条件、问题背景和可定位依据移入对应条目，只保留支持理解、作答和溯源的内容。
- F 项保留编号、适用场景或对象、事实和正式来源。E 项保留编号、适用场景和待做的体验判断。建议修改保留编号、具体改法和依据。三类均不要求产品逐项回复，不计入待确认状态。
- Q 项使用「编号 · 场景 · 问题主题」标题。同组多个独立决定使用有序子项，沿用原有顺序。一个子项对应一个可独立回答和关闭的业务决定。

## 4. 产品回复与复核写法

1. **首轮**：在问题或对应子项下写「产品回复：待回复」。根据需要展示问题上下文，不在其他章节重复呈现。
2. **明确答复**：在对应编号和子项下保留产品原话，用「产品回复（已确认）」表达复核结果，省去单独的「关闭状态」「关闭依据」「问题组状态」及重复的「产品明确确认」。仍按现行规则逐项判断，并保留文档级状态。
3. **回复不完整**：保留原问题和已有回复，在对应子项标「仍待确认」。会话按原编号只追问仍未关闭的决定。组内其他已关闭项仍可辨认，任何阻断项未关闭时不生成基线。
4. **产品明确本期不做**：保留原问题、编号和原回复，在对应项或明确覆盖的多个子项下简记「不属于本期」，按现行关闭依据处理。基线只记录已确认的范围决定。若复核发现问题本身不成立，沿用现有「问题移出记录」规则，保留原编号、依据和来源。
5. **补充信息**：沿用现行规则保留用户原文，复核受影响的原问题，以及相关的 F、E 和建议修改。新问题按现行编号规则追加，既有编号和子项不重新排列。根据现有来源规则记录依据。

## 6. 验收样例

- **初审输出**：问题、场景和回复位置在同一处。编号和各子项清晰可见，记录使用标题和列表。
- **部分回复**：用 Q-002 的两个决定验证只回复其中一项时，另一项保持待确认。下轮只追问未答项，且不提前生成正式基线。用 Q-008 验证「撤销后不再授权」不能自行扩写成「审批任务立即终止」。
- **本期不做**：用 Q-007、Q-009 或 Q-010 验证产品明确排除后，按原编号记录回复和范围结论，不再追问未交付能力的规则，也不补写状态、责任人或实现方式。
- **基线对照**：用同一份 PRD、正式知识和产品回复，核对新旧记录转写出的业务事实、条件、例外、范围、体验事项及来源。覆盖 F、E、复核新增的 Q-011，以及一个多子项问题。以原始证据为准，不保留旧输出中未经确认的推断。
