# 子管理员双重权限范围的体验处理

## 1. 知识讨论背景

诊断咨询中讨论了子管理员同时承载"自身用户"和"管理者"两个角色的体验问题。核心发现：子管理员的"自身权限范围"和"可对外管理权限范围"共享同一套组织×应用的配置边界，且存在严格子集关系——可管理范围 = 自身权限范围 ∩ 超管配置的管理上限。子管理员不能授予自己不具备的权限。当前系统在三个场景下存在信息不可见问题：授权受阻原因不可区分、自身权限变动静默影响管理能力、"先有权限才能授权"规则对用户不可见。

## 2. 候选知识

### 2.1 业务规则

- 子管理员可授予他人的权限，不能超过自身已拥有的权限范围。
- 子管理员授权受阻有三个独立层级：组织管辖范围外、应用管辖范围外、自身无此权限。
- 超管修改子管理员自身权限时，会连带影响其对下级的授权能力。

### 2.2 体验原则

**授权受阻原因必须可区分。** 子管理员在授权界面选不了某个权限时，系统应区分三种卡点并给出不同提示：

- 超出组织管辖范围 → "该成员不在你的管理范围内"
- 超出应用管辖范围 → "该功能不在你的管理范围内"
- 自身无此权限 → "你需要先拥有此权限，才能授予他人"

**前置约束规则必须可见。** 在子管理员授权页面常驻展示规则说明，不弹窗、不阻塞：

> 你可以授予的权限，不能超过你自身已拥有的权限范围。

**权限变更的连锁影响必须主动通知。** 超管修改子管理员自身权限后，子管理员进入管理页时应看到受影响的功能列表：

> 你的权限已更新。以下功能将不再出现在你可授权的范围中：{功能名列表}。

三个改动不修改权限模型本身，只改信息呈现和提示策略。

## 3. 影响范围

- 变更类型：新增
- 影响业务域：权限管理
- 影响对象：子管理员授权界面、受阻提示文案、权限变更通知
- 建议更新位置：`knowledge/raw/业务/权限管理/`（可新建体验原则文件，或补充到现有页面载体语义文件中）
- 处理建议：新增

## 4. 不确定点

- [QUESTION] 子管理员自身权限变更后，对已授权下级的连锁处理策略待确认——是自动收回下级的对应权限，还是仅标记不生效但不自动收回。这会影响通知文案和后续体验设计。
